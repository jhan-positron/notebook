## Short version

The user asked whether changing the K layout to VNNI in PR 4424 could affect the FPGA attention path. A 300-agent trace found exactly one production code path that reads K bytes out of host pages for the FPGA, gof::populate through k_head_fn, and the PR rewired that callback to gather each token's row into caller scratch, so no functional impact was found. What stays open is the cost of that gather (unmeasured), the absence of any FPGA run at the PR head or against the `main` base, and the fact that no CI lane has ever run the VNNI build on an FPGA.

## Current state

Verified facts (each survived three adversarial verifiers, citations at ff680c8020):

- One consumer. The only production code that reads K bytes from host pages for the FPGA is gof::populate through k_head_fn, and shuffle_k_entry indexes the returned row as a contiguous 128-element array [src/tron/gof.cpp:213; h/pos/hwattention.hpp:778-781]. The DMA reads the staging block only. The HBM format is outside the diff: h/pos, h/libpos.hpp, lib, fpga-reg and h/tron/hardware are unchanged between c7844ca2ce and ff680c8020.
- The rewiring. Under the layout gate the lambda calls get_k_row into caller scratch and returns the scratch. Otherwise it returns the old in-page pointer [h/tron/scheduler/full.hpp:2644-2660]. gof::populate allocates the scratch [src/tron/gof.cpp:203]. gather_row is tested bit-exact as the inverse of the store for every token of a page [t/t_k_vnni_layout.cpp:126, 394].
- Gate consistency. A slot becomes a hardware slot only when its geometry equals hardware_attention_geometry.kv exactly [h/tron/models/kv_cache.hpp:404-416]. The staging lambda and the K store cannot disagree on the layout. 64-dimension heads (gpt-oss) stay row-major on both sides.
- Completion and ordering unchanged. populate's callers still require all four tokens complete before reading. The shared block save marks tokens complete only after every helper has left the window. Masked stores never write another token's lane.
- Page copies and relocation. Whole-page copies are one memcpy. Partial ranges move token by token with gather and scatter [h/tron/models/kv_cache.hpp:2099-2117]. Page relocation rebuilds page_info through the same factory.
- What changes in an FPGA run: the CPU-scored share (positions below the engagement point, the tail not yet in HBM, sliding-window layers) uses qk_group or the VNNI AMX kernel, never the row-major dotter, and TRON_AMX_DISABLE=1 does not bring the dotter back [h/tron/models/self_attention.hpp:1574-1640]. Issue 4444 records this contract change.

## Gotchas & decisions

- The layout gate depends on head size only. kv_mul 4 is an AMX kernel condition, not a layout condition. A kv_mul 8 model (qwen-3-30b-a3b) stores K in the VNNI layout and scores every page with qk_group.
- In the option tree, the only leaf that gives pre-PR 3879 numerics inside an AMX-capable binary is TRON_AMX_DISPATCH=ON with TRON_K_VNNI=OFF and TRON_AMX_DISABLE=1. With TRON_K_VNNI=ON the kill switch runs the VNNI reader. With TRON_AMX_DISPATCH=OFF and TRON_K_VNNI=ON, cmake configure fails with FATAL_ERROR [src/tron/CMakeLists.txt:209-213].
- USE_HW_ATTN is an orthogonal axis. Unset, the FPGA scores query positions 127 and up on ingested models, and positions 0 to 126 follow the CPU tree.
- The gather reads 64 cache lines per token and KV head where the old path read 4. populate runs on the attention workers with a budget of 4 GOFs per job, and the forward thread drains the rest before logits, so the tail is inside TTFT [h/tron/models/model.hpp:3179-3188].
- The Workflow output file is a JSON object with keys summary, agentCount, logs, result. The result of this run was about 4 MB and had to be condensed to a per-finding table before reading.
