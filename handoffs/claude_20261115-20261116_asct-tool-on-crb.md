## Words used here

- **claude-agentsrv**: the podman container this Claude Code ran in, on the user's Linux dev server agentsrv (same home directory, same files).

- **Kernel**: one benchmark loop. It is not the Linux kernel.
- **ASCT read loop**: the function `my_read_no_nops_rep_64b` of ASCT's `bandwidth.c`. It loads 8 bytes of each 64-byte line, and ASCT counts 64 bytes for the line.
- **Injected NOPs (N)**: the ASCT option `--bw-fine-delay N`. For N above 0 ASCT runs an empty loop of N rounds after each load. This handoff also calls it the padded loop.
- **Old read, new read (`asmread`)**: the read loops of the user's own benchmark before and after the rewrite of 2026-11-13. Their numbers here are the values of 2026-11-15. They were not run again.
- **Line**: one 64-byte cache line. **L1, L2**: the 64 KiB and 2 MiB caches of one core. **SLC**: the 128 MiB system-level cache that all cores share. **Mesh**: the on-chip network between cores, SLC and memory. Mesh 0 serves CPUs 0 to 63 and mesh 1 serves CPUs 64 to 127.
- **64+56**: one thread on each of CPUs 0 to 63 and 64 to 119, 256 MiB per thread. **64+0, 0+56, 56+56**: the same with only the named count of threads per mesh.
- **ASCT total**: the sum of the per-thread rates that ASCT prints. **Lower bound**: all bytes of a process divided by the time of its slowest thread. The ASCT total is too high when threads finish at different times.
- **Long-latency miss**: a load that had to wait for its line (counter events `l1d_cache_lmiss_rd`, `l2d_cache_lmiss_rd`, `ll_cache_miss_rd`). **Prefetch counters**: events that count lines fetched ahead by the hardware prefetchers (for example `l1d_cache_hwprf`, `l2d_cache_hwprf`).
- **r**: L2 refills per line (`l2d_cache_refill`), the share of lines that enter L2 from the SLC.
- **Probe build, dietperf**: ASCT's benchmark binary built with the flag `USE_PROBE`. Its built-in counter code (dietperf) reads core counters for the measured phase without root.
- **P-A1, D-A2, R-A3, P-A4, P-A5, P-B1, P-B2, P-B3, R-M1, R-M2**: names of the predictions (P), the descriptive fit (D) and the rules (R) that the session wrote down before the data. The table in "Results" states each one.

### Answers given in chat only (requests 1, 2 and 4)

Typical usages of ASCT, as given on 2026-11-15. On CRB only the commands without a benchmark load ran (`version`, `help`, `--dry-run`, `report system-info`, `view`, `diff`, `config`).

```bash
source ~/asct/asct_venv/bin/activate   # once per shell

asct report system-info
asct run memory -o runA                # all 7 memory benchmarks (needs root or preallocated huge pages)

asct run all ^storage ^long-runtime    # ^ excludes a name or keyword
asct config save memory --config-file my.json
asct run memory --config-file my.json -o runB
asct view runA                         # reprint a past run
asct resume runA                       # finish an interrupted run
asct diff runA runB                    # the first folder is the baseline
```

## Gotchas and decisions

- **`asct run` cannot be used on CRB.** Its one-core benchmark is fixed to the last CPU of node 0, which is the isolated CPU 127. Its whole-machine benchmark uses all CPUs. Both depend on a benchmark that needs huge pages, and CRB has none free.
- **The method that works without root.** Start ASCT's benchmark binary directly, with the command line that the front end builds: `numactl --membind 0 ~/asct/asct_venv/bin/loaded-latency-asct-sve.bin --duration D --delay-seconds 0 --bw-cpu C [--bw-cpu C ...] --bw-buflen BYTES --bw-fine-delay N --bw-write=0 --bw-cacheline-bytes 64`.
- **Core counters without root.** Build the probe variant from the inner tarball with `-DASCT -DUSE_PROBE -DHAS_SVE -march=armv8.2-a+sve`. Set `DIETPERF_PMUv3` (a comma list of raw event codes, at most 6 plus `cpu_cycles` per run in this work) and `DIETPERF_OUTDIR`. Create the output folder before the launch: two threads that create it at the same time make the binary exit with code 17.
- **ASCT's total is too high when threads finish at different times.** Give the lower bound beside it.
- **`asct --version` is not valid.** The command is `asct version`.
- **The permission system refused `sudo -n perf stat -a`.** The session had read the user's request for mesh counters as the approval, and had announced the plan at 12:41. That was not enough. Ask the user for an explicit approval of a root command before planning runs that need it.
- **Defect in `run_chip.sh`.** The function `one` used the variable `r` for the count of runnable tasks, and steps LAY and MIX use `r` as the process number. 8 result files were overwritten. The variable is now `rq`. The analysis merges the first folder and the rerun folder, so these cells have 3 or 4 processes.
- **Rebuilding from the raw folders overwrites inputs.** `analyze.py`, `facts.py` and `notes.py` write `asct.json`, `facts.json` and `notes.json` in Xa. Only the `report.py` command with `<OUT>` is safe to repeat. The full chain, run from Xa, is: `python3 analyze.py asct.json <the five result folders>`, `python3 facts.py asct.json baseline.json facts.json`, `python3 notes.py facts.json baseline.json notes.json`, `python3 report.py facts.json baseline.json notes.json <OUT>`.
