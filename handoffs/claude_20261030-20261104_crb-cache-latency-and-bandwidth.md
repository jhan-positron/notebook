## Words used here

- **CRB**: the Arm "Phoenix Reference Server" at 192.168.2.45 (hostname `ubuntu`, reached by ssh as user jhan). 128 Neoverse V3AE cores at a fixed 2.8 GHz, no SMT, 320 GiB DRAM, Ubuntu 24.04 with kernel 7.1.3-arm-agi-20260916. A shared machine. Only CPUs 0 to 119 may be used.
- **Neoverse V3AE**: the Arm core in CRB (part 0xd83, revision r0p2). L1 data 64 KiB 4-way and L2 2 MiB 8-way, both private per core.
- **CMN S3**: Arm's Coherent Mesh Network, the on-chip interconnect. CRB has two meshes, seen by Linux as the counter units arm_cmn_0 and arm_cmn_1. Each mesh is a 9 by 8 grid of crosspoints.
- **Crosspoint (XP)**: one router of the mesh. Devices attach to its ports.
- **Home node (HN-S)**: the mesh node that owns an address range. Each holds one 1 MiB slice of the mesh cache. There are 64 per mesh.
- **Mesh cache, SLC (System Level Cache), slice**: the 128 MiB cache that Linux reports as L3. It is 128 slices of 1 MiB, one per home node.
- **Chiplet**: as the report defines it, one mesh with its 64 cores, its 64 slices and 5 of the 10 DDR5 channels. CPUs 0 to 63 are on mesh 0 and CPUs 64 to 119 on mesh 1.
- **Proxy slice**: a slice on the core's own mesh that keeps a copy of a line whose home node is on the other mesh.
- **Pair port**: cores 2k and 2k+1 share one crosspoint port. Arm's CAL2 block is the documented mechanism. No document confirms it for CRB.
- **Fresh chain**: a random pointer chase walked exactly once. The V3AE core learns a repeated miss sequence and prefetches it, which hides the true latency.
- **perf_event_paranoid**: a Linux sysctl. At its default value 2 only user-mode core counters work. The mesh counters need the value 0 or root.
- **RUNNING marker**: the file /tmp/positron-perf.RUNNING on CRB. Jeremy creates it while his timed runs are on. Every script of this session stops if the file exists.
- **Jeremy**: a colleague (CRB account positron-perf) who runs timed latency blocks on CRB, announced in the Slack channel phoenix-crb. **Bill**: the requester, who also wrote an independent CRB evaluation. **Jesse Zhang**: the engineer who builds and runs code on the Asimov emulator. **Jibin Han**: the user, the administrator of CRB.
- **Asimov**: Positron's chip. One hemisphere has 5 DSUs (DynamIQ Shared Units, 2-core clusters) of Arm C1-Nano cores, a CMN S3 mesh with 5 home nodes, a 5 MiB SLC, OCM and a 16 MB scratchpad. **OCM**: 4 of the 16 SLC ways per home node locked by firmware, 5 regions of 256 KiB, reached through /dev/ocm. **SPM**: the scratchpad, reached through /dev/asimov-spm, non-cacheable, aligned 8, 16 or 32 byte accesses only.
- **Emulator**: Jesse's cycle-exact model of Asimov. One second of chip time takes about 46 minutes of wall time.
- **codex**: the user's other AI agent. It reviewed crb/plan-2026-11-02.md four times.
- **homelat**: bench/homelat.c, the root-only tool written on 2026-11-01. It flushes and loads each cache line and reads the home-node counters to find the line's home, then times chains of lines per slice.
- **asm kernels**: hand-written aarch64 ldp and stp loops in bench/bandwidth.c (kernels asmread, asmwrite, asmcopy). The compiler's loops reach only about half of the L1 bandwidth.
- **Workflow**: the Claude Code multi-agent tool. Four workflows ran on 2026-10-30.
- **Artifact**: a page published on claude.ai. "Version N" is the publish count of one page.
- **Part 1 to 5**: the five parts of bench/run_sudo.sh, the root run script (1 self-test, 2 full slice matrix, 3 write counters, 4 cross-mesh write counters, 5 single-writer write path).

### One-core L1 read against the load-pipeline limit (asked 2026-11-04)

| Quantity | Value | Source |
|---|---|---|
| Potential, one core, L1 read | 134.4 GB/s | 3 loads x 16 B per cycle x 2.8 GHz [SOG, Table 3-13, page 23] |
| Measured, one core, L1 read (asm LDP q loop) | 132.7 GB/s | report, section "What 3 loads + 2 stores of 16 B per cycle means" |
| Ratio measured / potential | 0.99 (99 %) | computed in chat |

The potential is the core's load-issue limit: three load pipelines, each starting one 16 B vector load per cycle, so 48 B per cycle. The asm read loop reaches that limit within 1 %, so there is no higher potential to compare against (a 64 B line cannot be loaded in fewer than four 16 B loads).

## Gotchas and decisions

- Never report best-of-N for a first-touch test. The cross-chiplet "2 to 7 ns" claim came from taking the best of two fresh walks, which was the second walk after the proxies were filled. The first walk is 85 to 88.5 ns.
- The V3AE core learns any repeated miss sequence, including a fixed-order evictor. Use a new random order per repeat and time each chain once (--fresh in latency.c; homelat does this).
- Mesh counter reads must run on the PMU's CPU (CPU 0 for both meshes). Reads from another CPU are interrupts whose handler pollutes the counts. Group reads return the leader first.
- The plain "read" home-node event counts a line homed on the other mesh twice (once at the proxy, once at the home). Use the home-bound filter (hbt).
- Compiled loops reach only about half of the L1 bandwidth on this core. Use the asm kernels for ceilings.
- Placement matters more than thread count for DRAM: one thread per pair, spread over both chiplets.
- The report's source file must start with `<meta charset="utf-8">`, or the user's browser on the Windows W: drive shows mojibake. The artifact publisher adds the tag itself, so the defect shows only locally.
