## Words used here

- **TRON** (also tron): Positron's inference program (GitHub repo positron-ai/tron). The code was read in the checkout /home/jhan/workspace/tron at commit e6c53ba7 (branch main, 2026-09-23, the merge of https://github.com/positron-ai/tron/pull/4528). Every file:line below refers to that commit.

- **Decode** (generation): the phase that produces one new token per user per pass. **Prefill**: the phase that processes the prompt.
- **Projection** (matmul): multiplying the activations by a weight matrix. One read of the weights serves every user in the batch.
- **KV cache**: the keys and values of all earlier tokens of one user, kept so attention does not recompute them. **KV page**: a block of 64 key/value entries of one layer in host memory. **KV head**: one key/value head. In Llama 3 8B one KV head serves 4 query heads.
- **Attention worker**: one of the CPU thread-pool workers that run software attention. **kv_section**: one KV head plus a run of pages, the unit of work handed to a worker.
- **Ranged mask**: the per-pass table of which queries may read which token ranges. It keeps each query on its own user's pages.
- **Join**: the step that merges each worker's partial softmax state (running max, sum, weighted value) into one result per query head.
- **Minibatch**: a cut of one pass's queries that moves through the model layers as one unit. **Affinity label**: the tag given to each request's tokens during the scheduler's tree walk. **Grain**: a run of at most 8 tokens, the smallest unit the cut moves. **chunk_evenly**: the function that cuts the labeled grains into minibatches [h/tron/models/model.hpp:209-276].
- **Shard**: 1,024 tokens of one user's context whose keys and values live in one FPGA card's HBM (on-card memory). **hw_pass**: one attention command sent to one card over up to 4 of its shards.
- **llama plugin**: the hand-written model plugin (h/tron/plugins/llama.hpp). **Ingested** (generated) plugins: plugins produced by the ingest tool from a model definition. They pin the minibatch count to 1.
- **Perfetto**: Google's tracing tool. TRON emits Perfetto events.

## The answer (as given in chat on 2026-10-19)

TRON never runs attention one user at a time. Ben's slide 33 states the premise: "Weight matmuls: one read of the weights serves every request in the batch. Attention: each request reads its own KV cache, alone." The code confirms there is nothing to batch in attention, only work to spread.

CPU path, one decode pass with N users:

- The planner builds one page list per minibatch and KV head, ranked by the first query that can see each page, so the list comes out grouped by user [h/tron/models/model.hpp:2340-2393].
- It cuts that list into runs of pages per worker by cumulative estimated work, weighted by each worker's measured speed [h/tron/models/model.hpp:2719-2790]. The unit handed to a worker is a kv_section [h/tron/models/common.hpp:696-706].
- Each worker loops page-outer, query-inner, and asks the mask whether the query may read the page before any dot product [h/tron/models/self_attention.hpp:1500-1503]. On a private page only the owner passes. On a shared-prefix page every reader passes, and the page is visited once.
- A join merges each worker's partial softmax state into one result per query head [h/tron/models/self_attention.hpp:1134-1200].
- User parallelism is a by-product. A long context straddles several workers. Several short contexts share one worker.

Minibatch level:

- Each decoding user's new token gets its own affinity label [h/tron/scheduler/full.hpp:2387-2389].
- With the llama plugin, N decode users split into 2 minibatches, so CPU attention of one overlaps FPGA matmuls of the other [h/tron/models/model.hpp:245-249, h/tron/models/common.hpp:928-960]. Ingested plugins pin 1 minibatch [ingest/src/TronCpp.hs:262].

FPGA path:

- Shards are placed round-robin across cards at creation [h/tron/scheduler/full.hpp:2545-2583].
- One pass is one command on one card over up to 4 of its shards and the queries that share them [h/tron/models/model.hpp:2486-2700]. Independent decode users never share a pass. Users with a shared prefix can ride one command over the shared shards.
- All passes of a layer launch in one loop, and each card retires its own in order [h/tron/models/self_attention.hpp:676-685].

Insufficient data: the attention-worker count on a given server, per-step timing, the real overlap between cards, and (added 2026-10-21) the real minibatch sizes. A Perfetto trace of one 4-user decode pass on delphi-3bda would give all of them (the "Create minibatch" events give the sizes).

Section 4, added 2026-10-21, "What a minibatch is": a minibatch is a cut of one pass's queries that moves through the layers as one unit. It is neither Ben's "batch" nor a request. The cut has five steps: a label per request during the tree walk, grains of at most 8 tokens, a target count (128-query cap in the llama plugin, raised to 2 minibatches for latency hiding, the `--max-minibatches` flag, generated plugins pinned to 1), a greedy merge, and one `struct batch` per chunk.

Worked example from the mirror script (computed from the same rules as chunk_evenly, not observed in a TRON run):

| Case | Target count | Target size | Minibatch sizes |
|---|---|---|---|
| 4 decode users, 1 token each (llama) | 2 | 2 | 2, 2 |
| 6 decode users (llama) | 2 | 3 | 3, 3 |
| 1 decode user (llama) | 1 | 1 | 1 |
| 200 decode users (llama) | 2 | 100 | 100, 100 |
| 300 decode users (llama) | 3 | 100 | 100, 100, 100 |
| 1 prompt of 20 tokens (llama) | 2 | 10 | 8, 12 |
| 1 prompt of 300 tokens (llama) | 3 | 100 | 104, 104, 92 |
| 1 prompt of 20 tokens + 3 decode users (llama) | 2 | 12 | 16, 7 |
| 4 decode users (generated plugin, 1 minibatch, cap 1024) | 1 | 4 | 4 |
| 1 prompt of 300 tokens (generated plugin) | 1 | 300 | 300 |

The 300-token and the "prompt + 3 users" llama rows show the merge is greedy, not optimal. The mirror leaves out adjust_grains_for_partners on purpose. That function changes nothing in these cases.
