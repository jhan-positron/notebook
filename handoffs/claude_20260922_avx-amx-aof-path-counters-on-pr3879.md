## Short version

jhan asked for counters that tell how much attention work runs on the AVX, AMX and AoF paths of tron, and for a page named counter.html. The session verified the code with a 30-agent workflow, corrected two premises in the request, and wrote counter.html (a design page, four versions, published as a private artifact). No code was changed in tron. The 2026-09-24 session implemented the design (see the handoff for "counter.html toggle: env var vs build option").

Words used here: tron = the inference program. AVX = the CPU vector instruction set used by the software attention loop. AMX = the Intel matrix unit and the attention kernel that uses it (PR 3879, merged 2026-09-15). AoF = attention on FPGA (tron calls it hardware attention, switched by USE_HW_ATTN). KV page = a 64-token block of the key/value cache. Visit = one call of apply_page_tok, that is one (query token, KV page, KV head) triple. K token = one cached key that a query token scores. PR0 = pull request 4267, the page-share counters behind the build option TRON_PAGE_SHARE_COUNTERS. FUSE leaf = a value published through tron's stats file system. rdtsc = the CPU cycle counter instruction. Perfetto = the trace tool tron already supports.

## Gotchas & decisions

- Two premises in the request are wrong, and the page says so in sections 1 and 2. Prefill runs attention and the FFN for every prompt token, in chunks of 128 tokens per user per forward (TRON_PER_USER_PROMPT_CHUNK_LIMIT), so prompt 1024 is 8 forwards. Only the last chunk requests logits. The prefill counter is the largest one, not a useless one. A decode token has no single path: tron picks AVX, AMX or FPGA per visit and joins the parts, so the counter unit must be K tokens scored per path, with a per-token path-set table for the token view.
- jhan's clarification ("prompt tokens are given, so no attention or FFN") does not hold. The K and V of token i at layer L are a linear map of that token's input to layer L, which is the output of layer L-1 after attention and the FFN. Only at layer 0 do K/V follow from the token id. A known prompt saves only the logits projection and the sampling. Evidence cited on the page: full.hpp:2014-2030 (a prompt token without K/V becomes a token job with do_kv = 1), llama.hpp:656-700, context.cpp:48-50, doc/hw-kv-rules.md:4, and two measurements (110.9 query tokens per page visit in prefill on 2026-08-19, and time to first token at prompt 8192 on qwen-3-4b: 15.8 s AVX, 6.9 s AMX, 6.7 s cold FPGA).
- Same path in every layer holds only for uniform models (llama-3.1-8b, llama-3.3-70b, mixtral-8x7b, qwen-3-4b). It fails for gpt-oss-120b (sliding-window layers never use the FPGA, head size 64 excludes AMX), gemma-4 and EAGLE.
- Proposed hook sites at main 0a51385e95: the three return sites of apply_page_tok (AMX :1768, empty :1820, AVX :1852), the FPGA plan site (:600), five same-thread rdtsc timers. The 2026-09-24 plan-verification found the exact return lines are :1772, :1824 and :1856 (the design page cited the comment lines above them).
- The two judges split on gating: the engineering judge preferred the PR0 compile-time shape, the user-side judge a run-time environment variable with FUSE leaves. Section 9 (version 4) used hook frequency as the rule: per-visit hooks = build option, per-job or per-forward hooks = environment variable TRON_ATTN_STATS (exactly "1"), perfetto for values that already have a span. This rule was overridden by measurement on 2026-09-24.
