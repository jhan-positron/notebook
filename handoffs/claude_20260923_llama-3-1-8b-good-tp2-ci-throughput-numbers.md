## Short version

jhan asked whether the nightly CI value "llama-3.1-8b-instruct-good-tp2 @32u: 32.5 TPS, prefill 354 tok/s, TTFT 11569 ms" from 2026-09-23 is as expected. The answer is yes: it is +15.0 % over the night before, and our own A/B campaign of 2026-09-20 with only the AMX kernels changed measured +14.0 %. The session also found the 09-22 prefill rate that Slack did not print (220 tok/s), wrote the report page CI-AMX-row-20260923.html, verified it with an 8-agent workflow, and published it.

Words used here: TPS = decode tokens per second per user in the CI benchmark. TTFT = time to first token. Prefill rate = the configured prompt length divided by the mean TTFT (the CI's own formula). AMX = the Intel matrix unit and tron's attention kernel for it (PR 3879). tron = the inference program. rinzler = its server binary. systems_test = the CI harness repository (positron-ai/systems_test). Talos = the CI result store (http://talos:5000). delphi-3bda = the Intel CI machine. andoria-b1a3 = the AMD CI machine (no AMX unit). tp2 / tp4 = model split over 2 or 4 FPGA cards. p05 = the linearly interpolated 5th percentile. Kill switch = TRON_AMX_DISABLE=1, which turns the AMX kernel off in a build that has it.

## Gotchas & decisions

- The 09-22 Slack line lacked prefill and TTFT because the systems_test formatter at commit 7327184 printed only TPS for a row with no threshold. PR 227 in systems_test changed that and merged at 17:48 UTC on 09-22, after that night's run. The harness computed prefill on 09-22 anyway. Talos holds it. gemma-4 got timing that night because it has a placeholder goal of 1.00 TPS.
- "Prefill" in the CI is prompt length divided by mean TTFT (scripts/perf.py:396-397). With 8 users per engine, TTFT includes waiting behind other users' prompts, so it is the rate one user sees, not the engine's prefill throughput. State the claim as "TTFT-derived prefill rate".
- The two nights differ by 32 first-parent merges between 3faba6d0fd and 5cf65b9241 (31 besides PR 4505). Each package ran once, so the CI pair alone cannot isolate AMX. Our 09-20 campaign gives the AMX-only number.
- The AMX kernels reached the package because PR 4505 (deb preset gains TRON_AMX_DISPATCH=ON) merged at 21:08:26 UTC on 09-22 (merge commit 9276183ad3), and publish-deb run 35806901506 built main 5cf65b9241 at 01:35 UTC on 09-23. delphi-3bda installed it at 03:40:06 UTC. The AMX row ran 04:09 to 04:18 UTC. Our light compile check on delphi-3bda that night started after 05:00 UTC, so it did not overlap the row.
- A refuted explanation: PR 4516 (https://github.com/positron-ai/tron/pull/4516) only updates CI test-timing data that the server never reads, so it cannot explain the tp4 rises.
- Corrected memory: the kill switch runs at no-kernel speed on the canonical code (14.745 vs 14.650 tok/s), so a kill-switch on/off pair is enough to isolate AMX. The old "2 to 5 points slower" figure is retired.
- The tp4 rows run on 2 engines, not 4 (the page says so after the critic's correction).
- The workflow's result JSON in the task output is wrapped in a {summary, result} envelope. Read `['result']`. The Talos records were found by the verifier and refetched by the session with curl to talos:5000 (the talos:5174 web UI answers HTML only).
