## qwen-3-30b-a3b failure (open bug, needs a tron-side fix)

- Every run aborts on `TRON_ASSERT(!std::isnan(elt)): Encountered NaN logit
  at token 0` (SIGABRT, exit 134). Reproduced at tp2 in a 1-round diagnostic
  (`tron-perfetto-diag-qwen3-30b-tp2-20260809T1857Z`), so not tp4-specific.
- Trap: the harness marked the crashed draws `ok` with exit 0 — a draw is
  `ok` if the trace capture completes; the only journal symptom is
  `generate=None tok/s`.
- Ruled out with evidence: general infrastructure (qwen-3-4b and
  gpt-oss-20b — also an MoE GPTQ model — ran fine on the same binary),
  weight availability (loads from local cache), config mismatch (HF snapshot
  config matches the GPTQ weights config).
- Labeled hypothesis: the 30b's GPTQ quantization rules keep the MoE router
  (`mlp.gate`) unquantized in bf16 — a code path the working models never
  exercise; the symbolized crash stack shows the forward pass already
  producing NaN (`top_k_accum_t::insert<bf16>` via sparse
  `fill_logits_buffer`, `model.hpp:3182`). The model is marked
  production-supported (https://github.com/positron-ai/tron/pull/3409), so
  something between its validation and commit `12804a8`, or specific to this
  build path, broke it.
- Confirming measurement (not run): run the official deb-packaged runtron on
  the same weights, or bisect tron main back from `12804a8`.

## Gotchas & decisions

- The harness exports its install `lib/` as `LD_LIBRARY_PATH`; never put a
  Nix glibc there — it breaks system binaries invoked by the harness. Keep
  Nix runtime libs in a separate dir reached only via the patched
  interpreter/rpath.
- `pgrep`/`pkill -x runtron` do not match runtron (it renames its main
  thread) — known from the 2026-08-06 session; the v4 harness carries the
  path-based fix.
- Harness `status=ok` does not imply the model actually generated tokens;
  check `generate` tok/s in results.csv.
- delphi-3bda's nightly CI window starts 02:45 UTC; campaigns were scheduled
  to end hours before it.
