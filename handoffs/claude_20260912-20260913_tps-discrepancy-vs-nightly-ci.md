## Short version

Our 2026-09-11 CI-harness numbers were far below the nightly's because we sent all 8 users to one engine, and the nightly spreads 8 users over 4 tp2 engines (or 2 tp4 engines) that run FPGA attention. The session then re-ran the Friday test set in the nightly's per-engine layout on our half of delphi-3bda (campaign p0perf-20260913, branch head 544ca05c7a). Result: the FPGA-attention arm reproduces the nightly's TPS within 5%, and switching qwen to CPU attention with AMX would lower the nightly's reported TPS by about one fifth even though AMX gains 8% over the AVX path.

## Gotchas & decisions

- The fpga arm must set `TRON_AMX_DISABLE=1` too. With FPGA attention tron still scores positions 0 to 126 on the CPU, and without the kill switch that share takes the AMX path, which the nightly's main package does not have.
- The permission classifier denied reading `/etc/rinzler/instance-1.env` and `/opt/positron/user/config.env` on delphi-3bda as a production read. The user pasted the file instead. It is archived as platformd-instance-1.env.txt in the results folder. Production sets `TRON_USE_SPECULATION=0` and does not set `USE_HW_ATTN`.
- tron's default log level is debug when `TRON_LOG_LEVEL` is unset (`src/system/spdlog.cpp`), so pinning debug in our launcher matches production.
- The Slack line's pass bar comes from the static table in `scripts/system_ci.py` `get_goal()`, not from `thresholds/system_ci_perf.yaml`. The yaml feeds a separate evaluation.
- Review agents that execute a campaign script locally can write into the shared log on NFS. The instance check must be anchored to the script path, and stale lines must be removed before the summary reads the log.
- A Monitor watch on the status file fires on every cell. Filter to phase changes, repetition starts, failures and the end marker.
- combine.py pools per-engine samples with population sd (`statistics.pstdev`). The report's cell sd is the sample sd over repetitions. The two labels were separated in the report after the verification.
- The CI harness sends real chat prompts cut to 1024 tokens. The server counts about 977 prompt tokens after the chat template. runtron sends exactly 1024 synthetic tokens. Same in every arm, so comparisons hold, but absolute TTFT differs between the two tools.
- The nightly's "anomalous tps" diagnostic lines are not proxy artifacts alone. One client-side burst sample appeared in our FPGA cell without any proxy.
- The 5% fidelity threshold for "reproduces the nightly" was chosen while writing the report, not before the campaign. The report says so.
- Decision: run on our half only with the nightly's per-engine load (2 users per tp2 engine, 4 per tp4 engine) rather than take the whole machine. Decision: add the fpga arm so that the AMX numbers link to the nightly's own numbers on one binary.
