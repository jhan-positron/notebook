- **Proxy line**: a copy, kept on the reader's own mesh, of a line whose home is on the other mesh. Arm calls the proxy role LCN and the proxy lines' share of a slice LCC.
- **Occupancy limit**: a register field that caps the share of a slice that home lines or proxy lines may fill. The deck and the old report text call it the "capacity partition".
- **Fresh chain**: a random pointer chain that is walked once, so the core's prefetcher cannot learn it.

### What Codex's review changed

Codex made eight points and the session accepted all eight after checking them. None changed a measured number. They changed which statements count as measured.

- No fixed half-and-half split of a slice is shown. Home lines and proxy lines share a slice under two occupancy limits that both reset to the maximum (CMN S3 TRM, pages 55, 335 to 336, 1038 to 1039).
- The 128 MiB of distinct data for the whole chip, and the duplication of shared lines, are hypotheses.
- "Half of every buffer" fails for small buffers. 20.0 % of 65 B buffers that start at a line boundary have both lines on one mesh.
- The 16-line pattern does not repeat. Root can read physical frames from /proc/self/pagemap.
- The whole-chip read of 1.38 TB/s combined 32 readers on mesh 0 and 8 on mesh 1.
- Local service does not mean a copy at every level. The mesh cache is exclusive of L1 and L2 for data lines.
- The write conclusion holds only for the tested stream.
- Both nodes on a crosspoint are homes. That does not prove that every node serves proxy lines.

### Answers given only in chat

- **Slide 4 row labels are footprints.** The rows use 32 KiB, 1 MiB, 8 MiB and 1 GiB per thread. The 73 GB/s write at 8 MiB is a DRAM write-path number: 0.75 misses out of 0.76 write requests per line and 0.76 memory requests per line.
- **67 GB/s read at 8 MiB.** The slices served 0.83 of the lines and the core's own L2 the other 0.17, so the mesh cache delivered about 55 GB/s (est., 0.83 times 67).
- **73 GB/s against 63 GB/s at 1 GiB.** The core issued 1.52 bus writes per line at 8 MiB and 2.00 at 1 GiB (results/sudo-20261102T211150Z/writepath.csv). Hypothesis: rewriting the same 8 MiB of pages gets more hits in the open rows of the DRAM and in the TLB (the core's cache of address translations). A write sweep over footprints from 8 MiB to 1 GiB with the memory-controller counters would test it. Not run.
- **89.5 GB/s writes at L1 and L2 stay in the core.** Two stores of 16 B per cycle at 2.8 GHz give 89.6 GB/s. 120 threads reached 10.7 TB/s, which is 24 times the measured DRAM write peak of 447 GB/s.
- **Write-back.** The L1 and L2 caches are write-back: a changed line stays in the cache until it is evicted. A stream of full-line writes above L2 uses write streaming, which does not allocate the lines in L1 or L2. The counters showed 0.000 L1 write-backs and 0.001 L2 write-backs per line during the 8 MiB stream.
- **Pipelines.** The core has three load pipelines and two store pipelines, 16 B each. Loads only: 134.4 GB/s by arithmetic, 132.7 GB/s measured. Stores only: 89.6 GB/s by arithmetic, 89.5 GB/s measured.
- **One core writes DRAM at 63 GB/s and reads it at 30 GB/s.** Hypothesis: a streaming write completes at the home node, and a read completes only after the full 148 ns. No counter confirms it. A per-core write sweep against crosspoint distance would test it. For the whole chip the order is reversed: 533 GB/s read, 447 GB/s write.
- **Counts.** One home node holds one slice (1 MiB, est.). One crosspoint with home nodes holds 2 home nodes. One mesh has 32 such crosspoints and 64 home nodes (64 MiB). The CRB has 128 home nodes (128 MiB).
- **How the test finds the home of a line.** bench/homelat.c tries every node id from 0 to 0xffff on each mesh's counter device and finds 64 home nodes per mesh. For each line it flushes and loads the line 256 times and reads each node's "home-bound requests received" counter. The node whose count rose by at least 192 is the home. A chain for one node uses 2,048 lines of that node only.
- **How core positions are known.** They are inferred. bench/fitpos.py tries each of the 70 core-port crosspoints and fits latency = base + slope times hops. For core 0 the best fit is mesh 0, crosspoint (1,2), with 2.86 ns per hop and a fit error of 0.90 ns (root-mean-square). Cores 120 to 127 have no latency data and no position.
- **What the mesh map shows.** Home nodes appear as "HN-S" on port 0 with two device lines. Rows 1 to 4 have them in columns 1 to 7 (28 crosspoints). Row 5 has them in columns 2, 3, 5 and 6 (4 crosspoints). Core ports appear as "RN-F" with no CPU number.
