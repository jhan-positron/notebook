## Short version

The nightly CI on delphi-3bda showed the AMX benchmark row rise from 28.3 to 32.5 TPS between 2026-09-22 and 2026-09-23. jhan asked whether any of the other merges between those two runs could also have moved decode or prefill speed. The audit of all 32 tron merges found that the AMX kernels explain almost all of the +15.0 % (our own same-code test on 09-20 measured +14.0 %), the AMD control machine moved by −0.3 % on the same two packages, and at most +0.29 TPS (+0.9 %) is left for the other 31 merges. The result is a report page with five charts and a merge-by-merge table.

## Words used here

- **TPS**: decode tokens per second per user, as the CI harness reports it.
- **TTFT**: time to first token, in ms. **Prefill**: prompt tokens processed per second, computed from prompt length and TTFT.
- **AMX benchmark row**: the CI row `llama-3.1-8b-instruct-good-tp2 @32u per machine`, 32 users, prompt 4096 tokens, 1536 generated tokens, 10 rounds, 320 requests. It is the one nightly row whose shape the AMX attention kernel serves.
- **AMX**: Intel Advanced Matrix Extensions. The tron kernels for it are compiled in only when the CMake option `TRON_AMX_DISPATCH` is ON.
- **nightly CI**: GitHub Actions workflow `system_ci_granite_rapids_72_rinzler_OCI.yaml` in repo positron-ai/systems_test, run on the machine delphi-3bda (Intel Granite Rapids). A second workflow "System CI (Rinzler 96-core system)" runs the same rows on andoria-b1a3 (AMD Genoa), which cannot run AMX and so serves as a control.
- **packages**: the tron Debian packages the two runs installed, `2026.09.18-3faba6d0` (09-22 run, no AMX kernels) and `2026.09.23-5cf65b92` (09-23 run, AMX kernels in). The version suffix is the tron main commit the package was built from.
- **tp2 / tp4**: a model split over 2 or 4 accelerator cards.
- **FPGA attention (HW attention)**: attention computed on the accelerator cards instead of on the CPU. It is on only for some generated ("ingested") models in CI.
- **same-package range**: for a CI row, the minimum and maximum over the nights that ran the older package. The 09-23 value is judged against it.
- **claude-box**: this container, `claude-agentsrv`.

### The #4534 hypothesis for the Intel-only tp4 jumps

- Before #4534, every timed wait incremented two shared atomic counters (`count_calls`, `count_waits` in `src/system/mwaitx.cpp`, lines 18, 19, 198, 200 at 3faba6d0).
- On Intel the wait uses RTM (restricted transactional memory) with a pause budget of 2048 TSC cycles (about 759 ns est.), so a 10 µs wait (`wait_for_layer`, `h/tron/models/common.hpp:950`) passed through the counter update about 13 times (est. from code constants). On AMD MWAITX the same wait updates them about 2 times (est.).
- Test that would confirm or reject it: rebuild with `-DTRON_MWAIT_STATS=ON` and run the 70b tp4 row alternating with the default build. Not done.

## Gotchas & decisions

- **The session name says "regression" but the row went up.** The title record is kept as is. The audit shows a gain credited to AMX.
- **`gh api .../jobs/<id>/logs` returns a 99-byte refusal** because of terminal escape sequences. Use `gh run view <run-id> --log` instead, then strip escapes with `sed 's/\x1b\[[0-9;]*m//g'`.
- **AMD 09-18 run 35302120794 was cancelled** and its rows are 20 to 45 % low. Exclude it from any AMD baseline.
- **"Outside the same-package range" is weak evidence** with 4 or 5 baseline nights: it happens by chance about 1 time in 3. The report's "clearly moved" rule requires the distance beyond the range to exceed the range width and the change to be at least 1 %.
- **#4516 "slice cost data" is CI unit-test timing data**, not a runtime setting. The morning page listed it as a candidate by mistake.
- **A 34-hour `journalctl` window on 3bda times out at 120 s.** Use windows of a few minutes around the engine start time from the CI log.
- **Node is not installed on claude-box.** The Playwright venv of session fcd18152 bundles Node v24 at `.../playwright/driver/node`, which runs the dataviz palette validator.
- **Python module named `numbers.py` shadows the standard library** (`statistics` imports `numbers`). The script was renamed to `calc_numbers.py`.
- **`gen_page.py` prints `len(page)` in characters**, so its "100,981 bytes" message understates the UTF-8 file size (101,477 bytes on disk).
