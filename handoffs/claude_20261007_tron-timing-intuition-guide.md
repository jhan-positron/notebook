## Words used here

- **tron**: Positron's inference program (GitHub repo positron-ai/tron). **runtron**: its command-line server binary used for test runs.
- **AMX**: Intel Advanced Matrix Extensions, the tile matrix instructions used by the attention kernel on the CPU. **AVX**: the AVX-512 vector path, the software loop the CPU uses without AMX. **AoF**: attention on FPGA, the configuration where the FPGA card scores the attention keys and the CPU keeps only the tail of 1 to 4 keys per page.
- **Decode step**: one forward pass that produces one token per user. **Prefill**: the forward pass over the prompt. **TTFT**: time to first token. **TPS**: decode tokens per second per user.
- **Page**: a 64-token block of the KV cache. **Visit**: one apply_page_tok call, the CPU attention work on one page for one KV head.
- **T1 to T5**: the attention-stats timers from PR 4596 (https://github.com/positron-ai/tron/pull/4596). T2 is attention busy time, T5 is join wait.
- **FUSE leaves**: the in-process stats files of runtron, read during a run to get per-layer timer values.
- **attnstats-20261002 campaign**: the 2026-10-02 runs on delphi-3bda whose results sit in /home/jhan/workspace/intel-AMX/exec/results/attnstats-20261002/. The page's per-layer numbers come from its `leaves/<run>/decode_like_layer_*` files.
- **delphi-3bda**: the Positron test server (Intel Xeon with AMX). Not touched in this session. **tp2**: tensor parallel over 2 devices.
- **kv_mul**: the ratio of query heads to KV heads. The AMX kernel gate needs a fitting shape.
- **CI harness**: the nightly test program that measures decode TPS. It measured a larger llama gain than lockstep runtron did.
- **Notion Scratch page**: https://app.notion.com/p/positron-ai/Scratch-3c3d132d3cfd80b38c47cc0f424f0511, a page holding one screenshot of a conversation about the gpt-oss time budget.
- **cairosvg**: the Python library used to render the SVG figures to PNG for a visual check.

## What the page says (key numbers)

The page did not run any test. Every number below is taken from earlier measurements, mostly the attnstats-20261002 campaign, and the page cites them.

- A decode step is other work (card matmuls, flat in context) plus attention (grows with context and users per engine). AMX touches only CPU page visits on full 64-token pages of a fitting shape.
- Visits per step = users x CPU layers x KV heads x pages (context / 64). They are shared by 13 to 26 of the 27 workers at tp2.
- One unit costs 3.6 us on AVX and 2.9 us with the kernel at prompt 8192. The 32 KiB memory time is 2.5 us, so AMX saves 0.5 to 0.75 us per visit, not the 1.1 us it saves when the page is hot.
- The saving passes 1:1 to the forward for one-minibatch plugins (qwen, gpt-oss). llama at 8 users and prompt 1024 passes only one third: its period stayed 247 us against 248 us while busy per job fell 9 %.
- Under AoF the CPU keeps 1-to-4-key tails. The kernel's unit never fills, so the AMX gain in decode is 0.
- gpt-oss scores 10 % of keys on the CPU. That is 6.3 % of worker time (T2 0.649 ms per forward per worker, 36.0 us per job, of a 10.26 ms forward). A 64x8 kernel could recover under 1 % (est.).
- Worked examples: llama-3.1-8b predicts +2.8 to +3.7 % at prompt 1024, measured +2.9 %. qwen3-4b under AoF predicts 0, measured within 1 %. gpt-oss re-derives the Scratch-page answer. qwen-2.5-32b has kv_mul 5 and fails the kernel gate.
- One open edge: for llama-3.1-8b at 8 users and prompt 1024, lockstep runtron decode gains +2.9 % but the CI harness measured +10.8 to +12.9 %. The page gives a hypothesis (mixed forwards with other users' prefill chunks, where the kernel is 1.7x to 2.5x faster per job) and names the measurement that decides it. No existing data settles it.
