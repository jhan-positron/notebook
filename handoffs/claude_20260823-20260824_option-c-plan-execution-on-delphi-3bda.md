## Objective

Execute the plan in `router/02-option-c-plan.md` (written by peer session
`intel-amx-3d`): decide whether moving the MoE router matmul (MoE = mixture
of experts; the router is the small per-layer matmul that picks which experts
process each token) from the FPGA to the host CPU would speed up decode in
tron (Positron's model-serving/inference runtime) for the gpt-oss-20b and
gpt-oss-120b models. The plan's phases: P0a = add perfetto trace markers
(perfetto = Chrome's tracing framework used by tron) around the router chain
and capture traces; P0b = a standalone CPU router-kernel microbenchmark;
G0 = a pre-registered go/no-go gate; P1a = a hand-edit spike that actually
runs the router on CPU inside serving, measured A/B. Testing on delphi-3bda
(the Intel test machine, DUT), status report HTML to `router/status-report/`.

## Gotchas & decisions

- Pre-registration discipline drove the whole flow: the G0 statistic was
  written before any data; the gate-variable deviation (wrong latch
  operationalized) went through a Sol round and explicit user endorsement;
  post-decision, the published decision JSONs were deliberately NOT
  regenerated (editing a decision artifact after the decision is itself a
  post-hoc edit).
- Perfetto tracing overhead inflated the measured stall ~2.5x — the P1a
  integrated A/B, not the P0 traces, gave the true recoverable time. This
  reversed the corrected-G0 PROCEED prediction.
- The generated plugin header is one class template instantiated for host
  AND device executors; a hand-edit must compile for both buffer families
  (the first spike build failed on `.data.get()` vs `std::array`).
- NFS attribute caching produced a false "empty marker" monitor trigger;
  later monitors required non-empty marker content.
- Adversarial review before use caught real defects three times: the bench
  accumulator count, the analyzer's M double-count and wrong flow-join hop,
  and the mislabeled 0.2% figure in the close-(c) argument.
- The first "numerics instrument-invalid" verdict was the session's own
  error twice over (missing determinism flags, then an ANSI log-extraction
  artifact); the corrected record shows the instrument is valid and the CPU
  router genuinely changes sampled output.
