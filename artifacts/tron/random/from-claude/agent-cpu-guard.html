Agent CPU guard on agentsrv

2026-11-20. All times are PST. Written by a Claude Code session for jhan. This page follows the incident report "Agents running slow at agentsrv" [Ref1].

Short version

Every shell command that Claude Code or Codex starts on agentsrv is now pinned to 6 fixed CPUs, so agent batch jobs can no longer use up the 8 CPUs that agentsrv allows per user.

In a test with 36 busy processes, the whole container was stalled for 77% of the time without the pin and for 0.3% of the time with it.

The 0.3% also needed a second fix: 54 forgotten tmux clients were detached, and they had been starting a script every 5 seconds.

Words used here
  • agentsrv: a shared development server with 32 CPUs.
  • claude-dev: the podman container on agentsrv in which jhan runs coding agents. Its hostname is claude-agentsrv.
  • agent: one Claude Code session or one Codex session.
  • quota: the CPU time that all processes of one user may use, set by the admins. Here it is 800 ms per 100 ms period, which equals 8 CPUs.
  • stall: time in which every process of the container that wanted to run had to wait for a CPU. The kernel counts it in the file cpu.pressure, line "full".
  • pin: the list of CPUs on which a process may run (its CPU affinity). Child processes inherit the list. The command taskset sets it.
  • guard: the new file ~/.config/agent-cpu-guard/guard.sh.
  • BASH_ENV: an environment variable. bash reads the file that it names before each non-interactive command.
  • nproc: a command that prints how many CPUs the calling process may use.
  • probe: a test thread that does 0.3 ms of work and then sleeps 5 ms, again and again. It is not pinned. It stands for an interactive tool.
  • burst: a short period, under one second, in which many CPUs are busy at once.
  • tmux: a program that keeps terminal sessions alive. A tmux client is one terminal that is attached to a session.
  • tmux-continuum: a tmux plugin that saves the window layout. It works through a script in the tmux status line.
  • herdr: the terminal manager that jhan uses for agents today.
  • Codex daemon: a long-running codex app-server process. It starts the commands of interactive Codex sessions.
  • LSF: the batch job scheduler that the admins provide for large jobs.

The solution

One file does the work for both tools [Ref2]. These are its active lines.

# ~/.config/agent-cpu-guard/guard.sh
[ -n "${AGENT_CPU_GUARD:-}" ] && return 0          # already pinned by an outer shell

case "${HOSTNAME:-}" in
  agentsrv|claude-agentsrv) _acg_cpus=26-31 ;;     # the host and its container
  *) return 0 ;;                                   # any other host: do nothing
esac

if taskset -pc "$_acg_cpus" $$ >/dev/null 2>&1; then
  export AGENT_CPU_GUARD=$_acg_cpus
fi
unset _acg_cpus
return 0

Claude Code loads it through its settings file [Ref3].

// ~/.claude/settings.json
"env": {
  "BASH_ENV": "/home/jhan/.config/agent-cpu-guard/guard.sh"
}

Codex loads it through its config file [Ref4].

# $CODEX_HOME/config.toml
[shell_environment_policy.set]
BASH_ENV = "/home/jhan/.config/agent-cpu-guard/guard.sh"

How it works

1. AgentClaude Code or Codex wants to run a command. The agent itself is not pinned.
→
2. bash startsBoth tools start /bin/bash -c <command> with BASH_ENV set.
→
3. Guard runs firstbash reads guard.sh before the command. This costs about 1.1 ms.
→
4. PinOn agentsrv the guard pins the shell to CPUs 26-31 with taskset.
→
5. CommandThe command and all its children run on those 6 CPUs. nproc prints 6.
  • Both tools start each command as /bin/bash -c ... [Ref6]. bash reads the file named by BASH_ENV before such a command [Ref7].
  • All agent sessions use the same 6 CPUs. So all their commands together cannot use more than 6 CPUs, however many processes they start.
  • The quota is 8 CPUs. The other 2 CPUs stay free for the agents themselves and for the terminal tools.
  • A pin and a quota act in different ways at their limit. When a quota runs out, the kernel pauses every process of the user. With a pin, only the batch processes wait for each other.
  • The container cannot set a quota of its own. Its control-group tree is read-only and has no CPU controller [Ref18].

Rules for agents

The instruction files of both tools have a new section, "agentsrv and its claude-dev container" [Ref5]. It tells agents these points.

  • agentsrv allows 8 CPUs, 64 GiB RAM and 8 GiB swap per user, and programs still see 32 CPUs.
  • Size worker pools from nproc or len(os.sched_getaffinity(0)), not from os.cpu_count().
  • Do not widen the pin unless the user asks.
  • If nproc prints 32 on agentsrv, the guard is not loaded. Tell the user.
  • Send larger jobs to LSF.

Test 2: does the pin stop the stall?

The load is 36 busy processes. That is the width of the two largest worker pools of the incident, 28 and 8 [Ref1]. The test starts them through /bin/bash -c, the way an agent does [Ref11].

Two instruments run during each test.

  • The kernel's stall counter of the container.
  • The probe. Its speed is the number of rounds it finishes per second. At rest, which means with no test load, it finishes 192 rounds per second.

Why 6 CPUs and not 4, 5 or 7

The same load ran for 20 s at each width [Ref11]. The tmux clients were still attached during these four runs.

  • The stall grows slowly from 4 to 6 CPUs and faster at 7.
  • 6 CPUs keeps three quarters of the quota for batch work. Going down to 4 CPUs would save 0.9 percentage points of stall.
  • Everything else in the container uses 0.55 CPUs after the tmux cleanup [Ref12]. So 6 pinned CPUs leave 1.45 CPUs spare, and 7 would leave 0.45.

Second cause: 54 idle tmux clients

The pin alone left a stall of 2.7% to 6.3%. A sampler that read the CPU use of every process each 100 ms found the reason [Ref12].

CPU use of the container with no test load, before and after the tmux cleanup

CPUs in use, averaged over each 0.1 s. Both panels show 60 s and use the same scale.

Before, a burst came every 5 s, and 11 of the 600 windows shown were above the 8-CPU quota. After, no window used more than 2.8 CPUs.

  • The tmux status line contained the save script of tmux-continuum, and the status line refreshed every 5 s [Ref13].
  • tmux ran that script once for each attached client. 54 clients were attached, so 54 copies started at the same moment [Ref13].
  • All 54 clients were attached in September. Their last key press was 53 to 69 days ago. All came from shells opened by claude-box enter, and none was inside herdr [Ref13].
  • With no other load, one burst used 2.07 CPU-seconds. That was 39% of all CPU time the container used in the sample [Ref12].
  • One burst needed 2.07 CPU-seconds, and the quota allows 0.8 CPU-seconds per 100 ms period. 84% of the stall time in that sample fell inside the bursts [Ref12].
  • The incident report saw the same bursts and could not name their source [Ref1].
  • The cost was higher while a real batch ran. From 20:32:27 to 20:33:27 the tmux server and its children used at least 135 CPU-seconds, which is 2.2 CPUs. The container was stalled for 27.2% of that minute [Ref12].
  • Why the tmux cost was 5 times higher in that minute: hypothesis only. tmux-continuum had started its 5-minute save 21 s earlier, and each of the 54 clients may have run a full save. A per-process sample across one save moment would confirm or reject this.

What was done

  • jhan approved a plain detach. At 20:44:31 each of the 54 clients was detached with tmux detach-client [Ref14].
  • The tmux session was not touched. It still has 3 windows and 6 panes, and the 6 pane programs are the same processes as before (vim, codex and 4 shells) [Ref14].
  • After the detach, tmux started no status script in a 6 s watch [Ref14].

Is the change permanent?

  • The guard: yes. It consists of files only. No process has to keep running, and each new command loads the guard again.
  • Five of the six changed files are in the NFS home directory. They survive a restart of the container, a re-creation of the container and a reboot of the host [Ref15].
  • The sixth file is the Codex config of the container. It is on the local disk of the host, in /var/tmp/jhan/persist/codex-home. claude-box mounts that folder into every container it creates [Ref15].
  • The guard matches the hostname claude-agentsrv. claude-box sets that name each time it creates the container [Ref15].
  • The tmux cleanup: no. It was done once. ~/.tmux.conf is unchanged, so the number of attached clients can grow again.
  • The guard can stop working without an error in three cases: the hostname changes, the machine shows fewer than 32 CPUs, or a later version of a tool stops passing BASH_ENV. The new agent rule about nproc printing 32 exists for this [Ref5].

How to check, bypass and switch off

GoalHow
Check that the guard is activeAsk an agent on agentsrv to run nproc. It prints 6.
Run one command on all CPUstaskset -c 0-31 <command>
Change the widthEdit the CPU list 26-31 in guard.sh. The next command of every session uses the new list.
Protect one more hostAdd one line with its hostname and a CPU list to the case block in guard.sh. For Codex on that host, also add the two config lines to its config.toml.
Switch off for every session at onceDelete the agentsrv|claude-agentsrv line in guard.sh.
Remove completelyRemove the env block from ~/.claude/settings.json and the [shell_environment_policy.set] block from both Codex config files.

Limits and open items

What the guard does not cover

  • It pins only what an agent starts through bash. The agents themselves, their built-in file search, herdr and tmux are not pinned.
  • A program can leave the pin by setting its own CPU list (taskset, numactl, os.sched_setaffinity). The bypass in the table above uses this on purpose.
  • os.cpu_count() still returns 32. A pool sized from it starts 32 workers on 6 CPUs. That works, but it uses more memory and switches between processes more often.
  • numpy follows the pin by itself. Its math library started 32 threads without the pin and 6 threads with it [Ref16].
  • The 6 CPUs are fixed. If other users load CPUs 26-31, agent commands run slower while other CPUs are free. Since boot, each of the 32 CPUs was busy for 13% to 17% of the time, so no CPU is preferred today [Ref17].
  • All agent commands together now get 6 CPUs, not 8.
  • The limits on memory (64 GiB) and swap (8 GiB) are not addressed.

What was not verified

  • Sessions on the agentsrv host, outside the container: Insufficient data. The config was edited, but no command could be run on the host from this session. Running nproc in a Claude Code or Codex session on the host would resolve it.
  • Codex sessions that were already open before 20:26: Insufficient data. No new command of such a session was observed. Asking one of them to run nproc would resolve it.
  • The throttle counter of the host (nr_throttled): Insufficient data. It is not visible inside the container. On the host, cat /sys/fs/cgroup/user.slice/user-$(id -u).slice/cpu.stat before and after a batch would show it.
  • One probe round took 1,023 ms at about 20:31, during the run that overlapped with the other session's batch. Its cause: Insufficient data. A per-process sample at that moment would have shown it.

Side effects of the tests

  • The run without the pin stalled all of jhan's sessions on agentsrv for 4.3 s at 20:16:57. It was kept this short on purpose.
  • The daemon test left one thread named "agent-cpu-guard check" in the Codex history.
  • Nothing was killed or restarted.

Possible next steps

  • Stop idle tmux clients from collecting again, for example with a tmux hook that detaches clients with no key press for 7 days.
  • Ask the admins to delegate the CPU controller to user sessions. A second quota for batch work would then be possible, and it would not depend on fixed CPUs.
