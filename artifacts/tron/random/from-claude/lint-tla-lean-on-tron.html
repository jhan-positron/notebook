Lint rules, model checking and proofs, shown on TRON code

Answers to two questions about Lauren Tan's talk "All Code Is Slop (Except Mine)" [Ref1]. Written 2026-11-22 from TRON commit 7eddde7895 (branch main, 2026-11-21).

Short version
  • After a correction, ask the agent for a check that fails on the bad line and passes on the fixed line.
  • A model checker (TLA+) tries every order of thread steps: TRON's capture slot passes in 32 states, and a seeded bug shows in 3 steps.
  • A proof (Lean) covers every input, and that question exposed chunk_evenly inputs that break the 128-token cap when --max-minibatches is 2 or more.

  • Agent: an AI coding tool that edits files and runs commands. Here it is Claude Code.
  • Lint rule: a check that a program runs on source text. It passes or fails without human judgment.

  • Baseline: a file that lists the old hits of a new rule. With it, the rule fails only on new hits.
  • Hook (Claude Code): a command that Claude Code runs at a fixed point, for example after each file edit.
  • Skill: a file of instructions that Claude Code loads when you type /name.
  • agentsrv: the Linux server on which your agents and this session run.
  • rinzler: TRON's server program.
  • runtron: TRON's command-line program for single runs.
  • Plugin: the TRON code for one model family. The llama plugin serves Llama models.
  • Catch2: the C++ test framework that TRON uses.
  • FUSE: the file-system interface through which rinzler takes commands such as "start a capture".
  • Perfetto capture: a recording of trace events, used for performance analysis.
  • SIGUSR1: a Unix signal. Sent to rinzler, it starts a capture of 10 seconds.
  • State machine: a list of states plus the allowed moves between them.
  • Model checker: a program that visits every state a model can reach and tests a rule in each one. TLA+ is a language for such models, and TLC is its checker.
  • Trace: the list of steps that a model checker prints to show how a rule breaks.
  • Seeded bug: a bug that I put into a copy of the model on purpose, to see whether the checker finds it.
  • Lean: a language in which you write a statement and its proof. The Lean program accepts the file only when the proof is complete.
  • Token job: one token that a forward pass computes. A forward pass is one run of the model over a group of tokens.
  • Minibatch (also "chunk"): a group of token jobs that are computed together. The llama plugin allows at most 128 token jobs per minibatch.
  • Grain: up to 8 token jobs of one group. chunk_evenly never splits a grain.

Part 1. From a correction to a lint rule

  • The talk gives this rule: "whenever you're correcting your agent, think about how you can make that a deterministic check instead of adding another line to your rules or your agents.md" [Ref1].
  • A sentence in AGENTS.md is advice. The agent may not have it in view at the moment of the mistake.
  • A check is a program. It fails every time, and its message arrives at the moment of the mistake.

1.2 How to request the rule

Type this right after the correction. The example lesson is a #if 0 block that the agent left in a diff.

You left a `#if 0` block in the diff, and I told you to delete it.
Turn that correction into a deterministic check for this repository.

1. State the rule in one sentence. Quote the bad line and the fixed line.
2. Choose the strongest place that can decide the rule: first the type system or
   a compiler flag, then a lint rule, then a test. Use a sentence in AGENTS.md
   only when no check can decide the rule, and say why.
3. Write the check. Its message must say why the pattern is wrong and what to
   write instead. The reader is an agent that has not seen this conversation.
4. Prove the check: show that it fails on the bad line and passes on the fixed line.
5. Run it on the whole tree. Report the old hits and record them in a baseline.
   Do not fix them now.
6. Wire the check as README.ci.md "Adding Lint Checks" says.

The same request, saved as a skill, is one line:

/lesson-to-lint
/lesson-to-lint no #if 0 blocks in h/, src/ and t/

The request needs three parts. Without them the result is weak.

  • A proof step: the agent shows the check failing on the bad line and passing on the fixed line. Without this step you can get a rule that never fires.
  • A message written for the next agent: why the pattern is wrong, and what to write instead. TRON's lint wrapper already prints a "To fix:" line for each failed check [Ref4].
  • A baseline for old hits: the rule blocks new hits at once, and the old hits are listed for later cleanup.

# Lesson to lint

The user corrected something. Make the tools reject that mistake from now on.

Lesson: $ARGUMENTS

When the line above is empty, use the most recent correction in this conversation.

## Steps

1. State the rule in one sentence: "PATTERN is not allowed in SCOPE. Write REPLACEMENT instead." Quote the bad line and the corrected line from this conversation. If the correction was a decision for this one case and not a general rule, say so and stop.
2. Choose where the rule lives. Try the places in this order and take the first that can decide the rule from the source alone:
   1. The code makes the mistake impossible: a type, `= delete`, `[[nodiscard]]`, `static_assert`, a narrower interface.
   2. A setting of a tool the repository already runs: a `-Werror=` flag, a Ruff rule, clang-format.
   3. A row in `bin/ci/lint-source-rules.py`, when one line of text decides it.
   4. A script that compares files, when the rule spans files. The model is `bin/ci/lint-ci-pins.sh`.
   5. A test, when the rule is about behavior and not about text.
   6. One sentence in the nearest AGENTS.md, only when no check can decide the rule. Say why no check can.
3. Write the check. Its message names the file and the line, gives the reason in one sentence, and says what to write instead. The reader of the message is an agent that has not seen this conversation.
4. Prove the check. Show the output of both runs:
   - it fails on the bad line from step 1,
   - it passes on the corrected line.
5. Run the check on the whole tree. Report the count of old hits. Do not fix them in this change. Record them in the baseline, so that the count can only go down.
6. Wire the check as README.ci.md "Adding Lint Checks" says: `lefthook.yml`, the `lint-toolchain` check in `flake.nix`, and the `lint` target of the GNUmakefile. Keep the three commands the same.
7. Report: the rule sentence, the place chosen, why the stronger places did not fit, the two proof outputs, the count of old hits, and the files changed. List what the check cannot see.

## Limits

- Do not weaken or delete an existing check to make the new one pass.
- Do not add the hit that caused the correction to the baseline.
- One lesson gives one rule in one change. Leave old hits alone.

Part 2. Model checking a state machine (what TLA+ does)

2.1 The state machine: TRON's capture slot

  • rinzler records at most one Perfetto capture at a time. The class capture_controller holds that one slot [Ref12].
  • Three threads use the slot. The FUSE request thread takes start and stop commands. The capture worker thread runs the capture. The SIGUSR1 thread runs a capture that a signal started.
  • A capture in the slot has one of 4 states: accepted, waiting, recording, stopping. It leaves the slot as finished, failed or stopped_before_start.
  • Each method of the class holds one mutex for its whole body. So each call is one indivisible step, and a bug can only come from the order of the calls.

Every move belongs to one thread. The danger is a stop that arrives between two moves of the worker.

Figure 2. The states of the capture slot and the thread that makes each move, read from src/pos/trace_capture.cpp [Ref12]. A stop command for a capture that is waiting or later only sets the flag stop_requested.

2.2 What a model checker does

  • You write the states and the steps as a small model. You also write rules that must hold in every state.
  • The checker starts at the first state. It tries every step of every thread, in every order.
  • It tests each rule in each state that it reaches.
  • When a rule breaks, it prints the shortest list of steps that leads there.

The four rules for the slot:

  • OneCapture: a SIGUSR1 capture never runs while a FUSE capture holds the slot or the worker runs one.
  • AssertActive: while the worker runs a capture, the slot is not empty. Three worker methods start with TRON_ASSERT(active_), which states this rule.
  • OwnJob: the capture in the slot is the one that the worker runs.
  • NeverStuck: the slot can always become empty again.
$ python3 -I capture_slot_check.py
=== The design as written in trace_capture.cpp
    32 reachable states, 53 steps explored
    PASS  OneCapture
    PASS  AssertActive
    PASS  OwnJob
    PASS  NeverStuck: the slot can always become empty again
    states with no next step (deadlocks): 0

The design in trace_capture.cpp passes all four rules. The whole search covers 32 states and 53 steps and takes 0.01 seconds.

Three steps empty the slot under a worker that still runs capture 1.

Figure 3. The 3-step trace that the checker printed for AssertActive, plus the worker's next call. The columns are steps in order. Their widths are not time.

  • The stop command empties the slot when it sees accepted. The comment in the code reads "The worker never saw it: no window" [Ref12].
  • With the bug, the worker did see the capture. Its next call, begin_recording(), finds an empty slot, and TRON_ASSERT(active_) aborts rinzler.
  • The 4-step trace is worse. A second start arrives before the worker's next call. The worker then marks capture 2 as recording while it runs capture 1.
  • So waiting means "the worker has this capture". From that state on, a stop only sets a flag.

2.6 What the tests cover, and what the checker adds

  • TRON's unit test runs one order of calls on one thread. That order includes start, take_start(), stop, begin_recording() [Ref13]. So the test would catch seeded bug 1.
  • The test covers that order because its author thought of it. The checker needs no such foresight: it covers all 53 steps.
  • The model is a copy of the code, made by hand. When the code changes, the model must change too.
  • The model leaves out shutdown, the wake-up semaphore, the list of ended captures, and the life of the Perfetto session. A bug in those parts is invisible to it.

Part 3. A proof for every input (what Lean does)

3.1 The line of code

  • chunk_evenly cuts the token jobs of one forward pass into minibatches [Ref14].
  • Line 246 computes the planned count of chunks: (n_token_jobs + max_minibatch_size - 1) / max_minibatch_size.
  • With the llama plugin's cap of 128 token jobs, a pass of 300 jobs gets 3 chunks.
  • Two statements about this line are worth a proof. "Enough room": the planned chunks hold all jobs. "No spare chunk": one chunk fewer would not hold them.

3.2 The statements and the proofs, in Lean

/-- The C++ expression, with 128 written out. `/` on Nat rounds down, as in C++. -/
def targetChunks (n : Nat) : Nat := (n + 127) / 128

/-- Enough room: the planned chunks, at 128 token jobs each, hold all n jobs. -/
theorem enough_room (n : Nat) : n ≤ targetChunks n * 128 := by
  unfold targetChunks
  omega

/-- No spare chunk: with one chunk fewer, some job would have no place. -/
theorem no_spare_chunk (n : Nat) (h : 0 < n) : (targetChunks n - 1) * 128 < n := by
  unfold targetChunks
  omega

/- A unit test of the same function checks single inputs, for example: -/
example : targetChunks 300 = 3 := rfl
example : targetChunks 128 = 1 := rfl
example : targetChunks 129 = 2 := rfl
  • (n : Nat) makes each statement a claim about every natural number n.
  • omega is the proof. It is a Lean procedure that decides statements built from addition, comparison, and division by a constant.
  • Lean runs no input. It accepts the file only when each proof is complete.
  • The three example lines are what a unit test does: one input each.

The file was not checked by Lean (see section 5). The range test below ran.

3.4 When a statement is false: the 128-token cap

  • TRON states a second property of chunk_evenly as an assert: no chunk is larger than max_minibatch_size [Ref14].
  • A proof of it needs a fact from another file. The scheduler admits at most max_minibatches × max_minibatch_size token jobs to one pass [Ref15].
  • Even with that fact, the property is false. I copied the real text of chunk_evenly from model.hpp by line range and compiled it with substitute types. Then I ran every split of n token jobs into two groups. A group is the set of token jobs with the same affinity label, for example the tokens of one prompt.

  • The smallest failing input has 250 token jobs in groups of 1 and 249, with max_minibatches at 2. The result is chunks of 121 and 129 token jobs.
  • The cause is the merge test on line 267. Once the chunk count reaches max_minibatches, every further grain joins the last chunk, also when it does not fit:
  for (size_t g = 1; g < grains.size(); ++g) {
    std::vector<int> grain = std::move(grains[g]);
    int old_sz = chunks.back().size();
    int new_sz = old_sz + grain.size();
    bool grain_fits = new_sz <= max_size;
    bool good_here = std::abs(new_sz - target_size) <= std::abs(old_sz - target_size);
    bool hit_chunk_limit = chunks.size() == (uint64_t)state.cfg.max_minibatches;
    if ((grain_fits && good_here) || hit_chunk_limit)
      chunks.back().insert(chunks.back().end(), grain.begin(), grain.end());
    else
      chunks.emplace_back(std::move(grain));
  }
Hypothesis for the real program, not confirmed.
  • runtron --max-minibatches 2 or rinzler --max-batches 2 aborts at model.hpp:359 when one pass gets such a mix of groups [Ref16]. TRON_ASSERT stays active in release builds.
  • The default setting (-1) and the value 1 showed no failure in the tested range.
  • The measurement that confirms or rejects it: a Catch2 case that calls chunk_evenly with 250 token jobs in groups of 1 and 249 and cfg.max_minibatches = 2.
  • Insufficient data: whether the scheduler ever forms such groups. A runtron run with that option and a logged group layout would show it.

This is how proof work finds bugs. The proof cannot be completed, and the case where it stops names the line. A person who tries to prove the cap in Lean stops at || hit_chunk_limit.

Limits of the harness: the types around the function are substitutes. For the step that keeps even and odd page offsets together, each group is one KV page (the block of memory that holds one group's attention keys and values) that starts at offset 0. I did not run TRON itself.
