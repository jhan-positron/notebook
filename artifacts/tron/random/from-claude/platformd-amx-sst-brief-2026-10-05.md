# platformd and two Intel features: what platformd needs to do for AMX and Speed Select

Meeting brief for John Mark, 2026-10-05. Written by Claude for jhan. Scope: WHAT platformd must own, know, decide, check and expose. Not how. Paths in brackets are under `~/workspace` unless they start with `~/.claude`. The long version with every fact is `platformd-amx-sst-brief-2026-10-05-long.md` in the same folder. Section 1 (build status) was checked separately on 2026-10-05 and is not in the long version.

## Words used here

- **platformd**: Positron's host daemon. At each provisioning it writes `/etc/rinzler/instance-N.env` (CPUAFFINITY and RZ_CLI_ARGS for one engine) and starts the `rinzler@N` units. **reconciliation**: platformd's stop-and-start of engines after a config change.
- **rinzler**: the inference server, one systemd unit per engine, runs as user `positron` without root. **tron**: the inference library rinzler is built from. **runtron**: tron's offline benchmark tool (no rinzler, no HTTP). **serving path**: measured through rinzler under HTTP traffic.
- **FPGA**: field-programmable gate array, the accelerator card tron runs the model on. **engine**: one running rinzler with its FPGA cards. **tp2 / tp4**: one model split over 2 or 4 cards. **users per engine**: concurrent users one engine serves.
- **resource-map.yaml**: tron's per-machine-type core assignment, installed at `/opt/positron/config/resource-map.yaml`. Roles: `platform_cores`, `rinzler_cores` (front end), `dev_cores` (FPGA driver), `tron_cores` (model workers), `peer_cores` (cores whose second thread is also free for work) [tron/config/resource-map.yaml:16-21].
- **6962P / 6960P**: the two Intel Xeon 6 machine types in the map. delphi-3bda is a 6962P with 288 logical CPUs. delphi-17cf is a 6960P. **die-A**: the first of the three compute dies on a 6962P socket. **power domain**: a group of 24 cores that shares one set of frequency windows.
- **HT sibling**: the second hardware thread of a physical core. Both threads share one clock.
- **AMX**: Intel Advanced Matrix Extensions, the tile matrix unit on Xeon 6. tron uses it in the CPU attention kernel. **AVX-512**: the vector path used when AMX is absent or off.
- **TRON_AMX_DISPATCH**: CMake build option that compiles the AMX kernels in. **TRON_AMX_DISABLE**: environment variable, exactly "1" turns AMX off for one process (the kill switch). **TRON_K_VNNI**: an unmerged tron option (PR 4424, PR = GitHub pull request) that changes the layout of the K cache (the attention key cache).
- **128x4**: head size 128 with 4 query heads per key/value head, the only attention shape the AMX kernel serves.
- **FPGA attention / CPU attention**: where attention runs. `USE_HW_ATTN` unset means FPGA attention for models whose build ships it (qwen-3-4b, gpt-oss-120b) and CPU attention for the rest.
- **SST**: Intel Speed Select, the per-core frequency control feature and its tool `intel-speed-select`. **CLOS**: class of service, a frequency window a CPU is assigned to. Shipped policy: CLOS0 fast (2700 MHz to 4400 MHz), CLOS3 capped (800 MHz to 2700 MHz). **turbo-freq**: the SST feature that lets high-priority cores reach the top bucket. **anchor CPU**: the one CPU per power domain on which per-domain commands are issued.
- **boot default**: the BIOS state, 32 logical CPUs fast and the other 256 capped at 2700 MHz. **intel-speed-select-state**: the boot service that applies the shipped policy today from a core list (`FAST_CORE_RANGES`) in `/etc/default/intel-speed-select-state`, rendered by Hannah's Ansible role (a configuration-management script).
- **FE un-clamp** (FE = front end, the `rinzler_cores` role): the pending change that moves `rinzler_cores` from CLOS3 to CLOS0.
- **TPS**: decode tokens per second per user. **TTFT**: time to first token. **prompt 1024**: a prompt of 1024 tokens (same form for other lengths). **resolved**: the 95 % interval excludes zero. **CV**: standard deviation divided by mean. **turbostat**: the Linux per-CPU frequency and power reader. **package power**: whole-socket power draw.
- **the nightly**: the systems_test CI that reinstalls tron and provisions through platformd on delphi-3bda every night. **Gate C**: a planned reboot A/B of the frequency policy, started 2026-08-01 and not completed.

## Short version

AMX needs little from platformd. The kernels already ship in the tron apt package and turn themselves on, so the main needs are an engine restart after a package install and a per-engine kill switch. Speed Select needs more: platformd must derive the fast core set from the resource-map roles it already reads, verify the CLOS state after boot and after provisioning, and John must decide whether platformd also owns the apply.

## 1. Build status (answer to "is AMX still off by default?")

- The CMake option `TRON_AMX_DISPATCH` is still OFF by default [tron/CMakeLists.txt:48].
- The `deb` preset sets it ON [tron/CMakePresets.json:80]. That came from tron PR 4505, merged 2026-09-22 (GitHub merge time 21:08 UTC, git commit time 19:02 UTC) [notebook/artifacts/intel-amx/memory/ci-amx-row-20260923.md:18].
- `make deb` uses that preset [tron/GNUmakefile:510]. The workflow publish-deb.yml runs `make deb` on the nightly cron, on version tags, and on manual or called runs [tron/.github/workflows/publish-deb.yml:3-23]. So nightly and tagged release packages carry the kernels [tron/README.ci.md:563].
- The first package with the kernels is tron 2026.09.23-5cf65b92 [notebook/artifacts/intel-amx/memory/first-ci-amx-row-20260922.md:53]. Packages up to 2026.09.18-3faba6d0 have none [same file:14-15].
- At run time AMX is on when compiled in and the host supports it. The only switch is `TRON_AMX_DISABLE=1` [tron/h/tron/kernels/amx_attn_iface.hpp:47].
- Consequence: the apt package needs no build change. Every other preset leaves the option OFF, so a product binary built outside `make deb` has AMX only if the build passes the option explicitly (the CI test job does) [tron/.github/workflows/cmake-single-platform.yml:355]. Whether such a product path exists is a question for the build owner, not for platformd.

## 2. AMX: what platformd needs to do

**What breaks if platformd gets it wrong.** Nothing crashes. A host without AMX, an ineligible model, or the kill switch all fall back to the AVX-512 path [tron/h/tron/kernels/amx_attn_iface.hpp:33-53]. The failure is a silently missed gain of up to 15 % TPS on CPU-attention models (section 7). The nightly AMX row has no pass threshold as of 2026-09-21, so CI would not catch a broken AMX binary either [notebook/handoffs/claude_20260921_systems-test-pr-221-amx-ci-test.md:13,63].

**Know**

- Model eligibility is fixed at compile time per model. Only the 128x4 shape reaches the kernel. In the nightly set that is llama-3.1-8b, mixtral-8x7b and qwen-3-4b. The other six nightly models are not eligible [notebook/handoffs/claude_20260918_amx-compatible-128x4-models-in-nightly-ci.md:74-86].
- Only CPU-attention engines gain. qwen-3-4b runs FPGA attention, so AMX scores 0 decode keys there. Moving it to CPU attention to use AMX costs about 20 % decode TPS at the nightly load (2 users per engine on tp2, 4 on tp4, 2026-09-13) and 37 % at 8 users per engine (prompt 1024 tokens, one repetition, 2026-10-02) (section 7). platformd should keep `USE_HW_ATTN` unchanged.
- FPGA-attention engines still run CPU attention when the FPGA key/value space is exhausted (about 800 fallbacks per night on qwen tp4 in the nightly's MMLU Pro phase, a multiple-choice accuracy benchmark) [notebook/artifacts/intel-amx/pr3879/PR1/nightly-amx-check-20260916.html:170]. Core sizing for those engines should keep spare cores for that path.
- Host eligibility needs no platformd gate. tron probes CPU feature bits and the kernel at the first attention call and falls back to AVX-512. If platformd wants a fleet inventory of AMX-capable hosts, the rule is Xeon 6 plus kernel 5.16 or newer [tron/src/tron/kernels/amx_attn.cpp:16]. AMD hosts run the same package with no regression (AMD nightly rows -0.9 % to +2.5 %) [notebook/handoffs/claude_20260923_amx-benchmark-tps-regression-between-ci-runs.md:99-110].
- The gain scales with users per engine. On llama-3.1-8b at prompt 1024: +0.2 % at 2 users per engine (not resolved: the 95 % interval includes zero), +3.9 % at 4, +12.9 % at 8 [notebook/artifacts/intel-amx/memory/l8bload-20260918-campaign.md:29-34; intel-AMX/exec/results/l8bload-20260918/summary.md:3]. Whoever owns the users-per-engine setting owns the size of the AMX gain.
- Memory does not change with the shipped kernel. AMX keeps no extra copy of K or V (the attention key and value caches). Hugepage (Linux large memory page) counts therefore stay as they are [notebook/artifacts/intel-amx/amx_software_attention.md:25-28]. The unmerged TRON_K_VNNI variant would change this.
- Placement question, not measured: Intel guidance is one AMX thread per physical core. tron pins one worker per logical CPU from `--app-cores` and does not check siblings [notebook/artifacts/intel-amx/intel-amx.md:92-95]. Insufficient data: a paired run with and without sibling pairs in `--app-cores`.

**Do**

- Restart engines after a tron package install. apt never restarts engines, and tron's postinst (the script apt runs after installing the package) only daemon-reloads (tells systemd to re-read unit files) [tron/packaging/postinst:36-44]. On the first night with the AMX row (2026-09-22, platformd 0.11, no-kernel package) the row ran on "already provisioned" engines with no restart [notebook/artifacts/intel-amx/memory/first-ci-amx-row-20260922.md:18-21]. Records for a same-model provision conflict (question 5). The gap is a restart when the package changes but the model does not. Without it the new binary never runs.
- Offer a per-engine kill switch. `TRON_AMX_DISABLE` is read once at the first attention dispatch [tron/src/tron/kernels/amx_attn.cpp:58-86]. A change therefore needs the variable in the engine environment and an engine restart. The sanctioned places are `instance-N.env` (platformd-owned, per engine) and `/opt/positron/user/config.env` (host-wide, loaded last, so its values override the instance env) [tron/packaging/systemd/rinzler@.service:26,43]. Today the instance env carries no free-form variable. Precedent: the `use_speculation` setting becomes TRON_USE_SPECULATION in the instance env, and the same variable also appears in config.env [notebook/artifacts/intel-amx/exec/results/p0perf-20260913/platformd-instance-1.env.txt:14,27].
- Contract rules for any env channel. platformd must own or audit config.env. A stale value there overrides every per-engine value. Never override RZ_FUSE_MOUNT_PRESCOPED from instance-N.env or config.env. The unit sets it to 1, and an override double-nests the stats mount path [tron/packaging/systemd/rinzler@.service:14-25; tron/README.stats.md:44-47]. Never carry SYSTEM_CONFIG (it replaces `--devices` and `--app-cores` after argv) [~/.claude/projects/-home-jhan-workspace-intel-AMX/memory/3bda-shared-with-bill.md:77-82].
- Know the rollback cost. The kill switch is not bit-exact with AMX on (different rounding order) [notebook/artifacts/intel-amx/amx_software_attention.md:57-61]. On llama-3.1-8b at 8 users and prompt 8192 it costs -13.8 % TPS and +128 % TTFT, one repetition per arm [notebook/handoffs/claude_20261001-20261002_amx-attention-stats-comparison-at-3bda.md:76-88]. Production llama-8b truncates prompts at 4096 tokens, so the 8192 figures do not occur there [notebook/artifacts/intel-amx/memory/l8b-levers-20260919-campaign.md:39-62]. The reachable gain is the 4096 cell, +14.0 % at 8 users per engine [notebook/handoffs/claude_20260923_amx-benchmark-tps-regression-between-ci-runs.md:62]. If TRON_K_VNNI ever enters the package, `TRON_AMX_DISABLE=1` no longer restores today's numerics [notebook/artifacts/intel-amx/amx_software_attention.md:111-115]. The meaning of a platformd "disable AMX" control is therefore tied to the package version.

**Check or expose**

- The installed rinzler has the AMX kernels compiled in. Today the only non-root signal is a string in the stripped binary (method in the long version) [notebook/handoffs/claude_20260917_amx-in-nightly-ci-on-delphi-3bda.md:82-90]. A feature flag exported by tron would be the durable check.
- The running engine executes the on-disk binary, not a deleted one [notebook/artifacts/intel-amx/memory/ci-mimic-20260918-campaign.md:51-52].
- AMX actually ran. The probe runs at the first attention call, so a readiness check cannot see it. Proofs exist only after traffic: the CPU counter EXE.AMX_BUSY (needs root), or the attention counters tron exposes when `TRON_ATTN_STATS=1` is in the engine environment (tron PR 4596) [notebook/artifacts/intel-amx/memory/attn-stats-pr-implementation.md:20-34]. Export of those counters to Prometheus (the metrics service that scrapes rinzler) is undecided (tron issue 4303) [notebook/artifacts/intel-amx/memory/attn-stats-why-not-fuse.md:38].

## 3. Speed Select: what platformd needs to do

**What breaks if platformd gets it wrong**

- Policy missing: 72 of the 80 busy worker threads on the machine (36 of 40 per socket) run at 2700 MHz [notebook/handoffs/claude_20260702-20260706_debug-flat-freq-on-ci-machine.md:12]. Measured gain of the shipped policy over the boot default: +12.93 % decode TPS on llama-3.1-8b, +4.03 % on qwen-3-4b, +1.75 % on mixtral, +2.57 % on qwen-2.5-32b [notebook/artifacts/intel-speed-select/results/sst-ab-20260917/summary.md:24-33]. Expressed as a loss, a missing policy costs about 11.5 % decode TPS on llama-3.1-8b (computed from the same pairs).
- Two writers of one CLOS table. The boot service re-applies its list at every boot and at every restart of its unit. The Ansible role rewrites its config on every run [notebook/artifacts/intel-speed-select/reminder.md:59-61,144,150-153]. A platformd-written state is overwritten unless one owner is chosen.
- Nothing re-asserts the policy during uptime. Any later association write by any tool persists until the next boot [notebook/artifacts/delphi-flat-freq/docs/flat_freq_tests-README.md:40-42,417-419]. Verification must run after experiments, not only after boot.
- Three tool commands change the policy without saying so. `core-power enable` resets the CLOS2 and CLOS3 windows. `turbo-freq enable --auto` rewrites the whole partition and clears all four windows. `turbo-freq disable` keeps the table but lowers the grant from 4100 MHz to 3900 MHz [notebook/artifacts/delphi-flat-freq/docs/ALLCORE_CEILING_HETERO_CLAUDE_20260702.md:33-35,118-131,249-258].
- A core list copied between machine types caps worker cores. delphi-17cf (a 6960P) carried the 6962P list in July 2026 [notebook/handoffs/claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1043-1055]. Inferred, not measured: 12 of its 80 tron cores sit in the capped class.
- Status readback misleads. Disabling the SST features never clears CLOS windows or associations, and the cap stays enforced [notebook/handoffs/claude_20260702-20260706_debug-flat-freq-on-ci-machine.md:24,48,63]. An idle CPU reads the 800 MHz floor in either class [notebook/handoffs/claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1076-1079].

**Know, per machine type**

- Only Intel map entries are candidates. The policy has no effect on AMD types.
- Read each CPU's HT sibling from the kernel topology. Do not assume N+144. Anchor CPUs (0, 24, 48, 72, 96, 120) are measured for the 6962P only [notebook/artifacts/intel-speed-select/reminder.md:71-73,80-81].
- The derivation rule: `tron_cores` plus `peer_cores` plus HT siblings into CLOS0, every other CPU into CLOS3. `peer_cores` is a subset of `tron_cores` today, and it is a map field platformd does not read yet. By computation the rule equals the deployed list (224 fast CPUs, 64 capped), and a live read on 2026-09-17 confirmed the counts and 17 sampled cores [tron/config/resource-map.yaml:190-208; notebook/artifacts/intel-speed-select/results/sst-ab-20260917/part1-config-coverage.md:17,19]. The map lists some die-A cores by sibling id on purpose, so platformd must map ids to physical cores first [tron/config/resource-map.yaml:185-189]. Unlisted cores stay capped: with every CPU fast, decode was 0.9 % to 1.8 % lower [notebook/artifacts/delphi-flat-freq/docs/flat_freq_tests-README.md:213].
- Which roles go fast, by evidence. `tron_cores`: shipped. `rinzler_cores` (the FE un-clamp): +1.12 % decode at 8 users and +2.44 % at 24 users, gpt-oss-120b tp4 in the serving path, for +6 W to +8 W (section 7). `platform_cores` and `dev_cores`: the only test also made cores 73-74 fast, in runtron, and saw deltas of -0.53 % to +0.15 % across four models, two of them statistically resolved but all under 0.6 % [notebook/artifacts/intel-speed-select/results/sst-ab-20260917/summary.md:26-35]. runtron places no thread on cores 72-74. That test therefore cannot see an effect there. No serving-path measurement exists for those two roles.
- The window definitions: CLOS0 2700 MHz to 4400 MHz, CLOS3 800 MHz to 2700 MHz. Two classes suffice. A three-tier layout gave the same decode TPS within the run-to-run spread [notebook/artifacts/delphi-flat-freq/docs/flat_freq_tests-README.md:216-228].
- Prerequisites platformd checks but does not own: the kernel modules that create `/dev/isst_interface`, and the tool binary. The deployed tool at `/opt/intel-speed-select/intel-speed-select` matches a locally patched build (root check removed) by size only, byte identity not checked [notebook/artifacts/intel-speed-select/reminder.md:39-45]. Running it needs root or a sudoers entry for that exact path [notebook/handoffs/claude_20260702-20260706_debug-flat-freq-on-ci-machine.md:52,56]. rinzler has no root, so platformd or a helper it owns is the only candidate writer. One host (delphi-3af6) booted without the drivers after a reboot [notebook/handoffs/codex_2026-06-30-2026-07-02_root-cause-flat-freq-not-working.md:52].
- Expected frequency under load is per machine type and per host BIOS. The 6960P reaches at most 3.9 GHz, against 4.4 GHz on the 6962P [notebook/handoffs/claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1049-1050]. Same-type hosts differ in BIOS version (3bda and 3c51) [notebook/handoffs/claude_20260810_compare-bill-delphi-3c51-with-delphi-3bda.md]. Set the expectation from one loaded read per host after install.

**Decide**

- Ownership: replace the boot service and the Ansible role, or verify only and leave the writer where it is.
- Scope on a shared host. CLOS windows are per power domain and shared by every process on it. Associations are per CPU. On delphi-3bda Bill owns socket 0 and jhan socket 1, and the September campaign wrote only socket-1 associations [notebook/handoffs/claude_20260916-20260917_speed-select-retune-delphi-3bda.md:15]. A whole-machine apply at every provisioning would rewrite the other owner's half.
- Failure policy when prerequisites are missing: block provisioning, warn and continue, or mark the host degraded. A silent skip leaves hosts in the mixed state seen on the fleet today (section 5).
- Timing: at boot or at each provisioning. One apply takes 2 s [notebook/artifacts/intel-speed-select/reminder.md:120-126]. A CLOS change took effect on a running rinzler without restart in the July A/B blocks [notebook/artifacts/delphi-flat-freq/docs/flat_freq_tests-README.md:780-800], so ordering against rinzler start is a performance question, not a correctness one (inferred). Open risk on boot-time apply: within-night TPS dispersion stepped from 1.54 % to 4.67 % on two hosts in July 2026, each time together with a reboot plus policy install. Live toggles were excluded as the cause. The boot-time apply is an unexcluded suspect, and Gate C never completed [notebook/handoffs/claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:2020-2027,2056-2062].
- The first change platformd would apply is the FE un-clamp, not deployed as of 2026-09-17.

**Own**: the desired per-CPU association table derived from the map, the boot-default table as the rollback target, and a readback snapshot before every change.

**Check**

- Before apply: tool present, device present, privilege available, CPU count and machine type match.
- During apply: the tool can fail on part of a CPU list and still exit 0. The result must be checked per CPU against the derived table, not from the exit code [notebook/handoffs/claude_20260702-20260706_debug-flat-freq-on-ci-machine.md:67].
- After apply, after boot, after rollback: turbo-freq enabled on every anchor, both windows exact, and the per-CPU association table equal to the derived table. Today that is 224 fast and 64 capped on the 6962P. After the FE un-clamp it is 232 and 56 (computed: `rinzler_cores` lists 8 CPUs) [tron/config/resource-map.yaml:183]. In Gate C the two-class layout survived a boot with the unit masked, so unit status says nothing about the table [notebook/handoffs/claude_20260730-20260802_tron-moe-randomness-investigation.md:148-156].
- Under load, without AMX, the 6962P fast set read 3952 MHz to 3981 MHz (section 7). 4400 MHz is the window top, not a delivered clock. An exact 2700 MHz with zero variance is the class cap. A plateau that moves by tens of MHz near 3.25 GHz is the package power limit [notebook/artifacts/delphi-flat-freq/docs/speed_select_intuition.html:198-202]. A pass threshold for the AMX case is not measured yet (section 4).
- Host knobs outside the CLOS table that platformd should read and expose: intel_pstate (the Linux CPU frequency driver) in active mode, the performance governor (the kernel frequency policy), turbo on, uncore (the socket's cache mesh and memory controller, outside the cores) frequency range 0.8 GHz to 2.5 GHz [notebook/handoffs/claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1053]. BIOS or the OS image sets them, not platformd. All four read correct in June 2026 while the CLOS3 cap on the worker cores was active, so correct knobs do not prove the policy [notebook/handoffs/codex_2026-06-30_check-speed-select-config.md:35-54]. Pinning the uncore from 2.5 GHz to 1.6 GHz cost 6.2 % to 7.3 % decode. A BIOS cap would do the same and leaves no CLOS signature [notebook/artifacts/delphi-flat-freq/docs/flat_freq_tests-README.md:1789-1799].

**Expose**: applied/verified status, per-class CPU counts, the derived fast set, frequency under load, and package power. The shipped policy drew 48 W to 60 W more on socket 1 than the boot default, whole-run means [notebook/artifacts/intel-speed-select/results/sst-ab-20260917/summary.md:24-33].

## 4. Cross-cutting

- **Machine-type detection.** Match the map section the way tron does: vendor, physical core count, NUMA (non-uniform memory access, one node per socket here) node count, model pattern [tron/src/system/system.cpp:1221-1248]. Otherwise the policy and the engines can disagree on which section applies.
- **Per-engine settings key on the instance slot.** platformd may reassign which `rinzler@N` unit serves which `--instance` slot at a provisioning. The slot fixes the cards and cores [notebook/artifacts/delphi-flat-freq/docs/flat_freq_tests-README.md:1893-1895; notebook/artifacts/intel-amx/memory/p0perf-20260913-campaign.md:22-23]. A per-engine kill switch or class membership must be stated per slot.
- **Stale map cache.** platformd 0.10.7 reads the map once at startup with no watcher. The nightly's tron reinstall replaces the map and restarts nothing, so platformd keeps its cached copy. This caused two stale provisionings in July [notebook/handoffs/claude_20260722_resource-map-change.md:25,88-93]. Whether 0.11 still caches is not recorded.
- **Per-engine channel.** `instance-N.env` is the only per-engine setting platformd owns. If platformd ever needs a second channel, a unit drop-in under `rinzler@.service.d/` is the only form that survives the nightly's apt remove and install [~/.claude/projects/-home-jhan-workspace-intel-AMX/memory/rinzler-unit-expert-replicas-750.md:151-163].
- **AMX lowers the core clock.** Under a 1-user, 8K-to-16K prompt serving load on 2026-08-31 (arms that predate the shipped kernel), AMX-busy cores ran 3.52 GHz to 3.55 GHz against 3.75 GHz for AVX [notebook/artifacts/intel-amx/memory/amx-vs-avx-sense.md:50-54]. No run has measured the fast set with the CLOS policy active and AMX on at the same time. Insufficient data: a turbostat read during an AMX serving run. A CLOS0 pass threshold for AMX engines must come from that measurement.
- **CI schedule and platformd restarts.** The ci-runner stop timer (the systemd timer on delphi-3bda that ends the CI window) POSTs inference up at 02:45 UTC. The nightly reinstalls tron at about 03:39 UTC and holds the machine until about 13:18 UTC [notebook/artifacts/intel-amx/memory/ci-mimic-20260918-campaign.md:44-46,81]. Restarting platformd during reconciliation aborts it, and with auto_start=false (the setting that stops it resuming) it does not resume [notebook/handoffs/claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1233-1236]. A policy apply that restarts platformd, or runs from an outside unit during provisioning, must be excluded.
- **platformd's own cores.** At 0.10.7 platformd ran with affinity over all 288 CPUs and used about 34 % of one CPU while engines were down and health checks failed [notebook/artifacts/intel-amx/memory/l8bload-20260918-campaign.md:47]. Pinning it to `platform_cores` would keep that load off worker cores. Hypothesis, not measured: a worker-core TPS A/B with platformd pinned and unpinned would show the effect.
- **Same type, different policy.** Two 6962P hosts ran different core lists in July 2026 (tron80 on 3bda, tron112 on 3bd6) [notebook/artifacts/delphi-flat-freq/docs/flat_freq_tests-README.md:363-366,692-699]. Only a per-host read catches this.
- **Acceptance needs more than one night.** gpt-oss-120b decode varies between provisionings with a CV of 2.4 % (serving tests) to 4.7 % (77 draws) [notebook/artifacts/delphi-flat-freq/docs/flat_freq_tests-README.md:2344-2352; notebook/handoffs/claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:2034-2035]. Over 13 nightlies, gpt-oss tp4 and qwen-3-4b tp4 were the two noisy configs, and the other 10 had CV at most 0.73 % [notebook/artifacts/intel-amx/memory/ci-mimic-20260918-campaign.md:47-49].
