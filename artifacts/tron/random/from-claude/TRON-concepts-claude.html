TRON attention concepts: seventeen tokens, one pass

How attention, the KV (key/value) cache page, the sliding window, the visible range of K/V, and the minibatch fit together in TRON (the inference engine under study, which runs LLMs, large language models, on Positron FPGA hardware, a field-programmable gate array accelerator card, plus the host CPU). Generated by Claude Code on 2026-09-19 from the TRON source at commit 9b11a912ba (git branch main, 2026-09-08) in ~/workspace/tron. Every file reference below is relative to that clone.

Short version. One TRON forward pass (one call of full_scheduler::forward(), which runs every model layer once for the tokens that are due) serves two requests that share a 9-token prompt, so 17 tokens take part and 6 of them are queries (tokens whose K/V or logits, the raw next-token scores, must be computed this pass).

The traversal of the token tree (the prefix tree that stores every request's tokens, with the shared prompt stored once) numbers the tokens, lists the 5 KV cache pages (fixed-size blocks of cached K/V entries), and builds one ranged mask (this page's reading of the brief's "visible range of K/V") before the 6 queries are cut into 2 minibatches (groups of queries that move through the layers together).

Attention then runs once per layer per minibatch and reads each page through two filters in order: the mask (tree causality: a query may attend only to tokens on its own path from the root, measured in token_ids, the per-pass numbering in traversal order), and on the windowed layer only, the sliding window (how recent the entry is, measured in positions, a token's depth in its own sequence).

Scope. The mock (the scaled-down example pass that every figure follows, defined in section 1) has no FPGA. Hardware attention differs from the mock in two places, both marked where they occur. On layers without a window, the attention routine tests each entry with the software-only mask instead of the union of both masks (section 6). Windowed layers never run on the FPGA (section 7).

1. The mock pass used in every figure

Every figure on this page follows the same forward pass. Using one fixed example lets you track the same 17 tokens through the tree, the pages, the mask, the minibatches, and the kernel (the routine that computes attention for one minibatch).

A live token is a token in this pass's context. All 17 tokens here are live. A live entry is a page slot that holds a live token.

  • Request B is decoding (it produces one new token per pass). It arrived first. Its sequence is the shared prompt s0..s8 (9 tokens whose K and V, the key and value vectors of attention, are already cached), then b0 and b1 (cached), then b2 (chosen as B's output token in the last pass, new this pass). B wants logits (the next-token scores) at b2.
  • Request A is prefilling (its new prompt tokens still need K and V). It arrived later with 5 new prompt tokens a0..a4 after the same shared prompt. A wants logits at a4.
  • The tree has one root edge S (the shared prompt) and two child edges, B and A.
    • Edge B continues S's book X. Before request A arrived, s0..s8, b0, b1 were one edge of request B, because decode tokens are appended to the same edge [h/tron/scheduler/full.hpp:727]. A's matching prefix split that edge after s8 [h/tron/scheduler/full.hpp:549-553].
    • Edge A is a new branch. It gets a new book Y. At most one child of a node can share its parent's book [h/tron/scheduler/token_tree.hpp:426].
    • The traversal visits B before A because B was inserted first. This order determines every number below. Reordering changes the token_ids of b0..b2 and a0..a4, every mask string, and both minibatches.
  • The model has 2 attention layers. Layer 0 is full causal (every query may read every earlier token on its path, window INT_MAX). Layer 1 has sliding window W = 6 positions. One KV head (one K and one V vector per token per layer), no FPGA.

A kv_ready flag on each token records whether a K/V job for that token has already been scheduled. It is false when the token is inserted [h/tron/scheduler/full.hpp:750]. It flips to true when the traversal schedules the token's K/V job, before the model computes anything [h/tron/scheduler/full.hpp:2132-2135]. If the pass has no room left, the flag stays false and the token waits for a later pass. The 6 tokens with kv_ready = false become the queries of this pass [h/tron/scheduler/full.hpp:1876].

The traversal numbers everything

The traversal is a depth-first walk of the tree by compute_forward_args [h/tron/scheduler/full.hpp:1990]. It is post-order. An edge's range-building step (the ascent, section 4) runs as soon as that edge's children are done. Descent and ascent therefore interleave. The descent visits S, then the first child B, then A. It gives every live token a token_id (its index in tokens[]), records its position and its page, and turns every token with kv_ready = false into a query with a token_job_id. It pushes each page onto kv_pages[] at the page's first entry and sets the page's lo there [h/tron/scheduler/full.hpp:2117].

Four numberings appear here. Keep them apart: position (depth in the sequence, persistent), token_id (traversal order, per pass), token_job_id (query index and mask bit, per pass), and later batch_job_ix (slot inside a minibatch).

2. Who owns what: the ownership tree

The five concepts have different owners at different depths. The page belongs to the persistent token tree. The sliding window's value belongs to persistent model state (the per-model object that outlives passes). The mask, the minibatches, and each attention run belong to one forward pass. full_scheduler (the per-model scheduler) is the first box that contains all five. The forward pass is the first box that contains the three per-pass concepts.

3. KV cache page: persistent storage, two per-pass numbers

A page is a fixed-size block of KV entries in a book. In code a page holds 64 entries [h/tron/models/kv_cache.hpp:1164]. The mock uses 4 entries per page. That makes page boundaries visible in the figures. The book owns the memory [h/tron/models/kv_cache.hpp:74-75]. It creates all its page objects at construction, and page_of(entry) is pages[entry / 64] [h/tron/models/kv_cache.hpp:790]. Books and pages are freed only by token-cache eviction: when host memory use is over its target, when an allocation fails, or when a request releases nodes that no other request holds [src/tron/scheduler/token_cache.cpp:125-159; :509; doc/memory_pressure_governor.md:7-8]. A forward pass never frees them [h/tron/scheduler/full.hpp:1700-1724].

Two fields on the page are per pass. lo is the token_id of entry 0 for this pass. Entry i therefore has token_id lo + i [h/tron/models/kv_cache.hpp:1227]. count() is the number of live entries this pass. The kernel reads entries [0, count()) only [h/tron/models/self_attention.hpp:1403]. Between passes both values are stale.

A page is pending in a pass when some query writes K and V into it this pass. Every other page is ready [h/tron/models/model.hpp:1897]. Attention over ready pages can start as soon as the query vectors exist. Attention over pending pages waits for the K/V writes through a countdown latch (a counter that releases the waiting attention work when all expected K and V writes have finished) [h/tron/models/model.hpp:1979].

A page is a per-pass object, or its lo and count are stable properties of the cached data, or the FPGA's 128-token page is the same thing.

Correct picture

The page and its bytes persist in a book across passes. Only lo and offset_bound (the field behind count()) are overwritten by every traversal [h/tron/models/kv_cache.hpp:1475]. The FPGA units are copies with their own sizes.

4. Visible range of K/V: one ranged mask per pass

The phrase "visible range of K/V" from the brief does not occur in the TRON source tree (the repository). This page reads it as the ranged mask. The mask is the only mechanism that decides which K/V entries a query may read [h/tron/models/kv_cache.hpp:96]. The older mechanism, a per-page high bound, was removed and only survives in old documents (see Insufficient data).

The ranged mask is one sorted, gap-free list of token_range spans [tok_lo, tok_hi) over token_ids [h/tron/models/ranged_mask.hpp:98-99; :214; :218]. Each span carries two disjoint bitmasks indexed by token_job_id: SW_REQUIRED (software must compute these queries) and HW_AVAILABLE (the FPGA could compute them) [h/tron/models/ranged_mask.hpp:96]. Each mask has room for 4096 queries [h/tron/models/ranged_mask.hpp:20].

visible(job) is true when the query's bit is in either mask [h/tron/models/ranged_mask.hpp:159]. It answers one question: may this query attend to these entries at all. The traversal lays tokens out depth first. So a query sees exactly its ancestors and itself. It never sees a sibling branch and never sees a later token on its own edge. The page-level gate (the test that admits or skips a whole page) in the kernel always uses visible(). Inside a page the kernel uses visible() in two cases: on a windowed layer, or when the layer does not use the FPGA. In every other case it uses sw_required() [h/tron/models/self_attention.hpp:1299-1303; :1406].

The mask is built on the ascent of the traversal, one edge at a time, as soon as the edge's children are done. For each edge, build_edge_ranges pops that edge's queries highest token first. Each pop closes the range above it and then adds the popped query's bit for the popped token and every lower token of the edge [src/tron/models/ranged_mask.cpp:42]. A query therefore sees itself and its ancestors on the edge. A parent ORs (combines with bitwise or) its children's masks into its own before it builds its ranges [h/tron/scheduler/full.hpp:2809]. A shared prefix is therefore visible to every descendant query. In the mock the FPGA is absent. HW_AVAILABLE is zero everywhere, and visible() equals sw_required().

Takeaway: one mask per pass, indexed by token_id and token_job_id. Range boundaries follow tree edges and queries, not page boundaries: range [0,9) spans P0, P1, and entry 0 of P2, and page P2 spans two ranges.

Bits are token_job_ids, not positions: a0 is bit 1 at position 9. Row b2 has bits on s0..s8 and b0..b2 only, never on a0..a4 (sibling branch). The mask says nothing about recency. Recency is the window's job. With FPGA shards present, forward() edits the finished mask once more and moves some bits from HW_AVAILABLE back to SW_REQUIRED [h/tron/scheduler/full.hpp:1794-1834].

Common confusion

Visibility is stored on each page as a high bound, or it is per minibatch, or it is indexed by position, or it already includes the sliding window.

Correct picture

There is one ranged mask per forward pass, built before any minibatch exists. The page struct has no visibility field. Pages reach the mask through token_id = lo + offset. The kernel gates a page on its first entry's range [h/tron/models/self_attention.hpp:1303], then walks ranges inside the page [h/tron/models/self_attention.hpp:1412]. The window is a separate second test.

5. Minibatch: a cut of this pass's queries

A minibatch (q_batch, struct batch) is a subset of this pass's queries [h/tron/models/common.hpp:880]. It exists so that the CPU attention of one minibatch can overlap the FPGA matrix multiplications of another [h/tron/models/model.hpp:223]. It is not a request, not a set of requests, and not the context tokens. The mock has no FPGA and still gets 2 minibatches. chunk_evenly never checks for hardware. It only looks at query count and labels [h/tron/models/model.hpp:185].

chunk_evenly builds the minibatches after the mask is final [h/tron/models/model.hpp:1740; :1767]. It works in four steps [h/tron/models/model.hpp:185-261]:

  • It groups queries by a tree-affinity label. An edge with new tokens (kv_ready = false) under a node that also has new tokens inherits the parent's label. An edge with new tokens under a node whose tokens are all cached starts a new label [h/tron/scheduler/full.hpp:2142-2144]. In the mock S is cached. B and A therefore get separate labels, gB and gA.
  • It cuts each group into grains of at most minibatch_grain_size queries (8 in code, 2 in the mock). The greedy merge below never splits a grain.
  • It keeps the even and odd offsets of one page in the same grain. The reason is that set_v writes both in one SIMD value (one CPU vector register that holds several entries) [h/tron/models/model.hpp:208].
  • It merges grains one at a time (greedily: a merge is never undone) toward ceil(n / max_minibatch_size) chunks, where n is the query count. If that target is 1 chunk and there is more than one label or more than one grain, the target is raised to 2 [h/tron/models/model.hpp:221-225]. If one chunk still remains after the merge, it is halved [h/tron/models/model.hpp:244-252]. A lone chunk cannot overlap with anything.

A query keeps its token_job_id (its mask bit) whatever minibatch it is placed in. Inside the minibatch it also gets a batch_job_ix, its position in items[] (the minibatch's list of token_job_ids). That index selects its scratchpad slot (the row in a worker's thread-local buffer that holds this query's partial attention result) [h/tron/models/self_attention.hpp:1243].

Mock cap 4 and grain 2 are scaled down together. The code requires cap ≥ grain [h/tron/models/model.hpp:191]. Real values: cap 128 [h/tron/plugins/llama.hpp:184], grain 8 [h/tron/models/common.hpp:355]. Generated plugins (plugin code that the ingest tool writes from a PyTorch model, unlike the hand-written llama plugin) force one minibatch of up to 1024 queries [ingest/src/TronCpp.hs:263-264]. The stated reason is that their generated run() processes batches one after another, and the matmul (matrix multiplication) launchers and the attention state are shared [ingest/src/TronCpp.hs:1093-1101]. The reason is not that FPGA attention forbids several minibatches.

Each minibatch gets its own page list

select_relevant_pages (the page filter) builds one page list per minibatch and per layer profile (layers with the same kernel geometry, window value, and hardware use share one profile). Kernel geometry means the query-head count, the KV-head count, and the head size. It keeps a page only if some query of that minibatch has its bit set in the range of the page's first entry. On a windowed layer that query must also pass the page-level window test: q_position − (first position of the page + count) < W, where first position + count is one past the page's newest entry [h/tron/models/model.hpp:2415-2427]. Different minibatches can therefore see different page lists for the same layer. kv_pages[] itself is never trimmed.

Why minibatches exist

Takeaway: the llama plugin's loop is layer-major and batch-minor [ingest/src/TronCpp.hs:1098-1099]. For each layer, for each minibatch, it runs WO (the output projection), the norm (layer normalization, a rescaling of the hidden vector) and the MLP (the feed-forward block), then the next layer's WQ (query projection) and K/V jobs for that minibatch [h/tron/plugins/llama.hpp:647-697]. While the main thread and the FPGA do this for one minibatch, the attention workers run the other minibatch's attention on the CPU. With one minibatch nothing overlaps. That is why a lone chunk is split in two.

Order follows the code. Durations are schematic. No per-step timing was measured. Solid blocks are work. The dashed outline is waiting for the pending pages' K/V writes. Before a minibatch reads pending pages, it waits for the K and V writes of every minibatch that holds a token in a page visible to it, itself included. In the mock kvs_needed = 4 K/V writes for both minibatches: 2 producer minibatches × K and V [h/tron/models/model.hpp:1979; h/tron/models/common.hpp:1004].

Common confusion

A minibatch is a request, a set of requests, a training batch, or the set of context tokens. It exists before, or independently of, the ranged mask.

Correct picture

A minibatch is a subset of this pass's queries, cut from token_jobs[] after the mask is final. One minibatch may hold queries from several requests, and one request's prompt may be split across minibatches. Each minibatch has its own page lists, attention plans (the split of its attention work among worker threads), Q/O channels (the buffers that carry its query rows in and its output rows out), and dependency latches. It lives for exactly one pass [h/tron/models/model.hpp:1881; h/tron/models/model.hpp:1826].

6. Attention: the kernel where the four meet

Attention runs once per (attention operation, minibatch). In the hand-written llama plugin the worker threads loop over operations in the outer loop and over minibatches in the inner loop [h/tron/models/self_attention.hpp:835-848]. Generated plugins run one minibatch per pass [ingest/src/TronCpp.hs:1093-1101] and call the kernel directly once per operation [h/tron/models/self_attention.hpp:835-836]. Each worker receives page ids in kv_sections (one unit of worker work: one KV head plus a list of page ids). It never sees books or the tree [h/tron/models/common.hpp:735]. For each page and each query of the minibatch it asks, in this order:

  1. Page gate. Is the query visible in the range that covers the page's first entry? If not, skip the page. This gate always uses visible() [h/tron/models/self_attention.hpp:1299-1303].
  2. Whole-page window test. Is even the page's newest live entry too old for the query? If q_position − (k_position + count) ≥ W, where k_position is the position of the page's entry 0, skip the page [h/tron/models/self_attention.hpp:1306]. On a full layer W is INT_MAX and this never fires.
  3. Entry loop over offsets [0, count()). When the entry's token_id crosses tok_hi, advance to the next range and re-read visibility [h/tron/models/self_attention.hpp:1412]. If the query is not visible in this range, jump to the range's end [h/tron/models/self_attention.hpp:1419]. If q_position − k_position ≥ W, skip this entry [h/tron/models/self_attention.hpp:1422]. Otherwise compute the dot product and keep it in a per-page score row. 7. Sliding window: a second filter, measured in positions

The sliding window is one optional integer on an attention operation's config [h/tron/models/kv_cache.hpp:197-198]. It is copied into attention_runtime_configs (the small per-operation record that model state keeps for the kernel) when model state is built. A missing value becomes illegal_sliding_window = INT_MAX [h/tron/models/model.hpp:660; h/tron/models/self_attention.hpp:196]. Its parent is the attention operation, not the model, not the page, and not the mask.

Real models set it per layer from the model config's layer pattern. GPT-OSS (an OpenAI open-weight model that TRON serves) alternates windowed and full layers. Its 120B (120 billion parameter) variant has 36 layers, so 18 are windowless and FPGA-eligible [comment at src/tron/gof.cpp:96; layer count in ingest/traces/ingested-gpt-oss-120b/metadata.json]. A Gemma 4 (Google model) test fixture uses full attention on every sixth layer [t/t_llama_unit.cpp:173].

The window is a position test, applied after the mask, at three points: per-minibatch page selection [h/tron/models/model.hpp:2415], the whole-page skip in the kernel [h/tron/models/self_attention.hpp:1306], and the per-entry skip [h/tron/models/self_attention.hpp:1422]. Distance is measured in sequence positions, not token_ids, so two sibling branches at equal depth are equally near. A windowed operation is never sent to the FPGA [h/tron/models/self_attention.hpp:482-490]. Its kernel therefore always tests visible() [h/tron/models/self_attention.hpp:1285].

The traversal, kv_pages[], and host KV memory do not change for a window. Two things do change: a windowed layer gets its own attention plan profile, and each minibatch gets a trimmed page list for it [h/tron/models/model.hpp:1509; :2415]. What the window saves today is dot products per query (the paired-dot chart below) and FPGA memory for layers that never use the hardware. No host KV memory is freed.

Takeaway: for b2 (position 11) on layer 1:

  • Q0 fails the mask gate. Q1 is not in MB0's page list at all (dropped at page selection, also by the mask).

The whole-page test uses count, one past the last live entry. The test therefore lets one extra page through: it may enter a page whose entries are all outside the window. Common confusion

A sliding window frees or evicts old KV pages, shrinks kv_pages[], is encoded in the ranged mask, or is a model-wide setting measured in token_ids.

Correct picture

The window is one integer per attention operation. It is a position test applied after the mask at three points. The traversal and kv_pages[] never change for it. b2 (token_id 11) and a0 (token_id 12) are neighbours in token_id but 2 positions apart (11 vs 9), so the same W reaches different tokens for them.
