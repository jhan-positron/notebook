TRON multi-user attention: how one decode pass spreads every user's attention across CPU cores and FPGA cards

Answer to a question logged at Ben Gamari's bootcamp talk "103: Why Inference Is Expensive" (16 October 2026), slides 32 to 34. The slide deck is on Google Drive at drive.google.com/file/d/1Ko2_5VUn9z-SGfhBcCCZYZIDDJKpjAIo. Written by Claude Code on 2026-10-19 from the TRON source at commit e6c53ba7 (branch main, 2026-09-23) in ~/workspace/tron. Every file reference is relative to that clone. Updated 2026-10-21: slide link added, and section 4 (what a minibatch is) added.

Short version. TRON never runs attention one user at a time. On the CPU, all users' KV pages form one list per KV head, the planner cuts that list into equal-work pieces for the attention worker threads, and a visibility mask keeps each query on its own user's pages. On the FPGA, each user's context sits in 1,024-token shards spread round-robin over the cards, so different users' attention commands run on different cards at the same time.

1. What Ben's slide 33 says, and why the question follows

Slide 33 states the two halves of the batching story in one line each. "Weight matmuls: one read of the weights serves every request in the batch." "Attention: each request reads its own KV cache, alone." [slide 33 of the talk]. The deck is on Google Drive [drive.google.com/file/d/1Ko2_5VUn9z-SGfhBcCCZYZIDDJKpjAIo].

The projection step multiplies each user's hidden vector by the Q, K and V weight matrices. Stacking four users' vectors as rows lets one weight read serve all four. Attention has no shared operand. User A's query meets user A's keys and values, which no other user needs. So there is nothing to batch, and the only lever left is to spread the work over more hardware. The rest of this page shows where TRON spreads it.

Takeaway: the left side has one shared box (the weights). The right side has four separate boxes and nothing between them. That absence is the question.

2. What a "user" is inside one decode pass

  • Each active request adds one new token to the pass, so a pass with four decoding users has four queries. The scheduler collects them in one depth-first walk of the token tree [doc/attention-scheduling.md, section 1].
  • The walk writes every visited token into one flat list, tokens[], and every KV page it may read into kv_pages[] [doc/attention-scheduling.md, sections 1.3 and 2.1].
  • A ranged mask records, for each range of tokens, the set of queries that may read it [doc/hw-kv-attn-work.md]. Pages on user A's branch carry a bit for A's query only. Pages of a shared prefix carry bits for every user under it.
  • The attention kernel never asks "which user". It asks "may query j read this range" [h/tron/models/self_attention.hpp:1503].
shared prefix Suser Auser Buser Cuser Dmask bit set: the query may read the page

Takeaway: the pass sees 11 pages and 4 queries, not 4 users. The mask is the only place where "user" survives, as a pattern of bits.

Mock sizes: 2 shared pages and 2, 4, 1 and 2 private pages. Real pages hold 64 entries each [h/tron/models/kv_cache.hpp:1713]. One KV head is drawn.

3. The CPU path: one page list per KV head, cut across workers

The design note in the kernel states the plan. The kernel iterates by KV page, not by query, and "processes all the relevant query positions for each KV-cache page". It parallelizes "over KV heads" and "along the KV-page dimension" [h/tron/models/self_attention.hpp:1287-1372]. Five steps turn that into threads.

  1. One page list per minibatch and per KV head. select_relevant_pages keeps a page when at least one query of the minibatch may read it. It ranks each page by the first query that sees it and sorts by that rank [h/tron/models/model.hpp:2340-2393]. Queries are in walk order, so the sorted list comes out grouped by user: shared pages first, then A's pages, then B's, and so on.
  2. Work per page. estimate_work counts, for every page, the dot products each query needs over it [h/tron/models/model.hpp:2395-2470]. A shared page read by four queries costs four times a private page.
  3. The cut. finish_sw_plan walks KV head by KV head and page by page. It moves to the next worker when the running work total crosses that worker's share [h/tron/models/model.hpp:2719-2790]. The shares come from the measured speed of each worker thread [h/tron/models/model.hpp:2233-2250]. Each worker ends with one or more kv_sections: one KV head plus a run of pages [h/tron/models/common.hpp:696-706].
  4. Run. Each worker loops over its sections [h/tron/models/self_attention.hpp:1098-1121]. For each page it loops over every query of the minibatch and asks the mask whether that query may see the page [h/tron/models/self_attention.hpp:1500-1503]. Only the owner's query, and any shared-prefix readers, pass the gate. The page's K and V bytes then serve each passing query in turn. The four query heads of one GQA group are handled inside that call [h/tron/models/self_attention.hpp:1287-1372].
  5. Join. Each worker holds a partial softmax state (m*, s*, v*) per query and head. The join reduces the partials from every worker into worker 0's scratchpad and writes the output rows. The join is parallel across queries, and each worker joins only the KV heads it computed [h/tron/models/self_attention.hpp:1134-1200].
shared S (4 queries read it)ABCDnumber in a box = work units (queries that read the page)

Takeaway: no worker is "user A's worker". Worker 0 serves four users on head 0 (the shared pages plus A's first page). Worker 1 serves A, B, C and D on head 0. User A's head-0 pages straddle workers 0 and 1, so A's head-0 result is joined from two scratchpads. User parallelism is a by-product of page parallelism, balanced by work, not by user count.

Work-weighted cut, schematic. The real planner weights each page by its estimated dot products and the worker's measured speed, and it orders pages that receive new K/V this pass after the ready pages of the same head [h/tron/models/model.hpp:2762-2790]. Four workers of equal speed are drawn.

When the FPGA has taken most of the context, or a sliding window has trimmed it, there can be fewer pages than workers. The planner then splits single-page sections by query range, so several workers serve the same page for different queries [h/tron/models/model.hpp:2793-2850].

Common picture

Each user's attention is a task. TRON hands user A to one thread, user B to another, and so on. With more users than threads, users queue.

What the code does

Each (KV head, run of pages) is a task. Users are invisible below the mask. A long context is cut across several threads. Several short contexts share one thread. The cut follows estimated work.

4. What a minibatch is

A minibatch is a subset of the queries of one pass that moves through the model's layers as one unit. In the code it is one struct batch object, and the list of them is named q_batches for historical reasons [h/tron/models/common.hpp:956-962 and 991]. The design note warns that the word is "not to be confused with numerous other ways in which 'batching' is used in ML" [h/tron/models/common.hpp:938-939]. ML means machine learning.

  • Not Ben's batch. The slides use "batch" for the set of requests served together. In TRON that set is the whole pass. A minibatch is a cut of that pass.
  • Not a request. One minibatch can hold several users' queries. One long prompt can be cut across two minibatches.
  • Why it exists. The FPGA runs the matmuls and the CPU runs attention. With two minibatches the FPGA can run the matmuls of one while the CPU runs the attention of the other [h/tron/models/common.hpp:930-942]. With one minibatch each side waits for the other.

How a pass is cut into minibatches

  1. Label. During the tree walk the scheduler gives every token of the pass a group label. A token whose parent is also computed in this pass inherits the parent's label. Any other token starts a new label [h/tron/scheduler/full.hpp:2387-2389 and 2471-2473]. In a decode pass each user's new token sits under a cached parent, so each user gets its own label. In a prefill pass (the pass that processes a new prompt) one prompt chunk shares one label. The label is a cheap stand-in for "these tokens share KV pages" [h/tron/models/model.hpp:198-203].
  2. Grains. chunk_evenly collects the tokens by label and cuts each group into grains of at most 8 tokens. A grain is never split again [h/tron/models/model.hpp:217-230; h/tron/models/common.hpp:310-315]. One fix follows: the even and odd token offsets of one KV page must stay in the same minibatch, because the V write packs the pair into one SIMD (single instruction, multiple data) register value [h/tron/models/model.hpp:232-237].
  3. Target count. The target is the query count divided by the plugin's cap, rounded up. The cap is 128 queries in the hand-written llama plugin [h/tron/models/model.hpp:240; h/tron/plugins/llama.hpp:184]. A target of 1 is raised to 2 when the pass has more than one label or more than 8 tokens, "to enable FPGA-vs-CPU latency hiding" [h/tron/models/model.hpp:245-249]. The runtime flag --max-minibatches can cap the count, and its default of -1 means no cap [h/tron/models/config.hpp:62; src/runtron.cpp:1034]. Generated (ingested) plugins set a cap of 1 minibatch of up to 1,024 queries [ingest/src/TronCpp.hs:262-263].
  4. Greedy merge. Grains are visited in order. A grain joins the current chunk when the chunk stays under the cap and the new size is at least as close to the target size as the old size. Otherwise the grain starts the next chunk [h/tron/models/model.hpp:250-265]. If one chunk comes out and it holds more than 8 tokens, it is split in half [h/tron/models/model.hpp:267-276].
  5. Objects. batch_evenly turns each chunk into one struct batch whose items are the chunk's token jobs. Each creation is a "Create minibatch" trace event [h/tron/models/model.hpp:344-367].

Takeaway: four decode users become two minibatches of two users. One 20-token prompt becomes two minibatches of 8 and 12 tokens. The cut follows labels and grains, not users.

Computed with a Python mirror of chunk_evenly (same rules, without the even/odd pair fix), not observed in a TRON run. The fix changes nothing here if the prompt starts at an even page offset. Mirror: TRON-multiuser-attention-chunk-mirror.py next to this page.

What one minibatch holds

Takeaway: a minibatch is more than a list of queries. It carries its own layer counter, its own attention plans and FPGA passes, and the latches that let the main thread and the attention workers hand work to each other.

How minibatches move through the layers

  • Each minibatch carries its own layer counter. The field comment gives the picture: "batch A can compute e.g. attention in layer 2 while batch B computes feed-forwards in layer 1" [h/tron/models/common.hpp:1083-1086].
  • The main thread's loop is layer-outer and minibatch-inner. For each layer it visits every minibatch in turn and launches that minibatch's output projection and feed-forward on the FPGA. The code calls this "alternating feed forwards of one q_batch with attention of the next" [h/tron/plugins/llama.hpp:650-659 and 86-95].
  • The attention workers loop over attention operations, then over minibatches, then over the tokens of the minibatch [h/tron/plugins/llama.hpp:56-67].
  • A query in one minibatch can need a K or V that a token in another minibatch writes in this pass, for example when a prompt is cut into two chunks. Three fields per minibatch track that: which minibatches to notify, how many K/V producers to wait for, and how many have finished [h/tron/models/common.hpp:964-989 and 1143-1154].
  • Each minibatch gets its own page list per layer profile and its own attention plan, as section 3 describes [h/tron/models/model.hpp:2340-2393; h/tron/models/common.hpp:1100-1128].

5. Minibatch level: two groups of users take turns on the CPU and the FPGA

  • Section 4 shows the cut. Each decoding user gets its own label, and a pass of 2 to 128 such users is cut into two minibatches of near-equal size [h/tron/models/model.hpp:240-265]. Generated (ingested) plugins pin the count to 1 [ingest/src/TronCpp.hs:262].
  • So a hand-written llama-plugin pass with four decoding users runs two minibatches of two users each. While the attention workers compute minibatch 0's attention on the CPU, the main thread and the FPGAs run minibatch 1's matmuls. Then the roles swap [h/tron/models/common.hpp:928-960, Note Mini-batching].
  • The attention workers are the last pool threads. Their count is the pool size minus the main helpers [h/tron/models/model.hpp:2233-2250]. The split is pinned at 2/7 of the pool to main helpers when there is one minibatch or in determinism mode, and otherwise autotuned to equalize the predicted CPU attention time and main-thread time [h/tron/models/model.hpp:1977-2016]. At most half the pool goes to main helpers [h/tron/models/model.hpp:76-78].

Takeaway: this is the second level of multi-user parallelism. Users in minibatch 0 are in attention while users in minibatch 1 are in projection, and then they swap.

Schematic only. Block order follows the code. Durations are not measured and are not to scale.

6. The FPGA path: shards spread across cards

  • The FPGA attends only on full-causal layers, and only over positions at or above the engagement point, 127 by default. Everything below stays on the CPU [h/tron/models/self_attention.hpp:487-494; h/libpos.hpp:85-91].
  • A context's FPGA-eligible K and V are stored in shards of 1,024 tokens. Each shard lives in the HBM of one card [h/tron/shard.hpp:1-30; h/tron/gof.hpp:36]. The scheduler picks the card round-robin when it creates the shard [h/tron/scheduler/full.hpp:1924-1925 and 2545-2583]. Consecutive shards of one context therefore land on different cards.
  • construct_hw_plan groups a context's shards by card, cuts each card's group into chunks of at most the on-chip memory limit (4 shards, 4,096 tokens), and makes one pass per (card, chunk) [h/tron/models/model.hpp:2486-2612; h/tron/models/common.hpp:742-751]. A pass is one command on one card.
  • Several queries share one pass only when they have the identical shard list on that card and their end positions are equal or adjacent, up to 32 queries per pass [h/tron/models/model.hpp:2604 and 2646-2700; h/libpos.hpp:32]. Independent decoding users never meet that test, so each has its own passes. Users that share a prefix can ride one command over the shared shards [h/tron/models/model.hpp:2570-2576].
  • One loop launches every pass of the layer. Each card retires its passes in launch order, and the CPU join folds each pass's partial result in as it completes [h/tron/models/self_attention.hpp:676-685; h/tron/models/common.hpp:772-776].
card 0card 1card 2card 3CPU: positions below 127 and the newest partial shard

Takeaway: the FPGA parallelism is also not per user. It is per (card, shard chunk). User A's 5 shards become 4 passes on 4 cards. Users B and C add passes that land on the other cards. All passes launch together.

Placement is illustrative. The round-robin index advances on every shard creation across all users, so the exact card of a given shard depends on history [h/tron/scheduler/full.hpp:2545-2583]. Three users with 5, 3 and 2 shards are drawn, no shared prefix.

7. What TRON does not do, and what that costs

  • There is no cross-user matmul in attention. The projection stacks users as rows of one matmul. Attention never stacks users into one operand, because each user has different K and V.
  • The only cross-user sharing is a shared-prefix page or shard. The CPU kernel visits such a page once per worker and serves every query that may read it [h/tron/models/self_attention.hpp:1494-1560]. The FPGA planner can put several users' queries on one command over the shared shards [h/tron/models/model.hpp:2570-2576].
  • Total attention work in a pass is the sum over users of context length times KV heads. Parallelism cuts wall time, not bytes. That is slide 34 of the talk: "KV cache reads dominate once batch size × context passes about 10k tokens" [slide 34].

8. Insufficient data

  • Attention worker count on a given server. It depends on the thread-pool size and the autotuned split. Resolving measurement: the pool size from app_pool().num_workers() and the main-helper count from a Perfetto trace of one pass on delphi-3bda.
  • Time per step of a decode pass. No trace was taken for this page. Resolving measurement: a Perfetto trace of one 4-user decode pass [README.perfetto.md].
  • Concurrency of the four cards' attention passes. The launch is one loop and each card retires in launch order, but the overlap between cards is not measured here. Resolving measurement: per-pass launch and completion timestamps from the same trace.
  • Minibatch sizes in a real pass. The worked examples in section 4 are computed from a mirror of chunk_evenly, not observed. Resolving measurement: the "Create minibatch" trace events of one pass in a Perfetto trace, one per minibatch [h/tron/models/model.hpp:362], read together with each minibatch's item count.
  • Shared-prefix savings on the CPU path. Counters exist behind TRON_PAGE_SHARE_COUNTERS [h/tron/models/self_attention.hpp:1431-1571] and were not run.

Words used here

TRON
Positron's inference engine. It runs LLM (large language model) forward passes with the host CPU and the Positron FPGA (field-programmable gate array) cards.
decode pass
One forward pass that produces one new token for every active request. One call of full_scheduler::forward().
user, request
One conversation being served. Inside a pass TRON has no user id. A request is a branch of the token tree.
token tree
The structure that stores every active conversation as a path from a shared root, so a common prompt is stored once.
KV cache page
A block of 64 key/value entries for one layer, held in host memory. The unit the CPU attention kernel works in.
KV head, GQA
One key/value head. With grouped-query attention (GQA) one KV head serves several query heads, 4 in Llama 3 8B.
minibatch
A subset of this pass's queries that moves through the layers together. Not a request and not a training batch. Section 4 explains how it is built.
label, grain, chunk
The three stages of the cut in section 4. A label marks tokens that share KV pages. A grain is a run of up to 8 tokens of one label that is never split. A chunk is a merged run of grains that becomes one minibatch.
attention worker, main helper
Thread-pool threads. Attention workers run CPU attention. Main helpers feed the FPGA matmuls and do the other CPU work.
kv_section
One unit of attention-worker work: one KV head plus a run of pages, and optionally a query sub-range.
ranged mask
A per-pass table saying which queries may read which token ranges. It encodes causality and user isolation.
join
The reduction that merges partial softmax states (running maximum m*, running sum s*, weighted value sum v*) from several workers or FPGA passes into one result per query head.
shard
1,024 consecutive tokens of one context whose K and V live in the HBM (high-bandwidth memory) of one FPGA card.
engagement point
The first sequence position the FPGA may attend over, 127 by default. Positions below it stay on the CPU.
pass (FPGA)
One FPGA attention command: one card, up to 4 of its shards, and the queries that share them.
TP4
Four FPGA cards serving one model, with the weight matrices split among them.
matmul
Matrix multiplication. The projections and the FFN of each layer are matmuls, and TRON runs them on the FPGA.
FFN
Feed-forward network: the matmuls of a layer that follow attention.
prefill pass, decode pass
A prefill pass processes a new prompt, many tokens of one request at once. A decode pass adds one token per request.
Perfetto
The trace format and viewer that TRON's trace events go to [README.perfetto.md].
runtron
The TRON command-line runner, src/runtron.cpp.
