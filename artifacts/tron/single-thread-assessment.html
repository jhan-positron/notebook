One Thread Per Core: what the proposal changes, and what it does not

Assessment of the idea in input-2-ai/single-thread.md: keep one tron thread per CPU core, make every software thread "truly single-threaded" (no thread launches other threads), keep concurrency only between cores. Motivation given: less concurrency complexity, less randomness in execution order. Evidence is the tron source at main (68783a17d) plus the July 2026 delphi-3bda measurements in the notebook.

Verdict in one screen

The premise is mostly already true. On the app side tron already runs exactly one pinned thread per core: app_pool() creates app_cores − 1 workers, each bound to its own core for the life of the process, and the workers never create threads. The places where two tron threads share a core are few and specific: the TX/RX pair per FPGA on SMT siblings (by design), the unpinned front-end threads (rinzler main, 8 drogon IO threads, and the work_queue coordinator) that share the taskset cores, TBB's hidden pool on the HT peers of app cores, and a handful of monitoring threads on platform core 0.

The complexity and randomness the proposal wants to remove do not live in thread topology. They live in (1) the synchronization graph of one forward pass — channels, tensor latches, barriers, DMA rings — which connects threads on different cores and stays unchanged when each thread is "single-threaded", and (2) timing-dependent decisions (speed-weighted attention plans, arrival-time batching, KV pagination, floating-point reduction order) that tron already documents in Note [Paying for Determinism] and partly controls with cfg.pay_for_determinism.

Reading A · no SMT sibling pairs
Possible, small, needs an A/B

Merging TX and RX into one thread per FPGA removes one deliberate two-threads-per-core case, but a naive merge deadlocks (TX blocks on counters that only RX returns), the freed sibling hardware thread is in no resource-map list (no capacity gain), and RX runs model callbacks that would then delay launches. Latency effect unmeasured. Does not touch the forward-pass sync graph.

Reading B · static thread creation, no hidden pools
Recommended hygiene

Create the pool and the coordinator eagerly at startup and keep TBB out of the serving path (a serial init path already exists). Removes lifecycle races (one already documented) and a hidden thread team. Coordinator pinning is a separate, measured change: the one placement A/B on record lost 1.7% decode. No change to output randomness.

Reading C · independent single-threaded pipelines per core
Not compatible with the design

The FPGA processes one shared batch; attention is split across all cores of that batch. Per-core independent pipelines would need per-core batches (weights streamed per pipeline) or the same cross-core sync graph under another name. From measured duty cycles, serializing attention per user is est. ≥3× slower at 8 users. Determinism gain: none beyond pay_for_determinism.

Section 5 lists where the randomness actually comes from, Section 6 where the complexity comes from, and Section 7 the recommendation with the measurements to run before any of this is changed. Section 8 records what the independent review confirmed, qualified, or refuted.

2. How the threads cooperate inside one forward pass

The proposal keeps "concurrency between threads on different cores". Figure 2 shows that this is exactly where all of tron's synchronization already is: every edge in the forward pass connects threads on different cores. No thread creates a thread during a forward pass; thread_pool::enqueue_to hands a lambda to a worker that is already running and pinned (threading.hpp:783-786, 820-828). In generated plugins the coordinator does no helper-kernel work at all (Note [Main Thread Skips Helper Kernels], ingest/src/TronCpp.hs:1855-1866): it dispatches, and the pinned workers compute. The RX driver thread is also a participant: matmul completion callbacks run on it, including RoPE-K and the K/V page writes (worker.cpp:611-618, llama.hpp:922-939).

Wall-clock view of one decode iteration

Figure 3 puts the same actors on a time axis, using the durations measured on delphi-3bda in July 2026 (gpt-oss-120b tp4, 8 users; notebook delphi-flat-freq/docs/flat_freq_explained.html, ab30/ab36 traces). The pattern that matters for this assessment: threads spend most of the iteration waiting for another core (dashed), and one third of the wall clock is hand-off latency where neither CPU nor FPGA computes. A design that adds hand-offs (Reading C) pays here; a design that removes one hand-off pair (Reading A) can only win here.

Result of the check. "One tron thread per CPU core" is already the rule for the 13-111 pool workers that do the CPU work. 4. Three readings of the proposal, and what each would change

The sentence "each sw thread is truly single thread" admits three concrete designs. They differ by an order of magnitude in scope.

ReadingConcrete change in tronConcurrency complexityRandomness of executionPerformanceVerdict
A
one thread per physical core: no SMT sibling pairs		 Merge worker_main (TX) and do_rx_inplace (RX) into one loop per FPGA that alternates between the work doorbell and the block counter. Leave the RX sibling idle or give it back to the app pool. Removes the TX↔RX ring hand-off (rx_head/launch_tail/prepare_tail invariants stay, now single-writer). Adds a multiplexed poll loop: one thread can arm a hardware wait on only one cache line, and the merged loop must service at least three unrelated trigger words (inwork_queue doorbell, mcnt_mbox written by the FPGA, the launch_tail/act_slots handshake), so it alternates timed waits. It would also run the completion callbacks (RoPE-K, K/V page writes) inline, delaying the next launch. A naive merge deadlocks: TX blocks in tx_wait_for_slots on act_slots_free/mm_in_flight/wcmd_words_in_flight (worker.cpp:2050-2096), which only the RX path returns (worker.cpp:485, 504); the merged loop must be a non-blocking state machine. None. TX/RX order is fixed by the descriptor rings; completion order is set by the FPGA. Unmeasured. Risk: added wake-up latency on whichever event is not being monitored, at ~11,000 hand-off gaps/s/device (median 16 µs), and two streams of register round-trips (TX descriptors, RX tail updates) serialized on one hardware thread. Gain: none — on granite_rapids_6962p the dev-core siblings (147-150, 219-222) appear in no resource-map list, so nothing can use the freed hardware thread. The alternative, RX on its own full core, would take one of the 13 pool cores per slice (est. +1.6% iteration time if attention stays on the critical path; not measured). A/B first
B
static thread creation, no hidden pools		 Create app_pool() and the work_queue thread eagerly in pos_startup; pin the work_queue thread explicitly (today it inherits whatever mask its creator had); keep TBB out of the serving binary (init loop over ≤8 devices can be serial or use the pool); make the rinzler "Main" core reservation intentional or return it. Removes lifecycle races of lazily created singletons — one is already documented as a use-after-free at exit (Note [The cpu set must outlive the app pool]). Sync graph of the forward pass unchanged. Removes OS-scheduler placement variance of the coordinator and IO threads; no effect on output. Neutral to slightly positive (no TBB pool, coordinator placement chosen rather than inherited). The July A/B says the coordinator's stock placement next to the HTTP threads and dev cores was better than migrating it to fast cores. do it
C
each thread is an independent single-threaded program; concurrency only via messages between cores		 Replace the fork-join forward pass (coordinator + helpers + attention workers cooperating on one batch through channels and latches) with per-core actors, each owning some tokens end-to-end. Does not reduce the number of edges: every token's matmul still goes through the shared TX/RX/FPGA path; every token's attention still needs the KV of other tokens (prefix sharing); layer L+1 still needs layer L's outputs. The same dependency graph would be re-expressed with queues instead of latches. Unchanged: arrival-time batching, KV pagination, and floating-point reduction order are independent of thread topology. Loses the overlap the design is built on: attention of minibatch A on CPUs while the FPGA runs feed-forward of minibatch B; per-token streaming from DMA into attention via payload latches; ready/pending attention split. One hardware matmul job carries up to max_b activations against one weight command (inferred from worker.cpp:703, 745-748 and hardware/tensor.hpp:474-507; no repo prose states it as a rationale), so per-core batches would multiply weight traffic by the number of independent pipelines unless weight-load reuse (WLR) happens to hit on adjacent requests. Bounds from the July duty cycles (labeled est., not measured for C): aggregate attention thread-time ≈ 112 workers × 2.1 ms ≈ 235 ms per 9.9 ms iteration, so one pipeline per user at 8 users needs est. ≥29 ms of attention per iteration (≥3× today); serializing the ~2.1 ms attention plus the ~88%-overlapped 2.9 ms of coordinator work inside a pipeline adds est. up to +4.6 ms (+46%) before the weight-stream effect. not viable

6. Where the complexity actually comes from

Concurrency complexity in tron is the number of kinds of synchronization and the invariants each carries, not the number of threads per core. The forward pass uses the eight kinds below (Figure 2). None of them exists because a thread launches other threads. What history says about changing who-does-what

  • PR #2764 "Free the main thread" (2026-05-19, b93559aaf) was reverted the next day (ce4be9930): moving CPU work off the main thread "revealed the insufficiency of the synchronization between the main and helper threads", observed as NaN and −inf m_star values in the Mixtral 8x7b determinism test. Any change to the thread roles — Readings A and C included — carries the same exposure and needs the same gate: the determinism tests with pay_for_determinism on.
  • aad4642d9 made the framework wait for all plugin threads before logits: a read-before-write race between the coordinator and pool helpers that failed the Mixtral determinism test about 1 time in 10 and 0 of 100 after the latch (now Note [Plugin-owned worker launch]). a2a19755f fixed the pool/cpu-set teardown order (use-after-free at exit). The first is cross-core; the second is a lifecycle bug of the class that Reading B removes.
  • The fix for the revert was stronger cross-core protocol, not fewer threads: signaled-producer channels (fab7344ec, 2026-05-29), an atomic readiness word (d8d75bb2a), acquire waits on latch waitables (f9c99b9f4), and the MoE activation-readiness ordering fix (7fa2d41a1, PR #2856). PR #2909 then re-landed the change because keeping RoPE-K on the coordinator serialized the K and V projections.
  • The one recorded win from reducing concurrency was removing a library-managed pool: daadf4a98 (2024-06-07) ran TBB task_group work inline, which removed a sporadic hang (issue #184) and raised Mixtral 8x7B prompt parsing from 102 to 153 tok/s (+50%) and generation by at least 10%. The own pinned pool followed (1e075ae09, 2024-08-06, "for replacing TBB entirely"); TBB was never fully removed.
  • Verification tooling: a formal race-freedom model exists (650cd4324, ingest/src/Concurrent/RaceFree.hs, 2026-06) but it models the Asimov device IR, not the C++ forward pass. The C++ path is covered by TSan with narrow suppressions (t/tsan/suppressions.txt; a broad TBB suppression once hid a real race in vfio_device_init, PR #2262), run manually via make test-tsan and not in CI (GNUmakefile:396-402), and by TronCheck.checkChannelSync (c760d984c), a static check of the generated channel protocol. The suppressions file also records unfixed debt: volatile used instead of std::atomic for the pool doorbell, the TX/RX ring counters, and the latch cast ("MUST be converted if tron ever targets ARM/RISC-V").
  • Rate: since 2025-01-01, 137 of 6,712 non-merge commits (2.0%) mention race, deadlock, TSan, or hang as whole words (1.0% in 2025, 2.7% in 2026 to date). Every incident found in that history is between threads on different cores or between the scheduler thread and HTTP/client threads; none involves two compute threads on one core.

7. Recommendation

Adopt Reading B; measure Reading A before deciding; do not pursue Reading C.

  1. Measure before changing anything. Every quantitative statement about the proposal's cost or benefit is currently an estimate or "Insufficient data". The knobs to bound the value of today's cooperation already exist: cfg.max_minibatches=1 (no cross-minibatch overlap), TRON_MAX_MAIN_HELPERS=0 (no helpers), pay_for_determinism=true (no autotune). Three interleaved A/B pairs each on delphi-3bda (outside the CI lease, with campaign_guard_acquire), gpt-oss-120b tp4 / 8 users, recording decode tok/s per user, TTFT, and ab36-style launch→collect FPGA occupancy.
  2. Adopt the low-cost part of Reading B. Replace the TBB parallel_for at driver.cpp:347 with the existing SERIAL_DEVICE_INIT path or thread_pool::parallel_for (keeping the Main-core ordering at driver.cpp:410), replace tensor.hpp:397 the same way, drop find_package(TBB), and delete app_peer_pin_group/find_peers/the peer_cores key. Construct app_pool() and the work_queue thread eagerly at startup and remove the lazy-init mutex. Expected steady-state effect: none (TBB is init-only in FPGA serving); removes one library-managed thread team and one documented lifecycle-race class.
  3. Treat coordinator placement as its own measured experiment. Today the rinzler coordinator inherits the taskset and shares a hardware thread with the HTTP threads while the reserved app core is idle; the resource-map comment about "Main/coordinator on die B" describes runtron, not rinzler. The July ab32 A/B (decode −1.7%, TTFT +11% for a placement change) says the direction is not obvious. Run the same interleaved method with the coordinator pinned to the reserved core vs stock before deciding; also log recommend_n_main_helpers() and worker_cumsum per pass to see whether co-location with HTTP threads churns the attention plan.
  4. Reading A only as a prototype behind a measurement. First capture TX/RX duty cycles (perfetto driver and driver-detail categories; worker.cpp:180, 330, 400, 611, 1997) and A/B RX pinned to a separate core vs the sibling. A merged loop must be non-blocking (TX's slot waits are returned by RX) and must absorb RX's callbacks; stop if the launch→collect gap distribution widens.
  5. Do not pursue Reading C for decode serving. Attention serialization alone is est. ≥3× slower at 8 users, per-pipeline matmuls multiply FPGA weight streams, and per-pipeline launch→collect chains add hops to the component (hand-off latency, ~34%) the July analysis identified as the floor. The determinism it targets is already a flag.
  6. Attack randomness where it is. If reproducible logits are wanted from rinzler, expose pay_for_determinism (hard-coded false at rinzler.cpp:2009) and require a fixed request.seed; validate with a double-run exact-agreement test like t/t_generate_ingest_1_mixtral.cpp:35-44. If a deterministic token→core mapping is wanted, replace the two greedy_range loops (llama.hpp:1158, 1220) with the static striping already used at llama.hpp:776 and feed_forward.hpp:862, and A/B the stage time. Reproducibility across instance sizes and co-resident users needs a canonical attention partition and join tree plus per-user KV isolation — a plan redesign, not a threading change.
  7. Attack complexity where it is. Run make test-tsan in CI (today manual; no reference in .github/workflows or ci/); convert the volatile signaling words to std::atomic (documented as zero-cost on x86) and apply the recorded THEIR_LOAD_ORDER acquire fix; extend static checking beyond generated plugins (TronCheck.checkChannelSync covers ingest output only; handwritten llama.hpp is covered by t_threading and manual TSan); decide whether the unused helper_cores pool is wired or deleted. Glossary

app core / tron core
A CPU listed in tron_cores of resource-map.yaml; holds one pool worker (or the Main thread).
dev core
A CPU listed in dev_cores; holds the TX thread of one FPGA. Its SMT sibling holds the RX thread.
SMT / HT sibling, peer
The second hardware thread of a physical core. On Granite Rapids 6962P, sibling of core p is p+144. peer_of() computes it with hwloc.
work_queue / coordinator
The single thread that drains requests and runs forward(); it launches matmuls and hands tasks to pool workers. Named <cpu>/?-work_queue.
Main
The thread that ran device startup; pinned to the lowest app core. In runtron it is the process main thread; in rinzler a temporary thread.
main helpers / attention workers
Roles taken by pool workers in one forward pass: the first workers help the coordinator with rmsnorm/feed-forward CPU work; the last n_attn_workers compute attention.
TX / RX
Per-FPGA driver threads: TX writes DMA descriptors and launches matmuls; RX polls the block counter for completed results and fires callbacks.
channel
tron's producer/consumer phase protocol over a buffer, backed by a whole-phase latch or per-item tensor latches.
tensor_latch
A wait on the last 8 bytes of a result buffer, pre-filled with NaN; the DMA or kernel overwrites them last.
mwaitx / monitorx, tpause, RTM
Hardware wait instructions: sleep until a cache line is written (AMD mwaitx; Intel via a TSX transaction plus tpause).
pay_for_determinism
Config flag that disables speed autotuning of the attention plan so identical passes on identical hardware give identical logits.
TBB
Intel Threading Building Blocks, a task library with its own worker pool; linked into tron and used at device init and in CPU-only or synthetic-weight paths.
WLR
Weight-load reuse: the FPGA skips reloading weights when consecutive matmul requests on a device use the same weight matrix (worker.cpp:1274-1275).
GOF tasks
Hardware-attention submission work items (gof_coop_queue) that attention workers drain while they wait between layers.
taskset / CPUAFFINITY
The systemd unit starts rinzler under taskset -c ${CPUAFFINITY}; unpinned threads stay within that mask.
Reading A / B / C
The three concrete designs the proposal could mean; see Section 4.
