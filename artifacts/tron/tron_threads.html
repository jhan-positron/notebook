Tron CPU Cores and Software Threads

How config/resource-map.yaml becomes app, peer, helper, and device CPU sets, where the Tron code launches and pins its main worker threads, and which threads execute which model functions in the software-attention path. Covers AMD Genoa96 and Intel Xeon 6962P.

Resource Map to Runtime

1. YAML server type

Tron loads the resource map, identifies the local server by CPU vendor, physical core count, NUMA count, and optional model pattern, then sets the active server type.

physical_cores num_numa_nodes vendor model_pattern

2. Instance selects slices

--instance id,n indexes instance_slices[n - 1]. The code builds contiguous slice IDs starting at id * slices.

slice IDs = id * slices_per_instance ... + slices - 1

3. Slices choose resources

For each selected slice, C++ joins YAML entries from devices, tron_cores, dev_cores, optional helper_cores, and numa_nodes.

tron_cores -> app dev_cores -> TX helper_cores

4. CPU sets pin threads

App and device pin calls remove the lowest available CPU from their hwloc bitmap. RX and peer groups are derived by hwloc from the selected CPU, so the result follows topology order.

app_pin_thread peer_of dev_pin_thread

The die-A sibling trick

Each 6962P socket has three compute dies. Per slice the 14 app cores are 2 die-A cores + 6 die-B cores + 6 die-C cores, but the die-A cores appear in tron_cores as their SMT-sibling thread ids (151-158 = physical cores 7-14 plus 144; 223-230 = physical cores 79-86 plus 144), for example slice 0 = "151-152,24-29,48-53". Because pinning always takes the lowest remaining id, this makes the lowest id in every instance a die-B core (24, 30, 36, 42, 96, 102, 108, 114 per slice), so the main thread lands on die B. The YAML comment gives the motivation: die-B L3 latency ~54ns vs die-A ~63ns, worth about +1.5% decode (figures stated only in that comment; not re-measured here). The die-A silicon still runs app work through the sibling thread ids - and, as shown in the next section, the highest-numbered app cores are exactly the ones that run attention.

Thread Families

App worker pool

app_pool() is a lazy singleton. It creates app_get_num_cpus() - 1 workers and each worker uses with_app_pin_thread, which calls app_pin_thread().

Genoa96 full: 143 app cores -> 142 app workers
6962P full: 112 app cores -> 111 app workers

Main model work

The main thread is pinned to one app CPU during startup. Per forward pass, the model enqueues main-helper and attention work onto the app pool; those are tasks, not extra permanent threads.

main + app workers = app core count

FPGA TX/RX workers

Tron keeps workers[8] for TX workers. Each active device starts one TX worker, and the TX worker starts one detached RX worker pinned to the TX core's SMT peer.

device threads = 2 x active devices, max 16 for 8 devices

TBB peer work

Before device initialization uses TBB, Tron binds the calling thread to the app-peer CPU set. TBB may create transient workers, but Tron does not expose a fixed TBB worker count in this path.

Helper cores

helper_cores are parsed into a helper CPU set and can be consumed one at a time with helper_pin_thread(). In the non-generated source searched here, this API is present and tested, but not used by a permanent production pool - and it is not what runs the "main helper" tasks below. On granite_rapids_6962p the key is absent entirely.

Auxiliary threads

Additional threads exist for TSC calibration, optional tracing, FUSE, scheduler queues, and token stream monitoring. They are not sized from tron_cores, and most are optional or created on demand.

Which Threads Run Which Functions (Software Attention)

This section traces one forward pass in software attention mode - attention computed on CPU while the FPGAs keep doing the weight matmuls - through the handwritten dense-FFN llama plugin (h/tron/plugins/llama.hpp). Software attention is the default for handwritten plugins: USE_HW_ATTN is read once (src/tron/models/hw_attn_config.cpp); unset falls back to the plugin's force_hw_attn default, which handwritten plugins do not define. Ingest-generated plugins default to hardware attention, and several eligibility gates (shapes, EMEM fit, devices present, sliding-window layers) can force the software path regardless.

How the app pool splits

At the start of every forward pass, the plugin's run() splits the one shared app pool by role. n_main_helpers workers (pool slots 0 .. n_main_helpers-1) get run_main_help tasks; the remaining n_attn_workers = num_workers - n_main_helpers workers (always the last pool slots, per Note [Attention workers are the last pool workers]) get attention tasks. The main thread runs the launch-and-norm schedule itself and also computes shares of the CPU math as worker 0.

Stage order within one layer, schematic - durations are not to scale and stages overlap heavily: attention on already-resident ("ready") KV pages starts while the FPGA is still producing this pass's K/V, and the main thread launches matmuls for one minibatch while another minibatch computes. After the last layer: final RMSNorm (main + helpers) > wcls (FPGA) > top-k + sampling (app-pool tasks).

Three traps. (1) "Main helpers" are ordinary app-pool tasks; the helper_cores facility is unused by the forward pass (tests only). (2) Software attention is not CPU-only inference: every weight matmul (wq/wk/wv, wo, w1/w2/w3, wcls) still runs on the FPGA; only softmax(QK^T)V moves to CPU. (3) The KV cache is written by device RX threads, not app threads - rope_k/save_k/save_v are matmul completion callbacks.

Where attention lands on the 6962P

Combining two conventions places software attention on specific silicon. App workers pin to ascending core ids, and attention workers are the last pool workers, so attention occupies the highest app core ids in each instance. On granite_rapids_6962p the highest ids are exactly the die-A sibling threads (151-158, 223-230), so die-A silicon runs attention exclusively - its 16 sibling ids always fall inside the attention range - while the main thread and main helpers occupy dies B and C. Attention does not fit on die A alone, though: at the pinned split 80 of the 111 workers run attention, so roughly 64 attention workers also sit on dies B and C. No code targets attention at named cores - the mechanism is purely which id values the YAML lists (tron_cores is parsed into an hwloc bitmap, so the order inside the string is irrelevant; listing die-A cores by their primary ids instead of sibling ids is what would move attention).

How Sibling Cores Are Chosen

Not random. App and device CPU assignment is deterministic: pick_from_cpu_set() chooses hwloc_bitmap_first() and clears that bit. Sibling cores are then derived with hwloc peer_of(cpu) or find_peers(app_cpu_set).

App peers

app_set_cpu_list() parses tron_cores into app_cpu_set, then calls find_peers() to fill app_peer_cpu_set from hwloc topology.

App workers

thread_pool starts workers one by one and waits for each to start so CPU assignment stays monotonically increasing. Each worker pins itself by constructing with_app_pin_thread.

Device TX/RX pair

The TX worker gets the first remaining dev_cores CPU. It then sets dev->rx_cpu = peer_of(tx_cpu), launches the RX worker, and the RX worker calls pin_to_cpu(dev->rx_cpu).

YAML peer_cores caveat

The checked-in YAML has peer_cores, but the C++ resource map path found here does not read that key. C++ computes peers with hwloc. The shell helper config/resource-parser.sh has a separate --peer mode for tooling. On granite_rapids_6962p the documented intent differs from Genoa96: each slice's peer_cores list is tron_cores minus the slice's lowest core, keeping the main thread's SMT sibling idle.

Glossary

software attention
Attention (softmax(QK^T)V over the KV cache) computed on CPU app-pool workers instead of the FPGA. Weight matmuls stay on the FPGA. Also the universal fallback when hardware attention is ineligible.
main helpers
App-pool tasks (run_main_help) that share the main thread's CPU math: RMSNorm, SiLU, residuals. Unrelated to helper_cores.
attention workers
The last n_attn_workers app-pool workers each forward pass; they run RoPE on Q and the software attention kernel (run_attn).
kv_section
The software-attention work unit: one KV head plus a set of KV-cache pages, covering all query tokens of the minibatch.
ready vs pending KV
KV pages already resident before this pass (ready) vs pages being written by this pass's wk/wv results (pending). Ready pages let CPU attention overlap the FPGA matmuls.
channel / latch
The producer-consumer handoff. For FPGA-produced results, consumers spin (mwaitx) on the buffer the DMA writes into; for CPU-produced stages, readiness travels through a separate release/acquire word (signaled channels) or an explicit fallback latch (attention output), since ordinary tensor stores do not publish the last bytes atomically. Completion callbacks run on RX workers.
wcls / LM head
The classifier (unembedding) matrix multiplying the final embedding into vocabulary logits.
GQA
Grouped-query attention: several query heads share one KV head. Tron parallelizes attention over KV heads and loops serially over each KV head's query heads.
die A / B / C
The three compute dies of one Granite Rapids socket. On the 6962P map, die A hosts platform/rinzler/dev cores and contributes app cores via SMT sibling ids; die B gets the main thread; B and C carry the app cores.
SMT sibling
The second hardware thread of a physical core. On the 6962P, thread N and N+144 share a core (pattern consistent throughout the YAML; not re-verified against live hwloc here).
rinzler cores
Cores reserved in the YAML for the Rinzler tooling/deployment layer; not read by the Tron C++ path traced here.
