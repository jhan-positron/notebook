## Structural lessons

- A completeness critic that scores "is every design row covered" can only add assertions. Pair it with checks 1, 2 and 4, which can remove or re-justify them.
- A design document written from the implementation is not an oracle for tests. Check 1's question ("name the consumer") must be asked per row against `h/` and `src/`, not against the design.
- Known limitations in design records (alias, hardware gate, owner sign-off) must be carried into the PR body as sentences, or they resurface as review comments.
- Reviews must re-run at the final head, reading the body, the branch log and the CI configuration. On PR 4557 nine of the thirteen points concern artifacts (body, commits, hunks) that did not exist when the only full review ran.
- When answering a reviewer, run the same checks on his comments. Two of the thirteen points (W5, L4a) are partly wrong in detail, and conceding them as written would have made the PR worse.
- Do not infer the identity of an earlier model from its wording, and do not claim that every earlier review overlooked every fact; the design records held three of these facts.
