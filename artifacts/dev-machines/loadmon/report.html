alpha vs sw-dev-01

Question: is moving your development work from alpha (32 cores, 157 GB, Ubuntu 22.04) to sw-dev-01 (16 cores, 168 GB, Ubuntu 24.04) worthwhile, judged by machine load?

Answer: not on load alone

sw-dev-01 is the busier machine. During work hours it averaged 34 % CPU busy against alpha's 8 %, and it ran at 80–100 % (all 16 cores) for 85 minutes spread over five build/simulation bursts from four different users. alpha never went above 33 % and had 29 idle cores on average, versus 13 on sw-dev-01 (and only 2.6 in sw-dev-01's worst work-hour decile).

alpha's problem is not CPU, it is I/O. It froze twice on NFS (09:57 and 11:28 PDT, 25 + 50 minutes) — load1 hit 150 while the CPUs were 94 % idle, and every process touching the home filesystem stalled, including the sampler. sw-dev-01 mounts the same filer but did not stall in this window (it did have an NFS livelock on 2026-08-18 per #hardware-systems, so the risk is shared, not alpha-specific).

Recommendation. If your work is CPU-bound (builds, simulation), alpha gives you about 3× more spare cores during the day on average and 10× in the worst decile; stay. Move to sw-dev-01 only for reasons this data cannot show — Ubuntu 24.04 toolchain, podman, its status as the validated LSF submission host — and if so, expect contention around 09:45, 10:30, 11:30–12:15, 12:45 and 17:00 PDT when the other developers build. Off-hours, both machines are idle.

Method and caveats

  • One weekday. This is a single Tuesday. The build bursts on sw-dev-01 come from four people (bcraig, airani, wmiller, jzhang) whose schedules will vary; a second day would show whether 34 % / 85 saturated minutes is typical. The NFS stalls on alpha match a pattern Mitchell Stokes reported for agentsrv (2026-07-23) and sw-dev-01 (2026-08-18) in #hardware-systems, so they are recurring but not daily-predictable.
  • Sampler. sample.sh ran on each host (not through SSH), every 300 s, writing to ~/workspace/random/loadmon/<host>.csv. CPU busy = 1 − (idle + iowait) / total from the /proc/stat delta between samples, so it is a true 5-minute average; I/O wait counts as idle, which is why alpha's stalls show as low CPU busy. load1/5/15 from /proc/loadavg; memory from free -g; users = distinct names in who; top process = first row of ps --sort=-pcpu.
  • Top-process attribution is a snapshot, not a share of CPU over the interval. In 13 sw-dev-01 samples the top process was the sampler's own ps (jhan) under heavy contention; those are excluded from the "who" column.
  • alpha was read from the host, not from the claude-box container; the container's /proc/loadavg was checked to match the host before starting.
  • Not measured: NFS latency or client statistics (mountstats), disk I/O, network, GPU/FPGA. Whether the 11:28 PDT coincidence (alpha stall start = sw-dev-01 saturation start) shares a cause needs the filer logs.

Glossary

CPU busy %
Share of all CPU time in the 5-minute window not spent idle or waiting for I/O. 100 % = every core fully used.
Idle cores
cores × (1 − CPU busy). The number of cores nobody was using, on average over the window.
load1 / load15
Linux load average over 1 / 15 minutes: the number of processes running or waiting (for CPU or uninterruptible I/O). A load far above the core count with low CPU busy means processes are blocked on I/O, not competing for CPU.
p90 / p95
The value that 90 % / 95 % of samples stay below — the "bad but not rare" level.
NFS stall / livelock
The network filesystem (home directories on filer.positron.internal) stops answering for minutes; every process that reads or writes it blocks. Seen here as a gap in the samples plus a huge load average with idle CPUs.
alpha
General Linux dev server, 32 cores, 157 GB RAM, Ubuntu 22.04; ~10 users logged in.
sw-dev-01
SW-team dev server set up May 2026, 16 cores, 168 GB RAM, Ubuntu 24.04, podman, validated LSF submission host; ~3 users logged in.
