Hello Arm Support team,

Short version

Our Phoenix Reference Server started with only 10 of its 12 memory modules in 5 of 12 boots at the memory speed 8000 MT/s. After we set the speed to 7200 MT/s, 6 of 6 reboots gave 12 modules. Please confirm whether this is the known issue "Intermittent DCS delay training failures" [Ref1], and please answer the five questions in section 6.

Words used here
  • Module, DIMM: one memory module. The server has 12 slots, 6 per half of the chip.
  • CP0, CP1: the two halves of the chip in the slot names. DIMM_CP0_5 is slot 5 of half 0.
  • DDR5: the memory standard of the modules.
  • MT/s: million transfers per second, the unit of memory speed.
  • GiB: 2^30 bytes.
  • EVT0, EVT1: revisions of the circuit board. EVT1 is the later one.
  • SMBIOS: the table in which the firmware lists the hardware for the operating system. The command dmidecode prints it.
  • Training: the step at power-on where the firmware tunes the signal timing of each memory module. DCS is a control signal of a DDR5 module. "DCS delay training" is one training step.
  • Error record: a message that the firmware passes to Linux when hardware reports an error. Linux prints it in the kernel log with the tag [Hardware Error].
  • BMC: the management controller on the board.
  • SCP: the system control processor. It runs the first firmware stage.
  • Warm reboot: a restart from Linux without a power-off.
  • UTC: Coordinated Universal Time. All times in this email are UTC.
  • est.: estimated, not measured directly.

2. Symptom

  • Some boots show all 12 modules. The kernel then reports 377.0 GiB of usable memory.
  • Other boots show 10 modules. The kernel then reports 314.0 GiB.
  • No saved boot shows 11 modules.
  • The firmware removes the two modules before Linux starts. In a 10-module boot the SMBIOS table has 10 module entries [Ref6]. The memory total in the kernel log is then exactly 64 GiB smaller (two modules of 32 GiB) [Ref5].
  • Two 10-module boots were checked for the slot names. Both miss slot 5 on each half.

  • The first 10-module listing was saved on 2026-10-30 [Ref6]. The second one was read on the screen on 2026-11-17 and was not saved.
  • The other 10 slots carry the same serial numbers in the saved 10-module listing and in the 12-module listing [Ref6].

  • Effect on our work: a memory read test with 120 threads reached 362.2 GB/s with 10 modules and 468.1 GB/s with 12 modules. That is 23 % lower. The 1-minute load average at the start of the two runs was 0.26 and 0.00.

4. Test at 7200 MT/s

  • Your changelog recommends 7200 MT/s for firmware 0.7.2 [Ref2].
  • On 2026-11-17 at 19:43 we changed "DIMM Frequency" from 8000 MT/s to 7200 MT/s with uefisettings. The tool confirmed the change [Ref8].
  • We then did 6 warm reboots in a row. We fixed the number 6 before the first reboot.
  • All 6 boots showed 12 modules, each at 7200 MT/s in the SMBIOS table [Ref8].
  • The first 5 of these boots ran Linux for only 10 to 17 s each.
  • 5 of the 6 boots logged 0 error records. One boot logged 1 recoverable record with the source name DDS1_CP1 in its first second.
  • At 8000 MT/s, 5 of 12 boots showed 10 modules. If that rate still applied, 6 boots with 12 modules in a row would occur with a probability of 3.9 % (est., from (7/12)^6).
  • So the result supports the memory speed as the cause. It does not prove it.
  • The gap before each of these 6 boots was 170 to 182 s (est.).
  • A start after a power-off was not tested at 7200 MT/s.
  • The setting is still 7200 MT/s.

5. Error records in the kernel log

  • The kernel logs of the 12 boots at 8000 MT/s hold 654 firmware error records [Ref5].
  • 652 records have the severity "corrected", and 2 records have the severity "recoverable".
  • 640 records carry a data section. The section type is always bf32d4d5-b427-4025-8495-8a9e5d4030e4.
  • Linux prints section type: unknown for this type. Linux therefore does not decode the records.
  • Each data section contains a source name. The names seen are DDS0_CP1, DDS1_CP0, DDS1_CP1, DDS2_CP0, DDS3_CP0, DDS4_CP0, DDS5_CP0, DDS5_CP1, DDS6_CP1 and DDS7_CP1.
  • Records appear with 10 modules and with 12 modules. Boot 6 (10 modules) logged 301 corrected records. Boot 7 (12 modules) logged 321 corrected records.
  • The most frequent source names differ between these two boots. In boot 6 they are DDS5_CP1 (112 records) and DDS1_CP0 (98 records). In boot 7 they are DDS3_CP0 (123 records) and DDS7_CP1 (119 records).
  • Boots 2 and 12 each logged 1 recoverable record with the source name DDS1_CP1 in the first second of the boot. One boot at 7200 MT/s did the same (section 4).
  • In boots 8, 9 and 11 the first record came 0 to 41 s after the start of a memory test with 120 threads. Boot 10 ran the same test for about 3.5 minutes and logged 0 records.
  • No kernel message reports a DIMM error or a training error.
  • Hypothesis: the records are corrected errors of the memory links, and memory traffic triggers them. Your decoding of the records would confirm or reject it.

6. Questions

  1. Is the 10-of-12 module result on firmware 0.7.2 at 8000 MT/s the known issue "Intermittent DCS delay training failures"? Your user guide for firmware 0.9.0 states: "When a training failure occurs, the affected DIMM is isolated, and boot continues with fewer DIMMs." [Ref1] The text names no memory speed and no earlier firmware version.
  2. Is the part MTC20F2085S1RC80BH1 NCKK validated on an EVT0 board, and at which speed? The validated lists of the user guide name MTC20F2085S1RC80BH1 P8CH and MTC20F2085S1RC80BHY M8CC [Ref3]. They do not name the NCKK part. A test report in your kit shows the NCKK part at 8000 MT/s on an EVT1 board with firmware 0.9.0 [Ref10].
  3. What do the error records with the section type bf32d4d5-b427-4025-8495-8a9e5d4030e4 and the source names DDS0 to DDS7 mean?
  4. Which log shows the training result per slot, and how do we collect it?
  5. Does our EVT0 board need a hardware change to run at 8000 MT/s? The user guide states: "DDR 8000 MT/s validation used EVT1 PCBs. Previous PCB versions might produce a higher error rate." [Ref4]

7. Logs and steps to reproduce

  • Your Quick Start Guide asks for BMC logs and SCP logs with a support case [Ref9]. These logs are not attached, and we have not collected them yet.
  • Please tell us which logs you need and how to collect them.
  • The server now runs at 7200 MT/s. Please tell us if you need a capture from a new 10-module boot at 8000 MT/s.

Steps to reproduce at 8000 MT/s:

  1. Set the speed with uefisettings: sudo ./uefisettings hii set "DIMM Frequency" "8000 MT/s"
  2. Reboot: sudo systemctl reboot
  3. After the boot, read the module count: sudo dmesg | grep "DIMM sockets"
  4. Read the module list: sudo dmidecode -t 17
  5. Repeat steps 2 to 4. In our history 5 of 12 boots showed 10 modules.
