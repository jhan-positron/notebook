Warmup — each sentence is one load-bearing fact

Read these first; every sentence links to the example that demonstrates it.

  1. Tron never sees "users" — it sees sessions, one per stream_generate() call; one user can hold several sessions at once. → Example 2
  2. A session is one prompt + its growing completion, plus the transaction state around it (handle_id). → glossary
  3. "Sequence" is not a tron concept — where other engines say sequence, tron says session, and the session's tokens are "the prompt + its completion". → glossary
  4. The token tree is the KV cache: each session's tokens are a root-to-leaf path, and sessions with a common prompt prefix share the same edges. → Example 3
  5. Every step, the scheduler collects the live tokens of all active sessions into one batch (token_jobs) — freely mixing prefill and decode, at different positions, from different users. → Example 2
  6. Tokens in one batch share only one thing: the model weights. Position is a per-token input, and attention is isolated per session by tree ancestry — so there is no "same position" requirement. → Example 4
  7. One forward() call = one forward pass: the whole batch flows through every layer exactly once — layers live inside a pass, never the other way around. → Example 1
  8. lm_head runs once at the end of a pass, and only for listeners — positions that requested logits. Mid-prefill passes have no listener and skip it. → Example 1
  9. A forward pass generates one token per listener (in decode: one per decoding session) — not "one token", and mid-prefill passes generate zero. → Example 2
  10. The first generated token comes out of the last prefill pass, so decode pass k yields generated token k+1. → Example 5
  11. Minibatch groups (q_batches) are how one pass internally splits its token jobs for attention workers — an execution detail inside the pass, not a serving concept. → Example 1

Example 1 — inside one forward() call (and the layer-vs-pass hierarchy)

Heard / assumed: "a forward pass is the execution of one layer" or "one layer has multiple forward passes" — i.e. layer ⊃ pass.
Actual: pass ⊃ layers. One forward() call runs every layer exactly once. Tron's own MoE counter total_passes increments once per forward() call (model.hpp:1565) — "pass" in tron's vocabulary is the whole-model unit.

Hierarchy, largest→smallest: request → forward passes → layers → attention/FFN sub-blocks. The multiplicity people talk about ("a layer runs many times") is across passes — layer 7 runs once in pass 1, once in pass 2, … — never multiple times within one pass.

Example 2 — one forward pass, three users, four sessions

The scene: user X submitted two prompts (two sessions A and B — this is what "one user can hold several concurrent generations" means), user Y has session C decoding, user Z's session D just arrived and is mid-prefill. The scheduler packs all of their live tokens into one batch.

Schematic — box sizes not proportional to compute. ★ = listener (a position whose logits were requested; in_listener_index, model.hpp:1516).

Held intuition: "a forward pass generates 1 token, so sharing a pass between users requires everyone to be at the same token."
Actual: a pass generates one token per listener. Nothing requires same token, same position, or same phase — Example 4 shows the mechanism that makes this safe.

Example 3 — the token tree: sessions A and B share a prefix

Continuing Example 2: user X's two sessions A and B started from the same system prompt. The token tree stores that prefix once; each session is a root-to-leaf path, and its seq_tip points at its newest token.

Dotted segments = tokens appended one per decode pass. Edge lengths not to scale.

Session = the transaction; its tokens = one root-to-leaf path = "the prompt + its completion". Attention isolation falls out of the tree: a query token attends to exactly its ancestors (kv_cache.hpp:87), so A's tokens see the shared prefix + A's path — never anything of B's beyond the shared prefix, and nothing of C's or D's at all. This is also the prefix-cache win: B's prompt reused 900 tokens of KV that were never recomputed (prompt_tokens_reused, context.hpp:66).

Example 4 — why mixed positions are safe: what is actually shared

The batch dimension is just rows of a matrix multiply. Every linear layer computes row × same weight matrix independently per row. Position and history enter per row, not per batch:

Your intuition — "everyone in the batch must be at the same token" — describes static batching: start N prompts together, step them in lockstep, pad the short ones. Modern engines (tron included) do continuous batching: sessions join and leave mid-flight, each at its own position, and the scheduler rebuilds token_jobs from scratch before every pass.

Example 5 — one session's lifetime in passes (the off-by-one)

Single session, no other traffic (your 5cat draw shape: batch = 1). Prompt of 1024 tokens, prefill chunk 512, generating 4 tokens:

Pass widths not to scale (a 512-token prefill pass takes far longer than a 1-token decode pass). Assumes no speculative decoding — with EAGLE active (in_eagle_* args, model.hpp:1531), one pass can accept several tokens and the 1:1 mapping breaks.

Assumed: decode forward pass N produces generated token N.
Actual: off by one — token 1 is produced by the last prefill pass; decode pass k produces token k+1. And when mining a shared-engine trace, first classify each pass as prefill-shaped vs decode-shaped (the PDJN caveat: both phases run the same forward()).
