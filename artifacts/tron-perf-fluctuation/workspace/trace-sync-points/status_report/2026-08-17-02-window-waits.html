Rest-of-cycle mining: the fluctuation is in host thread handoffs

Report 05 · mined from campaign fpgastat-armB-20260817T114401Z (no new machine time) · 16 draws × 4,095 decode tokens, qwen-3-4b tp4 on delphi-3bda · 2026-08-17

Verdict: the draw-level TPS fluctuation is carried by three host-side waits in the inter-pass window — the worker join, the wcls block-arrival tail inside fill_logits_buffer, and the listener-notify wait — all of which slow together as a per-draw level shift. Chip work (report 04) and per-request chip turnaround (this report: median 20 µs, slow−fast delta +0.0 µs) are constant. 82% of the fast4→slow4 period delta sits in the window, 18% in the 36-layer span; within a draw, token-to-token noise is 77% span. The named suspect [open→F1] is confirmed as one of the three handoffs, not the sole carrier.

1. TL;DR

  • Serial time budget of the fast4→slow4 delta (+360 µs/token): [open→F1] +112 µs (31%) · [F1→listeners-notified] +159 µs (44%) · [notify→window end] +23 µs (7%) · 36-layer span +65 µs (18%).
  • The waits that grow (direct duration measurements, overlapping in time): fill_logits_buffer +147 µs (corr with TPS −0.70), listeners_notified +110 µs (−0.64), workers_done join +70 µs (−0.79). Alloc and callback are flat (+2, +8 µs).
  • Inside fill: the growth is entirely the wcls block-arrival tail — fill-start to last-block-consumed runs 489 µs in the fastest draw vs 897 µs in the slowest, while post-arrival processing is constant at ~30 µs.
  • The chip is ruled out at request granularity too: tx-dispatch→rx-completion turnaround is 19.9–20.2 µs median (p99 73–84 µs) in every draw, fast or slow. The span’s +65 µs appears as host inter-dispatch gap growth, not turnaround growth.
  • Level shift, not per-token contention: within a draw the three waits do not co-move token-to-token (pairwise corr ≤ 0.14). Something set per draw slows every scheduler-thread handoff by a near-constant amount.

2. Glossary

Handoff wait
A scheduler-thread wait on other host threads: workers finishing the forward pass (join), RX threads delivering wcls result blocks (consumed inside fill_logits_buffer), listener threads acknowledging new logits.
[open→F1] / F1F3 / F3end (fence3_dump convention)
Serial slices of the inter-pass window: layer-35 barrier end → workers_done end (contains the join wait); → listeners_notified end (contains alloc, fill, callback, notify); → next layer-0 start. Report 04’s narrower “[F1→F3] 0.29 ms” equals this F1F3 minus the listeners wait; the two views reconcile exactly.
Chip turnaround
Time from a tx-dispatch stamp (tag 3000) to the matching rx-completion stamp (tag 4000), paired in order per device (est.: assumes in-order completion).
Level shift
A per-draw offset: every token in a slow draw pays roughly the same extra wait, rather than a few tokens paying large stalls.

4. The three waits that grow — and the chip that doesn’t

  • fill_logits_buffer +147 µs: split by the per-block consume stamps, fill-start→last-block is 489 µs (fastest draw d02) vs 897 µs (slowest d10); last-block→fill-end is 29 vs 32 µs. The entire growth is waiting for wcls result blocks to be consumed — with dispatch cadence, chip work, and turnaround all constant, the stretch is in the RX-thread→scheduler delivery path or the consume pacing, not in the chip. (Same direction as the bypass verdict, which removed the hardware and kept the jitter.)
  • listeners_notified +110 µs: waiting for listener threads to pick up the new logits.
  • workers_done join +70 µs: waiting for the last worker thread to arrive at the pass-end barrier — this is the [open→F1] join wait named by the fence-3 report, now measured across 16 draws (corr with TPS −0.79, the strongest of the three).
  • Span +65 µs: appears as inter-dispatch gap growth on the TX stream (slow4−fast4: +66 µs/token in-span, dev0), i.e. the host issues requests slightly later; per-request chip turnaround unchanged.

5. Level shift, not contention events

  • Within a draw, the three waits are uncorrelated token-to-token: pairwise corr (join, fill) = 0.00–0.02, (join, notify) = −0.01–0.14, (fill, notify) = −0.01–0.02 (checked on d10/d04/d02/d09). A slow draw is not a normal draw plus occasional stalls; every token pays a roughly constant surcharge on every handoff.
  • Token-level variance within a draw is a separate pool: 77% of per-token period variance is the span (range 69–90% across draws), consistent with the two-pools structure from the bypass report. That pool does not move draw TPS; the handoff level shift does.
  • This localizes the earlier “window level-shift mode” (wadefix A/B, both arms): the shifted quantity is host handoff latency, set once per draw (= per engine bring-up).

6. What can set a per-draw handoff latency? (hypotheses, each with its measurement)

  • Thread placement drift: worker/RX/listener threads may land on different cores each bring-up (relative to each other, to IRQs, or to NUMA); a bad draw = a bad placement. Measurement: per-draw ps -T -o tid,psr,comm snapshot of runtron (trivial harness addition) — compare placements of fast vs slow draws. TRON’s pinned threads (TX 3–6 etc.) are fixed; the question is the unpinned ones.
  • Wakeup path cost: futex/condition-variable wakeup latency between the involved cores (cpuidle depth, IPI path, sibling load). Measurement: perfetto linux.ftrace sched_wakeup/sched_switch for one campaign — wakeup-to-run latency of the scheduler/RX/listener threads, fast vs slow draws. Not yet captured (track_event scheduler category is TRON spans, not kernel sched).
  • Memory/NUMA placement of run allocations: logits buffer or queue pages landing remote in some bring-ups. Measurement: per-draw numa_maps snapshot of the relevant mappings.

All three are cheap to instrument in the existing harness; none needs new probe code in tron. Not excluded but de-prioritized by this data: anything per-token or chip-side.
