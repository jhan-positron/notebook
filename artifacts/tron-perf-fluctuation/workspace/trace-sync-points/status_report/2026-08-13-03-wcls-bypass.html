Bypassing the FPGA during fill_logits_buffer

The verification hack, scoped and then executed: make the wcls (logits) stage constant-time by not waiting for FPGA results, so a collapse (or survival) of per-token jitter attributes it to the FPGA wcls pipeline vs the rest of the system. Result first; the pre-run scoping (patch plan, delay choice) follows as the record.

RResult (executed 2026-08-14, delphi-3c51)

The bypass ran clean, and the answer is unambiguous: pinning the wcls stage to a constant does not remove the jitter. Within-run per-token jitter and the draw-to-draw speed spread both survive essentially unchanged in absolute terms, and the variance relocates onto the forward pass and the transfer phase.

R.4  Which segment drives draw-level TPS jitter?

Draw-level TPS fluctuation across the 16 draws is the ultimate metric. This section answers, in that metric and using pre-bypass data only: how much of it comes from the inter-pass window, and how much from the forward pass?

First, what a draw's TPS can and cannot see. A draw's TPS is the average of ~4,096 tokens, so token-to-token wobble cancels inside it: the per-token noise (sd 635.6 µs) shrinks by √4095 to ~10 µs in a draw mean. What survives averaging is only the persistent per-run offset — and the 16 draw means indeed spread with sd 78.6 µs (which is exactly the TPS CV of 1.33%). So draw-level TPS jitter is made of the small persistent pool, and the question "which segment drives it" must be answered inside that pool:

R.5  Run facts and hygiene

  • Binary: worktree tron-wclsbypass @ 12804a812 + probe patch + bypass; runtron sha256 8fa58da286e8…; deployed as install-wclsbypass. Control smoke reproduced the reference token sha 66af1d58… exactly — the dormant bypass code does not perturb numerics.
  • Campaigns: 3c51-wclsbyp-ctl-tp4-20260814T045710Z and 3c51-wclsbyp-on-tp4-20260814T051813Z, both smoke+16/16, zero freeze holes (max record gap 10.7 / 7.1 ms), machine restored after each.
  • Delay adequacy: after each 2.5 ms hold, the deferred result drain took p50 28.5 µs / p99 53.9 µs — real wcls results were essentially always complete inside the hold. Exception: 32 of 262,144 drains (0.012%) took 1–6.01 ms, always hitting all 4 devices at the same token — whole-system stall events of the same family as the known once-per-run event, not a bypass failure.
  • Deviations from the plan: no force-feed file was needed — the standing harness already runs greedy (--threshold_p 0) with --dont-stop, so length is fixed by construction. Bypass token output varies across draws (16 distinct hashes): the discarded result DMA races the consumer, so the argmax sees different bytes per run — benign for timing, fixed length maintained.
  • Statistics conventions: cycles → µs at 2.700 GHz TSC; variance and sd are unaffected by the constant hold (translation-invariant); CV is affected, so bypass CVs are also given at the control-scale denominator; all headline numbers were independently recomputed from raw kvwait.bin files with exact agreement.
What this changes for the investigation.
The logits stage — previously the strongest TPS correlate (corr −0.85 across three independent methods) — is excluded as the jitter source: severing its data dependency leaves both jitter dimensions intact and merely decorrelates the stage itself. The run-wide condition that sets a draw's speed acts on the forward pass (FPGA layer matmuls + per-layer host driver work, interleaved — not yet separated) and the [open→F1] transfer phase. "FPGA vs host software" remains open inside the forward pass; the sharpened next measurement is per-layer bracketing there (the wcls-stage instrumentation pattern of this experiment applies directly).

The plan's "rx" and "tx" are swapped relative to the codebase's thread names.

Two facts remove most of the plumbing the plan expected to need:

  • "Workers inform rx drivers the stage is fill_logits_buffer" already exists. The literal "wcls" flows from model.hpp:3266-3267 into wqentry.debug_label (driver.cpp:613) and is readable inside tx_launch. No new worker→driver signal is needed; nothing in worker/model code changes.
  • "rx informs tx" already exists. The two threads share a per-request rxinfo ring slot (h/pos/device.hpp:145-183), and tx_launch's launch_tail += 1 (worker.cpp:2313) is the existing wake signal the RX worker sleeps on (worker.cpp:323-326).
The load-bearing mechanism: the worker does not wait on the driver — it waits on the data itself.
The wcls result has two independent ready signals, and the bypass must fake both:
  1. Per-block sentinels. Before launch, stream_result_t::prepare() writes 0xffff (a bf16 NaN pattern) into the last uint16 of every result block (h/libpos.hpp:215-223). fill_logits_buffer spin-polls these words across all 4 device tiles (model.hpp:3226-3235, libpos.hpp:232-246); normally the FPGA's result DMA overwrites them. Firing the callback alone bypasses nothing — the spin loop would still wait for real data.
  2. The logits_done latch. One count-down per device, fired by the RX worker's rx_entry.callback() (worker.cpp:613-617). The scheduler thread waits it under waiting_for_logits (model.hpp:3088-3089) before Fence 3's listeners_notified.wait() (model.hpp:3092-3098).
Verified end to end: clearing the sentinels + firing the 4 callbacks releases everything between Fence 1 and Fence 3; no other blocking dependency on real FPGA data exists on the runtron sparse-logits path (dense-logits, log-intermediates, and draft-model paths are all off by default).

Side finding that corrects an earlier reading: Mike's "data ready" instant (worker.cpp:2246-2252) fires on the TX worker after act_ready.wait(), which is an empty waitable for wcls — it stamps the launch, not result arrival. The v11 finding "data-ready leg flat" therefore says wcls dispatch is flat; result arrival remains unmeasured, which is exactly what this experiment probes.

Why the delay cannot "let the FPGA data come in" during the hold — and why that is fine.
Result-block moves to the host are authorized by the RX descriptor doorbell, which only the drain loop advances (worker.cpp:439-444). During the hold, results pile up in device-side RMEM until its backpressure threshold (869, programmed at device.cpp:305-309) and the chip's result pipeline stalls — a stall regime the normal run never enters (expect large mm_rmem_bp counts in FPGA metrics; an artifact, not a finding). So the constant delay buys time for the FPGA to finish computing; the actual transfer runs as a short burst right after the deadline (~304 KB per token across 4 devices), typically done ~130 µs before the next pass's first transfers (next-step construction alone is a measured 127–140 µs median after F3).

6Optional second arm: hold-the-callback (no garbage)

Verification surfaced a strictly simpler variant worth running as a companion arm: run the drain unchanged first, then hold the callback until t0 + Δ (spin inserted immediately before the existing fire at worker.cpp:613-617). No memset, no new buffer plumbing, no NaN source, and — because consumers eat real data — the token stream and its hash stay identical to baseline. F3 still lands at the constant deadline whenever real completion < Δ.

  • What it adds: site-4000 minus site-3000 in this arm is the per-token real wcls completion time — the direct measurement of the "late arrival vs slow consume" question the occupancy synthesis named as the open item, collected for free across 16 draws.
  • What it lacks: host consumption of real streamed blocks keeps its data-dependent timing, so "jitter persists" is ambiguous in this arm — it cannot replace arm A as the severing intervention.
  • Recommendation: arm A (garbage bypass, as specified) is the primary experiment; arm B is a cheap add-on draw set with high measurement value.

8Run design checklist

  1. Control arm = same binary, TRON_WCLS_BYPASS_NS=0, same force-feed file, same NaN-skip, same flags, same host. Historical fence13/fence13pf campaigns are secondary references only (the bypass arm changes token content and duty cycle).
  2. Pin the environment knobs that shape the logits stage: TRON_MAX_LOGITS_CHUNK_SIZE and TRON_MAX_MAIN_HELPERS (they set chunk count and consume parallelism, model.hpp:72-85).

Glossary

wcls / fill_logits_buffer
The classifier-head matrix multiply producing next-token logits (vocab 151,936, split over 4 devices), and the model function that consumes its streamed result blocks (model.hpp:3203-3259).
Fence 1 / Fence 3 (F1/F3)
Per-token sync points: workers finish transformer layers and join (F1, tag 7601); logits delivered to all listeners (F3, tag 7600). [F3→F3] = full token period.
sentinel
The 0xffff word planted in each result block's last uint16 before launch; overwritten by arriving data. The consumer's per-block ready signal.
latch (logits_done, listeners_notified)
Count-down synchronization objects; a waiter unblocks when the count reaches zero.
TX-dd / RX-dd workers
Per-device driver threads: TX submits work/activations to the FPGA; RX drains results and fires completion callbacks. (Opposite of the rx/tx naming used in the experiment request.)
rxinfo / drain / mcnt / RMEM
Per-request contract slot between TX and RX threads; the RX loop that authorizes and accounts result-block transfers; the FPGA-written monotonic result-block counter; device-side result memory (fills and backpressures if the host doesn't drain).
forward pass / forward segment
Layers 0–35 of the next token's computation: FPGA layer matmuls, attention, and per-layer host driver work interleaved. Measured here as token period minus (construction + transfer phase + logits stage).
draw / campaign
One benchmark run (here 4096 generated tokens); a set of 16 draws plus smoke on one host/config.
traced vs untraced campaign
fence13pf (perfetto tracing on, timestamps in ns) vs fence13 (probe-only, timestamps in 2.700 GHz TSC cycles; µs values derived).
CCDF
"Fraction longer than x" curve — the chart in section 4.
IQR / CV
Interquartile range (p75−p25); coefficient of variation (standard deviation / mean).
