Does memory allocation happen in the inter-forward-pass gaps?

Testing Ben's suspicion that malloc/free churn between forward passes causes the decode-perf fluctuation · data: the one sys-category Perfetto campaign (tron-perfetto-syscheck-20b-20260809T0335Z, gpt-oss-20b-tp4, software attention, 3 captures × ~9 s of steady decode, ~1300 generation steps each) · analysis 2026-08-11

Verdict: not supported. Allocation churn is real (~2,000 allocations per forward pass on average) but it lives inside the forward pass, arrives in rare large bursts (57% of steps show none at all), and the inter-pass gaps carry a median of ≈0 allocations with no consistent correlation between gap length and allocation count. Combined with the July allocator-flavor A/B (arena and legacy both fluctuate), memory alloc/de-alloc is not the inter-pass time sink.

Window definitions

Owner's gap (used for manual inspection): end of the last rx collecting results slice → start of the next compute_forward_args. It includes the forward's host-side tail (logits fill, sampling, listener callbacks) — real work belonging to the pass — hence its larger median (382–712 µs). Strict gap: end of the forward slice → start of the next one (median 110–128 µs) — the complete "between passes" region and nothing else. Both computed above; the conclusion is the same in both. For future captures the new seq marker allows the cleanest form: step N start → step N+1 start, decomposed into in-pass + between-pass.

Method & queries

The sys category's malloc counter (src/pos/memperf.cpp) overrides operator new and emits TRACE_COUNTER("sys","malloc") every 25th allocation — so allocations ≈ counter samples × 25, and any window with fewer than ~25 allocations can legitimately show zero samples. Extraction (trace_processor, per capture):

SELECT "fwd" AS kind, s.ts, s.dur FROM slice s WHERE s.name="forward"
UNION ALL SELECT "rx",  s.ts, s.dur FROM slice s WHERE s.name="rx collecting results"
UNION ALL SELECT "cfa", s.ts, s.dur FROM slice s WHERE s.name="compute_forward_args"
UNION ALL SELECT "malloc", c.ts, 0
  FROM counter c JOIN counter_track t ON c.track_id=t.id WHERE t.name="malloc"
ORDER BY ts;

Windows were built in Python (bisect over sorted timestamps); per-window sample counts × 25 give allocation estimates; Pearson r computed per capture across its ~1,300 windows. Analysis artifacts: delphi-3bda:/scratch/jhan/pdjn/mine7/.

Caveats

  • All three sys-enabled captures are similar-speed draws (98.6–99.0 tok/s) — a slow-launch vs fast-launch malloc comparison is not possible with existing data; the within-draw window analysis above is the strongest available test. A future slow+fast pair of sys-enabled captures would close this fully.
  • 1-in-25 sampling: "median 0 samples" means "fewer than ~25 allocations", not literally zero.
  • The counter tracks operator new — allocations by non-C++ paths (raw malloc in C libraries) are not counted; the DMA-heap allocator (pos_heap) is separate and was excluded independently (addrmap campaign, report 04).
  • Supporting prior evidence: July allocator-flavor A/B (arena vs legacy — both fluctuate, difference is level not dispersion).

Glossary

forward pass / generation step
One trip of a token batch through all model layers, producing one token per user; at this workload ~7–8 ms.
inter-forward-pass gap
Wall-clock time between two consecutive forward passes (scheduler, queue handoff, dispatch).
rx collecting results / compute_forward_args
Trace spans: the driver thread gathering the FPGA's results for a pass, and the scheduler preparing the next pass's arguments.
1-in-25 sampling
The malloc counter emits one trace sample per 25 allocations to keep overhead low.
r (Pearson correlation)
−1…+1 measure of linear association; ~0 means window length and allocation count move independently.
