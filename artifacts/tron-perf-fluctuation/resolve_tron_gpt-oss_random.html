What â€œrandomnessâ€ means here

Source verified

No active explicit RNG found in the measured branch

The campaign uses fixed seed, --threshold_p 0, and speculation off. Sampling returns the sorted argmax. Generated gpt-oss routing calls topk_fixed<4> and build_moe_routing_from_indices<128,4>. The environment-controlled TRON_RANDOMIZE_EXPERTS belongs to legacy MoE routing and is not on the generated gpt-oss path.

Still stochastic in practice

Closed-loop timing can change content without a random call

With multiple users, listener completion order and closed-loop request timing can change which sequences co-reside. Token outputs differ across fresh launches even under fixed seed. Tight Mixtral also produced different outputs, so trajectory variation is not sufficient; a gpt-oss-specific content interaction remains possible. Use --pay-for-determinism or a matched -u 1 control only after the listener meter is in place.

03 Â· Ranked causal model

What can still produce fast and slow launches

The observed object is a launch-dependent probability of a long decode barrier. The report deliberately separates the amplifier (why the event is expensive in gpt-oss) from the trigger (why its frequency differs between launches).

H1

Streamed WCLS consumer backlog on an active listener

A listener does not keep up with result production, leaving a large residual vocabulary scan, heap work, or sort/callback after final RX. The trigger may be descheduling, on-CPU throughput loss, polling/readiness cadence, or cache/DRAM interference.

Fits: wide 201k scan, TP sensitivity, barrier mixture, suggestive fill_logits_buffer coverage.Missing: cursor-at-final-RX and last-releaser identity.
H2

Listener callback, lock, allocation, or notification fan-in

The scan completes normally, but top-k output allocation, sampling/next-token enqueue, pin cleanup, a tree/work-queue lock, or the final latch creates the long barrier.

Fits: source lies directly on the barrier path.Against: 51 inactive tasks normally retire during WCLS flight; only four active listeners should be critical.
H3

Result readiness / sentinel visibility / tile cadence

The worker stays on CPU but observes blocks late or polls inefficiently. TP changes the number and cadence of independent tiles, consistent with amplitude sensitivity.

Fits: an on-CPU delay and geometry sensitivity.Missing: poll-miss, block-gap, and tile-order counters.
H4

120B predecessor state or generated-plugin interaction

The 36-layer/128-expert run leaves particular queues, cores, caches, or memory state before the common WCLS tail. This could raise the event rate while Mixtral and dense controls remain tight.

Fits: gpt-specific presence despite shared output path.Best split: gpt-oss-20B TP4 preserves output geometry but reduces layers/experts.
H5

Content-dependent heap work or invalid vocabulary rows

Heap replacement count and exact result arrival order depend on logits. gpt-oss emits 201,088 classifier rows while its tokenizer accepts 200,019 IDs; filtering 1,069 invalid rows happens after top-320 selection.

Fits: generated content varies and heap work is data dependent.Against: 1,069 extra comparisons are too small to explain a ~600 Âµs step alone.
