struct alignas(64) queue_t {
  volatile uint64_t doorbell;
  moodycamel::ConcurrentQueue<task_t> queue;
  void enqueue(task_t&& task) {
    queue.enqueue(std::forward<task_t>(task));
    doorbell += 1;                         // non-atomic cross-thread access
  }
  bool dequeue(task_t& task, uint64_t timeout_ns) {
    uint64_t old_doorbell = doorbell;
    if (queue.try_dequeue(task)) return true;
    tron::hardware::mwaitx::wait_for_not_event(&doorbell, old_doorbell, timeout_ns);
    return queue.try_dequeue(task);
  }
};

Fence 1 → Fence 3 audit (2026-08-13)

Source under review: 2026-08-12-07-stall-map.html §3.6, checked against the same 12804a812166 probe worktree used for this lane map.

Verdict: I agree that both boundaries are definitive scoped joins, but I do not agree that either is a global quiescent/BSP point under the stall-map’s own definition, “every operation on every thread is before or after; nothing concurrent.” Fence 1 joins the plugin-owned app-pool cohort. Fence 3 joins the listener-task cohort and, by scheduler program order, follows full WCLS completion. Those are strong, deterministic cuts for attribution; they do not prove that every TX, RX, device, callback epilogue, or next-request operation is globally quiescent at one instant.

Terminology matters: both primitives are one-way countdown latches, not BSP barriers. A participant decrements and continues into its return epilogue; it does not wait at the cut. If the stall-map convention explicitly excludes idle/poll work, RX/task epilogues, prelaunch WCMD activity, and next-request construction/publication, then F1 and F3 may be called its two “definitive” workload cuts. That is a project convention, not the literal all-thread property stated in its glossary. Also, tag t0+dur is sampled by a second now() immediately after wait(), so it is a close marker—not the literal return instruction.

Definitive source synchronization inside the F1→F3 interval

Yes—there are many definitive local synchronization edges between the two joins. There is no additional all-lane/global barrier in the ordinary u1 decode interval. “Streaming region” describes the overlap topology; it does not mean “no synchronization.”

  • Actual queue sleeps, TX capacity loops, trace-phase locks, cancellation/OOM branches, and eligible coalescing/destruction depend on runtime state.
Probe Instrumentation adds shared atomic contention

kvwait_probe.hpp:39–41

void add(uint64_t t0, uint64_t dur, uint64_t tag) noexcept {
  uint64_t i = count->fetch_add(1, std::memory_order_relaxed);
  if (i < kMax) recs[i] = rec{t0, dur, tag};
}

When the probe is enabled, every tag—including every streamed block—contends on this one atomic counter. Relaxed RMWs have one modification order but create no functional cross-lane happens-before edge. This is probe-only cache-line serialization, not a production fence; it should nevertheless be considered when interpreting probe timing.

What is constrained too much, and too little?

Over-constrained: S14’s 70-way join for one useful listener; S12’s inline client/output callback despite a documented non-stalling callback contract; S2’s timing-only attention barrier; the one global scheduler’s inability to service S11 until S10 and S14; full WCLS completion on the continuation lifetime; and synchronous token-tree maintenance.

Under-constrained: the app-pool doorbell’s non-atomic cross-thread accesses; the plain DMA-written stream sentinel; and POS host/device ring publications that use ordinary or volatile memory without a visible release/acquire or DMA-read contract. These are real source-level correctness debts, although static analysis alone does not establish that they caused the observed launch-to-launch fluctuation.

No classic missed wakeup found: latch countdowns use acquire/release atomics, the scheduler CV waits with a predicate, and no global tree mutex is held while the scheduler waits for listener workers. The shape is tail amplification and overserialization, not an obvious circular lock dependency.
