02 / MODEL PATH

The discontinuity is the expert job graph

For a fixed router input, the generated path is deterministic. What changes performance is the graph after top-k: rows are grouped by expert, empty experts are skipped, and every active expert becomes a separate TP1 prepare/launch. Completion waits for the last active expert.

01

Router matmul + bias

Produces 128 gate values per token.

02

Deterministic top-4

topk_fixed<4>; lowest lane wins AVX equal-value ties.

03

Group by expert

Builds variable per-expert row lists from the four indices.

04

TP1 fanout

One small prepare/launch per active expert, on its assigned card.

05

Card queues + helpers

Route collisions create queue skew; one helper often owns all one-row work.

06

Last-expert barrier

The phase advances only after every active expert callback finishes.

Why gpt-oss is sensitive

  • Four selected expert IDs per token determine card-local work.
  • Across a 4Ã—1-token decode cycle, selected rows can cluster or spread across experts and cards.
  • Small expert matmuls have meaningful host launch overhead, shouldered by one core.
  • One slow or overloaded card holds the shared completion callback.
  • Expert-major helper striping underuses helpers when each expert has only one row.

Why dense Llama is comparatively insensitive

  • Its FFN executes the same dense W1/W3/W2 topology for every token batch.
  • Different token values change arithmetic, not the number of FFN launches or which card owns an expert.
  • There is no expert cutoff discontinuity, active-expert set, or expert completion barrier.
  • The ab59 control proves this difference matters in practice: token streams varied, TPS did not.
Single-token nuance. For exactly one decoded token, gpt-oss always selects four experts, so active-expert count cannot vary. Expert identity, device collisions, expert service time, and helper-0 serialization still can. With several concurrent one-token requests in the same forward pass, both the distinct-expert count and rows per expert vary.

06 / FALSIFICATION

A short experiment ladder that identifies the branch

Run fresh-process draws and preserve mean TPS as well as dispersion; a mitigation that collapses CV by slowing every draw is not a clean win. Use the existing frozen harness and change one mechanism at a time.

T0

Prove the effective command and environment for every draw

Archive /proc/$pid/cmdline and /proc/$pid/environ. Assert fixed --seed, --threshold_p 0, speculation state, and absence of TRON_RANDOMIZE_EXPERTS. Do not set that variable to â€œ0â€; unset it.

Closes: accidental fallback to raw stochastic defaults or environment drift.
T1

Interleave --pay-for-determinism OFF/ON across fresh launches

Keep prompts, users, cores, cards, KV state policy, seed, and greedy sampling fixed. Capture token files and compare both CV and mean TPS. For ingested gpt-oss, the relevant change is equal attention-worker weighting; the main/helper count is already fixed in one-minibatch mode.

Positive result: ON collapses dispersion and stabilizes route/token hashes â†’ runtime attention partitioning is upstream of the lottery.
T2

Force an identical token stream, ideally together with deterministic attention

Use --force-feed-text-token-file (or the validated equivalent) and verify emitted token IDs. This removes sampling and autoregressive token-trajectory differences. Pair with T1 to suppress the known numerical plan variation. The configured force-feed vector is shared across requests, so compare dispersion rather than treating its changed mean as directly comparable to the baseline.

Positive result: variation collapses only with force-feed â†’ content/trajectory-driven expert routing is necessary.
T3

Use built-in expert telemetry before adding heavy traces

Take before/after deltas from /model/<id>/experts/layer_L/counts, active_histogram, and total_passes. Log placement with TRON_LOG_PLACEMENT. Project expert rows onto cards and compute active experts, max rows per expert, aggregate card rows, and card-load concentration. Read only outside the timed interval: FUSE snapshots take the same per-layer mutex as the routing writer. These cumulative statistics cannot reconstruct per-forward co-occurrence, temporal order, or the maximum card in each layer; use T4 if the aggregate result is null or ambiguous.

Positive result: TPS tracks projected card skew or active-expert fanout across draws â†’ route workload is the visible mediator.
T4

Add a compact per-layer route and device timing record

Record route hash, per-expert rows, expertâ†’device, prepare/launch time, per-card queue depth and slot waits, first/last expert completion, helper row counts/cycles, and sparse-WCLS first/last tile readiness. Avoid a multi-gigabyte activation dump; one structured row per layer/phase is sufficient.

Distinguishes: host dispatch, helper serialization, card queue/service time, last-expert barrier, and WCLS slowest-tile tail.
T5

Replay routes; then balance versus concentrate them by card

The generic --forced-routing path should not be assumed to work for generated gpt-oss at this commit. Add or validate a generated-path replay hook. Compare identical route+placement, deliberately card-balanced routes, and deliberately card-concentrated routes.

Causal test: controlled card concentration changes latency/variance â†’ expert queue skew and the last-card barrier are causal.
T6

Isolate sparse WCLS and match dense geometry

First correlate decode time with maximum WCLS tile lag/spin cycles. If feasible, force a non-streaming logits path. Separately run the pre-registered Llama-70B-TP4 control to match footprint and geometry while remaining dense.

Closes: the strongest non-routing gpt-oss differential and the size/TP4 confound.

How to read the outcomes

If T1 collapses CV
Attention-plan feedback is the upstream dice.

Confirm that token and route hashes stabilize, then measure the mean-throughput price of determinism.

If only T2 collapses CV
Token trajectory drives the route workload.

Sampling may already be greedy; the differing trajectory can still originate from batch/KV context.

If route metrics track TPS
MoE fanout/card imbalance is the mediator.

Use T5 to turn correlation into a controlled cause and evaluate placement/load-balancing mitigation.

If identical routes still roll
Look below routing.

Prioritize per-card queue/service times, sparse WCLS tile lag, host IOVA/state, then low-level races.

07 / APPENDIX

Negative controls and audit boundaries

No unordered expert iteration found

Runtime expert containers are indexed vectors and launch in ascending expert ID order. Scheduler children use an insertion-ordered map.

Top-k tie behavior is mostly explicit

AVX bf16 top-k selects the lowest matching lane. Scalar partial_sort lacks a total equal-value comparator, but adds no fresh entropy for identical binary/input.

Placementâ€™s â€œshuffleâ€ is repeatable

The seed is hard-coded to 20240531. gpt-oss expert TP1 placement is deterministic for fixed device and tensor order.

Expert weights are not host-streamed

They are resident in FPGA HBM after load. Host hugepage/NUMA state can affect KV, activation, and result traffic, not per-token expert-weight streaming.

Speculation is not a default explanation

Speculative decoding has its own logic and RNG surfaces, but the campaign asserted speculation off. Treat it as configuration-dependent, not the gpt-oss baseline.

Current source comparison

At inspected current HEAD 96891b665840, the relevant MoE, top-k, and generator behavior is unchanged from the frozen commit; nearby model edits are trace instrumentation.

Sparse WCLS has a separate tie surface

The incremental top-k heap compares scores only. TP blocks are polled by fixed tile index, but readiness decides which blocks are consumable in each pass; exact bf16 ties can therefore retain different tokens.

Expert telemetry is aggregate, not route replay

active_histogram and counts are high-value before/after snapshots, but they do not preserve per-pass expert co-occurrence, card maxima, or route order. A null aggregate result cannot close every route-shape mechanism.

The seed CLI loses integer precision

cxxopts::value<float> rounds large seed literals before storing them as uint32_t. The campaignâ€™s effective fixed seed is 2954953984, not 2954953865; inactive for greedy, but a real reproducibility bug.

Small-batch routing does avoidable work

For batches below 16, the per-expert reserve expression is zero; active experts allocate dynamically. The common route also builds expert_major, which the generated gpt-oss path does not read. Both are amplifiers, not random sources.

Do not make this inference: â€œThe source contains std::random_device near MoE, therefore random expert routing caused the lottery.â€ That code is real, and CIâ€™s separate benchmark helper even sets the enabling environment variable, but the generated gpt-oss path at this commit never calls it. The observed checkerboard scripts did not set it either.
