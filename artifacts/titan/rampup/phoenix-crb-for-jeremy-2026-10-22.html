3. The rules for counted runs, as agreed on 22 October

  • Windows: Mon–Fri 13:00–21:00 UTC. That is 06:00–14:00 PDT and 09:00–17:00 EDT until 31 October, and 05:00–13:00 PST and 08:00–16:00 EST from 2 November (US clocks change on Sunday 1 November). Your script refuses a run that would end after 21:00 UTC.
  • Notice: at least 2 h ahead, in the phoenix-crb channel, where the other users of the host see it.
  • RUNNING file: /tmp/positron-perf.RUNNING for the whole block. While it exists, nobody else logs in or runs anything. Outside blocks the host is shared as usual: builds and untimed tests on cores 0–95 at any time.
  • Launch line: start the label with the outer taskset -c 120-125 so that the shell and Python land on a balanced core, then widen the set. Once the device thread pins itself, the inner set may be 120–127.
taskset -c 120-125 taskset -c 120-125,127 prlimit ... bash tools/ci/run_scheduled_gate.sh churn ...   # until the device-thread pin lands
taskset -c 120-125 taskset -c 120-127     prlimit ... bash tools/ci/run_scheduled_gate.sh churn ...   # after it: 127 pass thread, 126 device thread
  • Clock rule: one CPPC pair on 126 and on 127, read before and after the block, never during it. Pass: delivered ≥ 2,772 MHz (99% of 2,800). A miss voids the run.
  • Do not run during a block: snap, unshare, podman, systemd-run or any service restart (they send interrupts to busy cores). Do not read feedback_ctrs or cpuinfo_cur_freq of 126 or 127 during a run (two to four interrupts per read). Your phx-isol.py already avoids this.
# as positron-perf, once before and once after a block, for CPU 126 and 127
cat /sys/devices/system/cpu/cpu127/acpi_cppc/feedback_ctrs            # ref:<R0> del:<D0>
# ... the block ...
cat /sys/devices/system/cpu/cpu127/acpi_cppc/feedback_ctrs            # ref:<R1> del:<D1>
# delivered MHz = 50 * (D1 - D0) / (R1 - R0) * 20      pass: >= 2772
