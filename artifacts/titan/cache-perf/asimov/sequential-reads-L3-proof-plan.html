Does L3 make the prefetcher run farther ahead?

Short version. The measured speedup is clear. Your explanation is plausible, but the present counters do not measure prefetched data waiting in L3 or the core waiting for late prefetches. Test those two claims directly, then remove L3 prefetch storage while preserving the rest of the request machinery as closely as the platform allows.

Success criterion: distinguish useful data stored ahead of demand from faster handling of requests that need no L3 residence. A result may support both mechanisms; the plan must allow that outcome.

Words used here
  • Asimov: the platform that produced these measurements. C1-Nano is its Arm processor core.
  • DSU: DynamIQ Shared Unit, the cluster containing CPUs 2 and 3. In this configuration, L1 data holds 32 KiB per core, L2 holds 128 KiB per cluster, and L3 holds 256 KiB per cluster.
  • L3 off: snoop-filter-only mode. The cluster tracks cache ownership but its L3 stores no data.
  • Prefetch: a read issued before the program needs the data. Demand: the program's own read.
  • Line: a 64-byte cache block. In flight: a request issued but not yet completed. Resident ahead: returned data waiting in a cache before it is needed. These are different quantities.
  • LFB: line-fill buffer, which tracks a cache line whose fill is still underway.
  • PMU: performance monitoring unit, the hardware counters. RTL: register-transfer-level hardware design, where signal traces or a controlled model change may be possible.
  • SLC: the 5 MiB cache in the chip's mesh interconnect. DRAM: external main memory. Home node: the mesh component responsible for an address.
  • GB/s: 10⁹ bytes per second. KiB and MiB use powers of 1024. est.: estimate.

  • Record executable hashes, firmware revisions and actual control-register values. Check the L3 state around each measurement group. A boot name alone is not a configuration check.
  • Run three timed repetitions initially. Preserve every row and use the median for new comparisons. Return to the starting condition after a comparison to check for drift. Repeat from independent resets or boot snapshots before making a causal claim.
  • For this plan, use a predeclared ±5% bandwidth equivalence margin for “no material change.” This is a decision threshold, not measured variability. Require the uncertainty interval from independent repeats to fit inside that margin. If it does not, take more repeats or report insufficient precision.

Decision: if A/B is large and C/D is equivalent to 1, the gain depends on prefetching under these conditions. If C/D also shows a material gain, prefetching cannot be the whole explanation. A smaller residual gain permits a mixed cause. Neither result identifies L3 storage.

Definitions: C1-Nano Technical Reference Manual, 107753_0002_06_en, pp. 143–145. The local hardware decoder includes 0x8264; whether these events count correctly on this emulator remains to be validated.

  • Report events per logical 64-byte line. Do not call these hit percentages: the kernel performs several load operations per line, and the event populations differ.
  • Use a repeated 16 KiB read as a ready-L1 control. Use a trace-confirmed late-prefetch case as the positive control for the late-fill events. The slower B stream is a candidate stimulus, not proof that the event must count.
  • Accept counters only with complete coverage and a verified event source. Split groups if the hardware cannot schedule them together. A column that always reads zero is unvalidated.

Prediction: your picture predicts less demand waiting for unfinished data in A. More late-prefetch events in B would support that part of the picture. Equal event counts do not reject it: the waiting duration may differ. Measuring that duration requires the trace in D.

C. Keep L3 enabled and change the prefetch destination

First measure which prefetcher uses L3. Add 0x00DE for L3 stride-prefetch accesses and 0x00DF for L3 offset-prefetch accesses. Retain 0x8156 for total L3-targeted activity and 0x81E6 for first demand hits on L3-prefetched lines. [C1-Nano manual, pp. 143 and 150]

  1. With L3 full and hardware prefetching on, compare the normal setting with IMP_CPUECTLR_EL1.L1SPFL2[6]=1. The documented change sends stride prefetches to L1 and L2 instead of L1 and L3. Confirm both baseline and test readbacks. If the baseline already reads 1, setting it to 1 is not an intervention. Verify the intended routing change with the stride counter and the existing L2-target event, 0x8155. [C1-Nano manual, p. 292]
  2. If L3 offset activity is present, test L3OPFCTL[14:13]=0b11 separately. It disables that offset prefetcher. Then test the combined setting if both paths were active. Keep all other fields fixed. [C1-Nano manual, p. 291]
  3. Restore the normal setting and reproduce the fast result. Compare bandwidth and late-fill events across the change and its reversal.

Decision: a reproducible loss after removing the active L3-directed path shows that path matters. It does not isolate stored data from request generation or handling, because redirecting a prefetch changes both. Unchanged bandwidth challenges that path's necessity only if the trace confirms its useful L3 storage was removed. Other prefetchers or compensating effects must remain visible.

Also collect 0x0120 and 0x0122, the L1-prefetch accesses reaching L3 and those receiving data from outside L3. These cover a path that 0x81E6 misses: a prefetch can move a line onward before demand reaches L3. Keep them as separate rates until their populations are validated. Their difference is not automatically a count of ready L3 hits. [C1-Nano manual, p. 155]

D. Capture the line history, then test storage causally

Ask the Asimov model owner for a trace in A, B, and the decisive condition from C. Capture several steady portions of the original 32 MiB read, away from startup and pass boundaries. Start with windows containing 4,096 consumed lines. Extend the capture before and after each window to include outstanding transactions at its edges. Check that traced and untraced bandwidth agree within the declared margin.

Compute these quantities from the same window:

  • Useful prefetched lines resident in L3 before their first onward request, and how many demand-line positions ahead they are. Exclude old lines left from a previous pass.
  • Time from prefetch issue to demand arrival, and from data-ready to demand arrival, in ns. Report the distribution and the fraction arriving late.
  • Outstanding external reads by counting issued-but-uncompleted transactions at each time. Keep this separate from completed lines waiting in caches.
  • Unique external data fetches per consumed line, split by prefetch and demand. Include extra fetches, unused prefetches, and source SLC versus DRAM.
  • Core stall cycles per consumed line, with overlapping waits counted once. Do not add the waiting times of parallel loads to explain elapsed time.

The strongest intervention: use a supported model control that prevents useful L3 prefetch residence while leaving L3 demand handling, prefetch generation rules, acceptance rules, transient matching, and resource configuration intact. Restore it afterward. No such control is established in the available files. The model owner must identify the control or implement and validate a narrow RTL experiment.

Verify the intervention in the trace. It must not silently disable prefetch generation, discard responses, or change the queue configuration. Later traffic can change as a consequence of removing storage; record that change. If the intervention cannot separate storage from request handling, label its conclusion accordingly.

Insufficient data: the available files do not establish access to the required trace signals or an independent allocation control. Without them, stages A–C can narrow the cause but cannot prove that L3 RAM residence caused the full speedup.

3. Decide the result before seeing the new data

OutcomeEvidence required
Support your mechanism as a causeUseful lines demonstrably wait in L3 ahead of demand; demand waiting falls; the selective storage intervention removes a material part of the gain; restoring it restores the gain. Trace the request sequence that connects those changes.
Reject L3 residence as necessary for this gainThe fast stream persists within the equivalence margin after useful L3 residence is removed, with the removal and preserved request machinery verified. Alternatively, a complete trace of the fast measured interval shows no useful L3 residence at all.
Favor changed request handlingThe speedup follows earlier acceptance, different matching/forwarding, or shorter resource waits without useful L3 RAM residence. A matched intervention on that mechanism reverses the effect.
Both contributeRemoving storage removes part of the gain, while a remaining gain follows the request-handling change. Report both measured effects; do not force an exclusive explanation.
UnresolvedOnly aggregate refill counts, target-access counts, whole-command queue occupancy, or unvalidated zero counters are available. Name the missing line-history or selective-control evidence.

4. Fit this into the existing run plan

  • Reuse: run_l3.sh already supplies the four firmware conditions' workload commands, the existing target counters, and the read/write/random-chain controls. Add the sequential-chain control and the two small counter groups above.
  • Fix measurement scope: add a kernel-phase marker or counter enable/disable handshake after warm-up and around the timed passes for mesh counts. The current cmncount counts the whole command. Longer runs alone do not make it a per-core concurrency measurement. Keep request and occupancy sets separate because their mesh filters conflict. [lib_run.sh:43–56]
  • Validate event selection: an L3-directed access is not an allocation. 0x400B shares 0xA2's signal in the inspected design. LL_CACHE events depend on EXTLLC and cache-presence signals. Neither is a fallback total external-fetch counter without validation. [common.h:388–426]
  • Defer explicitly: the H3 multi-reader placement sweep answers a separate question about shared cluster limits. It is useful after a trace identifies a candidate shared resource. It is not needed first to decide whether one stream benefits from L3 residence.
  • Output: save raw repetitions, register readbacks, counter coverage, trace data, and request identities. Plot bandwidth and late-fill rates by condition. Plot outstanding requests and useful resident lines separately. Draw wall-clock lanes from measured trace timestamps, with waiting shown dashed and core-blocking intervals highlighted.
