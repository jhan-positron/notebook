Asimov C1-Nano memory performance: brief

Latest: run 4 boot E (membench-jibin-010, 2026-11-05, commit b79dffa, SCP 0.48.0-nopcie-l3.1 (the system control firmware), TF-A 0.35.0 (the Arm Trusted Firmware)) on the GA13 Palladium (one Asimov hemisphere), the first boot with the DSU L3 in use as a cache (IMP_CLUSTERPWRSTAT_EL1 0x70 on CPU 2's cluster, Jesse's README). Beside it: run 3 (membench-jibin-004, 2026-11-03) and run 4 boots A to D (005 to 008), all measured with the L3 of CPUs 2 to 9 holding no data (register 0x0, 0 L3 hits). One C1-Nano core on CPU 2 unless stated. DRAM is an emulator memory, not LPDDR5X. Full reports: asimov-c1nano-perf.html, asimov-cme-perf.html. Every number here is read from the CSV files by gen_brief.py through gen_perf.py.

Words used here

run, boot
A run is one job on the emulator (run 3 = membench-jibin-004). Run 4 is five boots: A as run 3, B the data prefetchers off, C the 64 KiB contiguous hint on the OCM mapping, D both, E the L3 on.
chase, hit set
A random pointer chain, one load per 64-byte line. Fresh: walked once. Flushed: every line cleaned and invalidated from the caches first. Hit set: the 64 KiB to 512 KiB chases with the L2 and L3 hit events.
sparse chain, dense chain
Dense chain: every 64-byte line of the buffer is a member of the chain. Sparse chain: one member line per 4 KiB page, so a line the prefetcher fetches next to a member is never a member.
single-call form, looped form
The two forms of run 4's L1 bandwidth rows: every pass of a rep inside one call (single-call), or one call per pass (looped).

3. What else the runs showed

  • The L3 is on for the first time. On runs 1 to 3 and boots A to D the L3 of CPUs 2 to 9 held no data (register 0x0, 0 L3 hits per load on boot C). Boot E's rebuilt SCP stages the full L3 before the clusters power on. Its hit set counts 47, 75 and 92 % L3 read hits per load at 192, 256 and 384 KiB, and the data read fell from 14.1, 19.7 and 22.7 ns on boot C to 7.8, 9.5 and 10.9 ns [latency-dram-small-l3.csv, Jesse's boot E README].
  • The 52 ns DRAM data read is a fixed-delay memory model. On boot B an address-order 8 MiB chain reads 52.762 ns per load and a random one 52.739 ns. The model answers in a fixed time. 24.2 ns of it is the home-node load (the 2 MiB SLC data read), and the rest, about 28.5 ns est., is the model's delay. The L3 does not change it (52.659 ns flushed on E, 52.657 on C) [latency-dram-seq.csv, latency-dram-flushed.csv, boots B, C, E].
  • One core reads 2.7 times more from DRAM with the L3 on. The plain read loop reads 32 MiB at 9.2 GB/s on run 3 and 9.2 GB/s on boot C, both with the L3 off. On boot E, with the L3 on, the same loop reads 24.5 GB/s. Adding a software prefetch hint (PRFM, the Arm prefetch instruction, issued 4 lines ahead) does not help. It changes boot C by +2 % and lowers boot E to 20.4 GB/s. Why the L3 makes the loop faster is Insufficient data. The refill counters per line are about the same on both boots (L1 0.99 and 0.99, L2 0.96 and 0.97, L1 prefetch 0.99 and 0.99 at 2 MiB), so they do not show the mechanism [bandwidth-read-prefetch.csv].

4. Caveats

  • DRAM on this emulator image is a memory model, not LPDDR5X, so the DRAM latency and multi-core bandwidth rows are not silicon numbers. Its configured delay is an open question to Jesse.
  • The bandwidth set (one-core sweep, multi-core, writer placement, OCM bandwidth) has not run with the L3 on.
  • hypothesis Boot E reads +0.64 ns at 32 MiB and +0.48 ns at 16 MiB above boot C (same commit): translation walks. A walk-counted 32 MiB row on E and C in one process would test it.
