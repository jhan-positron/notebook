## The prefetchers: where they were turned off, and the readbacks

- **Where:** this boot's BL31 is TF-A 0.35.0-pfoff.1 (`5a9e2a8`, debug): TF-A 0.35.0 rebuilt by this box with one added hook, never published (its banner, `uart_1.log` line 2: `version: 5a9e2a8 (0.35.0-pfoff.1)  (debug)`). Linux cannot make these writes itself: the release BL31 traps an EL2 write to either register. The hook runs at EL3 at the end of every power-on of CPUs 2-9 (each PSCI CPU_ON, CPU 3's return included), before BL31 returns to Linux; CPUs 0-1 are left alone. In order it sets IMP_CPUECTLR_EL1 (S3_0_C15_C1_4) bit 48, ALLPFDIS, if clear; writes IMP_CMESELR_EL1 (S3_0_C15_C11_1) with 0, which selects the cluster's one CME for the CME register accesses that follow; sets IMP_CMECFG_EL1 (S3_0_C15_C11_4) bit 28, PF_DISABLE, if clear; reads the registers back and prints one line on the AP console.
- **Readbacks** (the AP console, `evidence/runs/membench-jibin-006/a01/evidence/run-evidence/uartout/uart_1.log`, lines 104-111 at boot and line 360 for CPU 3's one return). In all nine lines the `ectlr`, `cmpx` and `cmecfg` values are what the RTL predicted before the boot (`evidence/firmware/tfa-v0.35.0-pfoff.1.txt` step 12). CPU 2's line reads the CME of DSU 1 and CPU 8's that of DSU 4, the two CMEs the plan asks about:
  - CPU 2: `pfoff cpu2 ectlr 0x900000->0x1000000900000 cmpx 0x340000009400 cmecfg 0x2a9f11115->0x2b9f11115 clusterpwrctlr 0xb40170 clusterpwrstat 0x0`
  - CPU 8: `pfoff cpu8 ectlr 0x900000->0x1000000900000 cmpx 0x340000009400 cmecfg 0x2a9f11115->0x2b9f11115 clusterpwrctlr 0xb40170 clusterpwrstat 0x0`
  - CPU 3, back online at the end of the script, after the CME rows: `pfoff cpu3 ectlr 0x900000->0x1000000900000 cmpx 0x340000009400 cmecfg 0x2b9f11115->0x2b9f11115 clusterpwrctlr 0xb40170 clusterpwrstat 0x0`
- **IMP_CPUECTLR_EL1 bit 48** went from 0 to 1 on every CPU at every power-on (`0x900000` is the reset value).
- **IMP_CMPXECTLR_EL1** (S3_1_C15_C1_4) reads `0x340000009400` on every CPU: bits 26 and 25, the translation-prefetch disables, are clear. The boot leaves this register alone.
- **IMP_CMECFG_EL1 bit 28** was set in each cluster's CMECFG at its first core's power-on (CPUs 2, 4, 6, 8: `0x2a9f11115->0x2b9f11115`) and was already set at its second core's (CPUs 3, 5, 7, 9: `0x2b9f11115->0x2b9f11115`). Until a cluster's CME first powers up, the cluster's CPU bridge answers CMECFG from its own copy, which the CME loads at its first power-up and saves back at each power-down, so the boot-time values are that copy. The reading of the CME itself is CPU 3's before-value at its return after the CME rows, `0x2b9f11115`: bit 28 held through the CME rows.

## L3 power

- **His question:** IMP_CLUSTERPWRSTAT_EL1 reads 0x0 at every power-on of CPUs 2-9 (the hook's line), and in his `log.txt` on CPU 2's cluster just before and just after his hit-counter command, both with CPU 3 offline (lines 7 and 9: `# box clusterpwrstat before l3: 0x0`, `# box clusterpwrstat after l3: 0x0`). By the DSU RTL's field names (Arm's TRM is not in the box), 0x0 is SLC [7:6] = 00, one L3 slice (this DSU has only one), and POR [5:4] = 00, the L3 RAM in the snoop-filter-only state, SFONLY (01 is HALF_ON, 11 FULL_ON); bits [1:0] are the cores' power-down and retention requests, which BL31 writes as 0 at every power-on, not a measured state. IMP_CLUSTERPWRCTLR_EL1 (S3_0_C15_C3_5) 0xb40170 is that register's reset value, which TF-A 0.35.0's DSU driver writes back at every power-on just before the hook reads it, so it does not show what the cluster's power controller asked for. Its PRTNRQ [5:4] = 11 and SLCRQ [7:6] = 01, with AUTOPRTN [14:12] and AUTOSLC [17:15] at 0, only feed hints to that controller, which runs in static mode and ignores them (`evidence/jibin/l3-power-rtl.md` parts 2, 4 and 7).
- **Why SFONLY:** SCP 0.48.0-nopcie.1 asks for all slices and full L3 RAM (cluster operating mode 7) only for the cluster of CPUs 0-1, at boot (asimov-scp-firmware at `scp-v0.48.0`, the source of this SCP, `product/asimov/module/asimov_system/src/mod_asimov_system.c:703`, in a file identical to `scp-v0.46.0`'s (git blob 45b32bb8); the staging came in commit `9ef7952`, where the call sits at lines 286-309; its comment at `:674-677` leaves the other clusters to "a follow-up", and the SCP console prints one `Staged cluster 0 PPU PWPR=0x00070008`). The clusters of CPUs 2-9 are powered on later, when Linux starts those CPUs, by the SCP's standard power-controller driver, which leaves them in the reset operating mode 0: one slice, SFONLY. Nothing changes it afterwards. SCP 0.34.0, which run 1 and round two's control run used, does the same.
- **What it does:** in that mode the DSU neither looks up nor allocates anything in its L3, so the 256 KiB L3 of CPUs 2-9 holds no data and every L2 miss goes to the SLC or DRAM. On the emulator nothing is switched off electrically; the L3 is unused by logic. What silicon would power down in this mode is not settled here.
- **What his rows show:** in `latency-dram-small-l3.csv` (CPU 2, CPU 3 offline, 64-512 KiB) `l3d_access_rd_per_load` (0xA0) equals `l3d_refill_rd_per_load` (0xA2) to within 0.0001 per load in every row (192 KiB: 0.4890, 0.4938 and 0.4933 for both): every L3 read missed. `l3d_hit_rd_per_load` (0x81C6) reads 0.0000 in all 21 rows; this boot is the first here to open 0x81C6, so its zeros agree but do not on their own show that it counts. The latency climbs from the L2's 6.06 ns at 128 KiB to 23.68-23.92 ns at 384 and 512 KiB with no level between. Boot A agrees: there, every L2 refill that no prefetcher requested is an L3 read refill from outside the cluster.
- **What this corrects:** the earlier READMEs (runs 1-3 and boot A) list a 256 KiB L3 per two-core cluster as a working cache, and readings rest on it: run 1's README labels its 192 KiB row "more than L2, less than L3", run 2's explains its per-region OCM rows by "the 256 KiB buffer fits in L2 plus L3 (384 KiB)", and run 3's places a core step at "192 KiB (its L3)". For CPUs 2-9 there is no L3 level: the 192 and 256 KiB rows mix L2 hits with SLC reads (0.51 and 0.19 L2 read hits per load, `l2d_hit_rd_per_load`), and at 384 KiB almost every load is an SLC read (0.001-0.003 hits per load). The record of this reading, with its RTL and firmware references, is `evidence/jibin/l3-power-rtl.md`.
- **Not yet done:** a CLUSTERPWRSTAT read on CPU 0 or 1, whose cluster the SCP sets to mode 7 (it should read 0x70, or 0x0 if that cluster was already on in mode 0 when the SCP set it, since a direct change from mode 0 to mode 7 is refused), and a read of a cluster power controller's own status. Giving CPUs 2-9 an L3 needs an SCP that sets mode 7 for each of their clusters before it powers on.

## OCM mappings

`dmesg.txt` has one line per `/dev/ocm` mapping, 110 in all, in the form `membench_ocm: map pid=207 comm=latency va=0xffff8468a000 pa=0xe0000000 len=0x40000 prot=0x68000000000fc3 pte=0x1680000e0000fc3 cont=0/64 same=64/64`. This module adds to boot A's line the process name, the first page-table entry, how many of the mapping's entries carry the contiguous bit, and how many share the first entry's attributes. Each line carries the kernel-log time, and the lines tie to his OCM commands in `log.txt` by the order of their `pid` groups, one process per command.

- Every mapping is one whole 256 KiB region at its base: 22 each at 0xE0000000, 0xE0100000, 0xE0200000, 0xE0300000 and 0xE0400000, over 86 OCM commands, all by `latency`.
- Every mapping has `prot=0x68000000000fc3` (Normal write-back memory, inner shareable, user read-write, never executable), 4 KiB pages, `cont=0/64` (no contiguous bit, as on boot A) and `same=64/64`.
- `va - pa` is a multiple of 16 KiB on 19 of the 110 mappings, of 32 KiB on 14 and of 64 KiB on 7 (boot A: 23, 8 and 5). The kernel places each mapping, so this alignment varies per command and between the boots. A TLB entry that merges neighbouring 4 KiB pages can only form where the two addresses share that alignment.

## Platform facts

These equal boot A's except the TF-A, the `/dev/ocm` module and the L3 (CPU placement and Caches); this boot's `sysinfo.txt` and `dmesg.txt` read the same.

- **Emulator image:** GA13 release `a10280100`, build `hemi_rtws_tlm`, RTL `0d9e214eb43b` (main, 2026-10-28), from this box's private copy. Real C1-Nano cores and clusters with their CMEs, the CMN-S3 mesh with its SLC and OCM; the matmul array is cut to one column.
- **Firmware:** SCP 0.48.0-nopcie.1 (`e361a83`, debug build) and TF-A 0.35.0-pfoff.1 (`5a9e2a8`, debug): boot A's TF-A 0.35.0 (`3b3df18`) plus the prefetcher hook above.
- **Kernel:** Linux 6.18.36 built from asimov-os `v0.0.17`'s config and patches plus transparent huge pages (madvise), hugetlbfs and debugfs; command line in `sysinfo.txt`.
- **CPU placement:** ten C1-Nano cores, all online at boot; CPUs 2-9 isolated from the scheduler and `nohz_full`, device interrupts on CPUs 0-1. Each pair {2,3}, {4,5}, {6,7}, {8,9} shares an L2, a CME and one mesh port.
- **Clock:** core 2.000 GHz against the 1 GHz generic timer: 4.01 cycles per 2.001 ns load on the 4 KiB control.
- **Caches:** L1 data and instruction 32 KiB per core, L2 128 KiB per two-core cluster, 64-byte lines. Each cluster has a 256 KiB L3, which on CPUs 2-9 holds no data (L3 power above). The SLC is five home nodes of 1 MiB; the firmware locks 4 of 16 ways of each as OCM.
- **OCM:** five regions of 256 KiB at 0xE0000000 + n MiB, mapped by this box's `/dev/ocm` module (sha256 `937077c761e5227b9799f2b2fd4a609705737d71b9bebe96b0320fa2f548e577`, loaded with `cont=0`, so it maps as boot A's did).
- **PMU:** `armv9_c1_nano`, 21 counters (20 plus the cycle counter; `dmesg.txt`); mesh PMU `arm_cmn_0`.
- **Huge pages:** 256 pages of 2 MiB reserved at boot; MemTotal 1,833,848 kB.
- **DRAM caveat:** AP DRAM on this image is an embedded emulator memory, not LPDDR5X, so no DRAM latency or bandwidth number here is silicon-like.
- No real-time clock: every time his script read shows 1970.
