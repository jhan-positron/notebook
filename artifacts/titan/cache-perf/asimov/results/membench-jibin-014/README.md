# cache-mem-perf on the Asimov emulator: run membench-jibin-014 (run 8, the mesh latency map: his boot 1)

Jibin Han's `cache-mem-perf` (github.com/jhan-positron/asimov, folder `cache-mem-perf`, commit `3b12e4f8a8c7414d14fb06b356c5a79e3e6c0a1e`) ran `sh run_map.sh --kernel-cpus` as boot 1 of his run 8, the L3 out of use and the data prefetchers off on CPUs 2-9, on one emulated Asimov hemisphere on the GA13 Palladium, on 2026-11-12 (UTC). His whole results directory is `results/bootM1/`, byte for byte as his script wrote it, with the kernel log as `dmesg.txt` and `SHA256SUMS` over all of them. This box checked that the files are whole. It did not analyse the numbers.

## Read first

- **His script ran whole.** Exit status 0, five commands (four `latency` control rows and one `meshmap`), `# run_map.sh done ...: 0 measurement command(s) failed`, `# meshmap: done cells=180/180`, all ten files back. `latency-map.csv` has 1,269 data rows: 7 passes for each of 180 cells and one idle row for each of the 9 CPUs.
- **His own lines in `latency-map.csv`:** `# mesh counters: level=1 events=hns_pocq_reqs_recvd_all,hns_mc_reqs_local_all,hns_cache_miss_all,hns_snp_sent pmu_cpu=0`, `# read_floor: 10 10 6 15 9`, `# classify: probe_ns=11647 lines=2048 projected_s=0.1491`, `# classify: probed=10255 ambiguous=41 unused=10 per_node=2049,2048,2050,2050,2048 lines=2048 probe_loads=64 elapsed_s=0.1212`, `# one_2mib_page: yes (backing=hugetlb)`, `# pagemap: pfn=0xc004800 page_bytes=4096 covers=buffer ...`. The classification kept 2,048 lines per cell and did not reach its time stop.
- **`--kernel-cpus` was on,** so the file has 20 cells from CPU 0 in a last block, after every other row. It was switched on because the rehearsal's CPU 0 command came back whole (`../membench-jibin-013/README.md`). On his question whether the option is safe: the boot E note he cites was about one kernel-mode register read made with interrupts off (IMP_CLUSTERPWRSTAT_EL1 on CPU 1), not about user-mode loads, and his CPU 0 block ran whole on the rehearsal and on this boot.
- **CPU 0's rows are not in the cache state of the other rows of this file.** On this boot the clusters of CPUs 2-9 have their L3 out of use and their prefetchers off, while CPU 0's cluster has its L3 in use and its data prefetchers on: the SCP stages the full-L3 mode for the cluster of CPUs 0-1 on every build, and the hook of TF-A 0.35.0-pfoff.1 that turns the prefetchers off covers CPUs 2-9 only. The file shows it: `l1d_refill_hwprf` or `l2d_refill_hwprf` is nonzero in 128 of the 140 CPU 0 cell rows and both read 0.0000 in all 1,120 cell rows of CPUs 2-9, and `l3d_refill_rd` reads 0.32 to 0.46 in the CPU 0 `ocm-flush` rows where CPUs 2-9 read 1.00 to 1.01. His README's rule is per boot ("A boot with the prefetchers on is not a distance map"); by the same reasoning CPU 0's rows are prefetcher-effect rows on this boot, which is this box's reading, not his rule. No register readback stands behind CPU 0's state: the hook prints for CPUs 2-9 only.
- **More on CPU 0.** Its cluster's mesh port (node 80, crosspoint (1,2)) is 1, 3, 3, 5 and 5 steps from home nodes 88, 160, 216, 288 and 344, the mirror image of the port of CPUs 8-9 (node 336, crosspoint (5,2): 5, 5, 3, 3 and 1). CPU 0 is the kernel's CPU: it is not isolated, keeps the 100 Hz timer tick, takes the device interrupts (`irqaffinity=0-1` allows CPUs 0 and 1, and this kernel's interrupt controller driver sends each interrupt to the first CPU of its mask; read from the driver's source, `/proc/interrupts` was not captured), and executes every mesh counter read (the mesh PMU's CPU is 0), so a read made from CPU 0 is local while the read floor was measured from CPU 2. His program runs there under SCHED_FIFO 10, as on every CPU. With `--last-cpus 0` it also pins itself to CPU 0 once at its start, for its pin test, before any row is written.
- **The mesh counters on this kernel.** A read of an event group stops the whole mesh PMU, reads every event and restarts it (Linux 6.18.36, `kernel/events/core.c` and `drivers/perf/arm-cmn.c`: his levels 1 and 2), so mesh requests that arrive during a read go uncounted. A read of an event opened alone (level 3) does not stop it. The mesh events count per home node, so the mesh columns of every row also hold the requests of the kernel's CPUs 0-1.
- **CPU 3 stayed online through every row,** idle while another CPU measured: `run_map.sh` only writes 1 to its online file (`cpu3 online=1`, a no-op here), and `meshmap` measures from it in its turn. The same four control rows (the dense flushed 256 KiB OCM chain) ran with CPU 3 offline on his round four boots.
- **The OCM mappings are placed differently on each boot.** `/dev/ocm` maps at the address the kernel picks, and `dmesg.txt` has one line per mapping (lines 203-211). `meshmap`'s five mappings are aligned to 4 KiB only against their physical addresses on this boot (`va=0xffffb557b000` for `pa=0xe0000000`, the other four alike), and to 256 KiB or more on boot 2. His `l1d_tlb_refill` column reads 0.0098 to 0.0195 per load in the `ocm-flush` and `ocm-evict` rows of CPUs 2-9 on this boot and 0.0059 to 0.0068 on boot 2 (0.0024 to 0.0029 in the `slc` and `dram-flush` rows on both). So an OCM cell of this boot against the same cell of boot 2 differs in the mapping as well as in the L3. Boot 3 has three of the five at 4 KiB only and two at 256 KiB or more (`../membench-jibin-016/README.md`). The four control rows, which `run_map.sh` calls "the same-boot reference for meshmap's ocm-flush cells", have mappings of their own (lines 203-206), aligned to 32, 4, 8 and 8 KiB. What a mapping's alignment can do to an OCM row was seen in round four: boot D, which mapped the OCM 64 KiB-aligned and with the contiguous hint, read its core OCM chase rows 0.944 to 1.017 times those of boot B, which had the kernel's placement (`../membench-jibin-008/README.md`, which also says that this core's TLBs merge 4 KiB entries only where the two addresses agree modulo 16 KiB and 32 KiB).
- **This boot ran its own classification.** Its buffer got the physical frame 0xc004800 (the first line of `map-homes.txt`), the same frame the rehearsal's two commands had; boot 2 got another, 0xc004c00, and boot 3 a third, 0xc004000, so each boot's rows go with its own `map-homes.txt`. `meshmap`'s set-up (the buffer's first touch, the first OCM stores, the open of the core counters) ran on CPU 9, the last CPU of its default list.
- **This boot did not wait for his look at the rehearsal** (Jesse's decision), and his boot 2 was queued once this box's check of this boot found nothing wrong, before these files reached him (the box's call: his results go to him in two messages).

## What the box added

- **The wrapper.** The init can run only `/bin/sh <script> --out <folder>`, so it ran the box's `box_run_map_cpu0.sh`, which runs his `run_map.sh --kernel-cpus --out .../results/bootM1`. No file of his is changed.
- **Two lines on stdout, none in his files.** The wrapper printed IMP_CLUSTERPWRSTAT_EL1 of CPU 2's cluster, read through the box module's sysfs file, before and after his script: `# box clusterpwrstat before run_map: 0x0` and `# box clusterpwrstat after run_map: 0x0`. They are the first and the last line of the init's capture of the program's output, which is not part of his folder.

## Platform

- **Image:** GA13 release `a10280100`, build `hemi_rtws_tlm` (RTL `0d9e214eb43b`), from this box's own copy. The AP DRAM on this image is the emulator's embedded memory model, not LPDDR5X, so no latency of a load fetched from DRAM is silicon-like here: that covers `meshmap`'s `dram-flush` rows, and an `slc` row only where the slice did not serve the loads (his `mc_reqs` rule tells the two apart).
- **Firmware:** SCP 0.48.0-nopcie.1 (`e361a83`, debug; its banner is `uart_0.log` lines 2 and 13) with TF-A 0.35.0-pfoff.1 (`5a9e2a8`, debug; `uart_1.log` line 2), the firmware of his round four boot B. The SCP console has `Staged cluster 0 PPU PWPR=0x00070008 (ON)` and no staging line for clusters 1-4.
- **BL31's readbacks** (the AP console `uart_1.log`, lines 104-111, one line per CPU 2-9 at its power-on; `run_map.sh` never takes CPU 3 offline, so there is no ninth line for a CPU 3 return as boots B and F2 had):
  - CPU 2: `pfoff cpu2 ectlr 0x900000->0x1000000900000 cmpx 0x340000009400 cmecfg 0x2a9f11115->0x2b9f11115 clusterpwrctlr 0xb40170 clusterpwrstat 0x0`
  - CPU 8: `pfoff cpu8 ectlr 0x900000->0x1000000900000 cmpx 0x340000009400 cmecfg 0x2a9f11115->0x2b9f11115 clusterpwrctlr 0xb40170 clusterpwrstat 0x0`
  - IMP_CPUECTLR_EL1 bit 48 went from 0 to 1 on all eight CPUs. IMP_CMECFG_EL1 bit 28 was set at each cluster's first core (CPUs 2, 4, 6, 8) and read already set at its second (CPUs 3, 5, 7, 9: `0x2b9f11115->0x2b9f11115`). IMP_CLUSTERPWRSTAT_EL1 read 0x0 in all eight lines, and 0x0 in the box's two run-time lines above.
- **Kernel:** this box's Linux 6.18.36 (transparent huge pages, hugetlbfs, debugfs, `CONFIG_PROC_PAGE_MONITOR=y`), command line `earlycon=pl011,0x2a400000 quiet nohz_full=2-9 isolcpus=domain,managed_irq,2-9 irqaffinity=0-1 earlycon=pl011,0x2a400000 console=ttyAMA0,480000 panic=0 loglevel=7 rdinit=/sbin/membench-init`. The kernel runs on CPUs 0-1; CPUs 2-9 are online and isolated. 256 huge pages of 2 MiB were reserved. `/dev/ocm` maps the OCM in 4 KiB pages: `dmesg.txt` has 9 map lines, one region for each control row and five for `meshmap`.
- **The run:** queue request 5294 on ga13pd01. The wrapper, his script inside it, took 1.217 chip seconds (`MB RUN end status=exit:0 ns=1217014381`, the init's measure, which also covers the box's two reads of the register; his estimate for the script with `--kernel-cpus` is 1.01 s), and `meshmap` reports `cells 180/180 in 1.1054 s`. The hang guard of 12 chip seconds did not fire. The emulator ran 2,780 wall seconds per chip second.
- **Evidence in the box:** `evidence/runs/membench-jibin-014/` (console logs, the launcher's events, the results window, the checker's verdict `judge-jibin.txt`: `JIBIN_CHECK PASS`).
