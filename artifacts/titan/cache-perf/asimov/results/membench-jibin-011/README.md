Each decodes to OP_STATUS [19:16] = 7, the staged mode, and PWR_STATUS [3:0] = 0, OFF, so each of clusters 1-4 reported mode 7 while still powered off.
- **Their order:** all five lie between line 181 and line 187, and so before every `Pinned CLUS<N>CORE<m>` line: `Pinned CLUS0CORE0` is line 190 (0.309214 s), and the cores of clusters 1-4 follow at lines 195-213 (0.480761-0.509558 s). From line 181 to line 187 is 9.310 ms of the SCP's clock, as on boot E.

This DSU has one slice, so 01 does not mean a second slice. Boot E read 0x70 around its core hit-counter command; boots B, C and D read 0x0 there (ONE_SLICE with SFONLY, snoop filter only).

## The memory model behind the home node

His question (2026-11-06): "what delay is the memory model behind the home node configured with?" The answer is read from the image's RTL (asimov-rtl at `0d9e214eb43b`; `evidence/jibin/memory-delay.md`, where all 38 cited files were checked byte-identical to the release's own clone on GA13); nothing was run for it.

- **No delay is configured.** The AP's DRAM (SMS, at 0xC0_0000_0000) is four embedded Cadence AXI memory models, one per SMS lane (XMS lanes 32-35, which the code calls the AUX lanes), and every delay control on those four is zero: read latency 0, write-response latency 0, READY delays and burst gaps 0, and no bandwidth or refresh scheduler. The lane wrapper loads a nonzero profile only when `DATAPATH_TIMING` is set, which is `GC_PAIR_INDEX` 0-15 (`emu/hemi_tlm/agents/goldcrest_ew_fullconn_avip.sv:118-119`, `:643`, `:689`); the SMS lanes are Goldcrest pairs 16 and 17 (`design/xms/packages/xms_pkg.sv:84-85`), and the repo's timing note says "The four AUX lanes retain native zero-delay startup" (`emu/hemi_tlm/doc/GC_DDR_TIMING.md:86-87`).
- **The DRAM-like profile does not apply to them:** 61 ns per read (a 40 ns link estimate plus a 21 ns LPDDR5 row hit), 40 ns per write response and a 38.4 GB/s cap are loaded only on the 32 datapath (weight-fetch) lanes (`goldcrest_ew_fullconn_avip.sv:112-141`; `GC_DDR_TIMING.md:70-80`).
- **The model's own response:** with its controls at zero it answers 3 lane-clock cycles after it accepts a read, 3 ns at the 1 GHz lane clock (`emu/hemi_tlm/tests/gc_avip_timing_tb.sv:342`, `:970-973`; `design/xms/rtl/xms_clk_gen.sv:11`). The repo checks that only in Xcelium, not on the Palladium build.
- **Where the rest comes from,** an inference by counting RTL stages: from the SN node's (SBSX) read request to the first data beat back is 20.0-20.5 ns for SMS ports 0-2 and 19.0-19.5 ns for port 3, made of the SMS bridge's register (0.5 ns each way at 2 GHz), 5 or 6 XMS register slices each way (2.5-3.0 ns), the 2 GHz to 1 GHz clock crossing (7.0-7.5 ns out, counting the FIFO write and the memory's accepting lane-clock edge, and 3 ns back) and the model's 3 ns (`memory-delay.md`, its path section, steps 3-11). The rest of his ~29 ns is inside the CMN: the home node's miss handling, the mesh hops to the four SMS SN nodes on the mesh's west column and back, and the SBSX's CHI to AXI conversion. Nothing in this tree configures that part, and this README does not determine its share. On F1 the flushed 8 MiB chase reads 52.658 ns and the 2 MiB SLC chase 23.714, 28.9 ns apart (the box's arithmetic), his reading of about 29 ns.
- **Address order:** nothing on the path models banks, rows, page hits or refresh, so no configured part of the delay depends on address order, which fits boot B's address-order 8 MiB chain (52.762 ns) equalling its random one (52.739 ns). What varies per line is which SMS port a line hashes to (port 3 about 1 ns quicker for the round trip) and the mesh distance between its home node and its SN node, the same mix for any order over the same buffer (inference).
- **Not determined:** the CMN's share of the ~29 ns, the 3-cycle native response on the Palladium build itself, the phase of the 1 GHz lane clock against the 2 GHz clock (whether the crossing out takes 7.0 or 7.5 ns), and an SN round-trip measurement on this image; a waveform of one miss would settle the first.
- **What he can cite:** the SMS memory model has zero configured delay (a 3 ns native response in the repo's Xcelium test, not checked on the Palladium build), and the DRAM leg is RTL pipeline latency, with the CMN's part not set anywhere in this tree.
