## L3 power

- **The samples:** IMP_CLUSTERPWRSTAT_EL1 reads 0x0 in his `log.txt` on CPU 2's cluster just before and just after his hit-counter command, both with CPU 3 offline (lines 7 and 9: `# box clusterpwrstat before l3: 0x0`, `# box clusterpwrstat after l3: 0x0`; both reads returned a value, not an error). C's TF-A has no hook, so unlike boots B and D this boot has no power-on readback of the register.
- **The reading,** as on boots B and D (boot B's README, L3 power, gives the fields): by the DSU RTL's field names, 0x0 is one L3 slice with the L3 RAM snoop-filter-only (SFONLY), the mode SCP 0.48.0-nopcie.1 leaves the clusters of CPUs 2-9 in, since it stages the full-L3 mode for the cluster of CPUs 0-1 only (its console, `uart_0.log` in the same folder as `uart_1.log` above, prints one staging line, line 182: `Staged cluster 0 PPU PWPR=0x00070008 (ON)`). In that mode the DSU neither looks up nor allocates in its L3, so the 256 KiB L3 of CPUs 2-9 holds no data and every L2 miss goes to the SLC or DRAM; on the emulator nothing is switched off electrically. The record, with its RTL and firmware references, is `evidence/jibin/l3-power-rtl.md`. The correction of the earlier READMEs, which list a working 256 KiB L3 per cluster, is the L3 note sent to him on 2026-11-04 at 18:51 PST; it is not repeated here.
- **This boot's hit-counter rows, the direct check:** in all 21 rows of `latency-dram-small-l3.csv` (CPU 2, CPU 3 offline, 64-512 KiB) `l3d_hit_rd_per_load` (0x81C6) reads 0.0000, and `l3d_access_rd_per_load` (0xA0) equals `l3d_refill_rd_per_load` (0xA2) to within 0.0001, to the printed four decimals in 18 of the 21 (the other three are rep 0 at 64, 192 and 384 KiB: 0.0003, 0.4628 and 0.9325 against 0.0002, 0.4629 and 0.9326), so every L3 read missed. 0x81C6 has now read 0 on boots B, C and D and nonzero nowhere, so its zeros agree with the reading but do not on their own show that it counts. These rows have no L3 level: the 192 and 256 KiB rows mix L2 hits with SLC reads (`l2d_hit_rd_per_load` 0.5264-0.5360 and 0.2265-0.2315), at 384 KiB the L2 serves 0.0592-0.0676 reads per load, and the latency climbs from the L2's 6.091 ns at 128 KiB to 22.669 and 23.722 ns at 384 and 512 KiB (best rows) with no level between. Boot A has no such file; these rows read 0.957-1.005 times boot B's and 0.958-1.006 times boot D's.

## OCM mappings

`dmesg.txt` has one line per `/dev/ocm` mapping, 115 in all (lines 204-318), in the form `membench_ocm: map pid=206 comm=latency va=0xffff99ac0000 pa=0xe0000000 len=0x40000 prot=0x68000000000fc3 pte=0x1780000e0000fc3 cont=64/64 same=64/64`: the process, the user and physical addresses, the length, the protection, the first page-table entry as read back, how many of the mapping's entries carry the contiguous bit and how many share the first entry's attributes. - Every mapping is one whole 256 KiB region at its base: 23 each at 0xE0000000, 0xE0100000, 0xE0200000, 0xE0300000 and 0xE0400000, over 91 OCM commands (85 of one region, 6 of all five), all by `latency`, pids 206 to 983.
- Every mapping has `prot=0x68000000000fc3` (Normal write-back memory, inner shareable, user read-write, never executable) and is made of 4 KiB page entries with the contiguous bit, so each 64 KiB block is one translation. Its `pte` (`0x1780000e0n00fc3` for region n) has bit 52, the contiguous bit, set; boot B's `0x1680000e0n00fc3`, from the same module with `cont=0`, differs from it only by that bit, and boot A's shorter line has no `pte` field.
- Per command, as he asked: every line of every one of the 91 commands reads `cont=64/64` and `same=64/64`, so the hint applied to all four 64 KiB blocks of every mapping.
- Per line: `(va - pa)` mod 16, 32 and 64 KiB is 0 on all 115 lines, since the module places each mapping congruent to its physical address modulo 64 KiB (boot A: 0 on 23, 8 and 5 of its 110 lines).
- By command: C's map lines 1-25 are G2 from CPU 2 (17 commands), 26-40 its TLB set (15), 41-45 the walk rows (5), 46-70 G2 from CPU 8 (17), 71-95 G4, the CME rows (17), and 96-115 G6, the route rows (20); map line k is `dmesg.txt` line 203 + k on this boot and on boot A.

- **How the core holds a block:** on the C1-Nano a contiguous block is one 64 KiB translation in the walker, the complex's shared L2 TLB and the CME, and two 32 KiB entries in the core's L1 data TLB (`nevis0_dcu_utlb_intf_entry.sv:558-562`). The alignment matters by itself on this core: four 4 KiB entries make one 16 KiB translation in the L2 TLB and the CME only where the user and physical addresses agree modulo 16 KiB, and the L1 data TLB merges fills into a 32 KiB entry only where they agree modulo 32 KiB.
- **The unmap:** the kernel splits a contiguous block back into single entries before it unmaps it, with one broadcast TLB invalidate per 64 KiB block, four per region, at every unmap; boot A's mappings, with no contiguous entries, need no such split. This happens outside every timed pass and core counter group, but inside counters that run for a whole command, such as G6's mesh counts.
