# cache-mem-perf on the Asimov emulator: run membench-jibin-016 (run 8, the mesh latency map: his optional boot 3)

Jibin Han's `cache-mem-perf` (github.com/jhan-positron/asimov, folder `cache-mem-perf`, commit `3b12e4f8a8c7414d14fb06b356c5a79e3e6c0a1e`) ran `sh run_map.sh --kernel-cpus` as the optional boot 3 of his run 8, the L3 in use and the data prefetchers on, on one emulated Asimov hemisphere on the GA13 Palladium, on 2026-11-12 (UTC). His whole results directory is `results/bootM3/`, byte for byte as his script wrote it, with the kernel log as `dmesg.txt` and `SHA256SUMS` over all of them. This box checked that the files are whole. It did not analyse the numbers.

## Read first

- **His script ran whole.** Exit status 0, five commands (four `latency` control rows and one `meshmap`), `# run_map.sh done ...: 0 measurement command(s) failed`, `# meshmap: done cells=180/180`, all ten files back. `latency-map.csv` has 1,269 data rows: 7 passes for each of 180 cells and one idle row for each of the 9 CPUs.
- **His own lines in `latency-map.csv`:** `# mesh counters: level=1 events=hns_pocq_reqs_recvd_all,hns_mc_reqs_local_all,hns_cache_miss_all,hns_snp_sent pmu_cpu=0`, `# read_floor: 12 13 12 15 8`, `# classify: probe_ns=11550 lines=2048 projected_s=0.1478`, `# classify: probed=10255 ambiguous=14 unused=2 per_node=2053,2050,2051,2051,2048 lines=2048 probe_loads=64 elapsed_s=0.1209`, `# one_2mib_page: yes (backing=hugetlb)`, `# pagemap: pfn=0xc004000 page_bytes=4096 covers=buffer ...`. The classification kept 2,048 lines per cell and did not reach its time stop.
- **This is the boot with the prefetchers on.** His README's rule: "A boot with the prefetchers on is not a distance map. Label its rows "prefetcher effect"." The file shows them on, on CPUs 2-9: `l1d_refill_hwprf` or `l2d_refill_hwprf` is nonzero in 937 of their 1,120 cell rows, where boots 1 and 2 read 0.0000 in all 1,120. The four control rows ran in the same state (`l2d_refill_hwprf_per_load` is nonzero in all eight of their rows, and 0.0000 on boots 1 and 2).
- **No BL31 readback stands behind this boot's state,** though he asked for the readbacks in the README: TF-A 0.35.0 has no hook and prints none (Platform, below). The L3 rests on the SCP's staging lines and the box's two run-time readings; the prefetchers rest on the columns above.
- **`--kernel-cpus` was on,** so the file has 20 cells from CPU 0 in a last block, after every other row. It was switched on because the rehearsal's CPU 0 command came back whole (`../membench-jibin-013/README.md`), and the CPU 0 blocks of boots 1 and 2 did too. On his question whether the option is safe: the boot E note he cites was about one kernel-mode register read made with interrupts off (IMP_CLUSTERPWRSTAT_EL1 on CPU 1), not about user-mode loads, and his CPU 0 block ran whole on the rehearsal and on all three boots.
- **On this boot alone CPU 0's rows are in the cache state of the other rows.** CPU 0's cluster has its L3 in use and its data prefetchers on with every firmware pair of this run, and here the clusters of CPUs 2-9 have the same. The file agrees: `l1d_refill_hwprf` or `l2d_refill_hwprf` is nonzero in 118 of the 140 CPU 0 cell rows, and `l3d_refill_rd` reads 0.33 to 0.53 in the CPU 0 `ocm-flush` rows where CPUs 2-9 read 0.32 to 0.55. On boots 1 and 2 CPU 0's rows differ from every other row in this (their READMEs). No register readback stands behind CPU 0's state on any boot.
- **More on CPU 0.** Its cluster's mesh port (node 80, crosspoint (1,2)) is 1, 3, 3, 5 and 5 steps from home nodes 88, 160, 216, 288 and 344, the mirror image of the port of CPUs 8-9 (node 336, crosspoint (5,2): 5, 5, 3, 3 and 1). CPU 0 is the kernel's CPU: it is not isolated, keeps the 100 Hz timer tick, takes the device interrupts (`irqaffinity=0-1` allows CPUs 0 and 1, and this kernel's interrupt controller driver sends each interrupt to the first CPU of its mask; read from the driver's source, `/proc/interrupts` was not captured), and executes every mesh counter read (the mesh PMU's CPU is 0), so a read made from CPU 0 is local while the read floor was measured from CPU 2. His program runs there under SCHED_FIFO 10, as on every CPU. With `--last-cpus 0` it also pins itself to CPU 0 once at its start, for its pin test, before any row is written.
- **`l3d_refill_rd` with the L3 in use and the prefetchers on.** On CPUs 2-9 it reads 0.32 to 0.55 (median 0.36) in the 280 `ocm-flush` rows, 0.27 to 0.99 (median 0.38) in the 280 `slc` rows, 0.37 to 1.00 (median 0.54) in the 280 `dram-flush` rows and 0.21 to 0.98 (median 0.32) in the 280 `ocm-evict` rows. On the same CPUs boot 2, with the L3 in use and the prefetchers off, read 1.00 in the `ocm-flush` and `dram-flush` rows and under 1 in the other two kinds (its README), and boot 1, with the L3 out of use, read 1.00 to 1.01 in all four. His README's rule for the column is "`l3d_refill_rd` near 1.0 per load says that each load left the cluster", and it says of his evictor "The loads push the chain lines out of the cluster's L1, L2 and L3". What the column says on this boot is his to judge.
- **The mesh counters on this kernel.** A read of an event group stops the whole mesh PMU, reads every event and restarts it (Linux 6.18.36, `kernel/events/core.c` and `drivers/perf/arm-cmn.c`: his levels 1 and 2), so mesh requests that arrive during a read go uncounted. A read of an event opened alone (level 3) does not stop it. The mesh events count per home node, so the mesh columns of every row also hold the requests of the kernel's CPUs 0-1.
- **CPU 3 stayed online through every row,** idle while another CPU measured: `run_map.sh` only writes 1 to its online file (`cpu3 online=1`, a no-op here), and `meshmap` measures from it in its turn. The same four control rows (the dense flushed 256 KiB OCM chain) ran with CPU 3 offline on his round four boots.
- **On this boot the OCM mappings differ between home nodes.** `/dev/ocm` maps at the address the kernel picks, and `dmesg.txt` has one line per mapping (lines 203-211). Of `meshmap`'s five mappings, those of nodes 88, 160 and 216 are aligned to 4 KiB only against their physical addresses (`va=0xffffadea7000` for `pa=0xe0000000`, `va=0xffffade67000` for `pa=0xe0100000`, `va=0xffffade27000` for `pa=0xe0200000`), and those of nodes 288 and 344 to 256 KiB or more (`va=0xffffadbc0000` for `pa=0xe0300000`, `va=0xffffadb80000` for `pa=0xe0400000`). His `l1d_tlb_refill` column follows it: in the `ocm-flush` and `ocm-evict` rows of CPUs 2-9 it reads 0.0098 to 0.0117 per load at nodes 88, 160 and 216 and 0.0059 to 0.0068 at nodes 288 and 344 (0.0024 to 0.0029 in the `slc` and `dram-flush` rows at every node). So on this boot an OCM cell of node 88, 160 or 216 against one of node 288 or 344 differs in the mapping as well as in the node. Boot 1 had all five at 4 KiB only and boot 2 all five at 256 KiB or more. The four control rows, which `run_map.sh` calls "the same-boot reference for meshmap's ocm-flush cells", have mappings of their own (lines 203-206), aligned to 8, 32, 16 and 16 KiB. What a mapping's alignment can do to an OCM row was seen in round four: boot D, which mapped the OCM 64 KiB-aligned and with the contiguous hint, read its core OCM chase rows 0.944 to 1.017 times those of boot B, which had the kernel's placement (`../membench-jibin-008/README.md`, which also says that this core's TLBs merge 4 KiB entries only where the two addresses agree modulo 16 KiB and 32 KiB).
- **This boot ran its own classification, on a third physical page, with the prefetchers on.** Its buffer got the physical frame 0xc004000 (the first line of `map-homes.txt`); the rehearsal and boot 1 had 0xc004800 and boot 2 0xc004c00. So a line's home node here is this boot's own: read this boot's rows with this boot's `map-homes.txt`. No earlier run classified with the prefetchers on. `meshmap`'s set-up (the buffer's first touch, the first OCM stores, the open of the core counters) ran on CPU 9, the last CPU of its default list.
- **This boot did not wait for his look at the files of boots 1 and 2.** His results go to him in two messages, one after the rehearsal and one after the full runs (Jesse's decision), so each boot was queued once this box's check of the one before it found nothing wrong (the box's call).

## What the box added

- **The wrapper.** The init can run only `/bin/sh <script> --out <folder>`, so it ran the box's `box_run_map_cpu0.sh`, which runs his `run_map.sh --kernel-cpus --out .../results/bootM3`. No file of his is changed.
- **Two lines on stdout, none in his files.** The wrapper printed IMP_CLUSTERPWRSTAT_EL1 of CPU 2's cluster, read through the box module's sysfs file, before and after his script: `# box clusterpwrstat before run_map: 0x70` and `# box clusterpwrstat after run_map: 0x70`. They are the first and the last line of the init's capture of the program's output, which is not part of his folder.

## Platform

- **Image:** GA13 release `a10280100`, build `hemi_rtws_tlm` (RTL `0d9e214eb43b`), from this box's own copy. The AP DRAM on this image is the emulator's embedded memory model, not LPDDR5X, so no latency of a load fetched from DRAM is silicon-like here: that covers `meshmap`'s `dram-flush` rows, and an `slc` row only where the slice did not serve the loads (his `mc_reqs` rule tells the two apart).
- **Firmware:** SCP 0.48.0-nopcie-l3.1 (`28663ab`, debug; its banner is `uart_0.log` lines 2 and 13) with TF-A 0.35.0 (`3b3df18`, debug; `uart_1.log` line 2: `NOTICE:  version: 3b3df18 (0.35.0)  (debug)`), the firmware pair of his boot F1 (run 6). This SCP stages the full-L3 operating mode for the clusters of CPUs 2-9 while they are still off: the SCP console has `Staged cluster 0 PPU PWPR=0x00070008 (ON)` and `Staged cluster N PPU PWSR=0x00070000 (OFF)` for clusters 1 to 4 (`uart_0.log` lines 182-186; SCP cluster N is the cluster of CPUs 2N and 2N+1).
- **BL31's readbacks: none on this boot.** TF-A 0.35.0 has no hook, and the AP console `uart_1.log` has no `pfoff` line, so nothing read IMP_CPUECTLR_EL1 bit 48, IMP_CMECFG_EL1 bit 28 or IMP_CLUSTERPWRSTAT_EL1 at any CPU's power-on. What there is in their place:
  - The L3: the SCP's five staging lines above, and the box's two run-time lines, which read IMP_CLUSTERPWRSTAT_EL1 as 0x70 on CPU 2's cluster before and after his script (all slices, full L3 RAM, by the DSU RTL's field names; boot 2 read 0x70 in the same two lines and in BL31's eight). The clusters of CPUs 4-9 rest on their staging lines alone.
  - The prefetchers: no register was read. TF-A 0.35.0-pfoff.1 is this TF-A plus the one hook, and on boot 2, which ran this SCP, that hook read IMP_CPUECTLR_EL1 bit 48 clear on each of CPUs 2-9 and IMP_CMECFG_EL1 bit 28 clear at each cluster's first core before it set them (`ectlr 0x900000`, `cmecfg 0x2a9f11115`; `../membench-jibin-015/README.md`). On this boot his prefetch refill columns are nonzero in rows of every CPU (Read first).
- **Kernel:** this box's Linux 6.18.36 (transparent huge pages, hugetlbfs, debugfs, `CONFIG_PROC_PAGE_MONITOR=y`), command line `earlycon=pl011,0x2a400000 quiet nohz_full=2-9 isolcpus=domain,managed_irq,2-9 irqaffinity=0-1 earlycon=pl011,0x2a400000 console=ttyAMA0,480000 panic=0 loglevel=7 rdinit=/sbin/membench-init`. The kernel runs on CPUs 0-1; CPUs 2-9 are online and isolated. 256 huge pages of 2 MiB were reserved. `/dev/ocm` maps the OCM in 4 KiB pages: `dmesg.txt` has 9 map lines, one region for each control row and five for `meshmap`.
- **The run:** queue request 5306 on ga13pd01. The wrapper, his script inside it, took 1.157 chip seconds (`MB RUN end status=exit:0 ns=1156679300`, the init's measure, which also covers the box's two reads of the register; his estimate for the script with `--kernel-cpus` is 1.01 s), and `meshmap` reports `cells 180/180 in 1.0466 s`. The hang guard of 12 chip seconds did not fire. The emulator ran 2,781 wall seconds per chip second.
- **Evidence in the box:** `evidence/runs/membench-jibin-016/` (console logs, the launcher's events, the results window, the checker's verdict `judge-jibin.txt`: `JIBIN_CHECK PASS`).
