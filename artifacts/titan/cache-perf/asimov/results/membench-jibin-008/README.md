## The prefetchers: where they were turned off, and the readbacks

- **Where:** this boot's BL31 is boot B's, TF-A 0.35.0-pfoff.1 (`5a9e2a8`, debug): TF-A 0.35.0 rebuilt by this box with one added hook, never published (its banner, `uart_1.log` line 2: `version: 5a9e2a8 (0.35.0-pfoff.1)  (debug)`). Linux cannot make these writes itself: the release BL31 traps an EL2 write to either register. The hook runs at EL3 at the end of every power-on of CPUs 2-9 (each PSCI CPU_ON, CPU 3's return included), before BL31 returns to Linux; CPUs 0-1 are left alone. In order it sets IMP_CPUECTLR_EL1 (S3_0_C15_C1_4) bit 48, ALLPFDIS, if clear; writes IMP_CMESELR_EL1 (S3_0_C15_C11_1) with 0, which selects the cluster's one CME for the CME register accesses that follow (a write that the snapshot's `MANIFEST.md` leaves out of its description of the hook); sets IMP_CMECFG_EL1 (S3_0_C15_C11_4) bit 28, PF_DISABLE, if clear; reads the registers back and prints one line on the AP console.
- **Readbacks** (the AP console, `evidence/runs/membench-jibin-008/a01/evidence/run-evidence/uartout/uart_1.log`, lines 104-111 at boot and line 367 for CPU 3's one return). All nine lines read as boot B's did, and in all nine the `ectlr`, `cmpx` and `cmecfg` values are what the RTL predicted before boot B (`evidence/firmware/tfa-v0.35.0-pfoff.1.txt` step 12).   - CPU 8 (line 110): `pfoff cpu8 ectlr 0x900000->0x1000000900000 cmpx 0x340000009400 cmecfg 0x2a9f11115->0x2b9f11115 clusterpwrctlr 0xb40170 clusterpwrstat 0x0`

- **IMP_CPUECTLR_EL1 bit 48** went from 0 to 1 on every CPU at every power-on (`0x900000` is the reset value).
- **IMP_CMPXECTLR_EL1** (S3_1_C15_C1_4) reads `0x340000009400` on every CPU: bits 26 and 25, the translation-prefetch disables, are clear. The boot leaves this register alone.
- **IMP_CMECFG_EL1 bit 28** was set in each cluster's CMECFG at its first core's power-on (CPUs 2, 4, 6, 8: `0x2a9f11115->0x2b9f11115`) and was already set at its second core's (CPUs 3, 5, 7, 9: `0x2b9f11115->0x2b9f11115`). The reading of the CME itself is CPU 3's before-value at its return after the CME rows, `0x2b9f11115`: bit 28 held through the CME rows.

That is why the writes come from BL31 at EL3, and it is the state the proof of the `clusterpwrstat` read assumes (The run below).

## L3 power

- **The samples:** IMP_CLUSTERPWRSTAT_EL1 reads 0x0 in his `log.txt` on CPU 2's cluster just before and just after his hit-counter command, both with CPU 3 offline (lines 7 and 9: `# box clusterpwrstat before l3: 0x0`, `# box clusterpwrstat after l3: 0x0`; both reads returned a value, not an error). The hook's nine lines read `clusterpwrctlr 0xb40170 clusterpwrstat 0x0` at every power-on of CPUs 2-9.
- **The reading,** as on boot B (its README, L3 power, gives the fields): by the DSU RTL's field names, 0x0 is one L3 slice with the L3 RAM snoop-filter-only (SFONLY), the mode SCP 0.48.0-nopcie.1 leaves the clusters of CPUs 2-9 in, since it stages the full-L3 mode for the cluster of CPUs 0-1 only (its console prints one staging line, `uart_0.log` line 182: `Staged cluster 0 PPU PWPR=0x00070008 (ON)`). In that mode the DSU neither looks up nor allocates in its L3, so the 256 KiB L3 of CPUs 2-9 holds no data and every L2 miss goes to the SLC or DRAM; on the emulator nothing is switched off electrically. 0xb40170 is IMP_CLUSTERPWRCTLR_EL1's reset value, which TF-A 0.35.0's DSU driver writes back at every power-on just before the hook reads it, so it does not show what the cluster's power controller asked for. The record, with its RTL and firmware references, is `evidence/jibin/l3-power-rtl.md`. The correction of the earlier READMEs, which list a working 256 KiB L3 per cluster, is the L3 note sent to him on 2026-11-04 at 18:51 PST; it is not repeated here.
- **This boot's hit-counter rows, the direct check:** in all 21 rows of `latency-dram-small-l3.csv` (CPU 2, CPU 3 offline, 64-512 KiB) `l3d_access_rd_per_load` (0xA0) equals `l3d_refill_rd_per_load` (0xA2) to the printed four decimals (192 KiB: 0.4900, 0.4956 and 0.4934 for both), so every L3 read missed, and `l3d_hit_rd_per_load` (0x81C6) reads 0.0000. 0x81C6 has now read 0 on boots B and D and nonzero nowhere, so its zeros agree with the reading but do not on their own show that it counts. ## The walk rows

- **The rows:** six files from CPU 2 with CPU 3 offline, commands 40-45 of 122, right after CPU 2's TLB-set rows and before CPU 8's G2 rows. Each is the TLB-set row of the same chain with `--events walk`, which keeps cycles, 0x03, 0x17, 0xA2 and 0x34 DTLB_WALK and replaces the TLB set's 0x05 and 0x2D with 0x8188 DTLB_WALK_BLOCK and 0x818A DTLB_WALK_PAGE (columns `dtlb_walk_per_load`, `dtlb_walk_block_per_load`, `dtlb_walk_page_per_load`). Every pass row reads `perf_cov` 1.0000.
- **Their data rows,** counted here since the run's checker does not count a CSV's rows: `latency-dram-walk-cpu2.csv`, the random 32 MiB chain on 4 KiB pages (`backing=4k`), has 2 pass rows (`fresh1` and `fresh2`, 524,288 loads each) and its best row; each `latency-ocm-region<r>-walk-cpu2.csv` (r = 0-4), the sparse chain over one 256 KiB region (`backing=ocm sparse=1`), has 7 pass rows (`fresh1` to `fresh7`, 64 loads each) and its best row. That is 37 pass rows and 6 best rows.
- **On the 32 MiB stimulus:** 0x34 reads 0.4381 and 0.4371 walks per load, 0x818A the same in both passes, and 0x8188 0.0000: every walk ended in a page descriptor, as on 4 KiB pages it must. So 0x818A counts on this image. The row reads 58.725 ns best.
- **On the five OCM rows:** all three walk columns read 0.0000 in every one of the 35 passes, so no data-side walk was counted in a timed pass (by the RTL, 0x34 leaves out the TLB's own prefetch walks). Before the timed passes his program walks chain 0 twice over the same 64 pages (`latency.c`: `warm-up: data resident, TLB filled`), and the flush before each pass touches every line of the region, so each pass starts with the region's translations already loaded; each timed chain itself is walked only once. The rows read 23.109-27.641 ns best, within 0.5% of the sparse TLB-set rows of the same regions on this boot.
- **0x8188 stays unvalidated:** it read 0 on every row, and on the rows where it could have counted, 0x34 counted no walk either. On this RTL a walk that ends in a page entry with the contiguous bit counts as a block walk, in 0x8188 and not in 0x818A (`nevis0_tlb_pagewalk.sv:3147`), so a nonzero 0x8188 on an OCM row would have shown the walker using the hint. Here the map lines are the only direct record of the hint.

- **How the core holds a block:** on the C1-Nano a contiguous block is one 64 KiB translation in the walker, the complex's shared L2 TLB and the CME, and two 32 KiB entries in the core's L1 data TLB (`nevis0_dcu_utlb_intf_entry.sv:558-562`). This happens outside every timed pass and core counter group, but inside counters that run for a whole command, such as G6's mesh counts.
