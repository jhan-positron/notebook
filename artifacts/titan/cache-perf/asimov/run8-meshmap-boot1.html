Run 8, the mesh latency map: rehearsal and boot 1

Asimov emulator, result folders 013 (rehearsal) and 014 (boot 1: L3 holds no data, prefetchers off). Files copied and checked 2026-11-11.

Short version

The rehearsal passed all ten checks, and boot 1 of the full run came back whole: 180 of 180 cells, 7 timed passes each.

A load from a CPU to a home node costs about 20.6 ns plus 2.0 ns per X step plus 1.0 ns per Y step, and a DRAM-backed line held in a node's cache slice costs the same as an OCM line of that node (mean difference +0.004 ns over 40 cells).

A flushed DRAM-backed line costs 50.0 to 57.3 ns, and its cost follows a three-leg path (CPU, home node, a memory bridge at the left edge of the mesh, CPU) to within 0.09 ns rms.

Words used here

  • Mesh: the chip's interconnect, 6 x 6 crosspoints. A message moves one crosspoint per step. Crosspoints are written (x,y).
  • Home node: one of five cache nodes on the mesh (ids 88, 160, 216, 288, 344). Each holds a 1 MiB slice of the system-level cache (SLC) and 256 KiB of on-chip memory (OCM).
  • DRAM-backed line: a 64-byte line of normal memory. A hash of its address selects its home node.
  • Cell: one CPU, one home node, one kind of row. Each cell has 7 timed passes of 2,048 dependent loads. Best is the smallest ns per load of the 7.
  • Kinds: ocm-flush (OCM lines, flushed first), ocm-evict (OCM lines, pushed out of the CPU's caches by loading other lines), slc (DRAM-backed lines held in the node's slice, same recipe as ocm-evict), dram-flush (the same DRAM-backed lines, flushed first, so every load goes to memory).
  • meshmap: the program that measures the cells. run_map.sh: the script that runs it with four control rows of the older program latency.
  • Mesh counters: per-node event counters of the mesh. req_<node> counts requests that reach a home node. mc_reqs counts requests a home node sends on to memory. cache_miss counts misses in the slice.
  • SBSX: the mesh's bridge to the memory model. rms: root mean square of the fit's errors. est.: an estimate.
  • Boot 1: firmware of the earlier boot B. The clusters of CPUs 2 to 9 keep no data in their L3, and their prefetchers are off. CPU 0's cluster is not in that state (section 6).

4. What the cells of CPUs 2 to 9 say

4.1 The slice of a node costs the same as its OCM

  • The hypothesis was: per node, slc latency equals ocm-evict latency.
  • Over the 40 cells, slc best minus ocm-evict best has a mean of +0.004 ns. The range is -0.25 to +0.35 ns, and the rms is 0.13 ns [Ref4].
  • So the data supports the hypothesis on this boot.

4.2 Cost per step

  • ocm-flush reads 0.37 ns above slc on average. The cause is not known (section 7).
  • dram-flush does not fit this form (rms 1.73 ns). Section 5 gives the form that fits.

  • One ocm-evict pass (CPU 6, node 344, pass 5) reads mc_reqs 0.45 per load. Its time is within 0.12 ns of the passes beside it.

  • No prefetch. Both prefetch refill counters read 0.0000 in all 1,120 cell rows of CPUs 2 to 9 (0 rows nonzero).

4.4 Passes 4 to 6 read about 1.3 ns above passes 0 to 3

  • Pass r of a cell reads its pointer from byte 8 x r of each 64-byte line [Ref11]. So passes 0 to 3 read the lower 32 bytes of the line, and passes 4 to 6 read the upper 32 bytes.
  • In all 120 cells of the three cache kinds, every one of passes 4 to 6 is slower than every one of passes 0 to 3. The best pass is a pass 4 to 6 in 0 of the 120 cells.
  • dram-flush shows no such step.
  • No counter column differs between the two groups of passes.
  • So every "best" on this page is a number for the lower half of the line. A load of the upper half costs about 1.3 ns (about 2.7 core cycles) more.

5. The flushed DRAM cells follow a three-leg path

  • Observation. From CPU 8 all five nodes cost 56.5 or 57.2 ns. From CPU 2 the cost rises from 50.0 ns (node 88) to 56.0 ns (node 344). Distance from CPU to home node alone does not explain this.
  • Test. I fitted ns = a + p x (X link crossings) + q x (Y link crossings) over the path CPU, home node, a memory point M, CPU. I tried every crosspoint as M.
  • Result. M at (0,3) or (1,3) gives rms 0.089 ns over 40 cells, with a = 46.07 ns for (0,3), p = 0.99 ns and q = 0.32 ns. The two positions cannot be told apart, since no CPU or node sits left of x = 1. The next best position has rms 0.24 ns.
  • Control model. A path where the data returns through the home node fits no better than rms 1.07 ns at any M.
  • The mesh map agrees. A memory bridge (SBSX) sits at crosspoint (0,3) [Ref8].
Hypothesis, not yet proven: the home node forwards the request to the SBSX at (0,3), and the SBSX sends the data straight to the CPU. The measurement that would confirm it: a second 2 MiB page whose lines use another SBSX, or the routing tables in the firmware source. One page was measured, so one bridge is seen.

Example: CPU 8 through node 216. Total 10 X crossings and 2 Y crossings. Fit: 56.56 ns. Measured: 56.46 ns.

  • The cache kinds cost 1.00 ns per X crossing and 0.49 ns per Y crossing (a round trip crosses each step twice). The DRAM fit gives 0.99 ns per X crossing but 0.32 ns per Y crossing. The Y difference is about 11 standard errors, and it is not explained (section 7).
  • dram-flush passes repeat within 0.13 ns. The cache kinds spread 1.2 to 2.0 ns between their 7 passes in 119 of 120 cells, and the step of section 4.4 is the cause.
  • With M on row y = 3, the Y crossings of the three-leg path equal those of the round trip. So q is the cost of the CPU-to-node Y steps, and it is lower here than in the cache kinds.

5.1 The address hash matches Arm's formula

  • The run printed one_2mib_page: yes and the frame number 0xc004800, so every line's physical address is known [Ref5].
  • Arm's formula for a number of nodes that is not a power of two folds address bits 51 to 6 into 12 bits and scales them to 0 to 4 [Ref9].
  • It predicts the measured home node of 10,245 of 10,245 classified lines in boot 1, and 320 of 320 in the rehearsal.
  • The order of the target table is 88, 216, 344, 160, 288 for formula results 0 to 4.

6. The CPU 0 cells

  • Jesse's side ran a second rehearsal command with CPU 0 and then switched --kernel-cpus on for the full run. Both ran whole. This answers the open question: measuring CPU 0 did not hang the boot [Ref6].
  • CPU 0's cells are in another cache state. A prefetch refill counter is nonzero in 128 of its 140 cell rows. Its ocm-flush cells read 12.7 to 15.7 ns, against 22.1 to 29.7 ns for CPUs 2 to 9 [Ref4].
  • Jesse's README gives the cause: the firmware changes cover CPUs 2 to 9 only, so CPU 0's cluster keeps its L3 in use and its prefetchers on. No register readback for CPU 0 is in the files, so this cause rests on the README.
  • So CPU 0's rows on boots 1 and 2 are not distance numbers. They can be compared with the other CPUs on boot 3 only.

7. Not explained, and not verified

  • ocm-flush is 0.37 ns slower than ocm-evict and slc. Insufficient data. A run of the ocm-flush block after the other blocks would show whether the order of the blocks matters.
  • The Y cost per crossing differs: 0.49 ns in the cache kinds, 0.32 ns in the DRAM fit. Insufficient data. The CPUs and nodes use only y = 2, 3 and 4, so Y is weakly determined. CPU 0's cells on boot 3 add no new y.
  • Why passes 4 to 6 are slower in the cache kinds and not in dram-flush (section 4.4). The older latency rows used one slot, so they do not show it.
  • The mesh map is from an earlier boot (folder 011). Boot 1's own files hold no mesh map. The mesh is the same hardware image.
  • The control rows have 2 timed passes each, so their agreement within 0.18 ns rests on a best of 2.
  • Jesse's README says a group read stops the whole mesh counter unit while it reads. I have not checked this against the kernel source. If true, requests that arrive during a read go uncounted. The per-load counts above are near whole numbers, so the loss is small in these rows.
  • CPU 3 was online. The 20 older OCM cells were taken with CPU 3 offline. The new cells still repeat the old fit within 0.62 ns.
  • Boot 2 is already queued (Jesse's README of folder 014). Boot 1 shows no defect that should stop it.
