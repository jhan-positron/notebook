Asimov OCM Interpretation

How I read Jesse Zhang's description of the Asimov on-chip memory, where it differs from Jibin's, and what the test would measure. Written 2026-10-30 from the Slack DM replies of 18:59 and 20:50 PDT and the notebook spec-study notes.

Short version.

Jesse's OCM is 1.25 MiB of the mesh cache (SLC) that firmware locks at boot: 4 of the 16 ways in each of the 5 home nodes, one 256 KiB region per home node, shared by every core on the chip and reached through a /dev/ocm driver. Jibin's description was a separate SRAM per DSU acting as an L4 for that DSU's two cores. Jesse's second reply explains the difference: Jibin's picture matches the March 2026 architecture spec v1.7, which put a home node on each DSU's crosspoint, and the current RTL moved to five home nodes shared by all cores. Each DSU still has a nearest region, one mesh hop from its port, so OCM1 should be the fastest region for our test core CPU 2.

Words used here

DSU
DynamIQ Shared Unit. One cluster of 2 C1-Nano cores with their shared L2 and L3. Asimov has 5 per hemisphere.
CMN
Arm's Coherent Mesh Network. The on-chip interconnect between the DSUs, the memory controller and the accelerator blocks.
Home node (HN)
A mesh node that owns a slice of the physical address space and holds that slice's share of the SLC. Asimov has 5.
SLC
System Level Cache. The cache inside the CMN, 5 MiB in total, 1 MiB per home node, 16 ways per home node.
Line (cache line)
The 64-byte block of memory that every cache on Asimov stores and moves as one unit. Every address belongs to exactly one line.
Way
One of the 16 parallel slots a cache line can occupy in a set. Locking a way means the hardware never evicts lines placed in it.
OCM
On-Chip Memory. In Jesse's description: the locked SLC ways, exposed as plain memory at fixed physical addresses.
SPM
Scratchpad Memory. A separate 16 MiB data memory on the mesh, reached through AXI slave ports. Jesse says it has different rules. Not covered here.
ACP
Accelerator Coherency Port. A side port into a core's cache. SPM pushes 46-byte metadata records through it. The notebook notes mention per-core OCM base registers for this path.
PA
Physical address.
/dev/ocm
A small Linux driver Jesse will add. mmap on it maps one 256 KiB OCM region into the process as normal cacheable memory.

1. What Jesse described

sourceJesse's reply comes from the image's RTL, firmware and kernel sources. Nothing has been measured yet. He will send real command output after the first boot.

Takeaway: OCM is not a separate memory block. It is part of the mesh cache with eviction switched off, so every core reaches every region through the same mesh path.

  • Five regions, each 256 KiB, at PA 0xE0000000, 0xE0100000, 0xE0200000, 0xE0300000, 0xE0400000. Only the first 256 KiB of each 1 MiB slot has storage behind it. The other 768 KiB are addresses with nothing behind them. Those empty addresses are unrelated to the 12 grey ways in the diagram, which hold DRAM lines. The equal size is a coincidence of 1 MiB minus 256 KiB.
  • Each region lives in a different home node, so latency may differ by region (distance across the mesh).
  • OCM must be mapped Normal write-back (cacheable). Device and non-cacheable mappings are not supported.
  • It has ECC and no reset initialisation. A range must be written before it is read.
  • Because it is cacheable, OCM lines also fill L1, L2 and L3. To time OCM itself the footprint must exceed L2 plus L3 (384 KiB), or the lines must be flushed with DC CIVAC first.
  • Linux does not list it. Jesse will add a /dev/ocm driver; one mmap per region, offset equal to the region's physical base.
  • The interpreter does not use OCM. Only firmware sets it up.

The two agree on one point: the count is five. They disagree on whether the five are tied to DSUs or to home nodes, and on whether the memory is private to a DSU or shared by the chip.

4. Why the two descriptions differ

sourceJesse's second reply, 20:50 PDT, answers this directly.

  • Jibin's picture is close to the March 2026 architecture spec v1.7. That version put a home node on each DSU's crosspoint, so each DSU had a home node, and its OCM, next to it.
  • The current RTL has five "super home nodes" (HN-S) that house the SLC and the OCM. They are mesh nodes, not DSU nodes, and every core reaches every one of them.
  • Each DSU still has a nearest region. DSU n's port sits one crosspoint from the home node holding OCM n. The RTL mesh config places DSU ports at crosspoints 12, 23, 32, 43, 52 and home nodes at 13, 24, 33, 44, 53. So CPU 2 (DSU 1) is one hop from OCM 1 at 0xE0100000, and that region should be the fastest for our test.
  • Region size is a firmware choice. Firmware may lock 1, 2, 4, 8 or 12 ways, so a region can be up to 768 KiB. The stock firmware locks 4 ways, which gives the 256 KiB per region in section 1. The 1 MiB Jibin remembers is the size of the address slot and of each home node's whole SLC slice.

Where this is specified, per Jesse: the firmware boot spec section 7.1.5 "OCM cold-boot policy" in the asimovsw-docs repository, the CMN micro-architecture spec v0.10 node table, and the RTL files cmns3_12_1.yml (mesh config) and cmn_hns_l3_tagpipe.sv (lock decoder) in the asimov repository.

The notebook's per-core cfg_acp_ocm_base registers [notebook: artifacts/asimov-spec-study/spm-meta-data-model.md:146-150] are a separate matter: they tell the SPM metadata path where to push records for each core. They do not partition the OCM.

6. What a test would measure

Expected result, as a hypothesis: OCM latency equals SLC-hit latency on the same home node, and OCM bandwidth equals SLC-hit bandwidth. The run confirms or rejects this by chasing a 512 KiB to 1.25 MiB OCM buffer and a 1 MiB to 3 MiB buffer in ordinary DRAM pages (which fits in the 12 normal ways) and comparing the two.

Tests the OCM part of the plan would include

  • Latency chase across 2, 3, 4 and 5 regions (512 KiB to 1.25 MiB), one core, CPU 2.
  • Latency per single region with the cache flushed before each pass, to see whether the five home nodes differ by mesh distance.
  • Read and write bandwidth of one core over all five regions, with the same inline-assembly kernels used on CRB.
  • The same chase and bandwidth over a buffer of 1 to 3 MiB in ordinary DRAM pages, as the SLC-hit reference.
  • Every region is written once before any read, as Jesse requires.
