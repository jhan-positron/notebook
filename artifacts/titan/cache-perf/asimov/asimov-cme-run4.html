Short version. The CME's refills now have a cause: the demand-read and hardware-prefetch refills add up to the inner plus outer refills within 2.1 % on every chase row, and boot B, with the CME prefetcher off, shows that the climb from 8 KiB on boot A was the prefetcher's: the chase reads 21.02 to 21.26 ns from 4 to 64 KiB and steps to 37.16 ns at 96 KiB, past the 64 KiB L1 (section 8). 1. Words used here

C1-Nano, DSU
The Arm core and its two-core cluster (DynamIQ Shared Unit). The hemisphere has 5 DSUs, CPUs 0 to 9. Device interrupts are routed to CPUs 0 and 1 (irqaffinity=0-1); the scheduler places no unpinned task on CPUs 2 to 9 (isolcpus=2-9) and their periodic tick stops while one task runs (nohz_full=2-9). The init started run_all.sh pinned to CPU 2, so the scripts, the shell and the counter helper ran on CPU 2 (cmncount sets no affinity of its own) and each measured program pinned itself to its --cpu. Every core takes its own timer and per-CPU interrupts, and a program's page faults and system calls run on its own core [Jesse's run 3 README, The run and CPU placement].
L1, L2, L3
32 KiB data cache per core, 128 KiB per DSU, 256 KiB per DSU, 64-byte lines [sysinfo.txt]. On this run, as on runs 1 and 2 and run 4 boots A to D, the L3 of CPUs 2 to 9 was in snoop-filter-only mode and held no data: the stock SCP firmware stages the full L3 for cluster 0 only, and run 4 boot B's hit counters read 0 L3 hits per load. There is no L3 level in these numbers; run 4 boot E turned the L3 on [asimov-c1nano-run4.html, sections 11.1 and 14].
mesh, crosspoint (xp)
The Arm CMN S3 interconnect, a 6 by 6 grid of routers. Distance between two points is the number of crosspoint steps, |dx| + |dy|.
home node (HN-S), SLC
The five mesh nodes that own all addresses, each with 1 MiB of System Level Cache in 16 ways. A DRAM address belongs to one home node by a hash, so a buffer spreads over all five.
OCM
On-Chip Memory: 4 of the 16 ways of each home node, locked as 256 KiB of memory at 0xE0000000 + n MiB. Region n lives in home node n only. Reached through /dev/ocm in 4 KiB pages.
node id
The mesh id of a home node (88, 160, 216, 288, 344). Its bits give the crosspoint: x = bits 8 to 6, y = bits 5 to 3.
chase
A pointer chase: each load reads the address of the next load, so the loads cannot overlap and the time per load is the load-to-use latency.
repeated chase, fresh chain, flushed
Repeated: a random chain walked many times, so later walks hit whatever cache holds it. Fresh: a chain walked once. Flushed: every line was cleaned and invalidated from the caches with DC CIVAC first.
boot A to E
The five boots of run 4 (round four). A is the run 3 platform (sections 1 to 10); B has the data prefetchers of CPUs 2 to 9 and their CMEs turned off (section 11); C maps the OCM in 64 KiB contiguous translations with the prefetchers on, and D with them off (section 13); E is boot C's program and platform with the OCM back in 4 KiB pages and a rebuilt SCP that turns the L3 on (sections 14 and 15). The CME page gives the CME side (its sections 8 and 9).
contiguous hint
The contiguous bit of a translation entry, which marks 16 neighbouring 4 KiB entries as one 64 KiB block; the TLB then holds the block as one entry (two 32 KiB entries in the core's L1 data TLB). Boots C and D load /dev/ocm with cont=1 and every mapping line reads cont=64/64 [dmesg.txt of 007 and 008; Jesse's boot C README, OCM mappings].
L3 full mode (operating mode 7)
The DSU cluster operating mode with all L3 slices and the whole L3 RAM open to lookup and allocation; IMP_CLUSTERPWRSTAT_EL1 reads 0x70 in it. Boot E's SCP (0.48.0-nopcie-l3.1) stages it for the clusters of CPUs 2 to 9; the stock SCP stages it for cluster 0 only.
prefetch-refill events
Three core PMU events added in run 4 beside run 3's three refill events: 0x81BC (L1 data cache refills a hardware prefetcher requested), 0x81BD (L2 refills for accesses generated by hardware prefetchers targeting the L2) and 0x0111 (L2 refills for accesses from the L1 data prefetcher) [C1-Nano TRM, event list]. Each is reported per load of the timed pass, beside 0x03 (L1 refills), 0x17 (L2 refills) and 0xA2 (L3 read refills).
TLB events
0x05 L1 data TLB refills (counts refills that hardware prefetches caused too), 0x2D L2 data TLB refills (excludes hardware prefetches) and 0x34 translation table walks (walks caused by a miss in the L2 TLB driven by a memory access) [C1-Nano TRM, event list]. Run on the CPU 2 OCM rows with run 3's three refill events.
CME refill events
0x3280 CME L1 refills caused by load instructions (demand reads), 0x32B2 refills by the CME's hardware prefetcher, 0x3281 refills caused by stores [C1-SME2 TRM, event list], beside run 3's 0x327D (refills from inside the cluster, inner) and 0x327E (from outside, outer).
dense, sparse, vary
Three chain shapes over one 256 KiB OCM region. Dense: every line of the region, 4,096 loads per pass (run 2's chain). Sparse: one line per 4 KiB page at one fixed line offset, 64 loads per pass (run 3's chain). Vary: one line per page at a line offset that changes from page to page, 64 loads per pass (new in run 4).
sequential chain
New in run 4: a chain whose members are the lines in address order, 8 MiB, every line flushed first. It is the stimulus a hardware prefetcher is built for, so it shows whether the prefetch events count at all.
CME
The Compute Matrix Engine: Arm's C1-SME2 unit (code name Griffin). One per DSU, shared by the DSU's two cores. It executes the cores' streaming-mode (SME) instructions, with its own 64 KiB 4-way L1 data cache, its own TLB and its own hardware prefetcher. Its path to memory is CME L1, then the DSU's L3 (which held no data on this run), then the mesh; the core's L1 and L2 are not on it [Jesse's run 3 README, CME; CME-plan.md section 1].
streaming mode, SMSTART, SMSTOP
The CPU state in which SVE instructions run on the CME. SMSTART enters it and SMSTOP leaves it; both zero the vector registers. The test kernels enter it once per timed call and leave at the end.
SVL
The streaming vector length: 64 bytes on this chip, one cache line [dmesg: SME default vector length 64 bytes].
cme-roundtrip, cme-call
Two controls with no memory access. cme-roundtrip moves a value into a vector register and back out (DUP then LASTB) 65,536 times inside one streaming span. cme-call does one such round trip per call, 64 calls, so it carries the SMSTART, register save and SMSTOP of a whole call.
CME counters
The CME's own PMU events read through the core PMU: 0x3246 CME cycles, 0x327D CME L1D refills from inside the cluster (inner), 0x327E refills from outside the cluster (outer). Per load means divided by the loads of the timed span. These events count prefetch refills too [CME-plan.md section 2.1].
CME power (dynamic mode)
The firmware arms each CME's power controller in dynamic mode, so the CME switches itself off when idle and back on at the next streaming instruction. Whether it was off at the start of a timed span is not recorded [Jesse's run 3 README, CME power].
ldr16, str16
The 64-byte forms of the read and write kernels (one vector per instruction) beside the 256 B forms (four vectors per instruction).
best, pass, rep
A command walks its chain several times (passes, or reps); best is the fastest. A sparse per-region row has 7 fresh passes, a dense all-five control 2, a repeated chase 3 reps.
refills per load
PMU events 0x03 (L1D refill), 0x17 (L2D refill), 0xA2 (L3D read refill) divided by the loads of the timed walk. 1.00 means one fill of that level per load. A fill can be a demand miss or a prefetch, so the count does not say which loads missed, and a useful prefetch can replace a later demand fill and leave the count near one.
perf_cov
New in run 3: the counter group's running time over its enabled time for the row. 1.0000 means the counters were never multiplexed; every row of this run reads 1.0000.
cmncount
The helper that opens the mesh PMU (arm_cmn_0) around one command and writes cmn-counts.csv: requests received per home node, memory-controller requests and SLC misses.
SCP, TF-A
The System Control Processor firmware (which also sets up the mesh) and Trusted Firmware-A (the boot firmware of the application cores). Run 3 ran SCP 0.48.0-nopcie.1 and TF-A 0.35.0, the same as run 2 [Jesse's run 3 README].
chip time
Time as the emulated chip sees it. One chip second took 2,776 wall seconds in run 3 [Jesse's run 3 README].
est.
An estimate, not a measurement.

4. Latency and refills by footprint

  • Why the CME has no L1 step at 64 KiB. Run 3 saw the CME latency climb from 8 KiB with no step at its 64 KiB L1, and more than one refill per load from 8 KiB, and offered the prefetcher as the hypothesis. Boot A counts it: at 8 KiB the prefetcher fills 3.1 lines per load, at 32 KiB 14.7, at 64 KiB 16.0 (means over the reps), and the demand reads, which should be near 0 while a chain fits the L1, are 0.17, 0.72 and 0.85 per load. hypothesis The prefetcher's fills evict the chain's own lines from the 64 KiB 4-way L1, so a random chain of 8 KiB and above never stays resident: the latency is set by how many loads miss the L1 (the demand-read count) and by the 14 to 17 prefetch requests per load that queue behind each demand miss from 24 KiB on. With the prefetcher off (boot B) the repeated rows to 64 KiB should read near the 4 KiB time (21.5 ns) and the demand reads near 0 there.
  • On the fresh chains the prefetcher does less. From 512 KiB the prefetch refills fall from 5.3 per load to 2.7 at 32 MiB while the demand reads sit at 0.96 to 1.00. hypothesis A chain walked once gives the prefetcher no repeated pattern to train on, and the larger footprints spread the loads over more pages; what it still fetches is the neighbourhood of each miss.

6. OCM through the CME by chain shape

  • The order of the three shapes. On the core the dense chain is fastest and the sparse slowest (core page, section 6); through the CME the sparse chain is fastest. hypothesis Through the CME a sparse-chain load's prefetches (0.39 to 0.56 lines per load) land on the next member often enough to make 37 to 54 % of the loads L1 hits, while the dense chain's 1.4 to 1.5 prefetches per load are mostly neighbours the random walk does not visit next (19 to 20 % hits); the vary chain draws 0.6 to 1.3 prefetches per load and hits on 6 to 8 % of them. Which prefetcher does this, and why the core's L2 prefetcher helps the sparse chain less, is not counted here. Insufficient data A per-load hit count (the CME's hit events, if the TRM lists them) would decide it.
  • Against run 3. Boot A's sparse rows read -8.3 to -0.6 % of run 3's by best pass (7 passes each; the passes of one row spread by up to 10.1 ns).

The CME prefetcher's fills set the chase time at these footprints on both boots, so the L3 hit latency through the CME as a single number is Insufficient data; a boot with the CME prefetcher off and the L3 on (not run) would give it.
