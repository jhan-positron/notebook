# Follow-up run plan: prefetch fills on the C1-Nano and the CME (run 4)

**Short version.** Run 3 left two questions the counters could not answer: which of the fills in the per-region OCM chase were prefetches, and why the CME refills from outside the cluster at footprints its 64 KiB L1 should hold. This plan adds the hardware-prefetch refill events to each counter group, a translation counter set, a third chain shape and a prefetch stimulus row, re-runs only the chase rows that carry those questions, plus one bandwidth check and one route check (138 commands, about 3.8 s of chip time per boot est.), and asks Jesse for up to three extra boots so the same script can be compared across prefetch-on and prefetch-off and across page sizes. Run 5 (section 10) adds one hit-counter command on the small rows and ten one-core read rows; run 5b (section 11) adds a walk counter set and six rows that say which descriptor the page walker used on the contiguous-hint boots; run 5c (section 12) adds sixteen one-core L1 rows that measure the per-pass cost of the bandwidth program and the L1 rate without it; phases G5 and G6 repeat eight write rows and the 20 OCM cells under the mesh counters. A full repeat of run 3 is not needed.

## Words used here

- **CME**: the Compute Matrix Engine, Arm's C1-SME2 unit, one per two-core cluster (DSU), with its own 64 KiB L1 data cache and its own hardware prefetcher.
- **chase, hop, pass**: a pointer chase loads a chain where each load gives the next address; one load is a hop; a pass is one walk of the chain, timed as one span.
- **dense chain**: run 2's OCM chain, every line of a 256 KiB region (4,096 hops a pass). **sparse chain**: run 3's, one line per 4 KiB page at one fixed line per chain (64 hops a pass). **vary chain** (new, `--sparse-vary`): the sparse chain with the member's line changing from page to page. **sequential chain** (new, `--seq`): the lines in address order, a chain a stride prefetcher can follow.
- **fill, refill**: a line brought into a cache. The Arm events count refills by cause: 0x03 L1D_CACHE_REFILL counts those the program's own loads and stores caused; 0x17 L2D_CACHE_REFILL counts every L2 refill (data and instruction misses, translation walks, L1 write-backs, prefetches); 0xA2 L3D_CACHE_REFILL_RD counts L3 fills from outside due to a read. **HWPRF** in an event name means a hardware prefetcher requested the fill.
- **inner, outer** (CME events 0x327D, 0x327E): a CME L1 refill whose data came from a cache inside the immediate cluster of the core (on Asimov the DSU's L3 or the other core's caches; the event does not say which) or from outside it (SLC, OCM, DRAM). **RD, HWPRF, WR** (0x3280, 0x32B2, 0x3281): CME L1 refills by cause: a load that missed, the CME prefetcher, a store that missed.
- **perf_cov**: the counter group's running time over its enabled time for a row; 1.0000 means the kernel did not multiplex the group.
- **IMP_CPUECTLR_EL1.ALLPFDIS**, **IMP_CMECFG_EL1.PF_DISABLE**: the core's and the CME's data-prefetcher-disable bits (Arm C1-Nano TRM, table A-100 bit 48, "disable all data-side prefetchers"; Arm C1-SME2 TRM, table A-13 bit 28). **IMP_CMPXECTLR_EL1.TLBPFDIS, TLBL2PFDIS** (bits 26 and 25 of the complex extended control register, table A-116): the two translation-prefetcher disables, separate from ALLPFDIS and in a different register (bits 26:25 of IMP_CPUECTLR_EL1 are L1WSCTL, the write-streaming threshold). All are implementation-defined system registers; none can be written or read from user space. EL1 access to the core registers needs ACTLR_EL3.ECTLREN set, and with EL2 enabled also ACTLR_EL2.ECTLREN set and HCR_EL2.TIDCP clear; the CME register needs ACTLR_EL3.CMEEN and ACTLR_EL2.CMEEN the same way [C1-Nano TRM lines 16735 to 16748; C1-SME2 TRM lines 5606 to 5619].
- **prefetch stimulus** (the sequential chain): a row on which a stride prefetcher can act, used to validate the prefetch events. Each event is validated separately, on a boot with the prefetchers enabled, when the activity it counts is established on that row; an event that stays zero without such evidence is unvalidated. On a disabled boot the readbacks and the previously validated counts assess the change; latency changes are reported without a required direction or equality with the random chain.
- **est.**: an estimate, not a measurement.

## 1. Context: what run 3 settled and what it left open

Run 3 (membench-jibin-004, 2026-11-03) repeated run 2's C1-Nano rows within 2.6 % and gave the first CME numbers (asimov-c1nano-perf.html, asimov-cme-perf.html). Codex's review of the two reports (codex-review-run3.md) was accepted in full and ends with the recommendation that drives this plan: update the reports, run targeted follow-ups for clean OCM latency and the unexplained CME cache behaviour, and do not repeat the whole suite.

The two open questions, each with the measurement that run 3 lacked:

1. **OCM latency per region.** The sparse per-region chases read 2.31 ns above run 2's dense ones on average and their seven passes spread 5.2 to 14.5 ns. Taking the best pass of each of the 20 CPU-region cells: the dense rows (run 2) count 0.76 to 0.92 L3 read refills per load and 1.13 to 1.45 L2 refills per load; the sparse rows (run 3) count 0.50 to 0.86 and 2.00 to 2.77. (Over all 140 timed sparse passes the L2 range is 1.92 to 3.78.) A refill count is lines filled per hop; 0xA2 counts L3 fills from outside due to a read and 0x17 counts every L2 refill whatever its cause. The aggregate L3 read-refill rates were 8 to 24 % below one refill per hop for the dense rows and 14 to 50 % below one for the sparse rows. These totals do not identify which hops caused refills or why. One reading, a hypothesis, is that the missing refills are lines a prefetcher had already brought inside the cluster. Under that reading the sparse chain did not stop a prefetcher from landing on its members. Run 3's events cannot say which fills a prefetcher made, and nothing in run 3 measures the translation activity of a sparse pass. The dense all-five control is repeatable (within 0.17 ns of run 2) but 1.00 fills per load does not prove 1.00 demand misses per load.
2. **CME refills at small footprints.** Through the CME, the outside-cluster refill event reads 1.65 to 3.43 per load at 8 KiB and 6.55 to 9.27 at 16 KiB, footprints a 64 KiB L1 should hold, and the latency climbs from 8 KiB on with no step at 64 KiB. The hypothesis is the CME prefetcher's traffic; run 3's two events include prefetch fills and cannot tell them from demand fills.

A third item came out of reading run 3 for this plan: the per-cell OCM latencies at one crosspoint count spread by 14 to 18 % in both runs (asimov-c1nano-perf.html table 4.2). Whether a given cell is fast or slow in both runs is unresolved: across all 20 cells the runs correlate 0.81, but that includes the distance effect, and after removing each run's mean at each distance the remaining cell differences correlate 0.22. A least-squares fit of the 20 cells (run 2 dense bests and run 3 sparse bests separately) says where the spread is not: the hop count alone explains 75 % of the variance (R² 0.75 and 0.76); adding which node or which CPU raises it to 0.78 to 0.81 only. Costing X hops and Y hops separately gives X 1.33 and Y 0.76 ns per hop in run 2, X 1.66 and Y 0.92 in run 3 (R² 0.79 and 0.80); adding a turn term reaches 0.80 and 0.86 with 0.8 ns of residual, but with 20 points and four parameters that term is not evidence. The reading that X links cost more than Y links is hypothesis H5 below; phase G6 records the outgoing data directions at each end, which neither counts the hops nor identifies the request route.

A fourth item is the one-core write rows: run 3's 16 to 256 KiB rows read 7.7 to 8.0 ns more per pass than run 2's, hypothesis the CME switch added to the bandwidth program's pass loop (asimov-c1nano-perf.html section 11). Phase G5 tests it.

## 3. Changes made

All in the working tree; verified on the x86 host build, on the CRB (Arm Neoverse V3AE, GCC 14.2, Jesse's flags) and by `--dry-run` (section 8). Nothing else in the suite changed, so run 3's rows are reproducible from the same tree, and the run 3 pages regenerate byte for byte.

### 3.1 Counter groups (common.h)

- `PERF_N` 4 to 7: cycles plus six raw events. The C1-Nano PMU has 6 or 20 event counters (TRM, "Number of PMU event counters"); cycles take the dedicated cycle counter, so six raw events fit either size, as long as nothing else holds a counter. G0 records the count from the boot log (`counters available`), and perf_cov rejects any row the kernel multiplexed. The CRB exposes 6 event counters plus cycles and ran every group with perf_cov 1.0000.
- Core prefetch set (default): cycles, 0x03, 0x17, 0xA2, plus 0x81BC L1D_CACHE_REFILL_HWPRF (L1D refills a prefetcher requested), 0x81BD L2D_CACHE_REFILL_HWPRF (L2 refills by prefetchers targeting L2) and 0x0111 IMP_L2D_CACHE_REFILL_L1DHWPRF (L2 refills by the L1D prefetcher's requests) [C1-Nano TRM event list, c1-nano-trm.txt lines 7487, 7490, 8272]. Each is reported as its own rate. 0x17 minus the two L2 prefetch events is "L2 refills not accounted for by these events" and is labelled that way; it is not a demand count, since 0x17 also counts instruction misses, translation walks and L1 write-backs [lines 6373 to 6377].
- Core TLB set (`--events tlb`): cycles, 0x03, 0x17, 0xA2, plus 0x05 L1D_TLB_REFILL, 0x2D L2D_TLB_REFILL and 0x34 DTLB_WALK [lines 6289, 6481, 6522].
- Core walk set (`--events walk`, run 5b): cycles, 0x03, 0x17, 0xA2, plus 0x34 DTLB_WALK, 0x8188 DTLB_WALK_BLOCK (demand data walks that ended in a block descriptor at level 1 or 2) and 0x818A DTLB_WALK_PAGE (walks that ended in a page descriptor) [lines 6522, 7380, 7386]. A walk through a contiguous-hint entry is a block walk: nevis0_tlb_pagewalk.sv line 3147 (`evt_descr_is_block_p2 = (block_entry | contig) & mmu on`), routed to 0x8188 at nevis0_dpu_pmu.sv line 4304, RTL 0d9e214eb43b, the image's revision (Jesse's note, verified 2026-11-04).
- CME set: cycles, 0x3246, 0x327D, 0x327E, plus 0x3280 CME_L1D_CACHE_REFILL_RD, 0x32B2 CME_L1D_CACHE_REFILL_HWPRF and 0x3281 CME_L1D_CACHE_REFILL_WR [C1-SME2 TRM, c1-sme2-trm.txt lines 4309, 4556, 4313]. The TRM lists four causes (RD, WR, HWPRF and 0x32B1 software preload); the chase kernel has no stores and no preloads, so for it RD + HWPRF should equal inner + outer. That is a consistency hypothesis for this kernel, checked per load.
- Optional events are opened independently (`PERF_REQUIRED` 4): a refused event costs its own column only, prints `-` there, and the events after it are still tried. The group read is mapped back to the named columns by position, so a refused event in the middle does not shift the rest. Tested on the host, where 0x81BD and 0x0111 are refused and 0x81BC between them is kept.

### 3.2 Output (latency.c)

- The counter columns are printed generically for `PERF_N` events; the header names them, so a file says which set it carries. The header line also records `seq=` and `events=`.
- A nonzero count that `%.4f` would print as `0.0000` is printed in exponent form (`4.6e-05`), so an exact zero stays distinct from a small count. The reader parses both.
- `--sparse-vary`: one member per 4 KiB page, in slot (chain + h) mod 8 of the page's eight slots of eight lines, at line h' of the slot, with h and h' bits of a hash of the page number. Chains never share a line. Over 64 pages a chain's member sits at 55 distinct line offsets.
- `--seq`: the chain is the lines in address order (member i points to member i + 1; the shuffle is skipped).

### 3.4 Reader (gen_run3.py) and its test

`lat_rows` reads any number of counter columns, takes perf_cov from the last column when the header names it, reads `-` as None (a refused or invalid counter, distinct from zero), checks every measured row against its header's column count, and lets the shorter best rows through. `test_lat_rows.py` runs it over run 2, run 3 and run 4 row shapes, a refused optional event, an invalid row, a small count in exponent form and a truncated row (rejected): PASS. Regenerating the run 3 pages after the change reproduces them byte for byte.

### 3.5 Estimator (est_chip_time.py)

The CME and core latency assumptions now come from run 3's best rows (cme-roundtrip 21.0 ns per hop instead of 5 ns est.; the CME sweep 21.4 to 70.3 ns by footprint; the dense all-five OCM rows). The launch cost stays 14 ms per command est.; no measurement of it exists (README, "Chip-time estimate"). The sequential chain is costed at the random chain's rate, a budgeting assumption (est.), not a proved bound. The 32 MiB TLB stimulus on 4 KiB pages is costed at 52.2 ns per hop, run 3's hugepage-backed rate; its translation-miss cost is not modelled, so its command and hop counts are exact and its time is an estimate with that omission. The per-call cost (21.7 ns) is derived from the two CME controls and is an estimate where it is reused for the bandwidth kernels.

## 4. Requests to Jesse: the boots

The script is the same on every boot; each boot gets its own `--out` directory and the README names the boot. Boots A and B are required: A answers G-a to G-d and G-g, G-h at the level of counts, and B is the only boot that gives a chase latency with the prefetchers out and the cross-check that tells an event that does not count from a prefetcher that did nothing (H1, H2). Boots C and D are optional and depend on what /dev/ocm can map.

1. **Boot A, the run 3 platform** (SCP 0.48.0-nopcie.1, TF-A 0.35.0, the same kernel and /dev/ocm). No change on Jesse's side. Chip time about 3.8 s est. (sections 10 to 12; boot A ran e8e4580 in 2.830 s of chip time against the 3.0 s est. of that commit).
2. **Boot B, data-side prefetchers disabled on CPUs 2 to 9 and on their CMEs.** The core bit is IMP_CPUECTLR_EL1.ALLPFDIS (bit 48) [C1-Nano TRM table A-100, lines 16468 to 16472]; the CME bit is IMP_CMECFG_EL1.PF_DISABLE (bit 28) [C1-SME2 TRM table A-13, line 5528]. Both are implementation-defined registers written at EL3 (TF-A, at CPU power-on) or at EL1 by a kernel module if ACTLR_EL3 permits EL1 writes; the choice is Jesse's. Four things to record in the README, since written values are not evidence that the boot changed: the readback of IMP_CPUECTLR_EL1 bit 48 on CPUs 2 and 8 after setup; the readback of IMP_CMPXECTLR_EL1 bits 26 and 25 on the same cores (the two translation-prefetch disables, which this boot does not ask to change but whose state matters for reading the TLB rows); the readback of IMP_CMECFG_EL1 bit 28 on the CMEs of DSUs 1 and 4; and where the writes happened, with the ACTLR_EL3 and ACTLR_EL2 enables if the writes were made at EL1. The CME's dynamic power-off does not undo the write: the TRM says implementation-defined register values are preserved across it [C1-SME2 TRM lines 1901 to 1903]. If only one of the two bits can be set, the boot still answers that side's question. The check of this boot is the readbacks and the same sequential row on A and on B: the prefetch events validated on A must read 0 on B. Its latency change is reported as an outcome, with no required direction and no required equality with the random chain, since address order also changes locality and translation behaviour. Same chip time.
3. **Boot C, OCM in larger translations, if /dev/ocm can map a region that way.** Today it maps 4 KiB pages. The regions sit at 0xE0000000 + n MiB, so regions 1 and 3 are not 2 MiB aligned and cannot each be one 2 MiB page [common.h alloc_ocm; run 3 README]. Two forms would do: a 2 MiB mapping of the whole 5 MiB range (regions at 1 MiB offsets inside it, which needs a different mapping call than today's per-region one), or 64 KiB granules or the contiguous-hint bit on groups of 16 entries. Before this boot is scheduled Jesse would say which the module can do, and the README would quote the mapping entries: granule, contiguous hint, memory attributes. The TLB rows (G-c) then say whether translation activity fell, and the walk rows (G-i, run 5b) whether the walks that remain ended in the contiguous entry: the map lines show what the kernel wrote, the walk counts what the walker used. Jesse's module (2026-11-04) does the contiguous-hint form: groups of 16 entries of 4 KiB, each mapping aligned to its physical address modulo 64 KiB. If the module cannot, this boot is dropped and the page-size comparison stays Insufficient data.
4. **Boot D, B and C together**, only if C exists. This is the only boot that measures the chase with both changes applied; A against B and A against C are conditional comparisons that need not add. Same chip time. D against B measures the combined change of the hint and the alignment: the hint module places every mapping 64 KiB-aligned to its physical address, while on B the kernel picks each mapping's address (on boot A, 5 of 110 mappings were 64 KiB-aligned and 23 were 16 KiB-aligned). ## 5. Data collection and outcomes

Per boot: `sysinfo.txt`, `log.txt`, `all.txt` and the CSV files of section 3.3, in one directory, plus Jesse's README as before (checksums, chip time, the boot's firmware, the register readbacks). The analysis reports, per row and pass:

- core rows: the three prefetch-refill rates per load beside 0x03, 0x17 and 0xA2; "L2 refills not accounted for by the prefetch events" as a labelled difference; the TLB rates on the CPU 2 per-region rows;
- CME rows: RD, HWPRF and WR per load beside inner and outer; RD + HWPRF against inner + outer as the consistency check; HWPRF per load against the climb of the latency from 8 KiB;
- the prefetch stimulus rows: the sequential rows' latency and prefetch columns on every boot, against the random flushed rows' on the same boot and against the same sequential row on the other boots;
- across boots: the same row on A and B, on A and C, and on D, with the controls of G-e as the drift check.

Hypothesis outcomes, each with the row that decides it:

- H1, the fills above one per hop in the per-region rows are prefetches: supported if the prefetch columns of the dense and sparse rows on boot A are of the size of the fills above 1.00 per load, and if on boot B the L3 read refills reach 1.00 per load and the L2 refills fall by about the prefetch rates measured on A. The L2 refills need not fall to 1.00 on B, since translation walks, instruction misses and write-backs remain possible. A numerical match is agreement between two measurements, not proof that the remaining one fill per hop was the pointer load's.
- H2, the sparse chain's fixed line offset is what a prefetcher reacts to: supported if the vary rows count more L3 read refills per load than the sparse rows on boot A and the difference is absent on boot B. A difference on A alone shows sensitivity to the offset pattern, not which prefetcher reacts to it or that it carries offsets between pages.
- H3, a sparse pass takes one L1 TLB refill per hop: decided by the 0x05 column of the sparse rows. On the CRB that column read 0.11 to 0.36 per hop, not 1.0, so the hypothesis is already doubtful there.
- H4, the page size is what separates sparse from dense: supported if on boot C the sparse and dense rows move toward each other while the TLB rates fall. This is an outcome, not a validity check of boot C.
- H5, an X hop of the mesh costs more than a Y hop (from the fit in section 1): G6 records outgoing data directions at both endpoints over the whole command. These counts include initialization, flush write-backs and unrelated traffic. They do not identify the read-request route or the read response's final link: read requests travel on the request channel, which G6 does not count. The X and Y distances in H5 remain coordinate assumptions. The 20 cells' latencies on boot A are fitted against those assumed hop counts, and the outgoing data directions are reported beside them as observations; supported if X and Y costs differ by more than the fit's residual and in the same direction as in runs 2 and 3. A direction with more data flits is an observed outgoing data direction; its magnitude does not identify the traffic's purpose, and the counts do not supply a route. Not supported if the two costs agree within the residual. What the counts cannot show: the read-request route, the response's last link, the links between the two ends, and per-link speed differences beyond X against Y.
- H6, the 7.7 to 8.0 ns per pass added to the small write rows is the program: supported if on one boot run 2's program reads run 2's numbers (30.6 GB/s at 16 KiB) and run 3's reads run 3's (30.1); not supported if both read the same.

What would support H1, in order of strength. Run 3 cannot: its events count fills by level, not by cause, and 0x17 also counts translation walks, instruction misses and write-backs. Run 4 can, at two levels:

1. Counting by cause, boot A. The three prefetch-refill events count the lines a prefetcher requested, per level and (for 0x0111) per prefetcher side. Their rates on the sparse rows are compared with the L2 refills above 1.00 per load; agreement supports H1 without proving that every remaining fill was the pointer load's. This needs the events to count on the C1-Nano, which each event's own validation on the sequential row decides.
2. Removing the cause, boot B. The qualitative comparison needs only run 3's events and the readbacks: with the data-side prefetchers disabled the L3 read refills should rise toward 1.00 per load on both chain shapes and the L2 refills should fall. The quantitative comparison uses the prefetch events as well: the fall in L2 refills from A to B is compared with the prefetch rates measured on A.

The C1-Nano also has one L2-refill event per prefetcher (0x00D9 correlating, 0x00DA spatial, 0x00DB offset, 0x010F stride, 0x0110 TLB descriptor [c1-nano-trm.txt lines 7953 to 8264]), which would say which prefetcher made the fills on the sparse rows; whether a filled line was later used by the chain is not something any of these events reports. They do not fit beside the run 3 events in a 6-counter group, so they are not in run 4; a later pass with `--events` extended to that set is the follow-up if H1 is supported and the prefetcher's identity matters.

## 6. Risks and what each costs

- An added event opens but does not count on the emulator's core (as 0x2A did in run 1, and as the three prefetch events read 0 on the CRB's sequential row, section 8). - The PMU has 6 event counters and something else holds one. Cost: the group multiplexes, perf_cov drops below 1.0000 and every counter column of the affected rows is invalid (the timing stays). G0's counter count and the first rows' perf_cov show this at once.

## 10. Run 5 additions (2026-11-04, after Bill's review of asimov-c1nano-perf-brief.html)

Bill's two questions on the brief (Slack DM, 2026-11-04 09:17 to 09:28 PST) were the "42 % L2 hit rate" at the L3 row, and the one-core DRAM read of 9.2 GB/s, which he expects to be a software limit. **Ask 1, the L3 row.** Run 3 inferred the L2 hit fraction from the refills (L2 refills per load, 0x17, which also counts prefetches and write-backs). The C1-Nano counts hits directly: 0x81C5 L2D_CACHE_HIT_RD, 0x81C6 L3D_CACHE_HIT_RD and 0xA0 L3D_CACHE_RD are in its common event list (TRM 107753 table 17-1). The new `--events l3` set keeps cycles, 0x03, 0x17 and 0xA2 and adds those three, so a row reads "L2 demand read hits per load, reads reaching the L3 per load, L3 demand read hits per load, L3 read refills per load", every column per program load. 0xA0's population: the TRM says every memory read counted by L3D_CACHE (0x2B), and the RTL of this image narrows it: requests of type ReadOnce or ReadNotSharedDirty not sourced by the hardware prefetcher, and not of prefetch origin (the origin_not_ldst flag, set for prefetch, TLB-prefetch and CME translations), so hardware-prefetch fills and prefetch-origin walks are left out, while the program's own page walks (table reads of demand origin, sent as ReadOnce) and software-prefetch reads stay in [nevis0_l2_tagctl.sv lines 10297 to 10304 and 2582; nevis0_tlb_pagewalk.sv line 3267; nevis0_l2_tlbsub.sv line 1438; nevis0_l2_pkg.sv lines 774 to 778; read 2026-11-04 after Jesse's note and codex R20]. Hits over accesses (0x81C6 over 0xA0) is therefore closer to a demand hit rate than the TRM wording suggests, and is still reported as an estimate (est.): the population is the RTL's reading, keeps the program's page walks and software-prefetch reads, and is not a count of the program's data reads. The columns are reported as independent counts per program load. Two derived ratios are estimates (est.) that rest on a population assumption, stated here and checked, not on the event names: that on a load-only chase the L1 refills (0x03, refills by speculatively executed loads or stores) are the demand reads that reach the L2, so l2d_hit_rd / l1d_refill estimates the L2 demand hit fraction, and l1d_refill - l2d_hit_rd estimates the demand reads reaching the L3, so l3d_hit_rd over that difference estimates the L3 demand hit fraction. The TRM states no such identity. The check: on the 64 KiB row l2d_hit_rd should be close to l1d_refill; where it is not, the assumption fails and only the counts are reported. G1 runs the set on the repeated rows 64 KiB to 512 KiB, one command. Per-event support, as for the prefetch events: 0x81C5 is supported if the 64 KiB row (fits the L2, misses the L1 on most loads: the L2-hit stimulus, not a zero control) reads it well above 0 and near l1d_refill; 0xA0 is supported if the 512 KiB row (beyond the L3, where every load reaches the L3) reads it well above 0 per load, with no required value, since its population is the RTL's reading rather than a count of the program's loads; 0x81C6 has no row where it must read near 1.0, so it is supported only if it reads nonzero on a row where 0xA0 is nonzero and l3d_refill_rd is below 0xA0, else its column is unvalidated, which is kept distinct from a measured absence of L3 hits. 0x2A L3D_CACHE_REFILL, which Bill's reviewer named, is not used: the TRM lists it as not implemented on the C1-Nano (PMCEID1_EL0 ID10 resets to 0, "not implemented, or not counted"; PMCEID0's ID10 is event 0x0A), and it read 0 on the emulator in October; 0xA2 is the L3 refill count. **Words used here.** Call: one execution of a kernel in cme_kern.S, from its entry to its return; the bandwidth program makes one call per pass (looped form) or one per rep (single-call form), the latency program one per timed pass. Span: the part of a call between the two counter reads inside streaming mode. Bracket: the caller's two clock reads around a call or around all calls of a rep (latency.c timed_walk, bandwidth.c worker). In-span time: CNTVCT_EL0 (the counter-timer, 1 GHz on the emulator, a system register that may be read in streaming mode) read just after SMSTART and just before SMSTOP, each read after an ISB; the kernels keep a running sum of their spans, and the caller resets it before a bracket and reads it after, so no C span collection runs inside a bracket (the caller's pass loop and dispatch still do). Instrumented outside-span interval: bracket minus span, per call. It holds the register save, SMSTART, SMSTOP, the restore, the call and return, the C loop step and the stamps' own instructions (three inside the span after the first stamp, eight outside it before SMSTOP); it is not the switch alone, and the switch alone stays Insufficient data in this run. Work the stamps add inside the span is in both the bracket and the span, so their difference does not show it. Looped form: one kernel call per pass, the form of every bandwidth row so far. Single-call form: all passes of a rep inside one call, `--asm-passes`; for the CME, inside one span (cme_read4_n, cme_write4_n). Fold: the read kernels' XOR of their 16 accumulators into one value at the end of each call, returned through FMOV; `--no-fold` runs the same kernel without it (cme_read4_nofold, which returns 0 through MOV). The two kernels' timing difference is the net effect of removing the reduction and its return dependency, overlap and completion waiting included; it is not the execution cost of the 17 removed instructions. Whole-kernel rate: a bandwidth row's bytes over its time, loads, vector XORs and loop instructions included; no row here is a memory-path rate. DSB ST: a barrier that waits until every earlier store has completed, the point at which every observer sees it; not the data reaching memory, and the CME's L1 may hold the written line [C1-SME2 TRM 107831, section 6.2]. `--dsb-st` puts one before SMSTOP in the CME write kernel (cme_write4_dsb). Posted store: a store the core counts as done once issued. F1, F2: the two boots requested below. Intercept: the fitted size-independent time per pass of a form, from the line through its four rows, as section 12 reads the core's G8 rows.

**What the rows so far show (run 3 and boot E).** A line through the 16 and 48 KiB CME rows gives 101 ns per call for cme-read at 134 GB/s and 0.5 ns per call for cme-write at 64 GB/s (two points, est.) [cme-bandwidth-dram-1core.csv, membench-jibin-004]. The 1 KiB write call takes 39 ns, 23 ns est. above its 16 ns of stores [cme-bandwidth-call-cost.csv, run 3]. cme-call minus cme-roundtrip is 22 ns est. per call on boot E [cme-latency-ocm-region1.csv, membench-jibin-010]; that difference holds the call and return, the register save and restore, the predicate setup and the C loop as well as SMSTART and SMSTOP, so it is a per-call interval, not the switch. So the read call carries a cost near 100 ns and the write rows at 16 KiB and above show no per-call cost at all. Hypothesis H10 (asimov-cme-perf.html section 10): stores are posted, so a call's last stores drain while it leaves streaming mode and the next call enters, and the switch hides behind them from 16 KiB up; the read kernel's fold waits for its loads and cannot overlap. Hypothesis H11: most of the looped read's per-call cost goes away with the final reduction and its return dependency; the `--no-fold` control tests it.

Success: that interval is the same number, within 20 %, on the cme-call rows (64 calls), the 1 KiB call-cost rows (4,096 calls) and the looped 4 to 24 KiB rows (176 to 1,024 calls), for read and for write. On the cme-roundtrip and 65,536-load chase rows it must read under 0.01 ns per load; that is a check on the measured outside-span contribution only. It does not show that those rows' per-load numbers are unchanged: work the stamps add inside the span is in both the bracket and the span, so the difference cannot measure it. F1's latency rows are reported on their own values. Any statement that F1 equals boot E or run 3 on a row (the 4 KiB CME chase 21.0 ns, cme-roundtrip 21.004 ns on every boot so far) is made from the actual old and new values with the differences stated: the stamps, the commit and the boot; isolating the stamps' own effect would need a matched control without them, which this run does not carry.
2. The two forms' intercepts, as section 12 reads them: the looped and single-call rows at 4, 8, 16 and 24 KiB, read and write, 5 reps, fitted through their four best reps with the 2 % residual rule, and the single-call rows at 48, 96, 160 and 256 KiB beside the sweep's looped rows at those sizes. Each intercept is that form's fitted cost per pass. Their difference is the net per-call difference between the forms: call, return, save, restore, the switch, the predicate and accumulator setup, the fold, the pass-loop control and the per-rep overhead divided by the pass count, together (the attribution rule of R24 for the core forms applies). No part of it is assigned from the difference alone. The `--no-fold` rows are the one matched control: the looped read's intercept minus the no-fold intercept is the net effect of removing the final reduction and its FMOV return dependency (H11); the two kernels differ in those 17 instructions, and the difference includes any change in overlap or in waiting for completion, so it is not the execution cost of those instructions. Both forms' rates are whole-kernel rates.
3. The write controls. The DSB ST rows at the same four sizes report the barrier's measured effect: the DSB ST intercept minus the looped write intercept. A positive effect near the outside-span interval of reading 1 is consistent with H10 and does not prove it; an effect near zero leaves the mechanism unresolved, since completion costs can sit in the fitted slope or overlap other work, and the stamps change the timing between calls. H10 stays a hypothesis after this run unless an observation beyond these rows identifies it; which observation would is Insufficient data. The per-call write rows at 1, 2, 4 and 8 KiB: the call size at which the 23 ns est. of the 1 KiB row disappears bounds the amount of store work the per-call interval can overlap with.
Outcomes: the CME read and write rows at 4 to 24 KiB and at 48 to 256 KiB are quoted in both forms, each named (the single-call rate as the whole-kernel rate with one switch per rep, the looped rate as what a caller pays per pass); the per-call interval is quoted from reading 1 as an instrumented interval with reading 2 as its check; the net effect of the fold and its return dependency from the matched control; the latency rows' per-load numbers are quoted on F1's own values, with the under-0.01 ns rule as the check on the outside-span contribution only, and the 64-load sparse OCM passes carry their one interval per pass at about 0.3 ns per load est., read beside the span column.

**Goal G-m: the refill sources of a CME load, and the CME L3 events.** Boot F2 runs the same script with the prefetchers off (boot B's TF-A) and the L3 on (boot E's SCP). With the CME prefetcher off, the CME L1 refills a row counts are refills that loads caused; the inner (0x327D, from inside the cluster) and outer (0x327E, from outside it) columns split them by source. Two things are read, in this order. First, the CME L3 events: 0x328E CME_L3D_CACHE_HIT, 0x328F CME_L3D_CACHE_MISS and 0x3290 CME_L3D_CACHE_REFILL exist in the event list [C1-SME2 TRM 107831, event table], and the `--events cme-l3` sweeps (phase F2, both boots) count them beside the inner and outer refills. They are exploratory counts in run 6. Two checks are made on them and neither validates them: hit plus miss is compared with inner plus outer on every row, but the two totals have different documented populations (L3 accesses, translation-resolution accesses included [C1-SME2 TRM 107831, event 0x328E and the L3 access events]; L1 line refills by source [events 0x327D, 0x327E]), so their agreement is a workload hypothesis, not an identity, and it says nothing about how the first total divides into hits and misses; and a hit column that reads 0 on a boot whose L3 holds no data is a necessary check that no run 6 boot provides (boot E's files have no CME L3 rows). A column that stays 0 on every row is unvalidated, not evidence. Second, the penalty fit: over the 8 to 384 KiB repeated-chase rows of F2, ns per load = a + inner x b + outer x c with a the 4 KiB row's time (the round trip plus an L1 hit). b and c are the fitted penalties per inner and per outer refill above a; the all-inner and all-outer predictions are a + b and a + c. They are not cache-level latencies: inner counts refills from the caches inside the immediate cluster (the DSU L3 or another core's caches [C1-SME2 TRM 107831, event 0x327D]; the snoop filter is not itself a source of data), and the refill events count lines, not identified loads, so a refill rate of 0.5 per load is not a statement that half the loads missed. The fit is reported with its residual and with an identifiability check on the fit matrix itself: the two columns (inner, outer) over the rows must have rank 2 with a condition number below 100, which a zero column or two proportional columns fail. If the check fails, neither b nor c nor the endpoint predictions a + b and a + c are quoted, since the same row times then fit more than one coefficient pair; only the measured rows, and predictions for source mixtures the rows contain, are reported. No fit reads the hit or miss columns in run 6: a hit-specific fit, and any L3-hit attribution, is Insufficient data until an independent control validates the hit and miss interpretation and the populations the fit would use. What that control is (a boot whose L3 holds no data for the 0-hit check, and a row whose L3 accesses are all hits or all misses by construction for the split) is named here so a later run can carry it; it adds no work to run 6. Success: residual under 5 % of each row and the identifiability check passed; otherwise the per-source penalties are Insufficient data and the rows are reported as measured.
