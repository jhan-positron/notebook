Short version. With the DSU L3 on (run 4 boot E), one core reads from its L1 in 2.0 ns, from the L2 in 6.0 ns, from an L3 hit in about 11 ns est., from the SLC in 24.2 ns and from DRAM in 52.7 ns (every line flushed). One core reads DRAM at 24.5 GB/s with the L3 on, against 9.2 GB/s with it off (boot C, the same build). The bandwidth set of sections 4.4 to 4.6, 8 and 9 is run 3's, measured with the L3 holding no data.

  • The L3 step. Runs 1 to 3 and boots A to D measured with the L3 of CPUs 2 to 9 holding no data (register 0x0, 0 L3 hits per load). Boot E's rebuilt SCP turns it on (register 0x70). The 192, 256 and 384 KiB chases (the hit-set rows) then read 7.8, 9.5 and 10.9 ns with 47, 75 and 92 % L3 hits per load, against 14.1, 19.7 and 22.7 ns on boot C (section 5).
  • Repeatability. Of the 70 rows boot E and run 3 share, 24 agree within 1 % and 47 within 5 %. The rows that moved most are the L3 rows (-51.6 % at 384 KiB) and the per-region OCM rows. Boot A against run 3, the same configuration, agrees within 1 % on 52 of 70 rows (section 4.8).
  • OCM. The dense all-five chain from CPU 2 reads 26.08 ns on boot E (run 3 25.34, boot A 26.01, boot C 24.96) with one L3 read refill per load. That is the OCM number to quote. On boot E only 0.41 to 0.82 of the loads in the per-region route rows are read from the mesh (L3 read refills per load). The other loads are served by the L3, so those rows are below the true OCM latency (section 6).
  • Bandwidth. One core reads DRAM at 24.9 GB/s (2 MiB) and 24.5 GB/s (32 MiB) with the L3 on. In one assembly call the L1 reads 59.8 to 60.6 GB/s at 16 and 24 KiB, 95 % of the 64 GB/s read path, and writes fit the 32 GB/s write path (section 7). Eight cores wrote 155 GB/s and one core read OCM at 14.8 to 16.6 GB/s per region on run 3, the L3 off (sections 9 and 10).

1. Words used here

PMU, TRM, SOG
PMU: the performance monitoring unit, the counters of a core, of the CME or of the mesh. TRM: Arm's Technical Reference Manual of a unit. SOG: Arm's Software Optimization Guide of a core.
TLB, table walk
TLB: the translation lookaside buffer, the core's cache of address translations. A table walk is the read of the page tables when the TLB misses. The counted events are L1 data TLB refills (0x05) and data TLB walks (0x34).
C1-Nano, DSU
The Arm core and its two-core cluster (DynamIQ Shared Unit). The hemisphere has 5 DSUs, CPUs 0 to 9. Device interrupts are routed to CPUs 0 and 1 (irqaffinity=0-1); the scheduler places no unpinned task on CPUs 2 to 9 (isolcpus=2-9) and their periodic tick stops while one task runs (nohz_full=2-9). The init started run_all.sh pinned to CPU 2, so the scripts, the shell and the counter helper ran on CPU 2 (cmncount sets no affinity of its own) and each measured program pinned itself to its --cpu. Every core takes its own timer and per-CPU interrupts, and a program's page faults and system calls run on its own core [Jesse's run 3 README, The run and CPU placement].
L1, L2, L3
32 KiB data cache per core, 128 KiB per DSU, 256 KiB per DSU, 64-byte lines [sysinfo.txt]. On runs 1 to 3 and run 4 boots A to D the L3 of CPUs 2 to 9 was in snoop-filter-only mode and held no data (the stock SCP stages the full L3 for cluster 0 only; register 0x0, 0 L3 hits per load). Boot E's rebuilt SCP turns it on: the register reads 0x70 and the hit set counts 0.75 L3 read hits per load at 256 KiB [Jesse's boot E README, L3 power; latency-dram-small-l3.csv].
mesh, crosspoint (xp)
The Arm CMN S3 interconnect, a 6 by 6 grid of routers. Distance between two points is the number of crosspoint steps, |dx| + |dy|.
home node (HN-S), SLC
The five mesh nodes that own all addresses, each with 1 MiB of System Level Cache in 16 ways. A DRAM address belongs to one home node by a hash, so a buffer spreads over all five.
OCM
On-Chip Memory: 4 of the 16 ways of each home node, locked as 256 KiB of memory at 0xE0000000 + n MiB. Region n lives in home node n only. Reached through /dev/ocm in 4 KiB pages.
node id
The mesh id of a home node (88, 160, 216, 288, 344). Its bits give the crosspoint: x = bits 8 to 6, y = bits 5 to 3.
chase
A pointer chase: each load reads the address of the next load, so the loads cannot overlap and the time per load is the load-to-use latency.
repeated chase, fresh chain, flushed
Repeated: a random chain walked many times, so later walks hit whatever cache holds it. Fresh: a chain walked once. Flushed: every line was cleaned and invalidated from the caches with DC CIVAC first.
sparse chain
New in run 3: a chain with one member line per 4 KiB page, at a different line offset per chain, so a line the hardware prefetcher fetches beside a member is never itself a member. A 256 KiB region gives 64 loads per pass; all five regions give 320. The run 2 chains were dense (every line of the region, 4,096 loads).
best, pass, rep
A command walks its chain several times (passes, or reps); best is the fastest. A sparse per-region row has 7 fresh passes, a dense all-five control 2, a repeated chase 3 reps.
refills per load
PMU events 0x03 (L1D refill), 0x17 (L2D refill), 0xA2 (L3D read refill) divided by the loads of the timed walk. 1.00 means one fill of that level per load. A fill can be a demand miss or a prefetch, so the count does not say which loads missed, and a useful prefetch can replace a later demand fill and leave the count near one.
perf_cov
New in run 3: the counter group's running time over its enabled time for the row. 1.0000 means the counters were never multiplexed; every row of this run reads 1.0000.
cmncount
The helper that opens the mesh PMU (arm_cmn_0) around one command and writes cmn-counts.csv: requests received per home node, memory-controller requests and SLC misses.
SCP, TF-A
The System Control Processor firmware (which also sets up the mesh) and Trusted Firmware-A (the boot firmware of the application cores). Run 3 ran SCP 0.48.0-nopcie.1 and TF-A 0.35.0, the same as run 2 [Jesse's run 3 README].
chip time
Time as the emulated chip sees it. One chip second took 2,776 wall seconds in run 3 [Jesse's run 3 README].
est.
An estimate, not a measurement.
run, boot
A run is one job on the emulator (run 3 = membench-jibin-004). Run 4 is five boots, A to E, each a job with one firmware and program configuration (section 2). Boot E is the latest.
L3 hit set
Run 4's repeated chases from 64 KiB to 512 KiB with the hit events 0x81C5 (L2 read hits), 0xA0 (L3 read accesses) and 0x81C6 (L3 read hits) per load beside the refill events [latency-dram-small-l3.csv].
sequential chain
A chain whose members are the lines in address order, 8 MiB, every line flushed first: the stimulus a hardware prefetcher is built for [latency-dram-seq.csv].
route row
The dense chase of one CPU-to-region cell run under the mesh's crosspoint counters (data flits sent per direction on the DSU's and the home node's crosspoint); 20 cells, CPUs 2, 4, 6, 8 by OCM0 to OCM4 [latency-ocm-region*-route-cpu*.csv, cmn-counts.csv].
contiguous hint
The contiguous bit of a translation entry, which marks 16 neighbouring 4 KiB entries as one 64 KiB block. Boots C and D map the OCM with it (cont=64/64 on every mapping line in dmesg.txt).
G2 rows
Run 4's dense, sparse and vary chases of each OCM region from CPUs 2 and 8 without the mesh counters, and the all-five chains [latency-ocm-region<r>-dense-cpu<c>.csv, latency-ocm-region<r>-cpu<c>.csv].
rms
Root mean square of the residuals: the fit's typical miss per cell, in ns.
G8 rows, per-pass and single-call forms
One-core L1 reads and writes of 4, 8, 16 and 24 KiB over many passes on boots C and E, timed with one call per pass (looped form, bandwidth-l1-passes.csv) or with every pass inside one assembly call (single-call form, bandwidth-l1-asmpasses.csv). A kernel is the program's inner loop function for one pass of reads or writes. A fit is a straight line, time per pass = fixed cost + bytes / rate, through a form's four rows, and its fixed cost is that form's per-pass cost.
read variants, PRFM
The plain one-core read loop and four variants (PRFM, the Arm prefetch-hint instruction, issued 4, 8 or 16 lines ahead, or two streams) at 2 MiB and 32 MiB [bandwidth-read-prefetch.csv].

2. The run and the platform

  • Where and when. Run 4 boot E ran on one emulated Asimov hemisphere on the GA13 Palladium (image hemi_rtws_tlm, RTL 0d9e214, release a10280100) on 2026-11-05 UTC as one job: run_followup.sh at cache-mem-perf commit b79dffa. 3.250 s of chip time, 138 commands, all exit 0 (0 failed), 113 files back with matching checksums [Jesse's boot E README, Read first and The run].
  • Platform. Boot A's, with one change: the SCP rebuilt as 0.48.0-nopcie-l3.1 to stage the full-L3 operating mode (all slices, the whole L3 RAM open) for the clusters of CPUs 2 to 9 before they power on. The stock SCP stages it for cluster 0 only, so on runs 1 to 3 and boots A to D the L3 of CPUs 2 to 9 held no data. TF-A 0.35.0, Linux 6.18.36, 256 huge pages of 2 MiB, /dev/ocm in 4 KiB pages (115 mappings, none with the contiguous hint), CPUs 2 to 9 isolated, CPU 3 offline for the whole script, the data prefetchers on. IMP_CLUSTERPWRSTAT_EL1 read 0x70 before and 0x70 after the hit-set command: the full-RAM encoding. That reading covers CPU 2's cluster only [Jesse's boot E README, The SCP and L3 power]. DRAM is an emulator memory, not LPDDR5X, so no DRAM number is silicon-like [the same README, DRAM caveat].
  • Counters. The PMU driver reports 21 counters, so no group of six events was multiplexed: every counted row reads perf_cov 1.0000 (699 latency rows and 110 bandwidth rows) and no row carries a "# perf:" flag.
  • Controls. The 4 KiB repeated chase reads 2.002 ns (4.01 cycles) on boot E, 2.002 on run 3 and 2.001 to 2.002 on the five boots. The CME round trip reads 21.004 to 21.006 ns on every boot (run 3: 21.004 to 21.006). The two uncounted 4 KiB controls read 2.014 ns (CPU 2) and 2.018 ns (CPU 8) on boot E [latency-dram-small.csv, cme-latency-*.csv, latency-control-cpu*.csv].
  • Run 3, whose rows stay on this page where run 4 did not repeat them: membench-jibin-004, commit ba834c0, SCP 0.48.0-nopcie.1, TF-A 0.35.0, 2026-11-03, 2.918 s of chip time, 100 commands, 77 CSV files, the L3 holding no data [Jesse's run 3 README].

2.1 What changed from run 3 to run 4 boot E

  • The code went from commit ba834c0 to b79dffa. The latency program gained the prefetch, TLB, walk and hit events, the sequential chain, the route rows and the vary chain. The bandwidth program gained the read variants and the G8 rows. The flags of every repeated row are unchanged, so a repeated row's numbers compare [Jesse's boot E README, Against boot C; follow-up-run-plan.md].
  • The firmware. One firmware component changed: the SCP, rebuilt to stage the full L3 for the clusters of CPUs 2 to 9. TF-A, the kernel and the OCM mapping are run 3's. So the L3 is the one platform difference between run 3's rows and boot E's, beside the run-to-run noise that boot A against run 3 measures (section 4.8).
  • Rows dropped. The bandwidth set (the one-core sweep, multi-core DRAM, writer placement, OCM bandwidth) and the OCM, SLC and control rows of CPUs 4 and 6 did not run on run 4. Their numbers on this page are run 3's and are labelled so.
  • Rows added. The L3 hit set (64 KiB to 512 KiB), the sequential 8 MiB chain, the one-core read variants at 2 MiB and 32 MiB, the G8 L1 rows, the TLB-set and walk rows of CPU 2, and the 20 route rows under the crosspoint counters.
  • Size. Run 3 ran 100 commands in 2.918 s of chip time. Boot E ran 138 commands in 3.250 s [Jesse's READMEs of 004 and 010].

5. Latency by level, CPU 2

  • An L3 hit costs about 10.8 ns (est.).   • The 52.7 ns DRAM data read is a fixed-delay memory model. Of the 52.7 ns, 24.2 ns is the home-node round trip (the 2 MiB SLC row) and the rest, about 28 ns est., is the model's delay.   • The sequential chain fell to 2.492 ns on E against 6.917 on C and 6.917 on A, with 0.9997 L1 prefetch refills per load on E and 0.9999 on C. 7. One-core bandwidth by level

  • The L1 read shortfall is a per-pass cost, not the L1's rate. Run 3's 16 KiB read of 58.1 GB/s is 91 % of the path. Between the 8 and 16 KiB G8 rows the added bytes move at 62.8 to 64.8 GB/s on every form and boot, the path's rate. A straight line t_pass = a + bytes / rate fits the write rows (residuals 0.0 to 1.9 %, under the 2 % rule) with a fixed cost of 23.7 to 25.7 ns per pass in the looped form and 9.1 to 14.0 ns in the single-call form. The read fits fail the rule (residuals 2.1 to 5.4 %), so no single per-pass cost exists for reads [asimov-c1nano-run4.html, section 15]. The C1-Nano is an in-order core, and that is why the per-pass cost shows. Its TRM lists an "in-order pipeline with direct and indirect branch prediction" [Arm C1-Nano Core TRM r0p2, document 107753_0002_06_en, section 1.1 "C1-Nano core features"]. In an in-order core the work at a pass boundary (the loop exit, the return, the register save and restore, the next call) must finish before the first load of the next pass can issue. That time adds to every pass. An out-of-order core issues the next pass's loads while that work is still in flight. The CRB (the Arm reference server used as the comparison machine) has Neoverse V3AE cores, which are out of order. On the same program the V3AE adds 4.2 ns per pass in the looped form, and its single-call form reads the same rate at every size [follow-up-run-plan.md, "CRB check of the two forms", from bandwidth-l1-read21-cpu3-passes.csv and -asmpasses.csv under ai-runs/run5c-crb-sample]. The out-of-order claim for the V3AE comes from Arm's public Neoverse V3 description, and no copy of that document is in the local vendor folder, so it is not cited by page.

7.1 How the L1 read rows are read

Each pass has two parts. One part is the bytes, read at the L1's rate. The other is a fixed time F that does not depend on the bytes. F is the work between the last load of one pass and the first load of the next. A row reports bytes over the whole pass time, F included. So F lowers every row. Subtracting two passes cancels F and leaves the L1's rate.

  • What F is. In the looped form (one kernel call per pass) F holds the loop exit, the return, the restore and save of the vector registers d8 to d15 (the registers the Arm calling convention makes a called function preserve), the C loop's step and the next call. The write fits put it at 24 to 26 ns per pass. In the single-call form (every pass of a rep inside one assembly call) only the inner loop's exit, the pointer reset and the pass count remain. The write fits put that at 9 to 14 ns, and the read passes above at 11.5 ns est. The single-call form moves the program's work out of each pass. That is why its rows read higher.
  • Why F shows at all. The C1-Nano is in order (section 7 above). The loads of the next pass cannot issue until the work at the boundary has run. On the out-of-order V3AE the same program keeps 4.2 ns per pass in the looped form and none in the single-call form.

8. Prefetching, in-flight reads and dependent loads

Words used here: in flight means issued and not yet returned. A dependent load is one whose address comes from the load before it, so it cannot issue until that load returns. A pointer chase is a chain of dependent loads. The hardware prefetcher is the part of the core that notices an address pattern and issues reads for the next lines before any load asks for them.

  • A dependent chain cannot be helped by anything that runs ahead. The random chain's next address is inside the line being read. So one DRAM read must finish before the next can start, 52.7 ns per load. The sequential chain's addresses are predictable. With the prefetchers off (boot B) nothing predicts them, and the chain takes the same 52.8 ns per load.
  • With the prefetchers on the same DRAM reads overlap. Boot E's sequential chain still reads every line from DRAM once (1.00 L2 refills per load, the lines flushed first). Its loads take 2.49 ns each. The prefetcher issues reads ahead of the loads, about 21 at a time (est.). The lines arrive in L1 (1.00 L1 prefetch refills per load) before or while the load waits for them. The time per load is close to the L1 chase's 2.00 ns. The stream runs at 64 bytes per 2.49 ns, 25.7 GB/s (derived), about the plain one-core DRAM read of the same boot (24.5 GB/s at 32 MiB, measured). On boot C, the L3 off, the same chain takes 6.92 ns per load and the plain read moves 9.2 GB/s. By the same arithmetic boot C keeps about 2.8 times fewer reads in flight (est.). What the L3 changes in how far ahead the prefetcher runs is Insufficient data (section 7).
  • Two counters tell the prefetcher's fills from the loads' own. Event 0x03 (L1D_CACHE_REFILL) counts every line that enters L1, whoever asked for it. Event 0x81BC (L1D_CACHE_REFILL_HWPRF) counts only the lines the hardware prefetcher asked for [Arm C1-Nano Core TRM r0p2, section 17.1 Common PMU Events]. The difference is the lines the loads fetched for themselves (demand refills, derived). The L2 has the same pair: 0x17 (L2D_CACHE_REFILL) and 0x0111 (IMP_L2D_CACHE_REFILL_L1DHWPRF, L2 refills for the L1 prefetcher's requests) [the same TRM, sections 17.1 and 17.2]. Per load, best pass:

  • Inside L1 the same rule holds. The 4 KiB chain's loads are dependent. They take 2.00 ns each (4.01 cycles), the L1 load-to-use time. The read loop's loads are independent. The core can issue two 16-byte loads every cycle, so a 64-byte line leaves the L1 every 1.0 ns, 64 GB/s (computed from the path width). The chase moves 32.0 GB/s from the same cache (derived from its time per load), 2 times less. The chase measures latency and the loop measures bandwidth. The gap between them is how many loads are in flight.
  • The 0.49 ns above the L1 time is derived (the sequential chain's 2.492 ns less the 4 KiB chain's 2.002 ns) and is not explained. In cycles it is 0.98: the sequential chain takes 4.99 cycles per load against the L1 chain's 4.01, one cycle more. hypothesis A whole cycle per load points at a cost inside the core, such as the prefetched line's write into L1 taking the cache for one cycle per line, rather than at a wait for a late line, which would not average to a whole cycle. A sequential chain with two members per line (32-byte stride) would test it: a per-line cost would halve per load, a per-load cost would not. The counters give refills, not hits, so they do not say whether a load waited for a line that had not yet arrived. A sequential-chain row under the L1 hit counters would show that part.
