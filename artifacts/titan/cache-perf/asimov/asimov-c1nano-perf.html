Asimov C1-Nano Memory Performance

Measured by the cache-mem-perf benchmark on the emulated Asimov chip. Every measured number is computed from the raw result files when the page is built.

Short version

  • This page reports the memory latency and bandwidth that the Arm C1-Nano cores of the emulated Asimov chip see on boot F1 (the main boot: L3 cache on, hardware prefetchers on).
  • A load whose address is the data of the load before it costs 2.002 ns from the L1 cache and 52.658 ns from the DRAM model (an emulator memory, not silicon timing) on CPU 2, and Figure 1 gives the levels between.
  • One core reads 56.085 GB/s with a 16 KiB buffer (the footprint) and 24.575 GB/s at 32 MiB, and it writes 31.997 GB/s at 32 MiB.

1 What was measured

1.1 The chip under test

  • The chip is one emulated Asimov chip with 10 Arm C1-Nano cores [Ref9]. Two cores form a cluster. The tests use CPUs 2 to 9, which are four clusters.
  • Each core has an L1 data cache of 32 KiB that stores 64-byte lines. The two cores of a cluster share an L2 of 128 KiB, an L3 of 256 KiB and one port on the mesh [Ref8] [Ref9].
  • The mesh has five home nodes. Each one holds a 1 MiB slice of the SLC (system-level cache). Each slice has 16 ways (a way is one of the equal parts of a cache, and a given line can be stored in one place of each way). The firmware reserves 4 ways of each slice as one region of OCM (on-chip memory). So 3.75 MiB est. of the SLC is left for DRAM lines (operator's README) [Ref10].
  • Behind the home nodes is the DRAM model. It is four emulator memory models with every delay control at zero. No number of this level is silicon timing (operator's README) [Ref8]. Insufficient data: the share of the DRAM-model latency that is spent on the mesh. A signal trace of one miss in the emulator would settle it (operator's README) [Ref8].

1.2 The mesh

  • The mesh is a grid of 6 x 6 crosspoints. A device at crosspoint (x, y) has node id 64 x + 8 y.
  • The home nodes of OCM regions 0 to 4 have the node ids 88, 160, 216, 288, 344 (lib_run.sh) [Ref12].
  • The ports of the clusters of CPUs 2 to 9 are at (2,3), (3,2), (4,3), (5,2) (operator's README) [Ref10]. The mesh map of Linux agrees [Ref9].
  • A step is one move between neighbour crosspoints. A home node at (hx, hy) is |hx - px| X steps and |hy - py| Y steps from a port at (px, py). Every shortest route has these counts.
  • Mean steps to the five home nodes: 1.8 from CPU 2, 2.6 from CPU 4, 1.8 from CPU 6, 3.4 from CPU 8.

1.3 The boots

  • A boot is one power-on of the emulated chip with one firmware set. It ran one script once.
  • Boot F1 gives every row that it has. Five other boots add rows that boot F1 does not have (Table 3). The boots differ in three conditions.
  • L3. In the state "L3 on" the L3 of a cluster stores lines. In the other state the L3 holds no data: it only tracks which core has a line. The firmware sets the state before the cores start (operator's README) [Ref8] [Ref13].
  • The logs of boots F1, E, B, C, D each hold two readings of the L3 status register of the cluster of CPU 2. They read 0x70 on boots F1 and E and 0x0 on boots B, C, D [Ref14] [Ref15] [Ref16] [Ref17] [Ref18]. Boot R3 has no reading. Its state is taken from the operator's README [Ref8].
  • Boots F1, E and C have no register reading for the clusters of CPUs 4 to 9 (operator's README) [Ref8] [Ref19] [Ref20]. On boots B and D a firmware hook prints the register at each power-on of CPUs 2 to 9, and every line reads 0x0 (operator's README of boots B and D) [Ref13] [Ref21].
  • Prefetchers. "prefetchers off" means that the firmware set the disable bit of the hardware data prefetchers on CPUs 2 to 9 (operator's README) [Ref13].
  • OCM mapping. Boots C and D map each OCM region with 4 KiB page-table entries that carry the contiguous hint (a flag that lets the core keep one translation for 16 neighbour entries). So one translation covers 64 KiB. Every mapping line of their Linux boot logs reads cont=64/64 [Ref22] [Ref23]. Boots F1, E and B use plain 4 KiB entries: every mapping line reads cont=0/64 [Ref11] [Ref24] [Ref25]. The folder of boot R3 has no Linux boot log. Its mapping (plain 4 KiB entries) is taken from the operator's README [Ref8] [Ref10].
  • Build and commands. The boots also differ in the benchmark build and in the command list (Table 2). Boots E and C run one build and the same 138 commands in the same order. Boot D runs the 116 commands of boot B in the same order on another build, with 6 more commands at positions 40 to 45. Boots F1 and R3 run another script, each on its own build. So two boots that differ in one condition can also differ in the build and in the commands that ran before a row. A comparison of two boots names the condition that was set on purpose. It does not prove that this condition alone causes a difference.
  • The operator compared the machine code of the builds. The loop of the latency test is the same instructions at the same place in their 64-byte lines in the builds of boots B, C, D, E and F1 (operator's README) [Ref19] [Ref20]. The read, write and copy loops of the bandwidth test are the same bytes in the builds of boots F1 and R3. In the build of boot R3 the loop of the latency test lies across two 64-byte lines (operator's README) [Ref8].

1.4 The latency test

  • The latency test builds a chain of pointers over a buffer. Each member line of 64 bytes holds the address of the next member. The members form one cycle. Its order is random, except in the chain kind "address order" [Ref33].
  • The address of each load is the data of the load before it. So a load starts only after the load before it has returned.
  • One rep is one timed interval. It holds one walk of the chain, or several walks for the kind "walked many times". The chain load is the elapsed time divided by the loads, in ns per load [Ref33]. The timer counts in units of 1 ns.
  • The best row of a footprint is its smallest rep [Ref33]. The page quotes best rows, with the counters of the rep that has the best value.
  • There are four chain kinds (Figure 5). A chain that is walked many times gets 65,536 to 67,584 loads per rep on boot F1. Every other kind gets one load per member.
  • Buffers in the memory of the DRAM model (DRAM-backed buffers) use huge pages of 2 MiB. OCM chains have two shapes: "every line" (all 4,096 lines of a region) and "one line per 4 KiB page" (64 lines of a region). Both flush every line first.
  • Each command also times two clock reads with no load between them (the clock-read cost). The median is 39 ns on boot F1 (39 commands, 39 to 59 ns) [Ref34]. The program does not subtract it. On a row of 64 loads that is 0.61 ns per load est., and on a row of 320 loads 0.12 ns per load est. The counts of a 64-load row are multiples of 1/64.
  • The background control is a 4 KiB chain on 4 KiB pages with 8,192 loads. It runs once per CPU under the mesh counters [Ref35]. A difference from it is the measured difference between two loops.

1.5 The bandwidth test

  • The bandwidth test times whole passes of a fixed loop over a buffer. One iteration moves 256 bytes: 8 loads of 32 bytes in the read loop, 8 stores of 32 bytes in the write loop [Ref36]. The copy loop runs both.
  • A rep is one untimed pass and then the timed interval with all its passes. On boot F1 a rep holds 256 passes at 16 KiB and 2 passes at 32 MiB. Each command of the one-core sweep runs 3 reps [Ref36].
  • The rate is the bytes transferred divided by the elapsed time, in GB/s (1e9 bytes per second). A copy counts the bytes read plus the bytes written [Ref36].
  • The best row is the largest rep [Ref36].
  • Bandwidth is loop throughput. The timed interval holds the loop and, in the looped form, one call of the loop per pass. So the page never gives a time for one load or one store. It gives "effective cycles per 64 bytes transferred": 128 divided by the rate in GB/s, at 2.0 cycles per ns.
  • Documented instruction throughput (SOG): 32 bytes per cycle for the read loop and 16 bytes per cycle for the write loop [Ref37]. At 2.0 cycles per ns that is 64 GB/s and 32 GB/s.
  • Rows of 2 MiB and more use buffers larger than the caches of one cluster. These rows are DRAM-backed: their buffers are in memory that the DRAM model backs. The DRAM model is an emulator memory with zero configured delay, not silicon timing (operator's README) [Ref8]. The page does not name the DRAM model as the level that serves these rows.
  • None of the 19 bandwidth files of boot F1 has core counters. CPU 3 is offline during the latency rows and the one-core rows, and online for the multi-core rows [Ref14].
Insufficient data

How the timed lines of a 2 MiB row split between SLC hits and fills by the DRAM model. A 2 MiB buffer is under the 3.75 MiB est. that the SLC has for DRAM lines (operator's README) [Ref10]. The mesh counts cover the whole command with its buffer fill and its untimed passes, not the timed passes (operator's README) [Ref8]. Counters that separate the two sources inside the timed interval would resolve it.

1.6 Counters, clock, integrity

  • Core counters. Each test thread counts cycles and six events in user mode. The counters start just before the first clock read and stop just after the second [Ref38].
  • A count is printed per load or per 64 bytes transferred. It is an aggregate. It does not give the history of each line, and a refill count includes prefetch fills.
  • Mesh counters. A wrapper counts mesh events over the whole life of a command: program start, buffer fill, untimed walks, flushes and timed reps [Ref39]. So the page gives mesh counts per command only.
  • Clock. The cycle counter and the timer give 2.000 cycles per ns on boot F1. The value is the sum of the cycles over the sum of the ns of the 79 timed rows of at least 4,096 loads. The single rows read 2.0000 to 2.0199 cycles per ns. The timer runs at 1000 MHz [Ref11]. So the core clock is 2.0 GHz in the time of the emulated chip.
  • Integrity. On boot F1 137 commands ran (67 core, 70 CME) and 0 failed [Ref14]. The CME rows are on a separate page. Every check of boot F1 passes: the checksums, the counter coverage (perf_cov), the best rows and the mesh counter rows (Table 2).

Five limits apply to these numbers.

  • The DRAM model is an emulator memory with zero configured delay, not silicon timing (operator's README) [Ref8]. This applies to the 52.658 ns row, to the 8 MiB chain in address order, to every DRAM-backed bandwidth row (2 MiB and more), and to every multi-core row.
  • A bandwidth value is loop throughput: bytes transferred over elapsed time. No write row waits for its lines to reach the DRAM model.
  • No counter inside the timed interval separates an SLC hit from a fill by the DRAM model. So the split of a 2 MiB row between the two is not known (section 1.5).

  • The L3 hit count and the L3-served estimate come from the hit set of boot E. These events are exploratory, with three consistency checks (section 3.3). The estimate uses the two rows that count more than 0.5 L3 hits per load. The 192 KiB row gives 9.9 ns est.

3 Latency by footprint

3.1 By footprint, CPU 2

  • The 4 KiB row (the L1 row) reads 2.002 ns per load, which is 4.01 cycles. The SOG documents an L1 hit at 2 to 4 cycles [Ref37].
  • The 128 KiB row reads 6.014 ns per load (12.03 cycles). The SOG documents an L2 hit at 10 to 12 cycles.
  • The 384 KiB chain (21.98 cycles) has a footprint equal to the L2 and L3 sizes added. The 2 MiB chain (47.44 cycles) counts 0.98 L3 read refills per load (section 3.2). The 32 MiB chain (104.43 cycles) is close to the DRAM-model row (section 3.4).

3.3 What an L3-served load costs

Boot F1 has no count of L3 hits. The hit set needs three counters, and the commands of boot F1 use those three counters for the prefetch refill events. Boot E (the firmware state of boot F1, another command set) ran the same chains with the hit set [Ref38]. On each of its 12 chains of up to 384 KiB the best row is within 0.19 % of boot F1, and the reps of the two boots overlap or touch (section 2.2).

One row measures an L3-served load almost directly: the 384 KiB chain of boot E. Per load it counts 0.915 to 0.924 L3 hits, 0.047 to 0.057 L2 hits and 0.020 to 0.032 refills from outside the cluster.

An estimate removes the other loads from the row. A chain is serial. So the time of a walk is the sum of the times of its loads. For each rep the estimate is (chain load - L1 share x L1 cost - L2 hits x L2 cost - L3 read refills x outside cost) / L3 hits. The L1 share is 1 minus the L1 refills per load. Two costs are rows of boot E: the L1 cost is 2.002 ns (4 KiB row) and the outside cost is 24.177 ns (2 MiB chain) [Ref69] [Ref70]. The L2 cost is 6.003 ns est. It is the 96 KiB row of the hit set (5.819 ns) with its L1 share removed: (chain load - L1 share x L1 cost) / L1 refills per load, the smallest of the three reps. The estimate reads each count per load as a share of the loads. That is an assumption, not a counted fact.

  • On the two rows that count more than 0.5 L3 hits per load (256 KiB and 384 KiB) an L3-served load costs 10.6 to 11.0 ns est.
  • The estimate depends on the row. The 192 KiB row gives 9.9 ns est. and the 512 KiB row 10.65 to 10.92 ns est.
  • The 512 KiB row of boot E is walked many times. The 512 KiB row of boot F1 is walked once. They are two different measurements.

The three events of the hit set are exploratory, with three consistency checks (Table 4). The third check uses boots B, C and D, where the L3 holds no data [Ref71] [Ref72] [Ref73].

5 Multi-core bandwidth

5.1 One core per cluster, all eight

The bandwidth test runs one thread per listed CPU, each with its own buffer. The aggregate rate is the bytes of all threads divided by the elapsed time of the slowest thread [Ref36]. Scaling is the aggregate rate divided by the one-core rate of the same kernel (read, write or copy) and footprint (section 4.1). Efficiency is the scaling divided by the number of cores.

  • With one core per cluster, four cores scale 3.984 to 4.001 times at 2 MiB [Ref7]. Each thread of the best rep runs within 1.2 % of the one-core rate (read +0.0 to +1.2 %, write within 0.01 %, copy -0.4 to +0.3 %).
  • The second core of each cluster adds 8.5 % and 9.7 % (read, 2 MiB and 16 MiB), 13.3 % and 12.5 % (copy), 29.1 % and 19.5 % (write) [Ref7] [Ref49].
  • All eight cores write 165.154 GB/s at 2 MiB, 5.164 times one core [Ref49]. It is the highest aggregate rate of any row. It is not a measured limit of the mesh or of the DRAM model.
  • The eight write threads are unequal. The slowest thread is 16.3 % (2 MiB) and 16.5 % (16 MiB) below the fastest. The file gives the rate of the slowest thread and of the fastest thread only, not the CPU of each.
Limits of these rows

The DRAM model is an emulator memory with zero configured delay, not silicon timing (operator's README) [Ref8]. No counter inside the timed interval separates an SLC hit from a fill by the DRAM model, so the split of a 2 MiB row between the two is not known (section 1.5). A write rate is the rate at which the store loop runs. No write row waits for the lines to reach the DRAM model. Hypothesis

With the L3 on, the prefetchers place lines of the read stream in the L3 ahead of the core, many lines at a time (project note) [Ref113].

Measurement that would confirm or reject it: Two counts on the 2 MiB and 32 MiB reads, in both L3 states. Count 1: prefetch accesses that target the L3. Count 2: demand reads whose line a prefetcher placed in the L3. A prepared command set has both (follow-up-run-plan.md) [Ref83].

Hypothesis

With the L3 on, the cluster issues or times the prefetch requests in another way, and the lines still arrive in the L1 and the L2 directly.

Measurement that would confirm or reject it: A boot with the L3 on and the stride prefetcher (one of the hardware prefetchers) set to fill the L2 in place of the L3 [Ref83], or a trace of the requests of the timed read stream.

Hypothesis

With the L3 on, more reads are in progress at the home nodes at one time.

Measurement that would confirm or reject it: The mean read-queue occupancy of the five home nodes around the same read, in both L3 states [Ref83]. It is a mean over the whole command.

Hypothesis

The gain needs the prefetchers.

Measurement that would confirm or reject it: The one-core read sweep with the prefetchers off, in both L3 states. No boot has core rows with the L3 on and the prefetchers off (Figure 26).

Insufficient data

Which of the four hypotheses holds. No results folder holds the rows of the prepared command set. Its counters can show that prefetch fills of the L3 occur. They cannot show how much of the gain these fills cause.

One of the equal parts of a cache. A given line can be stored in one place of each way.
