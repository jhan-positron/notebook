Asimov CME memory performance: brief

Latest: run 4 boot E (membench-jibin-010, 2026-11-05, commit b79dffa, SCP 0.48.0-nopcie-l3.1 (the system control firmware), TF-A 0.35.0 (the Arm Trusted Firmware)) on the GA13 Palladium (one Asimov hemisphere), the first boot with the DSU L3 in use as a cache (IMP_CLUSTERPWRSTAT_EL1 0x70 on CPU 2's cluster, Jesse's README). Beside it: run 3 (membench-jibin-004, 2026-11-03) and run 4 boots A to D (005 to 008), all measured with the L3 of CPUs 2 to 9 holding no data (register 0x0, 0 L3 hits). One C1-Nano core on CPU 2 unless stated. DRAM is an emulator memory, not LPDDR5X. Full reports: asimov-c1nano-perf.html, asimov-cme-perf.html. Every number here is read from the CSV files by gen_brief.py through gen_perf.py.

Words used here

CME
The Compute Matrix Engine, Arm's C1-SME2 unit: one per two-core cluster (DSU), runs the cores' streaming-mode (SME) instructions, with its own 64 KiB L1 data cache, TLB and hardware prefetcher. Its path to memory is CME L1, DSU L3 (in use on boot E only), then the mesh. The core's L1 and L2 are not on it.
run, boot
A run is one job on the emulator (run 3 = membench-jibin-004). Run 4 is five boots, A to E: A as run 3, B the prefetchers off (the CME's too), C and D the OCM mapped with a 64 KiB hint (D with the prefetchers off), E the L3 on.
streaming mode
The CPU state (SMSTART to SMSTOP) in which SVE instructions execute on the CME. The vector length here is 64 bytes, one cache line.
round-trip baseline
The latency test's loop with the load replaced by a register move (DUP then LASTB), so it measures one core-to-CME-to-core round trip with no memory access.

4. What it means, and what it does not

  • A single load through the CME is slow, a stream is fast. The CME path (core to CME to core, with the CME's own L1 and the DSU L3 behind it) adds 19.4 ns to a dependent load and 9.4 ns to a DRAM load that misses every cache on boot E. A 256-byte load per instruction with no dependency gives 4 times the core's read rate and 2 times its write rate (run 3, L3 off).
  • Writes through one CME exceed what two cores write together (run 3, L3 off). One CME writes a 32 MiB buffer at 62.0 GB/s through the cluster's mesh port, 1.51 times the 40.9 GB/s CPUs 2 and 3 write together. hypothesis The two-core write limit of the cluster is on the cores' side. A two-core write row with one core in streaming mode (through its CME) would test it.
  • The CME prefetcher explains the climb from 8 KiB. With the prefetcher off (boot B) the chain load reads 21.02 to 21.26 ns from 4 to 64 KiB and 37.16 ns at 96 KiB [cme-latency-dram-small.csv, boot B]. That is the L1 step the other boots hide. With the L3 on (boot E) the prefetcher's fills at 8 to 24 KiB come from inside the cluster. They are 99.5 to 88.0 % of the CME's L1 refills, against 16.8 % or less on boot C. The refills from outside the cluster per load (mean over passes) fall from 3.33 and 6.55 on C to 0.02 and 1.25 on E at 8 and 16 KiB. The time does not fall. Boot E's time over boot C's is 1.019 at 8 KiB, 1.120 at 16 KiB and 0.940 to 0.977 from 48 to 384 KiB. The prefetcher sets the time, so the source of a refill does not change it. Through the CME no row gives an L3 hit number. No CME event names the level that served a load.
  • OCM through the CME costs more per load than from the core. On boot E the all-five chain over every line reads 43.3 ns through the CME, 17.2 ns above the core's 26.1 ns [cme-latency-ocm-*.csv]. The per-region rows through the CME do not order by mesh distance. The three regions 1 crosspoint away read 29.0 to 37.2 ns, and the two regions 3 crosspoints away read 37.1 to 37.7 ns, so the spread within one distance is larger than the gap between distances. The CME streams OCM at 1.4 to 1.6 times the core's rate (run 3, L3 off).
  • Not measured. Insufficient data Two cores of one DSU in streaming mode at once. The CME is shared, and no two-core CME row has run. A CME matrix multiply with its operands in an OCM region has not run either. hypothesis Each 64-load OCM pass carries a fixed wake-up cost of 0.1 to 0.3 us est. (if the CME was powered down at the start of a timed span, the timed part of one command, which is not recorded. The bounds are from Jesse's run 3 README). A per-pass timestamp on those passes would test it.
