Asimov CME memory performance: brief

Latest: run 6 boots F1 and F2 (membench-jibin-011 and 012, 2026-11-06 and 07, commit 0c190a1, SCP 0.48.0-nopcie-l3.1 (the system control firmware), TF-A 0.35.0 and 0.35.0-pfoff.1 (the Arm Trusted Firmware; F2 turns the data prefetchers off)) on the GA13 Palladium emulator (one Asimov hemisphere), the DSU L3 in use as a cache (IMP_CLUSTERPWRSTAT_EL1 0x70 on CPU 2's cluster, Jesse's READMEs). Beside them: run 4 boot E (010, 2026-11-05, the L3 on), boot B (006, the L3 off, prefetchers off) and run 3 (004, 2026-11-03, the L3 off). CPU 2 with CPU 3 offline. DRAM is an emulator memory, not LPDDR5X. Full report: asimov-cme-perf.html. Every number is read from the CSV files by gen_brief.py through gen_perf.py.

Words used here

CME, streaming mode
The Compute Matrix Engine, Arm's C1-SME2 unit: one per two-core cluster (DSU), runs the cores' streaming-mode (SME, SMSTART to SMSTOP) instructions with a 64-byte vector length, with its own 64 KiB L1 data cache, TLB (translation buffer) and hardware prefetcher. Its path to memory is CME L1, DSU L3 (in use on boots E, F1 and F2), then the mesh; the core's L1 and L2 are not on it.
run, boot
A run is one job on the emulator (the GA13 Palladium; run 3 = membench-jibin-004). Run 4 is five boots, A to E (B the prefetchers off, the CME's too; E the L3 on). Run 6 (commit 0c190a1): F1 the L3 on, prefetchers on (every row); F2 the L3 on, the prefetchers of the cores and the CMEs off (the CME rows).
bracket, in span; looped, single-call form
Run 6 times every CME call by the clock reads around the call (bracket) and by clock reads inside the streaming span (in span). An L1 bandwidth row calls the kernel once per pass (looped form) or runs every pass of a rep inside one call (single-call form). Fold: the read kernel's end-of-call sum of its 16 running totals. DSB ST: the Arm barrier that waits for every earlier store.
round-trip baseline
The latency test's loop with the load replaced by a register move (DUP then LASTB): one core-to-CME-to-core round trip with no memory access.
OCM, SLC, crosspoint; SOG, TRM, LLVM model
OCM: the on-chip SRAM, five regions, each behind one home node of the mesh. SLC: the mesh's system level cache, 3.75 MiB over five home nodes. Crosspoint: one switch of the mesh; a region's home node is 1 or 3 crosspoints from the DSU. SOG, TRM: Arm's Software Optimization Guide and Technical Reference Manual. LLVM model: the public C1-Nano timing table in the LLVM compiler.

1. Read latency: core against CME, data path end point: the core

2. Bandwidth: core against CME. Data path end point: core registers for core read, CME registers for CME read, memory (writes)

4. What it means, and what it does not

  • A single load through the CME is slow, a stream is fast. The CME path adds 19.4 ns to a dependent load and 9.4 ns to a DRAM load that misses every cache (boot E). A 256-byte load per instruction with no dependency gives 1.5 times the core's DRAM read rate and 1.3 times its write rate with the L3 on (F1).
  • The L3-served load through the CME is 32.8 to 33.9 ns (boot F2). With the prefetchers off every CME refill is a demand refill, and the 192 to 384 KiB chains refill once per load from inside the cluster: 11.8 to 12.9 ns above the round-trip baseline (derived; the core's own L3 hit: 10.6 to 11.0 ns est.). Boot B, the L3 off, read 39.5 to 41.7 ns. hypothesis 0.49 to 0.64 of those loads hit the L3 by the exploratory events, the rest come from CPU 2's own cache (it built the chain); no control validates those events yet [full page, section 5.2].
  • The CME prefetcher explains the climb from 8 KiB, and carries half of a DRAM stream. With the prefetcher off (boots B and F2) the chain load reads 21.02 to 21.26 ns from 4 to 64 KiB: the L1 step the other boots hide. With it on (boot E) its fills evict the chain and cost 14.0 ns per load at 16 KiB. On a stream it doubles the DRAM read rate: 17.7 GB/s at 32 MiB with it off (F2) against 36.6 with it on (F1); the writes do not change.
  • The L3 on costs the CME's writes. On F1 and F2 alike the CME writes 52 to 53 GB/s by the bracket from 16 to 256 KiB and 40 to 43 from 1 MiB (in span too from 96 KiB on), where run 3 wrote 64 GB/s at 16 KiB to 2 MiB and 62 at 32 MiB with the L3 off; the core's own writes did not move and the kernels are run 3's byte for byte. hypothesis The CME's stores allocate in the L3 and drain at its write rate; a CME write row with the L3 events, or Arm's statement of the CME L1's write policy, would test it [full page, section 10].
  • OCM through the CME: the demand-only latency is 47.9 to 52.1 ns per region (boot F2). One refill per load from outside the cluster, the same as boot B within 3 %, so the L3 on does not change these rows; with the prefetcher on they read 37.3 to 39.2 ns (F1) and 29.0 to 37.7 (E). The CME streams OCM at 34.4 GB/s over all five regions against the core's 19.8 (F1, the L3 on; run 3 23.2 against 16.0) and writes it at 30.7 against 20.3.
  • Not measured. Insufficient data Two cores of one DSU in streaming mode at once (the CME is shared), a CME matrix multiply with its operands in OCM, and the wake-up cost of a 64-load OCM pass (full page, section 10).
