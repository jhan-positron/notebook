Short version: this folder holds the C tests that Jesse Zhang runs on the Asimov emulator (commit 9c6b8e7 in https://github.com/jhan-positron/asimov, folder cache-mem-perf). The CRB work in ../crb is finished except for one root-only run, and it produced methods and lessons that apply to Asimov's mesh. The job of the new session is to decide what Asimov needs beyond the existing tests (mesh topology, home-node mapping, per-slice latency), ask Jesse and the design team the three open questions below, and extend the code only after those answers.

## Words used here

- Asimov: Positron's chip. One hemisphere has 5 DSUs (DynamIQ Shared Units, 2-core clusters) of Arm C1-Nano cores, a CMN S3 mesh with 5 home nodes, a 5 MiB SLC, OCM and a 16 MB scratchpad.
- CMN, crosspoint (XP), home node (HN-S), SLC, slice: the Arm mesh interconnect, its routers, the nodes that own address ranges, the System Level Cache, and the part of it inside one home node. Every address has exactly one home node, chosen by a hash of the physical address.
- OCM: 4 of the 16 SLC ways per home node locked as on-chip memory, 5 regions of 256 KiB, reached through /dev/ocm.
- CRB: the Arm Phoenix Reference Server used as the comparison machine (Neoverse V3AE, two CMN S3 meshes of 9 by 8 crosspoints, 64 home nodes per mesh). Its report and data are in ../crb.
- Emulator: Jesse's cycle-exact model. 1 s of chip time is about 46 min of wall time. Our program runs as root under a minimal Linux (asimov-os).
- Fresh chain: a random pointer chase walked exactly once. Both C1-Nano and V3AE cores learn a repeated load sequence and prefetch it, which hides the real latency.

## What the CRB work established that carries over

Read ../crb/crb-memory-hierarchy.html (published at https://claude.ai/artifact/Wtk42eJd8ykC6FV4FFTEtM) and ../crb/plan-2026-11-02.md before changing anything. The parts that matter for Asimov:

1. Mesh topology can be read from Linux: `sudo cat /sys/kernel/debug/arm-cmn/map` (one file per mesh instance, map_1 for the second). It prints the crosspoint grid with the node type on every port and the logical ids of the home nodes. The driver's source is drivers/perf/arm-cmn.c (function arm_cmn_map_show). It needs debugfs mounted and root. On Asimov the RTL already gives this, but the map is the cheap confirmation that the emulator's mesh matches the RTL.
2. Which home node an address goes to is not public (the hash is configured per chip). On CRB it is being found with the mesh counters: flush a line, load it once, see which home node's "read requests received" counter rose (../bench/homelat.c, step 2). On Asimov this step is probably unnecessary: Positron configures the CMN, so the home-node count, slice size and hash can come from the design (the CMN_uArch_Spec and the RTL yml). Ask before measuring.
3. Per-slice latency needs care with prefetchers. Lessons measured on CRB on 2026-11-02 (../bench/homelat.c, comments at the top): a sequential read of 8 MiB does not push lines out of L2; a fixed random evictor order is learned after one repeat and replayed; a fill chain walked every repeat is learned too. What works: fill with independent loads in a new random order each repeat, evict with independent loads in a new random order each repeat, and time every chain exactly once. The existing Asimov latency.c already uses fresh chains and an explicit flush (DC CIVAC), which is the safer method when the number of lines is small.
4. Placement changes the numbers more than thread count. On CRB, 64 writers on one mesh write 394 GB/s to DRAM and 32 plus 32 across the two meshes write 173 GB/s. Asimov has one mesh per hemisphere, so the analogue is DSU placement relative to the home node of the data: with 5 home nodes and 5 DSUs, each buffer's lines are spread over all 5 slices, and a core's average latency depends on its hop count to each.
5. Core position shows in latency. On CRB the fresh mesh-cache latency ranges from 25.4 ns to 30.5 ns by core, and partner cores on one crosspoint match to 0.2 ns. On Asimov the equivalent test is the same chase from CPU 2, 4, 6 and 8, which the current run_asimov.sh does not do (it uses CPU 2 only). It costs one fresh pass per core per size, cheap in chip time.

## Open questions to settle before writing code (ask Jesse and the design team)

1. Does the emulator kernel have debugfs and the arm-cmn map file, and does `perf_event_open` on the arm_cmn PMU work as root with `bynodeid` and `nodeid` filters? Jesse said the driver is in the kernel. A one-line test: `cat /sys/kernel/debug/arm-cmn/map` and `perf stat -e arm_cmn_0/hns_pocq_reqs_recvd_read/ -- sleep 0.001` in his image.
2. Can the design team give the home-node hash directly (which physical address bits select the home node, and the slice size per node)? With it, lines are classified by arithmetic and the counter-based classification is not needed. Also ask whether the OCM lock changes the hash (it should not; it locks ways, not addresses).
3. Chip-time budget. The CRB classification takes about 80 chip-seconds (262,144 probes, each with about 128 counter reads through syscalls). At 46 min per chip second that is more than two days of emulator time, so it is out. Everything on Asimov must stay in the low chip-seconds: a few hundred probes at most if counters are used, otherwise the hash from question 2.

## What the Asimov extension would measure, once the questions are answered

- Topology check: the map (or the RTL) gives 5 home nodes at crosspoints 13, 24, 33, 44, 53 and DSU ports at 12, 23, 32, 43, 52. Confirm the home node that holds each OCM region.
- Per-slice latency from one DSU: chains over lines homed at each of the 5 nodes, flushed, fresh, from CPU 2; then from CPU 4, 6, 8. Expect a 1-hop to 4-hop spread. Compare with the OCM latency per region, which is the same path with a locked way.
- Per-core average: the existing SLC-regime chase from each free core. 
- Write placement: not an issue with one mesh, but DRAM write with 2, 3, 4 writers on different DSUs is worth one row each.
