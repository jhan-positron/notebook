Run 8, the mesh latency map: the three boots

Asimov emulator, result folders 014 (boot 1), 015 (boot 2) and 016 (boot 3). Files copied and checked 2026-11-12. The trial run and the full detail of boot 1 are on the page run8-meshmap-boot1.html.

Short version

All three boots returned complete files: 180 of 180 cells each, and Arm's hash formula predicts the home node of every classified line on three different memory pages.

With the L3 in use (boot 2), the flushed kinds repeat boot 1 to within 0.7 ns, but the slc and ocm-evict cells drop to 13 to 17 ns: about 70% of their loads never left the cluster, so on this boot these cells are not a distance map of the slice.

With the prefetchers on as well (boot 3), the flushed kinds drop to 12 to 35 ns and stop following the distance, and the evicted kinds stay as on boot 2.

Words used here

  • Mesh: the chip's interconnect, 6 x 6 crosspoints. A message moves one crosspoint per step. Crosspoints are written (x,y).
  • Home node: one of five cache nodes on the mesh (ids 88, 160, 216, 288, 344). Each holds a slice of the system-level cache (SLC) and 256 KiB of on-chip memory (OCM).
  • DRAM-backed line: a 64-byte line of normal memory (DRAM). A hash of its physical address selects its home node. Frame number: the physical address of a page divided by 4 KiB.
  • Cluster: two CPUs that share one L2 cache and one L3 cache (CPUs 2-3, 4-5, 6-7, 8-9, and 0-1). The L3 sits between the L2 and the mesh. Prefetcher: hardware in a CPU that fetches lines before the program loads them.
  • Cell: one CPU, one home node, one kind of row. Each cell has 7 timed passes of 2,048 dependent loads (each load gives the address of the next). Best is the smallest ns per load of the 7 passes.
  • Kinds: ocm-flush (OCM lines, flushed first), ocm-evict (OCM lines, pushed out of the CPU's caches by the evictor), slc (DRAM-backed lines held in the node's slice, same recipe as ocm-evict), dram-flush (the same DRAM-backed lines, flushed first, so every load goes to memory). The flushed kinds are the first and the last. The evicted kinds are the middle two.
  • Evictor: one load of each of 30,720 other lines, made before a timed pass of an evicted kind.
  • meshmap: the program that measures the cells. Classification: its first step, which finds the home node of each DRAM-backed line with the mesh counters. run_map.sh: the script that runs it, after four control rows of the older program latency.
  • Core counters, all per load: l3d_refill_rd counts demand loads whose data came from outside the cluster. l2d_refill_hwprf counts L2 fills made by the prefetcher. l1d_tlb_refill counts misses in the address translation cache (TLB). perf_cov is the share of the pass that the core counters covered.
  • Mesh counters, all per load: req_<node> counts requests that reach a home node. mc_reqs counts requests that a home node sends on to memory. Level 1 means that all mesh counters opened.
  • Share: l3d_refill_rd per load of one pass, read as the share of the loads that left the cluster.
  • Unit of distance: 2 per X step plus 1 per Y step. On boot 1 one unit costs 1.00 ns.
  • Chip second: one second of time on the emulated chip. rms: root mean square of a fit's errors. est.: an estimate.
  • Boots: boot 1 = L3 holds no data, prefetchers off. Boot 2 = L3 in use, prefetchers off. Boot 3 = L3 in use, prefetchers on. The states hold for CPUs 2 to 9. CPU 0's cluster has its L3 in use and its prefetchers on at every boot (section 7). Jesse: Jesse Zhang, who operates the emulator.

4. Boot 2: the flushed kinds repeat boot 1

  • ocm-flush: boot 2 minus boot 1 is +0.05 ns on average over 40 cells (range -0.39 to +0.51 ns). The fit of the best values is 21.04 ns + 1.99 ns per X step + 1.01 ns per Y step.
  • The medians of boot 2's ocm-flush cells fit with the smallest error of any row so far: 21.23 ns + 2.00 ns per X step + 1.00 ns per Y step, rms 0.01 ns over 40 cells. At 2 cycles per ns that is 4 cycles per X step and 2 cycles per Y step, for the request and the data together.
  • The base of the median fit is 0.19 ns above the base of the best fit. A few cells have one pass that reads about 0.5 ns below the others, and the best value takes that pass.
  • dram-flush: boot 2 is +0.62 ns above boot 1 in every cell (range +0.55 to +0.67 ns). The offset does not depend on the CPU or the node.
  • The three-leg memory path of boot 1 fits boot 2 equally well, with the same memory point and the same costs:

  • In the first passes the evictor works as designed. Nearly every load leaves the cluster (share 0.98), and the cell reads a mesh value: 23.5 ns for CPU 2 to node 88 on boot 2.
  • Then the share falls to about 0.35 within a few passes, and stays there for the later cells of that cluster. On boot 3 the fall takes longer and reaches into the second node.
  • The second CPU of a cluster never shows it. CPUs 3, 5, 7, 9 measure the same lines of node 88 with a share of 0.29 to 0.37. So the effect belongs to the cluster's first cells of a kind, not to node 88.
  • CPU 0 shows it on all three boots (last row of the table), since its cluster has its L3 in use on every boot.
Hypothesis: the cluster keeps the chain lines once it has seen the store-then-evict cycle several times. The evictor is not too small: it loads 30,720 lines (1.875 MiB), 7.5 times the 256 KiB L3 that the project README gives, after one store to every chain line [Ref8]. A fixed rule (for example "dirty lines stay, clean lines go") does not fit, since the first passes of a cluster do evict the chain lines. Something in the cluster changes over about 5 to 10 cycles. What changes is not measured. The test: one boot 2 cell under the L3 hit counter set (--events l3), and one cell whose evictor stores to its lines.

6. Boot 3: the prefetcher acts on the flushed kinds

  • ocm-flush: 12.3 to 15.5 ns, against 22.0 to 30.0 ns on boot 2. The prefetcher made 0.54 L2 fills per load (median), and demand refills from outside the cluster fell to 0.36 per load.
  • dram-flush: 25.4 to 35.4 ns best, against 50.6 to 57.8 ns on boot 2. The best value is not a stable number here: the passes of one cell differ by 3.0 to 29.9 ns, and the cell medians span 26.7 to 56.5 ns. In some cells the prefetch fills stop after two passes, and the later passes read boot 1's value (section 4).
  • The evicted kinds are boot 2's mix again. In the slc rows the prefetch columns have a median of 0.00 per load. The slow slc and ocm-evict cells of boot 3 (up to 28.5 ns) are first cells of a cluster (section 5), not a prefetcher effect.
  • The chain is a dependent chain in a new random order each pass, yet the prefetcher helps. The request counts of section 3 show that the prefetches go to the chain's own lines. Hypothesis: the prefetcher replays the set of lines that earlier passes touched in the region. The test: one cell whose line set changes between passes.
  • The four control rows read 15.6 to 19.6 ns where the map's cells read 12.6 to 15.4 ns (section 8). The control chain has 4,096 lines of the whole region and the map's chain 2,048 lines. Whether that explains the difference is not tested.
