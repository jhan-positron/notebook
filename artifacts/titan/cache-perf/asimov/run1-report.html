Asimov Cache Run 1

Jesse Zhang's run of cache-mem-perf commit 9c6b8e7 on the Asimov emulator, 2026-10-31. Data: results/membench-jibin-001/ in this folder (a copy of /home/jzhang/dev/emuMemBenchBox/results/jibin/membench-jibin-001/ on the lab /home, checksums verified). Written 2026-11-01 by Claude for Jibin Han.

Short version. The first emulator run finished in 1.24 s of chip time and gives the whole level map for one core: L1 2.0 ns, L2 6.1 ns, mesh cache (SLC) 24 ns, DRAM 52 ns, and OCM 18.8 to 23.2 ns by region, with the one-hop regions faster than the three-hop regions.

Two rows measured the wrong thing: the "flushed" DRAM rows measured DRAM (the flush removes lines from the SLC too), and the OCM write rows measured the speed of the cache-flush instruction, not of writing to OCM.

Run 2 needs five changes to run_asimov.sh and no new C code, once the OCM copy row is dropped. Three questions remain for Jesse: two carried from the handoff and one new one about the OCM lock mode; his notes answered the chip-time budget and the hop counts.

Words used here

DSU
DynamIQ Shared Unit, a cluster of 2 C1-Nano cores. CPU 2 and CPU 3 form DSU 1 and share one L2 and one L3.
L1, L2, L3
32 KiB per core, 128 KiB per DSU, 256 KiB per DSU (sysinfo.txt cache topology lines).
SLC, home node
System Level Cache inside the CMN mesh: 5 home nodes of 1 MiB. Every address belongs to one home node. 4 of the 16 ways in each node are locked as OCM, so 3.75 MiB caches DRAM.
OCM
On-Chip Memory: 5 regions of 256 KiB, one per home node, reached through /dev/ocm in 4 KiB pages. Jesse: CPU 2's DSU port is one mesh crosspoint from the home nodes of OCM 0, 1, 2 and three from OCM 3, 4.
hop
One crosspoint-to-crosspoint step on the mesh.
repeated chase
A random pointer chain over the buffer walked many times. Later walks hit whatever cache holds the buffer.
fresh chain
A random chain walked exactly once. A prefetcher that learned an earlier walk cannot help.
flushed
DC CIVAC on every line (clean and invalidate from the core caches) before a single timed pass.
refills per load
PMU counts 0x03 (L1D refill), 0x17 (L2D refill), 0xA2 (L3D read refill) divided by the loads of the timed walk. About 1.0 at a level means every load missed that level.
chip time
Time as the emulated chip sees it. One chip second took 2,779 wall seconds in this run (Jesse's README).
est.
An estimate, not a measurement.

The run

  • 34 measurement commands, all exit 0, 1.237 s of chip time, 57 min of wall time (Jesse's README, "The run"). The results directory is byte for byte what the script wrote (SHA256SUMS, 26 files, all OK).
  • Build and platform as requested: GCC 14.2, -O2 -mcpu=cortex-a520 -static, CPUs 2 to 9 isolated, CPU 3 offline for phases A to D, 256 huge pages of 2 MiB reserved and used (log.txt:3, every DRAM row prints backing=hugetlb), 0xA2 counts (every latency row has a live L3 column).
  • Skipped: the scratchpad phase. This emulator image cannot load /dev/asimov-spm, so no SPM file exists (sysinfo.txt devices block).
  • Caveats from Jesse: DRAM is an emulator memory, not LPDDR5X. The firmware is SCP 0.34.0, without 0.46.0's later mesh setup (HN-S-to-SMS route overrides and HN-S queue caps, Jesse's README). OCM is mapped in 4 KiB pages, so the 1.25 MiB all-five rows may include TLB misses.
  • The mesh PMU driver registered its PMU: arm_cmn_0 is listed under /sys/bus/event_source/devices (sysinfo.txt:192). The handoff's first question (the arm-cmn map file, and perf_event_open with node filters) stays open; the listing is only the precondition.

1. Latency by level, CPU 2

  • L1: 2.00 ns, 4 cycles, up to 24 KiB; 32 KiB already shows 4 % L1 refills (latency-dram-small.csv:24 to 26).
  • L2: 6.07 ns, 12 cycles, at 128 KiB with 0.99 L1 refills and 0.004 L2 refills per load (latency-dram-small.csv:44).
  • L3: not isolated by this sweep. At 192 KiB, 0.57 of loads leave L2 and 0.46 leave L3 too, so the L3 served only about 0.11 of loads (latency-dram-small.csv:49). At 256 KiB and 384 KiB the L3 read refills are 0.74 and 0.94 per load. Hypothesis: the DSU L3 keeps few lines of a chain that touches each line once per pass. A measurement that would settle it: a chase at 144 KiB and 160 KiB, and the DSU L3 hit event if the PMU has one.
  • SLC: 23.1 to 24.0 ns for fresh chains of 512 KiB to 2 MiB with 0.95 to 1.00 L3 read refills per load (latency-dram-large.csv:6 to 22). 3 MiB reads 25.4 ns, 4 MiB 29.8 ns, 8 MiB 45.1 ns. The transition sits between 2 and 16 MiB, consistent with Jesse's 3.75 MiB of SLC for DRAM (an RTL configuration figure); the sweep does not measure the size itself.
  • DRAM: 52.3 ns at 32 MiB fresh (latency-dram-large.csv:46) and 52.7 ns for every flushed best row from 1 MiB up (repeats 52.7 to 53.3 ns; latency-dram-flushed.csv:9 to 27). Emulator memory, not silicon.
  • The flushed 256 KiB row reads 35.7 to 44.7 ns with only 0.78 to 0.90 L3 read refills per load (latency-dram-flushed.csv:4 to 6). Some lines arrived before their load. See section 5.

2. OCM latency by region, CPU 2

  • The region order matches Jesse's topology note: OCM 0, 1, 2 one hop from CPU 2's DSU port, OCM 3, 4 three hops. The gap between the group means is 3.4 ns (est.) for two extra hops. The per-region rows carry 9 to 23 % prefetched lines, and the fraction differs by row, so the per-hop cost is not yet a measurement.
  • OCM reads within 1.2 to 1.5 ns (5 to 6 %) of an SLC hit, close to the hypothesis in ocm-interpretation.html: all five flushed 25.5 ns (latency-ocm-all5-flushed.csv:7), all five fresh without flush 25.2 ns (latency-ocm-all5-fresh.csv:6), DRAM-backed fresh chain at 2 MiB 24.0 ns (latency-dram-large.csv:22). The 1.25 MiB OCM rows run on 4 KiB pages and the 2 MiB DRAM row on 2 MiB pages, so whether the remainder is TLB cost on 4 KiB pages or mesh cost is not yet measured (Jesse's note).
  • The fresh row without a flush reads 0.3 ns (1 %) below the flushed row, and the two repeat ranges do not overlap. At 1.25 MiB the footprint is 3.3 times the 384 KiB of L2 plus L3, so the core caches cannot hold the chain either way, and the flush adds at most 0.3 ns here.

3. One-core bandwidth by level, CPU 2

  • L1 read 57.6 GB/s is 28.8 bytes per cycle at 2 GHz (bandwidth-dram-1core.csv:7). Write is 30.6 to 32.0 GB/s at every size, 15.3 to 16.0 bytes per cycle at 2 GHz (bandwidth-dram-1core.csv:11 to 86), so the store path, not the memory, sets the one-core write rate.
  • Reads inside L2 already fall: 17.5 GB/s at 48 KiB and 12.1 at 96 KiB, both within the 128 KiB L2 (latency-dram-small.csv:39 to 41 show 0.002 L2 refills per load at 96 KiB). Beyond L2: 10.1 at 256 KiB, 9.3 at 2 MiB, 9.2 at 32 MiB. The SLC and DRAM regimes read the same, although their latencies differ by 2.2 times. Hypothesis: a rate limit in the core or DSU near one 64-byte line per 14 cycles, not a limit on outstanding requests: with a fixed number of outstanding requests the 2.2 times shorter SLC latency would give 2.2 times the bandwidth, and by Little's law the core holds 3.5 lines in flight at 24 ns against 7.5 at 52.3 ns. The OCM read rows (section 4) reach 16.6 GB/s from one core, so the mesh can deliver more. A measurement that would settle it: the mesh counters for SLC hits and memory requests around the 2 MiB read row.

5. Problems in run 1 and the fix for run 2

5a. OCM rows timed without a flush first (Jesse's note)

Jesse is right that three row kinds break the README's sentence "every timed OCM pass starts with a flush". The three differ in what they cost us.

  • All-five fresh latency (run_asimov.sh:113). Harmless. It was meant as the unflushed comparison, and it read 25.2 ns against 25.5 ns flushed with 0.99 refills per load. At 1.25 MiB the core caches cannot hold the chain. Fix: give it --flush as well, so every OCM row obeys the rule and the row becomes the fresh-plus-flushed form that section 5b needs anyway.
  • All-five read, 4 passes, no flush (run_asimov.sh:128). Harmless and redundant: 16.4 GB/s against 16.0 GB/s for the flushed single pass. Fix: drop the row.
  • Write rows, flushed after (run_asimov.sh:126 and :147). wrong number The timed region holds the stores plus the DC CIVAC of the buffer (bandwidth.c:248 to 254). The one-core store rate is 32 GB/s at every footprint, so the stores take 8.2 us for 256 KiB whether or not the warm-up pass left the lines in the core caches (not measured). The row took 36.5 to 36.6 us (262,144 bytes at 7.16 to 7.18 GB/s, bandwidth-ocm-write.csv:4 to 6; the elapsed_s column prints 37 us at 1 us resolution). The remaining 28.3 to 28.4 us is the flush of 4,096 lines, 6.9 ns per line (est.). So 7.2 GB/s is the rate of stores into the core caches followed by a serial DC CIVAC write-back of 256 KiB to OCM, not a streaming OCM write rate; the data cannot say how much of the 28 us is the instructions and how much the write-back itself. The 4-core write row (29.2 GB/s, 7.3 per core) has the same defect, and the copy row (12.0 GB/s, 44 us) is about 16 us of loads from OCM 1 and about 28 us of this flush of OCM 2 (est.).

Fix for the write rows: measure streaming writes whose footprint exceeds the core caches, so the lines reach OCM by eviction during the timed passes, as the DRAM write rows do. Only the all-five buffer (1.25 MiB) is large enough: bandwidth --threads 1 --cpus 2 --mem ocm --ocm-regions 0,1,2,3,4 --bytes 1280K --kernel write --flush-before --passes 4 --reps 3. The copy kernel cannot use this form: it needs two buffers of five regions and only five regions exist (bandwidth.c:199 to 215 exits with an error), so the OCM copy row is dropped; a 512 KiB copy over regions 0 to 3 would be the only alternative, and its destination is just 1.3 times the core caches. The per-region write cannot be measured this way from one core, since 256 KiB fits the core caches; drop it, or keep the flush-after row with its label changed to "store then DC CIVAC". The 4-core OCM write row has the same limit and should be dropped.

5b. Prefetched lines in every 256 KiB flushed row

All flushed rows with 4,096 lines count 0.77 to 0.91 L3 read refills per load (latency-dram-flushed.csv:4 to 6, latency-ocm-region0.csv:4 to region4.csv:6), while rows with 16,384 lines or more count 0.99 to 1.00. The chain in these rows is chain 0, which the warm-up walked twice and each repeat walks again. A prefetcher that records the miss sequence can replay part of it after the flush. The same effect was measured on CRB (crb-validation/.../latency-dram-flushed.csv:4 to 6, 0.15 to 0.38 L1 refills per load). Fix: use --fresh 3 --flush for every flushed row, so each timed pass walks a chain that has never been walked. latency.c already supports the pair: timed_walk flushes before each fresh chain (latency.c:87 to 88). Expected sign of success: 1.00 refills per load in the per-region rows, and the per-region latencies rise by 1 to 3 ns (est.).

5c. Flushed DRAM rows measure DRAM

The flushed rows at 1 to 8 MiB read 52.7 ns, the DRAM value, with 1.00 refills at every level. DC CIVAC removed the lines from the SLC as well. The row cannot stand for an SLC hit. Keep one such row (8 MiB) as the DRAM reference and drop the rest; the fresh chains already give the SLC.

5d. Scratchpad

Phase C was skipped because /dev/asimov-spm does not exist on this image. The script handles that (run_asimov.sh:88 and :151). The README still describes the SPM rows; mark them postponed.

6. Run 2: what changes

  1. Phase B: every OCM latency row becomes --fresh 3 --flush (rows 110 to 113 of run_asimov.sh). Add the same five per-region rows from CPUs 4, 6 and 8, so the hop count is measured from four of the five DSUs (DSU 0 holds the kernel CPUs 0 and 1): 20 rows of 256 KiB, about 4 ms of chip time each (est.), under 0.1 s in all.
  2. Phase A: the flushed DRAM rows shrink to 8 MiB only. The 256 KiB flushed row goes, since 5b explains it.
  3. Phase D: drop the unflushed 4-pass all-five read; replace the write row by the 1.25 MiB streaming form with --flush-before --passes 4; drop the copy row.
  4. Phase E: drop the 4-core OCM write row. Keep the 4-core read row.
  5. sysinfo: add CONFIG_DEBUG_FS to the config grep, a debugfs mount attempt and cat /sys/kernel/debug/arm-cmn/map, cat /sys/bus/event_source/devices/arm_cmn_0/cpumask and ls /sys/bus/event_source/devices/arm_cmn_0/events. Negligible chip time (est., under 1 ms), and the map confirms the crosspoint layout.
  6. README: SPM marked postponed, the OCM flush sentence corrected, the new rows described.

No C change is needed for these, because the OCM copy row is dropped (the 1.25 MiB copy form would need a bandwidth.c change). Chip time stays near 1.3 s (est.): the added OCM rows cost under 0.1 s and the dropped rows save about as much. Cores needed: 2 to 9 online, CPU 3 offline for the single-core phases as before. Huge pages: 256 as before.

7. Questions for Jesse before run 2

  1. Is CONFIG_DEBUG_FS in the kernel, and can debugfs be mounted so that /sys/kernel/debug/arm-cmn/map prints the mesh? One line: zcat /proc/config.gz | grep DEBUG_FS; mount -t debugfs none /sys/kernel/debug; cat /sys/kernel/debug/arm-cmn/map. The map shows the crosspoint of every home node and DSU port, which checks the one-hop and three-hop statement against the RTL at no chip cost.
  2. Which mesh events does arm_cmn_0 list, and is the perf tool in the image? ls /sys/bus/event_source/devices/arm_cmn_0/events | grep -E 'pocq_reqs_recvd|mc_reqs_local|slc_sf'; which perf. With these, run 3 can count SLC hits and memory requests per home node around a row, which settles the read-bandwidth question of section 3.
  3. For the OCM lock: is each region a plain locked range (hnf_slc_lock_ways and lock_base) or the CMN OCM mode? The TRM says a CleanInvalid of an OCM-mode line does nothing in the SLC, while a locked line in a normal range can be pushed to memory by a non-allocating request. Run 1 shows DC CIVAC keeps OCM data (every flushed OCM row reads 18.8 to 26.0 ns, not 52 ns), so the question is only about interpretation, not safety.

8. Open items, insufficient data

  • L3 hit latency: not isolated (section 1). Needs a 144 KiB and 160 KiB chase, or a DSU L3 hit counter.
  • Per-hop cost on the mesh: the per-region rows carry prefetched lines (section 5b). Run 2's fresh-plus-flushed rows from four DSUs give it.
  • Why one-core reads beyond L2 stop at 9.2 GB/s while OCM reads reach 16.6 GB/s: hypothesis only (section 3). Needs mesh counters.
  • OCM write bandwidth: no valid number yet (section 5a). Run 2's streaming row gives it.
  • Whether the C1-Nano learns a repeated chain the way the V3AE on CRB does: the 256 KiB flushed rows say partly yes (0.09 to 0.23 of lines prefetched). Run 2's fresh rows confirm it if their refills read 1.00.
