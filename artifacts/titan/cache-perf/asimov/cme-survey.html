Asimov C1-Nano CME: what Positron has, what is measured, what to measure next

Survey written 2026-11-02 from the RTL repo, the Arm documents in the Arm IP delivery, the public Arm guides, the firmware repos and the asimov-bench measurements. Every number cites its file.

Short version. The CME is Arm's C1-SME2 unit (Arm code name Griffin), one per DSU, shared by the DSU's two C1-Nano cores, built in the half-rate matrix configuration with a 512-bit streaming vector length. Positron's asimov-bench team already measured its peak on the emulator in October 2026: one FMOPA every 2.04 cycles (251 MAC/ns FP32, 502 MAC/ns BF16), which is 98 % of the half-rate ceiling. What is still unmeasured is the part that matters for a kernel: int8 rates, operands from the SLC, OCM and DRAM under load, two cores with memory operands, all five DSUs at once, and a real matrix multiply.

1. Words used here

CME
Compute Matrix Engine. Positron's name (and Arm's register-level name) for the Arm C1-SME2 unit, the block that executes SME and SME2 instructions. Arm code name: Griffin.
SME, SME2
Scalable Matrix Extension, versions 1 and 2. Arm instructions for outer products into a tile register (ZA) and multi-vector operations.
Streaming mode
The CPU state (PSTATE.SM = 1, entered with SMSTART) in which SVE instructions run on the CME at the streaming vector length instead of on the core's own vector unit.
SVL
Streaming vector length: the vector width in streaming mode. 512 bits (64 bytes) on Asimov. The core's own SVE length is 128 bits.
ZA
The CME's tile storage: SVL x SVL bits = 4 KiB, viewed as four 16 x 16 FP32 tiles (ZA0 to ZA3).
FMOPA, BFMOPA, UMOPA, SMOPA
Outer-product-and-accumulate instructions: FP32 in, FP16 or BF16 in (FP32 out), unsigned int8 in, signed int8 or int16 in (int32 out).
MAC
One multiply-accumulate. One FP32 FMOPA at SVL 512 is 16 x 16 = 256 MACs; BF16 or FP16 input is 512 MACs; int8 input is 1,024 MACs.
MMDP
Matrix multiply data path. The CME PMU event CME_OP_MMDP_ISSUE counts outer-product issues to it.
Half matmul
The Arm build option FULL_MATMUL = FALSE. Arm's own test comments give the rate: half matmul executes one FMOPA per 2 cycles, full matmul one per cycle.
DSU
Arm DynamIQ Shared Unit, the two-core cluster (code name Pilatus) with its L2, L3 and one CME. Asimov has five per hemisphere.
Nevis, Pilatus, Griffin
Arm code names for the C1-Nano core complex, the C1-DSU and the C1-SME2 unit, as used in the RTL folder names.
PPU
Power Policy Unit. Each CME has one. It must be set to dynamic mode by the SCP firmware before any streaming instruction, or the issuing core stalls forever.
SOG
Arm Software Optimization Guide: the public document with per-instruction latency and throughput.
llvm-mca
LLVM's machine code analyzer. Its C1-Nano model (public) encodes the CME pipelines and throughputs that Arm gave LLVM.
Boot M2, boot M3, Spokane request 1504/1511
Names of the October 2026 emulator runs of the asimov-bench team that measured the CME.
Emulator
The Palladium model hemi_rtws_tlm that Jesse Zhang runs: real C1 and CME RTL, 2 GHz core clock, about 2,779 wall seconds per chip second.

2. What the CME is on Asimov

Facts, each with its source:

  • One CME per DSU, two C1-Nano cores per DSU. NUM_CORES 2, NUM_CME 1 [ip/c1/logical/C1_DSU_DynamIQ_Cluster_1/pilatus/logical/config/C1_DSU_DynamIQ_Cluster_1.yaml:29,33 in Positron-AI-TSMC/asimov at 0d9e214, the RTL of the run 1 image]. CME_NUM_CPUS 2 [griffin0_cme_channels_pkg.sv].
  • Half matmul. FULL_MATMUL: FALSE [same yaml:473]. Arm's max-power test selects the half-matmul loop when IMP_CMECFR_EL1 bit 2 is 0 and comments the rates: full "4 iterations of 4 FMOPA per cycle: target 16 cycles", half "2 iterations of 4 FMOPA each, each executing in 2 cycles: target 16 cycles" [griffin/logical/testbench/execution_tb/tests/aarch64/maxpwr_cme/maxpwr_cme_asm.s:175-189,277]. The Arm floorplan example in the delivered guide is "Griffin 9cpus, half matmul" [arm_c1_sme2_iBEP_User_Guide.pdf p11].
  • SVL 512 bits. CME_SVL 512, CME_SVLB 64 [griffin0_cme_channels_pkg.sv]; firmware boot spec 7.3.3 says the same; the October probe read 64 B with RDSVL [asimov-bench engines/cme.py docstring].
  • Supported element types (ID_AA64SMFR0_EL1 read on the emulator): F32F32, B16F32, F16F32, I8I32, I16I32 present; F64F64, I16I64, B16B16, F16F16 absent; FA64 absent, so no Advanced SIMD in streaming mode [engines/cme.py docstring; run 1 cpuinfo shows the same hwcaps: sme smei8i32 smei16i32 smef16f32 smeb16f32 smef32f32 smebi32i32].
  • Version. C1-SME2 r1p3-00rel0 [griffin0_cme_channels_pkg.sv header]. Core: C1-Nano, CPU part 0xd8a revision 3 [run 1 sysinfo.txt].
  • The emulator contains the real CME RTL. The hemisphere build's setup script swaps the Griffin clock-gate cells, which only matters if Griffin is compiled in [emu/hemi_tlm/scripts/setup_tree.sh:967-969]; the DSU file list includes 455 griffin files [design/css/cmn/cdc/qualified/C1_DSU_DynamIQ_Cluster_1.f].
  • Own PMU. The CME has 31 counters, 16-bit event numbers [CME_PMU_CNT_NUM, CME_PMU_EVENT_WIDTH in griffin0_cme_channels_pkg.sv]. Linux reaches CME events through the core PMU with raw event numbers (section 5).
  • Issue bandwidth from the core. "The CPU has a maximum bandwidth of three instructions to the C1-SME2 unit. With the use of MOVPRFX fusion this can be increased to four." Loads and stores: two per cycle. SMSTART and SMSTOP are single-issue [Arm C1-Nano SOG 109590_0001_04 section 2.33].
Safety rule for every SME test. The CME PPU resets in static mode. "A core issuing SSVE against a static/off CME PPU stalls until the PPU is reprogrammed" and there is no rescue path on the SoC [firmware_boot_spec.md, "CME (SME2 unit) PPU" section]. The SCP firmware arms the PPU on every core-ON [asimov-scp-firmware mod_asimov_system.c, asimov_system_enable_cme_dynamic, commit 32658a4c of 2026-07-06]. That function is present in scp-v0.34.0, the firmware of run 1 [checked at the tag; run 1 README line 19]. The asimov-bench CME runs on this emulator confirm it works. Any image with older SCP firmware would hang on the first SMSTART.

4.3 Measured with the CME counters (dpa/stress, Palladium, 2026-10-14 and 15)

  • Arm's half-matmul max-power loop ported verbatim to user space: CME_OP_MMDP_ISSUE / CME_CYCLES = 0.3455 on all 5 workers [FORMAT.md section 6.4, Spokane request 1504]. That is 69 % of the 0.5 ceiling. The bench authors attribute the gap to the in-order C1-Nano front end: about 44 instructions per 8 FMOPA at an IPC of 1.9 [kernels.h, cme_fmopa_fit comment].
  • The same loop re-balanced for the front end (8 FMOPA + 8 LD1B + 12 FMLA per loop): 0.4916 to 0.4922, 98 % of the ceiling [request 1511].
  • CME_CYCLES / CPU_CYCLES = 0.9993: the CME stays allocated to the core for the whole window.

So two independent methods (timer and counters) agree: a single core can keep the half-rate CME at 98 % of its ceiling with register operands or L1 operands, if the instruction stream is arranged for the in-order front end.

5. How to measure: the method that already works on this emulator

  • Build. Hand-written assembly with .arch armv9.3-a+sve2+sme+sme2 in its own file, called from C compiled with Jesse's flags (-O2 -mcpu=cortex-a520 -static, GCC 14.2 of the asimov-os SDK). The bench team did exactly this [dpa/stress/src/kernels/k_cme.S]. Keeping SME out of the C files avoids the compiler emitting streaming instructions in code that runs before SME is enabled. The CRB (gcc 14.2) can compile-check the binary; it cannot run it (Neoverse V3AE has no SME).
  • Timing. CNTVCT (1 ns per tick, 2 cycles) around 4,096-instruction loops; median of 5 repetitions; subtract the 25 ns empty timer pair [engines/cme.py, MEM_LOOP].
  • Counters. perf_event_open on the core PMU with raw event numbers (12 fit in one group; the RTL has 20 core counters): 0x11 CPU_CYCLES, 0x08 INST_RETIRED, 0x3246 CME_CYCLES, 0x3264 CME_OP_MMDP_ISSUE, 0x3261 CME_OP_MAC_ISSUE, 0x324B and 0x324C CME_STALL_FRONTEND_*, 0x3213 CYCLES_CME_ALLOC, 0x835E SME_INST_SPEC, 0x8376 SME_FP_MOPA_SPEC, 0x837E SME_INT_MOPA_SPEC, 0x32A8 SSVE_CONTEXT_SWITCH [dpa/stress/src/counters.c:33-35; names in FORMAT.md section 6.2]. Our cache-mem-perf common.h already has perf_open for the core PMU; it needs only the event list.
  • Rules inside a timed region. No system call and no signal (a syscall clears PSTATE.SM, a signal handler runs with SM = 0 and ZA = 0) [dpa/stress/src/sme_ctx.S header, citing Linux Documentation/arch/arm64/sme.rst]. No Advanced SIMD (FA64 absent). The first SMSTART of a thread traps once; run one untimed pass. Save d8 to d15 and FPCR around SMSTART/SMSTOP (they zero the vector state). A CME test on one core of a pair while the partner core runs SVE code shares the VPU but not the CME; two SME cores on one DSU share the CME.
  • Cost. One 4,096-instruction row is about 4.2 us of chip time; one thousand rows are 4.2 ms, or about 12 s of wall time at 2,779x. A full CME sweep is far cheaper than the cache benchmarks (run 1 used 1.24 s of chip time).
  • Configuration check in the program. RDSVL must return 64; print ID_AA64SMFR0_EL1 (Linux emulates the read at EL0). IMP_CMECFR_EL1 (full or half) is not readable at EL0; rely on the RTL yaml.

7. Open questions for the design team and Jesse

  1. Where are the delivered Arm C1-SME2 TRM (107831), the CIM (107832), the C1-DSU TRM (107804) and the SME SWOG (111048)? They are not in any repo I can read. The SWOG is the source of the per-instruction CME numbers, the TRM lists the CME PMU events, and the CIM defines what FULL_MATMUL changes.
  2. Is half matmul final for silicon? The config file, the firmware spec and the SW architecture notes all say half rate; this doubles or halves every peak number.
  3. Can the gemm_bf16_sme2 testbench sources be checked in or shared? Only their Makefile.inc is in the tree.
  4. For row 4, may both cores of DSU0 (CPUs 0 and 1, the kernel's cores) run a worker, or do we stay on CPUs 2 to 9? Run 1 isolated CPUs 2 to 9 only.
  5. Is any kernel planned to run on the CME at all? The bench notes say "No flown Program uses it." If the answer is no, rows 1, 2 and 6 are enough to document the engine.

9.1 Test code written (not yet run on the emulator)

Phase F of cache-mem-perf repeats the phase A, B and D rows through the CME from CPU 2 with the same chains, footprints and flush rules, so each CSV row has a C1-Nano twin:

  • cme_kern.S: streaming-mode chase (LD1D + LASTB), a register round trip with no memory access (DUP + LASTB, the floor under every CME hop), read, write and copy with LD1B/ST1B of four vectors (256 B per instruction) and of one vector (64 B).
  • latency --cme and bandwidth --cme switch the engine; --perf with --cme counts CME_CYCLES, CME L1D refills on read and CME bus reads through the core PMU.
  • cme_test.c checks every kernel against a scalar reference. It passes under QEMU 11.1.3 user mode with SME2 (SVL 64 B); the first run caught a partial-fold bug in the read kernels, since fixed. The programs build with Jesse's flags on the CRB (GCC 14.2) and refuse to run where SME2 is absent.
  • Chip time of phase F: about 0.4 s (est.), dominated by the chase rows at about 22 ns per hop.
