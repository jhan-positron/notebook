Short version. Boot A repeats run 3 and its counters show that the fills above one per load on the sparse OCM chains are hardware prefetches, which boot B confirms with the prefetchers off while its hit counters show that the DSU L3 of CPUs 2 to 9 held no data on runs 1 to 4 (sections 4 to 11). Boots C and D map the OCM in 64 KiB translations: the L1 TLB refills fall from 21 to 599 per pass to 11 to 15, and the OCM rows gain 1.5 % by geometric mean with the prefetchers off (section 13). Boot E turns the L3 on through a rebuilt SCP: the 192 to 384 KiB chases fall to 7.8 to 10.9 ns (an L3 hit costs about 10.8 ns est.), the plain one-core read of 32 MiB rises from 9.2 to 24.5 GB/s, and the dense all-five OCM row stays at 26.1 ns (sections 14 and 15).

1. Words used here

C1-Nano, DSU
The Arm core and its two-core cluster (DynamIQ Shared Unit). The hemisphere has 5 DSUs, CPUs 0 to 9. Device interrupts are routed to CPUs 0 and 1 (irqaffinity=0-1); the scheduler places no unpinned task on CPUs 2 to 9 (isolcpus=2-9) and their periodic tick stops while one task runs (nohz_full=2-9). The init started run_all.sh pinned to CPU 2, so the scripts, the shell and the counter helper ran on CPU 2 (cmncount sets no affinity of its own) and each measured program pinned itself to its --cpu. Every core takes its own timer and per-CPU interrupts, and a program's page faults and system calls run on its own core [Jesse's run 3 README, The run and CPU placement].
L1, L2, L3
32 KiB data cache per core, 128 KiB per DSU, 256 KiB per DSU, 64-byte lines [sysinfo.txt]. On this run, as on runs 1 and 2 and run 4 boots A to D, the L3 of CPUs 2 to 9 was in snoop-filter-only mode and held no data: the stock SCP firmware stages the full L3 for cluster 0 only, and run 4 boot B's hit counters read 0 L3 hits per load. There is no L3 level in these numbers; run 4 boot E turned the L3 on [asimov-c1nano-run4.html, sections 11.1 and 14].
mesh, crosspoint (xp)
The Arm CMN S3 interconnect, a 6 by 6 grid of routers. Distance between two points is the number of crosspoint steps, |dx| + |dy|.
home node (HN-S), SLC
The five mesh nodes that own all addresses, each with 1 MiB of System Level Cache in 16 ways. A DRAM address belongs to one home node by a hash, so a buffer spreads over all five.
OCM
On-Chip Memory: 4 of the 16 ways of each home node, locked as 256 KiB of memory at 0xE0000000 + n MiB. Region n lives in home node n only. Reached through /dev/ocm in 4 KiB pages.
node id
The mesh id of a home node (88, 160, 216, 288, 344). Its bits give the crosspoint: x = bits 8 to 6, y = bits 5 to 3.
chase
A pointer chase: each load reads the address of the next load, so the loads cannot overlap and the time per load is the load-to-use latency.
repeated chase, fresh chain, flushed
Repeated: a random chain walked many times, so later walks hit whatever cache holds it. Fresh: a chain walked once. Flushed: every line was cleaned and invalidated from the caches with DC CIVAC first.
boot A to E
The five boots of run 4 (round four). A is the run 3 platform (sections 1 to 10); B has the data prefetchers of CPUs 2 to 9 and their CMEs turned off (section 11); C maps the OCM in 64 KiB contiguous translations with the prefetchers on, and D with them off (section 13); E is boot C's program and platform with the OCM back in 4 KiB pages and a rebuilt SCP that turns the L3 on (sections 14 and 15). The CME page gives the CME side (its sections 8 and 9).
contiguous hint
The contiguous bit of a translation entry, which marks 16 neighbouring 4 KiB entries as one 64 KiB block; the TLB then holds the block as one entry (two 32 KiB entries in the core's L1 data TLB). Boots C and D load /dev/ocm with cont=1 and every mapping line reads cont=64/64 [dmesg.txt of 007 and 008; Jesse's boot C README, OCM mappings].
walk events
0x34 translation table walks (data side), 0x8188 walks that ended in a block entry and 0x818A walks that ended in a page entry [C1-Nano TRM, event list], run on the TLB-set chains of boots C, D and E (the -walk-cpu2.csv files).
L3 full mode (operating mode 7)
The DSU cluster operating mode with all L3 slices and the whole L3 RAM open to lookup and allocation; IMP_CLUSTERPWRSTAT_EL1 reads 0x70 in it. Boot E's SCP (0.48.0-nopcie-l3.1) stages it for the clusters of CPUs 2 to 9; the stock SCP stages it for cluster 0 only.
G8 rows, looped and single-call forms
Run 5c's one-core L1 rows on boots C and E: a read and a write of 4, 8, 16 and 24 KiB over many passes, timed in two forms: the looped form, one call of the kernel per pass (bandwidth-l1-passes.csv), and the single-call form, all passes of a rep inside one assembly call (bandwidth-l1-asmpasses.csv, header asm_passes=1). Read with l1_reader.py.
geometric mean
The n-th root of the product of n ratios: the average ratio when rows are compared as ratios, so one row at half the time and one at twice the time average to 1.
prefetch-refill events
Three core PMU events added in run 4 beside run 3's three refill events: 0x81BC (L1 data cache refills a hardware prefetcher requested), 0x81BD (L2 refills for accesses generated by hardware prefetchers targeting the L2) and 0x0111 (L2 refills for accesses from the L1 data prefetcher) [C1-Nano TRM, event list]. Each is reported per load of the timed pass, beside 0x03 (L1 refills), 0x17 (L2 refills) and 0xA2 (L3 read refills).
TLB events
0x05 L1 data TLB refills (counts refills that hardware prefetches caused too), 0x2D L2 data TLB refills (excludes hardware prefetches) and 0x34 translation table walks (walks caused by a miss in the L2 TLB driven by a memory access) [C1-Nano TRM, event list]. Run on the CPU 2 OCM rows with run 3's three refill events.
CME refill events
0x3280 CME L1 refills caused by load instructions (demand reads), 0x32B2 refills by the CME's hardware prefetcher, 0x3281 refills caused by stores [C1-SME2 TRM, event list], beside run 3's 0x327D (refills from inside the cluster, inner) and 0x327E (from outside, outer).
dense, sparse, vary
Three chain shapes over one 256 KiB OCM region. Dense: every line of the region, 4,096 loads per pass (run 2's chain). Sparse: one line per 4 KiB page at one fixed line offset, 64 loads per pass (run 3's chain). Vary: one line per page at a line offset that changes from page to page, 64 loads per pass (new in run 4).
sequential chain
New in run 4: a chain whose members are the lines in address order, 8 MiB, every line flushed first. It is the stimulus a hardware prefetcher is built for, so it shows whether the prefetch events count at all.
route rows
Phase G6: the dense chase of each of the 20 CPU-to-region cells run again under the mesh's crosspoint counters (mxp__dat_txflit_valid, dir = e, w, n, s) on the crosspoint of the CPU's DSU and on the crosspoint of the region's home node. The events count transmitted data-channel flits over the whole command.
data flit
One unit of the mesh's data channel. Read requests travel on a different channel (the request channel), which G6 does not count.
X-first
A route that takes its horizontal (X) crosspoint steps before its vertical (Y) steps. Used here as the direction a route's first link would have if the mesh routed that way.
mapping alignment
Each /dev/ocm mapping places a 256 KiB region at a user address the kernel chooses. The difference between the user and the physical address is a multiple of 16, 32 or 64 KiB on some mappings and of 4 KiB only on the others [dmesg.txt, membench_ocm lines]. A TLB entry that merges neighbouring 4 KiB pages needs the two addresses to share that alignment [Jesse's run 4 README, OCM mappings].
snoop-filter-only mode (SFONLY)
A DSU L3 state in which the L3 RAM holds no data and the L3 only keeps the snoop filter (the record of which lines the cores hold). The cluster power status register IMP_CLUSTERPWRSTAT_EL1 reads 0x0 in it. In this state every L2 miss goes to the mesh (SLC, OCM or DRAM).
L2 and L3 hit events
Run 5's hit set on the 64 KiB to 512 KiB chases: 0x81C5 L2 read hits, 0xA0 L3 read accesses and 0x81C6 L3 read hits per load, beside the three refill events [latency-dram-small-l3.csv].
PRFM
The AArch64 prefetch-memory instruction (PRFM PLDL1KEEP): a software hint that fetches a line into the L1 without using it. The read variants issue it 4, 8 or 16 lines ahead of the load.
H1 to H7
The hypotheses of follow-up-run-plan.md section 5 and 10, each with the row that decides it. H1: the fills above one per load are prefetches. H2: the sparse chain's fixed line offset is what a prefetcher reacts to. H3: a sparse pass takes one L1 TLB refill per load. H4: the page size separates sparse from dense (boot C). H5: an X step costs more than a Y step. H6: the 7.7 to 8.0 ns per pass added to the small write rows in run 3 is the program. H7: the plain read loop keeps too few lines in flight (the run 5 rows, not in boot A).
best, pass, rep
A command walks its chain several times (passes, or reps); best is the fastest. A sparse per-region row has 7 fresh passes, a dense all-five control 2, a repeated chase 3 reps.
refills per load
PMU events 0x03 (L1D refill), 0x17 (L2D refill), 0xA2 (L3D read refill) divided by the loads of the timed walk. 1.00 means one fill of that level per load. A fill can be a demand miss or a prefetch, so the count does not say which loads missed, and a useful prefetch can replace a later demand fill and leave the count near one.
perf_cov
New in run 3: the counter group's running time over its enabled time for the row. 1.0000 means the counters were never multiplexed; every row of this run reads 1.0000.
cmncount
The helper that opens the mesh PMU (arm_cmn_0) around one command and writes cmn-counts.csv: requests received per home node, memory-controller requests and SLC misses.
SCP, TF-A
The System Control Processor firmware (which also sets up the mesh) and Trusted Firmware-A (the boot firmware of the application cores). Run 3 ran SCP 0.48.0-nopcie.1 and TF-A 0.35.0, the same as run 2 [Jesse's run 3 README].
chip time
Time as the emulated chip sees it. One chip second took 2,776 wall seconds in run 3 [Jesse's run 3 README].
est.
An estimate, not a measurement.

2. The run and the platform

  • Where and when. One emulated Asimov hemisphere on the GA13 Palladium (image hemi_rtws_tlm, RTL 0d9e214, release a10280100), 2026-11-04 UTC, as one job: run_followup.sh at commit e8e4580. 2.830 s of chip time against the 3.0 s estimate; 105 commands, all exit 0 (0 failed); 103 files back with matching checksums [Jesse's run 4 README, The run; SHA256SUMS checked here].
  • Platform. Run 3's: the same image copy, SCP 0.48.0-nopcie.1 and TF-A 0.35.0, Linux 6.18.36, 256 huge pages of 2 MiB, CPUs 2 to 9 isolated, CPU 3 offline for the whole script. /dev/ocm maps the regions in 4 KiB pages as before and now logs each mapping [Jesse's run 4 README, Read first]. The PMU driver reports 21 counters (20 event counters and the cycle counter), so no group of six events was multiplexed: every row reads perf_cov 1.0000 (641 counted rows) and no row carries a "# perf:" flag.
  • Controls (criterion G-e). The 4 KiB repeated chase reads 2.002 ns (4.01 cycles) against run 3's 2.002; the CME round trip reads 21.004 to 21.006 ns in its 63 reps against 21.00. Both are within 0.5 %, so the boot is run 3's as far as these two numbers can tell. The two uncounted 4 KiB controls read 2.017 ns (CPU 2) and 2.016 ns (CPU 8).
  • What this boot alone cannot answer. Every comparison across boots (prefetchers off, 64 KiB translations, the L3 on) needs boots B to E, which sections 11 to 15 carry. Run 5's additions (the L2 and L3 hit set, the one-core read variants, the walk rows, the G8 rows) came after e8e4580 and are not in boot A's data.

  • The prefetch events count. On the sequential chain every L1 refill was requested by a hardware prefetcher (0x81BC 0.9999 per load beside 1.0000 L1 refills) and every L2 refill came from the L1 prefetcher's requests (0x0111 0.9999 beside 1.0000 L2 refills). 0x81BD (prefetchers targeting the L2) reads 0.0001 there and up to 2.98 per load on the OCM rows, so it counts; the sequential chain is served by the L1 prefetcher, not by one targeting the L2.
  • The TLB events count. On the 32 MiB chain on 4 KiB pages: 0.996 L1 TLB refills, 0.521 L2 TLB refills and 0.521 walks per load, at 58.8 ns per load against 52.2 ns for the same footprint on 2 MiB huge pages. hypothesis The L2 TLB refill and the walk count agree to the fourth digit on that row, so on this chain every L2 TLB miss walked and every walk refilled the L2 TLB; the 48 % of loads with an L1 TLB refill but no L2 TLB refill hit in the L2 TLB.
  • The L3 read refill event does not count prefetch fills. On the sequential chain the L2 refills are 1.0000 per load but the L3 read refills 0.0001, although every line came from outside the DSU (it was flushed). hypothesis Either the L1 prefetcher's fills do not allocate in the L3, or 0xA2 counts demand reads only; the TRM text ('level 3 accesses that receive data from outside the L3 cache due to a memory-read operation') does not say which. On the random chains 0xA2 therefore counts the loads that missed the L3, not every line that entered the DSU.

6. OCM latency by cell: three chain shapes, three runs

  • What the split says (H1). supported On every OCM row the L2 refills that 0x81BD does not count equal the L3 read refills within 0.02 per load (table 3.4, last column). So the fills above one per load that run 3 saw are refills a hardware prefetcher targeting the L2 made, and the L1 prefetcher made none (0x81BC and 0x0111 read at most 0.0000 on these rows). This is agreement between two counts on boot A; whether removing the prefetcher changes the chase time is boot B's question.
  • The prefetched lines are partly used. The L3 read refills are 0.74 to 0.96 per load on the sparse rows and 0.82 to 0.92 on the dense ones, while every load misses the L1 (1.02 L1 refills per load or more). hypothesis The loads that did not refill the L3 hit a line the prefetcher had already brought into the L2 or L3: about a quarter of the sparse-chain loads and a tenth of the dense ones. A prefetch that lands before the load shortens that load, so the per-load time of these rows is below the OCM service time of an unprefetched load; boot B measures that time.
  • Pass-to-pass. Within a row, a pass's time correlates only weakly with its counts: +0.19 with the prefetch refills (0x81BD), +0.33 with the L2 refills and +0.30 with the L3 read refills (each row's mean removed, pooled over the sparse and vary rows of CPUs 2 and 8). Run 3's sparse rows showed +0.84 with the L2 refills. So on this boot the spread between the passes of one row is not explained by how many lines the prefetcher fetched.
  • Vary against sparse (H2). not supported The vary chain counts more L3 read refills than the sparse chain in 6 of 10 cells, not in all, and its prefetch refills are 1.15 to 1.73 per load on CPU 2 against the sparse chain's 1.81 to 2.22 (CPU 8: 1.54 to 2.98 against 1.11 to 1.85). The prefetcher reacts to both one-line-per-page chains, at rates that differ more between the two CPUs than between the two shapes, so the fixed line offset is not what it reacts to. hypothesis What it reacts to is the page stride itself (one member per 4 KiB page): a stride or spatial prefetcher that sees a load every 4 KiB fetches the next page's candidate lines whatever their offset. The per-prefetcher refill events (0x00D9 to 0x00DB, 0x010F, 0x0110) would name it. The vary chain is nevertheless faster than the sparse chain in 10 of 10 cells by median, by 3.5 ns on average; Insufficient data its cause: the two chains differ in offset pattern, in which prefetched lines are useful, and in their walks (table 3.5), and no row here separates those.

7. Translation activity by chain shape (H3)

  • H3 as stated is not supported. not supported A sparse pass takes 0.67 to 0.72 L1 TLB refills per load, not 1.0, on 64 pages per pass. The dense rows, 4,096 loads over the same 64 pages, take 0.005 to 0.136 per load, which is 21 to 558 refills per pass of 64 pages.
  • Walks without L2 TLB refills. The sparse and vary rows count 0.16 to 1.24 walks per load and 0.000 L2 TLB refills. On the TLB stimulus the two were equal. hypothesis 0x2D excludes refills that hardware prefetches caused and 0x34 counts any walk driven by a memory access [C1-Nano TRM, 0x002D and 0x0034], so these walks are translations for the prefetcher's requests into other pages, which are not installed in the L2 TLB as demand refills; the dense rows, whose prefetches stay within pages the chain has touched, walk 0.015 times per load or fewer. The demand-only walk event 0x813C DTLB_WALK_RW would separate the two.
  • Alignment. 23 of the 110 mappings are 16 KiB aligned or better (table 3.5, second table). Among the 15 TLB rows, 2 had such a mapping: OCM3 vary (16 KiB); OCM4 dense (64 KiB). The one dense row with an aligned mapping (OCM4, 64 KiB) reads 0.005 L1 TLB refills per load; the four with 4 KiB-only mappings read 0.044 to 0.136. hypothesis On the aligned mapping the L1 TLB merged neighbouring pages into fewer entries, so the 64 pages of a region stayed resident. One row is a reading of the table, not a test: the kernel sets the alignment per mapping and the four unaligned rows differ among themselves by a factor of three. Boot C, which asks for larger entries by design, is the test. Insufficient data H4 (boot C): not run.
  • What the TLB rows cost in time. The sparse rows under the TLB set read 23.7 to 25.3 ns best against 22.9 to 27.6 under the prefetch set, the same chains on the same CPU, so the counter set does not change the row.

11.5 The hypotheses on the pair of boots

  • supported H1 (the fills above one per load are prefetches): on boot B the sparse rows count 1.002 to 1.007 L2 refills and 1.011 to 1.022 L3 read refills per load, one line per load, where boot A counted 1.96 to 2.94 L2 refills; the extra fills vanish with the prefetchers.
  • not supported H2 (the fixed line offset is what the prefetcher reacts to): on boot B the vary chain is faster than the sparse one by median in 6 of 10 cells (-0.91 to +0.09 ns), against 10 of 10 on boot A: boot A's vary advantage came from the prefetcher, whose fills were more often useful on the vary chain, not from more prefetches on the sparse chain (boot A counted the same number on both).
  • not supported H3 (one L1 TLB refill per sparse-chain load): 0.42 to 0.76 L1 TLB refills per load on boot B, and the page-table walks fall from boot A's 0.27 to 1.24 per load to 0.00: the walks on boot A were the prefetchers' translations, not the chain's.
  • supported H4 (page size separates sparse from dense): with the OCM in 64 KiB translations the L1 TLB refills fall to 11 to 15 per pass and the sparse-minus-dense gap narrows by mean on both pairs (section 13.2).
  • supported H5 (an X step costs more than a Y step): with the prefetchers off the 20 route cells fit 20.75 + 1.99 ns per X step + 0.95 ns per Y step with 0.09 ns rms, against 0.90 ns rms on boot A; the cells now order by distance.
  • supported H6 (the per-pass write cost is the program): run 3's program is again slower per pass than run 2's on one boot, by 3.1 to 8.3 ns.
  • supported H7 (the plain read loop keeps too few lines in flight): PRFM 4 lines ahead more than doubles the plain loop's rate at both sizes on the prefetcher-off boot (11.4).
