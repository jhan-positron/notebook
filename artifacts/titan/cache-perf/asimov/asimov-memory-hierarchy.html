Asimov Memory Hierarchy

What run 2 of cache-mem-perf (commit 8ae533c) measured on one Asimov hemisphere of the GA13 Palladium emulator on 2026-11-02, drawn on one map of the hemisphere. Data: results/membench-jibin-002/ in this folder, a checksum-verified copy of Jesse Zhang's /home/jzhang/dev/emuMemBenchBox/results/jibin/membench-jibin-002/. Every number comes from the CSV files through gen_hierarchy.py. Written 2026-11-02 by Claude for Jibin Han.

Short version. One core reads its L1 in 2.0 ns, its L2 in 6.1 ns, the mesh cache (SLC) in 23 to 25 ns, OCM in 18.5 to 24.7 ns by mesh distance, and DRAM in 52 ns, and the mesh counters confirm which home node holds each OCM region.

Four or eight cores write DRAM at 128 to 155 GB/s on the new firmware (SCP 0.48.0), against 87 to 89 GB/s on run 1's firmware in both run 1 and the control run, so the firmware caused that change (one core writes 32 GB/s, and two cores in one DSU share 41 GB/s on both).

Every other shared number agrees across the three runs within 5 %, most within 1 %, and the one remaining defect is that the 256 KiB per-region OCM rows still contain prefetched lines (a sparse-chain fix is written for run 3 and not yet run).

1. Words used here

C1-Nano, DSU
The Arm core and its two-core cluster (DynamIQ Shared Unit). The hemisphere has 5 DSUs, CPUs 0 to 9. CPUs 0 and 1 (DSU 0) run the kernel. CPUs 2 to 9 are isolated for tests.
L1, L2, L3
32 KiB data cache per core, 128 KiB per DSU, 256 KiB per DSU, 64-byte lines [sysinfo.txt].
mesh, crosspoint (xp)
The Arm CMN S3 interconnect, a 6 by 6 grid of routers. Distance between two points is the number of crosspoint steps, |dx| + |dy|.
home node (HN-S), SLC
The five mesh nodes that own all addresses, each with 1 MiB of System Level Cache in 16 ways. A DRAM address belongs to one home node by a hash, so a buffer spreads over all five.
OCM
On-Chip Memory: 4 of the 16 ways of each home node, locked as 256 KiB of memory at 0xE0000000 + n MiB. Region n lives in home node n only. Reached through /dev/ocm in 4 KiB pages.
node id
The mesh id of a home node (88, 160, 216, 288, 344). Its bits give the crosspoint: x = bits 8 to 6, y = bits 5 to 3.
RN-F port
The crosspoint where a DSU joins the mesh (the map prints RN-F_E_E).
SBSX
The mesh bridge toward a memory controller. DRAM on this image is an emulator memory, not LPDDR5X.
fresh chain, flushed
A random pointer chain walked exactly once. Flushed means every line was cleaned and invalidated from the core caches with DC CIVAC first.
DC CIVAC
The Arm instruction that cleans and invalidates one cache line by address.
PMU
The core's Performance Monitoring Unit, its hardware event counters.
SCP, TF-A
The two firmware components that boot and configure the chip: the System Control Processor firmware (SCP, which also sets up the mesh) and Trusted Firmware-A (TF-A, the boot firmware of the application cores).
debugfs
The kernel's debug file system. The arm-cmn driver prints the mesh map there.
RTL, asimov-bench
RTL is the chip's hardware design source, the emulator runs a build of it. asimov-bench is Positron's earlier pre-silicon benchmark repository.
refills per load
PMU events 0x03 (L1D refill), 0x17 (L2D refill), 0xA2 (L3D read refill) divided by the loads of the timed walk. 1.00 means every load missed that level.
cmncount
The helper that opens the mesh PMU (arm_cmn_0) around one command and writes cmn-counts.csv: requests received per home node, memory-controller requests and SLC misses.
chip time
Time as the emulated chip sees it. One chip second took 2,779 wall seconds (Jesse's README).
est.
An estimate, not a measurement.

13. What is settled, what is open

  • settled The home node of each OCM region, by counter: 88, 160, 216, 288, 344 for OCM0 to OCM4, at crosspoints (1,3), (2,4), (3,3), (4,4), (5,3) [cmn-counts.csv, sysinfo.txt].
  • settled OCM and SLC latency follow mesh distance, and each DSU's mean distance orders the per-core SLC latency [tables 3.2 and figure 6].
  • settled A flushed DRAM line is read from DRAM (52.7 ns, 1.00 L3 refills), and one core's streaming OCM write is 20.4 GB/s [latency-dram-flushed.csv, bandwidth-ocm-write.csv].
  • settled The counters cost the measured command under 5 % and did not multiplex (running time equals enabled time on every row) [cmn-counts.csv].
  • open The 256 KiB per-region rows still count 0.76 to 0.95 L3 read refills and 1.11 to 1.45 L2 refills per load, as in run 1 [latency-ocm-region*-cpu*.csv]. So fresh chains did not remove the prefetched lines. In 19 of 20 rows the faster pass is the one with fewer L3 refills. Hypothesis: a prefetcher fetches lines near a missed line, not the learned sequence. The 1.25 MiB chase defeats it only because its lines are evicted before use. Fix written for run 3 (latency.c option --sparse, in the working copy on 2026-11-02, not yet committed or run on the emulator): each chain uses one line per 4 KiB page (64 lines per region, seven fresh chains), so no chain member is a neighbour of another. Run 3 keeps the dense 1.25 MiB row as the control. The sparse rows should count 1.00 L3 refills per load if the hypothesis holds.
  • settled The firmware caused the write change: run 2's code on run 1's firmware returns to run 1's 87 to 89 GB/s limit within 0.4 % [results/membench-jibin-003/, section 9].
  • open Why, on the old firmware, the four-writer row puts 828,928 extra requests on node 344 and no extra memory requests or misses. Hypothesis: retried requests. Test: count hns_pocq_retry_all per node in run 3.
  • open Which part of the newer firmware removes the limit (the route overrides, the rest of SCP 0.48.0, or TF-A 0.35.0). Insufficient data: the control run changed the whole firmware set at once.
  • open The all-five OCM latency rows load the five nodes unevenly: 129,929 to 154,463 requests over the four rows [cmn-counts.csv]. On every CPU, OCM1's node takes the most, OCM0's sits just under it, and the count falls from OCM1 to OCM4. The timed walk visits every region equally. Insufficient data: the counts cover the chain build, the warm-up and the flushes too. A count of the timed walk alone would resolve it.
  • open OCM reads at 18.5 ns from one crosspoint against asimov-bench's 14.4 ns 64 KiB chase on an older RTL (Jesse's README cross-check). Not explained by these runs.
