Short version. Through the CME on boot E (the DSU L3 on) a dependent load costs 21.4 ns at 4 KiB, against a 21.0 ns round-trip baseline (a register move with no memory access). From 8 KiB on the chain load climbs as the CME's prefetcher fills its L1, and the L3 on does not lower it (1.019 times boot C's at 8 KiB, 0.940 to 0.977 from 48 to 384 KiB). The bandwidth rows are run 3's with the L3 off, not repeated: 36.6 to 37.2 GB/s of reads and 62.0 to 63.9 GB/s of writes through the CME from 160 KiB to 32 MiB.

  • Latency (boot E). 21.4 ns at 4 KiB (chain load minus round-trip baseline 0.37 ns, a derived number, not the memory latency), 24.9 at 8 KiB, 35.1 at 16 KiB, 45.6 at 64 KiB, 51.0 at 256 KiB, 70.5 at 32 MiB. The core's same rows read 2.0, 2.0, 2.0, 5.1, 9.5 and 52.9 ns (section 5). Run 3 read 21.4, 24.2, 31.6, 47.6, 53.1 and 70.3 ns on the same CME rows. The climb from 8 KiB is the CME prefetcher's: on boot B, with that prefetcher off, the chain load reads 21.0 to 21.3 ns up to 64 KiB. With the L3 on, 99.5 % of the CME's refills at 8 KiB come from inside the cluster (boot C, the L3 off: 15.1 %). No row gives an L3 hit time through the CME.
  • Bandwidth (run 3, the L3 off). Reads peak at 104.9 GB/s at 48 KiB. Writes hold 62.0 to 63.9 GB/s at every footprint, 32 bytes per cycle (section 6).
  • OCM (boot E). 29.0 to 37.7 ns per region through the CME (best of the chains with one line per page) against 19.1 to 20.4 ns for the core's own loads of the same chains. Part of those loads are served by the L3 on this boot, so the core's values are below the true OCM latency (section 7). The all-five chain over every line reads 43.3 ns through the CME against the core's 26.1 ns (section 7). The OCM bandwidth rows are run 3's: 23.2 GB/s read through the CME against the core's 16.0.
  • Open. No CME bandwidth row has run with the L3 on. No CME event names the level that served a load, so the L3 hit time through the CME is unmeasured (section 10).

1. Words used here

PMU, TRM, SOG
PMU: the performance monitoring unit, the counters of a core, of the CME or of the mesh. TRM: Arm's Technical Reference Manual of a unit. SOG: Arm's Software Optimization Guide of a core.
TLB, table walk
TLB: the translation lookaside buffer, the core's cache of address translations. A table walk is the read of the page tables when the TLB misses. The counted events are L1 data TLB refills (0x05) and data TLB walks (0x34).
CME
The Compute Matrix Engine: Arm's C1-SME2 unit (code name Griffin). One per DSU, shared by the DSU's two cores. It executes the cores' streaming-mode (SME) instructions, with its own 64 KiB 4-way L1 data cache, its own TLB and its own hardware prefetcher. Its path to memory is CME L1, then the DSU's L3 (on and holding data on boot E, empty on runs 1 to 3 and boots A to D), then the mesh. The core's L1 and L2 are not on it [Jesse's run 3 README, CME; CME-plan.md section 1].
streaming mode, SMSTART, SMSTOP
The CPU state in which SVE instructions run on the CME. SMSTART enters it and SMSTOP leaves it; both zero the vector registers. The test kernels enter it once per timed call and leave at the end.
SVL
The streaming vector length: 64 bytes on this chip, one cache line [dmesg: SME default vector length 64 bytes].
cme-roundtrip, cme-call
Two controls with no memory access. cme-roundtrip moves a value into a vector register and back out (DUP then LASTB) 65,536 times inside one streaming span. cme-call does one such round trip per call, 64 calls, so it carries the SMSTART, register save and SMSTOP of a whole call.
CME counters
The CME's own PMU events read through the core PMU: 0x3246 CME cycles, 0x327D CME L1D refills from inside the cluster (inner), 0x327E refills from outside the cluster (outer). Per load means divided by the loads of the timed span. These events count prefetch refills too [CME-plan.md section 2.1].
CME power (dynamic mode)
The firmware arms each CME's power controller in dynamic mode, so the CME switches itself off when idle and back on at the next streaming instruction. Whether it was off at the start of a timed span is not recorded [Jesse's run 3 README, CME power].
ldr16, str16
The 64-byte forms of the read and write kernels (one vector per instruction) beside the 256 B forms (four vectors per instruction).
CME refill events by cause
Run 4 adds three CME events to the two of run 3: 0x3280 CME L1D refills for demand reads (the chain's own loads), 0x32B2 refills requested by the CME's hardware prefetcher, 0x3281 refills for writes. Inner plus outer equals demand read plus prefetch plus write on every row [asimov-cme-run4.html, section 3.1].
round-trip baseline
The cme-roundtrip row: the latency test's loop with the load replaced by a register move (DUP then LASTB), so it measures one core-to-CME-to-core round trip with no memory access.
chain, chain load
The latency test walks a chain of dependent loads: each load reads the address of the next, so the loads cannot overlap. A chain load is one load of that chain, and its time is the load-to-use latency. A chain is walked many times (later walks hit whatever cache holds it), walked once, or walked with every line flushed from the caches first. The OCM chains have one line per 4 KiB page (64 loads per pass, at one offset or at a different offset per page) or every line of the region (4,096 loads per pass).
pass mean
A counter value averaged over the timed passes (reps) of a row, written "per load". Run 3's page quoted the fastest pass. This page quotes the pass mean and says so where it differs.
E / C
Boot E's ns per load divided by boot C's on the same row. The two boots ran the same commit, build and kernel, and only the SCP differs, so the ratio isolates the L3 [Jesse's boot E README, Against boot C].
run, boot
A run is one job on the emulator (run 3 = membench-jibin-004). Run 4 is five boots, A to E, each a job with one firmware and program configuration (section 2). Boot E is the latest.
C1-Nano, DSU
The Arm core and its two-core cluster (DynamIQ Shared Unit). The hemisphere has 5 DSUs, CPUs 0 to 9. Device interrupts are routed to CPUs 0 and 1 (irqaffinity=0-1); the scheduler places no unpinned task on CPUs 2 to 9 (isolcpus=2-9) and their periodic tick stops while one task runs (nohz_full=2-9). The init started run_all.sh pinned to CPU 2, so the scripts, the shell and the counter helper ran on CPU 2 (cmncount sets no affinity of its own) and each measured program pinned itself to its --cpu. Every core takes its own timer and per-CPU interrupts, and a program's page faults and system calls run on its own core [Jesse's run 3 README, The run and CPU placement].
L1, L2, L3
32 KiB data cache per core, 128 KiB per DSU, 256 KiB per DSU, 64-byte lines [sysinfo.txt]. On runs 1 to 3 and run 4 boots A to D the L3 of CPUs 2 to 9 was in snoop-filter-only mode and held no data (the stock SCP stages the full L3 for cluster 0 only; register 0x0, 0 L3 hits per load). Boot E's rebuilt SCP turns it on: the register reads 0x70 and the hit set counts 0.75 L3 read hits per load at 256 KiB [Jesse's boot E README, L3 power; latency-dram-small-l3.csv].
mesh, crosspoint (xp)
The Arm CMN S3 interconnect, a 6 by 6 grid of routers. Distance between two points is the number of crosspoint steps, |dx| + |dy|.
home node (HN-S), SLC
The five mesh nodes that own all addresses, each with 1 MiB of System Level Cache in 16 ways. A DRAM address belongs to one home node by a hash, so a buffer spreads over all five.
OCM
On-Chip Memory: 4 of the 16 ways of each home node, locked as 256 KiB of memory at 0xE0000000 + n MiB. Region n lives in home node n only. Reached through /dev/ocm in 4 KiB pages.
node id
The mesh id of a home node (88, 160, 216, 288, 344). Its bits give the crosspoint: x = bits 8 to 6, y = bits 5 to 3.
best, pass, rep
A command walks its chain several times (passes, or reps); best is the fastest. A per-region OCM row has 7 passes, an all-five row over every line 2, a chain walked many times 3 reps.
refills per load
PMU events 0x03 (L1D refill), 0x17 (L2D refill), 0xA2 (L3D read refill) divided by the loads of the timed walk. 1.00 means one fill of that level per load. A fill can be a demand miss or a prefetch, so the count does not say which loads missed, and a useful prefetch can replace a later demand fill and leave the count near one.
perf_cov
New in run 3: the counter group's running time over its enabled time for the row. 1.0000 means the counters were never multiplexed; every row of this run reads 1.0000.
cmncount
The helper that opens the mesh PMU (arm_cmn_0) around one command and writes cmn-counts.csv: requests received per home node, memory-controller requests and SLC misses.
SCP, TF-A
The System Control Processor firmware (which also sets up the mesh) and Trusted Firmware-A (the boot firmware of the application cores). Run 3 ran SCP 0.48.0-nopcie.1 and TF-A 0.35.0, the same as run 2 [Jesse's run 3 README].
chip time
Time as the emulated chip sees it. One chip second took 2,776 wall seconds in run 3 [Jesse's run 3 README].
est.
An estimate, not a measurement.

2.1 What changed from run 3 to run 4 boot E for the CME

  • The L3 holds data. On run 3 (and on boots A to D) the L3 of CPUs 2 to 9 was in snoop-filter-only mode: the stock SCP stages the full L3 for cluster 0 only, and the hit counters read 0 L3 hits per load. Boot E's rebuilt SCP turns it on. The core's hit set (the 64 KiB to 512 KiB chains run with the L2 and L3 hit events) counts 0.47, 0.75 and 0.92 L3 read hits per load at 192, 256 and 384 KiB. The data read fell from boot C's 14.101, 19.690 and 22.669 ns to 7.811, 9.489 and 10.906 ns [latency-dram-small-l3.csv of 010 and 007; Jesse's boot E README, L3 power].
  • Three more CME events. Run 4 counts 0x3280 (demand read refills), 0x32B2 (hardware prefetch refills) and 0x3281 (write refills) beside run 3's 0x3246, 0x327D and 0x327E, so the CME's refills split by cause (table 4.1, section 5).
  • Rows added. The 8 MiB chain in address order through the CME, and two more chain shapes of each OCM region (every line, and one line per page at varied offsets) beside the one line per page chain (table 4.2).
  • Rows not repeated. Every CME bandwidth row (the one-core sweep, the 64-byte forms, the call-cost rows, the OCM bandwidth) and the mesh counters around CME commands. Sections 4.3 to 4.6, 6 and 8 keep run 3's values, labelled run 3 (the L3 off), not repeated with the L3 on.
  • The core rows are from boot E. Every core number beside a CME number on this page is boot E's own cache-test row of the same footprint, so the comparison carries no firmware or image difference. The core page is asimov-c1nano-perf.html.
  • Repeat check against run 3. Of the 24 CME chain rows run 3 also ran, 7 read within 1 %, 14 within 3 % and 18 within 5 %. The largest change is +10.8 % at 16 KiB (walked many times), a row where the L3 on changes where the prefetcher's fills come from (section 5). The CME rows of boot A, run 3's configuration, are the repeatability reference [asimov-cme-run4.html, section 3.3].
  • The other boots on this page. Boot C (the same commit as E, the L3 off) is the boot that isolates the L3. Boot B (the CME and core prefetchers off through a TF-A hook) gives the demand-only reading. Boot A (run 3's configuration) is the reference of the run 4 pages.

3. The hemisphere map, CME path

The left column is the CME's path outward: its own L1, then the DSU's L3 (on and holding data on boot E), then the mesh to the home node (SLC or OCM), with DRAM behind the home node. The core's L1 and L2 are not on it. The chain-load times written in the boxes are measured at a footprint. Which level served them is not measured, because no CME event names the source of a refill (section 5). The label under each home node is the CME's best chain with one line per page over that region beside CPU 2's own, both from boot E.

3.1 The data path of one CME load

The example is one load of the latency test's kernel: LD1D {z0.d}, p0/z, [x0] then LASTB x0, p0, z0.d in streaming mode [cme_kern.S]. Words used here: MMU (the core's memory management unit, which translates a virtual address to a physical one), GPR (a general-purpose register such as x0), PIPT (a cache indexed and tagged by physical address), SCU (the DSU's snoop control unit, which keeps the cluster's caches coherent), CHI (the Arm bus protocol between the DSU and the mesh), SBSX (the mesh bridge toward a memory controller).

  1. Core. CPU 2 is in streaming mode. It decodes the LD1D, but does not execute it: SME instructions are decoded on the core and issued to the CME, up to three per cycle, loads and stores two per cycle [C1-Nano SOG 109590, section 2.33]. The core's MMU translates the address in x0 first, so the CME receives a physical address and never asks for a translation of its own for a load or a store [C1-SME2 TRM 107831, chapter 5]. The core's L1 data cache and L2 are not on the path.
  2. Bridges. The instruction and its physical address cross the DSU on the streaming request channel (CMEREQ). A second channel (CMETLB) carries the translation requests of the CME's prefetcher back to the core [TRM 107831, chapter 1]. There is one SME2 unit bridge between each CME and the DSU [TRM 107831, section 2.1].
  3. CME. The CME decodes, renames and issues the load to its L1 data memory system: a 64 KiB, 4-way, 16-bank, physically indexed and tagged cache with 64-byte lines and two 512-bit read paths into the vector registers, so one line fills Z0 in one transfer. A hardware prefetcher with 128 streams, indexed by instruction address, fills this L1D and the DSU L3. It works in virtual addresses and keeps its own TLB [TRM 107831, table 6-1 and sections 5 and 6.3]. LASTB then moves the last active element of Z0 into x0, and that GPR update travels back to the core, where the next LD1D waits for it (the core's event 0x3205 counts the waiting cycles) [C1-Nano TRM 107753, PMU events 0x3204 and 0x3205].
  4. DSU L3. A CME L1D miss goes to the DSU's L3 memory system: the SCU's snoop filter, which tracks the CME's L1D beside the cores' caches, and the 256 KiB L3. On a simultaneous hit in both, the L3 supplies the line [C1-DSU TRM 107804, chapter 2]. A line that comes from inside the cluster counts as an inner refill (event 0x327D). On boot E the L3 holds data: at 8 KiB the CME counts 3.98 inner and 0.02 outer refills per load, where boot C (the L3 off) counts 0.59 and 3.33 [cme-latency-dram-small.csv of 010 and 007]. On runs 1 to 3 and boots A to D the L3 held no data (register 0x0, 0 L3 hits per load), so the inner refills counted there were not L3 hits. Which lines that event counted, those files do not show.
  5. Mesh, home node, DRAM. An L3 miss leaves the cluster on the DSU's 256-bit CHI memory interface [DSU TRM 107804, chapter 2] and crosses the mesh from crosspoint (2,3) to the home node that owns the address, 1 crosspoint away for three of the five nodes and 3 for the other two (table 4.2). There the line is in the SLC, or in the OCM ways when the address is an OCM region, or is fetched from DRAM through the SBSX bridge. The line returning from outside the cluster fills the L3 and the CME L1D and counts as an outer refill (event 0x327E). The counter cannot say which of SLC, OCM or DRAM supplied it (section 5).

10. Open items

  • hypothesis A fixed cost of 0.1 to 0.3 us est. per timed span (CME wake-up from dynamic power-down, Jesse's run 3 README bounds) inflates the 64-load OCM passes: on boot E the one line per page medians run 3.6 to 12.7 ns above the bests (section 7). A row that times the first and the later passes of one span separately would decide it.
  • open The bandwidth set (the one-core sweep, the 64-byte forms, the call cost, the OCM bandwidth) has not run through the CME with the L3 on. Sections 4.3 to 4.6 and 6 are run 3's. The core's plain one-core read rose from 9.3 GB/s (run 3) to 24.9 GB/s at 2 MiB with the L3 on [bandwidth-read-prefetch.csv of 010], so the CME's rates may have moved too (why the core's rate rose is an open item of asimov-c1nano-perf.html, section 12). The measurement: the CME test script's bandwidth rows (run_cme.sh) on a boot with E's SCP. Planned: run 6 boot F1, the L3 on with the prefetchers on, not yet run [follow-up-run-plan.md, section 13].
  • Insufficient data Which level served a CME load: no CME event names it, so SLC against DRAM through the CME (the 2 MiB chain walked once at 56.7 ns and the 8 MiB row with every line flushed first at 62.1 ns, 5.4 ns apart, both with about one demand refill per load: 0.99 and 0.99) and a load served by the L3 through the CME stay unmeasured. The measurement: a boot with the L3 on and the CME prefetcher off (boot B's TF-A with boot E's SCP), which would make every refill a demand refill. Planned: run 6 boot F2, not yet run [follow-up-run-plan.md, section 13].
  • open The memory model's configured delay behind the rows with every line flushed first (asked of Jesse, unanswered). The L3 state of the clusters of CPUs 4 to 9 on boot E was not read (the README's reading covers CPU 2's cluster), so the CME rows of other DSUs are untested with the L3 on. No mesh counter has run around a CME command since run 3.
  • open Two cores of one DSU in streaming mode at once (the CME is shared), and the CME with operands in OCM for a matmul.
  • open A CME write call carries no fixed cost. A CME read call carries about 101 ns.
    • What the rows show. Each bandwidth pass is one call of the kernel (the test loop in cme_kern.S). A call enters streaming mode with SMSTART, moves its bytes and leaves with SMSTOP. A straight line through the 16 and 48 KiB rows, time per pass against bytes, gives the fixed cost per call as its intercept (two points, est.). For cme-write the intercept is 0.5 ns per call at a fitted rate of 64 GB/s. For cme-read it is 101 ns per call at 134 GB/s [cme-bandwidth-dram-1core.csv, run 3].
    • A short write call does show a cost. The 1 KiB write call takes 39 ns. Its stores take 16 ns at 64 GB/s. The rest, 23 ns est., is the call's own cost [cme-bandwidth-call-cost.csv, run 3].
    • What every call pays. The register save, SMSTART, SMSTOP and the restore cost 22 ns est. together (cme-call minus cme-roundtrip on boot E). The read kernel also adds up the 16 running totals it kept while loading and returns the result. The write kernel returns nothing.
    • hypothesis Why the write rows hide the cost. Stores are posted: the core counts a store as done before the data reaches memory. So the last stores of one call are still draining while the kernel leaves streaming mode and the next call enters. From 16 KiB up, the mode switch overlaps with those stores. The read kernel's final sum waits for its loads, so nothing overlaps there.
    • Three tests would settle it. All three are in run 6, phase F2 of run_cme.sh, requested for boot F1 and not yet run [follow-up-run-plan.md, section 13].
      • A single-call form for the CME (all passes of a rep in one streaming span, cme_kern.S) for read and write at 4, 8, 16 and 24 KiB, beside the looped form (one call per pass). Read the two forms as the core's L1 rows are read (asimov-c1nano-perf.html, section 7.1). The difference of the two intercepts is the cost per call. A difference near zero for writes confirms the overlap.
      • A write variant with DSB ST (a barrier that waits for all earlier stores to complete) before SMSTOP. If about 22 ns per call then appears, the overlap is confirmed.
      • Per-call writes at 1, 2, 4 and 8 KiB, to find the size at which the 23 ns disappears.
