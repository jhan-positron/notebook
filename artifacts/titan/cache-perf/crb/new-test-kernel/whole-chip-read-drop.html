Why the whole-chip read rate fell with the new test kernel

CRB, 120 threads, DRAM-sized buffers. Measured on 2026-11-15, 16:56 to 21:03 UTC. A generator script builds this page [Ref19]. Its numbers come from the facts sheet [Ref1].

Short version

With 120 threads only read really dropped (about 300 GB/s against about 468 GB/s, -36 %): copy did not drop, and most of the write drop comes from the stop rule of the benchmark.

The new read loop holds loads only, and the out-of-order window of a core (the instructions that it can start ahead) then covers 36 to 40 cache lines (64 B each) instead of 18 to 22 (one-thread test), and the 120-thread total falls when the window covers more than about 30 lines.

Adding 72 or more do-nothing instructions per 256 B of data read restores 459 to 480 GB/s, and the drop did not appear when the same loads read the memory in one scrambled order instead of address order, and the exact rule inside the core is not established.

1. Only read really dropped

  • The original run used the whole-pass stop and 0.5 s per interval [Ref2]. Read fell there by more than one third. Write fell by a smaller amount. Copy did not fall.
  • Copy was measured again at 64+56 with a common stop and 6 s. All five copy loops gave 152.4 to 153.6 GB/s [Ref3].
  • Write was measured again at 64+56 with a common stop and 8 s. The old loop gave 126.1 to 126.8 GB/s. The new loops gave 120.2 to 129.3 GB/s [Ref3]. Padding does not change write.
  • The write drop depends on the stop rule. Earlier controlled runs compared old write and new C write under four timing rules [Ref4]. The old loop is 21.5 % higher with the whole-pass stop and 0.5 s. It is 3.1 % to 3.7 % higher with a common stop.
  • So most of the write drop in the original run comes from the whole-pass stop rule. 3 to 4 % remains with a common stop.
  • The original file supports this. At equal pass count (296 passes) old write is 144.2 to 145.6 GB/s. New write is 143.6 GB/s and 147.8 GB/s [Ref2].
  • Read is different. The drop stays with a common stop: 288.5 to 309.8 GB/s against 465.5 to 470.1 GB/s (section 2) [Ref6].

2. The read rate follows the window depth

  • A window test with one thread on CPU 2 measured how much one core holds in its window [Ref5]. The window holds 684 nop, or 159 vector-register writes, or 191 integer adds.
  • The same test measured the window depth of each loop in lines. One loop body was the unit. The result is a range: the last count that fits, to the first count that does not fit [Ref5].
  • 29 loop variants were then run at 64+56. Figure 1 shows the total of each variant against its window depth [Ref6].
  • Every variant with a window of 32 lines or more is slow: 280 to 310 GB/s. read_1pl covers about 160 lines and gives 230 to 235 GB/s.
  • Every variant whose measured range is at or below 24 to 28 lines is fast: 459 to 480 GB/s. read_nop256 covers 8 to 12 lines and gives 543.9 to 549.0 GB/s.
  • The four variants whose measured range lies inside 26 to 32 lines are slow or between (read_nop56, read_dadd4, read_nop64, read_sp32).
  • The old read loop is fast because its 8 vector adds per 128 B occupy vector registers. The window holds 159 vector-register writes [Ref1][Ref5].
  • The adds do not need to wait for data. read_iadd16 has adds that do not use the loaded data. read_dadd16 has adds that use it. The two totals overlap (469.2 to 469.7 GB/s and 466.7 to 469.8 GB/s) [Ref6].
  • Software prefetch does not restore the rate. read_pf256 gives 289.1 to 300.1 GB/s (n = 4). read_pf512 gives 302.3 to 303.9 GB/s (n = 2). read_pf1024 gives 311.8 to 315.8 GB/s (n = 2) [Ref6].
  • The page size does not matter. With 4 KiB pages instead of 2 MiB pages (huge pages) the results are the same. The differences to the process with huge pages are -2.4 % to +0.2 % (one process per page size) [Ref7].

5. The slow state is not congestion

Latency probe and lines in flight

  • One core per mesh (CPU 2 and CPU 66) ran a latency probe (a pointer chase). Each step issues two independent loads that miss the cache at the same time. So the step time is about the time of one DRAM read. The other 118 cores ran a read loop [Ref10].
  • On the idle machine one step takes 146.9 ns on both CPUs [Ref10].
  • With the load-only loop on all cores (total 298 GB/s) one step takes 203.1 ns and 211.3 ns. With the padded loops on all cores one step takes 238.0 to 286.5 ns [Ref10].
  • With the load-only loop on mesh 0 against read_nop256 on mesh 1, one step takes 297.1 ns on mesh 0 (fast) and 236.4 ns on mesh 1 (squeezed). In the reverse case one step takes 212.9 ns on mesh 0 (squeezed) and 223.5 ns on mesh 1 (fast) [Ref10].
  • So one memory request takes less time in the slow state than in the fast states: 203 to 211 ns against 238 to 297 ns. The 297 ns is the fast mesh 0 of the mixed case.
  • Lines in flight per streaming core (est.) = lines per second per thread x probe time. The estimate assumes that a request of a streaming core takes as long as a request of the probe.
  • Slow or squeezed meshes have 6.5 to 9.2 lines in flight per core (est.). Fast meshes have 14.9 to 25.3 (est.).

Data path, busy level and core counters

  • Per line, a core gets 0.50 + 0.50 flits from the two memory-port columns of its own mesh and 1.00 flit from the gateway row. This holds in every state: slow, fast, squeezed and alone [Ref13].
  • So half of the lines arrive directly from the memory ports of the own mesh. The other half arrive through the gateway from the other mesh.
  • Response messages with busy level 0 are 82 to 93 % on slow or squeezed meshes. They are 4 to 26 % on fast meshes [Ref14].
  • Three cases are in between. Mesh 1 under read_nop96 or oldread at 64+56 has 73 to 74 %. Mesh 1 with asmread against read_nop256 on mesh 0 has 44 to 46 % [Ref14].
  • So the squeezed cores do not receive a higher busy level than the fast cores.
  • Data that arrives through the gateway carries busy level 3 in 89 to 100 % of the flits. This holds in every state, also with the other mesh idle [Ref14].
  • The core counters per line are the same in the slow and fast states. They are 2.08 bus accesses (transfers between the core and the mesh), 1.000 L2 refills (lines that arrive in the L2 cache, the second cache level of the core) and 1.000 L2 hardware-prefetch events (as counted by the core for its hardware prefetcher). The instruction counts are as coded [Ref1].
  • Only the cycles per line differ: 66 to 77 in the slow state against 35 to 37 in the fast state on mesh 0. The core clock is 2.8 GHz in all runs [Ref1].

6. The drop needs a sequential stream

The scrambled-order loops

  • Three more loops were added to the benchmark program (bwx13, the runner): rand_nop0, rand_nop96 and rand_nop256 [Ref21].
  • They read the same bytes as the load-only loop: 8 load-pair instructions per 256 B block, and every block once. They add 0, 96 or 256 nop per block.
  • So their loads and padding are those of the load-only loop (asmread), of read_nop96 and of read_nop256.
  • The difference is the order. The 8192 blocks of each 2 MiB chunk are visited in a scrambled order. Visit number i reads block (i x (2i + 1)) mod 8192 [Ref1].
  • The intent was that the hardware prefetcher cannot follow the order from block to block. The one-thread counters below do not confirm an idle prefetcher.
  • The window depth in lines is taken from the sequential loop with the same loads and padding: 36 to 40 lines, 20 to 24 lines and 8 to 12 lines. The scrambled loops have 5 more integer instructions per block [Ref1]. Their window depth was not measured separately.

One thread

  • One thread on CPU 2 read a 256 MiB buffer. This section uses two runs of 0.5 s per loop, both with the common stop: one for the rate, and one with the core counters switched on [Ref21].
  • The load-only loop in sequential order read 35.7 GB/s. In scrambled order the loops read 10.8 GB/s (no padding), 8.4 GB/s (96 nop) and 4.8 GB/s (256 nop).
  • The core counters differ per line. The scrambled loops have 1.63 to 1.64 L2 refills per line against 1.00 in sequential order. They have 0.41 to 0.42 loads per line that miss all caches against 0.00 to 0.06 (read_nop256 has 0.00) [Ref1][Ref21].
  • The scrambled loops show 1.84 to 1.91 L2 hardware-prefetch events per line against 1.00 in sequential order [Ref1][Ref21]. So the hardware prefetcher is not idle in scrambled order.
  • A second counter run of the same test used the whole-pass stop. Its scrambled loops show 1.44 to 1.51 L2 hardware-prefetch events per line and 0.58 to 0.60 loads per line that miss all caches [Ref1][Ref21].
  • So with one thread the scrambled order is the slower one, and the loop has more cache misses.

120 threads at 64+56

  • Two processes ran at the same time, one per mesh, for 10 s. There is one interval per cell [Ref20].
  • With the scrambled loops on both meshes the total is 489.6 GB/s (no padding), 473.5 GB/s (96 nop) and 382.5 GB/s (256 nop).
  • Two sequential controls ran in the same run. The load-only loop gave 297.8 GB/s. read_nop256 gave 547.2 GB/s. Both lie inside the ranges of section 2.
  • read_nop96 in sequential order was not repeated in this run. Figure 4 uses its range from section 2: 465.5 to 470.6 GB/s (n = 16) [Ref6].

Mixed pairs

  • In the four pairs of a sequential loop against a scrambled loop, the mesh with the sequential loop reads more (rows 6 to 9 of the table).
  • With read_nop256 on the other mesh, rand_nop0 reads 182.8 GB/s on mesh 0 and 158.4 GB/s on mesh 1. With rand_nop0 on both meshes it reads 268.8 GB/s and 220.8 GB/s.
  • Mesh 0 alone reads 342.8 GB/s with rand_nop0 and 223.3 GB/s with rand_nop256.

Reading

  • In scrambled order the deep window is the faster one: 489.6 GB/s (no padding) is above 473.5 GB/s (96 nop), and that is above 382.5 GB/s (256 nop). In sequential order it is the reverse: 297.8 GB/s is below 465.5 to 470.6 GB/s, and that is below 547.2 GB/s.
  • Hypothesis: part of the fall to 382.5 GB/s is the limit of one core with 256 nop. rand_nop256 reads 4.8 GB/s with one thread [Ref21]. It reads 3.15 to 3.22 GB/s per thread with 120 threads [Ref20]. A run of rand_nop256 with fewer threads per mesh would test this. That run was not done.
  • The same loads and padding (window depth assumed equal, not measured) read 489.6 GB/s in scrambled order and 297.8 GB/s in sequential order. So the deep window alone does not lower the total. In this run the drop appeared in sequential order. It did not appear in the one scrambled order tested.
  • So the drop depends on how the cores handle a sequential stream. The facts sheet reads this as: the rule is in the cores, not in the mesh, the gateways or DRAM [Ref1]. This narrows the open item of section 7. The exact rule inside the core is still not established.

Limits of this section: every cell is one interval of 10 s from one evening. No cell was repeated. Only one scrambled pattern was tested. The hardware prefetcher was not switched off. Its settings were not read. The one-thread counters show hardware-prefetch events in scrambled order too (1.84 to 1.91 per line), so the scrambled loops do not show the cores without prefetch. The window depth of the scrambled loops was not measured. The latency probe did not run with the scrambled loops, so their lines in flight are not known.

7. What is established and what is not

Established

  • Read is the only real drop. Its size at 64+56 is about 300 GB/s against about 468 GB/s (-36 %) (sections 1 and 2) [Ref1].
  • Cause in the benchmark (section 2) [Ref1]:
    • The load-only loop lets the window of a core cover 36 to 40 lines.
    • The old loop covered 18 to 22 lines.
    • Above about 30 lines the 120-thread total falls.
    • Vector adds are not needed.
  • Mechanism as far as measured (sections 4 and 5) [Ref1]:
    • Cores (or their prefetchers) whose loop covers more lines take a larger share.
    • A whole mesh then runs with about 8 lines (est.) in flight per core instead of about 20 (est.).
    • Each request is served faster in that state.
    • Nothing is congested.
    • DRAM does one read per line.
  • Narrowing (section 6) [Ref1][Ref20]:
    • A loop with the same loads and padding (window depth assumed equal, not measured) reads 489.6 GB/s in scrambled order and 297.8 GB/s in sequential order.
    • So the deep window alone does not lower the total.
    • The drop depends on how the cores handle a sequential stream.
    • This rests on one scrambled pattern and on one interval of 10 s per cell from one evening.
  • Fix verified (section 2) [Ref1]: 72 nop or more per 256 B in the load-only loop restores 459 to 480 GB/s. 256 nop gives 544 to 549 GB/s. That is 17 % above the old loop.

Not established

  • Insufficient data: which rule inside the core lowers the lines in flight for a sequential stream in the slow state. Section 6 shows that the drop depends on the sequential stream. It does not identify the rule. The prefetch controls of the V3AE core cannot be read from a normal Linux program. Two hypotheses exist. Neither is confirmed. H-a and H-b are only labels for them [Ref1].
    • Hypothesis H-a: the cores set their request limit or their prefetch strength dynamically. The manual of the Neoverse V2 core documents a dynamic limit of outstanding requests that the busy level drives (IMP_CPUECTLR2_EL1 TXREQ_LIMIT_DYNAMIC) and adaptive prefetch modes (PF_MODE). It is not known whether the V3AE core has this limit. It is not known how the firmware set it. One finding contradicts a simple form of H-a: the squeezed cores receive lower busy levels.
    • Hypothesis H-b: a prefetcher adapts its distance to how early the data arrives. This combines with the need to receive both halves of the lines in order (the half from the own mesh and the half from the other mesh).
    • Measurement that would resolve it: read the registers IMP_CPUECTLR_EL1 and IMP_CPUECTLR2_EL1 on CRB (this needs a Linux kernel module or firmware access). Other sources: the prefetch section of the V3AE manual, or a question to Arm support with the data of sections 4, 5 and 6.
  • Insufficient data: why the write total falls with writers on both meshes. The fall is the same for old and new loops. The facts sheet names no measurement for it. A first step would be the mesh counters of section 5 during write runs at 64+0 and at 64+56.
  • Insufficient data: why old write stays 3 to 4 % above new write under a common stop. The facts sheet names no measurement for it. A first step would be the core counters per line for both write loops.

Limits of this work

  • All runs come from one evening (2026-11-15, 16:56 to 21:03 UTC) and one machine.
  • Many cells have n = 2 intervals from one process. The layout table has one interval per cell. The sample count of each value is in the tables.
  • The window depth of each loop is a measured range from a test with one thread. It was not measured during the 120-thread runs.
  • The lines in flight are estimates (est.). They depend on the assumption named in section 5.
  • The scrambled-order results of section 6 have one interval of 10 s per cell. No cell was repeated.
  • The two "first step" proposals above come from this report. They are not in the facts sheet.

8. Recommendation for the benchmark

  • Keep the new load-only loops for one-thread and cache-size measurements. They measure the load path without extra work.
  • For whole-chip DRAM read numbers, state the loop. Report the load-only loop and a window-limited loop. One example is read_nop256: 544 to 549 GB/s at 64+56. With one thread and a 32 KiB buffer it reaches 23 GB/s, and the core limits it there [Ref1].
  • The 465 to 470 GB/s of the old read loop is one value among several. The value depends on the loop. It is not a constant of the chip [Ref1].
  • For write totals use a common stop time or a long interval. The whole-pass rule with 0.5 s raises old write by 14 % (144 GB/s against 126 GB/s, median) [Ref1][Ref4].
  • The source of the benchmark was not changed [Ref1].
