ASCT cross-check of two open read-throughput questions on CRB

CRB is the Arm Phoenix Reference Server in our lab. ASCT is the Arm System Characterization Tool, version 0.7.1+77461b3. Runs of 2026-11-16, 23:12 to 23:47 UTC. Page built from facts.json by report.py.

Short version

  • 8 MiB on one core. The read loop of ASCT also loses rate from 1 MiB to 8 MiB (95.9 to 57.2 GB/s on CPU 2), and no form of it reads 8 MiB faster than our new read loop (69.0 against 71.0 GB/s).
  • Whole chip. On the same 120 CPUs the ASCT loop reads 229.4 GB/s, and with 10 injected delay rounds it reads 622.5 GB/s, so the low whole-chip number is a state of CRB and not its capacity.
  • Counters. In both slow cases the core counters show loads that run ahead of the hardware prefetchers, and the mesh counters are missing, because the root command for them was refused in this session.
Words used here
  • CRB: the Arm Phoenix Reference Server in our lab, 128 cores (Arm part 0xd83), one NUMA node.
  • ASCT: the Arm System Characterization Tool, version 0.7.1+77461b3. It is Arm's tool for memory latency and bandwidth tests.
  • read loop: the few instructions that a benchmark repeats to read a buffer. This report compares three read loops.
  • old read: the read loop of our benchmark before 2026-11-13. It loads every byte and adds the loaded values.
  • new read: the read loop of our benchmark since 2026-11-13. It loads every byte and does no other work. Its values here are those of the assembly form (asmread) unless a line says otherwise.
  • ASCT read: the read loop of ASCT (function my_read_no_nops_rep_64b). It loads 8 bytes of each 64-byte line.
  • line: one 64-byte cache line. Caches and memory move data in lines.
  • L1, L2: the two private caches of a core, 64 KiB and 2 MiB.
  • SLC: the system-level cache, 128 MiB, shared by all cores. Linux calls it L3.
  • mesh: the on-chip network that links cores, SLC and memory ports. CRB has two meshes: mesh 0 holds CPUs 0 to 63, mesh 1 holds CPUs 64 to 127.
  • 64+56: 64 threads on CPUs 0 to 63 and 56 threads on CPUs 64 to 119, one thread per CPU, 256 MiB per thread.
  • injected NOPs (N): an ASCT option (--bw-fine-delay N). ASCT then runs an empty loop of N rounds after each load. ASCT calls the rounds NOPs. One round has 3 instructions.
  • window: the instructions that a core holds in flight at one moment. A read loop with few instructions per line puts many lines into one window.
  • prefetcher: the part of a core that requests lines before the program asks for them.
  • core counter: a hardware counter inside a core, for example cycles or cache refills. ASCT reads them through its capture code named dietperf.
  • probe build: the variant of the ASCT benchmark binary that contains the capture code.
  • mesh counter: a hardware counter of the mesh (Linux units arm_cmn_0 and arm_cmn_1). Reading it needs root.
  • L2 refill: one line that enters L2 from the SLC or from memory. The counter is l2d_cache_refill.
  • long-latency miss: a load that had to wait for its line. A load whose line was prefetched in time is not counted.
  • L1 prefetches, L2 prefetches: the counts of the counters l1d_cache_hwprf and l2d_cache_hwprf. One count is one request of the hardware prefetcher of that cache.
  • busy level: a number from 0 to 3 that the mesh sends to a core with each answer. 3 means most busy. The core counts the answers of each level (counters l2_chi_cbusy0 to l2_chi_cbusy3).
  • hop: one step from one crosspoint of the mesh to the next.
  • slow state: the condition at 64+56 in which a thread reads about 2 GB/s. In the fast condition it reads about 5 GB/s.
  • lower bound of a total: all bytes that the threads of one process read, divided by the time of the slowest thread. ASCT itself adds the rates of the threads.
  • huge page: a memory page of 2 MiB or more. A normal page has 4 KiB. With transparent huge pages the kernel gives huge pages to a program that did not ask for them.
  • P-A1, R-A3, D-A2 and similar names: the predictions (P), rules (R) and descriptive items (D) of the decisions file. They were written before the data that they judge.
  • part U, N, C, NC: the four parts of the one-core runs. U: no counters. N: injected NOPs, no counters. C: counters. NC: injected NOPs with counters.
  • marker file: the file /tmp/positron-perf.RUNNING on CRB. The other user of CRB creates it while his tests run.
  • process: one start of the ASCT benchmark binary. It prints one rate.
  • median, range: the middle value of the processes of a cell, and the smallest to the largest value.
  • GB: 109 bytes. KiB, MiB, GiB: 210, 220, 230 bytes.
  • Arm reference machines A0 and A1: the two machines of the vendor baseline runs in the Arm welcome kit. They have firmware v0.9.0 and two NUMA nodes.
  • NUMA node: a group of cores and the memory that the firmware declares as local to them.
  • block: a time window that Jeremy Conner reserves on CRB in Slack channel #phoenix-crb.
  • est.: an estimate, not a measurement.

1. What was asked, and how ASCT was used

Two results of our own read benchmark on CRB are not understood.

  • Question 1, 8 MiB. The new read loop is 27.0 % faster than the old read loop at 1 MiB on one core. At 8 MiB the gain was 0.78 % in the first run of 2026-11-13 [Ref1]. The runs of 2026-11-15 found 0.2 to 6.7 % [Ref2].
  • Question 2, whole chip. At 64+56 threads the old read loop reads 465.5 to 470.1 GB/s in total. The new read loop reads 288.5 to 309.8 GB/s [Ref3].

The request for this work: repeat both tests with ASCT on the same cores and sizes, compare the rates with the old and the new loop, and capture the counters and registers that ASCT can reach, with a focus on the prefetchers.

The ASCT front end (the command asct run) could not be used on CRB as it is. There are four reasons.

  • Fixed core. The ASCT benchmark bandwidth-sweep takes its one core from the code: the last CPU of NUMA node 0. On CRB that is CPU 127 [Ref4]. CPU 127 is isolated and must not be used [Ref13].
  • All CPUs. The ASCT benchmark peak-bandwidth uses every CPU of the node. On CRB that includes CPUs 120 to 127. Our runs may use CPUs 0 to 119 only [Ref4] [Ref13].
  • Huge pages. Both benchmarks first run the ASCT benchmark latency-sweep, which needs huge pages. CRB has 0 free huge pages. Adding huge pages needs root and changes a system setting [Ref7] [Ref10].
  • One user setting. bandwidth-sweep has one user setting, cycle_base. It has no setting for the core or for the buffer sizes [Ref4].

So each run started the ASCT benchmark binary directly. The command line is the one that the front end builds [Ref4]:

numactl --membind 0 loaded-latency-asct-sve.bin --duration D --delay-seconds 0 \
    --bw-cpu C [--bw-cpu C ...] --bw-buflen BYTES --bw-fine-delay N --bw-write=0 --bw-cacheline-bytes 64
  • D is the length of the measured phase in seconds. The ASCT default is 0.25 s.
  • C is a CPU. One thread runs on each CPU that the command line names.
  • BYTES is the buffer size of each thread.
  • N is the number of injected NOPs.

What is the same as in a run through the front end, and what is not:

  • Same binary. Runs without counters used the binary that the ASCT installer built on CRB [Ref10].
  • Same loop in the counted runs. Runs with counters used the probe build. It was built on CRB from the ASCT source archive, with the compiler flags of the ASCT configuration file [Ref6] [Ref9]. The machine code of the two ASCT read functions is identical in both binaries. A rebuild without the probe flag gave a file with the same SHA-256 sum as the installed binary (first 8 digits e26babf6) [Ref10].
  • Timing. One-core runs used the ASCT default of 0.25 s. Whole-chip runs used 2 s. Three whole-chip processes used 0.25 s as a check.
  • Pages. The ASCT bandwidth code allocates its buffer with posix_memalign and does not ask for huge pages [Ref5]. The CRB kernel setting for transparent huge pages is "always". A 64 MiB test buffer on CRB was backed by 2 MiB pages for all of its 64 MiB [Ref10]. The Arm reference machines record the setting "madvise" [Ref11]. So their buffers used 4 KiB pages (est. from the setting, not measured).
  • Different by design. The CPUs, the buffer sizes and the thread layout are ours, not those of the front end.

The three read loops

  • Old read. It loads all 64 bytes of a line with 2 pair-load instructions (ldp q, 32 bytes each). Then it adds the loaded values with 4 vector add instructions [Ref3].
  • New read. It loads all 64 bytes of a line with 2 ldp q instructions. It does no other work [Ref3].
  • ASCT read. It loads the first 8 bytes of a line with 1 load instruction (ldr x). It does no other work. One loop round covers 8 lines and has 3 more instructions for the loop itself [Ref5]. The counters give 1.375 instructions per line.
  • ASCT read with N injected NOPs. ASCT then uses the function my_read. It loads 8 bytes of a line and then runs an empty loop of N rounds [Ref5].
  • All three count 64 bytes per line. So a rate in this report is a rate of lines: 64 GB/s is 1.0 × 109 lines per second for each loop.

The machine code of the ASCT read loop on CRB, from the installed binary (8 loads, then 3 loop instructions):

The window of a loop matters for question 2. The work of 2026-11-15 estimated how many lines one window covers: 18 to 22 lines for the old read loop and 36 to 40 lines for the new read loop [Ref3]. The ASCT read loop has fewer instructions per line than both. So its window covers more lines than that of the new read loop (est., not measured for this loop).

2. Question 1: the small gain of the new read loop at 8 MiB

The runs of this section use one thread on one CPU. One process gives one rate.

  • ASCT read: 16 buffer sizes on CPUs 2 and 41, 8 processes per size and CPU, measured phase 0.25 s [Ref9] [Ref10].
  • Old read and new read: the values of 2026-11-15 on the same two CPUs [Ref2]. They were not run again in this work.
  • Load of CRB: the 1-minute load average at the start of the 800 processes was 0.08 to 1.22. At most 3 tasks were runnable. A load near 1 is the test itself (est.) [Ref10].
  • The ASCT loop loses about 40 % from 1 MiB to 8 MiB. It reads 95.9 GB/s at 1 MiB and 57.2 GB/s at 8 MiB on CPU 2 and 95.3 GB/s at 1 MiB and 58.1 GB/s at 8 MiB on CPU 41 [Ref10].
  • Prediction P-A1 holds on both CPUs. It said that the ratio of the two rates is below 0.90. The ratio is 0.596 on CPU 2 and 0.609 on CPU 41 [Ref8].
  • The Arm reference machines show the same fall. The ASCT loop reads 93.1 and then 57.3 GB/s on machine A0 (ratio 0.616). It reads 106.5 and then 63.5 GB/s on machine A1 (ratio 0.596). Each value is one process of the vendor run [Ref11].
  • Our loops for comparison. The new read loop reads 85.2 GB/s at 1 MiB and 71.0 GB/s at 8 MiB on CPU 2 (ratio 0.833). The old read loop reads 67.1 and 67.0 GB/s (ratio 0.999) [Ref2].
  • The order of the loops turns around. At 1 MiB the order on CPU 2 is ASCT read (95.9 GB/s), new read (85.2), old read (67.1). At 8 MiB it is new read (71.0), old read (67.0), ASCT read (57.2).
  • The ASCT loop shows one rate at 8 MiB. Its 8 processes lie within 57.18 to 57.25 GB/s on CPU 2 and 58.03 to 58.08 GB/s on CPU 41. On 2026-11-15 the new read loop moved between two rates at 8 MiB: about 67.5 and 71.1 GB/s on CPU 2, about 69.1 and 71.6 GB/s on CPU 41 [Ref2].
  • No step at 8 MiB. The ASCT rate falls at every size step from 2 MiB to 32 MiB on both CPUs. The fall from 6 MiB to 8 MiB is 2.33 GB/s on CPU 2 and 2.36 GB/s on CPU 41. The fall from 8 MiB to 12 MiB is 2.10 GB/s on CPU 2 and 2.15 GB/s on CPU 41.

Core counters: cost per line

The counted runs use the probe build and the ASCT capture code. Each cell has 2 processes per event set. Every value below is a count per 64-byte line of the measured phase [Ref6] [Ref9].

  • L2 refills per line is the share of lines that enter L2 from outside, which means from the SLC or from memory. The work of 2026-11-15 named it r.
  • Check of the counted runs. The rate of the counted processes differs from the rate of the uncounted processes by at most 0.9 % on CPU 2 and 1.0 % on CPU 41 over the 16 sizes.
  • Clock. Cycles per line times lines per second gives 2.798 to 2.799 GHz on CPU 2 and 2.798 to 2.799 GHz on CPU 41 at every size.
  • Fitted cost of the ASCT loop (item D-A2 of the decisions file). Cycles per line = 1.69 + 1.76 × r (largest distance of a point from the line: 0.14 cycles) on CPU 2 and 1.71 + 1.69 × r (largest distance of a point from the line: 0.12 cycles) on CPU 41, over the 13 sizes from 1 to 32 MiB [Ref8] [Ref10].
  • Fitted cost of the new read loop on 2026-11-15. Cycles per line = 2.09 + 0.66 × r on CPU 2 and 2.08 + 0.65 × r on CPU 41 [Ref2].
  • The ASCT loop is cheaper while the lines come from L2. Its fixed cost is 1.69 cycles per line against 2.09 for the new read loop (CPU 2). It has half the instructions per line.
  • The ASCT loop pays more for a line from outside L2. It pays 1.76 cycles against 0.66 for the new read loop (CPU 2). That is 2.7 times as much.
  • Both loops take the same share of lines from outside L2. At 8 MiB r is 0.815 for the ASCT loop and 0.827 for the new read loop (CPU 2). So at this size r is almost the same for both loops.
  • Cost at 8 MiB. The ASCT loop needs 3.13 cycles per line, the new read loop 2.52, the old read loop 2.67 (CPU 2) [Ref2] [Ref10].

Core counters: the prefetchers

CRB lists 9 prefetch events for the data caches. All 9 were counted at all 16 sizes on both CPUs [Ref9] [Ref10].

  • l1d_cache_hwprf, l2d_cache_hwprf: prefetches of the hardware prefetcher of L1 and of L2.
  • l2d_cache_l1hwprf, l2d_cache_refill_l1hwprf: L2 accesses and L2 refills that the L1 prefetcher caused.
  • 5 events for prefetch instructions (l1d_cache_prfm, l1d_cache_refill_prfm, l2d_cache_prfm, l2d_cache_refill_prfm, prf_spec). All 5 are 0 at every size. The ASCT loop holds no prefetch instruction.
  • l1d_cache_lmiss_rd, l2d_cache_lmiss_rd: long-latency read misses of L1 and of L2. They show the result of prefetching: a line that arrived in time causes no long-latency miss.

The ASCT loop with injected NOPs: a test of the prefetch explanation

Injected NOPs slow the ASCT loop down by a known amount. With N injected NOPs the loop has 6 + 3 × N instructions per line. The counters give 9.0, 12.0 and 18.0 instructions per line for N = 1, 2 and 4 [Ref5] [Ref10].

  • Part N, no counters: 1, 2, 4 and 8 injected NOPs at 32 KiB, 1 MiB and 8 MiB, 4 processes per CPU and cell [Ref9].
  • Part NC, with counters: 1, 2 and 4 injected NOPs at 1 MiB and 8 MiB, 6 processes per CPU and cell (2 for each of 3 event sets). This part was defined after the first data. Its prediction P-A5 was written before its own data [Ref8].
  • Load of CRB for part NC: 1-minute load average 1.14 to 1.25 at the start of the 72 processes, at most 2 runnable tasks [Ref10].

5. What ASCT can capture, and what was captured

The request asked for every counter and register that ASCT can capture. ASCT has four ways. One gave data without root. The other three need root or a kernel module, and they gave nothing in this work.

  • Core counters: captured. The probe build contains the ASCT capture code named dietperf. It reads a list of raw event codes from the environment variable DIETPERF_PMUv3 [Ref6]. It counts in user mode. It counts only the measured phase of each thread. It needs no root. This work counted 43 events in 7 sets of 7 [Ref9]. The sets include the 9 prefetch events that CRB lists for the data caches: 4 for the hardware prefetchers and 5 for prefetch instructions. Not counted: 2 events for address-translation work caused by prefetch instructions, and the events of the instruction cache.
  • The front-end switch for core counters: not used. The switch ASCT_DEBUG_ENABLE_PMU=1 selects a fixed list of events. That list holds no prefetch event [Ref6]. So the runs passed their own event codes to the capture code.
  • Mesh counters: not captured. The ASCT capture code has a setting for mesh counters (DIETPERF_CMN). It opens them as system-wide events [Ref6]. CRB allows system-wide events to root only (the kernel setting perf_event_paranoid is 2) [Ref10]. So the benchmark itself would have to run as root. The plan was to read the same kernel counters with the Linux command perf stat -a as root, while the benchmark runs without root. That root command was refused by the permission system of this agent session.
  • Core registers: not captured. The report asct report sysreg needs a kernel module that shows registers under /sys/kernel/sysreg. CRB has no such folder [Ref10]. The ASCT source lists three core types for this report (Neoverse N1, N2 and V2). The core type of CRB is not in that list [Ref6].
  • Mesh registers: not captured. The report asct report cmn reads the mesh registers through /dev/mem as root [Ref6]. Its option --detect also puts a load on every CPU in turn, which includes the isolated CPUs 126 and 127. No root command ran in this work. So this report was not run. The layout of the mesh is known from the kernel record of 2026-11-02 [Ref14].

Insufficient data on the prefetcher settings. No run of this work read a control register of a prefetcher. The measurement that would resolve it: the register report of ASCT after Arm supplies the kernel module with support for this core type, or a statement from Arm on the prefetcher settings of firmware v0.7.2.

7. Open items

  • Mesh, SLC and hop counters for the ASCT loop. They need an approval of a read-only root command on CRB (sudo perf stat -a on the units arm_cmn_0 and arm_cmn_1). The scripts and run lists are ready [Ref9]. Run time: about 20 minutes (est.).
  • Registers. ASCT can read core registers only with a kernel module that CRB does not have, and its mesh register report needs root and /dev/mem. A statement from Arm on the prefetcher settings of firmware v0.7.2 would also answer it.
  • Firmware. The Arm reference machines with firmware v0.9.0 and two NUMA nodes do not show the slow whole-chip state. The same ASCT runs on CRB after a firmware change would show whether the firmware is the cause.
  • Prefetch counters for our own loops. This work counted the prefetch events for the ASCT loop only. The same 7 event sets for the old and the new read loop would complete table 4.
  • The two rates of the new read loop at 8 MiB stay open from 2026-11-15. The ASCT loop shows one rate.
  • The spread of the ASCT loop with 2 injected NOPs at 1 MiB (58 to 87 GB/s between processes) is not explained.
