Why the whole-chip read rate fell with the new test loop: easy read

CRB, 120 threads. The investigation ran on 2026-11-15. The original run is from 2026-11-13. This page is the simple version of the full report [Ref2]. All numbers come from the facts sheet [Ref1].

Short version

The benchmark has read, write and copy loops, and with 120 threads only the read total dropped by a large amount: about 300 GB/s with the new loop against about 468 GB/s with the old loop (36 % lower).

The new read loop holds only loads, and each core then works on 36 to 40 cache lines at one time instead of 18 to 22.

The total is 230 to 310 GB/s above about 30 lines, 459 to 480 GB/s at 12 to 28 lines, and 543.9 to 549.0 GB/s (the highest measured) at 8 to 12 lines, and the rule inside the core that causes this is not established.

1. The goal

The problem

  • The benchmark got new test loops for read, write and copy.
  • The new loops were made to do less work per byte. For example, the new read loop has no adds.
  • An earlier test run used old and new loops with 120 threads on CRB [Ref3].
  • The read total and the write total were lower with the new loops. The copy total was not lower in that file.

Why it is a mystery

  • Less work gave a lower rate. The new read loop does only loads. It was expected to be at least as fast as the old loop.
  • With threads on one mesh there is no drop. 64 threads on mesh 0 read 348.0 GB/s with the old loop and 348.4 GB/s with the new loop [Ref8].
  • More threads gave a lower total. The new loop reads 445.0 GB/s with 64+32 threads and 300.1 GB/s with 56+56 threads [Ref8].
  • The goal: find which drops are real, and find the cause.

2. The answer in one chart

  • Each point is one read loop, run with 120 threads (64+56).
  • The horizontal position is the window depth: how many cache lines the core works on at one time.
  • The vertical position is the total read rate.
  • The old loop is fast for a reason that nobody intended. Its 8 vector adds per 128 B fill the window. So its window covers only 18 to 22 lines.
  • The new loop removed the adds. Its window covers 36 to 40 lines. This is above the limit of about 30 lines.
  • The remedy is verified. 72 to 192 nop per 256 B give 459 to 480 GB/s. 256 nop give 543.9 to 549.0 GB/s. This is 17 % above the old loop.
  • The best point is not known. The loop with 8 to 12 lines gave the highest total. No loop with fewer than 8 lines was tested.
  • Write and copy are not part of this. Copy did not drop. Most of the write drop comes from the stop rule of the benchmark (step 1).

How to read the table

  • Window. A window is not one pass of the loop. It is a part of the core: the list of instructions that the core has fetched and has not yet finished. On CRB it holds up to 684 nop. Several passes of a loop fit in it at one time.
  • Window depth. The number of 64 B cache lines that the loads inside one full window touch. The core can request all these lines from memory at one time. Example: about 9 to 10 passes of the new loop fit in the window, and each pass reads 4 lines, so the depth is 36 to 40 lines.
  • Sum of the read rates. 120 threads run at the same time: 64 threads on CPUs 0 to 63 and 56 threads on CPUs 64 to 119 (written 64+56). The value is the sum of the rates of all 120 threads.
  • Timed intervals (n). The number of timed measurements behind the row. The rate column shows the lowest and the highest of these n measurements.

1Did read, write and copy all drop?Idea held

Question
  • Read and write looked lower. Copy did not. Is each of these three results real?
Idea
  • The benchmark uses the whole-pass stop.
  • With this rule the threads stop at different times.
  • This can move a total without any change in the chip.
Test
  • Run old and new loops with a common stop at 64+56 [Ref4].
  • Compare write under two stop rules (whole-pass stop, common stop), each with intervals of 0.5 s and 15 s. These are earlier runs with 64 processes. Each case has 64 intervals [Ref5].
Result
  • Copy: 152.4 to 153.6 GB/s for all loops. No drop.
  • Write, earlier runs, whole-pass stop at 0.5 s: old is 21.5 % above new (medians 144.1 and 118.6 GB/s).
  • Write, earlier runs, common stop: old is 3.7 % above new at 0.5 s (medians 126.4 and 122.0 GB/s) and 3.1 % above new at 15 s (126.6 and 122.8 GB/s). The percentages are copied from the facts sheet.
  • Write at 64+56 with a common stop: old 126.1 to 126.8 GB/s, new 121.3 to 129.3 GB/s (2 intervals per loop) [Ref4].
  • Read: 465.5 to 470.1 GB/s (old) against 288.5 to 309.8 GB/s (new). This drop stays [Ref6].
  • So only read dropped by a large amount. Copy did not drop. Write keeps a small difference of 3 to 4 %.

2What in the loop decides fast or slow?Idea A rejected, idea B held

Question
  • The old loop has 8 vector adds per 128 B. The new loop has none. Do the adds matter?
Idea
  • Idea A: the adds must wait for the loaded data, and this slows the loads down in a useful way.
  • Idea B: enough extra instructions of any kind help, also instructions that do nothing.
Test
  • Build 26 new loop variants in a copy of the test program [Ref13].
  • Add vector adds that use the loaded data. Add vector adds that do not use it. Add nop instructions.
  • Measure each variant at 64+56 [Ref6].
Result
  • 16 adds per 256 B that use the data: 466.7 to 469.8 GB/s.
  • 16 adds per 256 B that do not use the data: 469.2 to 469.7 GB/s. This is the same.
  • 72 to 192 nop per 256 B: 459 to 480 GB/s. 256 nop per 256 B: 543.9 to 549.0 GB/s.
  • 32 to 56 nop per 256 B: 284.8 to 309.1 GB/s. This is too little filler.
  • Software prefetch instructions: 289 to 316 GB/s. They do not help.
  • Idea A is rejected. Idea B held: the kind of filler does not matter, the amount does.

3Why does filler help?Idea held

Question
  • What does a nop change, when it does no work?
Idea
  • The window of a core holds a fixed number of instructions.
  • Filler takes places in the window. Then fewer loads fit in the window.
  • So the window covers fewer lines.
Test
  • Measure the window with one thread [Ref7].
  • Measure, for each loop, how many lines one full window covers.
Result
  • The window holds 684 nop, or 159 instructions that write a vector register.
  • Old loop: 18 to 22 lines. New loop: 36 to 40 lines.
  • All loops with a range at or above 32 to 34 lines are slow. All loops with a range at or below 24 to 28 lines are fast.
  • Four loops lie between these (26 to 32 lines). Two are slow and two are in between (325.5 to 366.6 GB/s).
  • The adds of the old loop use up the vector-register places of the window (159 places). The old loop is fast for this reason, not because the adds wait for data.
  • This is the chart of section 2.

4Is it the same in other thread layouts?Idea held

Question
  • Does a padded loop behave like the old loop everywhere?
Idea
  • If the window depth is the cause, a padded loop with a similar depth follows the old loop in every layout.
Test
  • Run the old loop, the new loop and two padded loops in 7 layouts [Ref8].
  • Each pair of loop and layout has one interval.
Result
  • Both padded loops (96 nop and 128 nop) are within 2.3 % of the old loop in all 7 layouts.
  • 64+0 (mesh 0 only): old 348.0 GB/s, new 348.4 GB/s. No drop.
  • 56+56: old 534.8 GB/s, new 300.1 GB/s.
  • The drop exists only with many threads on both meshes.

5Do deep-window cores take from the others?Idea held

Question
  • Does the rate of a thread depend on the loop of the other threads?
Idea
  • A core with a deep window requests more lines ahead. It may take a larger share of the memory traffic.
Test
  • Run two processes at the same time, one per mesh, with different loops [Ref9].
Result
  • New loop on mesh 0, 256-nop loop on mesh 1: mesh 0 reads 349.8 GB/s, mesh 1 reads 108.2 GB/s.
  • Mesh 0 alone with the new loop reads 348 GB/s. So mesh 0 reads as if mesh 1 were idle.
  • 256-nop loop on both: 327.4 and 221.8 GB/s (total 549.1 GB/s).
  • New loop on both: 175.7 and 127.2 GB/s (total 302.9 GB/s).
  • The deeper window takes the larger share. When all cores have a deep window, all are slow.

6Is the chip congested in the slow state?Idea rejected

Question
  • Are the mesh or DRAM overloaded in the slow state?
Idea
  • Too many requests fill the queues of the mesh. Requests are retried. DRAM does wasted reads.
Test
  • Read the counters of the mesh and of the 24 memory ports with root rights [Ref11].
  • Measure the time of one memory request on one core per mesh, while the other 118 cores read [Ref10].
Result
  • DRAM gets 1.00 read request per line in the slow state and 1.00 in the fast state with 96 nop. The 256-nop loop has 1.08. So the slow state wastes no read.
  • Request retries per line: 0.047 (slow) against 0.072 (fast). The slow state has fewer.
  • One exception: data-link stalls to the north and south are higher in the slow state (north: 0.119 against 0.069 per line).
  • One memory request takes 203 to 211 ns with the new loop on all cores (slow) against 238 to 287 ns with a padded loop on all cores (fast). The slow state is quicker.
  • Lines in flight per core: 6.5 to 9.2 (slow, est.) against 14.9 to 25.3 (fast, est.).
  • No queue and no memory port is congested. In the slow state the cores keep fewer requests outstanding.

7Is the deep window alone enough?Idea held

Question
  • Is the cause the number of lines in the window, or the way a core treats a stream in address order?
Idea
  • A core treats a stream in address order in a special way (the prefetcher follows it).
  • If this is part of the cause, the same loads in a scrambled order do not show the drop.
Test
  • Read the same bytes with the same loads, but visit the 256 B blocks in a scrambled order [Ref12].
  • One interval of 10 s per loop and order at 64+56. One scrambled order was tested.
Result
  • Address order, load-only loop: 297.8 GB/s.
  • Scrambled order, same loads: 489.6 GB/s.
  • In scrambled order the deep window is the faster one (489.6 against 382.5 GB/s with 256 nop).
  • In this run the drop needed a deep window and address order together.
  • Hypothesis: a core limits its own requests for a stream in address order (section 4). Steps 6 and 7 fit this. They do not prove it.

4. What is still open

  • The exact rule inside the core. Insufficient data. Hypothesis: the core lowers its limit of outstanding requests, or its prefetcher asks for less, for a stream in address order. The manual of an older core type (Neoverse V2) documents such controls. Three things can resolve it. First: read two control registers of the core on CRB. This needs a kernel module or firmware access. The approval for this task did not cover either. Second: read the prefetch section of the manual of this core type (Neoverse V3AE). Third: ask Arm, with the data of steps 5 and 6.
  • The write total with writers on both meshes. Write falls from 455 GB/s on one mesh to 120 to 129 GB/s at 64+56. This is the same for old and new loops. Insufficient data on the cause.
  • The 3 to 4 % by which old write stays above new write with a common stop. Insufficient data on the cause.

5. Limits of the data

  • One machine. All new runs are from one evening: 2026-11-15, 16:56 to 21:03 UTC. Figure 1 is the original run of 2026-11-13. The write comparison under two stop rules (step 1) uses earlier runs with 64 processes.
  • System load: the 1-minute load average was 0.00 to 71.24 at the start of the scripts, and up to 109.60 at a process launch (101 launches). The high values follow the scripts' own earlier 120-thread processes (hypothesis, not checked further). At every launch 1 task was runnable and 0 users were logged in [Ref14].
  • Steps 4 and 7 have one interval per measured case.
  • Step 7 tested one scrambled order. The window depth of the scrambled loops was assumed equal to the address-order loops. It was not measured.
  • Lines in flight (step 6) are estimates: lines per second of a thread times the time of one probe request.
  • The benchmark source bench/bandwidth.c was not changed. The new loop variants are in two copies of the test program [Ref13].
