Parts B and C, question Q2: 64+56 threads at 256 MiB

Short version. With 64 threads on one half of the test server CRB and 56 on the other, each reading its own 256 MiB buffer, the old read loop moved 158.1 to 167.5 GB/s more in total than the new read loop (median per timing setting, resolved in 8 of 8 settings of step B7, 1 session), while two copies of one loop differed by at most 6.6 GB/s. 0 of 12 single changes of the timing method (stop method, interval length, start position) changed that difference by a resolved amount, so the timing hypotheses for read are "not rejected" (H7a) and "not rejected" (H7b) only because one session cannot give "rejected". For the write loops the same hypotheses are "not rejected" and "not rejected" and H11 is "not rejected", H8 is "not resolved" and H9a is "not resolved" (they need pattern labels that are not used), H9b is "not tested", and H10 is "not tested" (the root counters of Part D were not run).

Question Q2 comes from the benchmark run of 2026-11-13: old read totalled 464 to 467 GB/s with 120 threads, new read 280 to 304 GB/s, and the write kernels gave several separate totals [Ref1]. This page gives the results of the steps B7, B10, B8, B5, B9 and C3 for that question. The decision rules are those of the handoff, applied by the analysis script [Ref2][Ref3].

Input: session s1 with 7 result folders (B7, B10, B8, B5, B9, C3). No step is missing. The page holds one session. Every "rejected" is impossible with one session, because rule 11 of the plan needs both sessions.

Words used here

  • CRB: the Arm Phoenix Reference Server (128 cores, AArch64). All measurements ran there.
  • Plan, handoff: the files plan.md (the reviewed test plan) and handoff.md (the instructions for its execution).
  • Part A, B, C, D: the parts of the plan. Part A: screening with the existing benchmark. Part B: the changed benchmark. Part C: core counters without root. Part D: counters and page addresses that need root. Part D was not run.
  • Q2, Q2a, Q2b: the second question of the plan. Q2a: why old read has a higher total than new read with 120 threads. Q2b: why the write kernels give several separate totals.
  • bwx: the changed copy of the benchmark bandwidth.c that Parts B and C use. It holds the old kernels, the new kernels and all variants in one program.
  • Kernel: one timed loop of the benchmark. It is not the Linux kernel.
  • Old read (oldread): the read loop before 2026-11-13. Per 128 B it runs 4 load instructions (ldp, 32 B each) and 8 vector adds.
  • New read (read): the read loop since 2026-11-13, written in C. Per 256 B it runs 8 ldp and no add.
  • asm read (asmread), asm read 2 (asmread2): the read loop written in assembly, with the same loop body as new read, and a second copy of it under another name.
  • Old write, new write, asm write, asm write 2: the write loops in the same four forms (oldwrite, write, asmwrite, asmwrite2).
  • nop: an instruction that does nothing.
  • read_nop4, read_nop8, read_nop16, read_nop32: the asm read loop with 4, 8, 16 or 32 nop instructions added per 256 B.
  • read_sparse: a read loop with 4 ldp and 9 nop per 128 B. It has the 16 instructions per 128 B of old read and no vector add.
  • Loop offset: the address of the first instruction of a loop modulo 64 B.
  • Process, launch: one start of bwx. Its name in the run script is its tag.
  • Sequence, interval, round, position: a process times a list of kernels (the sequence), one interval per entry. A round is one run of the whole sequence. The position counts the entries from 0.
  • Pass: one sweep of a thread over its whole buffer.
  • Process value: one number per process, for example the median total of its intervals. Decisions use process values, never single intervals.
  • Warm-up pass: one pass that a thread makes with the kernel before the timed interval starts. It is not timed.
  • Header line, env.txt, launches.txt: the run script writes one header line per launch into the csv file, with the load readings. env.txt holds the readings at the start and the end of a visit. launches.txt holds a second reading and the 5 busiest processes before each launch.
  • Root: administrator rights on CRB. Our scripts do not use them.
  • Session: one run of all steps. The plan asks for two sessions some hours apart.
  • 256 MiB, GB/s: each thread has its own buffer of 256 MiB (1 MiB = 220 bytes), which is read from main memory. Rates are in GB/s (1 GB = 109 bytes).
  • Mesh 0, mesh 1: the two halves of the chip. CPUs 0 to 63 are on mesh 0. CPUs 64 to 127 are on mesh 1, and we use 64 to 119.
  • a+b threads, 64+56: a threads on mesh 0 and b threads on mesh 1. 64+56 is all 120 CPUs that we may use.
  • Thread rate: the bytes of one thread divided by its own elapsed time.
  • Total, M_hist: the bytes of all threads divided by the longest elapsed time of a thread. This is what the benchmark prints. It is the decision metric.
  • M_sum: the sum of the thread rates. It is reported next to M_hist as a description.
  • Median: the middle value of a sorted list. With an even count it is the mean of the two middle values.
  • q: the thread rate at the 10th percentile divided by the thread rate at the 90th percentile, in one interval. With 120 threads these are the 12th and the 108th smallest rate. q near 1 means that all threads have nearly the same rate.
  • Split, uniform: the two pattern labels of the handoff (q below 0.65, q above 0.85). They are not used on this page.
  • Setting: one combination of stop method, interval length and start.
  • Stop method: "whole passes": a thread stops after a whole pass, as in bandwidth.c. "common stop": all threads stop at one common time and count the bytes of the partial pass.
  • Start: "common start": every thread starts at the start of its buffer. "offset start": every thread starts at its own offset inside its buffer.
  • Reproduction condition: the setting "whole passes, 0.5 s, common start". It is the timing method of the run of 2026-11-13.
  • 2 % check: rule 7 of the plan for whole passes: one pass must take at most 2 % of the interval. That means at least 50 passes per thread.
  • D: the total of old read minus the total of new read, in GB/s. One value per process: the mean over its rounds.
  • A/A control, A/A spread, E: an A/A control is one loop that exists twice in the program (asm read and asm read 2). E is the difference of the two copies in one process. The A/A spread is the largest absolute E over the processes of a setting.
  • Resolved: the absolute median of the process values is larger than the A/A spread, and all process values have one sign. A change between two settings is resolved if it is larger than the sum of the two A/A spreads and the two sets of values do not overlap.
  • Spread (B10): for one write kernel in one process: the highest minus the lowest total of its 4 intervals.
  • Controls (B10): three values from asm write and asm write 2: the control of the spread, of the total, and of the rate of each mesh.
  • Irregular interval, late, end skew: a thread is late if it starts more than 100 µs after the common start. The end skew is the latest end minus the earliest end of the threads. An interval is irregular if a thread is late or if the end skew with the common stop is above 5 ms.
  • Page state, P row: how many bytes of a buffer are on 2 MiB pages (huge-page coverage), read from /proc/self/smaps and printed in a P row.
  • I row, T row, C row: output rows of bwx. I: one per interval. T: one per thread and interval, with bytes and times. C: one per thread and interval with the counter values.
  • Counter, cycles, refill, last-level read miss: a counter is a hardware event counter of one core. Cycles are clock ticks of the core. An L1 or L2 refill is a line that the first or second cache level of the core had to fetch. A last-level read miss is a read that the last cache level did not hold.
  • Line: 64 B, the unit of a cache.
  • Clock: cycles of an interval divided by the CPU time of the thread in that interval, in GHz.
  • CPU time: the time for which a thread really ran on its CPU (the thread CPU clock of Linux).
  • Load, runnable tasks, waited, logins: the Linux 1-minute load average (average count of tasks that run or wait to run), the count of tasks that can run at one moment, the time the script waited for a quiet system before a launch, and the count of logged-in users.
  • B7: step: the four read kernels at 64+56 threads in all 8 settings, and the reproduction condition with one kernel per process.
  • B10: step: the four write kernels at 64+56 threads in 8 settings, with 0.5 s and 15 s as the two intervals.
  • B8: step: old read, asm read and asm read 2 at 64 threads on mesh 0 and 32 to 56 threads on mesh 1.
  • B5: step: old read against new read, read_sparse, the four nop variants and asm read at 64+56 threads.
  • B9: step: old read with one buffer and with two buffers per thread.
  • C3: step: the sequences of B7 and B5 with core counters.
  • D1: step of Part D: counters of the mesh (the network that joins the cores and the memory), which need root. Not run.
  • H7a: hypothesis: a part of the difference is made by the stop method and the short interval.
  • H7b: hypothesis: a part of the difference is made by the common start.
  • H8: hypothesis: with threads on both meshes the chip has two states. A loop that only loads reaches the uniform state at a lower thread count than old read.
  • H9a: hypothesis: the second buffer per thread moved old read to the uniform pattern on 2026-10-30.
  • H9b: hypothesis: the pattern of old read differs between days or sessions for a reason other than the kernel.
  • H10: hypothesis: in the uniform state the memory system fetches lines that the loop does not consume.
  • H11: hypothesis: the write totals differ because the threads of one mesh run faster in some intervals.
  • H3b: hypothesis of question Q1: the physical address of the pages decides the level at 8 MiB.
  • The five words: rule 11 of the plan. "rejected": the bounded prediction failed in both sessions. "not rejected". "not observed": an event that the test could have shown did not occur. "not resolved": the difference is inside the A/A spread, or the rule cannot be applied. "not tested".
  • Supported, contradicted: the words of the plan for B8 and H11. This page writes "not rejected" and "rejected" and adds the word of the plan in brackets.
  • est.: an estimate, not a measurement.

Local rules of this page

  • L1. The labels split and uniform are not used. This is a decision of the user of 2026-11-13. The reason is that q did not fall into two groups in Part A [Ref5]. A rule that needs a label gives "not resolved". The page reports q and the median thread rate of each mesh in its place.
  • L2. The analysis gives H11 one result per kernel and setting (a cell). The word of the table is "not observed" if every cell is "not observed". It is "rejected" if every cell with another word is "rejected". It is "not rejected" if at least one cell is "not rejected" and none is "rejected". Otherwise it is "not resolved".
  • L3. H9b needs at least two sessions. With two or more, the word is "not observed" if the ranges of q of old read at 64+56 threads overlap between the sessions. Otherwise it is "not resolved", because a change of pattern cannot be named without labels.
  • L4. H10 is "not tested". The plan gives the counters of C3 no decision, and step D1 was not run [Ref1].

H10 and H9b: what these data can and cannot say

H10: "not tested"

  • Can say: how many refills of its own caches a core counted for each 64 B line that the loop read, per kernel and mesh. The section of C3 gives these values.
  • Cannot say: whether the memory system fetched lines that the loop did not consume. The core events count refills that the core saw. The plan states that H10 could still hold for traffic that these events do not count [Ref1].
  • Insufficient data: memory requests per line read. Step D1 would give them (mesh counters hns_mc_reqs_local_all and hns_mc_reqs_remote_all, with root). Part D was not run. Even D1 can support H10 and cannot reject it [Ref1].

H9b: "not tested"

  • One session (s1) has data. A comparison between sessions needs at least two.
  • Can say: whether q and the median thread rates of old read at 64+56 threads were the same in the sessions that were run.
  • Cannot say: why old read gave totals of 365 to 368 GB/s on 2026-10-30 [Ref1]. That run is a number from an earlier result folder. Rule 10 of the plan uses such a number for hypotheses only, not as evidence.
  • Cannot say: anything about other days. The sessions of this page lie some hours apart.
  • Insufficient data: the same steps on another day, and after a restart of the machine. They would show whether the values of old read change for a reason other than the kernel.

Limits of this page

  • No value on this page is the traffic of the time in which all threads ran. A thread records only its total, so the bytes of the common time are not measured [Ref2]. Rule 6 of the plan is met only in part.
  • The page state of an interval with many threads is the reading taken after the interval before it. A change during the warm-up pass shows only in the next reading [Ref2].
  • A thread that is off its CPU inside an interval is not flagged in a run without counters. This was found in the short run [Ref16]. Only C3 has the CPU time of each thread.
  • With 120 threads the main thread of bwx has no CPU of its own. It shares a CPU with a worker [Ref15]. Insufficient data: the size of this effect on CRB. A run with the main thread on a spare CPU would give it, and the rules of the host allow CPUs 0 to 119 only.
  • The loop of read_sparse starts at 4 modulo 64, and the other asm read loops start at 20 [Ref10][Ref15]. So B5 compares read_sparse at another loop offset.
  • Part D (root counters, physical pages) was not run. So H3b of question Q1 is "not tested", and H10 is "not tested" [Ref1].
  • The limits 100 µs and 5 ms for an irregular interval are provisional [Ref2].
  • One session only. Every result is the result of that session. "rejected" needs a second session [Ref1].
  • Insufficient data: load readings during an interval. The script reads the load only before each launch.
  • The chart colours were not checked with the palette checker of the chart rules, because Node.js is not installed on the machine where this page was built. Every chart also uses position, marker shape or a text label.
