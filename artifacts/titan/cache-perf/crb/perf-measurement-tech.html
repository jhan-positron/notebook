Cache and DRAM Measurement Techniques

How the benchmark isolates each level of a 128-core Arm server's memory hierarchy, with the code that does it. Written for an engineer who wants to build the same measurement by hand.

Short version. A bandwidth number is only meaningful when you know which hop in the data path limited it. The benchmark isolates that hop with three measurement variables, changed one at a time: the footprint per thread (hence the cache level), the instruction mix (loads-only, stores-only, or compiled loop), and the thread placement (a shared port, one mesh, or the chip link). Hardware counters, taken as the difference of a short and a long run, then confirm where each line was served.

Words used here

CRB: the Phoenix Reference Server, 128 Neoverse V3AE cores at a fixed 2.8 GHz, one socket; CPUs 0 to 119 may be used.
Footprint: the bytes one thread streams over, per pass; the measurement variable that picks the cache level.
L1, L2: the private per-core caches, 64 KiB (4-way) and 2 MiB (8-way), 64 B lines.
Mesh cache, SLC: Arm's System Level Cache, 128 slices of 1 MiB (est.), which Linux reports as one 128 MiB L3; one core reaches 64 MiB of it.
CMN: Arm's Coherent Mesh Network, the on-chip grid of routers; CRB has two meshes (chiplets), arm_cmn_0 for CPUs 0 to 63 and arm_cmn_1 for CPUs 64 to 119.
XP: a crosspoint, one router of the mesh; its "ports" attach devices such as cores and home nodes.
Flit: a flow-control unit, the fixed-size piece of a mesh packet that one link moves per cycle; the mxp_*_txflit_valid events count them and mxp_*_txflit_stall counts cycles a flit waited.
HN-S: a home node, the owner of an address range; it holds one SLC slice and the coherence directory for its lines.
RN-F: a fully coherent requesting node, what a core is to the mesh.
SN-F: a memory-side port of the mesh, in front of a memory controller.
CCG: a chip-to-chip gateway, the link between the two meshes.
Pair port: cores 2k and 2k+1 share one XP port (measured, not documented).
Proxy: a home node on the core's own mesh that serves lines homed on the other mesh.
THP: transparent huge pages, 2 MiB pages the kernel gives without a request.
TLB: translation lookaside buffer, the core's cache of virtual-to-physical page translations; a miss costs a page-table walk.
PMU: a performance monitoring unit, the hardware counters read with perf stat; armv8_pmuv3_0 for a core, arm_cmn_0/1 for the meshes.
B/cycle: bytes per core clock, GB/s divided by 2.8; GB means 1e9 bytes, K/M/G in sizes are powers of 1024.
asm kernel: a hand-written loop of only loads or stores (asmread, asmwrite, asmcopy), next to the compiled C loops (read, write, copy).
x86 terms in the Elsewhere notes: AVX-512 and zmm (Intel's 512-bit vector instructions and their registers); SysV ABI (the x86-64 Linux calling convention); SMT (two hardware threads on one core); IMC (the memory controller on the chip); UPI (Intel's socket-to-socket link); uncore and CHA (the blocks outside the cores, and the caching/home agent that owns one L3 slice); APIC id (a logical CPU's hardware id).

3.1 Choosing the data-set size: one footprint per level

Half the level, four times the level above

  • 32 KiB for L1 (64 KiB), 1 MiB for L2 (2 MiB), 8 MiB for the mesh cache (4 × L2), 1 GiB for DRAM (8 × the 128 MiB SLC) with 1 to 8 threads, 256 MiB with 16 or more threads.
  • Half the level leaves room for stack and code, so a read or write stream does not spill. For copy the two buffers together equal the level exactly (2 × 32 KiB = 64 KiB, 2 × 1 MiB = 2 MiB), so a few sets also hold stack or static data. README puts that effect under about 1 %. Four times the level above keeps the level above from serving a large share of hits.
  • 256 MiB at 16+ threads keeps the resident total at 60 GiB at 120 threads (two buffers per thread, since all includes copy: under a fifth of the 320 GiB) and the first touch short: 120 × 2 × 1 GiB would take minutes (est.) to touch.
  • Sum over threads: the mesh-cache lists stop at 14 for read and write (14 × 8 MiB = 112 MiB) and at 7 for copy, which holds two buffers per thread (7 × 2 × 8 MiB = 112 MiB). That cap was sized against the 128 MiB Linux reports. One core reaches 64 MiB, and the counters showed 0.30 slice misses per line at 14 threads. The whole-chip mesh number was then taken with 40 threads × 3 MiB.

Pitfall: a footprint equal to the level (64 KiB for L1) shares sets with stack and static data, and the figure drifts toward the next level. 32 threads × 8 MiB is 256 MiB, twice the cache; the result is a DRAM number labelled as a cache number.

Elsewhere: read /sys/devices/system/cpu/cpu0/cache/index*/size and shared_cpu_list, then apply the same ratios. Keep threads × footprint under about three quarters of the shared capacity that one core can reach, then confirm with the last-level miss counter.

2 MiB-aligned buffers with an explicit huge-page request

  • alloc_buf rounds the length up to a 2 MiB multiple, maps one extra 2 MiB, aligns the start to a 2 MiB boundary, and asks for MADV_HUGEPAGE.
  • With 4 KiB pages a 1 GiB buffer is 262,144 pages. The page-table walks that refill the TLB then become part of the measurement. With 2 MiB pages it is 512 pages.
  • --no-thp asks for MADV_NOHUGEPAGE, the only way to get 4 KiB pages on CRB where THP is set to "always"; it is the control for the TLB share of a number.

Pitfall: a malloc buffer is page aligned at best. On CRB (THP "always") its first and last partial 2 MiB are therefore 4 KiB pages. On a THP "madvise" host the whole buffer is 4 KiB pages.

Elsewhere: same code on x86-64 Linux. Confirm with AnonHugePages in /proc/self/smaps_rollup after the first touch.

Pin first, then allocate and first-touch on the owning thread

  • Each worker pins itself, maps its own buffer, and writes every byte of it with k_write before any timing starts. A copy run allocates and touches the second buffer the same way.
  • Page faults and the kernel's zero-fill happen before the timed loop, on the core that will stream the buffer. On a NUMA host (non-uniform memory access: each group of cores has its own nearer memory, and a page lives in the memory of the core that first writes it), this is also what places the pages. CRB has one NUMA node, so this does not apply here.
  • Pinning decides which core, port and mesh the stream starts from. It does not decide where the lines are homed: the address hash spreads every 2 MiB chunk half on each mesh.

Pitfall: one array allocated by the main thread and sliced among workers puts the faults into the first timed repetition and the pages on the main thread's NUMA node.

Elsewhere: sched_setaffinity in the worker before mmap, then a full write pass, is the standard NUMA first-touch recipe.

3.2 Load and store instructions: the hot loop

A loads-only loop: eight ldp (load pair) of 16 B registers per 256 B

  • The whole hot loop is one inline-asm block. So the compiler cannot add arithmetic, reorder or drop anything. The body is 8 × ldp (load pair: one instruction fills two 16 B registers, 32 B, from one address), add, cmp, b.lo: 11 instructions per 256 B.
  • Sixteen distinct destination registers let all eight loads be in flight at once. The only limit left is the core's 3 load pipes: 48 B/cycle = 134.4 GB/s at 2.8 GHz; measured 132.7 GB/s (99 %).
  • v8 to v15 are callee-saved in the Arm calling convention. Naming them in the clobber list (the third colon-separated list in the asm block, which tells gcc which registers the block overwrites) makes gcc save d8 to d15 once per call, outside the loop.

Pitfall: using v8 to v15 without listing them corrupts the caller's vector state. Using only v0 to v7 halves the loads per iteration and doubles the loop overhead per byte.

Elsewhere: on x86 use 8 × vmovups zmm, [mem+off] per 512 B; on the SysV ABI no vector register is callee-saved. Compare the result with pipes × width × clock before blaming a cache.

A stores-only loop: broadcast once, then eight stp of the same register

  • dup v0.2d fills one vector register with the 64-bit value before the loop label. The loop body carries no ALU work: 8 × stp q0, q0 (store pair: one instruction writes two 16 B registers, 32 B, to one address; here the same register twice), add, cmp, b.lo.
  • Bound: 2 store pipes × 16 B = 32 B/cycle = 89.6 GB/s. Measured 89.5 GB/s into L1 and into L2. The compiled C write loop reaches 44.0 GB/s, about one 16 B store per cycle.

Pitfall: a broadcast inside the loop, or stores from general registers (stp x0, x1, 16 B per instruction), adds issue slots or halves bytes per store, and the write figure lands below the pipe bound.

Elsewhere: vpbroadcastq zmm0, reg before the loop, then 8 × vmovups [mem+off], zmm0.

        "dup v0.2d, %[v]\n\t"
        "1:\n\t"

        "stp q0, q0, [%[p], #32]\n\t"
        ...

Copy: load all 256 B into 16 registers, then store them

  • Eight ldp fill q0 to q15, then eight stp drain them to the destination. Both pointers advance by 256 B; the loop ends on the source pointer only. 20 instructions per 256 B read and 256 B written.
  • Loading everything first lets the eight loads issue back to back without waiting on a store. Bound: 2 loads + 2 stores of 16 B per cycle = 64 B/cycle = 179.2 GB/s; measured 178.4 GB/s in L1.

Pitfall: interleaving one load with one store through two registers serialises each store behind its load.

Elsewhere: 8 loads into 8 zmm registers, then 8 stores. Never rep movsb or memcpy: their microcode and non-temporal paths are a different measurement.

The compiled read loop: 16 accumulators, and why it is still slower

  • k_read sums into 16 independent accumulators, which gcc folds into 8 vector chains on NEON (Arm's 128-bit vector instruction set). Eight chains hide the 2-cycle add latency. The loop is therefore not limited by add latency.
  • It is still issue-bound (limited by how many instructions the core can start per cycle): one vector add per load. Measured 66.8 GB/s at 32 KiB, which is 1.5 loads of 16 B per cycle (about 24 B/cycle), half of the asm loop. The report's hypothesis is the two vector pipelines; the confirming test (3 loads per 2 adds) was not run.
  • Keep both loops: the C loop is what application code looks like, the asm loop is the pipe upper bound.

Pitfall: with one accumulator the loop is bound by add latency and reports a fraction of either number. With only the C loop, L1 and L2 read look identical (66.8 vs 67.1 GB/s).

Elsewhere: on AVX-512 the 16 accumulators become 2 zmm chains; check the generated loop with objdump -d and count loads against arithmetic per iteration.

bandwidth.c:135-148, README.md:33-39

/* 16 independent accumulators keep the loop load-bound: on 128-bit NEON gcc
 * folds them into 8 vector chains, enough to hide a 2-cycle add latency;
 * on AVX-512 they become 2 zmm chains. */
__attribute__((noinline)) static uint64_t k_read(const uint64_t *a, size_t n)
{
    uint64_t s[16] = { 0 };
    for (size_t i = 0; i < n; i += 16)
        for (int j = 0; j < 16; j++)
            s[j] += a[i + j];
    uint64_t sum = 0;
    for (int j = 0; j < 16; j++)
        sum += s[j];
    return sum;
}

Keep the compiler out of the loop: noinline, a volatile sink, no memset folding

  • Every kernel is static and noinline. So each pass is one real call with runtime pointer and length. The read result goes to a volatile word. So the loads cannot be dead-code-eliminated.
  • The store value is built at runtime from the pid and thread index times a large odd constant, and the pass counter is added each pass. The value is not byte-repeating. gcc therefore cannot turn k_write into memset. The pass counter also makes each pass write different data.
  • The Makefile adds -fno-tree-loop-distribute-patterns as a second defence: it stops gcc from rewriting the write and copy loops as memset and memcpy calls. It also uses -march=native rather than -mcpu=native: gcc 14 on CRB resolves -mcpu=native to nothing.

Pitfall: a zero-fill loop at -O3 becomes memset. On arm64 glibc, memset of a large buffer uses DC ZVA (the Arm "data cache zero by address" instruction, which zeroes a whole cache line without going through the store pipes). The number is then not the application's store path.

Elsewhere: same flags on gcc; -fno-builtin on clang. Check the disassembly for calls to memset or memcpy and for rep stosb.

A per-thread sink on the thread's own stack

  • The read checksum is stored through a pointer to a volatile uint64_t that lives on the worker's stack.
  • One shared sink would be a cache line written by 120 cores after every pass. At 32 KiB per pass that is a coherence transfer every 0.25 µs per thread, which is the size of the thing being measured.

Pitfall: a global sink, or per-thread results packed into adjacent 8-byte slots, causes false sharing (several cores write different words of one 64 B line, so the line moves between their caches on every write). The many-thread L1 number then falls, and the drop looks like a mesh limit.

Elsewhere: every per-thread mutable word on that thread's stack or in its own 64 B (128 B on some cores) slot; write results back only after the timed window.

No tail loop: refuse sizes that are not a multiple of the loop's stride

  • The asm loops advance 256 B per iteration and test after the add. So a size that is not a multiple of 256 would run one iteration past the end. main refuses such sizes once, for every kernel.
  • A tail loop inside the kernel would be timed with the rest and would change the instruction mix at the end of every pass.

Pitfall: 100,000 B reads up to 255 B past the buffer: silent on a huge-page mmap, a fault or corruption on a tight malloc.

Elsewhere: with 8 × 64 B loads the stride is 512 B; reject other sizes at argument parsing.

Know when the core stops allocating: the write-streaming check

  • Arm cores can detect a long run of full-line stores with no loads and switch to a write-streaming mode that bypasses L1 and L2 allocation. The 32 KiB write would then be a number for the level below.
  • The test is a counter rate per pass: L1 and L2 refills near bytes / 64 mean the lines are not being absorbed by the level you think you measure. On CRB the asm write into L1 and L2 both reach the 89.5 GB/s store-pipe bound, above the 73.2 GB/s mesh write, so the mode did not pull those rows down.
  • run_sudo.sh part 5 counts the same family on CPU 2 with the write-only raw events 0x41, 0x43, 0x51, 0x53 (L1D and L2D cache and refill, write) plus bus and memory writes 0x61, 0x67.

Pitfall: a low 32 KiB write is blamed on a slow L1 when the core had stopped allocating there.

Elsewhere: non-temporal stores, or a memset that picks them, give the same symptom on x86; compare the L1D fill count per pass with bytes / 64.

3.3 Read and write patterns: causing hits, causing misses

  • Sequential streaming, whole passes. Every kernel walks its buffer start to end. The prefetcher therefore helps. The number is the throughput of the hop that saturates. This is a bandwidth pattern, not a latency one.
  • Hits by footprint. A pass fits in the level, and the untimed warm-up pass before every repetition loads it there. The timed passes then hit (0.000 slice misses at 8 MiB, 1 thread, in the bandwidth tool; the latency tool shows 0 L1 refills up to 64 KiB, and no counter run was taken on the bandwidth loop at 32 KiB).
  • Misses by footprint. 1 GiB per thread is 8 × the mesh cache, so every line misses every level: 0.99 last-level misses per load at 1 GiB in the latency tool, and 1.00 slice misses per line for the asmwrite 1 GiB stream at 14 threads (part 3), up from 0.75 at 8 MiB.
  • Misses by sum. 14 threads × 8 MiB fits "128 MiB" but not the 64 MiB a core reaches: 0.30 slice misses per line. The sum, and the reachable capacity, decide.
  • Writes do not behave like reads. A streaming write is not kept by the slice (0.013 fills per line) and goes to memory. So a "mesh write" footprint measures the DRAM write path. Read the counters before naming a write number after a cache.
  • Exclusive allocation shows in the counters. A slice hit removes the line from the slice; the later L2 eviction writes it back. So for reads, accesses equal fills (0.83 and 0.83), and that is normal, not a miss.
  • Fresh data every pass for writes. v + p changes the stored value each pass, so hardware cannot skip a store of an unchanged line.
  • Latency needs the opposite pattern. The latency tool uses one dependent load over a random cycle (a fresh permutation per run). So the prefetcher is defeated and one load is in flight. Its numbers (1.43, 3.75, 29, 148 ns) are what Figure 1 shows.

3.6 Hardware counters: proving where a line was served

Bandwidth says how fast; counters say which hop. The script reads three PMUs along the path, each with its own scope and counter budget.

Short run, long run, subtract: the counter rate of the loop alone

  • counted() runs the same command twice under perf stat, with --min-ms 200 and 2000, both with --reps 1. So one window holds exactly one warm-up and one timed loop.
  • The analysis divides the count difference by the line difference (bytes / 64), after subtracting the idle rate times the interval difference. It also refuses any counter that ran less than 99.9 % of its interval and any long run that moved fewer bytes than the short one.
  • An idle control (sleep 2 under the same event set) is recorded first for every set.
  • Same recipe for the latency tool in run_crb.sh: short = 2 timed cycles (--min-ms 0 --min-cycles 2), long = at least 1 s and 6 cycles (--min-ms 1000 --min-cycles 6), and summarize.py divides the count difference by the load difference. 3.7 Running on a shared host without corrupting anyone's data

Re-exec under taskset, refuse to start on a marker, kill the whole process group

  • The script re-executes itself once under taskset -c 0-119. Every child inherits that mask. The reserved CPUs 120 to 127 are never touched.
  • guard() launches each measurement with setsid, so perf and the benchmark form one process group. It polls the shared-host marker every 5 s. If the marker appears, it kills the group (TERM, then KILL after 1 s) and exits 3. The kills are guarded against set -e.
  • Results go to a UTC-stamped directory. stdout and stderr are copied into log.txt. The binaries are rebuilt first. An exit trap gives the result files back to the invoking user.
  • PARTS picks which numbered parts run: the default 1234 skips part 5, so sudo PARTS=5 ./run_sudo.sh runs the six-minute write-path part alone and PARTS=12 runs the two homelat parts only.

Pitfall: kill $pid on a backgrounded perf stat kills perf only; 120 pinned threads keep streaming and corrupt the other team's run.

Elsewhere: wrap every launch in a function that uses setsid or a cgroup, polls your site's stop signal, and kills by negative pid.

4. Summary: what to remember

  1. A bandwidth number names a hop, or it names nothing. Decide which hop you want to saturate, then choose footprint, instruction mix and placement so that only that hop can limit.
  2. Footprint picks the level: half of the target level, four times the level above. Then check the sum over threads against the capacity one core can actually reach, not the number Linux prints.
  3. Run a loads-only and a stores-only loop next to the compiled loop. Where they differ, the core's instruction mix was the limit; where they agree, the limit is below the core. Compare with pipes × width × clock.
  4. Keep the compiler out of the loop: noinline kernels, a volatile sink per thread, a runtime non-repeating store value, no memset or memcpy substitution, no tail loop.
  5. Setup outside the clock: pin, allocate and first-touch on the owning thread with 2 MiB pages, warm up, then start every thread on one barrier.
  6. Time per thread, aggregate conservatively: Σ bytes / max elapsed, best of N, clock reads amortised over a byte budget, and the per-thread spread always printed.
  7. Placement is a measurement variable. One thread per shared port; one mesh versus both; the same thread count in each case. Change one thing per experiment.
  8. Writes are not reads. A streaming write may bypass a cache and may collapse across a chip link while reads do not. Read the counters before naming a write number after a cache level.
  9. Counters as a difference quotient: short run and long run, identical setup, subtract, divide by lines, subtract the idle background, reject anything multiplexed.
  10. Respect the counter budget: distinct event ids per run, no more events than counters, scope -C for a core and -a for an uncore device, node-id filters for one crosspoint, a cycle counter in the same run.
  11. Label what is not proven. When a number rests on a reading that no counter confirmed, say so next to the number and name the test that would settle it.

If you build it yourself: the order of work

  1. Read the cache sizes and sharing lists from sysfs; pick the five footprints and the thread caps.
  2. Write the allocator (2 MiB aligned, huge-page advice), the worker (pin, touch, warm-up, barrier, timed loop, per-thread result), and the aggregation line.
  3. Write the three C kernels, then the three asm kernels for your ISA; check the disassembly of the C kernels.
  4. Sweep footprint × kernel on one core; the dumbbell of Figure 3 is your first result and your first sanity check against the pipe peaks.
  5. Sweep threads with stride lists; compare contiguous against strided placement at the shared level.
  6. Only then add counters: idle control, short and long runs, one question per event pair, scope by PMU.
