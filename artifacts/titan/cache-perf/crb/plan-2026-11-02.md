## Words used here

- CRB: the Arm "Phoenix Reference Server" at 192.168.2.45, 128 Neoverse V3AE cores at 2.8 GHz, two chiplets. Only CPUs 0 to 119 may be used. Shared machine: Jeremy's timed runs are announced in Slack and marked by the file /tmp/positron-perf.RUNNING. Every script stops if that file exists.
- Report: ~/workspace/titan/cache-perf/crb/crb-memory-hierarchy.html, published at https://claude.ai/artifact/Wtk42eJd8ykC6FV4FFTEtM (version 11 as of 03:50 UTC). The local file and the published page are always the same content.
- Mesh: Arm CMN S3, the on-chip interconnect. Each chiplet has one mesh of 9 by 8 crosspoints (XPs). Linux exposes two mesh counter units, arm_cmn_0 and arm_cmn_1.
- Mesh cache, SLC, slice: the 128 MiB cache that Linux calls L3. It is Arm's System Level Cache, split into 128 slices of 1 MiB (est.), one per home node (HN-S). Every address has exactly one home node, chosen by a hash of the physical address that Arm does not publish.
- Home node (HN-S): the mesh node that owns an address range, holds that range's slice and its snoop filter, and forwards misses to a memory port (SN-F).
- Pair port: two cores share one crosspoint port (an Arm CAL2). Measured: two partner cores together get 78 GB/s from the mesh cache, two cores from different pairs get 134 GB/s.
- Map: crb/results/cmn-map.txt, the crosspoint grid printed by the Linux driver, read by Jibin with sudo on 2026-11-01. Both meshes are identical: 64 home nodes per mesh (two per crosspoint on 32 crosspoints), 35 core ports, 12 memory ports, 8 chip-to-chip gateways.
- DTC: debug trace controller, one per mesh quadrant (4 per mesh). Each DTC has 8 counters, so at most 8 mesh events can be counted at once per quadrant. From the map: rows 4 to 7 are DTC 1 (columns 0 to 4) and DTC 0 (columns 5 to 8); rows 0 to 3 are DTC 2 (columns 0 to 4) and DTC 3 (columns 5 to 8).
- perf_event_paranoid: the kernel setting that decides who may open counters. It is 2 on CRB, so the mesh counters need root. Nothing on CRB is changed; the scripts only read counters.
- Fresh chain: a pointer chase that is walked exactly once. CRB's cores learn a repeated chase (a temporal prefetcher) and bring 16 MiB latency from 29 ns down to 5.6 ns, so every timed chase in this plan is a chain that has never been walked.

## Part 2: the root tool, homelat (review this)

Source: bench/homelat.c (compiled on CRB, no warnings). Script: bench/run_sudo.sh. Jibin runs `sudo ./run_sudo.sh` in ~/cache-perf/bench on CRB. Results go to ~/cache-perf/results/sudo-<timestamp>/ and are chowned back to jhan.

Step 1, discover home nodes. For each mesh counter unit, perf_event_open is called with bynodeid=1 for every node id from 0 to 0xffff. The driver returns EINVAL for an id that is not a home node, so the ids that open are the home nodes. Expected: 64 per mesh. The id packs x, y, port and device; the tool tries the two layouts the driver uses and keeps the one under which every id lands on a map crosspoint (x 1 to 7, y 1 to 5). nodes.csv lists them.

Step 2, classify lines. Buffer of 16 MiB on 2 MiB pages, 262,144 lines of 64 B. For each line: load its two neighbours (so a next-line prefetch causes no mesh request), flush the line with `dc civac`, read the open per-node counters, load the line once with a `dsb` after it, read the counters again. The one node whose count rose is the home. Event: hns_pocq_reqs_recvd_read (read requests received by the home node). Only 8 nodes per DTC quadrant can be counted at once, so the tool opens up to 8 per quadrant per pass (32 per mesh) and makes about three passes, re-probing the lines not yet classified. After each pass it checks that every counter ran 100 % of the time, and aborts if the kernel multiplexed them. If none of the first 256 lines raises any counter, it aborts and suggests another event. Cost: about 300 µs per probe, about 2 to 3 minutes in total.

Review this: the assumption that a flushed line's next load causes exactly one read request at exactly one home node. Risks: a hardware prefetcher fetching other lines (noise at other nodes; the tool retries a line up to 3 times when two counters rise), the kernel's own memory traffic during the counter reads, and the event not counting the request type a V3AE core issues (the abort covers that; hns_pocq_reqs_recvd_all or hns_slc_sf_cache_access_all are the fallbacks).

Step 3, latency per core per node. For each core 0 to 119 and each home node: take 2048 of that node's lines (128 KiB), build two random cycles through them (two 8-byte slots), walk chain A once (fill), read an 8 MiB evictor buffer so L1 and L2 drop the lines, then time one pass of chain B. Repeat 7 times alternating the roles, report the median, minimum and maximum in ns per load. Also one "mixed" chain over lines of all nodes as the baseline, expected 29 to 30 ns.

Review this: the claim that after the 8 MiB evictor read the lines sit in the slice and nowhere closer. Supporting evidence: the report's 16 MiB chase (lines evicted from L2 by capacity, then re-read) measured 29 ns, which is the mesh-cache number. The evictor is 8 MiB, which is 4 times L2, and it spreads 128 KiB over each of the 64 slices, so it does not push the 128 KiB chain out of a 1 MiB slice. If the timed latency comes out near 148 ns the lines were not in the slice and the method is wrong. If it comes out near 3.7 ns the evictor did not clear L2.

Expected output: latency.csv with 120 cores by 128 nodes. From it: the nearest-versus-farthest spread per core, the position of each core (its nearest nodes), and whether the 64 nodes of the other mesh are all slower by the same amount. chunks.csv gives, per 2 MiB chunk, its physical frame and how many of its lines are homed on mesh 0 and mesh 1, which settles the "two mesh halves" item directly.

## Part 3: mesh-cache write bandwidth (in the same sudo run)

perf stat over asmwrite streams, 1 and 14 threads, 8 MiB per thread (mesh regime) and 1 GiB per thread (DRAM regime), plus asmread as the control. Two events per mesh per run so nothing is multiplexed: write and read requests received, cache access and miss, fill and memory requests (local), memory requests (remote) and evictions, snoop-filter hits and all requests. The question: at 8 MiB per thread, do the home nodes send the writes on to memory (mc_reqs about equal to lines written) or absorb them (fills about equal to lines written, mc_reqs near zero)? The first means the 73 GB/s write number in the report is a DRAM-path number, the second means the mesh cache allocates on write and the number is a mesh-cache number.

Now the evictor is 8 MiB of independent loads in a new random order every repeat, the fill is independent loads in a new random order, and each timed chain is walked exactly once. With that, the mixed chain reads 27 to 31 ns on every repeat, which is the mesh-cache number. One core takes about 1.1 s, so the full run is about 3 minutes plus 2 to 3 minutes of classification.
