## Short version: purpose

This file holds the lines that `go.sh` (the driver script of the rerun) and the two scripts it calls, `ra.sh` and `rx.sh`, printed on CRB on 2026-11-17 from 22:12:09 to 22:22:18 UTC. It records four machine settings, the machine state before the first step and after each of the 10 steps, and the result folder of each step.

<details>
<summary>Words used here</summary>

- **CRB**: the Arm reference server under test. It has 128 CPUs.
- **Rerun**: the test of 2026-11-17 on CRB that this log belongs to. It is the read test with 120 threads, run again after the memory speed was lowered from 8000 MT/s to 7200 MT/s.
- **MT/s**: million transfers per second, the unit of memory speed.
- **Memory module**: one DIMM. CRB has 12 slots.
- **Read kernel**: the inner loop of the benchmark that reads memory. On this page "kernel" means this loop. The operating system kernel is always written "Linux kernel".
- **Old read kernel**: portable C code with 16 running sums. Each load is followed by an add. Its name is `read` in the binary bw_old and `oldread` in the runner bwx12.
- **New read kernel**: NEON intrinsics (C functions that map to Arm vector instructions), loads only. Its name is `read` in the binary bw_new and `read` in bwx12.
- **asmread**: a hand-written load-only loop. It has the same 8 "ldp q" loads per 256 B as the new read kernel. "ldp q" is the Arm instruction that loads two 16-byte vector registers.
- **read_nop96, read_nop256, read_1pl**: test loops of bwx12: the asmread loop with 96 or 256 no-operation instructions per 256 B, and a loop with one load per 64 B line.
- **bandwidth.c, bw_old, bw_new**: the benchmark and its two binaries of 2026-11-13. bw_old was built from the old source, bw_new from the new source.
- **bwx12, bwx11, bwx**: later runner programs for the same loops. They print one row per thread. bwx12 is the runner of the 2026-11-15 investigation. bwx11 and bwx are older versions.
- **Process, interval, round, position**: a process is one start of a benchmark binary. An interval is one timed measurement inside a process. bwx12 times a sequence of kernels and repeats the sequence: each repeat is a round (counted from 0), and the position is the place of a kernel in the sequence (counted from 0). In part A the round (1 or 2) is the round of the script: round 2 runs the processes in the reverse order.
- **Session**: one pass of go.sh through part A, part L and part C.
- **Part A**: the 120-thread part of the test of 2026-11-13, repeated with the same two binaries.
- **Part L**: one bwx12 process with the kernel sequence oldread, asmread, read_nop96, read_nop256, read_1pl.
- **Part C**: one bwx12 process with the sequence oldread, read, asmread (cfwd) or asmread, read, oldread (crev).
- **Step**: one call of `ra.sh` or `rx.sh` by `go.sh`. `go.sh` ran 10 steps: part A, part L and part C of 3 sessions, and one more part C process.
- **Tag**: the name of a step, for example `T72A1`. The letter names the part (A, L or C). The last digit is the session number. In `T72C4` the last digit means the fourth part C process.
- **Spec file**: a file with one line. The line holds a name for the csv file (for example `cfwd`) and the arguments of one bwx12 process. `rx.sh` reads it.
- **Result folder**: the folder that `ra.sh` or `rx.sh` creates on CRB for one step. `ra.sh` writes two files into it: `threads120.csv` (for each process one header line of the script and the output of `bw_old` or `bw_new`) and `probe.txt` (the machine state before the first process and after the last process). `rx.sh` writes four files into it: the csv file (the output of bwx12), `env.txt` (the machine state when `rx.sh` starts), `launches.txt` (one `launch` line before the bwx12 process and one `rc` line after it) and `stderr.txt` (the error output of bwx12).
- **Agent**: the AI coding assistant (Claude Code) that ran the rerun on CRB for the user. FACTS.md calls it "the agent".
- **Transcript**: the file in which Claude Code saved each command that the agent ran, with its time and its output.
- **Start command**: the command line that started `go.sh` on CRB and sent its output to this file. It is not part of a script.
- **State line**: a line that go.sh or go2.sh prints with the time, the boot id, MemTotal, the load, the logins and the processes per user.
- **Load average**: the number of tasks that are runnable or wait for disk input and output, averaged by Linux over the last 1, 5 and 15 minutes (file /proc/loadavg [Ref5]). "Load at launch" is the 1-minute value read directly before a process starts. The fourth field of the file gives the tasks that are runnable now and the number of all tasks.
- **Task**: a process or a thread, as the Linux scheduler counts it.
- **Login**: one line of the tool `who`, which prints the users who are logged in.
- **Boot id**: a random identifier that Linux creates at each start. Equal boot ids mean the same boot.
- **MemTotal**: the usable memory that Linux reports, in kB.
- **Marker file**: `/tmp/positron-perf.RUNNING`. Another user creates it during a performance test. Our scripts stop when it exists.
- **Governor**: the Linux policy that sets the CPU frequency.
- **2 MiB pages**: transparent huge pages. The "P" rows of bwx12 report how many kB of each buffer lie on them.
- **rc**: the exit status of a process. 0 means success.
- **CPU list**: the list of CPUs on which Linux may run a process (its CPU affinity).
- **Process group**: a set of processes that can receive one signal together. A process id with a minus sign in front of it, given to the command `kill`, means the group with that number.
- **Linux kernel command line**: the options that the boot loader passes to the Linux kernel when the machine starts.

</details>

## How to read this file

1. Line 1 is the first line that `go.sh` prints. It gives the process id of the script (line 1).
2. Lines 2 to 5 give four machine settings. Each one was read once, before the first step: the Linux kernel command line, the governors, the huge page setting and the CPU list of the shell (lines 2-5).
3. Every other line that starts with `== ` is a state line. The file has 12. Line 6 is the first one, and its row explains the fields (line 6).
4. A line `done <folder>` marks one step. The tag in the folder name names the step: `T72A1` is part A of session 1, `T72L1` is part L, `T72C1` is part C, and `T72C4` is the extra part C process. The file has 10 such lines (line 7).
5. After the `done` line of a bwx12 step (part L or part C) come two lines with one number each: the number of non-empty lines in `launches.txt` and the number of bytes in `stderr.txt` (lines 9-11).
6. Start of a step: read the time in the folder name of its `done` line. `ra.sh` and `rx.sh` take this time when they start. In all 10 steps it is equal to the time of the state line directly above the `done` line.
7. End of a step: read the time of the state line `after <tag>`, the first state line below the `done` line. In all 10 steps it is equal to the end time in the files of the step: the `load_after` line of `probe.txt` (part A) or the `rc` line of `launches.txt` (bwx12 steps).
8. Load before a step: read the field `load` of the state line directly above the `done` line. For T72A1 this is the line `start`. For each of the 9 other steps it is the line `after <tag>` of the step before.
9. The load at the launch of the first benchmark process of a step is not in this file. `ra.sh` and `rx.sh` wait at least 5 s before that launch. They write the load at launch into `probe.txt` and `threads120.csv` (part A) or into `launches.txt` (bwx12 steps). Example: step T72L1 has a 1-minute load average of 80.50 in this file at 22:13:29, and of 74.05 in `launches.txt` at the launch at 22:13:34.
10. End of the run: the state line `end` and the line `ALLDONE`. A line that starts with `FAILED:` would mark a run that stopped early. This file has none (lines 41-42).
11. Code that reads this file: `facts_data.py` (function `read_log`, called by `build_facts.py`) keeps every field of a state line except the fifth field of `load` (the newest process id). It also keeps the four settings lines [Ref11]. `make_report.py` (function `state_lines`) keeps the label, the time, the boot id, MemTotal, the 1-minute load average, the logins, the marker and the processes per user [Ref12]. `build_facts.py` and `make_report.py` test for the line `ALLDONE` and for lines that start with `FAILED`.

## Behavior a reader must know

- `go.sh` does not write this file itself. It holds no command that names the file. The file was written by the start command, the command line that started `go.sh` on CRB. No script of the run folder holds the start command, and sections 1 and 2 of FACTS.md (the facts sheet of the rerun) do not record it [Ref4]. The transcript of the agent that ran the rerun records it [Ref15]. The agent sent one command line to CRB with `ssh` (the remote login tool), as the user `jhan`. The part that starts `go.sh` reads: `L=~/cache-perf/results/go-T72-$(date -u +%Y%m%dT%H%M%SZ).log; nohup setsid ~/cache-perf/w120-7200-20261117/go.sh > $L 2>&1 < /dev/null &`.
- `> $L 2>&1` sends the standard output and the error output of `go.sh` to this file. The scripts that `go.sh` calls inherit the two outputs. Each of the 42 lines of the file is a line that a script prints to standard output. So nothing was written to the error output. `ra.sh` does not redirect the error output of `bw_old` and `bw_new` [Ref2]. So a text that one of these two binaries writes to its error output would be a line of this file. The file has no such line.
- The time in the name of this file comes from the start command. It reads the clock of CRB directly before it starts `go.sh`: 22:12:09 UTC.
- `< /dev/null` gives `go.sh` an empty input. `nohup` starts `go.sh` with the hangup signal ignored. The hangup signal tells a program that its terminal or connection was closed. `setsid` makes `go.sh` the first process of a new process group. The review of the run plan made a local trial. It started a `go.sh` with `nohup setsid` and then killed the shell that had started it. `go.sh` kept running. Its process group id was its own process id [Ref14]. On CRB the start command printed the process id 4864 for the program that it started [Ref15]. Line 1 shows the same number.
- The start command holds no `taskset`. So it does not set the CPU list that line 5 shows. The review of the run plan had proposed a start command with `taskset -c 0-119` in front of the path of `go.sh` [Ref14]. The command that ran has no such part [Ref15].
- After the start, the same command line waited for the end of `go.sh`, printed its exit status and printed this file. The recorded output holds `go.sh exit status 0` [Ref15].
- The file holds no measured rate. `ra.sh` sends the standard output of `bw_old` and `bw_new` to `threads120.csv`. `rx.sh` sends the standard output of bwx12 to the csv file of the step and its error output to `stderr.txt` [Ref2] [Ref3].
- The result folders of the 7 bwx12 steps (parts L and C) hold no boot id and no MemTotal. For these steps the two values come from the state lines of this file only. The 3 folders of part A hold both values in `probe.txt`. FACTS.md takes the equal boot id as the proof of the memory speed of 7200 MT/s [Ref4].
- `go.sh` prints a state line before the first step, after `ra.sh` or `rx.sh` has returned, and at the end. Both scripts wait for the end of their benchmark processes before they return. So no benchmark process of the rerun runs while a state line is read.
- Load before the steps (1-minute load average): 0.07 before T72A1, and 80.50 to 114.40 before the 9 other steps. Each of these 9 steps started in the second in which the step before it ended. FACTS.md gives the cause of the high values as a hypothesis that was not tested: the load comes from the 120-thread processes of the rerun itself, and Linux averages it over the last minute [Ref4].
- All 12 state lines hold the same boot id and the same MemTotal, 0 logins, the marker `absent`, 1 runnable task, and 11 processes of the user `jhan`. Of the 8 process counts per user, only the count of `root` changes (985 to 1004).
- `users 0` means that `who` listed no login at the 12 moments of the state lines. The `ssh` connection that started `go.sh` stayed open until `go.sh` ended [Ref15]. `who` did not list it. So `users 0` does not show that no connection to CRB was open. The transcript holds no other command that the agent sent to CRB between the start of `go.sh` and its end [Ref15].
- All times are UTC from the clock of CRB, with a resolution of 1 s.
- The folder paths in the `done` lines are paths on CRB. The copies of the 10 folders lie in the folder of this log file, under the same folder names. After the run the agent copied this log file and the 10 folders from CRB in one command. The command packed them on CRB with `tar` (a tool that joins files into one stream), sent the stream through `ssh` and unpacked it in the folder of this log file [Ref15].

## Call sequence in the whole-chip test

- `go.sh`: driver script: prints lines 1 to 6, the state lines and ALLDONE
  - `go.sh:state`: prints one state line: at the start, after each step, at the end
  - `ra.sh`: part A: prints the done line of a k120 folder
  - `go.sh:runx`: runs one bwx12 step, checks it, then calls state
    - `rx.sh`: prints the done line and the two numbers of a w120 folder
    - `go.sh:rxok`: tests launches.txt for one rc 0 line, prints nothing
- `facts_data.py:read_log`: analysis: parses the state lines and the four settings lines
- `make_report.py:state_lines`: analysis: parses the state lines for the checks of the report
