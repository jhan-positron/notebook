Parts B and C, question Q2: 64+56 threads at 256 MiB

Short version. With 120 threads on the test server CRB (64 on one half of the chip and 56 on the other, each reading its own 256 MiB buffer), the old read loop moved 158.1 to 178.7 GB/s more in total than the new read loop in all 8 timing settings of both sessions. The largest change of that difference between two timing methods (stop rule, interval length or start position) was 16.15 GB/s (9.5 % of the difference), so no timing method removed it. The cause inside the chip is not tested, because the counters that need root were not run.

  • Thread rate: the bytes of one thread divided by its own elapsed time.
  • Total, M_hist: the bytes of all threads divided by the longest elapsed time of a thread. This is what the benchmark prints. It is the decision metric.
  • M_sum: the sum of the thread rates. It is reported next to M_hist as a description.
  • Median: the middle value of a sorted list. With an even count it is the mean of the two middle values.
  • q: the thread rate at the 10th percentile divided by the thread rate at the 90th percentile, in one interval. With 120 threads these are the 12th and the 108th smallest rate. q near 1 means that all threads have nearly the same rate.
  • Pattern: how the thread rates of one interval are distributed over the threads.
  • Split, uniform: the two pattern labels of the handoff (q below 0.65, q above 0.85). They are not used on this page.
  • Bounded prediction: the one measurable statement of a hypothesis that a step tests.
  • Setting: one combination of stop method, interval length and start.
  • Stop method: "whole passes": a thread stops after a whole pass, as in bandwidth.c. "common stop": all threads stop at one common time and count the bytes of the partial pass.
  • Start: "common start": every thread starts at the start of its buffer. "offset start": every thread starts at its own offset inside its buffer.

  • Group (C3): one setting and one sequence.

An L1 or L2 refill is a line that this cache level had to fetch. A last-level read miss is a read that the last cache level did not hold.

  • CPU time: the time for which a thread really ran on its CPU (the thread CPU clock of Linux).

H10 and H9b: what these data can and cannot say

H10: "not tested"

  • Can say: how many refills of its own caches a core counted for each 64 B line that the loop read, per kernel and mesh. The section of C3 gives these values.
  • Cannot say: whether the memory system fetched lines that the loop did not consume. The core events count refills that the core saw. The plan states that H10 could still hold for traffic that these events do not count [Ref1].
  • Insufficient data: memory requests per line read. Step D1 would give them (mesh counters hns_mc_reqs_local_all and hns_mc_reqs_remote_all, with root). Part D was not run. Even D1 can support H10 and cannot reject it [Ref1].

H9b: "not observed", open for the user

  • The hypothesis table gives the ranges of q and of the total of old read per session, and the two readings of the word.
  • Cannot say: why old read gave totals of 365.10 to 368.25 GB/s on 2026-10-30 [Ref1]. That run is a number from an earlier result folder. Rule 10 of the plan uses such a number for hypotheses only, not as evidence.
  • Cannot say: anything about another day or about the state after a restart of the machine. The section "When the sessions ran" gives the times.
  • Insufficient data: the same steps on another day, and after a restart of the machine. They would show whether the values of old read change for a reason other than the kernel.

Limits of this page

  • The sessions are one continuous run of one night. Session s2 started 14 s after session s1 ended. No result of this page says anything about another day or about the state after a restart.
  • No value on this page is the traffic of the time in which all threads ran. A thread records only its total, so the bytes of the common time are not measured [Ref2]. Rule 6 of the plan is met only in part.
  • The page state of an interval with many threads is the reading taken after the interval before it. A change during the warm-up pass shows only in the next reading [Ref2].
  • A thread that loses its CPU inside an interval is not marked in a run without counters [Ref25]. Only C3 has the CPU time of each thread.
  • With 120 threads the main thread of bwx has no CPU of its own. It shares a CPU with a worker [Ref24]. Insufficient data: the size of this effect on CRB. A run with the main thread on a spare CPU would give it, and the rules of the host allow CPUs 0 to 119 only.
  • The loop of read_sparse starts at 4 modulo 64, and the other asm read loops start at 20 [Ref16][Ref24]. So B5 compares read_sparse at another loop offset.
  • Part D (root counters, physical pages) was not run. So H3b of question Q1 is "not tested", and H10 is "not tested" [Ref1].
  • The limits 100 µs and 5 ms for an irregular interval are provisional [Ref2].
  • The decisions use many comparisons of two settings. No correction for the number of comparisons is made.
  • Insufficient data: load readings during an interval. The script reads the load only before each launch.
  • The chart colours were not checked with the palette checker of the chart rules, because Node.js is not installed on the machine where this page was built. Every chart also uses position, marker shape or a text label.
