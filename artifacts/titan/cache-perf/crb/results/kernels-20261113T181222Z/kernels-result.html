New C kernels of bandwidth.c, measured on CRB

Short version. The three C kernels of bandwidth.c (read, write, copy) now use the same algorithm as the hand-written asm kernels. With one thread, the best rate of each new C kernel differs from the best rate of the asm kernel of the same binary by -2.91 % to +0.41 % over the 12 cells (3 kernels x 4 buffer sizes). With 120 threads and 256 MiB per thread, the best read rate changed from 466.65 GB/s (old C kernel) to 304.05 GB/s (new C kernel).

Words used here

  • CRB: the Arm Phoenix Reference Server, 128 cores, where all runs were made.
  • Kernel: the timed loop of the benchmark bandwidth.c. It is not the Linux kernel.
  • Old C kernel: k_read, k_write or k_copy as it was before 2026-11-13 (binary bw_old).
  • New C kernel: the same function after the rewrite with NEON intrinsics (binary bw_new). NEON is the 128-bit vector instruction set of AArch64.
  • asm kernel: k_asmread, k_asmwrite or k_asmcopy, written in inline assembly. Their source is the same in both binaries.
  • Rate: bytes moved per second, in GB/s (1 GB = 109 bytes). The copy kernels count the bytes read plus the bytes written.
  • Repetition: one timed interval of at least 0.5 s. Each process makes 3 repetitions.
  • Best, median, lowest: the highest, the middle and the lowest rate of the repetitions of one cell.
  • L1, L2, SLC: the three cache levels of a core. SLC is the system-level cache (L3), shared by all cores.
  • DRAM: main memory.
  • Load: the Linux 1-minute load average, the average count of tasks that run or wait to run.

What the data shows

  • One thread, new C kernel against asm kernel: the best rates differ by -2.91 % to +0.41 % over the 12 cells.
  • One thread, new C kernel against old C kernel: the best rate changes by +0.1 % to +103.4 % over the 12 cells.
  • Control: the asm kernels have the same source in both binaries. With one thread their best rates differ between the binaries by -0.35 % to +0.14 %. This run does not establish whether a C-kernel difference of similar size is repeatable.
  • 120 threads: the same control differs by -0.06 % to +6.20 %. Each 120-thread cell has only 2 processes per binary.
  • 120 threads, read: old C 466.65 GB/s, new C 304.05 GB/s, asm 305.90 GB/s (best of 6). The change of -34.8 % is larger than the control difference.
  • 120 threads, write: old C best 186.88 GB/s and median 144.62 GB/s. New C best 147.78 GB/s and median 131.92 GB/s. The repetitions of the write kernels range from 117.26 to 186.88 GB/s.

Limits of this run

  • Each one-thread cell has 4 processes (2 rounds, CPUs 0 and 2) of 3 repetitions. The 3 repetitions of one process use the same buffer, so they are not independent samples.
  • Each 120-thread cell has 2 processes of 3 repetitions, at one buffer size.
  • No hardware counter was read. The run does not show why a rate is what it is.
  • The page size that each process received was not recorded. Transparent huge pages were set to "always".
  • The color palette is three slots of the dataviz skill. Its validator script was not run (no node on this machine).

Conditions

  • Host CRB, gcc 14.2.0, flags -O3 -march=native -fno-tree-loop-distribute-patterns -pthread -Wall -Wextra -std=gnu11 [Ref1].
  • Load before the run: 0.03. No user was logged in [Ref1].
  • Load at the start of the one-thread processes: 0.10 to 1.00 [Ref2]. Our own processes are part of this load.
  • Load at the start of the 120-thread processes: 1.00 to 85.38 [Ref3]. Every process after the first one followed a process with 120 threads. Hypothesis: this load comes from our own processes. The process list was recorded only before the run, so no file confirms it.
  • One process per binary and kernel. Round 2 reversed the order of the binaries and of the kernels [Ref4].
  • The marker file of Jeremy's runs (/tmp/positron-perf.RUNNING) was checked before every timed process [Ref4]. His block was announced to end at 18:10 UTC in the Slack channel #phoenix-crb (not saved as a file). The run started at 18:12:22 UTC [Ref1].
