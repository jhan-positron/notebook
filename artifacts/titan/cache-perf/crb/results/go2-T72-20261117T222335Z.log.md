## Short version: purpose

This file holds the lines that `go2.sh` (the script of control I) and the script it calls, `rx.sh`, printed on CRB on 2026-11-17 from 22:23:35 to 22:33:34 UTC. It records the machine state at the start, after each of the 2 waits for an idle machine, after each of the 2 bwx12 processes, and at the end.

<details>
<summary>Words used here</summary>

- **CRB**: the Arm reference server under test. It has 128 CPUs.
- **Rerun**: the test of 2026-11-17 on CRB that this log belongs to. It is the read test with 120 threads, run again after the memory speed was lowered from 8000 MT/s to 7200 MT/s.
- **MT/s**: million transfers per second, the unit of memory speed.
- **Memory module**: one DIMM. CRB has 12 slots.
- **Read kernel**: the inner loop of the benchmark that reads memory. On this page "kernel" means this loop. The operating system kernel is always written "Linux kernel".
- **Old read kernel**: portable C code with 16 running sums. Each load is followed by an add. Its name is `read` in the binary bw_old and `oldread` in the runner bwx12.
- **New read kernel**: NEON intrinsics (C functions that map to Arm vector instructions), loads only. Its name is `read` in the binary bw_new and `read` in bwx12.
- **asmread**: a hand-written load-only loop. It has the same 8 "ldp q" loads per 256 B as the new read kernel. "ldp q" is the Arm instruction that loads two 16-byte vector registers.
- **read_nop96, read_nop256, read_1pl**: test loops of bwx12: the asmread loop with 96 or 256 no-operation instructions per 256 B, and a loop with one load per 64 B line.
- **bandwidth.c, bw_old, bw_new**: the benchmark and its two binaries of 2026-11-13. bw_old was built from the old source, bw_new from the new source.
- **bwx12, bwx11, bwx**: later runner programs for the same loops. They print one row per thread. bwx12 is the runner of the 2026-11-15 investigation. bwx11 and bwx are older versions.
- **Process, interval, round, position**: a process is one start of a benchmark binary. An interval is one timed measurement inside a process. bwx12 times a sequence of kernels and repeats the sequence: each repeat is a round (counted from 0), and the position is the place of a kernel in the sequence (counted from 0). In part A the round (1 or 2) is the round of the script: round 2 runs the processes in the reverse order.
- **Part A**: the 120-thread part of the test of 2026-11-13, repeated with the same two binaries.
- **Part L**: one bwx12 process with the kernel sequence oldread, asmread, read_nop96, read_nop256, read_1pl.
- **Part C**: one bwx12 process with the sequence oldread, read, asmread (cfwd) or asmread, read, oldread (crev).
- **Control I**: the part L line, started from an idle machine, twice. It was added after the first numbers were seen. It is not part of the plan fixed before the run.
- **Line, argument line**: the arguments of one bwx12 process, as a spec file holds them. "The same line" means a process with the same arguments.
- **Idle start**: a launch at a 1-minute load average below 1.0.
- **Step**: one call of `rx.sh` by `go2.sh`. It runs one bwx12 process. `go2.sh` ran 2 steps.
- **Tag**: the name of a step: `T72I1` or `T72I2`. The last digit is the number of the process.
- **Spec file**: a file with one line. The line holds a name for the csv file (here `a6456`) and the arguments of one bwx12 process. `rx.sh` reads it.
- **Result folder**: the folder that `rx.sh` creates on CRB for one step. `rx.sh` writes four files into it: `a6456.csv` (the output of bwx12), `env.txt` (the machine state when `rx.sh` starts), `launches.txt` (one `launch` line before the bwx12 process and one `rc` line after it) and `stderr.txt` (the error output of bwx12).
- **Agent**: the AI coding assistant (Claude Code) that ran the rerun on CRB for the user. FACTS.md calls it "the agent".
- **Transcript**: the file in which Claude Code saved each command that the agent ran, with its time and its output.
- **Start command**: the command line that started `go2.sh` on CRB and sent its output to this file. It is not part of a script.
- **State line**: a line that go.sh or go2.sh prints with the time, the boot id, MemTotal, the load, the logins and the processes per user.
- **Load average**: the number of tasks that are runnable or wait for disk input and output, averaged by Linux over the last 1, 5 and 15 minutes (file /proc/loadavg [Ref4]). "Load at launch" is the 1-minute value read directly before a process starts. The fourth field of the file gives the tasks that are runnable now and the number of all tasks.
- **Task**: a process or a thread, as the Linux scheduler counts it.
- **Login**: one line of the tool `who`, which prints the users who are logged in.
- **Boot id**: a random identifier that Linux creates at each start. Equal boot ids mean the same boot.
- **MemTotal**: the usable memory that Linux reports, in kB.
- **Marker file**: `/tmp/positron-perf.RUNNING`. Another user creates it during a performance test. Our scripts stop when it exists.
- **Governor**: the Linux policy that sets the CPU frequency.
- **rc**: the exit status of a process. 0 means success.
- **CPU list**: the list of CPUs on which Linux may run a process (its CPU affinity).
- **Process group**: a set of processes that can receive one signal together. A process id with a minus sign in front of it, given to the command `kill`, means the group with that number.
- **Linux kernel command line**: the options that the boot loader passes to the Linux kernel when the machine starts.

</details>

## How to read this file

1. Line 1 is the first line that `go2.sh` prints. It gives the process id of the script (line 1).
2. Every line that starts with `== ` is a state line. The file has 6. Line 2 is the first one, and its row explains the fields (line 2).
3. A state line with the label `idle before <tag>` is printed when a wait for an idle machine has ended. Idle means here: the 1-minute load average is below 1.0 (line 3).
4. A line `done <folder>` and the two number lines after it come from `rx.sh`. They mark one step, which is one bwx12 process. The tags are `T72I1` and `T72I2` (lines 4-6).
5. Start of a step: read the time of the line `idle before <tag>`. In both steps it is equal to the time in the folder name of the `done` line, which `rx.sh` takes when it starts.
6. End of a step: read the time of the state line `after <tag>`. In both steps it is equal to the time of the `rc` line in `launches.txt` of the step.
7. Load before a step: read the field `load` of the line `idle before <tag>`. The 1-minute load average is 0.95 before T72I1 and 0.99 before T72I2.
8. The load at the launch of the bwx12 process is not in this file. `rx.sh` waits at least 5 s before the launch and writes the load at launch into `launches.txt`. There the 1-minute load average is 0.87 for T72I1 (launch at 22:27:05) and 0.91 for T72I2 (launch at 22:32:32).
9. Length of a wait: the time of the line `idle before <tag>` minus the time of the state line above it. The waits took 205 s and 260 s.
10. End of the run: the state line `end` and the line `ALLDONE`. A line that starts with `FAILED:` would mark a run that stopped early. This file has none (lines 13-14).
11. Code that reads this file: `facts_data.py` (function `read_log`, called by `build_facts.py`) keeps every field of a state line except the fifth field of `load` (the newest process id) [Ref6]. `make_report.py` (function `state_lines`) keeps the label, the time, the boot id, MemTotal, the 1-minute load average, the logins, the marker and the processes per user [Ref7]. `build_facts.py` and `make_report.py` test for the line `ALLDONE` and for lines that start with `FAILED`.

## Behavior a reader must know

- `go2.sh` does not write this file itself. It holds no command that names the file. The file was written by the start command, the command line that started `go2.sh` on CRB. No script of the run folder holds the start command, and sections 1 and 2 of FACTS.md (the facts sheet of the rerun) do not record it [Ref3]. The transcript of the agent that ran the rerun records it [Ref11]. The agent sent one command line to CRB with `ssh` (the remote login tool), as the user `jhan`. The part that starts `go2.sh` reads: `L=~/cache-perf/results/go2-T72-$(date -u +%Y%m%dT%H%M%SZ).log; nohup setsid ~/cache-perf/w120-7200-20261117/go2.sh > $L 2>&1 < /dev/null &`.
- `> $L 2>&1` sends the standard output and the error output of `go2.sh` to this file. The scripts that `go2.sh` calls inherit the two outputs. Each of the 14 lines of the file is a line that a script prints to standard output. So nothing was written to the error output.
- The time in the name of this file comes from the start command. It reads the clock of CRB directly before it starts `go2.sh`: 22:23:35 UTC.
- `< /dev/null` gives `go2.sh` an empty input. `nohup` starts `go2.sh` with the hangup signal ignored. The hangup signal tells a program that its terminal or connection was closed. `setsid` makes `go2.sh` the first process of a new process group. The review of the run plan made a local trial. It started a `go.sh` with `nohup setsid` and then killed the shell that had started it. `go.sh` kept running. Its process group id was its own process id [Ref10]. On CRB the start command printed the process id 15823 for the program that it started [Ref11]. Line 1 shows the same number.
- After the start, the same command line waited for the end of `go2.sh`, printed its exit status and printed this file. The recorded output holds `go2.sh exit status 0` [Ref11].
- Control I is not part of the plan that was fixed before the run. It was added after the first numbers of parts A, L and C were seen [Ref3].
- This file has none of the four settings lines of the log of `go.sh` (Linux kernel command line, governors, huge page setting, CPU list). `go2.sh` does not read these settings. The boot id is the one of the log of `go.sh` [Ref5]. The start command of `go2.sh` holds no `taskset` [Ref11]. So neither this file nor the start command shows the CPU list of the shell that ran `go2.sh`. `rx.sh` starts each bwx12 process through `taskset -c 0-119` (a tool that starts a program with the given CPU list) [Ref2].
- The file holds no measured rate. `rx.sh` sends the standard output of bwx12 to the file `a6456.csv` of the step and its error output to `stderr.txt` [Ref2].
- The result folders of the 2 steps of control I hold no boot id and no MemTotal. For these steps the two values come from the state lines of this file only. FACTS.md takes the equal boot id as the proof of the memory speed of 7200 MT/s [Ref3].
- `go2.sh` prints a state line only when no bwx12 process of its own runs: at the start, after a wait, after `rx.sh` has returned, and at the end.
- All 6 state lines hold the same boot id and the same MemTotal, 0 logins, the marker `absent`, 1 runnable task, and 11 processes of the user `jhan`. Of the 8 process counts per user, only the count of `root` changes (1006 to 1014).
- `users 0` means that `who` listed no login at the 6 moments of the state lines. The `ssh` connection that started `go2.sh` stayed open until `go2.sh` ended [Ref11]. `who` did not list it. So `users 0` does not show that no connection to CRB was open. The transcript holds no command of the agent between the start command and the end of `go2.sh` [Ref11].
- All times are UTC from the clock of CRB, with a resolution of 1 s.
- The folder paths in the `done` lines are paths on CRB. The copies of the 2 folders lie in the folder of this log file, under the same folder names. After the run the agent copied this log file and the 2 folders from CRB in one command. The command packed them on CRB with `tar` (a tool that joins files into one stream), sent the stream through `ssh` and unpacked it in the folder of this log file [Ref11].

## Call sequence in the whole-chip test

- `go2.sh`: script of control I: prints line 1, the state lines and ALLDONE
  - `go2.sh:state`: prints one state line
  - `go2.sh:waitidle`: waits for a 1-minute load average below 1.0, prints nothing
  - `rx.sh`: prints the done line and the two numbers of a w120 folder
  - `go2.sh:rxok`: tests launches.txt for one rc 0 line, prints nothing
- `facts_data.py:read_log`: analysis: parses the state lines
- `make_report.py:state_lines`: analysis: parses the state lines for the checks of the report
