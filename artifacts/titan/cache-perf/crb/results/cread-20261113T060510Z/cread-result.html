C loop that only loads, measured on CRB

Short version. A read loop written in C that only loads (k_cread) reads at nearly the same rate as the hand-written asm loop (k_asmread) at all four buffer sizes. The best rates differ by less than 0.7 %. The old C loop with 16 sums (k_read) reaches about half of that rate at 32 KiB.

Words used here

  • CRB: the Arm Phoenix Reference Server, 128 cores, where all runs were made.
  • k_asmread: the read loop written by hand in assembly. One pass runs 8 ldp q instructions (16 loads of 16 B, 256 B), one add, one compare and one branch.
  • k_cread: the new loop in C. It loads 16 values of 16 B and names them in an empty asm statement. In the measured binary gcc 14.2 compiles one pass to 11 instructions of the same kinds and counts as k_asmread [Ref2].
  • k_read: the old loop in C. It adds every 8 B word into one of 16 sums. One pass of 128 B runs 4 ldp q and 8 vector adds [Ref2].
  • SLC: system level cache, the cache that all cores share. Linux lists it as L3.
  • GB: 109 bytes. KiB, MiB, GiB: 210, 220, 230 bytes.

What the data shows

  • At 32 KiB the best rates of both loops that only load are 133.2 to 133.3 GB/s, which is 2.97 loads of 16 B per cycle (est., assuming 2.8 GHz). This run measured neither the clock nor cycles. The best rate of the loop with sums is 66.76 GB/s, which is 1.49 (est., assuming 2.8 GHz) [Ref1].
  • At 1 MiB and 8 MiB the rates of the two loops that only load are still nearly equal (they differ by less than 0.2 %). The loop with sums stays at about 67 GB/s at 32 KiB, 1 MiB and 8 MiB [Ref1]. So up to 8 MiB its rate does not depend on the buffer size.
  • At 1 GiB the best rate of the loop with sums (28.73 GB/s) is 7.1 % below the best rate of k_cread (30.93 GB/s) and 6.5 % below that of k_asmread (30.74 GB/s) [Ref1].
  • At 32 KiB this run gives rates close to those of the report. The report gives 132.7 GB/s for the asm loop and 66.8 GB/s for the loop with sums, measured on 2026-10-30 with an earlier build [Ref3]. In this run the best of 12 repetitions was 133.21 and 66.76 GB/s [Ref1].

Limits of this run

  • Order. In every process the loops ran in the order k_read, k_asmread, k_cread. At 1 GiB the best rate of k_cread was 0.26 % to 0.81 % above the best rate of k_asmread in each of the four processes [Ref1]. An effect of the order is not excluded. A run with the order reversed would resolve it.
  • Low repetitions. At 32 KiB the three repetitions of k_cread in the first process (CPU 0, round 1) gave 131.84 to 131.95 GB/s, about 1 % below the other nine. At 8 MiB on CPU 2, round 1, the six repetitions of the two loops that only load gave 67.85 to 68.31 GB/s, against 69.75 to 71.15 GB/s in the other three processes. At 8 MiB the first repetition of k_asmread was also low in two more processes (70.01 and 69.75 GB/s). The cause was not examined.
  • One thread only. No run with several threads was made.
  • The loop start addresses differ. The loop of k_cread starts at 0x1e24 and the loop of k_asmread at 0x1d1c [Ref2]. The rates are still nearly equal in this run.
  • Not a test of hypotheses A and B of the report. k_cread has no vector adds. The loop with loads and adds in a 3:2 ratio is still not run.

Conditions

  • Host load (1-minute load average of Linux) before the run: 0.06, with no logins [Ref2]. The highest load recorded before a process was 0.71 [Ref1]. This benchmark ran one busy thread during that time. No file shows what else ran.
  • The run script stops if the file /tmp/positron-perf.RUNNING exists, and it checks before every process [Ref4].
  • A check by hand in the login before the run (06:04 UTC) showed no process of the account positron-perf. Its output was not saved, so no file holds this observation.
  • Run started 2026-11-13 06:05:10 UTC and ended 06:06:25 UTC [Ref2].
  • gcc 14.2.0, flags -O3 -march=native -fno-tree-loop-distribute-patterns -pthread, the flags of bench/Makefile [Ref2].
  • The binary is a scratch copy of bench/bandwidth.c with the kernel cread added. bench/bandwidth.c was not changed [Ref4].
  • The color palette is the first three slots of the dataviz skill. Its validator script could not be run here (no node on this machine).
