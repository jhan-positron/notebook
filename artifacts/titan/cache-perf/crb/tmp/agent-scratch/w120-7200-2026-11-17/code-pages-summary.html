Short version

How the pages were checked

  • The tool writes a page only after it has read the new section back, with a reader of its own and with pandoc 2.9.2.1. Every source cell must equal its source line, and the section must hold no HTML element [Ref6].
  • A second Markdown reader, markdown-it-py 4.3.0, read all built pages back at the end. Every row gave back its source line [Ref6].
  • A check step refuses an explanation that holds an HTML tag, a bare |, a reference to a line that the file does not have, a citation that the page does not list, or one of the idioms on its list.
  • A reviewer is a second agent. It reads the source first and the row after that, and it corrects the rows that are wrong [Ref7].

Findings about the source code

  • The writers and reviewers reported points about the source code. They fill 183 list entries in SOURCE-NOTES.md, in three groups: points that touch a measurement, comments that do not fit the code, and files that the repo copy lacks [Ref5].

  • The points below are the ones that touch the whole-chip test. Each hypothesis names the measurement that would confirm or reject it.

Points that touch a measurement or an analysis result

  • Rate of part A (bandwidth.c, bandwidth.orig.c): a thread stores only the length of its own interval. The rate of an interval is the bytes of all threads divided by the longest of these lengths. So one slow thread lowers the rate of the whole interval.
  • Hardware record (hw.sh, written on 2026-11-24): the frequency sampler and the tool atx are pinned to CPU 119 and run during the timed intervals. In a process with 120 threads they share that CPU with one benchmark thread. Hypothesis, not measured: this lowers the part A rate of such a process. One part A run with HW=off against one with HW=on in the same boot would confirm or reject it. The rerun of 2026-11-17 had no hardware record.
  • Parts L, C and I of the whole-chip test (rx.sh line 24, which is line 19 of the text that ran on 2026-11-17): while the binary measures, the shell of rx.sh starts one sleep process per second. The taskset of line 22 limits only the binary, so these processes use the CPU list of the caller. The log of the run of 2026-11-17 records that list as the CPUs 0 to 119 [Ref10]. So each of these processes ran on a CPU that also ran one pinned benchmark thread. Part A is not affected: ra.sh starts nothing while its binary runs. Insufficient data on the size of the effect: the count of involuntary context switches of each benchmark thread would show it.
  • ra.sh line 46 and run_kernels.sh line 68: a comment in hw.sh says that hw_begin must stand before the quiet time of the launch. These two scripts have no pause between hw_begin and the start of the binary.
  • ra.sh line 27 and rx.sh line 14: the sampler and atx already run when the scripts count the runnable tasks. Insufficient data on the effect: the value runnable= in probe.txt of a run with HW=on would show it.
  • Runner bwx12.c, option --stop common: the deadline counts from the common start, and each thread reads its own start time a little later. So the time of a thread can be shorter than --min-ms: 5.999979 s for 6000 ms in the rerun. This is a property of the design, not a bug.
  • Load record of the run scripts: the list of "busiest processes" comes from ps --sort=-pcpu. That column is the CPU time of a process divided by the time from its start to now. It is not the load at the launch. In the 9 files launches.txt of the result folders bwx10-*, 3,874 of 3,945 process lines show 0.0. The load averages and the login count in the same record are not affected.
  • Facts sheet: build_facts.py expects two texts of the older scripts (lines 849 and 880 to 882). The repo texts of go.sh, go2.sh and ra.sh of 2026-11-24 no longer hold them. The scratch copy of go.sh was also edited on 2026-11-24, so its sha256 no longer equals the value in local.sha, and a new build of the facts sheet stops at that check. The stored FACTS.md is from before the edit.
  • manual-run/run.sh line 4 compares the scripts with the list local.sha. The list names the checksums of the scripts of 2026-11-17. With the repo texts of 2026-11-24 the command stops at line 4 until a new list is written.
  • stat_bwx.py and the runner: the field bytes of a thread row is the size of the buffer part of each kernel call. For the kernel read_1pl, which loads 16 of every 64 bytes, it is not the number of bytes loaded.
  • Comment of CHECK_BYTES in the kernel sources and in bwx12.c: it says that the clock is read after at least 8 MiB. The division rounds down, so a buffer below 8 MiB that does not divide 8 MiB is checked after less. The sizes of the tests (32K, 1M, 8M, 256M, 1G) are not affected.
  • Other tests, not the whole-chip test (parts A to C of the plan of 2026-11-13, and the investigation into the 8 MiB buffer size): while a benchmark process runs, their run scripts start one date process and one sleep process per second on the CPUs 0 to 119. Hypothesis, not measured: such a process lowers the rate of an interval when it runs on the CPU of a benchmark thread. The count of involuntary context switches of the benchmark thread during an interval would confirm or reject it.

How to change a page

  • Edit the explanation in the annotation file of the source file: ann/FOLDER/FILE.ann, or a part file in ann/FOLDER/FILE.ann.d/. One line holds one row, in the form LINE: text.
  • Then run python3 lbl.py build KEY in the tool folder. KEY is the path of the source file below the code folder, for example w120-7200-2026-11-17/go.sh.
  • python3 lbl.py build-all builds every page. python3 lbl_main.py pages-check reads every page back. python3 lbl_main.py index writes the index.
  • After a change of a source file, run python3 lbl.py manifest first. It records the new text and its sha256. Then write the rows of the changed lines and build the page.
