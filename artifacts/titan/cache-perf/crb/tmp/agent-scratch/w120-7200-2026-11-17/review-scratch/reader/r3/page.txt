

Whole-chip read test at 7200 MT/s

# Whole-chip read test at 7200 MT/s: old read kernel against new read kernel

2026-11-17, all times in UTC. Machine: CRB (an Arm reference server with 128 CPUs). 120 threads on CPUs 0-119, 256 MiB per thread. 12 memory modules at 7200 MT/s.

## Short version

Yes: at 7200 MT/s with 12 memory modules the new read kernel (a benchmark loop with loads only) still read 30.5 % to 31.2 % less than the old read kernel (each load is followed by an add) when it ran directly after the old one, and 29.7 % to 31.1 % less when it ran directly after another load-only loop (4 pairs of 6 s measurements each).

Against the 8000 MT/s runs chosen beforehand for the comparison, the old read kernel gives "no difference seen" in two of the three tests of the rerun (parts A and C) and "differs between the 8000 MT/s boot and the 7200 MT/s boot" in the third (part L), where its rates were lower.

In the rerun the load-only loop gave higher rates than these 8000 MT/s runs in all 4 comparisons made for it (Table 2), and the data do not show that the memory speed is the cause.

More detail for these three sentences:

- Part L (sentences 2 and 3): n = 6 intervals / 3 processes / 3 sessions / 1 boot against 11 intervals / 7 processes / 1 boot. A boot is one run of the machine between two restarts. Old read kernel: 461.61 to 464.29 against 465.53 to 470.05 GB/s. It was lower by 1.24 GB/s at the nearest ends of the two ranges and by 6.27 GB/s between the medians (0.3 % and 1.3 % of the 8000 MT/s values). The data do not show the cause. Load-only loop (asmread in place of the new read kernel): 321.65 to 327.93 against 288.54 to 309.17 GB/s.

- Parts A and C (sentence 2): the tests cannot exclude a difference of about 1.2 % and 1.0 % (est.). Table 2 gives the ranges and n.

- Sentence 3: each memory speed has only 1 boot. F72d12 (earlier run of the same boot, not part of the rerun) ran the test line of part L. Its load-only loop gave 301.90 to 302.78 GB/s (2 intervals / 1 process / no session / 1 boot). That is inside the 8000 MT/s range (288.54 to 309.17 GB/s). It is 18.87 GB/s below part L at the nearest ends.

Words used here

Q1, Q2
The two questions of the rerun. Q1: is the whole-chip read rate of the new read kernel still below that of the old read kernel at 7200 MT/s, and by how much. Q2: did the rate of either kernel differ from the earlier runs at 8000 MT/s.
Rerun
The 10 steps that go.sh ran at 7200 MT/s on 2026-11-17 from 22:12:09 to 22:22:18 UTC: 3 sessions of parts A, L and C, and one more part C process. Parts A and L repeat tests that ran earlier at 8000 MT/s. Part C is new. No earlier run in the results folder used one of its two kernel orders. Control I (added after the first numbers were seen) and F72d12 (earlier run of the same boot) are not part of the rerun.
CRB
The Arm reference server under test. It has 128 CPUs.
Whole chip, 120 threads
The runs use 120 threads on CPUs 0-119 only. Each thread reads its own buffer of 256 MiB from memory (1 MiB is 2^20 bytes).
MT/s
Million transfers per second, the unit of memory speed.
Memory module
One DIMM (dual in-line memory module). CRB has 12 slots for them.
GB/s
Gigabytes per second. 1 GB is 1e9 bytes.
Read kernel
The inner loop of the benchmark that reads memory. In this page "kernel" means this loop. The operating system kernel is always written "Linux kernel".
Old read kernel
Portable C code with 16 running sums. Each load is followed by an add. Its name is read in the binary bw_old and oldread in the runner bwx12.
New read kernel
NEON intrinsics (C functions that map to Arm vector instructions), loads only. Its name is read in the binary bw_new and read in bwx12.
asmread
A hand-written load-only loop. It has the same 8 "ldp q" loads per 256 B as the new read kernel. "ldp q" is the Arm instruction that loads two 16-byte vector registers.
Load-only loop
The new read kernel or asmread.
bandwidth.c, bw_old, bw_new
The benchmark and its two binaries of 2026-11-13. bw_old was built from the old source, bw_new from the new source.
bwx12, bwx11, bwx
Later runner programs for the same loops. They print one row per thread. bwx12 is the runner of the 2026-11-15 investigation. bwx11 and bwx are older versions.
Process, interval, round, position
A process is one start of a benchmark binary. An interval is one timed measurement inside a process. bwx12 times a sequence of kernels and repeats the sequence: each repeat is a round (counted from 0), and the position is the place of a kernel in the sequence (counted from 0). In part A the round (1 or 2) is the round of the script: round 2 runs the processes in the reverse order.
Rate
Part A: the column aggregate_GBps that bandwidth.c prints. bwx12 and bwx: the sum over the threads of bytes / elapsed time. Unit GB/s.
Interval row, thread rows
bwx12 and bwx write two kinds of row into a csv file that this page uses. An interval row starts with the letter I and holds one interval. A thread row starts with the letter T and holds one thread of one interval. The 120 thread rows of an interval follow its interval row.
Median
The middle value of a sorted list. For an even number of values it is the mean of the two middle values.
Facts sheet
The file FACTS.md with its data file facts.json. It is the detailed record of this rerun. A script built it from the raw result files.
R, S
Short forms of two folders: R is the results folder, and S is the scratch folder of this rerun. The reference list gives both paths.
Session, step
One pass of go.sh through part A, part L and part C. go.sh ran 3 sessions and then one more part C process (T72C4). The n column calls T72C4 the extra process. A step is one part of one session, the extra part C process, or one process of control I (added after the first numbers were seen).
go.sh, go2.sh
The driver scripts. go.sh ran the planned rerun. go2.sh ran control I (added after the first numbers were seen).
Part A
The 120-thread part of the test of 2026-11-13, repeated with the same two binaries. Each session ran 24 processes: 6 kernels (read, write, copy, asmread, asmwrite, asmcopy) x 2 binaries x 2 rounds. This page uses the 4 read processes of each session. The facts sheet holds the other 20 (its sections 3.1 and 5) [Ref1].
Part L
One bwx12 process that times oldread, then asmread, then three other test loops that this page does not use. The process runs this sequence twice (rounds 0 and 1).
Part C, cfwd, crev, kernel order
One bwx12 process with the sequence oldread, read, asmread (cfwd) or asmread, read, oldread (crev). Each process runs its sequence twice (rounds 0 and 1). The kernel order is the order of the kernels in this sequence.
Control I
The part L line, started from an idle machine, twice. It was added after the first numbers were seen. It is not part of the plan fixed before the run.
F72d12
One process of the part L line. It ran at 20:02 UTC on 2026-11-17 for another test, in the same boot as the rerun and before it. It is not part of the rerun.
T72A1 to T72I2
The names of the result folders of the rerun (parts A, L, C) and of control I (I, added after the first numbers were seen): T72, then the letter, then a number.
A-1, A-2, A-3
The 8000 MT/s rows for part A, all of 2026-11-13, with the same two binaries. A-1 is the original test. A-2 is a second run with another process order. A-3 is three more processes of bw_old read.
L-1, L-2, L-3, L-4
The 8000 MT/s rows for parts L and C, all with bwx12. L-1 (2026-11-17) used the argument line of part L unchanged. L-2 to L-4 (2026-11-15) used 4 s measurements and counted other hardware events of the CPU. From these rows only oldread at position 0 and asmread at position 1 are used.
a6456, p1nop, p2add, st1, st2, st3, thp
Names of argument lines. In the rows L-1 to L-4 and in F72d12 (earlier run of the same boot, not part of the rerun) a bwx12 process carries the name of its line, and so does its csv file. A tooltip names such a process by this name. a6456 is the part L line.
onebuf-ms500-1 to onebuf-ms500-3
The tags that the csv file of row A-3 gives its three processes.
Line, argument line, test line, spec file
The arguments of one bwx12 process, as a spec file holds them. "The same line" means a process with the same arguments. A spec file is a text file with one argument line.
Visit
One time at which the same line was run. A later visit is the same line run again at a later time.
Idle start
A launch at a 1-minute load average below 1.0.
Whole-pass stop
The stop rule of bandwidth.c: after the minimum time (0.5 s here) each thread finishes the pass over its buffer that it is in. The threads stop at different times.
Pass count
Part A only: the number of buffer passes that all 120 threads completed in one interval.
Pair, drop
A pair is one load-only interval and one old-kernel interval of the same process and round. The drop of a pair is (1 - load-only rate / old-kernel rate) x 100, in percent. In part A the two kernels run in two processes. There the drop uses the medians of the two processes of one session and round.
List of 8000 MT/s rows
The 8000 MT/s runs with 12 modules that this page compares with: rows A-1 to A-3 and L-1 to L-4. The rules file fixed them before the run. The rules file also names rows of two older runner binaries (bwx11 and bwx). This page does not use the bwx11 rows. It shows the bwx rows in one note under Table 2 only.
Pool
The intervals of several rows taken together as one range.
Overlap of two ranges
Two min-to-max ranges share at least one value.
Distance of the nearest ends, farthest ends
For two ranges that do not overlap: the lowest value of the higher range minus the highest value of the lower range. The distance of the farthest ends is the highest value of the higher range minus the lowest value of the lower range.
n
The number of measurements that a range comes from. It is written as intervals / processes / sessions / boots (rule V1 point 1). "No session" marks a row that is not part of a session of go.sh.
Rules V1 to V4, F1, F2
The comparison rules in baselines-and-rules.txt.
Boot, boot id
A boot is one run of the machine from a start to the next restart. The boot id is a random identifier that Linux creates at each start. Equal boot ids mean the same boot. The rerun ran in boot 3bfc57a1 (the first 8 characters of its boot id).
MemTotal
The usable memory that Linux reports, in kB.
State line
A line that go.sh or go2.sh prints with the time, the boot id, MemTotal, the load, the logins and the processes per user.
Load average, load
The number of tasks that are runnable or wait for disk input and output, averaged by Linux over the last 1, 5 and 15 minutes (file /proc/loadavg). "Load at launch" is the 1-minute value read directly before a process starts. The fourth field of the file gives the tasks that are runnable now and the number of all tasks.
%CPU, process list
A process list is the output of the tool ps that a run script saves before a launch. %CPU is the column pcpu of this output. It is the CPU time that a process has used, divided by the time since the process started. So it is an average over the life of the process. It is not the use at the moment of the reading.
pr/ttyAMA-1
A Linux kernel thread in the process lists. Its name suggests that it prints Linux kernel messages to the serial console ttyAMA. This meaning was not checked on CRB.
Exit status
The number that a process returns when it ends. 0 means success.
Root
Administrator rights on the machine. They were not approved for this task.
Journal, kernel log
The kernel log is the list of messages of the Linux kernel. The journal is the saved system log of one boot. It holds the kernel log.
Hardware error record, corrected record
A message that the firmware passes to Linux when hardware reports an error. Linux prints it in the kernel log with the tag "[Hardware Error]". Its severity is "corrected" (the hardware repaired it) or "recoverable" (not repaired, the system continues).
Module list
The output of the command dmidecode -t 17. It holds one entry "Memory Device" per memory module, with the configured speed of the module.
Firmware setting, DIMM Frequency, TXREQ
A firmware setting is a value that the machine applies at its next start. "DIMM Frequency" sets the memory speed. TXREQ is a group of settings that were changed for another investigation.
GiB
2^30 bytes.
est.
Estimated, not measured directly.

## 1. Is the new read kernel still below the old one? (Q1)

- The rerun ran parts A, L and C three times (three sessions) and then part C once more, from 22:12:09 to 22:22:18 UTC (10 min 9 s), all in boot 3bfc57a1 [Ref2][Ref3].

- Part A repeats the 120-thread part of the test of 2026-11-13 with the same two binaries [Ref4]. With its whole-pass stop the pass count of an interval changes by whole passes, and the rate changes with it. So part A is less exact than parts L and C [Ref1].

- Part C runs the new read kernel itself [Ref5][Ref6]. Part L runs asmread in its place [Ref7]. asmread is a hand-written loop with the same loads [Ref1].

## 2. Did a rate differ from the 8000 MT/s runs? (Q2)

- The comparison rules and the list of 8000 MT/s rows were fixed before the run [Ref25]. A rule compares the lowest-to-highest range of the 7200 MT/s intervals with that of the 8000 MT/s rows.

- Overlap: "no difference seen". The width of the 8000 MT/s range is then the size that the test cannot exclude (est.).

- No overlap: "differs between the 8000 MT/s boot and the 7200 MT/s boot".

- Each memory speed has exactly 1 boot. So a difference between the two boots is not shown to be an effect of the memory speed.

## 3. What the data do not show

- Insufficient data: whether a difference of the new read kernel comes from the memory speed. Runs in several boots per speed would resolve it (needs reboots and a change of the firmware setting).

- Insufficient data: why the rate of the load-only loop changed between the three visits of the one 7200 MT/s boot (Table 3). Two measurements would resolve it. First: run the part L line alternately from an idle start and directly after part A, at least 3 times each in one boot. Second: repeat the idle-start line some hours later in the same boot, and once directly after a reboot (needs approval).

- Insufficient data: why the old read kernel was lower in part L. The first of these two measurements would resolve it.

- Insufficient data: no 8000 MT/s run of kernel read with bwx12. A run of the two part C lines at 8000 MT/s would resolve it (needs a firmware change and a reboot).

- Insufficient data: whether hardware error records occurred during the rerun. A count of the "[Hardware Error]" lines of the kernel log would resolve it (needs root, which was not approved for this task).

- Insufficient data: a direct reading of the memory speed during the rerun. A module list read during the rerun would resolve it. The command sudo dmidecode -t 17 prints this list (needs root).

- Insufficient data: whether the work before the first 120-thread process changes the rate of the new read kernel. On 2026-11-13 the test script launched 192 one-thread processes from 18:12:23 to 18:17:20 UTC, directly before its 120-thread part [Ref48]. The rerun did not repeat this one-thread phase. A run with the new kernel at several positions, after an idle start and after 120-thread work, would resolve it [Ref25].
