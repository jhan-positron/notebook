Short version. A CRB core sees four levels: a 64 KiB L1 at 1.43 ns, a 2 MiB private L2 at 3.75 ns, a 128 MiB SLC (system level cache: the shared cache that Linux lists as L3, located in the on-chip mesh interconnect) at about 30 ns, and DRAM at 148 ns. One core reads at most 133 GB/s from L1, 85 GB/s from L2, 67 GB/s from the SLC and 30 GB/s from DRAM, and the whole chip reads 15.9 TB/s from L1, at least 0.62 TB/s from the SLC and 533 GB/s from DRAM. Two findings matter for software: with a buffer of 8 MiB each, the two cores of a pair (cores 2k and 2k+1, three pairs tested) together read only about 78 GB/s, against 125 to 134 GB/s for two cores of different pairs, and the core's prefetcher learns a repeated access pattern, so simple cache benchmarks under-report the SLC latency by five times.

What "3 loads / 2 stores of 16 B per cycle" means

The core has four pipelines that start loads and stores. Three of them can each start one load per cycle (named Load/Store 0, Load 1 and Load 2). Two of them can each start one store per cycle (Load/Store 0 and Store 1). Load/Store 0 is in both groups. Each pipeline accepts one operation per cycle. So in one cycle Load/Store 0 does either a load or a store [SOG, section 2.1 page 11, Figure 2-1 and Table 2-1, pages 12 to 13].

It follows that the core can start at most 3 loads + 1 store, or 2 loads + 2 stores, in one cycle. So the label "3 loads / 2 stores" gives two separate limits. It does not mean five operations in one cycle. The core never starts 4 loads + 1 store in one cycle. Only three pipelines accept loads. The guide gives these roles as part of the core's design. It describes no setting that changes them.

The asm copy loop (the hand-written loop that loads 16 B registers from one buffer and stores them to another) is a measured case of the second mix. It measured 178.4 GB/s in L1, which counts the bytes read plus the bytes written (table "Per-core bandwidth" in Record). A mix of 2 loads + 2 stores of 16 B per cycle is 179.2 GB/s at 2.8 GHz.

The widest register a plain load or store can fill is a 128-bit vector register (a "q register"), which holds 16 B. Arm's throughput table gives 3 such loads per cycle (LDR q: 3 per cycle; LDP q, which loads two 16 B registers in one instruction: 1.5 per cycle) and 2 such stores per cycle (STR q: 2 per cycle; STP q: 1 per cycle) [SOG, Table 3-13 page 23 and Table 3-14 pages 24 to 25]. So the L1 can deliver 48 B per cycle to loads and take 32 B per cycle from stores.

The guide draws two more memory pipelines, Store data 0 and Store data 1 [SOG, Figure 2-1 page 12]. They carry the data of a store from a general-purpose register and do not start a store. The data of a 16 B store from a q register goes through one of the two vector pipelines, FP/ASIMD 0 and FP/ASIMD 1 [SOG, Table 2-1 page 13 and Table 3-14 pages 24 to 25].

The measured L1 numbers are the pipeline limit. 48 B per cycle at 2.8 GHz is 134.4 GB/s, and the asm read loop measured 132.7 GB/s (99 %). 32 B per cycle is 89.6 GB/s, and the asm write loop measured 89.5 GB/s. The asm loops use exactly LDP q and STP q [bench/bandwidth.c:179 to 186 and 204 to 211].

The read loop compiled from C: 1.5 loads per cycle

The read loop compiled from C reaches 66.8 GB/s, which is 1.5 loads of 16 B per cycle. The asm read loop measured 132.7 GB/s, which is 99 % of 3 loads per cycle. The limit of two vector adds per cycle can explain at most part of this gap. The cause of the rest is not established. This section gives the source code, the machine code, the limits that were checked, and the test that is missing.

Source code. The read loop compiled from C is the function k_read in bench/bandwidth.c [lines 138 to 148]. It adds every 8 B word of the buffer into one of 16 running sums, and gcc 14.2 chooses the instructions.

__attribute__((noinline)) static uint64_t k_read(const uint64_t *a, size_t n)
{
    uint64_t s[16] = { 0 };
    for (size_t i = 0; i < n; i += 16)
        for (int j = 0; j < 16; j++)
            s[j] += a[i + j];
    uint64_t sum = 0;
    for (int j = 0; j < 16; j++)
        sum += s[j];
    return sum;
}

The core has two vector pipelines (FP/ASIMD 0 and 1), and Arm's table gives 2 vector adds per cycle [SOG, Table 2-1 page 13 and Table 3-15 page 26]. Cache ways: what "4-way" and "8-way" mean

A cache does not search all of its slots for an address. It is divided into sets, and a line (64 B) can live only in the one set that its address bits select. Inside that set there are a fixed number of slots side by side, and that number is the number of ways. "4-way" means each set has 4 slots, so a line has 4 possible places in the whole cache, no more.

The geometry of CRB's three caches comes from the cores' own cache identification registers, as read through sysfs on CRB [/sys/devices/system/cpu/cpu0/cache/index0, index2, index3, read 2026-11-01]. The SLC's 16 ways match one of the two values Arm offers for it, 12 or 16 [CMN S3 TRM, Table 1-9 pages 31 to 32].

Why the number of ways matters. More ways make it less likely that two useful lines fight for the same slot, and fewer ways make lookups cheaper. The 4-way L1 has 256 sets of 64 B, so two addresses exactly 16 KiB apart land in the same set. A program that cycles through 5 lines spaced 16 KiB apart misses in L1 on every access, although it uses only 320 B. The benchmarks in this report avoid this: the random cycle spreads lines evenly over all sets, which is why the 64 KiB footprint shows 0 L1 refills (table in Latency).

A worked example with real addresses

The address does not choose the slot inside a set. The cache control logic does. The seven addresses below show how. Each is split for the L1 data cache: offset = bits 5 to 0, set index = bits 13 to 6, tag = bits 47 to 14. C, D, E and F are each 16 KiB (0x4000) further than A. Adding 16 KiB does not change bits 13 to 0, so the set stays 37 and only the tag changes. G is 64 B further than A, so it is the next line and lands in set 38.

What each field does.

  • Set index (bits 13 to 6) is a plain lookup. For A the hardware goes straight to set 37, with no search.
  • Offset (bits 5 to 0) picks one byte inside the 64 B line. B is byte 16 of A's line.
  • Tag (bits 47 to 14) is the address shifted right by 14 bits. For A: 0x7f1234560940 >> 14 = 0x1fc48d158. 14 bits is 3 hex digits plus 2 bits, so drop "940" to get 0x7f1234560, then divide by 4. 234 different lines map to set 37, and the tag stored in a slot says which one of them the slot holds.

How a slot is chosen when a line is loaded. Every load does two separate checks. First, "is this line already here?" compares the tag of the address with the tag stored in each of the 4 slots. Second, if it is not here, "where do I put it?" looks for a free slot, and evicts a line only when none is free. Starting from an empty set 37:

  1. Load A. No slot has tag 0x1fc48d158, so it is a miss. All 4 slots are free. A goes into slot 0, and its tag is stored next to the 64 bytes.
  2. Load C. Slot 0 holds tag 0x1fc48d158 (A), which is not C's tag 0x1fc48d159. Slots 1 to 3 are empty, so they cannot match either. Miss. Slot 0 is taken, so C goes into the next free slot, slot 1.
  3. Load D, then E. Same two checks. They go into slots 2 and 3. Set 37 is now full.
  4. Load F. No slot has tag 0x1fc48d15c. Miss. No slot is free, so the cache evicts one of the four lines and puts F in its place. Which line goes depends on the core's replacement rule, usually the one used longest ago. The V3AE core manual that states the rule was not available, so the figure assumes slot 0 (est.).
  5. Load A again. If A was the evicted line, this is a miss. The report calls this a conflict miss: the program touched only 5 lines, 320 B, in a 64 KiB cache, and still missed.

How a slot is found on a read. Read B, 0x7f1234560950. Bits 13 to 6 give 37, so the hardware goes to set 37. It compares 0x1fc48d158 with the four stored tags in parallel, and slot 0 matches. Bits 5 to 0 give 16, so byte 16 of slot 0's line is returned. "4-way" therefore means four tag comparators per lookup, and four lines with the same set index can be in the cache at once. In a 1-way (direct-mapped) cache, A and C would already push each other out.

On Arm cores the stored tag is built from the physical address after translation, not from the virtual address shown above. The lookup works the same way. The V3AE core manual that would confirm this detail for CRB was not obtainable (see "Arm documents cited").

The SLC (L3) and the pair port

Three questions from the review: is the SLC an L3 cache, why did older versions of this report call it the "mesh cache", and is the pair port the way the SLC is reached. Each answer is tied to an Arm document or to a measurement. The CAL2 and the two hypotheses on the pair port are marked as an inference or as hypotheses.

Is it an L3 cache?

Linux lists it as cache level 3, unified, 128 MiB, 16-way, shared by CPUs 0 to 127 [/sys/devices/system/cpu/cpu0/cache/index3]. The core itself has two levels: Arm lists "Separate L1 data and instruction caches" and a "Private, unified data and instruction L2 cache" and no L3 for this core [SOG, section 1.1 page 9]. So it is the third level a core sees, and in that sense it is the L3. It is not inside the core or a core cluster. It sits in the interconnect, and Arm's name for it is the System Level Cache (SLC): "The System Level Cache (SLC) is a last-level cache" inside each home node [CMN S3 TRM, section 2.1.1.3 page 54].

The mesh, and why older versions said "mesh cache"

CRB's interconnect is Arm's CMN S3, the Coherent Mesh Network. The Linux mesh counter driver reports part number 0x43e, which the driver source names CMN S3 [/sys/bus/event_source/devices/arm_cmn_0/identifier = 43e05; Linux drivers/perf/arm-cmn.c, PART_CMN_S3 = 0x43e], and its event names start with "hns", the Super Home Node of CMN S3. Arm describes the structure as "a configurable rectangular grid that is composed of network routers that are known as Crosspoints (XPs)", where "each XP connects horizontally and vertically to other XPs, creating a two-dimensional mesh structure", and "each XP can have up to four device ports for connecting CHI-compliant devices" [CMN S3 TRM, section 1.4 page 17]. "Each byte of address space is assigned to a single Home Node (HN)", and "each HN-S can contain an SF and an SLC" [CMN S3 TRM, Home Nodes, page 19]. The SLC is therefore a set of slices, one per home node, spread over the mesh, and every address has exactly one home. An L2 miss travels across the mesh to the home node of its address, or to a local proxy of it. Versions of this report before 2026-11-12 called the SLC the "mesh cache" for that reason. The report now uses Arm's name. A home node also acts as a proxy (Arm: the LCN role of the super home node, whose proxy lines share the slice with its home lines as the LCC) for addresses homed on the other mesh [CMN S3 TRM, Super Home Node, page 55], so a line can be cached by its home slice or by a proxy slice on the other mesh. Whether a line sits in both at once was not measured. The root run measured service from both kinds (section "Latency from each core to each slice").

The mesh driver prints a map of each mesh for root: sudo cat /sys/kernel/debug/arm-cmn/map /sys/kernel/debug/arm-cmn/map_1, one file per mesh [Linux drivers/perf/arm-cmn.c, arm_cmn_debugfs_init and arm_cmn_map_show]. Is the pair port how the SLC is reached?

Yes. A core reaches everything beyond its L2 through one connection: its requester interface (an RN-F in Arm's terms) into a crosspoint device port. Every L2 miss, every write-back and every snoop answer from the core uses that connection, so the SLC, the other cores' caches and DRAM are all behind it.

Arm provides a block that puts two devices on one such port: "A Component Aggregation Layer (CAL) allows multiple devices to connect to a single device port on an XP", and the two-device version "CAL2" supports fully coherent requesters (RN-F) [CMN S3 TRM, section 2.1.1.15 page 63].

The measurement in "The pair finding" ran two cores at the same time. Each core read its own buffer of 8 MiB, which does not fit in its L2. The rates of the two cores were added. One core alone gets 67 GB/s. When the two busy cores are partners (cores 2k and 2k+1, for example 0 and 1), the total is 78 GB/s, so they share one limit. When the two busy cores come from different pairs, the total is 125 to 134 GB/s. That is 1.9 to 2.0 times the rate of one core alone. For example, CPUs 0 and 2 together read 126.6 GB/s with the read loop compiled from C and 129.7 GB/s with the asm loop. Only cores on different meshes (CPUs 0 and 64, CPUs 0 and 119) reached 134 GB/s. Every core has a partner, so the limit does not depend on which cores exist. It depends on which cores are busy at the same time. With one more busy core on another pair, a core with an idle partner read 62.4 to 67.1 GB/s (seven runs, best repetition of each). A core with a busy partner read 37.8 to 40.3 GB/s (five runs, best repetition of each).

What is confirmed by the document is that the mechanism exists. What is measured is that the two cores of a pair slow each other on the three pairs that were tested (CPUs 0 to 5). That CRB attaches its core pairs through a CAL2 is the simplest reading of the two, and it is not confirmed by any CRB document: the firmware tables give each core its own cluster [/sys/devices/system/cpu/cpu*/topology/cluster_cpus_list]. The mesh map adds a counting argument: 64 cores per mesh sit on 35 core ports, so at least 29 ports carry two cores, and the map shows the home nodes on the same crosspoints already sharing ports in twos [crb/results/cmn-map.txt].

Latency from each core to each slice (root run)

On 2026-11-02 Jibin ran the root tool bench/homelat on CRB (final set 05:49 to 06:04 UTC, results in results/sudo-20261102T054936Z/). It works in three steps. First it finds the home nodes: a mesh counter opened with a node id answers only for a node that exists, and 64 answered on each mesh. Second it finds the home node of every 64 B line of a 32 MiB buffer: flush the line, read the 8 home-node counters of a quadrant with one call, load the line 256 times with a flush between loads, read again, and take the one node that rose by 256. Third, for every core and every home node, it builds a random chain through 2048 lines of that node, loads them once in a random order, pushes them out of L1 and L2 with 8 MiB of random loads, and times one walk of the chain that has never been walked, seven times with a fresh chain each time.

Lines homed on the other mesh are served by a local proxy

The home node of a line is fixed by the address hash, and the hash spreads every 2 MiB chunk evenly: each of the 16 chunks put exactly 16,384 of its 32,768 lines on each mesh [full/chunks.csv]. The hash is per line: within every chunk the mesh is the XOR of address bits 6, 8, 10, ... 20 (the pattern of the first 16 lines is 0101 1010 0101 1010, and 80 % of neighbouring lines have different homes), and 4 of the 16 chunks come out inverted, so higher physical-address bits, which user space cannot see, also enter the hash [full/homes.csv, checked on 2026-11-02 over all 524,288 lines]. So half of the lines of any buffer of 2 MiB or more are homed on the other mesh, and a small buffer need not split evenly. A core still sees those lines at 19 to 44 ns, the same range as its own mesh, and the latency to a remote slice is anti-correlated with the latency to the same-numbered local slice (correlation -0.74, median over cores). Arm's design explains it: a home node also acts as a proxy for addresses homed on the other mesh (the LCN role of the super home node, whose proxy lines share the slice with its home lines as the LCC) [CMN S3 TRM, Super Home Node, HBT and LBT, page 55]. The counters confirm the service: in the cache-state check, the 4 remote slices saw 0.00 to 0.01 accesses per load at their home while the loads were served at SLC latency, and during a repeated 8 MiB read stream from CPU 0 the other mesh counted nothing at all (0.000 accesses per line on arm_cmn_1 against 0.827 on arm_cmn_0) [writebw.csv, case asmread-8M-1, analysed with bench/subtract.py]. Hypothesis: which proxy serves which home is a fixed function of the home's position, roughly its mirror image, which would fit two identical chiplets placed rotated. The anti-correlation is the only evidence for it, and this report does not use the remote rows to place anything.

So all of a core's cached lines live on its own mesh, as home lines and as proxy lines in the same 64 slices. That is why one buffer sees 64 MiB of SLC: one mesh's 64 slices of 1 MiB. The earlier explanation, that a buffer is homed on one mesh, was wrong and is withdrawn. Home lines and proxy lines share each slice's storage, and firmware can cap the share of each kind with an occupancy limit that resets to the maximum (CMN S3 TRM, capacity partitioning, pages 335 to 336, and the register fields on page 1039). The limits were not read. A buffer whose lines are homed half and half fills a slice half and half by demand, whatever the limits allow. So the 64 MiB figure is measured, and the only inference about the limits is that neither was below about half for this workload (est.).

Why the SLC row uses 40 threads, not 120

The SLC test needs two things at once. Each thread's buffer must be larger than its 2 MiB L2, or the data never leaves the core. All buffers together must fit in the SLC, or the misses go to DRAM and the number becomes a DRAM number. With 3 MiB per thread, 40 threads is 120 MiB, within the 128 MiB nominal size. 120 threads would be 360 MiB and would overflow. The mesh counters confirm the 40-thread run fit: 2.9 % misses [results/uncore2-20261030T203752Z/cmn-asmread-3M-40T-even.csv]. A second rule halves the usable thread count: one thread per pair. At 8 MiB two partner cores together read only 1.15 to 1.17 times as much as one core alone: 77.5 to 78.5 GB/s against 66.9 to 67.5 GB/s (section "Is the pair port how the SLC is reached?"). So 40 is the largest count tested that fits, and the SLC-served part was still rising at 40, which is why 0.62 TB/s is a lower bound.

The placement was uneven: the first 40 even-numbered CPUs are 32 pairs on chiplet 0 and 8 on chiplet 1. The 8 threads on chiplet 1 got 58 to 62 GB/s each, the 32 on chiplet 0 got 25 to 30 GB/s each [perthread-asmread-3M-40.csv]. Hypothesis: a per-chiplet shared limit, so 20 threads per chiplet would give a higher chip-wide number. The test is the same run with CPUs 0, 2, ... 38 and 64, 66, ... 102; not run.

Method and caveats

  • All code is our own C, compiled on CRB with gcc 14.2 at -O3 -march=native. Threads are pinned. Buffers are 2 MiB-aligned and first-touched by the thread that uses them. Transparent huge pages were in effect (AnonHugePages equals the buffer size in every run).
  • Latency is the minimum over reps, which is what "best case" means here. Each rep is at least 0.3 s or 2 full cycles (repeated chain) or exactly one pass (fresh chain).
  • Bandwidth is the best of 3 reps of at least 0.5 s; aggregate = total bytes / slowest thread's time.
  • The SLC latency and bandwidth rows carry a few percent of L2 hits because the footprint rule (above 2 MiB per thread, below 128 MiB total) leaves little room. The corrected latency is labelled est.
  • The "learned pattern" explanation of the repeated-chain curve is a hypothesis that fits the counters (L2 refills 1.0 per load at 5.4 ns). Confirming it needs the core's prefetch controls, which require kernel privilege.
  • The 8 reserved cores (120-127) were never used - this is a simple operation agreement between Jeremy and me, there is no technical reason - and the whole-chip tests used 120 of 128 cores.
  • Mesh counters (arm_cmn PMUs) were read in two short passes with perf_event_paranoid at 0, set and reset by Jibin. No governor, package or boot setting was changed. Only files under /home/jhan/cache-perf were written.

    • Measured or documented. The mesh clock is 2.0 GHz. The mesh cycle counter measured it in part 5 of run_sudo.sh [results/sudo-20261102T211150Z/writepath.csv]. A data flit holds 32 B [CMN S3 TRM, Table A-2 page 2120].

The Linux mesh driver on CRB lists events for a second response channel (rsp2) and none for a second data channel (dat2) [results/probe-20261111T210017Z.txt]. The driver hides the dat2 events when the mesh reports fewer than two data channels [Linux drivers/perf/arm-cmn.c, function arm_cmn_event_attr_is_visible]. That source is Arm's kernel source for firmware 0.9.0. CRB runs the kernel build for firmware 0.7.2, and its source is not in Arm's kit.
    • Hypothesis 1, capacity. The pair port has one data channel in each direction, and a channel passes at most one data flit per mesh cycle. That is 32 B × 2.0 GHz = 64 GB/s of data that crosses the port in each direction. The limit of one flit per clock cycle follows from the signals of Arm's CHI link protocol. CHI is the Coherent Hub Interface, the protocol of the mesh ports and links. One channel has one flit bus and one valid signal [AMBA CHI specification, IHI 0050 issue H, Figure B13.14 and Table B13.5, pages 469 to 470]. The flit bus is the set of wires for one flit. The valid signal marks a cycle that carries a flit. None of the Arm documents that were read states the limit in one sentence.
    • Hypothesis 2, saturation. Four kinds of run fill this capacity, and the full port is what limits them. They are the runs of two partner cores that read 8 MiB each, of two partner cores that write 8 MiB each with the asm loop, of one core that writes 1 GiB with the asm loop, and of two partner cores that write 1 GiB each. A size such as 8 MiB or 1 GiB is the size of the buffer of each core. Each core reads or writes its own buffer again and again. This report calls these four kinds of run the runs of hypothesis 2. Hypothesis 2 is a separate statement. Hypothesis 1 can hold while a run leaves the port partly idle.
    • Conversion, two assumptions. The measured rates count the bytes that the loops read or wrote. Both hypotheses are about the bytes that cross the port. The conversion between the bytes of the loops and the bytes that cross the port makes two assumptions.
      • The first assumption: one bus read or bus write of a core is one data flit of 32 B at the port (see "bus access" in "Words used here").
      • The second assumption: a count per line that was measured on one core alone also holds for two partner cores.
      • Most counts are from part 5 (2026-11-02). Most of the pair rates are from runs of 2026-10-30. Each item below names its sources.
      • For one core alone the counts of part 5 fit the first assumption. One writer at 1 GiB sends 2.00 bus writes per 64 B line [writepath.csv, case w1G-c2]. Words used here

CRB
The Arm "Phoenix Reference Server" at 192.168.2.45: 128 Arm cores (part 0xd83, which the Linux kernel table names Neoverse V3AE), fixed 2.8 GHz clock, 320 GiB DRAM, Linux 7.1.3.
cycle
One clock period at 2.8 GHz = 0.357 ns. Cycle counts above are ns multiplied by 2.8.
mesh clock, mesh cycle
The clock of the mesh interconnect (Arm CMN). It ran at 2.0 GHz on CRB with firmware 0.7.2. One mesh cycle is then 0.5 ns. It is a different clock from the 2.8 GHz core clock. It was measured with the mesh cycle counter (the cycle counter of the mesh's performance monitor, perf event dtc_cycles) in part 5 of run_sudo.sh on 2026-11-02, with the machine idle and with 1 to 4 busy cores [results/sudo-20261102T211150Z/writepath.csv]. It was not measured with the whole chip busy. Arm's user guide for firmware 0.9.0 gives the same value [SVK user guide, page 10]. Firmware 0.9.0 also adds frequency scaling for the mesh [SVK user guide, page 7], so the clock must be measured again after a firmware update.
flit, data flit, data channel
"Flit" is short for "flow control unit". It is a known term of link protocols. Arm's CHI specification defines it: "FLow control unIT (Flit) is the smallest flow control unit" [AMBA CHI specification, IHI 0050 issue H, page 32]. CHI (Coherent Hub Interface) is the protocol of the mesh ports and links. In this report a flit is one transfer unit on a mesh link or port. A data flit carries data and holds 32 B [CMN S3 TRM, Table A-2 page 2120]. A 64 B line needs two data flits. A data channel is the part of a link or port that carries data flits.
credit stall, data stall
A sender on a mesh link needs one credit from the receiver for each flit [AMBA CHI specification, IHI 0050 issue H, page 518]. A credit-stall cycle is one count of the link event "TX flit stall". Arm describes it as "signaled when flit transmission is stalled and waiting on credits" [CMN S3 TRM, page 1679]. A data stall is one count of the home-node event for a home node that has a data flit to send and no credit for it [CMN S3 TRM, page 391, event PMU_HN_TXDAT_STALL_EVENT]. The table of part 5 calls it a "data-send stall".
back-pressure
This report's word for the waits of a sender that has no credit. Credit-stall cycles and data stalls count such waits.
write in flight
A write that the core has sent and that is not yet complete.
streaming write
A write whose line is not allocated in L1 or L2. Part 5 counted 0.000 refills for writes per line with the asm write loop. The counts are in section "Where one writer's 73 GB/s limit sits (part 5, 2026-11-02)".
bus access, bus read, bus write
One data transfer between a core and the mesh, as the core's own counters count it (Arm events BUS_ACCESS and BUS_ACCESS_WR). A bus write goes from the core to the mesh, and a bus read goes to the core. Arm's event list for this core says that each beat of data is counted individually [Linux source in Arm's kit, tools/perf/pmu-events/arch/arm64/arm/neoverse-v3/bus.json]. The file is in the folder neoverse-v3 of that source. The table mapfile.csv of the same source assigns part 0xd83, the part number of CRB's cores, to that folder. A beat is one transfer on the bus. This report takes one transfer as 32 B. That belongs to the first assumption of the conversion in "Open items". One count of part 5 fits it: one writer sent 2.00 bus writes per 64 B line at 1 GiB.
bus reads in part 5
Part 5 counted all bus accesses and the bus writes. It did not count the bus reads. This report takes them as all bus accesses minus bus writes (est.). Arm's list also says that the count of all bus accesses includes snoop requests and snoop responses. A snoop is a request from the mesh to a core about a line that the core may hold. So the difference can hold more than bus reads. The port counts of case r8M-c2 (the 2 s run minus the 0.2 s run) hold 4,182 snoop flits and 3.3 × 109 data flits from the crosspoint to the port in 1.8 s. So snoops were a small part of the traffic at that port.
L1, L2
The first and second cache level inside each core: 64 KiB data L1 and 2 MiB L2, both private to one core (confirmed by measurement, see the pair section).
SLC (L3)
The system level cache. That is Arm's name for the 128 MiB cache that all 128 cores share. Linux reports it as "L3". Versions of this report before 2026-11-12 called it the "mesh cache". It sits in the on-chip mesh interconnect (Arm CMN). Mesh counters confirm that L2 misses are served there. CRB has two meshes (arm_cmn_0 and arm_cmn_1). The mesh map shows 64 home nodes in each, so each mesh holds 64 slices, 64 MiB, at 1 MiB per slice (est. from 128 MiB / 128 nodes). A core's lines are all cached on its own mesh, as home lines or as proxy lines in the same 64 slices, so one core sees 64 MiB. Home lines and proxy lines share each slice under occupancy limits that were not read. See "The SLC (L3) and the pair port" and "Latency from each core to each slice".
proxy (LCN, LCC)
A home node on a core's own mesh that caches lines whose home is on the other mesh. Arm calls the role LCN (local coherency node) and the proxy lines' share of the slice LCC (local coherent cache). Home lines and proxy lines share the slice's storage [CMN S3 TRM, page 55]. Measured on CRB: lines homed on the other mesh and already in the SLC are served on the core's own mesh at the same 19 to 44 ns as a local line.
DRAM
Main memory: 10 Micron 32 GB DDR5-8000 registered DIMMs (part MTC20F2085S1RC80BH1, 2 ranks, 80-bit width), one per channel, running at 8000 MT/s. Ten channels at 8000 MT/s give 640 GB/s theoretical peak. Source: dmidecode type 17, run by Jibin on 2026-10-30.
GB/s, TB/s
Bandwidth in 109 or 1012 bytes per second. Cache and buffer sizes use KiB, MiB, GiB (powers of 1024). "At 8 MiB" or "at 1 GiB" gives the size of the buffer of each thread. Each thread reads or writes its own buffer again and again. A copy thread has two buffers of that size. It reads one and writes the other [bench/bandwidth.c, lines 4 to 6 and 301 to 306; column bytes_per_thread of the bandwidth result files, for example results/followup-20261030T194205Z/asm.csv]. The bandwidth tests with one, two or four threads use 8 MiB per thread for the SLC and 1 GiB per thread for DRAM [bench/run_crb.sh, lines 83 to 89; caption of the first figure in "Bandwidth per core"]. The whole-chip tests use 3 MiB per thread for the SLC and 256 MiB per thread for DRAM (caption of the first figure in "Bandwidth of the whole chip").
pointer chase
The latency test: each load reads the address of the next load, so loads cannot overlap. Lines are 64 B and visited in one random cycle.
repeated chain
The usual chase: the same random cycle is walked many times. CRB's cores learn it (see Latency).
fresh chain
Each line holds 8 chains. The data is warmed with chain 0, then one single pass is timed on a chain the core has never walked.
compiled loop, asm loop
Two versions of each bandwidth kernel in bench/bandwidth.c. "Compiled" is the version written in C and compiled by gcc 14.2 at -O3. For read it is a vector loop of 8 loads and 8 adds per 128 B. For write and copy it is a loop that moves one 16 B vector per pass (machine code read on CRB on 2026-11-11). "asm" is a hand-written loop of only 16 B loads or stores, which shows the true pipe limit.
pair port, partner cores
The crosspoint port that cores 2k and 2k+1 share. The two cores of one pair are called partner cores, or partners. The sharing is inferred from two timing tests (the latency fit and the pair test) and from the port count of the mesh map. It was not read from hardware or from documentation. What limits the rate of a pair was not measured (see "Open items").
one thread per pair
Threads placed on even-numbered cores only, so no two threads share a pair port.
way, set
A cache is divided into sets. Each line can be stored only in one set, chosen from its address. A set holds a fixed number of lines side by side, and that number is the number of ways ("4-way" = 4 slots per set). See "Cache ways" above.
chiplet
One of the two halves of the CRB processor. Each half has its own mesh (Linux shows two CMN devices, arm_cmn_0 and arm_cmn_1), 64 cores (CPUs 0 to 63 on chiplet 0 and 64 to 127 on chiplet 1, measured in the root run), 64 SLC slices, and 5 DDR5 channels (the DIMM inventory names the slots DIMM_CP0_0 to 4 and DIMM_CP1_0 to 4). The halves are joined by chip-to-chip gateways (CCG, 8 per mesh in the map). Whether they are two separate dies is not readable from Linux; "chiplet" here means one mesh with its cores and memory.
CMN, XP, home node, CAL
Arm's Coherent Mesh Network, the on-chip interconnect on CRB (model CMN S3). XP = crosspoint, one router of the mesh grid. Home node (HN-S) = the mesh node that owns an address range and holds a slice of the SLC. CAL = Component Aggregation Layer, Arm's block that lets two devices share one crosspoint port. See "The SLC (L3) and the pair port" above.
