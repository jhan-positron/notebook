Short version. The physical address of a line (64 bytes) picks the home node of the line. Each home node is at one crosspoint of one mesh. Some lines have their home on the other mesh. A core that has read such a line before gets it from its own mesh. Counters support this for CPU 0, and the latency supports it for the other cores. Arm calls the answering node a proxy, and its position is fitted from latency.

What picks the home node.

  • The input. The mesh uses the physical address (PA) of the line. Each request of a core passes through an address map in the mesh (Arm's name: RN SAM). The address map picks the target node of the request. Arm lists "The Physical Address (PA) of the request" as one of the two inputs of the address map. The other input is the kind of request [CMN S3 TRM, section 2.4.5 page 134].
  • Not the virtual address. The virtual address (VA) is the address that a program sees. The kernel chooses the physical page behind each virtual page. A program without the CAP_SYS_ADMIN privilege (root has it) cannot read the PA. For such a program the kernel returns 0 in the page frame number field of /proc/self/pagemap. That field holds the number of the physical page [Linux Documentation/admin-guide/mm/pagemap.rst].
  • The mesh. Take the 16 even-numbered PA bits from 6 to 36 (bits 6, 8, 10, ... 36) and XOR them. XOR (exclusive or) gives 1 when an odd number of the bits are 1. The result 0 means mesh 0, and the result 1 means mesh 1. This rule gives the measured mesh for all 524,288 lines of the 32 MiB buffer [full/homes.csv, full/chunks.csv, checked by crb/tmp/agent-scratch/proxy-examples-2026-11-12/hash/hash2.py].
  • The node (a fitted model). Six more XOR results, each over a different set of PA bits, pick one of the 64 home nodes of that mesh through a lookup table. So 7 XOR results together pick one of the 128 home nodes. The model fits all 524,288 lines [crb/tmp/agent-scratch/proxy-examples-2026-11-12/hash/hash.py]. The lookup table of the model was built from the measured home nodes. It was not read from the hardware. The coordinates X and Y of the node are not XOR results themselves.
  • Limit of the rule. The buffer had 16 chunks of 2 MiB, and each chunk is one physical page. PA bits 37 and higher had the same value in all 16 chunks. So the data cannot show whether the rule uses them. The data fix the bits 6 to 20 of each XOR result. For the bits 21 to 36, other choices fit the 16 chunks as well as the even-numbered bits do [crb/tmp/agent-scratch/proxy-examples-2026-11-12/refute-hash/refute.out].
  • The same rule on the VA fails. It gives the wrong mesh for 262,144 of the 524,288 lines. It is wrong for every line of 8 chunks and right for every line of the other 8 [crb/tmp/agent-scratch/proxy-examples-2026-11-12/worker/va_rule.py]. Inside one 2 MiB page the VA and the PA have the same bits 0 to 20. So the VA shows which lines of one page have their homes on the same mesh. It does not show which mesh that is. That depends on PA bits 21 and higher.

  • A and B are neighbours, and their homes are on different meshes. B differs from A in PA bit 6 only. Bit 6 is one of the even-numbered bits. So the XOR result changes from 0 to 1.
  • A and C are 6 MiB apart in virtual memory. The kernel put the page of C at a physical address 48 GiB below the page of A. The home of C follows from that physical address. A program cannot predict the mesh or the node of C from the virtual address.
  • Every pair of lines splits. Lines 2k and 2k+1 of the buffer differ in PA bit 6 only. Their homes are on different meshes in all 262,144 pairs [crb/tmp/agent-scratch/proxy-examples-2026-11-12/worker/bit6_rule.py]. So for a core on either mesh, half of the lines of this buffer are homed on the other mesh. This holds for these pairs only. Example: lines 3 and 4 are neighbours too, and both are homed on mesh 1. Bit 6 is in the mesh rule. So the same half split is expected for any buffer that consists of complete pairs of this kind. Such a buffer starts at a physical address that is a multiple of 128 bytes, and its length is a multiple of 128 bytes. A buffer with another start or length has lines without a pair at its ends, and it need not split in half. Only this buffer was measured.
  • Each chunk splits. Each of the 16 chunks has exactly 16,384 of its 32,768 lines on each mesh [full/chunks.csv]. Two neighbouring lines never have the same home node [crb/tmp/agent-scratch/proxy-examples-2026-11-12/hash/hash.py].

What picks the proxy node.

  • Arm's design. A Super Home Node (HN-S, the node type that the mesh driver reports for the home nodes of CRB) is a home node for some lines. It is also a proxy for lines that are homed on another chip. Arm calls the proxy role LCN (Local Coherency Node) [CMN S3 TRM, page 13]. Arm writes that the HN-S "allows caching of remote addresses which allows local sharing without going off-chip" [CMN S3 TRM, section 2.1.1.4 page 55].
  • The path in Arm's design. Arm's manual says "chip" for one mesh with its cores. On CRB that is one chiplet. When the address map is set up for HN-S, it returns a node of the core's own chip as the target for such a line [CMN S3 TRM, Figure 4-1 page 325, Table 4-1 page 326]. The target table of the address map on the core's chip has entries for the home nodes of the other chip. Those entries hold node ids of the core's own chip [CMN S3 TRM, Figure 4-2 page 327, and the example for 2 chips on pages 328 to 329]. The manual also has cases that do not use the local HN-S. For one kind of link between chips (CML_SMP), Table 4-2 sends non-shareable requests to the gateway node, and it names no target for shareable requests [CMN S3 TRM, Table 4-2 page 326]. The manual does not say which setup CRB uses, and it does not give the table of CRB.
  • Measured on CRB, position fitted. Take the lines of one home node of mesh 1. Their latency from the cores of mesh 0 (64 cores on 32 crosspoints) rises with the distance, in crosspoint hops, from one crosspoint of mesh 0. The fit takes that crosspoint as the position of the proxy. The same holds for each of the 64 home nodes of mesh 1 [full/latency.csv, fitted by crb/tmp/agent-scratch/proxy-examples-2026-11-12/proxyfit/proxyfit.py]. The fit is as close as for the slices of mesh 0 itself (table below).
  • No extra latency. Over all 120 cores, lines homed on the other mesh take 18.8 to 44.0 ns for each load, by home node. Lines homed on the core's own mesh take 18.8 to 44.2 ns [full/latency.csv].
  • The result is a one-to-one map in this run. Each of the 32 crosspoints with slices on mesh 1 has one proxy crosspoint on mesh 0 (second figure below). The two home nodes of one crosspoint have the same proxy crosspoint. The latency data does not show which of the two nodes on the proxy crosspoint serves a line.
  • The rule behind the map. The proxy crosspoint of a line is the home crosspoint of the line that differs in PA bit 6 only. Example: the proxy of B on mesh 0 is at (2,5). That is the home crosspoint of A. This holds for all 262,144 pairs of lines 2k and 2k+1, with the homes as measured and the proxies as fitted [crb/tmp/agent-scratch/proxy-examples-2026-11-12/worker/bit6_rule.py]. In the terms of the model: the six XOR results select one node on each mesh. The mesh result says which of the two is the home. The crosspoint of the other node is the fitted proxy crosspoint. Whether that node itself is the proxy is a hypothesis. One line supports it (next bullet).
  • One check by node id. An earlier attempt of the root run (03:45 UTC, 2 MiB buffer) counted all read requests at each node (event hns_pocq_reqs_recvd_read). That attempt stopped in its self-test. CPU 0 loaded one line 256 times in each of three probes. It flushed the line from all caches before each load, so each load was a first read. This differs from the state of evidence 2 below. Two counters rose by 255 to 262 read requests in each probe: node 0x288 of mesh 0, at crosspoint (5,1), and node 0xa0 of mesh 1, at crosspoint (1,4). The log does not say which of the two is the home. The proxy map pairs (5,1) of mesh 0 with (1,4) of mesh 1. This check covers one line of another buffer. The final run counted requests at the home only (event hns_pocq_reqs_recvd_hbt), so it cannot repeat this check [results/sudo-20261102T034539Z/log.txt, lines 16 to 18].
  • The other direction. The fits from the cores of mesh 1 agree with this map. For 24 of the 32 crosspoints they give the crosspoint that the map gives. For the other 8 they give two candidates, one in column 6 and one in column 7 of mesh 1, and the map gives one of the two. The cause: no measured core is in column 7 of mesh 1. CPUs 120 to 127 were not measured. By the layout of mesh 0 they are in that column (inferred).
  • No geometric rule. The map is not a mirror image and not a rotation of the grid. A mirror image or a rotation matches at most 3 of the 32 crosspoints. With a shift of the columns and rows added, the best rule matches 8 of the 32 [crb/tmp/agent-scratch/proxy-examples-2026-11-12/refute-proxy/out.txt, section B].

RMS is the root of the mean squared difference between the fitted line and the 32 values of one node. There is one value for each crosspoint with cores. It is the lower latency of the 2 cores there. Limits of the fit: it finds the crosspoint where the latency is lowest. It does not read which node answered. It chooses among the 32 crosspoints that have slices. It uses one run of one boot. The core positions that it uses are fitted too. A second test uses no core positions. It compares the latencies of each home node of mesh 1 with those of the 32 crosspoints of the core's own mesh. It gives the same 32 proxy crosspoints. For the 8 open cases of mesh 1 it picks the candidate that the map gives, when it compares absolute latencies [crb/tmp/agent-scratch/proxy-examples-2026-11-12/refute-proxy/out.txt, section G].

Where the data is stored.

  • Home on the core's own mesh: in the slice of the home node.
  • Home on the other mesh: on the core's own mesh. Counters support this for CPU 0 (evidence 2 and 3). The slice is taken to be the slice of the proxy node, from the latency (evidence 1). Arm calls this share of a slice LCC (Local Coherent Cache) [CMN S3 TRM, section 2.1.1.4 page 55].
  • Tested state. The core had read each line once and had then pushed it out of its own L2. Lines that cores of both meshes use were not tested here.
  • Evidence 1 (latency, fitted). For lines homed on the other mesh, the latency from each core matches the latency of a slice of the core's own mesh at the proxy crosspoint. The difference is at most 0.33 ns (RMS over the cores of mesh 0) [crb/tmp/agent-scratch/proxy-examples-2026-11-12/refute-proxy/out.txt, section G].
  • Evidence 2 (counters, CPU 0, 4 home nodes of mesh 1). A check in the root run counted mesh accesses during timed loads. In one pass each of the 4 home nodes counted 0.000 to 0.003 accesses for each load, at 31 to 36 ns for each load. In a second pass all of mesh 1 counted 0.01 to 0.08 accesses for each load. All of mesh 0 counted 1.04 to 2.05 accesses and 0.01 to 0.30 misses for each load. The accesses above 1 for each load are not attributed. Each count is the total of a whole mesh, minus the count of an empty window, divided by the number of timed loads. The counters do not match an access or a miss to one load. So the share of the timed loads that hit on mesh 0 was not measured. Together with the latency (evidence 1), the counts support service from mesh 0. They do not prove it for each load, and they do not show which slice [full/verify.csv].
  • Evidence 3 (counters, CPU 0). During a repeated 8 MiB read stream, mesh 1 counted 0.000 accesses and 0.000 cache fills for each line. Mesh 0 counted 0.827 accesses and 0.828 cache fills for each line. The homes of this buffer were not measured. By the mesh rule, half of its lines are homed on mesh 1 (inferred) [writebw.csv, case asmread-8M-1, analysed with bench/subtract.py].
  • Cores of mesh 1. Only the latency was measured. No counter was read for them.
  • Not measured: which node id stores a line, and whether a line can be in its home slice and in a proxy slice at the same time.
  • First read. The first read of a line that only the other chiplet holds is slower. See "A first read of lines cached on the other chiplet costs 85 ns, later reads 32 ns".
