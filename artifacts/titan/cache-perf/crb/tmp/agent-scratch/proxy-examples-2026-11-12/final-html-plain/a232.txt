<p><b>Short version.</b> The physical address of a line (64 bytes) picks the home node of the line. Each home node is at one crosspoint of one mesh. When the home is on the other mesh, a core is answered by a proxy node on its own mesh, for a line that it has read before.</p><p><b>What picks the home node.</b></p><ul><li><b>The input.</b> The mesh uses the physical address (PA) of the line. Arm lists "The Physical Address (PA) of the request" as one of the two inputs of the lookup. The other input is the kind of request [CMN S3 TRM, section 2.4.5 page 134].</li><li><b>Not the virtual address.</b> The virtual address (VA) is the address that a program sees. The kernel chooses the physical page behind each virtual page. A program without the CAP_SYS_ADMIN privilege (root has it) cannot read the PA. The kernel returns 0 in the frame number field of <code>/proc/self/pagemap</code> [Linux Documentation/admin-guide/mm/pagemap.rst].</li><li><b>The mesh.</b> Take the 16 even-numbered PA bits from 6 to 36 (bits 6, 8, 10, ... 36) and XOR them. XOR (exclusive or) gives 1 when an odd number of the bits are 1. The result 0 means mesh 0, and the result 1 means mesh 1. This rule gives the measured mesh for all 524,288 lines of the 32 MiB buffer [<code>full/homes.csv</code>, <code>full/chunks.csv</code>, checked by <code>crb/tmp/agent-scratch/proxy-examples-2026-11-12/hash/hash2.py</code>].</li><li><b>The node (a fitted model).</b> Six more XOR results, each over a different set of PA bits, pick one of the 64 home nodes of that mesh through a lookup table. So 7 XOR results together pick one of the 128 home nodes. The model fits all 524,288 lines [<code>crb/tmp/agent-scratch/proxy-examples-2026-11-12/hash/hash.py</code>]. The lookup table was read off the data. The coordinates X and Y of the node are not XOR results themselves.</li><li><b>Limit of the rule.</b> The buffer had 16 chunks of 2 MiB, and each chunk is one physical page. PA bits 37 and higher had the same value in all 16 chunks. So the data cannot show whether the rule uses them. The data fix the bits 6 to 20 of each XOR result. For the bits 21 to 36, other choices fit the 16 chunks as well as the even-numbered bits do [<code>crb/tmp/agent-scratch/proxy-examples-2026-11-12/refute-hash/refute.out</code>].</li><li><b>The same rule on the VA fails.</b> It gives the wrong mesh for 262,144 of the 524,288 lines. It is wrong for every line of 8 chunks and right for every line of the other 8 [<code>crb/tmp/agent-scratch/proxy-examples-2026-11-12/worker/va_rule.py</code>]. Inside one 2 MiB page the VA and the PA have the same bits 0 to 20. So the VA shows which lines of one page have their homes on the same mesh. It does not show which mesh that is. That depends on PA bits 21 and higher.</li></ul><p><b>Three example lines.</b> All three are lines of the buffer of the root run [<code>full/homes.csv</code>, <code>full/chunks.csv</code>, <code>full/nodes.csv</code>].</p><div class="tw"><table><tr><th>Line</th><th>Virtual address</th><th>Physical address</th><th>XOR of the even-numbered PA bits 6 to 36</th><th>Home mesh</th><th>Home node</th></tr><tr><td>A</td><td><code>0xffff8a000000</code></td><td><code>0x21dd7e00000</code></td><td>0</td><td>mesh 0</td><td>0x128, at crosspoint (2,5)</td></tr><tr><td>B (the next line, 64 bytes after A)</td><td><code>0xffff8a000040</code></td><td><code>0x21dd7e00040</code></td><td>1</td><td>mesh 1</td><td>0x290, at crosspoint (5,2)</td></tr><tr><td>C (6 MiB after A)</td><td><code>0xffff8a600000</code></td><td><code>0x211c3c00000</code></td><td>1</td><td>mesh 1</td><td>0x390, at crosspoint (7,2)</td></tr></table></div><ul><li><b>A and B are neighbours, and their homes are on different meshes.</b> B differs from A in PA bit 6 only. Bit 6 is one of the even-numbered bits. So the XOR result changes from 0 to 1.</li><li><b>A and C are 6 MiB apart in virtual memory.</b> The kernel put the page of C at a physical address 48 GiB below the page of A. The home of C follows from that physical address. A program cannot predict the mesh or the node of C from the virtual address.</li><li><b>Every pair of lines splits.</b> Lines 2k and 2k+1 of the buffer differ in PA bit 6 only. Their homes are on different meshes in all 262,144 pairs [<code>crb/tmp/agent-scratch/proxy-examples-2026-11-12/worker/bit6_rule.py</code>]. So for a core on either mesh, half of the lines of this buffer are homed on the other mesh. Bit 6 is in the mesh rule, so the same is expected for any buffer. Only this buffer was measured.</li><li><b>Each chunk splits.</b> Each of the 16 chunks has exactly 16,384 of its 32,768 lines on each mesh [<code>full/chunks.csv</code>]. Two neighbouring lines never have the same home node [<code>crb/tmp/agent-scratch/proxy-examples-2026-11-12/hash/hash.py</code>].</li></ul><p><b>What picks the proxy node.</b></p><ul><li><b>Arm's design.</b> A Super Home Node (HN-S, the node type that the mesh driver reports for the home nodes of CRB) is a home node for some lines. It is also a proxy for lines that are homed on another chip. Arm calls the proxy role LCN (Local Coherency Node) [CMN S3 TRM, page 13]. Arm writes that the HN-S "allows caching of remote addresses which allows local sharing without going off-chip" [CMN S3 TRM, section 2.1.1.4 page 55].</li><li><b>The path in Arm's design.</b> When the lookup is set up for HN-S, the request of a core for such a line goes first to a proxy on the core's own chip [CMN S3 TRM, Figure 4-1 page 325, Table 4-1 page 326]. The lookup table of the core's chip has entries for the home nodes of the other chip. Those entries hold node ids of the core's own chip [CMN S3 TRM, Figure 4-2 page 327, and the example for 2 chips on pages 328 to 329]. The manual also allows a setup that sends the request straight to the other chip. The manual does not say which setup CRB uses, and it does not give the table of CRB.</li><li><b>Measured on CRB, position fitted.</b> Take the lines of one home node of mesh 1. Their latency from the cores of mesh 0 (64 cores on 32 crosspoints) rises with the distance, in crosspoint hops, from one crosspoint of mesh 0. The fit takes that crosspoint as the position of the proxy. The same holds for each of the 64 home nodes of mesh 1 [<code>full/latency.csv</code>, fitted by <code>crb/tmp/agent-scratch/proxy-examples-2026-11-12/proxyfit/proxyfit.py</code>]. The fit is as close as for the slices of mesh 0 itself (table below).</li><li><b>No extra latency.</b> Over all 120 cores, lines homed on the other mesh take 18.8 to 44.0 ns for each load, by home node. Lines homed on the core's own mesh take 18.8 to 44.2 ns [<code>full/latency.csv</code>].</li><li><b>The result is a one-to-one map in this run.</b> Each of the 32 crosspoints with slices on mesh 1 has one proxy crosspoint on mesh 0 (second figure below). The two home nodes of one crosspoint have the same proxy crosspoint. The latency data does not show which of the two nodes on the proxy crosspoint serves a line.</li><li><b>The rule behind the map.</b> The proxy crosspoint of a line is the home crosspoint of the line that differs in PA bit 6 only. Example: the proxy of B on mesh 0 is at (2,5), which is the home crosspoint of A. This holds for all 262,144 pairs of lines 2k and 2k+1, with the homes as measured and the proxies as fitted [<code>crb/tmp/agent-scratch/proxy-examples-2026-11-12/worker/bit6_rule.py</code>]. In the terms of the model: the six XOR results select one node on each mesh. The mesh result says which of the two is the home. The other one is the proxy.</li><li><b>One check by node id.</b> A self-test of the root run counted all read requests at each node. Loads of one line from CPU 0 raised two counters by 255 to 262 in each of three probes: node 0x288 of mesh 0, at crosspoint (5,1), and node 0xa0 of mesh 1, at crosspoint (1,4). The map gives (5,1) as the proxy crosspoint of (1,4). This check covers one line of another buffer [<code>results/sudo-20261102T034539Z/log.txt</code>, lines 16 to 18].</li><li><b>The other direction.</b> The fits from the cores of mesh 1 agree with this map. For 24 of the 32 crosspoints they give the crosspoint that the map gives. For the other 8 they give two candidates, one in column 6 and one in column 7 of mesh 1, and the map gives one of the two. The cause: no measured core is in column 7 of mesh 1. CPUs 120 to 127 were not measured. By the layout of mesh 0 they are in that column (inferred).</li><li><b>No geometric rule.</b> The map is not a mirror image and not a rotation of the grid. The best rule of that kind matches 8 of the 32 crosspoints.</li></ul><div class="tw"><table><tr><th>Fit of latency against hops, cores of mesh 0</th><th>64 home nodes of mesh 0 (position known from the map file)</th><th>64 home nodes of mesh 1 (position of the proxy fitted)</th></tr><tr><td>Distance from fit to measurement (RMS), median over the nodes, ns</td><td>0.86</td><td>0.84</td></tr><tr><td>The same, worst node, ns</td><td>1.16</td><td>1.11</td></tr><tr><td>Cost of one hop, median, ns</td><td>2.66</td><td>2.65</td></tr><tr><td>Latency at 0 hops, median, ns</td><td>19.6</td><td>19.6</td></tr></table></div><p class="note">RMS is the root of the mean squared difference between the fitted line and the 32 values of one node.
