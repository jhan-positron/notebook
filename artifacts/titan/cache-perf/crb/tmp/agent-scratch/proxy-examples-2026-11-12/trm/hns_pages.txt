About CMN S3(AE)
Home Nodes
In CHI, each byte of address space is assigned to a single Home Node (HN). That HN is responsible
for handling all memory transactions that are associated with that address.
There are three types of HN devices within the CMN S3(AE) system:
HN-F
HN-F device instances are the Home Nodes for all coherent memory. HN-Fs also support
non-coherent memory accesses. Memory that is mapped to an HN-F targets DRAM. Each
HN-F can contain an SF and an optional SLC slice. The amount of SLC required determines
the number of HN-Fs. The total SLC size required divided by the number of HN-F instances
determines the recommended SLC size for each HN-F instance. Generally, each HN-F
partition has the same SLC size. You must conﬁgure the amount of SLCs and number of HN-
Fs separately.
The optimal total SF size is twice the total exclusive cache size for all local RN-
Fs. For example, for a 32MB local RN-F total cache size, the recommended SF
size is 64MB.
HN-S
In this book any descriptions related to the Fully coherent Home Node (HN-F)
also apply to the Super Home Node (HN-S).
HN-S device instances, act as HN-F nodes for local coherent memory and Local Coherency
Nodes (LCNs) for remote coherent memory. HN-S also support non-coherent memory
accesses for local memory. Memory that is mapped to HN-S targets local and remote DRAM.
Each HN-S can contain an SF and an SLC, both shared between HN bound traﬃc (HBT) and
LCN bound traﬃc (LBT). For more information about partitioning the SLC between HBT and
LBT lines, see HN-S SLC and LCC capacity partitioning.
The amount of SLC required determines the number of HN-Ss. The total SLC size required
divided by the number of HN-S instances determines the recommended SLC size for each
HN-S instance. Generally, each HN-S partition has the same SLC size. The amount of SLC
and number of HN-S nodes are conﬁgured separately.
The optimal total SF size is twice the total exclusive cache size for all RN-
Fs and total LCC size on remote chips. For example, for a 32MB RN-F total
cache size and a 16MB total LCC cache size, the recommended SF size is
96MB.

Functional description
2.1.1.4 Super Home Node
The Super Home Node (HN-S) is responsible for managing part of the local address space and
managing local coherency for part of the remote address space.
The HN-S has dual functionality acting as an HN-F for local coherent memory and LCN for remote
coherent memory and hence is typically used in multi-chip conﬁgurations. HN-S allows caching
of remote addresses which allows local sharing without going oﬀ-chip. Local memory bound
transactions targeting HN-F are referred as Home Bound Transactions (HBT) and remote memory
bound transactions targeting LCN for local coherency resolution are referred as LCN Bound
transactions (LBT).
In this book any descriptions related to the HN-F also apply to the HN-S.
The HN-S consists of the following:
System Level Cache
The System Level Cache (SLC) is shared between HBT and LBT lines.
Part of the SLC used for LBT lines is referred as Local Coherent Cache (LCC).
The SLC is a last-level cache for HBT lines. The SLC allocation policy is exclusive for data lines,
except where sharing patterns are detected and pseudo-inclusive for code lines, as indicated by
the RN Fs. All code lines can be allocated into the SLC on the initial request. When MTE is enabled,
SLC stores data and tags.
For more information about how to partition SLC between HBT and LBT lines, see HN-S SLC and
LCC capacity partitioning.
Combined PoS/PoC
The combined Point-of-Serialization (PoS) and Point-of-Coherency (PoC) is responsible
for the ordering of all memory and snoop requests sent to the HN-S. Ordering includes
serialization of multiple outstanding requests/snoops and actions to the same line fragment.
Snoop Filter
The Snoop Filter (SF) tracks cachelines that are present in the RN-Fs. It reduces snoop
traﬃc in the system by favoring directed snoops over snoop broadcasts when possible. This
approach substantially reduces the snoop response traﬃc that might otherwise be required.
SF is shared between HBT and LBT lines.

4.2 SAM support for coherency domains
The HTG contains Cache-id[9:0] programming along with the address range. An HTG match is
based on the incoming snoop address match and incoming snoop cache-id match.
The Cache-id programming is only required in the CCG RA RNSAM to route incoming snoops to
the Local Coherency Nodes (LCN) in a coherency domain, where one HTG is programmed for each
coherency domain. For a given chip, multiple coherency domains can have same address ranges
and unique cache-ids. This value will come from the ExpandedRAID mapped to the coherency
domain’s LDID in por_ccg_ra_hns_ldid_to_exp_raid_reg and the BaseID programmed in the
por_ccla_cfg_ctl.ccg_baseid ﬁeld, that is {0bExpandedRAID,0bBaseID}.

4.3 LCN SAM
The LCN SAM is instantiated in HN-S to determine the CCG node-ids for the LBT bound
transactions and is derived from the RNSAM with only HTG structures and conﬁg space that is
deﬁned in HN-S.
The LCN SAM HTG programming is similar to the RNSAM HTG structures.
The LCN SAM programming does not require programming HN-S target-ids, as LBT bound
transactions only direct towards CCG nodes. The LCN SAM requires CPA_EN bit vector and CPA
group-ID programming for each HN-S entry.

HN-S to CCG CBusy based throttling
HN-S can track the read and write busyness from all CCGs over a conﬁgurable transaction window.
It can be programmed to track the last 128 or 256 transactions. When HN-S has received as many
responses from CCG, it measures the current busyness for each group of CCG and request types
(read and write). The measured busyness is then used to throttle the traﬃc to CCG appropriately.
The threshold for measuring the CBusy for the last 128 or 256 transactions is also conﬁgurable.
For example, consider a scenario where HN-S is programmed to calculate the last 128 CBusy
responses. HN-S tracks the number of times it receives CBusy values of 00, 01, 10, and 11 from all
CCGs.
In this example, the HN-S receives more than 16 CBusy = 11 responses from CCGs out of the last
128 responses. In this case, HN-S treats the ﬁnal CCG CBusy value as 11 for the subsequent 128
transactions while continuing to accumulate new CBusy response values.
HN-S can be conﬁgured to throttle outgoing requests in either a static mode or a default dynamic
mode using cmn_hns_cbusy_ccg_ctl register:
•
Static throttling mode: HN-S controls the outstanding transactions at any point for all CCGs
group and request to values as programmed in cmn_hns_cbusy_ccg_ctl register:
◦
CBusy = 11 (Very busy): HN-S will throttle back outstanding transactions to value
programmed in cbusy_ccg_static_ot_count_cbusy11 ﬁeld.
◦
CBusy = 10 (Medium busy): HN-S will throttle back outstanding transactions to value
programmed in cbusy_ccg_static_ot_count_cbusy10 ﬁeld.
◦
CBusy = 01 (Low busy): HN-S will throttle back outstanding transactions to value
programmed in cbusy_ccg_static_ot_count_cbusy01 ﬁeld.
◦
CBusy = 00 (Not busy): HN-S can issue as many requests as the number of POCQ entries
•
Dynamic throttling mode: The number of Outstanding Transactions (OTs) can be dynamically
throttled according to programmed values. It can be conﬁgured to increment or decrement the
transaction count by one, two, four, or eight transactions after every 128 or 256 transaction
window (as programmed).
◦
CBusy = 11 (Very busy): Decrement the OT count
◦
CBusy = 10 (Medium busy): No change to the current OT count
◦
CBusy = 01 (Low busy): Increment the OT count
◦
CBusy = 00 (Not busy): Increment the OT count

4.6 Conﬁguring non-clustered RN-F tracking in HN-S SF
For HN-S device, NUM_REMOTE_RNF deﬁnes the number of remote chips in a hierarchical system,
rather than the number of individual remote RN-Fs as in a ﬂat system.
To enable non-clustered mode in HNS, set SF_MAX_RNF_PER_CLUSTER parameter to 1, and set
NUM_REMOTE_RNF to number of remote chips. The LDID of each Local RN-F and each remote chip is
assigned to a single index entry in the SF RN-F vector index.
In a CML conﬁguration with HN-S, all remote chips must have LDIDs assigned to them after the
local RN-F LDIDs have been assigned.
For example, consider a 4-chip system with 64 RN-Fs, divided into 16 local RN-Fs on each chip. In
this system, LDIDs 0-15 are preassigned to the local RN-Fs. NUM_REMOTE_RNF is set to 3, and LDIDs
16-18 must then be assigned to 3 remote chips.

4.7 HN-S error handling
CMN S3(AE) error handling in the HN-F also applies to error handling for the HN-S.
The following are additional rules that only apply to the HN-S:
NDEs on Snoop request
When the HN-S is processing an incoming Snoop request from CCG RA, HN-S can have
double-bit ECC error on LCC Tag RAM or NDEs in snoop responses from RN-F. Both are
logged and reported as UE, and HN-S doesn’t propagate NDE to CCG RA.
NDEs on responses
The HN-S can receive NDEs from other data and response sources such as RN-F, RN-I, and
SN-F. For LBT:
•
If HN-S sends early responses back to the requester, NDE from remote HN-S is logged
and reported as a UE.
•
If HN-S sends late reponses back to the requester, it propagates the errors to the
requestor as an NDE.
For more information about error handling in the HN-S, see HN-F error handling

4.9 HN-S restrictions
The following describes the restrictions that are present when using an HN-S device.
The HN-S does not support the following features:
•
Clustered mode for SF tracking
•
UDP and SD cache line states in RN-Fs
The following features are supported in HN-S devices with HBT bound traﬃc only, which targets
local memory regions:
•
MTE. Any mesh with CCG nodes must have CHI_MTE_ENABLE = 0.
•
StrongNC
•
Address-based ﬂushing
•
SLC replacement hint
In multi-chip conﬁgurations with HN-S devices, remote traﬃc is expected to go
through HN-S for local coherency resolution. see SAM support for HN-S.
HN-S device needs a minimum of two caching agents to track in its snoop ﬁlter. For
a mesh conﬁgured with IOHUB_EN = 0, this requires either two RN-F interfaces on
the mesh, or one RN-F interface and NUM_REMOTE_RNF >= 1. For a mesh conﬁgured
with IOHUB_EN = 1, which does not require the presence of RN-F nodes, this
requires NUM_REMOTE_RNF >= 2.
