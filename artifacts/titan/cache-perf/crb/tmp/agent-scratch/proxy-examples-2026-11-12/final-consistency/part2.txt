342 Why the SLC row uses 40 threads, not 120

343 The SLC test needs two things at once. Each thread's buffer must be larger than its 2 MiB L2, or the data never leaves the core. All buffers together must fit in the SLC, or the misses go to DRAM and the number becomes a DRAM number. With 3 MiB per thread, 40 threads is 120 MiB, within the 128 MiB nominal size. 120 threads would be 360 MiB and would overflow. The mesh counters confirm the 40-thread run fit: 2.9 % misses [results/uncore2-20261030T203752Z/cmn-asmread-3M-40T-even.csv]. A second rule halves the usable thread count: one thread per pair. At 8 MiB two partner cores together read only 1.15 to 1.17 times as much as one core alone: 77.5 to 78.5 GB/s against 66.9 to 67.5 GB/s (section "Is the pair port how the SLC is reached?"). So 40 is the largest count tested that fits, and the SLC-served part was still rising at 40, which is why 0.62 TB/s is a lower bound.

344 The placement was uneven: the first 40 even-numbered CPUs are 32 pairs on chiplet 0 and 8 on chiplet 1. The 8 threads on chiplet 1 got 58 to 62 GB/s each, the 32 on chiplet 0 got 25 to 30 GB/s each [perthread-asmread-3M-40.csv]. Hypothesis: a per-chiplet shared limit, so 20 threads per chiplet would give a higher chip-wide number. The test is the same run with CPUs 0, 2, ... 38 and 64, 66, ... 102; not run.

403 Method and caveats

405 All code is our own C, compiled on CRB with gcc 14.2 at -O3 -march=native. Threads are pinned. Buffers are 2 MiB-aligned and first-touched by the thread that uses them. Transparent huge pages were in effect (AnonHugePages equals the buffer size in every run).

406 Latency is the minimum over reps, which is what "best case" means here. Each rep is at least 0.3 s or 2 full cycles (repeated chain) or exactly one pass (fresh chain).

407 Bandwidth is the best of 3 reps of at least 0.5 s; aggregate = total bytes / slowest thread's time.

408 The SLC latency and bandwidth rows carry a few percent of L2 hits because the footprint rule (above 2 MiB per thread, below 128 MiB total) leaves little room. The corrected latency is labelled est.

420 Hypothesis 1, capacity. The pair port has one data channel in each direction, and a channel passes at most one data flit per mesh cycle. That is 32 B × 2.0 GHz = 64 GB/s of data that crosses the port in each direction. The limit of one flit per clock cycle follows from the signals of Arm's CHI link protocol. CHI is the Coherent Hub Interface, the protocol of the mesh ports and links. One channel has one flit bus and one valid signal [AMBA CHI specification, IHI 0050 issue H, Figure B13.14 and Table B13.5, pages 469 to 470]. The flit bus is the set of wires for one flit. The valid signal marks a cycle that carries a flit. None of the Arm documents that were read states the limit in one sentence.

421 Hypothesis 2, saturation. Four kinds of run fill this capacity, and the full port is what limits them. 451 flit, data flit, data channel "Flit" is short for "flow control unit". It is a known term of link protocols. Arm's CHI specification defines it: "FLow control unIT (Flit) is the smallest flow control unit" [AMBA CHI specification, IHI 0050 issue H, page 32]. CHI (Coherent Hub Interface) is the protocol of the mesh ports and links. In this report a flit is one transfer unit on a mesh link or port. A data flit carries data and holds 32 B [CMN S3 TRM, Table A-2 page 2120]. A 64 B line needs two data flits. A data channel is the part of a link or port that carries data flits. credit stall, data stall A sender on a mesh link needs one credit from the receiver for each flit [AMBA CHI specification, IHI 0050 issue H, page 518]. A credit-stall cycle is one count of the link event "TX flit stall". Arm describes it as "signaled when flit transmission is stalled and waiting on credits" [CMN S3 TRM, page 1679]. A data stall is one count of the home-node event for a home node that has a data flit to send and no credit for it [CMN S3 TRM, page 391, event PMU_HN_TXDAT_STALL_EVENT]. The table of part 5 calls it a "data-send stall". back-pressure This report's word for the waits of a sender that has no credit. Credit-stall cycles and data stalls count such waits. write in flight A write that the core has sent and that is not yet complete. streaming write A write whose line is not allocated in L1 or L2. Part 5 counted 0.000 refills for writes per line with the asm write loop. The counts are in section "Where one writer's 73 GB/s limit sits (part 5, 2026-11-02)".

452 bus access, bus read, bus write One data transfer between a core and the mesh, as the core's own counters count it (Arm events BUS_ACCESS and BUS_ACCESS_WR). A bus write goes from the core to the mesh, and a bus read goes to the core. Arm's event list for this core says that each beat of data is counted individually [Linux source in Arm's kit, tools/perf/pmu-events/arch/arm64/arm/neoverse-v3/bus.json]. The file is in the folder neoverse-v3 of that source. The table mapfile.csv of the same source assigns part 0xd83, the part number of CRB's cores, to that folder. A beat is one transfer on the bus. This report takes one transfer as 32 B. That belongs to the first assumption of the conversion in "Open items". One count of part 5 fits it: one writer sent 2.00 bus writes per 64 B line at 1 GiB. bus reads in part 5 Part 5 counted all bus accesses and the bus writes. It did not count the bus reads. This report takes them as all bus accesses minus bus writes (est.). Arm's list also says that the count of all bus accesses includes snoop requests and snoop responses. A snoop is a request from the mesh to a core about a line that the core may hold. So the difference can hold more than bus reads. The port counts of case r8M-c2 (the 2 s run minus the 0.2 s run) hold 4,182 snoop flits and 3.3 × 10 9 data flits from the crosspoint to the port in 1.8 s. So snoops were a small part of the traffic at that port.

453 L1, L2 The first and second cache level inside each core: 64 KiB data L1 and 2 MiB L2, both private to one core (confirmed by measurement, see the pair section).

454 SLC (L3) The system level cache. That is Arm's name for the 128 MiB cache that all 128 cores share. Linux reports it as "L3". Versions of this report before 2026-11-12 called it the "mesh cache". It sits in the on-chip mesh interconnect (Arm CMN). Mesh counters confirm that L2 misses are served there. CRB has two meshes (arm_cmn_0 and arm_cmn_1). The mesh map shows 64 home nodes in each, so each mesh holds 64 slices, 64 MiB, at 1 MiB per slice (est. from 128 MiB / 128 nodes). A core's lines are all cached on its own mesh, as home lines or as proxy lines in the same 64 slices, so one core sees 64 MiB. Home lines and proxy lines share each slice under occupancy limits that were not read. See "The SLC (L3) and the pair port" and "Latency from each core to each slice".

455 proxy (LCN, LCC) A home node on a core's own mesh that caches lines whose home is on the other mesh. Arm calls the role LCN (local coherency node) and the proxy lines' share of the slice LCC (local coherent cache). Home lines and proxy lines share the slice's storage [CMN S3 TRM, page 55]. Measured on CRB: lines homed on the other mesh and already in the SLC are served on the core's own mesh at the same 19 to 44 ns as a local line.

456 DRAM Main memory: 10 Micron 32 GB DDR5-8000 registered DIMMs (part MTC20F2085S1RC80BH1, 2 ranks, 80-bit width), one per channel, running at 8000 MT/s. Ten channels at 8000 MT/s give 640 GB/s theoretical peak. Source: dmidecode type 17, run by Jibin on 2026-10-30.

457 GB/s, TB/s Bandwidth in 10 9 or 10 12 bytes per second. Cache and buffer sizes use KiB, MiB, GiB (powers of 1024). "At 8 MiB" or "at 1 GiB" gives the size of the buffer of each thread. Each thread reads or writes its own buffer again and again. A copy thread has two buffers of that size. It reads one and writes the other [bench/bandwidth.c, lines 4 to 6 and 301 to 306; column bytes_per_thread of the bandwidth result files, for example results/followup-20261030T194205Z/asm.csv]. The bandwidth tests with one, two or four threads use 8 MiB per thread for the SLC and 1 GiB per thread for DRAM [bench/run_crb.sh, lines 83 to 89; caption of the first figure in "Bandwidth per core"]. The whole-chip tests use 3 MiB per thread for the SLC and 256 MiB per thread for DRAM (caption of the first figure in "Bandwidth of the whole chip").

458 pointer chase The latency test: each load reads the address of the next load, so loads cannot overlap. Lines are 64 B and visited in one random cycle.

459 repeated chain The usual chase: the same random cycle is walked many times. CRB's cores learn it (see Latency).

460 fresh chain Each line holds 8 chains. The data is warmed with chain 0, then one single pass is timed on a chain the core has never walked.

461 compiled loop, asm loop Two versions of each bandwidth kernel in bench/bandwidth.c . "Compiled" is the version written in C and compiled by gcc 14.2 at -O3. For read it is a vector loop of 8 loads and 8 adds per 128 B. For write and copy it is a loop that moves one 16 B vector per pass (machine code read on CRB on 2026-11-11). "asm" is a hand-written loop of only 16 B loads or stores, which shows the true pipe limit.

462 pair port, partner cores The crosspoint port that cores 2k and 2k+1 share. The two cores of one pair are called partner cores, or partners. The sharing is inferred from two timing tests (the latency fit and the pair test) and from the port count of the mesh map. It was not read from hardware or from documentation. What limits the rate of a pair was not measured (see "Open items").

463 one thread per pair Threads placed on even-numbered cores only, so no two threads share a pair port.

464 way, set A cache is divided into sets. Each line can be stored only in one set, chosen from its address. A set holds a fixed number of lines side by side, and that number is the number of ways ("4-way" = 4 slots per set). See "Cache ways" above.

465 chiplet One of the two halves of the CRB processor.
