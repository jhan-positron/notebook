52 Short version. A CRB core sees four levels: a 64 KiB L1 at 1.43 ns, a 2 MiB private L2 at 3.75 ns, a 128 MiB SLC (system level cache: the shared cache that Linux lists as L3, located in the on-chip mesh interconnect) at about 30 ns, and DRAM at 148 ns. One core reads at most 133 GB/s from L1, 85 GB/s from L2, 67 GB/s from the SLC and 30 GB/s from DRAM, and the whole chip reads 15.9 TB/s from L1, at least 0.62 TB/s from the SLC and 533 GB/s from DRAM. Two findings matter for software: with a buffer of 8 MiB each, the two cores of a pair (cores 2k and 2k+1, three pairs tested) together read only about 78 GB/s, against 125 to 134 GB/s for two cores of different pairs, and the core's prefetcher learns a repeated access pattern, so simple cache benchmarks under-report the SLC latency by five times.

122 What "3 loads / 2 stores of 16 B per cycle" means

123 The core has four pipelines that start loads and stores. Three of them can each start one load per cycle (named Load/Store 0, Load 1 and Load 2). Two of them can each start one store per cycle (Load/Store 0 and Store 1). Load/Store 0 is in both groups. Each pipeline accepts one operation per cycle. So in one cycle Load/Store 0 does either a load or a store [SOG, section 2.1 page 11, Figure 2-1 and Table 2-1, pages 12 to 13].

124 It follows that the core can start at most 3 loads + 1 store, or 2 loads + 2 stores, in one cycle. So the label "3 loads / 2 stores" gives two separate limits. It does not mean five operations in one cycle. The core never starts 4 loads + 1 store in one cycle. Only three pipelines accept loads. The guide gives these roles as part of the core's design. It describes no setting that changes them.

125 The asm copy loop (the hand-written loop that loads 16 B registers from one buffer and stores them to another) is a measured case of the second mix. It measured 178.4 GB/s in L1, which counts the bytes read plus the bytes written (table "Per-core bandwidth" in Record). A mix of 2 loads + 2 stores of 16 B per cycle is 179.2 GB/s at 2.8 GHz.

126 The widest register a plain load or store can fill is a 128-bit vector register (a "q register"), which holds 16 B. Arm's throughput table gives 3 such loads per cycle (LDR q: 3 per cycle; LDP q, which loads two 16 B registers in one instruction: 1.5 per cycle) and 2 such stores per cycle (STR q: 2 per cycle; STP q: 1 per cycle) [SOG, Table 3-13 page 23 and Table 3-14 pages 24 to 25]. So the L1 can deliver 48 B per cycle to loads and take 32 B per cycle from stores.

127 The guide draws two more memory pipelines, Store data 0 and Store data 1 [SOG, Figure 2-1 page 12]. They carry the data of a store from a general-purpose register and do not start a store. The data of a 16 B store from a q register goes through one of the two vector pipelines, FP/ASIMD 0 and FP/ASIMD 1 [SOG, Table 2-1 page 13 and Table 3-14 pages 24 to 25].

135 Cache ways: what "4-way" and "8-way" mean

136 A cache does not search all of its slots for an address. It is divided into sets, and a line (64 B) can live only in the one set that its address bits select. Inside that set there are a fixed number of slots side by side, and that number is the number of ways. "4-way" means each set has 4 slots, so a line has 4 possible places in the whole cache, no more.

138 L1 data cache of one CRB core: the address selects one of 256 sets, and the line may sit in any of the 4 ways of that set. The 6 offset bits pick the byte inside the 64 B line. The tag (the remaining address bits) is stored with the line and compared on lookup.

139 The geometry of CRB's three caches comes from the cores' own cache identification registers, as read through sysfs on CRB [ /sys/devices/system/cpu/cpu0/cache/index0, index2, index3 , read 2026-11-01]. The SLC's 16 ways match one of the two values Arm offers for it, 12 or 16 [CMN S3 TRM, Table 1-9 pages 31 to 32].

142 L1 data 64 KiB 256 4 64 B 256 × 4 × 64 = 64 KiB bits 13 to 6 (8 bits)

146 Why the number of ways matters. More ways make it less likely that two useful lines fight for the same slot, and fewer ways make lookups cheaper. The 4-way L1 has 256 sets of 64 B, so two addresses exactly 16 KiB apart land in the same set. A program that cycles through 5 lines spaced 16 KiB apart misses in L1 on every access, although it uses only 320 B. The benchmarks in this report avoid this: the random cycle spreads lines evenly over all sets, which is why the 64 KiB footprint shows 0 L1 refills (table in Latency).

162 Set index (bits 13 to 6) is a plain lookup. For A the hardware goes straight to set 37, with no search.

166 How a slot is chosen when a line is loaded. Every load does two separate checks. First, "is this line already here?" compares the tag of the address with the tag stored in each of the 4 slots. Second, if it is not here, "where do I put it?" looks for a free slot, and evicts a line only when none is free. Starting from an empty set 37:

168 Load A. No slot has tag 0x1fc48d158 , so it is a miss. All 4 slots are free. A goes into slot 0, and its tag is stored next to the 64 bytes.

169 Load C. Slot 0 holds tag 0x1fc48d158 (A), which is not C's tag 0x1fc48d159 . Slots 1 to 3 are empty, so they cannot match either. Miss. Slot 0 is taken, so C goes into the next free slot, slot 1.

170 Load D, then E. Same two checks. They go into slots 2 and 3. Set 37 is now full.

171 Load F. No slot has tag 0x1fc48d15c . Miss. No slot is free, so the cache evicts one of the four lines and puts F in its place. 172 Load A again. If A was the evicted line, this is a miss. The report calls this a conflict miss: the program touched only 5 lines, 320 B, in a 64 KiB cache, and still missed.

176 How a slot is found on a read. Read B, 0x7f1234560950 . Bits 13 to 6 give 37, so the hardware goes to set 37. It compares 0x1fc48d158 with the four stored tags in parallel, and slot 0 matches. Bits 5 to 0 give 16, so byte 16 of slot 0's line is returned. "4-way" therefore means four tag comparators per lookup, and four lines with the same set index can be in the cache at once. In a 1-way (direct-mapped) cache, A and C would already push each other out.

177 On Arm cores the stored tag is built from the physical address after translation, not from the virtual address shown above. The lookup works the same way. The V3AE core manual that would confirm this detail for CRB was not obtainable (see "Arm documents cited").

178 The SLC (L3) and the pair port

179 Three questions from the review: is the SLC an L3 cache, why did older versions of this report call it the "mesh cache", and is the pair port the way the SLC is reached. Each answer is tied to an Arm document or to a measurement. The CAL2 and the two hypotheses on the pair port are marked as an inference or as hypotheses.

180 Is it an L3 cache?

181 Linux lists it as cache level 3, unified, 128 MiB, 16-way, shared by CPUs 0 to 127 [ /sys/devices/system/cpu/cpu0/cache/index3 ]. The core itself has two levels: Arm lists "Separate L1 data and instruction caches" and a "Private, unified data and instruction L2 cache" and no L3 for this core [SOG, section 1.1 page 9]. So it is the third level a core sees, and in that sense it is the L3. It is not inside the core or a core cluster. It sits in the interconnect, and Arm's name for it is the System Level Cache (SLC): "The System Level Cache (SLC) is a last-level cache" inside each home node [CMN S3 TRM, section 2.1.1.3 page 54].

182 The mesh, and why older versions said "mesh cache"

183 CRB's interconnect is Arm's CMN S3, the Coherent Mesh Network. The Linux mesh counter driver reports part number 0x43e, which the driver source names CMN S3 [ /sys/bus/event_source/devices/arm_cmn_0/identifier = 43e05; Linux drivers/perf/arm-cmn.c, PART_CMN_S3 = 0x43e], and its event names start with "hns", the Super Home Node of CMN S3. Arm describes the structure as "a configurable rectangular grid that is composed of network routers that are known as Crosspoints (XPs)", where "each XP connects horizontally and vertically to other XPs, creating a two-dimensional mesh structure", and "each XP can have up to four device ports for connecting CHI-compliant devices" [CMN S3 TRM, section 1.4 page 17]. "Each byte of address space is assigned to a single Home Node (HN)", and "each HN-S can contain an SF and an SLC" [CMN S3 TRM, Home Nodes, page 19]. The SLC is therefore a set of slices, one per home node, spread over the mesh, and every address has exactly one home. An L2 miss travels across the mesh to the home node of its address, or to a local proxy of it. Versions of this report before 2026-11-12 called the SLC the "mesh cache" for that reason. The report now uses Arm's name. A home node also acts as a proxy (Arm: the LCN role of the super home node, whose proxy lines share the slice with its home lines as the LCC) for addresses homed on the other mesh [CMN S3 TRM, Super Home Node, page 55], so a line can be cached by its home slice or by a proxy slice on the other mesh. Whether a line sits in both at once was not measured. The root run measured service from both kinds (section "Latency from each core to each slice").

211 Is the pair port how the SLC is reached?

212 Yes. A core reaches everything beyond its L2 through one connection: its requester interface (an RN-F in Arm's terms) into a crosspoint device port. Every L2 miss, every write-back and every snoop answer from the core uses that connection, so the SLC, the other cores' caches and DRAM are all behind it.

213 Arm provides a block that puts two devices on one such port: "A Component Aggregation Layer (CAL) allows multiple devices to connect to a single device port on an XP", and the two-device version "CAL2" supports fully coherent requesters (RN-F) [CMN S3 TRM, section 2.1.1.15 page 63]. The measurement in "The pair finding" ran two cores at the same time. Each core read its own buffer of 8 MiB, which does not fit in its L2. The rates of the two cores were added. One core alone gets 67 GB/s. When the two busy cores are partners (cores 2k and 2k+1, for example 0 and 1), the total is 78 GB/s, so they share one limit. When the two busy cores come from different pairs, the total is 125 to 134 GB/s. That is 1.9 to 2.0 times the rate of one core alone. For example, CPUs 0 and 2 together read 126.6 GB/s with the read loop compiled from C and 129.7 GB/s with the asm loop. Only cores on different meshes (CPUs 0 and 64, CPUs 0 and 119) reached 134 GB/s. Every core has a partner, so the limit does not depend on which cores exist. It depends on which cores are busy at the same time. With one more busy core on another pair, a core with an idle partner read 62.4 to 67.1 GB/s (seven runs, best repetition of each). A core with a busy partner read 37.8 to 40.3 GB/s (five runs, best repetition of each). What is confirmed by the document is that the mechanism exists. What is measured is that the two cores of a pair slow each other on the three pairs that were tested (CPUs 0 to 5). That CRB attaches its core pairs through a CAL2 is the simplest reading of the two, and it is not confirmed by any CRB document: the firmware tables give each core its own cluster [ /sys/devices/system/cpu/cpu*/topology/cluster_cpus_list ]. The mesh map adds a counting argument: 64 cores per mesh sit on 35 core ports, so at least 29 ports carry two cores, and the map shows the home nodes on the same crosspoints already sharing ports in twos [crb/results/cmn-map.txt].

218 On 2026-11-02 Jibin ran the root tool bench/homelat on CRB (final set 05:49 to 06:04 UTC, results in results/sudo-20261102T054936Z/ ). It works in three steps. First it finds the home nodes: a mesh counter opened with a node id answers only for a node that exists, and 64 answered on each mesh. Second it finds the home node of every 64 B line of a 32 MiB buffer: flush the line, read the 8 home-node counters of a quadrant with one call, load the line 256 times with a flush between loads, read again, and take the one node that rose by 256. Third, for every core and every home node, it builds a random chain through 2048 lines of that node, loads them once in a random order, pushes them out of L1 and L2 with 8 MiB of random loads, and times one walk of the chain that has never been walked, seven times with a fresh chain each time.
