52: Short version. A CRB core sees four levels: a 64 KiB L1 at 1.43 ns, a 2 MiB private L2 at 3.75 ns, a 128 MiB SLC (system level cache: the shared cache that Linux lists as L3, located in the on-chip mesh interconnect) at about 30 ns, and DRAM at 148 ns. One core reads at most 133 GB/s from L1, 85 GB/s from L2, 67 GB/s from the SLC and 30 GB/s from DRAM, and the whole chip reads 15.9 TB/s from L1, at least 0.62 TB/s from the SLC and 533 GB/s from DRAM. Two findings matter for software: with a buffer of 8 MiB each, the two cores of a pair (cores 2k and 2k+1) together read only about 78 GB/s, against 125 to 134 GB/s for two cores of different pairs, and the core's prefetcher learns a repeated access pattern, so simple cache benchmarks under-report the SLC latency by five times.

122: What "3 loads / 2 stores of 16 B per cycle" means
123: The core has four pipelines that start loads and stores. Three of them can each start one load per cycle (named Load/Store 0, Load 1 and Load 2). Two of them can each start one store per cycle (Load/Store 0 and Store 1). Load/Store 0 is in both groups. Each pipeline accepts one operation per cycle. So in one cycle Load/Store 0 does either a load or a store [SOG, section 2.1 page 11, Figure 2-1 and Table 2-1, pages 12 to 13].
124: It follows that the core can start at most 3 loads + 1 store, or 2 loads + 2 stores, in one cycle. So the label "3 loads / 2 stores" gives two separate limits. It does not mean five operations in one cycle. The core never starts 4 loads + 1 store in one cycle. Only three pipelines accept loads. The guide gives these roles as part of the core's design. It describes no setting that changes them.
125: The asm copy loop (the hand-written loop that loads 16 B registers from one buffer and stores them to another) is a measured case of the second mix. It measured 178.4 GB/s in L1, which counts the bytes read plus the bytes written (table "Per-core bandwidth" in Record). A mix of 2 loads + 2 stores of 16 B per cycle is 179.2 GB/s at 2.8 GHz.
126: The widest register a plain load or store can fill is a 128-bit vector register (a "q register"), which holds 16 B. Arm's throughput table gives 3 such loads per cycle (LDR q: 3 per cycle; LDP q, which loads two 16 B registers in one instruction: 1.5 per cycle) and 2 such stores per cycle (STR q: 2 per cycle; STP q: 1 per cycle) [SOG, Table 3-13 page 23 and Table 3-14 pages 24 to 25]. So the L1 can deliver 48 B per cycle to loads and take 32 B per cycle from stores.
127: The guide draws two more memory pipelines, Store data 0 and Store data 1 [SOG, Figure 2-1 page 12]. They carry the data of a store from a general-purpose register and do not start a store. The data of a 16 B store from a q register goes through one of the two vector pipelines, FP/ASIMD 0 and FP/ASIMD 1 [SOG, Table 2-1 page 13 and Table 3-14 pages 24 to 25].
129: Left: the asm read loop issues LDP q instructions, so all three load pipelines carry 16 B every cycle. Right: the asm write loop issues STP q, so the two store pipelines each start a 16 B store every cycle and Load 1 and Load 2 have nothing to do. Clock 2.8 GHz.
130: The measured L1 numbers are the pipeline limit. 48 B per cycle at 2.8 GHz is 134.4 GB/s, and the asm read loop measured 132.7 GB/s (99 %). 32 B per cycle is 89.6 GB/s, and the asm write loop measured 89.5 GB/s. The asm loops use exactly LDP q and STP q [bench/bandwidth.c:179 to 186 and 204 to 211].
131: The read loop compiled from C: 1.5 loads per cycle The read loop compiled from C reaches 66.8 GB/s, which is 1.5 loads of 16 B per cycle. The asm read loop measured 132.7 GB/s, which is 99 % of 3 loads per cycle. The limit of two vector adds per cycle can explain at most part of this gap. The cause of the rest is not established. This section gives the source code, the machine code, the limits that were checked, and the test that is missing. Source code. The read loop compiled from C is the function k_read in bench/bandwidth.c [lines 138 to 148]. It adds every 8 B word of the buffer into one of 16 running sums, and gcc 14.2 chooses the instructions. __attribute__((noinline)) static uint64_t k_read(const uint64_t *a, size_t n) { uint64_t s[16] = { 0 }; for (size_t i = 0; i < n; i += 16) for (int j = 0; j < 16; j++) s[j] += a[i + j]; uint64_t sum = 0; for (int j = 0; j < 16; j++) sum += s[j]; return sum; } The asm loop is written by hand and only loads. It is the function k_asmread in the same file [lines 173 to 195]. One pass of its loop runs 8 LDP q instructions (16 loads of 16 B, which is 256 B), one add, one compare and one branch. __attribute__((noinline)) static void k_asmread(const uint64_t *a, size_t n) { const uint64_t *p = a; const uint64_t *end = a + n; __asm__ volatile( "1:\n\t" "ldp q0, q1, [%[p]]\n\t" "ldp q2, q3, [%[p], #32]\n\t" "ldp q4, q5, [%[p], #64]\n\t" "ldp q6, q7, [%[p], #96]\n\t" "ldp q8, q9, [%[p], #128]\n\t" "ldp q10, q11, [%[p], #160]\n\t" "ldp q12, q13, [%[p], #192]\n\t" "ldp q14, q15, [%[p], #224]\n\t" "add %[p], %[p], #256\n\t" "cmp %[p], %[end]\n\t" "b.lo 1b\n\t" : [p] "+r"(p) : [end] "r"(end) : "v0", "v1", "v2", "v3", "v4", "v5", "v6", "v7", "v8", "v9", "v10", "v11", "v12", "v13", "v14", "v15", "memory", "cc"); } Machine code. The machine code of k_read on CRB was read with objdump -d on 2026-11-11, with no test run [results/probe-20261111T210017Z.txt]. For each 128 B the loop runs these 16 instructions: 1b68: ldp q6, q5, [x0] 1b6c: add x1, x1, #0x1 1b70: ldp q4, q3, [x0, #32] 1b74: ldp q2, q1, [x0, #64] 1b78: ldp q0, q23, [x0, #96] 1b7c: add x0, x0, #0x80 1b80: add v24.2d, v24.2d, v6.2d 1b84: add v25.2d, v25.2d, v5.2d 1b88: add v26.2d, v26.2d, v4.2d 1b8c: add v27.2d, v27.2d, v3.2d 1b90: add v28.2d, v28.2d, v2.2d 1b94: add v29.2d, v29.2d, v1.2d 1b98: add v30.2d, v30.2d, v0.2d 1b9c: add v31.2d, v31.2d, v23.2d 1ba0: cmp x1, x2 1ba4: b.cc 1b68 <k_read+0x68> // b.lo, b.ul, b.last 4 LDP q (8 loads of 16 B) 8 vector adds 2 integer adds one compare and one branch So the compiled loop does issue one vector add per 16 B load. 135: Cache ways: what "4-way" and "8-way" mean
136: A cache does not search all of its slots for an address. It is divided into sets, and a line (64 B) can live only in the one set that its address bits select. Inside that set there are a fixed number of slots side by side, and that number is the number of ways. "4-way" means each set has 4 slots, so a line has 4 possible places in the whole cache, no more.
138: L1 data cache of one CRB core: the address selects one of 256 sets, and the line may sit in any of the 4 ways of that set. The 6 offset bits pick the byte inside the 64 B line. The tag (the remaining address bits) is stored with the line and compared on lookup.
139: The geometry of CRB's three caches comes from the cores' own cache identification registers, as read through sysfs on CRB [ /sys/devices/system/cpu/cpu0/cache/index0, index2, index3 , read 2026-11-01]. The SLC's 16 ways match one of the two values Arm offers for it, 12 or 16 [CMN S3 TRM, Table 1-9 pages 31 to 32].
141: Cache Size Sets Ways Line Check: sets × ways × line Address bits that pick the set
142: L1 data 64 KiB 256 4 64 B 256 × 4 × 64 = 64 KiB bits 13 to 6 (8 bits)
143: L2 2 MiB 4,096 8 64 B 4,096 × 8 × 64 = 2 MiB bits 17 to 6 (12 bits)
144: SLC (L3) 128 MiB 131,072 16 64 B 131,072 × 16 × 64 = 128 MiB a hash of the address picks the home node and the set
146: Why the number of ways matters. More ways make it less likely that two useful lines fight for the same slot, and fewer ways make lookups cheaper. The 4-way L1 has 256 sets of 64 B, so two addresses exactly 16 KiB apart land in the same set. A program that cycles through 5 lines spaced 16 KiB apart misses in L1 on every access, although it uses only 320 B. The benchmarks in this report avoid this: the random cycle spreads lines evenly over all sets, which is why the 64 KiB footprint shows 0 L1 refills (table in Latency).
148: A worked example with real addresses
149: The address does not choose the slot inside a set. The cache control logic does. The seven addresses below show how. Each is split for the L1 data cache: offset = bits 5 to 0, set index = bits 13 to 6, tag = bits 47 to 14. C, D, E and F are each 16 KiB (0x4000) further than A. Adding 16 KiB does not change bits 13 to 0, so the set stays 37 and only the tag changes. G is 64 B further than A, so it is the next line and lands in set 38.
151: Name Address Tag (bits 47 to 14) Set (bits 13 to 6) Offset (bits 5 to 0) Relation to A
152: A 0x7f1234560940 0x1fc48d158 37 0 start of a line
153: B 0x7f1234560950 0x1fc48d158 37 16 same line, 16 B in
154: C 0x7f1234564940 0x1fc48d159 37 0 A + 16 KiB
155: D 0x7f1234568940 0x1fc48d15a 37 0 A + 32 KiB
156: E 0x7f123456c940 0x1fc48d15b 37 0 A + 48 KiB
157: F 0x7f1234570940 0x1fc48d15c 37 0 A + 64 KiB
158: G 0x7f1234560980 0x1fc48d158 38 0 A + 64 B, the next line
160: What each field does.
162: Set index (bits 13 to 6) is a plain lookup. For A the hardware goes straight to set 37, with no search.
163: Offset (bits 5 to 0) picks one byte inside the 64 B line. B is byte 16 of A's line.
164: Tag (bits 47 to 14) is the address shifted right by 14 bits. For A: 0x7f1234560940 >> 14 = 0x1fc48d158 . 14 bits is 3 hex digits plus 2 bits, so drop "940" to get 0x7f1234560 , then divide by 4. 2 34 different lines map to set 37, and the tag stored in a slot says which one of them the slot holds.
166: How a slot is chosen when a line is loaded. Every load does two separate checks. First, "is this line already here?" compares the tag of the address with the tag stored in each of the 4 slots. Second, if it is not here, "where do I put it?" looks for a free slot, and evicts a line only when none is free. Starting from an empty set 37:
168: Load A. No slot has tag 0x1fc48d158 , so it is a miss. All 4 slots are free. A goes into slot 0, and its tag is stored next to the 64 bytes.
169: Load C. Slot 0 holds tag 0x1fc48d158 (A), which is not C's tag 0x1fc48d159 . Slots 1 to 3 are empty, so they cannot match either. Miss. Slot 0 is taken, so C goes into the next free slot, slot 1.
170: Load D, then E. Same two checks. They go into slots 2 and 3. Set 37 is now full.
171: Load F. No slot has tag 0x1fc48d15c . Miss. No slot is free, so the cache evicts one of the four lines and puts F in its place. Which line goes depends on the core's replacement rule, usually the one used longest ago. The V3AE core manual that states the rule was not available, so the figure assumes slot 0 (est.).
172: Load A again. If A was the evicted line, this is a miss. The report calls this a conflict miss: the program touched only 5 lines, 320 B, in a 64 KiB cache, and still missed.
175: Set 37 of the L1 data cache during the example. Left: after A, C, D and E are loaded, all four slots hold a line and the tags tell them apart. Middle: F arrives, no slot is free, one line is evicted (slot 0 shown, est.). Right: a read of B compares its tag with all four stored tags at the same time, slot 0 matches, and the offset 16 picks the byte inside that line.
176: How a slot is found on a read. Read B, 0x7f1234560950 . Bits 13 to 6 give 37, so the hardware goes to set 37. It compares 0x1fc48d158 with the four stored tags in parallel, and slot 0 matches. Bits 5 to 0 give 16, so byte 16 of slot 0's line is returned. "4-way" therefore means four tag comparators per lookup, and four lines with the same set index can be in the cache at once. In a 1-way (direct-mapped) cache, A and C would already push each other out.
177: On Arm cores the stored tag is built from the physical address after translation, not from the virtual address shown above. The lookup works the same way. The V3AE core manual that would confirm this detail for CRB was not obtainable (see "Arm documents cited").
178: The SLC (L3) and the pair port
179: Three questions from the review: is the SLC an L3 cache, why did older versions of this report call it the "mesh cache", and is the pair port the way the SLC is reached. Each answer is tied to an Arm document or to a measurement. Each claim that neither confirms is marked as an inference or as a hypothesis.
180: Is it an L3 cache?
181: Linux lists it as cache level 3, unified, 128 MiB, 16-way, shared by CPUs 0 to 127 [ /sys/devices/system/cpu/cpu0/cache/index3 ]. The core itself has two levels: Arm lists "Separate L1 data and instruction caches" and a "Private, unified data and instruction L2 cache" and no L3 for this core [SOG, section 1.1 page 9]. So it is the third level a core sees, and in that sense it is the L3. It is not inside the core or a core cluster. It sits in the interconnect, and Arm's name for it is the System Level Cache (SLC): "The System Level Cache (SLC) is a last-level cache" inside each home node [CMN S3 TRM, section 2.1.1.3 page 54].
182: The mesh, and why older versions said "mesh cache"
183: CRB's interconnect is Arm's CMN S3, the Coherent Mesh Network. The Linux mesh counter driver reports part number 0x43e, which the driver source names CMN S3 [ /sys/bus/event_source/devices/arm_cmn_0/identifier = 43e05; Linux drivers/perf/arm-cmn.c, PART_CMN_S3 = 0x43e], and its event names start with "hns", the Super Home Node of CMN S3. Arm describes the structure as "a configurable rectangular grid that is composed of network routers that are known as Crosspoints (XPs)", where "each XP connects horizontally and vertically to other XPs, creating a two-dimensional mesh structure", and "each XP can have up to four device ports for connecting CHI-compliant devices" [CMN S3 TRM, section 1.4 page 17]. "Each byte of address space is assigned to a single Home Node (HN)", and "each HN-S can contain an SF and an SLC" [CMN S3 TRM, Home Nodes, page 19]. The SLC is therefore a set of slices, one per home node, spread over the mesh, and every address has exactly one home. An L2 miss travels across the mesh to the home node of its address, or to a local proxy of it. Versions of this report before 2026-11-12 called the SLC the "mesh cache" for that reason. The report now uses Arm's name. A home node also acts as a proxy (Arm: the LCN role of the super home node, whose proxy lines share the slice with its home lines as the LCC) for addresses homed on the other mesh [CMN S3 TRM, Super Home Node, page 55], so a line can be cached by its home slice or by a proxy slice on the other mesh. Whether a line sits in both at once was not measured. The root run measured service from both kinds (section "Latency from each core to each slice").

211: Is the pair port how the SLC is reached?
212: Yes. A core reaches everything beyond its L2 through one connection: its requester interface (an RN-F in Arm's terms) into a crosspoint device port. Every L2 miss, every write-back and every snoop answer from the core uses that connection, so the SLC, the other cores' caches and DRAM are all behind it.
213: Arm provides a block that puts two devices on one such port: "A Component Aggregation Layer (CAL) allows multiple devices to connect to a single device port on an XP", and the two-device version "CAL2" supports fully coherent requesters (RN-F) [CMN S3 TRM, section 2.1.1.15 page 63]. The measurement in "The pair finding" ran two cores at the same time. Each core read its own buffer of 8 MiB, which does not fit in its L2. The rates of the two cores were added. One core alone gets 67 GB/s. When the two busy cores are partners (cores 2k and 2k+1, for example 0 and 1), the total is 78 GB/s, so they share one limit. When the two busy cores come from different pairs, the total is 125 to 134 GB/s. That is 1.9 to 2.0 times the rate of one core alone. For example, CPUs 0 and 2 together read 126.6 GB/s with the read loop compiled from C and 129.7 GB/s with the asm loop. Only cores on different meshes (CPUs 0 and 64, CPUs 0 and 119) reached 134 GB/s. Every core has a partner, so the limit does not depend on which cores exist. It depends on which cores are busy at the same time. A core with an idle partner reads the full 67 GB/s of one core alone. What is confirmed by the document is that the mechanism exists. What is measured is that CRB's cores are limited in pairs. That CRB attaches its core pairs through a CAL2 is the simplest reading of the two, and it is not confirmed by any CRB document: the firmware tables give each core its own cluster [ /sys/devices/system/cpu/cpu*/topology/cluster_cpus_list ]. The mesh map adds a counting argument: 64 cores per mesh sit on 35 core ports, so at least 29 ports carry two cores, and the map shows the home nodes on the same crosspoints already sharing ports in twos [crb/results/cmn-map.txt].

217: Latency from each core to each slice (root run)
218: On 2026-11-02 Jibin ran the root tool bench/homelat on CRB (final set 05:49 to 06:04 UTC, results in results/sudo-20261102T054936Z/ ). It works in three steps. First it finds the home nodes: a mesh counter opened with a node id answers only for a node that exists, and 64 answered on each mesh. Second it finds the home node of every 64 B line of a 32 MiB buffer: flush the line, read the 8 home-node counters of a quadrant with one call, load the line 256 times with a flush between loads, read again, and take the one node that rose by 256. Third, for every core and every home node, it builds a random chain through 2048 lines of that node, loads them once in a random order, pushes them out of L1 and L2 with 8 MiB of random loads, and times one walk of the chain that has never been walked, seven times with a fresh chain each time.

231: Lines homed on the other mesh are served by a local proxy
232: Short version. The physical address of a line (64 B) picks its home node, which is one mesh and one crosspoint. A core does not cross to the other mesh for a line that it has read before. A proxy node on the core's own mesh holds that line and serves it. What picks the home node. The mesh uses the physical address (PA) of the line. Arm lists "The Physical Address (PA) of the request" as the input of the lookup [CMN S3 TRM, section 2.4.5 page 134]. The virtual address (VA, the address that a program sees) is not used. The kernel chooses the physical page behind each virtual page. A program without root cannot read the PA [Linux Documentation/admin-guide/mm/pagemap.rst]. The mesh. Take PA bits 6, 8, 10, ... 36 (every even bit) and XOR them (XOR, exclusive or, gives 1 when an odd number of the bits are 1). The result 0 means mesh 0, and the result 1 means mesh 1. This rule gives the measured mesh for all 524,288 lines of the 32 MiB buffer [ full/homes.csv , full/chunks.csv , checked by tmp/agent-scratch/proxy-examples-2026-11-12/hash/hash2.py ]. The node. Six more XOR sums of PA bits pick one of the 64 home nodes of that mesh from a table. So 7 XOR sums together pick one of the 128 home nodes. This fits all 524,288 lines [ tmp/agent-scratch/proxy-examples-2026-11-12/hash/hash.py ]. The position of the node on the grid follows no simple rule of the 7 sums. Limit of the rule. The buffer had 16 physical pages of 2 MiB. PA bits 37 and higher had the same value in all 16 pages, so the data cannot show whether they enter. Three other choices of the bits 21 to 36 fit the 16 pages as well as "every even bit" does. The same rule on the VA fails. It gives the wrong mesh for 262,144 of the 524,288 lines [ tmp/agent-scratch/proxy-examples-2026-11-12/worker/va_rule.py ]. That is one half, which is what a random guess gives. Three example lines. All three are lines of the buffer of the root run [ full/homes.csv , full/chunks.csv , full/nodes.csv ]. Each home node is also a proxy for lines that are homed on the other mesh. Arm calls this role LCN (Local Coherency Node). Arm writes that it "allows caching of remote addresses which allows local sharing without going off-chip" [CMN S3 TRM, section 2.1.1.4 page 55]. The request of a core for such a line goes first to a proxy on the core's own mesh [CMN S3 TRM, Figure 4-1 page 325]. The PA picks that proxy through a second table, which holds node ids of the core's own mesh [CMN S3 TRM, section 4.1.1 page 329]. The manual does not give the table of CRB. Measured on CRB. Take the lines of one home node of mesh 1. Their latency from the 64 cores of mesh 0 rises with the distance, in crosspoint hops, from one crosspoint of mesh 0. 233: So all of a core's cached lines live on its own mesh, as home lines and as proxy lines in the same 64 slices. That is why one buffer sees 64 MiB of SLC: one mesh's 64 slices of 1 MiB. Home lines and proxy lines share the storage of each slice. Firmware can cap the share of each kind with an occupancy limit. The limit resets to the maximum [CMN S3 TRM, capacity partitioning, pages 335 to 336, and the register fields on page 1039]. The limits of CRB were not read. Half of the lines of a buffer are home lines and half are proxy lines. So the buffer fills each slice half and half, whatever the limits allow. The 64 MiB is measured. The only inference about the limits is that neither was below about one half for this workload (est.).

342: Why the SLC row uses 40 threads, not 120
343: The SLC test needs two things at once. Each thread's buffer must be larger than its 2 MiB L2, or the data never leaves the core. All buffers together must fit in the SLC, or the misses go to DRAM and the number becomes a DRAM number. With 3 MiB per thread, 40 threads is 120 MiB, within the 128 MiB nominal size. 120 threads would be 360 MiB and would overflow. The mesh counters confirm the 40-thread run fit: 2.9 % misses [results/uncore2-20261030T203752Z/cmn-asmread-3M-40T-even.csv]. A second rule halves the usable thread count: one thread per pair. At 8 MiB two partner cores together read only 1.15 to 1.17 times as much as one core alone: 77.5 to 78.5 GB/s against 66.9 to 67.5 GB/s (section "Is the pair port how the SLC is reached?"). So 40 is the largest count tested that fits, and the SLC-served part was still rising at 40, which is why 0.62 TB/s is a lower bound.
344: The placement was uneven: the first 40 even-numbered CPUs are 32 pairs on chiplet 0 and 8 on chiplet 1. The 8 threads on chiplet 1 got 58 to 62 GB/s each, the 32 on chiplet 0 got 25 to 30 GB/s each [perthread-asmread-3M-40.csv]. Hypothesis: a per-chiplet shared limit, so 20 threads per chiplet would give a higher chip-wide number. The test is the same run with CPUs 0, 2, ... 38 and 64, 66, ... 102; not run.

403: Method and caveats
405: All code is our own C, compiled on CRB with gcc 14.2 at -O3 -march=native. Threads are pinned. Buffers are 2 MiB-aligned and first-touched by the thread that uses them. Transparent huge pages were in effect (AnonHugePages equals the buffer size in every run).
406: Latency is the minimum over reps, which is what "best case" means here. Each rep is at least 0.3 s or 2 full cycles (repeated chain) or exactly one pass (fresh chain).
407: Bandwidth is the best of 3 reps of at least 0.5 s; aggregate = total bytes / slowest thread's time.
408: The SLC latency and bandwidth rows carry a few percent of L2 hits because the footprint rule (above 2 MiB per thread, below 128 MiB total) leaves little room. The corrected latency is labelled est.
409: The "learned pattern" explanation of the repeated-chain curve is a hypothesis that fits the counters (L2 refills 1.0 per load at 5.4 ns). Confirming it needs the core's prefetch controls, which require kernel privilege.
410: The 8 reserved cores (120-127) were never used - this is a simple operation agreement between Jeremy and me, there is no technical reason - and the whole-chip tests used 120 of 128 cores.
411: Mesh counters (arm_cmn PMUs) were read in two short passes with perf_event_paranoid at 0, set and reset by Jibin. No governor, package or boot setting was changed. Only files under /home/jhan/cache-perf were written.

418: Measured or documented. The mesh clock is 2.0 GHz. The mesh cycle counter measured it in part 5 of run_sudo.sh [results/sudo-20261102T211150Z/writepath.csv]. A data flit holds 32 B [CMN S3 TRM, Table A-2 page 2120].
419: Not read. The number of data channels at the pair port was not read from CRB. Field dat_vc_num_p of register por_mxp_p0-5_info_1 holds it [CMN S3 TRM, page 1656]. Arm's manual draws one data channel in each direction at a device port, also when the links between crosspoints have two [CMN S3 TRM, Figure 2-25 page 89]. For the links there is a hint. The Linux mesh driver on CRB lists events for a second response channel (rsp2) and none for a second data channel (dat2) [results/probe-20261111T210017Z.txt]. The driver hides the dat2 events when the mesh reports fewer than two data channels [Linux drivers/perf/arm-cmn.c, function arm_cmn_event_attr_is_visible]. That source is Arm's kernel source for firmware 0.9.0. CRB runs the kernel build for firmware 0.7.2, and its source is not in Arm's kit.
420: Hypothesis 1, capacity. The pair port has one data channel in each direction, and a channel passes at most one data flit per mesh cycle. That is 32 B × 2.0 GHz = 64 GB/s of data that crosses the port in each direction. The limit of one flit per clock cycle follows from the signals of Arm's CHI link protocol. CHI is the Coherent Hub Interface, the protocol of the mesh ports and links. One channel has one flit bus and one valid signal [AMBA CHI specification, IHI 0050 issue H, Figure B13.14 and Table B13.5, pages 469 to 470]. The flit bus is the set of wires for one flit. The valid signal marks a cycle that carries a flit. None of the Arm documents that were read states the limit in one sentence.
421: Hypothesis 2, saturation. Four kinds of run fill this capacity, and the full port is what limits them. They are the runs of two partner cores that read 8 MiB each, of two partner cores that write 8 MiB each with the asm loop, of one core that writes 1 GiB with the asm loop, and of two partner cores that write 1 GiB each. A size such as 8 MiB or 1 GiB is the size of the buffer of each core. Each core reads or writes its own buffer again and again. This report calls these four kinds of run the runs of hypothesis 2. Hypothesis 2 is a separate statement. Hypothesis 1 can hold while a run leaves the port partly idle.
422: Conversion, two assumptions. The measured rates count the bytes that the loops read or wrote. Both hypotheses are about the bytes that cross the port. The conversion between the bytes of the loops and the bytes that cross the port makes two assumptions. The first assumption: one bus read or bus write of a core is one data flit of 32 B at the port (see "bus access" in "Words used here"). The second assumption: a count per line that was measured on one core alone also holds for two partner cores. Most counts are from part 5 (2026-11-02). Most of the pair rates are from runs of 2026-10-30. Each item below names its sources. For one core alone the counts of part 5 fit the first assumption. 433: Capacity. Read the number of data channels at the port (field dat_vc_num_p above). The manual does not say which value of this field stands for which number of channels [CMN S3 TRM, page 1656]. A value of 0 would show that the field counts in another way. Then this rule does not apply. A run can reject hypothesis 1 only by a rate above 64 GB/s through one pair port in one direction. Count the bus reads of both cores (Arm event BUS_ACCESS_RD) and the mesh cycles (perf event dtc_cycles) in the same run. If both cores together make more bus reads than the mesh has cycles, the port carried more than one flit per mesh cycle. This step uses the first assumption of the conversion. So such a result rejects hypothesis 1 or the first assumption, and the run alone does not show which. The flit counter of the port cannot show which of the two is wrong. It covers one data channel, and its event is one signal. So it cannot count more than one flit per mesh cycle. A read of the register field can show it. The expected count is close to one bus read per mesh cycle. With the share of 0.83, the existing rates give 2.00 to 2.03 × 10 9 bus reads per second for two partner readers (est.). With the scaled share of 0.81 they give 1.97 to 1.99 × 10 9 bus reads per second (est.). The mesh has 2.00 × 10 9 cycles per second. No margin is set here. Repeated runs must give the variation of the count first.
434: Saturation. Let two partner cores read 8 MiB each. Count the data flits that the crosspoint sends to the port (perf event mxp_p1_dat_txflit_valid) and the mesh cycles. A rate near 1.0 flit per mesh cycle supports hypothesis 2. A rate clearly below 1.0 means that this data channel had idle cycles. Then a full channel toward the cores did not limit the pair. A reader also sends data the other way, 1.653 bus writes per line for one reader. So count the bus writes of both cores in the same run. If both directions had idle cycles, the result rejects hypothesis 2 for reads. For the bus writes this step uses the first assumption of the conversion. The result leaves hypothesis 1 open. No threshold is set here. Only one value of this counter exists for a reader. It is 0.92 flits per mesh cycle for one reader alone (case r8M-c2, the count of the 2 s run minus the count of the 0.2 s run). So its variation from run to run is not known. Repeated counts must give that variation before a threshold is set. This counter covers reads only. It counts the flits that the crosspoint sends to the port, and write data goes the other way. For writes, count the bus writes of both partner cores and the mesh cycles. A total near 1.0 bus write per mesh cycle supports hypothesis 2 for writes, through the first assumption of the conversion. Part 5 holds two first values, each of one core only: 0.98 bus writes per mesh cycle for one writer alone at 1 GiB, and 0.50 for CPU 2 at 8 MiB while its partner also wrote (est.). The runs that counted these bus writes did not count the mesh cycles. Each value is the bus writes per second divided by the mesh clock of 2.0 GHz.
435: Conversion. Let the read test above count the bus reads of both cores and the data flits at the port in one run. As many bus reads as flits supports the first assumption. For the second assumption, compare the flits per line of the pair with the 1.653 of one core. Suppose that the bus reads stay at or below the mesh cycles. If the flits per line of the pair differ from the 1.653 of one core, the second assumption fails for reads. Then the converted rates in the item "Reads at 8 MiB" are wrong. That result does not test hypothesis 1. If the bus reads differ from the flits, the first assumption is in doubt. Then every converted number that uses a bus count is in doubt too, for example the 84 GB/s in the item "Writes at 8 MiB". More bus reads than flits can also mean a second data channel. The flit counter covers one data channel. It would not count the flits of a second one. So that result rejects the first assumption or hypothesis 1, and the run alone does not show which. A read of the register field can show it. More bus reads than mesh cycles is the case of the capacity item above. For writes, compare the bus writes per line of both partner cores with the 1.52 (8 MiB) and the 2.00 (1 GiB) of one core. Part 5 gives a first value for one of the two cores: the 1.52 of CPU 2 in the item "Writes at 8 MiB".

449: cycle One clock period at 2.8 GHz = 0.357 ns. Cycle counts above are ns multiplied by 2.8.
450: mesh clock, mesh cycle The clock of the mesh interconnect (Arm CMN). It ran at 2.0 GHz on CRB with firmware 0.7.2. One mesh cycle is then 0.5 ns. It is a different clock from the 2.8 GHz core clock. It was measured with the mesh cycle counter (the cycle counter of the mesh's performance monitor, perf event dtc_cycles) in part 5 of run_sudo.sh on 2026-11-02, with the machine idle and with 1 to 4 busy cores [results/sudo-20261102T211150Z/writepath.csv]. 451: flit, data flit, data channel "Flit" is short for "flow control unit". It is a known term of link protocols. Arm's CHI specification defines it: "FLow control unIT (Flit) is the smallest flow control unit" [AMBA CHI specification, IHI 0050 issue H, page 32]. CHI (Coherent Hub Interface) is the protocol of the mesh ports and links. In this report a flit is one transfer unit on a mesh link or port. A data flit carries data and holds 32 B [CMN S3 TRM, Table A-2 page 2120]. A 64 B line needs two data flits. A data channel is the part of a link or port that carries data flits. credit stall, data stall, back-pressure A sender on a mesh link needs one credit from the receiver for each flit [AMBA CHI specification, IHI 0050 issue H, page 518]. A credit-stall cycle is one count of the link event "TX flit stall". Arm describes it as "signaled when flit transmission is stalled and waiting on credits" [CMN S3 TRM, page 1679]. A data stall is one count of a home-node event. Arm describes it as "Counts number of times HN-F has a pending TXDAT flit but no credits to upload" [CMN S3 TRM, page 391]. Back-pressure is this report's word for such waits. write in flight A write that the core has sent and that is not yet complete.
452: bus access, bus read, bus write One data transfer between a core and the mesh, as the core's own counters count it (Arm events BUS_ACCESS and BUS_ACCESS_WR). A bus write goes from the core to the mesh, and a bus read goes to the core. Arm's event list for this core says that each beat of data is counted individually [Linux source in Arm's kit, tools/perf/pmu-events/arch/arm64/arm/neoverse-v3/bus.json]. The file is in the folder neoverse-v3 of that source. The table mapfile.csv of the same source assigns part 0xd83, the part number of CRB's cores, to that folder. A beat is one transfer on the bus. This report takes one transfer as 32 B. That belongs to the first assumption of the conversion in "Open items". One count of part 5 fits it: one writer sent 2.00 bus writes per 64 B line at 1 GiB. bus reads in part 5 Part 5 counted all bus accesses and the bus writes. It did not count the bus reads. This report takes them as all bus accesses minus bus writes (est.). Arm's list also says that the count of all bus accesses includes snoop requests and snoop responses. A snoop is a request from the mesh to a core about a line that the core may hold. So the difference can hold more than bus reads. The port counts of case r8M-c2 (the 2 s run minus the 0.2 s run) hold 4,182 snoop flits and 3.3 × 10 9 data flits from the crosspoint to the port in 1.8 s. So snoops were a small part of the traffic at that port.
453: L1, L2 The first and second cache level inside each core: 64 KiB data L1 and 2 MiB L2, both private to one core (confirmed by measurement, see the pair section).
454: SLC (L3) The system level cache. That is Arm's name for the 128 MiB cache that all 128 cores share. Linux reports it as "L3". Versions of this report before 2026-11-12 called it the "mesh cache". It sits in the on-chip mesh interconnect (Arm CMN). Mesh counters confirm that L2 misses are served there. CRB has two meshes (arm_cmn_0 and arm_cmn_1). The mesh map shows 64 home nodes in each, so each mesh holds 64 slices, 64 MiB, at 1 MiB per slice (est. from 128 MiB / 128 nodes). A core's lines are all cached on its own mesh, as home lines or as proxy lines in the same 64 slices, so one core sees 64 MiB. Home lines and proxy lines share each slice under occupancy limits that were not read. See "The SLC (L3) and the pair port" and "Latency from each core to each slice".
455: proxy (LCN, LCC) A home node on a core's own mesh that caches lines whose home is on the other mesh. Arm calls the role LCN (local coherency node) and the proxy lines' share of the slice LCC (local coherent cache). Home lines and proxy lines share the slice's storage [CMN S3 TRM, page 55]. Measured on CRB: lines homed on the other mesh and already in the SLC are served on the core's own mesh at the same 19 to 44 ns as a local line.
456: DRAM Main memory: 10 Micron 32 GB DDR5-8000 registered DIMMs (part MTC20F2085S1RC80BH1, 2 ranks, 80-bit width), one per channel, running at 8000 MT/s. Ten channels at 8000 MT/s give 640 GB/s theoretical peak. Source: dmidecode type 17, run by Jibin on 2026-10-30.
457: GB/s, TB/s Bandwidth in 10 9 or 10 12 bytes per second. Cache and buffer sizes use KiB, MiB, GiB (powers of 1024). "At 8 MiB" or "at 1 GiB" gives the size of the buffer of each thread. Each thread reads or writes its own buffer again and again. A copy thread has two buffers of that size. It reads one and writes the other [bench/bandwidth.c, lines 4 to 6 and 301 to 306; column bytes_per_thread of the bandwidth result files, for example results/followup-20261030T194205Z/asm.csv]. The bandwidth tests with one, two or four threads use 8 MiB per thread for the SLC and 1 GiB per thread for DRAM [bench/run_crb.sh, lines 83 to 89; caption of the first figure in "Bandwidth per core"]. The whole-chip tests use 3 MiB per thread for the SLC and 256 MiB per thread for DRAM (caption of the first figure in "Bandwidth of the whole chip").
458: pointer chase The latency test: each load reads the address of the next load, so loads cannot overlap. Lines are 64 B and visited in one random cycle.
459: repeated chain The usual chase: the same random cycle is walked many times. CRB's cores learn it (see Latency).
460: fresh chain Each line holds 8 chains. The data is warmed with chain 0, then one single pass is timed on a chain the core has never walked.
461: compiled loop, asm loop Two versions of each bandwidth kernel in bench/bandwidth.c . "Compiled" is the version written in C and compiled by gcc 14.2 at -O3. For read it is a vector loop of 8 loads and 8 adds per 128 B. For write and copy it is a loop that moves one 16 B vector per pass (machine code read on CRB on 2026-11-11). "asm" is a hand-written loop of only 16 B loads or stores, which shows the true pipe limit.
462: pair port, partner cores The crosspoint port that cores 2k and 2k+1 share. The two cores of one pair are called partner cores, or partners. The sharing follows from two timing tests (the latency fit and the pair test) and from the port count of the mesh map. It was not read from hardware or from documentation. What limits the rate of a pair was not measured (see "Open items").
463: one thread per pair Threads placed on even-numbered cores only, so no two threads share a pair port.
464: way, set A cache is divided into sets. Each line can be stored only in one set, chosen from its address. A set holds a fixed number of lines side by side, and that number is the number of ways ("4-way" = 4 slots per set). See "Cache ways" above.
465: chiplet One of the two halves of the CRB processor. Each half has its own mesh (Linux shows two CMN devices, arm_cmn_0 and arm_cmn_1), 64 cores (CPUs 0 to 63 on chiplet 0 and 64 to 127 on chiplet 1, measured in the root run), 64 SLC slices, and 5 DDR5 channels (the DIMM inventory names the slots DIMM_CP0_0 to 4 and DIMM_CP1_0 to 4). The halves are joined by chip-to-chip gateways (CCG, 8 per mesh in the map). Whether they are two separate dies is not readable from Linux; "chiplet" here means one mesh with its cores and memory.
466: CMN, XP, home node, CAL Arm's Coherent Mesh Network, the on-chip interconnect on CRB (model CMN S3). XP = crosspoint, one router of the mesh grid. Home node (HN-S) = the mesh node that owns an address range and holds a slice of the SLC. CAL = Component Aggregation Layer, Arm's block that lets two devices share one crosspoint port. See "The SLC (L3) and the pair port" above.
