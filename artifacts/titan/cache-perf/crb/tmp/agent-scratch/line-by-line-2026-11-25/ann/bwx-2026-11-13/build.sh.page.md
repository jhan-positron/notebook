## Short version: purpose

`build.sh` builds four binaries of the first runner `bwx` on CRB, runs the self-test of each, and writes the machine code of every kernel of every binary to `listing.txt`. It records the build in `build.txt`: host, load, compiler, flags, extra options, self-test results and sha256 values. The build script of the next runner version, `build8.sh`, builds one binary without extra options and adds a check of the timed function of the trial mode, which `bwx` does not have.

## Words used here

- **CRB**: the Arm reference server under test. It has 128 CPUs.
- **Runner**: a benchmark program that times a sequence of kernels in one process and prints one row per thread. The versions are named `bwx`, `bwx8`, `bwx10`, `bwx11`, `bwx12` and `bwx13`.
- **Runner source**: the C file of the runner, here `bwx.c`. This script compiles it four times.
- **Kernel**: the inner loop of a benchmark that reads, writes or copies memory. On this page "kernel" means this loop. The operating system kernel is always written "Linux kernel".
- **Read kernel**: the kernel that reads memory.
- **Old read kernel**: portable C code with 16 running sums. Each load is followed by an add. Its name is `read` in the binary `bw_old` and `oldread` in the runners.
- **New read kernel**: NEON intrinsics (C functions that map to Arm vector instructions), loads only. Its name is `read` in the binary `bw_new` and in the runners.
- **`asmread`**: a hand-written load-only loop. It has the same 8 `ldp q` loads per 256 B as the new read kernel. `ldp q` is the Arm instruction that loads two 16-byte vector registers.
- **`bandwidth.c`, `bw_old`, `bw_new`**: the benchmark and its two binaries of 2026-11-13. `bw_old` was built from the old source (`bandwidth.orig.c`), `bw_new` from the new source (`bandwidth.c`).
- **`copy`, `asmcopy`, `asmcopy2`**: three copy kernels of the runner. `copy` is C code with NEON intrinsics, `asmcopy` is hand-written assembly, and `asmcopy2` is a second copy of `asmcopy` under another name.
- **Step B3, B3 binaries**: step B3 of the test plan of 2026-11-13 runs the copy kernels in builds whose copy loops start at 0, 36 and 52 modulo 64. The binaries `bwx_o0`, `bwx_o36` and `bwx_o52` are these builds.
- **`handoff.md`, B.7**: `handoff.md` is the note that specifies the runner `bwx`. Its section B.7 is "Loop addresses" [Ref13].
- **Self-test**: a program that checks what the kernels do to memory, without timing.
- **Self-test file**: the C file `bwx_selftest.c`. The runner source includes it, and the option `--selftest` of the runner runs it.
- **Machine-code listing**: the instructions that the compiler produced for a function, as text (output of the tool `objdump`).
- **Marker file**: the file `/tmp/positron-perf.RUNNING` on CRB. It exists while another user runs a performance test. Our scripts stop when it exists.
- **Load average**: the number of tasks that are runnable or wait for disk input and output, averaged by Linux over the last 1, 5 and 15 minutes (file `/proc/loadavg`). The fourth field of the file gives the tasks that are runnable now and the number of all tasks.
- **GB, MiB**: GB = 1e9 bytes. MiB = 1048576 bytes (2 to the power of 20).
- **sha256**: a checksum. Two files with the same sha256 have the same content.
- **Rate**: bytes divided by time, in GB/s.
- **Pinned**: a thread that is pinned to a CPU may run on that CPU only.
- **Exit status**: the number that a process returns when it ends. 0 means success.
- **UTC**: Coordinated Universal Time.
- **Development machine**: the machine on which the check scripts run. It is not CRB. The header comment of the script uses this name.
- **Build records, CRB build 1, CRB build 2**: the build records are the folders `bwx-crb-build-1` and `bwx-crb-build-2` of the test data. Each holds files that one run of this script wrote on 2026-11-13, and its printed output [Ref1] [Ref2] [Ref6]. This page calls the two runs CRB build 1 and CRB build 2. By a note of the project the first build was not used [Ref10].
- **Loop start**: the address of the first instruction of the loop of a kernel. This script takes the target of the first backward branch of the function.
- **`objdump`, `taskset`**: two Linux tools. `objdump` prints the machine code of a binary as text. `taskset` starts a program that may run on a given list of CPUs only.
- **`PLACE`, pad, `PAD`, `HEAD`**: `PLACE` is a macro of the runner source. It puts padding bytes (a pad) directly before a function. Then the function starts at a planned address modulo 64. `PAD_<name>` is the number of padding bytes of one kernel. `HEAD_<name>` is the number of bytes from the function start to the loop start.
- **Page**: the unit in which Linux gives memory to a process. Its size is 4096 B in the self-test outputs of CRB build 1 [Ref5].

## Main flow

1. Stop when the marker file exists. Then start the script again under `taskset`, limited to the CPUs 0 to 119 ({L19-23}).
2. Set the folder of the script, the compiler, the ten compiler flags, the extra options and the names of the four binaries ({L24-28}).
3. Write the first lines of `build.txt`, with the extra options of every binary ({L29-37}).
4. Compile `bwx.c` four times. The three B3 binaries get `-DB3_OFFSET=0`, `36` or `52`. Exit status 5 when a compiler call fails ({L38-44}).
5. For each binary: check the marker file and run the binary with `--selftest`. Exit status 4 when a self-test fails ({L46-53}).
6. For each binary and each kernel name that the binary prints with `--list`: append the machine code of the kernel function to `listing.txt`, and append one row with the function start and the loop start to `offsets.tsv` ({L57-74}).
7. Append the sha256 values, the load and the end time to `build.txt`. Print `build.txt` and `offsets.tsv` ({L75-82}).

## Behavior a reader must know

- The script times nothing and computes no rate. It reads the load averages at the start and at the end only for the record ({L31}, {L78}).
- Three checks stop the script, each with its own exit status: the marker file (status 3, checked at {L22} and before each self-test at {L47}), a compiler call (status 5) and a self-test (status 4). With the rule `-e` of {L19} another failed command also ends the script. The row of {L19} names the exceptions.
- The four runs of a binary with `--list` have no marker check of their own ({L60}).
- The script does not check the listing. The script `check_listing.py` does that later, on the development machine ({L16}).
- A run that reaches its end replaces the four binaries, `build.txt`, the four self-test outputs, `listing.txt` and `offsets.tsv` in the folder of the script. A run that stops earlier replaces only the files that it wrote before the stop. Files of an older run can then stay in the folder beside the new ones. Example: after a stop at the first marker check of {L47} the folder holds the new `build.txt` and the four new binaries, beside the self-test outputs and the listing of an older run.
- The CPU limit of {L23} holds for every program that the script starts. The script pins no program to one CPU. Two environment variables change the limit. A `BWX_CPUS` that is set and not empty replaces the list `0-119`. A `_PINNED` that is already set and not empty at the start makes the script set no limit at all.
- The `shellcheck` comment of {L40} does not stand directly before the command that it is written for, the compiler call of {L42}. The assignment of {L41} stands between them, and by the ShellCheck documentation the comment holds for that assignment only [Ref12]. This has no effect on the run of the script.
- The loop start in `offsets.tsv` is the target of the first backward branch. In both CRB builds each kernel function holds exactly one backward branch [Ref4] [Ref11].
- The two CRB builds differ in one input: CRB build 2 ran with `EXTRA_bwx_o52=-falign-loops=1` [Ref1] [Ref2]. In CRB build 1 the loop of `copy` in `bwx_o52` starts at 0 modulo 64 and not at the planned 52. In CRB build 2 it starts at 52 [Ref3] [Ref11].
- Results of both CRB builds: gcc 14.2.0, no compiler message, and four self-tests with exit status 0 and `# failures=0` [Ref1] [Ref2]. `offsets.tsv` has 84 kernel rows, 21 for each binary, and no row holds `NA` [Ref3] [Ref11].
- No compiled binary is in a local folder. `build.txt` gives the sha256 of each binary. The value of `bwx` begins with `5b702073` in both builds [Ref1] [Ref2].
