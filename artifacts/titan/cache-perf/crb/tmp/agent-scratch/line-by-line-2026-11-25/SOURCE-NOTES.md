## Points that touch a measurement or an analysis result

- Whole-chip test, parts L, C and I (`w120-2026-11-15/rx.sh` line 24, which is line 19 of the older text that ran on 2026-11-17): while the binary measures, the shell of `rx.sh` starts one `sleep` process per second. The `taskset` of line 22 limits only the binary. The shell and its `sleep` processes use the CPU list of the caller. The log of the run of 2026-11-17 records this list as the CPUs 0 to 119 (`/home/jhan/workspace/ai-proj/arm-crb/tests/2026-11-17-whole-chip-7200/go-T72-20261117T221209Z.log`, the line `affinity of this shell`). So each of these processes ran on a CPU that also ran one pinned benchmark thread. Part A is not affected: `ra.sh` runs its binary in the foreground and starts nothing while it runs (line 48). Insufficient data on the size of the effect: the count of involuntary context switches of each benchmark thread, or the bytes of each CPU in the thread rows of one interval, would show it. Found by the main session on 2026-11-26.

- Load record of the run scripts (`run_bwx10.sh` lines 109, 110, 266, and the same `ps` command in `run_bwx11.sh`, `run_bwx9.sh`, `rx.sh`, `ra.sh`, `run_partA.sh`): the comment says "the 5 busiest processes". `ps --sort=-pcpu` sorts by `pcpu`, which is the CPU time of a process divided by the time from its start to now. A reviewer tested it: a process that was idle for 3 s and then busy for 2 s showed 40.0. Data: the 9 files `launches.txt` of the result folders `bwx10-*` hold 789 records with 3945 process lines. 3874 lines show 0.0, 51 lines are the `ps` process itself with 100, and the other 20 lines are `bash` and `systemd` of our own login. So this list did not show which processes were busy at a launch. Insufficient data on that point: a sample over a short interval (for example `top -b -n 2 -d 1`) would give it. The fields of `/proc/loadavg` and the login count in the same record are not affected.
