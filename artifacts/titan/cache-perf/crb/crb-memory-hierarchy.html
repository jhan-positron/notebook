CRB Memory Hierarchy

Latency and bandwidth of L1, L2, the mesh cache and DRAM on the Phoenix Reference Server (CRB), measured 2026-10-30 by Jibin Han's Claude. Requested by Bill. Explanation sections (pipelines, cache ways, mesh and pair port) added 2026-11-01 after Jibin's review. Mesh map and follow-up measurements (write placement, per-core sweep) added 2026-11-02. Root run (latency from each core to each slice, proxies, write allocation) added 2026-11-02.

Short version. A CRB core sees four levels: a 64 KiB L1 at 1.43 ns, a 2 MiB private L2 at 3.75 ns, a 128 MiB mesh cache at about 30 ns, and DRAM at 148 ns. One core reads at most 133 GB/s from L1, 85 GB/s from L2, 67 GB/s from the mesh cache and 30 GB/s from DRAM, and the whole chip reads 15.9 TB/s from L1, at least 0.62 TB/s from the mesh cache and 533 GB/s from DRAM. Two findings matter for software: each pair of neighbouring cores shares one path to the mesh of about 80 GB/s, and the core's prefetcher learns a repeated access pattern, so simple cache benchmarks under-report the mesh-cache latency by five times.

Words used here

CRB
The Arm "Phoenix Reference Server" at 192.168.2.45: 128 Arm cores (part 0xd83, which the Linux kernel table names Neoverse V3AE), fixed 2.8 GHz clock, 320 GiB DRAM, Linux 7.1.3.
cycle
One clock period at 2.8 GHz = 0.357 ns. Cycle counts below are ns multiplied by 2.8.
L1, L2
The first and second cache level inside each core: 64 KiB data L1 and 2 MiB L2, both private to one core (confirmed by measurement, see the pair section).
mesh cache (SLC)
The 128 MiB cache that Linux reports as "L3", shared by all 128 cores. It sits in the on-chip mesh interconnect (Arm CMN), and Arm calls it the system level cache (SLC). Mesh counters confirm that L2 misses are served there. CRB has two meshes (arm_cmn_0 and arm_cmn_1). The mesh map shows 64 home nodes in each, so each mesh holds 64 slices, 64 MiB, at 1 MiB per slice (est. from 128 MiB / 128 nodes). A core's lines are all cached on its own mesh, half in home slices and half in proxy slices, so one core sees 64 MiB. See "The mesh cache and the pair port" and "Latency from each core to each slice".
proxy (LCN, LCC)
A home node on a core's own mesh that caches lines whose home is on the other mesh. Arm calls the role LCN (local coherency node) and the part of the slice it uses LCC (local coherent cache) [CMN S3 TRM, page 55 and page 1216]. Measured on CRB: every line homed on the other mesh is served by such a proxy at the same 19 to 44 ns as a local line.
DRAM
Main memory: 10 Micron 32 GB DDR5-8000 registered DIMMs (part MTC20F2085S1RC80BH1, 2 ranks, 80-bit width), one per channel, running at 8000 MT/s. Ten channels at 8000 MT/s give 640 GB/s theoretical peak. Source: dmidecode type 17, run by Jibin on 2026-10-30.
GB/s, TB/s
Bandwidth in 109 or 1012 bytes per second. Cache and buffer sizes use KiB, MiB, GiB (powers of 1024).
pointer chase
The latency test: each load reads the address of the next load, so loads cannot overlap. Lines are 64 B and visited in one random cycle.
repeated chain
The usual chase: the same random cycle is walked many times. CRB's cores learn it (see Latency).
fresh chain
Each line holds 8 chains. The data is warmed with chain 0, then one single pass is timed on a chain the core has never walked.
compiled loop, asm loop
Two bandwidth kernels. "Compiled" is gcc's vector loop (8 loads and 8 adds per 128 B). "asm" is a hand-written loop of only 16 B loads or stores, which shows the true pipe limit.
pair port
Cores 2k and 2k+1 share one path to the mesh. Measured, not read from documentation.
one thread per pair
Threads placed on even-numbered cores only, so no two threads share a pair port.
way, set
A cache is divided into sets. Each line can be stored only in one set, chosen from its address. A set holds a fixed number of lines side by side, and that number is the number of ways ("4-way" = 4 slots per set). See "Cache ways" below.
chiplet
One of the two halves of the CRB processor. Each half has its own mesh (Linux shows two CMN devices, arm_cmn_0 and arm_cmn_1), 64 cores (CPUs 0 to 63 on chiplet 0 and 64 to 127 on chiplet 1, measured in the root run), 64 mesh-cache slices, and 5 DDR5 channels (the DIMM inventory names the slots DIMM_CP0_0 to 4 and DIMM_CP1_0 to 4). The halves are joined by chip-to-chip gateways (CCG, 8 per mesh in the map). Whether they are two separate dies is not readable from Linux; "chiplet" here means one mesh with its cores and memory.
CMN, XP, home node, CAL
Arm's Coherent Mesh Network, the on-chip interconnect on CRB (model CMN S3). XP = crosspoint, one router of the mesh grid. Home node (HN-S) = the mesh node that owns an address range and holds a slice of the mesh cache. CAL = Component Aggregation Layer, Arm's block that lets two devices share one crosspoint port. See "The mesh cache and the pair port" below.
Arm documents cited
SOG = Arm Neoverse V3AE Core Software Optimization Guide, document 110075, issue 3.0, for core revision r0p2 (CRB's cores report r0p2). CMN S3 TRM = Arm Neoverse CMN S3(AE) Technical Reference Manual, document 107858, revision r2p3. Local copies: crb/refs/.

What "3 loads + 2 stores of 16 B per cycle" means

The core has five pipelines that handle memory instructions. Three of them can each start one load per cycle (named Load/Store 0, Load 1 and Load 2). Two of them can each start one store per cycle (Load/Store 0 and Store 1). Load/Store 0 is shared, so in one cycle it does either a load or a store [SOG, Figure 2-1 and Table 2-1, page 12 to 13].

The widest register a plain load or store can fill is a 128-bit vector register (a "q register"), which holds 16 B. Arm's throughput table gives 3 such loads per cycle (LDR q: 3 per cycle; LDP q, which loads two 16 B registers in one instruction: 1.5 per cycle) and 2 such stores per cycle (STR q: 2 per cycle; STP q: 1 per cycle) [SOG, Table 3-13 page 23 and Table 3-14 page 25]. So the L1 can deliver 48 B per cycle to loads and take 32 B per cycle from stores.

The measured L1 numbers are the pipeline limit. 48 B per cycle at 2.8 GHz is 134.4 GB/s, and the asm read loop measured 132.7 GB/s (99 %). 32 B per cycle is 89.6 GB/s, and the asm write loop measured 89.5 GB/s. The asm loops use exactly LDP q and STP q [bench/bandwidth.c:176 to 210]. The compiled read loop reaches 66.8 GB/s, which is 1.5 loads of 16 B per cycle. Hypothesis for the gap: the compiled loop also issues one vector add per load, and the core has only two vector pipelines (FP/ASIMD 0 and 1) [SOG, Table 2-1]. The test that would confirm it is a loop with loads and adds in a 3:2 ratio, not run.

Cache ways: what "4-way" and "8-way" mean

A cache does not search all of its slots for an address. It is divided into sets, and a line (64 B) can live only in the one set that its address bits select. Inside that set there are a fixed number of slots side by side, and that number is the number of ways. "4-way" means each set has 4 slots, so a line has 4 possible places in the whole cache, no more.

The geometry of CRB's three caches comes from the cores' own cache identification registers, as read through sysfs on CRB [/sys/devices/system/cpu/cpu0/cache/index0, index2, index3, read 2026-11-01]. The mesh cache's 16 ways match one of the two values Arm offers for the system level cache, 12 or 16 [CMN S3 TRM, Table 1-9 page 31].

Why the number of ways matters. More ways make it less likely that two useful lines fight for the same slot, and fewer ways make lookups cheaper. The 4-way L1 has 256 sets of 64 B, so two addresses exactly 16 KiB apart land in the same set. A program that cycles through 5 lines spaced 16 KiB apart misses in L1 on every access, although it uses only 320 B. The benchmarks in this report avoid this: the random cycle spreads lines evenly over all sets, which is why the 64 KiB footprint shows 0 L1 refills (table in Latency).

A worked example with real addresses

The address does not choose the slot inside a set. The cache control logic does. The seven addresses below show how. Each is split for the L1 data cache: offset = bits 5 to 0, set index = bits 13 to 6, tag = bits 47 to 14. C, D, E and F are each 16 KiB (0x4000) further than A. Adding 16 KiB does not change bits 13 to 0, so the set stays 37 and only the tag changes. G is 64 B further than A, so it is the next line and lands in set 38.

NameAddressTag (bits 47 to 14)Set (bits 13 to 6)Offset (bits 5 to 0)Relation to A
A0x7f12345609400x1fc48d158370start of a line
B0x7f12345609500x1fc48d1583716same line, 16 B in
C0x7f12345649400x1fc48d159370A + 16 KiB
D0x7f12345689400x1fc48d15a370A + 32 KiB

F0x7f12345709400x1fc48d15c370A + 64 KiB
G0x7f12345609800x1fc48d158380A + 64 B, the next line

What each field does.

  • Set index (bits 13 to 6) is a plain lookup. For A the hardware goes straight to set 37, with no search.
  • Offset (bits 5 to 0) picks one byte inside the 64 B line. B is byte 16 of A's line.
  • Tag (bits 47 to 14) is the address shifted right by 14 bits. For A: 0x7f1234560940 >> 14 = 0x1fc48d158. 14 bits is 3 hex digits plus 2 bits, so drop "940" to get 0x7f1234560, then divide by 4. 234 different lines map to set 37, and the tag stored in a slot says which one of them the slot holds.

How a slot is chosen when a line is loaded. Every load does two separate checks. First, "is this line already here?" compares the tag of the address with the tag stored in each of the 4 slots. Second, if it is not here, "where do I put it?" looks for a free slot, and evicts a line only when none is free. Starting from an empty set 37:

  1. Load A. No slot has tag 0x1fc48d158, so it is a miss. All 4 slots are free. A goes into slot 0, and its tag is stored next to the 64 bytes.
  2. Load C. Slot 0 holds tag 0x1fc48d158 (A), which is not C's tag 0x1fc48d159. Slots 1 to 3 are empty, so they cannot match either. Miss. Slot 0 is taken, so C goes into the next free slot, slot 1.
  3. Load D, then E. Same two checks. They go into slots 2 and 3. Set 37 is now full.
  4. Load F. No slot has tag 0x1fc48d15c. Miss. No slot is free, so the cache evicts one of the four lines and puts F in its place. Which line goes depends on the core's replacement rule, usually the one used longest ago. The V3AE core manual that states the rule was not available, so the figure assumes slot 0 (est.).
  5. Load A again. If A was the evicted line, this is a miss. The report calls this a conflict miss: the program touched only 5 lines, 320 B, in a 64 KiB cache, and still missed.

How a slot is found on a read. Read B, 0x7f1234560950. Bits 13 to 6 give 37, so the hardware goes to set 37. It compares 0x1fc48d158 with the four stored tags in parallel, and slot 0 matches. Bits 5 to 0 give 16, so byte 16 of slot 0's line is returned. "4-way" therefore means four tag comparators per lookup, and four lines with the same set index can be in the cache at once. In a 1-way (direct-mapped) cache, A and C would already push each other out.

On Arm cores the stored tag is built from the physical address after translation, not from the virtual address shown above. The lookup works the same way. The V3AE core manual that would confirm this detail for CRB was not obtainable (see "Arm documents cited").

The mesh cache and the pair port

Three questions from the review: is the mesh cache an L3 cache, why is it called the mesh cache, and is the pair port the way the mesh cache is reached. Each answer is tied to an Arm document or to a measurement, and the one claim that neither confirms is marked.

Is it an L3 cache?

Linux lists it as cache level 3, unified, 128 MiB, 16-way, shared by CPUs 0 to 127 [/sys/devices/system/cpu/cpu0/cache/index3]. The core itself has two levels: Arm lists "Separate L1 data and instruction caches" and a "Private, unified data and instruction L2 cache" and no L3 for this core [SOG, section 1.1 page 9]. So it is the third level a core sees, and in that sense it is the L3. It is not inside the core or a core cluster. It sits in the interconnect, and Arm's name for it is the System Level Cache (SLC): "The System Level Cache (SLC) is a last-level cache" inside each home node [CMN S3 TRM, section 2.1.1.3 page 54].

Why "mesh cache"

CRB's interconnect is Arm's CMN S3, the Coherent Mesh Network. The Linux mesh counter driver reports part number 0x43e, which the driver source names CMN S3 [/sys/bus/event_source/devices/arm_cmn_0/identifier = 43e05; Linux drivers/perf/arm-cmn.c, PART_CMN_S3 = 0x43e], and its event names start with "hns", the Super Home Node of CMN S3. Arm describes the structure as "a configurable rectangular grid that is composed of network routers that are known as Crosspoints (XPs)", where "each XP connects horizontally and vertically to other XPs, creating a two-dimensional mesh structure", and "each XP can have up to four device ports for connecting CHI-compliant devices" [CMN S3 TRM, section 1.4 page 17]. "Each byte of address space is assigned to a single Home Node (HN)", and "each HN-S can contain an SF and an SLC" [CMN S3 TRM, Home Nodes, page 19]. The SLC is therefore a set of slices, one per home node, spread over the mesh, and every address has exactly one home. This report calls it the mesh cache for that reason: an L2 miss travels across the mesh to the home node of its address, or to a local proxy of it. A home node also acts as a proxy (Arm: the LCN role of the super home node, with its own part of the slice, the LCC) for addresses homed on the other mesh [CMN S3 TRM, Super Home Node, page 55], so a line can be held by its home slice and by a proxy slice on the other mesh. The root run measured both (section "Latency from each core to each slice").

The mesh driver prints a map of each mesh for root: sudo cat /sys/kernel/debug/arm-cmn/map /sys/kernel/debug/arm-cmn/map_1, one file per mesh [Linux drivers/perf/arm-cmn.c, arm_cmn_debugfs_init and arm_cmn_map_show]. Jibin read both on 2026-11-01 [crb/results/cmn-map.txt]. The node names below are Arm's [CMN S3 TRM, Table 1-1 page 13]. What the map shows:

  • Grid. Each mesh is 9 columns by 8 rows, 72 crosspoints. The two maps are identical, so the two meshes are the same design.
  • 64 home nodes per mesh, 128 in total. They sit two per crosspoint on port 0 of the 32 crosspoints in rows 1 to 5, columns 1 to 7 (blue in the figure). Three crosspoints in row 5 (columns 1, 4 and 7) have the home-node port but no node enumerated, so they hold no slice.
  • 1 MiB per slice (est.), 64 MiB per mesh. Arm sizes the slices as total SLC divided by the number of home nodes [CMN S3 TRM, Home Nodes, page 19]. 128 MiB from sysfs divided by 128 nodes is 1 MiB. The map does not print sizes, so this is derived. 64 slices of 1 MiB per mesh matches the 64 MiB effective capacity measured for one buffer (Latency section), which was a hypothesis until the map was read. The earlier estimate in this report, 32 home nodes, was wrong: it assumed Arm's 4 MiB maximum per node.
  • 35 core ports per mesh (RN-F, Arm's "fully coherent Requesting Node", which is what a core is to the mesh), on port 1 of the same 35 crosspoints. 64 cores per mesh on 35 ports means at least 29 ports carry two cores. The driver prints no ids for cores, so the map cannot show that pairing directly. It does show two home nodes sharing port 0 on every blue crosspoint, which is the CAL arrangement, so the design uses CALs.
  • 12 memory ports per mesh (SN-F, Arm's "CHI Completer Node", the memory side), in columns 0 and 8, rows 1 to 6. 8 chip-to-chip gateways per mesh (CCG), the links between the two meshes. Rows 0, 6 and 7 otherwise hold I/O home and request nodes (HN-I, HN-T, HN-P, HN-D, RN-I, RN-D, SBSX) and six ports of a type this driver version does not know, printed "????".

Where each core sits, how far each slice is from it, and which mesh homes a given line were all measured on 2026-11-02 with the mesh counters under root. See "Latency from each core to each slice (root run)" below.

Is the pair port how the mesh cache is reached?

Yes. A core reaches everything beyond its L2 through one connection: its requester interface (an RN-F in Arm's terms) into a crosspoint device port. Every L2 miss, every write-back and every snoop answer from the core uses that connection, so the mesh cache, the other cores' caches and DRAM are all behind it.

Arm provides a block that puts two devices on one such port: "A Component Aggregation Layer (CAL) allows multiple devices to connect to a single device port on an XP", and the two-device version "CAL2" supports fully coherent requesters (RN-F) [CMN S3 TRM, section 2.1.1.15 page 63]. The measurement in "The pair finding" ran two cores at the same time, each streaming its own buffer from the mesh cache, and added their bandwidths. One core alone gets 67 GB/s. When the two busy cores are partners (cores 2k and 2k+1, for example 0 and 1), the total is 78 GB/s, so they share one limit. When the two busy cores come from different pairs (for example 0 and 2), the total is 134 GB/s, which is two times the single-core value. Every core has a partner, so the limit does not depend on which cores exist. It depends on which cores are busy at the same time: a port serving one busy core and one idle core gives the busy core its full 67 GB/s. What is confirmed by the document is that the mechanism exists. What is measured is that CRB's cores are limited in pairs. That CRB attaches its core pairs through a CAL2 is the simplest reading of the two, and it is not confirmed by any CRB document: the firmware tables give each core its own cluster [/sys/devices/system/cpu/cpu*/topology/cluster_cpus_list]. The mesh map adds a counting argument: 64 cores per mesh sit on 35 core ports, so at least 29 ports carry two cores, and the map shows the home nodes on the same crosspoints already sharing ports in twos [crb/results/cmn-map.txt].

For software, the pair port is a 78 GB/s limit per two cores on traffic beyond L2. That is about 28 B per core cycle (est. from 78 GB/s at 2.8 GHz). It is the reason one thread per pair gets 1.6 to 1.7 times more mesh-cache bandwidth than two threads on a pair. For DRAM streams the port is not the limit, because DRAM latency limits each core first (2 threads at 1 GiB get 53 GB/s paired or not).

Arm's documentation site serves its pages by script and could not be read by the fetch tool. The three documents above were downloaded as PDFs from Arm's documentation service and are kept in crb/refs/. The Neoverse V3AE core TRM (document 101595) could not be downloaded, so the L1 and L2 way counts rest on the cores' own registers via sysfs.

Latency from each core to each slice (root run)

On 2026-11-02 Jibin ran the root tool bench/homelat on CRB (final set 05:49 to 06:04 UTC, results in results/sudo-20261102T054936Z/). It works in three steps. First it finds the home nodes: a mesh counter opened with a node id answers only for a node that exists, and 64 answered on each mesh. Second it finds the home node of every 64 B line of a 32 MiB buffer: flush the line, read the 8 home-node counters of a quadrant with one call, load the line 256 times with a flush between loads, read again, and take the one node that rose by 256. Third, for every core and every home node, it builds a random chain through 2048 lines of that node, loads them once in a random order, pushes them out of L1 and L2 with 8 MiB of random loads, and times one walk of the chain that has never been walked, seven times with a fresh chain each time.

Checks that passed in that run: 524,288 lines classified with none left over; 511 of 512 lines probed again with only their assigned node's counter open agreed, with one probe where a control node also rose; all 128 nodes received exactly 4096 lines; all 16 chunks of 2 MiB were physically contiguous on every page; and on 8 slices the timed loads showed 1.00 to 1.04 accesses and 0.000 to 0.016 misses at the home for the 4 local slices, 0.000 to 0.003 for the 4 remote ones, 1.04 to 1.23 L2 refills per load in the pass that counts the home's own counters (1.02 to 2.05 in the separate pass that counts both whole meshes, where accesses summed over both meshes were 1.01 to 2.13 and misses -0.006 to 0.346 per load, an excess beyond the timed loads that is recorded but not attributed), at 22 to 36 ns, with an empty counter window of the same cache state subtracted [full/verify.csv, run.log]. The repeat spread of the 7 chains is 3 % of the median (5 % at the 90th percentile) [full/latency.csv, every repeat kept]. An earlier complete run at 04:06 UTC gave the same matrix within 0.2 ns per row (median) and the same core positions; it is kept in results/sudo-20261102T040631Z/.

The 29 to 30 ns "mesh cache" latency in the hierarchy figure is the average of this over all slices. Lines homed on the other mesh are served by a local proxy

The home node of a line is fixed by the address hash, and the hash spreads every 2 MiB chunk evenly: each of the 16 chunks put exactly 16,384 of its 32,768 lines on each mesh [full/chunks.csv]. The split is not line by line: within every chunk the mesh is the XOR of address bits 6, 8, 10, ... 20 (the pattern of the first 16 lines is 0101 1010 0101 1010), and 4 of the 16 chunks come out inverted, so higher physical-address bits, which user space cannot see, also enter the hash [full/homes.csv, checked on 2026-11-02 over all 524,288 lines]. So half of any buffer is homed on the other mesh. A core still sees those lines at 19 to 44 ns, the same range as its own mesh, and the latency to a remote slice is anti-correlated with the latency to the same-numbered local slice (correlation -0.74, median over cores). Arm's design explains it: a home node also acts as a proxy for addresses homed on the other mesh (the LCN role of the super home node, with its own part of the slice, the LCC) [CMN S3 TRM, Super Home Node, page 55; HBT and LBT, page 1216]. The counters confirm the service: in the cache-state check, the 4 remote slices saw 0.00 to 0.01 accesses per load at their home while the loads were served at mesh latency, and during a repeated 8 MiB read stream from CPU 0 the other mesh counted nothing at all (0.000 accesses per line on arm_cmn_1 against 0.827 on arm_cmn_0) [writebw.csv, case asmread-8M-1, analysed with bench/subtract.py]. Which proxy serves which home is a fixed function of the home's position, roughly its mirror image, which fits two identical chiplets placed rotated; this report does not use the remote rows to place anything.

So all of a core's cached lines live on its own mesh, half in the home slices and half in the proxies. That is why one buffer sees 64 MiB of mesh cache: one mesh's 64 slices of 1 MiB. The earlier explanation, that a buffer is homed on one mesh, was wrong and is withdrawn. How each slice is split between home lines and proxy lines is a configuration setting that was not read (CMN S3 TRM, capacity partitioning, pages 335 to 336), so the 64 MiB figure is measured and the split behind it is a hypothesis.

Effective capacity is 64 MiB for one buffer

Mesh-cache misses for a single buffer start at 64 MiB (11 % of loads) and reach 81 % at 96 MiB, far earlier than a 128 MiB cache predicts. The same counters show all of the buffer's traffic on the core's own mesh (arm_cmn_0) up to 96 MiB, and 34 % on the other mesh at 1 GiB. The root run of 2026-11-02 explains it: half of the lines are homed on the other mesh, but a proxy on the core's own mesh serves them, so a core's whole working set is cached on its own mesh, 64 slices of 1 MiB (section "Latency from each core to each slice"). The earlier hypothesis in this paragraph, that physical memory is assigned to a mesh in large pieces and a buffer lives in one half, was wrong: every 2 MiB chunk splits exactly in half between the meshes.

A first read of lines cached on the other chiplet costs 85 ns, later reads 32 ns

Corrected on 2026-11-02 after a question from Jibin: the earlier version of this section reported the best of two walks and so hid the cost of the first one. Method: a chain is built and walked once on one core, so every line of it sits in that core's chiplet (in its slices, and the last 2 MiB of the walk in its L2). A core on the same or the other chiplet then walks two fresh chains over the same lines, one after the other, and the time of each walk is kept. Pairs across chiplets: built on 3 and walked on 67, 67 to 3, 64 to 3, 3 to 119; same-chiplet controls: 3 to 3 and 67 to 67. At 16 MiB the same-chiplet walks take 29.0 to 29.3 ns per load. Across chiplets the first walk takes 85.0 to 88.5 ns per load, and the second walk 31.7 to 33.2 ns. So a line that the other chiplet's slices hold costs about 56 to 59 ns more on first access: the load misses in the proxy slice on the reader's own mesh, crosses to the slice on the other mesh that holds the line, and comes back. Once read, the line is kept in a slice on the reader's own mesh, and the second walk is close to the own-mesh value. The remaining 2.6 to 4 ns of the second walk above each core's own-mesh figure (28.9 to 29.4 ns for cores 3, 64, 67 and 119 [results/followup3-20261102T031936Z/percore-latency-1.csv]) is not explained. At 32 MiB: first walk 82.8 to 87.7 ns, second 32.7 to 37.3 ns, same-chiplet 30.2 ns. At 64 MiB DRAM misses enter: first walk 93.6 to 97.9 ns against 48.7 to 51.5 ns same-chiplet. The 85 to 88 ns first walk agrees with the 81 to 88 ns Bill reports for "L3, other domain", so the earlier hypothesis that his lines were dirty in a remote L2 is withdrawn. Caveat: about one eighth of the lines (the last 2 MiB walked by the builder) may still be in the builder's L2 at the first walk and be served core to core; the test does not separate them. Files: results/followup2-20261031T073513Z/cross.csv.

Mesh-cache latency by core position

The same 16 MiB fresh pointer chase was run pinned to each CPU from 0 to 119, twice, with a new buffer each time, plus a one-thread asmread stream at 8 MiB from each CPU [results/followup3-20261102T031936Z/percore-latency-1.csv, -2.csv, percore-asmread-1.csv, -2.csv].

Mesh-cache latency depends on where the core sits: 25.4 ns on CPU 94 to 30.5 ns on CPU 56, a 5 ns spread, repeatable to 0.2 ns. Partner cores (2k and 2k+1) share the same value, as they should if they sit on the same crosspoint. The repeated chase, which the core learns and prefetches, shows no spread (5.3 to 5.8 ns). One-thread read bandwidth varies only from 66 to 72 GB/s. The spread is an average over all slices of the core's mesh, and the root run shows what it is made of: 19 ns to the nearest slice, 2.6 ns per hop, up to 44 ns to the farthest (section "Latency from each core to each slice").

The older per-thread spread (25 to 58 GB/s per thread, 40 threads one per pair, 3 MiB each) was rerun with one line per thread and repetition [results/followup3-20261102T031936Z/perthread-asmread-3M-40.csv]. In each of the 3 repetitions the 32 threads on mesh 0 got 25.4 to 30.5 GB/s and together 869 to 890 GB/s, and the 8 threads on mesh 1 got 58.1 to 61.6 GB/s and together 473 to 482 GB/s. So that spread was the two meshes, not core position: 32 readers share one mesh, 8 readers have the other to themselves.

Why the mesh-cache row uses 40 threads, not 120

The mesh-cache test needs two things at once. Each thread's buffer must be larger than its 2 MiB L2, or the data never leaves the core. All buffers together must fit in the mesh cache, or the misses go to DRAM and the number becomes a DRAM number. With 3 MiB per thread, 40 threads is 120 MiB, within the 128 MiB nominal size. 120 threads would be 360 MiB and would overflow. The mesh counters confirm the 40-thread run fit: 2.9 % misses [results/uncore2-20261030T203752Z/cmn-asmread-3M-40T-even.csv]. A second rule halves the usable thread count: one thread per pair, because two partner cores share one port and together get no more than one (section "The pair finding"). So 40 is the largest count tested that fits, and the mesh-served part was still rising at 40, which is why 0.62 TB/s is a lower bound.

The placement was uneven: the first 40 even-numbered CPUs are 32 pairs on chiplet 0 and 8 on chiplet 1. The 8 threads on chiplet 1 got 58 to 62 GB/s each, the 32 on chiplet 0 got 25 to 30 GB/s each [perthread-asmread-3M-40.csv]. Hypothesis: a per-chiplet shared limit, so 20 threads per chiplet would give a higher chip-wide number. The test is the same run with CPUs 0, 2, ... 38 and 64, 66, ... 102; not run.

Writers on both meshes collapse DRAM write bandwidth

The fall above 64 threads is a placement effect, not a thread-count effect. CPUs 0 to 63 are on one mesh and 64 to 127 on the other, so "more than 64 threads on CPUs 0, 1, 2, ..." also means "the second mesh joins in". A follow-up on 2026-11-02 varied the two counts separately: a writers on mesh 0 (CPUs 0 to a-1) and b writers on mesh 1 (CPUs 64 to 64+b-1), asmwrite with 256 MiB per thread [results/followup3-20261102T031936Z/writegrid.csv].

64 writers on one mesh write 394 GB/s. 32 writers on each mesh, the same 64 threads, write 173 GB/s. 56 writers on mesh 1 alone write 361 GB/s. 16 on each mesh still write 346 GB/s, and the collapse starts once both meshes have about 32 writers or more. Reads with the same placements do not collapse: 32 on each mesh read 328 GB/s and 64 plus 56 read 298 GB/s. Memory is spread over the memory ports of both meshes, so a write from mesh 0 to memory homed on mesh 1 crosses the chip-to-chip gateways. Hypothesis: heavy write traffic crossing the gateways in both directions at once is what collapses, and heavy read traffic is not. The counters that would confirm it (requests arriving over the gateways, retries, memory throttling) were read in part 4 of the root run.

Root run result [results/sudo-20261102T054936Z/crossmesh.csv, bench/subtract.py]: with 64 writers on mesh 0 (393 GB/s) the mesh-0 home nodes retried 0.058 write requests per line and throttled memory requests 0.103 times per line. With 32 writers on each mesh (141 GB/s) retries were 0.013 and 0.012 per line and throttling 0.000 and 0.000 on the two meshes. Summed over both meshes, write-request events were 1.56 and 1.53 per line written and memory-request events 1.65 and 1.94 in the two cases; these are event counts, not unique writes, because a proxy counts a remote-homed request as well as its home. So the two home-node indicators that signal overload fell in the collapsed case. That does not locate the bottleneck: other home-node limits, the chip-to-chip gateways and the memory controllers were not counted, with idle background subtracted (under 0.001 per line). The mechanism stays a hypothesis.

The pair finding

Two threads each streaming 8 MiB (above L2, inside the mesh cache) get 134 GB/s together when they sit on any two cores from different pairs, and 78 GB/s when they share a pair. The same two cores with 1 MiB each (inside L2) get 134 GB/s, so the L2 is private and the shared part is the path to the mesh.

Placing one heavy thread per pair is worth 1.6 to 1.7 times the mesh bandwidth of a pair. For DRAM traffic the port is not the limit: 2 threads at 1 GiB get 53 GB/s whether paired or not.

Method and caveats

  • All code is our own C, compiled on CRB with gcc 14.2 at -O3 -march=native. Threads are pinned. Buffers are 2 MiB-aligned and first-touched by the thread that uses them. Transparent huge pages were in effect (AnonHugePages equals the buffer size in every run).
  • Latency is the minimum over reps, which is what "best case" means here. Each rep is at least 0.3 s or 2 full cycles (repeated chain) or exactly one pass (fresh chain).
  • Bandwidth is the best of 3 reps of at least 0.5 s; aggregate = total bytes / slowest thread's time.
  • The mesh-cache latency and bandwidth rows carry a few percent of L2 hits because the footprint rule (above 2 MiB per thread, below 128 MiB total) leaves little room. The corrected latency is labelled est.
  • The "learned pattern" explanation of the repeated-chain curve is a hypothesis that fits the counters (L2 refills 1.0 per load at 5.4 ns). Confirming it needs the core's prefetch controls, which require kernel privilege.
  • The 8 reserved cores (120-127) were never used, so whole-chip numbers are for 120 of 128 cores. Per-core numbers do not depend on this.
  • Mesh counters (arm_cmn PMUs) were read in two short passes with perf_event_paranoid at 0, set and reset by Jibin. No governor, package or boot setting was changed. Only files under /home/jhan/cache-perf were written.

Open items

  • Slice partition. The 64 MiB a core sees is explained as one mesh's 64 slices holding both home lines and proxy lines. The configured split between the two (CMN S3 TRM, capacity partitioning, pages 335 to 336) was not read. Reading it needs the mesh configuration registers, not perf.
  • Write collapse mechanism. Writers on both meshes at once collapse DRAM write bandwidth from 394 to 173 GB/s, and the home nodes' retry and throttle counts fall in the collapsed case, which does not locate the bottleneck. The chip-to-chip gateways and the memory controllers have counters in the mesh driver (ccg and port events) that were not used. A run with those counters is the next step.
  • Cross-chiplet first access. The 85 to 88 ns first walk mixes lines held in the other chiplet's slices with lines still in the builder's L2 (about one eighth), and mixes the two home cases (proxy miss with the data at the remote home, and own-home miss with the data in the remote proxy). Separating them needs chains chosen by home mesh from full/homes.csv with the builder on the other chiplet, which homelat does not do yet. The 2.6 to 4 ns residual of the second walk is also unexplained.
  • Crosspoints without slices. Cores 34, 35, 98 and 99 sit on the crosspoint (4,5) that has a core port and no slice; their nearest slice is one hop away (21.9 ns). Whether the third such crosspoint, (1,5), holds unused cores is not known.
