The mesh latency map of the Asimov emulator

What a load costs from each CPU to each home node of the mesh, measured in run 8 (2026-11-11 and 2026-11-12, result folders 013 to 016). Written 2026-11-12.

Short version

A load from a CPU to a home node of the mesh costs about 20.6 ns, plus 2.0 ns for each step in X and 1.0 ns for each step in Y between the CPU and the node.

This holds for lines in a node's on-chip memory and equally for lines in a node's cache slice, across all 40 pairs of CPU and node, to within 0.32 ns.

A load that must go to memory costs 50.0 to 57.3 ns on the emulator, and its cost follows a longer path through the home node and a memory bridge at the left edge of the mesh.

Words used here

  • Asimov emulator: the hardware emulator that runs the chip's design before silicon exists. It is slow (about 2,780 seconds for one chip second) but counts cycles exactly. Jesse Zhang operates it.
  • Mesh: the chip's interconnect, a grid of 6 x 6 crosspoints. A message moves from one crosspoint to a neighbour at a time. Crosspoints are written (x,y).
  • Step: one move of a message from a crosspoint to its neighbour.
  • Cluster: two CPUs that share one L2 cache and one L3 cache, attached to one crosspoint. CPUs 2 to 9 form four clusters for tests. CPUs 0 and 1 run the operating system.
  • Home node: one of five cache nodes on the mesh (ids 88, 160, 216, 288, 344). Each holds two things: a slice of the system-level cache (SLC), and 256 KiB of on-chip memory (OCM).
  • Line: 64 bytes of memory, the unit that caches hold. A DRAM-backed line is a line of normal memory. A hash of its address selects the one home node that may hold it.
  • Memory bridge (SBSX): a port at the edge of the mesh that leads to memory (DRAM).
  • Dependent load: a load whose address comes from the load before it. A chain of them cannot overlap, so time per load is the latency of one load.
  • Flush: an instruction that removes a line from every cache. Evictor: loads of 30,720 other lines, which push the chain lines out of the CPU's caches.
  • Prefetcher: hardware in a CPU that fetches lines before the program loads them.
  • Cell: one CPU, one home node, one kind of row. Pass: one timed walk of the chain. Best: the smallest ns per load of a cell's 7 passes.
  • meshmap: the program that measures the map. run_map.sh: the script that runs it. latency: the older program, used for control rows.
  • Mesh counters: event counters in the mesh, one set per home node. Core counters: event counters in a CPU.
  • Boot: one start of the emulator with one firmware setting. rms: root mean square of a fit's errors. est.: an estimate.

1. The mesh

CPU pair (one cluster) home node memory bridge

  • Five CPU pairs sit at five crosspoints. Four of them (CPUs 2 to 9) are the test CPUs.
  • Five home nodes sit in the middle rows, at (1,3), (2,4), (3,3), (4,4) and (5,3).
  • Ten memory bridges sit on the left and top edges [Ref8].
  • A load that misses the cluster's caches sends a request over the mesh to one home node. The data returns over the mesh.
  • The distance between a CPU and a node is counted in X steps and Y steps. From CPUs 2-3 at (2,3) to node 344 at (5,3) it is 3 X steps and 0 Y steps.
  • The question of this run: what does each of the 4 x 5 = 20 distances cost, and does it cost the same for the node's OCM and for its cache slice?

2. How the map was measured

  • Step 1 is needed only for DRAM-backed lines. An OCM line belongs to its node by address. For a DRAM-backed line the program finds the node with the mesh counters: it flushes and loads the line 64 times and reads which node counted the requests.
  • Step 2 isolates one node. All 2,048 lines of a chain belong to the same home node, so every load of a pass travels the same distance.
  • Step 3 decides who answers the load. The four kinds differ only here:
KindLines of the chainBefore each timed passWho answers the load
ocm-flushon-chip memory (OCM) of the nodeflush every chain linethe node's OCM, over the mesh
ocm-evictOCM of the nodestore to every chain line, then the evictorthe node's OCM, over the mesh
slcDRAM-backed lines whose home is the nodestore to every chain line, then the evictorthe node's cache slice, over the mesh
dram-flushthe same DRAM-backed linesflush every chain linememory (DRAM), through the node
  • Why a store before the evictor: the store makes the line dirty, so the cluster must write it to the home node's slice when the evictor pushes it out.
  • Step 5 gives 7 passes per cell. The page quotes the best pass. Pass r reads byte 8 x r of each line.
  • Size of one boot: 9 CPUs x 5 nodes x 4 kinds = 180 cells, 1,260 timed passes, about 1.1 chip seconds.

4. The cost of one step

Each dot is one cell: a CPU and a node. The horizontal position is the distance in units, where one X step counts 2 and one Y step counts 1.

All three series lie on one line: 1.0 ns per unit. One X step costs 2.0 ns and one Y step costs 1.0 ns.

BootKindBase, nsPer X step, nsPer Y step, nsrms, nsLargest error, ns
Boot 1ocm-evict20.612.001.000.090.19
Boot 1slc20.642.000.980.100.29
Boot 1ocm-flush21.031.951.050.220.42
Boot 2ocm-flush21.041.991.010.110.46
  • In cycles: the CPU runs 2 cycles per ns. So one X step costs 4 cycles and one Y step costs 2 cycles. Each figure covers the request going out and the data coming back.
  • One way, that is 2 cycles per X step and 1 cycle per Y step. This split assumes that both directions cost the same. The data give only the sum.
  • The base of about 20.6 ns is everything that does not depend on distance: the CPU's own cache lookups, the cluster's port, and the home node's lookup.
  • The step cost does not depend on the L3 state. Boot 2's flushed OCM cells give 1.99 and 1.01 ns per step with the L3 in use. Their medians fit 21.23 ns + 2.00 ns per X step + 1.00 ns per Y step with an rms of 0.01 ns [Ref3].
  • Flushed OCM lines read about 0.4 ns above evicted ones on boot 1 (base 21.03 against 20.61 ns). The cause is not known.

5. Is the cache slice as fast as the on-chip memory?

Yes, on boot 1. This was the hypothesis under test.

  • The test: slc and ocm-evict use the same recipe on two kinds of line. Their difference is the difference between a slice and the OCM of the same node.
  • The result: slc minus ocm-evict is +0.004 ns on average over 40 cells. The range is -0.25 to +0.35 ns [Ref2].
  • The check that the slice answered: the mesh counter for requests sent on to memory reads at most 0.0122 per load in slc cells (cell medians). It reads 1.00 per load in dram-flush cells.
  • The check that the right node answered: in every cell the cell's own node counts about 1.2 more requests per load than each other node.

6. A load that goes to memory

  • Measured: 50.0 to 57.3 ns on boot 1 and 50.6 to 57.8 ns on boot 2. The 7 passes of a cell agree to within 0.13 ns.
  • The plain distance to the home node does not explain these cells (rms 1.73 ns).
  • A three-leg path does (rms 0.089 ns on boot 1, 0.085 ns on boot 2): request to the home node, then on to a memory bridge, then the data directly back to the CPU.
  • Cost: 46.1 ns + 0.99 ns per X link + 0.32 ns per Y link on that path.
  • Where the bridge is: the fit selects row y = 3 at the left edge. The mesh map shows a bridge at (0,3) [Ref8].
  • A path that returns through the home node fits worse (rms 1.07 ns).
Two limits on this section. The path is a hypothesis about routing: each boot measured the lines of one 2 MiB page, and two pages agree. The absolute values are not silicon values: the emulator's memory is a model, not real DRAM (Jesse's README) [Ref6].

7. Which node holds a line

  • The program measured the home node of about 10,250 DRAM-backed lines per boot with the mesh counters.
  • Arm's manual gives a hash formula from a line's physical address to one of five targets [Ref7].
  • The formula predicts every measured line: 10,245 of 10,245 on boot 1, 10,251 of 10,251 on boot 2, 10,253 of 10,253 on boot 3. The three boots used three different memory pages [Ref4].
  • The target order is 88, 216, 344, 160, 288. With it, the home node of any line can be computed from its address, with no measurement.
  • Each node holds one fifth of the lines: 2,048 to 2,053 of the probed lines per node.

9. What the L3 and the prefetchers change

One dot is one cell of CPUs 2 to 9. The position is the best ns per load.

boot 1: L3 holds no data, prefetchers offboot 2: L3 in use, prefetchers offboot 3: L3 in use, prefetchers on

  • Flushed OCM lines: boots 1 and 2 agree (+0.05 ns on average). The map does not depend on the L3.
  • Flushed DRAM lines: boot 2 reads +0.62 ns above boot 1 in every cell. Insufficient data on the cause.
  • Evicted kinds on boot 2: 13 to 17 ns, and not a distance map. Only about 0.3 of the loads left the cluster. The cluster kept the other lines, although the evictor loads 7.5 times the size of the L3.
  • Those cells are a mix of two costs. A model fits the 280 passes of each kind to 0.09 to 0.10 ns: about 10.3 ns est. for a load that stays in the cluster, and the mesh cost of boot 1 for a load that leaves it (0.97 to 0.99 ns per unit).
  • Boot 3: with the prefetchers on, the flushed kinds drop to 12 to 35 ns and no longer follow the distance. A flushed DRAM line costs about half.
  • CPU 0: its cluster has the L3 in use and the prefetchers on at every boot, so its 20 cells are not distance numbers.

10. Limits and open questions

  • Emulator, not silicon. Cycle counts on the mesh come from the real design. Memory latency does not.
  • One X and one Y cost for the whole mesh. The CPUs and nodes use columns 1 to 5 and rows 2 to 4. Links outside that area were not measured.
  • Passes 4 to 6 read about 1.3 ns above passes 0 to 3 wherever a load comes over the mesh from a cache or the OCM. These passes read the upper 32 bytes of the line. Every best value is therefore a lower-half value. The cause is not known.
  • The slice was compared with the OCM on boot 1 only. On boot 2 the evicted kinds are a mix (section 9).
  • Why the cluster keeps the chain lines on boot 2. In the first passes of a cluster's first cell the evictor works, then it stops working. Two tests would narrow the cause: one cell under the L3 hit counters, and one cell whose evictor stores to its lines.
  • The Y cost on the memory path is 0.32 ns per link, against 0.5 ns one way in the cache kinds. Insufficient data: the test uses only three rows.
  • Not verified: the firmware state of each boot is taken from Jesse's README. The counters agree with it.
