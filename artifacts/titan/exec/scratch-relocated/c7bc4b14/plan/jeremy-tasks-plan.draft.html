Where Jeremy's statements differ from the host

  • “Both need root and a reboot.” The governor needs root but no reboot: it is a live kernel setting. isolcpus needs root and one reboot. nohz_full and rcu_nocbs need more than a reboot: the running kernel was built without them, so a rebuilt kernel is required.
  • “No boost.” Already true, by firmware. The highest performance level equals the nominal 2.8 GHz, so there is no boost range to disable.
  • “The clock stays fixed.” The performance governor requests the highest clock permanently. A busy core already reaches 2.8 GHz under schedutil, 14 ms to 110 ms after it becomes busy (measured). A thread that sleeps between short bursts, the fake device's pattern, stays at a 1.6 GHz request and an effective 1.4 GHz (measured, section 5.3). The delivered clock over a whole run is still unmeasured.
  • “No outbound network; we copy everything in.” The host has outbound network, and the staging of the SDK workspace on 21 October downloaded packages on the host (pip wheels at 44.8 MB/s). The requirement reads as “not needed”, not “must be blocked”. Nobody should block it to match the sentence.
  • “Ubuntu 24.04's packages cover these.” Partly. CMake 3.28.3 and Python 3.12.3 with headers are installed system-wide. clang-18 and ninja-build are not installed (they exist in the package index). The staging solved this with a user-level toolchain under the account, so no package install is needed.
  • How many cores. Message 1 asks for one or two, message 2 for one, message 3 for cores 120–127 (eight). This is an inconsistency to settle, not an error (decision D3).
  • “Isolated cores for the pass thread.” The pass thread is not what voided the first run. The record was voided because the fake device thread's mean lateness passed the band, and the SDK does not pin that thread. The host's clock alone does not explain that lateness (section 5.3). The thread's placement is the first fix, and isolation of the pass core is the second (decision D5).
  • “One job at a time.” No host mechanism enforces it. The SDK's perf lane holds a lock while it runs. Jeremy's churn job script holds none. Jibin's own logins count as well (decision D4).

What this means for hypothesis H1 of the first draft (“the 1.6 GHz sleep-pattern clock causes the fake device's lateness”): not supported as a sufficient cause. On a dedicated idle CPU at the low clock the same wait pattern is late by 0.02 µs on average, 300 times below the 2.5 µs band. The clock does matter for the tick's cost. At the low clock a tick stall exceeds 2.5 µs in 1.2% of spin windows (max 5.8 µs). At 2.79 GHz it does so in 0.3% (p99 1.99 µs). The rare 8 µs to 11 µs stalls occur at both clocks. So the performance governor shortens the typical tick stall by about the clock ratio but cannot by itself turn a 6.2 µs mean into less than 2.5 µs.

Remaining hypotheses for churn-r1's 6.2 µs mean, each with the measurement that decides it:

  • H2, CPU sharing. The device thread is unpinned and shared CPUs 120–126 with the harness's other threads and the launcher's Python, so its wake-up could have to preempt a running thread. Those CPUs took 1,300 to 7,700 interrupts per second from the threads' own timed sleeps (Figure 2). Measurement: a re-run with the device thread pinned to an otherwise idle CPU (D5), comparing late_mean_s.
  • H3, the retire path's own work. In fake_device.cpp the thread writes the pass's drain rows and pushes the completion before it computes the lateness, so late_mean includes that work. If that cost scales with the clock, the governor cuts 6.25 µs to about 3.6 µs (est., 1.6/2.8 of it), still above the band. Measurement: govtest-1 (governor only, before the reboot).
  • H4, the 50 µs timer slack. The thread's sleep ends about 53 µs after the requested time, so only about 47 µs of the 100 µs spin window remain for absorbing a late wake-up. A 1 µs slack (one prctl call, no privilege) widens that margin. Measurement: hiccup with and without the slack, then the SDK change (D5).

How to read the clock without disturbing a run: scaling_cur_freq is the governor's request and costs nothing. The CPPC feedback counters give the delivered clock but each read sends two IPIs to the CPU being read (measured: 10 reads added 20 function-call interrupts), and root's cpuinfo_cur_freq sends four. The reference counter runs at 1,000 MHz only while the CPU is not idle, so the counter pair over a run measures the delivered clock during the active time. Rule for counted runs: one counter pair on the pass core before and after the run, no polling in between. Wake-up latency is favourable: no cpuidle driver is registered (“driver: none”), so idle CPUs wait in the shallow wait-for-interrupt state (WFI) and wake in about 3 µs (measured as overshoot minus slack).
