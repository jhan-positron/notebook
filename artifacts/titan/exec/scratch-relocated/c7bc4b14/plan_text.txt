 Asimov cards Positron's accelerator boards. None is attached to phoenix-crb, and Jeremy's tests do not need one. 
 LSF A batch job scheduler whose shared worker hosts Jeremy calls too noisy for timing. phoenix-crb runs no LSF. 
 pass thread The one runtime thread, named positron-pass , that plans and issues each forward pass (one model step). The SDK pins it to the CPU given as pass_thread_core . 
 fake device / null_timing The SDK's simulated device backend. One “fake device” thread sleeps until 100 µs before each pass's retirement time, then spins and posts the completion. Its lateness is measured against a band. The SDK does not pin this thread. 
 lateness band / void The allowed mean lateness of the fake device: 0.2% of the shortest pass period, 2.5 µs in the run seen here. A record whose mean lateness passes the band is “void”, and the latency judge reports INFRA (no measurement). The rule uses the mean, not the maximum. 
 latency judge / churn label The SDK tools ( tools/conformance/churn.py and latency_judge.py ) that run the per-user latency gate named per-user-latency.qwen3_5_0_8b.P-TP1 and judge the record. They require only that the pass thread is pinned. They record whether the pass core is in isolcpus but do not require it. 
 perf lane A different SDK tool ( tools/perf/perf_lane.py , records.py ) for the TPS gate's host timing and the timed compile. It refuses any host that has no online core in both isolcpus and nohz_full. TPS means tokens per second. 
 D21, U1 p99, U5 waking, D17 lane SDK names used in its design documents. D21 is the set of per-user latency targets. U1 p99 is the 99th-percentile per-user latency target. U5 waking is the consumer-wake target. The D17 lane is the tool lane that measures them. The design says U1 p99 and U5 waking “count only from an isolated host”. 
 counted run A run whose numbers go into the 5 November demo, as opposed to a trial run. 
 isolcpus A kernel boot argument. With the domain flag the listed CPUs leave the scheduler's load balancing: a thread placed there stays there, and no other thread is moved there automatically. With managed_irq the kernel keeps kernel-managed device interrupts off them when the queue has other CPUs to use. It takes effect only at boot and cannot be undone without another reboot. 
 nohz_full A kernel feature (build option CONFIG_NO_HZ_FULL) that stops the periodic scheduler tick on a CPU running a single task. The running kernel was built without it. 
 rcu_nocbs A kernel boot argument that moves RCU callback work (deferred kernel clean-up, RCU = read-copy-update) off the listed CPUs. It needs the build option RCU_NOCB_CPU, which a NO_HZ_FULL kernel includes. 
 expedited RCU grace period A fast form of RCU synchronisation that sends a function-call IPI to every busy CPU on the host. A sandboxed service start or a namespace teardown triggers one. The kernel setting rcu_normal=1 turns them into normal, slower grace periods without IPIs. 
 tick / HZ The periodic scheduler interrupt. The running kernel has HZ = 250, one tick every 4 ms on a busy CPU. 
 IRQ / managed IRQ A hardware interrupt request. A managed IRQ is one whose CPU assignment the kernel controls (here the NVMe disk queues, one queue per CPU). It cannot be moved by writing to /proc/irq. 
 IPI Inter-processor interrupt: one CPU asking another to do something (for example a function call or a reschedule). No isolation setting removes all of them. 
 cpufreq governor The kernel policy that picks a CPU's clock. schedutil (today) follows CPU utilization. performance always requests the highest clock. 
 boost A clock above the nominal maximum. phoenix-crb's firmware exposes no boost range: the highest level equals the nominal 2.8 GHz, so there is nothing to disable. 
 CPPC / feedback_ctrs / AMU Collaborative Processor Performance Control, the firmware interface behind the cppc_cpufreq driver. Its feedback counters (read from the CPU's Activity Monitors Unit, AMU) are readable by any user and give the delivered clock: delivered performance = 50 × Δdelivered / Δreference, and one performance unit is 20 MHz on this host. Each read sends two IPIs to the CPU being read. 
 scaling_cur_freq The sysfs file that reports the governor's last clock request for a CPU, not the delivered clock. Reading it costs no IPI. 
 timer slack The kernel's allowed lateness for a sleeping thread's wake-up, 50 µs by default. A thread can lower its own slack with prctl(PR_SET_TIMERSLACK) without privilege. The SDK's waker thread does this (1 µs). The fake device thread does not. 
 vendor kernel The running kernel 7.1.3-arm-agi-20260916-v0.7.2-g4dbc8bb88858 . It was built on 16 September 2026 by an Arm engineer (the package maintainer address is at arm.com) with workarounds for this A0 silicon (A0 is the first silicon revision). It was installed from a local package on 28 September. 
 GIC, TLB, TLBI GIC is the Arm interrupt controller. TLB is the translation lookaside buffer, the CPU's cache of address translations, and TLBI the instruction that invalidates it. 
 SVK Arm's software validation kit: the installer that set up this board on 29 September and left its toolchain in /opt/arm-svk . 
 BMC, EFI BMC: the board's management controller, a small separate computer for remote console and power control (an ASPEED chip is present on the board, but no driver device exists). EFI: the firmware's boot interface, which keeps the boot entries. 
 SCHED_FIFO, POSIX CPU timers SCHED_FIFO is Linux's real-time scheduling policy. POSIX CPU timers are per-process timers that count CPU time. Both matter only for the nohz_full rules in P4. 
 PATH, PID, LTS, LVM, NTP, DNS, CI Common system terms: PATH is the shell's program search list, PID a process id, LTS Ubuntu's long-term-support release, LVM the logical volume manager (not used here), NTP network time synchronisation, DNS name lookup, CI continuous integration. 
 stock kernel Ubuntu's 6.8.0-147-generic , installed automatically by unattended-upgrades on 15 October 2026 but never booted on this board as far as the host records show. 
 linux-tools (package) The vendor package that ships perf , cpupower and bpftool for the running kernel. Its files are owned by user id 1001, which on this host is positron-perf. 
 GRUB drop-in A file under /etc/default/grub.d/ that adds boot settings. update-grub then regenerates the boot menu. 
 cpuset isolated partition A cgroup v2 setting (cgroup v2 is the kernel's resource-control tree) that removes CPUs from scheduler load balancing while the system runs. It needs root but no reboot. It does not stop the tick and does not show in /sys/devices/system/cpu/isolated . 
 unattended-upgrades / apt timers Ubuntu's automatic package updater and the systemd timers that drive it. The timers are active on the host and installed two kernels in October. 
 hiccup, isol.py Scratch tools left in ~/positron/runs/ : a probe of the fake device's wait pattern (hiccup), and a snapshot/sampler of isolation, governors and per-CPU thread placement (isol.py). This check re-ran hiccup (section 5.3). 
 churn-r1, govtest-1, govtest-2 Run tags. churn-r1 is the run of 21 October. govtest-1 and govtest-2 are the proposed re-runs after the governor change and after the reboot. 
 launcher The shell and Python processes that start Jeremy's job ( ev3-churn-job.sh , churn.py , the judge). Where they first land decides where their threads stay once cores are isolated.

 Where Jeremy's statements differ from the host 
 
 “Both need root and a reboot.” The governor needs root but no reboot: it is a live kernel setting. isolcpus needs root and one reboot. nohz_full and rcu_nocbs need more than a reboot: the running kernel was built without them, so a rebuilt kernel is required. 
 “No boost.” Already true, by firmware. The highest performance level equals the nominal 2.8 GHz, so there is no boost range to disable. 
 “The clock stays fixed.” The performance governor requests the highest clock permanently. A busy core already reaches 2.8 GHz under schedutil, 14 ms to 110 ms after it becomes busy (measured). A thread that sleeps between short bursts, the fake device's pattern, stays at a 1.6 GHz request and an effective 1.4 GHz (measured, section 5.3). The delivered clock over a whole run is still unmeasured. 
 “No outbound network; we copy everything in.” The host has outbound network, and the staging of the SDK workspace on 21 October downloaded packages on the host (pip wheels at 44.8 MB/s). The requirement reads as “not needed”, not “must be blocked”. Nobody should block it to match the sentence. 
 “Ubuntu 24.04's packages cover these.” Partly. CMake 3.28.3 and Python 3.12.3 with headers are installed system-wide. clang-18 and ninja-build are not installed (they exist in the package index). The staging solved this with a user-level toolchain under the account, so no package install is needed. 
 How many cores. Message 1 asks for one or two, message 2 for one, message 3 for cores 120–127 (eight). This is an inconsistency to settle, not an error (decision D3). 
 “Isolated cores for the pass thread.” The pass thread is not what voided the first run. The record was voided because the fake device thread's mean lateness passed the band, and the SDK does not pin that thread. The host's clock alone does not explain that lateness (section 5.3). The thread's placement is the first fix, and isolation of the pass core is the second (decision D5). 
 “One job at a time.” No host mechanism enforces it. The SDK's perf lane holds a lock while it runs. Jeremy's churn job script holds none. Jibin's own logins count as well (decision D4).

 D1 Which message is newer, does Friday stand, and is a Friday setup without nohz_full and rcu_nocbs acceptable? Message 2 asks for Friday, message 3 says “whenever you have a moment”, and their order is uncertain. The running kernel cannot provide nohz_full. Message 2 allows “the rest of the list” to follow later, but it named the reboot as the example, not the missing kernel feature. Friday stands. Proceed on the current kernel. Treat nohz_full as a parallel kernel task (plan step P4). 
 D2 Which SDK path produces the counted numbers: the latency judge (churn label) or the perf lane? The latency judge runs on the current kernel and needs only a pinned pass thread. The perf lane refuses a host with no core in both isolcpus and nohz_full, which puts the kernel rebuild on the critical path before 5 November. The SDK README says the per-user figures “count only from the perf host”, and the design says U1 p99 and U5 waking count only from an isolated host. That is policy, not code, so Jeremy must say which host state makes a judge-path run count. Assume the latency judge. Keep the kernel task running in parallel. 
 D3 Which CPUs to isolate, and the matching change to the job's launch command. On isolcpus CPUs the scheduler does no load balancing. Jeremy's job pins the pass thread to CPU 127 and lets its other threads float over 120–126, where they moved across all seven CPUs in the first run. If all eight are isolated and the threads are not pinned one by one, they stay wherever they first land. With only 126–127 isolated and the job's taskset -c 120-127 unchanged, the launcher's shell and Python can land on an isolated CPU and never leave (the kernel places them on any CPU of the mask). The choice is irreversible without another reboot. Isolate 126–127. The job runs the label with the CPU set 120-125,127 and starts it as taskset -c 120-125 taskset -c 120-125,127 … . CPU 126 stays free for a pinned fake-device thread. One-core variant: isolate 127 only. 
 D4 Run windows in UTC, the reservation rule, and the clock pass rule. The host runs UTC. US clocks change on Sunday 1 November (Jeremy at 06:00 UTC, Jibin at 09:00 UTC), inside the run period. No host mechanism serialises jobs, and Jibin's own logins count. The acceptance rule for “fixed clock” is not stated anywhere. Windows Mon–Fri 13:00–21:00 UTC. Jeremy's job writes /tmp/positron-perf.RUNNING (start, end, pid, tag) and removes it at the end, counted windows are announced 2 h ahead, one job at a time, and nobody touches the host while the marker exists. Clock rule: delivered clock on the pass core ≥ 2,772 MHz (99% of 2,800 MHz) from one feedback-counter pair read before and after the run, no polling during it.

On a dedicated idle CPU at the low clock the same wait pattern is late by 0.02 µs on average, 300 times below the 2.5 µs band. The clock does matter for the tick's cost. At the low clock a tick stall exceeds 2.5 µs in 1.2% of spin windows (max 5.8 µs). At 2.79 GHz it does so in 0.3% (p99 1.99 µs). The rare 8 µs to 11 µs stalls occur at both clocks. So the performance governor shortens the typical tick stall by about the clock ratio but cannot by itself turn a 6.2 µs mean into less than 2.5 µs.

 5.8 What the SDK's own tools require 
 
 churn.py / latency judge (the per-user latency gate run on the host): the judge's isolation check passes whenever pass_thread_core is an integer, that is when the pass thread was pinned. It records core_isolated (pass core in /sys/devices/system/cpu/isolated ) and the isolated CPU list as facts and never reads nohz_full. The record is void when the fake device's mean lateness passes the band. 
 tools/perf/records.py and perf_lane.py (the host timing of the TPS gate and the timed compile): refuse a host with “no online core in both isolcpus and nohz_full”. They require the run to be the dedicated local user on bare-metal aarch64. They flag a one-minute load above 0.5, other users' processes at 5% CPU or more, and any CI-runner process. The workers, the client and the fake device run on the non-isolated CPUs in this tool. The lane holds a lock while its job runs. 
 Policy in the SDK's documents: the README says the per-user figures “count only from the perf host”, and the design says U1 p99 and U5 waking count only from an isolated host. The code of the judge does not enforce that. Whether a judge-path run counts is Jeremy's decision (D2). 
 Thread placement in the runtime : the pass thread pins itself to pass_thread_core . Worker threads remove the pass CPU from their mask and otherwise keep the job's mask. No code sets the fake device thread's affinity. Only the waker thread lowers its timer slack (to 1 µs). Nothing uses SCHED_FIFO or mlockall. 
 Consequence for the no-reboot route : a cpuset isolated partition never shows in /sys/devices/system/cpu/isolated , so churn.py would record core_isolated: false and the perf lane would still refuse the host. The SDK tooling forces the boot-argument route.

On this kernel it gives the scheduler-isolation part of isolcpus and also removes the CPUs from unbound workqueues, unbound kernel threads and the timer-migration hierarchy. It does not give nohz_full, does not move the managed NVMe interrupts, and does not persist across reboot. It does not show in /sys/devices/system/cpu/isolated , so Jeremy's tools record core_isolated: false and the perf lane still refuses the host. Three more limits: 
 positron-perf cannot move its own processes into the partition. Root must write the process id, or delegate the cgroup. 
 One process cannot straddle the partition and the rest. Jeremy's one-process layout then needs the whole job inside, or an untested threaded-cgroup variant. 
 systemd 255 can drop a hand-enabled cpuset controller when it next re-realizes the root slice with a new controller set. 
 Use it only if the reboot slips, tell Jeremy what it lacks (decision D1 then includes it), and test it once before offering it.

echo 126-127 > /sys/fs/cgroup/positron-isolated/cpuset.cpus
echo isolated > /sys/fs/cgroup/positron-isolated/cpuset.cpus.partition
cat /sys/fs/cgroup/positron-isolated/cpuset.cpus.partition # expect: isolated (anything else names the reason)
chown positron-perf /sys/fs/cgroup/positron-isolated /sys/fs/cgroup/positron-isolated/cgroup.procs # lets the job join it

# weaker alternative without a partition (keeps services off the group, no isolation): systemctl set-property --runtime system.slice AllowedCPUs=0-119 
 Rollback 
 
 Governor: echo schedutil into every policy's scaling_governor , and disable the unit. 
 Timers: the restore commands in P5. 
 Boot arguments: remove /etc/default/grub.d/60-positron-isolation.cfg , run update-grub , reboot. In an emergency the GRUB menu lists every entry. It shows on the EFI console (serial mirroring unverified), and a failed boot retries the saved entry after 10 s. Console access (A3) is the real safety measure. 
 Kernel: keep the current entry. The saved-entry setting selects it until changed, and grub-reboot trials return to it. 
 rcu_normal : echo 0 into /sys/kernel/rcu_normal , and drop the boot argument.
