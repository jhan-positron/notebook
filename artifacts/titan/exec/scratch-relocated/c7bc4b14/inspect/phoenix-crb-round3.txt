# SDK CI toolchain and venv (Phoenix)

Set up 2026-10-21 for positron-perf, approved by Jeremy that day ("user-only toolchain on Phoenix").
It is the same toolchain as sw-dev-01's `sdk-ci-2026-10` (2026-10-06), built for linux-aarch64.
Everything is under `$HOME/positron`. Nothing system-wide changed, and no sudo was used.

## Verified 2026-10-21 (`~/positron/work/toolchain-verify/`)

- **Interface.** Running the script directly exits 2. A bad argument returns 2 and a missing
  environment returns 1. Sourcing it three times leaves one PATH entry. CC, CXX, LDFLAGS,
  SDK_TOOLCHAIN and SDK_TOOLCHAIN_PREFIX are set.
- **Compilers.** clang reports `Target: aarch64-conda-linux-gnu`, reads the `.cfg` and selects the
  environment's gcc 13.3.0.
- **C++23 program.** One program, compiled with `-std=c++23 -O2 -Wall -Wextra -Werror` by both
  clang++ and g++, builds and runs (rc 0). It uses zip, enumerate, fold_left, multidimensional
  `operator[]`, static `operator()`, `if consteval`, `auto(x)` and byteswap.
  - The binaries load the environment's libstdc++ and libgcc_s through RPATH.
  - Their newest glibc symbol is GLIBC_2.34.
- **Sanitizers.** ASan+UBSan and TSan builds of the same program run with ASLR on, for both
  compilers (kernel 7.1.3, 52-bit VA).
- **CMake.** A CMake project with `cmake_minimum_required(3.25)`, as in the repo, builds with Ninja
  for both compilers.
- **Venv.** `pip install --require-hashes --only-binary=:all:` installed all 23 packages from aarch64
  or pure wheels. `pip check` is clean, every module imports, and numpy 2.5.3 runs.

Notes:
- **Policy 3.28 and C++20 modules.** The environment has no `clang-scan-deps` (sw-dev-01's doesn't
  either). A project that sets policy 3.28 or later with C++20 or later fails under clang at the
  module scan, unless it sets `CMAKE_CXX_SCAN_FOR_MODULES=OFF`. The SDK uses policy 3.25 and C++20,
  so it is not affected.
- **No `std::expected` with clang 18.** libstdc++ 13 offers `std::expected` only when
  `__cpp_concepts >= 202002L`, and clang 18 reports 201907L. This is the same on sw-dev-01.
- **gcc 13's C++23 marker.** gcc 13 reports `__cplusplus` 202100 for `-std=c++23`. clang 18
  reports 202302.
- **Environment layout.** `CMAKE_AR` and `CMAKE_LINKER` resolve to the host's `/usr/bin` tools. The
  compiler drivers link with the environment's ld, as on sw-dev-01.

# shellcheck shell=bash
# sdk-toolchain.sh: put the Positron SDK CI toolchain first on PATH. Source it (bash); do not run it.
#
#   . ~/positron/tools/sdk-toolchain.sh gcc     # CC/CXX: gcc/g++ 13.3.0
#   . ~/positron/tools/sdk-toolchain.sh clang   # CC/CXX: clang/clang++ 18.1.8 with gcc 13.3.0's libstdc++
#
# This is Phoenix's copy (aarch64, Ubuntu 24.04), with the same interface as sw-dev-01's. The toolchain
# is the conda-forge environment ~/positron/toolchains/sdk-ci-2026-10 (lockfile
# ~/positron/toolchains/sdk-ci-2026-10.lock, platform linux-aarch64). It has the same package versions
# and build numbers as sw-dev-01's linux-64 lock of 2026-10-06: gcc 13.3.0, clang 18.1.8, CMake 3.31.6,
# Ninja 1.13.2, binutils 2.46.1, with the ASan, UBSan and TSan runtimes of both compilers. It uses its
# own sysroot (glibc 2.34, kernel headers 5.14) and its own libstdc++, never the host's compilers or
# headers. The repo's presets build unchanged: cmake --preset P; cmake --build --preset P; ctest --preset P.
#
# It sets:
#   PATH       the environment's bin first (sourcing again, with either argument, replaces it)
#   CC, CXX    absolute paths of gcc and g++, or of clang and clang++, in the environment
#   LDFLAGS    -Wl,-rpath,<env>/lib, so that what you build loads the environment's libstdc++ and
#              gcc's sanitizer runtimes when it runs (not the host's), and -Wl,-rpath-link,<env>/lib,
#              so that ld finds the libstdc++ a shared library needs when it links a C program
#              against it (without it, ld warns). CMake reads CC, CXX and LDFLAGS only when it
#              configures a new build tree.
#   SDK_TOOLCHAIN (gcc or clang) and SDK_TOOLCHAIN_PREFIX (the environment)
# and unsets CFLAGS, CXXFLAGS and CPPFLAGS, which CI does not set either.
# It does not set LD_LIBRARY_PATH (that would load the environment's openssl and curl into system
# tools such as git and ssh) and does not run conda's activation scripts (their default flags would
# change the build). The sysroot needs no flag: gcc has the environment's sysroot built in, and clang
# reads it from <env>/bin/aarch64-conda-linux-gnu.cfg, which also makes it select the environment's
# gcc 13.3.0 (libstdc++ headers, crt files and ld).
# SDK_TOOLCHAIN_ENV=<prefix> selects another environment, for example one recreated from the lockfile.
#
# Sanitizer tests: if an ASan or TSan test fails at startup with a memory-mapping error, run it with
# ASLR off, e.g. `setarch -R ctest --preset tsan`: CI lowers vm.mmap_rnd_bits with sudo, which is not
# available here.

if ! (return 0 2>/dev/null); then
  echo "sdk-toolchain.sh: source it, e.g.  . $0 gcc|clang" >&2
  exit 2
fi

_sdk_toolchain() {
  unset -f _sdk_toolchain
  local which="${1:-}" prefix="${SDK_TOOLCHAIN_ENV:-$HOME/positron/toolchains/sdk-ci-2026-10}"
  local cc cxx path old
  case "$which" in
    gcc) cc=gcc; cxx=g++ ;;
    clang) cc=clang; cxx=clang++ ;;
    *) echo "sdk-toolchain.sh: usage: . sdk-toolchain.sh gcc|clang (got '$which')" >&2; return 2 ;;
  esac
  if [ ! -x "$prefix/bin/$cc" ] || [ ! -x "$prefix/bin/$cxx" ]; then
    echo "sdk-toolchain.sh: $prefix/bin/$cc or $cxx is missing" >&2
    return 1
  fi
  # Drop every earlier copy of this environment's bin (and of the previous one, if it differs).
  path=":${PATH:-}:"
  for old in "$prefix/bin" "${SDK_TOOLCHAIN_PREFIX:+$SDK_TOOLCHAIN_PREFIX/bin}"; do
    [ -n "$old" ] || continue
    while [ "${path#*":$old:"}" != "$path" ]; do path="${path/":$old:"/:}"; done
  done
  path="${path#:}"; path="${path%:}"

#!/bin/bash
# Phoenix: the churn label exactly as run_scheduled_gate.sh's churn branch runs it (dev_job.sh's environment and
# memory cap), the whole label on CPUs 120-127 (so churn.py pins the pass thread to 127, the job's last CPU, and
# the runs' other threads to 120-126), its isolation recorded before, during and after. Usage: ev3-churn-job.sh TAG
set -u
B=$HOME/positron
tag="${1:?tag}"
R=$B/runs/churn-$tag
mkdir -p $R
exec > $R/job.log 2>&1
. $B/tools/sdk-toolchain.sh clang || exit 90
cd $B/src/phoenix-int || exit 91
export POSITRON_COMMIT="$(git rev-parse HEAD)" POSITRON_THREADS=8 POSITRON_MEMORY_CAP=1
export POSITRON_MODEL_CACHE=$B/weights
export POSITRON_BASE_VENV=$B/venvs/phoenix-int-base
export POSITRON_WORK_DIR=$B/work/phoenix-int
echo "== $(date -u +%FT%TZ) host=$(hostname) head=$POSITRON_COMMIT tree=$(git rev-parse 'HEAD^{tree}') dirty=$(git status --porcelain | wc -l)"
echo "== CC=$CC CXX=$CXX: $($CXX --version | head -1)"
I=$B/runs/isol.py
taskset -c 0 python3 $I snap $R/isol.before.json
rm -f $R/sample.stop
taskset -c 0 python3 $I sample $R/isol.samples.jsonl $R/sample.stop &
SP=$!
T0=$(date +%s)
taskset -c 120-127 prlimit --data=51539607552 timeout --signal=TERM --kill-after=5m 45m \
  bash tools/ci/run_scheduled_gate.sh churn $R/record > $R/log.txt 2>&1
rc=$?
T1=$(date +%s)
touch $R/sample.stop; wait $SP
taskset -c 0 python3 $I snap $R/isol.after.json
echo "== label rc=$rc ($(( T1 - T0 )) s)"
taskset -c 0 python3 $I diff $R/isol.before.json $R/isol.after.json
tail -n 25 $R/log.txt | cut -c1-400
ls -la $R/record $R/record/churn $R/record/latency 2>&1
echo "JOB-DONE rc=$rc"

# Positron SDK

The runtime, compiler and ABIs for serving models on Asimov and Titan at maximum tokens per second.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/architecture/shipping-architecture-dark.svg">
  <img alt="Positron SDK shipping architecture: frameworks and apps exchange token IDs with the C ABI; the C++ runtime drives libasimov, the kernel driver and the device software that executes GOLD; the compiler writes the deployment artifact." src="docs/architecture/shipping-architecture.svg">
</picture>

**How the SDK fits together:**
- **Serving frameworks** such as vLLM and SGLang keep their own tokenizer and chat template; no text crosses the SDK's C ABI.
- **The C++ runtime** plans and binds each forward pass, and reaches the device only through libasimov.
- **On the device,** the GOLD interpreter runs resident programs, compiled at deploy time and loaded once, at model load.
- **The box-level package** ships the SDK together with the device software that executes GOLD. The SDK owns the compatibility check and a TPS gate, which holds software exposed on the critical path and the useful slots that software, sampling fallbacks and the planner lose together to 1% of device time (D17), with per-user latency targets beside it (D21).

The diagram is the target design. [Status](#status) says what the tree holds and where each part runs.

**More:** [How a model loads](docs/architecture/README.md#model-plan-pass) · [What happens every pass](docs/architecture/README.md#forward-plan-pass) · [All documentation](docs/README.md)

## Status

The SDK runs on its two test backends: `cpu_reference`, which computes, and `null_timing`, which times. Device programs are synthetic test catalogs, which hold no GOLD program. Every device time is modeled. No simulator or silicon runs an SDK program.

- **Runtime.** `libpositron_rt` (`runtime/`) implements C ABI 0.8 (`include/positron/runtime.h`): the deployment load, admission, the pass planner, the binders, the pass loop, host sampling, events and recovery.
- **Backends.** `cpu_reference` executes each pass's visits over the IR in FP32 (`docs/cpu-reference-backend.md`). Its native mode, the device's arithmetic on the IR, runs from `positron-cpuref forward --mode native`, outside the runtime. Its command-level native engine executes decoded GOLD commands of the matrix engine and SAL over the backend's modeled per-hemi memories, as the RTL computes them, and its tests run it on its own (`backends/cpu_reference/native_engine/`). `null_timing`'s fake device takes each pass's time from a timing table and computes no output (`docs/null-timing.md`). `libasimov` drives libasimov v0.1, one hemi per handle with no device services. Its tests run it over a scripted mock (`docs/libasimov-backend.md`).
- **Serving.** Unpatched vLLM 0.31.0 (`integrations/vllm`) and SGLang 0.5.21 (`python/positron_sglang`) drive one serving core, `positron.serving.ServingCore`. The core makes every runtime call, through `positron.runtime`, the binding of the C ABI. CI tests the faces on `FakeRuntime` and the binding on a compiled tiny cell. `vllm serve` and `sglang serve` run only where their venvs are installed (`tests/python/test_vllm_serve.py`, `test_sglang_serve.py`).
- **Compiler.** `positron-compile` imports Hugging Face checkpoints of Qwen3.5, Qwen3.5 MoE, Qwen3 and OLMoE, and OLMoE GGUF files (`compiler/positron/compiler/descriptors/`). A build places the model on a registered scheme, P-TP1, P-FRONT2, P-TP2 or P-RPA4, or on a scheme file, such as the one `positron-compile optimize` writes (`docs/scheme-optimizer.md`). It writes every artifact section but `catalog` and `lparams` (`docs/artifact-v1.md` §1). Device weights are BF16, the one format that the device layout writes (`compiler/positron/compiler/device/layout.py`).
- **GOLD.** No layer kind or template is lowered (`compiler/positron/compiler/lower/layers/`, `lower/templates/`), and a build writes no catalog, so no artifact holds a GOLD program. The encoders, the Python and C++ static decodes, the engine primitives with the ring places and place slots of their copies and loads inside a ring or an array, each hemi's driver over σ with its pass shape and CALL targets, and L2 with its progress and operand rules are built and tested on their own (`docs/lowering/README.md`, `runtime/gold/`).
- **Device programs.** In place of GOLD, a load takes a synthetic test catalog, which only a dev build accepts (`pos_runtime_config.test_catalog_dir`; `docs/synthetic-catalog-v1.md`). Each has one driver per hemi that CALLs its visits in σ, as `bind.json` documents and decoded commands. Their footprints and accesses are empty, so they record no memory range (§9 there). The `libasimov` backend refuses them.
- **In CI.** Three tiny random-weight models, dense, GDN hybrid and MoE, are compiled on every registered scheme. The runtime serves each one on `cpu_reference`, where each user's greedy tokens are those of a plain FP32 forward pass (`Executor::forward`), and on `null_timing` (`tests/cpp/runtime/binder_progress/`). The C harness serves four users at once on the GDN hybrid's P-TP1 and P-RPA4 cells, on both backends, and each user gets its solo one-shot reference's tokens (`tests/cpp/runtime/harness/`). On P-TP2 and P-RPA4, `cpu_reference` gives P-TP1's rows bit for bit (`tests/cpp/backends/cpuref_exec/placements_test.cpp`). The counts gate holds the pass thread to no syscall and no allocation in every measured pass on `null_timing` (`tests/cpp/counts/`).
- **Nightly.** On the pinned Qwen3.5-0.8B, `cpu_reference`'s FP32 forward is held to Hugging Face's (T1a). Its GDN core and its Mode L form are held to their references (T2, T2c), and the weight layouts to the checkpoint, bitwise (W0). The legs are in `.github/workflows/scheduled.yml`, and the gates in `tools/conformance/README.md`.
- **On LSF, not in CI.** Jobs submitted from sw-dev-01 serve Qwen3.5-0.8B's dense trace on P-TP1 through the runtime. The C harness runs it on `cpu_reference` and on `null_timing` (the dev lane's `harness` label). `tools/conformance/demo_cells.py run` serves it through both frameworks on `cpu_reference`, each stream held bitwise to the C harness's, and on `null_timing` (the gate `demo-function.qwen3_5_0_8b.P-TP1`). `tools/conformance/demo_d17.py run` runs the cell's D17 lane on `null_timing` (`demo-d17`).
- **OLMoE.** OLMoE-1B-7B-0924-Instruct, from its Q4_K_M GGUF file, has registered fixtures on P-TP1, P-TP2 and P-RPA4 (`tools/conformance/demo_traces/fixtures.json`) and the scheme optimizer's case `olmoe-4hemi`, which the dev lane's `optimize` label runs (`tools/conformance/optimize_cases/`). No demo trace or gate is registered for it.
- **Timing.** The shared core refuses a cost model that marks any input calibrated (`core/cost/inputs.cpp`), so every timing table and every T is modeled. `null_timing` measures real host time against that modeled device time. The D17 lane's figures, D21's among them, are advisory: they count only from the perf host (`tools/conformance/README.md`).
- **Absent.** No lane runs an SDK program on a simulator or on silicon (`.github/workflows/scheduled.yml`, `tools/ci/dev_lane.py`). ASIM supplies only a reference command plan and numerics fixtures (`tools/conformance/l1/asim_plan.py`, `tools/conformance/n0_gate.py`). No box-level package is cut (`tools/package/`). The Lean catalog check holds only its pins, its exit codes and the decode of one GOLD frame (`tools/lean/PositronCheck/Basic.lean`).

The [design spec](docs/superpowers/specs/2026-09-24-sdk-v2-design.md) is the binding design. That file is its entry point, and §4–§14 are one file per chapter beside it, listed in its chapter index. Each of its revisions is one file in [`changes/`](docs/superpowers/specs/changes/), named for the revision, and the newest has the highest number. The earlier Codex drafts are archived under the `archive/*` tags.
