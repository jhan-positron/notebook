Short version. With the DSU L3 on (run 4 boot E), one core reads from its L1 in 2.0 ns, from the L2 in 6.0 ns, from an L3 hit in about 11 ns est., from the SLC in 24.2 ns and from DRAM in 52.7 ns (every line flushed). One core reads DRAM at 24.5 GB/s with the L3 on, against 9.2 GB/s with it off (boot C, the same build). Tables 4.4 to 4.6 and section 9 give run 6 boot F1's values (the L3 on) beside run 3's (the L3 off); section 8 is run 3's only.
The L3 step. Runs 1 to 3 and boots A to D measured with the L3 of CPUs 2 to 9 holding no data (register 0x0, 0 L3 hits per load). Boot E's rebuilt SCP turns it on (register 0x70). The 192, 256 and 384 KiB chases (the hit-set rows) then read 7.8, 9.5 and 10.9 ns with 47, 75 and 92 % L3 hits per load, against 14.1, 19.7 and 22.7 ns on boot C (section 5).
Repeatability. Of the 70 rows boot E and run 3 share, 24 agree within 1 % and 47 within 5 %. The rows that moved most are the L3 rows (-51.6 % at 384 KiB) and the per-region OCM rows. Boot A against run 3, the same configuration, agrees within 1 % on 52 of 70 rows (section 4.8).
OCM. The dense all-five chain from CPU 2 reads 26.08 ns on boot E (run 3 25.34, boot A 26.01, boot C 24.96) with one L3 read refill per load. That is the OCM number to quote. On boot E only 0.41 to 0.82 of the loads in the per-region route rows are read from the mesh (L3 read refills per load). The other loads are served by the L3, so those rows are below the true OCM latency (section 6).
Run 6 boot F1 (the L3 on, 2026-11-06) ran run 3's whole command set. The bandwidth rows with the L3 on: one core reads 24.6 GB/s at 32 MiB (run 3 9.2), four cores on four DSUs read 98.1 GB/s together at 16 MiB each (run 3 34.0) and eight cores 107.6 (run 3 66.7); every write row of 2 MiB and above repeats run 3 within 6.4 %, and the pair's 160 KiB write rises 23 % (sections 7 and 9). One core reads an OCM region at 19.9 to 20.1 GB/s (run 3 14.8 to 16.6) and the OCM write stays at 20.3 (section 10). The memory model's delay is answered (section 2.2).
Bandwidth (boot E). One core reads DRAM at 24.9 GB/s (2 MiB) and 24.5 GB/s (32 MiB) with the L3 on. In one assembly call the L1 reads 59.8 to 60.6 GB/s at 16 and 24 KiB, 95 % of the 64 GB/s read path, and writes fit the 32 GB/s write path (section 7). Eight cores wrote 155 GB/s and one core read OCM at 14.8 to 16.6 GB/s per region on run 3, the L3 off (sections 9 and 10).
1. Words used here
PMU, TRM, SOGPMU: the performance monitoring unit, the counters of a core, of the CME or of the mesh. TRM: Arm's Technical Reference Manual of a unit. SOG: Arm's Software Optimization Guide of a core.TLB, table walkTLB: the translation lookaside buffer, the core's cache of address translations. A table walk is the read of the page tables when the TLB misses. The counted events are L1 data TLB refills (0x05) and data TLB walks (0x34).C1-Nano, DSUThe Arm core and its two-core cluster (DynamIQ Shared Unit). The hemisphere has 5 DSUs, CPUs 0 to 9. Device interrupts are routed to CPUs 0 and 1 (irqaffinity=0-1); the scheduler places no unpinned task on CPUs 2 to 9 (isolcpus=2-9) and their periodic tick stops while one task runs (nohz_full=2-9). The init started run_all.sh pinned to CPU 2, so the scripts, the shell and the counter helper ran on CPU 2 (cmncount sets no affinity of its own) and each measured program pinned itself to its --cpu. Every core takes its own timer and per-CPU interrupts, and a program's page faults and system calls run on its own core [Jesse's run 3 README, The run and CPU placement].L1, L2, L332 KiB data cache per core, 128 KiB per DSU, 256 KiB per DSU, 64-byte lines [sysinfo.txt]. On runs 1 to 3 and run 4 boots A to D the L3 of CPUs 2 to 9 was in snoop-filter-only mode and held no data (the stock SCP stages the full L3 for cluster 0 only; register 0x0, 0 L3 hits per load). Boot E's rebuilt SCP turns it on: the register reads 0x70 and the hit set counts 0.75 L3 read hits per load at 256 KiB [Jesse's boot E README, L3 power; latency-dram-small-l3.csv].mesh, crosspoint (xp)The Arm CMN S3 interconnect, a 6 by 6 grid of routers. Distance between two points is the number of crosspoint steps, |dx| + |dy|.home node (HN-S), SLCThe five mesh nodes that own all addresses, each with 1 MiB of System Level Cache in 16 ways. A DRAM address belongs to one home node by a hash, so a buffer spreads over all five.OCMOn-Chip Memory: 4 of the 16 ways of each home node, locked as 256 KiB of memory at 0xE0000000 + n MiB. Region n lives in home node n only. Reached through /dev/ocm in 4 KiB pages.node idThe mesh id of a home node (88, 160, 216, 288, 344). Its bits give the crosspoint: x = bits 8 to 6, y = bits 5 to 3.chaseA pointer chase: each load reads the address of the next load, so the loads cannot overlap and the time per load is the load-to-use latency.repeated chase, fresh chain, flushedRepeated: a random chain walked many times, so later walks hit whatever cache holds it. Fresh: a chain walked once. Flushed: every line was cleaned and invalidated from the caches with DC CIVAC first.sparse chainNew in run 3: a chain with one member line per 4 KiB page, at a different line offset per chain, so a line the hardware prefetcher fetches beside a member is never itself a member. A 256 KiB region gives 64 loads per pass; all five regions give 320. The run 2 chains were dense (every line of the region, 4,096 loads).best, pass, repA command walks its chain several times (passes, or reps); best is the fastest. A sparse per-region row has 7 fresh passes, a dense all-five control 2, a repeated chase 3 reps.refills per loadPMU events 0x03 (L1D refill), 0x17 (L2D refill), 0xA2 (L3D read refill) divided by the loads of the timed walk. 1.00 means one fill of that level per load. A fill can be a demand miss or a prefetch, so the count does not say which loads missed, and a useful prefetch can replace a later demand fill and leave the count near one.perf_covNew in run 3: the counter group's running time over its enabled time for the row. 1.0000 means the counters were never multiplexed; every row of this run reads 1.0000.cmncountThe helper that opens the mesh PMU (arm_cmn_0) around one command and writes cmn-counts.csv: requests received per home node, memory-controller requests and SLC misses.SCP, TF-AThe System Control Processor firmware (which also sets up the mesh) and Trusted Firmware-A (the boot firmware of the application cores). Run 3 ran SCP 0.48.0-nopcie.1 and TF-A 0.35.0, the same as run 2 [Jesse's run 3 README].chip timeTime as the emulated chip sees it. One chip second took 2,776 wall seconds in run 3 [Jesse's run 3 README].est.An estimate, not a measurement.run, bootA run is one job on the emulator (run 3 = membench-jibin-004). Run 4 is five boots, A to E, each a job with one firmware and program configuration (section 2). Boot E is the latest.L3 hit setRun 4's repeated chases from 64 KiB to 512 KiB with the hit events 0x81C5 (L2 read hits), 0xA0 (L3 read accesses) and 0x81C6 (L3 read hits) per load beside the refill events [latency-dram-small-l3.csv].sequential chainA chain whose members are the lines in address order, 8 MiB, every line flushed first: the stimulus a hardware prefetcher is built for [latency-dram-seq.csv].route rowThe dense chase of one CPU-to-region cell run under the mesh's crosspoint counters (data flits sent per direction on the DSU's and the home node's crosspoint); 20 cells, CPUs 2, 4, 6, 8 by OCM0 to OCM4 [latency-ocm-region*-route-cpu*.csv, cmn-counts.csv].contiguous hintThe contiguous bit of a translation entry, which marks 16 neighbouring 4 KiB entries as one 64 KiB block. Boots C and D map the OCM with it (cont=64/64 on every mapping line in dmesg.txt).G2 rowsRun 4's dense, sparse and vary chases of each OCM region from CPUs 2 and 8 without the mesh counters, and the all-five chains [latency-ocm-region<r>-dense-cpu<c>.csv, latency-ocm-region<r>-cpu<c>.csv].rmsRoot mean square of the residuals: the fit's typical miss per cell, in ns.G8 rows, per-pass and single-call formsOne-core L1 reads and writes of 4, 8, 16 and 24 KiB over many passes on boots C and E, timed with one call per pass (looped form, bandwidth-l1-passes.csv) or with every pass inside one assembly call (single-call form, bandwidth-l1-asmpasses.csv). A kernel is the program's inner loop function for one pass of reads or writes. A fit is a straight line, time per pass = fixed cost + bytes / rate, through a form's four rows, and its fixed cost is that form's per-pass cost.read variants, PRFMThe plain one-core read loop and four variants (PRFM, the Arm prefetch-hint instruction, issued 4, 8 or 16 lines ahead, or two streams) at 2 MiB and 32 MiB [bandwidth-read-prefetch.csv].

The bandwidth program gained the read variants and the G8 rows. The flags of every repeated row are unchanged, so a repeated row's numbers compare [Jesse's boot E README, Against boot C; follow-up-run-plan.md].

The memory model's delay, answered. The AP's DRAM (AP: the application processor, the Arm cores' side of the chip) is four Cadence AXI memory models (AXI: an Arm bus protocol), one per SMS lane (the four memory lanes that serve the AP), with every delay control at zero (read latency, write response, READY delays, burst gaps; no bandwidth or refresh scheduler). Even at zero the model answers 3 ns after it accepts a read. By Jesse's count of the RTL stages (RTL: the chip's hardware source; an inference, not a measurement) about 20 ns of the DRAM leg is fixed pipeline between the mesh's SN bridges (the SBSX nodes that connect the mesh to memory) and the memory, and the rest is inside the mesh. Nothing on the path models banks, rows or refresh, so the delay does not depend on address order, which is what boot B's address-order and random 8 MiB chains showed (52.762 against 52.739 ns, section 5) [Jesse's F1 README, The memory model behind the home node].

Words in the SCP row. Snoop filter: the DSU's record of which lines each core's L1 and L2 hold, used to answer the mesh's coherence requests without asking the cores. L3 lookup: on an L2 miss, the check whether the L3 RAM holds the line. L3 allocation: placing a line into the L3 RAM so that a later lookup can hit it. In snoop-filter-only mode the L3 RAM keeps only the snoop filter, there is no lookup and no allocation, and every L2 miss goes to the mesh. The three words are general cache terms, used for every vendor's caches; the mode names are the DSU's own. IMP_CLUSTERPWRSTAT_EL1: the DSU's cluster power status register (IMP: implementation defined, an Arm register that is not part of the architecture; EL1: readable from exception level 1 up). By the DSU RTL's field names, 0x70 is bits [7:6] = 01 (all slices on; this DSU has one L3 slice), bits [5:4] = 11 (the L3 RAM fully on) and bits [3:0] = 0 (no core asking for retention or power-down): the full L3 operating mode, with lookup and allocation open. The L3-off boots B, C and D read 0x0 (one slice, snoop filter only); run 3 did not read the register, so its mode rests on the SCP's staging lines. Arm's TRM was not consulted for the decode [Jesse's F1 README, The L3 and the prefetchers, lines 66 to 70].

Under the mesh counters (which run for each whole command, chain build, flushes and unmap included), F1's core latency commands ran longer: the four counted 4 KiB controls 1.31 to 1.42 times run 3's command time, the 20 sparse OCM rows 1.24 to 1.60 times. The counted 2 MiB bandwidth read ran 0.648 times run 3's command time. So the L2's misses are served inside the cluster on F1. That is the L3 holding the chain, a measurement [latency-dram-small.csv of 011 and 004].
What the counters say about the read streams. Boot E against boot C (one build, the L3 the one change) read 2.68 times at 2 MiB and 2.67 at 32 MiB with the same refills per line (32 MiB: L1 1.00 and 1.00, L2 1.00 and 1.00, L2 refills caused by the L1 prefetcher 1.00 and 1.00, L3 read refills 0.0000 and 0.0004). On F1 the counted 2 MiB read put 0.975 times run 3's requests on the five home nodes (2.5 % fewer) while the command ran 0.648 times as long. So the L3 did not serve these reads without the mesh: nearly the same number of requests reached the home nodes, in less time [bandwidth-read-prefetch.csv of 010 and 007; cmn-counts.csv of 011 and 004].
What the counters say about the OCM rows. The sparse OCM passes count 0.71 0xA2 refills per load on run 3 and 0.42 on F1 (means over the 140 passes of each boot), with the same L2 refills (2.78 and 2.80). So on F1 part of the OCM lines came from the L3, not from the region's home node. The /dev/ocm module maps OCM as Normal write-back memory (the cacheable memory type), so the L3 may hold its lines [latency-ocm-region<r>-cpu<c>.csv of 011 and 004; Jesse's run 3 README, Platform facts, OCM].

Event 0xA2 is the Arm PMU event L3D_CACHE_REFILL_RD: a read that the L3 could not serve and that brought the line in from outside the cluster, that is from the mesh (SLC, OCM or DRAM). This page's reading, not a measurement: the event counts the demand reads that miss the L3 and not the lines the hardware prefetcher brings in; the streams run on the prefetcher (1.00 and 1.00 L1 prefetcher refills per line at 32 MiB) and the chains do not (F1's 32 MiB chain: 0.00 per load; run 3's latency rows did not count the prefetch events). Run 3's bandwidth rows carry no core counters, so the stream refill columns are boots C (L3 off) and E (L3 on), the same build with the L3 as the one change; the chain columns are run 3 and F1 [bandwidth-dram-1core.csv and latency-dram-large.csv of 004 and 011; bandwidth-read-prefetch.csv of 007 and 010].
Hypotheses. Each one names what supports it, what it has to explain, and the measurement that would confirm or reject it.
hypothesis More reads in flight per cluster.
The idea. In run 3's snoop-filter-only mode every L2 miss goes straight to the mesh. In the full mode the L3 handles the miss first. The L3's miss handling may keep more read requests open at once (in flight: issued and not yet returned). With more requests in flight, a stream of independent reads waits less per line, wherever the lines come from: the L3, the SLC, OCM or DRAM.
Why only the sequential reads got boosted. A random read chain has one load in flight, so it gains nothing. When a write is posted, the core does not wait for it, so there is no room to boost performance through overlapping writes. But we observe every sequential read stream of 48 KiB and above gained performance on multiple test shapes:
one core (CPU 2)
CPUs 2 and 3 (the two cores of the same cluster)
OCM reads (CPU 2, and CPUs 2, 4, 6, 8)
one core per cluster (CPUs 2, 4, 6, 8)
all 8 cores (CPUs 2 to 9)
What else. The refills per line are the same on both boots. The mesh requests are nearly the same. The chains of 1.5 MiB and above hold within 4 %. The one-core writes and the placement rows hold within 0.3 %, the multi-core writes of 2 MiB and above within 7 %. The eight-reader row shows a limit shared inside each cluster.
The test. Count the read requests in flight at the DSU's mesh port during the same one-core read, once on an L3-on boot and once on an L3-off boot. This needs a mesh PMU event for requests in flight (to be checked in the CMN-S3 event list). No file on disk counts requests in flight.
hypothesis The prefetcher's requests are the ones that overlap more.
The idea. The streams run on the hardware prefetcher. It issues the same number of requests per line on both boots (1.00 L2 refills caused by the L1 prefetcher per line on boot E, 1.00 on boot C). The counters do not say how many of those requests it keeps open at once. The full L3 mode may let it keep more open.
What is known. With the prefetchers off and the L3 off, boots B and D read 2.38 and 2.38 GB/s at 32 MiB. That is 26.9 ns per 64-byte line, about two lines per DRAM load of 52.2 ns. Without the prefetcher there is almost no overlap.
The test. Run run 3's one-core read lines with the prefetchers off on an L3-on boot (boot F2's firmware; F2 ran run_cme.sh only). A rate near 2.4 GB/s says the rise needs the prefetcher. A rate well above it says the L3 path overlaps demand misses on its own.
hypothesis A per-cluster limit, not a per-core one.
The idea. Something caps how many reads one cluster (a DSU with its two cores and its L3) keeps in flight. If the cap sits in the cluster, two cores of the same cluster share it and each gets about half of the one-core rate. If the cap sits in each core, two cores of the same cluster each get the full one-core rate. The L3 mode is a cluster setting, so a cluster cap is where the L3 mode could act.
What the data on disk say. One reader on CPU 2 reads 24.6 GB/s at 32 MiB. Four readers, one per cluster, read 24.5 to 24.6 GB/s each: no sharing across clusters. Eight readers, two per cluster, read 107.6 GB/s together, 13.4 each, about 27 GB/s est. per cluster. That looks like two cores sharing one cluster's cap.
Why that is not settled. Eight readers may instead be hitting a limit of the mesh or the memory for the whole chip. Section 9 reads the eight-reader rows as one shared ceiling of about 109 GB/s. The rows on disk cannot tell a per-cluster cap from a chip-wide ceiling, because every row with two cores per cluster also has all eight cores running.
The test. Run the bandwidth program with two threads, 16 MiB each, twice: once on CPUs 2 and 3 (one cluster), once on CPUs 2 and 4 (two clusters). Two readers are far below the chip-wide ceiling. If CPUs 2 and 3 together read about 27 GB/s and CPUs 2 and 4 about 49, the cap is per cluster. If both pairs read about 49, the cap is per core and the eight-reader row was the chip-wide ceiling. The writer-placement rows already run these two CPU sets for writes (write-cpus2-3 and write-cpus2-4), so the read version is the same command with the read kernel.
Nearest row on disk. The pair at 160 KiB (33.7 GB/s on F1 against 21.2 on run 3) runs two cores of one cluster, but it sits in the L2 and L3, not in DRAM, so it does not settle this.
ruled out The build. k_read, k_write and k_copy are byte for byte the same in both builds, and boot E against boot C, one build, shows the read rise (2.68 and 2.67 times) with the L3 as the one change. What the build may have moved: the 16 KiB rows, whose buffers fit the L1 (one core read 0.965 times, write 1.016, the pair read 0.966); run 3's README tied its own 16 KiB write shift to a rebuilt bandwidth, and pass differs again. Insufficient data: these files do not show why the 16 KiB rows moved [Jesse's F1 README, Core rows against round three; Jesse's run 3 README].
ruled out Boards or run-to-run noise. The controls repeat within 0.3 %, the one-core writes from 48 KiB on within 0.3 %, the chains from 1.5 MiB on within 3.9 %, and the reps of the one-core read rows spread 1.8 % or less inside each boot. Boot E and boot C ran on other boards and show the same ratio.
partly Page placement on the OCM rows. The /dev/ocm module differs and every process gets its own physical pages, so a single sparse cell (0.69 to 0.95 times) is within its own spread (up to 68 % between passes of one row on run 3, 60 % on F1). What placement cannot explain: all 20 cells faster, and the 0xA2 fall with the same L2 refills, which says the L3 served part of the loads. The test: the sparse rows with the L3 hit event (the hit set of boot E, section 5) on an L3-on boot.

The write rows are the full width of the core's write path. The C1-Nano has one 128-bit write path from the core to its L1 memory system [Arm C1-Nano TRM, "Write path"]. That is 16 bytes per cycle. The latency rows put the core at 2.0 GHz (4.01 cycles per 2.002 ns at 4 KiB), so the path carries 32.0 GB/s. Every run 3 write row from 2 MiB to 32 MiB reads 31.98 to 32.00 GB/s. So the store stream runs at the path's width at every footprint, DRAM included, and the memory behind it is not the limit for one core. The G8 write rows of boots C and E fit the same path: 31.9 to 32.1 GB/s (section 7).
The rows below 2 MiB fall short of the path's width because of the test program, not the core. Each pass of the store kernel carries a fixed cost: the G8 write fits measure it at 23.7 ns (boot C) and 25.7 ns (boot E) per pass with one call per pass, and 9.1 and 14.0 ns with every pass inside one assembly call [bandwidth-l1-passes.csv, bandwidth-l1-asmpasses.csv of 007 and 010]. A 16 KiB pass lasts 534 ns on boot E, so that cost is 5 % of it and the row reads 30.7 GB/s. A 2 MiB pass lasts 66 us, where the cost is below 0.05 %. The same per-pass cost shapes the copy rows.
The read rows are not at the path's width. The read path is dual 128-bit, 32 bytes per cycle or 64.1 GB/s. Run 3's 16 KiB row, in L1, reads 58.1 GB/s (91 % of the path). The G8 rows of boots C and E show that the shortfall is a cost per pass of the loop, not the L1's rate (section 7). Every larger row is set by the level that serves it: run 3 read 9.2 GB/s from DRAM with the L3 off, and boot E reads 24.5 GB/s with it on (boot C, same build, L3 off: 9.2).

Why the four-DSU rows keep 100 % on write but 93 % on read (run 3, the L3 off). The two streams hit different limits. A store stream is pinned at the core's own write path, 32.0 GB/s, whatever is behind it: the four writers read 31.980 to 31.982 GB/s each, and 4 times 32 is below the DRAM write ceiling that eight writers reach (table 4.4, 155 GB/s), so nothing shared is saturated. A read stream beyond L2 is bound by latency (a fixed number of lines in flight per core), and the aggregate is defined by the slowest thread: the four readers read 8.65 to 9.26 GB/s each against 9.31 for one core alone, so the fastest reader kept 99.4 % of the one-core rate and the slowest 93 %. The spread is a per-core property, not interference: with eight readers the per-thread range is 8.47 to 9.04 GB/s, nearly the same, and the aggregate doubles. hypothesis The slowest reader is the core farthest from the home nodes: the 2 MiB chase reads 24.1, 24.6, 24.7 and 26.1 ns from CPUs 2, 4, 6 and 8 on run 3, an 8 % spread that matches the 7 % spread in read rate. The program does not record which thread was slowest.
Where write loses instead. In two groups of rows write keeps less than read: two writers in one DSU at 160 KiB, and eight writers at any size. There the writers share one path. For the pair it is the DSU's one mesh port. For the eight it is the DRAM write ceiling (section 8). A write stream is 32 GB/s per core and a read stream beyond L2 was 9.2 to 9.3 GB/s on run 3. So writers fill a shared path about three times sooner than readers do. With the L3 on, one core reads 24.6 GB/s from DRAM (section 7). Run 6 boot F1 ran these rows with the L3 on: the four-DSU readers rise from 34.6 to 100.2 GB/s at 2 MiB, the eight readers from 67.8 to 108.7, and the write rows of 2 MiB and above stay within 6.4 % (the F1 column above).

The number is derived, not measured: the hit-set row's ns per load, less its L2 read hits per load at the 128 KiB row's time (an L2 hit) and its L3 read refills per load at boot C's 384 KiB time (a read from the mesh), divided by its L3 read hits per load. The 52.7 ns DRAM data read is a fixed-delay memory model. Of the 52.7 ns, 24.2 ns is the home-node round trip (the 2 MiB SLC row) and the rest, about 28 ns est., is the model's delay. The model's configured delay was asked of Jesse and is unanswered [message-to-jesse-round4.md].

The sequential row with the prefetchers off and the L3 on (not run) would show how much of the difference is the prefetcher's.

The C1-Nano is an in-order core, and that is why the per-pass cost shows. Its TRM lists an "in-order pipeline with direct and indirect branch prediction" [Arm C1-Nano Core TRM r0p2, document 107753_0002_06_en, section 1.1 "C1-Nano core features"]. In an in-order core the work at a pass boundary (the loop exit, the return, the register save and restore, the next call) must finish before the first load of the next pass can issue. That time adds to every pass. An out-of-order core issues the next pass's loads while that work is still in flight. The CRB (the Arm reference server used as the comparison machine) has Neoverse V3AE cores, which are out of order. On the same program the V3AE adds 4.2 ns per pass in the looped form, and its single-call form reads the same rate at every size [follow-up-run-plan.md, "CRB check of the two forms", from bandwidth-l1-read21-cpu3-passes.csv and -asmpasses.csv under ai-runs/run5c-crb-sample]. The out-of-order claim for the V3AE comes from Arm's public Neoverse V3 description, and no copy of that document is in the local vendor folder, so it is not cited by page.

The small write rows' per-pass cost is the program's. 7.1 How the L1 read rows are read
Each pass has two parts. One part is the bytes, read at the L1's rate. The other is a fixed time F that does not depend on the bytes. F is the work between the last load of one pass and the first load of the next. A row reports bytes over the whole pass time, F included. So F lowers every row. Subtracting two passes cancels F and leaves the L1's rate.

What F is. In the looped form (one kernel call per pass) F holds the loop exit, the return, the restore and save of the vector registers d8 to d15 (the registers the Arm calling convention makes a called function preserve), the C loop's step and the next call. The write fits put it at 24 to 26 ns per pass. In the single-call form (every pass of a rep inside one assembly call) only the inner loop's exit, the pointer reset and the pass count remain. The write fits put that at 9 to 14 ns, and the read passes above at 11.5 ns est. The single-call form moves the program's work out of each pass. That is why its rows read higher.
Why F shows at all. The C1-Nano is in order (section 7 above). The loads of the next pass cannot issue until the work at the boundary has run. On the out-of-order V3AE the same program keeps 4.2 ns per pass in the looped form and none in the single-call form.
8. Prefetching, in-flight reads and dependent loads
Words used here: in flight means issued and not yet returned. A dependent load is one whose address comes from the load before it, so it cannot issue until that load returns. A pointer chase is a chain of dependent loads. The hardware prefetcher is the part of the core that notices an address pattern and issues reads for the next lines before any load asks for them.

A dependent chain cannot be helped by anything that runs ahead. The random chain's next address is inside the line being read. So one DRAM read must finish before the next can start, 52.7 ns per load. The sequential chain's addresses are predictable. With the prefetchers off (boot B) nothing predicts them, and the chain takes the same 52.8 ns per load.
With the prefetchers on the same DRAM reads overlap. Boot E's sequential chain still reads every line from DRAM once (1.00 L2 refills per load, the lines flushed first). Its loads take 2.49 ns each. The prefetcher issues reads ahead of the loads, about 21 at a time (est.). The lines arrive in L1 (1.00 L1 prefetch refills per load) before or while the load waits for them. The time per load is close to the L1 chase's 2.00 ns. The stream runs at 64 bytes per 2.49 ns, 25.7 GB/s (derived), about the plain one-core DRAM read of the same boot (24.5 GB/s at 32 MiB, measured). On boot C, the L3 off, the same chain takes 6.92 ns per load and the plain read moves 9.2 GB/s. By the same arithmetic boot C keeps about 2.8 times fewer reads in flight (est.). What the L3 changes in how far ahead the prefetcher runs is Insufficient data (section 7).
Two counters tell the prefetcher's fills from the loads' own. Event 0x03 (L1D_CACHE_REFILL) counts every line that enters L1, whoever asked for it. Event 0x81BC (L1D_CACHE_REFILL_HWPRF) counts only the lines the hardware prefetcher asked for [Arm C1-Nano Core TRM r0p2, section 17.1 Common PMU Events]. The difference is the lines the loads fetched for themselves (demand refills, derived). The L2 has the same pair: 0x17 (L2D_CACHE_REFILL) and 0x0111 (IMP_L2D_CACHE_REFILL_L1DHWPRF, L2 refills for the L1 prefetcher's requests) [the same TRM, sections 17.1 and 17.2]. Per load, best pass:

Every row refills L1 once per load. So the refill count alone cannot tell the three rows apart. The prefetch counter can. On the random chain and on boot B it reads 0 per load, so every refill was a load waiting for its own line. On boot E's sequential chain it reads 0.9997 per load, so the loads fetched almost nothing themselves. The L3 column shows that the prefetched lines did not pass through the L3 (0.0001 L3 read refills per load, against 1.0001 on the random chain). Where inside the DSU the L2 prefetch fills come from is Insufficient data.
Inside L1 the same rule holds. The 4 KiB chain's loads are dependent. They take 2.00 ns each (4.01 cycles), the L1 load-to-use time. The read loop's loads are independent. The core can issue two 16-byte loads every cycle, so a 64-byte line leaves the L1 every 1.0 ns, 64 GB/s (computed from the path width). The chase moves 32.0 GB/s from the same cache (derived from its time per load), 2 times less. The chase measures latency and the loop measures bandwidth. The gap between them is how many loads are in flight.
The 0.49 ns above the L1 time is derived (the sequential chain's 2.492 ns less the 4 KiB chain's 2.002 ns) and is not explained. In cycles it is 0.98: the sequential chain takes 4.99 cycles per load against the L1 chain's 4.01, one cycle more. hypothesis A whole cycle per load points at a cost inside the core, such as the prefetched line's write into L1 taking the cache for one cycle per line, rather than at a wait for a late line, which would not average to a whole cycle. A sequential chain with two members per line (32-byte stride) would test it: a per-line cost would halve per load, a per-load cost would not. The counters give refills, not hits, so they do not say whether a load waited for a line that had not yet arrived. A sequential-chain row under the L1 hit counters would show that part.

12. Open items
settled The memory model's configured delay behind the home node: none. Every delay control of the four memory models is zero and the model answers 3 ns after it accepts a read; the rest of the 28 ns est. the chains put behind the home node is RTL pipeline by Jesse's stage count, an inference (section 2.2) [Jesse's F1 README, The memory model behind the home node].
open Why the L3 makes a read stream faster. With the L3 on the plain loop reads 24.5 GB/s at 32 MiB against 9.2 on boot C, the same build, with the same refill counters per line (L1 1.00 and 1.00, L2 1.00 and 1.00, L1 prefetch 1.00 and 1.00). Run 6 boot F1 repeats it (24.6 GB/s) and shows the same on every read stream beyond the L3: the one-core reads at 2 and 32 MiB (2.68 to 2.69 times run 3), four readers on four DSUs (2.89 times at 16 MiB), eight readers (1.61 at 16 MiB) and the one-pass OCM reads (1.21 to 1.36), while no write stream moves (sections 7, 9 and 10); the L2 and L3 footprints of the one-core sweep (48 to 256 KiB) rise 1.56 to 2.59 times as well. The dependent chains beyond the L3 do not move either (2 MiB 24.2 ns on E, 24.1 on C). hypothesis With the L3 in full mode the cluster keeps more read requests in flight toward the mesh (the L3's miss handling takes over from the snoop filter's), so a stream of independent reads overlaps more of its DRAM time while a chain of dependent loads gains nothing. The mesh's crosspoint counters around a one-core read on an L3-on and an L3-off boot, with the read requests in flight at the DSU's port, would test it; the data on disk do not name the mechanism. Section 2.3 lists what differed between the two boots, the counter evidence and the hypotheses with their tests.
open Boot E's 4 KiB per-pass L1 read reads 40.9 GB/s against boot C's 46.2, with the other 15 G8 rows within 3 %. Insufficient data: the G8 rows with the perf columns on a second L3-on boot would show whether the row repeats [bandwidth-l1-passes.csv of 010 and 007].
open The walk rate on the 32 MiB stimulus differs 129 times between two processes of one boot (D: 0.003 against 0.438 walks per load). Insufficient data: the same chain in several walk-counted processes of one boot would show whether the rate is the process's placement [latency-dram-tlb-cpu2.csv, latency-dram-walk-cpu2.csv of 008].
open The G8 read fits fail the 2 % residual rule (residuals 2.1 to 5.4 %), so no single per-pass cost exists for reads. More sizes between 4 and 24 KiB, or the perf columns per pass, would show the shape of the cost [bandwidth-l1-passes.csv, bandwidth-l1-asmpasses.csv of 007 and 010].
open The single-call form still keeps a per-pass cost: 9 to 14 ns on the write fits and 11.5 ns est. on the read passes (section 7.1). Only the inner loop's exit, the pointer reset and the pass count run between its passes. Whether that remainder is the core's or the program's is Insufficient data. A form with the passes written out one after another with no loop, or a per-pass cycle count from the PMU, would separate them. The CRB's V3AE (at 2.8 GHz) keeps 4.2 ns per pass in the looped form and none in the single-call form, on its read rows. The C1-Nano's call-per-pass read passes keep 32.4 ns est., 8 times more (est.), against a clock ratio of 1.4. Why is also Insufficient data [bandwidth-l1-passes.csv and bandwidth-l1-asmpasses.csv of 007 and 010, follow-up-run-plan.md, CRB check].
hypothesis The 0.6 ns at 32 MiB and 0.5 ns at 16 MiB that boot E reads above boot C are translation walks. A walk-counted 32 MiB row on E and C in one process would test it [latency-dram-large.csv of 010 and 007; section 5].
