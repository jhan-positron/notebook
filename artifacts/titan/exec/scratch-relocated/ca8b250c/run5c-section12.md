## 12. Run 5c additions (2026-11-04 evening, after Bill's point 7 on the one-core L1 read)

**Short version.** Run 3's 16 KiB one-core read reads 58.1 GB/s, 91 % of the C1-Nano's load-pipe limit of 64 GB/s (two 128-bit load pipes, 32 B per cycle, at the 2.0 GHz the emulator models). The missing 9 % is most likely the bandwidth program's cost at every pass boundary, not the L1, and no row can prove it because 16 KiB is the only size inside the L1 that run 3 measured. Run 5c adds sixteen one-core rows at 4, 8, 16 and 24 KiB in two forms, so the per-pass cost and the L1 rate without it are both measured. Sixteen commands, 0.24 s est., almost all of it launch time.

**Words used here.** Pass: one walk of the kernel over the whole buffer. Pass boundary: the loop exit, the return from the kernel, the C loop's next iteration, the call into the kernel and the pipeline refill at the start of the next pass. Per-pass form: the program as it is, one kernel call per pass, timed around all passes of a rep [bandwidth.c, the `for (p ...)` loop in `worker`]. `--asm-passes` form: the new option, all passes of a rep inside one assembly call, so a rep has one call, one loop exit and one return.

**The arithmetic (run 3 and boot A).** A 16 KiB pass is 64 iterations of 16 paired 128-bit loads, 512 cycles at 32 B per cycle. The run 3 row reads 281.9 ns per pass, 564 cycles at 2.0 GHz, 52 cycles over [run 3 bandwidth-dram-1core.csv]. Boot A's G5 write rows at 16, 48, 96 and 256 KiB fit a straight line, time per pass = fixed cost + bytes / rate: fixed 30.4 ns (61 cycles) with run 3's program and 21.0 ns (42 cycles) with run 2's, both at 32.0 GB/s asymptotic (est., least squares over four points) [boot A bandwidth-write-small.csv, bandwidth-write-small-r2prog.csv]. If the read pass carries a similar fixed cost of about 26 ns, the loop body of the 16 KiB read row runs at 64.0 GB/s est., the pipe limit. The CRB's V3AE pays 9 cycles per 32 KiB pass on the same structure (692 measured against 683 ideal cycles at 48 B per cycle) [crb/data-all.json, asmread 32 KiB, 132.67 GB/s]: an out-of-order core overlaps the boundary with loads in flight; the C1-Nano is in-order [refs/AArch64SchedC1Nano.td lines 24 to 25] and pays it in full. Hypothesis H8: the per-pass cost on the C1-Nano is about 50 cycles for read and about 40 to 60 for write, independent of size, and the L1 read rate without it is 32 B per cycle.

**Goal G-j.** The per-pass cost of the bandwidth program on the C1-Nano, for read and write, and the one-core L1 read and write rate with that cost removed. Success: the four per-pass rows of a kernel fit a line with a residual under 2 % of the smallest pass time, the intercept is the per-pass cost, and the `--asm-passes` rows read within 2 % of the slope's rate. If the `--asm-passes` read rows read 64 GB/s within 2 %, the 16 KiB row's 91 % is the program and the page can say the L1 serves 32 B per cycle. If they read 58 GB/s as before, the boundary is not the cause and H8 is refuted; the L1 then holds a limit of its own, and the TRM's L1 bandwidth is the next source to read.

**Changes.** bandwidth.c: `--asm-passes` (read and write only, one segment, no CME form; the kernels `k_read_n` and `k_write_n` are the `k_read` and `k_write` bodies as an inner loop under an outer loop that resets the pointer and counts the passes down); `pass_asm` runs it once per rep in `worker` where the C pass loop ran; the header line gains `asm_passes=0|1`; host stand-ins loop over `k_read` / `k_write`. The default form, the other kernels, the CME path and the counters are unchanged, so every existing row is the same program as before. One difference between the forms on the write side: the default form adds the pass index to the stored value at each pass, the `--asm-passes` form stores one value for the whole rep; the read rows, which carry the question, have no such difference. run_followup.sh: phase G8 after G7: for 4K:1024, 8K:512, 16K:256, 24K:176 passes, kernels read and write, the per-pass command into `bandwidth-l1-passes.csv` and the `--asm-passes` command into `bandwidth-l1-asmpasses.csv`, each `--perf`; `--quick` runs the 4 KiB rows only. README.md: the option in the bandwidth table and paragraph, G8 in the run_followup.sh row.

**Reading the rows.** Time per pass = elapsed_s / passes. Per kernel, fit the four per-pass rows (intercept = per-pass cost, slope = bytes per second without it); report the fit's residual. The `--asm-passes` rows are read as rates directly; their one remaining boundary per rep is one part in 176 to 1024 of the pass count, under 0.1 % at the C1-Nano's cost, so no correction is applied. `--perf` on every row: l1d_refill_per_line near 0 (below 0.01) shows the buffer stayed in the L1; a row above that is reported as not an L1 row. 24 KiB is the largest size used: the L1 is 32 KiB 4-way, and a 32 KiB buffer would share its sets with the stack and the harness's own lines. The write rows also measure the pass boundary on the store side, which boot A's G5 measured with the per-pass form only.

**Which boots.** Any boot on the run 5c commit. The rows are L1-resident and do not depend on the prefetcher state or the OCM mapping, so one boot is enough; the first boot built from the commit (D or C if Jesse can rebuild, else none of the run 4 boots) carries them. B stays on 7921962. If no rebuild fits, the rows wait for the next run.

**What stays open.** The rows measure the program's cost and the L1's rate; they do not say which part of the boundary costs what (loop exit, return, call, refill). A row with the per-pass form at 4 KiB (16 iterations per pass) against 24 KiB (96) bounds it as one number per pass. The CRB numbers above are from a non-isolated core with 3 to 5 reps and up to 20 % rep spread; only the best reps are quoted, and the C1-Nano rows run on isolated CPU 2.
