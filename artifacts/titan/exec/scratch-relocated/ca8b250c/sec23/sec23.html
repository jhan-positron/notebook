2.3 Boot F1 against run 3: what differed, what moved, and the hypotheses

Short version. Boot F1 ran run 3's 67 core command lines in run 3's order, on boot E's firmware, where the one platform change that matters is the L3 of CPUs 2 to 9 in full mode. Every stream of independent reads got faster (1.2 to 2.9 times), while the dependent chains beyond the L3 (within 4 %), the one-core writes, the writer-placement rows and the controls (within 0.3 %) repeated run 3. The counters show the same number of refills per line and the same number of mesh requests per command, so the reads overlap more of their time rather than skipping the mesh, and the mechanism is a hypothesis with a test, not a measurement.

  • What the counters say about the L3-sized chains. At 192 to 384 KiB the L2 refills per load are the same on both boots (0.58 to 1.11 on run 3, 0.58 to 1.10 on F1), and the L3 read refills from outside the cluster (event 0xA2: a line that the L3 had to fetch from the mesh) fall from 0.46 to 0.94 per load to 0.00 to 0.03. So the L2's misses are served inside the cluster on F1. That is the L3 holding the chain, a measurement [latency-dram-small.csv of 011 and 004].
  • What the counters say about the read streams. Boot E against boot C (one build, the L3 the one change) read 2.68 times at 2 MiB and 2.67 at 32 MiB with the same refills per line (32 MiB: L1 1.00 and 1.00, L2 1.00 and 1.00, L2 refills caused by the L1 prefetcher 1.00 and 1.00, L3 read refills 0.0000 and 0.0004). On F1 the counted 2 MiB read put 0.975 times run 3's requests on the five home nodes while the command lived 0.648 times as long. So the L3 did not take these reads off the mesh: the same lines were fetched, by the same number of requests, in less time [bandwidth-read-prefetch.csv of 010 and 007; cmn-counts.csv of 011 and 004].
  • What the counters say about the OCM rows. The sparse OCM passes count 0.71 0xA2 refills per load on run 3 and 0.42 on F1 (means over the 140 passes of each boot), with the same L2 refills (2.78 and 2.80). So on F1 part of the OCM lines came from the L3, not from the region's home node. OCM is Normal write-back memory, so the L3 may hold its lines [latency-ocm-region<r>-cpu<c>.csv of 011 and 004].
  • What the multi-core rows add. Four readers on four clusters each keep 100 to 100 % of F1's one-core rate at 16 MiB (24.5 to 24.6 GB/s against 24.6), so four clusters do not share the limit. Eight readers, two per cluster, read 107.6 GB/s together, 13.4 each, so two readers in one cluster share about 27 GB/s est. per cluster, near one reader's rate [bandwidth-perdsu.csv, bandwidth-all8.csv of 011].
  • Hypotheses. Each one names what supports it, what it has to explain, and the measurement that would confirm or reject it.
  • hypothesis More reads in flight per cluster. With the L3 in full mode the cluster's miss handling goes through the L3 (the snoop-filter-only mode of run 3 passes every L2 miss to the mesh without an L3 lookup). If that path keeps more read requests open at once (in flight: issued and not yet returned), a stream of independent reads overlaps more of its DRAM time, while a chain of dependent loads has one load open and gains nothing, and a store stream is posted (the core does not wait for a store) and already overlaps. Fits: the same refills per line, the same mesh requests, chains beyond the L3 within 4 %, the one-core writes and the placement rows within 0.3 % (the multi-core writes of 2 MiB and above within 7 %), and the per-cluster limit the eight-reader row shows. The test: a count of the requests in flight at the DSU's mesh port around the same one-core read on an L3-on and an L3-off boot, if the mesh PMU offers such an event (to be checked in the CMN-S3 event list). The data on disk do not count requests in flight.
  • hypothesis The prefetcher's requests are the ones that overlap more. The L2 refills caused by the L1 prefetcher are 1.00 per line on E and 1.00 on C, so the prefetcher issues the same number of requests per line on both; the counters do not say how many it keeps open at once. With the prefetchers off and the L3 off, boots B and D read 2.38 and 2.38 GB/s at 32 MiB, one line per DRAM latency. The test: run 3's one-core read lines with the prefetchers off on an L3-on boot (boot F2's firmware, which ran run_cme.sh only). A rate near 2.4 GB/s would say the rise needs the prefetcher; a rate above it would say the L3 path overlaps demand misses on its own.
  • hypothesis A per-cluster limit, not a per-core one. Four readers on four clusters scale one for one with one reader, and eight readers (two per cluster) get 27 GB/s est. per cluster. The test: two readers on two clusters against two readers in one cluster at 16 MiB, the same command otherwise; the pair row at 160 KiB (33.7 GB/s on F1 against 21.2 on run 3) is the nearest row on disk and sits in the L2 and L3, not DRAM.
  • ruled out The build. k_read, k_write and k_copy are byte for byte the same in both builds, and boot E against boot C, one build, shows the read rise (2.68 and 2.67 times) with the L3 as the one change. What the build may have moved: the 16 KiB rows, whose buffers fit the L1 (one core read 0.965 times, write 1.016, the pair read 0.966); run 3's README tied its own 16 KiB write shift to a rebuilt bandwidth, and pass differs again. Insufficient data: these files do not show why the 16 KiB rows moved [Jesse's F1 README, Core rows against round three; Jesse's run 3 README].
  • ruled out Boards or run-to-run noise. The controls repeat within 0.3 %, the writes from 48 KiB on within 0.3 %, the chains from 1.5 MiB on within 3.8 %, and the reps of the one-core read rows spread 1.8 % or less inside each boot. Boot E and boot C ran on other boards and show the same ratio.
  • partly Page placement on the OCM rows. The /dev/ocm module differs and every process draws its own pages, so a single sparse cell (0.69 to 0.95 times) is within its own spread (up to 60 % between passes of one row). What placement cannot explain: all 20 cells faster, and the 0xA2 fall with the same L2 refills, which says the L3 served part of the loads. The test: the sparse rows with the L3 hit event (the hit set of boot E, section 5) on an L3-on boot.
