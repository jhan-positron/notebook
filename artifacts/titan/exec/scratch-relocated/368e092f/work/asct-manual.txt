# Arm System Characterization Tool 
The Arm System Characterization Tool (ASCT) is a standalone command-line utility for running low-level benchmarks, diagnostic scripts, and system tests to analyze and debug performance on Arm-based platforms. 
ASCT provides a standardized environment for evaluating key hardware characteristics, such as memory latency and bandwidth, and is especially suited for platform bring-up, system tuning, and architectural comparison tasks. It helps developers and system architects gain early and repeatable insights into performance-critical subsystems. 
Current capabilities include: 

- 
System report. Generate a structured inventory of CPU, caches, NUMA topology, operating system, kernel, and tooling state. You can also generate Arm Coherent Mesh Network (CMN) and network topology and configuration reports on demand. For more information, see System report. 
- 
Memory latency and bandwidth benchmarks. Measure how latency and bandwidth change across cache levels and DRAM. Characterize NUMA effects, including idle latency, loaded latency, core-to-core latency, and peak bandwidth. For more information, see Memory characterization. 
- 
Storage latency and bandwidth benchmarks. Run controlled fio-based parameter sweeps. Vary request size, queue depth, process count, and access pattern. Measure bandwidth, IOPS, latency, and CPU utilization under input and output load. For more information, see Storage characterization. 
- 
System diff. Compare one or more ASCT run output directories. Highlight configuration differences and benchmark differences. Generate CSV and JSON output, plots for supported benchmarks, and grouped register differences for CMN reports. For more information, see Compare run results.  
Planned features include: 

- 
Hardware register inspection and configuration for debug and bring-up use 
- 
Locking and synchronization stress tests 
- 
Floating-point compute performance measurement in FLOPS

# Install ASCT 
You can run ASCT from a standalone package or install it from the source distribution on supported Linux platforms. 

## Choose an installation option 
Choose an installation option according to whether you want a self-contained package or want to manage the Python environment yourself. 

- 
Option 1: Source distribution with the helper script. This is the recommended option for this release. The script creates a Python virtual environment and installs ASCT into it. 
- 
Option 2: Source distribution with pip. Install ASCT manually into a new or existing Python environment. 
- 
Option 3: Source distribution with uv. Install ASCT as a system-wide tool that is available on the system PATH. 
- 
Option 4: Standalone package. Extract the package and run ASCT directly. You do not need to install Python, Python packages, or build tools. This option is particularly suitable for an offline target system.  
Options 1, 2, and 3 use the same source release bundle and require Python and build tools on the target system. 

## Install from the source distribution 
Use the source distribution when you want to manage the Python environment or provide a system-wide installation. 

### Requirements 
All source-installation options require: 

- A supported Linux operating system 
- gcc 
- make  
Options 1 and 2 also require: 

- Python 3.10 or later 
- pip  
The source release bundle does not contain a Python runtime or all required dependencies. The target system must be able to obtain the dependencies, or you must provide them locally before installing offline. 
Option 3 does not require pip. uv creates an isolated environment and uses a compatible installed Python interpreter or downloads one automatically. This option also requires: 

- uv. For installation instructions, see Installing uv. 
- Root privileges 
- Permission to create /opt/uv/tools and /usr/local/bin  

### Download the source release bundle 

- 
On a system with network access, go to ASCT distributions and open the directory for your ASCT release. 
For users within the Arm network, early-access versions might be available at artifacts.internal.tools.arm.com. 
- 
Download the source release bundle and its checksum file. The checksum file has the same name as the bundle with .sha256 appended. 
- 
Verify the downloaded bundle: 
```
sha256sum --check <source-release-bundle-name>.tar.gz.sha256
```

- 
Copy the bundle and checksum file to the target system. 
- 
On the target system, verify the bundle again: 
```
sha256sum --check <source-release-bundle-name>.tar.gz.sha256
```

- 
Extract the source release bundle: 
```
tar -xzf <source-release-bundle-name>.tar.gz
```

- 
Change to the extracted directory: 
```
cd asct-<version>
```

## Option 1: Use the helper script 
The helper script creates a Python virtual environment and installs ASCT from the source distribution in the release bundle. 

### Procedure 

- 
Run the helper script: 
```
./install.sh --install-dir /path/to/install/directory
```

If --install-dir is not specified, the script installs into the directory containing install.sh. 
The installer uses python3 by default and requires Python 3.10 or later. If your supported Python is installed under another command, use --python with its command name or absolute path: 
```
./install.sh --python /usr/bin/python3.12 --install-dir /path/to/install/directory
```

If the selected interpreter is unavailable or unsupported, the script exits without trying another Python. 
The install.sh script performs the following tasks: 

- Creates a Python virtual environment 
- Installs ASCT from the source archive in the release bundle 
- Checks for numactl, fio, mpstat, and iperf3. If a suitable system tool is unavailable, it attempts to build one into the virtual environment.  
An optional tool build failure is reported as a warning and does not prevent ASCT from installing. Local builds use the directory containing install.sh for temporary source files, so that directory must be writable when a build is needed. The installer does not modify system packages. 
By default, the virtual environment is created at <install-dir>/asct_venv. 
After installation, follow the instructions printed by the script to activate the virtual environment before running ASCT. 

## Option 2: Use pip 
Manual installation with pip lets you install ASCT into a new or existing Python environment. 

### Install into a new virtual environment 

- 
Create a virtual environment: 
```
python3 -m venv asct_venv
```

- 
Activate it: 
```
source asct_venv/bin/activate
```

- 
Install ASCT from the bundled source distribution: 
```
python3 -m pip install ./asct-<version>.tar.gz
```

ASCT is now installed inside the virtual environment.  

### Install into an existing environment 
```
python3 -m pip install ./asct-<version>.tar.gz
```

ASCT is installed into the currently active Python environment. 

## Option 3: Use uv 
System-wide installation with uv makes ASCT available on the system PATH. 
Run the following commands as root. 

### Procedure 

- 
Create the required directories: 
```
mkdir -p /opt/uv/tools /usr/local/bin
```

- 
Install ASCT with uv and place the executable in /usr/local/bin: 
```
UV_TOOL_DIR=/opt/uv/tools UV_TOOL_BIN_DIR=/usr/local/bin uv tool install ./asct-<version>.tar.gz
```

After installation, ASCT is available on the system PATH.  

## Option 4: Use the standalone package 
The standalone package contains ASCT, a Python runtime, Python dependencies, native benchmark binaries, licenses, and offline HTML documentation. 

### Requirements 
The target system must meet these requirements: 

- A supported Linux operating system 
- One of the following architectures: 

- An x86 64-bit system. To confirm, run uname -m. The command must return x86_64. 
- An Arm 64-bit system. To confirm, run uname -m. The command must return aarch64 or arm64.  
- glibc 2.31 or later. To check the installed version, run ldd --version.  
You need network access only on the system that downloads the package. The target system can remain offline. 
Note: The standalone package does not include workload-specific Linux tools such as numactl, fio, and mpstat. If the target system will remain offline, install the required runtime tools before disconnecting it from the network. 

### Procedure 

- 
On a system with network access, go to ASCT distributions and open the directory for your ASCT release. Standalone packages are available for version 0.7.0 and later. 
For users within the Arm network, early-access versions might be available at artifacts.internal.tools.arm.com. 
- 
Download the standalone package for the target architecture and its checksum file. The checksum file has the same name as the package with .sha256 appended. 
- 
Verify the downloaded package: 
```
sha256sum --check <standalone-package-name>.tar.gz.sha256
```

- 
Copy the package and checksum file to the target system. 
- 
On the target system, verify the package again: 
```
sha256sum --check <standalone-package-name>.tar.gz.sha256
```

- 
Extract the standalone package: 
```
tar -xzf <standalone-package-name>.tar.gz
```

- 
Change to the extracted directory: 
```
cd <standalone-package-name>
```

- 
Verify that ASCT starts: 
```
./asct help
```

Run ASCT from the extracted directory or add that directory to your PATH. You do not need to activate a Python environment. 
To read the bundled documentation without network access, open asct_docs/index.html in a web browser. 

## Runtime tools 
Installation requirements and runtime requirements are separate. Some workloads require additional system tools, such as: 

- numactl 
- fio 3.36 or later 
- mpstat  
If tools are missing, ASCT reports this at runtime. 
Note: Some benchmarks require root privileges to configure huge pages and access certain system information. You can run ASCT without root privileges, but some benchmarks might be unavailable or have limited functionality. 

## Run ASCT 
Run the executable for your installation method. 

- For a standalone package, run ./asct from the extracted directory or add that directory to your PATH. 
- For a virtual environment, activate the environment before you run asct. 
- For a system-wide uv installation, run asct without activating an environment.  
To verify a standalone package, run: 
```
./asct help
```

To verify a source installation, run: 
```
asct help
```

For a standalone package or source release bundle, you can open the offline documentation at asct_docs/index.html.

```

### Option 2: If you manually installed ASCT using pip 
If you installed ASCT into a dedicated virtual environment, you can remove that environment directory. 
Alternatively, activate the relevant Python environment and uninstall ASCT:

python3 -m pip uninstall asct
```

### Option 3: If you installed ASCT system-wide using uv

```
UV_TOOL_DIR=/opt/uv/tools UV_TOOL_BIN_DIR=/usr/local/bin uv tool uninstall asct
```

### Option 4: If you use the standalone package 
Remove the extracted standalone package directory. The standalone package does not install files outside that directory.  

# Getting started 
You can run ASCT with several commands that follow this pattern: 
```
asct [command] [arguments]
```

[!IMPORTANT] Some operations require root privileges to access certain system information or change the huge-page allocation. Run ASCT as root for these operations. 
For a standalone package, ensure that the root user’s PATH includes the extracted package directory, or run ./asct from that directory. For a virtual-environment installation, activate the virtual environment as root before running ASCT. 
Command examples use asct. If you use a standalone package without adding its directory to your PATH, use ./asct instead. Run commands that require root privileges from a root shell.  

  | Command  | Description  | More information    
  | asct config check  | Verifies a benchmark user configuration file  | See asct config command  
  | asct config save  | Writes a benchmark user configuration file  | See asct config command  
  | asct diff  | Compares results from previous ASCT runs  | See Compare run results  
  | asct help [command]  | Displays the general help page or help for a specific command  | Run asct help  
  | asct list  | Lists available benchmarks and benchmark keywords  | See asct list command  
  | asct report cmn  | Collects information about the Arm Coherent Mesh Network (CMN) interconnect when it is present on your system  | See System report  
  | asct report network-info  | Collects network interface, address, namespace, and tuning information  | See System report  
  | asct report system-info  | Displays system information and exits. ASCT also includes this information by default with every benchmark run.  | See System report  
  | asct resume  | Resumes a partially completed benchmark run from an existing output directory  | See Saved results  
  | asct run <keyword>  | Runs benchmarks selected by benchmark name, short name, or keyword  | See asct run command  
  | asct version>  | Displays the ASCT version  | Run asct version  
  | asct view>  | Views results from a previous ASCT run without rerunning benchmarks  | See Saved results    
For more information on a specific command, run: 
```
asct [command] --help
```

To display the ASCT version, run: 
```
asct version
```

To get started, run the default set of benchmarks: 
```
asct run
```

### asct run command 
The asct run command runs one or more benchmarks. 

#### Default behavior 
```
asct run
```

Running the asct run command with no arguments executes a default set of benchmarks and displays the results in the terminal. 
The default set does not include storage benchmarks. To run storage benchmarking, select storage benchmarks explicitly, for example with the storage keyword or specific storage sweep names. 
Each time you run asct run, ASCT collects system information and includes it with the benchmark results. ASCT also saves detailed output in a directory under the current working directory. 
The output can include data in multiple formats, such as CSV and JSON. Some benchmarks also generate additional artifacts, such as plots or raw data dumps. 
By default, ASCT creates an output directory named: data.<YYYYMMDD_HHMMSS_microseconds>. 
You can change the output location using the --output-dir flag.  
[!IMPORTANT] ASCT saves run metadata and completed benchmark results in the output directory. This saved data lets you view previous results with asct view and resume interrupted runs with asct resume.  

#### Select benchmarks 
To run all available benchmarks: 
```
asct run all
```

To run specific benchmarks, pass a list of benchmark names as arguments to the asct run command. 
For example, to run the latency-sweep and idle-latency benchmarks: 
```
asct run latency-sweep idle-latency
```

Alternatively, each benchmark also has associated keywords that you can use to select multiple benchmarks that match those keywords. 
For example, to run all benchmarks tagged with the memory keyword: 
```
asct run memory
```

To run all benchmarks tagged with the storage keyword: 
```
asct run storage
```

You can exclude benchmarks by prefixing the name or keyword with a caret (^). 
For example, to run all benchmarks but exclude all of those tagged with the bandwidth keyword: 
```
asct run all ^bandwidth
```

[!NOTE] If a benchmark is a dependency for running another benchmark, excluding it has no effect. For example, if you use ^latency-sweep to exclude the latency-sweep benchmark, but another benchmark depends on latency-sweep, the latency-sweep benchmark still runs.  
To view the list of available benchmarks and their keywords, run the following command: 
```
asct list
```

#### Output options 
The run command also supports the following arguments: 

- --format, -f [stdout, csv, json] 

- 
Specify the output format, either to the terminal with stdout (default), individual CSV files (benchmark-name.csv), or a single combined JSON file (report.json) 
For example: asct run idle-latency --format=json  
- --log-level, -L [debug,info,warning,error,critical] 

- Set the verbosity level (info by default).  
- --log-file LOG_FILE 

- Specify the output file for logs, based on the --log-level setting. ASCT writes logs to this file and also prints them to standard error stderr. 
- If no log messages are generated, ASCT does not create the log file.  
- --output-dir, -o OUTPUT_DIR 

- Set the directory for output files. By default, ASCT saves output files in a directory named data.<YYYYMMDD_HHMMSS_microseconds> in the current working directory. Use this flag to specify a different directory. You can specify an absolute or a relative path.  
- --force 

- When the output directory specified by --output-dir already exists, ASCT displays an error and quits to avoid overwriting data. Use the --force flag to overwrite the output directory if it exists.  
- --quiet, -q 

- Disable all output to stdout and stderr, including critical errors and log messages. Use --log-file to capture and view logs.  
- --no-progress-bar 

- Disable the animated progress bar. Single-line update messages display instead.   

### asct list command 
Run the following command to get the list of available benchmarks and their associated keywords: 
```
asct list
```

### asct config command 
The asct config command writes or verifies benchmark user configuration files. 

#### Save a configuration file 
Use asct config save to generate a JSON configuration file from ASCT defaults. 
```
asct config save --config-file my-config.json
```

If no file is specified, ASCT writes to config.json in the current directory. 
You can limit output to selected benchmarks or report types by passing filters. 
```
asct config save latency --config-file latency.json
```

You can override selected values while generating the file. 
```
asct config save latency --config-file latency.json --update-config loaded-latency.duration=15
```

If the output file already exists, use --force to overwrite it. 
```
asct config save --config-file my-config.json --force
```

#### Check a configuration file 
Use asct config check to validate a user configuration file. 
```
asct config check --config-file my-config.json
```

If no file is specified, ASCT checks config.json. 

#### Save command options 

- 
filter 
Optional list of benchmark or report filters to include in the generated file. 
- 
--config-file 
Output path for save and input path for check (default: config.json). 
- 
--update-config 
One or more setting overrides in key=value format. 
- 
--force 
Overwrite an existing output file when using save.   

# System report 
This section describes the system reporting commands in ASCT. Use these commands to view hardware, software, and platform configuration details. 
ASCT collects system information each time you run asct run. Arm Coherent Mesh Network (CMN) and network reporting are available as separate commands. 
Use these commands: 

- asct report system-info: View hardware and operating system information 
- asct report cmn: View CMN topology and configuration when present 
- asct report network-info: View network interfaces, addresses, namespaces, and tuning settings  

## View system information 
Use the asct report system-info command to generate a report that summarizes the hardware and software configuration of the system. 
The report captures CPU, memory, interconnect, operating system, and related platform characteristics. Use this information to understand the benchmark environment and interpret performance results. 

### What asct report system-info collects 
The asct report system-info report provides a structured snapshot of your system. It includes the following information: 

- CPU architecture, core count, and CPU model 
- Cache hierarchy and cache line size 
- NUMA topology 
- Interconnect identification 
- Memory capacity and theoretical peak bandwidth 
- Memory module details, including manufacturer and part number when available through DMI 
- Operating system and kernel details 
- Performance tooling and kernel feature checks 
- Vulnerability status from kernel reporting  

### Run asct report system-info 
Run this command: 

```
asct report system-info
```

If you run the command without root privileges, ASCT collects only a limited set of information. ASCT cannot access Desktop Management Interface (DMI) platform and memory details without root privileges. 

### Use asct report system-info options 
asct report system-info supports the common ASCT output and logging options. 
Example: 

```
asct report system-info --format=json --output-dir data --force --log-level=error --log-file data/asct.log --quiet
```

### View asct report system-info output 
ASCT supports these output formats: 

- --format=stdout (default): Prints the report to the terminal 
- --format=csv: Writes a key-value CSV to the output directory 
- --format=json: Writes a combined JSON file to the output directory

- system-info.csv 
- report.json

### What asct report cmn collects 
Use asct report cmn to collect information about the CMN interconnect when it is present on your system. asct report cmn requires root access to gather CMN information. 
Depending on the options that you select, the output includes:

## View network information 
Use the asct report network-info command to inspect network configuration and tuning settings. 
The command shows local host addresses and per-interface network details. Use --verbose to also show network namespace details and additional performance-related settings when they are available. Use this information to analyze connectivity and network configuration. 

### What asct report network-info collects 
Use asct report network-info to report networking configuration. It includes the following information: 

- Local IPv4 and IPv6 addresses 
- Host aliases and hostnames, when available 
- Interface details such as MAC address, link state, current and maximum supported speeds when available, MTU, and device type 
- Per-interface IPv4 and IPv6 addresses 
- Network namespace details and per-namespace interfaces, when available 
- Network socket-buffer, TCP, UDP, and network-namespace system settings, including the active and available TCP congestion-control algorithms 
- Driver, interrupt-coalescing, and pause-frame settings for non-virtual network interface controllers (NICs)  
ASCT uses ethtool to collect NIC-specific settings. If ethtool is unavailable or a NIC does not support a query, the corresponding settings are omitted. Values that ethtool reports as n/a are also omitted. 

### Run asct report network-info 
Run this command: 

```
asct report network-info
```

You can run this command without root privileges. When you use --verbose, some namespace details might be unavailable without root privileges. 
By default, terminal output includes selected system-wide settings and settings for the NIC that provides the default route. Use --verbose to show network namespace details, all collected network system settings, and available settings for every non-virtual NIC: 

```
asct report network-info --verbose
```

The --verbose option changes terminal output only. ASCT includes all collected network tuning and namespace data in CSV and JSON output, whether or not you use --verbose. 

### View asct report network-info output 
ASCT supports these output formats: 

- --format=stdout (default): Prints the report to the terminal 
- --format=csv: Writes a key-value CSV to the output directory 
- --format=json: Writes a combined JSON file to the output directory

# Memory characterization 
ASCT includes benchmarks that measure memory latency and bandwidth. 

## Memory benchmark output units 
You can choose whether supported memory benchmarks report results using cycle-based or time-based units. 
Set cycle_base with --update-config to choose the output units: 

- cycle_base=true uses cycle-based latency and bandwidth units such as cycle and B/cycle. 
- cycle_base=false uses time-based and throughput units such as ns and GB/s.  
The following example runs selected benchmarks and sets cycle_base to true for each selected benchmark: 

```
asct run latency-sweep bandwidth-sweep loaded-latency --output-dir runA \
        --update-config latency-sweep.cycle_base=true \
        --update-config bandwidth-sweep.cycle_base=true \
        --update-config loaded-latency.cycle_base=true
```

## Huge-page requirements for runs without root privileges 
You can run memory benchmarks without root privileges when the system has enough free preallocated huge pages. 
The idle-latency and loaded-latency benchmarks request huge-page memory on each NUMA node that they use. For each node, the requested amount is the greater of 1 GiB and 12 times the size of that node’s last-level cache (LLC). 
The latency-sweep benchmark requests huge-page memory on each NUMA node. It sets its maximum sweep data size to the larger of 1 GiB and 12 times the largest detected cache size, capped by the memory per logical CPU of the most constrained NUMA node. If you override a cache-level measurement size above that maximum, the benchmark uses the override to determine its memory request. It rounds the resulting allocation up to a whole number of 1 GiB pages. 
The bandwidth-sweep, cross-numa-bandwidth, peak-bandwidth, and c2c-latency benchmarks depend on latency-sweep. On a fresh run, this dependency introduces the latency-sweep huge-page requirement. When ASCT reuses cached latency-sweep results instead of running the dependency, the dependency does not require additional huge pages. 
When you run ASCT as root, it allocates the requested huge pages temporarily. After the run, the tool restores the original huge-page allocation. 
When you run ASCT without elevated privileges, it does not change the system huge-page allocation. It uses free huge pages that an administrator has preallocated. The tool first looks for enough free 1 GiB huge pages to satisfy the request. If there are not enough 1 GiB pages, it can use an equivalent amount of free memory from a smaller supported huge-page size. 
Before you run a benchmark without root privileges: 

- 
Check which NUMA nodes the system provides: 
```
ls -d /sys/devices/system/node/node[0-9]*
```

- 
Ask an administrator to ensure that each NUMA node used by the benchmark has enough free preallocated huge-page memory. For idle-latency and loaded-latency, provide the greater of 1 GiB and 12 times the size of that node’s last-level cache (LLC). For latency-sweep, provide the larger of its calculated maximum sweep size and any cache-level measurement size overrides, rounded up to whole 1 GiB pages. If 1 GiB pages are unavailable, an equivalent allocation can use a smaller supported page size. For example, 512 free 2 MiB pages provide 1 GiB of huge-page memory. The following command shows the number of free huge pages for each supported size on each node: 
```
grep -H . /sys/devices/system/node/node*/hugepages/hugepages-*kB/free_hugepages
```

- 
Run the benchmark without root privileges. For example: 
```
asct run latency-sweep
```

If there are not enough free huge pages on a required NUMA node, ASCT skips the affected benchmark and reports which allocation is missing. Preallocated huge pages remain allocated after the run. 

## Latency 
The following latency benchmarks are available: 

- Latency sweep 
- Idle latency 
- Loaded latency 
- Core-to-core latency  

### Latency sweep 

- 
Use this benchmark to measure memory latency across data sizes, starting at 128 bytes. The calculated maximum data size is at least 1 GiB and increases when 12 times the largest detected cache size is greater than 1 GiB. It is capped by the memory per logical CPU of the most constrained NUMA node. 
- 
The results show how memory access latency changes across cache levels and dynamic random-access memory (DRAM). These changes indicate transitions in the cache hierarchy. 
- 
Randomized linked lists prevent hardware prefetching from influencing the latency measurements. 
- 
The benchmark uses one or more 1 GiB huge pages on each NUMA node. It allocates enough pages to cover the maximum sweep data size or the largest cache-level measurement size override, whichever is greater. Using huge pages reduces the effect of page table walks and translation lookaside buffer lookups on latency measurements. Note that on some systems, huge pages are referred to as large pages. 
- 
The benchmark calculates: 

- 
Lower and upper bounds for each cache level 
- 
Average latencies 
- 
The optimal data size for L1, L2, last-level cache (LLC), and DRAM. The benchmark selects a data size 90% of the way between the detected lower and upper bounds.   
To measure at a specific size for a cache level, set l1_size, l2_size, llc_size, or dram_size with --update-config. You can pass multiple settings after a single --update-config flag. For example: 

```
asct run latency-sweep \
        --update-config latency-sweep.l2_size=512KiB \
                        latency-sweep.dram_size=2GiB
```

The sweep still calculates the optimum from the detected bounds. Its Optimum Datasize column shows that calculated size. When you set any override, the output adds a User override column, and the reported latency for an overridden level comes from measuring at the override size. Dependent benchmarks use the measured size for that level unless you set their own data_size. 
```
    Latencies at different levels of cache
    --------------------------------------
    Level Lower bound Upper bound Optimum data size Latency [ns]
    L1           128         64K         57.6123K          1.5
    L2           64K        512K         467.199K          5.2
    LLC           1M          8M             7.3M         48.1
    DRAM         32M          1G           924.8M        107.6
```

The plot includes the following information: 

- 
cache-size markers and labels such as L1, L2, and LLC

Latency stays low (~1.3 ns) up to 32 KiB, then increases in steps at cache and DRAM transition points.

### Core-to-core latency 

- 
Use this benchmark to measure the latency of cache line transfers between pairs of CPU cores across the system. 
- 
By default, the benchmark uses the L2 measurement size from latency-sweep. To choose a different size for this benchmark, set data_size, for example: 

```

```

- 
The benchmark uses a ping-pong microbenchmark that alternates shared memory access and modification between 2 threads pinned to different cores. 
- 
The shared memory region is a randomized linked list. The benchmark pointer-chases this list so that each memory access depends on the result of the previous one. This approach prevents hardware prefetchers from interfering with results. 
- 
The benchmark binds the memory region to a specific NUMA node. This approach enables you to measure core-to-core latency both locally on the same node and remotely across nodes. This distinction helps you understand the impact of NUMA topology on inter-core communication.

-

-

- 
Asymmetry in latency between different directions, for example A to B versus B to A.

#### Ping-pong microbenchmark 

- 
Use this benchmark to measure latency between 2 CPU cores by forcing cache line transfers between them. 
- 
The benchmark pins 2 threads on the target cores. 
- 
Each thread alternates between accessing and modifying the shared data structure. During its turn, a thread performs a complete pointer chase on the structure. 
- 
The benchmark uses cache invalidation and data dependency chains to estimate latency. 
- 
When one thread writes to the shared data structure, the corresponding cache line in the other core is evicted.    A diagram titled Inter-Core Ping-Pong Synchronization showing communication between two threads on separate CPUs. Thread A on CPU_1 waits for a spin signal from Thread B on CPU_2, then follows a pointer chain with a write operation, and finally signals Thread B to proceed. A note below explains that threads A and B alternate modifying and reading cache lines, with writes on one causing cache invalidation on the other.  

#### NUMA and memory binding 

- The benchmark distinguishes between local and remote cache line transfers by binding the memory region to a specific NUMA node. Local transfers, where the cores and memory are on the same node, typically show lower latency. Remote transfers, where the cores and memory are on different nodes, show the cost of traversing the NUMA interconnect.

# Storage characterization 
This section describes the storage benchmarks in ASCT. These tests evaluate the performance characteristics of block devices and filesystems using fio under controlled sweep parameters. 

## What ASCT storage benchmarking measures 
ASCT evaluates storage performance by sweeping parameters and measuring their impact on input/output (I/O) performance. 

- Sustained bandwidth 
- Input/Output Operations Per Second (IOPS) and latency 
- Host CPU utilization during I/O  
CPU utilization is reported as a breakdown of time spent in user space, kernel code, I/O wait, and hardware and software interrupt handling. This information helps identify whether performance is limited by the application, the kernel, or the storage device. 

## Sweeps included 
ASCT automates multiple types of parameter sweeps, each designed to isolate one dimension of I/O behavior: 

- Request Size Sweep (4 KiB → 128 KiB) Reveals throughput scaling as well as controller or device saturation points 
- I/O Queue Depth Sweep (QD=1 → QD=128, powers of two) Capture parallelism gains and concurrent access behavior 
- Concurrent Process Count Sweep (1 → 16 concurrent processes, powers of two) Show scaling across CPU cores 
- Access Pattern Sweep (Sequential versus random, read/write/mixed ratios, the default is 70% reads) Use this sweep to show how performance varies by workload  

## How ASCT runs parameter sweeps 
ASCT uses fio to perform controlled parameter sweeps. For each sweep, ASCT changes one parameter at a time while keeping all other parameters fixed. It then repeats the sweep for each configured parameter set. 

  | Sweep type  | Example values    
  | Request size  | 4K, 8K, 16K, 32K, 64K, 128K  
  | Queue depth  | 1, 2, 4, 8, 16, 32, 64, 128  
  | Jobs  | 1, 2, 4, 8, 16  
  | Access pattern  | seq read, seq write, rand read, rand write, seq mixed, rand mixed    
For each sweep point, ASCT records the following key metrics: 

- From fio: bandwidth, I/O rate, average latency, latency distribution 
- From mpstat: CPU utilization breakdowns (user/system/iowait/hard irq/soft irq)  

## Run storage benchmarking 
Use the run command with storage keywords and optional --update-config parameters to select a device or create a temporary file. 

```
# Run a specific sweep (in order of Request Size Sweep, I/O Depth Sweep, Concurrent Process Count Sweep, Access Pattern Sweep)
asct run storage-request-size-sweep ...
asct run storage-io-depth-sweep ...
asct run storage-process-count-sweep ...
asct run storage-access-pattern-sweep ...
```

Alternatively, use the short-form alias: 

```
# Run a specific sweep (short form in order of Request Size Sweep, I/O Depth Sweep, Concurrent Process Count Sweep, Access Pattern Sweep)
asct run srss ...
asct run sids ...
asct run spcs ...
asct run saps ...
```

ASCT requires a target device or file. CAUTION: tests might overwrite file content. 

```
# Provide a target file (ASCT will use /tmp/mytest.dat for test, user needs to create file upfront)
asct run srss --update-config srss.filenames=/tmp/mytest.dat
# Provide a target device (ASCT will use the device /dev/nvme07, user needs to ensure device exists)
asct run srss --update-config srss.filenames=/dev/nvme07
```

ASCT exposes several user overrides, including the following examples: 

- Create a temporary file for file benchmarking so that you do not need to provide the device name:  

```
# Auto-create temporary file for file I/O
asct run srss --update-config srss.create_temp_file=1
```

 
- Change the read-write mix ratio:  

```
# Change read write mix ratio for access pattern sweep to use 20% read instead of default of 70%
asct run saps --update-config saps.rwmixread=20
```

 
- Change the sweep steps:  

```
# Use linear iodepth sweep step between 4 and 8 for more details
asct run sids --update-config sids.iodepth_sweep_steps=4,5,6,7,8
```

See the ASCT help for a full list of user overrides.

# Compare run results 
Use asct diff to compare results from previous ASCT runs. Each ASCT run produces an output directory that contains benchmark results and system information. 
You can use asct diff to carry out the following tasks: 

- Compare results before and after system changes. Examples include kernel updates, firmware updates, tuning changes, or configuration changes to the Basic Input/Output System (BIOS) or Unified Extensible Firmware Interface (UEFI). 
- Compare 2 different systems that use the same benchmark set  

## What asct diff compares 
Each ASCT run output directory contains a structured summary of the following information: 

- Benchmark measurements 
- System configuration information 
- Metadata  
When you run asct diff, ASCT performs the following tasks: 

- Loads results from each run directory 
- Groups fields by benchmark or measurement name 
- Groups matching Arm Coherent Mesh Network (CMN) register differences so that one result lists all affected hardware locations 
- Produces a table in standard output or machine-readable CSV or JSON format  

### How asct diff shows values 
For benchmark measurements, ASCT prints the percentage difference between the baseline and each comparison run. 
For system configuration reports such as system-info, cmn, and metadata, ASCT prints raw values instead of percentage differences. 
If a field is missing in one run, ASCT displays <missing>. It reports the change as added or removed.  

## Run asct diff 
Use the asct diff command to compare one or more run directories. 

### Compare runs 
asct diff supports comparing any number of runs. ASCT always uses one run as the baseline and compares every other run against it. 
To compare 2 runs, use: 

```
# ASCT uses the first run directory as the baseline
asct diff runA runB
```

To compare 3 runs against the first run as the baseline, use: 

```
# Compare 3 runs against the first run as the baseline
asct diff runA runB runC
```

To compare many runs against the first run as the baseline, use: 

```
# Compare any number of runs against the first run as the baseline
asct diff runA runB ... run_n
```

### Specify a baseline 
To specify a baseline explicitly, use --baseline: 

```
# Use runB as the baseline and compare runA against it
asct diff runA --baseline runB

# Use runA as the baseline and compare runB and runC against it
asct diff runB runC --baseline runA
```

## Use asct diff options 
The asct diff command supports the common ASCT output and logging options: 

- --format with values stdout, csv, or json 
- --output-dir, --force 
- --log-level, --log-file, --quiet  
In addition, asct diff supports the following options: 

- 
--baseline, -b BASELINE_DIR 

- Specify the baseline run directory. 
- When you set this option, you can compare 1 or more run directories against the baseline. You do not need to pass 2 run directories to establish a baseline.  
- 
--benchmarks, -k BENCH [BENCH ...] 

- Limit the comparison to selected benchmarks or reports. 
- Prefix a benchmark with ^ to exclude it from the comparison.  
Examples: 

```
# Compare only these reports
asct diff runA runB --benchmarks system-info peak-bandwidth

# Compare everything except system-info
asct diff runA runB --benchmarks ^system-info
```

- 
--sort-by, -s RUN_DIR 

- Sort the main delta table by a specific comparison column. 
- RUN_DIR must match one of the run directory arguments. It must not be the baseline.  
Example: 

```
asct diff runA runB runC --sort-by runC
```

## View asct diff output 
Use --output-dir to specify an output directory. 
When you use --format=csv, ASCT writes diff.csv to the output directory. 
When you use --format=json, ASCT writes diff.json to the output directory. 

### Grouped register differences 
CMN is the Arm Coherent Mesh Network interconnect. When compared runs contain CMN register differences, ASCT generates additional parsed and grouped views of those differences. 
The grouped view combines rows with the same register, bitfield, baseline value, and comparison values. Instead of repeating a result for each hardware location, it lists all affected locations in a cases(...) column. This makes it easier to identify register changes that occur in multiple locations. 

#### View grouped differences in standard output 
When you use --format=stdout, ASCT prints the parsed and grouped register-difference tables after the main diff output. 
For each supported report type, the output can include: 

- 
Parsed register differences: ASCT splits each raw difference field path into meaningful columns, such as register, bitfield, NUMA node, coordinate, feature, port, or device. Each row generally represents one original field difference, with values from each comparison run in separate columns. 
- 
Grouped register differences: ASCT combines rows that have the same register, bitfield, baseline value, and comparison values. The cases(...) column collects the affected hardware locations, making repeated differences easier to scan. 
- 
Grouped raw register values: This is the grouped view filtered to whole-register value differences only. 
- 
Grouped register bitfields: This is the grouped view filtered to decoded bitfield differences only.  

#### Save grouped differences to files 
When you use --format=csv or --format=json, ASCT writes the additional files to the output directory for the applicable CMN report type. 
For a report type named cmn, the files are: 

- diff_parsed_cmn.<format> 
- diff_grouped_cmn.<format> 
- diff_grouped_cmn_raw.<format> 
- diff_grouped_cmn_bitfields.<format>  
Replace <format> with csv or json. JSON files contain newline-delimited JSON records. 
ASCT creates these files only when the compared runs contain differences for that report type. 
In addition to tabular output, asct diff can generate comparison plots for supported benchmark types. ASCT writes these plot files to the diff output directory with the other generated artifacts. 
To ensure that comparisons appear more consistently in asct diff results, loaded-latency and c2c-latency provide structured diff fields. Structured diff fields represent differences between runs as explicit data fields (for example, baseline, new value, and percentage change). This approach enables filtering, sorting, and automated analysis. 

### Diff graphs 
asct diff can generate PNG graphs in the diff output directory. 
When the run dataset contains multiple units for the same measurement type, asct diff generates one PNG chart per unit instead of a single combined chart.
