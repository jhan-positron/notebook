Conditions common to every test in this ledger

  • Hardware attention was DISABLED in every model run. Verified four ways (07-31): the engine banner HW attention: DISABLED (USE_HW_ATTN=0) + hw_layers: 0 appears in the gpt-oss draw logs (ab57) and the dense-control draw logs (ab59); the boot journal shows hw_layers: 0 for every production model loaded (llama-3b/8b/70b — the A5 check); and neither run-benchmark.sh nor the runtron binary exposes any hw-attention flag, so no command line in this campaign could have changed it. All attention ran on host CPUs in every test — no verdict below is confounded by hw-attention differences, and (per A5) hw-attention cannot explain the gpt-oss-vs-llama model dependence either.
  • Sampling was greedy with a fixed seed in every measured draw (--threshold_p 0 forces argmax; seed frozen in each kit's argv), and each kit's runtron argv was frozen byte-identical across its draws (modulo per-draw output paths where stated).
  • DUT = delphi-3bda, instance 0 (cards 10/13/38/3b), trio serving stopped during draws — except where a row says otherwise (ab45 = AMD andoria-06; ab53 also ran instance 1; nightly-archive rows are the fleet's own runs).

Group F · added 2026-07-31

Instruction-level scoping — what a slow token actually spends (fast vs slow under the PMU)

jhan's two questions, answered from captures already on disk (zero new DUT time): did the fast draw execute more real instructions, and does the slow draw burn its extra time in wait/mwait-style non-functional instructions? Data: the per-draw 15 s per-CPU perf stat block that every kit since ab49 carries (cycles, instructions, cache, on all 56 app + 4 device CPUs), across 221 archived draws in 9 kits = 11 same-config groups (ab55/ab56 stratified per SST arm), plus ab58's cycles-sampling + sched perf data, IMC/IIO uncore, turbostat and the DRAM probe. Fast8 = 8 highest-gen draws per group, slow8 = 8 lowest (7/side where n=15). The counter window sits at benchstart+8 s→+23 s, verified pure decode on all 221 draws — in every draw it contains per-user token ≈530→≈1800, so the requested “token ~900” decode path is inside the counted window by construction; ab58's sampling window (+35→+45 s) covers tokens ≈2800–3700, the “towards the end” variant. Within a draw the rate is constant (ttlt = ttft + 4096/gen to <0.2%), so these window numbers ARE the per-token numbers, up to one caveat handled below (the long-barrier mixture). Hostile-verified: 6/6 independent recomputations from raw, plus a design audit; verdicts below.
questionverdictanswer
Q1 — did the fast draw execute more real instructions? ANSWERED — YES Fast draws retire +6.3…+11.5% more instructions/s on the app pool (11/11 groups, perm p ≤ 0.015, most ≤ 0.0007; ρ(gen, instr/s) = +0.82…+0.97 across all draws of every kit). Q2 — does the slow draw execute more wait/mwait-style non-functional instructions? ANSWERED — NO* Not on the app pool: the wait there is instruction-LIGHT. Slow draws burn +5.5…+10.6% more cycles/token while retiring fewer instructions/token, i.e. the extra time is parked cycles (the spin primitive's bounded-tpause loop inside TSX retires almost nothing while the clock runs). The IPC deficit alone accounts for 124–151% of the cycles/token excess in every group. *The exception proves the mechanism: the 4 device TX/RX cores (busy-poll at the 2700 MHz clamp) show the classic instruction-DENSE poll signature instead — +7.4% instructions/token when slow (more poll iterations per token as the device-side step rate drops).

Per-thread sampling (perf cycles, −F 297, TIDs mapped via threads_psr): the shift is pool-wide, not thread-local — every one of the 55 workers moves its own leaf mix (wait_for_event 38.2→40.7%, wait_for_not_event 21.3→23.0%, attention apply_page_range 20.4→16.8%, run_joins 4.5→3.7%), while per-thread cycles/s and class shares stay flat (workers 93.4 vs 93.5% of samples). Per-CPU counters agree: 55/56 app CPUs lose instructions/s in slow draws; the top-8 carry only 23.9% of the total loss (uniform would be 14.3%) — no culprit core, consistent with A9's uniform-slowdown result on 335 draws. The TX/RX device threads are ~93–94% poll-spin in both fast and slow — a constant tax whose iteration count per token rises when slow (the dev-pool +7.4% instr/token above).

The token-level statement (why “pick token 900” needs one refinement)

Within the window the slowdown is not a uniform per-token tax — it is a coin-weight (the ab58 mixture-shift finding, extended here from 3 to all 16 r3 draws): each cycle ends in either a short (~150 µs) or long (~880 µs) end-of-step barrier, i.i.d. per cycle, and only the weight moves. p(long) = frac(tail ≥ 300 µs): fast pair 0.48 / 0.43 vs slow pair 0.80 / 0.84 (all-16 range 0.23–0.85, two-clustered). So token 900 of a slow draw is most often an ordinary token followed by a long barrier more often — any single-token comparison samples the coin, not the state. The correct token-scope endpoints are the window rates above plus p(long); both are now on the record.
