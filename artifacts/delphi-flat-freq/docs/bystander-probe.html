The bystander probe (m8) — code, setup, and test data

Dedicated record of the DRAM pointer-chase experiment on delphi-3bda (kits ab44–ab54, 2026-07-27…29) · every number sourced from on-host analysis files, collected and re-verified 2026-08-09 · companion to goal1-conclusion.html §3.3 and the suspicion-ledger "m8" row · rendered view for GitHub readers
What this test showed. A tiny standalone C program, running on a spare CPU core and doing nothing but chasing pointers through its own private 2 GiB buffer, could feel which lottery ticket the concurrently-running engine had drawn: when runtron had a fast draw, the bystander's memory latency was lower (ab44: ρ = −0.81 discovery / −0.74 confirmation, pre-registered split). The same program, run on the empty machine before each launch, read flat every time (spread <1 ns, n=25). The per-launch state is therefore machine-visible on the shared memory path — but only while the engine's traffic flows — and it is not a property of tron's own code. Later, heavier-instrumented nights attenuated the signal, and a confound check downgraded it from "predictor" to "sometimes-visible symptom" — both kept on the record below.

1 · The program

Source: delphi-3bda:/scratch/jhan/f3kit/dramprobe.c (4,767 bytes; build: gcc -O2 -pthread -o dramprobe dramprobe.c). One latency thread plus N optional bandwidth-injector threads; the bystander test uses latency-only mode (N=0).

How it measures pure memory latency. It allocates a 2 GiB anonymous buffer (MADV_HUGEPAGE, first-touched on the pinned CPU so the memory is NUMA-local), then builds one giant closed loop through it: a full-cycle random permutation of cache lines (Fisher–Yates shuffle, xorshift64 PRNG, fixed seed), one pointer per 64-byte line. Each load's result is the address of the next load — so the hardware prefetcher can't guess ahead and exactly one memory request is ever outstanding. The reading is a pure DRAM round-trip time, insensitive to bandwidth.

/* the chain build + inner loop, verbatim from dramprobe.c */
size_t *idx = malloc(n * sizeof(size_t));
for (size_t i = 0; i < n; i++) idx[i] = i;
uint64_t rng = 0x9e3779b97f4a7c15ULL;
for (size_t i = n - 1; i > 0; i--) {                 /* Fisher-Yates */
    rng ^= rng << 13; rng ^= rng >> 7; rng ^= rng << 17;
    size_t j = rng % (i + 1);
    size_t t = idx[i]; idx[i] = idx[j]; idx[j] = t;
}
for (size_t i = 0; i < n; i++)                        /* one pointer per cacheline */
    buf[idx[i] * 8] = (uint64_t)(&buf[idx[(i + 1) % n] * 8]);
free(idx);

uint64_t *cur = (uint64_t *)buf[0];
const int CHUNK = 20000;
while (!stop_flag) {
    double t0 = now_s();
    for (int i = 0; i < CHUNK; i++) cur = (uint64_t *)*cur;   /* dependent loads */
    double t1 = now_s();
    a->ns_per_load = (t1 - t0) * 1e9 / CHUNK;
    __asm__ volatile("" ::"r"(cur));
}

Latency = wall time of 20,000 dependent loads ÷ 20,000 (CLOCK_MONOTONIC), republished once per second as CSV rows sec,inj_threads,write_pct,inj_GBps,lat_ns after a built-in 3 s warm-up.

  • When: launched at benchstart+8 s (after the engine's "model loaded" log marker); the scored window, rows 3–28 = seconds +11…+36 of the draw, sits fully inside steady decode (prefill ends ~+4 s). Pre-declared in the kit comments and the metric manifest (m8: "mean of samples 3..28").
  • Which core: the kit's node0_spare_cpu() parses the engine's own "Pinning application cores to…" / "Pinning device driver cores to…" log lines and returns the first CPU ≥ 3 on NUMA node 0 not in that set (CPUs 0–2 reserved as platform cores). With the engine's deterministic pinning (driver 3–6; app 24–71 + 151-158…), the pick is always CPU 7 — same socket and memory controllers as the engine and its store, deliberately: a probe on the other socket would sense nothing by design.
  • Row 0 artifact: the first row's bandwidth column is inflated by warm-up accounting (investigated + live-tested 2026-07-28); the 3–28 window predates and avoids it.

4 · What it established — and what it did not

  • Established: the per-launch state is visible to a process that shares nothing with tron but the socket's memory path — it is a machine-level memory-service condition, not tron-internal accounting. And it expresses only under the engine's concurrent traffic (pre-launch flat, during-decode separated) — which is why every idle-machine probe in the campaign came back null.
  • Magnitude: the bystander feels roughly a third to half of tron's relative penalty (+5–11% latency vs tron's ~10–15% throughput deficit) — consistent with the probe sampling only the serialized-latency component while tron compounds it across many parallel requests plus DMA.
  • NOT established — kept honest: it is a symptom, not a cause or a predictor. The ab47 check broke the predictor reading (see table); heavier instrumentation swamps it (ab50/51/52); and the ledger's standing verdict is "a sometimes-visible symptom, never a predictor." It was later folded into the launch-health early-warning idea only as a possible additional signal, not a gate.
All caveats in one place: (1) CPU 7's HT sibling is CPU 151, an active tron app core — front-end/L1/L2 shared, so the probe is a close neighbor, not a perfect outsider. (2) The node0_spare_cpu() exclusion parse reads the two "Pinning…" log lines only; tron's RX threads (147–150) weren't in the parse — harmless here because the scan returns CPU 7 first, but a re-user of the function should know. (3) probe.csv row 0 carries a warm-up accounting artifact in its bandwidth column; the pre-declared rows 3–28 window avoids it. (4) ab44's "fast ≈157 ns" figure quoted in older docs is the fast-mode median; the mean is 161.9 ns — this page uses means.

6 · Glossary

pointer chase
A loop where each memory read yields the address of the next read — serializing all requests and defeating prefetch, so the time per read ≈ true memory round-trip latency.
bystander
The probe shares no code, data, or cores with the engine — only the socket's memory controllers. Anything it feels must live in shared hardware.
m8
The metric-manifest name for this measurement: decode-window loaded latency, mean of probe rows 3–28.
discovery/confirmation split
Correlations computed separately on odd-numbered and even-numbered draws, pre-registered — a guard against one-half flukes.
warm-arm confound (ab47)
In ab47, every warm relaunch followed its fresh partner in time, so "warm" and "later" are entangled; the 4 highest-latency draws were all warm → their leverage can't be attributed cleanly.
