Claude’s key-layout change: decode gains with short-prompt latency costs

Reviewed 14 September 2026, UTC. Candidate 5e45ae55ae3277f025bd69a29e93741e2690e3e3 on jhan-amx-vnniK. Base 544ca05c7a954f892f0e23ccb465f74ad46bea5e. Documents captured at 15:48:55 UTC; hashes are in the review manifest.

Short version

Claude implemented one packed key representation and updated the matrix, vector, copy, and hardware-upload paths. The raw logs reproduce the reported performance tables, including higher decode speed in five configurations and worse first-token latency in three. Keep the change experimental until the CI coverage, numerical follow-up, and latency tradeoff are resolved.

Words used here

  • K, Q, V: saved attention keys, current queries, and saved values.
  • VNNI layout: a pair-interleaved arrangement of keys for matrix and vector dot products.
  • AMX, AVX-512: CPU matrix and vector instruction sets.
  • bf16, fp16, fp32: bfloat16, half precision, and single precision. The two 16-bit formats encode values differently.
  • KV page: a 64-token cache block. A KV slot identifies persistent attention storage.
  • TPS: generated tokens per second per request. TTFT: time to first token.
  • TP2 / TP4: a model split across 2 or 4 accelerator cards.
  • QK / PV: query-key scoring / attention weights multiplied by values.
  • kv_mul: query heads per KV head. CI: continuous integration.
  • GOF: the hardware-upload group of four tokens. Logits: per-word scores used to select an output token.
  • Control repeat: the same binary and settings run again to check reproducibility.
  • off / base: the PR3879 binary with AMX disabled / enabled. vnnioff / vnni: the candidate binary with AMX disabled / enabled.

1. Findings that change the conclusion

High priority: the new storage integration has no enabled CI configuration

TRON_K_VNNI defaults off. No required CI configuration enables it. The new t_k_vnni_layout test also lacks a scheduling-cost entry. Primitive packed-layout tests can run with the option off, but page accessors and production attention then exercise row-major storage. [CMakeLists.txt; cmake-single-platform.yml; test-benchmarks.json; t_k_vnni_layout.cpp:241–248]

Required change: add the option to an appropriate existing CI configuration, keep an off configuration, and add measured cost data. Verify collection and execution at the exact proposed revision. The repository’s test policy requires committed tests to run in CI.

High priority for the performance decision: latency does not improve across the requested prompt lengths

The candidate adds 70.504 ms at TP2 / prompt 1024, 170.835 ms at TP4 / prompt 1024, and 229.446 ms at TP4 / prompt 2048. Every repetition of those cells has the same sign. TP2 / prompt 2048 has a −0.764 ms mean difference with mixed signs across repetitions. Treat that cell as no clear change. [main_results and paired_repetitions]

The report’s TP4 prose calls the short-prompt result “the one TTFT cost” and says longer prompts cover it. Its own 2048-token row contradicts that statement. Its universal claim of a faster vector path also misses TP4 / prompt 1024: vector-only TPS falls 1.6% and TTFT rises 3.1%. [frozen report, “Reading the numbers” and TP4 comparison table]

Required change: correct those statements and retain the measured short/mid-prompt tradeoff in the headline. The report itself identifies a prior 2% short-prompt gate; both TP2 and TP4 mean latency changes exceed it. The present evidence does not support a default rollout under that gate.

Medium priority: the campaign does not isolate the cost of key stores

The candidate changes the key writer, vector reader, query preparation, and matrix score output together. The vector-only comparison still changes both writer and reader. No per-stage store or kernel timings were recorded in this campaign. “This is the store cost” is therefore a hypothesis, not a measured decomposition. [frozen report, “the one TTFT cost”; performance audit]

All repetitions use the fixed order off → base → vnni → vnnioff. The 2 TP4 rounds and 3 TP2 rounds show repeatability in that sequence. They do not remove time-order effects. [campaign.sh:61, 380–393; arm_orders]

Measurement to resolve it: rotate or reverse the order, use control repeats, and collect save-K plus attention phase durations. A store-only change or a block-store variant can test the proposed cause. Until then, label the scatter explanation explicitly.

Medium priority: the generation smoke narrows the numerical question but does not answer it

Both control repeats reproduce all 128 output tokens. The two binaries first differ at zero-based generated-token index 52, in both AMX states. These observations associate the difference with the binary change that remains when AMX is disabled. They do not isolate the partial-page reader or prove a near-tie. [smoke.txt; k_vnni.hpp:151–181]

The direct AMX test does establish identical QK scores for its two seeds. That is narrower than a guarantee for every model state. The native vector reader uses a different summation order, so it is a plausible cause. The report’s final caveat recognizes this limit, but its preceding causal sentence is stronger than the evidence. [t_amx_numerics.cpp:188–234; frozen report, section 4.1]

Measurement to resolve it: force the same token sequence in both binaries. Compare logits and the top-two score margin around index 52, plus attention outputs for full and partial pages. Separate ordinary summation error from a storage or integration defect before claiming equivalent model quality.

Medium priority: the reader’s stated shape coverage exceeds its implementation

The design says the vector reader handles any kv_mul. Its static assertion permits only 1–16 heads per KV head. The storage gate checks only head size 128. A valid geometry with 32 query heads and one KV head therefore selects packed storage and cannot instantiate the reader. [k_vnni.hpp:52–57, 128–144; self_attention.hpp:1616–1625; kv_cache.hpp:165]

This is a conditional compilation limitation. No measured model here has that geometry. Required change: either process heads in bounded groups, provide a fallback, or state and enforce the supported model set before selecting this layout.

2. Design and implementation review

The core data flow is consistent with the single-copy goal. The source keeps one K plane, writes it before the existing completion counter, removes misleading row accessors for packed slots, adapts arbitrary-offset copies, and provides separate scratch space for each hardware-upload head. [model.hpp:2754–2783; kv_cache.hpp:1322–1427, 1754–1800; gof.cpp:203–219]

Claude’s masked vector reader leaves excluded scores at negative infinity. Its fp32 query path preserves query precision. The fp16 path widens to fp32 before scoring. Those choices avoid treating every query buffer as bf16. [k_vnni.hpp:128–181]

Claude removes the score transpose but retains padded query work and temporary score stores. That is a defensible way to reuse the baseline tile contract. Four-row tiles are a further candidate for measurement, not a demonstrated improvement. The Codex proposal’s calculated 80% reduction in score-write bytes does not describe Claude’s implementation. [amx_attn.cpp:188–236; independent design, section 4]

The two panel orders are both mathematically valid. For token 0, dimension 32, Claude uses byte offset 4,096 and Codex uses byte offset 1,024. For token 16, dimension 0, those offsets reverse. Every writer and reader must use its own matching formula. [k_vnni.hpp:62–65; layout calculations]

Documentation corrections

  • Claude’s design section 3.6 says all 64 tokens revisit the same 64 cache lines. A K plane contains 256 cache lines of 64 bytes. Each token touches 64 of them; each 16-token block shares that subset. This is address accounting, not measured cache residency. [frozen design, section 3.6; index formula]
  • The design’s writer description still shows every bf16 row passing through a stack buffer. The final implementation scatters bf16 directly from the producer buffer. Only other producer types use a conversion buffer. [model.hpp:2757–2774]
  • The report copies a previous TP2 baseline comparison into its TP4 paragraph. The previous TP4 summary reports +6.8% TPS and −10.5% TTFT, not the quoted TP2 +13.2% and −20.0%. Keep configuration-specific comparisons separate. [previous summary, TP4 lines; frozen report, “tp4, the known AMX gain”]
  • The index-anchor test comment calls a panel 1,024 elements. It is 512 bf16 elements, or 1,024 bytes. Its assertions use the correct element offsets. [t_k_vnni_layout.cpp:55–71]

3. Results independently recomputed from full logs

Measured scope: Qwen3-4B-Instruct-2507 on delphi-3bda, the test server. Each run uses 8 concurrent requests and 256 output tokens per request. Prompt lengths are 1024, 2048, and 8192 tokens. The model runs on 2 or 4 accelerator cards with CPU attention (USE_HW_ATTN=0). [rt-results.txt:1–5; campaign.sh:63–64, model names]

All 60 accepted logs equal their first-attempt logs byte for byte. There are 480 completed requests, no retries, no excluded attempts, and no early stop. Each request has 256 output tokens with 253 timed decode steps. All 24 cell means and standard deviations match Claude’s summary within a floating-point tolerance of 10⁻¹² in the stored metric units. The displayed result tables also match. [counts, cells, summary_mismatches; independent parser]

Metric boundary: TPS is the arithmetic mean of the 8 request rates in each run. TTFT is the maximum of the 8 request prompt-completion durations. The latter is a batch completion statistic, not the mean request latency or a measured client first-token timestamp. [metric_definitions; stream_generate.hpp:236–264, 747–764]

These are Claude’s recorded runs at 5e45ae55, checked against their complete output files. Codex did not rerun the C++ suite or launch a DUT workload. [tests.txt; code and test audit]

  • fp16 arithmetic still needs a nonzero-output check. The direct score tests use bf16 and fp32. The fp16 dispatch case checks routing on zero-valued data. Add fp16 queries whose low precision bits would expose accidental conversion to bf16. [t_k_vnni_layout.cpp:132–177; t_amx_dispatch_dtype.cpp:118–219]
  • NaN poison does not prove an excluded lane was never loaded. Vector lanes are independent, and output stores are masked. An unmasked load could read a dead lane without changing any asserted live score. The source does use masked loads, but a test that claims read suppression needs an inaccessible-memory boundary or equivalent read detector. [k_vnni.hpp:156, 181; t_k_vnni_layout.cpp:153–204]
  • Hardware staging remains outside this campaign. All performance runs disable hardware attention. The per-head scratch adapter is present in source, but these four test outputs do not establish real upload correctness or its cost. Exercise staging, including multiple heads and page relocation. [gof.cpp:203–219; campaign settings]
  • General model-quality evidence is still missing. The mask test uses one bounded random input corpus. Kernel error bounds and a 128-token smoke do not replace forced-sequence logits or a quality evaluation for a changed summation order.

The source review found no demonstrated indexing defect in the measured head-128/group-4 path. That statement is limited to the code and evidence reviewed. It does not certify every supported geometry, scheduling interleaving, or hardware path.

5. Recommended next changes

  1. Correct the report’s TP4 statements and label the scatter-store explanation as a hypothesis.
  2. Enable and verify CI coverage for the new layout. Resolve the reader’s group-size contract.
  3. Run the forced-token numerical comparison around generated index 52. Add a nonzero fp16 assertion and hardware-adapter coverage.
  4. Measure short-prompt save-K and attention time with rotated run ordering. Evaluate batched full-line key stores only after proving who owns each token block and when it may be published.
  5. Consider four-row matrix tiles as a separate change. Preserve compatible QK/PV region configuration and buffer bounds. Measure it against the current candidate before attributing a benefit.

These are review recommendations. This task does not modify Claude’s implementation or start another benchmark campaign.
