Independent design · source pinned · performance unmeasured

Generate the key cache in the layout that the matrix kernel consumes

Prepared 14 September 2026, UTC. Baseline: PR3879, branch jhan-amx-p0, commit 544ca05c7a954f892f0e23ccb465f74ad46bea5e. The core design was completed before reading Bill’s investigation or Claude’s design. The later investigation section records that second pass.

Short version

Store each completed key directly in a pair-interleaved cache, then compute attention scores in their final orientation. Update vector reads, page copies, and hardware uploads together with the matrix kernel. The design removes identifiable data movement, but its effect on generation speed and time to first token requires measurements.

Decision: one persistent key representation per eligible cache block, arranged in panels of 16 tokens. Keep an explicit vector fallback that reconstructs one key row in temporary storage.

Words used here

  • tron: the inference program under test. runtron: its command-line tool.
  • Q, K, V: queries, keys, and values used by attention. A query compares with saved keys to weight saved values.
  • KV page: a 64-token block of keys and values. A KV slot identifies persistent attention storage. A head is one attention feature group.
  • AMX, AVX: CPU instruction sets. AMX operates on matrix tiles. AVX-512 operates on vectors.
  • VNNI: Vector Neural Network Instructions. Here, “VNNI layout” means adjacent pairs along the reduction dimension, arranged for the matrix instruction’s right operand. It is a storage layout, not a requirement to execute integer VNNI instructions.
  • bf16: bfloat16, a 2-byte floating-point format. fp16 is a different 2-byte floating-point format. fp32 is 4-byte floating point.
  • QK: the query-key score product. PV: the product of attention weights with values. Softmax converts scores into weights.
  • GQA: grouped-query attention. kv_mul is query heads per KV head. This AMX kernel serves 4 query heads per KV head and 128 dimensions per head.
  • RoPE: rotary positional embedding, the position-dependent transformation applied before saving a key.
  • TPS: generated tokens per second. TTFT: time to first token. Prefill: processing the prompt. Decode: generating subsequent tokens.
  • FPGA: the programmable accelerator. GOF: tron’s hardware-upload group of four tokens. CI: continuous integration. DUT: device under test.

2. Exact layout contract

Use a compile-time storage option, proposed name TRON_VNNI_K, independent of AMX runtime availability. Default it off during evaluation. Enable the new layout for 64-token pages with head size 128 in the TRON_CHUNK_SIZE=16 build. Keep other geometries in their existing layout.

The storage choice must depend on the cache block’s geometry. It must not depend on the query’s type, its visibility, or the runtime AMX disable switch. Multiple query operations can consume one KV slot.

P = 64 tokens per page
D = 128 dimensions per head
W = 16 tokens per panel

Physical K shape: [P/W][D/2][W][2]

bf16_index(token, dim) =
  (((token / W) * (D / 2) + dim / 2) * W + token % W) * 2
  + dim % 2

byte_offset = 2 * bf16_index(token, dim)
Integer division is used throughout.
  • One panel occupies 4,096 bytes. One K page per KV head occupies 16,384 bytes. V occupies another 16,384 bytes. The layout adds no persistent key mirror.
  • Each 64-byte row holds one dimension pair for 16 tokens. The pair belongs to one token, so adding a token does not need to modify a neighboring token’s pair.
  • The whole K block has 64-byte alignment. A token’s individual pair has 4-byte alignment. A token is not a contiguous 256-byte row.
  • A valid alternative is [D/2][P][2], with a 256-byte row stride. This proposal chooses 16-token panels for contiguous 1,024-byte matrix operands. Neither form has a measured performance advantage here.

Change the common save_k_impl boundary. The input already contains the completed key, including any model-specific transformations. Replace the contiguous pg.k(...).set(kout) store with a layout-aware setter. This meets “at generation” at the persistent cache write. It does not require changing the projection output or the positional-transform arithmetic. [model.hpp:2731–2769]

  • Preserve bf16 bit patterns. For fp16 and fp32 producers, preserve the existing conversion to bf16. A storage change must not introduce a new rounding rule.
  • Store only the selected token’s 64 dimension pairs. Use scalar pair stores or a verified vector scatter with disjoint 4-byte destinations. Do not implement whole-row read-modify-write stores that can overwrite another token.
  • Finish every head’s K store before mark_k_complete. Preserve the existing release/acquire counter and downstream latches. Cache-line sharing is a performance concern, while overlapping stores would be a correctness defect. [kv_cache.hpp:1458–1484]
  • Do not delay publication until a panel fills. Decode must use a token immediately. Do not repack a published panel later.

Write-side cost needs measurement. One appended key contains 256 bytes in either layout. Row-major storage touches 4 aligned cache lines. This layout touches 64 cache lines within one panel. The counts describe addresses touched, not 16× more measured memory traffic. Measure save-K duration, ownership transfers between cores, and end-to-end TTFT.

The existing PV output allocation can stay at 8,192 bytes initially. Under the new configuration, only the useful 2,048 bytes are written. Keep begin/end calls around each worker’s existing region. AVX: reconstruct one key, then preserve the existing dot product

The existing dotter accepts contiguous tensor views. A strided K expression cannot be passed to it unchanged. Use an aligned 256-byte bf16 scratch row per worker invocation. Gather the selected token once, then share that row across the query heads. Its bit patterns and dimension order must match the old row. [dotter.hpp:175–222; self_attention.hpp:1555–1582]

  • Keep the existing token visibility and sliding-window loop. Gather only a token that the loop will consume.
  • Keep the original query type. Do not round fp32 or fp16 queries to bf16 to fit a new vector kernel.
  • The fallback covers partial pages, irregular masks, disabled AMX, and unavailable AMX. The storage option must also compile with matrix dispatch disabled.
  • The expected vector arithmetic remains unchanged. Verify bit-for-bit output against the baseline for identical bf16 cache values and execution order.

Deferred optimization, explicitly outside the first implementation: a native vector kernel can load 16 tokens’ key pairs and broadcast one query pair. That removes row reconstruction, but changes accumulation order. Add it only as a separately measured change with a numerical comparison. The first design accepts the reconstruction cost as an open performance risk, including the all-vector case.

What we can learn

  • One packed format can feed both instruction sets. Bill packs a K mirror during save_k. His blocked vector reader broadcasts one query pair and consumes one packed row for 16 tokens. This is a concrete implementation reference for the native vector alternative deferred in section 4. [model.hpp:1863–1880; avx512_blocked_attention.hpp:35–77]
  • The panel order matches this proposal. His offset is (token/16)*head_dim*16 + (dim/2)*32 + (token%16)*2 + dim%2. It equals section 2’s formula. Claude’s implementation instead places the dimension-step index before the token-panel index. Both orders can serve matrix tiles, but their stored bytes are not interchangeable. [amx_kv_layout.hpp:53; Claude k_vnni.hpp:62–65]
  • Small query groups need their own measurement. Bill selects the ordinary dotter below 4 query rows, blocked vectors for 4–7 rows, and AMX from 8 rows when available. Those thresholds apply to his kernels and padding. They do not settle whether this proposal’s 4-row AMX kernel is faster. [attention_dispatch.hpp:174–187]
  • His prototype is not yet a single-copy cache. Both original K and packed K remain. For a 64-token, 128-dimension head, the extra plane adds 16,384 bytes. K/V payload grows from 32,768 to 49,152 bytes, or 50%. Removing the original plane requires the copy and hardware adapters in this proposal. [kv_cache.hpp:938–963]
