Improve the key writer first; add helper threads through an explicit save phase

14 September 2026 · Review of Monday report §7.1 and Claude design §7 · Source revision 5e45ae55ae3277f025bd69a29e93741e2690e3e3

Short version

I agree with testing (a), then (b), and measuring their combination. The block transpose fits the stored layout, but “16× fewer store instructions” is incorrect for the current vector scatter. Whether either change removes the measured time-to-first-token regression remains unmeasured.

Words used here

  • TTFT: time to first token. Prefill processes the prompt. Decode generates subsequent tokens.
  • K / V: attention keys / values. A key head has 128 dimensions in this model. A KV page holds 64 tokens. A slot selects the persistent storage for an attention operation.
  • VNNI-K: Claude’s candidate, which stores pairs of key dimensions together. bf16 is the 2-byte bfloat16 format. One dimension pair occupies 4 bytes.
  • Scatter: a vector instruction that writes its elements to separate addresses. A cache line is 64 bytes here. A write fragment below means one explicitly addressed destination piece, not a measured hardware transaction.
  • Main helpers assist the main CPU thread. Attention workers run attention in a separate group. TP2 / TP4 split one model copy over 2 / 4 accelerator cards. AMX is the CPU matrix instruction set.

(a) Yes: transpose complete blocks and write full lines

One stored line holds a dimension pair from each of 16 consecutive tokens. Transposing a complete block produces exactly those lines. The destination layout stays the same. [k_vnni.hpp:16–24, 62–65]

Performance hypothesis: contiguous stores cost less than the scatters they replace, even after the register shuffles. Measure the complete block writer, including loads, conversion, shuffles, and stores. These counts do not establish a speedup or a reduction in memory traffic.

  • Group by the actual page and aligned 16-token destination block. All 16 tokens must be present and eligible for this save. Consecutive batch entries alone do not prove that condition. [model.hpp:2745–2751]
  • Keep per-token scatter for incomplete blocks and ordinary decode. Do not wait for future tokens to fill a block. Preserve the current conversion to bf16 for other source formats. [model.hpp:2754–2771]

(b) Yes, with a coordinated phase in the existing helpers

Separate 16-token destination blocks have disjoint cache lines. Assign each block to one worker. Assigning neighboring tokens in the same block to different workers would make them write different bytes of the same lines. [k_vnni.hpp:16–24; address audit]

“Idle” does not mean available to execute a newly queued task. The generated pipeline already places long-lived helper and attention tasks on the pool. Helpers currently skip the attention statement containing the saves. A nested parallel loop that queues work to this pool and waits can deadlock. This follows from the worker schedule and the pool’s run-to-completion task loop. [TronCpp.hs:1150–1163, 2279, 2339–2353; threading.hpp:789–800, 820–827]

The implementation should add an explicit save phase to the existing main/helper streams. Use the actual allocated helper count, with a serial path when it is zero. Keep the current attention-worker allocation for the first experiment. Disjoint destination bytes establish write independence, but they do not establish input readiness or completion ordering. [model.hpp:1937–1981]

  1. Wait until the block’s source keys are ready. Keep their buffers valid while helpers read them. The current generated main path waits on the key channel before calling the save. [TronCpp.hs:2339–2353]
  2. Write every key head before marking a token complete or crediting its hardware-upload completion. Preserve exactly one completion per saved token. [model.hpp:2754–2782]
  3. Join all helper stores before releasing the batch’s key-ready dependency or source buffers. Notify each downstream batch once. Attention over pages being written waits on the combined key/value dependency. [model.hpp:2785–2787, 2850–2852; self_attention.hpp:782–788]

Performance hypothesis: helper work shortens the save phase enough to offset dispatch, synchronization, and cache costs. Measure phase wall time and helper waiting. The existing source does not prove that extra threads will improve TTFT.

(c) Measure each change before choosing both

Insufficient data: the campaign has no isolated key-save timing. The TP4 regression is measured, but its attribution to scatter stores is not. The existing Save K trace span provides a starting point. [Monday report §7.1; model.hpp:2739; recomputed campaign results]

  • Check TP2 and the 8,192-token prompt before accepting the change. Measure ordinary decode too. Retain the numerical checks for partial pages, skipped tokens, block boundaries, and completion ordering.
  • Compare end-to-end TTFT with phase timing. Summed worker CPU time is not elapsed save time. Attention can also wait for saved values or other work. A shorter key-save phase alone does not prove the same reduction in TTFT. [self_attention.hpp:777–788]

Recommendation: implement and measure (a) first. Add (b) if the remaining save phase justifies the scheduling change. Choose the combination only if its measured TTFT and decode results support it.

Scope: source review and exhaustive destination-address enumeration for all four full token blocks.
