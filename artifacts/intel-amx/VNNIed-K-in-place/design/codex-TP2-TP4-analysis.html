Words and measurement boundaries

  • TP2 / TP4: one model copy split across 2 / 4 FPGA accelerator cards. An FPGA is a programmable accelerator. An engine serves one independent model copy. Several engines can run on one machine. CI is continuous integration, the nightly automated test.
  • AMX: the CPU matrix instruction set. AMX off uses the baseline CPU vector path. AMX baseline is PR3879 with matrix instructions enabled. VNNI-K is Claude’s candidate, which stores attention keys in a paired layout and enables its AMX path.
  • TPS: decode tokens per second per user. Higher is faster. Both reports average per-user rates, rather than sum the machine throughput. TTFT: time to first token. Lower is faster. The two reports use different timing and aggregation boundaries, described below.
  • Prefill: processing the prompt. Decode: generating subsequent tokens. In Claude’s campaign, each request produces 256 output tokens, of which 253 decode steps are timed. There are 3 runs per TP2 configuration and 2 per TP4 configuration.
  • Decode ms/token: each request’s logged decode duration divided by its timed token count, averaged across requests and runs. It includes all work and waiting in that interval. It is not a matrix-kernel duration.

Moving from TP2 to TP4 in CI gives each model copy twice as many cards and nominally twice as many users. It also halves the number of independent model copies serving the machine. The measured result says that the TP4 deployment handles this fixed machine workload less efficiently. It does not say that adding cards to an engine at the same user count makes that engine slower.

This reversal also appears in a prior test with matching per-engine loads. The September 13 test used 4 cards: two TP2 engines with two users each, versus one TP4 engine with four users. With AMX enabled, TP2 measured 152.46 tokens/s/user and TP4 measured 123.89. TP2 also led with AMX disabled and with FPGA attention. These are separate measurements, not the user’s quoted nightly values. [September 13 summary:10–17]

Other measurement differences

  • The CI label @8u per machine describes client distribution. Its TPS is the mean of per-request rate samples. Its TTFT is also a mean. [tps.py:276–304; perf.py:350–367]
  • CI requests 1,536 generated tokens and measures decode between generated positions 896 and 1,024. Claude’s campaign times 253 early decode steps. They do not measure the same part of generation. [perf.py:138–160; campaign scope]
  • Claude’s campaign forces CPU attention. The quoted CI excerpt does not identify its build or attention backend. The archived September 11 nightly used FPGA attention by model default, but that does not prove the backend of the quoted snapshot. [September 11 inspection]

Insufficient data to divide the observed gap among causes: user distribution, batching, CPU scheduling, and cross-card work can all differ. Stage timings and per-engine request assignments under a fixed whole-machine workload would identify their contributions. The deployment conclusion already holds: TP2 is faster for the eight-user nightly workload in the supplied results.

The elapsed-time view shows the remaining question. At 8,192 tokens, the change saves 5.438 ms/token on TP2 and 2.014 ms/token on TP4. Those are whole-decode interval savings calculated from logged request durations. They do not isolate time inside attention. [base_to_vnni, decode_records]

A faster baseline alone does not explain why the elapsed-time saving shrinks. If the same number of milliseconds were removed from a shorter decode interval, the relative speedup would grow. The cause therefore needs a stage-level timing comparison. This arithmetic does not establish a slower AMX instruction or a less accurate layout.

What the evidence supports about the mechanism

These are CPU-attention experiments. Every run sets USE_HW_ATTN=0. Both model variants use 32 query heads, 8 key heads, 128 dimensions per head, and 36 layers. The CPU attention path retains the full geometry. Each eligible AMX call still serves 4 query heads. [TP2 log:102–103; TP4 log:146–147; common.hpp:74–79; self_attention.hpp:199–206]

Recorded resourceTP2TP4
FPGA cards24
Application logical CPUs2856
Shared-pool workers2755
Query / key heads used by CPU attention32 / 832 / 8

The shared pool reserves one application CPU for the main thread. The pool’s division between attention and other work depends on scheduling. The pool size is not the number of attention workers. [threading.hpp:855–861; model.hpp:1937–1969; CPU allocations:3–4]

  • Hypothesis — less attention time is exposed in TP4’s decode interval. The larger CPU pool can change scheduling and overlap with accelerator work. Measure attention execution, actual worker assignments, and the joins that delay the next operation. Compare the same CPU allocation at both card counts to separate card scaling from CPU scaling.
  • Hypothesis — scattered key writes add exposed prefill cost. The candidate writes a 256-byte key as 64 separate 4-byte pairs across 64 cache lines. The previous key row is contiguous. That address pattern is verified, but its timing impact is unmeasured. Record key-save time, producer stalls, and cache-line ownership transfers under both CPU allocations. [k_vnni.hpp:62–97; baseline model.hpp:2731–2769]

Insufficient data: the saved logs contain no separate key-save, query–key score, or weighted-value stage durations. They do not contain actual attention-worker assignments or cache counters. The report cannot attribute the first-token regression specifically to key stores. Its candidate also changes the vector reader and AMX query/score handling. [limitations; amx_attn.cpp:188–236]

Claude’s added section 7: plausible mechanism, unmeasured allocation of time

The store loop is serial within each call. This is visible in the common save_k_impl implementation. The report’s claim that the tested store runs on the receive worker of the last completed tensor-parallel shard is not established by its handwritten Llama-plugin citation. The tested model is ingested Qwen. Its generator emits key saving in an attention-submission sequence after reading the key channel. The generated Qwen schedule or thread-tagged trace is needed to identify the actual executing thread. A serial loop within one call also does not prove that all minibatches use one global writer. [model.hpp:2745–2778; llama.hpp:967–1025; TronCpp.hs:2310–2349]

The updated report divides the TP4 1,024-token latency increase by an assumed 2,359,296 saved key rows. This gives about 72 ns per row if the entire increase comes from key stores. That is a conditional estimate, not a measurement of the candidate’s store loop. Claims that the store is fully exposed on TP4, or that attention time halves when the CPU allocation doubles, still need stage timings. [updated report, sections 7.1–7.2]

The older scatter microbenchmark cited there records scalar-mirror results of 70.8–71.0 ns per key row under its own workload. The similar magnitude makes the store explanation worth testing. It does not establish the new vector-scatter cost, the cost above the old contiguous store, or how much of that cost delays this campaign. [August 24 scatter measurements]

The next useful experiment is a paired baseline/candidate trace with fixed request tokens and rotated run order. Collect the existing Save K, Attention Ready, Attention Pending, and attention-join events. Add separate score-kernel and weighted-value durations. Include one run pair with CPU allocation held equal across TP2 and TP4. [model.hpp:2739; self_attention.hpp:996, 1203]
