VNNIed K in place: design

Claude design document for the "make K VNNI layout at its generation" project. Written 2026-09-14 (Monday, 06:xx UTC) before the delphi-3bda test window. Branch jhan-amx-vnniK in ./tron-VNNIed-K, first commit 73125f5464 on top of jhan-amx-p0 at 544ca05c7a (PR #3879 head, jhan's merge of main). Status of each part is marked built, measured or planned. Measured results (2026-09-14 13:14 UTC) are in status/Monday-morning-report.html and summarized in section 8.

Short version. PR #3879 (the AMX baseline) keeps K stored one row per token, so its AMX kernel has to compute the scores transposed and transpose them back for every page. This design stores the K of every 128-dim head directly in the AMX pair-interleaved layout, so the kernel computes the scores in the right orientation, the partial pages are served by a new AVX-512 reader of the same layout, and no second copy of K exists. The price moves to the K store (a scatter of 64 dim pairs per token), and the Monday test on delphi-3bda measures whether the exchange pays in TPS and TTFT at prompt lengths 1024, 2048 and 8192.

2. What the AMX baseline pays, and what the mirror cost

The AMX tile multiply (TDPBF16PS) accepts a row-major matrix only as its left operand, A. Its right operand, B, must be in the VNNI layout. PR #3879 keeps K as stored (row-major), so it must use K as A and the packed query group as B. The product then comes out transposed, ST[token][head], as four 16 x 16 fp32 tiles [amx_attn_iface.hpp, Note [QK orientation]]. The kernel stores the four tiles to a 4 KiB buffer and runs an AVX-512 register transpose to write the 4 real rows into the caller's score array [amx_attn.cpp, qk_rowmajor_128x4]. Only 4 of the 16 tile columns carry real queries in decode, so 12 of 16 columns of every tile are padding work.

The cost of that orientation was measured twice.

  • Kernel level (2026-08-19, one L2-resident page, width 4): row-major AMX 1250 ns per page against 686 ns for the mirror kernel that reads a pre-built VNNI copy, a gap of 564 ns per page [exec/results/slot1/fused-sweep-v2.txt].
  • Serving level (2026-09-01, prompt 8192, one user, one query x one page x one KV head): the row-major AMX unit took 2.89 us and the mirror unit 2.66 us. The QK phase alone was 1.49 us against 1.12 us, a gap of 0.37 us [exec/results/single-attn-20260901/summary.json]. The whole-unit gap is smaller (0.22 us) because the mirror's PV phase was 0.12 us slower, for a reason not yet measured.

The mirror removed the transpose but added a second copy of K. Its measured costs were the reason PR 2 was parked.

  • Memory: the arena held 39.3 to 46.5 GiB of ordinary RAM per tp2 engine over a one-hour soak [PR3879/more-testing/round-1/status.md].
  • TTFT in the serving path: qwen tp4 with 8 concurrent prefills 2022 ms against 1630 ms for row-major AMX (+24.0%), llama tp2 +17.7% [exec/results/g1-20260908/summary.md]. The G1 probe split the qwen penalty into about 190 ms for the 64-line scatter store pattern, about 190 ms for the arena placement, and about 12 ms for the second (row-major) store.
  • Page-table work: about 80 M 4 KiB page walks per 12 s window on the arena (base pages), costless in wall time after the THP experiment [exec/results/perfstat2-20260831, thp-20260901].

The in-place design keeps the mirror's kernel and drops the second copy: no arena, no arena placement penalty, no coherence invariant, no page-table tax. What stays is the store pattern (the scatter), which becomes the primary store. Section 3.6 states the expectation and the measurement that settles it.

3. The design

3.1 The layout built

For a page of 64 tokens and a head of 128 dims, define for token p and dim d: s = d / 32 (dim step), c = p / 16 (token block), dp = (d % 32) / 2 (dim pair), t = p % 16 (token in block), j = d % 2 (value in pair). The stored element index is

plane[(((s * 4 + c) * 16 + dp) * 16 + t) * 2 + j] == K[p][d]      // 64 x 128 bf16 = 16 KiB

The plane is 16 panels of 1 KiB. Panel (s, c) has 16 rows of 64 bytes: row dp holds dim pair (2dp, 2dp+1) of the 16 tokens of block c. One panel is exactly one AMX B tile, and one 64-byte row is exactly one AVX-512 register [h/tron/kernels/k_vnni.hpp]. The bytes and the page capacity are the same as the row-major plane; only the order changes. Token p owns column t of block c in every panel, so tokens are written independently, without read-modify-write between neighbours (unlike the pair-interleaved V plane, which pairs tokens 2i and 2i+1 in one 32-bit lane).

Figure 1. The same 16 KiB of K in the two layouts. Left: 64 rows of 256 bytes. Right: 16 panels; the AMX kernel loads one panel per (dim step, token block) as its B operand. Schematic, not to scale.

3.2 The gate: a property of the storage geometry built

The layout is selected at compile time by the new CMake option TRON_K_VNNI (default OFF; it requires TRON_AMX_DISPATCH=ON, otherwise CMake stops with an error) and applies to every KV slot whose head size is 128: k_vnni::layout_on<head_size> [k_vnni.hpp]. Every other head size keeps the row-major plane. The gate depends on neither the query type nor whether AMX is available at run time, so every reader and writer of a slot sees the same layout. V is unchanged: its pair-interleaved layout is already the AMX B operand for the PV product.

Why compile time and not a run-time choice: a run-time layout flag would have to be threaded through every accessor of the KV cache and checked on every hot-path access; the code base already selects the AMX dispatch and the K-mirror at compile time, and the test matrix of this project (row-major build against VNNI build, same commit) is what we measure.

3.4 The AMX kernel qk_vnni_128x4 built

Tile plan per (query group, page): zero 4 C tiles (one per token block). For each of the 4 dim steps: load the Q rows step (tile 4: 16 rows x 32 dims, row stride 256 bytes; rows 4..15 are zero padding), then for each token block load the K panel (1 KiB, 64-byte rows) and multiply into that block's C tile. Store the 4 C tiles (16 rows x 64 fp32 each) into a kernel-internal buffer and copy rows 0..3 into the caller's s[4][64]. Counts: 4 A loads, 16 B loads, 16 TDPBF16PS, 4 tile stores, 1 KiB copy. The row-major kernel has the same 16 multiplies and 20 loads, plus the 64 x 16 fp32 transpose (16 unpack and 12 shuffle instructions per 4 x 16 block, 4 blocks) [amx_attn.cpp]. This kernel is the mirror kernel of the parked PR 2 (qk_mirror_128x4) with an explicit score stride and the 16-row store handled inside.

Numerics: the kernel adds the same four 32-dim partial dots in the same order inside the tile multiply as the row-major kernel, so its scores are bit-identical to qk_rowmajor_128x4 on the same logical K. The test asserts this on random inputs (section 5). The PV kernel, its rounding of the weights and the numerics contract of Note [AMX attention dispatch] are unchanged.

3.5 The AVX-512 reader for partial pages built

Every query has one partial page (the page its own token lives in) per layer and KV head, and every page is partial under the kill switch or on a host without AMX. The row-major dotter cannot read the VNNI plane (a token's values are 64 bytes apart across 16 panels). The reader k_vnni::qk_group<kv_mul, q_scalar> iterates the other way round: for each 16-token block with at least one live token, for each of the 64 dim pairs, load the 64-byte pair row with a lane mask of the live tokens (dead tokens are never loaded; their storage may be unwritten), broadcast the query's dim pair, and accumulate with VDPBF16PS, one accumulator per query head. 4 heads share every K load. The scores of live tokens are stored with the same mask; the caller's -inf preset stays for the others. For prompts whose last page is short, blocks with no live token cost nothing.

Numerics: the same exact bf16 x bf16 products are added in fp32; the add order differs from the dotter's (4 lanes-of-16 accumulators then a horizontal reduction). The test bounds the difference by the same envelope the AMX tests use (1e-4 of the absolute product mass plus 1e-6) over every prefix mask and random hole masks (section 5). The prototype of this reader, measured on one Granite Rapids core on 2026-09-08 with L1-hot data and one query, took 182 ns per page against 222 ns for the row-major dotter at 64 visible tokens (-18%), was faster at every visible count of 3 or more, and slower only at 1 visible token (46 ns against 36 to 45 ns) [exec/g1-20260908/g3-lite.sh, PR3879-codex/single-k-evidence/single_k_probe.md]. Our reader serves 4 heads per K load where the prototype served 1; this is a change in favour of the reader, not yet measured.

3.6 The store: the cost that moves built, cost planned

A row-major K store writes 256 contiguous bytes: 4 cache lines, 4 stores. A VNNI store writes 4 bytes into each of 64 cache lines (16 rows of each of 4 panels). Our store does it with 4 VPSCATTERDD instructions of 16 dwords (one per dim step) from a bf16 row on the stack; the row conversion from the executor's activation type to bf16 is the same conversion the row-major store performed in place.

What is known about the cost of this pattern.

  • The mirror's scalar scatter (64 dword stores in a loop) took 70.9 ns per row on one L2-resident core [exec/results/bench-scatter-20260824.txt], 20.4 us per prefill token summed over 36 layers x 8 heads.
  • In the serving path (rinzler, 8 concurrent short prefills through the nightly's harness), the G1 probe's in-place variant of that scalar scatter cost +11.7% TTFT on qwen tp4 (1820 ms against 1630 ms) and +8.0% at 1 user; the arena placement of the mirror added about the same again [exec/results/g1-20260908/summary.md]. This is the single number that made the breakup plan's single-K gate read FAIL at the agreed 2% threshold.
  • In the runtron batch prefill path (8 users, prompt 8192), the same probe cost +1.1% of prefill time (63.01 s against 62.34 s), and its decode was +10.3% faster than row-major AMX (18.67 against 16.92 tok/s per user) because it used the mirror kernel [exec/results/g1-20260908/summary.md].

Expectation for this design (est., to be replaced by the measurement): the scatter instructions replace 64 scalar loads and stores plus their address arithmetic with 4 loads and 4 scatters, so the store should cost less than the probe's 70 ns per row; the cache-line count (64 per token) is unchanged, and in prefill the 64 tokens of a page hit the same 64 lines of the same 16 KiB plane, which stays in L1 or L2 across the page. The measurement in section 6 is the arbiter for TTFT at 1024, 2048 and 8192 tokens; section 7 lists the block-transpose optimization that removes the partial-line stores if the measurement says the store dominates.

3.7 The FPGA path built (adapter), cost planned

Hardware attention does not read the CPU pages directly: gof::populate obtains one K row per token and KV head through page_info::k_head_fn and shuffles it into the FPGA staging block (4 tokens = 8 KiB), which is then copied to the card [src/tron/gof.cpp, h/pos/hwattention.hpp shuffle_k_head]. For a VNNI slot the callback now gathers the row into caller-owned scratch (4 gather instructions) and the shuffle proceeds unchanged, so the bytes that reach the card are identical. The cost per GOF token is 4 gathers (one 256-byte row) per KV head: 128 gathers per GOF for 8 KV heads, est. 1 us per GOF and layer, est. 9 ms of extra staging work for a 1024-token prompt over 36 layers, on the staging path that runs at the workers' idle points. It is not exercised by the Monday measurement (USE_HW_ATTN=0 selects CPU attention) and it is the G2 gate item of the breakup plan (a hot and a cold measurement of gof_populate). The direct shuffle from the plane (read dim pairs straight into the staging order, no row) is the planned optimization if G2 says the gather costs.

3.8 Kill switch and rollback built

TRON_AMX_DISABLE=1 keeps the layout: a TRON_K_VNNI binary then runs the AVX-512 VNNI reader on every page. It is a same-layout AMX-off arm and a valid emergency switch, but not a rollback to the row-major binary's numerics (the add order of the two software readers differs). Rollback to row-major storage is the row-major build. The Monday test therefore takes its AMX-off and AMX-baseline arms from the row-major binary of the base commit (p0perf13), and adds the VNNI binary's kill-switch arm as a fourth cell that isolates the AVX-path change [section 6].

3.9 What this design does not do

  • It does not change head sizes other than 128 (gpt-oss, head 64, keeps row-major K and never runs AMX attention).
  • It does not change the AMX gate (head 128 and kv_mul 4 with a bf16 executor); a head-128 model with another kv_mul (llama-3.2-3b, kv_mul 3) gets the VNNI layout and the AVX-512 reader with 3 accumulators, not AMX.
  • It does not add a run-time layout switch, a second copy of K, or new memory.
  • It does not touch the V plane, the PV kernel, or the softmax update.

7. Risks, open items and follow-ups

  • Store cost in the serving path. The G1 probe's scalar in-place scatter cost +11.7% TTFT with 8 concurrent short prefills (section 3.6). Our scatter is vectorized but touches the same 64 lines per token. Measured 2026-09-14 (Monday report 7.1): TTFT +2.2% at tp2 and +7.8% at tp4 at prompt 1024, +4.9% at tp4 prompt 2048, gains at prompt 8192. Follow-up: in prefill, save_k receives the K of a whole pass; transpose 16 tokens of one page at a time in registers (a 16 x 16 dword transpose per panel) and write full 64-byte lines, so the partial-line stores disappear, and/or stripe the save_k token loop over the idle helper threads. Decode keeps the per-token scatter (one token per user per step).
  • Who runs the store, and false sharing (checked in the code, corrected 2026-09-14 after the measurement). For ingested plugins (qwen, the model measured) save_k is a statement of the forward pass's main thread: once per layer and pass it loops serially over the pass's tokens (at most 1024, one minibatch per pass) and the 8 KV heads, the helper threads skip it, and the attention over the pass's own pages waits for it [ingest/src/TronCpp.hs:262-263, 2212, 2279, 2309-2353; model.hpp save_k_impl; self_attention.hpp:782-788]. For the handwritten llama plugin save_k runs once per minibatch inside the WK completion callback on the RX worker of the last tensor-parallel shard [h/tron/plugins/llama.hpp:967-1025, h/tron/hardware/tensor.hpp:333]. In both cases one thread writes a page's plane during a pass, so two threads write the same cache lines only at a minibatch boundary inside a 16-token block (handwritten plugin) or never (ingested plugin). The cost that remains is serial per-token store work on one thread that does not shrink with more cards or cores; the measured TTFT at tp4 (Monday report 7.1) shows it. Remedies: the block transpose above, or striping the save_k loop over the idle helper threads by 16-token block (tokens write disjoint bytes in this layout).
  • The AVX-512 reader pays a whole 16-token block for a sparse block. qk_group scores every block that has at least one live token at the full block cost (64 masked loads, 256 broadcasts, 256 VDPBF16PS at kv_mul 4, about 576 instructions), where the dotter costs about 68 instructions per live token. In decode the partial page holds 1 to 63 live tokens, so its QK cost follows a period-16 sawtooth instead of a line; at 1 live token the reader issues about 8.5x the dotter's instructions (est. 0.2 us extra per (partial page, KV head, layer) at that step), and it is cheaper than the dotter from about 8 live tokens on, so the average over a page's fill favours the reader. The measured single-query prototype showed the same shape (slower only at 1 visible token). Not a defect; a cost-model fact to keep in mind when reading the decode TPS at short prompts. A per-token fallback for blocks with one or two live tokens is a possible refinement.
  • Page copies that are not page-aligned. copy_storage_slot takes the whole-page memcpy only for a full page at offset 0; every other range moves token by token (4 gathers and 4 scatters per token, est. 9 k cycles per page and KV head against one 16 KiB memcpy). book::append splices a child's book at the parent's current length, so a splice that is not a multiple of 64 moves every page of the child token by token, under the tree lock. Not exercised by the Monday cells (one prompt per user, no tree merges); a same-offset masked-row copy and a block-aligned copy are possible refinements.
  • FPGA staging cost (G2). The gather adapter adds 4 gathers per KV head per GOF token on the staging path; unmeasured here (CPU attention in the test). Follow-up: shuffle straight from the plane, and measure gof_populate hot and cold.
  • Same-layout kill switch. Section 3.8: the kill switch is not a numerics rollback. Operators who want the row-major binary must deploy it.
  • Other kv_mul values. The reader handles any kv_mul (accumulator count), but only kv_mul 4 is measured. llama-3.2-3b (kv_mul 3) would run the reader on every page with AMX never engaging; not measured.
  • CI coverage. The CMake CI lane builds with TRON_AMX_DISPATCH=ON and TRON_K_VNNI OFF; the new unit test runs there against the row-major slot. A VNNI lane (or a matrix entry) is needed for the VNNI-specific cases to run in CI; the AMX case still executes only on an Intel runner. New tests also need cost-data entries (bin/slice bench --update) before a PR can pass the slice check.
  • Poison in dead slots. The reader never loads a dead token's lanes (asserted by the test with NaN poison). The AMX kernel reads the whole plane of a dense page, which the dense predicate guarantees is fully written, as the row-major kernel already assumed.
