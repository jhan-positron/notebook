Find where FPGA-attention decode loses time

Trace the K-layout regression in Tron issue #4500. Prove which work delays the next token before choosing a fix.

Source reviewed: clean PR #4424 head 30c4ac82cbb6959f7e4f66b29efb36f5e0749b48. Historical measurements below belong to their recorded builds. Proposed events and experiments are labeled separately.

Short version

Compare otherwise identical builds with the key-cache layout off and on, then follow each four-token upload from CPU storage through hardware availability. Measure both direct upload delay and extra CPU attention caused by late uploads. Confirm the cause with an intervention that removes the suspected delay and restores untraced decode speed.

Attention keys, values, and queries. A KV page is a 64-token cache block. A slot identifies persistent K/V storage for an attention operation.
VNNI layout, row-major, bf16
VNNI is the pair-interleaved key layout introduced by PR #4424. Row-major keeps each token's values contiguous. bf16 is the 16-bit floating-point representation used for these cached keys.
CPU, AMX, AVX-512
CPU is the central processor. AMX and AVX-512 are its matrix and vector instruction sets. TRON_AMX_DISPATCH compiles the AMX path. TRON_K_VNNI selects the K layout at build time.
GOF, populate, cooperative queue
A GOF is a group of four saved tokens. Populate prepares its K/V upload buffers. Workers drain the cooperative queue while they can help with those uploads.
Layer, CPU tail, critical path
A layer is a repeated model block. The CPU tail is the part of attention not covered by available hardware data. The critical path is the chain of dependencies that determines when a forward or token finishes.
Perfetto, flow, span, ID, SQL
ID means identifier. SQL is the query language used for trace analysis. Perfetto records timed events. A flow links work across threads. A span is an interval between a recorded start and end.

Client time per token is reconstructed as mean(1000 / request_TPS) from the raw request rates. The harness divides 128 tokens by its timed capture interval. This is not 1000 / mean(TPS), and it is not an engine-forward duration. [testlib/tps.py:450–456, 501]

Correct the latency target. The TP4 client loss is 0.817009 ms/token using the individual measurements. The issue's “about 0.3 ms per step at tp4” is inconsistent with those data. The TP2 loss is 0.282979 ms/token. Do not divide these per-user intervals by the user count to invent an engine-step cost.

Evidence that still needs controls

Insufficient data: no matched trace in the reviewed evidence assigns the loss to a stage. The required measurement is a correlated engine trace with fixed build flags and matched token windows.

2. Trace the whole upload dependency

1 · Save K and VWrite CPU cache rows. Credit completion for each saved token.
2 · Queue a complete GOFFour tokens with both K and V saved make the upload eligible.
3 · Prepare and submitA worker gathers keys, prepares buffers, and submits transfers.
4 · Observe availabilityCompletion polling updates the hardware prefix used by later plans.

Dependency diagram; widths do not encode time. The scheduler can drain remaining preparation work before the forward ends. [model.hpp:3146–3188]

  • The gather is bursty. GOF readiness requires eight save credits: K and V for each of four tokens. Population can also repeat after staging eviction or backfill. Record counts and reasons instead of assuming one populate call per generated token. [gof.hpp:353–364; gof.cpp:188–221]
  • The layout changes more than upload. It changes key stores and the CPU attention reader too. The remaining CPU work can use dense AMX pages or the masked AVX-512 qk_group reader. That reader does not reconstruct each K row with the upload gather. [Save K; CPU attention dispatch]
  • Delayed upload can add CPU work later. The hardware plan uses a snapshot of the completed prefix. Current attention launch does not wait for current K/V transfers. Follow an upload through the next plans that could use it. [boundary snapshot; hardware launch]
  • The default engagement threshold is query position 127. Keep USE_HW_ATTN unset in the primary campaign. An override can disable hardware attention or raise the threshold. Queries below the threshold stay on CPU attention. This does not mean the first 127 keys remain CPU-only for every later query. Record the actual split for every traced query. [per-query hardware gate; environment override]

Keep the probes smaller than the effect

  • The first patch adds coarse correlation IDs and counts to existing parent spans. Enabling hwattention-detail also enables existing per-row shuffle spans. Measure that cost. If it is too high, place coarse population probes in a separately gated category. Add per-row K/V timing only in a short second capture.   • Guard trace-only work with the repository category/window gate. Use common/perfetto.hpp. Its application gate can be bypassed by including the raw Perfetto header directly. [perfetto.hpp]
  • No allocation, formatted log output, globally locked statistics, or atomic increment per gather lane. Do not reorder loops to create convenient large spans.
  • Proposed overhead gate: the upper confidence bound for instrumentation cost must be below both 1% of baseline token latency and 10% of the reproduced A/B latency gap. Check original→dormant probes and dormant→recording separately in both arms. Measure overhead inside matched selected-token windows. If the gate fails, remove detail or reduce probe frequency and rerun the check. Shortening a capture reduces file volume; it does not reduce per-token probe cost.

5. Capture settings that actually contain the evidence

The default capture hides the suspected function. At the reviewed revision, perfetto/runtron.cfg disables both hwattention-detail and driver-detail. The local tracing reference describes an older default. Use the current config as authoritative and flag the reference for correction. [runtron.cfg:53–65]
  • Create a private capture config. Include model, scheduler, hwattention, hwattention-detail, driver, gen, and rinzler. Include matmul to account for the rest of the forward. Enable driver-detail only when investigating driver admission or queues. Verify actual category names in the trace.
  • Enable kernel scheduling events and process/thread metadata for the traced engine. These separate CPU residency, runnable delay, and sleep. Explicit wait probes distinguish spin-wait from useful work while Running. The default runtron config does not provide that scheduling evidence.
  • Use the repository's pinned Perfetto capture binaries and trace processor. Use private producer/consumer sockets shared by the selected engine and capture processes. If several engines are captured together, attach them to one deliberate trace session.
  • For rinzler, start the external session and signal the exact engine process IDs with SIGUSR1. Do not use killall. Rinzler has no runtron trace flag. The external config controls its session length.
  • For a runtron diagnostic, use bin/runtron through the approved route. --trace-gen with --trace-passes selects forward passes, not generated-token indices. Establish the mapping first. Avoid assuming the legacy in-process file capture's fixed five-second window contains the desired late-decode interval.
  • If FPGA counters are needed, verify the hardware tracer thread is started and pinned away from worker/driver cores. Runtron's --tracer-core starts that counter reader; it does not start a trace. Keep the same tracing-core reservation in the control.

6. Measure work, then measure how much was exposed

The primary outcome is a matched server token interval. Link each token-ready event to its producing forward. Include gaps between forwards. Retain the original client TPS alongside it. A forward can batch several users, so a per-user client interval cannot be replaced by a total forward duration divided by batch size.

Work accounting

  • K-store time and combined K-read/K-shuffle time per row, GOF, layer, and generated token.
  • GOFs queued, populated, rebuilt, and transferred; useful and submitted bytes.
  • CPU rows by reader and per-query hardware coverage.
  • Wall time, time scheduled on a CPU, and runnable delay for synchronous spans.

Dependency accounting

  • Queue delay and host task completion that postpones the forward-end barrier.
  • Hardware-plan availability and extra CPU attention on following forwards.
  • Driver admission and observed hardware-result latency.
  • The final unfinished dependency that delays attention output or the next forward.

For each complete forward, build a dependency graph from per-thread order, GOF flows, hardware requests, and explicit join-ready events. Follow the last dependency to complete at every join. Partition the resulting wall-clock path into nonoverlapping stage intervals. Keep any interval without a proven dependency as unattributed.

queue delay           = dequeue − ready
host preparation      = task end − dequeue
observed transfer     = completion observation − DMA publication
server token interval = token-ready(i) − token-ready(i−1)

measured A/B interval change
  = change in nonoverlapping critical-path stage intervals
  + change in unattributed time
  • Subtract the union of nested child intervals to compute exclusive parent time. Do not add gof_populate to its own K-read and shuffle children.
  • Do not add simultaneous worker waits, asynchronous hardware service, and CPU work as elapsed time. Report total CPU work separately from exposed delay.
  • A worker shown as Running can be spinning. Split useful compute from explicit wait spans. Apply CPU-residency joins only to spans owned by a single thread.
  • A completion poll gives host observation time. If the previous poll was incomplete, completion lies between that poll and the successful one. Do not report this envelope as pure DMA or FPGA execution time.
  • Analyze several consecutive forwards. Longer population can affect a later hardware-prefix snapshot without enlarging the current forward's GOF barrier.

Required wall-clock view

The final analysis must show one lane per scheduler, worker, DMA queue, and FPGA attention request. Use a shared time axis with durations to scale. Solid blocks mean work; dashed outlines mean waiting, including spin-wait. Mark the measured serial delay in red. Retain tiny intervals at their true width and label them outside the block.

Compare distributions by engine, layer, CPU/hardware split, GOF population reason, and absolute token position modulo four. Also inspect position modulo 16 and 64 for layout-block and page boundaries. Record mean, median, p95, counts, and totals normalized by actual completed tokens.

Strongest test of the gather hypothesis

Diagnostic intervention, not a proposed shipping fix

  1. Add a row-major K copy to the VNNI build solely for this experiment. Allocate and maintain the copy in both diagnostic arms. Write it from the same completed K values with the same lifetime and readiness ordering.
  2. In arm C-gather, keep staging reads from VNNI. In arm C-direct, change only k_head_fn to read the row-major copy. Keep VNNI storage and CPU attention enabled in both.
  3. Check exact staged K/V bytes for the same saved tokens before timing. Check model outputs for the matched workload. Do not skip staging, send dummy data, or remove the GOF barrier.
  4. Compare C-gather→C-direct with tracing off and on. Require the net K-read/K-shuffle change, its critical-path or later-tail effect, and the server-token recovery to agree. Return to C-gather and confirm the effect returns.
  5. Compare C-gather with original B. The extra copy changes stores, memory use, and cache state. If it changes the original behavior materially, report that limitation and test a gather optimization in original B before generalizing.

A four-token gather microbenchmark can explain instruction and cache costs. Sweep relevant warm/cold states and worker placement only after the trace indicates their relevance. Preserve actual output and consume a checksum. Its result cannot establish an end-to-end root cause by itself.

Use hardware attention off or AMX disabled only as secondary controls. Hardware attention off also removes staging and changes the workload. AMX disabled retains the VNNI layout and changes the CPU reader. Neither is a selective gather test.

8. Acceptance, implementation order, and open evidence

Root cause is established when

  1. The untraced loss reproduces with matched flags, routing, and workload beyond A/A variation.
  2. A verified trace shows the suspected work delaying token completion, directly or through later CPU work.
  3. A selective, correct intervention removes that delay and improves untraced token latency across independent blocks.
  4. Restoring the behavior restores the delay. Any residual loss is quantified and remains explicitly unattributed.

Proposed numerical acceptance

The trace overhead passes section 4's gate. Complete critical-path accounting leaves a residual no larger than the greater of the A/A uncertainty bound and 10% of the reproduced latency gap.

Call a mechanism a partial cause when it explains only part of the loss. Report the recovered fraction with uncertainty. Crossing 135 TPS alone does not establish a cause or recover the baseline.

Implement in this order

  1. Identity and baseline patch: forward/sequence mappings, GOF queue flows, build manifest, and trace coverage checks. Reuse existing spans.
  2. Targeted timing patch: key stores, K/V read split, queue/lock boundaries, transfer observations, and actual CPU/hardware coverage. Enable detailed probes only where the first trace leaves a gap.
  3. Analysis script: read with the pinned trace processor; validate trace loss and IDs; produce per-forward, per-GOF, and per-request tables. Build dependency paths with an explicit unattributed category.
  4. Selective diagnostic: implement only the intervention supported by the trace. Verify relevant existing storage, staging, and model tests before DUT timing. Register any committed new test in an existing required CI suite.
  5. Report: preserve manifests, raw client records, traces, query files, and exclusion reasons. Export a light-theme HTML report with paired-rate dots, measured wall-clock lanes, exact tables, and a bounded conclusion.

Checks that protect the investigation

  • A sampled GOF must connect readiness, dequeue, preparation, each transfer, and completion observation without ID collision after reuse. Multiple device transfers are allowed; unexplained duplicates are not.
  • Hardware and CPU coverage must match the plan used for each query, with no missing or double-scored range. Record bounds and query masks needed to verify this.
  • Tracing must not change staged bytes, readiness order, or outputs under identical execution. Validate trace loss, overhead, and selected-token coverage before trusting timing.
  • Keep a record of every attempted run. Reject invalid runs under predeclared rules, preserve their logs, and repeat the whole affected block.
