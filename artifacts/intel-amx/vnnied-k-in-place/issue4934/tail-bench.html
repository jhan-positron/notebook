Issue #4934: the tail-row score paths, measured one visit at a time

tail_bench on delphi-3bda, 2026-10-16 13:18 to 13:22 UTC, two runs. Page generated by exec/i4934-20261015/bench/bench_page.py from exec/results/i4934-tailbench/.

Short version. The fix scores the row-major tail rows of a KV page one row at a time (the dotter path), and this benchmark measures that path against PR 3's block reader for the same tail block. The dotter path is cheaper per visit in every cache scenario, by -97 ns when hot and by -333 ns in the one-decode-step scenario, which is -5.6 to -57.8 us per decode step in the fix's favour against a measured gap of +156 us. So the tail-row scoring does not cause the remaining 1.1 % decode loss, and a 16-row tail-block kernel has nothing to recover: the best candidate equals the dotter path within 3 ns.

Words used here

  • tron: the inference program under test. qwen-3-4b: the model of every number here (36 layers, 8 KV heads, 4 query heads per KV head).
  • KV page: 64 tokens of a user's K and V state. Block: 16 tokens of a page. Tail block: the page's newest, incomplete block. Live rows n: how many of its 16 tokens exist (1 to 15).
  • VNNI block: a block stored in the layout the AVX-512 (Advanced Vector Extensions, 512-bit vectors) bf16 dot-product instruction reads, one token per vector lane, 64 cache lines of 64 bytes. Row-major row: one token's K vector stored as it is, 256 bytes, 4 cache lines.
  • PR 3 (#4898): every token is written into its VNNI block at once, so the tail block is always a VNNI block. PR 4 (#4901): tail blocks stay row-major until complete, then convert. The fix (branch jhan-vnnik-5-i4934, head b87d20dd81): PR 4 plus the issue #4934 repairs.
  • Kill switch: TRON_AMX_DISABLE=1, the AMX (Advanced Matrix Extensions) kernels off at run time, the AVX reader runs. All decode numbers here are kill-switch numbers.
  • kv_mul: query heads per KV head (4 for qwen-3-4b, 8 shown as a second case). Visit: one worker scoring one tail block against one KV head's query group for one user.
  • Arms: dotter = the fix's path (kv_mul dot-product objects built per visit, one row at a time). reader = PR 3's path (k_vnni::qk_group on the VNNI block, all 16 lanes). rowbat = candidate: row loaded once, dot products into per-head accumulators. xpose = candidate: rows transposed in registers into VNNI order, then scored like the reader, no memory write. tmpblk = candidate: rows packed into a temporary VNNI block in memory, then the reader.
  • TPS: decode tokens per second per user. TTFT: time to the first token (prefill). est.: an estimate, not a measurement.

1. The per-step budget: what the gap needs against what the tail visits cost

Round 2 measured the fix 1.1 % below PR 3 in decode TPS at tp2 prompt 1024 (kill switch). One decode step takes 14,195 us there, so the gap is 156 us per step. Each attention worker makes 57.6 tail visits per step (36 layers x 4 KV heads per engine x 8 users / 20 workers). For the tail-row scoring to explain the gap alone, the dotter path would have to cost 2,711 ns more per visit than the reader. The benchmark measures the opposite sign in every scenario.

The red bar is the measured loss. The blue bars are what the fix's tail visits cost relative to PR 3's, converted to one decode step: they are negative in every scenario, so the tail visits save time. The 1.1 % comes from somewhere else.

7. Method and lineage

  • Program exec/i4934-20261015/bench/tail_bench.cpp, compiled with the compiler and flags of the fix tree's own test t_k_vnni_layout.cpp (clang 19, -O3, -mavx512bf16, the AMX and VNNI defines) inside the nix shell of /var/tmp/jhan/tron-i4934 at b87d20dd81. It includes the tree's real kernels: k_vnni::qk_group, dotter, row_major_row, store_row, store_row_major, store_block.
  • # tail_bench reader_cpu=72 writer_cpu=90 tsc_ghz=2.7000 iters_hot=20000 iters_cold=3000. The reader core and the writer core are first hyperthreads of socket 1 (our half of the machine) whose siblings were idle. Timing by rdtscp. Per cell the median, p10 and p90 of 20,000 iterations (hot) or 3,000 iterations (other scenarios), the first tenth discarded as warm-up.
  • Machine state: the nightly CI had released its lease at 13:16 UTC. Two rinzler (production server) processes left by the nightly were running (load average 127 on 288 logical CPUs), pinned to other cores. 13 core pairs of socket 1 were idle. This is not a quiet machine, which is why the cold scenarios show run spreads up to 43 %. The sign of every difference is the same in both runs.
  • The step scenario is the one that matches decode: the newest token's K was just written by another core (the main thread's Save K), the older live rows come from L3. For the reader arm the writer uses PR 3's per-token scatter store into the VNNI block (store_row), for the row arms the fix's row store (store_row_major).
  • What the benchmark does not cover: the softmax and PV (probability times V) work after the scores, the conversion of a completed block (3.6 us per block, pooled, measured in round 1 traces), the Save K write cost on the main thread (hidden under the workers in both arms, round-1 traces), and any effect of code layout in the full binary.
  • First launch at 04:11 UTC failed at the link step after the lease was released (libgcc_s not on the command line, undefined _Unwind_Resume). bench-run.sh gained -lgcc_s, and the second launch at 13:17 UTC compiled in 17 s and ran both runs in 97 s each.

8. What this means for the open 1.1 %

  • Refuted: the hypothesis that scoring the row-major tail rows one at a time costs the 1.1 % (the round-1 ablation a1 attributed 1.2 % to it). The tail visits are cheaper in the fix than in PR 3 in every cache state measured here.
  • Why the ablation disagreed, as a labelled hypothesis: ablation a1 forced every live token through the reader, which made the dotter code dead and let the compiler lay out the attention loop differently. The attribution would then be a code-layout effect, not a scoring cost. Test: build the fix with the split decided at run time (an environment variable) so the code stays, and measure a1 again.
  • Where else to look, with the measurement for each: the round-1 traces put the loss inside the workers' attention spans (+4.8 ms summed over 20 workers per step at prompt 1024, +215 us on the slowest worker) with the same instruction count and lower IPC, so it is spread over all page visits (about 20,000 per step), not the 1,152 tail visits. Candidate: more cache misses per page visit. Test: perf stat of L2 and LLC misses per attention worker, fix against PR 3 against PR 4, and a count of the page-object cache lines each arm touches per visit.
  • Option (b), a 16-row tail-block kernel, is not worth building for this gap: rowbat equals the dotter path within 2 to 41 ns per visit, xpose and tmpblk are slower than the dotter path for most n.
