Short version. The fix idea for issue #4500 was built on a side branch (not pushed, PR #4424 untouched), and on the two FPGA-attention cells (test configurations) it removes about a third of the loss of the VNNI layout (40 % of the extra step time at tp2, 29 % at tp4). That fix-vs-vnni change is NOT resolved at n = 3 (paired t 1.6 at tp2 and 1.8 at tp4 against the 4.30 threshold), and the generated tokens are identical to the PR head under FPGA attention. Two unit tests failed at the measured commit 617cb8333f, and three later commits (branch head f34b0fe2ec) make all 10 + 42 cases of the two test binaries that had failed pass in both builds, without a re-measurement of throughput or tokens.

2. What the problem was

  • PR #4424 stores K in the VNNI layout: one token's 256 B row lies as 4 B in each of 64 cache lines, not 4 whole lines [root-cause-debug.html:29].
  • Three CPU operations of decode under FPGA attention access it per token [root-cause-debug.html:17, :104-106]:
    • the K save on the main thread. It does 64 read-for-ownership fetches (the core reads each of the 64 lines before it writes 4 B into it).
    • the K-row gather for the card.
    • the workers' tail scoring (the tokens after the last complete block).
  • In the nightly configuration the card launches after the K save. The save is therefore in series with the card [model.hpp:91-105; store-remedies-report.html 0.5; root-cause-debug.html:53]. That configuration is 2 users per engine at tp2, below the early-launch threshold TRON_HWATTN_EARLY_LAUNCH_MIN_B (default 4: a batch of 4 or more users starts the card before the K/V saves).
  • A micro-benchmark measured the VNNI store at +350 ns per row over the row-major store [root-cause-debug.html:17]. In runtron (tp2, 8 users) the per-layer K save grew from 4.6 to 20.3 us. That is +0.57 ms per step, 7 % of the 8.0 ms step [store-remedies-report.html 0.5].
  • On 2026-09-19 (m6, one batch of cells in the 2026-09-18 issue-4500 campaign, n = 2) the PR #4424 package lost 4.3 % TPS at tp2 (2 users per engine) and 13.4 % at tp4 (4 users) against a nightly package without AMX code [issue4500-20260918/m6/summary.md].

3. What the fix does

A 16-token K block stays row-major until all 16 rows are saved. The main thread then converts it in place, once, at the end of the forward pass that saved the 16th row. Both layouts use the block's own 4 KiB [k_vnni.hpp:240-253]. A decode step thus writes and reads 4 lines per row, not 64 [kv_cache.hpp:709-712].

Figure 1. Top: one 256 B row, row-major (green) or VNNI (orange). Bottom: the four states of a block in decode. State 1 is read by the dotter and by memcpy, and state 4 by qk_group and gather_row [kv_cache.hpp:740-746, :1875-1886, :1916-1928; self_attention.hpp:1548-1563, :1596-1610, :1639-1665]. The dashed return path is k_forget_row and copy_storage_slot (book::append's page copy) [kv_cache.hpp:2141-2146, :2204-2241, :2384-2500]. k_forget_row runs from clear_kv_complete_at (the routine called when a new token takes a page offset) under the token-tree lock (the lock over all live requests' tokens).

  • State bits. Per storage slot (one K and V store of the book) plus an EAGLE entry: k_rows_saved_ (a bit per page offset) and k_vnni_blocks_ (a bit per block). A block bit implies its 16 row bits [kv_cache.hpp:2262-2274]. k_state_ix(slot) picks the entry and asserts slot.i < logical_slot_count() [kv_cache.hpp:2163-2166].
  • Conversion (states 2 and 3). After wait_for_coop_gof() (the drain of the GOF staging, GOF = group of four tokens staged for the card) the main thread converts each queued block per KV head through a 4 KiB stack copy. It then publishes the block bit with a release store (a reader that sees the bit sees the bytes) [model.hpp:1711-1716, :2820-2825, :3080-3093; kv_cache.hpp:1797-1813, :1843-1866]. A full 16-token prefill run (a run is the consecutive tokens of one block that one save call writes) skips the states. set_k_block still transposes such a block in registers [model.hpp:2945-2980].
  • Why the forward end, not save_k. A block can be split across two minibatches (groups of 8 tokens) of one pass. The GOF staging gather of the earlier minibatch may then still read the block row-major. At the same time the later minibatch saves the block's last rows. The attention workers read a pending page (the page this step's tokens are written into) only after every writing minibatch counted its latch (a countdown) down [kv_cache.hpp:681-694; model.hpp:2803-2810].
  • Removed (diff: 8 files, +1132/-100 lines):
    • set_k_block's present-mask parameter (the bit mask of rows present in the run) is gone [PR head kv_cache.hpp:1726]. The local variable present still ends a run at a repeated offset [model.hpp:2939]. It also feeds the TRON_ASSERT that a 16-token run covers its block [:2964].
    • K_SCATTER_RUN_LEN_1 (the PR head's constant: only a 1-token run took the per-row store path) is gone [PR head model.hpp:2794, :2914]. Now every run of 1 to 15 tokens is row-major (n < K_STORE_BLOCK_16) [model.hpp:2945].
    • The partial-block save of 2 to 15 tokens is gone [amx_attn_iface.hpp:219-226].

qwen3-4b tp2, 1 user, temperature 0 (greedy: always the top-scoring token), --pay-for-determinism, seed 1 [smoke.sh:2-8; smoke/smoke.txt].

  • A CPU-attention difference is of an allowed kind. The fix scores a tail block with the dotter, the PR head with qk_group. Both add the same VDPBF16PS products (the bf16 dot-product instruction of AVX-512, Intel's 512-bit vector instructions) in a different fp32 (32-bit float) order. A score can therefore differ at a bf16 tie (two candidate tokens with equal scores at bf16 precision). One flipped greedy token changes all later ones [k_vnni.hpp:311-313; smoke.sh:6-8].
  • Not yet proven to be only that: 128 greedy tokens cannot tell a tie flip from a numerics defect. The proof would be a forced run (teacher forcing with --force-feed-text-token-file) of both binaries at prompt 1000. It would compare the Top-k Logits record (tron's dump of a step's highest per-word scores, the logits) at the first divergent step, token 6.
  • Identical FPGA-attention rows are consistent with equal K bytes reaching the card, not a proof. A dump of the K plane (the K storage bytes) or a checksum of the staged rows would be one.

6. Reading: what the numbers say and do not say

  • They say: llama-8b keeps the VNNI gain (Table 2). The FPGA-attention loss shrinks, and no fix-vs-vnni pair is resolved.
  • They do not say that the fix works, nor why two thirds of the loss remain. Hypotheses, each with its deciding measurement:
    • H1: the forward-end conversion is a new serial main-thread cost (4 KiB read and written per block per KV head). Measure: a TRON_CHECKPOINT span (tron's timing macro) around convert_pending_k_blocks().
    • H2: the row-major tail readers still cost more than base. Measure: Perfetto (the tracing tool) spans of the workers' pending section and the staging copy, fix against base.
    • H3: the per-row save is still slower than base (row-bit bookkeeping). Measure: the root-cause page's per-layer K-save micro-benchmark (section 2) on the fix binary.
    • H4: an AMX-side part remains at tp4 (the kill switch recovered +6.8 % TPS there on 2026-09-19 [m6/summary.md]). Measure: fix with TRON_AMX_DISABLE=1 against fix, n = 3.
    • H5: the tp4 two-group spread hides the effect. Measure: 6 or more repetitions of the two qwen cells.
