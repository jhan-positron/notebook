Remove the need for construct_kv_blocks()

Short version: use one real bf16[] array per cache allocation, then return typed K and V views into that array. Remove the kv_block and packed-V owner objects overlaid on byte storage. The allocation boundary must establish the array’s lifetime before the cache receives it.

// book owns scalar arrays through the corrected typed DMA allocator.
hardware::unique_dma<bf16[]> payload;

// Each accessor creates a view by value over live array elements.
auto k = page.k<geometry>(slot, head);
auto v = page.v_packed<geometry>(slot, head);

The sketch shows the implemented ownership contract. Compilation is still pending. A returned view borrows storage; it does not own or create the array.

1. Ownership and access describe different objects

The cache’s book owns byte arrays. Its accessors interpret those allocations as arrays of kv_block, each containing K and V for one attention head and cache page. The new v_vnni_tensor owns an inline packed-V array inside each block. [S1] [S2]

The middle step changes from constructing objects to selecting existing elements.

The placement-new expression is a valid construction operation. When performed before access with the required storage and alignment, it prevents the missing-lifetime error. The design concern is that book must reconstruct an object hierarchy after allocating a differently typed owner. Calling this operation “dummy” would obscure its actual language role. [S3] [C++23 object creation]

The new member function is not itself the cause. A trivial class can be created implicitly by specified allocation operations. Private data and member functions do not automatically require placement-new. A cast alone is still insufficient. [S2] [C++23 class properties] [C++23 object creation]

B: when typed block ownership is preferable

Allocate blocks through an owner that creates the array and its members together. An ordinary allocating new Block[count] can use a class-specific DMA allocation function. The language then constructs the requested objects as part of allocation. This removes the separate construction pass. [C++23 new expressions]

  • For uniform geometry, retain one typed array for retained storage and one per sliding chunk.
  • For mixed geometries, group owners by block type and retention, or keep a typed owner per slot. The block type depends on head width; differing head counts alone do not require different types. [S6]
  • Separate owners can change allocation counts, rounding and failure points. A generated aggregate of all slots per page avoids some separate allocations, but changes the current slot/head/page ordering. Neither choice is a surgical replacement for the existing heterogeneous arena. [S7]
  • Fill K and V through their own arrays. Do not retain the whole-block bf16* cast.

C: when the payload should remain bytes

Store and retrieve scalar representations with memcpy to and from live local bf16 values. Use byte offsets for address calculations. Vector operations must use documented memory-load/store intrinsics with suitable alignment. The byte allocation itself still needs a valid lifetime contract.

This design cannot keep returning bf16& from packed element access. It also cannot pass an imagined bf16[] to the existing native-K view. Those interfaces must become value-based or byte-aware. The current row and matrix accessors return real scalar references, so this is the largest interface change. [S2] [S6]

3. Recommended scope for this PR

Make typed views the PR’s layout abstraction. Give allocation ownership to a scalar payload owner. The cache does not need a separate C++ owning object at every logical K/V block boundary.

Preserve the physical layout

A block remains a logical region containing K followed by V. For the 64-token, 128-dimension case, each plane occupies 16,384 bytes and the pair occupies 32,768 bytes. These sizes are calculated from two bytes per bf16 element. [S6] [S7]

Native K16,384 bytestoken-major scalar elements
Packed V16,384 bytesadjacent tokens interleaved

Widths are proportional to byte counts. Both regions belong to the same scalar array; neither requires an overlaid class object.

K0 elements8,192 elements64 bytes

Let R be tokens per page, D dimensions per head, P pages in the selected allocation, h the head index, and p the local page index. For a slot starting at scalar offset s, its block starts at s + (h × P + p) × (2 × R × D). K starts there; V starts R × D elements later. This follows the current accessor ordering. [S4]

4. Design A: concrete changes and execution order

One draft PR on top of #4557 is sufficient. Its base is jhan-kv-typed-tensors. Keep the allocation foundation and the cache migration in separate commits within that PR. The final change replaces the storage model as one reviewed unit.

The existing unique_dma owner already records the element count for release. Reuse it. The needed change is its allocation contract, followed by scalar-array ownership throughout the cache. A new general tensor framework or a second allocator hierarchy is unnecessary.

Allocation: make the actual allocation operation create the objects

auto payload = hardware::try_make_unique_dma_for_overwrite<bf16[]>(
    element_count, std::align_val_t{storage_alignment});

// On success, payload owns one live bf16 array.
// It is ready for writes; its values are not yet initialized.

Add a DMA-specific allocating operator new[] overload. It obtains storage from the existing DMA heap. The fallible helper explicitly calls that allocation function with the checked byte count and alignment. Restrict the new path to trivial element types suitable for implicit creation.

C++23 specifies implicit object creation for an explicit call to an operator new[] function. This provides the array and scalar element lifetimes at allocation. The call is the operation that obtains memory; there is no subsequent construction pass over an existing payload. [C++23 object creation, paragraph 13]

  • Call the allocation function directly. An array new-expression can include implementation bookkeeping before its returned element pointer. A direct function call has no array-expression bookkeeping to add to the requested bytes.
  • Keep the current failure-injection point and empty-owner result. Check element-count multiplication before requesting memory.
  • Keep the existing release path with the original allocation address and exact byte count. Avoid changing unrelated DMA helpers.
  • Do not initialize the scalar values during allocation. Existing cache writes remain responsible for valid token data and V padding.

Execute the migration in dependency order

  1. Establish the allocation contract. Review the new allocation function against C++23’s object-creation rule. Compile the helper and exercise existing allocation success, failure and cleanup coverage.
  2. Introduce the borrowed page-region view. Build native-K and packed-V views from its scalar pointer. Keep pointer construction private. A const cache access must produce a const-element view even though page internally stores a reference to its book.
  3. Switch ownership and addressing together. Convert byte counts to checked element counts at allocation. Convert slot offsets exactly. Replace every old block accessor before removing the block type and construction function.
  4. Finish all consumers. Update the random fill, native K, packed V, row-major V and weighted sum. Preserve the even-token partner initialization rule. Search for remaining block casts and vector-array address calculations.
  5. Validate the final implementation. Format the changed C++ files, run focused existing tests, then the repository’s build and host-test gates. Check both lane-count configurations and the AMX-enabled kernel build. Record any baseline failures or unavailable checks explicitly.
  6. Publish the draft. Push the child branch and open the draft against #4557’s branch with the required Skip benchmarks label. Keep it draft while its parent is unmerged. After the parent merges, rebase this PR onto main and rerun affected checks before making it ready.

5. The DMA boundary is part of the solution

Changing uint8_t[] to bf16[] in the current helper is insufficient. try_make_unique_dma_for_overwrite casts the allocator result and skips construction for trivial element types. A typed smart pointer does not itself start an array’s lifetime. [S10]

The real backend delegates to a custom DMA heap. The fake backend calls aligned_alloc, which has standard implicit-object-creation semantics. Tests using that fake do not establish the real heap’s lifetime contract. [S11] [C++23 allocation functions]

The proposed owner must provide all of these guarantees:

  • Its returned pointer addresses the first element of one live array of the requested extent. Element lifetimes have begun before any view is published.
  • Allocation preserves 64-byte plane alignment, checked size arithmetic, fallible allocation behavior and the existing DMA mapping.
  • Default initialization does not clear the full cache. The existing even-token V append still initializes its odd partner before readers may consume it. [S9]
  • Reclamation invalidates all borrowed views. Restoration allocates a fresh live array before publication; callers must reacquire views.
  • Deallocation retains the correct original address and byte count, including any bookkeeping required by the chosen allocation mechanism.

The implementation in section 4 now supplies this boundary through the DMA-tagged allocating operator new[]. It preserves the original allocation pointer and byte count. Insufficient data: compiled behavior and runtime tests remain unverified until the build and test hosts are available.

Changes that only replace the spelling

  • std::construct_at still performs placement construction. It does not resolve the ownership mismatch. [C++23 construction]
  • std::start_lifetime_as_array explicitly starts an array lifetime. It can serve an allocator contract, but substituting it into this function retains the same delayed construction design. [C++23 lifetime management]
  • A pointer cast, std::launder, or a std::span cannot replace the required object creation. Neither size/alignment assertions nor unchanged machine instructions prove that an object exists. [P0593R6 §3.2]

6. Acceptance criteria for the redesign

These are acceptance criteria. The implementation status below distinguishes completed source checks from pending compiled tests.

  1. Lifetime proof: identify the operation that creates each allocation’s array and elements. Show that every scalar pointer calculation stays within that actual array. Show that views do not survive reclamation.
  2. No overlaid owners: for A, remove construct_kv_blocks, all casts to kv_block*, and whole-block scalar casts. Inspect both lane-count builds and the software weighted sum.
  3. Layout equivalence: compare old and new K/V addresses for every supported geometry, retention group, chunk boundary and EAGLE offset. Verify plane alignment and exact bytes through append, copy and restore.
  4. Existing behavior: run the relevant t_llama_unit cases for mixed geometry, mixed retention, transactional restoration, allocation failure, EAGLE, append, packed-value bits and padding. Run the applicable typed-kernel checks. [S12]
  5. Allocation and generated code: verify unchanged requested byte counts and failure points for A. Inspect allocation code for unwanted clearing and kernel code for extra work. Performance neutrality requires measurements of the redesigned code.

Insufficient data: Design A is implemented but has not yet been compiled or benchmarked. B and C remain alternatives. The object-lifetime argument covers the changed allocation and access path; it does not certify the entire cache or its concurrency behavior.
