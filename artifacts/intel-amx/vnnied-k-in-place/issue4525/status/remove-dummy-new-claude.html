Issue #4525 · PR #4557 design review

KV Blocks Without Placement New

Reviewed: PR #4557 at head 633cb88896. New design: draft PR #4587 (branch jhan-kv-alloc-creates-blocks, head c73e7fb2f9, stacked on #4557). Compared with draft PR #4584. Written 2026-09-24 (UTC). This version replaces the 2026-09-23 18:43 PDT page, which is kept as remove-dummy-new-claude-r1.html.

Short version

PR #4557 needs construct_kv_blocks because C++ creates no objects in memory from the DMA pool, so the cache starts the kv_block lifetimes in a second pass after each allocation.

That pass repeats the address formula of the accessors and throws away its result, so in strict C++ the accessors still do not point at the objects.

The recommended design, draft PR #4587, lets the allocation call create the objects, keeps the typed V owner inside kv_block, and should be folded into #4557 before its first review.

2. What construct_kv_blocks shows

The pass itself costs nothing at run time. The objdump of the AMX-on t_llama_unit at 1c87d66926 found no rep stos, no memset and no loop in any of the 36 allocate instances. Only a 3-instruction size assert is left [evidence/3bda-first-test/rebase, re-run in this review]. The problem is what the pass says about the design.

  • The pool creates no objects. dma_allocate_aligned is an ordinary function over hugepages, so C++ creates no object in the memory it returns [src/system/memory.cpp:461-469; N4950 [intro.object]/10]. The factory only casts the pointer for trivial types [h/system/memory.hpp:331-336].
  • Main had the same gap. Main reads kv_block through reinterpret_cast of arena bytes and calls its member functions, with no placement new [main 996f58ec82 kv_cache.hpp:1533, 1542, 1578]. Member access on an object that does not exist is UB whatever the member type is [basic.life]/6-7, [expr.ref]/8. So the PR did not create the gap. It made the gap visible, because v became a class with member functions.
  • The pass throws away its result. ::new returns a pointer to the new objects, and the pass drops it [kv_cache.hpp:1476, 1490-1491]. The accessors cast a uint8_t* instead [kv_cache.hpp:1593, 1602, 1642]. That cast still points at the byte, not at the kv_block [expr.static.cast]/14, [basic.life]/8 Note 5. So the Note's sentence "The ::new line above avoids undefined behavior" does not hold as written.
  • The pass is a second copy of the layout. Its heterogeneous branch repeats the slot offset formula of slot_page [kv_cache.hpp:1487-1491 and 1516-1524]. No test can catch the two copies drifting apart. The pass emits no instructions, and the unit-test allocator (aligned_alloc) creates objects by itself [src/pos/fake.cpp:352-357]. Checking its coverage took a model of 24 layouts.
  • The C++23 call is not available. std::start_lifetime_as_array would do this job, but the product's libstdc++ 14.3.0 does not declare it (grep over the nix include tree on delphi-3bda: 0 files).

The defect: object creation is split from allocation. The fix belongs where raw memory becomes typed storage, which is the allocation call.

3. Designs that need no ::new

Five candidates were specified in full. Two more ideas were rejected early:

  • std::start_lifetime_as_array: not in libstdc++ 14.3.0.
  • memmove(p, p, n) (it also creates objects): it would copy every arena, up to gigabytes per book.
  • Moving ::new (raw) U[n] into the factory: it works, but it is still a placement new.

4. Which gaps each design closes

  • G1: kv_block objects exist in production pool memory.
  • G2: the accessor pointer points at the kv_block object.
  • G3: byte arithmetic on the arena happens inside a live byte array.
  • G4: K is read as bf16 values of a real bf16 array.
  • G5: fill_storage_slot (test fill) stays inside one array.
  • G6: scaled_v_expr steps through V with bf16 pointers, not vector pointers.

G5 and G6 predate #4557 and are outside its scope. #4584's scaled_v_expr and fill_storage_slot hunks are a ready follow-up for them. P' closes G2 only in the unit tests. The reviewers found no text against it and no example that shows it.

6. The chosen design: A2-min + K1 (draft PR #4587)

Commit 39a6899446: create the blocks in the allocation

  • system/memory.hpp: tag dma_allocation_t, a global operator new[](size_t, dma_allocation_t, std::align_val_t) noexcept that forwards to dma_allocate_aligned, and Note [DMA allocation creates objects].
  • kv_cache.hpp: construct_kv_blocks, both calls and RECLAIMABLE_FALSE/TRUE deleted. std::launder at the 3 casts. Trivial-type asserts added to the uniform accessor. Note [KV block lifetime] rewritten.
  • Tests: trivially-destructible checks for kv_block and v_vnni_tensor. The fallible factory must return 64-byte-aligned memory.

Commit c73e7fb2f9: K as a plain bf16 array (K1)

  • kv_block::k becomes alignas(kv_block_alignment) bf16 k[page_size * head_size]: the same bytes, alignment and row order.
  • k_view builds its views with no reinterpret_cast. This closes G4.
  • It touches native K, which the agreed design said keeps its storage. It is a separate commit, so it can be dropped alone.

8. Recommendation

Use the new design. Do not merge #4557 as it is. Its Note claims that the placement new avoids undefined behavior, and the discarded result means it does not.

  1. Build and test #4587 on delphi-3bda: done on 2026-09-24 (section 7). Correctness and performance show no regression once code placement is controlled.
  2. Ask the reviewing maintainer the question below. It is drafted here and has not been posted.
  3. If the answer is yes, fold the two #4587 commits into #4557 before its first review. Then update the #4557 body: the Note summary, the two sketch-table rows of section 3 that name the placement new, the section 5 row that says kv_block::k is unchanged (K1), the file list (add memory.hpp), and two wrong claims from the earlier objdump text. The measured range is 68 to 94 instructions, not 68 to 92. The 4 backward jumps go to exits and form no loop.
  4. If the answer is no, ship P' instead. That means std::launder at the 3 casts plus a corrected Note. If only K1 is rejected, drop that commit alone.
  5. #4584 conflicts with #4557 once #4587 lands, because both change the same factory. Closing or parking it is the repository owner's decision. Its scaled_v_expr and fill_storage_slot hunks remain the best follow-up for G5 and G6.

Draft question for the reviewing maintainer (not posted)

In #4557 the kv_block objects (which hold the v_vnni_tensor owner) would be created by the arena allocation call instead of a placement-new pass. The KV book gets its DMA memory through a tagged operator new[]. C++ says a call of a function with that name creates the implicit-lifetime objects that the program then uses (N4950 [intro.object]/13). The accessors reach them with std::launder. No bytes are written. Separately, kv_block::k would become a plain bf16 array with the same bytes. Does this satisfy "The page arena must construct the actual storage type"? If not, we keep the placement new and add std::launder at the three casts.
