3. Is jhan's reading of Ben's reservation right?

Ben's sketch has three parts: a layout struct with a static offset function, a storage owner templated on the layout, and a view templated on the layout. His reservation was: "I'm not entirely convinced of the necessity of separate k_vnni_layout from vnni_view but regardless, it's a starting point". jhan read this as: the layout should be the view, and agreed. The design agrees too and says jhan's interpretation is "mostly right".

jhan's reading is right on the point Ben raised. Ben's doubt concerns only the separate layout type. Folding the offset formula into the view removes that type. Storage stays a separate owner in Ben's sketch, in jhan's reading, and in the design.

Two precisions the design should state instead of "mostly right":

  • Ben's sketch is not a chain layout -> storage -> view. The layout type is a template parameter of both the storage and the view (vnni_tensor<Layout> and vnni_view<T, Layout>), and the view calls Layout::offset. jhan's chain wording describes the dependency, not the shape. Nothing in jhan's reading proposed merging storage into the view, so the design's storage sentence does not correct a mistake (F03).
  • Ben voiced a doubt, not a decision. The design turns it into a rule ("Simplify: each view type contains its address calculation") without saying that the merge is the design's own choice and that Ben should confirm it. The design does fix the resulting type shape (vnni_tensor<R, D>, vnni_view<T, R, D>, no Layout parameter), so an implementer is not left guessing; the verifiers rejected that concern (F06 in section 7). The trade-off is still worth one sentence for Ben: one view type per layout (a V view now, a K view in the child) repeats the const conversion, the deleted rvalue access and the friend accessor, instead of one template over a layout parameter.
  • The design departs from Ben in three further places and lists no questions for him (F02, F04). It makes a const view yield read-only rows where Ben wrote "as with std::span, a const view object does not make its elements const"; the design flags this and cites the rank-2 view, but the repository is split (the rank-1 view states Ben's rule verbatim in a comment), and the design never says what a const row yields. It replaces Ben's at(token, dim) with operator[][] without saying why (the expr base requires operator[]). It adds slices, iterators and generic expression assignment that Ben did not ask for (F08). jhan's item 3 said to stop and write questions when disagreeing with Ben. Stopping was not required, because the reservation was soft and the merge is the direction jhan and Ben both lean to. A short "Questions for Ben" block in the design, and a one-paragraph reply in the PR thread pointing him at issue #4525, would close the loop. As of 2026-09-22 00:3x UTC the PR thread has no reply after Ben's sketch and the issue has no cross-reference from the PR.

The invariant the blockers turn on

The most consequential finding (F01) turns on the Zero-Initialized V Slots invariant. The figure shows one V pair on a page offset that is being reused, under today's code and under the two write operations the design defines. Only the third lane is safe, and the design never says by name that the model's save path takes it.

Findings in full

Major F01. Model V save path: the design never names which operation save_v_impl calls

Where
6. Behavior the implementation must preserve (V padding and write ordering) and 7. Implementation steps, step 5 (Model saves)
Claim
Ambiguity: the design never says which of its two V write operations save_v_impl (the model.hpp function that stores one token's V vector into the cache) calls after the parent PR. Today save_v_impl calls page::set_v. The even-token path of set_v zero-extends each value, so the odd partner row becomes zero. That zeroing is the only thing that keeps the padding row zero when a page offset is reused, because clear_kv_complete_at (the function run when an offset is reassigned) resets completion counters and never touches V bytes. Two design sentences point the model path at the new 'logical operations', and the design defines the logical row operation row.set() as pair-preserving. An implementer who follows those sentences leaves a stale odd row in place after an even write on a reused offset. scaled_v (the weighted V sum) rounds its loop bound up to a full pair, so a stale NaN in that odd row is multiplied by weight 0 and the sum becomes NaN. The existing regression test calls page::set_v directly, so it would keep passing while the model path regressed.
Design says
"Keep existing page methods where needed. Make them call the new logical operations." / "Call typed K/V operations using logical coordinates. Remove V layout choices from save_v_impl, which saves model values in the cache." / "// Logical public operations remain ordinary assignment and conversion. destination_view[token].set(source_expr);" / "The cache chooses when to use the behavior for a newly added row."
Evidence

Recommendation
Add to section 6 and to step 5, in these words: "save_v_impl writes every token through the cache-append operation (append_v_row: on an even token it writes the even row and zeroes the odd row in one store; on an odd token it preserves the even row). It never calls row.set(). page::set_v keeps its name and its zeroing behavior and is the only caller of append_v_row for model saves. In the parent PR no production code calls ordinary assignment on a packed V row." Add a verification row: poison an odd row, write the even partner through the same page method that save_v_impl calls (not a test-only path), then check scaled_v with count = 1 produces no NaN.
Lead's reading
The finder graded this a blocker. All three verifiers graded it major, because section 6 already requires that the model's even-token write zero the odd partner and draws the save sequence as append-even, record completion, append-odd. What is missing is the function-level link: no sentence says that save_v_impl keeps calling page::set_v, that page::set_v is implemented with the append operation, and that no production code calls the pair-preserving row.set on packed V. I accept major. It stays first on the list because a wrong guess here corrupts attention sums silently, and the existing test would not catch it (it calls page::set_v directly).
