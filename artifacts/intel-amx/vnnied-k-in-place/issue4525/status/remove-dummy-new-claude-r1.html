Removing the placement new in construct_kv_blocks

PR #4557 (typed KV-cache tensors), head 633cb88896. Design scope only, no code changed. Written 2026-09-23.

Short version. The ::new in construct_kv_blocks exists because the cache reads raw DMA pool bytes as kv_block objects that nothing creates, a gap that main already has and that every dmatensor<bf16> buffer shares. The placement new does not fully close the gap, because the accessors never use the pointer it returns. The recommended design lets the DMA allocator start object lifetimes (one place, zero instructions) and stores each KV arena as one bf16 array read only through views, so no kv_block or v_vnni_tensor object lives in pool memory.

Words used here

Lifetime (of an object)
The C++ rule that an object exists only between its creation and its destruction. Reading a member of an object whose lifetime has not started is undefined behavior (UB: the standard gives the program no meaning) [basic.life].
Implicit object creation
A C++20 rule (paper P0593R6): some operations create objects of simple types automatically. The list is malloc, aligned_alloc, calloc, realloc, operator new, std::allocator::allocate, memcpy, memmove, and starting the lifetime of an unsigned char or std::byte array [intro.object]/10-13, [c.malloc], [cstring.syn].
Implicit-lifetime type
A type that implicit object creation may create: a scalar, an array, or a class with a trivial default constructor and a trivial destructor [class.prop]/9. kv_block, v_vnni_tensor and bf16 all qualify.
Placement new
::new (p) T[n]: starts the lifetime of objects at address p without allocating. For a trivially default-constructible T without () it writes no bytes.
std::launder
A C++17 function that turns a pointer to old storage into a pointer to the object that now lives there. It generates no instructions.
std::start_lifetime_as_array
The C++23 library call made for exactly this case (paper P2590R2). Our toolchain does not have it (finding F3).
DMA pool
Tron's own allocator for device-visible memory (dma_allocate_aligned, backed by heap_v2 or pos_heap over hugepages). It returns void*.
Arena, chunk
The retained arena is one DMA allocation for all retained KV slots. A reclaimable chunk is one DMA allocation for some pages of the sliding slots (PR #4455).
kv_block
The struct for one KV head of one 64-token page: a K plane followed by a V plane.
Uniform / heterogeneous layout
Uniform: every KV slot has the same head count and head size, so one kv_block type fills the arena. Heterogeneous: slots differ, so one arena holds several kv_block types at byte offsets.
Owner / view
v_vnni_tensor owns the packed V bytes. v_vnni_view is a pointer plus the address formula. In the PR, only the owner can create a view.

1. Where the gap is

Today the cache follows these steps:

DMA pooldma_allocate_aligned returns void*
→
Typed factorytry_make_unique_dma_for_overwrite<uint8_t[]>: casts, starts nothing
→
Gapno object lives in the bytes
→
Cache readreinterpret_cast<kv_block_t*>(base)[i]
→
Member use.v.as_view(), .k_view()

Red dashed box = the step the standard requires and nobody performs. The PR fills it with construct_kv_blocks inside the cache.

F1. The gap exists on main, before PR #4557

  • Main's kv_block is already a class with member functions: k_view(), k_at() and v_base() [main h/tron/models/kv_cache.hpp:2449-2497].
  • Main reaches it the same way, through reinterpret_cast<kv_block_t*> of arena bytes [main kv_cache.hpp:1533, 1542, 1578].
  • Main has no placement new in kv_cache.hpp (grep -c "::new" = 0).
  • Member access such as blocks[i].v[i_page] on an object that was never created is the same UB, whether or not the member has a class type [basic.life]/7.

So the Note's reason ("kv_block::v has a class type whose member functions the cache calls") is true but incomplete. The PR did not create the gap. The PR made it visible, because v_vnni_tensor put the gap into a type the review looked at.

F2. The gap starts at the allocator, and it is shared by every DMA buffer

  • In production, dma_allocate_aligned is Tron's own pool [src/system/memory.cpp:461-469]. It is not on the implicit-object-creation list. So no object exists in the bytes it returns.
  • The typed factories start lifetimes only for types that are not trivially constructible [h/system/memory.hpp:251, 333]. For uint8_t, bf16 and kv_block they do nothing.
  • Every dmatensor<bf16> buffer (weights, activations) is built by the same factory and read through bf16* [h/tron/hardware/dmatensor.hpp:186-191]. It has the same gap for its bf16 elements.
  • In the unit-test build, the fake allocator calls aligned_alloc [src/pos/fake.cpp:353-357]. aligned_alloc is on the list. So the unit tests have no gap, even without the placement new. Only production builds have it.

F3. The C++23 library call is not available

The nix toolchain compiles with clang 19 against libstdc++ 14.3.0. A search of that libstdc++ include tree on delphi-3bda (the test server) found no start_lifetime_as (0 files). So std::start_lifetime_as_array cannot replace the placement new today.

F4. Why the PR's own design needs an object in pool memory

The PR's rule is that only the owner (v_vnni_tensor) can create a v_vnni_view: the view has no public pointer constructor. So the cache must find a live owner object inside the arena before it can read V. A live owner in pool memory requires a lifetime start. The placement new is the price of the rule "only the owner creates a view".

F5. Under the strict rule, the placement new is not enough on its own

  • construct_kv_blocks throws away the pointer that ::new returns [kv_cache.hpp:1476, 1490-1491].
  • The accessors later build their own pointer: reinterpret_cast<kv_block_t*>(kv_blocks_alias) or (storage.base), starting from a uint8_t* [kv_cache.hpp:1593, 1602, 1642].
  • A pointer to old storage refers to a new object automatically only if the new object has the same type as the old one ("transparently replaceable", [basic.life]/8). A kv_block never replaces a uint8_t in that sense.
  • So the strict reading needs std::launder at those three cast sites as well. This is the standard example for std::launder: placement new into a byte buffer, then access through a cast of the buffer pointer [ptr.launder].

Clang and GCC do not use this rule for optimization today. The point is only that the PR's cover is itself incomplete. A design that needs no cover avoids both questions.

2. Designs that need no construct_kv_blocks

Design A. The allocator starts the lifetime

Change the typed DMA factories so that they always start the lifetime of U[size]. For a trivially constructible U, this writes nothing and compiles to no instructions. This is the same fact the PR already measured for construct_kv_blocks (objdump of allocate_retained_storage: 0 rep stos, 0 memset).

// h/system/memory.hpp, try_make_unique_dma_for_overwrite<T[]> (and the asserting form)
void* raw = dma_allocate_aligned(size * sizeof(U), size_t(alignment));
if (raw == nullptr) return unique_dma<T>(nullptr, c_dma_deallocate<T>(0));
U* array;
if constexpr (std::is_trivially_default_constructible_v<U>)
  array = ::new (raw) U[size];   // default-init: starts lifetimes, writes no bytes
else {
  array = static_cast<U*>(raw);
  for (size_t i = 0; i < size; ++i) new (array + i) U;
}
return unique_dma<T>(array, size);
  • Closes the gap for every DMA user at once, including dmatensor<bf16> and main's existing kv_block reads.
  • The lifetime code lives in the one function that turns raw pool memory into typed storage. That function is the correct owner of this rule.
  • With A alone, the uniform layout can allocate kv_block_t[] directly and index a typed pointer. construct_kv_blocks and its three static_asserts are then not needed.
  • A alone does not fix the heterogeneous layout. That arena stays uint8_t[] with several block types at byte offsets. Starting a uint8_t array's lifetime does create the blocks implicitly [intro.object]/13. But the reinterpret_cast pointer still points to a uint8_t, so each cast site would need std::launder. That is again code whose only purpose is lifetime, so it does not meet the goal.
  • Cost: one change in h/system/memory.hpp, outside the files of PR #4557. It touches every DMA allocation, although for trivial types it adds no instructions. It fits as a small PR of its own ahead of #4557.

Design B. One typed arena per block type

Allocate one kv_block_t[] per (geometry, retention group) instead of one byte arena with byte offsets. Combined with A, every arena is a live typed array from birth.

  • No reinterpret_cast, no std::launder, no placement new anywhere in the cache.
  • Cost: it rewrites the arena addressing of PRs #4455/#4456 (storage_location, slot_base, slot_page, the retained arena plus reclaimable chunks). It also adds allocations for heterogeneous caches. This is much larger than issue #4525.

Design C. No block objects in pool memory: one bf16 array per arena, views only (recommended with A)

Every K and V plane holds bf16 values. So each arena and chunk can be one bf16 array. The cache then computes plane addresses by pointer arithmetic inside that array and returns views. No kv_block object and no v_vnni_tensor object ever lives in pool memory.

// storage: one live bf16 array per arena (A starts its lifetime)
hardware::unique_dma<bf16[]> retained_data;          // was unique_dma<uint8_t[]>

// the block becomes geometry, not an object
template <size_t page_size, size_t head_size>
struct kv_block_geometry final {
  static constexpr size_t PLANE_ELEMENTS = page_size * head_size;
  static constexpr size_t K_OFFSET = 0;
  static constexpr size_t V_OFFSET = PLANE_ELEMENTS;
  static constexpr size_t BLOCK_ELEMENTS = 2 * PLANE_ELEMENTS;
};

// book returns views built from an address inside the live bf16 array
bf16* block = arena + block_index * geometry::BLOCK_ELEMENTS;
auto k = view<bf16, VIEW_ALIGNED_TRUE, VIEW_DMA_FALSE, seq<page_size, head_size>>{
    block + geometry::K_OFFSET};
auto v = detail::v_vnni_access::make_view<bf16, page_size, head_size>(
    block + geometry::V_OFFSET);                        // book-only factory, see below
  • Every member function call is on a view object on the stack. Those objects are created normally, so their lifetime is not in question.
  • Every pool access is bf16* arithmetic inside one array. With A, that array is live. There is no reinterpret_cast of arena memory, no std::launder and no placement new.
  • It works the same for the uniform and the heterogeneous layout. Slot byte offsets become element offsets (divide by sizeof(bf16), 2 bytes). They are already whole blocks, so the division is exact.
  • Without A, C leaves the cache with exactly the element-level gap that every dmatensor<bf16> buffer has today. That is consistent with the rest of the codebase. It is not a gap specific to the KV cache.

What C gives up:

  • The alignas(kv_block_alignment) on the struct no longer enforces plane alignment through the type. An assert on the arena alignment (storage_alignment) and a static_assert that BLOCK_ELEMENTS * sizeof(bf16) is a multiple of 64 bytes must replace it.
  • The typed owner in the 8-lane build disappears. That build keeps V row-major and never stored V in the owner anyway (Note [Packed V layout]).
  • It departs from the design page's choice of an owner type inside kv_block. That choice was recorded in the design review, so it is a design reversal that needs a line in the PR's decision record.

Rejected: return to main's plain arrays

Keeping kv_block with plain bf16s arrays and deleting the placement new would restore main's state. Main has the same gap without a line that covers it (F1). This hides the UB. It does not remove it.

4. Recommendation

  • A + C. A puts the only lifetime rule in the allocator, which is where raw memory becomes typed storage. C removes objects from pool memory, so the cache has nothing whose lifetime can be wrong.
  • Order: A as a small PR of its own (one function pair in h/system/memory.hpp, codebase-wide, no instruction change for trivial types). Then C in #4557 or in a follow-up commit on it.
  • If A is not wanted outside #4557: C alone still removes construct_kv_blocks. The cache is then exactly as defined as every other DMA buffer, and the one remaining gap has a single home in the allocator.

5. How to verify a chosen design

  • Instruction identity: the same objdump comparison as Step F of the PR (the 19 noinline wrappers, plus allocate_retained_storage / allocate_reclaimable_chunk). Expected: identical hot-path bodies, 0 rep stos, 0 memset.
  • Bits: the existing t_llama_unit cases "packed V rows keep their bits through set_v, get_v and expression reads" and "Sliding KV chunks reserve and restore transactionally" (44 cases, 252718 assertions on 1c87d66926).
  • Numerics: t_amx_numerics (12301 assertions with real AMX, 2060 with the kill switch).
  • No lifetime code left: grep -n "::new\|launder\|reinterpret_cast<.*kv_block" h/tron/models/kv_cache.hpp returns nothing.

6. Open points

  • Decision for you: A + C, C only, or A only (with std::launder in the heterogeneous path).
  • Which production models use the heterogeneous layout: Insufficient data. The ingest generator can emit heterogeneous_kv_cache [ingest/src/TronCpp.hs:582-597], and the unit tests cover it. A grep of the generated model plugins of a full build would answer it. This affects how urgent the heterogeneous half is, not the recommendation.
  • Toolchain claim F3 covers the libstdc++ that the clang 19 wrapper uses on delphi-3bda. A libc++ build was not checked.
