## Summary
- Replace the two 64-bit divides in `precise_scale` with a 64x64→128 multiply + shift (one `mulq` on x86_64) — `cycles_to_ns` / `ns_to_cycles` drop from ~30–50 cycles to ~5.
- The TSC calibration thread caches fixed-point reciprocals of `cpu_frequency_hz` alongside it and refreshes them on every freq update; writes are ordered reciprocal-then-frequency so a reader past the existing `!= 0` gate observes a valid pair.
- `ns_per_cycle` stored in Q.64 (all fractional — ns-per-cycle < 1 for any freq > 1 GHz). `cycles_per_ns` stored in Q.61, reserving 3 integer bits for the small cycles-per-ns rate (covers up to ~8 GHz; realistic x86_64 invariant TSC is 2–4 GHz). Round-to-nearest at both reciprocal computation and the final shift preserves the strict round-trip behavior the existing precision tests rely on.

> **Overview**
> **Speeds up hot-path TSC conversions** by caching `cpu_frequency_hz` reciprocals as Q3.61 fixed-point values and using `__uint128_t` multiply + round-shift in `cycles_to_ns` / `ns_to_cycles` instead of `precise_scale`’s 64-bit divides.
> 
> The TSC calibration thread recomputes those reciprocals on every frequency update via new `update_freq_reciprocals()` (with freq bounds asserts) and publishes them **before** writing `cpu_frequency_hz`, so readers past the existing `cpu_frequency_hz != 0` gate always see a consistent pair. Header documentation in **Note [Cycle Frequency Reciprocals]** explains the format and ordering; `precise_scale` is left in place for other callers (e.g. in-loop `new_freq` estimation).
