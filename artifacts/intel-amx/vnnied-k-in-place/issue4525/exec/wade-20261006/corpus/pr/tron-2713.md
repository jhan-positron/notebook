## PR body (as it is now; may have been edited after the review)

The investigation of STORY-425 led to a conclusion that the large number of 8K `hwcacheblock` objects being allocated and released was fragmenting the DMA-able, hugepage-backed memory heap.

A specification for an allocator with separate slabs for each allocation size was developed and reviewed. It is part of the changeset for this PR.

The new allocator is *disabled* by default. To enable it, set the environment variable `TRON_USE_ARENA_ALLOCATOR=1`. 

The python fuzzer, `/tools/rinzler-fuzz.py` is able to reproduce the defect (when you run rinzler without `TRON_USE_ARENA_ALLOCATOR=1`). Note: in order for the memory pressure to trigger cache evictions, you need more than the default 16 `POS_NR_HUGEPAGES`. (I use 32.) Evictions typically begin once the memory exceeds 50% used.

## Performance: pos_heap_v2 vs pos_heap

A microbenchmark (`t/t_alloc_contention.cpp`, gated by `[.perf]`) compares both allocators under concurrent threads doing tight `allocate / touch / deallocate` loops. Three scenarios on andoria-06 (16 hugepages, 500 ms wall clock per scenario):

| Scenario | Threads | Legacy ops/s | v2 ops/s | v2 / legacy |
|---|---|---|---|---|
| Single-thread baseline (class 3, 8 KiB) | 1 | 2.84 M | 49.6 M | **17.5×** |
| Same-class contention (all class 3) | 16 | 0.78 M | ~2.7 M | **~3.4×** |
| Multi-class parallelism (classes 3, 5, 8, 10) | 16 | 0.83 M | ~6.3 M | **~7.6×** |

Two structural wins:

1. **Per-op cost is lower even single-threaded.** Free-list pop/push on a per-class slab is cheaper than buddy splinter/coalesce on a global tree.
2. **Per-class mutex parallelizes as designed.** Legacy collapses to a single mutex under any concurrency; v2 scales with the number of distinct classes in flight.

### The pool.mu finding

The original v2 had a hidden bottleneck the microbench surfaced: with one slot in flight per thread, every `alloc + dealloc` cycle locked the global `pool.mu` twice (release the slab on dealloc-when-empty, acquire one on the next allocate). Per-class `arena.mu` parallelism didn't help because the work crossed the arena boundary on every cycle.
