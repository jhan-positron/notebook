## PR body (as it is now; may have been edited after the review)

Initial work to try coalescing DMA transfers for runs of KV cache within a layer like we create during prompt parsing.

## Descriptor tradeoff

For a 128-token prompt block, the expected K+V data-descriptor count is shown below. The V side has 32 descriptors per window; the K side has one descriptor per GOF in the window.

| Coalescence tokens | Windows per 128 tokens | K+V descriptors per 128 tokens |
|---:|---:|---:|
| 8 | 16 | 544 |
| 16 | 8 | 288 |
| 32 | 4 | 160 |
| 64 | 2 | 96 |
| 128 | 1 | 64 |

### issue-comment 5498556672 at 2026-09-01T18:31
I seemed to notice the V-populate path doing a lot of extra work in these changes. So I prompted Claude with that (and told it to look at the PR overall). I also asked it to evaluate any collateral concurrency risks... below are those results:

  - **Top robustness item** — batch teardown is unsafe by default (dma_tracker.hpp): dropping a queued batch pending_xfer without a manual abandon() frees the buffer under live DMA; only dma_tracker::clear remembers today. Also nothing asserts the gof-pin and batch-pin fields are mutually exclusive. Fix: abandon-in-destructor unless completed, plus an XOR assert in push().
  - **Heavy-concurrency risk** — decode at ≥32 users escalates the drain budget 4→8: the "prompt-sized pass" test counts token jobs, so co-batched decode qualifies; up to 8 populate+submit rounds at a pre-barrier idle point serializes the attention workers. Gate on pass shape, not token count.
 - **Hot-path costs:** you were right about this. The V-populate path does 32x the work now of the path it's replacing... batch V populate re-runs the full head gather 32× per element consumed (and widens a pre-existing cross-layer v_buf race window by the same factor); each batch does a redundant up-to-128 KiB memset + 6 mallocs + an avoidable sort; help_drain_gof now mallocs per call in decode spin loops; the kv_complete assert loop runs twice per decode GOF.
  - **Branching trees:** shard-fanout now populates and pins one batch buffer per shard instead of sharing one staging population.
  - **Consistency nits:** batch path lacks the n_kv_heads ≤ HW_MAX_KV_HEADS assert every sibling writer carries — parity, not a live bug since  eligibility gating keeps over-wide models off the HW path; and it uses % FETCHERS_PER_DEVICE where the single path spells % dev->num_fetchers — moot given the  32-fetcher design invariant, but worth spelling the same way.
