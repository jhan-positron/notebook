## PR body (as it is now; may have been edited after the review)

## Why

Running ingested qwen3-30b-a3b with hardware attention failed on the very first forward pass with
`Encountered NaN s_star`. It happened at tp2 and tp4, from a 16-token prompt upward. Every other hardware
attention model we run has 8 KV heads; qwen3-30b has 4, and it was the first model to exercise that
difference.

The cause was in how the K cache is written to the FPGA. The hardware reserves a fixed slot for each token:
room for 8 KV heads of 128 elements, regardless of what the model actually has. The code that writes K
assumed the slot was only as wide as the model's KV head count. With 8 heads the two agree. With 4 heads,
the second, third and fourth tokens in every block of four were written to the wrong place, and the FPGA
read K values that had never been written. V was already laid out for 8 heads, which is why the failure
showed up in the softmax denominator rather than in the attention output.

Fixing that and testing it at 4 heads surfaced a few related problems, all fixed here as separate commits:

- The V write path had its own geometry bug. The "readback fence" (the word the host waits on to know a
  DMA has landed) was placed based on the transfer length instead of the row size, so at 4 heads it pointed
  past the bytes being written. Production does not use the fence, but the tests do.
- Several helpers silently clamped an unsupported KV-head count instead of rejecting it.
- A model with 32 or more query heads per KV head would pass the hardware-eligibility check and then abort
  at runtime, because a 5-bit command field cannot hold that ratio.
- The debugging code that reads K back from HBM used the wrong geometry too, and nothing in the tree
  compiled it, so it had rotted unnoticed.

This is unrelated to the `NaN v_star` failure seen in the field on 8-head models.

## What changed

**K cache DMA.** Positions within a block are now stepped by the hardware's fixed slot size. The transfer
still carries only the heads the model has. This is the fix for the qwen3 failure and it changes nothing for
8-head models.

**V cache DMA.** The transfer length and the readback fence are now both derived from the block's row
layout, so the fence always sits inside the bytes the DMA writes. Production behavior is unchanged.

**Rejecting unsupported shapes.** Every K and V transfer helper now asserts that the KV-head count is
between 1 and 8 instead of clamping it. The eligibility check that decides whether a model may use hardware
attention now also requires `n_heads / n_kv_heads <= 31`, which is what the 5-bit `gqa` field can hold.
A shape past that limit takes software attention instead of aborting on the first hardware command. The
runtime assertions and the worker reference the same constant, so the limit is defined once.

**K cache readback (debug only).** The reader now inverts the exact layout the writer produces, so a dump
of a model with 64-wide heads is no longer scrambled. The dump header is compiled by one test target so
future drift is caught at build time.

**Documentation.** The hardware attention doc now says K is written as one contiguous descriptor per token
(splitting by head across FPGAs is planned, not implemented) and has a corrected V layout table. Two helpers
carry doc comments answering questions raised in review: why one keeps a `head_size` parameter production
never varies, and that the other is test-only.

## How it was tested

**Batch test at 4 and 8 KV heads.** `t_hwattention_batch` now runs its whole battery at both head counts.

correct maximum score; if any slot still holds poison, that maximum comes back wrong. The unused V rows are
