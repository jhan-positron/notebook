## PR body (as it is now; may have been edited after the review)

## Summary

`--trace-passes SPEC` records only the named primary forward passes — trace
size is bounded by window width, not run length. `0` also captures startup
(init + model load).

    bin/runtron -m llama-3-8b -l 32 \
      --trace-gen story662.pftrace --trace-passes 0,5-8 -- "prompt"

Result: inference unchanged; the trace shows model load, a silent gap
(passes 1–4 gated), then exactly 4 `forward` slices with full detail, all
slices paired. Sample: `/scratch/bcraig/story662-traces/`.

## What

- New runtron option `--trace-passes SPEC` guiding Perfetto instrumentation
  (requires `--trace-gen` — a file path for in-process capture, or `traced`
  to record through the external daemon): application track events are
  captured only during the selected
  primary forward passes. SPEC is 1-based ranges (`2-4`, `500-`, `-150`,
  `10,60,100-110`); `0` selects **startup** — everything before the first
  forward pass (init, device bring-up, model load). Prompt parse is pass 1,
  not startup. Takes precedence over `--trace` when both are given.
- Emission-side gate: the TrackEvent macros in `h/common/perfetto.hpp` AND in
  a process-global atomic (storage isolated in `src/pos/trace_gate.cpp`,
  coupled to allocator tracing). The scheduler opens/closes the gate at the
  `full_scheduler::forward()` boundary via a per-scheduler pass counter
  (`h/common/trace_passes.hpp`); speculators/EAGLE children are excluded and
  no-work forwards do not count.
- Windowed runs use a duration-free in-process session — legacy `--trace` /
  `--trace-gen` keep their 5 s cap — with an exception-safe start/action/stop
  lifecycle on a core-0-pinned thread (`h/runtron/trace_lifecycle.hpp`).
  `--trace-passes` overrides `TRON_TRACE_FROM_TOKEN` (warns). Composes with
  `--trace-gen traced` daemon mode: the gate is emission-side and
  backend-agnostic.
- Response-slice pairing: the pre-forward "Generate response" BEGIN records
  iff the gate is open at that moment; the END restores the state captured at
  BEGIN, so the pair records or drops together — including repeated
  generations (`--isolated-iterations`), where the second run starts with the
  gate closed by the first run's teardown.
- Tests: `t_trace_passes` (unit — spec parser incl. the `0` grammar, pass
  counter, gate semantics, lifecycle, surrogate scheduler),
  `t_trace_passes_host` (integration on llama-3-8b-host — real forwards,
  in-process capture, pairing incl. the repeated-generation regression), CLI
  validation cases in `t_runtron_cli`; shared trace-inspection helpers in
  `t/trace_test_util.hpp`.

## Why

Legacy tracing is all-or-nothing: `--trace`/`--trace-gen` capture every pass
and stop at a hardwired 5 s, so long-run traces are either truncated or
unusably large, and there is no way to inspect a specific region deep in a
long generation. Pass windowing bounds capture by window width instead of run
length — measured on andoria-02: a 3-pass window of a 30-pass run is 927 KB
vs 9.1 MB legacy; an 11-pass window at pass ~7900 of an 8000-pass run is
6.5 MB. The `0` (startup) selector additionally captures init/model load,
which no legacy file mode records.

Below are the items it came up with. I do think there's some merit to a few of them, but could be a follow-up if you prefer. I'll approve as-is.

>   1. Perfetto internal-macro override is fragile against silent version drift (highest-value issue).
>   h/common/perfetto.hpp #undefs and re-defines PERFETTO_INTERNAL_TRACK_EVENT_WITH_METHOD and
>   PERFETTO_INTERNAL_CATEGORY_ENABLED, copying Perfetto's implementation (including the GCC 7 workaround). The >   #ifndef … #error guards only fire if the macro is renamed or removed — they will not catch a Perfetto bump that changes the macro body while keeping the name. In that case the override silently diverges from upstream (e.g., a new fast-path or arg the copy doesn't replicate) with no compile error.
>   - Suggestion: pin the reviewed Perfetto version/commit in the comment ("re-diff these overrides at vX.Y") and, if
>   feasible, add a runtime test asserting the gate actually suppresses a real emitted slice under the current Perfetto
>   (the t_trace_passes gate-filter test partially does this — good — but tie it explicitly to the override contract).
> 
>   2. The gate only covers emission sites that include common/perfetto.hpp. Any translation unit that emits track events
>   via a direct Perfetto include would bypass the gate and leak events into a windowed trace. Worth a one-line note in
>   the header (and/or a lint/grep guard) that all track-event emission must route through this header.
> 
>   3. Process-global mutable state + relaxed atomics — document the single-writer assumption.
>   detail::configured_trace_passes (inline optional in a header) and the application_track_events_gate atomic are
>   process-global and unsynchronized aside from the gate's relaxed loads/stores. This is fine for runtron's single
>   generation-pipeline model, and relaxed is acceptable for best-effort tracing — but it does mean events racing a gate
>   flip on other threads land in/out non-deterministically, and it assumes exactly one generation pipeline
>   configures/flips at a time. A short comment stating that invariant would help the next reader who tries to reuse this
>   outside runtron.
> 
>   4. UX gotcha with repeated generations. As documented, pass numbering restarts per scheduler, so --isolated-iterations
>   3 --trace-passes 5-8 produces three windows, not one, while startup (0) fires only once. It's in the README, but it's
>   an easy surprise — consider surfacing it in the --trace-passes help text too (currently the CLI help doesn't mention
>   the per-generation restart).
