## PR body (as it is now; may have been edited after the review)

In TP2 or higher, it is possible for a work_req to be reused too soon. When the issue occurs, the following log messages are logged:

```
[error] TRON_ASSERT(other_sp.m_star != -std::numeric_limits<float>::infinity()): Encountered -inf m_star in a valid scratchpad. KV_head 5, to worker 0, from worker 11, batch_job_ix 6
```

Currently, this problem is quiescent with the original heap implementation, but when `TRON_USE_ARENA_ALLOCATOR=1`, the defect is reproduced very quickly in soak tests.

The fix is to make sure the previous work request is finished before reusing to begin a new prepare.
- Add wait_until_work_req_idle()
- Wait for previous launch of a work_req to complete before mutating

> [!NOTE]
> **Medium Risk**
> Changes synchronization on the hot path for hardware matmul/attention scheduling; incorrect ordering could stall or mis-handle in-flight work, but the fix uses an existing atomic guard already set at enqueue and cleared on completion.
> 
> **Overview**
> Fixes a **TP2+ race** where plugins reuse the same `wqentry` / `hardware_job` launcher while matmul/attention launches are still asynchronous: the main thread could **fill or prepare** the next job before TX/RX workers finished reading the prior entry, leading to corrupted `work_req` state (especially visible with `TRON_USE_ARENA_ALLOCATOR=1`).
> 
> Adds **`wait_until_work_req_idle`**, which spins on `wqentry::in_flight` with **acquire** loads until the prior job’s completion callback clears it with **release** (set at enqueue, cleared after the job completes). That wait runs at the start of **matmul/attention fill**, **matmul prepare**, and **attention prepare** so fields are not mutated while a launch is still in flight. Documents the protocol in **Note [WQEntry Reuse Race]** and ties the existing enqueue `in_flight` store to that note.

WADE: I have some reservations about this... I literally went down this road a couple weeks ago or so, and almost committed the same spin-wait you've added. But I loathe spin-waits, and we backed it out for a couple reasons (which I let Claude summarize for me below):

---
1. It turns a loud tripwire into a silent forever-hang.

"When RX is stuck (which is the symptom here), the callback that clears in_flight never fires; the next hw_prepare for that wqentry will spin forever instead of failing loudly… The original assert was a useful tripwire — restoring it would surface the real first violation faster."

The spin only "works" when the completion path is healthy — which is exactly when you don't need it. When it isn't healthy (the arena-allocator soak case), it converts a diagnosable assert into a hang.

2. The serialization it adds already exists. We worked out that main relies implicitly on the rxinfo_ring overflow backpressure at the top of hw_prepare:

"in_flight is cleared before rx_head increments, so per-slot backpressure transitively guarantees per-wqentry backpressure as well. So main never trips the same condition. The assertion exists for a case main physically can't hit: hwattn introduced multi-device matmul dispatch [the same wqentry re-targeted to a different device]."

---

I did fix some wrap-count bugs with https://github.com/positron-ai/tron/commit/9e4ebd056e080ecf464e6d4d8dfc9083f1fa732f awhile back.

I suppose we can land this if it's critical to get the test pipeline moving forward. But spin-waits just suck in general, IMO. I wonder... is "m_star == -inf" really even a "reused too soon" bug? It's on matmul_rx_q (raw desc_idx polling, no check_xfer_complete). If this is an unserialized upstream issue, or false-completion feeding a stale scratchpad, the fix should be to serialize/correct that signal... not wait indefinitely/blindly on 'in_flight' IMO. Just feel like there's more sleuthing to be done ;-p
