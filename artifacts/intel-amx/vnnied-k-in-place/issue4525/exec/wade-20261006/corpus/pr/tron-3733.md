## PR body (as it is now; may have been edited after the review)

Add a debug-only Perfetto `memory` category for selective DMA and HBM allocator tracing without flooding steady-state allocation paths.

## Problem

Allocator pressure, HBM activity, heap expansion, reserve draining, large-slab acquisition, and OOMs were difficult to identify in existing Perfetto traces. Tracing every DMA allocation would produce excessive event volume.

## Solution

Register the debug-tagged `memory` category and add these selective allocator events:

- `hardware::allocator::allocate` — requested HBM allocation size
- `hardware::allocator::deallocate` — released HBM address
- `hardware::allocator::dump_profile` — profile tag; available with `HBM_ALLOC_SHADOW`
- `pos_heap_v2::expand` — number of DMA hugepages added
- `pos_heap_v2::drain_reserves` — number of cached slabs released
- `pos_heap_v2::oom` — requested size, size class, and caller addresses
- `slab_pool_t::acquire_large` — LARGE allocation size class
- `slab_pool_t::release_small_hugepage` — complete SMALL hugepage reclamation

Routine LARGE pre-drains and steady-state DMA allocation/deallocation remain untraced to avoid event flooding. Wildcard-only trace configurations do not enable this category; it must be explicitly enabled with `memory`. Structured trace assertions cover the event payloads, and the `t_hwalloc` Slice benchmark metadata is refreshed.

## Testing

- Default `build-test`, `t_heap_v2`, `t_hwalloc`, and `[perfetto]` passed; HBM-shadow `[perfetto]` and `[shadow]` passed
- `make lint`, `git diff --check`, and touched-file `clang-format-19 --dry-run -Werror`
- Dice `bin/slice bench --remote --remote-sku sku0 --update t_hwalloc` passed and refreshed the `genoa96` metadata
- DUT captures validated the expected memory events and annotations alongside model loading and generation activity

Enabling the `memory` category had negligible performance impact. We compared three runs with the category enabled against three otherwise identical runs with it disabled. Each used llama-3.1-8b with hardware attention enabled (8K-token input, 64K-token output). Enabled traces contained 10,131 memory events; disabled traces contained none, and all traces had zero loss indicators.

| Median metric | Disabled | `memory` | Change |
| --- | ---: | ---: | ---: |
| Model loading | 1.465630 s | 1.467667 s | +0.14% |
| Generation time | 573.704928 s | 574.418353 s | +0.12% |
| Generation throughput | 114.228 tok/s | 114.086 tok/s | -0.12% |
| TTLT | 577.146341 s | 577.840951 s | +0.12% |

No material performance regression was measurable; all median changes were below 0.2%.
