## PR body (as it is now; may have been edited after the review)

This PR is the first piece of breaking up PR #3879. This PR is based on `main` and does not depend on the other breakup pieces.

## What it adds

`h/tron/kernels/page_share_counters.hpp` and five hook blocks guarded by `TRON_PAGE_SHARE_COUNTERS` in `h/tron/models/self_attention.hpp`. For every page visit - a page visit is the processing of one (KV page, kv_head) pair in the software attention loop - the hooks count the query tokens which have relevant K tokens, keep a histogram of it (slots are 1, 2, 3, 4, 5-8, 9-16, >16 query tokens) and add the per-call totals to process-wide counters. Visits without any relevant K tokens are not counted. At normal process exit, a static object's destructor prints the summary to stderr if at least one visit was counted.

The CMake option `TRON_PAGE_SHARE_COUNTERS` (top-level `CMakeLists.txt`, default OFF) adds the define of the same name to the `tron` library. Without the define the header declares no instrumentation and the preprocessor removes the five hook blocks, so a default build compiles no counter code into the library. The new test supplies the define to its own translation unit.

The CI build job leaves the option OFF, so the runtron it bundles as the benchmark artifact carries no instrumentation. The weekly coverage preset (CMakePresets.json, built by cpp-coverage.yml) sets it ON, so the hooks are compiled there and exercised by t_llama_unit.

## What does this PR serve?

Following is from example runs (qwen-3-4b, tp2 = tensor parallelism over two FPGA cards, attention on the CPU, 8 users). The numbers are workload-wide averages; they show how often several query tokens visit the same page, which is the condition under which a per-page kernel could serve several query tokens from one page load:

| Workload (8 users) | Query tokens per page visit, average |
|---|---|
| prefill-heavy: prompt 2048 tokens, 2 generated | 110.9 |
| decode-heavy, private prompts: prompt 64 tokens, 512 generated | 1.02 |
| decode with a shared system prompt: 1024 shared + 64 private prompt tokens, 256 generated | 5.06 |

The kernel in the next PR serves one query token (its four query heads) per page load. The counters tell where batching several query tokens per page load would help (prefill, shared prompts) and where it would not (private decode: 1.02 query tokens per visit).
The counter instrumentation, behind an option, makes the measurement repeatable when the batching behavior changes. A query counts as long as at least one K token on the page is relevant to it; the counters do not measure whether the page was dense (all 64 tokens visible) for that query.

## Review history

Ben [asked why the counters are global inline variables](https://github.com/positron-ai/tron/pull/3879#discussion_r3936847383) and then [named the C++17 feature himself](https://github.com/positron-ai/tron/pull/3879#discussion_r3937150401): a C++17 inline variable may be defined in every translation unit that includes the header, yet the program has exactly one object with one address, so the instrumentation needs no .cpp file.

The agent review Wade (Wado-posi) posted on #3879 ([comment](https://github.com/positron-ai/tron/pull/3879#issuecomment-5544513215)) asked for the instrumentation to leave the tree; this PR keeps it behind an option with a test and a stated purpose instead.
