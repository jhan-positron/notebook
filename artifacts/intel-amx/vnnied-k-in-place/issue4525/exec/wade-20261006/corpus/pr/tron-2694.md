## Summary

Three coordinated changes to `ranged_mask`, plus two explanatory comments added in response to CQA review:

- **`h/tron/models/ranged_mask.hpp`** drops the stub `shard` struct in favour of `using shard = tron::hardware::shard;` — the real type lands via [#2676](https://github.com/positron-ai/tron/pull/2676).
- **`src/tron/models/ranged_mask.cpp`** has two surgical fixes plus two explanatory comments:
  - Push-time cursor fix: the shard pop now uses `< hi` instead of `< edge_hi`, matching the loop comment.
  - Pop-time `dma_complete` gate is removed.
  - New comment above the `have_shard`/`have_query` guards explains why the shard guard uses the shrinking `hi` while the query guard keeps `edge_hi` (prior pop_backs already trim the query stack to match — both reach the same trim).
  - New comment in the SW→HW transition block notes that DMA-complete eligibility is enforced at push time by the walker (`h/tron/scheduler/full.hpp`), so the unconditional pop here relies on a caller guarantee.
- **`t/t_ranged_mask.cpp`** swaps the stub `b_shard` aggregate initializer for `shard(nullptr, 0, 0)` (the real shard has a deleted copy ctor; `max_layers=0` is the test-stub sentinel that makes `dma_complete()` true).

Why now: [#2676](https://github.com/positron-ai/tron/pull/2676)'s headers provide the real shard type, so the local stub becomes redundant. The `dma_complete` eligibility filter is moving from pop-time to push-time — a follow-up walker PR will only push DMA-complete shards onto the shard stack, so the pop-time gate has no work left to do.
