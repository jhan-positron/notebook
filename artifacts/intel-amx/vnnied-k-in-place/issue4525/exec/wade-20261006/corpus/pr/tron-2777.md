## PR body (as it is now; may have been edited after the review)

## Summary

Initial draft/RFC from an investigation into loading `gpt-oss-120b` TP4 on a vatlas4 system.

The vatlas systems are a new bring-up target for this workflow. Please read this as evidence from loading `gpt-oss-120b` onto a vatlas4 system, not as a settled runtime policy. This is not my area of expertise, and I am skeptical of the implementation until someone familiar with generated model loading, `app_pool`, tensor placement, and FPGA weight loading reviews it carefully.

This PR is a single commit against `main`. It intentionally does not include the #2614 in-process weights-cache work or the previously cherry-picked `99c6708f2db8e38fa1932c4c42d89cba72479e44` commit.

## Changes

- Generated expert safetensor loading now calls a C++ helper that visits experts in parallel.
- Per-tensor quantization/load work uses bounded fanout via `TRON_PER_TENSOR_LOAD_WORKERS`, defaulting to 16 workers.
- `set_hardware_weights` is serialized per target `PosDevice`; `alloc_hardware_weights` remains unwrapped because the allocator path already locks.
- Rotated placement shares atomic rotation state across loader threads while preserving thread-local placement contexts.
- Tag-selected model builds pass `--min-support working` so local `support_level: none` overrides cannot emit stale plugin declarations.

WADE: I'm inclined to balk at this a bit... this sort of free-floating lock placement is detached from what it's actually protecting. IMO it would be better to add a mutex member to the PosDevice (or DmaQueue) and use it directly inside of `device::set_hardware_weights`. A few reasons:

1. it co-locates the lock with the thing it's protecting... in this case (critically) the `load_weight_q` which is mutated inside that function
2. finer-grain control over the lock period: based on my read of the code, it's really only the `xfer_blocks` we need to span with protection. The `wait_for_xfer_blocks` busy-spin is is just a read of monotonic, per-range descriptors. I _think_ it would be safe for concurrent waiters to land there, cuz they'd have their own disjoint desc values.
3. with this placement, it forces two parallel callers to fully serialize, even over that `wait_for_xfer_blocks` which as discussed, I don't think is necessary
4. any future parallel state/access to that DMA q from elsewhere will have to do this same thing (and can be missed). If we put it at-the-source, we don't have that potential drift

On the other hand, I also get nervous about introducing mutex locks in high-volume functions like that, if not absolutely necessary for a general solution. At the end of the day this is probably 'fine' just because I don't think we're actually parallelizing across the **same device**, right? Ergo, this approach may be acceptable.

I would still ultimately defer to @mcherba 's input/insight on this matter.
