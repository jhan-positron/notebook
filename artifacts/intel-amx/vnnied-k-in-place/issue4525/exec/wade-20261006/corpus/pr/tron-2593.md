## PR body (as it is now; may have been edited after the review)

When running `gen/t_generate_2` at "tp1" (all eight FPGA devices claimed), a `TRON_ASSERT` fires in fire_gof_rodeo (h/tron/models/model.hpp:1597): "GOF rodeo for job 17 but token at pos 348 not kv_complete at layer 0"

The problem is that in TP1, the minibatch size is sometimes not a multiple of 4, which produces a situation where the downstream minibatch can fire the GOF before the upstream has finished writing the mates' K/V.

The fix provided here:

Replace the firing-token-only predicate `(pos+1)%gof_tokens==0 && k_completing` with a per-GOF, per-layer atomic `save_count` on `tron::hardware::gof`. Every `save_k`/`save_v` on a GOF participant — firing token or non-firing mate — does `fetch_add(1, acq_rel)`; the increment that reaches `2*gof_tokens` (8) fires `gof_rodeo`. At gal construction, mates already kv_complete from prior forwards (or non-query mates without saves coming) are pre-loaded by 2. The scheduler also replicates the firing slot's `gof_jobs[]` entry into each non-firing query mate's job_id, so any mate's save can fire and `gof_rodeo_impl` produces identical work via shared `gal_ptr`/`tok_position`/`shards_getting_gofs`.
