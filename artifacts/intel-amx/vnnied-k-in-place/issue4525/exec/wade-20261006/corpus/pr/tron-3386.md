## Summary
Adds host CPU telemetry (temperature, frequency, package power) to Tron Perfetto traces,
complementing the sibling story's kernel/OS events. Closes #3198. Two independent layers
(they toggle separately):

- **App-side `hw` sampler** (`src/pos/hwperf.cpp`) — a background thread polls `/sys` and
  emits `TRACE_COUNTER`s on a new `hw` track_event category: hwmon CPU temperature,
  cpufreq avg/max, and RAPL `energy_uj` → Watts. Works in the in-process `--trace FILE`
  backend (unlike ftrace). On by default; `TRON_HW_SAMPLER=0` opts out,
  `TRON_HW_SAMPLER_INTERVAL_MS` tunes the 100 ms interval,
  `TRON_HW_SAMPLER_ALL_SENSORS=1` adds per-sensor temperature detail.
- **Hardware ftrace** — `power/cpu_idle` + `power/cpu_frequency` added to the `--os-events`
  overlay (daemon backend only).

### Tracks emitted, per socket

| Track | Source | Notes |
|-------|--------|-------|
| `socket<N> package temp (C)` | hwmon `Tdie`/`Tctl`/`Package id N` | one per socket |
| `socket<N> core temp min/avg/max (C)` | the per-die/per-core sensors | aggregated |
| `<driver> socket<N> <label> (C)` | every individual sensor | only with `TRON_HW_SAMPLER_ALL_SENSORS=1` |
| `cpu avg/max freq (MHz, N of M app cores)` | cpufreq sysfs | bounded sample, see below |
| `<domain> power (W)` | RAPL `energy_uj` | needs the grant below |

**Temperatures are aggregated by default.** The raw sensor count is large and
vendor-dependent — a dual EPYC exposes 26 (`k10temp`, 13/socket), a dual Granite Rapids
~146 (`coretemp`, one per core) — so the default is package + min/avg/max per socket (4
tracks/socket), which still surfaces a single hot die in the max. Per-sensor detail is one
env var away. Individual sensors are named `<driver> socket<N> <label>`, so a multi-socket
box never produces anonymous tracks.

**Frequency is a bounded sample, and the track name says how bounded.** A cold
`scaling_cur_freq` read blocks: reading all 384 cpus of a dual EPYC measures ~7.9 s per
pass on `acpi-cpufreq` (warm reads no cheaper), so a full scan can't run at trace cadence.
The sample is taken over the configured **app (compute) cores** — the cores tron actually
pins compute to — so a loaded run can't read as idle; it falls back to online cpus when no
app core list is configured. This needed one new accessor,
`tron::hardware::system::app_get_cpus()`, exposing the configured app cpu list (a snapshot
that `app_pin_thread()` doesn't consume).

## Why the diff touches runtron.cpp / perf.cpp (hw-sampler lifecycle)
The hw sampler's enable/disable is consolidated into the single
`start_tracing()`/`end_tracing()` pair (`src/pos/perf.cpp`) instead of being wired
separately into `runtron.cpp`'s phase callbacks + teardown and the SIGUSR1 path — so every
trace path (whole-run, phased `--trace-gen`, pass-gated `--trace-passes`, rinzler SIGUSR1)
enables the sampler at session start and disables it before the flush by construction. The
sampler thread starts once at `pos_startup()` and joins at `pos_shutdown()`; it parks on a
condition variable until a trace begins, so a process that never traces pays only a
sleeping thread (no periodic wakeups), and the first sample lands immediately on enable
rather than up to an interval later.

`disable_hw_sampling()` is a **real quiesce**, not a flag store: the sampler holds a mutex
across each tick body, so once `disable` acquires it no tick is emitting and none can
start. That is what lets `end_tracing()` flush a settled session. It costs at most one tick
body of blocking, on the trace-teardown path only.
