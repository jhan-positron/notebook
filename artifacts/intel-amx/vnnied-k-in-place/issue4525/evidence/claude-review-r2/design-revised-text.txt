Short version

This revision incorporates the supplied design review. The interface choices below are concrete proposals; the reviewer questions remain open before implementation. Review dispositions record accepted fixes, deferred scope, and recommendations that require separate work.

2. Review request and proposed decisions

The problem is that a bare bf16* pointer does not identify the cache layout. The same pointer type can describe native K, packed V, or the child's blocked packed K. The proposed types make those kernel arguments distinct. [Saved review text]

The interpretation of the reviewer's reservation is right: it concerns a separate layout type. In the sketch, the layout is a template argument of both the owner and the view. It is not an ownership stage between them. The reviewer expressed doubt about that separation, rather than a final decision. [Saved review text]

-   Retain: private packed storage, restricted construction of views, mutable-to-read-only conversion, typed kernel arguments, and optimized bulk operations.
-   Choose: one concrete view per layout. This repeats a small amount of view plumbing when the child adds packed K. It avoids a public layout-policy template.
-   Limit the parent: expression reads and existing row operations. Defer slices, iteration, generic expression assignment, and expression constructors until a caller needs them.
-   Native K: reuse its current storage and view types. Typing the native-K kernel argument is the requested parent scope beyond the reviewer's packed-tensor sketch.

Questions for the reviewer before implementation

Use the choices below to review this design. They are proposals, not recorded reviewer approval. The document revision does not require answering them now.

  Question                                                           Proposed answer
  ------------------------------------------------------------------ -----------------------------------------------------------------------------------------------------------------------------------------------------------------
  May the address formula live in each concrete view?                Yes. Use separate V and K families with separate owners. Keep the duplicated conversion and access plumbing small.
  Should a const view object prevent mutation of its elements?       Yes, at both matrix and row rank. A const matrix yields a read-only row; a const row yields a read-only element. This differs from the sketch's span-like rule.
  May the view provide operator[] as well as at(token, dimension)?   Yes. The expression interface requires row indexing. Retain at() as an equivalent bounds-checked spelling.
  Is the smaller parent scope sufficient?                            Yes. Include expression reads and typed bulk operations; defer the general tensor write and slice interfaces.

The repository has mixed const behavior: a const matrix returns a read-only row, while a const rank-1 view can return a writable element. This design chooses the matrix rule for both new types. It does not claim a uniform repository precedent. [S3]

A future PR reply should link issue #4525 and these questions. This revision sends no message and changes no GitHub issue or PR.

Only the order in memory changes. A row still contains one token’s dimensions.

  Representation        Position from the start of the plane, in bf16 elements                                                             Where selected
  --------------------- ------------------------------------------------------------------------------------------------------------------ ------------------------------------------------------------------------------------------------------------------------
  Native K and AVX2 V   token * D + dimension                                                                                              First pull request. Keep the existing row-major path.
  Packed V              (token / 2) * (2 * D) + 2 * dimension + token % 2                                                                  First pull request, for V in the build with 16 fp32 values per vector instruction.
  Blocked packed K      ((((dimension / 32) * (R / 16) + token / 16) * 16 + (dimension % 32) / 2) * 16 + token % 16) * 2 + dimension % 2   PR #4424 only. Keep the existing layout-selection condition. Keep the kernel restricted to 64 tokens × 128 dimensions.

R is the stored token count. D is the stored dimension count. The packed-K formula uses groups of 32 dimensions and groups of 16 tokens. Within a tile, K uses the transposed packing idea. Across the plane, its 16-token and 32-dimension block order is also required; swapping the two plane coordinates alone is insufficient. [S1] [S10]

The new V storage type requires a positive even number of rows. Its column count must be positive and divisible by chunk_size, the selected SIMD width. This satisfies the sketch’s positive-dimension rule. The 16-lane packed set_v still requires widths divisible by 32 dimensions. The 8-lane forwarding wrapper retains its existing contiguous-row constraints; scaled_v_expr still supports 64, 128, 256, or 512 dimensions. Type constraints do not expand kernel support.

5. Interface design

These declarations specify the proposal. They have not been compiled. Keep the types in namespace tron and follow the repository's attributes and formatting.

    template <size_t Rows, size_t Cols> class v_vnni_tensor;
    template <typename T, size_t Rows, size_t Cols> class v_vnni_view;
    template <typename T, size_t Cols> class v_vnni_row;

    template <size_t Rows, size_t Cols>
    using native_k_view = view<bf16, true, false, seq<Rows, Cols>>;
    template <size_t Rows, size_t Cols>
    using const_native_k_view = const_view<bf16, true, false, seq<Rows, Cols>>;

Owner and expression reads

-   v_vnni_tensor contains a 64-byte-aligned bf16 array. It allocates no separate memory. Default construction leaves values uninitialized. Keep default construction, copying, and destruction trivial.
-   The owner does not inherit expr. Its interface is as_view() & and as_view() const &. Delete both rvalue forms, including const &&. Keep same-type copy and move operations defaulted. Store no pointer to its own array.
-   v_vnni_view<T,R,D> inherits expr<view_type,R,D>. v_vnni_row<T,D> inherits expr<row_type,D>. Restrict T to bf16 or const bf16.
-   The row stores its pair address and even/odd position by value. It remains valid after a temporary view object disappears, while the owner remains alive. Set dma = false: logical row values are not consecutive in memory.
-   Supply the shape and element aliases required by the existing expression consumers. Keep dim, element, const_element, shape0(), and valid() consistent with existing views. Do not inherit views<>, whose leaf rows must be contiguous.
-   Leave the rank-1 expression concept unchanged. Existing host tensors and hardware tensors read the matrix through its row expressions. Native K remains compatible with dotter, the existing query/key dot-product helper. [S2] [S3] [S4]

  Operation                                               Contract
  ------------------------------------------------------- ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  matrix[token][dimension], matrix.at(token, dimension)   Assert bounds using repository assertions. Non-const writable access changes only that element. Const matrix access yields a read-only row.
  const v_vnni_row<bf16,D> indexing                       Return read-only element access. An explicitly read-only row always rejects mutation, regardless of the row object's own const qualifier.
  row.chunk(i)                                            Return fp32 values in logical order. Read pair chunk i at pair_base + 2 * chunk_size * i. Extract the even or odd half with vector instructions.
  bf16s bf16_chunk(size_t i) const noexcept               Use this exact non-template override signature. Extract stored bf16 bits directly. The expression base detects the override through its member function; a different signature can silently select conversion instead.
  View copy / conversion                                  Copying a view rebinds access. Allow writable-to-read-only conversion only. No public pointer constructor, .data member, or pointer conversion for packed views.
  Raw storage access                                      detail::vnni_access is the internal friend used only by tensor operations and layout-specific kernels. It is an implementation boundary, not a security boundary.

For the 16-lane build, a pair chunk loads 32 bf16 elements in 64 bytes. The existing even_part shifts each 32-bit lane left by 16 bits; odd_part masks the high 16 bits. Reuse this extraction pattern for fp32 reads and narrow the selected halves for bf16 reads. A stride-2 ordinary row view has the right addresses but uses scalar extraction; it is not the bulk-read implementation. [S5] [F35]

One cache row-write rule

append_v_row is this design's name for the sketch's V store_row. The name records its cache semantics: an even destination zeros its odd partner; an odd destination preserves its even partner. There is no generic packed row.set(expr) in the parent.

    // Signature families: Source is bf16, fp16, or float.
    append_v_row(writable_v_view dst, size_t token, contiguous_source_row src);
    load_row(readonly_v_view src, size_t token, contiguous_destination_row dst);
    copy_token(writable_v_view dst, size_t dst_token,
               readonly_v_view src, size_t src_token);
    copy_plane(v_owner& dst, v_owner const& src);

The names writable_v_view and contiguous_source_row above describe parameter families, not additional types to implement.

-   Packed overloads take v_vnni_view<bf16,R,D> or v_vnni_view<const bf16,R,D>. Sources use the existing contiguous row view with the caller's scalar type and alignment. Preserve those properties at the call site.
-   append_v_row moves today's set_v vector bodies into h/tron/tensor/vnni.hpp. Keep even-token write and partner zeroing in one pass without a destination read. Odd-token writes merge into the initialized pair.
-   load_row moves today's get_v loops. Support the existing bf16 and float destinations needed by its callers. Wrap caller-owned scratch in an existing contiguous view; add no scratch-view type.
-   copy_token moves the four even/odd branches of today's append_v. An even destination zeros its partner. An odd destination preserves it. Retain the existing restrictions on overlap and fresh destination ranges.
-   copy_plane copies identical-layout owners byte for byte. Cache range splitting and completion copying remain in cache code.
-   The row-major V overload is a thin forwarder to existing contiguous .set(). It never clears another row.

6. Behavior the implementation must preserve

V padding and write ordering

A packed-V weighted sum rounds an odd live-token count up to a complete pair. The unused odd row must be zero: a NaN multiplied by a zero weight still contaminates the sum. The row-major path reads exactly the live-token count. [S5]

Reused pairOld even rowOdd row: NaN poison

→

Append even tokenNew even valuesOdd row: all zero

→

Append odd tokenEven values preservedNew odd values

The even append must clear the partner every time the pair is reused. This is an operation sequence, not a timing diagram.

  Write                   Destination read?                    Partner result
  ----------------------- ------------------------------------ -------------------------------------------------------------------
  Even cache append       No                                   Odd row becomes zero
  Odd cache append        Yes, pair must be initialized        Even row is preserved
  Direct element update   No read of other elements required   Other elements unchanged; this does not establish cache readiness

-   Production packed-V row writes use page::set_v or page::append_v. Both call the typed append/copy operations. Direct element mutation is useful for fixtures; it must not replace cache append.
-   Keep V pair writes sequential. A new view type does not make read/modify/write stores safe across threads.
-   Keep adjust_grains_for_partners, the scheduler's pair-preserving work partition, in model.hpp. Keep token_ix_needed, the partner-readiness rule, in common.hpp. Their layout knowledge remains necessary outside the tensor. Update their explanatory comments. [C02]
-   Completion counters, token allocation, live-token selection, EAGLE slot remapping, dependency notifications, and hardware submission remain cache/model responsibilities.

Conversions and weighted sums

  Path                                Required behavior
  ----------------------------------- ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Native K and 8-lane row-major V     Keep existing row-view .set() conversion. Do not substitute packed V conversion or clear adjacent rows.
  Packed V append from bf16           Preserve exact input bits. No float round trip.
  Packed V append from fp16 / float   Keep today's conversion to fp32 and upper-16-bit truncation. Do not substitute general expression conversion.
  Expression reads                    bf16_chunk() preserves stored bits. Existing destination types retain their own conversion rules.
  scaled_v_expr                       Keep the live count separate from the storage shape. Keep pair rounding only in the 16-lane packed path; the 8-lane row-major path reads exactly count rows. Preserve supported widths, weight conversion, unrolled loops, and addition order. Obtain the physical address only inside the typed implementation.

Packed set_v can turn an fp32 NaN with no upper mantissa bits into infinity when it discards the lower bits. Generic fp32s_to_bf16s, the expression conversion helper, sets the lowest retained mantissa bit when the exponent is all ones and discarded bits are nonzero. It skips that correction when TRON_IGNORE_NAN is defined. This preserves a NaN but does not necessarily make it a quiet NaN. Neither path rounds to nearest. Preserve each existing path separately. [S5] [S7]

Arena construction without clearing

book keeps ownership of the retained and reclaimable byte arenas. A kv_block still contains K followed by V for one head and page. Replace only the 16-lane V array with the packed owner. Keep native K and 8-lane V as their existing arrays. [S8]

    // Default-initialize the array at its allocated address.
    // No parentheses or braces after the array bound.
    ::new (static_cast<void*>(region_base)) kv_block_t[block_count];

-   Require trivial default construction, copyability, and destruction for both owner and block. Require 64-byte alignment, unchanged K/V offsets, and the existing block byte size. Keep the element storage uninitialized until written.
-   Do not use std::construct_at(p), T(), or T{} here. For the proposed trivial owner they value-initialize and clear storage. The pinned standard library does not provide the proposed std::start_lifetime_as alternative; remove that option. [F12] [F40]
-   Run the construction helper in book::allocate_kv_group after installing a successful allocation, before publishing access. Both initial allocation and restore_reclaimable_kv_storage use this path. Preserve the early return for zero-byte arenas.
-   For uniform geometry, construct one array over the just-allocated arena’s complete contiguous block region. Its bound is the checked arena byte count divided by sizeof(kv_block_t). This matches the existing uniform accessor's indexing across slots.
-   For heterogeneous geometry, enumerate physical storage offsets once and select only slots in the just-allocated arena. Restoring the reclaimable arena must not restart objects in the retained arena. Use the slot specifications to choose each region's compile-time head width and head count. layout_t::storage_location identifies its arena; slot_base gives arena + n_pages * byte_offset. Construct geometry.n_kv_heads * n_pages blocks at that address. Do not construct the same region again for a logical alias.
-   Include the physical EAGLE KV slot once, with the primary geometry. Do not touch x_data, the separate EAGLE embedding buffer; it contains no KV blocks. Construction cannot rely solely on the logical active-slot loop, which omits that extra physical slot. [C01] [C09]
-   Preserve failed-allocation and unpublished-restoration behavior. Do not construct in an accessor or cast an existing SIMD array object into the new owner.
-   Views expire when the arena is released, replaced, or destroyed. Do not retain them across restore. Append of an even token initializes a pair without reading it; append of an odd token requires the even partner to have been initialized.

Verify the construction form with the pinned compiler. Check the optimized allocation/restore paths for no memory-clearing loop or call. Test lifetime handling through mixed-geometry allocation, release, restore, and failure paths. A successful cast alone does not establish the required object lifetime.

Copies and hardware preparation

-   Preserve whole-plane byte copies, the four source/destination token-parity combinations, page-boundary splitting, overlap restrictions, and completion-state copying.
-   FPGA preparation still consumes dimension-ordered bf16 rows. The parent keeps native K directly readable and unpacks V into the existing caller-owned buffer.
-   Keep the parent's hardware::page_info K callback shape. The extra K scratch parameter belongs to the child. [S9]
-   Update Note [Zero-Initialized V Slots], the cache V-layout note, and comments naming v_data or physical V indexing. Describe the new call chain without weakening the partner-zero rule. [C06]
