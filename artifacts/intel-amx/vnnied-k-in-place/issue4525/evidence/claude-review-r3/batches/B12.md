# Batch B12: 4 items to check against the ROUND-3 design text

### N25 [round-2 NEW finding, severity MINOR] EAGLE bullet omits uniform-geometry requirement; misread as heterogeneous
- Where in the round-2 design: 6. Behavior the implementation must preserve (Arena construction without clearing)
- Relates to round-1 id(s): C01, C09, C01
- Claim: Ambiguity and omission: the EAGLE bullet follows the heterogeneous-geometry bullet and reads as part of that enumeration. EAGLE (the speculative model's extra cache slot) exists only with uniform geometry: eagle_compatible requires layout_t::uniform_geometry, storage_slot_count_for_layers asserts it, and calculate_allocation_sizes returns nullopt otherwise. Under uniform geometry the design's own rule is one array over the whole arena, which already covers the extra slot because arena_sizes adds it to the retained arena. So the heterogeneous enumeration never meets an EAGLE slot, and the bullet's warning about 'the logical active-slot loop' applies to a loop the design does not prescribe for that case. An implementing agent may add a dead EAGLE branch to the heterogeneous path or search for a heterogeneous EAGLE slot that cannot exist. Round-1 C01 asked for exactly this statement and the revision did not add it.
- The round-2 design text said: "Include the physical EAGLE KV slot once, with the primary geometry. Do not touch x_data, the separate EAGLE embedding buffer; it contains no KV blocks. Construction cannot rely solely on the logical active-slot loop, which omits that extra physical slot."
- Evidence given in round 2: kv_cache.hpp@2880c3aa9b:771 `eagle_compatible = layout_t::uniform_geometry && x_bytes > 0`; :788-789 TRON_ASSERT "EAGLE cache views require uniform geometry and embedding storage"; :1158 `if (support_eagle && (!eagle_compatible || ...)) return std::nullopt;`; :717-719 arena_sizes adds `offsets.values[1].total()` to `result.retained`; :1288-1289 uniform accessor indexes one array from kv_blocks_alias. design.txt:331-333. r1-findings.md C01 claim: 'Because EAGLE requires uniform geometry, a single array construction over the whole retained arena already covers the extra slot; the design does not say this either.'
- RECOMMENDATION (what the design was asked to change): Rewrite the bullet: 'EAGLE storage exists only with uniform geometry [kv_cache.hpp:771, 788-789, 1158]. The whole-arena array of the uniform case therefore already covers the extra EAGLE KV slot, which arena_sizes appends to the retained arena [717-719]. The heterogeneous enumeration never meets an EAGLE slot. Do not touch x_data, the separate EAGLE embedding buffer; it contains no KV blocks.' Move the bullet directly after the uniform-geometry bullet.
- VERIFIER CORRECTION (source lens): One refinement, not a refutation. The finding says the bullet's caution about "the logical active-slot loop" applies to a loop the design does not prescribe. The caution is still correct and useful: for_each_active_slot (kv_cache.hpp:1243-1249) iterates only `slot < logical_slot_count()` over slot_specs and cannot reach the EAGLE offset, and fill_random (:1060-1064) needs a separate `fill_storage_slot<layout_t::primary_geometry>(eagle_storage_offset(), ...)` call; round-1 C09's verifier correction named exactly that for_each_active_slot + EAGLE pattern as the precedent to reuse. N25's recommended rewrite drops the caution; keep it, qualified as in R09 ("if the implementer uses a per-offset loop for uniform layouts too, it must run over offsets 0 .. storage_slot_count_ - 1 and include eagle_storage_offset() with layout_t::primary_geometry; for_each_active_slot omits it"). Add to the rewrite that the EAGLE slot is the last primary-geometry slot of the RETAINED arena (:727-735, :716-719) and is constructed only in the constructor because restore re-allocates only the reclaimable arena (:968); without the arena placement the reader cannot link line 332's retained-arena sentence to EAGLE.
- VERIFIER CORRECTION (design-text lens): Two precisions to the finding's evidence, neither changes the verdict. (1) The design's heterogeneous bullet prescribes enumerating PHYSICAL storage offsets (design.txt:332: "enumerate physical storage offsets once"), so the sentence "Construction cannot rely solely on the logical active-slot loop" (design.txt:333) is a caution against the existing for_each_active_slot idiom [kv_cache.hpp@2880c3aa9b:1059-1064, where fill_random adds a separate eagle_storage_offset() call], which the design never prescribes; the finding should say the sentence warns against an approach the design does not use, rather than that it "applies to a loop the design does not prescribe for that case". (2) The cited "uniform accessor indexes one array from kv_blocks_alias" [kv_cache.hpp:1288-1289] is the uniform_reclaimability branch only; the else branch [1291-1299] uses slot_base per physical slot. This does not weaken the argument: the EAGLE slot is in the retained arena in both cases [storage_location :731-734], so the per-arena array of design.txt:331 covers it. Add to the recommendation, from R09 and round-1 C01 (b): "The EAGLE slot is constructed only in the constructor, because restore_reclaimable_kv_storage re-allocates the reclaimable arena only [kv_cache.hpp:968]."

### M04 [round-2 NEW finding, severity MINOR] Heterogeneous construction pass: the compile-time geometry dispatch helper is unnamed although book already has one
- Where in the round-2 design: 6. Behavior the implementation must preserve (Arena construction without clearing, heterogeneous bullet); 7. step 2
- Relates to round-1 id(s): C09, F12, C01
- Claim: Ambiguity. The heterogeneous bullet says to use the slot specifications to choose each region's compile-time head width and head count, but the geometry is a template argument of kv_block_t and the slot specifications are a constexpr array, so the agent needs a compile-time loop that hands each slot index its geometry as a template argument. book already has exactly that: for_each_active_slot, built on for_each_slot_impl over std::index_sequence, calls a generic lambda with `<size_t slot, kv_geometry geometry>` for every active logical slot. fill_random is the precedent: it runs for_each_active_slot and then handles the EAGLE slot separately with the primary geometry. The design names neither, so an agent may write a second index_sequence dispatch. Two facts that make the helper usable from inside allocate_kv_group, where the design places the construction, are also unstated: storage_slot_count_ is set in the constructor's initializer list before allocate_kv_group runs, so logical_slot_count() and slot_base are valid there; and slot_base returns nullptr for an arena not yet allocated, so the retained-arena pass (which runs before the reclaimable arena exists) must select slots by layout_t::storage_location(...).reclaimable, as the bullet says, not by a null check alone.
- The round-2 design text said: "For heterogeneous geometry, enumerate physical storage offsets once and select only slots in the just-allocated arena. Restoring the reclaimable arena must not restart objects in the retained arena. Use the slot specifications to choose each region's compile-time head width and head count."
- Evidence given in round 2: h/tron/models/kv_cache.hpp@2880c3aa9b:1236-1250 (`template <size_t... slots, typename F> static constexpr void for_each_slot_impl(std::index_sequence<slots...>, F&& function) { (function.template operator()<slots, kv_slot_specs[slots].geometry>(), ...); }` and `void for_each_active_slot(F&& function) const { size_t const active_slots = logical_slot_count(); ... if (slot < active_slots) function.template operator()<slot, geometry>(); }`), :1055-1065 (fill_random precedent), :1090-1094 (constructor initializer list sets `storage_slot_count_(storage_slot_count)`), :1101-1102 (`allocate_kv_group(false, retained_kv_bytes_) || allocate_kv_group(true, reclaimable_kv_bytes_)`), :1188-1197 (slot_base: `if (!arena) return nullptr;`). design.txt:332, :334 ("Run the construction helper in book::allocate_kv_group after installing a successful allocation"); grep of design.txt for for_each_active_slot: no match.
- RECOMMENDATION (what the design was asked to change): Add to the bullet: "Use book::for_each_active_slot (kv_cache.hpp:1243-1250), which calls a lambda with `<slot, geometry>` for each active logical slot, as fill_random does (:1057-1065); inside it, keep only slots whose layout_t::storage_location(offset, logical_slot_count()).reclaimable equals the arena being constructed, then construct geometry.n_kv_heads * n_pages blocks at slot_base(offset). storage_slot_count_ is already set when allocate_kv_group runs (:1094), so these calls are valid there. Do not test slot_base for null to select slots: the reclaimable arena is absent during the retained pass (:1193)."
- VERIFIER CORRECTION (source lens): Keep the claim, with two edits. (1) Replace the null-check sentence with: "A null test on slot_base selects correctly only in the retained pass (the reclaimable arena does not exist yet, kv_cache.hpp@2880c3aa9b:1192). In the reclaimable pass (constructor second call :1102 and restore_reclaimable_kv_storage :968) the retained arena is present, so retained slots also return non-null and would be constructed again. Filter by layout_t::storage_location(offset, logical_slot_count()).reclaimable == reclaimable (:727-735) in both passes." (2) Add: "The design alludes to the helper without naming it: design.txt:333 'the logical active-slot loop'. Name it." Cite slot_base's null return as :1192, not :1193.
- VERIFIER CORRECTION (design-text lens): Keep the finding as minor with these corrections. (a) Claim wording: the design refers to the helper obliquely ("the logical active-slot loop", design.txt:333) but never names for_each_active_slot, for_each_slot_impl or fill_random, and none of its kv_cache.hpp links (L1187-L1206, L1274-L1334, L946-L981) reaches lines 1055-1065 or 1236-1249; round-1 C09's verifier corrections asked for exactly this naming and the "Accepted" row at design.txt:468 did not adopt it. (b) Null-check reasoning: during the retained pass (first allocate_kv_group call, kv_cache.hpp:1101) the reclaimable arena is absent, so slot_base returns nullptr for reclaimable slots (:1193) and a null check would skip them by accident. The hazard is the reclaimable pass (:1102) and restore_reclaimable_kv_storage (:968): both arenas exist then, so a null check selects every slot and re-constructs the retained arena's objects, which design.txt:332 forbids ("Restoring the reclaimable arena must not restart objects in the retained arena"). Select by layout_t::storage_location(offset, logical_slot_count()).reclaimable == reclaimable, as the design already says. (c) Validity inside allocate_kv_group: both storage_slot_count_ and support_eagle_ are set in the initializer list (:1091-1093), and has_eagle_storage() returns support_eagle_ (:925-927), so logical_slot_count() (:920-922) is already correct there. (d) EAGLE: the heterogeneous per-slot pass never meets the EAGLE slot, because EAGLE requires uniform geometry (:771, :1149-1151) and the design constructs uniform arenas as one whole-arena array (design.txt:331). So for_each_active_slot alone is complete for the heterogeneous pass; the EAGLE branch of fill_random is needed only if the agent chooses per-slot construction for uniform layouts too. Recommended sentence for the bullet: "Reuse book::for_each_active_slot (kv_cache.hpp:1242-1249), which calls a lambda with <slot, geometry> template arguments as fill_random does (:1058-1065); inside it keep only slots whose storage_location(offset, logical_slot_count()).reclaimable equals the arena being constructed, and construct geometry.n_kv_heads * n_pages blocks at slot_base(offset). Do not select slots by a null slot_base: in the reclaimable pass and in restore both arenas exist."
- VERIFIER CORRECTION (intent lens): Three corrections, none changing the verdict. (a) "The design names neither" overstates: design.txt:333 refers to the helper descriptively ("Construction cannot rely solely on the logical active-slot loop, which omits that extra physical slot") but only as something insufficient for EAGLE; it never tells the agent to use it for the heterogeneous pass. Restate as: the design mentions the loop only as a caution and does not name for_each_active_slot or fill_random as the thing to reuse. (b) The null-check hazard is in the wrong pass. During the retained pass the reclaimable arena is absent, so slot_base returns nullptr for reclaimable slots [kv_cache.hpp@2880c3aa9b:1192] and a null check would skip them correctly by accident. The hazard is the reclaimable pass (initial at :1102, restore at :968): both arenas exist, a null check selects every slot, and the retained arena would be re-constructed. The design already forbids this at design.txt:332 ("layout_t::storage_location identifies its arena"; "must not restart objects in the retained arena"), so this sub-item needs no design change; drop it or keep it as a note. (c) Line nits: the null check is at :1192 (finding says :1193); storage_slot_count_ is initialized at :1093 (finding says :1094). Recommended design text stays as the finding proposes, minus the null-check sentence: "Use book::for_each_active_slot (kv_cache.hpp:1242-1249), which calls a lambda with <slot, geometry> for each active logical slot, as fill_random does (:1057-1065); inside it keep only slots whose layout_t::storage_location(kv_storage_offset(slot), logical_slot_count()).reclaimable equals the arena just allocated, then default-construct geometry.n_kv_heads * n_pages blocks at slot_base(kv_storage_offset(slot))."

### F12 [round-1 finding, round-1 grade MAJOR; round-2 status PARTLY] Arena construction pass under-specified: form, enumeration, check method
- Round-2 checker assessment of the previous revision: Round 1 (as narrowed by the verifiers) asked for four things: (a) the exact construction spelling with no parentheses or braces, (b) an explicit ban on std::construct_at(p), T() and T{} as value-initialization, (c) the call sites book::allocate_kv_group and restore_reclaimable_kv_storage named in prose, and (d) an executable check for unwanted clearing, plus the refinement that construction runs once per slot region and that the EAGLE region exists only under uniform geometry. Items (a), (b) and (c) are met exactly (design.txt:324-330). The enumeration is right and verified: retained/reclaimable bytes are n_pages times the sum over slots of n_kv_heads * (2 * 64 * head_size * 2) bytes [kv_cache.hpp:651-668, 1160-1166 @2880c3aa9b], so under uniform geometry the arena is an exact multiple of sizeof(kv_block_t) and the whole-arena array bound is correct; the uniform accessor indexes blocks[(slot.i * n_kv_heads + kv_head) * n_pages + pg] from one base [kv_cache.hpp:1283-1284], which the whole-arena array matches; storage_location and slot_base are described correctly [kv_cache.hpp:727-736, 1188-1198]; the zero-byte early return exists [kv_cache.hpp:1200]; restore allocates only the reclaimable arena [kv_cache.hpp:963-974]. The EAGLE bullet (design.txt:333) is accurate but incomplete: the EAGLE physical slot exists only when `eagle_compatible = layout_t::uniform_geometry && x_bytes > 0` [kv_cache.hpp:771] and calculate_allocation_sizes returns nullopt otherwise [kv_cache.hpp:1157-1158]; it lives in the retained arena after the active retained prefix [kv_cache.hpp:716-718, 733-735], so the uniform whole-arena array already covers it, and the heterogeneous path never has one. The bullet does not say this, so an implementer may add a dead EAGLE branch to the heterogeneous enumeration. Item (d) was met by a different means: the type-trait-only check was replaced by inspection of the optimized allocation/restore paths for memset or clearing loops (design.txt:337, 399, 441). That detects the failure mode but is a manual disassembly step rather than the executable poison-fill test the verifier asked for. The tensor.hpp:263 construct_at precedent warning is absent; the explicit ban at :329 covers its practical effect. Note, not a defect: the array form places element 0 at region_base without an array cookie only because kv_block_t is trivially destructible (Itanium ABI cookie rule), which design.txt:328 already requires.
