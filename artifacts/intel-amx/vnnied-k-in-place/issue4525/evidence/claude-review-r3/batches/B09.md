# Batch B09: 6 items to check against the ROUND-3 design text

### N14 [round-2 NEW finding, severity MINOR] native_k_view alias relies on Stride default; header unstated
- Where in the round-2 design: 5. Interface design (declarations block, kernel signatures, Build and include boundaries)
- Relates to round-1 id(s): F43, F11
- Claim: Ambiguity that makes the implementer guess: the alias `native_k_view<Rows,Cols> = view<bf16, true, false, seq<Rows, Cols>>` has four template arguments and relies on the fifth parameter's default `Stride = row_major<Dim>`. That default is declared only in h/tron/tensor/views.hpp (the header that defines tron's view primary template), which pulls in expr.hpp and the SIMD intrinsics headers. The same section tells the implementer to keep amx_attn_iface.hpp (the AMX kernel interface header) intrinsics-free, to forward-declare the five-parameter view/const_view templates, and not to repeat template defaults. A forward declaration without the default cannot supply it, so the kernel declaration `qk_rowmajor_128x4(const_native_k_view<PAGE_TOKENS_64, HEAD_SIZE_128> k_page, ...)` as printed cannot be written in that header. The two spellings the design offers (std::integer_sequence or a shared declarations header) both require the stride to be written out. Round-1 F43's verifiers asked for exactly this (stride spelled as sseq<Cols,1>); the revised alias text did not change. The resulting type is the same as page::k / kv_block::k_view return today, so the risk is a compile error and a guess, not a wrong build.
- The round-2 design text said: "using native_k_view = view<bf16, true, false, seq<Rows, Cols>>; [...] using const_native_k_view = const_view<bf16, true, false, seq<Rows, Cols>>; [...] Forward-declare the packed view and the existing five-parameter view/const_view templates. Spell native dimensions and strides with std::integer_sequence, or share a small intrinsics-free declarations header. [...] Do not repeat template defaults."
- Evidence given in round 2: h/tron/tensor/views.hpp:22-27@2880c3aa9b (`template <typename T, bool aligned, bool dma, typename Dim, typename Stride = row_major<Dim>> struct view`) and :31-36 (const_view with the same default); h/tron/kernels/expr.hpp:17-22@2880c3aa9b (forward declarations of view/const_view WITHOUT the default: the precedent the design follows); h/tron/tensor/seq.hpp:21-25, 393-394@2880c3aa9b (seq, sseq, row_major; seq.hpp includes only common/assert.hpp, common/attributes.hpp, common/numerics/std.hpp, none of which contain intrinsics per grep); h/tron/models/kv_cache.hpp:2208-2219@2880c3aa9b (k_view returns view<bf16, true, false, seq<page_size, head_size>> / const_view<...>, i.e. the defaulted stride sseq<head_size,1>); design.txt:203-205, :261, :272-273; r1-findings.md F43 verifier correction ('the alias const_native_k_view needs seq.hpp included and the stride spelled out (sseq<HEAD_SIZE_128,1>)').
- RECOMMENDATION (what the design was asked to change): Change the two aliases to five arguments: `using native_k_view = view<bf16, true, false, seq<Rows, Cols>, sseq<Cols, 1>>;` and the const twin (sseq<Cols,1> equals row_major<seq<Rows,Cols>>). State where they live: a small intrinsics-free declarations header that includes tron/tensor/seq.hpp, forward-declares `template <typename T, bool aligned, bool dma, typename Dim, typename Stride> struct view;` and `struct const_view;` (five parameters, no default, as expr.hpp:17-22 does), and forward-declares `template <typename T, size_t Rows, size_t Cols> class v_vnni_view;`. amx_attn_iface.hpp includes that header. Add one sentence: the alias is the exact type page::k / kv_block::k_view return today (kv_cache.hpp:2210, 2217), so callers need no conversion.
- VERIFIER CORRECTION (design-text lens): The design already instructs the implementer to spell dimensions and strides explicitly inside amx_attn_iface.hpp (design.txt:272) and records that intent in section 9 (design.txt:475), so the claim "the kernel declaration as printed cannot be written in that header" applies to the alias and snippet as printed, not to the design's stated method. The residual defects are three: (1) the stride value is never given (row_major<seq<Rows,Cols>> resolves to sseq<Cols,1>, seq.hpp:379-394@2880c3aa9b); (2) no header is named as the single definition site of native_k_view and const_native_k_view, and steps 1-4 (design.txt:352-355) do not place them; (3) the kernel snippet at design.txt:261 uses the four-argument alias inside a declaration that step 4 places in amx_attn_iface.hpp, which contradicts :272 for that header. The recommendation stands: write the two aliases with five arguments (`sseq<Cols, 1>` as Stride), name the intrinsics-free declarations header that defines them (including tron/tensor/seq.hpp and forward-declaring view, const_view and v_vnni_view), say amx_attn_iface.hpp includes it, and add one sentence that the alias equals the type kv_block::k_view returns (kv_cache.hpp:2210, 2217@2880c3aa9b).
- VERIFIER CORRECTION (intent lens): The finding is right; one addition strengthens it. The design's option 1 ("Spell native dimensions and strides with std::integer_sequence", design.txt:272) is a consistent route only if the element types are also stated: dims are std::integer_sequence<size_t, ...> (seq, seq.hpp:21-22) and strides are std::integer_sequence<ptrdiff_t, ...> (sseq, seq.hpp:24-25). A stride written as std::integer_sequence<size_t, 128, 1> names a different const_view type from the one page::k / kv_block::k_view return (kv_cache.hpp:2215-2219, default row_major<seq<64,128>> = sseq<128,1>), and the call site then fails to compile. The recommendation should therefore say: write the fifth argument as sseq<Cols, 1> (or row_major<seq<Rows, Cols>>, which seq.hpp:393-394 provides intrinsics-free), and name the one header that defines the two aliases exactly once.

### N20 [round-2 NEW finding, severity MINOR] v_vnni_row constructor not covered by no-public-pointer rule
- Where in the round-2 design: 5. Interface design (operation contract table)
- Claim: Ambiguity. The reviewer's rule is that a private constructor prevents relabelling an arbitrary row-major pointer as packed data. The design applies "No public pointer constructor ... for packed views", but v_vnni_row (the logical-row expression type) "stores its pair address and even/odd position by value" and is not called a view, so an implementing agent may give it a public (pointer, parity) constructor; any caller could then relabel a pointer as a packed row and write through it.
- The round-2 design text said: "View copy / conversion  Copying a view rebinds access. Allow writable-to-read-only conversion only. No public pointer constructor, .data member, or pointer conversion for packed views."
- Evidence given in round 2: Ben comment 5765866077: "The private constructor prevents routine callers from relabelling an arbitrary row-major pointer as packed data." design.txt:212, :222; design.txt:43 (Words: "v_vnni_row reads one logical row").
- RECOMMENDATION (what the design was asked to change): Add to the contract row: "v_vnni_row has the same restrictions: its (pair address, parity) constructor is private, v_vnni_view<T,R,D> is its friend and only producer, it exposes no pointer, and detail::vnni_access is the only pointer reader."
- VERIFIER CORRECTION (design-text lens): The finding stands; sharpen its recommendation in two places. (1) The friend list needs one more entry: the design requires writable-to-read-only conversion for all packed types [design.txt:222], so v_vnni_row<const bf16,D> must accept v_vnni_row<bf16,D>; give the row a `template <typename, size_t> friend class v_vnni_row;` declaration (Ben's sketch does the same for vnni_view with `template <typename, typename> friend class vnni_view;`). (2) Replace "detail::vnni_access is the only pointer reader" with "the row exposes no pointer; its own operator[], chunk() and bf16_chunk() are the only readers of the stored pair address, and detail::vnni_access need not be its friend", because the design's bulk operations take matrix views plus a token index, not rows [design.txt:231-236]. Optionally add "reject a v_vnni_row constructed from a raw pointer" to the compile-check row at design.txt:397, so the rule has a test.
- VERIFIER CORRECTION (intent lens): Claim stands as written. Sharpen the recommendation in two places: (1) also befriend v_vnni_row<bf16,D> from v_vnni_row<const bf16,D> so the writable-to-read-only conversion the design allows at design.txt:222 still compiles with a private constructor; (2) add "construct a packed row from a raw pointer" to the reject list of the compile-check row at design.txt:397, so the rule is tested. Note for the lead: the kernel boundary is unaffected either way, because kernels take v_vnni_view and no row-to-view conversion exists.
