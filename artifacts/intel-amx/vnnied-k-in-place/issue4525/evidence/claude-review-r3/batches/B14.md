### N31 [round-2 NEW finding, severity MINOR] K token lane sentence imprecise: one lane per line, 64 lines
- Where in the round-2 design: 7. Implementation steps and files (K stores differ from V stores)
- Relates to round-1 id(s): C05
- Claim: Factual imprecision: the sentence says a K token owns several 4-byte lanes in one shared cache line. In the child layout a token owns exactly one 4-byte lane (its two consecutive dimensions) in each of 64 different 64-byte lines, and 16 tokens share every line. The rest of the paragraph is right: the row store is 4 dword scatters, the block store uses lane-masked stores, and the shared save lets two threads write disjoint lanes of the same lines.
- The round-2 design text said: "A K token owns separate 4-byte lanes in a shared cache line."
- Evidence given in round 2: h/tron/kernels/k_vnni.hpp@30c4ac82cb:16-17 "One 64-byte row holds that dimension pair for 16 consecutive tokens"; :29-30 "Token i owns column (i % 16) of token block (i / 16) in every panel"; :139-146 scatter_row = 4 x _mm512_i32scatter_epi32 with DWORD_BYTES_4 scale; :210-214 masked `_mm512_mask_storeu_epi32(panel + dp * ROW_ELEMS_32, present, r[dp])`. h/tron/gof.hpp@30c4ac82cb (child diff) "One 64-byte line holds that 4-byte unit for 16 tokens, so a token's 128 values sit in 64 lines". h/tron/models/common.hpp@30c4ac82cb (child diff k_store_window_t comment) "Their writers touch disjoint token lanes (masked stores). So two threads may write one block without conflict."
- RECOMMENDATION (what the design was asked to change): Replace with: "A K token owns one 4-byte lane (two consecutive dimensions) in each of 64 cache lines. Sixteen tokens share every line."
- VERIFIER CORRECTION (design-text lens): The finding stands as written. Recommended sentence: "A K token owns one 4-byte lane (two consecutive dimensions) in each of the 64 cache lines of its token block. Sixteen tokens share every line."
