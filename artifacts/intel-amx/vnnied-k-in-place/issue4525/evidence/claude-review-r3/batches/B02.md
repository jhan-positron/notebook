### N02 [round-2 NEW finding, severity MAJOR] TRON_IGNORE_NAN on in every non-Debug build; NaN row build-dependent
- Where in the round-2 design: 6. Behavior the implementation must preserve (Conversions and weighted sums) and 8. Verification (Bits and conversions row)
- Relates to round-1 id(s): F41
- Claim: Omission: the design says the generic conversion skips its NaN correction when TRON_IGNORE_NAN (the compile-time switch that disables NaN handling in the SIMD conversion helpers) is defined, but it does not say when that happens. TRON_IGNORE_NAN is defined for every non-Debug configuration, as a PUBLIC compile option of the tron library, so every test that links tron inherits it. All three configurations in the design's section 8 table use `cmake --preset native`, and the native preset is RelWithDebInfo. The required Nix CI build is also RelWithDebInfo. In every one of those builds fp32s_to_bf16s (the generic bf16 conversion) truncates exactly like the packed set_v path, so 0x7F800001 becomes 0x7F80 (+Inf) on both paths. Only the Debug presets asan, tsan and coverage produce the 0x7F81 result the design's paragraph describes. The section 8 row 'Keep packed append and generic expression conversion expectations separate' therefore cannot be implemented with fixed NaN expectations: a value chosen from the design's prose passes in Debug and fails under `--preset native` and in required CI, or the reverse. The same build dependence applies to fp16 NaN sources, where the two paths give 0x7FC0 versus 0x7FC1 in Debug and identical 0x7FC0 elsewhere. The round-1 F41 verifier correction stated this dependence explicitly; the revised text carries only the conditional clause.
- The round-2 design text said: "It skips that correction when TRON_IGNORE_NAN is defined. This preserves a NaN but does not necessarily make it a quiet NaN. Neither path rounds to nearest. Preserve each existing path separately. [S5] [S7]"
