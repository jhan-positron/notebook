### M02 [round-2 NEW finding, severity MINOR] fill_storage_slot: a whole-block raw V writer the search pattern and the raw-access rule both miss
- Where in the round-2 design: 5. Interface design (Raw storage access row); 7. Implementation steps (step 2, step 6, caller search at the end of the table)
- Relates to round-1 id(s): F10, C06, F01
- Claim: Omission. The design says detail::vnni_access (the private friend that hands out the packed plane pointer) is the only raw access, and its caller search uses the names v_base, v_data, set_v, get_v, append_v and scaled_v. book::fill_storage_slot (a test-only helper called by book::fill_random) matches none of those names. It reinterpret_casts a whole kv_block (the per-head K-then-V storage block) to bf16* and writes every element, including the V plane, by index. Its comment says it bypasses the zero-initialized V invariant on purpose. After the parent, that loop writes through the packed owner's object representation from outside the type. The implementing agent has to decide whether that stays (a byte fill of a trivially copyable block is legal and keeps the test's intent) or moves into the owner, and the design gives no rule and would not find the site with its own search. t_llama_unit's fixed-layout append case depends on fill_random.
- The round-2 design text said: "detail::vnni_access is the internal friend used only by tensor operations and layout-specific kernels. It is an implementation boundary, not a security boundary."
- Evidence given in round 2: h/tron/models/kv_cache.hpp@2880c3aa9b:1365-1374 (`void fill_storage_slot(kv_storage_offset offset, Distribution& distribution, Gen& gen) noexcept { ... auto& block = kv_block_at_storage<geometry>(offset, kv_head, pg); bf16* data = reinterpret_cast<bf16*>(&block); for (size_t i = 0; i < sizeof(block) / sizeof(bf16); ++i) data[i] = static_cast<bf16>(distribution(gen)); }`), :1055-1065 (`// For testing only. - RECOMMENDATION (what the design was asked to change): Add to the callers table: "book::fill_storage_slot / fill_random (test-only, kv_cache.hpp:1055-1065, 1365-1374): keep as a byte fill of the whole trivially copyable block; it intentionally bypasses the partner-zero rule and stays outside the typed operations. Say so in its comment." Add `fill_random|fill_storage_slot` to the search at design.txt:360, and state in the definition of done that this test-only fill is the one raw whole-block writer allowed outside detail::vnni_access.
- VERIFIER CORRECTION (source lens): Three wording fixes, none changing the verdict. (a) The design does not literally say detail::vnni_access "is the only raw access"; design.txt:223 says it "is the internal friend used only by tensor operations and layout-specific kernels", and :450 says packed physical addresses are confined to those places. - VERIFIER CORRECTION (design-text lens): Omission (narrowed). The revised design never mentions book::fill_random / book::fill_storage_slot (kv_cache.hpp@2880c3aa9b:1055-1065, 1364-1374), the test-only helper that fills every bf16 of a whole kv_block, including the V plane, through reinterpret_cast<bf16*>(&block), used by t/t_llama_unit.cpp:784-785 and :2008. ### M07 [round-2 NEW finding, severity NOTE] detail::vnni_access: one struct for two view families in two headers, or two structs, is unstated
- Where in the round-2 design: 5. Interface design (Raw storage access row); 7. Then adapt PR #4424 (child step 4 and the t_k_vnni_layout paragraph)
- Relates to round-1 id(s): N58, N59, C04
- Claim: Ambiguity (child scope). The reviewer's sketch has one detail::vnni_access whose packed_data is a template over vnni_view<T, Layout>. The design keeps the name for the V view and reuses it for the K view, but it splits the types into h/tron/tensor/vnni.hpp (V) and h/tron/tensor/k_vnni.hpp (K). A friend declaration must name one struct, so either k_vnni.hpp includes vnni.hpp to befriend the same struct and vnni_access gains overloads for both families, or each header defines its own access struct under a different name. The design says neither, and N58 and N59 do not cover this.
- The round-2 design text said: "Adapt t_k_vnni_layout to create actual aligned k_vnni_tensor owners and call typed store/load/block/reader operations through as_view(). Retain the independent index expectations. For physical-byte checks, copy the trivially copyable owner's object representation into a test buffer. Do not use detail::vnni_access to recreate raw production calls."
- Evidence given in round 2: Ben comment 5765866077 (github-review.json comments[3]) section 4: `namespace detail { struct vnni_access { template <typename T, typename Layout> static T* packed_data(vnni_view<T, Layout> view) noexcept { return view.data_; } }; }`. design.txt:223 ("detail::vnni_access is the internal friend"), :385 ("Do not use detail::vnni_access to recreate raw production calls"), :352 (vnni.hpp, new), :369 ("Define k_vnni_tensor, k_vnni_view, and its row expression in h/tron/tensor/k_vnni.hpp").
- RECOMMENDATION (what the design was asked to change): Add one sentence to child step 4: "detail::vnni_access is defined once in h/tron/tensor/vnni.hpp; k_vnni.hpp includes vnni.hpp, k_vnni_view befriends the same struct, and packed_data gains an overload (or a template over both view families)." Or name a separate detail::k_vnni_access and say why.
- VERIFIER CORRECTION (source lens): The claim stands as written. Refine the recommendation's option list: besides (a) k_vnni.hpp includes vnni.hpp and befriends the same struct, and (b) a separately named detail::k_vnni_access, there is (c) the form in Ben's sketch: k_vnni.hpp forward-declares `namespace detail { struct vnni_access; }` and befriends it, with one definition of vnni_access (a template over any packed view type) kept in vnni.hpp or a small shared header that h/tron/kernels/k_vnni.hpp includes. The design should name one of the three in child step 4 (design.txt:369) or next to the t_k_vnni_layout sentence (design.txt:385).
- VERIFIER CORRECTION (design-text lens): One clause of the finding's mechanism sentence is too narrow, not wrong. A C++ friend declaration with a qualified name (`friend struct detail::vnni_access;`) needs only a prior declaration of that struct, not its definition. Ben's sketch does exactly this with `namespace detail { struct vnni_access; }` before the view (github-review.json comments[3].body, section 2). So tensor/k_vnni.hpp does not have to include tensor/vnni.hpp to befriend the same struct; a forward declaration suffices. What still must be decided is where the one definition of `packed_data` lives and how it accepts both view families: a generic template over any befriending view type in a header both families' kernels include, or overloads that require the definition to see `k_vnni_view`, or a second struct under a different name (for example detail::k_vnni_access). The finding's conclusion that the design states none of this stands; its recommendation's parenthetical "(or a template over both view families)" already covers the generic-template option. Suggested wording for child step 4: "detail::vnni_access is declared once (forward declaration in each view header) and defined once in h/tron/tensor/vnni.hpp as a template over any befriending view type; k_vnni_view befriends it" or "the K family defines its own detail::k_vnni_access", with one clause saying why.
- VERIFIER CORRECTION (intent lens): What survives is a wording nit, not an ambiguity requiring a structural sentence: design.txt:385 uses the V family's struct name detail::vnni_access inside the K test paragraph, while :80 says the K family has its own duplicated access plumbing. Change :385 to "Do not use the K family's internal accessor (the K counterpart of detail::vnni_access) to recreate raw production calls." Do not add the recommended "k_vnni.hpp includes vnni.hpp" sentence: a forward declaration of the friend struct suffices, as Ben's sketch shows.
