### N13 [round-2 NEW finding, severity MINOR] bf16_chunk 'different signature silently selects conversion' is wrong
- Where in the round-2 design: 5. Interface design (operation table) and 8. Verification (Expression reads row)
- Relates to round-1 id(s): F35
- Claim: Factual error: the revision repeats the claim that a different bf16_chunk signature silently selects conversion. The expr base (expr.hpp, tron's expression interface) decides by comparing member-function pointers: `if constexpr (&B::bf16_chunk != &expr::bf16_chunk)`. Only a MISSING override takes the fallback silently. A mismatched const qualifier, parameter type, return type, an overload set, or a template makes `&B::bf16_chunk` ill-formed or incomparable, which is a compile error. A missing noexcept still compares unequal and the override is used. Factual error: section 8 calls the fallback lossy. The fallback fp32s_to_bf16s(chunk(i)) truncates and only changes bits when the exponent is saturated and the low 16 bits are nonzero; after even_part (shift left 16) or odd_part (mask high 16) the low 16 bits are always zero, so the fallback is bit-exact for stored bf16 and only costs extra instructions. The section-8 check 'exact bf16 copies with independent patterns' therefore cannot detect an omitted override. Round-1 F35's verifier corrections said both of these; the revised handling of F35 kept the wrong sentence.
- The round-2 design text said: "bf16s bf16_chunk(size_t i) const noexcept  Use this exact non-template override signature. Extract stored bf16 bits directly. The expression base detects the override through its member function; a different signature can silently select conversion instead. [...] The new type cannot be consumed by expr, or silently takes a lossy fallback."
- Evidence given in round 2: h/tron/kernels/expr.hpp:110-117@2880c3aa9b (`bf16s bf16_chunk(size_t i) const noexcept { if constexpr (&B::bf16_chunk != &expr::bf16_chunk) return self().bf16_chunk(i); else return fp32s_to_bf16s(self().chunk(i)); }`); h/tron/simd/bf16.hpp:92-109@f46e48ba (fp32s_to_bf16s: OR 0x00010000 only where exponent == 0x7f800000 AND low 16 bits != 0, then srli 16); h/tron/models/kv_cache.hpp:2000-2007@2880c3aa9b (odd_part = and hi_16_of_32, even_part = slli_epi32 16: low 16 bits zero); design.txt:221 and :398; r1-findings.md F35 verifier corrections ('Silent fallback happens only when vnni_row declares no bf16_chunk at all ... a compile error, not a silent fallback'; 'bit-exact for data that came from bf16').
- RECOMMENDATION (what the design was asked to change): Replace the contract text with: 'expr<B,N>::bf16_chunk compares member-function pointers (&B::bf16_chunk != &expr::bf16_chunk, expr.hpp:112). Declare exactly one non-template, non-overloaded `bf16s bf16_chunk(size_t) const noexcept` in v_vnni_row. Omitting it silently selects fp32s_to_bf16s(chunk(i)); that fallback is bit-exact for stored bf16 but adds a shift, NaN check, and narrow per chunk. Guard the override with `static_assert(std::is_same_v<decltype(&v_vnni_row<const bf16, 128>::bf16_chunk), bf16s (v_vnni_row<const bf16, 128>::*)(size_t) const noexcept>)` in vnni.hpp.' In section 8, change 'silently takes a lossy fallback' to 'silently takes the fp32 conversion fallback (bit-exact, slower)' and name the static_assert or the instruction record, not a bit-pattern test, as the detection.
- LEAD NOTE (final grade minor): The verifiers agree on the mechanism: expr.hpp compares member-function pointers, so a wrong signature is a compile error and only a missing override falls back silently. They also agree the fallback is bit-exact for stored bf16 (the low 16 bits are zero after even_part or odd_part), so section 8's word lossy is wrong and a bit-pattern test cannot detect the omission. The revision introduced this sentence; the original design did not have it.
- VERIFIER CORRECTION (source lens): Replace "the revision repeats the claim" with "the revision introduces the claim" (the original design row at design-text.txt:260 had neither the "different signature" sentence nor "lossy fallback"). Qualify the noexcept sub-claim: per the C++ standard a missing noexcept compiles and the override is used, but g++ 11.4 rejects the comparison as distinct pointer types; clang 19 (the tron toolchain) was not tested here. In both cases the result is a compile-time outcome, never a silent fallback.
- VERIFIER CORRECTION (design-text lens): Two wording corrections to the finding; the substance stands.

(1) "the revision repeats the claim" and "kept the wrong sentence" are inaccurate. The original design (/tmp/issue4525-design-before.html, 67,216 bytes = the round-1 size in facts-r2.md) contains zero occurrences of "lossy", "silently" or "different signature"; its bf16_chunk row read "Extract the stored bf16 bits directly.
