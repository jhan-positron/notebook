# Typed cache tensors for packed V and native K

Issue #4525 <https://github.com/positron-ai/tron/issues/4525> · Assigned to jhan-positron · Repository: positron-ai/tron

[#short]

## Short version

Give packed V its own storage type and use layout-specific cache arguments at the kernel boundary. Native K keeps its existing storage and view. Add this interface on main first, then adapt PR #4424 to use a separate packed-K owner.

This revision incorporates the round-2 review <claude-review-design-new-tensor-type.html>, including its verifier corrections. It narrows the 8-lane work, makes conversion checks depend on the build mode, and specifies the child's storage migration. The decision record separates proposed choices from reviewer agreement. Section 9 records the changes and remaining implementation or approval work.

## 2. The reviewer's comments and proposed decisions

The problem is that a bare bf16* pointer does not identify the cache layout. The same pointer type can describe native K, packed V, or the child's blocked packed K. The proposed types make those kernel arguments distinct. [Saved GitHub comments and issue] <../evidence/github-review.json>

| Request | Source, 21 September 2026 UTC | Decision |

| #2: typed tensors | Review 5270587330 , 18:53:47 | Keep rank-2 expression access and logical row reads. Give bulk load/store and kernel arguments types that identify their layout. |
| #3: interface sketch | Comment 5765866077 , 18:58:31; edited 18:59:58 | Keep an aligned owner separate from the view. Put the address formula inside each concrete view. Treat this as this design's choice, pending reviewer agreement. |

The issue author's reading identifies the reviewer's concern correctly: the concern is a separate layout type. In the sketch, the layout is a template argument of both the owner and the view. It is not an ownership stage between them. The reviewer expressed doubt about that separation, rather than a final decision. [Saved GitHub comments and issue] <../evidence/github-review.json>

- Retain: private packed storage, restricted construction of views, mutable-to-read-only conversion, typed kernel arguments, and optimized bulk operations.
- Choose: one concrete view per layout. This repeats a small amount of view plumbing when the child adds packed K. It avoids a public layout-policy template.
- Limit the parent: expression reads and existing row operations. Defer slices, iteration, generic expression assignment, and expression constructors until a caller needs them.
- Native K: reuse its current storage and view types. The issue author requested native-K typing in issue #4525. The parent changes the K parameter of qk_rowmajor_128x4 from a pointer to the existing read-only matrix view. This is an issue-author scope decision beyond the sketch's packed types.

| Representation | Position from the start of the plane, in bf16 elements | Where selected |
| Native K and AVX2 V | token * D + dimension | First pull request. Keep the existing row-major path. |
| Packed V | (token / 2) * (2 * D) + 2 * dimension + token % 2 | First pull request, for V in the build with 16 fp32 values per vector instruction. |
| Blocked packed K | ((((dimension / 32) * (R / 16) + token / 16) * 16 + (dimension % 32) / 2) * 16 + token % 16) * 2 + dimension % 2 | PR #4424 only. Keep the existing layout-selection condition. Keep the kernel restricted to 64 tokens × 128 dimensions. |

R is the stored token count. D is the stored dimension count. The packed-K formula uses groups of 32 dimensions and groups of 16 tokens. Within each 16-token by 32-dimension panel, K uses transposed packing. Across the plane, dimension groups are outermost and token blocks are next. Swapping the two plane coordinates alone does not produce this order. [S1][S10]

The new V storage type requires a positive even number of rows. Its column count must be positive and divisible by chunk_size, the selected SIMD width. This satisfies the sketch’s positive-dimension rule. The 16-lane packed set_v still requires widths divisible by 32 dimensions. The packed scaled_v_expr supports 64, 128, 256, or 512 dimensions. The unchanged 8-lane path requires head_size / chunk_size % 8 == 0. There is no new 8-lane V-save wrapper. Type constraints do not expand kernel support.

## 5. Interface design

These declarations specify the proposal. They have not been compiled. Keep the types in namespace tron and follow the repository's attributes and formatting.

// h/tron/tensor/kv_cache_fwd.hpp: declarations only, no intrinsics. template <size_t Rows, size_t Cols> class v_vnni_tensor; template <typename T, size_t Rows, size_t Cols> class v_vnni_view; template <typename T, size_t Cols> class v_vnni_row; template <size_t Rows, size_t Cols> using native_k_view = view<bf16, true, false, std::integer_sequence<size_t, Rows, Cols>, std::integer_sequence<ptrdiff_t, Cols, 1>>; template <size_t Rows, size_t Cols> using const_native_k_view = const_view<bf16, true, false, std::integer_sequence<size_t, Rows, Cols>, std::integer_sequence<ptrdiff_t, Cols, 1>>;

The new declarations header also forward-declares the actual bf16, view, and const_view classes in their existing namespaces. Declare all five view parameters without defaults. Include only the standard headers needed for sizes and integer sequences. The explicit strides avoid depending on a default declared in an intrinsics-bearing header. [S15]

### Owner and expression reads

- v_vnni_tensor contains exactly one 64-byte-aligned bf16 array. It allocates no separate memory. Default construction leaves values uninitialized. Keep construction, copying, and destruction trivial. The owner does not inherit expr.
- Provide as_view() & and as_view() const &. Delete both rvalue forms, including const &&. Keep same-type copy and move operations defaulted. Store no pointer to the owner's own array.
- v_vnni_view<T,R,D> inherits expr<view_type,R,D>. v_vnni_row<T,D> inherits expr<row_type,D>. Restrict T to bf16 or const bf16. A row stores its pair address and parity by value. It outlives a temporary matrix view while the owner remains alive.
- The packed types have no DMA template parameter or static DMA flag. No proposed consumer requires one. An arbitrary logical row is not a contiguous DMA input. The backing arena can still be DMA-safe memory. Do not inherit views<>, whose leaf rows must be contiguous.
- Supply dim, element, const_element, shape0(), and valid() as required by expression consumers. Leave the rank-1 expression concept unchanged. The named V expression consumer is the ordinary host-tensor construction check in section 8. Production V paths continue to use bulk operations. Native K remains compatible with dotter, the existing query/key dot-product helper. [S2][S3][S4]

| Operation | Contract |
| matrix[token][dimension] , matrix.at(token, dimension) | Assert bounds using repository assertions. Writable access changes only that element. A const matrix returns a read-only row. A const row returns a read-only element, even when its element type is bf16 . |
| row.chunk(i) | Return fp32 values in logical order. In bf16-element units, pair_base = plane + (token / 2) * 2 * D . Read chunk i at pair_base + 2 * chunk_size * i and extract the even or odd half. |
| bf16s bf16_chunk(size_t i) const noexcept | Use this non-template, non-overloaded signature to extract stored bits directly. A missing override uses the expression base's fp32 conversion fallback. A wrong signature can fail compilation; omitting noexcept does not silently select that fallback. Verify the member-pointer type. Do not claim the fallback corrupts stored bf16 bits. [S15] |
| View copy and conversion | Copying a view rebinds access. Allow writable-to-read-only conversion only. Owners, views, and rows expose no public raw-pointer constructor, data member, or pointer conversion. Rows are constructed only by the matrix view. |
| Internal storage access | Use detail::v_vnni_access , a friend declared with the V types, only inside typed tensor operations and V-specific kernels. The child uses a separate detail::k_vnni_access in its own header. Cache callers and tests do not use these helpers. |

A 16-lane pair chunk contains 32 bf16 values in 64 bytes. Reuse the existing even_part left shift and odd_part high-half mask for fp32 reads. Narrow the selected halves for bf16 reads. A stride-2 ordinary view has the right addresses but uses scalar extraction. [S5]

### One cache row-write rule

// Parameter families, not new wrapper types. append_v_row(v_vnni_view<bf16, R, D> dst, size_t token, const_view<Source, true, Dma, seq<D>, sseq<1>> src); load_row(v_vnni_view<const bf16, R, D> src, size_t token, view<Destination, true, Dma, seq<D>, sseq<1>> dst); copy_token(v_vnni_view<bf16, R, D> dst, size_t dst_token, v_vnni_view<const bf16, R, D> src, size_t src_token);

- Source is bf16, fp16, or float. Destination is bf16 or float. Dma preserves the existing contiguous view's DMA flag. Explicitly construct read-only source views where template deduction would otherwise see writable views. The shown alignment flag is true: preserve the existing aligned load/store contract and use 64-byte-aligned rows at every migrated call site. The flag describes a precondition; wrapping a pointer does not establish alignment. Add alignas(64) to the V fixture in t/heterogeneous_scheduler_compile.cpp. [S16]
- append_v_row moves today's packed set_v bodies into h/tron/tensor/v_vnni.hpp. An even destination writes its row and zeros its odd partner in one pass, without reading the destination. An odd destination merges into the initialized pair and preserves its even partner.
- load_row moves today's get_v loops. Wrap existing caller-owned scratch in the ordinary contiguous destination view.
- copy_token moves the four source/destination parity branches of append_v. Preserve overlap restrictions and fresh destination ranges. Even destinations zero their partner. Odd destinations preserve it.
- Do not add copy_plane for V. The existing append path copies token rows, including when a requested range spans a whole page. Range splitting and completion copying remain in cache code. Defaulted same-type owner copying is sufficient if an ordinary owner copy is needed.
- Preserve book::fill_random and its fill_storage_slot helper. This existing test-support operation fills an entire K/V block without interpreting coordinates. It is an explicit exception to the raw-access rule and must not establish readiness. Retain its comment about bypassing partner zeroing. The parent adds no new claim about the existing whole-block cast's C++ aliasing behavior. [S16]

### Build and include boundaries

- Keep packed V class definitions and typed kernel declarations available at both chunk widths. The unconditional fake AMX definitions require complete by-value parameter types. This does not require 8-lane implementations of packed-V SIMD operations.
- Guard packed operation bodies and packed-only tests with TRON_CHUNK_SIZE == 16. Retain the existing 8-lane row-major cache. Use the limited 8-lane baseline comparison in section 8; its existing full-suite failures are not parent work.
- Type constraints are positive even rows and positive columns divisible by chunk_size. Keep stricter operation constraints, including the packed append width. The AMX kernels retain their fixed 64-token by 128-dimension shape.
- amx_attn_iface.hpp includes kv_cache_fwd.hpp and remains free of intrinsics. v_vnni.hpp and later k_vnni.hpp supply definitions. Include full definitions in real/fake function definitions and callers that need them. Do not forward-declare seq or sseq as classes; they are aliases. [S15]

### Explicitly deferred

No new packed slice or iterator API. No generic row.set, set_pair, matrix.set, or owner expression constructor/assignment. No runtime shapes, general transpose, or V plane-copy helper. Leave h/tron/tensor/slice.hpp unchanged.

The existing generic expression-slice fallback can accept an lvalue packed view. It captures that view by reference, so the view and owner must outlive the slice. Do not pass a temporary packed view or use the owner overload: that overload creates a temporary view internally. This proposal adds no lifetime guarantee for that existing fallback. Ordinary tensors may still copy from a packed matrix expression. [S15]

## 6. Behavior the implementation must preserve

### V padding and write ordering

A packed-V weighted sum rounds an odd live-token count up to a complete pair. The unused odd row must be zero: a NaN multiplied by a zero weight still contaminates the sum. The row-major path reads exactly the live-token count. [S5]

Reused pairOld even rowOdd row: NaN poison

→

Append even tokenNew even valuesOdd row: all zero

→

Append odd tokenEven values preservedNew odd values

The even append must clear the partner every time the pair is reused. This is an operation sequence, not a timing diagram.

| Write | Destination read? | Partner result |
| Even cache append | No | Odd row becomes zero |
| Odd cache append | Yes, pair must be initialized | Even row is preserved |
| Direct element update | No read of other elements required | Other elements unchanged; this does not establish cache readiness |

- Production packed-V row writes use page::set_v or page::append_v. Both call the typed append/copy operations. Direct element mutation is useful for fixtures; it must not replace cache append.
