Shared save: let idle helpers
write the K cache.

Short version

One thread used to save all of a pass’s key vectors before attention could use them. Shared save divides that work among the main thread and its existing helpers. Main waits for every helper before announcing that the keys are ready. [1]

Source checked against PR #4424, commit 30c4ac82cb. Timing examples below distinguish mock from measured. No new hardware run was performed for this page.

Helpers run per-token kernels. Attention workers compute attention. Shared save uses the helpers.

A window is one shared save. A claim reserves one unit. A latch is a counter that opens a dependency gate at zero.
01

Two changes solve different parts of the save

The new K layout groups values by dimension pair across 16 tokens. It is called VNNI (Vector Neural Network Instructions) layout. AMX (Intel Advanced Matrix Extensions) can then use the stored keys directly as the right-hand matrix in attention. [2]

How one unit writes

Block store: combine the writes

Gather up to 16 token rows. Transpose them in vector registers. Store one dimension pair for those tokens in each 64-byte cache line.

A full block writes 64 complete lines per key/value head (one group of K and V vectors). A partial block writes only its token positions. One token uses scatter stores: small writes to separate addresses. [2]

Who writes the units

Shared save: use the available helpers

Main prepares the units. Main and its helpers repeatedly claim the next unit from one atomic counter. A thread takes another unit when it finishes its current one.

There is no fixed assignment of blocks to threads. The existing attention workers continue their separate work. [1]

03

Follow one unit into the cache

Mock values · real geometry

The same values, in a different order

For one head, each token has 128 key values. Each value occupies 2 bytes in bf16 (a 16-bit floating-point format). One full unit contains 16 token rows: 4 KiB (4096 bytes) of K data.

Above: one destination cache line, wrapped for readability. Each cell is one token’s 4-byte pair. Mock input: K[token, dimension] = token + dimension. These small integer values are exactly representable in bf16.

16 tokens × 4 bytes = one 64-byte line.
64 dimension pairs × 64 bytes = 4 KiB.

The transpose repeats in 4 steps of 32 dimensions. With 8 heads, one unit writes 32 KiB. The layout uses the same number of bytes as the original token rows. [2]

Source rule

A unit need not be a full block

Main cuts the item list whenever the destination page, 16-token block, or “write K/V” flag changes. Items from one block can appear in separate units. [1]

This 24-item mock pass illustrates the partition. unit_start = [0, 8, 9, 17, 23, 24]. A range includes its first item and excludes its end.

Different units can write different positions in the same cache line.

Masked stores preserve the other token positions. Disjoint positions avoid overlapping writes; they do not guarantee an absence of cache contention. A unit with no K/V work still gets claimed but writes nothing. [1]

05

Why “the queue is empty” is not enough

The shared window, in order

  1. Main publishes a complete unit table.

    Main resets the claim and finished counters. It increments opened with release ordering. A helper’s matching acquire read makes the published inputs visible. [1]

  2. Each claim gets one unique index.

    fetch_add(1) atomically returns the old counter value and increments it. Indices below n_units name work. Higher indices end that thread’s claim loop. [1]

  3. Each helper signals after its final store.

    Its release increment of finished records departure. Main has completed its own units and waits for n_workers − 1 helpers with acquire reads. [1]

  4. Main publishes K completion after the join.

    Main preserves token order for completion marks and hardware dispatch credits. It then counts down the downstream K/V latch. Save V supplies the other signal in this example. [1] [3]

Release/acquire are memory-order rules: they make earlier writes visible to the thread observing completion. The claim counter is on a separate cache line from the counters that waiting threads poll. [1]

When does sharing run?

  • The build enables TRON_K_VNNI, and the current operation’s K heads have 128 dimensions.
  • The pass contains more than 16 items. The gate counts all items, including items without K/V work.
  • The worker count, including main, is from 2 through 128. [1]

If any of these three checks fails, main stores alone. Block stores can still apply when sharing is off. Handwritten plugins default to one worker. An 8-item decode pass does not share. [1]

Eligible callers must supply matching helper calls. Generated model code does this at each K/V-writing attention operation. A missing helper call causes main to wait; it does not select the unshared path. [1] [3]

Two details the animation exposes

  • A late helper must still enter and leave its window, even when it gets no useful unit. Try the late-helper scenario.
  • A helper matches the first, second, and subsequent shared save calls using its own window count. Main cannot reuse the state until every helper has left. [1]

Main’s join includes a watchdog. It checks the clock every 1,048,576 spins and aborts 120 seconds after its first clock read if helpers have not finished. This is a failure check, not a normal window duration. [1]
