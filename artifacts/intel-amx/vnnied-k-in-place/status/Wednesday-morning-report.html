2. The question

PR #4424 (VNNI K: store the K cache of 128-dimension heads in the AMX VNNI layout) lists this open item:

128-dimension heads with kv_mul other than 4 (measure before merging). For qwen-3-30b-a3b (kv_mul 8) the VNNI layout is on. The AMX kernel is not eligible for that shape. So every page goes through the AVX-512 reader of the layout instead of the row-major dotter. The decode store also scatters into cold lines (64-byte cache lines not yet present in the CPU cache). One run showed -5.4% decode TPS (a loss: 34.3 vs 36.3 TPS/user) and -7% TTFT (a gain of 369 ms; lower TTFT is better) against base. If more repetitions confirm the decode loss, the layout gate k_vnni::layout_on<head_size> should also require the AMX shape (kv_mul 4), or the reader needs work for larger groups (more query heads per KV head).

Two remedies are named. Remedy (a) gates the layout on kv_mul 4. A kv_mul 8 model then keeps row-major K and the dotter. Remedy (b) makes the reader faster for larger groups.

The measurement here decides three things:

  • whether the loss is real (repetitions with a paired test).
  • whether the PR's code with the layout off already equals main for this model. This is the binary headoff, and it is what remedy (a) would run.
  • whether the loss comes from the reader (a per-page cost that grows with the prompt length) or from the decode store (a per-token cost that does not).

Decision rule, written before the runs (exec/vnnik6-20260916/PLAN.md section 6): the loss is confirmed when the paired t of vnni minus base at tp2 prompt 1024 is below -2 with 6 repetitions. headoff equals base when |t| is below 2.

5. Attribution: reader or store?

5.1 The prompt-length trend

The decode step of one user takes 1000 / TPS milliseconds. The figure shows that time for vnni minus base. The reader scores every KV page of the context (the prompt plus the tokens generated so far) on every step. So its cost grows with the prompt length. The decode store (Save K in a decode step) writes one K row per token per layer whatever the context length. So its cost is flat over the prompt length.

5.2 The traces

One traced run per binary and tp (prompt 1024, 32 tokens). A section is one attention worker's work item over a set of KV pages, recorded as one trace span. Per pass the figures and the table give: the pass time, the attention workers' section time per worker, the Save K time on the main thread, and the kernel time per main helper. Each value is the mean over the traced passes of that kind (prefill or decode).

Columns of the trace tables (this one and those of sections 5.3 and 5.4):

  • Save K share % = the Save K time of the pass as a percentage of the pass time.
  • attention ready = the workers' sections over the pages written in earlier passes, summed and divided by the attention-worker count.
  • attention pending = the workers' sections over the pages written in this pass, summed and divided by the worker count. A pending section starts after Save K and Save V of the layer.
  • join = the step that adds the workers' partial results of one KV head into one result, summed and divided by the worker count.

Five analysis agents (Claude Code subagents: automated language-model sessions launched by one workflow script, each given one prompt and one topic) read the code. For each topic, two further agents (the checkers, ten in total) opened every cited line and tried to refute every claim. Only claims that both checkers of a topic confirmed are stated as facts. The record of that analysis is the workflow journal wf_0818cf73-833 (the log of the 15 agents' prompts and answers) in the session's workflows folder. Estimates are marked "est.". 6.1 Where the gate lives, and why kv_mul cannot be read there today

  • The gate is the variable template k_vnni::layout_on<head_size>. It is true for head size 128 when TRON_K_VNNI is defined and false otherwise [h/tron/kernels/k_vnni.hpp:91-97]. TRON_K_VNNI becomes a public compile definition of the tron target [src/tron/CMakeLists.txt:213]. It requires TRON_AMX_DISPATCH [src/tron/CMakeLists.txt:210-211].
  • The gate is read at 20 places in four headers. 13 are in kv_cache.hpp (eight page::k overloads, k_vnni_plane, set_k_row, set_k_block, get_k_row, copy_storage_slot, at lines 1619-1740 and 2099). 3 are in self_attention.hpp (1365, 1436, 1574). 3 are in model.hpp (2807, 2865, 2967). 1 is in full.hpp (2648, the FPGA staging path: "staging" is the copy of a token group's K and V rows into the buffer that is sent to the FPGA attention hardware). Four more uses are in tests (t_llama_unit.cpp:720, 2789; t_k_vnni_layout.cpp:389, 391).
  • The 13 kv_cache.hpp sites see only a kv_geometry (KV head count and head size) or the page's raw head_size parameter. The storage types (uniform_kv_cache, kv_layout, book, page, kv_block) receive only n_kv_heads and head_size. The query-head count appears nowhere in book or page [kv_cache.hpp:112-117 (struct kv_geometry), 805-812, 820-826, 1447-1456, 1515-1520]. So kv_mul cannot be computed at these sites without a change to the cache type.
  • The 7 sites in self_attention.hpp, model.hpp and full.hpp hold an attention_geometry (query heads plus kv_geometry). They can compute geometry.kv_mul() today [kv_cache.hpp:194-215]. A gate evaluated only there would break the invariant the headers state: every code path that reads or writes a slot sees one layout [k_vnni.hpp:86-90; kv_cache.hpp:160-166, 176, 658-660]. The physical layout is decided inside the page's set_k_row, get_k_row, set_k_block, k_vnni_plane and copy_storage_slot.
  • The model plugins are tron's per-model C++ code. They are either generated by ingest (the pipeline that turns a PyTorch model into a plugin) or written by hand. A plugin builds the cache type from (n_kv_heads, head_size) [generated: ingest/src/TronCpp.hs:564-579 (uniform cache); handwritten: h/tron/plugins/llama.hpp:197-203 and mock.hpp:113-118]. It builds the kernel spec from (n_query_heads, kv_geometry) [generated: ingest/src/TronCpp.hs:348-363 (kernel spec); handwritten: h/tron/plugins/llama.hpp:197-203 and mock.hpp:113-118]. The generator (the Haskell part of ingest that writes the plugin header) chooses between a uniform cache (one kv_geometry for every slot) and a heterogeneous cache (an explicit spec per slot) on (kvHeads, headSize) only [ingest/src/LoopyTron.hs:127, 169-173]. No check compares kv_mul between two kernels, or between a kernel and a slot. The existing checks compare kv_geometry only [kv_cache.hpp:366-401]. So one uniform cache may in principle serve kernels with different kv_mul values. Whether any real ingested model does so is not established. The generated plugin headers are produced at build time and are not part of the repository.
  • No runtime switch exists. Every gate use is a C++ requires clause or an if constexpr, both resolved at compile time. The only environment variable in this code, TRON_AMX_DISABLE, controls AMX availability and not the layout.

6.4 The decode store for this model

  • A decode step of 8 users is one minibatch of 8 items. The K store is shared with the main helpers only when the minibatch holds more than 16 items. So a decode step takes the per-token scatter path (one scatter instruction writes 16 4-byte pieces to 16 addresses) on the thread that calls save_k, the generated plugin's main thread. The helpers' save_k_helper returns at once [model.hpp:2806-2814, 3009, 3040, 2970; TronCpp.hs:2277, 2402-2408].
  • One (token, KV head) row in the VNNI layout is 4 scatters of 16 dwords. Each dword lands in a different 64-byte cache line. So one row touches 64 lines with 4 bytes each [k_vnni.hpp:126-148; kv_cache.hpp:1704-1706]. Row-major, the same row is one 256-byte write into 4 full lines through the page's row view [model.hpp:2865-2875 in the PR head with the layout off; the same form at c7844ca2ce model.hpp:2757].
  • Per decode step, qwen-3-30b-a3b stores 1536 K rows (48 layers x 4 KV heads x 8 tokens): 98,304 touched lines in the VNNI layout against 6,144 row-major. qwen3-4b stores 2304 rows (36 x 8 x 8): 147,456 against 9,216.
  • The traces of section 5.2 measured the store for this model at tp2, prompt 1024: VNNI 0.914 ms per step (19.0 us per layer, 595 ns per row, 3.23% of the 28.31 ms step), row-major 0.154 ms per step (3.2 us per layer, 100 ns per row, 0.56% of the 27.70 ms step), a difference of 0.760 ms per step (2.7 percentage points). That measurement replaces the estimate that follows. Before the traces, the code analysis scaled the qwen3-4b decode trace of 2026-09-14 (VNNI 444-540 ns per row, row-major 72-91 ns per row) to this model's 1536 rows per step. That scaling gave est. 0.68-0.83 ms per step for VNNI (14.2-17.3 us per layer, 2.5-3.0% of a 27.6 ms step). The 27.6 ms step is 1000 / TPS (the formula of section 5.1) applied to the 2026-09-15 base run at tp2 prompt 1024, not a measurement of this campaign. Row-major came to est. 0.11-0.14 ms per step. The difference is est. 0.57-0.69 ms per step, 2.1-2.5 percentage points of the step time. The estimate reuses another model's per-row cost.
  • The store sits on the serial path of a layer (the chain of steps that the layer's later work must wait for). The main thread waits for every token's K channel (the readiness tracker of the buffer that holds that token's K row). It then runs save_k and save_v. Each of the two counts down one latch (a countdown counter). The waiting threads are released when the latch reaches zero. The attention workers' pending sections (the attention work over the pages written in this pass) wait on that latch. A minibatch is on its own list of dependents: a token attends to itself. Generated plugins run exactly one minibatch (--max-minibatches 1). So no other minibatch's attention overlaps the store [model.hpp:2782-2784, 3056-3058, 1873-1888; self_attention.hpp:782-784; common.hpp:951-960; TronCpp.hs:1172-1174, 1275-1277].

6.5 What the analysis says about the one-run result

The reader's instruction counts do not predict a kv_mul-8-specific loss. Two costs that this model pays without any AMX gain do not depend on kv_mul:

  • the per-token scatter store. The tp2 decode traces of section 5.2 measured its share of the step time: 3.23% for vnni against 0.56% for base, 2.7 percentage points (0.914 against 0.154 ms per step). The code analysis had estimated 2.1-2.5 percentage points (section 6.4).
  • the whole-block cost of the page that is filling. The reader scores 16-token blocks whole. A partly filled block costs as much as a full one.

The 2026-09-15 run compared two different code heads (544ca05c7a against dc950be5f2). The background load also differed: the 1-minute load average (runnable processes, averaged over one minute) was 12.5 at the start of the 544ca05c7a run and 16.2 at the start of the dc950be5f2 run. So noise and drift were also candidates.

The campaign of this report removes those two differences: interleaved repetitions against the exact merge base, with the traces separating the store from the attention time.

7. Recommendation

The repetitions do not resolve a decode difference at tp2 prompt 1024 (paired t +1.3, section 4.4). The one-run -5.4% decode TPS per user of 2026-09-15 (34.3 against 36.3 TPS, section 2) did not repeat under interleaved repetitions against the exact merge base.

In the tp2 traces the decode step of vnni is +0.61 ms against base (28.31 against 27.70 ms). There is one traced run per binary. So this difference is within the run-to-run spread. Inside the step, two effects have opposite signs. The Save K span on the main thread costs +0.760 ms more per step (0.914 against 0.154 ms, 19.0 against 3.2 us per layer). That is the per-token scatter store. The attention workers' time per worker moves by -0.791 ms per step (6.050 against 6.841 ms). That is the reader against the dotter. In prefill (8 passes of 128 tokens x 8 users), the Save K span per layer falls from 157.7 to 51.8 us (the shared block save). The attention workers' time per worker per pass falls from 293.5 to 246.0 ms. The pass itself goes from 652.1 to 601.9 ms (-50.1 ms per pass, -401 ms over the 8 prefill passes). That is the TTFT gain.

Recommendation: no gate change for kv_mul 8. Close the open item with these numbers. Write these five points into the PR:

  • For a model without an AMX gain, the layout trades the per-token scatter store (the Save K numbers above) against a faster software reader.
  • At prompt 1024 the two cancel in decode.
  • At prompt 8192 the reader's gain dominates: the decode step falls by a fifth (section 5.3).
  • The block save and the reader together lower TTFT at every prompt length, by 7% to 16%.
  • The prompt-2048 cell is the one exception. It shows a resolved decode loss of 4.1%. Section 5.4 gives its traces and the open hypothesis.

7.1 Why the 2026-09-15 run showed a loss

The one-run cell of 2026-09-15 compared runtron.p0perf13 (commit 544ca05c7a, the PR's base at that time) with runtron.vnnik4 (commit dc950be5f2, the PR head of that time). It measured 36.28 TPS per user for the base and 34.31 TPS per user for the VNNI binary [exec/results/vnnik4-models-20260915/results.txt, cell=qwen30b]. Today's main binary (c7844ca2ce) measures 34.26 TPS per user with a sample standard deviation of 0.66 TPS over 6 repetitions at the same cell. Today's VNNI binary measures 34.79 TPS per user with a sample standard deviation of 0.86 TPS over the same 6 repetitions. So the VNNI binary runs at the same speed as on 2026-09-15. The base moved from 36.28 to 34.26 TPS per user (-2.0 TPS, -5.6%).

Two explanations were open before the extra cell of section 7.3 ran:

  • The code between 544ca05c7a and c7844ca2ce changed the decode speed of this model. That range holds 149 commits from 26 merged pull requests. Two of them change the KV cache. PR #3054 introduces per-layer KV arenas (an arena = one memory region reserved once, from which the cache takes its KV pages). PR #3067 reclaims out-of-window sliding KV under memory pressure (sliding-window attention lets a query see only the most recent tokens, and this change frees the KV pages of tokens that have left that window when memory runs short).
  • The 2026-09-15 base run was a favourable single sample.

The extra cell measured both binaries interleaved, 6 repetitions each, at the same cell (section 7.3). The old base runs at 34.96 TPS per user (standard deviation 1.35) and main at 33.92 (standard deviation 0.69). Main is slower by 1.04 TPS (paired t -1.6, not resolved with 6 repetitions). So the 36.28 TPS of the 2026-09-15 run sits about one standard deviation above the old base's own mean: it was a high single sample. A small slowdown of main (about 1 TPS, 3%) may add to it. The measurement that would resolve the second part: the same two binaries with 12 or more repetitions.

The PR's open item was based on a comparison of two different code heads, one run each, under different background load (1-minute load average 12.5 against 16.2 at run start). The interleaved repetitions of this campaign against the exact merge base remove all three differences: the code difference (every binary is compared with its exact merge base), the load difference (the binaries run one after another inside each repetition), and the single run (every cell is repeated, section 3.2).

9. Notes and traps

  • Where the vnni binary came from. runtron.vnnik5 was built from commit d5b59b1101 (2026-09-16 00:09 UTC). The worktree was then moved to 65a1c41d72, a change to one test file. Only libversion.so was relinked. So the runtron file kept its sha256 (7f508484...). Its "Version:" log line, however, says 65a1c41d. The PR head ff680c8020 adds one JSON row of cost data to 65a1c41d72 and no C++. The base and headoff binaries were built by this campaign. Their build records are in section 3.1.
  • No AMX-on / AMX-off pair. The AMX kernel serves head size 128 with kv_mul 4 (amx_attn_iface.hpp shape_ok). qwen-3-30b-a3b has kv_mul 8. So the AMX path for dense pages (a full 64-token page that the query sees in full) is never compiled in for this model. TRON_AMX_DISABLE=1, the runtime switch that turns AMX off, changes nothing. All three binaries run the software attention path for this model.
  • Why headoff is the gate's stand-in. The layout gate is a compile-time constant (k_vnni::layout_on, TRON_K_VNNI). A gate on kv_mul 4 would leave qwen-3-30b-a3b on row-major K with the PR's other code (save_k with a worker count, save_k_helper calls that return at once, the k_head_fn scratch parameter). A build of the PR head with TRON_K_VNNI off runs exactly that code for every model. So headoff measures the gate's outcome for this model without writing the gate.
  • Log level. The cells ran with TRON_LOG_LEVEL=debug and SPDLOG_LEVEL=debug. That is the convention of the qwen3-4b campaigns of PR #4424. It is also the default of the nightly. The 2026-09-15 one-run cell used TRON_LOG_LEVEL=info. The smokes and traces use info.
  • Machine sharing. The marker file /bill-has-instance-0,2 was present. So the first half of delphi-3bda belonged to the other user during the runs. Every run recorded his process count (rt-results.txt machine line). Our runs used CPU socket 1 and cards 90/93 (tp2) or 90/93/b9/bc (tp4).
  • Chart colors.
    • The colors come from the reference palette of the dataviz chart-design guide used for this report: its first color (blue) for headoff, its second (orange) for vnni, and a neutral gray for base, the control binary.
    • The guide states that its first three colors pass its color-vision checks (simulated red-green color blindness) for every pair of the three. The guide's validator script runs under Node.js (a command-line JavaScript runtime). The container this report was written in (claude-box) does not have Node.js. So the validator was not run here.
    • Every bar and dot carries a direct value label, and every chart has a table. So no reading depends on color.
  • Traces. One traced run per binary and tp. Trace overhead on the earlier qwen3-4b runs was 0 to 3% of TTFT. The traced runs generate 32 tokens (not 256) and are not part of the TPS/TTFT cells.
  • Dry runs. summarize.py, compare_tokens.py and gen_report.py were exercised on synthetic data before the campaign. analyze.py reproduced the 2026-09-14 numbers on the earlier qwen3-4b trace (Save K 273.6 us per layer in prefill) before the KV-head count was changed to 4 for this model.
