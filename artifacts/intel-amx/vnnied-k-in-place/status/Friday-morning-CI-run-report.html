Friday morning CI run: the nightly perf phase by hand, base vs AMX + VNNI-K target

delphi-3bda, whole machine, 2026-09-18 after the nightly. Generated 2026-09-18 18:51 UTC by exec/ci-mimic-20260918/gen_report.py from the run records.

Short version

The base run, on the nightly's own package (2026.09.18-3faba6d0) and through the nightly's client path, gave TPS (decode tokens per second per user) within 5.3 % of the same-day nightly on all 12 configs, and no config fails the fidelity rule of section 2.

The target package (PR #4424, which stores the K cache in the layout the AMX instructions read, built with AMX turned on) changes TPS by a resolved amount (larger than the night-to-night noise, section 3) on 4 of 12 configs: qwen-3-4b tp4 @8u -11.0%, qwen-3-4b tp2 @8u -5.0%, llama-3.2-3b fast tp2 @32u -3.7% (not trusted, see the caveats), llama-3.3-70b good tp2 @4u +1.1%, while llama-3.1-8b, where the AMX kernel ran (30.1 billion AMX-busy cycles against 0 on base), changes only +0.8%.

Read the caveats first: the client host was CPU-saturated by other containers for most of the base run and the first five target configs, and with a single run per arm, differences smaller than a config's night-to-night band are not resolved.

Words used here

nightly, CI, systems_test, CI runner
CI = continuous integration, the automated nightly test job. The nightly is the systems_test job "System CI (Rinzler 72-core Intel system OCI version)" that runs on delphi-3bda (the 72-core Intel Granite Rapids test machine) every night at 03:30 UTC. systems_test is the repository that holds the system tests. The CI runner is the machine that runs the nightly's client code. This page repeats the nightly's perf phase by hand.
arm, config
An arm is one of the two packages under test, base or target, run once through all configs. A config is one row of the nightly's perf list: a model, its tensor-parallel width and a user count, for example llama-3.1-8b good tp2 @8u.
harness
The nightly's client code (systems_test scripts/perf.py and testlib/tps.py). It provisions each model, starts the users' requests, and computes TPS and TTFT. The same code produced every number here.
platformd, rinzler@N, engine, Caddy
platformd is the daemon on the machine that writes one env file per engine and starts the rinzler@N systemd units. rinzler is the production tron server, and one running rinzler is one engine. Caddy is the port-80 proxy in front of the engines. It sends each new user to the engine with the fewest connections.
deb, preset, PR
The deb is the tron apt package the nightly installs. The preset is the CMake build recipe ("deb") that builds it. PR = pull request. PR #4424 is the VNNI-K change (branch jhan-amx-vnniK).
base
The package the nightly installed on 2026-09-18 (2026.09.18-3faba6d0). It contains no AMX code. The deb preset never turned the AMX option on.
target
Our package 2026.09.18-29a8a547-jhan-ci-mimic-target. It is PR #4424 merged into the same main commit as the nightly's package, built with the deb preset carrying TRON_AMX_DISPATCH=ON and TRON_K_VNNI=ON.
AMX, VNNI-K, K cache, KV head, kv_mul, head size
AMX = Intel Advanced Matrix Extensions, the tile matrix instructions of Granite Rapids CPUs. The AMX kernel accelerates software attention for models with a head size of 128 elements and 4 query heads per KV head (kv_mul = 4). A KV head is one key/value head of attention that several query heads share. The K cache is the stored keys of all earlier tokens. VNNI-K = storing the K cache in the pair-interleaved layout the AMX instructions read (two consecutive tokens side by side), the change of PR #4424.
FPGA attention, CPU attention, ingested, USE_HW_ATTN
Ingested models (models converted by tron's ingest compiler) run attention on the FPGA cards (Positron's accelerator cards) by default; here that is qwen-3-4b and gpt-oss. gemma-4-31b is ingested but has no FPGA attention (head size 256). It therefore runs attention on the CPU. Hand-written models (models coded by hand in tron) run attention on the CPU, where AMX and VNNI-K act. USE_HW_ATTN is the environment variable that would force one or the other. It was unset, as in the nightly.
tp2, tp4, @Nu, round
tp2 and tp4 = tensor-parallel width, the number of FPGA cards one engine uses (2 or 4). The machine's 8 cards therefore give 4 or 2 engines. @Nu = N concurrent users. A round is one pass in which every user sends one request. Every config runs 10 rounds with fixed prompts.
TPS, TTFT, slowest user, prefill
TPS = decode tokens per second per user, measured between generated token 896 and 1024 (2 and 333 for llama-3b), mean over users and rounds. TTFT = time to first token in ms, measured on the client. Slowest user = the minimum TPS sample of a config. Prefill = processing the prompt before the first token.
paired t, 95 % interval, z, sd, 13-night band, Slack reports
Paired t = the mean of the 10 per-round differences divided by its standard error. The prompts are fixed. Round r of one run therefore pairs with round r of the other. The 95 % interval is the confidence interval of that mean. sd = standard deviation. The Slack reports are the summary messages the nightly posts to a Slack channel. The 13 reports of 2026-09-05 to 09-17 give each config a mean and sd. z = (base minus the 13-night mean) / the 13-night sd. The band drawn is the 13-night mean +/- 2 sd.
thresholds, granite_rapids_72_rinzler
The static goals are the mean-TPS and slowest-user limits the Slack report applies (from systems_test scripts/system_ci.py for the machine profile named granite_rapids_72_rinzler). The ratchet thresholds are a second set in YAML files that tightens over time and is not shown in Slack.
EXE.AMX_BUSY probe
A 20 s read of the CPU counter EXE.AMX_BUSY, which counts cycles in which the AMX unit was busy, summed over all engine processes while 4 short requests run. It runs before the benchmark of the probed config. It therefore does not touch the measured rounds.
PSI, DUT, sha256, runtron, MoE, talos
PSI = Pressure Stall Information. Its "some" value is the share of time at least one task waited for a CPU. DUT = device under test, delphi-3bda. sha256 = a hash that identifies a file's content. runtron = tron's command-line tool, used in earlier campaigns instead of the server. MoE = mixture of experts. talos = the CI's metrics recorder, replaced here by a local stub.

1. What ran

  • Machine and layout: the whole of delphi-3bda. The marker file that reserves half the machine for Bill was removed at 01:10 UTC (and again before each relaunch, after the failed attempts had re-created it) and re-created for good at 17:58 UTC after the run. Engines were created by platformd for every config exactly as in the nightly: 4 engines for tp2, 2 for tp4, users spread by Caddy.
  • Client: the harness's own test_performance loop, run by st_ci_perf.py from claude-agentsrv (a container on the same network as the CI runner) with the same Python dependency lock file (uv.lock) as the CI runner, through http://delphi-3bda.positron.internal/v1. Speculative decoding (draft-token prediction) was off (SYSTEM_CI_SPECULATION=0), as in the nightly. Each config ran 10 rounds with a 1024-token prompt and 1536 generated tokens (llama-3b: 800 shared prompt tokens + 200 own prompt tokens, 845 generated tokens).
  • Arms: base = nightly package 2026.09.18-3faba6d0; target = 2026.09.18-29a8a547-jhan-ci-mimic-target. The swap used the nightly's own sequence (apt-get remove, apt-get install), and the nightly's package was reinstalled at the end.
  • Reference: the 2026-09-18 nightly run 35303980268 (package 2026.09.18-3faba6d0) and the 13 Slack reports 2026-09-05 to 09-17.

Deviations from the real nightly (recorded by the driver)

  • perf phase only
  • ssh as jhan (key) instead of positron
  • talos recording stub
  • client host = claude-agentsrv
  • layout snapshots after provisioning, AMX probe before selected benchmarks
  • The nightly runs 25 min of functional tests first, then perf, then MMLU Pro (an accuracy benchmark) and a 3 h soak (a long steady-load test). Here the perf phase followed the nightly's soak (base) or the package swap (target).
  • One run per arm, one nightly for the same-day comparison. Effects below a config's 13-night band are therefore not resolved (section 3).

Caveats and incidents (read before the numbers)

  • The client host (claude-agentsrv, the container that ran the harness) was CPU-saturated by other containers for most of the base arm and the first 5 target configs. The CI runner (the machine that runs the nightly's client code) has no load record. The comparison assumes it is idle. Evidence, from the driver's snapshots unless noted:
    • Base arm (13:43 to 15:27 UTC): the 1-minute load average (runnable tasks, on a 32-CPU host) at the 14 snapshots ranged from 4.5 to 147. A spot check at 14:52 UTC showed 0 % idle CPU and a CPU pressure (PSI "some", the share of time at least one task waited for a CPU) of 93 %. The driver and its 8 workers used about 20 % of the host's CPU in that spot check (est.). The 1-minute load fell below 32 from about 15:00 UTC (configs 8 to 11), while the 15-minute load stayed at 62 to 98. The base arm has no PSI record of its own.
    • Target arm: PSI 96 % to 99 % and load 97 to 258 at the start of configs 1 to 5 (llama-3b to llama-70b tp4, snapshots 16:13 to 17:06 UTC). The load fell during config 5. Configs 6, 7, 10, 11 and 12 (mixtral, qwen-2.5-32b, gemma-2, gpt-oss, gemma-4) ran at PSI 0 % to 4 % and load 2 to 25. The two qwen-3-4b configs (8 and 9) ran at PSI 27 % to 48 % and load 10 to 20.
    Effects:
    • Rounds took up to 11 times longer on the client. Method: config wall time divided by 10 rounds. llama-3b: 42 s per round on base (5.6 times the nightly's 7.4 s) and 84 s on target (11.3 times).
    • Each arm's perf phase took 103.8 min against the nightly's 79 min. The extra time sits inside the rounds, not in our provisioning path. For the 7 target configs from mixtral onward, our snapshots, probes and provisioning added 0.7 min in total against the nightly (7.3 against 6.7 min). The rounds themselves took 34.3 min against 28.5 min, about 20 % longer at equal TPS, even at PSI 0 % to 4 %.
    • Short TTFTs are inflated: llama-3b 119 ms (base) and 62 ms (target) against 56 ms in the nightly.
    • A stall can slow a whole round. Base llama-3b round 7 averaged 166 TPS (the other 9 rounds 194 to 200). Without that round the base mean is 197.67 TPS, equal to the nightly's 197.66. Base llama-70b tp4 round 4 averaged 27.3 TPS (others 29.9 to 30.3). So the base-vs-nightly gaps of -1.6 % (llama-3b) and -0.7 % (llama-70b tp4) are client artifacts. The other TPS means are within 2 sd of the 13 nights, except llama-70b tp2 @4u (z +5.1, where the same-day nightly was high by the same amount, see section 2) and qwen-2.5-32b (z +2.0, at the band edge).
    • Stalls lower the slowest-user values: llama-3b 118 (base) and 163 (target) against 173 in the nightly, and llama-70b tp4 23.0 (base) against 29.6. llama-8b's base slowest user (109) is below the 13-night range (116 to 138). A stall is likely there but not shown in the logs.
    • TTFT differences between target and base for the configs from mixtral onward compare unlike client conditions (base under load, target lightly loaded). Example: base qwen-3-4b tp2 TTFT was 556 ms, 47 ms above the 13-night mean (509.5 +/- 7.2 ms), while the target's 504 ms is a normal night's value. The TTFT marks on mixtral (-1.8 %) and qwen-3-4b tp2 (-9.4 %) therefore cannot be attributed to the package with this data. A package effect of that size is possible: the 2026-09-16 runtron cells with FPGA attention measured a TTFT gain of 34 to 58 ms on qwen-3-4b for PR #4424 alone.
  • The two arms did not run one right after the other. Base ran 13:43 to 15:27 UTC and target 16:13 to 17:57 UTC. Three launch failures happened, all in our scripts, none in the harness or on the DUT (device under test, delphi-3bda):
    • 13:19 UTC: a bash flag-expansion bug in the campaign script. It aborted before any package step.
    • 13:35 UTC: a conflict between two event loops of asyncio (Python's asynchronous I/O library), one in our driver and one in the harness. The target was installed at 13:35 and the nightly's package restored at 13:36:50.
    • 15:29 UTC: a missing import after a mid-run edit of the driver. The target was installed at 15:27 and the nightly's package restored at 15:29:38. This failure caused the 47 min gap between the arms. The first two delayed the campaign's start.
  • Target config 1 (llama-3b) ran on engines started at 15:28 UTC by the failed attempt. Those four engines showed a deleted executable. The package file was replaced twice after they started. The sha256 (a hash that identifies a file's content) of each running executable equals the target package's rinzler (3ee9c8f0...). So they served the target binary. Every later target config except llama-70b tp2 @4u (which reuses the @8u engines by design) re-provisioned its engines. Every base config ran on the nightly's binary (sha 27e6883c...).
  • gpt-oss-120b base vs nightly is +5.3 %, the largest same-day difference. This config's 13 nightlies vary by 3.0 TPS (sd, standard deviation). The 09-18 nightly (101.16 TPS) is at the low end of that band. The base value 106.51 is 0.6 sd above the 13-night mean.
  • Engine layout matched the nightly for every config: 4 engines for tp2 and 2 for tp4 were running after every provisioning. The driver checked this. The harness itself only warns. The rinzler service file was the deb's unmodified copy in both arms (the hand edit that added --num-expert-replicas 750 on 09-17 was gone). The Intel Speed Select policy (the CPU core-priority setting) was verified before both arms: clos0 224 cores and clos3 64 cores, where clos = class of service, a core-priority group. The nightly logs do not record it.
  • Reference limits. gemma-4-31b has only 3 nightlies (09-15 to 09-17). Its "13-night" band is a 3-night band. The 09-18 nightly itself failed two Slack thresholds, llama-8b (mean 140.66 below 144, slowest 136.34 below 140) and llama-70b tp2 @8u (16.58 below 27), as on all 13 earlier nights. It passed qwen-2.5-32b for the first time (slowest user 35.03 against a goal of 35). The 13 earlier nights had 33.48 to 34.82.

Reading rule and reference limits

  • A row is marked * only if all three hold: |z| > 3 against the 13 nights, base at least 1 % from the 13-night mean, and base at least 1 % from the same-day nightly. The third condition was added after seeing the data, for the case below. The rule was therefore not fixed before the data.
  • llama-70b tp2 @4u has z +5.1 (base 27.98 TPS against a 13-night mean of 27.64 +/- 0.07 TPS) but is not marked. The same-day nightly was also high, at 27.93 TPS (z +4.3), and base differs from it by +0.2 %. Both runs of that day were high by the same amount. That is not a fidelity miss.
  • llama-3b (z -2.8) and llama-70b tp2 @8u (z -2.2) are outside 2 sd but inside 3 sd. The llama-3b gap is the client stall described in the caveats.
  • llama-70b tp2 @8u has a 13-night sd of 0.01 TPS (Slack prints 2 decimals), and llama-3b's reference TTFT is an integer (56 or 57 ms). Tiny z values there carry no information.
  • qwen-3-4b tp4 and gpt-oss tp4 vary 3 to 5 TPS night to night on their own, and gemma-4-31b has only 3 reference nights.

Reading the effects

  • qwen-3-4b tp2 −5.0 % and tp4 −11.0 % (both resolved). These two configs keep FPGA attention in the nightly setting. The AMX kernel therefore touches only the query positions the CPU still scores (positions 0 to 126 plus the most recent tokens not yet copied to HBM, the high-bandwidth memory on the FPGA card). The VNNI-K layout changes how the K cache is written and how the FPGA path reads it. The direction matches the 2026-09-16 runtron cells with FPGA attention. The size matches for tp4 (−11.0 % here, −9.7 % to −11.5 % there) but not for tp2 (−5.0 % here, −1.8 % to −2.2 % there). Under the nightly's static thresholds this turns qwen-3-4b tp4 from PASS to FAIL (133.4 TPS against a goal of 135).
  • llama-3.1-8b +0.8 % (not resolved: below the 1 % floor). AMX ran: the probe counted 30.1 billion AMX-busy cycles across the four engines, against 0 on base. The +17 % of 2026-09-16 came from 8 users on ONE engine with runtron. The nightly layout spreads the 8 users over 4 engines (2 per engine). Hypothesis, untested here: at 2 users per engine, attention is a small share of each decode step, and the kernel then has little to accelerate. The measurement that would test it is runtron at 2 users, AMX on against off. TTFT is 579 ms on target against 611 ms on base (−5.3 %). But base was already 53 ms below the same-day nightly (664 ms) on the same package. So the TTFT attribution is not isolated.
  • llama-3.2-3b −3.7 % (flagged by the rule, but not trustworthy). This 32-user config is the one the saturated client host affected most. Its rounds took 84 s on target against 42 s on base and 7 s in the nightly. The per-sample spread grew (sd 26.9 TPS on target, 25.1 on base, 22.4 in the nightly). The paired t is only −2.5 with a 95 % interval of ±3.4 %. Treat it as unresolved until a run from an idle client.
  • llama-3.3-70b tp2 @4u +1.1 % (resolved, small). A consistent difference with a narrow 95 % interval (t +10, ±0.3 %) on a CPU-attention model that gets only the VNNI-K layout (8 query heads per KV head, no AMX kernel). Its TTFT falls into two groups in the three nightlies with per-request data (09-16 to 09-18): per round, 0 to 4 of the 4 users see about 0.3 s and the rest about 5.3 s. Base had 6 fast requests of 40, the 09-18 nightly 5, target 12. The −16.9 % TTFT difference is that 12-against-6 count. Whether the count is a package effect is unresolved at one run per arm. The 13 nightly TTFT means (3418 to 4418 ms) imply about 7 to 15 fast requests of 40 per night (est.), a range that covers the target and sits one to two requests above base and the 09-18 nightly.
  • Everything else is below the 1 % floor or not resolved. A control config is one where no effect is possible.
    • llama-70b tp2 @8u +0.2 % (t +6.4, below the 1 % floor).
    • llama-70b tp4 +1.6 % (95 % interval ±2.2 %).
    • mixtral (AMX-eligible, MoE = mixture of experts) −0.3 %.
    • qwen-2.5-32b −0.1 %.
    • gemma-2 +0.2 %.
    • gemma-4 −0.3 % (t −2.1).
    • gpt-oss −0.3 % (interval ±3.5 %). The 09-16 runtron cells had gpt-oss at −5.0 % with n = 6 repetitions and FPGA attention. That did not repeat here.
    • gemma-2, gemma-4 and gpt-oss have head sizes of 256, 256 and 64 elements. Neither AMX nor VNNI-K applies to them. Their near-zero differences are the expected result for control configs.

Which configs can react, and why

  • llama-3.2-3b fast tp2 @32u: CPU attention; VNNI-K layout in target (kv_mul 3, no AMX kernel)
  • llama-3.1-8b good tp2 @8u: CPU attention; AMX kernel + VNNI-K in target
  • llama-3.3-70b good tp2 @8u: CPU attention; VNNI-K layout in target (kv_mul 8)
  • llama-3.3-70b good tp2 @4u: same engines as the @8u cell (no re-provisioning)
  • llama-3.3-70b good tp4 @4u: CPU attention; VNNI-K layout in target
  • mixtral-8x7b tp2 @8u: CPU attention; AMX kernel + VNNI-K in target
  • qwen-2.5-32b fast tp2 @8u: CPU attention; VNNI-K layout in target (kv_mul 5)
  • qwen-3-4b tp2 @8u: FPGA attention (nightly default); AMX only in the CPU share
  • qwen-3-4b tp4 @8u: FPGA attention; night-to-night noisy (sd 5 TPS)

  • gemma-4-31b tp2 @8u: head 256: neither applies; 3 nights of reference only
