0.5 Issue #4500: the VNNI per-token K access in decode

The problem. Under the VNNI layout, three CPU operations of FPGA-attention decode access one token's K row across 64 cache lines, not 4: the per-token K save, the K gather for the card, and the workers' tail scoring. The card is not the cause (identical bytes in both binaries). With CPU attention the workers overlap the save. With FPGA attention in the nightly layout the card launches after the save, and nothing overlaps it.

The largest part is the save: up from 4.6 to 20.3 us per layer (tp2, 8 users, runtron), or +0.57 ms per step in series over 36 layers (7 % of the 8.0 ms step). The CI loss (-5.0 % TPS at tp2, 09-18 run) reproduced with rinzler at -4.3 % TPS, and -13.4 % TPS at tp4.

Suggested fixes. The fix idea below was built on 2026-09-28 on the side branch jhan-amx-vnniK-i4500 (three commits on the PR #4424 head, top 617cb8333f). It is under test on delphi-3bda on 2026-09-29. It is not pushed, and PR #4424 is untouched.

  • Fix idea (measurement running): keep a 16-token block row-major until it is complete, then convert it to the VNNI layout. Section 3.1's prefill block save already converts that way.
  • The issue (no comment yet) lists four options: a row-major staging copy, a tuned gather, the layout off for FPGA-attention models, or accepting the loss.
  • Mitigation (not in the issue): the run-time switch TRON_HWATTN_EARLY_LAUNCH_MIN_B=1 launches the card before the K and V saves. It makes the branch +6.2 % TPS faster than the shipped nightly package (tp2, 2 users per engine), and that package itself +7.7 % faster.
  • The fix idea and the mitigation are different things. The fix idea removes the cost: the per-token save writes 4 cache lines instead of 64. It needs new code in the K save path of PR #4424. The mitigation hides the cost: the slow save runs while the card is busy instead of before it. The save stays slow. The switch needs no code change, only an environment variable at run time.
  • Two consequences. The mitigation helps only where the card can overlap the save: it was measured at tp2 with 2 users per engine, and it does nothing for the workers' tail read at tp4. It also speeds up the shipped package without PR #4424 (the +7.7 % above), so it is a separate finding about the launch default, not a fix for the layout. The fix idea would make the mitigation unnecessary for this issue. The mitigation would still be worth its own change.

Details.

  • At tp2, 8 users (runtron): the loss is +0.58 ms per step larger with the card launched after the save than before it (paired t 19.7).
  • At tp2 the AMX kernel is not the cause (kill switch +0.3 % TPS, n.r.), and the layout-off build equals main within 0.006 ms per step.

Short version. In prefill the VNNI K store (Save K) takes 859 us per layer against 274 us for the baseline's row-major store, and the layer's attention work waits for it, which makes this store the cause of the VNNI-K TTFT cost. In decode the store is also slow (28 us per layer against 5 us), but it overlaps the attention workers' work on the earlier pages and adds no time to a decode step. Two remedies, a block store (16 tokens transposed in registers, whole cache lines written) and helper striping (the idle helper threads share the store), are built as switchable paths in one binary, and their measurement is in section 4.

The findings in more detail:

  • The Perfetto trace (the trace recorder built into tron) puts Save K at 859 us per layer at tp2 (the model split over two FPGA cards) and 862 us at tp4 (four cards). It is one thread's serial work, so the tensor-parallel width does not change it.
  • The baseline's row-major store (one contiguous 256-byte row per token) takes 274 us at tp2 and 281 us at tp4.
  • The store's share of a prefill pass rises 3x: from 2.5% to 7.7% at tp2, and from 3.7% to 10.5% at tp4.
  • The pending attention sections (the work over the pages written in this pass) start only after Save K and Save V. So every microsecond of Save K moves the end of the layer (section 2.2).

At tp2 the measured increase was +71 ms, so the transpose-free attention kernel (it reads the VNNI plane directly) offsets about 98 ms (est.).
  • In decode the store takes 28 us per layer against 5 us for base, about 8% of a 12.7 ms step (1.0 ms per step).
  • The attention workers run their Ready sections (this step's query against the users' earlier pages) during Save K. Each worker's Pending section starts only after its own Ready work, about 110 us after Save K began. A shorter store would therefore not shorten the step (section 2.3).
  • Commit 9928cb2849 adds the block store and the helper striping, each with a runtime switch, so one binary provides the arms vnni0 (both off) / a / b / a+b. 3. The two remedies, built as switchable paths in one binary

Commit 9928cb2849 on jhan-amx-vnniK (7 files, +469 / -45 lines). Both remedies default on; each has a runtime switch (exactly "0" disables, like the AMX kill switch), so one binary gives the arms vnni0, a, b, ab and the arms interleave inside every repetition.

3.1 (a) Block store: transpose 16 tokens in registers, write whole lines

What it does. The pass's tokens arrive in position order, so runs of up to 16 consecutive tokens fall into one 16-token block of one page. For such a run save_k now loads the 16 rows (one 64-byte load per row per dim step), transposes the 16 x 16 matrix of 32-bit dim pairs in registers (64 shuffles), and writes each of the panel's 16 pair rows as one 64-byte store: 64 full-line stores per block and KV head instead of 64 scatters that write 4 bytes into each of 64 lines. A partial run uses a masked store of the present tokens' lanes; a token alone in its block (decode) keeps the per-token scatter [h/tron/kernels/k_vnni.hpp store_block, transpose_16x16_epi32; h/tron/models/kv_cache.hpp set_k_block; h/tron/models/model.hpp store_k_block]. Switch: TRON_K_VNNI_BLOCK=0.

3.2 (b) Striping: the idle main helpers share the store

What it does. In the generated plugin the main helpers are idle while main runs save_k (figure 2.2). The code generator now emits, at the same statement position of the helpers' schedule, a call to save_k_helper, and main's save_k receives the worker count. Main opens a window over the pass's token list, every thread claims 16-token blocks of it with an atomic counter and stores them, and main waits until every helper has left the window and every block is stored before it marks the tokens complete and releases the attention workers. Windows are counted on both sides, so a helper enters window N exactly when main opens window N; a pass with at most 16 tokens (decode) opens no window and nothing waits [ingest/src/TronCpp.hs runHelperStatement, submitAttentionOperation; h/tron/models/model.hpp Note [Striped K store], save_k_helper; h/tron/models/common.hpp batch::k_store_window]. Switch: TRON_K_VNNI_STRIPE=0. The handwritten plugins and the unit tests call save_k without a worker count and never stripe.

3.2.1 The window, step by step

Why it is safe for K and not for V. In the VNNI K plane a token owns 4 bytes of each line it touches and no other token writes those bytes, so threads storing different blocks never write the same bytes (a 16-token block owns whole lines). The V plane interleaves token pairs in one 32-bit lane, so two threads storing the two tokens of a pair would race; save_v stays serial [h/tron/kernels/k_vnni.hpp header comment; model.hpp save_v_impl comment].

Checks. The emitter test ingest/test/LoopyTronSpec.hs counts one save_k_helper call per KV-writing operation; the C++ unit tests (t_k_vnni_layout, t_amx_numerics, t_amx_dispatch_dtype, t_llama_unit) and the Haskell test suite run in the build phase below; the greedy smoke (section 5) must give identical tokens for vnni, vnni0, a, b and ab, because the store is data movement.

6. Open items

  • Decode store: the remedies do not touch it (one token per user per step: no 16-token run, no window). Measured at 28 / 35 us per layer (tp2 / tp4), 1.0 ms of a 12.7 ms step, hidden behind the attention workers' Ready sections at prompt 1024 but present. Candidates: stripe the 8 decode tokens over the helpers one token each (a window with block size 1), or prefetch the 64 lines of the token's column; both unmeasured.
  • The remaining prefill span with both remedies (about 60-80 us per layer) is below the row-major store's 275 us; whether the residual is the block loop, the join, or the helpers' arrival is not separated here (a per-block span would do it).
  • Model-level test of the striped window: the C++ unit tests exercise store_block and the grouping through the handwritten plugin path (n_workers 1), the emitter test counts the helper call, and the end-to-end greedy smoke checks the result; a fake-device test that drives save_k with n_workers greater than 1 does not exist yet.
  • Other plugins: every generated plugin with a KV-writing attention operation now emits the helper call; only qwen3-4b was run. The handwritten llama plugin keeps the serial store (n_workers 1) and gets the block store only.
  • Switch defaults: both remedies are on by default in the commit; the switches exist for this measurement and can be removed before a PR.
