Attention statistics · PR 4596

What work ran where, and what time it took

Counter meanings and worked examples · PR #4596 at 04da001cb5 · Raw measurements from Claude’s test artifacts

1. What the counters cover, top down

Short version. PR 4596 measures which attention paths ran, how much key-token work each path served, and where attention time accumulated. Token-job counts, page visits, and scored key tokens describe different sizes of work. The examples below show why a run can use AMX for every decode token job while still doing some work through AVX.

2. Why several kinds of count are necessary

QuestionEvidenceWhat the answer means
Did a query use AMX, AVX, or the card?token_jobs_by_path_setWhich paths touched a token job anywhere in its forward. A job belongs to exactly one set, such as avx+amx.
How much attention work did each path serve?*_k_tokens and fpga_k_tokens_x_kv_headsScored key-token work on a common scale. This is the meaningful denominator for a work-share percentage.
Why is AVX still present when AMX is available?Ready/pending split, visits, and *_avx_full_page_visitsSeparates older pages from pages written in the current forward. Distinguishes partial-page work from full pages that also used AVX.
Is attention time spent doing work or waiting for results?T1–T5, especially join_wait_cycles / busy_cyclesSeparates forward duration, attention-job duration, and no-progress join waits.
Is work uneven across layers or worker threads?<class>_layer_<L> and <class>_worker_<W>Shows where work and waiting accumulate. A class is one of the two forward categories below.

A token job is one query token of one user in one forward. An attention job is one worker’s attention work for one layer and one minibatch. A visit is one query-token/page/key-value-head encounter. A scored key token is one key considered for that query, counted once per key/value head. The same stored key can contribute to many queries, layers, and forwards.

A high AMX work share establishes that AMX served the work. It does not establish an equal share of elapsed time or a particular speedup. A token job with a small AVX tail and many AMX pages still belongs to avx+amx.

3. What each group of fields means

Forward classes describe the whole forward

A listener receives a completion notification for a scheduled token, with output scores when requested. Generated tokens have listeners. The final token of each submitted prompt chunk also has a listener.

ClassExact ruleInterpretation
decode_likeEvery token job has a listener.Usually decode work. A one-token final prompt chunk or a speculative verification step can also qualify.
prompt_or_mixedAt least one token job has no listener.Prompt processing, possibly alongside other users’ generated tokens. All work of that forward stays in this class.

listener_jobs counts jobs with listeners. kv_only_jobs counts the other jobs, which supply key/value data without requesting output scores. At a completed-forward boundary, listener_jobs + kv_only_jobs = token_jobs. The listener count is not a count of generated tokens.

Work counters: volume, coverage, and page shape

FieldsUnit and meaning
forwards, token_jobsNumber of completed model forwards and the query-token jobs they carried.
token_jobs_by_path_setOne count per token job, across all its layers, heads, and pages. The eight sets are none, avx, amx, avx+amx, fpga, fpga+avx, fpga+amx, and fpga+avx+amx. Their counts sum to token_jobs after a forward finishes. none means no serving path was recorded.
ready_*, pending_*Two software passes. Ready pages were not written in this forward. Pending pages contain data written in this forward. These prefixes do not mean prompt versus decode.
*_amx_visits, *_avx_visits, *_empty_visitsPage visits by outcome. Empty means no software scoring occurred in that visit. It does not measure FPGA work. Pages skipped before a visit are not counted.
*_amx_k_tokens, *_avx_k_tokens, *_empty_k_tokensKey tokens scored per key/value head. One AMX visit contributes 64 in this model’s page format. AVX contributes the actual relevant count. Empty contributes zero.
*_avx_full_page_visitsThe subset of AVX visits that served all 64 key tokens of a page. Already included in *_avx_visits and its key-token count.
fpga_queriesToken jobs assigned FPGA attention in a forward. Each query job is counted once.
fpga_query_passesQuery/pass pairs, summed across hardware passes and layers. A query can contribute repeatedly.
fpga_k_tokens, fpga_k_tokens_x_kv_headsRaw FPGA key count per query/pass, then that count multiplied by the number of key/value heads. Only the second quantity shares the software counters’ scale.

kv_mul is the number of query heads per key/value head. Multiplying normalized key-token work by kv_mul gives the corresponding number of query/key dot products. It does not give floating-point operation counts or elapsed time.

Timers: five different intervals

All timer values are ticks of the CPU time stamp counter (TSC). tsc_hz gives ticks per second. Seconds = cycles ÷ tsc_hz. A worker-second is one second accumulated on one worker. Concurrent workers add worker-seconds without adding the same amount of wall time.

Timer / fieldWhat it measuresUseful arithmetic
T1 · wall_cyclesWhole model-forward duration, including layers, output scores, and listener delivery. Scheduler work outside the forward is excluded.T1 / forwards: mean forward duration in cycles.
T2 · busy_cyclesAttention work on all participating workers: the two passes and the join. Excludes upstream K/V wait. Includes T5.T2 / attn_jobs: mean busy duration per worker-job.
T3 · wall_cycles_w0Full attention-job duration, observed by attention worker 0. Includes upstream K/V wait. This worker is not necessarily pool thread 0.Divide by the number of jobs observed by that attention worker. Total attn_jobs counts all workers.
T4 · period_cycles_w0Time from attention worker 0’s first job of one layer’s attention operation to its first job of the next operation. Includes intervening work. The final layer has no following period.T4 / period_count_w0: mean observed layer period.
T5 · join_wait_cyclesNo-progress waiting for peer workers or FPGA results during the join. Covers both software-only and hardware joins.T5 / T2: fraction of accumulated attention busy time spent in this wait.

wall_max_cycles, wall_max_cycles_w0, and period_max_cycles_w0 are the largest individual T1, T3, and T4 observations. They are neither sums nor percentiles. T2 and T5 sum across workers. T1, T3, and T4 do not. Adding all five timers would count overlapping time more than once.

Views and metadata explain the scope

The live files are exposed through FUSE (a user-space filesystem) under /model/<id>/attention/. The same model state prints its final report to stderr (standard error) when it ends.

Collection is opt-in through TRON_ATTN_STATS=1. With collection off, summary reports on: false and class totals/forwards are empty objects ({}). An empty record means no measurement is available.

ViewWhat it contains
summaryIdentity and interpretation: model_id; eagle for a speculative draft model; on and switch for collection status; AMX build/runtime availability; n_kv_heads, kv_mul, head_size (components per head), n_layers, page_size, worker counts, and tsc_hz.
<class>_forwardsForward counts, token-job counts and path sets, T1, FPGA queries, and the minimum/maximum attention-worker count used by this class.
<class>_totalsWork and attention-job counts summed across layers and workers, T2–T5, and FPGA work.
<class>_layer_<L>One layer summed across workers, including T3/T4 and FPGA work.
<class>_worker_<W>One pool thread summed across layers. Contains software work, job counts, T2, and T5. Does not contain T3/T4 or FPGA work.

n_workers is the pool size. active_workers counts pool threads that have done any attention job during this model state, across both classes. It is not a current concurrency measurement. n_attn_workers_min and n_attn_workers_max describe the split used by each class. With 27 pool threads and 20 attention workers, attention uses pool threads 7–26.

Counts accumulate for one model state. A new state has new counts, even if it reuses the model identifier. Totals, layer views, and worker views describe the same work at different resolutions. They are not independent quantities to add together. [Counter definitions]

4.1 What was counted as prompt work and decode work?

Prompt forwards: 1,024 prompt tokens/user ÷ 128 tokens/chunk = 8 forwards
Prompt jobs: 8 forwards × 8 users × 128 tokens/user = 8,192 token jobs
Prompt listeners: 8 forwards × 8 users = 64 listener jobs
Remaining prompt jobs: 8,192 − 64 = 8,128 K/V-only jobs
Decode jobs: 255 forwards × 8 users = 2,040 listener jobs

The final prompt forward supplies the scores for the first output token. The remaining output tokens require 255 decode forwards. In this run the prompt and decode phases are separate, so their forward classes match those two phases exactly.

Decode attention jobs: 255 forwards × 36 layers × 20 workers = 183,600 worker-jobs
Prompt attention jobs: 8 forwards × 36 layers × 20 workers = 5,760 worker-jobs

These identities show one attention minibatch per layer per forward in this run. An attention job can handle many query-token jobs.

4.3 Why “every token used AMX” does not mean “all work used AMX”

Decode path sets: 24 amx-only jobs + 2,016 avx+amx jobs = 2,040 token jobs
Jobs using AMX: (24 + 2,016) ÷ 2,040 = 100%
Jobs also using AVX: 2,016 ÷ 2,040 × 100 = 98.8235%

The AVX part can be a small tail of the newest page. It still places the job in the two-path set. The 24 AMX-only jobs are 3 full-page steps × 8 users. Each such step contributes 36 layers × 8 heads × 8 users = 2,304 pending AMX visits. Across the three steps that is the reported 6,912 pending AMX visits.

AMX visits: 10,278,144 ready + 6,912 pending = 10,285,056 visits
AMX work: 10,285,056 visits × 64 keys/visit = 658,243,584 key-token units
AVX mean: 18,579,456 key-token units ÷ 580,608 visits = 32 keys/visit

AMX has 94.6565% of nonempty software visits, but 97.2549% of scored-key work. The difference comes from the different amounts of work per visit. For prompt processing, 1,024 avx-only + 7,168 avx+amx = 8,192 token jobs. The first prompt chunk has no earlier ready pages. Later chunks can use AMX on earlier pages.

Prompt processing also records 1,216,512 pending AVX full-page visits. Those visits are a subset of the 3,538,944 pending AVX visits. They show that AVX work is not restricted to partial pages during prompt processing. They must not be added to the visit total again.

7. What the evidence supports

  • Work shares are measured coverage. They describe scored key tokens or token-job participation. They are not speedup estimates, memory-byte counts, or time shares.
  • Forward classes can mix user phases. During continuous serving, one user’s prompt work and another user’s generated tokens can share prompt_or_mixed. That class cannot yield a separate decode-only work total.
  • Time denominators must match. Sum-over-worker timers belong with worker-job counts or a known worker-time capacity. A cumulative maximum is a largest observation, not an interval sum.
  • Intervals require the same model state. Differences of additive counters describe work between two reads. Subtracting maxima does not give an interval maximum. Separately read live files are not one simultaneous snapshot.
  • Availability is not use. amx_available = true says the AMX path is available. The path counters establish whether measured work actually used it.
