MoE router x AMX: ramp-up and scoping

Written 2026-08-23. Question (from input-2-ai/router-amx.md): TRON's router matrix calculation was suggested as an AMX use case, to speed up prefill and decode for MoE models such as gpt-oss. (1) Ramp up on what the MoE router is and where it lives in tron; (2) decide how this relates to the ongoing AMX attention project, given that project's attention kernels do not support gpt-oss geometry.

Legend: code = verified in source (file:line cited); meas = number from a measurement artifact; est = computed estimate (script: router/router_cost_model.py); hyp = hypothesis, paired with the measurement that would settle it. Source trees: ~/workspace/tron (main, 1407f48dd) and the generated-plugin snapshot ~/workspace/tron/gen_sst_round4_ingest/.

TL;DR
  • What the router is: a per-layer scorer in every MoE block: one small matmul ([tokens x 2880] x [2880 x n_experts] for gpt-oss) + bias + top-k + softmax. It picks which 4 of 128 experts (gpt-oss-120b) run for each token. It is approximately 0.4% of the selected-expert FFN arithmetic, but it is on the critical dependency path: this batch's expert selection, routing build, and expert launches cannot proceed until its router result is available.
  • Scope: the routing machinery is tron framework code; the per-model instantiation is generated from ingest for gpt-oss (not hand-coded). Two execution paths exist today: hand-written plugins (mixtral) compute router logits on CPU (fp32, serial loop); ingest-generated plugins (gpt-oss) compute them on the FPGA, adding a small-matmul round trip between two CPU steps in every MoE layer.
  • MoE-only: dense models have no router and, in production executors, zero CPU matmuls at all — a router/AMX kernel gives dense models nothing.
  • Recommendation: neither option (a) nor (b) as posed. Router kernels and gpt-oss attention kernels are technically independent. They should share the AMX availability, tile-region, isolated-TU, build, and kill-switch pattern currently implemented on jhan-amx-p0, but router work should not be stacked on the attention kernels themselves. If PR #3879 is not landing first, extract or land the model-agnostic AMX plumbing as a small prerequisite, then develop router and gpt-oss attention support as independent increments (option c below), starting with a measurement: how much decode time the FPGA router round trip actually costs. Do not sequence router work behind gpt-oss attention kernels — those are ~1 week of work with an estimated ~0 production payoff (production gpt-oss runs FPGA attention).

1. What a MoE router is

A dense transformer block runs one feed-forward network (FFN) on every token. A mixture-of-experts (MoE) block instead holds n_experts separate FFNs (“experts”) and runs only k of them per token (“top-k routing”). The router (also called the gate) is the component that chooses: 

logits[t] = x[t] · W_router^T (+ bias)     // x: [dim], W_router: [n_experts x dim]
chosen[t] = top-k(logits[t])                 // k expert indices
scales[t] = softmax(logits[t][chosen])       // blend weights (gpt-oss: softmax over the top-4)
out[t]    = sum_j scales[t][j] * expert_{chosen[t][j]}(x[t])

This runs in every MoE layer, for every token, in both prefill and decode. Two properties matter for kernel work:

  • The router weight is one shared matrix per layer — unlike attention KV pages, which are per-user. Batching the router matmul across all tokens of a scheduling batch (including different users) is always valid. code (the framework already does this: run_gate batches over q_batch->items, feed_forward.hpp:479-492; generated code fills one matmul template over q_batch->items, ingested_gpt_oss_120b.hpp:2046).
  • Everything downstream waits on it: the per-expert matmuls cannot even be prepared (templates filled, hardware slots reserved) until top-k output exists, because the per-expert token lists come from the routing (moe_routing.per_expert, mixture_of_experts.hpp:411-431). code

For mixtral it means “replace a serial fp32 CPU loop”; for gpt-oss it means “move a small matmul off the FPGA to remove a round trip” — and gpt-oss is the model that motivates the ask.

3. The per-layer dataflow, and what a CPU router changes

Supporting evidence that gpt-oss-120b is sensitive to CPU↔FPGA synchronization and serial expert dispatch, motivating direct measurement of the router chain:

  • Note [Expert matmuls] (common.hpp:55-71): matmul prepare/launch overhead “is shouldered by a single core … In practice, this resulted in FPGA starvation under GPT-OSS-120b as the core dispatching matmuls could not keep up.” The router round trip feeds this exact single-core chain. code
  • On gpt-oss-tp4 decode, waiting on a different FPGA matmul channel (qs_for_attn_channel.start_reading) measured 73% of attention-worker time in the Aug-3 capture (PR #2934 dataset). This demonstrates sensitivity to FPGA waits in that configuration, but does not measure the router channel or establish the router's end-to-end contribution. meas
  • The framework instruments routing (perfetto spans kernel_add_topk_softmax, “Assign tokens to experts”, per-expert “MoE matmul” events, FUSE expert_stats) but has no span around the router matmul itself — the round trip is currently invisible in traces except as channel-wait gaps. code

4. Cost model: why this is a latency play, not a FLOPs play

Computed by router/router_cost_model.py from the measured dims. est where marked.

modelrouter MACs / token / layerexpert-FFN MACs / token / layer router MACs / selected-expert-FFN MACs

Moving the router to any engine cannot win by saving arithmetic; the candidate wins are (1) deleting the per-layer FPGA round trip + earlier expert dispatch, and (2) freeing FPGA queue slots in a workload that is already FPGA-wait-bound.

On the CPU side, the router is weight-bandwidth-bound at decode widths est: the kernel reads the whole 720 KB (120b, bf16) weight per layer regardless of M. Napkin bounds for M x 2880 x 128 on one 6962P core (from measured per-instruction numbers, amx-overhead-20260821.txt):

M (tokens in batch)AMX bf16 instruction bound / L3 lower bound est AVX-512, weights in L2 est AVX-512, weights in L3 est
1~6.9 µs instr; ≥10.9 µs if L3-served~4.3 µs~10.9 µs
4~6.9 µs instr; ≥10.9 µs if L3-served~4.3 µs~10.9 µs
8~6.9 µs instr; ≥10.9 µs if L3-served~8.5 µs~10.9 µs
16~6.9 µs instr; ≥10.9 µs if L3-served~17.1 µs~17.1 µs
  • The ~6.9 µs AMX number is an instruction/tile-issue bound, not an L3-served wall-time estimate. AMX and AVX-512 both read the same 720 KB bf16 weight, so at the assumed 25 B/c per-core L3 rate both have a common lower bound of ~10.9 µs per layer. In this napkin model AMX separates from AVX-512 only once AVX computation exceeds that common bandwidth floor; the crossover is therefore not established at M≈4 and must be measured. The honest framing stands: the win may come mostly from “CPU instead of FPGA round trip”, with AMX the right engine only once M is batched (which the router allows across users). hyp — settled by the P0 microbenchmark below.
  • All-layer bf16 router weights for 120b total 25.3 MB, well below 3bda's 432 MB/socket aggregate L3 capacity. They can therefore be capacity-resident if execution and allocation remain on the same socket, but actual L3 residency and bandwidth are unmeasured and may be reduced by competing model/runtime traffic. The P0 benchmark should include warm cyclic-all-layer and cache-disrupted cases. A single layer's 720 KB does not survive a full decode step in L2, so the L3 column is the realistic single-core decode case. est
  • These bounds ignore multi-core splitting (the framework's non-serialized CPU matmul path already tbb-parallelizes, tensor.hpp:397-403) and the AMX license clock; both belong to the microbenchmark, not to this table.
Insufficient data (the deciding number): the wall-clock cost of the FPGA router round trip per MoE layer in decode (launch → logits back on host → topk start), and the M distribution per q_batch in decode. Neither is derivable from source. Measurement: one perfetto trace of ingested-gpt-oss-120b (or 20b) decode on delphi-3bda; the gap on worker 0/helpers between mlp_router_weight_launcher dispatch and kernel_add_topk_softmax span start, per layer, at 1u and 8u. Until then, every end-to-end payoff number for the router work is a hypothesis.

5. Relationship to the ongoing AMX attention project

Inventory of the jhan-amx-p0 branch (13 files, +1975/-27 vs main), verified 2026-08-23:

reusable by a router kernel (model-agnostic plumbing) attention-specific (irrelevant to router)
  • amx_attn::available(): CPUID 7.0 EDX bits 22/24 + XCR0[18:17] + per-process arch_prctl(ARCH_REQ_XCOMP_PERM), cached; one grant serves any AMX kernel in the process
  • begin_region()/end_region() per-thread tile-config bracket (max-shape config, TILERELEASE)
  • isolated single-TU -mamx compile pattern + intrinsics-free interface header
  • cmake option + TRON_AMX_DISABLE kill switch (same-binary A/B, measured at clean-binary speed)
  • standalone self-validating bench pattern (amx_fused_bench.cpp) and the numerics-pin test pattern (t_amx_numerics.cpp)
  • QK/PV kernels, Q-group packing, transpose epilogue, rolling-softmax integration
  • K mirror parallel arena in kv_cache.hpp + coherence write sites (lineage: “mirror” = the S=Q·KT formulation from Bill's PR #2934; the arena implementation is ours)
  • the attention geometry gate (head 128, kv_mul 4) and its twins

Coupling: none that forces an ordering between the kernels. One delivery-level dependency exists: the reusable plumbing lives on jhan-amx-p0 (PR #3879, open), not on main — router work either waits for that PR to land or extracts the model-agnostic plumbing as a small prerequisite change. At the kernel level, the router path (feed_forward.hpp / generated plugin FFN section) never touches self_attention.hpp, kv_cache.hpp, or the KV cache. Three soft interaction points, none blocking: the shared kill switch (would want a router-specific one), per-thread tile-config state (a same-thread mix of router and future shape-specific attention configs must re-issue LDTILECFG; today both would use the max config), and dtype (hand-written-path router weights are fp32; AMX multiplies bf16/int8, so that path would need a one-time bf16 conversion with a numerics note — the generated path's weights are already device bf16).

What “adding gpt-oss support to the current AMX implementation” actually means, per the existing estimate (rampup/gptoss-estimate.html, Sol-reviewed): new qk_st_64x8/pv_64x8 attention kernels + two-shape gate, ~1 week + tests, payoff +4…+7% decode at 1u/8K in all-software mode est, ~0 in production FPGA-attention mode est. That work item neither contains nor enables any router work.

(d) hand-written-path (mixtral) gate only AMX-accelerate run_gate's serial loop Negligible: 64 KB weights, N=8, 0.01% of block arithmetic; the serial fp32 loop is already cheap at mixtral's size. Fix only if it falls out of (c) for free.
(e) FPGA-side pipeline fusion instead investigate whether post-attention residual add + rmsnorm and the router matmul can be fused or kept card-side so router logits return without a separate host→card router-input transfer Attacks the same synchronization boundary without AMX, but it is a larger cross-stage FPGA change than router-matmul fusion alone: today the router input is produced by CPU add + rmsnorm, so the router cannot simply piggyback the o_proj DMA. Feasibility, ownership, numerical behavior, and expected latency must be priced before P1. The router-round-trip measurement is useful to both options, but this alternative also needs a feasibility estimate for migrating or fusing add + rmsnorm.
Recommended plan (option c):
  1. P0 — measure (low code risk, one quiet slot on 3bda): (i) first verify that existing trace events identify router dispatch, logits readiness, top-k start/end, routing completion, and first expert launch; if they do not, add narrowly scoped perfetto markers around those boundaries. Then capture ingested-gpt-oss decode at 1u and 8u and report separately: (a) router dispatch → logits ready / topk start, which a CPU router can replace; (b) topk/routing/prepare → first expert launch, which remains unless separately optimized; (c) the combined critical-chain interval — plus the decode M distribution. The segmentation matters for the stop/go decision: the entire red slice is not the achievable router-matmul saving. (ii) standalone microbenchmark (amx_fused_bench pattern): router shape M x 2880 x {32,128}, arms = current-style AVX fp32 dot loop / AVX-512 bf16 / AMX bf16, M in {1,2,4,8,16}, weights warm cyclic-all-layer (L3) and cache-disrupted as well as L2-pinned. Together these bound the achievable end-to-end win before any integration work. Also share the P0 trace with the FPGA team to price option (e).
  2. P1 — prototype behind a switch: ingest change: leave the router weight host-resident (today promoteToDeviceMemory is unconditional for L.Matmul, LoopyTron.hs:800-802 — add a router/size-aware placement or an explicit MoeGate marker) + a CPU router kernel (AMX with AVX fallback via the existing available() chain, new TRON_AMX_ROUTER-style toggle so attention and router A/B independently). The buffers the CPU needs (post-norm activations in, logits out) are host-visible already.
  3. P2 — A/B + numerics: same-binary A/B at 1u/8u, 2K/8K on ingested-gpt-oss-20b/120b; numerics pin per the t_amx_numerics pattern: compare router logits against the device-matmul reference, record the margin between ranks k and k+1, require exact expert-set agreement away from a defined near-tie tolerance, and apply the established T1 treatment to top-k-cutoff near-tie cases (selection changes alter expert dispatch discontinuously, so record the cutoff margin rather than treating every mismatch uniformly); then the standard suite.
Decision points: if P0(i) segment (a) — the part a CPU router can actually replace — is <1% of decode step time, stop: write the number down and close the item. If P0(ii) shows AVX-512 within noise of AMX at measured M, ship the CPU router without AMX first and add the AMX kernel when batching justifies it.

7. Does any of this help dense models?

No. The router exists only in MoE blocks. Beyond it, a code sweep found exactly one production CPU matmul in tron (the hand-written-path router gate itself); every other matmul — QKV/O, expert FFNs, lm_head/logits — is a device tensor executed on the FPGA under all production executors (tp1/tp2/tp4). Dense models therefore have zero production CPU matmuls for a router-shaped kernel to serve. (The host executor family runs everything on CPU, but those are test/emulation targets with large-N shapes — a different kernel class.) code

The honest generalization statement: a router AMX kernel is a skinny-M GEMM against a small, shared, host-resident weight matrix. Today the MoE router is the only production site with that shape. If future models or executor changes move other small matmuls onto the CPU, the kernel generalizes; nothing in the current tree needs it.

8. Glossary

MoE / expertmixture-of-experts: a block holding many FFNs, running only the top-k per token
router / gatethe scorer choosing which experts run; “gate” is the older name used in the hand-written path and mixtral weight names (block_sparse_moe.gate.weight)
logits (router)the n_experts raw scores per token, before top-k
M / K / NGEMM sizes: M = tokens in the batch, K = model dim (2880), N = n_experts
dtensor / btensortron tensor families: device-resident weights (FPGA) vs host DMA-visible bf16 activations; plain tensor = host fp32
worker 0the scheduler thread running the plugin's per-layer statement stream; helper workers run the ParKernel loops (norms, topk, swiglu, blend)
channel / latch / waitabletron's producer-consumer synchronization between CPU kernels and FPGA jobs; a “round trip” = launch an FPGA job, DMA the result back, wake the waiting CPU reader
prepare / launchtwo-step FPGA matmul dispatch: fill a job template + reserve per-device slots, then fire; per-expert in MoE (the single-core cost in Note [Expert matmuls])
ingesttron's model importer: torch.export trace → Haskell pipeline → generated C++ plugin header in the build tree
AMX / tile / TDPBF16PSIntel Advanced Matrix Extensions: 1KB tile registers + a matmul unit; TDPBF16PS multiplies bf16 pairs into fp32 accumulators (see rampup/01-amx-rampup.html)
VNNI pair-interleavethe B-operand layout AMX requires (pairs of K rows interleaved); router weights are constant, so packing happens once at load, unlike the attention K mirror
