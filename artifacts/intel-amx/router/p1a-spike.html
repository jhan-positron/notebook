2. Why the corrected G0 estimate did not materialize

  1. The mechanism works exactly as designed meas: with the CPU router on, the driving thread's block at the top-k output read collapses from 19.7 µs to 0.36 µs per layer (1u; 32.9 → 0.36 at 8u) in the traced reps.
  2. Tracing inflated the P0 stall ≈2.5× est: untraced baselines run 254 tok/s where P0's traced steps implied 206. Back-computing from the measured net gains, the untraced recoverable stall is ≈8 µs/layer at 1u and ≈12 µs at 8u — against a kernel cost of 6.4 / 22 µs (avx_bf16, P0b) the margin is ≤1–2 µs/layer at 1u and negative at 8u.
  3. The serialized placement adds a new serial wait: the CPU branch waits for the helpers' rmsnorm output on the driving thread before computing. The traced CPU-router slice is 21.0 µs/layer at M=1 meas. Using the independently measured 6.4 µs AVX-bf16 kernel cost gives an inferred ≈14.6 µs rmsnorm-arrival component. Because this phase did not place a separate arrival-ready marker, 14.6 µs is derived attribution est rather than a directly measured slice. The async FPGA path parks that wait on the TX worker. A faster kernel cannot remove it; only a different placement can (below).

3. What the spike proved (Phase S: all checklist items green)

  • Mixed host/device generated TP code compiles and runs: a host fp32 weight member beside device members, in the tp2 executor, all executor instantiations green. The launcher and channel types key on the executor alias — the working design is dual members with a runtime branch, which tells the future emitter change its required shape.
  • Loading: the normal visit_named_tensors/safetensors path fills the host tensor from the BF16 checkpoint by assignment dispatch — no loader change.
  • Latch/channel behavior: a synchronous CPU write satisfies consumers when the payload's last-8-byte sentinel word is stored once, release-ordered, after the other elements; per-index latches and the whole-phase barrier both behave. The host-executor instantiation needs the plain fallback-latch path (no sentinel).
  • Numerics instrument finding: the attempted seeded OFF-vs-OFF control diverged from the first tokens under the command used for this phase. That attempt does not establish that token comparison is instrument-invalid: the pre-registration required greedy decoding, and the attention-project t1-quick record established deterministic runtron output with --temperature 0 -s 42 --pay-for-determinism on its tested models/configurations. Audit of the preserved P1a command confirmed all three flags were absent (only --seed 42). The correctly flagged retry (r0-p1a-numerics2.sh, 2026-08-24) resolved it: the OFF-vs-OFF control is token-identical — the instrument IS valid with the full recipe, and gpt-oss MoE routing does not break determinism — and OFF-vs-ON genuinely diverges, first divergence at token ≈16 of a 34-token stream meas. Interpretation (labeled hypothesis): the CPU's bf16×bf16→fp32 router logits differ from the FPGA's quantized computation enough to flip a top-k selection near a tie — the exact phenomenon the plan's numerics design anticipated. Deciding measurement: the P2 logits/expert-set pin with cutoff margins at the divergence step. Any future integrated claim stays gated on that investigation. (An earlier "instrument-invalid-even-flagged" verdict was a normalization artifact — a run-specific log line interleaved into the token stream; re-verdicted by color-span token extraction, note inside p1a-numerics2-verdict.txt.) On-arm output was qualitatively sane.

Spike artifacts: exec/r0-p1a-patch-header.py (the auditable hand-edit), the edited header (marker-blocked, confined to tron-router-p0), exec/results/router/ingested_gpt_oss_20b.hpp.{pristine,cpu-router-spike}.

4. Follow-on options, each with measured inputs (decisions for jhan)

  • Bounded-parallel CPU router (P1a variant the plan pre-named): run the router on a bounded helper placement rather than on the driving thread, allowing the rmsnorm-arrival wait and router computation to overlap with otherwise available work. The estimated untraced gross router-dependent stall is ≈8 µs/layer at 1u and ≈12 µs/layer at 8u; at 1u/2K the former is ≈4.8% of the decode step. After paying kernel, synchronization, and any contention costs, the modeled net opportunity is only ≈+1–2% decode est. That net figure is an estimate, not the cost of the round trip. The Note [Expert matmuls] worker-contention and FPGA-feed risks apply. Cheap to prototype in the existing spike harness under Sol's staged stop conditions (exec/results/router/sol-p1a-review.md sec 3).
  • AMX engine (P1b, not authorized) changes 8u only: 6.6 vs 22 µs at M=8 (P0b), turning the 8u cells from loss to ≈flat-positive est — still likely under +1% serialized; worth pricing only together with the parallel placement.
  • Option (e), card-side fusion: its architectural case is unchanged — card-side fusion avoids both host CPU compute and host placement. Its payoff magnitude must, however, be repriced: P1a indicates that the P0 Perfetto capture inflated the host-observed router-dependent stall, with the untraced recoverable component estimated at ≈8 µs/layer at 1u and ≈12 µs/layer at 8u. Use the P0 chain decomposition (p0-trace.html sec 4) together with this P1a recalibration; do not price fusion directly from the traced 19.7/32.9 µs blocked-read values.
  • Close option (c): defensible if the bounded-parallel placement check above is declined or fails its gate. At 1u/2K, the estimated untraced gross router-dependent stall is ≈8 µs/layer, or ≈4.8% of the ≈3,972 µs decode step — not 0.2%. The serialized implementation recovers that dependency but pays the CPU kernel and driving-thread placement costs, producing only +0.81% [95% CI −0.22, +1.85] end to end. The ≈0.2% figure is the post-replacement top-k-output blocked-read residual (0.36 µs × 24 layers), not the original round-trip cost. Sol-corrected wording, 2026-08-24

5. Deviations in this phase (surfaced per Rule 12)

  • The first A/B pass ran a placeholder kernel (generic expr dot), not the pre-registered avx_bf16 arm — detected by attribution, corrected, and re-run; both generations preserved (p1a-arm-fp32expr/ vs current files).
  • Rep extension to n=6/arm was performed in all four configurations because every n=3 interval exceeded the pre-registered precision target. This was execution of the registered adaptive-rep rule, not a post-hoc sample-size change.
  • The token-control run did not use the previously established complete deterministic runtron recipe (--temperature 0 -s 42 --pay-for-determinism), despite the pre-registration requiring greedy comparison — confirmed by command audit of the preserved log (only --seed 42 was passed). Its OFF-vs-OFF divergence is therefore inconclusive. A correctly configured gpt-oss retry remains required before token comparison can be declared unavailable.
  • The "cpu router compute" trace slice includes the rmsnorm arrival wait — the pre-registered boundary list called for separate compute start/end vs publish marks; the arrival wait was not separately sliced. Attribution separated it arithmetically (kernel cost matches P0b); a follow-on run should slice it directly.
  • Traced attribution reps exist for the 2K contexts only (pre-registered scope said one traced rep per config; the 8K cells were not traced — scope cut, stated).
