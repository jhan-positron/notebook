Muse Glimmer and AMX

Code facts at tron main 6198824246 (2026-10-16 18:11 UTC). HF config read from delphi-3bda on 2026-10-16. Written for jhan. Updated 2026-10-17: section 4 now records what the implementation needed. The measured gains are in muse-glimmer-amx-results.html.
Short version

Muse Glimmer 30B (in tron main) has the attention shape kv_mul 16 (query heads per key/value head: 32 query heads over 2 KV heads of 128 dims), where the AMX kernels on main serve kv_mul 4 only.

It is not a pure attention-on-FPGA model, because 39 of its 52 layers use a 2048-token sliding window, which the ingest compiler marks software-only, so those 39 layers run the CPU software attention loop under every setting of USE_HW_ATTN.

With the kernels generalized to kv_mul 16 (section 4) and measured on 2026-10-16/17, decode is 4.4 to 15.2 % faster per user in the production configuration and prefill is 0.6 to 8.7 % shorter (results page).

Q (query), K (key) and V (value) are the three per-token tensors attention computes. K and V are stored per token in the KV cache and read back at every step. A KV head is one 128-dim K/V pair shared by a group of query heads. The engagement point (position 127) is the first position from which the card serves a layer.
TRON_ATTN_STATS, perfetto
TRON_ATTN_STATS=1 makes tron print an exit report with per-layer counters of the K tokens scored by the AMX kernel, the AVX loop and the FPGA. perfetto is the trace tool that records a timeline of one run.
A/B
Two runs that differ in one setting only, here AMX on against AMX off (TRON_AMX_DISABLE=1) with the same binary.
MMLU Pro, GPTQ, ATEM, RoPE
MMLU Pro is a multiple-choice question-answering accuracy benchmark (its threshold is a percentage of correct answers). GPTQ int4 is a 4-bit integer weight quantization. ATEM is the tool-calling message format rinzler serves for this model. RoPE is the rotary position embedding, the way positions are mixed into Q and K.
TDPBF16PS, requires-probes, VNNI-K
TDPBF16PS is the AMX instruction that multiplies two bf16 tiles and accumulates in fp32. Requires-probes are compile-time checks (C++ requires-expressions) that a kernel overload exists. VNNI-K is the K layout of PR 4424 (K stored in the AMX B-operand order).
tron, runtron, rinzler
tron is the inference program under test, runtron its command-line tool, rinzler the production server.
ingested plugin
A model whose C++ code is generated by tron's ingest compiler (Haskell, ingest/src) from a traced HuggingFace model, as opposed to the hand-written llama plugin.
AMX, AVX-512, the dotter
AMX is Intel's tile-matrix instruction set. AVX-512 is the vector instruction set of the existing software attention loop, called the dotter in the code.
AoF, FPGA attention, USE_HW_ATTN
Attention on FPGA: the card scores K and V for positions at or above the engagement point (position 127). USE_HW_ATTN unset means on for ingested models and off for others. USE_HW_ATTN=0 turns it off for all models.
kv_mul, GQA
Grouped-query attention: several query heads share one KV head. kv_mul is the ratio (query heads divided by KV heads).
KV page
A 64-token block of K and V storage. The AMX kernels work on whole pages only.
sliding window
A layer that attends only to the last N tokens (N = 2048 here). A full-attention layer attends to the whole context.
software_only, kv_slot_candidate
The two values of attention_hardware_capability the ingest compiler assigns per layer. Only a kv_slot_candidate layer can go to the FPGA.
bf16, tile
bf16 is the 2-byte float format K, V and Q are stored in. An AMX tile is a register of 16 rows x 64 bytes (16 rows x 32 bf16).
TRON_AMX_DISPATCH, deb preset, kill switch
TRON_AMX_DISPATCH is the CMake option that compiles the AMX kernels. The deb preset is the package build CI ships. The kill switch is TRON_AMX_DISABLE=1, which keeps the AMX binary on the AVX path.
TPS
Generated tokens per second per user, the nightly performance metric.

3. Where its attention runs (the AoF question)

Only partly on the FPGA. The ingest compiler decides per layer, at ingest time, whether a layer may use the card, and a sliding-window layer never may.

  • Rule. A layer is a hardware candidate only when its attention type is full causal and its geometry is the model's standard one [ingest/src/AttentionHardware.hs:14-18]. The ingest checker rejects any sliding-window layer marked hardware-capable [ingest/src/TronCheck.hs:1067-1069].
  • Runtime side agrees. is_hardware_attention_candidate returns false when the operation has a sliding window [h/tron/models/kv_cache.hpp:412-419], and the model template asserts this at compile time [h/tron/models/model.hpp:716-720].
  • Glimmer's generated header. 39 operations carry software_only with window 2048, and 13 carry kv_slot_candidate with no window [ingested_meta_models_Muse_Glimmer_30B.hpp:107].
  • The 13 full layers do qualify for the card. The hardware limits are head size 128 or 64, at most 8 KV heads, and a GQA ratio of at most 31 [h/tron/models/model.hpp:728-738; h/libpos.hpp:57, 62]. Glimmer has 2 KV heads and ratio 16.
  • Default policy. Ingested plugins set force_hw_attn = true [ingest/src/TronCpp.hs:242], so USE_HW_ATTN unset means on [h/tron/models/hw_attn_config.hpp:12-14]. The CI test runs the model this way. Positions below the engagement point (127) stay on the CPU in every case.
Three of every four layers stay on the CPU. "AoF" describes 13 layers, not the model.
Layer kinds from the HF config layer_types and the generated header's 39 + 13 operation descriptors.

How much K and V the CPU reads per decode step

Bytes read from the KV cache is the quantity the AMX work so far has tracked. At these sizes the attention time is set by how many bytes are read from memory, not by the arithmetic. The numbers below are computed from the shapes, not estimated. One decode step, one user, bf16 K and V.

At the window limit the CPU side of Glimmer reads 82 MB per user per step, 2.4 times what the card side reads, and about half of llama-8b's all-CPU load.
Formula: layers x KV heads x tokens x 128 dims x 2 bytes x 2 (K and V). Sliding layers read at most 2048 tokens. The llama-8b row uses the nightly 8-user cell's 1152-token context. Bytes are a proxy; the attention time share of a Glimmer step is unmeasured (see section 5).

4. What AMX support for this shape needs

The kernels on main serve head size 128 with kv_mul 4, and they already allocate a 16-column tile for the query group. kv_mul 16 fills that tile exactly, so the change is a generalization of the existing kernels, not a new kernel design.

Status: implemented on 2026-10-16 as branch jhan-amx-kvmul16 (head 5061623a34, not pushed, worktree ~/workspace/ai-runs/tron-glimmer-amx). What needs no new work

  • Sliding windows. The dense-page predicate already takes the window: a page is dense only when every token is inside it [h/tron/models/self_attention.hpp:1711-1722], and the planner drops out-of-window pages before the kernels see them [h/tron/models/model.hpp:2476-2497]. With a 2048-token window, 31 or 32 of the 32 pages per (layer, KV head) are dense. The page at the window edge takes the dotter.
  • K layout. main stores K row-major, which is what qk_rowmajor_128x4 reads [h/tron/kernels/amx_attn_iface.hpp:222-225]. The VNNI-K reader of PR 4424 is not on main. If it is merged first, its reader needs the same group-size generalization.
  • Build and rollout. The deb preset already sets TRON_AMX_DISPATCH ON [CMakePresets.json:68], so the nightly package carries the kernels. The kill switch TRON_AMX_DISABLE=1 and the per-process AMX probe apply unchanged [h/tron/kernels/amx_attn_iface.hpp:46-56].
  • Executor scalar. The tp1/tp2/tp4 executors store Q as bf16, which the packer requires [h/tron/kernels/amx_attn_iface.hpp:153-160]. Glimmer runs on tp executors (section 1).
  • FPGA path. The 13 full layers keep their card path. The AMX change touches only the software path that the 39 sliding layers already use.

Expected cost and gain

  • Fact. Per page the AMX kernels issue the same 32 tile multiplies for 4 or 16 heads, while the AVX dotter's multiply-add count grows 4x with the group size (65,536 to 262,144 per page for QK plus PV). The AVX cost of a Glimmer page is therefore 4x a llama page's, and the AMX cost is about the same.
  • Measured (2026-10-16/17, runs 23:34 to 00:18 UTC, runtron A/B, AMX on vs TRON_AMX_DISABLE=1, our half of delphi-3bda, 8 users, 2 repetitions). Production configuration (FPGA on the 13 full layers): decode +9.0 % (tp2, prompt 1024), +15.2 % (tp2, prompt 2048), +4.4 % (tp4, prompt 1024), +10.2 % (tp4, prompt 2048). Prefill time in the same order: -2.8 %, -8.7 %, -0.6 %, -6.9 %. All 52 layers on the CPU: decode +13.4 %, +21.2 %, +6.1 %, +13.7 %. llama-3.1-8b, the unchanged 4-head path: +5.2 %. The two repetitions of one arm differ by at most 0.41 tokens/s per user (llama-8b, AMX off) and by at most 0.31 tokens/s per user on the Glimmer cells, far below the smallest decode gain. Details and charts: results page. The single-attention micro-benchmark was not re-run.
  • Ceiling. The TPS gain is bounded by the attention share of a decode step. The results page (section 5) gives the attention workers' busy share of a decode forward from the TRON_ATTN_STATS cycle counters, with and without the kernel, as a guide to that share.

5. Verdict and next step

The "it is AoF, so AMX is pointless" premise does not hold for this model. 75 % of its layers run software attention on the CPU in every configuration, each reading up to 2048 tokens of K and V per user per step. The gain is now measured: decode +4.4 % to +15.2 % per user over the four production-configuration cells (results page). The cost of adding the shape was a bounded generalization of the existing kernels (section 4).

Update 2026-10-17: the order below was not followed. The kernels were generalized first (section 4) and the A/B was run directly. Its numbers are in the results page. The "measure first" run is therefore superseded.

Recommended order, as written on 2026-10-16:

  • Measure first. One runtron run of Glimmer tp2 at 8 users, prompt 2048, with TRON_ATTN_STATS=1 and a perfetto trace, on our half of delphi-3bda outside the CI window. The attention-stats per-layer line shows the avx and fpga path counts per layer (expected: 39 layers avx only, 13 layers fpga plus a small avx tail), and the trace gives the attention time share per step. That share is the gain ceiling.
  • Then decide. If the attention share at the nightly cell is small (below 10 % of a step), stop. If it is comparable to llama-8b's (where the measured gain was +10 to +15 % at 8 to 32 users), implement the 128x16 shape per the change list and run the A/B.

Glimmer's TPS on our half with the branch binary is now measured (results page, section 2). The attention share of a step is still not measured directly. The results page gives the attention workers' busy share from the counters as the closest available number.
