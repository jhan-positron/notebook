The helper emits 3 shuffles per k, 4 k per lane, 4 lanes at 16 heads, so 48 per 16-token block [src/tron/kernels/amx_attn.cpp:163-168, :244-253]. `pair_sel` depends only on bit 0 of the lane and `quad_sel` only on bit 1 [:159, :161]. So stage 3 has 16 distinct results per block and 32 is the floor. Your 40 vshuff64x2 also matches the object of the kernel file, at the commit you reviewed and at the final head (clang 19.1.7, `qk_rowmajor_128x4`: 0 / 40 `vshuff64x2` for 4 / 16 heads).

I checked the hoisted form in a standalone probe. It writes the same `s` rows as the head code for 4 and 16 heads. With an `if constexpr (lanes > 1)` guard the 4-head path keeps its 3-shuffle sequence at the intrinsic level; whether clang still emits identical object code for `<4>` is for the follow-up's object compare. One note: g++ 11.4 at -O3 already merges the duplicate stage-3 shuffles (32 per block for both forms), so the saving is specific to clang, which is what we ship.

Why not here: the 16-head instruction stream at this head is the reference for the object compare in #5021, which also lists kernel performance as out of scope. The hoist changes that stream, so it needs its own object compare, a Granite Rapids numerics run and a timing. No timing exists for the 16 saved shuffles per block; the follow-up's per-kernel timing on Granite Rapids would give it.
