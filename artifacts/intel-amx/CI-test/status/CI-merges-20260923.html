Did other merges change decode or prefill speed on 09-23?

Two nightly runs: 09-22 (tron 2026.09.18-3faba6d0, systems_test run 35683952944) and 09-23 (tron 2026.09.23-5cf65b92, run 35815209295). Between the two packages, 32 pull requests were merged into tron main. Each one was read and checked against the rows of both CI machines.

Short version

  • The AMX kernels explain almost all of the +15.0 % decode gain of the 32-user llama-3.1-8b row: our own test of the old code with and without the kernels measured +14.0 %.
  • Only 4 of the other 31 merges can change code that this row runs, and together with setup differences they have at most +0.29 TPS (+0.9 %) left to explain.
  • Other merges did move other rows: #4258 made the FPGA-attention models faster on both CI machines, and #4534 is the likely cause of the Intel-only gains of the three tp4 rows.

Words used here

TPS: decode speed, generated tokens per second for one user. The CI measures it between generated tokens 896 and 1024 of each request and averages all samples.
TTFT: time to first token, in milliseconds (ms). With 8 users per engine it includes the wait behind other users' prompts.
Prefill rate: prompt length divided by mean TTFT, in tokens per second (tok/s). The CI computes it on the client.
AMX: Advanced Matrix Extensions, the matrix unit of Intel Xeon CPUs such as the Xeon 6962P in delphi-3bda.
AMX kernels: tron's attention code that uses AMX. The build option TRON_AMX_DISPATCH compiles it in. It serves only models with head size 128 and 4 query heads per KV head ("AMX shape").
Old / new package: tron 2026.09.18-3faba6d0 (no AMX kernels, ran 09-18 to 09-22) and tron 2026.09.23-5cf65b92 (AMX kernels in, ran 09-23).
Merge, #NNNN: one pull request merged into tron main, named by its number.
delphi-3bda, andoria-b1a3: the two CI machines. delphi-3bda has an Intel Xeon 6962P (has AMX). andoria-b1a3 has an AMD Genoa CPU (no AMX unit). Both ran the same two packages.
Engine: one rinzler server process. rinzler is the server program in the tron package.
tp2, tp4: the model is split over 2 or 4 accelerator cards (tensor parallel). A tp2 row runs 4 engines of 2 cards. A tp4 row runs 2 engines of 4 cards.
Hand-written, generated model: C++ model code written by hand (hand_authored in config/models.yaml), or produced by the ingest compiler (generated, and CI names start with "ingested-").
FPGA attention: attention computed on the accelerator cards ("hardware attention", USE_HW_ATTN). In the CI it is on for qwen-3-4b and gpt-oss-120b only.
Sliding-window attention: layers that look back only a fixed number of tokens (gemma-2, gemma-4, gpt-oss).
MoE, expert placement: mixture-of-experts models (mixtral, gpt-oss), and the rule that decides which card holds each expert's weights.
Timed wait: tron's wait loop with a timeout (src/system/mwaitx.cpp). Worker threads use it between layers and for card events.
RTM, MWAITX: the CPU instructions that the timed wait uses to sleep until memory changes: Intel's transactional memory (RTM, part of TSX) and AMD's monitor-wait (MWAITX).
Same-package range: lowest to highest value of a row over the nights with the old package: delphi-3bda 09-18 to 09-22 (5 nights), andoria-b1a3 09-19 to 09-22 (4 nights, without its cancelled 09-18 run).
Clearly moved: the 09-23 value lies outside the same-package range by more than the range's own width, and differs from the mean by at least 1 % (and by at least 3 ms for TTFT). A value just outside the range proves little: with 5 nights it happens by chance in about 1 of 3 cases.
Base, canon: the two builds of our 2026-09-20 test on delphi-3bda. Base is the old package. Canon is the same code (3faba6d0) built with the AMX option.

1. What changed between the two nights

Four things could differ between the two runs: the tron package, the test harness, the machine, and the benchmark itself. Only the tron package changed in a way that can affect speed.

  • tron package. The CI replaced the old package with the new one. The new package holds 32 more merges (102 commits) [git log --first-parent 3faba6d0..5cf65b92]. Both packages were built with Clang 19.1.7. Their CMake settings differ only in TRON_AMX_DISPATCH="ON" [configure output of publish-deb runs 35295875031 and 35806901506].
  • Why 32 merges at once. The nightly package build failed to start on 09-19, 09-20, 09-21 and 09-22 [publish-deb runs 35413074014, 35481888971, 35551712750, 35676322727: startup_failure]. #4510 fixed its permissions. The build at 2026-09-23 01:35 UTC took main at 5cf65b92.
  • Test harness. systems_test moved from 7327184 to 5b2250b9 (12 files). The logged benchmark settings are identical: 32 users, 10 rounds, prompt 4096 tokens, 1536 generated tokens, and the same 320 prompts in the same order [run logs: "Using 332 eligible conversations for 320 requests at prompt length 4096; cycling in dataset order"]. The changes are Slack formatting (#227), thresholds (#229), failure recovery (#223), telemetry parsing (#226), the exit code (#225) and one expected reply text (#218).
  • Machine. delphi-3bda was not rebooted between the runs (up since 2026-09-15 23:54 UTC). It kept kernel 6.8.0-138-generic and platformd 0.11.0 on both nights [last -x, uname -r, /var/log/dpkg.log]. platformd went from 0.10.7 to 0.11.0 on 09-21 at 19:58 UTC, before both runs. On 09-23 apt also upgraded libssh2, linux-libc-dev and linux-tools-common. None of them is part of the running server.
  • The AMX kernels are in the new package. The installed rinzler contains the kill-switch text TRON_AMX_DISABLE once. The old package contains it 0 times [strings /opt/positron/bin/rinzler on delphi-3bda, 2026-09-23 17:24 UTC]. This morning's page counted 86 AMX tile instructions in the same binary [CI-AMX-row-20260923.html, section 3].

4. The four merges that touch the AMX row's code

#4534: timed waits no longer update shared counters

  • Before #4534, every pass through the timed-wait loop added 1 to a process-wide atomic counter, and every call added 1 to a second one [src/system/mwaitx.cpp:18-19, 198-200 at 3faba6d0].
  • All waiting threads of an engine write the same two counters. Only diagnostic tests read them.
  • The pull request describes the cost: "Those updates add contention during inference."
  • Its first diagnostic removed only the counter updates on 4-card gpt-oss-20b. Decode per user rose +11.25 % with 1 user and +6.94 % with 4 users [PR #4534 description].
  • A later full comparison "no longer shows the earlier large four-card slowdown" [same]. The machine type of the diagnostic is not stated: Insufficient data.
Hypothesis: the counters cost more on Intel. Figure 3 shows one 10 µs timed wait, the timeout that wait_for_layer uses between layers [h/tron/models/common.hpp:949-954 at 3faba6d0]. On AMD, MWAITX sleeps until the watched memory changes or the timeout ends. So the wait makes 1 pass and 2 counter updates (est.). On Intel, each RTM pass ends after at most 2048 TSC cycles, about 759 ns at the 2.7 GHz named in the code comment [src/system/mwaitx.cpp:124]. So the same wait makes 14 passes and 15 counter updates (est.), about 7.5 times as many. The delphi-3bda engines use the RTM path [rinzler log 09-23 04:05:34: "INIT: Intel RTM (TSX) supported"]. Measurement that decides it: rebuild the new package with -DTRON_MWAIT_STATS=ON (counters back) and run the 70b tp4 row in alternating passes against the default build.
waiting (sleep or RTM pass)one locked add to a counter shared by all waiting threads
  • Effect on the AMX row: small. On delphi-3bda, the hand-written tp2 rows without the AMX shape moved between −0.3 % and +0.3 % [table in section 5].
  • One of them, llama-3.2-3b, makes about 6 times as many decode steps per second as the AMX row (198 against 32.5 TPS). It moved only +0.3 %, inside its range.
  • So at tp2 the effect of #4534 fits inside the +0.29 TPS residual of the AMX row.

#4205 with #4203: model code compiled in new object files

  • Before #4205, the model code was compiled inside the tron library, in numbered group files (models_0.cpp and so on).
  • Now each model family (llama, mixtral, qwen, …) is compiled as its own object file with a copied set of compile options [src/tron/CMakeLists.txt:300-349 at 5cf65b92]. #4203 adds the generator filter that picks one family per file.
  • I compared the copied option list with the tron library's own list. They match: the same instruction-set flags (-mavx2, -mfma, the AVX-512 set), -O3, TRON_AMX_DISPATCH and the other definitions, and LTO (link-time optimization) on each object [same file, lines 268-298 against 314-331 and 349].
  • The pull request states the same: "Model selection, compile flags, LTO, generated-plugin dependencies, and public runtime behavior remain unchanged."
  • The compiler can still inline and lay out the hot loops differently in a new object file. The size of that effect was not measured: Insufficient data. It is a candidate for part of the +0.29 TPS.

#4456: one position record per pin

  • For every model, each request step now records the token position of each pin and removes it when the pin is released [src/tron/scheduler/full.cpp:193 and 201, h/tron/scheduler/full.hpp:463]. A pin is the scheduler's reference that keeps needed KV history.
  • Each step also calls one memory-pressure check. It returns at once unless the process is in arena mode and over its memory target [src/tron/scheduler/full.cpp:80, token_cache.cpp:123-124 and 159-161].
  • The reclamation itself works only on sliding-window layers. llama-3.1-8b has none.
  • Expected effect: a few vector operations per step, against a decode step of about 31 ms (1 / 32.5 TPS). Negligible (est.).

Two merges that edit files this row compiles, but not code it runs

  • #4258 rewrote the attention join in self_attention.hpp. llama-3.1-8b runs software attention only [rinzler log 09-23 04:05:52: "HW attention disabled for model 'llama-3.1-8b-instruct-good-tp2': default off for this model"]. For software-only layers, the new code merges the worker scratchpads in the same order as before (join_software, then finish_job) [self_attention.hpp:1193, 1234-1252 at 5cf65b92]. The pull request's own control measured 8-user llama-3.1-8b with FPGA attention off as "equivalent" (under 1 %).
  • #4455 changed KV storage for sliding-window layers. Models without them keep direct K/V indexing [h/tron/models/kv_cache.hpp:578-580: "Uniform full-history views preselect their base pointer"]. Its new book checks return early when a book has no sliding-window storage.

Generated models with FPGA attention: faster on both machines

  • On AMD, qwen-3-4b tp4 decode rose +2.5 % and gpt-oss-120b rose +1.2 %. Their TTFT fell −5.7 % and −3.5 %. qwen-3-4b tp2 TTFT fell −5.0 %.
  • No hand-written row clearly moved on AMD.
  • FPGA attention is on for exactly these three rows [rinzler log 09-23: "HW attention enabled for model 'ingested-qwen-3-4b-instruct-2507-tp2'", "…-tp4", "'ingested-gpt-oss-120b-tp4'"]. It is off or not available for every other row.
  • #4258 is the merge that changes FPGA attention. Its pull request measured, on a Genoa machine with 4 cards: TTFT −2.07 % for 8-user gpt-oss-120b at a 2K prompt, and larger gains at longer contexts (TTFT −7.57 % and decode +15.9 % at 32K, 1 user).
  • So #4258 is the likely cause of these gains. On Intel the tp4 rows gained more, as the next part shows.

tp4 rows: faster on Intel only

  • llama-3.3-70b tp4 rose +3.6 % on Intel (31.33 TPS against 30.14 to 30.37), and −0.2 % on AMD.
  • qwen-3-4b tp4 rose +18.4 % on Intel and +2.5 % on AMD. gpt-oss-120b tp4 rose +10.8 % on Intel and +1.2 % on AMD.
  • llama-3.3-70b tp4 is the clearest test. It is hand-written, runs software attention, has 8 query heads per KV head (no AMX shape), and has no sliding window and no experts. Of the 32 merges, only #4534, #4205 and #4456 can change its code.
  • A tp4 engine drives 4 cards instead of 2 [run log: tp4 models provisioned on engines default-0 and default-1, tp2 models on default-0 to default-3]. So one engine process has more waiting threads writing the shared counters. Their number per engine was not read: Insufficient data.
  • This makes #4534 the likely cause (see the hypothesis in section 4). The measurement named there decides it.
  • For gpt-oss-120b, #4531 also changes which card holds each non-expert tensor tile, because this model places its experts by measured load [rinzler log 09-23 05:19:19: "Using ExpertsByPlan placement strategy with device_count=4, n_moe_routers=36"]. Its effect on speed is unknown: Insufficient data.

mixtral-8x7b: slower prefill on Intel only

  • mixtral TTFT rose +2.4 % on Intel (1,293 ms against 1,259 to 1,264 ms) and +0.4 % on AMD. Its decode did not move on either machine.
  • Mixtral has the AMX shape, so on Intel its attention now runs partly on AMX.

  • Hypothesis: a side effect of the AMX path at 1024-token prompts. Measurement that decides it: run the mixtral row with the new package, with and without TRON_AMX_DISABLE=1.

gemma-4-31b: moved in opposite directions

  • gemma-4-31b decode fell −1.8 % on Intel and rose +1.1 % on AMD.
  • It has no FPGA attention [rinzler log 09-23 05:22:53: "HW-attention not available for this model. Will use SW-only path."] and no AMX shape (head size 256).
  • The merges that can change its code are the sliding-window pair (#4455, #4456), the 8 ingest-compiler refactors and the generic ones. None of them explains opposite signs on the two machines: Insufficient data. More nights of the new package would show whether the change persists.
