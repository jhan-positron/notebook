AMX nightly regression, 2026-10-09

Why the monitor emailed "AMX CI/CD perf regressed", how large the change is, and which of the ten tron merges between the two nightly packages could explain it. Written 2026-10-09 by Claude for jhan. All times UTC.

Short version

The email fired on the AMX row's prefill number, 343 tokens per second against the monitor's minimum of 353. The only metric that moved is that test's time to first token, up from 11,517 ms to 11,931 ms (+3.6 %), with decode and every other row inside their normal ranges. Two merges touch this code path (#4366, #4784), but the old package re-measured today was also slow (11,814 ms), so a back-to-back A/B of the two packages on delphi-3bda must decide between code and machine.

Words used here

AMX row
The nightly test "llama-3.1-8b-instruct-good-tp2 @32u per machine (AMX benchmark)": 32 concurrent users, 4,096-token prompts, 1,536 generated tokens, on delphi-3bda (the Intel Xeon 6 CI machine). AMX is Intel Advanced Matrix Extensions, the CPU matrix instructions tron's attention kernel uses for this model shape.
TTFT
Time to first token, in ms: how long a user waits for the first generated token. It covers the queue wait plus the prompt processing (prefill).
prefill≈
The Slack report's prompt-processing rate, computed as prompt length / TTFT (4,096 tokens / TTFT). It is the same measurement as TTFT in another unit.
TPS
Decode rate: generated tokens per second per user, averaged over the run.
nightly, package
The System CI run of positron-ai/systems_test that starts at about 03:45 UTC. It installs that day's tron Debian package, named by date and tron main commit, for example 2026.10.09-26b6df7d.
be0d5565, 26b6df7d
The tron main commits of the 10-08 and 10-09 packages. The ten merges listed below are the commits between them.
the monitor
The 07:00 PDT cron job in ~/workspace/random/amx-ci-monitor/check.py. It reads the Slack line and emails "regressed" when decode TPS < 32.3 or prefill < 353 tok/s.
campaign
One of jhan's own measurement runs on delphi-3bda (exec/pr4424ci-20261009). It drives the nightly's own client code (systems_test at commit 14f0ce4, the same as the 10-09 nightly) from claude-agentsrv against engines started by platformd, exactly as the nightly does.
first-token order
Within one round of 32 simultaneous requests, the position in which a request received its first token (1 = earliest, 32 = last).

The nightly's own thresholds passed (105 % of 31.00 TPS). The email came from the monitor's stricter prefill minimum. The two numbers are one measurement: prefill 343 tok/s is 4,096 tokens divided by a TTFT of 11.93 s.

One side finding about the monitor itself. Its prefill minimum of 353 tok/s equals a TTFT of 11,603 ms. The slowest normal night (10-01) had 11,612 ms, or 352.7 tok/s. It passed only through the Slack line's rounding to 353. The minimum therefore has about 0.1 % of headroom over the observed normal range. A night that is 1 standard deviation slow would also email.

2. Nothing else moved

Decode rates tell the same story. The AMX row's 32.56 TPS is inside its 13-night range (32.40 to 32.78). Three rows ended slightly below their eight-night minimum:

  • ingested-gemma-4-31b-it-tp2 @8u: -0.3 % against its eight-night minimum
  • ingested-qwen-3-4b-instruct-2507-tp2 @8u: -1.1 % against its eight-night minimum
  • llama-3.1-8b-instruct-good-tp2 @8u: -0.4 % against its eight-night minimum
  • llama-3.3-70b-instruct-good-tp2 @8u: -0.1 % against its eight-night minimum

With eight baseline nights, a new value lands outside the range about one time in five by chance. Three such rows out of 14 is therefore not a signal.

The same model's 8-user test with 1,024-token prompts did not move at all: TTFT 660 ms on both nights, 143.37 to 142.56 TPS.

3. Where inside the test the time went

10-08, package be0d556510-09, package 26b6df7d

This shape excludes a uniform slowdown of prompt processing. A uniform 3.6 % would have delayed the first user by about 250 ms as well. Instead, the extra 500 ms appears late in the batch. By then the contexts are long, and the early users are already decoding while the later ones are still being prefilled. Both a code change in the mixed prefill-plus-decode phase and a slower machine during that phase fit this shape.

4. Machine or code?

The campaign method is comparable to the nightly. On 2026-09-20 the same method measured 11,472 to 11,485 ms for an AMX build. The nightlies of the following week measured 11,505 to 11,535 ms. So the method read 20 to 60 ms low then, not 300 ms high. Today it read the old package 297 ms higher than the 10-08 nightly did. Every measurement on this machine after 04:00 UTC on 10-09 lies between 11,794 and 11,931 ms, whatever the package. Every measurement before that lies between 11,470 and 11,612 ms.

That points at the machine, but the evidence is indirect, and the checks below found nothing wrong. All were read on 2026-10-09 between 19:00 and 19:25 UTC while the campaign kept the machine under its normal four-engine load.

#4366, Round BF16 stores to nearest even (candidate 1)

  • Changes every CPU conversion from FP32 to BF16 from truncation to round-to-nearest-even, using the CPU's AVX-512 BF16 instruction. The llama plugin's RMSNorm and residual kernels store BF16 this way, and the V-cache row writes of the AMX attention path go through the changed append_v_row [h/tron/tensor/v_vnni.hpp].
  • The AMX kernel's own conversion of softmax weights already used the rounding instruction and is unchanged [src/tron/kernels/amx_attn.cpp:239].
  • The PR measured itself on an AMD host with 4 prompts of 2,048 tokens: prompt processing −0.25 % for ingested-llama-3.1-8b, within noise. It was not measured at 32 users and 4,096 tokens, and not on the Intel AMX path.
  • The numerics change is visible in the 10-09 nightly: two golden-response functional tests that passed on 10-08 failed on 10-09 (llama-3.1-8b tp4 and qwen-2.5-32b tp4, "response differed from expected"). This shows the change is active in the package. It does not show a speed effect.

#4784, Skip the weight-command lock when TX has nothing to post (candidate 2)

  • In the FPGA worker, the launch step no longer takes the per-card weight-command mutex when the request's weight commands were already posted at prepare time [src/pos/worker.cpp:2182-2232].
  • The PR describes the effect as more weight prefetch when one request is prepared while another is launched on the same card. That is exactly the mixed phase in Figure 3, where the late users' extra 500 ms appears. The PR body reports no measurement.

The other eight

#4719 and #4723 change host-kernel loop helpers that only the generated plugins (ingested-* models) include. #4782 is mixture-of-experts code. #3906, #3907 and #3393 change the ingest compiler. #4801 changes a nix file. #4709 changes rinzler's request path, but every new branch is behind a Qwen check. It stays a low-probability candidate.

6. What decides it

  1. Back-to-back A/B on delphi-3bda. Both packages are already saved on the machine as /var/tmp/jhan/pr4424ci-20261009/nightly.deb (be0d5565) and restore.deb (26b6df7d). Run the two llama-3.1-8b configs (8 users / 1,024 and 32 users / 4,096) in the order new, old, new, old with the campaign driver. One pass is about 15 min, so the four passes take about one hour. If 26b6df7d is about 400 ms slower than be0d5565 in the same hour, the code is the cause. If both read about 11.8 s, the machine changed. The running pr4424ci campaign ends at about 20:30 UTC today. The machine is then free until the nightly hold at 01:40 UTC. It is free again after the 10-10 nightly (about 13:40 UTC), where merge4737-precheck2 is already queued at 13:00 UTC.
  2. If the code is the cause, bisect with two builds of 26b6df7d: one with #4366 reverted, one with #4784 reverted. Each build is one make deb on the machine.
  3. Tomorrow's nightly (10-10) is one more data point. If its AMX-row TTFT is back near 11,550 ms with a package that still contains the ten merges, the 10-09 value was a machine effect.
  4. Monitor threshold. Consider lowering the prefill minimum to 350 tok/s (TTFT 11,703 ms, about 4 standard deviations above the mean), or basing it on TTFT directly. Then a normal night does not email.
