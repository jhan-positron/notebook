Your shape observation is correct. GPT-OSS-120B has 64 elements per attention head and eight query heads per key/value head. It does not pass the AMX attention gate. 3. What actually changes on that ordinary CPU path?

Before commit 1
  1. Prepare one dotter for each query head.
  2. Scan visibility ranges and the sliding window.
  3. For each accepted token, check the key view and score immediately.
After commit 1
  1. Scan the same filters and build the selected-token mask.
  2. If the mask is nonempty, prepare the query dotters and obtain the key view.
  3. Visit selected bits and score the corresponding key rows.

The source changes are concrete: setup moves after selection, a per-accepted-token view-validity check disappears, and selection is separated from dot products. Mask construction and bit iteration add work too. The dot-product kernel is unchanged. [Before, After]

Hypothesis: compiler output may improve. Preparing queries after range selection can shorten the time their prepared values must stay live. That can change register allocation, memory spills, or instruction scheduling. The exact build’s generated instructions and a CPU profile are needed to test this explanation. The source diff alone cannot assign a percentage to it.

Conditional saving: empty visits skip query setup. This applies only when execution reaches the changed block with no selected tokens. Many whole-page rejections already happen in the caller. GPT-OSS’s alternating sliding and full attention layers do not establish how often this particular saving occurs. Count empty visits that reach this block before treating them as the cause. [Earlier page rejection, Nonempty guard, Layer configuration]

Do not assume this is performance-neutral. The row-major staging caller gains a row copy. Packed expression saves now pass through a temporary row, including expressions whose input is already bf16. Whether the compiler removes any added work depends on the build. Neither change was present in the linked benchmark. [Second-commit diff, Conversion and row copying]
Why the AMX fallback remains safe
  1. The caller still excludes unsupported head shapes and query scalar types at compile time.
  2. It still requires the existing packed query pointer and a dense page before attempting this path.
  3. The cache returns false for packed keys before modifying the score array.
  4. The attention wrapper returns false before changing normalization or value accumulators.
  5. The caller returns from the AMX branch only on success. Refusal continues into ordinary scoring.

This is the control-flow contract visible in the code. It is not a new test result. [Caller, Cache attempt, Early refusal before accumulation]

Beginner background: why keys, masks, and scores exist

Self-attention lets a token use information from selected tokens in its sequence. For one query head, the raw score for key k_i is a dot product: multiply corresponding elements, then add the products.

raw_score[i] = q[0] × k_i[0] + q[1] × k_i[1] + …
Compare Q with KProduce a raw score for each selected token.
→
Turn scores into weightsApply the model’s scaling and normalization.
→
Combine VUse those weights to accumulate value vectors.

The code processes cached keys and values a page at a time. It keeps running normalization state between pages. PR 5047 changes the selection and raw-score stage inside one page visit. [Attention equations and page accumulation]

Not every cached token belongs in a particular software visit. The range mask records visibility and hardware/software assignment. A sliding window can also reject old keys. The mask named live records the tokens that survive those existing rules. [Selection loop]

apply_page_tok (the per-page attention function) receives one query token, one KV head, and one KV page. All query heads sharing that KV head are processed together. The caller later consumes its token count and returned range hint. [Caller, Function inputs]

Pass the complete selected-token mask to qk_group. Its masked loads avoid unselected key storage. Its masked stores leave unselected scores untouched. [Reader contract, Implementation]

The packed storage layout and its scoring kernel are already on this PR’s base branch. This PR changes how the surrounding code organizes token selection and reader setup. [Single-commit diff]

Why the scores are intended to stay the same

  • Same selected offsets. The candidate bounds, range checks, and sliding-window comparison are unchanged. Each accepted offset still increments the count once. [Old filters, New filters]
  • Same row-major scoring order. The old scan visits accepted offsets in increasing order. Clearing the lowest set bit produces that same order. The inner query-head loop and dot-product expression are retained. [Old scoring, New scoring]
  • Same packed call. Its key view, query-group pointer, output pointer, and row stride are unchanged. The selected-token count is positive exactly when the constructed mask is nonzero. [Old call, New call]
  • Same score initialization and continuation. Rejected scores start at negative infinity in both versions. The scale/softcap and value-accumulation code after this block is untouched. [Initialization, Continuation]

This is a source-level equivalence argument. It is not a claim that inference outputs were compared in this session.

Four details that are easy to misread

  1. The mask uses a page offset. A page might start at token identifier 100. Its first bit still represents offset 0, not bit 100. The identifier is only used to find the visibility range. [Index use]
  2. The layout choice is compile-time. TRON_K_VNNI is a build option. With it enabled, the layout gate is true for 128-dimension heads. A packed slot has no row-major k() accessor for this geometry. Keeping that call in the discarded else branch is necessary. [Layout gate, Row accessor constraints]
  3. The shared assertion does not enable smaller packed pages. It allows any page capacity that fits in 64 mask bits. The actual page remains 64 tokens. The packed view independently requires exactly 64 tokens and 128 dimensions. [New assertion, Page size, Packed-view assertion]
  4. An early AMX return still precedes this code. Eligible dense row-major pages can finish in the separate matrix-instruction path. This refactor affects visits that reach the software block below it. [Earlier dispatch]
Boundary cases: empty mask, offset 63, and softcapping
  • Empty mask. The outer guard skips both readers. The existing count check returns an empty visit before value processing. [Guards]
  • Offset 63. The 64-bit unsigned literal supports the highest valid page bit. For 1 << 63 interpreted as the actual uint64_t{1} expression, the mask is 0x8000000000000000. Its next selected offset is 63, and clearing that bit produces zero. The plain literal 1 would not provide the required 64-bit type. [Typed shift]
  • Softcapping. Do not generalize the raw −∞ initialization into a claim about every final weight. The unchanged softcap branch applies a hyperbolic tangent before exponentiation. The simple “−∞ becomes zero weight” explanation applies directly to ordinary positive scaling, not automatically to that branch. [Existing transformation]
