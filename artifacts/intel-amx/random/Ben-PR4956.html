Ben's PR 5047 on PR 4956

Generated 2026-10-22 17:36 UTC from the PR 5047 head ade89a9d9c (branch bgamari/vnnik-1) and its base a5697f86d3 (PR 4956 head, branch jhan-vnnik-1-layout). Performance campaign state: ok. Line references name the head unless marked "base".

Short version. PR 5047 is Ben's two-commit rewrite on top of jhan's PR 4956 branch. It moves every decision about how K is stored into the KV cache page (two new scoring methods and a conversion overload of set_k_row) and deletes the page's public raw K views. About half of the 307 lines it removes are older code from main (tron's trunk branch) rather than PR 4956 code, its GitHub build check fails on one test line it did not convert, and the throughput measurement on 3bda (the Intel test server delphi-3bda) shows (final, 4 of 4 repetitions) no degradation beyond the band in any of the 10 pairs over 6 cells, with 1 pair inside the band by the 0.4 TPS floor only. The diagnostic kill-switch cell (every K token through the software loop) is beyond the band: prefill +2.9 % (+2.25 s), decode +0.3 %.

the option
The CMake option TRON_K_VNNI that PR 4956 adds. OFF (the default in every preset): K rows of 128-dimension heads are stored one row per token (row-major). ON: they are stored in the VNNI layout (VNNI = Vector Neural Network Instructions, Intel's name for the layout that interleaves pairs of rows), the format the AMX tile multiply takes as its right operand.
K, V, KV cache, page, slot, plane
K and V are the key and value vectors saved per token for attention. The KV cache holds them in pages of 64 tokens. A slot is one K/V storage region, usually one per layer. A plane is the K or the V storage of one page and one KV head. A KV head is one key/value head, shared by several query heads. For K, a plane is 64 tokens × 128 dimensions × 2 bytes = 16 KiB.
row, row view
One token's 128 K values in dimension order. set_k_row and get_k_row move one row into or out of the cache in whatever layout the slot uses.
AMX, AVX-512
Intel instruction sets. AMX multiplies 16-row tiles. AVX-512 handles 16 floats per instruction. Both are CPU paths, as opposed to the FPGA (field-programmable gate array, the accelerator card).
the dotter
The AVX-512 routine that scores one query head against one row-major K row (one dot product). The "dotter loop" scores a page token by token.
the reader
k_vnni::qk_group, PR 4956's AVX-512 routine that scores a query group (the query heads that share one KV head) against one VNNI page, one token per vector lane.
the dense-page kernel
amx_attn_h128g4::qk_rowmajor_128x4, main's AMX kernel for a full 64-token page of row-major K. The gate that chooses it is the "AMX dispatch gate".
live mask
A 64-bit integer with one bit per token of a page. A set bit means the token takes part in this query's attention.
FPGA staging
gof::populate copies K and V rows into a buffer the FPGA reads. It gets each row through two callbacks the scheduler builds, k_head_fn and v_head_fn.
cell, arm
A cell is one model-and-shape configuration of the 3bda test, for example llama-3.1-8b with 8 users at prompt 1024. An arm is one of the binaries run inside a cell.
base, head, basev, headv
The four runtron binaries of the 3bda test. base = PR 4956 head with the option OFF. head = PR 5047 head with the option OFF. basev and headv = the same two commits with the option ON.
TPS, prefill time, band
TPS = decode tokens per second per user. Prefill time = the slowest user's prompt-processing time in seconds. The band is the decision threshold: twice the larger of the two arms' standard deviations, never below 0.4 TPS or 0.15 s.
forward timer
With TRON_ATTN_STATS=1 runtron reads the CPU cycle counter before and after every forward pass and sums the cycles per class (prefill forwards, decode forwards) into its exit report. It is a second clock, independent of the per-request timings runtron prints.
kill switch
TRON_AMX_DISABLE=1, the run-time switch that keeps the AMX kernels from running.
Build Tron
The GitHub check that compiles tron and its tests with the option ON (.github/workflows/cmake-single-platform.yml lines 353-356).

Are all of Ben's changes about PR 4956's code?

No. Every removed line of the diff was attributed with git blame at the PR 4956 head. 155 of the 307 removed lines were last written by PR 4956. The other 152 lines were in main before PR 4956, some since 2024. Level 2

What the refactor does, in one picture

At the PR 4956 head, four files test the layout gate k_vnni::layout_on<head_size> with if constexpr and choose different code for row-major and VNNI K. After PR 5047 only kv_cache.hpp tests it. The callers ask the page to score, store or load, and the page picks the layout-specific code. The counts below are grep -c layout_on per file (comments included).

  • Still outside the page: the AMX query pack, is_dense_amx_page (head 1710), the softmax step and the PV kernel (the multiply of the softmax weights by V).
  • Still a raw row inside the cache: kv_block::k_view and k_at (head 2589-2607), which the four page methods use for row-major slots.
  • The arrow from the scheduler is the one whose work changes for the production (row-major) build. It used to return a pointer into the page and now copies the row.
Level 3

Commit 1: select the tokens first, then score them

This commit changes only the scoring loop of apply_page_tok, the function that scores one query against one 64-token page on the CPU path. At the PR 4956 head the loop did two jobs at once. It decided which tokens take part (visibility ranges, the sliding window) and, for row-major K, it scored each selected token inside the same loop. For VNNI K it only set a bit in a mask and scored after the loop. The two layouts therefore had two different control flows in one function, selected by if constexpr in three places (base self_attention.hpp:1917, 1929, 1953).

What this commit does not change: the per-token checks (visibility range, window), the counter relevant_k_tokens, the kernel used for VNNI K, and the dot products themselves. The one small behaviour change: the dotter array and the row view are now built only when at least one token is live. The base built the dotter array before the loop even when nothing was live (base 1915-1924 versus head kv_cache.hpp:1993-1998).

The three new page operations

// head h/tron/models/kv_cache.hpp:1978  (abridged)
template <attention_geometry geometry, typename Q>
void score_k(kv_slot_id slot, size_t kv_head, const Q& q, uint64_t live, float* scores, size_t stride) const noexcept {
  if (live == 0) return;                                   // no storage access for an empty selection
  if constexpr (k_vnni::layout_on<dims>) {
    k_vnni::qk_group<kv_mul>(block.k.as_view(), q.data + kv_head * kv_mul * dims, live, scores, stride);
  } else {
    auto dot_q = ... std::array{ dotter<scalar_t, dims>(slice<dims>()(q, (kv_head * kv_mul + I) * dims))... };
    const auto keys = block.k_view();
    for (uint64_t remaining = live; remaining != 0; remaining &= remaining - 1) {
      const size_t i = std::countr_zero(remaining);
      for (size_t h = 0; h < kv_mul; ++h) scores[h * stride + i] = dot_q[h](keys[i]);
    }
  }
}

// head 2015: AMX only for a layout that has an AMX reader
template <kv_geometry geometry>
bool try_score_k_amx(kv_slot_id slot, size_t kv_head, const bf16* q_packed, float* scores, size_t stride) const noexcept {
  if constexpr (k_vnni::layout_on<geometry.head_size>) return false;
  else { amx_attn_h128g4::qk_rowmajor_128x4(kv_block<geometry>(slot, kv_head).k_view(), q_packed, scores, stride); return true; }
}

// head 2052: store an activation row of any scalar type
template <kv_geometry geometry, typename X>
void set_k_row(kv_slot_id slot, size_t kv_head, size_t i_page, const expr<X, geometry.head_size>& row) noexcept {
  if constexpr (k_vnni::layout_on<geometry.head_size>) {
    alignas(64) bf16 converted[geometry.head_size];
    k_destination_row<geometry.head_size>(converted).set(row);     // convert (or copy) to bf16 first
    set_k_row<geometry>(slot, kv_head, i_page, k_source_row<geometry.head_size>(converted));
  } else {
    kv_block<geometry>(slot, kv_head).k_at(i_page).set(row);
  }
}

The tests

With page::k gone, every test that wrote or read one K element through it needed another way.

  • Ben adds t/kv_cache_helpers.hpp with two helpers. test::set_k_tag writes a whole row whose first element is the tag and the other 127 elements are zero. test::k_tag reads the row back and returns the first element.
  • 24 call sites in two test files switch to them.
  • The test that checked view identity and lazy views ("page K views preserve geometry and row addressing") becomes a store-and-load round trip of elements 0 and 127 ("page K rows ...").
  • Two #ifdef TRON_K_VNNI branches in t_llama_unit.cpp disappear. Both layouts now expose the same operations, and the test no longer needs to tell them apart.
Level 5

What problems Ben addresses, and what the change costs

The problems, in his words and in the code

"a bit spaghetti": two control flows mixed in one loop.
The base scoring loop needed placeholder lambdas returning 0, [[maybe_unused]] variables and three if constexpr tests to keep the row-major and the VNNI flow in one function (base self_attention.hpp:1909-1971). Commit 1 removes all of that.
Layout knowledge spread over four files.
The attention code, the model's save path and the scheduler's FPGA staging each tested layout_on and read or wrote page storage through a layout-specific accessor. After the change they call score_k, try_score_k_amx, set_k_row and get_k_row, and only kv_cache.hpp tests the gate (level 2).
Raw storage views as public API.
page::k() gave any caller a writable row view of the plane, including tests that wrote single elements through k(...)[0]. The commit message names this: "remove the public raw K views". The replacement is row transfer and scoring operations only (head kv_cache.hpp:738-739).
The AMX path coupled to the storage layout at compile time.
The base excluded the whole AMX branch for VNNI slots with && !layout_on in the dispatch gate. Ben turns this into a question the page answers: "do you have an AMX reader for your layout?" (try_score_k_amx returns false). When PR 4957 adds the VNNI AMX kernel, only that function changes.

Level 6

The GitHub benchmark comment, and what it does not show

The bot comment on PR 5047 ("Benchmark of commit 251529f", 16:05 UTC) reports gpt-oss-120b tp4 generation throughput +7.18 % and llama rows within ±0.5 %. Three facts limit what this can mean.

  • Commit 251529f is "Merge e17a12ff09 into a5697f86d3": the first commit only, merged onto the PR 4956 head. The second commit (the page API) was pushed after the benchmark ran.
  • The comparison is "vs Golden baseline (nightly, multi-repeat)", that is main's nightly numbers, not PR 5047's base. The +7.18 % therefore contains PR 4956 and whatever else separates the branch from those nightly commits. It is not a measurement of PR 5047.
  • The machine class is "2 x 96core (andoria-09)", an AMD host. It has no AMX. The dense-page kernel path that commits 1 and 2 touch on Intel therefore does not run there.

gpt-oss-120b has 64-dimension heads. The option never applies to it, and neither does the dense AMX path. On that model, commit 1 changes only the dotter loop's control flow. A +7 % generation gain from that alone is not plausible, and the comparison above explains the number without it. One row of the same table points the other way: ingested-llama-3.1-8b tp2 parse throughput -0.42 %, marked "regression (3/3)". On an AMD host every page goes through the loop commit 1 restructured, so that row is a weak hint about the dotter path. It is as unclean as the gpt-oss row, for the same three reasons.
