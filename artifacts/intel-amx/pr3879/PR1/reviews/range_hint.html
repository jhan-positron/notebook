Short version

range_hint is a bookmark, not a decision. It is a pointer to the entry of the ranged mask (the per-pass table that says which query tokens may see which stored tokens) where the last lookup landed, so that the next lookup is one comparison instead of a binary search. Every lookup still checks the token against the range it returns, so a stale bookmark costs time and never changes a result. The AMX path takes a page only when the whole 64-token page lies inside the range the bookmark already points at [is_dense_amx_page, 1449], so there is no boundary to move the bookmark past. It hands the bookmark back unchanged [1597], which is exactly what the AVX loop hands back for such a page, because that loop moves the bookmark only when an entry reaches the range's end [1623]. Eighteen independent verifier passes over the six claims behind this argument found no counterexample (section 4.2). A page with a boundary inside it goes to the AVX loop as before. How often that happens was measured once, on the mirror arm of the measurement branch (qwen-3-4b, one user, FPGA attention off, 2026-09-01): 60.0 / 9.1 / 2.3% of prefill page visits at prompt 256 / 2048 / 8192 tokens, and 0% of decode page visits. So no extra range_hint handling is needed in the AMX path, and there is nothing it could slow down.

2. What range_hint is

2.1 The ranged mask: the source of truth for visibility

Every forward pass, the scheduler walks the token tree and builds one ranged mask for the pass (compute_forward_args, h/tron/scheduler/full.hpp, calling build_edge_ranges at line 2790). The mask answers one question for any stored token and any query: may this query attend to this token? The old design answered it with a per-page upper bound; the ranged mask replaced that so that visibility no longer depends on page boundaries and so that a hardware (FPGA) attention path can take over sub-ranges [doc/hw-kv-attn-work.md, Appendix B].

A boundary between two ranges appears where the set of queries that may see the tokens changes. build_edge_ranges (src/tron/models/ranged_mask.cpp:13-97) walks the events of an edge from the highest token down. At each query token it closes the range above that token, adds the query's bit to the SW mask, and opens the next range at the query itself. So token k is visible to every query at or after k; that is the causal rule. A hardware-offload event moves the accumulated SW bits to the HW mask. finalize_ranges (ranged_mask.cpp:99-158) then fills any gaps with zero-mask ranges and merges neighbours with identical masks, so the final list is sorted, non-overlapping and gap-free. find_range asserts on a gap (ranged_mask.hpp:254).

The consequence that matters for this page: stored tokens that carry no query in this pass share one range, because nothing changes the mask between them. Query tokens split the ranges: in a prefill pass every prompt token being processed is a query, so the pages that hold the pass's own tokens contain a boundary at every token.

Two further sources of boundaries exist. First, when FPGA attention is on, hardware-offload events add boundaries during construction, and after finalize_ranges the scheduler may still split a range at the edge of a hardware plan entry and move query bits from the HW mask to the SW mask (split_range_at and the loop after it, full.hpp:1791-1826). The counter runs in section 4.3 had FPGA attention off, so they do not measure these. Second, in a token tree only the first child of a node may continue its parent's KV page (full.hpp:2670-2680; a second child sharing the parent's book is rejected, token_tree.hpp:509-518), so one page can hold a parent's last tokens and its first child's first tokens; where a sibling's query may not see the child's tokens, a boundary falls inside that page. Every page with a boundary inside it fails the dense predicate and runs on the dotter, whatever put the boundary there.

A caution on the documentation: doc/hw-kv-ranged-mask.md describes the masks with 128-bit examples and says the shard stacks are "always empty today"; the code has a capacity of 4096 queries (ranged_mask.hpp:20) and pushes shard events when FPGA attention is on. The code is authoritative where the two differ.

2.2 The hint: a bookmark for the sequential walk

The attention worker visits pages in order and, inside a page, entries in order. Looking up the range of every entry by binary search would cost O(log n) per entry. find_range(tok, hint) [ranged_mask.hpp:240-264] avoids that: if tok is inside the hinted range it returns the hint at once; if not, it steps forward through at most 4 neighbouring ranges (asserting there is no gap between them); only then does it fall back to the binary search. The hint is therefore never trusted blindly: every lookup verifies the token against the range it returns. A wrong or stale hint can cost time; it cannot return a wrong range.

The loop keeps the bookmark in two variables. In apply_page_range, page_end_hint is initialised once from the first page's first token [1298-1299], and for each page page_begin_hint is looked up from the page's first token with page_end_hint as the hint [1347-1348]. That range decides at page level whether the query sees the page at all [1356]. apply_page_tok receives page_begin_hint as range_hint, walks the page, and returns the range it ended in; the caller stores it as the next page_end_hint [1384-1386].

History: Bill Baumann introduced the ranged mask in February 2026 (a22374a3cc, 2026-02-02, first pass; 34f7e4d484, 2026-02-23, first cut in core attention) and added the hint in the commit "Fix page range hints logic to be O(1) during attention page walk" (05b78a0b7e, 2026-03-13). The 2026-02-23 commit looked the range up once per page from the page's first token and passed it into apply_page_tok; the next day's commit (3fcd809e87) carried that page-level hint from page to page. On 2026-03-11 (6c2850a466) find_range(tok, hint) got its 4-step forward walk, the no-gap assertion and the binary-search fallback, with a unit test for the fallback. Before the 2026-03-13 fix, apply_page_tok advanced a local copy of the hint while walking a page and discarded it on return, so the next page's lookup started from the previous page's first range and fell back to a binary search whenever that page had held more than 4 boundaries; the fix made apply_page_tok return the pair {count, final hint} and the caller keep it as page_end_hint, which is the shape PR1 inherits. All of it reached main through PR #2106 (2026-03-31).

3. Why it matters, and what Ben asked

The ranged mask has a correctness role and the hint has a performance role, and it helps to keep them apart.

  • Correctness. The mask is the only visibility source for CPU attention (doc/hw-kv-ranged-mask.md, "Current State"). If a path used the wrong range for a token, a query could attend to a token it must not see (a later token, or another user's branch), or skip a token it must see. Both change the model's output.
  • Performance. The hint keeps the per-entry cost at one comparison against tok_hi inside a range [doc/hw-kv-attn-work.md, "The inner loop"]. If a path returned a poor hint, later lookups would take the 4-step walk or the binary search more often. The output would be unchanged.

Put differently: the AMX path does not "skip" the hint logic. The hint logic is a loop that moves the bookmark when the walk crosses a boundary. The AMX path is entered only for pages that contain no boundary, where that loop would do nothing to the bookmark. Ben's suspicion in the call ("it doesn't update it, it just passes it because it needs the range") is right on both counts: the predicate needs the range to test tok_hi, and there is nothing to update.

Independent checks. Each claim above was handed to three verifier agents told to refute it, one per lens: unusual inputs (shared prefixes, branches, stale entries, EAGLE, zero-mask gap ranges, the SW/HW split, sliding windows, a query at offset 63, an exhausted hint walk), literal re-derivation from the code at both commits, and a plain skeptic. None found a counterexample. Separately, three agents read the diff without seeing these claims; one traced ten tree shapes through a small model of the walk and found no (query, page) pair where the two paths differ in the K rows used, the count returned, or the hint returned; another confirmed with diff that the dotter loop at 1620-1642 is byte-identical to main's. Their 14 findings concern comments, missing tests and the timing of the Q pack, none the hint's correctness (section 5).

4.3 (H2) Can it slow the walk ("pessimizing")? No; and what a boundary does cost, measured.

The AMX path adds no find_range call [1592-1597]. The predicate is five comparisons on values the prologue already computed. By C2 the next page's lookup [1347-1348] starts from the same hint either way, so the number of 4-step walks and binary searches in the hint mechanism is unchanged. Three verifiers confirmed these code facts; one objected to an earlier wording that called the measured shares below "PR1 measurements", and the text now says how they carry over.

What a range boundary does cost is a different thing: a page with a boundary inside it is not dense, so it runs on the dotter, exactly as it does today without AMX. How often that happens was measured with a counter build that is not part of PR1: branch jhan-amx-fence, commit 3cd2670df1, counts every (page, KV head) visit of an AMX-eligible attention operation by the first gate condition that failed, in the order the gate tests them. The run: qwen-3-4b tp2 with attention on the CPU (USE_HW_ATTN=0, so no FPGA attention and no hardware-offload boundaries), 1 user, 256 generated tokens, mirror arm, two repetitions per prompt length, 2026-09-01; the repetitions agree to the digit because the causes are structural. The fence gate tests the same five conditions as is_dense_amx_page, written inline rather than as a helper, and the mirror arm has one extra condition (the mirror plane present) that never failed. The shares carry over to PR1 by reasoning, not by measurement: the range structure, the batching and the five conditions are outside PR1's diff. In these runs no visit failed the visibility test, so "range_cut" here equals "a boundary inside a full, visible page".

The counts match the construction rule of section 2.1. Assume each prefill pass carries 128 query tokens (two pages). In a pass whose queries sit on pages 2c and 2c+1, the 2c earlier pages hold no query and are one range, so every query takes them on AMX; the two query pages hold a boundary at every token, so every visit to them is range_cut. Summing over the passes of a 256-token prompt gives 256 AMX and 384 range_cut visits per (layer, KV head); times 36 layers and 8 KV heads that is 73,728 and 110,592, the measured values. The same sum for prompt 2048 (16 passes) and 8192 (64 passes) gives 8,847,360 and 148,635,648 AMX visits, again the measured values. In decode the only query is the newest token, in the tail page, so no boundary falls inside a full page; the 72,576 partial-page visits are the tail page in 252 of the 255 decode passes (the three passes that land on a page boundary have a full tail page), times 36 layers and 8 KV heads. Where the 128-token pass size comes from was not traced in the scheduler (Insufficient data: the qwen plugin's own limit is 1024 query tokens per minibatch, gen/src/tron/h/tron/plugins/qwen_3_4b_instruct_2507.hpp:48). The chunk size itself was seen before: the token-30 campaign of 2026-08-30 found the first AMX-induced per-layer difference at query token 128, "the first query seeing complete READY pages; pages filled in the same 128-token prefill chunk are not dense-dispatched" (memory note token30-campaign). Decode was measured with one user only; with several users or shared prefixes a boundary can lie inside a page shared by a parent's tail and its first child (section 2.1), and such a page takes the dotter; no per-cause count exists for that case.

So the answer to "pessimizing" has two parts. The hint mechanism runs exactly as before. The dotter still serves every page that has a boundary inside it, which today means the diagonal pages of prefill; that is a limit of what the AMX kernel accepts, not a cost the hint adds. Serving those pages with a masked AMX kernel is a possible future project and is outside PR1.

4.4 (H3) Is the hint "your problem" (the time-to-first-token regression)? No.

The TTFT regression discussed in the call belongs to the mirror arm, as Ben himself noted (section 3). The run-to-run spread of TTFT is 0.2% (the qwen "off" arm was run twice: 1777 and 1781 ms, same table), so the qwen and llama differences are real and the mixtral ones are not. The two arms were two binaries built from 60d66d9c04, differing only in the K-mirror build option. In that file the dense-page test was one inline expression (lines 1568-1571; it is the expression that later became is_dense_amx_page), and every hint line sits outside the mirror #ifdef: the boundary branch of the dotter at 1602-1611 and the AMX returns at 1680 (canonical) and 1715 both hand back the incoming hint. The mirror build had one extra runtime condition, "mirror plane present", which falls through to the dotter when a book has no mirror arena; the round-1 server logs show the arena present in both regressed cells ("137.93 GB DMA + 68.96 GB K mirror"), so both arms took the AMX path for the same (query, page) pairs and ran the same hint logic. A hint effect would therefore show equally in the canonical arm, whose TTFT is faster than AMX off. The hint is not the mirror arm's problem; the open hypothesis there is the write-through of K into the mirror arena during prefill (round-1 notes, 20:15 and 21:10 UTC). This argument excludes the hint as the cause of the difference between the arms; that the hint costs nothing in absolute terms follows from C2 and section 4.3, not from this table.

Verification note: an earlier draft of this section said the two arms ran "identical dispatch code (the same is_dense_amx_page)" and gave the percentages for all models. Two of three verifiers refuted that wording (the helper did not exist at 60d66d9c04; the mirror build has the extra plane check and a different Q packer; the percentages hold for qwen and llama only). The conclusion survived with the corrected premises above.

4.5 What the tests and CI already cover, and what they do not

  • t/t_amx_dispatch_dtype.cpp drives the production apply_page_range with a one-range mask over one page and checks kernel call counts: a full 64-token page gives one QK and one PV call; a 63-token page gives none (partial_page); float and fp16 executors never reach the packer.

5. What this audit did not establish, and side observations

  • Not established: where the 128-query-per-pass prefill split comes from (section 4.3). It affects only the reconciliation of the counter totals, not the safety argument.
  • Not measured: the fallback shares on the canonical arm itself (the counters live on the fence branch and were run on the mirror arm only); the shares with FPGA attention on, where hardware-offload boundaries exist (Insufficient data; a counter run with USE_HW_ATTN unset on an FPGA host would give them); decode with several users or shared prefixes, per cause.
  • Pre-existing, unchanged by PR1: when every query of the minibatch skips a page at the page level (not visible, 1356; whole page outside the window, 1360-1361), page_end_hint is not advanced for that page, so the next page's lookup may need the 4-step walk or the binary search. Main has the same lines (main 1310 and following).
  • Pre-existing pessimization, unchanged by PR1: the EAGLE first-token exception sets begin = 1 on one page per sequence, which keeps that page off the AMX path; it runs on the dotter as before. Whether any EAGLE draft model has the AMX shape was not checked.
  • Side observations from the fresh-eyes readers (not about the hint): the Q group of a token is packed at its first page that passes the page-level checks, before the dense predicate, so a token pays one 4 KiB pack per (token, KV head, call) even when all of its pages go to the dotter, and on hardware-offload layers a token visible only through the HW mask is packed and then rejected by the predicate. Performance only, bounded by one pack per token per call. Comment wording: the dense-predicate comment says "visible" where the code tests sw_required on hardware-offload layers; the pack-timing comment at 1302-1305 lists two of the three outer checks (the EAGLE one-token skip is missing); the AMX return at 1597 has no comment saying why the unchanged hint is exact (Ben: "there is no comment explaining what this does"). Section 6 proposes that comment.
  • Stale documentation: doc/hw-kv-ranged-mask.md says the shard stacks are always empty and uses 128-bit mask examples; the code pushes shard events when FPGA attention is on and has capacity 4096 (section 2.1). Not PR1's doing; worth a docs fix.

6. Suggested reply to Ben

range_hint is the cached pointer into the ranged mask that apply_page_tok uses so that crossing a range boundary inside a page costs an O(1) lookup instead of a binary search. The AMX path never crosses a boundary: is_dense_amx_page admits a page only when its last token is still below the hinted range's tok_hi, so the whole page sits inside the range the caller already looked up. For such a page the dotter loop would never advance the hint either (it advances only when an entry reaches tok_hi), so returning the hint unchanged is the same value the dotter returns, and the caller's page_end_hint sequence is identical with AMX on or off. Pages with a boundary inside them run on the dotter as before; the per-cause counters (2026-09-01) put that at 60 / 9.1 / 2.3% of prefill page visits at prompt 256 / 2048 / 8192 and 0% in decode. So no range_hint update is needed in the AMX path, and there is nothing it could pessimize. I can add a host test that puts a boundary inside a full page and asserts no kernel call, if you want that pinned.

And, since Ben noted that no comment explains the hint, the following comment now sits above the AMX return (commit 524c510609, lines 1606-1610 at that head) and answers the question in the code itself:

// The hint is returned unchanged: is_dense_amx_page proved that the page's last
// token is below range_hint->tok_hi, so the dotter's advance (kv_idx >= tok_hi
// below) could not have fired for this page either.
return {int(page::page_size), range_hint};
