You were right, and our comment gave a scope reason ("this PR does not touch attn_accum") dressed up as a technical one; sorry for the confusion. The pack is per-worker, per-token scratch for one `apply_page_range` call, which is exactly attn_accum's index space, and nothing in the join or the hardware path depends on it.

It is now a member of attn_accum: `std::vector<amx_qpack_slot> amx_qpack;`, indexed by batch_job_ix like the other arrays, sized on first use with `resize(items.size())` (same allocation pattern as before, no thread_local left): 752e9f571a. t_amx_numerics, t_amx_dispatch_dtype and t_llama_unit pass on the 6962P with the dispatch on, and t_llama_unit with it off.

We kept it a vector rather than a `std::array<amx_qpack_slot, max_minibatch_size>` because the array adds 512 KiB (llama plugin) or 4 MiB (ingested plugins) to every attn_accum instance, i.e. all 55 pool-worker scratchpads per model state plus both copies in every hw_attn_results, for eligible and non-eligible models alike (27.5 MiB or 220 MiB per model state on the 6962P with `--instance 1,2`), while the vector stays at 24 bytes wherever the AMX path never runs. If you would rather have the array anyway, that variant also builds and passes the same tests (250ff8204d on the prototype branch); say so and we will take it instead.
