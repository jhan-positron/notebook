amx_qpack: thread_local or attn_accum?

Investigation of Ben's review thread on PR #3879 (r3936949728, 2026-09-04, and r3973410716, 2026-09-09) and of the AMX walkthrough meeting of 2026-09-09 (transcript). Code: h/tron/models/self_attention.hpp at the PR 1 head 26a0338c3b. Written 2026-09-10.

Short version

Ben is right: the packed-Q buffer can live in attn_accum, and the reason we gave for keeping it out ("a pack is per (token, kv_head) and this PR keeps attn_accum's ownership unchanged") was a scope choice, not a technical obstacle. We moved the buffer into attn_accum in two prototype builds, once as a lazily sized std::vector member and once as Ben's std::array<amx_qpack_slot, max_minibatch_size>; both build and pass the three attention test binaries on the AMX machine. We recommend the std::vector member: it keeps today's allocation pattern (one growth per worker to the largest minibatch it has seen) and costs 24 bytes in every scratchpad that never runs the AMX path, whereas the array costs 512 KiB (llama plugin) or 4 MiB (ingested plugins) in each of the 55 scratchpads of a model state and in both copies of every hardware-attention scratchpad, used or not.

Decision (jhan, 2026-09-10): option B. It is committed on the PR 1 branch as 752e9f571a (local, not pushed), with jhan's shorter member comment; the same three test binaries pass on that exact commit, with the dispatch flag on and off. Left to do: push the branch, post the reply in section 8, and edit row 3 of the thread-map comment.

1. Words used here

tron, PR 1
tron is the inference program under review. PR #3879 is now "PR 1" of the split: the AMX attention kernels and their dispatch, without the K mirror (the second copy of K, which is PR 2).
AMX, the AMX path
AMX is Intel's Advanced Matrix Extensions, tile-matrix instructions on the Xeon 6. The AMX path replaces the AVX-512 dot-product loop (the "dotter") for dense 64-token pages when the head size is 128 and there are 4 query heads per KV head.
KV head, kv_head, kv_mul
A KV head is one key/value head of the attention layer. kv_mul is the number of query heads that share it: 4 for llama-3.1-8b and Qwen3-4B, 8 for llama-70b and gpt-oss-120b, 3 for llama-3.2-3b.
page
64 consecutive tokens of K and V in the KV cache.
minibatch, batch_job_ix, max_minibatch_size
The tokens one forward pass processes together. batch_job_ix is a token's position in that minibatch. max_minibatch_size is the compile-time upper bound: 128 in the handwritten llama plugin (llama.hpp:184), 1024 in the mock plugin and every ingested plugin (mock.hpp:98, TronCpp.hs:264).
pool worker, attention worker, main helper
The app thread pool has num_workers long-lived threads (55 under --instance 1,2 on the 6962P: 56 CPU ids minus one). The last n_attn_workers of them run attention; the first n_main_helpers are "main helpers" that never touch attention (llama.hpp:595, model.hpp Note [Attention workers are the last pool workers]).
attn_accum, scratchpad, attn[w]
The per-worker struct that holds the running softmax state of every token of the minibatch (self_attention.hpp:280). attn is a vector with one attn_accum per pool worker, indexed by attention-worker index; the code calls the index "scratchpad".
v*, s*, m*, valid
The running state of the deferred softmax: the weighted sum of V, the softmax denominator, the largest score seen, and a flag per (token, kv_head) saying whether a state exists yet.
section, plan, join
A kv_section is one kv_head plus a range of pages, assigned to one worker. A worker's plan is its list of sections for a layer. After the sections, join_page_ranges combines the workers' states into one.
Q pack, packed Q, amx_qpack_slot, amx_qpack
The AMX QK kernel cannot read a token's 4 query heads (4 x 128 bf16 = 1024 bytes) as stored; they must be copied into the tile-operand layout the kernel expects, padded to 16 columns with zeros: 4096 bytes per token. That copy is the "pack"; amx_qpack_slot is the 4096-byte type; amx_qpack is the buffer of one slot per token of the minibatch.
thread_local, TLS
A C++ variable with one copy per OS thread (thread-local storage), created at the thread's first use and destroyed when the thread exits.
hw_attn_results
The scratchpad of one hardware-attention (FPGA) pass. It contains two attn_accum copies (data, unpack_tmp). The deque of them is empty for models that run attention on the CPU only.
bf16
The 2-byte bfloat16 floating-point format.

2.3 The point in plain words

  • The shape of the data is "per worker, one slot per token of the minibatch". That is exactly the shape of every array in attn_accum. Ben's proposal is a fifth array: std::array<amx_qpack_slot, max_minibatch_size> amx_qpack; inside attn_accum.
  • The buffer is declared at the wrong level. It is a thread-level variable, but the code that fills and reads it is the per-worker loop over tokens and pages inside apply_page_range. The per-worker scratchpad is the natural home for per-worker loop state. (This is how jhan summarised Ben's point after the meeting.)
  • thread_local is a second mechanism for the same thing. Every thread of the process gets a copy of the variable, not only the attention workers; access to a thread_local costs more than a plain member; and the code base already has one place for per-worker attention scratch.
  • Our written reason did not explain anything. "A pack is per (token, kv_head)" is also true of attn_accum's own valid array. "This PR keeps attn_accum's ownership unchanged" is not a property of the data.
  • The ask: either move the buffer into attn_accum, or write down the real reason it cannot move.

4. What attn_accum is

  • One struct per pool worker. The state constructor runs attn.resize(app_pool().num_workers()) once (self_attention.hpp:472). With --instance 1,2 on the 6962P that is 55 instances per model state (resource-map.yaml gives 56 CPU ids, threading.hpp:869 subtracts one). Only the first n_attn_workers are used by software attention; the main-helper slots are allocated and never touched.
  • Two more copies per hardware-attention pass. Each hw_attn_results holds attn_accum data and attn_accum unpack_tmp (self_attention.hpp:392, 399). The deque grows to the largest pass count of any minibatch plan and never shrinks; it stays empty for CPU-only attention, which is the case for our AMX runs.
  • Four arrays, all indexed by the token's position in the minibatch. They are the deferred-softmax state that must survive across pages and sections and be read by another worker's join. Every per-page intermediate of the attention loop (scores, PV output, correction factors) is a stack local; nothing else lives in attn_accum (claim C9).
  • Its bulk is already out-of-line memory behind handles. On the bf16 executors v_stars[tok] is a btensor, which is a 16-byte handle (dmatensor.hpp:176) to a separately allocated, zero-filled 8192-byte block from the DMA pool (make_unique_dma, system/memory.hpp:213-226; pos_heap power-of-two classes). The blocks are allocated eagerly, one per token slot, when the struct is constructed: attn.resize(55) performs 55 x 128 = 7,040 such allocations for the llama plugin. So "attn_accum owns one out-of-line block per token" is already the design, and a per-worker std::vector member is one more such block, allocated later and on the worker.
  • Who touches attn[w]. Worker w writes it inside apply_page_range. Other workers read the rows of a finished kv_head in run_joins as soon as the atomic counter sections_left[kv_head] reaches zero, while w may still be writing rows of another kv_head, and they write into attn[0], the join target, in the same way (disjoint sub-objects, no data race; self_attention.hpp:1060-1071, 1094-1095). A pack member would be outside all of that: only worker w writes or reads it, and the join never touches it. Worker n_attn_workers-1 clears validity on every instance between barrier phases (free_scratchpads, :757-761). Pool workers are long-lived threads with their own queues and no work stealing, and all forward passes run serially on one work-queue thread, so within a forward pass one OS thread owns one attention-worker index. Between passes the mapping can shift: recommend_n_main_helpers recomputes the helper/attention split every pass when pay_for_determinism is off and there is more than one minibatch (model.hpp:2043-2087), and attention worker i runs on pool thread n_main_helpers + i. Two consequences: today's thread_local buffers can end up on any pool thread over a long run, and attn[i] is written by different threads in different passes, exactly as v_stars already is (claim C1, refuter correction). For ingested plugins the validity reset runs on the main thread (prepare_attention_job), between barrier phases, never during a section.

The in-code comment "each element is ~1MB" on the hw_attn deque undercounts: two attn_accum copies own 2.07 MiB (llama) or 16.5 MiB (ingested).

5. What amx_qpack is and how the loop uses it

  • One 4096-byte slot per token of the minibatch. The packer copies the token's 4 query heads for the call's kv_head into the tile layout and writes only columns 0..3 of each 16-column panel; columns 4..15 must already be zero and are never written (amx_attn_iface.hpp:176-185, amx_attn.cpp:102-116). Today resize() zero-fills new slots, which satisfies that contract.
  • Packed at most once per (token, call). packed_amx_query packs when the call-local bitset amx_packed has the token's bit clear, at the token's first page that passes the visibility and window checks (self_attention.hpp:1417-1432). The test t_amx_dispatch_dtype pins this to exactly one pack per token per call.
  • Read only inside the same call. The single reader is the QK kernel, reached through apply_page_tok and apply_dense_amx_page for each dense page (:1487-1488). Nothing outside apply_page_range names the buffer; the join never sees it (claim C4).
  • Re-packed every call by design. A call handles one kv_head, and the packed bytes depend on the kv_head, so the next section must pack again; a worker's consecutive sections in one plan never share a kv_head (common.hpp:855-864).
  • What thread_local buys and costs today. The variable is one 24-byte std::vector object per OS thread per template instantiation of apply_page_range; the heap storage is allocated only on threads that run a call with the AMX path on, and it is never given back. The AMX PV kernel already keeps its own 2 KiB thread_local scratch in amx_attn.cpp:197, so this is the second thread_local of the AMX path, not the first (claim C9). What the thread_local costs at run time was read off the existing runtron binary (built 2026-08-31 from the pre-split tree, which declares the buffer the same way): the binary uses the local-exec TLS model, so every access is one %fs-relative load and there is no __tls_get_addr call; a call of apply_page_range executes 7 TLS instructions in steady state (a 3-instruction init-guard check and two address computations) and none inside the page and token loops, where the slot address is rebuilt from a stack slot with 2 ordinary loads per (page, token). The first call on each thread also registers the vector's destructor with __cxa_thread_atexit, once per thread per template instantiation (74 instantiations in that runtron, 32 bytes of static TLS each), and that happens even when the AMX path is off and in instantiations that can never be eligible. Ben's "not particularly efficient" is therefore true in kind but small in size: 7 instructions per call against a call that runs one QK and one PV kernel per token for each of its pages (claim C6). All of this exists only in builds with TRON_AMX_DISPATCH on (default off); the default build carries none of it. One more detail: libstdc++ grows a vector to size + max(size, growth), so the kept capacity lies between the largest minibatch seen and about twice it.

Today, thread_local: the same bytes as option B, keyed by OS thread instead of worker index (and, because the helper/attention split can move between passes, spread over more threads in a long run), plus a 24 B vector and an 8 B guard per thread per template instantiationas Bas B

For scale: attn_accum is already sized for the worst case. Its v_stars blocks reserve 1 MiB (llama plugin) or 8 MiB (ingested plugins) per instance at construction, zero-filled, whether or not a minibatch ever reaches max_minibatch_size. Ben's array is a 48% increment on that, not a new kind of cost; the difference is that it would be the first per-token attention buffer that is eligibility- and host-dependent and still always resident. Three more differences that the chart cannot show:

  • Where the memory is first touched. Option B and today's thread_local allocate on the attention worker itself, so the pages land on that worker's NUMA node. Option A's arrays are zero-filled by whichever thread constructs the model state. On our single-socket runs (--instance 1,2) this makes no difference.
  • Hosts without AMX. The dispatch flag is a build option, but availability is decided at run time (amx_attn_h128g4::available(): CPU, kernel permission, TRON_AMX_DISABLE). On a host where it returns false, or for an operator who sets the kill switch, option A's arrays are resident memory that can never be used, and no compile-time gate removes them; option B and today's thread_local stay at 24 bytes because the resize sits under if (amx_on) (completeness critic, item 7).
  • Static gating. The AMX-eligible models are those with 32 query heads, 8 KV heads and head size 128 on a bf16 executor (llama-3.1-8b, llama-3-8b, mistral-7b, ministral-8b, mixtral-8x7b, Qwen3-4B); llama-70b (kv_mul 8), llama-3.2-3b (kv_mul 3), gpt-oss-120b (head 64) and every host-executor build (float Q) are not (claim C8). Option A's cost in the non-eligible instantiations could be removed with a compile-time gate: plugin_t::attention_kernels is a constexpr list of geometries, the tree already folds over it for max_kernel_query_width, and std::conditional_t<..., std::monostate> with tron_no_unique_address has precedents (expert_stats_, static_option; claim C8). That gate cannot remove the cost in the two hardware-attention copies of eligible models. Option B needs no gate.

8. Recommendation

Move the buffer into attn_accum as a std::vector<amx_qpack_slot> member (option B, commit 5b5eeca67f), keep the resize(items.size()) on first use, and delete the thread_local. This gives Ben the placement he asked for (one home for per-worker, per-token attention scratch, no thread-local storage, no new representation), keeps the allocation pattern he already accepted (one growth per worker to the largest minibatch seen), and adds nothing measurable to scratchpads that never pack a query.

Three phrases of the first draft that were hard to read, and what they meant: "one 4096-byte slot per token of the minibatch" = one element per token of the current minibatch, element batch_job_ix for the token at that position, each element 4096 bytes; "scratch of one apply_page_range call (one kv_head)" = temporary data, meaningful only during the call that wrote it, and that call handles a single kv_head; "empty (24 bytes) in the scratchpads that never run the AMX path" = in an attn_accum whose worker never runs the AMX path the vector is never resized, so it owns no heap memory and costs only the 24-byte vector object, against 512 KiB or 4 MiB for the array.

9. What this investigation did not measure

  • A possible small saving that neither placement takes today. The plan builder assigns a kv_head's ready pages and then its pending pages to the same worker, and run_attention_job runs the two plans as two apply_page_range calls, so in multi-minibatch passes a (token, kv_head) pair is packed twice per layer per worker (model.hpp:2802-2818, self_attention.hpp:814-826). A per-worker "packed for kv_head" tag next to the slots would let the second call reuse the first pack; an attn_accum member is the natural place for such a tag. Not needed for the placement question; noted by the completeness critic (item 4).
  • Decode speed, thread_local versus member. Not measured. The expected difference is below run-to-run noise: the TLS access happens once per apply_page_range call, i.e. once per section, and the slot pointer is then a plain vector element either way. The measurement that would settle it is an A/B decode run of 5b5eeca67f against 26a0338c3b with the perf-round recipe (same prompt lengths, 8 users, TVD and tokens per second).
  • Memory at run time. The byte counts above are computed from the declared types and the 55-worker pool of --instance 1,2; a resident-set comparison of the two prototype binaries under runtron would confirm them.
  • Cache-line sharing. A pack slot is 64-byte aligned and 4096 bytes long, so no cache line is shared with the s*, m*, valid rows that other workers read during the join; no measurement is needed for that, but none was taken.
