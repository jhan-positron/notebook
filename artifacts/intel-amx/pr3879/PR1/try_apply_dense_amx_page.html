apply_dense_amx_page (formerly try_apply_dense_amx_page): a walk-through with diagrams

Source: h/tron/models/self_attention.hpp in the tron worktree ~/workspace/tron-amx, branch jhan-amx-p0, commit 866e588578 (2026-09-08). Line numbers below refer to that commit.

Name note. The pushed PR #3879 head (55b2a56d2f) still calls this function try_apply_dense_amx_page. Local commit 866e588578 (not pushed at the time of writing) splits it: the dense-page test moved to the caller as is_dense_amx_page, and the arithmetic part was renamed apply_dense_amx_page with seven parameters instead of fourteen. The math is unchanged. This page describes the split version and points out where the old version differed.

Short version

The function computes attention between one query token and one full 64-token KV page for the 4 query heads that share one KV head, using two AMX tile kernels for the two matrix products (scores and weighted values) and ordinary vector code for the softmax step in between. It then folds the page's result into the running softmax state (m*, s*, v*) exactly as the existing AVX-512 code does. It is called only when the page is dense (all 64 tokens live, visible and inside the sliding window); every other page keeps the old per-token loop.

1. Words used here

tron, runtron
tron is the inference program under test; runtron is its command-line tool. Not needed for this page beyond context.
AMX, AVX-512
AMX (Intel Advanced Matrix Extensions) multiplies small matrices held in 8 "tile" registers of 16 rows × 64 bytes. AVX-512 is the 512-bit vector instruction set the existing attention code uses.
bf16, fp32
bf16 (bfloat16) is a 2-byte floating-point format used for Q, K and V in storage. fp32 is ordinary 4-byte float; scores, softmax weights and the running state are fp32.
KV page
A block of 64 consecutive tokens' K and V rows for one layer and one KV head (page::page_size == 64).
kv_mul, GQA
GQA (grouped-query attention) lets several query heads share one KV head. kv_mul is that ratio; the AMX kernels serve kv_mul 4 and head size 128 only.
QK, PV
QK is the score product (query dot key, one number per token per head). PV is the product of the softmax weights P with the value rows V.
Online (deferred) softmax
Softmax needs the maximum over all tokens before any exponential can be normalized. The code avoids a second pass by keeping three running values per head: m* (largest scaled score seen so far), s* (sum of exp(score − m*) so far), v* (the 128-dim sum of exp(score − m*) × V so far). When a page raises the maximum, the old sums are rescaled by c = exp(m*old − m*new). The final attention output is v*/s*, computed after the last page, not in this function.
scratchpad, was_valid
The scratchpad is the per-(worker, token) storage of the running state for all heads. was_valid is true when it already holds a state for this KV head from earlier pages; false means this page starts the state.
the dotter, the dotter loop
The existing AVX-512 code path: dotter<bf16,128> computes one q·k dot product per token; the loop around it in apply_page_tok is "the dotter loop".
VNNI layout, A / B operand
The AMX bf16 multiply TDPBF16PS computes C[m][n] += Σk A[m][2k]·B[k][n][0] + A[m][2k+1]·B[k][n][1]. A is row-major. B must be "pair-interleaved" (VNNI, Vector Neural Network Instructions layout): each B row holds one pair of the summed dimension for 16 columns.
dense page
A (query, page) pair where all 64 tokens are live, one visibility range covers the whole page, the query may see it, and token 0 is inside the sliding window. Defined by is_dense_amx_page.

2. Where the function sits

One attention worker handles one KV head. It walks every page in its range and, inside each page, every query token of the minibatch. Two cheap checks (visible, inside the window) and the Q packing happen in that loop. The per-(query, page) work is then handed to apply_page_tok, which decides between the AMX path and the dotter loop [self_attention.hpp:1342-1404, 1591-1598].

3. The dense-page test (is_dense_amx_page)

The AMX kernels always process 64 whole tokens; they cannot skip one. So the AMX path may be used only when the per-token loop would have used every one of the 64 tokens anyway. The predicate spells that out as five conditions, all on values the dotter loop would otherwise check token by token [self_attention.hpp:1440-1452].

In the pushed PR head these checks are the first statement of try_apply_dense_amx_page and a failing check makes it return false without touching anything. In 866e588578 the caller runs the check and the function always applies the page.

5. Step 1: the QK kernel writes raw scores

tensor<operation_kv_mul, page::page_size> s_pages;              // [4][64] fp32
const auto k0 = pg.template k<geometry.kv>(slot, kv_head, 0);    // token 0's K row
amx_attn_h128g4::qk_rowmajor_128x4(k0.data, q_packed, &s_pages[0][0], page::page_size);

The kernel computes s_pages[h][t] = Σd=0..127 Q[h][d] · K[t][d] for h in 0..3 and t in 0..63 [amx_attn.cpp:124-187]. Two facts explain its shape.

  • K is the A operand, Q is the B operand. The tile multiply accepts a row-major matrix only on the left. K is stored row-major (one 256-byte row per token) and is the larger matrix, so K goes left and Q must be pre-arranged into the pair-interleaved B layout. The product therefore comes out transposed: ST[token][head] [amx_attn_iface.hpp:187-217, Note [QK orientation]].
  • Only 4 of the 16 B columns are real. A tile is 16 columns wide; the group has 4 heads. Columns 4..15 of the packed Q are zero, so 12 of every 16 result columns are wasted zeros. The kernel transposes only the 4 real columns back into s_pages[4][64].

6. Step 2: scale, running maximum, exponentials

float corr_arr[4], m_new_arr[4], sum_arr[4];
for (size_t offset = 0; offset < 4; ++offset) {
  tensor<64>& s_page = s_pages[offset];                      // this head's 64 raw scores
  scratchpad_ref<geometry> head_sp = scratchpad[kv_head * 4 + offset];
  if constexpr (softcapping) {
    s_page = tanh(s_page * (operation_scale / softcap)) * softcap;
  } else {
    s_page = s_page * operation_scale;                        // usually 1/sqrt(128)
  }
  float m_page = max(s_page);                                 // page maximum
  if (was_valid) m_page = std::max(head_sp.m_star, m_page);   // never below the old maximum
  s_page = exp(s_page - m_page);                              // P: weights in (0, 1]
  m_new_arr[offset] = m_page;
  sum_arr[offset]   = sum(s_page);                            // sum of P over the page
  corr_arr[offset]  = was_valid ? std::exp(head_sp.m_star - m_page) : 0.f;
}

This loop is a line-for-line copy of the dotter epilogue [self_attention.hpp:1648-1677], run on the AMX scores instead of the dotter's. Per head it produces three scalars and turns the 64 raw scores into the 64 softmax weights P, in place. The corr value when was_valid is false is never read (see step 4).

7. Step 3: the PV kernel

alignas(64) float amx_o[16 * 128];                 // 16 rows, not 4: see Note [Tile stores write 16 rows]
amx_attn_h128g4::weights_times_v_128x4(
    pg.template v_data<geometry.kv>(slot, kv_head),  // V page, pair-interleaved, read in place
    &s_pages[0][0],                                  // P[4][64] fp32
    page::page_size,                                 // row stride of P, in floats
    amx_o);

The kernel computes O[h][d] = Σt=0..63 bf16(P[h][t]) · V[t][d] [amx_attn.cpp:190-239]. Three facts explain its shape.

  • P is converted to bf16 first, rounding to nearest even. The tile multiply takes bf16 inputs. The kernel writes P into a thread-local 16 × 64 bf16 buffer whose rows 4..15 stay zero forever [amx_attn.cpp:199-207]. The AVX path truncates P to bf16 instead; this is one of the two numeric differences between the paths [amx_attn_iface.hpp:70-86].
  • V is the B operand and is read as stored. The KV cache stores V with token pairs interleaved (v[p/2][dim][p%2]) so that the AVX code can use _mm512_dpbf16_ps; the same layout is exactly the pair-interleaved B layout the tile multiply needs [kv_cache.hpp:1884-1892, 1299-1303].
  • The output has 16 rows although only 4 are useful. TILESTORED writes all 16 configured rows. The caller's buffer must therefore be 8192 bytes, and rows 4..15 (zeros, from the zero rows of P) are ignored [amx_attn_iface.hpp:90-112].

8. Step 4: fold the page into the running state

for (size_t offset = 0; offset < 4; ++offset) {
  scratchpad_ref<geometry> head_sp = scratchpad[kv_head * 4 + offset];
  tensor<128> scratch;
  std::memcpy(&scratch[0], amx_o + offset * 128, 128 * sizeof(float));  // row `offset` of amx_o = O for this head
  if (was_valid) {
    auto corr_ = constant<page::page_size>(corr_arr[offset]);            // c, broadcast to every lane
    head_sp.v_star.set(fma(head_sp.v_star, corr_, scratch));            // v* = v* * c + O
    head_sp.s_star = head_sp.s_star * corr_arr[offset] + sum_arr[offset]; // s* = s* * c + sum(P)
  } else {
    head_sp.v_star.set(scratch);                                         // v* = O
    head_sp.s_star = sum_arr[offset];                                    // s* = sum(P)
  }
  head_sp.m_star = m_new_arr[offset];                                    // m* = m_new
}
  • Which row of amx_o. Output row i of a tile multiply comes from row i of the A operand, and row i of P is head i. So head offset reads amx_o + offset * 128.
  • Why the constant is sized 64 while v* has 128 lanes. constant<N> is an expression whose chunk(i) returns the same broadcast register for any i, and fma on tensors works chunk by chunk [expr.hpp:293-320, 523-549]. The N is therefore not used for the lane count; the dotter loop uses the identical constant<page::page_size> idiom [self_attention.hpp:1667]. The value is correct; the size parameter is a stylistic leftover, not a bug.
  • The corr of 0 when not valid. corr_arr is set to 0 when was_valid is false, and the else branch does not read it. It is a placeholder, not a formula.
  • Validity is marked by the caller. This function does not call mark_valid_for; the caller marks the scratchpad valid once m* has left −∞ for at least one head of the group [self_attention.hpp:1388-1402].

Both paths multiply bf16 inputs and add in fp32. For finite, non-subnormal inputs their outputs differ for exactly the two shaded arithmetic reasons: the bf16 rounding of P and the order of the fp32 additions. The unit test t/t_amx_numerics.cpp checks that the kernels stay inside the error band those two causes allow [amx_attn_iface.hpp:70-86].
