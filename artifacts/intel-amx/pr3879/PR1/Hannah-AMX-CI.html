AMX Coverage on CI

What the AMX attention code in pull request (PR) #3879 does and does not get from continuous integration (CI) after it merges, and the smallest CI change that makes a real AMX execution a required check that fails when AMX does not run.

Prepared by jhan for Hannah · 2026-09-11 · source: branch jhan-amx-p0 at 47f6f2dceb (PR #3879 head), main at 632c6181ed, and the 49 CI runs on main and in the merge queue between 2026-09-05 and 2026-09-11. Every file reference and number was re-checked by two independent readers on 2026-09-11.

Short version. After PR #3879 merges, CI compiles the AMX code, but the AMX instructions execute only when a test job is placed on an Intel runner and actually runs its tests. Last week that happened in 7 of 47 test-host jobs; in the other 40 the tests ran on AMD (where the AMX cases warn and pass) or were skipped as an earlier pass of the same source. The fix is one short extra job pinned to Intel runners plus a small change to one test file that turns the warning into a failure there.

Words used here

Terms, in the order they appear

CI, PR
CI is continuous integration: the GitHub Actions workflows that build and test every commit. A PR is a pull request.
AMX
Intel Advanced Matrix Extensions, the tile-matrix instruction set of Sapphire Rapids and later Xeons. Granite Rapids (Xeon 6, the delphi hosts) has it. AMD EPYC Genoa (the andoria hosts) does not.
CMake workflow and its jobs
CMake is the build system. The CMake workflow is .github/workflows/cmake-single-platform.yml. Its jobs are named lint, ci-machinery-tests, build, test-host (tests that need no accelerator), test-fpga (tests that need one), test (the fan-in, defined below) and benchmark.
self-hosted runner, runner label
A lab machine registered with GitHub Actions. A job's runs-on list names labels; GitHub sends the job to any registered runner that carries all of them.
green, red
A job or check that GitHub reports as succeeded, or as failed.
kernel
On this page a kernel is a compute kernel: a small routine that does one piece of arithmetic, here the AMX attention routines. The operating system kernel is always written "Linux kernel".
tron, runtron, rinzler
tron is the inference program under test. runtron is its command-line tool. rinzler is the production server built from the same code.
AVX path
The existing software attention kernels, written with AVX-512 (Advanced Vector Extensions, 512-bit) vector instructions. Every runner, Intel or AMD, can run them.
TRON_AMX_DISPATCH
The CMake option (default OFF) that compiles the AMX kernels and the code that dispatches to them. When it is OFF the source is not compiled at all.
available()
The runtime probe tron::amx_attn_h128g4::available(). It checks CPUID (the CPU's feature-report instruction), the operating system's AMX tile state, and asks Linux for permission with the arch_prctl system call. When it returns false, the AVX path runs even in an AMX build. The result is computed once per process.
TRON_AMX_DISABLE
Runtime kill switch. Setting it to exactly 1 before the process starts makes available() return false.
FPGA, FPGA slice
A field-programmable gate array, the accelerator card that runs most of a model in production. All lab runners carry FPGA cards. An FPGA slice is one share of a card that a test can claim.
executor
The compute back end a model variant is compiled for. host is the CPU-only executor; tp1, tp2, tp4 and the permuted variants are FPGA executors.
bf16
16-bit brain floating point, the activation (intermediate result) format of the FPGA executors. The AMX kernels only accept bf16 inputs.
content hash, test artifact
The build job hashes every tracked source file into a 7-character content hash. It publishes the built test tree (executables and libraries) to NFS (the lab's shared network file system) under that hash, so a test job on another runner can restore it, and so a later run of identical source can reuse it.
fan-in, required check
The test job waits for the test jobs and asserts each succeeded. Branch protection lists it as a required check, so a red fan-in blocks merging. Its success also releases the benchmark job.
.passed marker
An empty file the fan-in writes next to the artifact once test-host and test-fpga succeeded, and only in a run whose tests actually ran (the step is gated on RUN_TESTS, workflow lines 673-675). A later run whose content hash already has this marker skips its test steps entirely. The marker records no platform.
slice
bin/slice, the in-repo test runner that places tests on FPGA slices. Its run command accepts only three filters: all, host, fpga. It has no way to run one test by name.
Catch2, CTest
Catch2 is the C++ test framework the tests are written in. CTest is CMake's test driver; a CTest label (such as fake, for tests that use the software stand-in for the FPGA) tells slice which job a test belongs to.
cost data
Each test's recorded run time and peak memory in config/test-benchmarks.json. slice uses it to schedule tests, and the build fails if a test has no entry.
64-token page
The unit of the attention cache the AMX kernels work on. The kernels serve models with head size 128 and 4 query heads per key/value head.
1 · What is true after the merge

The AMX code compiles in CI; whether it executes depends on runner choice and on the artifact cache

A common assumption is that CI never compiles the AMX code because the option defaults to OFF. That is only partly correct. The PR adds -DTRON_AMX_DISPATCH=ON to the configure step of the build job, so the CMake workflow compiles the AMX kernels and the dispatch whenever that job builds [.github/workflows/cmake-single-platform.yml:365-367]. It is the only build configuration in the repository that does so. Every CMake preset (a named configure recipe in CMakePresets.json), the nix builds (a second, reproducible build system), the coverage workflow and the .deb (Debian package) release keep the default OFF.

Compiling is not executing. The dispatch calls available() before every use of the kernels [h/tron/models/self_attention.hpp:1328-1331]. On an AMD runner the CPUID check fails and available() returns false, so the AVX path runs. The two kernel test cases then print a warning ("AMX unavailable on this host - QK precision check skipped", and the same with PV) and return, and the test passes [t/t_amx_numerics.cpp:145-148, 189-192].

Which runner executes a job is GitHub's choice. The build, test-host and test-fpga jobs all request the labels self-hosted fpga test avx512, which every machine in the FPGA runner group carries, Intel and AMD alike. When the content hash already has a .passed marker, the test job skips its test steps and still reports success. Nothing in a green (succeeded) job log distinguishes "AMX executed", "AMX skipped with a warning" and "tests not run".

2 · Measured

How often the AMX tests actually ran on an Intel runner

I (jhan) listed the jobs of the last 49 runs of the CMake workflow on main and in the merge queue (29 pushes, 20 merge-queue runs, 2026-09-05 to 2026-09-11) through the GitHub API. For each job I recorded which runner executed it. For each test job I read the step results to see whether the test step ran or was skipped because of a .passed marker. One run was cancelled before its build job and one build failed, so there are 48 build jobs and 47 of each test job; the benchmark job runs only after a successful fan-in on a push to main, so there are 25 of those.

Job placement alone was closer to even: test-host was placed on an Intel runner 26 times and on an AMD runner 21 times. Pinning a job to Intel runners would not add waiting time. After its build finished, a test-host job started after 29 s on average on Intel (longest wait 654 s) and after 194 s on average on AMD (longest wait 3597 s).

4 · Proposal

One short job pinned to Intel runners, and a warning that becomes a failure there

Add a test-amx job. It restores the same test artifact as test-host, but requests the intel label and runs only the two AMX test binaries. It sets an environment variable that makes the kernel cases fail instead of skip when AMX is missing. Wired into the test fan-in, it is covered by the existing required check, and the .passed marker is then written only after a real AMX execution.

Precondition: an Intel runner must be online at all times

The job can only run where an intel runner is online. When none is, GitHub keeps a self-hosted job queued for up to 24 hours, the required fan-in waits with it, and every merge is blocked for that time. By the table above, only delphi-3bd6-0 is known to be registered 24 hours a day; delphi-17cf-0's schedule is unverified, delphi-3bda-0 is out of the pool, and delphi-3af6-0's label is unverified. Hannah's item 1 below is therefore a precondition, not a formality. The escape route, if a runner outage ever blocks merges, is a PR that deletes the single test-amx entry from the fan-in's needs list, merged with the fan-in temporarily taken out of branch protection by an Admin.

Workflow snippet (adapted from the existing test-host job)

  # Real-AMX execution gate. Same portable test tree as test-host, but pinned to
  # the Intel runners and running only the AMX tests, with skipping turned into
  # failure (TRON_CI_REQUIRE_AMX). Runtime is well under a minute.
  test-amx:
    runs-on: [self-hosted, fpga, test, intel, avx512]
    needs: build
    timeout-minutes: 15
    env:
      RUN_TESTS: >-
        ${{
          needs.build.outputs.artifact_verified != 'true' ||
          github.run_attempt > 1
        }}
      TRON_CI_REQUIRE_AMX: "1"
    steps:
    - name: Debug Info
      run: |
        uname -a
        lscpu | grep -E 'Model name'
        grep -o -w -E 'amx_[a-z0-9]+' /proc/cpuinfo | sort -u | tr '\n' ' '; echo
    - uses: actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd # v6
      with:
        repository: "positron-ai/tron"
        path: ${{github.workspace}}/tron
    - name: Get hash of all files in git
      # identical to the step in test-host
      ...
    - name: Verify build content hash
      # identical to the step in test-host
      ...
    - name: Restore test artifact
      if: env.RUN_TESTS == 'true'
      working-directory: ${{github.workspace}}/tron
      run: bin/ci/ci-restore-test-artifact.sh ${{needs.build.outputs.sha7}} ${{needs.build.outputs.artifact_run_id}} ${{needs.build.outputs.artifact_run_attempt}}
    - name: Set up restored test environment
      if: env.RUN_TESTS == 'true'
      working-directory: ${{github.workspace}}/tron
      run: |
        runtime_libs="$PWD/gen/src/tron:$PWD/gen/libfuse3_external-prefix/src/libfuse3_external-build/lib"
        printf 'LD_LIBRARY_PATH=%s\n' "${runtime_libs}${LD_LIBRARY_PATH:+:${LD_LIBRARY_PATH}}" >> "$GITHUB_ENV"
    - name: Require AMX on this runner
      if: env.RUN_TESTS == 'true'
      run: grep -q -w amx_bf16 /proc/cpuinfo   # fails fast on a mislabelled runner
    - name: AMX kernel tests
      if: env.RUN_TESTS == 'true'
      working-directory: ${{github.workspace}}/tron
      run: |
        ./gen/t_amx_numerics
        ./gen/t_amx_dispatch_dtype   # hardware-independent; kept as a link check of the AMX build

  # In the existing fan-in job:
  test:
    needs: [build, test-host, test-fpga, test-amx]
    steps:
    - name: Require successful dependencies
      env:
        ...
        TEST_AMX_RESULT: ${{ needs.test-amx.result }}
      run: |
        ...
        test "$TEST_AMX_RESULT" = success

Why run the binaries directly: the restored tree holds only the executables and their libraries, not the CMake test registry, and bin/slice run has no per-test filter. The portable test manifest (the file ci-create-portable-test-manifest.py writes) fixes the working directory as the repository root, which is what the snippet uses. Unlike slice, this sets no SYSTEM_CONFIG or TRON_LOG_DIR; the fake driver then takes its whole-machine default, which is fine for a 1.5-second test. The RUN_TESTS expression is the one test-host uses: when a previous run already marked the identical build content .passed, the tests are skipped and the job passes. That stays correct because, with test-amx in the fan-in, a .passed marker can only exist after an AMX execution succeeded, and because the workflow edit itself changes every content hash (the hash covers every tracked file, including the workflow), so no marker from before the change applies. The uses: line keeps the action referenced by its full commit hash rather than a tag, which make lint enforces.

Test snippet (t/t_amx_numerics.cpp)

#include <cstdlib>  // std::getenv (not yet included by this file)

// Inside the file's anonymous namespace, under #ifdef TRON_AMX_DISPATCH.
// CI sets TRON_CI_REQUIRE_AMX=1 on jobs pinned to AMX runners. There, a host
// without AMX is a failure (mislabelled runner, disabled tile state), not a
// skip. Everywhere else the cases keep skipping with a warning.
bool amx_required() {
  const char* v = std::getenv("TRON_CI_REQUIRE_AMX");
  return v != nullptr && std::strcmp(v, "1") == 0;
}
// ... in the QK case (the PV case is identical, with "PV" in both messages):
if (!tron::amx_attn_h128g4::available()) {
  if (amx_required()) FAIL("TRON_CI_REQUIRE_AMX=1 but AMX is unavailable on this host");
  WARN("AMX unavailable on this host - QK precision check skipped");
  return;
}

Why an environment variable and not Catch2's SKIP(): a skipped Catch2 binary exits with code 4. slice counts exit code 4 as a failure unless the test carries the skip_return_code_4 label. With the label, slice counts it as skipped and the job stays green. Neither gives "fail only where AMX must exist".

Against the README checklist for new jobs

  • Needs FPGA hardware? No. It runs on FPGA runners only because those are the Intel machines. It touches no device and claims no FPGA slice.
  • New secrets? None.
  • Affects benchmarks? Only by delaying the fan-in, and so the benchmark start, by about half a minute.
  • Timeout: 15 minutes, generous for a job that should take under one. Add it to the README timeout table.
  • Dependencies: needs: build; the fan-in gains one dependency. The build job does not run on draft pull requests, so test-amx does not run on them either. It runs on merge-queue events (GitHub's queued merges into main) like the other test jobs, so a required check is never left waiting for a run that does not exist.
  • No new test, so no new cost data. If the two tests are ever relabelled, their entries in config/test-benchmarks.json must follow.
