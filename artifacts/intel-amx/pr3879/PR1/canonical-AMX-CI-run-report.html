Canonical AMX at the CI harness: the nightly perf phase with PR #3879 only

delphi-3bda, whole machine, 2026-09-18/19. Generated 2026-09-19 00:56 UTC by exec/canon-ci-20260918/gen_report.py from the run records.

Short version

Turning on the canonical AMX kernels of PR #3879 in the nightly package (canon against base) lost TPS (decode tokens per second per user) by a resolved amount on none of the 12 configs and gained +1.2 % on llama-3.1-8b good tp2 @8u, where the probe counted 30.2 billion AMX-busy cycles in 20 s (0 on base).

The qwen-3-4b TPS loss of issue #4500 appears when PR #4424 is added on top of canon (target against canon: tp2 -5.1 %, tp4 -8.6 %, both resolved) and not when the canonical kernels alone are turned on (canon against base: tp2 +0.1 %, tp4 -2.6 %, both unresolved).

Every arm ran once (10 rounds per config, as in the nightly), and a repeat run is needed before these items are accepted: the two unresolved canon drops (gpt-oss-120b tp4 -3.9 %, qwen-3-4b tp4 -2.6 %) and the resolved target-against-canon loss outside qwen-3-4b (llama-3.2-3b fast tp2 -5.1 %, a candidate PR #4424 regression, section 3).

  • Words: base = the nightly's own package of 2026-09-18 (no AMX code). canon = the same main commit 3faba6d0fd plus the deb preset line TRON_AMX_DISPATCH=ON, built for this campaign. target = canon plus PR #4424 (the VNNI-K layout of the K cache) with TRON_K_VNNI=ON, from the 2026-09-18 ci-mimic campaign. Every term is defined under Words used here.
  • Resolved = a TPS difference that passes three tests (section 2): a paired t test over the 10 rounds with |t| >= 2.26, a size of at least 1 %, and a size of at least the config's 13-night band (2 standard deviations of the last 13 nightlies).
  • Static goals (section 5): canon passes every goal the same-day nightly passed, except qwen-2.5-32b fast tp2 (slowest 34.88 against 35 TPS, base 34.83).
  • Other resolved target-against-canon changes: llama-3.3-70b good tp2 @4u +1.2 % (section 3).

Words used here

nightly, CI, systems_test, CI runner
CI = continuous integration, the automated nightly test job. The nightly is the systems_test job "System CI (Rinzler 72-core Intel system OCI version)" that runs on delphi-3bda (the 72-core Intel Granite Rapids test machine) every night at 03:30 UTC. systems_test is the repository that holds the system tests. The CI runner is the machine that runs the nightly's client code. This page repeats the nightly's perf phase by hand.
arm, config
An arm is one package under test (base, canon or target), run once through all configs. A config is one row of the nightly's perf list: a model, its tensor-parallel width and a user count, for example llama-3.1-8b good tp2 @8u.
harness
The nightly's client code (systems_test scripts/perf.py and testlib/tps.py). It provisions each model, starts the users' requests, and computes TPS (decode tokens per second per user) and TTFT (time to first token). The same code produced every number here.
snapshot
One record of the machine's engine layout, the running binaries and the client load, taken by our driver before the run, after each provisioning and after the run (14 per arm). The per-config client numbers on this page come from the after-provisioning snapshot of that config.
good, fast (config labels)
The nightly's own labels for a model's serving profile, part of the model name platformd provisions (for example llama-3.1-8b-instruct-good). What each profile selects is not recorded here.
platformd, rinzler@N, engine, Caddy
platformd is the daemon on the machine that writes one env file per engine and starts the rinzler@N systemd units. rinzler is the production tron server (tron = the inference program under test), and one running rinzler is one engine. Caddy is the port-80 proxy in front of the engines. It sends each new user to the engine with the fewest connections.
deb, preset, PR, main
The deb is the tron apt package the nightly installs. The preset is the CMake build recipe ("deb") that builds it. PR = pull request. main = the main branch of the tron repository. All three arms are built from main commit 3faba6d0fd, the commit of the nightly's deb of 2026-09-18.
PR #3879, canonical AMX
PR #3879 added the AMX attention kernels to tron. It was merged into main on 2026-09-15. Its kernels are compiled only when the CMake option TRON_AMX_DISPATCH is ON. The nightly deb preset never sets it. "Canonical" means these kernels as merged, with the K cache in its original layout.
PR #4424, VNNI, VNNI-K
VNNI = Vector Neural Network Instructions. The VNNI layout is the pair-interleaved data format those instructions and the AMX tile products read (two consecutive tokens side by side). VNNI-K = the K cache stored in that layout. PR #4424 (branch jhan-amx-vnniK) adds that layout and the CMake option TRON_K_VNNI. It is not merged. It also changes gof::populate (the copy of K to the FPGA) and the dispatch code.
issue #4500
The GitHub issue in positron-ai/tron, filed 2026-09-18: qwen-3-4b loses 5 to 11 % TPS with PR #4424 under FPGA attention (tp2 and tp4). This page's effect B on the two qwen-3-4b rows is the same loss.
dispatch gate
The run-time check in tron that decides, per model, whether attention takes the AMX kernel (head size, kv_mul, CPU attention). A package effect on a control config could come from this check rather than from the kernel.
base
The package the nightly installed on 2026-09-18 (2026.09.18-3faba6d0). Its source contains PR #3879. The deb preset left TRON_AMX_DISPATCH off. The package therefore has no AMX code. Measured in the ci-mimic campaign of 2026-09-18 and not re-run here.
canon
Our package 2026.09.18-0594dc54-jhan-ci-canon: main 3faba6d0fd plus one commit that adds TRON_AMX_DISPATCH=ON to the deb preset. It contains the canonical AMX kernels of PR #3879 and no PR #4424 code. Run in this campaign.
target
Our package 2026.09.18-29a8a547-jhan-ci-mimic-target: PR #4424 (head 30c4ac82cb, merge commit 0f086eecc2, package head 29a8a54740) merged into the same main commit, built with the deb preset carrying TRON_AMX_DISPATCH=ON and TRON_K_VNNI=ON. Measured in the ci-mimic campaign of 2026-09-18 and not re-run here.
effect A, effect B
Effect A = canon against base: what the canonical AMX kernels change. Effect B = target against canon: what PR #4424 adds on top of them. The 2026-09-18 report measured target against base, the two combined (the percentages compound, and the plain sum is only approximate).
AMX, K cache, KV head, kv_mul, head size
AMX = Intel Advanced Matrix Extensions, the tile matrix instructions of Granite Rapids CPUs. The AMX kernel accelerates software attention (attention computed on the CPU) for models with a head size of 128 elements and 4 query heads per KV head (kv_mul = 4). A KV head is one key/value head of attention that several query heads share. The K cache is the stored keys of all earlier tokens.
FPGA attention, CPU attention, CPU share, ingested, USE_HW_ATTN, HBM
Ingested models (models converted by tron's ingest compiler) run attention on the FPGA cards (Positron's accelerator cards) by default. Here that is qwen-3-4b and gpt-oss. gemma-4-31b is ingested but has no FPGA attention (head size 256). It therefore runs attention on the CPU. Hand-written models (models coded by hand in tron) run attention on the CPU, where AMX acts. The CPU share is the part of attention the CPU still computes under FPGA attention: positions 0 to 126 of each query and the most recent tokens not yet copied to HBM. USE_HW_ATTN is the environment variable that would force one or the other. It was unset, as in the nightly. HBM = the high-bandwidth memory on the FPGA card.
tp2, tp4, @Nu, round, prompt 1024
tp2 and tp4 = tensor-parallel width, the number of FPGA cards one engine uses (2 or 4). The machine's 8 cards therefore give 4 or 2 engines. @Nu = N concurrent users. A round is one pass in which every user sends one request. Every config runs 10 rounds with fixed prompts. Prompt 1024 = a prompt of 1024 tokens (llama-3b uses 800 shared plus 200 own prompt tokens).
TPS, TTFT, slowest user, prefill
TPS = decode tokens per second per user, measured between generated token 896 and 1024 (2 and 333 for llama-3b), mean over users and rounds. TTFT = time to first token in ms, measured on the client. Slowest user = the minimum TPS sample of a config. Prefill = processing the prompt before the first token.
paired t, 95 % interval, sd, 13-night band, Slack reports, resolved
Paired t = the mean of the 10 per-round differences divided by its standard error. The prompts are fixed. Round r of one run therefore pairs with round r of the other. The 95 % interval is the confidence interval of that mean. sd = standard deviation. The Slack reports are the summary messages the nightly posts to a Slack channel. The 13 reports of 2026-09-05 to 09-17 give each config a mean and sd. The band is 2 sd of those 13 nights, in percent of their mean. It is recomputed here from the 13 values. gemma-4-31b entered the nightly on 2026-09-15, so its band comes from 3 nights. The statistics file rounds sd to 2 decimals, and a check against that rounded field can therefore differ by up to 0.03 percentage points. A change is resolved when |t| >= 2.26, |delta| >= 1 % and |delta| is at least the band.
thresholds, granite_rapids_72_rinzler
The static goals are the mean-TPS and slowest-user limits the Slack report applies (from systems_test scripts/system_ci.py for the machine profile named granite_rapids_72_rinzler). The ratchet thresholds are a second set in YAML files that tightens over time. They are not shown in Slack.
EXE.AMX_BUSY probe
A 20 s read of the CPU counter EXE.AMX_BUSY, which counts cycles in which the AMX unit was busy, summed over all engine processes while 4 short requests run. It runs before the benchmark of the probed config. It therefore does not touch the measured rounds.
PSI, load average, DUT, sha256, ci-mimic, talos
PSI = Pressure Stall Information. Its "some" value is the share of time at least one task waited for a CPU. avg10 = its 10-second average. The load average is the number of runnable tasks, here on a 32-CPU client host. DUT = device under test, delphi-3bda. sha256 = a hash that identifies a file's content. ci-mimic = the 2026-09-18 campaign that produced the base and target arms. talos = the CI's metrics recorder, replaced here by a local stub.
marker, flock, lease, handoff, hugepages, ci-runner-stop timer
The marker is the file /bill-has-instance-0,2 on delphi-3bda that reserves the first half of the machine (the cards on socket 0) for Bill. The flock is the host-wide lock file /var/tmp/jhan/3bda-campaign.lock that lets only one of our campaigns run at a time. The lease is /run/lock/systems-test-ci.lease, which the nightly holds while it runs. The handoff is the end state this campaign leaves for the next one (here: production engines down, hugepages free). Hugepages are the 1 GiB memory pages the engines reserve (HugePages_Free = pages not in use). The ci-runner-stop timer is a systemd timer on delphi-3bda that brings production serving back at 02:45 UTC before the nightly (recorded in campaign.sh's header, not verified in this run).

2. Effect A: canon vs base (the canonical AMX kernels alone)

Test: swap only the package, keep everything else. Observation: the two charts and the table. Meaning: see the rules below.

  • A resolved TPS change (marked *) meets three conditions: its 95 % interval over the 10 paired rounds excludes zero, its size is at least 1 %, and its size is at least the config's 13-night TPS band (2 sd).
  • The band condition is needed. The nightlies of 2026-09-16 and 09-17, two consecutive packages without AMX, differ by +4.7 % on qwen-3-4b tp4 with a paired t of 4.2. The t test alone would flag too many changes on the noisy configs.
  • The TTFT * uses the same three conditions: |t| >= 2.26, |delta| at least 1 % and at least 1 ms, and |delta| at least the config's 13-night TTFT band.
  • TTFT rows that involve base compare unlike client conditions (section 1). Their TTFT marks are not attributed to the package for the 3 configs whose base TTFT differs from the same-day nightly by more than 5 % (llama-3.2-3b fast tp2, llama-3.1-8b good tp2, qwen-3-4b tp2). A client stall of tens of ms is visible only on TTFTs that short.
  • Only llama-8b and mixtral run the AMX kernel with CPU attention. qwen-3-4b gets it only in the CPU share (the part of attention the CPU still computes under FPGA attention, section 7). Every other config is a control for canon (section 7).

Reading the effects

  • llama-3.1-8b (CPU attention, AMX kernel eligible). canon vs base +1.2 % (paired t +2.8), the only resolved canon effect. The kernel ran: 30.2 billion AMX-busy cycles in the 20 s probe, 0 on base. The target arm had shown +0.8 % on the same config. Both are small. The nightly layout puts 2 users on each engine, and each engine has 28 application cores (the --app-cores list in its unit). A campaign on 2026-09-18 measured the same kernel at +0.2 %, +3.9 % and +12.9 % with 2, 4 and 8 users per engine (VNNIed-K-in-place/status/llama8b-AMX-gain-vs-load.html). The 2-user layout is therefore the likely reason (hypothesis). The CI number cannot show the kernel's larger gains.
  • qwen-3-4b tp2 and tp4 (FPGA attention, AMX only in the CPU share). canon vs base: tp2 +0.1 % (t +0.1), tp4 -2.6 % (t -3.7). The tp4 change is inside that config's 13-night band of 7.0 % (sd 5.09 TPS). It is therefore not resolved. target vs canon: tp2 -5.1 % (t -7.4) and tp4 -8.6 % (t -7.3), both resolved. The kernel did run in canon on tp2 (10.5 billion AMX-busy cycles, target 13.7 billion). Effect B isolates PR #4424 as a package, not one part of it. The loss tracked in issue #4500 appears in target vs canon (tp2 -5.1 %, tp4 -8.6 %, both resolved) and not in canon vs base (tp2 +0.1 %, tp4 -2.6 %, unresolved). So the canonical AMX kernel is not the main cause. The kernel's own share on tp4 is bounded by the unresolved -2.6 % (paired t -3.7, 95 % interval +/-1.6 %, band 7.0 %) and needs a repeat run to be set to zero. Which part of PR #4424 causes the loss (the VNNI-K layout in the K cache, the gof::populate copy of K to the FPGA, or the dispatch changes) is a hypothesis this run cannot separate. The issue #4500 root-cause campaign measures that. Client conditions: the target arm provisioned qwen-3-4b tp2 at 45 % and tp4 at 27 % client CPU pressure, canon at 5 % and 0 %. The stall indicator shows no effect: 2 and 0 anomalous samples in target, 1 and 0 in canon (section 1). The two qwen rows therefore compare like client conditions. Threshold: canon passes the qwen-3-4b tp4 goal of 135 TPS (146.05). The target arm failed it (133.44).
  • mixtral-8x7b (CPU attention, AMX kernel eligible). canon vs base -0.6 % (t -2.2), below the 1 % floor. It is therefore not resolved. No AMX probe ran on mixtral in any arm. Whether the kernel engaged there is therefore not measured in this run. A probe on the mixtral benchmark would resolve it.
  • Controls (no AMX kernel for their shapes). gpt-oss-120b tp4: canon vs base -3.9 % (t -2.6), inside its 13-night band of 5.7 % (sd 3.01 TPS). It is therefore not resolved. The same-day nightly gave 101.16 TPS, closer to canon (102.33) than to base (106.51). llama-3.3-70b tp4 @4u: +1.8 % (t +1.8), t below 2.26, not resolved. Five of the six other controls are within 0.3 % of base. The sixth, llama-3.2-3b, is +1.5 % (95 % interval +/-3.7 %, not resolved). Its base value was lowered by the client stall (hypothesis, see the llama-3.2-3b bullet).
  • llama-3.3-70b tp2 @4u. canon equals base (-0.0 %). target is +1.1 % against base and +1.2 % against canon (t +18.3 against canon). The change belongs to the target arm. Two candidate causes remain: the VNNI-K layout (kv_mul 8, no kernel) or the mix of this config's two TTFT groups (0.3 s and 5 s per request), which differs between runs: mean TTFT 4567 ms base, 3302 ms canon, 3794 ms target. Neither cause is isolated by this data.
  • llama-3.2-3b (client-affected in the earlier arms). canon 197.36 TPS against the same-day nightly's 197.66 (-0.2 %). This is consistent with the base value of 194.54 having been lowered by the client stall on 2026-09-18 (hypothesis). canon vs base is +1.5 % with a 95 % interval of +/-3.7 %. The run therefore does not resolve it. A base repeat on an idle client would. target vs canon -5.1 % (t -19.4) is marked resolved by the rule. The target arm ran this config at 99 % client CPU pressure at provisioning, but its stall indicator shows 3 anomalous samples, the same as canon and the nightly (section 1). So the client-load explanation is not supported by the harness's own indicator. The -5.1 % may be a real PR #4424 effect on a CPU-attention model with kv_mul 3 (the VNNI-K layout applies, the AMX kernel does not). One 10-minute re-run of the target package on llama-3b on an idle client decides it. Until then this page reports it as an open candidate regression of PR #4424, not as noise.
  • TTFT. canon TTFT is within 2 % of the same-day nightly on 8 of 12 configs. The 4 configs outside: llama-3.3-70b good tp2 @4u -29.3 % (3,302 against 4,673 ms), llama-3.1-8b good tp2 -14.3 % (569 against 664 ms), llama-3.2-3b fast tp2 +3.6 % (58 against 56 ms), qwen-3-4b tp2 -2.2 % (516 against 528 ms). llama-3.1-8b is 14 % lower than the nightly (569 ms against 664 ms) and 7 % lower than base (611 ms). base, without AMX, was already 8 % below the nightly on this config. 7. Which configs can react, and why

canon has the AMX kernel only for models with head size 128, kv_mul 4 and CPU attention. In the nightly list those are llama-3.1-8b and mixtral-8x7b. qwen-3-4b runs FPGA attention and gets the kernel only in the CPU share. llama-3b, llama-70b, qwen-2.5-32b, gemma-2, gemma-4 and gpt-oss are controls for canon: no kernel effect is expected there. A resolved change on a control has three candidate causes: night-to-night noise, a client-side artifact, or a package effect outside the kernel (for example the dispatch gate). Such a change needs a repeat run before it is accepted. target adds the VNNI-K layout on top of canon.

  • llama-3.2-3b fast tp2 @32u: CPU attention, kv_mul 3, no AMX kernel. A control for canon. target adds the VNNI-K layout.
  • llama-3.1-8b good tp2 @8u: CPU attention, head 128, kv_mul 4: the AMX kernel runs in canon and in target. target adds the VNNI-K layout on top.
  • llama-3.3-70b good tp2 @8u: CPU attention, kv_mul 8, no AMX kernel. A control for canon. target adds the VNNI-K layout.
  • llama-3.3-70b good tp2 @4u: same engines as the @8u cell (no re-provisioning). A control for canon. target adds the VNNI-K layout.
  • llama-3.3-70b good tp4 @4u: CPU attention, kv_mul 8, no AMX kernel. A control for canon. target adds the VNNI-K layout.
  • mixtral-8x7b tp2 @8u: CPU attention, head 128, kv_mul 4: the AMX kernel runs in canon and in target. target adds the VNNI-K layout on top.
  • qwen-2.5-32b fast tp2 @8u: CPU attention, kv_mul 5, no AMX kernel. A control for canon. target adds the VNNI-K layout.
  • qwen-3-4b tp2 @8u: FPGA attention (nightly default). canon's AMX kernel acts only in the CPU share (positions 0 to 126 of each query and the most recent tokens not yet copied to HBM). target adds the VNNI-K layout to the K cache the FPGA path reads.
  • qwen-3-4b tp4 @8u: FPGA attention, as tp2. Night-to-night noisy (sd 5 TPS).

9. Not measured in this run, and what would measure it

  • AMX engagement on mixtral-8x7b and on qwen-3-4b tp4: no probe ran on them in any arm. One 20 s EXE.AMX_BUSY probe per config resolves it.
  • Run-to-run noise of our own arms: every arm ran once. A second canon run (about 90 min, whole machine) sets the within-day band.
  • TTFT effect of the kernel: base ran on a saturated client (121 anomalous samples on llama-3b, no PSI record). A base re-run on an idle client resolves the TTFT rows of llama-3.2-3b fast tp2, llama-3.1-8b good tp2, qwen-3-4b tp2.
  • gpt-oss-120b tp4 canon vs base -3.9 %: inside its 5.7 % band, and the model has no kernel path. A repeat run decides noise against a dispatch-gate effect.
  • llama-3.2-3b target vs canon -5.1 %: resolved by the rule, and its stall indicator equals canon's (section 1). One re-run of the target package on llama-3b on an idle client decides whether PR #4424 slows this CPU-attention model.
  • Client CPU pressure inside a config: PSI is sampled only at the 14 snapshots. The per-config anomalous-tps count (section 1) is the only in-run indicator.
  • Cause of the qwen-3-4b loss inside PR #4424 (the VNNI-K layout in the K cache, the gof::populate copy of K to the FPGA, or the dispatch changes): effect B isolates the PR as a package. The issue #4500 root-cause campaign measures the parts.
  • Foreign load on the DUT during base and target: the DUT load row of section 6 shows the engines' own load only (no value far above the idle-engine level). No process list was recorded.
  • Functional tests, MMLU Pro and the 3 h soak: not run in any arm.
