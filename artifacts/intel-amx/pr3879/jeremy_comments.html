1. Words used here

  • tron — the inference program under test; the code here is its CPU attention path.
  • AMX — Intel's tiled matrix-multiply instruction set. LDTILECFG loads the tile configuration (shapes of the 8 tile registers); TILERELEASE returns the tile state to its initial empty state; TILELOADD loads one tile from memory, row by row.
  • page — a 64-token block of the KV cache. A dense page is one that passes the predicate letting it take the AMX path: all 64 tokens stored, one visible range covering the whole page, entirely inside the sliding window, and (in mirror builds) a mirror plane present.
  • the dotter — the pre-existing AVX dot-product loop; every page that is not dense uses it.
  • Q pack — copying one token's 4 query heads (4 × 128 bf16 values) into the zero-padded 4 KB tile-shaped buffer the AMX kernels read; kv_mul = query heads per KV head (4 is the AMX shape).
  • apply_page_range / apply_page_tok — the function that walks one section (one KV head × one chunk of pages) / the per-(token, page) worker it calls; the dense predicate lives in the second.
  • codex — an automated reviewer; Jeremy had it review the PR and filed its two findings under his account.

2. The code both comments point at

The AMX block at the top of apply_page_range (self_attention.hpp:1352–1375 at head) computes one flag, sizes one buffer, and opens the tile region:

constexpr bool amx_eligible =
    amx_attn::eligible<typename model::activation_scalar>(
        geometry.kv.head_size, geometry.kv_mul());          // bf16 + head 128 + kv_mul 4
const bool amx_on = amx_eligible && amx_attn::available();  // + CPU/OS/kill-switch
thread_local std::vector<uint16_t> amx_qpack;               // <-- comment 2
uint64_t amx_packed_mask[(max_minibatch_size + 63) / 64] = {};
if (amx_on) {
  amx_qpack.resize(items.size() * amx_attn::Q_PACK_ELEMS_2048);
  amx_attn::begin_region();                                 // <-- comment 1 (LDTILECFG)
}

Then, inside the page loop, each token's Q group is packed at its first surviving page (1421–1442) and reused for all later pages; the dense predicate that decides AMX vs the dotter sits one function deeper, in apply_page_tok (1564–1566). end_region() (TILERELEASE) closes the call at 1475. Figure 1 places both comments on this flow with the measured costs.

3. Comment 1 — eager tile region and eager Q pack (r3858305362)

jeremyconner1975 · self_attention.hpp, line 1369 at head · 2026-08-25

What it says, in plain words

comment saysin plain words
“amx_on only checks geometry and CPU support”The switch that turns the AMX path on looks only at the model's shape and at whether the CPU can do AMX. It never looks at the pages about to be processed.
“every eligible page range executes LDTILECFG/TILERELEASE”Every call of the page-walking function on an AMX-capable setup runs the tile configure instruction at entry and the tile release instruction at exit, whether or not any page ends up using AMX.
“packs each query before the dense-page predicate is evaluated”Each token's query data is copied into the AMX-shaped buffer before the code has checked whether any page qualifies for the AMX kernel.
“partial pages, masked/sliding-window pages, and null-mirror fallbacks … pay AMX setup plus a 4 KB pack even though every page uses AVX”In the cases where pages cannot take the AMX kernel (page not full; page cut by a visibility mask or the attention window; the mirror copy of K missing), the setup and copies were wasted — the old AVX loop does all the work.
“Could we lazily begin the region and pack Q only when the first page actually satisfies the dense predicate?”Proposal: delay both the tile configuration and the query copy until the moment a page actually qualifies.

The measured costs

Measured (bench_amx_overhead, delphi-3bda Xeon 6962P, idle core, 2026-08-21; exec/results/amx-overhead-20260821.txt):
  • LDTILECFG 181.9–215.6 cycles (67.5–80.0 ns at the 2.7 GHz time-stamp counter); TILERELEASE 15.1–15.5 cycles (~5.7 ns); the pair back-to-back 228.7–229.1 cycles ≈ 85 ns.
  • One-time per-thread tile-state setup (the first tile-data instruction, TILEZERO, after the permission call): 4.1–8.8 µs, once per thread — not part of the per-call cost.
Measured (fused-page sweep, 2026-08-18; exec/results/slot1/fused-sweep-v2.txt — the file header names only “cpu 96”; the same-host attribution rests on the PR record): full QK+softmax+PV per dense 64-token page at query width 4, L2-resident: mirror kernel 686.0 ns, canonical kernel 1249.9 ns, AVX dotter 1618.1 ns. (Known bench caveat, from the internal round-5 notes: the canonical variant re-packed Q inside its timer, inflating its gap to the mirror variant by roughly the pack cost.)

Measured 2026-08-31 (campaign exec/jeremy-measure-20260831.sh, results in exec/results/jeremy-measure-20260831/) — both former gaps are now numbers:
  • Pack cost on the 6962P (bench_qpack, real kernel TU, destination zeroed once per the contract): pack_q_rows_128x4 (the mirror-build packer production uses) = 6.3 ns per pack; pack_q_group_128x4 (canonical builds) = 63 ns. The old 65–95 ns figure was an estimate from another host and overstated the mirror packer tenfold.
  • Zero-AMX-page call fraction (per-call counters on jhan-dd-debug @ 8d02eaba8c, mirror build, qwen-3-4b decode, 253 generated tokens per user): ctx 2048 / 1 user: 20.6% of AMX-on calls ended with zero AMX pages (77,796 of 378,288); ctx 2048 / 8 users: 23.2%; ctx 8192 / 8 users: 24.0%; off-grid short-sequence cell (ctx 32 / 1 user): 36.7%.
What the waste amounts to (arithmetic from the measured values, upper bounds): per decode step, the zero-AMX calls burn 26–32 µs of region pairs plus at most their fraction share of pack time (packs total 0.06–1.1 ms of CPU per step depending on the cell, mostly in calls that do use them) — together ≤ 0.5–0.8% of one step's CPU, spread across the 12 attention workers, so on the order of 0.05% of wall-clock decode (est.). The 2026-08-30 perf round's whole-system parity within noise is consistent with this.
Decision (2026-08-31, per the agreed measure-first rule): the cost is low — no code change. The eager structure stays; the draft reply below closes the thread with the data. If a future shape shifts the balance (a CPU-served sliding-window model, say), the ~5-line page.count() gate is the first move on record.

4. Comment 2 — the packed-Q buffer is not 64-byte aligned (r3858305367)

jeremyconner1975 · self_attention.hpp, line 1363 at head · 2026-08-25
The kernel interface requires each packed-Q buffer to be 64-byte aligned, but std::vector<uint16_t> guarantees only alignof(uint16_t). Since each slice is exactly 4096 bytes, every query inherits the base misalignment and TILELOADD can repeatedly straddle cache lines. Could this use a 64-byte-aligned allocator or aligned fixed storage?
— Codex review, submitted at Jeremy's request

What it says, in plain words

comment saysin plain words
“The kernel interface requires each packed-Q buffer to be 64-byte aligned”The header that declares the packing functions states, as a caller obligation, that the buffer's address must be a multiple of 64.
“std::vector<uint16_t> guarantees only alignof(uint16_t)”The standard container used for the buffer promises far less alignment than 64 (in fact 16 on this platform — the comment under-states the guarantee, which changes nothing: 16 < 64 either way).
“each slice is exactly 4096 bytes, every query inherits the base misalignment”Each token's part of the buffer starts at a multiple of 4096 bytes from the base. 4096 is a multiple of 64, so if the base is off by 16, every token's part is off by exactly the same 16.
“TILELOADD can repeatedly straddle cache lines”The AMX load instruction reads the buffer in 64-byte rows; when the address is off by 16, every such row spans two 64-byte cache lines, making each read touch twice as many lines.

Claim-by-claim verdict at head

claimverdictwhat the code actually does at head
The interface requires 64-byte alignmentTRUEBoth packer contracts state it: pack_q_group_128x4 — “packed must hold Q_PACK_ELEMS_2048 bf16 (4 KB), 64B-aligned, with columns 4..15 of every panel already zero” (amx_attn_iface.hpp:192–193); pack_q_rows_128x4 — “must hold 16 * 128 bf16 (= Q_PACK_ELEMS_2048, 4 KB, 64B-aligned)” (:252–253). The requirement predates the comment and survived all three later commits.
vector guarantees only alignof(uint16_t)PARTLYUnder-stated but immaterial: operator new guarantees __STDCPP_DEFAULT_NEW_ALIGNMENT__ = 16 on this toolchain (measured; clang++-19, gnu++23), not 2 — still short of 64.
4096-byte slices propagate the base residueTRUEQ_PACK_ELEMS_2048 = 16 × 128 = 2048 uint16 = 4096 bytes, pinned by a static_assert (iface:130–131); slice base = data() + ix * 2048 (1417–1418).
Misalignment actually occursTRUEProbed on this host's glibc (internal round-5 probe): a vector<uint16_t> resized to 4 KB–1 MB landed at data() % 64 = 48 or 16 depending on size, never 0. Below glibc's ~128 KB mmap threshold the residue depends on heap history (0 only by accident); at or above it — the full llama-family buffer is 512 KB — it is deterministically 16 mod 64. The thread-local buffer keeps the alignment of its largest resize for the thread's lifetime, so an unlucky base is permanent.
TILELOADD straddles cache linesTRUEWhen misaligned, every 64-byte tile row spans two cache lines: 4 Q-tile loads × 16 rows = 64 split row-reads per (token, dense page). TILELOADD has no architectural alignment requirement (Intel SDM) and the packers store with scalar writes/memcpy — no aligned-form SIMD instruction ever touches this buffer — so this is a performance and contract-hygiene defect, not a latent crash. The unit tests pass alignas(64) stack buffers (t_amx_numerics.cpp), so they can never surface it.

Reply to r3858305367 — POSTED 2026-08-31 as r3896108631 (plain-English form, verbatim)

Agreed, and fixed in 60d66d9c04. Both packer contracts require a 64-byte-aligned
4 KB buffer (amx_attn_iface.hpp:192 and :253), and this was the only 64-byte
contract in that header we did not honor: the `o` and `s` buffers get
`alignas(64)` storage (self_attention.hpp:1577, 1655), while the pack buffer was
a plain `std::vector<uint16_t>`, which only carries operator new's 16-byte
guarantee. We probed it on our glibc: the vector's base landed 48 or 16 bytes
past a 64-byte boundary depending on size, never on one. A thread keeps the
alignment of its largest resize, so a bad base was permanent for that thread.
The slices are 4096 bytes each, so every token inherited the same misalignment,
as you said.

The fix is the aligned-storage variant you suggested, in vector form: the
element type becomes `struct alignas(64) amx_qpack_slot { uint16_t
v[Q_PACK_ELEMS_2048]; }`. C++17 routes over-aligned element types through the
aligned operator new, the slot stays exactly 4096 bytes, and the vector's
zero-fill on growth preserves the padding-must-stay-zero contract. All five AMX
and attention test binaries pass on the production CPU.

Two calibrations, now with the number you would want. First, nothing could
crash: the buffer is only read by TILELOADD, which has no architectural
alignment requirement, and the packers store with scalar writes and memcpy.
Second, we measured the split-row penalty you predicted, with an A/B run of the
real qk_mirror kernel at a packed-Q base of +0 vs +16 bytes: the misaligned base
costs +9.3 ns per page (+10.6%) when the K page is hot in L1 cache, +3.2 ns per
page (+0.5%) with a 512-page K ring resident in L2, and is within noise at RAM
residency. Real, small, and gone with the fix.

7. Glossary

tron / rinzler
The inference program this repository builds / its production server binary.
AMX / tile
Intel Advanced Matrix Extensions: instructions that multiply small matrices held in eight on-core tile registers, configured by LDTILECFG and cleared by TILERELEASE.
