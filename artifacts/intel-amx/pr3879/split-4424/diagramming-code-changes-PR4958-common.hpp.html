Short version

PR 4958 (tron pull request 4958, the third of four PRs that split PR 4424) lets the idle helper threads of a generated plugin share the K store of a forward pass with the main thread, and stores a run of 2 to 16 consecutive tokens of one 16-token block as whole 64-byte lines (store_block) instead of one scatter per token. In common.hpp the PR adds one data model: batch::k_store_window_t, the K store window of one minibatch (one window per layer and pass). It holds the claim counter next_unit, the window counter opened, the helper counter finished, the unit count n_units, the unit table unit_start and the per-helper table helper_windows. The protocol that uses them is in model.hpp (Note [Shared block save]). This page draws the window's data model, who reads and writes each field, the field values through one window, the three threads over wall-clock time and the work-unit invariants (section 1), then shows the one logical change of the file (the new struct and its member) beside two diagrams (section 2).

The four PRs of the split, one line each (a run = the consecutive tokens of one pass that land in the same 16-token block of a page)

  • PR 4956 changes how one K row is stored (scattered into the VNNI plane instead of written as a row) and how the CPU reads it (the AVX-512 reader instead of the row-major dotter).
  • PR 4957 changes who scores a full page (the AMX tile kernel reads the VNNI plane as its B operand) and how the queries are packed for it.
  • PR 4958 changes how a run of tokens is written (a 16-token block at once, transposed in registers) and which threads write it (the idle helpers share the store). (this PR)
  • PR 4959 changes what a run shorter than a block saves (row-major rows) and when that block turns VNNI (at the end of the pass that completes it, or never under hardware attention). It also turns the option on in the deb package.

COMMON-B1. Data model: batch, k_store_window_t, work units, cache lines

One batch (a minibatch) owns one K store window. The window holds three counters, a unit count and two tables. A work unit is a run of consecutive items in one 16-token block of one page. The bottom row shows the memory placement: next_unit and opened each start a cache line, so a claim does not invalidate the line the waiting threads poll. Every arrow says how many. The worked example's tables are at the lower left.

COMMON-B2. Function model: callers, save_k and its helpers, the fields each one touches

The generated plugin calls save_k from run() (main, worker 0) and from run_main_help (each helper, its worker_ix) at the same statement position. One save_k_impl serves both sides and calls k_store_shared, k_store_cut_units (main only) and store_k_block (once per claimed unit). The right column lists, per field, who reads and writes it and with which memory order.

COMMON-B3. Sequencing model: the window fields through one shared save_k window

The field values after each step of one window of the worked example: main cuts, resets and opens; the helpers count their window and wait for opened; all three claim with fetch_add and store; the helpers bump finished; main joins and marks. The two release / acquire edges (opened, finished) are named under the table.

COMMON-B4. Interaction model: main, two helpers and the attention workers over wall-clock time

Wall-clock lanes of one shared window: the helpers wait for opened, the three stores overlap, main waits for finished and then marks the tokens, which releases the attention workers' pending sections. Main's serial part (the cut, the open, the join wait, the marks) is the critical path. Durations are schematic.

COMMON-B5. The work-unit invariants: what ends a unit, disjoint lanes, full-line stores

Three cases on one 16-token block: a run of 16 fills the block (one full-line store per pair row); a job without KV work between two items ends the run; items of one block that are not consecutive fall into several units whose writers touch disjoint lanes (masked stores). This is why two threads may write one block without conflict.
