Short version

PR 4958 (tron pull request 4958, the third of four PRs that split PR 4424) makes save_k in model.hpp store K in 16-token blocks and share that store with the idle helper threads. save_k is the function that stores the K rows (the keys of one attention layer) of one minibatch into the KV cache (the paged store of keys and values). With the VNNI K layout of PR 4956 (the pair-interleaved layout the AMX tile multiply reads), a run of 2 to 16 consecutive tokens of one 16-token page block is now stored as one block (set_k_block: a register transpose, then 64-byte line stores, masked to the present tokens when the block is partial), a run of one token keeps the per-row scatter (set_k_row), and the store of a minibatch with more than 16 items is shared with the idle main helper threads (2 to 128 workers) through a window of work units (Note [Shared block save]). This page draws the data model, the call graph, the window protocol, the threads over one layer and the store decision once (section 1), then each of the eight logical changes of the file beside its diagram (section 2).

The four PRs of the split, one line each (a run = the consecutive tokens of one pass that land in the same 16-token block of a page)

  • PR 4956 changes how one K row is stored (scattered into the VNNI plane instead of written as a row) and how the CPU reads it (the AVX-512 reader instead of the row-major dotter).
  • PR 4957 changes who scores a full page (the AMX tile kernel reads the VNNI plane as its B operand) and how the queries are packed for it.
  • PR 4958 changes how a run of tokens is written (a 16-token block at once, transposed in registers) and which threads write it (the idle helpers share the store). (this PR)
  • PR 4959 changes what a run shorter than a block saves (row-major rows) and when that block turns VNNI (at the end of the pass that completes it, or never under hardware attention). It also turns the option on in the deb package.

MODEL-B1. Data model: the minibatch, the K store window, the page and the work unit

A batch holds the items of one minibatch (token jobs), each at one page offset. The PR adds batch::k_store_window_t in common.hpp (the claim counter next_unit, the counters opened and finished, the unit table unit_start and the helpers' window counters helper_windows) and the constants of the store in model.hpp. Every arrow says how many. The worked example is one shared window of 41 items with 3 workers (main and 2 main helpers): units [0,16) [16,32) [32,41).

MODEL-B2. Function model: save_k, its helpers, and what they call in the page

save_k (two overloads) calls save_k_impl. save_k_impl decides the sharing (k_store_shared), cuts the units (k_store_cut_units), stores the runs (store_k_block) and marks the tokens. store_k_block calls page::set_k_block (a run of 2 to 16 tokens), page::set_k_row (a run of one token) or page::k(...).set (a row-major slot). The generated plugins call save_k from run() (worker 0) and run_main_help (the helpers). Every cell says in one line what the function does.

MODEL-B3. Sequencing model: one shared save_k window, step by step

The ordered steps of one window, each citing the line that does it. Main cuts the units, resets the counters and opens the window (release on opened). Each helper waits for its window number (acquire on opened). Every thread claims units with fetch_add on next_unit and stores them. Each helper increments finished (release). Main joins (acquire on finished) under a watchdog. Main marks the tokens, credits the GOFs and counts the downstream latches down.

MODEL-B4. Interaction model: threads over one layer and the forward end (wall-clock lanes)

One lane per thread: main, the two main helpers of the worked example, the attention workers, and the forward end. Solid blocks are work, dashed outlines are waiting. The critical path (main's serial part) is marked with a thick red frame. Durations are schematic. The order and the overlap are what the diagram shows. The two numbers quoted (0.86 ms per layer before, 80 us after) come from the comment of Note [Shared block save] and from the PR body.

MODEL-B5. Decision model: what one run of tokens becomes in the page

For each run of consecutive items in one 16-token block of one page, three cases. A row-major slot stores one row per token and KV head through page::k(...).set. A VNNI slot stores a run of one token with set_k_row (the per-row scatter: 4 bytes into each of the token's 64 lines) and a run of 2 to 16 tokens with set_k_block (one block, the present mask naming the lanes: whole-line stores when the mask is full, masked line stores otherwise). The sharing of the store is a separate decision (k_store_shared), drawn at the top.

comment only head lines 3075-3136 +62 / -0 lines

Commits that last touched these lines (hover for the subject): bb342d9033

  • Comment text only. It is the design record the code below follows, so it is listed first and shown in full.
  • The problem (3077-3086): with the VNNI K layout and one set_k_row scatter per token on the main thread alone, the K store is the main thread's largest serial piece of work in a prefill layer. The measurement of 2026-09-14 on the test server delphi-3bda (qwen3-4b, 8 users, prompt 1024, 128 tokens of each user per pass) gave 0.86 ms per layer, 105 ns per (token, KV head) row. The attention workers' pending sections wait behind it.
  • The two remedies (3087-3101): the block save (store_block, page::set_k_block: a run that fills part or all of one 16-token block is transposed in registers and written as whole 64-byte lines, chosen per run in store_k_block), and the sharing with the main helpers (the generated run_main_help calls save_k at the same statement position with the helper's worker_ix; every thread claims work units until none is left; n_workers == 1 never shares).
  • The window protocol (3102-3128): both sides decide with k_store_shared; main cuts the items into units, zeroes next_unit and finished and increments opened (release); a helper's W-th call waits for opened >= W (acquire); every thread claims units with fetch_add on next_unit; a helper increments finished (release) when its claim loop ends; main returns only when finished == n_workers - 1 (acquire); the per-token completion marks and GOF credits stay on main after the join.
  • Why the join cannot deadlock (3129-3136): main waited for every token's K channel before save_k, the channel phase cannot advance while main is inside save_k, and nothing blocks a helper between its K/Q rope kernel and its save_k call. A join that does not complete within about two minutes (k_join_timeout_s after the first clock read) aborts with the counters in the message.
