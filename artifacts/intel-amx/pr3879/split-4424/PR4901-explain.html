K row, KV page, 16-token block, KV head
A K row is one token's key vector (128 values in bf16, the 16-bit floating-point format, for the heads this PR concerns). A KV page (KV: the key and value cache of the attention layers) holds 64 tokens. The page is split into four 16-token blocks for the K layout. A KV head is one key/value head of an attention layer, shared by several query heads.
VNNI layout, row-major block, plane, tail block
The VNNI layout (VNNI: Vector Neural Network Instructions) is the pair-interleaved order of a K block that the AMX (Intel Advanced Matrix Extensions, a CPU instruction set) kernel reads in place. A block holds its rows row-major (one row after another) until all 16 rows are saved and the block is converted. The page records which blocks are converted in k_vnni_blocks_, one bit per block. A plane is the K storage of one KV head for one page (16 KiB). The tail block is the last, not yet complete 16-token block of a page.
slot, geometry, book, EAGLE storage view, state entry
A slot is the K/V storage of one model layer (the uniform layout has one logical slot per active layer). A logical slot is a slot as the model addresses it, and a physical slot is where the book stores it. A slot's geometry (kv_geometry) is its number of KV heads and its head size. A book is the object that owns one KV cache's pages and storage. EAGLE is the draft model of speculative decoding (a small model proposes several tokens, and the main model checks them in one pass). EAGLE's K/V storage is one extra physical slot past the logical slots. While the EAGLE view is selected, logical slot zero maps onto that extra slot. k_state_ix(slot) returns the index of a slot's K layout state (its own index, or the extra entry for the EAGLE storage).
Note [...], the consumers list, the forward end, staging gather
A Note is a named comment block in the code, and other comments refer to it by its bracketed name. The consumers list is the numbered list of readers of a VNNI slot inside the Notes of kv_cache.hpp. The forward end is the end of one forward pass. A forward pass is split into minibatches, and the staging gather copies each minibatch's K rows into the buffer that the FPGA (field-programmable gate array card) attention reads.
KV restore, chunk
A chunk is a run of whole pages of a sliding-window slot's storage, allocated and freed as one unit. A KV restore re-allocates the reclaimed chunks of a book. It has a prepare step and a publish step (finish or abort).
syntax cell, the matrix, the step-4 check

Q3. What does (void)slot; do? removed in B

if constexpr (!k_vnni::layout_on<geometry.head_size>) {
  (void)slot;
  return BLOCK_COMPLETED_FALSE;
}
"what does (void)slot; do ?"

What it does. It is an expression statement that casts the parameter slot to void and discards the result. No code is generated for it (measured: identical assembly with and without, g++ and clang, -O0 and -O2). Its only purpose is to count as a use of slot. That use keeps the compiler's unused-parameter warning silent. That warning is -Wunused-parameter. clang turns it on with -Wextra, and GCC turns it on with -Wall -Wextra together. The project passes both flags [CMakeLists.txt:584].

Here it is not needed. if constexpr discards only the statements inside its own braces. The statements after the closing brace are compiled in every instantiation, and the first of them is const size_t ix = k_state_ix(slot);, which references slot [kv_cache.hpp:2171-2175]. So every instantiation references the parameter, and the cast is dead.

Q7. What runs behind f.template operator()<geometry>()? explanation

"what code got called by f.template operator()<geometry>() and f.template operator()<layout_t::primary_geometry>() ?"

The short answer. Both calls run the body of the lambda that the caller wrote, with geometry set to the given value. f is a C++20 lambda with an explicit template parameter list, [&]<kv_geometry geometry>() { ... }. Its call operator is a member function template, and f.template operator()<G>() is the explicit way to call it with G as the template argument. There are two such lambdas in the file:

  • In k_block_to_vnni_at: for every KV head, convert block c of the slot's plane to the VNNI layout with block_to_vnni, then set converted = true [kv_cache.hpp:2227-2235].
  • In k_forget_row: for every KV head, convert block c back to row-major with block_to_rows [kv_cache.hpp:2578-2586].

Why the word template is there. Inside k_with_storage_geometry the type of f is the template parameter F, so f.operator() is a dependent name. Without the keyword the parser reads f.operator()<geometry>() as a less-than comparison. Measured: without it, clang 19.1.7 says missing 'template' keyword prior to dependent template name 'operator()', and g++ 11.4 reports two errors at the same line. The same keyword appears for the same reason in for_each_active_slot and for_each_slot_impl [kv_cache.hpp:1696, 1704].

Branch 1, a logical slot. The slot's geometry sits in the constexpr array layout_t::slot_specs, but storage_offset.i is a run-time number. So the code cannot index the array and get a compile-time geometry. It unrolls over all slots instead. for_each_active_slot calls for_each_slot_impl. Its fold expression expands at compile time into one call per slot, with that slot's index and geometry as template arguments [kv_cache.hpp:1693-1706]. Each unrolled copy runs two run-time compares, slot < active_slots and slot == storage_offset.i, and exactly one copy passes the second and calls f [kv_cache.hpp:1704, 2529]. The walk does not stop at the match. For a 32-layer model, with one slot per layer and two compares per slot, that is 64 comparisons in the source (est.: a 32-slot stand-alone copy of the same three functions, compiled at -O2, kept 63 to 64 of them and built no jump table).

Branch 2, the EAGLE storage. The EAGLE storage is one past the logical slots and has no descriptor in slot_specs [kv_cache.hpp:1092-1095, 963-964]. So the function calls f with layout_t::primary_geometry directly [kv_cache.hpp:2532]. primary_geometry is pinned to slot zero's geometry by a static_assert [kv_cache.hpp:868-869, 953], and kv_block_at_storage asserts the same at run time for such an offset [kv_cache.hpp:1791-1795].

Why the geometry must be a compile-time value. kv_block_at_storage<geometry> reinterprets the slot's bytes as a struct whose k member type depends on head_size: a k_vnni_tensor when the layout is on, a plain bf16 array otherwise [kv_cache.hpp:2997-3007]. Only k_vnni_tensor has as_view() [h/tron/tensor/k_vnni.hpp:215], so the if constexpr (k_vnni::layout_on<geometry.head_size>) gate inside the lambda must be a constant to discard that line for a row-major geometry. block_to_vnni also keeps a bf16 rows[16][Cols] copy on the stack, which needs Cols at compile time [h/tron/tensor/k_vnni.hpp:506-517].

Q9. The {} after k_vnni_blocks_ explanation

std::array<std::atomic<uint8_t>, layout_t::n_slots + EAGLE_STORAGE_SLOTS_1>
    k_vnni_blocks_{};
"how come "{}" can be part of variable name? Is it allowed in modern C++?"

The braces are not part of the name. k_vnni_blocks_{} is the name followed by an empty braced initializer. C++ lets a class member carry its own initializer in its declaration (a default member initializer). Empty braces ask for an empty initialization: 0 for a number, null for a pointer, and element by element for an aggregate such as std::array. This has been legal since C++11, and the project compiles as C++23 [CMakeLists.txt:55].

int x;    // no initializer: a local or a member holds an indeterminate value
int x{};  // empty braces: x is 0

What it does for this member. Each element is a std::atomic<uint8_t> (uint8_t: an 8-bit unsigned integer), one byte per storage slot, used as a bit mask with one bit per 16-token block [kv_cache.hpp:2623-2627, 2516-2519]. With the braces every byte starts at 0 under every language version. Without them the answer depends on the version. Since C++20 (by the C++ committee paper P0883) the default constructor of std::atomic sets the value to 0, and before C++20 it left the byte uninitialized. The project's libstdc++ (the GNU C++ standard library) 14.3.0 writes this as _M_i _GLIBCXX20_INIT(0), a macro that expands to = 0 for C++20 and later and to nothing before [bits/atomic_base.h:348, 162-166]. Measured with a demo that constructs the array into memory pre-filled with 0xFF: C++17 without braces prints 255 255 255 255, with braces 0 0 0 0, and C++20 and C++23 print 0 0 0 0 either way. The braces make the zero start explicit and independent of the version.

  • Neither page constructor names k_vnni_blocks_ in its initializer list, so the {} runs in both [kv_cache.hpp:1956-1958, 1962-1976]. The move constructor then stores each element from the source page in its body [kv_cache.hpp:1962-1976].
  • The sibling members use the same form: kv_saves_{} predates this PR, and k_rows_saved_{} was added by it [kv_cache.hpp:2610-2611, 2621-2622]. So the braces follow the class's existing style.
  • One caveat for other types: for a class with a hand-written default constructor, {} runs that constructor, and members it does not set stay indeterminate (measured: every byte read back as 255). std::atomic's constructor is = default, so the caveat does not apply here [libstdc++ 14.3.0 atomic:763].

Q11. What does ~uint64_t{} return, and why not ~uint64_t{0}? changed to {0}, in A

const uint64_t range = count == page_size
                           ? ~uint64_t{}
                           : (k_vnni::offset_bit(count) - 1) << dst_begin;
"what does ~uint64_t{} return?"
and, after the first answer: "why not ~uint64_t{0} ?"
and then: "change to ~uint64_t{0}"

What it returns. uint64_t{} is a 64-bit unsigned integer built from empty braces, which is 0. ~ is the bitwise complement. So the result has every one of the 64 bits set: 0xFFFFFFFFFFFFFFFF, decimal 18446744073709551615, the largest uint64_t. It equals std::numeric_limits<uint64_t>::max() and UINT64_MAX (measured with both compilers, g++ 11.4 and clang 19.1.7). The type stays uint64_t. A narrower type would give an unexpected result: ~uint8_t{} is promoted (widened by the C++ integer promotion rules) to int first and gives -1.

Why the special case exists. range is the mask of the destination page offsets the copy overwrites, one bit per offset [kv_cache.hpp:2717-2721]. For a partial copy it is count ones shifted up to dst_begin (the first destination offset of the copy), built from offset_bit(count) - 1 with offset_bit = uint64_t{1} << offset [h/tron/tensor/k_vnni.hpp:101-105].

When count equals the page size of 64 tokens, that branch would shift by 64 bits. C++ defines a shift only for a count smaller than the width. So a shift by 64 is undefined behaviour (the C++ standard sets no result for it, and the compiler may produce anything).

The compilers reject it in a constant expression (an expression the compiler evaluates at compile time), and they warn for a literal 64. For a run-time count, as here, neither warns (measured).

Executed anyway, the unguarded expression gave three different outcomes: 0 under g++ and clang at -O2, both 1 and all-ones within one clang run, and an abort under the undefined-behaviour sanitizer (a run-time checker for undefined behaviour).

With the outcome 0, new_saved (the saved-row bits the copy writes to the destination page) would equal dst_saved (the destination page's saved-row bits before the copy) [kv_cache.hpp:2720-2721]. The destination page would then keep stale saved-row bits, and its block bits would come from the source [kv_cache.hpp:2737-2739]. So the full mask is written directly.

  • No existing 64-bit constant fits: k_vnni.hpp has FULL_BLOCK_0XFFFF (16 bits, one per token row of a block) and BLOCKS_PER_PAGE_MASK_0XF (4 blocks) only [h/tron/tensor/k_vnni.hpp:83-96].
  • The layout test builds the same mask for the same n == 64 case (a whole page of 64 tokens) as ~uint64_t{0} [t/t_k_vnni_layout.cpp:391].
  • k_forget_row (the function that drops the saved-row bits at and above one page offset) has no such case. Its offset is below 64 (the page size in tokens) by the assert in clear_kv_complete_at (its caller, which clears the completion state of one page offset) [kv_cache.hpp:2474-2478]. So offset_bit(offset) - 1 is always defined there [kv_cache.hpp:2559].

Why not ~uint64_t{0}?

There is no technical reason. uint64_t{} and uint64_t{0} are the same zero of the same type. Empty braces value-initialize the integer, and for an integer that means zero. Braces around 0 initialize it from the literal 0. The complement of either is the same all-ones value, of type uint64_t, and both are constant expressions. Measured: a file of static_asserts compiles under g++ 11.4 and clang 19.1.7 with -Wall -Wextra -Wpedantic. The file compares the two spellings with each other, with UINT64_MAX and with std::numeric_limits<uint64_t>::max(). It also checks that both have the type uint64_t.

The difference is what the reader sees. {0} shows the zero. {} asks the reader to know that empty braces mean zero. Your Q9 and Q11 both asked about that spelling. No reason for the choice of {} is recorded in the PR, its commits or its comments. Most sites in the tree use the explicit spellings. In code lines at the head (comment mentions excluded):
