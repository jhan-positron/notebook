Tracking decode regression through logits comparison, the path from logits to a token, and what a floating-point tie means

Written 2026-10-11 for jhan. The worked example is the token-247 probe of PR #4887. Paths that start with exec/ or definitive-decode/ are relative to /home/jhan/workspace/intel-AMX. Source paths (h/, src/, t/) are relative to the tron tree at commit 0ee8671d35, checked out at /home/jhan/workspace/ai-runs/tron-split-pr2. The layer count (36) and the hidden size (2,560 values) come from the model description. The vocabulary size (151,936 tokens) is the length of every "Logits" record in the probe. Every number comes from exec/results/p247-20261011 (steps-new-vs-newoff.json, verdict.txt, tokens.txt, runs.txt), from exec/results/pr2-20261011 (the smoke run, tests-pr2.txt, mutation-result.txt), from the body of PR #4887, or from the September study (the earlier investigation of a token flip at step 22 under the previous AMX kernel, written up in definitive-decode/token30-results.html). Source lines cite the tree at commit 0ee8671d35.

Short version. At generated token 247, the PR-2 binary (the pull request under review) with AMX (a CPU matrix instruction set) on scored two candidate tokens exactly equal and took the lower token id, and the same binary with AMX off scored them one bf16 notch (the smallest step of the 16-bit score format) apart, with token 624 higher. The probe fed both binaries the same token list and showed that this step is an exact tie, the limiting case of a near tie, and not a defect. The two arithmetic paths differ at every step by notch-sized amounts, and only a tie turns such a difference into a different token.

The five sections answer five questions in order:

  • what happens after a flip (a step where the two runs pick different tokens), and whether the runs can produce the same tokens again later.
  • the exact path from the last layer to a token.
  • whether recorded reference values make a good regression check.
  • what the probe decided, and what "correct decode" means.
  • whether the AMX rounding difference caused the flip.

Words used here

tron, runtron
tron is the inference program under test. runtron is its command-line tool.
AMX, AVX-512, kernel, FPGA
AMX and AVX-512 are two CPU instruction sets. AMX multiplies small matrices held in tile registers (a CPU register of 16 rows by 64 bytes). AVX-512 works on vectors of 16 numbers. A kernel is a compute routine written for one instruction set. An FPGA (field-programmable gate array) is the accelerator card that tron uses for the large matrix multiplies.
attention, query
Attention is the part of each layer where the current token's query vector is scored against the key vectors of all past tokens, and the scores weight the value vectors of those tokens. The query is the current token's vector in that scoring.
KV cache, K, V
The stored key (K) and value (V) vectors of every past token in every layer. Each new token reads them and adds its own.
PR 4424, PR-1, PR-2, packed K layout
PR 4424 is the original, larger pull request of this work. It was divided into parts. PR-1 is the first part (#4868, commit 82d05e94be). It introduces the packed K layout (a new memory arrangement of the cached key vectors) and an AVX-512 routine, the reader, that scores keys stored that way. PR-2 is the second pull request (#4887, commit 0ee8671d35). It adds the AMX kernel that scores keys in that layout.
page, dense page
A page is a 64-token block of the KV cache. A dense page is a full page that the query sees whole. It also lies inside the sliding window (the span of recent tokens the model may attend to). Only dense pages take the AMX kernels. With AMX on, a dense page uses the AMX kernels. With AMX off, the reader scores the page.
new, newoff, head
new is the PR-2 binary with AMX on. newoff is the same binary run with TRON_AMX_DISABLE=1 (the kill switch, an environment variable that turns AMX off at run time). head is the PR-1 binary. It has no kill switch set. It also has no AMX kernel for the packed layout. So the reader scores every page in it too.
the probe
The forced-run experiment of 2026-10-11 (four runs and their step-by-step comparison, diagram B in section 4).
bf16, fp32, notch
bf16 is a 16-bit number format with 8 significant binary digits, about 2 to 3 decimal digits. fp32 is the usual 32-bit float. A notch (one ulp, unit in the last place) is the distance between two adjacent bf16 values at a given size. Around 26.6 a notch is 0.125. Around 10 it is 0.0625.
score, logit, executor
The score (logit) is the number the model gives each of the 151,936 vocabulary tokens at one step. The highest score wins under greedy decode. The executor is the set of tensor types tron is built with for one run. It fixes where each matrix lives and its number format. The executor used here (tp2, named for tensor parallelism 2, defined below) stores these scores as bf16.
token, position, step, flip
A token is one piece of text, roughly a word, with an integer id. Positions count from 0 in the token files. So "token 247" is the 248th generated token. The comparison script (exec/dd/dd_logits_step.py, the per-step comparison box of diagram B) counts steps from 1. So that token is step 248 there. A flip is a step where two runs pick different tokens.
greedy decode, temperature
Temperature is the sampling setting that controls randomness. Temperature 0 removes it. That setting is called greedy decode. Under greedy decode the token with the highest score is taken at every step. On an exact tie the lower id wins [h/common/top_k_accum.hpp:84-88].
margin, near tie
The margin is the gap between the best and the second-best score at one step. A near tie is a margin of a few notches. An exact tie is a margin of 0.
free run, forced run
A free run chooses its own tokens. A forced run takes its next token from a given list instead (runtron --force-feed-text-token-file). The scores are still computed at every step. So two runs fed the same list score the same context at every step.
layer, FFN, RMSNorm, residual add, embedding vector
The model computes in 36 stages (layers). Each layer has an attention part and a feed-forward part (FFN). The residual add adds a layer's input back to its output. RMSNorm (root-mean-square normalization) is the normalization step. The final RMSNorm feeds the language head. An embedding vector is the learned numeric vector that stands for one token id at the model's input.
language head (wcls)
The matrix multiply that turns the final 2,560-value vector into the 151,936 scores. In tron it is the wcls matrix. That matrix is a device tensor (stored on the accelerator, not in CPU memory). So the multiply runs on the FPGA devices.
top-k accumulator, top-p
The accumulator keeps the best 320 (score, id) pairs while the scores stream in, then sorts them best first. Top-p sampling is a random draw among the best tokens whose probabilities add up to p. It is not used in the probe.
the model, tensor parallelism
Every run uses Qwen3-4B-Instruct-2507 (36 layers, hidden size 2,560 values, vocabulary 151,936 tokens) with tensor parallelism 2 (its matrices split across two FPGA devices).
smoke, cell
A smoke is a short one-user greedy run compared token by token between binaries. A cell is one test configuration. The smoke of 2026-10-11 ran three cells: CPU attention at prompt length 1,024 tokens, CPU attention at 8,192 tokens, and FPGA attention at 1,024 tokens.
QK, PV weights, add order
QK is the query-key score product of attention. The PV weights are the attention probabilities P that multiply the values V. The add order is the sequence in which fp32 partial products are summed. Different orders give different rounding.
AVX dotter, identity case, mutation check
The AVX dotter is the AVX-512 dot-product loop that scores row-by-row keys in the main branch. The unit test t_amx_numerics uses it as the reference for the main-branch AMX QK kernel (qk_rowmajor_128x4, the kernel that reads row-major K), within a documented band [t/t_amx_numerics.cpp:173-216]. The new packed-layout kernel is checked against that kernel bit for bit instead (the identity case). The PV kernel is checked against an exactly rounded weight reference [t/t_amx_numerics.cpp:8-13]. The identity case is the t_amx_numerics test case that checks that the new kernel reproduces the main-branch AMX kernel bit for bit. A mutation check is a deliberate code change that a test must catch.
GOLD values, canonical build
GOLD values are a stored reference that later runs are compared against. The canonical build is the unmodified AMX build of the September study.
mean |delta|, fraction changed, TVD, relative L2
Per step, over all 151,936 scores: the mean absolute difference between two runs, the fraction of scores that differ at all, and the total variation distance (half the sum of absolute probability differences, between 0 and 1) of the two runs' probability distributions over the next token. Relative L2 is the length of the difference vector divided by the length of the reference vector.
control
A comparison whose outcome is known in advance. It checks the method, not the question. R3c is the September study's control run that changed only the core count, with AMX off.
record, label, plugin
With --intermediates-file, tron writes selected values to a text log, one line per (label, layer, token). Labels used here, each written as "<label> of token N" in the log: "Logits", "Top-k Logits", "Top-k Token IDs for Logits" (diagram A shortens the last one to "Top-k Token IDs"). The probe's filter "Logits of token" therefore keeps all three records, 768 lines for 256 tokens [runs.txt]. The plugin is the per-model-family C++ code of tron (h/tron/plugins/llama.hpp for this model).
band, rollback contract, clean binary, issue #4444
A band is the allowed range of a difference. The rollback contract is what the kill switch promises to give back. The dispatch note in the code promises AMX off, the same layout, the same AVX dotter, and the numbers of a clean binary (a build with both the packed K layout and AMX dispatch off) [h/tron/kernels/amx_attn_iface.hpp:49-53]. Issue #4444 is the tron issue that tracks the token divergence of the packed-K binary and that contract.

1. Why every later token differed, and whether the runs could produce the same tokens again

Your reading: later tokens are decoded from earlier ones, so a different token 247 changes what follows. But the two candidates had almost equal scores. So the later differences might be small, and the "right" token might be chosen again later.

The first half is right. The second half mixes two different things: scores and tokens.

  • The chosen token id becomes the input of the next step. Its embedding vector enters layer 0, and its K and V vectors are written into the KV cache of every layer [diagram A in section 2, green boxes]. Every later step reads those vectors.
  • Tokens 13 and 624 (the two candidates at token 247) had equal scores in new, but they are different words. Their embedding vectors are unrelated, not one notch apart. So from step 249 on, the first step whose input is the differing token, the two runs process different text. The later per-token vectors inside the model differ as much as the vectors of two different words differ, not by one rounding step.
  • Neither token is the right one. The model's own arithmetic rated them equal on one path and one notch apart on the other. A greedy decoder has to pick one. The pick depends on the tie rule and on the last notch of rounding.

The data agree. After the flip, none of positions 248 to 255 matches between new and newoff. The texts do rejoin in content. new produced four tokens (13 358 198 19016) where newoff produced three (624 40 614). Both then continue with the same five tokens 3884 279 1879 504 279. The rejoin is one position apart. So a position-by-position comparison stays "different" for the rest of the run.

So: yes, later tokens can coincide again, in content. No, there is no later "correction". Neither choice was wrong. And no, the runs will not match position by position after one run inserts an extra token.

2. From the end of the last layer to a generated token

Your point: the sequence between the end of the FFN and a generated token was unclear.

Step by step, with the source:

  1. The last layer finishes its attention and FFN parts and the residual add. The final RMSNorm, in the model's plugin, produces a 2,560-value bf16 vector per token and stores it in final_embedding[j] (j is the token's job slot in the batch) [h/tron/plugins/llama.hpp:514, :1308-1309]. model.hpp declares that buffer and reads it as the input of the language head [h/tron/models/model.hpp:1155, :3398].
  2. The language head multiplies that vector by the wcls matrix (151,936 rows). The multiply runs on the two FPGA devices and streams its result back to the CPU in slices of the vocabulary. The result is 151,936 scores per token, held in the tensor logits_t. For the executor used here (tp2) that tensor is bf16 [model.hpp:1195, :1224-1227, :3416, h/tron/models/common.hpp:79, :95, h/tron/hardware/btensor.hpp:21].
  3. The scores are written to the model's own score tensor. The probe's "Logits of token N" record is written from that tensor, before the code branches by buffer type and before any patch [model.hpp:3508]. The code then branches by buffer type. A dense buffer (the caller asked for all scores) receives all 151,936 scores. The plugin may patch them (patch_logits) [model.hpp:3517]. A sparse buffer (the caller asked for only the best few) feeds the scores into the top-k accumulator as the slices arrive [model.hpp:3519-3533]. The probe's runs sample from the sparse path, which the generation code always requests [src/tron/generation/context.cpp:50].
  4. The top-k accumulator keeps the best 320 (score, id) pairs (max_top_k) [h/tron/generation/stats.hpp:16]. Its comparison is "higher score first, and on an exact tie, lower id first" [h/common/top_k_accum.hpp:84-88]. The sort returns them best first, and the "Top-k Logits" and "Top-k Token IDs for Logits" records are written here [model.hpp:3537-3539]. The plugin may then patch the sorted list in place before the sampler sees it [model.hpp:3546-3548].
  5. When the temperature is 0, or top_k is 1, or top_p is 0 (each means greedy decode), the sampler takes entry 0 of the sorted list [src/tron/generation/stats.cpp:133-135]. Otherwise it draws at random from the top-p set.
  6. In a forced run, the next id is taken from the given list and the sampler is not called [src/tron/generation/context.cpp:136-139]. The scores were already computed and recorded in the model before that point [model.hpp:3508, :3537-3539].
  7. The chosen id goes to the client as text, and it becomes the next step's input. During that next pass its K and V vectors are appended to the KV cache of every layer.

Two consequences matter for the probe.

  • The scores are bf16, with 2 to 3 significant digits. So two unrelated tokens can get exactly the same value near a score of 26, where one notch is 0.125. This run had 2 exact ties and 12 margins of 2 notches or less in 256 steps [steps-new-vs-newoff.json].
  • Both picks are deterministic. The tie rule makes the free run of new always take 13 at that step. newoff always takes 624. Its score for 624 is one notch higher there.

Why the AMX run took 13 and the AVX run took 624

Both runs use the same rule: the higher score wins, and on an exact tie the lower id wins. The rule gave different answers. Only one run had a tie. The table lists the four scores at that step [steps-new-vs-newoff.json, step 248].

RunScore of token 13Score of token 624WinnerRule that decided
new (AMX on)26.62526.62513exact tie, lower id wins
newoff (AMX off)26.62526.750624higher score wins, no tie
  • The score of token 13 is the same in both runs. The score of token 624 is one notch higher (0.125 at this size) with AMX off. The largest change of any of the 151,936 scores at this step is 0.171 (1.4 times the 0.125 notch of the top scores). That largest change sits at token 105663, a low-scoring token, not at one of the top scores [steps-new-vs-newoff.json, step 248]. So a one-notch change in the top pair is typical.
  • Each score is a dot product of the final 2,560-value vector with that token's row of the language-head matrix, stored as bf16. The two attention paths produce final vectors that differ by rounding-sized amounts (section 5 names the two causes). For token 624 that small difference crossed a bf16 rounding boundary. The stored score therefore moved up one notch. For token 13 it did not cross one.
  • The probe kept only the score records. Its script copied the "Logits of token" lines from the full intermediates log and deleted the rest [exec/pr2-20261011/probe247.sh]. So it does not say which entries of the final vector differed. The "Final embedding" record would show that in a re-run. The plugin writes that record per token after the final RMSNorm [h/tron/plugins/llama.hpp:1309]. The per-layer records (section 3) find the earliest layer where the two paths first differ.

3. Recorded reference values as a regression check

Your idea: record the scores and all bf16 values of the post-FFN steps once as GOLD values (a stored reference that later runs are compared against). On a later change, record again at run time and compare with GOLD, to find the earliest point where a bug started.

The idea is sound. The probe itself used exactly these tools. Four points decide whether such a check works.

  • Values are a better check than tokens. Token equality is a threshold on continuous scores. A one-notch change flips a tie and changes every later token. A real defect may instead be hidden by a large margin. The per-step statistics (mean absolute change, largest change, fraction changed, TVD) separate the two cases. At the probe's step 248 the mean change (0.040, median 0.038) and the largest change (0.171, median 0.19) are typical. The fraction changed (96 %, the 93rd percentile of the 256 steps) is high. The TVD (0.030) is the second highest of the 256 steps (median 0.0012). A high TVD at an exact tie is expected. Most of the next-token probability is shared by the two equal top tokens. A one-notch shift moves that probability from one of them to the other. Typical sizes of change plus a tie are what identify a near tie [verdict.txt, steps-new-vs-newoff.json].
  • Exact equality is the wrong test across intended arithmetic changes. Turning AMX on, changing the core count, or changing the K layout changes the add order. The September study measured that a core-count change alone, with AMX off, changed nearly every value of every one of the 36 layers from the first affected token on [token30-results.html, the R3c control]. Here new and newoff differ at every one of the 256 steps. Per step, 43 % to 99.6 % of the scores change (median 81 %, and 96 % at step 248). A bit-exact GOLD would therefore flag every such change. The comparison must use tolerances: changes in notches, relative L2 distance, TVD, and the count of flipped steps, with an expected band per path.
  • Record the layers, not only the last stage. The last stage of diagram A is where tokens are chosen. The arithmetic that differs between two paths sits in the attention of each layer. The records WQ roped, WK roped, WV and WO give that location. They are the per-layer outputs of the attention projections: the query and the key after the rotary position encoding (the rotation that writes the token's position into the query and key vectors), the value, and the attention output projection. In September the earliest difference was in the WO record of layer 0 of the first affected token. The script exec/dd/dd_first_divergence.py already finds the first differing (label, layer, token). The September study added an Attn out record (the attention result before the WO multiply) in its own instrumented build. That record proved unreliable. It differed between two identical AMX-off runs. So the study excluded it from every check [token30-results.html, caveats]. A layer-level GOLD check would need that record placed correctly, or the stable records alone. A defect shows as magnitude and shape (very large notch counts, a missing token or block, a difference that starts at one page boundary), not as the mere presence of a difference.
  • Force the context and fix the configuration. A GOLD comparison needs the same prompt, the same token list at every step (a forced run), the same model, the same core placement (which CPU cores the threads run on) and the same random seed. Otherwise the two runs stop scoring the same context at the first flip, and the later differences mean nothing.

A workable scheme is therefore two-level. At the unit level, keep tests against a reference within a documented band, as t_amx_numerics does against the AVX dotter. Demand bit identity only where the design promises it. At the run level:

  • keep one recorded forced run per configuration as the baseline.
  • compare with the statistics above.
  • refresh the baseline when a numerics change is intended.

The first-divergence scan then points at the earliest layer and label where the new run leaves the band.

4. What the newoff-versus-new probe decided, and what "correct decode" means

Your question: the goal seemed to be to tell whether two close values caused a different token. If so, what next? And does LLM (large language model) decode have a right answer at all?

The goal was to decide between two explanations of one observation. The observation: the smoke rule "newoff matches new" failed in one of three cells, at token 247. The two explanations:

  • A defect in the new kernel, for example a wrong panel address. That produces scores unrelated to the correct ones for every dense page. The signs would be an early divergence, large per-step changes, and many flipped steps. The mutation check shows what such a defect looks like: the identity case fails at the first wrong token.
  • Two legitimate arithmetic paths that differ by rounding. The signs are notch-sized changes at every step, a flip only at a near tie, and typical sizes of change at the flip step.

The probe found the second case: margin 0 notches at the flip, a one-notch change of that pair, typical changes elsewhere, and one flip in 256 steps (diagram B). What came next was documentation, not code:

  • The PR body states the measured identity in two cells and the exact tie in the third.
  • Its open item on issue #4444 records that the kill switch gives an AMX-off run of the same binary. It does not give the tokens of a clean binary.
  • The reviewers decide the wording of that rollback contract.

On correctness. Greedy decode has no single right token. The model defines a probability over the next token, and the implementation computes that probability with finite precision. Two implementations are both correct when each step's values stay within a documented distance of a reference, and when the generated text has the same quality on benchmarks.

A token comparison between two such implementations measures how often near ties occur, not which one is right. Here, 12 of the 256 steps have a margin of 2 notches or less. Two of them are exact ties. So a flip somewhere in 256 steps is expected whenever the paths differ at all. The chart shows this.

The useful correctness checks are therefore:

  • bit identity where the design promises it (the identity case of t_amx_numerics).
  • tolerance bands against a reference where it does not (t_amx_numerics against the AVX dotter).
  • the forced-run statistics for a whole run.
  • quality benchmarks for the product.

Token identity across different arithmetic paths is only a coarse indicator. Near ties make it unreliable.

5. Did the fp32-to-bf16 rounding difference cause token 247?

Your question: the AMX kernel differs from the AVX kernel in the fp32-to-bf16 conversion. Is that the cause?

For inputs that are finite and not subnormal (a subnormal is a float smaller than the smallest normal value, stored with fewer significant digits), the two paths differ in exactly two documented ways [h/tron/kernels/amx_attn_iface.hpp:77-85]:

  1. The PV weights, the attention probabilities, are converted to bf16 before the PV multiply. The AVX path truncates (drops the low 16 bits). The AMX path rounds to nearest even.
  2. The fp32 partial products are added in a different order, in QK and in PV.

For the QK step of this PR only the second difference exists. The new kernel's scores are bit-identical to those of the AMX QK kernel on the main branch (the identity case). The AVX-512 reader multiplies the same bf16 pairs, and each product is exact in fp32 on both paths [h/tron/kernels/k_vnni.hpp:53-54]. So the reader and the kernel differ by add order alone. For the PV step both differences exist.

This probe did not separate the two causes for token 247. It compared the whole path with AMX on against the whole path with AMX off. Insufficient data for that step alone: the two measurements at the end of this section would resolve it.

The September study did separate them for its flip at step 22, on the same model. Its AVX path was the AVX dotter of that time (the AVX-512 loop that scores keys stored row by row) [h/tron/kernels/amx_attn_iface.hpp:62, h/tron/kernels/k_vnni.hpp:53-54]. This probe's AVX path is the reader. The two documented differences are the same on both paths:

  • The truncation build (TRON_AMX_PV_TRUNC: the AMX path with AVX-style truncation of the PV weights) moved the scores by about the same amount as the canonical AMX build: the median mean change was 0.89 times that of the canonical build. It also flipped the same two steps (22 and 37) in the 64 steps compared. The rounding difference was therefore not the cause of the flip there. At the source (the WO record of layer 0) the rounding term was the larger local change, about 30 times the add-order term. End to end, after 36 layers, both terms produced score changes of the same size [token30-results.html, section "Where the AMX difference comes from: rounding vs addition order"].
  • A run with AMX off and two fewer cores changes only the add order. That run changed nearly every value of every layer, and it flipped the same tie. The add order alone is enough.

The conclusion that also applies here: a flip at an exact tie needs only the add-order difference, and the rounding difference neither prevents nor requires it. Two measurements would settle it for token 247:

  • Rebuild PR-2 with the PV weights truncated to bf16 instead of rounded. The numerics note in the kernel header (the comment block that lists the two differences, cited above) says this is a one-line change at the cvtne2ps_pbh call (the round-to-nearest-even conversion the AMX path uses now) [h/tron/kernels/amx_attn_iface.hpp:82-84]. Repeat the forced run. See whether step 248 still flips.
  • Run the per-layer first-divergence scan on the two forced runs. Compare the sizes of the PV-side and QK-side changes.

What this page does not cover

  • It does not measure the performance cells with 8 concurrent users. Those are in the PR body.
  • The September study ran on an earlier tree (the earlier AMX kernel that read K row by row, before the packed layout). The mechanism it found also applies here. Its numbers do not apply to this probe.
