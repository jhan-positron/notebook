Short version

PR 4956 (tron pull request 4956, the first of four PRs that split PR 4424) adds the build option TRON_K_VNNI (default OFF). With it on, the K plane (the stored keys of one KV head on one 64-token page) of every 128-dimension head is a typed owner (k_vnni_tensor) in the VNNI layout (the pair-interleaved value order that the AMX tile multiply reads as its B operand), instead of one row per token. In kv_cache.hpp the plane is reached only through typed views and typed operations: kv_block::k becomes k_storage, the row view page::k exists only for row-major slots, the new page::k_packed hands the read-only plane to the score reader, the new set_k_row / get_k_row move one token's row in and out of any slot, and page copies move a whole page as one owner assignment or any other range token by token. This page draws the data model, the two layouts, the call graph, the life of one token's K row and the thread timing once (section 1), then shows each of the seven logical changes of the file beside the diagram it alters (section 2).

KV_CACHE-B1. Data model: book, page, kv_block and the typed K plane

A book holds one storage slot per layer (plus one EAGLE storage), pages of 64 token offsets, and one kv_block per (slot, KV head, page). The PR types the K plane of a kv_block (k_storage: k_vnni_tensor for a VNNI slot, a bf16 array otherwise) and adds the page accessors that reach it. Every arrow says how many. The worked example (page 7, slot 5, KV head 0, offsets 0..40 saved) is the strip at the bottom.

KV_CACHE-B2. One K plane, two layouts in the same 16 KiB

The K plane of one (slot, KV head, page) is 64 tokens x 128 bf16 = 16 KiB in either layout. Native K is one 256-byte row per token. The VNNI plane is 16 panels of 1 KiB, one per (dimension step, token block), with one dimension pair of 16 tokens per 64-byte line. The layout is a compile-time property of the slot (k_vnni::layout_on). Under each layout are the accessors that reach it; page::k does not exist for the VNNI one.

KV_CACHE-B3. Function model: callers, page and book API, k_vnni.hpp operations

Each row is one call path through kv_cache.hpp: the caller in another file, the page or book function it calls, and the typed operation of h/tron/tensor/k_vnni.hpp that touches the bytes. Every function cell says in one line what the function does and cites its definition.

KV_CACHE-B4. Sequencing model: the life of one token's K row in a VNNI slot

Token 37 of the worked example: save_k stores its row through set_k_row and store_row (4 scatters into the token's column), then marks K complete. Three readers take the same bytes through typed views: the attention workers through k_packed and k_vnni::qk_group, the FPGA staging through get_k_row and load_row into a scratch row, and a page copy through copy_token or one owner assignment.

KV_CACHE-B5. Interaction model: which thread touches the K plane when

One forward pass of one layer and the tree work between passes, as lanes. The main thread writes the rows and counts the slot's latch down; the attention workers wait on that latch before they read; the GOF staging runs on idle workers between layers and on main at the forward end; page copies run in the scheduler's defrag under tree_lock. Durations are not to scale. The order is what matters.
