The picture

In one line: the writer cannot know who will read its slot, so it fills the mirror plane for every head-128 slot when an AMX reader could exist at all (bf16 executor), and leaves the ratio question to the reader.

"The save_k write-through gate:" save_k (save_k_impl, model.hpp:2751) stores each new token's K row into the KV page. "Write-through" = right after that store, the same row is also scattered into the K mirror plane (set_k_mirror, model.hpp:2796-2800). "a K row is mirrored when its slot has the kernels' head size and the model stores bf16 activations" Two conditions. (2) The executor's activation scalar is tron::bf16 (query_scalar_ok, 147-148). The second condition is about the readers: the AMX Q packers copy Q bits as bf16 without converting (141-146), so a host (float) or host_fp16 executor can never have an AMX reader. K itself is stored as bf16 in the page for every executor (kv_cache.hpp:2230), so this term is not about K; it means "an AMX reader can exist for this model at all".
"regardless of the WRITER operation's own query/KV ratio." Ratio = attention_geometry::kv_mul() = n_query_heads / n_kv_heads (kv_cache.hpp:156-158): how many query heads share one KV head. The AMX kernels serve ratio 4 only (shape_ok, 137-139). Before 323b9d5499 the gate was eligible(head_size, kv_mul) evaluated on the writing operation's geometry; the commit removed the ratio term, and nothing else.
"A valid attention configuration may share one KV slot between the operation that writes it and read-only consumers with other query-head counts (valid_attention_operation_descriptors in kv_cache.hpp)," The validator (kv_cache.hpp:284-311) lets several operations bind the same kv_slot as long as exactly one has writes_kv (line 308) and it is listed before the read-only ones (306). Operations sharing a slot must have the same KV geometry (valid_attention_configuration, 324-328), so the query-head count is the only thing that can differ. "May" means permitted, not present: all 17 registered plugins (llama, mock, 15 generated) have one writer per slot and writes_kv = true everywhere (uniform_attention_operations, kv_cache.hpp:385-397; generated operation arrays parsed: 0 read-only, 0 shared slots).
"and it is a consumer's ratio, not the writer's, that decides whether the mirror is read:" The read side evaluates eligible on the reading operation's own geometry (self_attention.hpp:1359-1361, 1507-1509), at compile time per operation (if constexpr (amx_eligible), 1563), and only then reads the plane (1574-1575) - if the arena exists, AMX is available, and the page is dense. So each operation that reads a slot decides by its own ratio; that includes the writer itself when it attends over its own slot.
"a writer of ratio 8 must still fill the plane a ratio-4 consumer reads." The concrete case (codex P1, PR3879-codex/review.md:18-24; test t_llama_unit.cpp:874-914): writer 8 query heads / 1 KV head / head 128, read-only consumer 4/1/128, same slot. The consumer's kernel makes amx_mirror_eligible true, so the arena gets allocated; before the fix the writer compiled no scatter; the consumer's dense-page path then read heap memory that operator new[] never initialised (kv_cache.hpp:1111) - wrong attention scores, no error. Latent: no registered plugin has this configuration.
"Whether the plane exists at all (the arena is allocated only when some kernel passes `eligible`, amx_mirror_eligible) is a runtime null check inside set_k_mirror." This gate is compile-time and cannot know whether the arena was allocated. That depends on four run-time facts: which book constructor ran (the 3-argument forms pass false, kv_cache.hpp:800, 1029; only the scheduler's path passes the real predicate), amx_mirror_eligible over the plugin's kernels array (true if any kernel passes eligible), amx_attn::available(), and the nothrow new succeeding (1106-1115). set_k_mirror (1628-1636) asks mirror() for the plane pointer and scatters only if it is non-null; the mirror_arena_ test itself sits in mirror_at_storage (1291). When the arena is absent each row costs a few predictable branches and no memory traffic.
"Planes of other head sizes are never read by a kernel, so save_k does not write them." The only production reader is self_attention.hpp:1574-1578, behind eligible (head 128). The arena does hold planes for every slot (it is kv_bytes/2 and covers all slots, the EAGLE slot included, 1153-1161, 1297-1301), so a head-64 slot's plane exists; save_k leaves it untouched. Precision the sentence lacks: copy_storage_slot (1966-1975, every page move: append, defrag) and fill_storage_slot (1365-1372, tests) rebuild the plane of every slot geometry when the arena exists, head 64 included - "never written" is true of save_k only. No registered plugin mixes head sizes, so the case has no instance.

Question (jhan, 2026-08-30): how can one layer be ineligible for AMX and the next layer eligible?

Because in tron "the model's shape" is not one value. A plugin declares an array of attention kernels (geometries), and each attention operation - one per layer - names the kernel it uses (attention_operation_descriptor::kernel, kv_cache.hpp:228-233). Eligibility is evaluated per operation, on that operation's kernel geometry: the dispatch is instantiated once per geometry and each instantiation computes its own constexpr amx_eligible (self_attention.hpp:1359-1361, 1507-1509). "Layer 4 ineligible, layer 5 eligible" therefore just means the two layers' operations name kernels with different geometries.

A registered model already alternates shapes across layers - with head sizes, not ratios:

pluginkernel 0 (local layers)kernel 1 (global layers)layer pattern
gemma_4_31b_it32 q-heads / 16 KV heads / head 256 (ratio 2), sliding window 1024 - 50 of 60 layers32 / 4 / head 512 (ratio 8), no window - 10 layers000001 repeated: five local layers, then one global
gemma_4_12b_it_permuted16 / 8 / 256 (ratio 2), window 1024 - 40 of 4816 / 1 / 512 (ratio 16) - 8same 000001 pattern

Read from the generated operation arrays in gen/src/tron/h/tron/plugins/ (operation→kernel-id string parsed 2026-08-30). This is the gemma architecture's alternation of sliding-window layers and global layers; the global layers use fewer KV heads. Both geometries have head 256/512, so this model is AMX-ineligible everywhere and allocates no arena - it shows the mechanism, not an AMX instance.

Three consequences, in increasing distance from today's tree:

  • Today: no registered plugin mixes a head-128 ratio-4 kernel with any other kernel (every head-128 plugin has exactly one kernel; the only two-kernel plugins are the gemma_4 pair above). So "one layer ineligible, the next eligible" for AMX does not occur in a registered model.
  • When it occurs (a future model with, say, ratio-8 head-128 layers next to ratio-4 head-128 layers): amx_mirror_eligible is an ANY over the kernels array (kv_cache.hpp:185-189), so the one eligible kernel allocates the arena for the whole book; the eligible layers take the AMX path, the ineligible ones keep the dotter loop; and save_k mirrors every head-128 bf16 slot - the ineligible-ratio layers' slots included, at the measured 70 ns/token-row, whether or not anything reads them. That over-approximation is exactly what mirror_write_ok's missing ratio term buys.
  • The comment's shared-slot case is one step further still: not two layers with different shapes, but two layers using the same KV slot - one writer, one read-only reader with a different query-head count (cross-layer KV reuse). The Tron IR and TronCheck permit it, Loopy has never emitted it (commit 323b9d5499's message); in-tree it exists only as the validator-level test t_llama_unit.cpp:874-914. That is the case the missing ratio term is required for, rather than merely tolerable.

The concepts and their scopes, in one picture

Why eligibility can flip per layer while the arena cannot: the three gates read the same registry at different scopes. eligible reads one operation's kernel geometry, so its answer is per layer (layer 4 and layer 5 name different kernels, different answers). amx_mirror_eligible reads all kernels with ANY, so its answer is per model - one arena decision for the whole book, even when only some layers would use it. mirror_write_ok reads only the head size of the writing operation's kernel, so its answer ignores the one field that varies between sharers of a slot (the query-head count), which is the point of the comment.

Why there are three predicates

The comment names two of them and the Note bullet a third; none of the three comments says how they relate.

reader · eligibleshape_ok(head, kv_mul) && bf16 (amx_attn_iface.hpp:154-157), evaluated on the reading operation's geometry (self_attention.hpp:1359-1361, 1507-1509). Has the ratio term because the kernel needs exactly 4 query rows.
allocator · amx_mirror_eligibleeligible over the plugin's kernels array, true if any kernel passes (kv_cache.hpp:183-193). Same predicate as the reader so allocator and reader can never disagree about which models have an arena.
writer · mirror_write_okhead == 128 && bf16 (170-173), evaluated on the writing operation's geometry. No ratio term: the writer must cover every reader its slot could have. Cost of the over-approximation: the scalar scatter, measured at 70 ns per token row on the RX worker (kv_cache.hpp:647-648), on head-128 slots no ratio-4 reader uses - a case no registered plugin has.

The other route codex offered - scan plugin_t::attention_operations for the slot's readers inside save_k - was not taken; the commit message gives no reason beyond the gate being simpler. Both routes give the same result for every registered plugin.

Glossary

ratio / kv_mul
n_query_heads / n_kv_heads: how many query heads share one KV head (grouped-query attention). The AMX kernels handle exactly 4.
KV slot
One region of the KV page holding K and V for one attention operation's layer. Declared with a KV geometry (KV heads, head size).
attention operation / kernel
An operation is one attention call in the model (layer, slot, kernel, whether it writes KV). A kernel is a compute geometry (query heads, KV heads, head size) that operations refer to.
writes_kv / read-only consumer
The operation that stores K and V into its slot, versus an operation that only reads a slot another operation writes. The validator requires exactly one writer per slot.
save_k / write-through
save_k stores each token's K row into the page; the write-through scatters the same row into the mirror plane immediately after, while it is still in L1.
mirror plane
The VNNI-layout copy of K for one (slot, KV head, page) inside the arena; 64 tokens x head size bf16. Read as the B operand by the AMX QK kernel.
arena
The book's block of ordinary RAM, kv_bytes/2, holding all mirror planes for all slots; allocated once per book, or not at all.
dense page
A 64-token page whose every token is visible to the query; the AMX fast path handles only this case, the AVX dotter loop handles the rest.
executor / activation scalar
The executor (tp1, tp2, host, host_bf16, host_fp16, ...) fixes the element type of activation tensors; Q is one of them. bf16 for tp*/perm_tp*/host_bf16, float for host, fp16 for host_fp16 (common.hpp:90-98).
TRON_AMX_K_MIRROR
CMake option (default OFF, needs TRON_AMX_DISPATCH) that compiles the arena, the write-through and the mirror-reading kernel path.
