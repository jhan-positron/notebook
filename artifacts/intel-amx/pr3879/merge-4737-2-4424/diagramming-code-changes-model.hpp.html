Short version

PR 4424 changes save_k in model.hpp, the function that stores the K rows of one minibatch into the KV cache. The store now writes whole 16-token VNNI blocks where a run of tokens fills one, and it is shared with the idle main helpers through a window of work units (Note [Shared block save]). This page draws the data model, the call graph, the window protocol, the threads over one layer and the store decision once (section 1), then each of the eight logical changes of the file beside its diagram (section 2).

MODEL-B1. Data model: the minibatch, the K store window, the pending list, and the K buffer

A batch holds the items of one minibatch (token jobs), each at one page offset. The PR adds batch::k_store_window_t (in common.hpp: the claim counter, the open/finished counters, the unit table and the helpers' window counters) and state::pending_k_blocks_ (the blocks to convert at the forward end). Every arrow says how many. The worked example is a 40-item window with 3 workers (main and 2 main helpers).

MODEL-B2. Function model: save_k, its helpers, and what they call in the page

save_k (two overloads) calls save_k_impl. save_k_impl decides the sharing (k_store_shared), cuts the units (k_store_cut_units), stores the runs (store_k_block) and records the rows (note_k_row_saved). convert_pending_k_blocks runs at the forward end. The generated plugins call save_k from run() (worker 0) and run_main_help (the helpers). Every cell says in one line what the function does.

MODEL-B3. Sequencing model: one shared save_k window, step by step

The ordered steps of one window, each citing the line that does it. Main cuts the units, resets the counters and opens the window (release on opened). Each helper waits for its window number (acquire on opened). Every thread claims units with fetch_add on next_unit and stores them. Each helper increments finished (release). Main joins (acquire on finished) under a watchdog. Main records the rows and queues the completed blocks. Main marks the tokens and credits the GOFs.

MODEL-B4. Interaction model: threads over one layer and the forward end (wall-clock lanes)

One lane per thread: main, the main helpers, the attention workers, and the forward end. Solid blocks are work, dashed outlines are waiting. The critical path (main's serial part) is marked with a thick frame. Durations are schematic. The order and the overlap are what the diagram shows. The one measurement quoted (0.86 ms per layer) comes from the comment of Note [Shared block save].

MODEL-B5. Decision model: what one run of tokens becomes in the page

For each run of consecutive items in one 16-token block of one page, three cases. A run of 16 tokens is stored as one VNNI block (set_k_block, then note_k_block_saved). A shorter run is stored row by row (set_k_row), into the row-major form, or into the VNNI column when the block is converted already. In more detail: after the stores, main records the saved rows. A block that a short run completed is queued. The forward end converts the queued blocks (convert_pending_k_blocks). Under hardware attention main records no row and queues no block, and the block stays row-major. The diagram reuses the block colours of the kv_cache.hpp page.
