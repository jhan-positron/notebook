Words used here

TTFT, TPS, prefill, decode
TTFT = time to first token in ms, the prefill latency a client sees. TPS = decode tokens per second per user. Prefill = processing the prompt; decode = generating tokens after it.
canonical, canon, canon2
The AMX kernel reads K (the stored attention keys) exactly as stored, one contiguous row per token; this is PR 1. canon2 = a second run of the same arm, to show the run-to-run spread.
mirror
PR 2: after the canonical row is stored, it is read back and scattered into a second copy of K in the VNNI layout (the order the AMX tile multiply consumes; each token's 128 values land in 64 different cache lines instead of 4). That copy lives in the "arena", a separate block of ordinary RAM, and the AMX kernel reads it from there.
sonly (scatter only)
Probe mode: the canonical store is skipped and the freshly computed row is scattered straight into the arena. Against mirror it isolates the cost of storing K twice; against inplace it isolates the cost of the arena's placement.
inplace
Probe mode: the canonical store is skipped and the row is scattered into the page's own 16 KiB K plane inside the hugepage KV block; the AMX kernel reads that plane. This is the single-K storage proxy: one store per row, VNNI pattern, canonical placement, no arena.
g1mirror, g1canon, g1kill
g1mirror = the probe binary with the variable unset, so the mirror arm on the probe build (a control for the probe binary). g1canon = the same head built with the mirror option off (canonical AMX). g1kill = the probe binary with AMX disabled by TRON_AMX_DISABLE=1 (the AVX baseline). "g1" marks binaries built today from head 60d66d9c04 plus the probe commit.
off
The canonical build with AMX disabled: attention on AVX, the pre-AMX behaviour.
probe modes and numerics
sonly and inplace give wrong model outputs on purpose (readers of the canonical K see stale or permuted values); only their timing is meaningful. On llama the wrong values tripped two different assertions (sonly: a "-inf" running maximum in the attention join, self_attention.hpp:1741; inplace: a NaN logit in the sampler, top_k_accum.hpp:44); on qwen they did not.
code heads in this campaign
Two, one debug commit apart. off, canon, canon2 and mirror are round 1's byte-identical binaries (head 60d66d9c04, checksums verified); g1mirror, sonly, inplace and all runtron arms are head 60d66d9c04 plus the 56-line probe commit fceeddc529, whose unset mode is the unchanged mirror path (g1mirror reproduced mirror within 0.6%). No arm is on the current PR 1 or PR 2 tip.

Reading the runtron table

  • Which differences are real. Each arm ran twice; the eight requests of a run are parsed as one batch and report the same time. Run-to-run prefill spread: g1canon 62.38 / 62.30 s, g1mirror 63.26 / 63.36 s, sonly 63.38 / 63.16 s, inplace 63.01 / 63.01 s, g1kill 128.4 / 129.3 s. So inplace is faster than mirror by 0.3 s (0.5%), consistent in both runs and in the expected direction (no arena traffic); sonly is not distinguishable from mirror (its two runs straddle mirror's), which matches the rinzler result that storing K twice costs almost nothing. The decode differences between the three mirror-kernel arms (18.59 to 18.67 tok/s) are inside the usual spread of this shape (about 0.5%) and are not resolved.
  • Why prefill takes 62 seconds. The number is the time to parse eight prompts of 8192 tokens as one batch with software attention forced (USE_HW_ATTN=0, the condition under which AMX can engage at all): 65,536 prompt tokens in 62.3 s is about 1050 tokens per second in total, 131 per request. With software attention the attention part of prefill grows with the square of the prompt length, so at 8192 it dominates; the AVX baseline takes 129 s and the AMX kernels halve it. In production, ingested models such as qwen run attention on the FPGA and their prefill is not this number.
  • Why 62 s and not 54 s. The 2026-09-07 run of the PR 1 tip (9723d56f62, rebased on main a80b102c18) at the same shape and placement took 53.7 / 53.5 s; today's g1canon is the old head 60d66d9c04 (round 1's), which measured 62.2 s on 2026-08-30 as well. So the old head is about 16% slower at this shape than the tip, and the gap is between code bases, not between days. Hypothesis, not measured: the speed-up came with main's changes in the rebase rather than with PR 1's own refactoring. The test that separates the two is one runtron run each of the pure split (pr1-pure, the old code on main a80b102c18) and pr1-stage2 at this shape (about 3 minutes each plus builds).

3. What it means for the gate

  • G1, first clause, qwen: fail. The rule agreed on 2026-09-05 kills single-K if the scatter-only store is worse than canonical by more than the run-to-run spread, about 2%, at 8 concurrent prefills. Measured: the in-place VNNI store is +11.7% at 8 users (1820 vs 1630 ms), +12.0% at 4, +8.5% at 2, +8.0% at 1, against a same-day canonical repeat of 0.2%. The comparison favours the probe if anything: the inplace arm reads K with the mirror kernel, which was 8% faster per attention unit in the 2026-09-01 measurement.
  • Where PR 2's penalty comes from. At 8 users on qwen: 190 ms from the 64-line store pattern (inplace vs canon), 190 ms more from writing into the arena instead of the page's K plane (sonly vs inplace), 12 ms from the second store and re-read (mirror vs sonly). The mirror penalty of round 1 reproduced (2022 vs 2009 ms), and the probe binary reproduces the mirror arm (2034 ms).
  • Short prompts pay, long prompts do not. In the runtron batch path at prompt 8192 the same stores cost 1.1% (inplace) to 1.6% (mirror) of prefill time, and the decode prize is intact in-plane (+10.3% over canonical, the same as the mirror's +9.8%). In the serving path at prompt about 1000 the per-token prefill time is about 4.5 times shorter, so a per-token store cost is a much larger share. The penalty is mostly per token: it is already +8% at 1 user and grows only to +12% at 8.
  • Not measured today. llama's probe cells (the assertion above); the gate's second clause (per-row store time); G2 (FPGA staging transform); anything on the current base (the probe is the old head); numerics of any kind.
  • G3, indicative: favourable. The VNNI reader is faster than the dotter transcription on Granite Rapids at every count above 3 and slower only at 1 visible token; the gate's real G3 (tron-linked, 4 queries, RAM regime) is still to run.

Reading for the 2026-09-16 gate, as of today: the single-K primary store as prototyped (one scatter per token into the page's K plane) fails its store-cost gate in the serving path on qwen, and the same mechanism is about half of PR 2's penalty. A hypothesis worth one day of work before the gate: a store that writes each of the 64 cache lines once per 16-token block (the block's tokens share those lines) instead of 16 times would remove most of the cost. The test is a fourth probe mode measured the same way; nothing about it is measured yet.
