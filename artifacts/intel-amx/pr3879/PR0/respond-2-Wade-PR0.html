Reply to Wade: FUSE for the page-share counters (PR 4267)

Prepared 2026-09-09 for jhan (the PR author). Wade's review: pullrequestreview-5156698046 (APPROVED, on head ef13273ba9). The PR was not updated. This page is the analysis and a draft reply.

Short version. Wade approved PR 4267 as it is, and asked whether the counters could instead be served as live files through FUSE (Filesystem in Userspace) with an environment-variable switch, so two reads can measure an interval. Tron already has that machinery and one precedent of the same structure (the expert routing statistics of the MoE models; MoE = mixture of experts), so the change is about 10 files (est.). Merge PR 4267 as approved and do FUSE as a follow-up: the FUSE version puts a disabled code branch into the attention page loop of every tron binary, and that cost has not been measured.

Words used here

tron
The inference program under test. rinzler is its production HTTP server. runtron is its command-line tool.
FUSE
Filesystem in Userspace: a Linux interface that lets an ordinary process serve a directory tree that other programs read with plain file calls such as cat. libfuse is the user-space library that implements the FUSE protocol. fusermount3 is its unmount tool.
tronstats
Tron's FUSE stats tree, and also the name of the layout convention it follows (platformd's collector and library carry the same name). A thread inside rinzler or runtron serves the tree; both binaries mount it at startup by default. [README.stats.md:1-13,57-70; src/system/fuse_sysfs.cpp:301-320]
leaf
One file in that tree, created with make_file. An optional read callback computes the value on every read. A getattr is the file-attribute lookup that precedes every read; it fires the callback too.
static leaf
A leaf created before stats::start. A collector sees it on its first scan; leaves created later are seen only on a periodic rescan. [h/system/fuse_stats.hpp:137-150]
casual leaf
A leaf created without exported=true. Readable by hand, no descriptor needed, not collected by platformd. [README.stats.md:224-237]
exported leaf
A leaf created with exported=true, mirrored under /exported/, and required to carry a descriptor (type, unit, description). Descriptors are grouped in families in the manifest, the table in src/system/fuse_tronstats_manifest.cpp.
.skip marker
A manifest entry that tells the convention checks to treat a grouping directory (a path segment that only groups leaves and carries no metric dimension) as structure, not as a dimension. A dimension is a Prometheus label, such as the instance number or a model id, that platformd derives from one segment of the leaf's path; the allowed dimension names are a fixed list in src/system/fuse_tronstats_lint.cpp. [README.stats.md:357-370]
convention lint
The check in src/system/fuse_tronstats_lint.cpp that every exported leaf has a descriptor and a valid metric name. The convention test (t_tronstats_convention) and rinzler's integration test run it over /exported/; the aggregate scan repeats it with every path prefixed by a synthetic instance number, as platformd sees it.
platformd
The external host agent. Its collector scans /exported/ in each instance's mount and serves the values over HTTP on port 9100 at the path /metrics, for Prometheus (a metrics database that polls HTTP endpoints). Its source is not in the tron repo. pho is platformd's command-line tool; pho tron stats read prints a table of the mount and watch is a live view. [README.stats.md:61-62,100-105]
counter, gauge
Prometheus metric types. A counter only rises and resets only on process restart. A gauge can rise and fall. [README.stats.md:405-416]
KV page, KV head
A KV page is a 64-token block of the key/value cache. A KV head is one key/value attention head; several query heads share one KV head.
software attention, hardware attention
Software attention is attention computed by CPU code; hardware attention is the FPGA card (the accelerator) computing it. When hardware attention is on, the CPU loop handles only the (query, page) pairs the ranged mask marks as software-required. apply_page_range is the member function template of software attention that walks a range of KV pages for one KV head. The five hooks of PR 4267 (short code blocks inserted into that loop to record counts) live in it. [ef13273ba9:h/tron/models/self_attention.hpp:1253-1359]
dense page
A KV page that passes the AMX kernel's gate in PR 3879: full, wholly visible to the query through one range, and inside the query's sliding window. [26a0338c3b:h/tron/models/self_attention.hpp:1432-1451]
page visit
One pass of apply_page_range over one KV page. The PR counts a visit only when at least one query token had a relevant K token on that page. A relevant K token is a key token the query token is allowed to attend to: not hidden by the attention mask (the rule that a token sees only earlier tokens) and inside the sliding window (the model's limit on how far back a token may look). [ef13273ba9:h/tron/kernels/page_share_counters.hpp:4-10,75-79]
ready page, pending page, tail page, chunk
A ready page was written in an earlier forward pass; a pending page is written in this one. The tail page is a session's newest, not yet full page. A chunk is the slice of prompt tokens one prefill pass processes. [h/tron/models/model.hpp:1893-1904,1917-1921]
canonical, arena-mirror
Two builds of the AMX kernel. Canonical (PR 3879) reads K from tron's existing page layout. Arena-mirror keeps a second copy of K in the layout the kernel reads directly; it is a separate, parked PR.
QK, PV
The two matrix multiplies of one attention unit: query times key, then the softmax weights times V.
prefill, decode
Prefill is processing the prompt tokens. Decode is generating one token per step. pending marks the second attention pass of a step, over pages whose K and V are written during the same forward pass. [ef13273ba9:page_share_counters.hpp:59-63]
atomic, fetch_add, relaxed load
An atomic is a counter that several threads update without a lock. fetch_add is its add operation. A relaxed load reads it with no ordering guarantee against other memory operations, the cheapest kind of read.
gate
The switch that decides whether the counting code compiles (a compile-time gate, the #ifdef) or runs (a run-time gate, a boolean tested at run time).
hot path

static destructor
The destructor of a process-lifetime object. It runs on a return from main or on exit(), and not on abort(), a crash, or SIGKILL. The PR's exit summary is one. [ef13273ba9:page_share_counters.hpp:115-118]

1. What Wade asked

"I'm ok approving this as-is, although I'm wondering if you looked at the possibility of using FUSE for this? Collection could still be opt-in (via env-var maybe), then they could be inspected live and measured over random chosen intervals instead."

The request has three parts. Publish the counters as tronstats leaves. Switch collection on at run time instead of build time. Read the counters while the process runs, so that two reads bracket an interval.

2. Where the counters go today, and where they would go with FUSE

Only the gate and the read side change. The counting code and the four existing tests carry over unchanged.

3. What already exists in tron

  • The stats tree is on by default and mounted by both binaries. ENABLE_FUSE_STATS defaults to ON. runtron and rinzler call stats::initialize and stats::start unconditionally in main. With the option OFF the leaves still work in memory; only the mount and the FUSE thread are skipped. CI mounts the tree in the test-host, test-fpga, benchmark and coverage jobs. [CMakeLists.txt:45; src/runtron.cpp:494,506; src/rinzler.cpp:4220,4435; src/system/fuse_sysfs.cpp:301-320; .github/workflows/cmake-single-platform.yml:474-476,594-596,752-754; .github/workflows/cpp-coverage.yml:53-54]
  • The API fits the counters. stats::make_file(path, value, read_only, exported) accepts uint64 and string values. set_read_callback may be installed after stats::start. Callbacks run on libfuse worker threads. Up to 10 threads run at once: that is the libfuse 3.17.4 default for max_threads (the worker cap), and tron sets only clone_fd (whether each worker gets its own device descriptor) and max_idle_threads (how many idle workers are kept), not the cap. A callback also fires on getattr, so one cat fires it about three times. make_file aborts if initialize never ran, so registration helpers guard with is_initialized(). 4. What the FUSE version would look like

  1. Keep the data path. page_visit_counts, record_page_visit and flush stay as they are. Drop the header's outer #ifdef so the struct and the atomics compile in every build. [ef13273ba9:h/tron/kernels/page_share_counters.hpp:18,67-113,153]
  2. Gate at the hook sites. Next to the visit_counts declaration add static const bool counting = page_share::enabled();. enabled() reads TRON_PAGE_SHARE_COUNTERS once per process through its own function-local static, the same pattern as init_logits_chunk_size. apply_page_range is a member function template (the compiler makes one copy of it per set of template arguments), so counting is one object per copy, each initialized from that cached value. [h/tron/models/model.hpp:78-85] Only the per-(page, query token) increment needs the test: if (counting && relevant_k_tokens > 0) n_relevant_query_tokens++;. The other hooks already do nothing at zero counts, so with counting off no atomic is ever touched. All five #ifdef/#endif pairs go. [ef13273ba9:h/tron/models/self_attention.hpp:21,1290-1292,1300-1302,1333-1335,1352-1354,1356-1358; ef13273ba9:h/tron/kernels/page_share_counters.hpp:79,100]
  3. Publish leaves. A free function (a function outside any class) page_share::register_fuse_files() returns early unless is_initialized(). Under /rinzler/stats/page_share/ it creates one read-only uint64 leaf per total: page_visits, relevant_query_tokens, shared_visits, shared_tokens and pending_visits. Each leaf's read callback is a relaxed load of the matching atomic. A sixth leaf, histogram, is a string that renders the seven histogram slots (visits that served 1, 2, 3, 4, 5-8, 9-16, and 17 or more query tokens) as a JSON array. A single summary JSON leaf is the alternative: it reads all totals in one callback, so the values can differ only by flushes that complete during that one callback (read skew). A casual leaf under a new directory needs no .skip marker, because the convention checks walk only /exported/. [ef13273ba9:page_share_counters.hpp:29-36,40-63; pattern h/tron/models/expert_stats.hpp:156-175,189-196; walk roots t/t_tronstats_convention.cpp:873-877 and t/t_rinzler.cpp:4595,4619-4622; README.stats.md:226-228]
  4. One registration call in each main, before the markers and descriptors. The documented order is leaf make_file calls, then register_tronstats_markers, then register_tronstats_metric_descriptors, then stats::start. runtron: after line 503 and before line 504. rinzler: after line 4424 and before line 4432. This gives static leaves, so platformd's collector sees them on its first scan. [README.stats.md:322-324; src/runtron.cpp:503-506; src/rinzler.cpp:4424-4435; h/system/fuse_stats.hpp:137-150]
  5. Keep the stderr exit summary. Section 5 shows why: both binaries unmount the tree before static destructors run, so a leaf cannot give an end-of-run total for a batch runtron campaign. The reporter already prints nothing when no visit was counted, so with counting off it is silent. [src/rinzler.cpp:4614-4639; src/runtron.cpp:483-485; ef13273ba9:h/tron/kernels/page_share_counters.hpp:125-127]
  6. Remove the build plumbing. The CMake option; the PUBLIC compile definition; the coverage-preset entry; the README.ci.md paragraph; and the test's DEFINES clause. [ef13273ba9:CMakeLists.txt:47; ef13273ba9:src/tron/CMakeLists.txt:231-237; ef13273ba9:CMakePresets.json:118; ef13273ba9:README.ci.md:513-522; ef13273ba9:t/CMakeLists.txt:268-271]
  7. Tests. The four Catch2 cases include the counters header but not self_attention.hpp, and call record_page_visit and flush directly. So they pass unchanged if the gate stays at the hook sites. A gate inside record_page_visit would fail 3 of the 4 cases. An optional fifth case can read the leaves in memory through file_handle::get_value() without a mount. [ef13273ba9:t/t_page_share_counters.cpp:16-21,43-117; src/system/fuse_sysfs.cpp:933-949]

5. Why the exit summary stays: startup and shutdown order

The two mechanisms are complementary. FUSE covers "while it runs"; the stderr summary covers "after it ends", and only after a clean end.

6. What the FUSE version is worth

This section answers "why do it at all", first for the AMX work and then for tron in general. Each item names a question, how it is answered today, and how the FUSE version answers it. Claims that no measurement supports yet are labelled hypothesis. Numbers derived by hand from recorded data are labelled est.

6.1 From the AMX project's perspective

  • The counters measure the one quantity a kernel variant can change to lower the AMX unit's memory time. An AMX unit is one query token times one KV page times one KV head. [perf-model/index.html:126] The perf-model report (perf-model/index.html, the 2026-09-03 model that predicts the AMX decode boost from measured parts) puts the unit's memory time at 2.494 us (microseconds). That is 32 KiB (kibibytes of 1,024 bytes: the K and V bytes of one page) divided by 13.14 GB/s (gigabytes per second), the per-core streaming rate measured with 27 cores reading at once. [perf-model/index.html:125,132] (An earlier estimate on the team's Notion wiki page "Estimate: the AMX decode boost from pre-AMX data, in plain English" used 2.06 us: the same 32 KiB at 15.9 GB/s.) [perf-model/index.html:131-132] At prompt length 8192 tokens the report measures the unit under load at 2.727 us, of which the compute part is 0.621 us. [perf-model/index.html:245-246] So at that length the unit time is set by the bytes streamed, not by the arithmetic. At prompt lengths 2048 and 256 the KV bytes one decode step reads (the working set: 306 MiB and 54 MiB) fit in the L3 cache (the last and largest cache level, 432 MiB here, shared by all cores of one CPU socket, that is one physical processor), so the memory rate is not the limit there. [perf-model/index.html:308-309] In tron itself the canonical kernel of PR 3879 (canonical = the AMX kernel that reads K from tron's existing page layout) measured 2.89 us per unit at prompt length 8192. The arena-mirror build (a separate build that keeps a second copy of K in the layout the AMX kernel reads directly) measured 2.66 us, and the AVX path 3.64 us. [PR3879/make-sense-amx-vs-avx.html section 7.2.1, line 461] The bytes per page visit are fixed by the page size. The bytes streamed per query token are those bytes divided by the query tokens served per visit. The page-share counters measure the distribution of that divisor. That divisor is one of several quantities that set the memory time. The K layout of the arena-mirror build lowered QK time (QK = the query-times-key multiply, the first half of the unit) while streaming the same bytes. [PR3879/make-sense-amx-vs-avx.html section 7.2.1, lines 462-463] The per-core streaming rate is another such quantity. The divisor is the only one of them that a kernel variant can change, by serving several queries per page load.
  • The decision "build a multi-query kernel variant" needs the decode-phase number. The kernel of PR 3879 serves one query token (its four query heads) per page load. [PR 4267 body, "What does this PR serve?"] The PR-body table says batching would help in prefill (110.9 query tokens per visit) and with shared prompts (5.06), and not in private decode (1.02). The 5.06 mixes the prefill of the 1,088 prompt tokens per user (1,024 shared plus 64 private) with the decode that follows, because the exit summary sums the whole run. [exec/results/slot1/p1-sharing.txt:12-16] For that synthetic run the histogram slots (the exit summary's seven counts of visits by query-token count, labelled 1, 2, 3, 4, 5-8, 9-16 and >16) separate the two phases; on real traffic they do not. [ef13273ba9:h/tron/kernels/page_share_counters.hpp:29-36] The >16 slot can only be prefill. The 5-8 slot holds the visits in which the 8 users' decode queries (one query token per user per step) met one of the 16 pages of the 1,024-token shared prompt (1,024 divided by 64 tokens per page), and the 1 slot holds decode visits to private pages. [exec/results/slot1/p1-sharing.txt:12,16] From those two slots the decode-only average is 3.55 query tokens per visit (est.: 8 x 1,175,040 plus 2,052,864, divided by 3,227,904 visits). [exec/results/slot1/p1-sharing.txt:16] Two reads that enclose a window in which no prefill runs give the decode-only value directly, in one run, whatever the sharing pattern inside the window. On traffic with continuous arrivals such a window has to be arranged, for example by holding new requests while it is measured. Today that value has no direct measurement.
  • pending_visits counts the visits the AMX kernel cannot take, up to two known deviations. The AMX path in PR 3879 runs only when two conditions hold: a packed Q exists, and the page is dense. A packed Q is the query vectors arranged once in the layout the AMX kernel reads; it is null when AMX is unavailable or disabled. [26a0338c3b:h/tron/models/self_attention.hpp:1581-1598] Dense means three things: the page is full, the query sees all 64 tokens through one visible range, and the page's first token is inside the query's sliding window. [26a0338c3b:h/tron/models/self_attention.hpp:1432-1451] (For EAGLE models only, speculative draft models that skip the first K token, the first KV page is never dense for a query after position 0.) [26a0338c3b:h/tron/models/self_attention.hpp:1565-1573] A pending visit is on a page whose K and V are written in this forward pass; a ready page is one written in an earlier pass. [ef13273ba9:h/tron/kernels/page_share_counters.hpp:59-63; h/tron/models/model.hpp:1893-1904,1917-1921] In decode the pending page is the session's tail page (the one page that holds the newest token and is not yet full). That page is partial in 63 of every 64 decode steps, so those pending visits take the AVX path. In prefill the pending pages are the ones the current chunk (the slice of prompt tokens one forward pass processes) writes. None of them is dense for any query of that chunk, even once complete. The causal mask (the rule that a token sees only itself and earlier tokens) gives each entry of such a page its own set of queries. So the page spans several visibility ranges and fails the one-range test. [26a0338c3b:h/tron/models/self_attention.hpp:1448-1449; doc/hw-kv-ranged-mask.md:203-206] So pending visits are non-AMX visits in both phases. The fence measurement of 2026-09-01 agrees. (The fence measurement is the single-attention timing run on the branch jhan-amx-fence, named for the fences, timestamps taken at fixed points of the token loop, that the branch adds; it ran one user on the arena-mirror build with a separate compile-time counter of fallback visits, the visits the AMX kernel declined so the AVX code ran.) In decode every fallback was on the tail page. The fallback count, 72,576 = 252 x 36 layers x 8 KV heads, equals the pending visits (255 decode passes x 288 = 73,440) less the 3 of 255 passes in which the tail page was full, because the prompts were multiples of 64 tokens. [PR3879/make-sense-amx-vs-avx.html section 7.7, lines 563-575] In prefill every fallback (query token, page) pair lay on a page cut by a visible-range boundary, and the fallback count of 1.5 pairs per prompt token per layer and KV head (est.: 110,592 / 288 = 384 at prompt 256) equals the pairs on the current 128-token chunk's own two pages, which are the pending pages. The fence counter counts (query token, page) pairs, not page visits, so in prefill the match with pending_visits is by page set, not by count. [PR3879/make-sense-amx-vs-avx.html section 7.7, lines 567-575; ~/workspace/ai-runs/tron-fence-amx h/tron/kernels/amx_fallback_counters.hpp:2-7,32-33; exec/results/slot1/p1-sharing.txt:3-6] Two deviations remain. pending_visits overcounts by the one step in 64 that fills the tail page. It undercounts by ready pages that fail the dense test. There are three kinds. 6.2 From the general feature perspective

  • Query tokens per page visit is a workload-shape metric, not an AMX metric. It measures how many query tokens of the current minibatch (the group of tokens one forward pass processes together) had a relevant K token on one KV page in one visit. [ef13273ba9:h/tron/kernels/page_share_counters.hpp:4-6] The count rises with prefill (many query tokens of one prompt on one page: 110.9 in the PR-body table), with prefix sharing (several sessions holding the same prompt tokens: 5.06) and with batching. [PR 4267 body, table under "What does this PR serve?"] Today tron reports prefix sharing only as prompt tokens served from the KV cache. Four places carry that number. The tokens_prompted_cached leaves under /rinzler/stats/monitor/ give it per process; their ratio to tokens_prompted is a cache-hit ratio. [src/rinzler/fuse-stats-monitor.cpp:200-203,216-219; src/system/fuse_tronstats_manifest.cpp:203-207] The cached_tokens field in the usage object of each completion's HTTP response (the token-count block of the reply) gives it per request. [src/rinzler.cpp:187-189,244-246] The per-session #EVT# history line (a debug log line, prefixed #EVT#, that lists a session's events) gives it per session. [src/tron/generation/token_stream_monitor.cpp:507-513] runtron's per-iteration "reused tokens" log line gives it per iteration. [h/runtron/stream_generate.hpp:972-979] Nothing reports how many query tokens share one page visit in one step. That is the quantity a multi-query kernel needs. Scheduler work on shared system prompts (the instruction text every user's prompt starts with) can use the same number to see whether sharing occurs in production.
  • Interval measurement lets one running process answer a before-and-after question. Two reads, one at each end of a window, give the counts for that window. The window can be a setting changed at run time, one tenant's burst (a tenant is one customer whose sessions share the server), or a stretch with no prefill in it. No restart, no rebuild. With exported leaves, Prometheus's rate() function (the average per-second increase of a counter over a chosen past window) gives the same difference for any past window. [README.stats.md:61-62,405-409]
  • It follows tron's stated observability direction. The observability egress design (doc/observability_egress_design.md) is the specification for reading tron's per-session event history from outside the process. Three of its goals are: remove the recurring #EVT# log reports of session data, keep zero impact on critical paths, and reuse the existing FUSE layer. [doc/observability_egress_design.md:44-46,54-57] It names FUSE as tron's machine-readable external channel. [doc/observability_egress_design.md:80-84] A four-line stderr summary at exit is outside that design's scope; it is a log line no collector reads. FUSE leaves are the channel the design adopts. Two features already use it: expert_stats (the per-router, per-expert routing counts of MoE models; the router is the part of an MoE layer that picks the experts for each token) and rinzler's memory-pressure stats (the leaves under /rinzler/stats/memory_pressure/).   • No build differs from another by the counter code. Codex objected that the benchmark artifact (the runtron binary the CI build job packages for the benchmark run) carried instrumentation. The fix moved the ON setting from the CI build job to the weekly coverage preset (a Debug build, one compiled without optimization, with coverage instrumentation). So the counting binary is now a build nobody benchmarks. 8. Open items before switching decide or measure

  1. A/A control of the gated-off build against the current OFF build. Run the CI benchmark flow (bin/ci/benchmark_save.py, five standard jobs) on delphi-3bda against two committed revisions. The script refuses a tree with unstaged edits to tracked files (it runs git diff --quiet). It files results under the commit and the host name. Its hardware check stops with an error unless --cpus-per-machine matches the host core count. Whether the repeat-to-repeat spread resolves a sub-percent effect: Insufficient data until the spread in the existing /scratch/tron-benchmark/*.json records is read. bin/slice (tron's unit-test scheduler) bench records per-test duration, peak RSS (resident set size, the most physical memory the test held) and viable slice counts (a slice is the scheduler's unit of machine share). It is not an inference benchmark, so it is the wrong tool. [bin/ci/ci-run-benchmark.sh:70,94; bin/ci/benchmark_save.py:87-90,112-114,173-175; doc/slice-benchmark-lifecycle.md:3-4]
  2. Register allocation. Compare objdump -d of apply_page_range for both builds. The gate keeps two locals live across the inner loop that the OFF build deletes.
  3. Casual or exported. Exported needs exported=true, a descriptor, and a .skip marker. Without the descriptor, the lint's per-instance scan reports an orphan leaf; without the .skip marker, the lint's aggregate scan reports a dimension name outside the allowlist. The JSON histogram would stay casual, as the expert_stats ones do. This decision is Wade's. [README.stats.md:234-237,354-370; fuse_tronstats_lint.cpp:187-200,234-235,262-267; expert_stats.hpp:68-70]
  4. What "intervals" means. Differencing two reads needs no code. A reset leaf would break the monotonic-counter contract. Ask Wade. [README.stats.md:407-409]
  5. Mounts in claude-box. CI already mounts the tree in every job that runs tron. Whether /dev/fuse is available inside the container: Insufficient data; running the t_fuse_sysfs test there would resolve it. A leaf unit test does not need a mount.
  6. Exit summary consumer. The only script that consumed a summary greps the predecessor's [P1] label; nothing consumes [page-share] today. Keeping the reporter needs a stated consumer. Dropping it removes the only end-of-run record for batch runtron. [exec/p1-counters.sh:23-28]
  7. Callback concurrency. Read callbacks can run on several libfuse threads at once. The JSON renderer must use local buffers only.

Merge PR 4267 as approved and do FUSE as a follow-up. Wade approved this exact head. [review 5156698046 on ef13273ba9] A rework now would reopen a reviewed diff. The FUSE change replaces the gate rather than adding to it: it removes the CMake option, the PUBLIC define, the preset entry and the README paragraph, and it edits the header and all five hooks. The counters' data path, the four test cases and the cost-data entry carry over unchanged into the FUSE version. The one property the follow-up changes for everyone is that a disabled branch enters the attention page loop of every binary, including the .deb rinzler. No measurement of that cost exists in the PR texts or the repo. The A/A control in section 8 should come before that decision, not after. Declining the idea is not warranted. The FUSE version is about ten files (est.) and matches two in-tree precedents. It gives live reads, interval measurement and production visibility, which the exit summary cannot give. Reworking now trades an approved PR for an unmeasured hot-path change.
