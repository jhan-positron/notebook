Monday 2026-09-07. Answers to the twelve review comments, the code changes they led to, and how each change was verified. Written for an engineer who has not read the PR.

Short version. All twelve comments are answered below; ten led to code changes, which sit as one commit on a side branch (not pushed) that builds and passes both tests on delphi-3bda with the option on and off. An independent review of the diff and of these answers by gpt-6-astra found no blocker and two comment wordings to fix; both are applied. Two premises in the review turned out wrong and are explained with evidence: n_visible counts query tokens, not K tokens, and the requested member names shared_visits/shared_tokens cannot be applied as a plain rename because they would hide the process-wide counters of the same name inside flush(); jhan chose to give every process-wide counter a total_ prefix instead, so no name is used twice in the file. Words used here

  • tron: the inference program under test. rinzler: its production server. runtron: its command-line tool.
  • KV page: a 64-token block of the attention key/value cache. kv_head: one key/value head. minibatch: the set of query tokens one attention call serves (the vector items in the code).
  • apply_page_range: the loop in h/tron/models/self_attention.hpp that applies one range of KV pages, for one kv_head, to every query token of the minibatch. A page visit is one pass of that loop over one (page, kv_head) pair.
  • relevant K token: a key on the page that a given query token attends to (it passes the visibility mask and the sliding window). The existing code returns that count per query as relevant_k_tokens.
  • pending pass: the second attention pass of a step, over pages whose K and V are written during that same forward pass.
  • PR tip: commit 8a867e03a3, the code the review was written against. Revision: the commit on branch jhan-page-share-counters-rev1 (see section 13).

1. "width"

Is "width" the number of query tokens served by a page visit? Yes. The hook sits inside the loop over the minibatch's query tokens and adds one for each query token whose relevant_k_tokens is greater than zero, then records the total once per page visit. So the number is: how many query tokens of the minibatch had at least one relevant K token on that page, per (page, kv_head) visit. [self_attention.hpp at the PR tip: loop at 1303, increment at 1334, record at 1353; one call handles one kv_head, call site 983]

apply_page_range callone worker, one kv_head, one page range; creates one page_visit_counts
→
per pagefor each query token of the minibatch: relevant_k_tokens > 0? then count it
→
record_page_visit(n, pending)n = query tokens served; n = 0 is not a visit; histogram slot; shared if n ≥ 2
→
flush()once per call: adds the counts to the process-wide totals (atomics)
→
exit reportfour [page-share] lines to stderr when the process exits normally

The counting path after the revision (names are the new ones; the mechanism is unchanged).

Does tron use "width" with this meaning? No. A whole-word search over the C++ files under h/, src/ and t/ at the PR tip finds 142 uses of "width" outside this PR, and none means "query tokens sharing a page". The meanings that exist, with the ones closest to this code first:

The collision matters inside the very file the hooks live in: there "query width" already means elements per query row, so a reader of self_attention.hpp meets "width = number of query tokens" a few hundred lines after "query width = 4096 elements".

tron already has a name for this quantity. The work estimator counts "relevant q tokens": work_estimate_t::scaled_vs is documented as "One per relevant q token per page per kv head" [common.hpp:688], and the perfetto trace point at the top of apply_page_range reports it under the label "relevant q tokens" [self_attention.hpp:1274]. The instrumentation's per-visit count is the measured form of that estimate for one (page, kv_head) visit. (Whether the two agree exactly is not verified; the estimator does not apply the EAGLE first-token exception the hook path applies, so they may differ on EAGLE models.)

Change made. The word "width" is gone from the header, the report lines and the test. The concept is written as "query tokens per page visit"; the per-visit counter is n_relevant_query_tokens (section 6); the histogram is histogram per call and total_histogram process-wide, with a comment naming the slots. The report line "avg width" is now "avg query tokens per visit". Note that this average is over visits that served at least one query token, because a visit with none is not counted [header, the early return in record_page_visit].

Alternatives if you prefer a shorter phrase: "queries per page visit" (shorter; a newcomer may read "queries" as query heads), "sharing degree" (matches the namespace name; degree 1 means no sharing, which reads oddly). "fan-in" is not recommended because tron already uses it for something else [full.cpp:99].

2. Why guard with TRON_PAGE_SHARE_COUNTERS instead of always counting?

Both patterns exist in tron, so this is a judgment call. The facts, then the recommendation.

Reasons to keep the compile-time guard

  • Cost is real and unmeasured. The per-(page, query token) hook is one compare and one add of a stack variable, next to roughly 64 keys × 4 query heads × 128 elements of dot products (est. for a 128-wide head with GQA factor 4), so about 1 part in 30,000 and not measurable. The flush is different: once per apply_page_range call it does up to 12 relaxed atomic adds on process-wide counters that every attention worker writes (96 bytes, two or three cache lines, no padding). The call rate is roughly (kv_heads + attention workers) × 2 passes × layers × steps per second, which is on the order of 104 to 105 flushes per second and can exceed that for 64-layer models (est.; the header's old "a few tens of thousands at most" was not measured either). No ON-versus-OFF throughput run exists for this PR, and the PR carries the Skip benchmarks label, so CI will not supply one.
  • The report is automatic stderr output at every normal exit that counted a visit. rinzler's systemd unit sends stderr to the journal [packaging/systemd/rinzler@.service:66-67], and rinzler's main returns normally after SIGTERM [rinzler.cpp:3947, 4618-4639], so an always-on build would print four raw lines at every stop of a server that ran software attention. spdlog's console sink is also stderr, so the difference from normal logging is not the destination but the form: no timestamp, no level, no copy in the rotating log file, no TRON_LOG_LEVEL filtering.
  • Precedent. tron's debug-logging hooks are compile-time gated: MODEL_DEBUG/CHANNEL_DEBUG are empty unless DEBUG_MODEL/DEBUG_CHANNELS is defined and no CMake file defines them [common.hpp:20-25]; DEBUG_HWATTN is a commented-out #define in self_attention.hpp:27. The option-to-define-to-#ifdef mechanism is the same one ENABLE_FUSE_STATS and AVX512 use. Always-compiled, runtime-gated instrumentation also exists (perfetto TRACE_EVENT; log_intermediate gated by cfg.log_intermediates), but those have production consumers.
  • Review history. Wade's agent review on #3879 asked for the instrumentation to leave the tree; the option was the recorded compromise (PR body, "Review history").

Reasons to drop the guard

  • A smaller tree: no CMake option, no PUBLIC define, no DEFINES clause on the test, no CI-lane flag (commit 8a867e03a3 exists only so the option-on build cannot rot unnoticed), no README.ci.md paragraph.
  • The numbers would be available from any binary without a rebuild.

What an always-on version would need instead

At minimum, one process-wide flag read once per apply_page_range call that skips the counting and the flush (tron's pattern is a static const latch that reads an environment variable, as in log_kv_footprint [kv_cache.hpp:442-449], or a relaxed atomic bool as in trace_gate.cpp:11). To keep the enabled cost low it would also want padded or per-worker counters instead of the shared cache lines, and to fit tron's logging it would route the report through spdlog or the FUSE stats tree instead of fprintf(stderr) at exit. Those two are implementation choices, not requirements, but together they make it a different, larger change than this PR.

Recommendation. Keep the guard for this PR. If you want the counters always available, measure decode throughput with the option ON and OFF in paired runs first, then do the runtime-switch version as a follow-up.

4. What "[0]=1, [1]=2, [2]=3, [3]=4, [4]=5-8, [5]=9-16, [6]=>16" means

It maps each index of the histogram array to the range of the per-visit query-token count that lands there. The "=" is the separator between index and range; "[6]=>16" is index 6 with the label ">16", not "greater than or equal to 16". The code confirms: 16 goes to index 5, and only 17 and above go to index 6 (the chain of comparisons in record_page_visit; the test pins every edge: 4→3, 5→4, 8→4, 9→5, 16→5, 17→6).

6. n_visible: does it count relevant K tokens? No.

The premise behind the proposed name n_k_visible is not what the code does. The evidence:

  • The variable is declared once per page and incremented inside the loop over items, which are the query tokens of the minibatch [self_attention.hpp:1300-1304].
  • The increment is if (relevant_k_tokens > 0) n_visible++; [1334]: one per query token, whatever the number of relevant K tokens that query had. relevant_k_tokens is the per-query K count returned by apply_page_tok [1329-1331, 1364, 1442]; it is only the gate, it is never added.
  • Supporting evidence: a page holds 64 tokens [kv_cache.hpp:1164], and the prefill measurement averaged 110.9 per visit, which a count of distinct K tokens on one page could not reach. The increment location above is the decisive evidence; the average only agrees with it.

New name: n_relevant_query_tokens, applied to the hook variable, the parameter of record_page_visit and the totals member (relevant_query_tokens, formerly visible_tokens). Reasons: it names the unit (query tokens), it mirrors the sibling relevant_k_tokens on the line above it, and it uses the word tron's own estimator and trace label use for this quantity ("relevant q tokens", section 1). The old word "visible" over-claims slightly: visible() is only the first of three gates a query passes before apply_page_tok runs, while the counter tests the final result.

Alternatives considered: n_visible_queries (keeps the PR's word), n_queries_with_k_on_page (most literal, longest), relevant_q_tokens (exact twin of relevant_k_tokens; "q_" is common in this file but is an abbreviation).

8. Names for v and t

Now n_visits and n_tokens, one declaration per line: the two numbers the report is about to print, read once from the atomics total_page_visits and total_relevant_query_tokens. (My first version called them total_visits and total_tokens; once the atomics took the total_ prefix in the follow-up, those names moved to the atomics.) The comma-chained declaration form uint64_t v = ..., t = ...; has one precedent in 125 files [full.hpp:387], so splitting it also matches the codebase. Single-letter locals as such are not against tron practice (the kernels use q, x, s for math operands), but these two are process-wide totals read for printing, and full words say so.

Alternative: no locals at all, reading the two atomics where needed (one extra load for the early return).

9. Is a report at process exit common in tron? What is ~dumper() worth?

Not a tron convention. Facts from the tree at the PR tip:

  • No atexit, _exit or quick_exit call in h/ or src/ (three std::atexit calls in t/ remove temporary directories).
  • the_dumper is the only namespace-scope inline object in h/ whose destructor prints. Seven destructors in h/ and src/ log something; all seven use spdlog, none prints counters. Three of them run at static destruction: the thread pool's speedometer_t prints "Worker speeds" [threading.hpp:663-665], rinzler's completions_controller prints "Rinzler shutting down. Removed PID file" [rinzler.cpp:2388], and TokenStreamMonitor logs on error paths.
  • tron's documented path for runtime counters is the FUSE stats tree, a virtual filesystem that rinzler and runtron mount so counters can be read as files [README.stats.md:3-5]; 61 make_file registrations exist, including a low-ceremony "casual stats" form [README.stats.md:223-232]. The closest existing analogue to these counters, the MoE expert routing statistics, publishes through that tree [expert_stats.hpp:22-27]. Whole-run summaries in runtron are explicit spdlog::info lines at the end of the run ("[Total over N iterations] ..." [stream_generate.hpp:995]; "Detected {} memory allocations" [runtron.cpp:359]).
  • tron does rely on static destruction for some teardown (thread joins, hwperf sampler), and three Notes describe ordering problems at that time [threading.hpp:891-906, proxy.cpp:161-164, system.cpp:1904-1907]. Those concern joining threads and freed memory; the report only reads six atomics and writes to stderr, so none of those hazards applies to it.

What the destructor is worth. It is the only path by which the counters leave the process; without it the instrumentation produces nothing. It fires on every normal exit: runtron returns from main on all generation paths [runtron.cpp:524-527; exit(0) only for --help/--version/--list-models], Catch2 test binaries return from main, and rinzler on SIGINT/SIGTERM sets a flag, quits the event loop and returns from main [rinzler.cpp:3947, 4438 disableSigtermHandling, 4618-4639]. The 2026-08-18 measurement and the four lines that t_llama_unit prints in the option-on CI lane both come from it.

Its limits (now stated in the header comment): no report after abort(), which is where every TRON_ASSERT failure ends [assert.hpp:59-72], after quick_exit(), after a crash, or after SIGKILL; stderr only, so no timestamp or level and no copy in the rotating log file; one total for the whole process, so a run that mixes prefill and decode cannot separate them (the three 2026-08-18 numbers are from three runs); and the four lines are read one atomic at a time, so they describe one moment only because the attention workers have stopped flushing by the time static destructors run.

Your call. (a) Keep the destructor as it is for this default-OFF instrumentation (done in the revision, renamed exit_reporter / report_at_exit, with the limits in its comment). (b) Replace fprintf(stderr) with a named function that runtron's main calls before shutdown_app_pool() and logs through spdlog::info, in the style of the "[Total over N iterations]" line; the test would call it too. (c) Register the six counters as casual FUSE stats, readable live with cat; that ends the header-only design and adds a registration point after stats::initialize().

12. shared_v to shared_visits, shared_t to shared_tokens

Done, but not as a plain rename, because that does not compile. At the PR tip the namespace tron::page_share already has process-wide atomics named shared_visits and shared_tokens, and flush() adds into them by their bare names. C++ looks a bare name up in the member function's own scopes, then in the class, then in the enclosing namespaces, and stops at the first match. A member named shared_visits therefore hides the atomic inside flush(), and the line becomes shared_visits.fetch_add(shared_visits, ...) on a plain integer:

renamed.hpp:76:19: error: request for member 'fetch_add' in
  '((tron::page_share::local*)this)->tron::page_share::local::shared_visits',
  which is of non-class type 'uint64_t' {aka 'long unsigned int'}

Reproduced with g++ 11.4 on a copy of the PR-tip header with only the two members renamed. The CI test build would catch it in every configuration, because the test target defines TRON_PAGE_SHARE_COUNTERS itself [t/CMakeLists.txt:271].

Fix applied (after jhan's choice in the follow-up). My first version grouped the six process-wide counters in a struct so that both sides could carry identical member names; jhan rejected identical names in one file. The final version keeps the six process-wide counters as plain inline atomics, as at the PR tip, and gives each the total_ prefix: total_page_visits, total_relevant_query_tokens, total_shared_visits, total_shared_tokens, total_pending_visits, total_histogram[7]. The per-call struct page_visit_counts has the same names without the prefix, so flush() reads as a sentence: total_shared_visits.fetch_add(shared_visits, ...). total_ is tron's usual prefix for a process-lifetime sum [kv_cache.hpp:443-444 total_bytes, total_books; expert_stats.hpp:101 total_passes]. No identifier appears twice in the file, and no member can hide a namespace name.

Alternatives that were on the table: a totals struct with identical member names on both sides (rejected: same names in one file), or qualifying the two lines in flush() as page_share::shared_visits.fetch_add(shared_visits, ...) (rejected: leaves the trap for the next edit). If you ever want the unit in the token member, shared_query_tokens is the one-word variant.

The revised header

#pragma once
// Page-share instrumentation for the software attention loop.
//
// For every visit of one (KV page, kv_head) pair in apply_page_range, the hooks
// count how many query tokens of the current minibatch had at least one
// relevant K token on that page (n_relevant_query_tokens). That number is how
// many queries a kernel could serve from one load of the page. It says nothing
// about whether the page was dense (all 64 tokens visible) for any of those
// queries; a query counts if at least one K token on the page is relevant to
// it.
//
// Compiled in only by the CMake option TRON_PAGE_SHARE_COUNTERS (default OFF),
// which defines TRON_PAGE_SHARE_COUNTERS. Without the define this header is
// empty and the hooks in self_attention.hpp compile to nothing.
//
// Report: printed to stderr at normal process exit, if any visit was counted.

#ifdef TRON_PAGE_SHARE_COUNTERS
#include <atomic>
#include <cstdint>
#include <cstdio>

namespace tron::page_share {

// Process-wide totals, summed over every apply_page_range call of every
// attention worker. Each has a per-call counterpart of the same name without
// the total_ prefix in page_visit_counts below.
//
// Histogram of the per-visit query-token count, one slot per range:
//   slot 0: exactly 1 query token    slot 4: 5 to 8
//   slot 1: exactly 2                slot 5: 9 to 16
//   slot 2: exactly 3                slot 6: 17 or more
//   slot 3: exactly 4
// The report prints the slots in this order, labelled 1 2 3 4 5-8 9-16 >16.
inline std::atomic<uint64_t> total_histogram[7];
// Visits with at least one relevant query token. A (page, kv_head) visit in
// which no query token had a relevant K token is not counted anywhere.
inline std::atomic<uint64_t> total_page_visits;
// Sum over the counted visits of the per-visit query-token count, i.e. the
// number of (query token, page visit) pairs. Each pair counts one, however many
// K tokens on the page were relevant to that query and whatever the number of
// query heads per kv_head; the report calls these pairs "work units" in that
// coarse sense. total_relevant_query_tokens / total_page_visits is the average
// number of query tokens per counted visit.
inline std::atomic<uint64_t> total_relevant_query_tokens;
// Visits with two or more relevant query tokens: visits where one load of the
// page could have served several queries. The counters record that
// opportunity; they do not observe page loads or any reuse.
inline std::atomic<uint64_t> total_shared_visits;
// The (query token, page visit) pairs that fell on shared visits.
// total_shared_tokens / total_relevant_query_tokens is the fraction of all
// pairs that a kernel serving several queries per page load could take from
// shared visits.
inline std::atomic<uint64_t> total_shared_tokens;
// Visits made in the second attention pass of a step (pending = true). That
// pass covers the pages whose K and V are written during this same forward
// pass, by this or another minibatch. See Note [Ready versus pending attention
// work] in model.hpp and Note [Minibatch Dependency Tracking] in common.hpp.
inline std::atomic<uint64_t> total_pending_visits;

// Counts gathered by one apply_page_range call (one worker, one kv_head, one
// page range) as plain integers, then added to the total_* atomics by flush().
struct page_visit_counts {
  uint64_t histogram[7] = {};
  uint64_t page_visits = 0;
  uint64_t relevant_query_tokens = 0;
  uint64_t shared_visits = 0;
  uint64_t shared_tokens = 0;
  uint64_t pending_visits = 0;
  // Records one (page, kv_head) visit in which n_relevant_query_tokens query
  // tokens had a relevant K token on the page. A visit with none is not
  // counted.
  inline void record_page_visit(uint64_t n_relevant_query_tokens, bool is_pending) {
    if (n_relevant_query_tokens == 0) return;
    page_visits++;
    relevant_query_tokens += n_relevant_query_tokens;
    if (is_pending) pending_visits++;
    if (n_relevant_query_tokens >= 2) {
      shared_visits++;
      shared_tokens += n_relevant_query_tokens;
    }
    int slot = n_relevant_query_tokens == 1    ? 0
               : n_relevant_query_tokens == 2  ? 1
               : n_relevant_query_tokens == 3  ? 2
               : n_relevant_query_tokens == 4  ? 3
               : n_relevant_query_tokens <= 8  ? 4
               : n_relevant_query_tokens <= 16 ? 5
                                               : 6;
    histogram[slot]++;
  }
  // Adds these counts to the total_* atomics. Call once per object (the hooks
  // create a fresh object per apply_page_range call); the counts are not reset.
  inline void flush() {
    if (page_visits == 0) return;
    for (int i = 0; i < 7; i++) {
      if (histogram[i] != 0)
        total_histogram[i].fetch_add(histogram[i], std::memory_order_relaxed);
    }
    total_page_visits.fetch_add(page_visits, std::memory_order_relaxed);
    total_relevant_query_tokens.fetch_add(
        relevant_query_tokens, std::memory_order_relaxed);
    total_shared_visits.fetch_add(shared_visits, std::memory_order_relaxed);
    total_shared_tokens.fetch_add(shared_tokens, std::memory_order_relaxed);
    total_pending_visits.fetch_add(pending_visits, std::memory_order_relaxed);
  }
};

// Prints the totals to stderr when the process exits normally. Static destructors
// run on a return from main and on exit(); they do not run on abort() (so not
// after a TRON_ASSERT failure), quick_exit(), a crash, or SIGKILL, and no
// report appears in those cases. The loads below are not one snapshot: the
// four lines are consistent only because the attention workers have stopped
// flushing by the time static destruction runs.
struct exit_reporter {
  ~exit_reporter() {
    const uint64_t n_visits = total_page_visits.load();
    const uint64_t n_tokens = total_relevant_query_tokens.load();
    if (n_visits == 0) return;
    std::fprintf(stderr,
        "\n[page-share] page visits=%llu  query-token work units=%llu  avg query "
        "tokens per visit=%.3f\n"
        "[page-share] visits with sharing (>=2 query tokens)=%llu (%.2f%% of "
        "visits, %.2f%% of work)\n"
        "[page-share] pending-phase visits=%llu\n"
        "[page-share] query tokens per visit: 1:%llu 2:%llu 3:%llu 4:%llu "
        "5-8:%llu 9-16:%llu >16:%llu\n",
        (unsigned long long)n_visits, (unsigned long long)n_tokens,
        (double)n_tokens / n_visits, (unsigned long long)total_shared_visits.load(),
        100.0 * total_shared_visits.load() / n_visits,
        n_tokens != 0 ? 100.0 * total_shared_tokens.load() / n_tokens : 0.0,
        (unsigned long long)total_pending_visits.load(),
        (unsigned long long)total_histogram[0].load(),
        (unsigned long long)total_histogram[1].load(),
        (unsigned long long)total_histogram[2].load(),
        (unsigned long long)total_histogram[3].load(),
        (unsigned long long)total_histogram[4].load(),
        (unsigned long long)total_histogram[5].load(),
        (unsigned long long)total_histogram[6].load());
  }
};
inline exit_reporter report_at_exit;

}  // namespace tron::page_share
#endif  // TRON_PAGE_SHARE_COUNTERS
