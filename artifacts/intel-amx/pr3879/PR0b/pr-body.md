# kv_cache: load last_print_bytes with a valid memory order

Three commits: the one-line fix, a regression test for it, and the test's cost-data entry.

**The fix.** `log_kv_footprint`, the function in `h/tron/models/kv_cache.hpp` that prints the throttled "KV cache footprint" log line (KV = the attention keys and values the server caches), loaded its `last_print_bytes` atomic (a counter several threads update) with `std::memory_order_release` (a memory order: the rule for how the operation is ordered against other memory operations; release is meant for stores). The C++ standard does not allow that order on a load: the precondition of `atomic<T>::load` ([atomics.types.operations]) is that the order is neither `memory_order::release` nor `memory_order::acq_rel`. The old call therefore had undefined behaviour. The loaded value only decides whether the footprint has changed enough to print the line again. The two totals in the same function (`total_bytes`, `total_books`) are already updated with relaxed operations. The load is not used to synchronise access to other data. The load therefore becomes relaxed; the store that follows keeps its release order.

Pre-existing on `main` (line 454 at a80b102c18). Ben (bgamari-positron) pointed at it while reviewing #3879 ([comment 3937077542](https://github.com/positron-ai/tron/pull/3879#discussion_r3937077542), anchored at line 487 of the head 60d66d9c04, where the same load sits inside that PR's version of the function). Separate PR so the fix does not depend on the AMX (Intel Advanced Matrix Extensions) attention change.

**The test** (`t/t_kv_footprint_memorder.cpp`, fake host test, no model files). The wrong and the right order compile to the same instructions with clang, so no check on program output can fail; the compiler, clang-tidy, ThreadSanitizer and UndefinedBehaviorSanitizer are silent too. The detector is libstdc++'s own precondition check inside `std::atomic::load`, enabled by `_GLIBCXX_ASSERTIONS` on this test target only (`add_catch_test ... DEFINES _GLIBCXX_ASSERTIONS`; the macro is independent of `NDEBUG` and does not change data layouts). `log_kv_footprint` is always-inline (`TRON(inline)`), so the test's translation unit compiles its own checked copy: a wrong order aborts (SIGABRT) at the first call. The test forks a child that calls `tron::log_kv_footprint(1, 0)` (below the print granularity, nothing is logged) and requires the child to exit normally, the pattern of `t_heap_guard.cpp`. Without the fix the test fails (`REQUIRE(sig == 0)` sees 6 = SIGABRT); with the fix it passes. The `#error` at the top of the file makes a dropped define a build failure instead of a test that can no longer fail. The bug entered `main` in 0b5bdf2c86 (2025-04-10). Verified on delphi-3bda (Xeon 6962P, clang 19): built with the project's CMake, the test passes on this branch and fails on `main` plus the test alone (1 of 2 assertions failed, the child died with SIGABRT). Its cost-data entry in `config/test-benchmarks.json` (about 0.7 s per run, 8 MB peak RSS) is the third commit.
