PR 0b: can a test guard the memory-order bug?

Part of the PR 3879 split. Written 2026-09-08 04:5x UTC, "Landed" table added 12:0x UTC. Evidence files: PR3879/new-PRs/PR0b/ub-guard/ (scripts, compiler outputs, the proposed test, the verification report). Experiments ran on delphi-3bda with tron's own toolchain (single-file compiles only, because the nightly CI held the machine).

Short version. No test that only watches program output can catch this bug: with tron's compiler the wrong line and the fixed line produce identical machine code, and no compiler warning, clang-tidy check, ThreadSanitizer or UndefinedBehaviorSanitizer report exists for it. One instrument does catch it: the C++ standard library's own precondition check, switched on by the macro _GLIBCXX_ASSERTIONS, which aborts the program at the first bad load. A small Catch2 test compiled with that macro on its own target fails on today's main and passes with PR 0b, inside the normal build; a pre-commit grep rule is a cheaper second guard for the literal spelling.

Words used here

  • PR 0b: draft pull request #4265 (branch jhan-kv-footprint-memorder, commit e2f22c7a09), a one-line fix in h/tron/models/kv_cache.hpp.
  • log_kv_footprint: the function in kv_cache.hpp that prints the throttled "KV cache footprint" log line (KV = the attention keys and values the server caches). Every KV book (one allocation of cache pages) calls it when created and destroyed.
  • memory order: the argument of an atomic operation that says how it is ordered against other memory operations. The standard forbids release and acq_rel on a load ([atomics.types.operations], unchanged since C++11). Breaking that rule is undefined behaviour: the compiler may do anything, including the right thing by accident.
  • libstdc++: the C++ standard library tron links (GCC 14.3's copy in the nix toolchain; GCC 11 or 12's copy on the CI runners). _GLIBCXX_ASSERTIONS: its switch for run-time precondition checks; independent of NDEBUG; does not change data layouts (unlike _GLIBCXX_DEBUG).
  • TSan / UBSan: ThreadSanitizer and UndefinedBehaviorSanitizer, clang's run-time checkers (tron presets tsan, option UBSAN).
  • always-inline: TRON(inline) expands to inline __attribute__((always_inline)) (h/common/attributes.hpp:78), so every translation unit that calls the function compiles its own copy.
  • lefthook: tron's pre-commit hook runner (lefthook.yml); the CI lint job runs the same hooks over the whole tree.
  • cost data: config/test-benchmarks.json; CI fails a build whose test binaries have no entry (bin/slice bench --check).

Takeaway: in tron's toolchain only the libstdc++ precondition check reacts. The identical machine code means the two versions behave the same way, so no assertion on outputs can tell them apart.

Why the compilers stay silent: clang's diagnostic for invalid orders fires only when the order is a constant at the builtin call; libstdc++ passes it through a function parameter, so clang never sees a constant and lowers the load to a relaxed load before TSan instruments it (LLVM 19 CGAtomic.cpp, ThreadSanitizer.cpp; LLVM's TSan runtime checks load orders only in debug builds of the runtime). GCC's warning exists but is attributed to the system header and hidden. libc++ would warn at compile time, but the nix toolchain has no libc++ (link fails on -lc++).

3. Guard A: a Catch2 test whose own target carries the define

Because log_kv_footprint is always-inline, a test translation unit compiled with _GLIBCXX_ASSERTIONS gets its own checked copy of the function, while the rest of tron is built as today. The test forks a child that calls the function once below the print granularity (so the load on line 454 executes and nothing is logged) and requires the child to exit normally. This is the pattern of t/t_heap_guard.cpp for code that must abort.

// t/t_kv_footprint_memorder.cpp (draft; full file in ub-guard/t_kv_footprint_memorder.cpp)
#ifndef _GLIBCXX_ASSERTIONS
#error "t_kv_footprint_memorder needs _GLIBCXX_ASSERTIONS (add_catch_test DEFINES); without it the test cannot fail"
#endif
#include <catch2/catch_test_macros.hpp>
#include "tron/models/kv_cache.hpp"
// fork_and_get_signal(fn): fork, run fn in the child, return the signal that killed it (0 = exited normally)

TEST_CASE("log_kv_footprint satisfies the atomic memory-order preconditions", "[kv_cache][memory_order]") {
  int sig = fork_and_get_signal([] { tron::log_kv_footprint(1, 0); });
  REQUIRE(sig == 0);
}
# t/CMakeLists.txt (draft). DEFINES is an argument add_catch_test already accepts (t/CMakeLists.txt:111).
add_catch_test(NAME t_kv_footprint_memorder LIBRARIES tron pos_fake
  DEFINES _GLIBCXX_ASSERTIONS   # the instrument: libstdc++ precondition checks in this translation unit only
  PROPERTIES LABELS fake)

Design points the verification pass insisted on

  • Put the define on the target, not as #define in the file: a precompiled header that pre-includes <atomic> would silently ignore a file-level define. tron has no precompiled header today (tron_header_files is never set), but the target form is safe either way. The #error guard makes a dropped define a build failure instead of a test that can no longer fail.
  • Call log_kv_footprint directly. Reaching it through a KV book constructor is not reliable: the constructor is a plain inline member, and the linker may keep the library's unchecked copy (seen on the host at -O0). The always-inline function has no such copy.
  • The test detects the bug only while log_kv_footprint stays a header always-inline function. If it moves into a .cpp file, the test passes on wrong code; the file comment should say so.
  • The bug entered main in commit 0b5bdf2c86 (2025-04-10), so the test meets the AGENTS.md rule that a regression test must reproduce a failure that existed on main.
  • Cost: a new test binary needs entries in config/test-benchmarks.json (the CI step bin/slice bench --check), the same gate PR 0 and PR 1 went through; measured 2026-09-08: about 0.7 s per run, 8 MB peak RSS (committed).

4. Guard B: a lefthook grep rule

Same shape as the existing no-cassert rule. Tested over h/, src/ and t/: the load rule hits exactly kv_cache.hpp:454; the store rule (order anchored as the store's own last argument, one level of nested parentheses tolerated) hits nothing; a naive store regex would false-positive on h/tron/shard.hpp:178 and :193. Stripping // comments first changes nothing today.

    valid-atomic-orders:
      glob: ["h/**/*.{hpp,cpp,h}", "src/**/*.cpp", "t/**/*.cpp"]
      run: |
        # C++ [atomics.types.operations]: a load may not use release/acq_rel; a store may not use acquire/consume/acq_rel.
        FOUND=$(find h src t \( -name '*.[ch]pp' -o -name '*.h' \) -not -path '*/_deps/*' -print0 \
          | xargs -0 grep -nE '\.load\(\s*std::memory_order(_|::)(release|acq_rel)\s*\)|\.store\(([^()]|\([^()]*\))*,\s*std::memory_order(_|::)(acquire|consume|acq_rel)\s*\)' || true)
        if [ -n "$FOUND" ]; then echo "$FOUND"; echo "Invalid memory order on an atomic load or store (undefined behaviour)."; exit 1; fi
  • Enforced on every pull request: the CI lint job runs lefthook run --all-files pre-commit (flake.nix:1649, cmake-single-platform.yml:112-116).
  • Because it scans the whole tree, it can only land together with or after PR 0b.
  • Blind spots: orders held in named constants (h/tron/generation/harvester.hpp:78-80 style), calls wrapped over several lines, orders passed through variables. It checks text, not intent.

5. Option C: the define on a whole build lane

A CMake option (next to ASAN/TSAN at CMakeLists.txt:39-42; add_compile_definitions(_GLIBCXX_ASSERTIONS) inside the sanitizer block at :575-586, which reaches src/, share/, t/ and Catch2 but not the third-party targets created before the :570 reset) turned on in the asan/tsan/coverage presets would check every libstdc++ precondition in every test. Today only the weekly coverage lane (Saturday 05:00 UTC) builds Debug and runs tests; pull-request CI builds the native preset (RelWithDebInfo) with /usr/bin/clang++-19 on Ubuntu 22.04 runners. Under such a lane the existing fake host test t_llama_unit, which constructs books directly without model files, would have aborted on main with no new test code. Insufficient data on what else would fire: the measurement is a Debug-preset build with the define plus bin/slice run --filter=host on main a80b102c18 and on e2f22c7a09, listing every assertion message. Not run: it is a full build and delphi-3bda was executing the nightly CI.

6. Recommendation

  • Do both A and B. A is a real regression test that fails on main and passes with the fix, inside the normal build; B closes the class of mistakes for the literal spelling at commit time.
  • A is landed in PR 0b (2026-09-08, commits dc5d496d06 and 7a7699b338). B is not added yet; it can only land with or after PR 0b (it fails on today's main).
  • Consider C later, after the measurement in section 5.

7. How this was verified

Three independent reviewer agents (standard-library semantics, tron build and CI integration, test design) tried to refute nine written claims, and a fourth resolved their contradictions. Their report is ub-guard/verification-workflow-wf_e11ca789.json. Their corrections shaped sections 3 and 4: the per-target define (claim "no unit test can catch it" was too strong), the direct call instead of the constructor route, the precompiled-header trap, the balanced-parentheses store regex, the cost-data gate, and the fact that the CI runners use Ubuntu's clang 19 with the system libstdc++ (the assertion exists in GCC 11, 12 and 14.3 headers). Two items they asked for were then measured: the assembly diff on the real header (identical) and the test under tron's clang 19 with lld (section 3).
