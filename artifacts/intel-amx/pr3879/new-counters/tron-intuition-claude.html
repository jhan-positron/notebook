A mental map of tron for timing estimates by hand

AMX / AVX / attention on the FPGA, for llama-3.1, qwen-2.5 and gpt-oss. Written by Claude for jhan, 2026-10-07, from the measurements of 2026-08-31 to 2026-10-04 on delphi-3bda. Every number is measured and cited unless marked est. Generator: exec/tron-intuition-20261007/gen_intuition.py.
Short version. A decode step of tron is one forward over all layers for all users of one engine, and its time is other work (the weight multiplies on the FPGA cards, about flat in context) plus attention (which re-reads the whole context every step, so it grows with prompt length and with users per engine). AMX changes only the attention page visits that run on the CPU, on a full 64-token page, for a model whose attention shape fits the kernel. So the estimate by hand is: count those visits, price them with the per-unit costs, and pass the saving to the forward through the layer's waits and overlaps.
  • llama-3.1-8b gains: +3 % at 8 users and prompt 1024 in lockstep decode, +16 % at prompt 8192, +11 to +14 % in the CI harness at 8 users per engine.
  • qwen-2.5-32b gains nothing today. It fails the kernel's shape gate (5 query heads per KV head), so every page visit stays on the AVX loop.
  • gpt-oss runs attention on the FPGA and keeps only 1-to-4-key tails and 128-key sliding windows on the CPU. A kernel for its shape could gain under 1 % of decode throughput (est.).

Words used here

tron, runtron, rinzler
tron is Positron's inference program. runtron is its command-line tool: one process, a fixed number of users, all users decode in lockstep. rinzler is the production server: continuous batching behind a proxy, started by platformd.
engine, tp2, tp4
An engine is one tron process bound to FPGA cards and CPU cores. tp2 splits every weight multiply over 2 cards, tp4 over 4. On delphi-3bda (the test server, two Intel Xeon 6962P sockets) a tp2 engine has 28 application cores (one main thread plus 27 workers) and a tp4 engine 56 (main plus 55).
nightly, CI harness, users per engine
The nightly is the systems_test performance run on delphi-3bda. Its harness spreads 8 users over 4 engines at tp2 (2 users per engine) or 2 engines at tp4 (4 per engine). The 32-user llama-3.1-8b row runs 8 users per engine. U in the formulas below is always users per engine.
AMX, AVX, dotter, kernel
AMX is Intel's tile matrix instruction set (bf16 tiles of 16 rows by 64 bytes, multiplied by one instruction). AVX is the 512-bit vector set. tron's AVX attention loop is called the dotter. "The kernel" below means tron's AMX attention kernel (canonical form, in main since 2026-09-15).
AoF, CPU attention
AoF = attention on the FPGA: the card scores the stored keys and values, and the CPU keeps a short tail. It is the default for ingested models (qwen3-4b, gpt-oss) when USE_HW_ATTN is unset. USE_HW_ATTN=0 forces CPU attention. Hand-written plugins (llama, qwen-2.5) default to CPU attention.
kill switch
TRON_AMX_DISABLE=1: the AMX binary with the kernel switched off. Every page visit then runs on the AVX loop. Same visits, same key counts, different speed.
bf16, KV cache, KV page
bf16 is the 16-bit floating-point format of the keys, values and queries. The KV cache stores every past token's keys and values per layer per KV head, in pages of 64 tokens: 16 KiB of keys plus 16 KiB of values = 32 KiB per page.
KV head, kv_mul, head size
Models store fewer key/value heads than query heads. kv_mul = query heads per KV head (also called the GQA ratio). Head size = numbers per head. The kernel serves exactly head size 128 and kv_mul 4 [amx_attn_iface.hpp:148-150].
unit, page visit
One query token (its kv_mul query heads) scored against one KV page of one KV head: the QK multiply, the softmax pieces, the PV multiply and the running-state update. It reads the page's 32 KiB. "Visit" and "unit" are the same thing: the counters say visit, the timing pages say unit.
forward, decode step, token job, TPS
A forward is one pass over all layers. In decode it produces one new token for each user: one token job per user. TPS = tokens per second per user. In lockstep decode (runtron) TPS = 1 / forward time.
prefill, chunk, TTFT
The prompt is scored in chunks of 128 tokens per user per forward (TRON_PER_USER_PROMPT_CHUNK_LIMIT, default 128 [libtron.hpp:194-205]). TTFT = time to first token, which the harness divides into the prompt length to print a prefill rate.
minibatch
The users of one forward can be split into groups whose card work and CPU attention overlap. The hand-written llama plugin allows this (max_minibatches = -1 [llama.hpp:183]) and runs 8 users as two minibatches of 4. Ingested plugins run one minibatch.
attention worker, main thread, job, ready pass, pending pass, join
The main thread runs the plugin schedule and launches the card jobs. Attention workers run the attention jobs: each layer's attention operation is split over the workers as (KV head, page range) sections, one job per worker. A job has a ready pass (pages that were complete before this layer), a pending pass (the newest page, after this layer's K/V landed) and a join (the fold of partial results across workers).
T1 to T5
The five timers of the attention stats (PR 4596): T1 = wall time of a forward. T2 = busy time of one attention job (both passes plus the join, without the K/V wait). T3 = wall time of a job as worker 0 sees it, waits included. T4 = layer period on worker 0 (from the start of one layer's job to the start of the next). T5 = join wait, inside T2.
GOF, shard, engagement
GOF = group of four tokens, the card's copy and scoring unit. A shard is 1024 tokens of K/V on the card. Engagement 127 = the card scores positions from 127 on. Earlier positions stay on the CPU.
sliding window
A layer whose attention sees only the last N keys. gpt-oss uses N = 128 on its even layers. Such layers never run on the card [model.hpp:1554-1556 per attn-stats-compare-QA.html 3.5].
prompt N
A prompt of N tokens. Every run quoted here then generates 256 tokens per user, so the context a decode step reads is N plus the tokens generated so far.
lever
A setting of the cell that moves the gain: users per engine, prompt length, attention mode.
est., Insufficient data
est. marks an estimate. Insufficient data marks a quantity nobody measured, with the measurement named.

2. What to internalize: ten rules with their numbers

These are the facts to keep in memory. Each has one measured number attached so that a guess can be checked against it.

1. A decode step is other work plus attention, and only attention grows.
The weight multiplies run on the cards and take about the same time whatever the context. Attention re-reads every stored page each step, so its time grows with context and with users per engine. Measured attention share of a worker's forward: 16 / 31 / 62 % at prompt 256 / 2048 / 8192 for one qwen3-4b user on the AVX path [make-sense-amx-vs-avx.html section 7]. At 8 users and prompt 1024 it is 56 % for qwen3-4b and 67 % for llama-3.1-8b. At prompt 8192 llama reaches 93 % (Table 1).
2. Attention is a loop over page visits, and the count is arithmetic.
Visits per decode step = U users x L layers on the CPU x KV heads x pages per user (context / 64, rounded up). The attention workers share them. Example: qwen3-4b, 8 users, context 1152 (prompt 1024 plus 128 generated tokens): 8 x 36 x 8 x 18 = 41,472 visits, 2,074 per worker with 20 workers.
3. A unit costs about 3 us, and AMX removes 0.5 to 1.0 us of it.
One unit (32 KiB read) takes 3.64 us on the AVX path and 2.89 us with the canonical kernel at prompt 8192, where the pages come from DRAM. At prompt 2048 the pair is 2.80 vs 2.14 us, and at prompt 256 (pages in cache) 2.88 vs 2.38 us [make-sense-amx-vs-avx.html 7.2.1]. Hot in the L2 cache the two paths take 1.68 and 0.62 us [perf-model/index.html section 5]. The memory time of a unit is 2.49 us (32 KiB at 13.1 GB/s per core while 27 cores read). So the arithmetic can be 33x faster and the unit still shortens by only 1.26x, because the bytes set the lower bound.
4. Pass the attention saving to the forward through the layer's overlap.
With one minibatch (ingested plugins: qwen3-4b, gpt-oss) a shorter attention job shortens the layer period 1:1. When the kernel was enabled, qwen3-4b's attention busy fell 33 us per layer (1.2 ms over 36 layers), T4 fell 1.41 ms and T1 fell 1.45 ms per forward. With two minibatches (llama at 8 users) the cards' work for the other minibatch overlaps the attention, and at prompt 1024 the period did not move at all (247 vs 248 us) although busy per job fell 9 %. At prompt 8192 attention is 93 % of the forward and the saving passed 1:1 again (period 1405 -> 1207 us). Working rule for llama: one third at short prompts, 1:1 at long prompts (section 3).
5. The path is chosen per page visit, not per model and not per token.
Figure 3 is the decision. Under AoF the card scores every whole GOF and the CPU keeps a 1-to-4-key tail, so the kernel's 64-key unit never fills: 0 AMX visits in the steady state. A sliding-window layer never goes to the card. The shape gate (head size 128 and kv_mul 4) is compile-time. llama-3.1-8b and qwen3-4b pass it. qwen-2.5-32b (kv_mul 5), llama-3.1/3.3-70b (kv_mul 8) and gpt-oss (head size 64, kv_mul 8) do not. A partial page always takes the AVX loop, so even under CPU attention the newest page is AVX in 63 of every 64 steps.
6. Keys are not time.
The counters count keys scored per path. Convert keys to visits, and visits to time with the unit costs. Keep the waits fixed: the join wait (T5) and the K/V wait do not shrink when a kernel is faster. gpt-oss scores 10.2 % of its decode keys on the CPU, which is 6.3 % of a worker's forward time, of which a kernel could remove under 1 % (section 6, example C).
7. Under AoF the step still grows with context, inside the card.
qwen3-4b at 8 users: T1 = 7.75 ms per forward at prompt 1024 and 15.96 ms at prompt 8192. The join wait (the workers waiting for the card's partial results) rises from 58 % to 88 % of the workers' busy time [attn-stats-compare.md section 7]. The CPU build matters little there: AMX on vs off differ by under 1 % in both cells. AoF beats CPU attention with AMX by 1.6x at prompt 1024 (126.6 vs 79.5 TPS) and 3.6x at prompt 8192 (61.5 vs 17.1 TPS, runtron 8 users) [attn-stats-compare.md section 1, and q4b-rt8u-20260922].
8. Users per engine is the lever in CI, not users in total.
The nightly's 8 users are 2 per engine at tp2 and 4 per engine at tp4. llama-3.1-8b gains +0.2 / +4.8 / +10.8 % at 2 / 4 / 8 users per engine (prompt 1024) and +14.0 % at 8 users per engine with prompt 2048 or 4096 (Figure 5). The same model at 2 users per engine and prompt 1024 shows nothing, which is what the nightly's 8-user llama row measures.
9. Prefill is the other place where the kernel counts.
The prompt is scored 128 tokens per user per forward. The kernel takes the full pages of earlier chunks, so under CPU attention prefill forwards run 1.7x to 2.5x faster per attention job [attn-stats-compare.md section 7]: llama-3.1-8b, 8 users, prompt 8192: TTFT 34.6 s with the kernel vs 78.8 s without. Under AoF the card does that work and the kernel sees only copy-lag pages (0.6 % of the prefill keys at prompt 8192). The nightly reports prefill as prompt length divided by TTFT. Nothing on the server times prefill.
10. Name the denominator, and check that AMX actually ran.
Three pairs are easy to mix: kill switch vs a clean AVX build (the switch costs 0 to 5 points by itself, build-dependent), runtron lockstep vs the CI harness (section 9, edge 1), and users in total vs per engine. A TPS step on the night AMX arrived is not proof: on 2026-09-23 qwen-3-4b tp4 rose +18.3 % and gpt-oss-120b +12.8 %, both AoF rows with 0 AMX visits, in a package with two other merges [Was-AMX-boosting-all-models.html section 1]. Proof is the stats (ready_amx_visits > 0) or the AMX busy-cycle counter (section 8, card 4).

4. Which path serves a page visit

The path is a property of one visit, decided at the moment the worker reaches the page. Three questions decide it. The right-hand panel has the closed forms that the counters reproduce exactly.

5. What a unit costs, and why the kernel's gain is 1.3x and not 8x

A unit is the smallest thing the kernel changes. Its cost has two parts: the instructions, and the wait for its 32 KiB. Hot in the L2 cache the AMX path is 2.7x faster than the AVX path (0.62 vs 1.68 us). Under decode load the pages come from DRAM at 13.1 GB/s per core, so the 32 KiB need 2.49 us however fast the instructions run, and the two paths end 0.75 us apart (2.89 vs 3.64 us at prompt 8192).

Two consequences for estimates. First, use the row that matches the context: 0.50 us saved per unit at prompt 256, 0.66 at 2048, 0.75 at 8192 (canonical kernel). Second, the AMX tile does useful work on 4 of its 16 rows in private decode (one query token per user, 4 query heads per KV head), so the 8x instruction-level figure never applies to decode. It applies to prefill, where many query tokens share a page [make-sense-amx-vs-avx.html section 4].

6. The recipe: six steps, then four worked examples

The steps turn the map into a number. Each example then runs the steps on one of your models and compares with a measurement when one exists.

  1. Fix the cell. Model, tp, users per engine U, prompt length, attention mode (AoF or CPU), and the two arms (kill switch vs kernel, or AVX build vs AMX build). Take the context at mid-run: prompt plus 128 generated tokens.
  2. Decide what is on the CPU. Figure 3: under AoF only the 1-to-4-key tails and the sliding-window layers are on the CPU, and no page is full. Under CPU attention every page is on the CPU.
  3. Count the kernel-eligible visits per forward per worker. U x (layers on the CPU) x KV heads x full pages per user, divided by the attention workers (Table 1 gives the worker counts the split heuristic chose). Only models that pass the shape gate have any.
  4. Price them. Saving per worker per forward = visits x (AVX unit - AMX unit) at that context: 0.50 us at prompt 256, 0.66 us at 2048, 0.75 us at 8192 (Figure 4). This is the drop in T2 summed over a worker's jobs.
  5. Pass the saving to the forward. One minibatch, or attention over 90 % of the forward: 1:1. llama at 8 users and a short prompt: about one third. New T1 = T1 - pass x saving. Gain = T1 / new T1 - 1.
  6. Check against an anchor. Table 1, Figure 5 or the nightly rows. When no anchor exists, name the cell to run (TRON_ATTN_STATS=1, both arms) instead of trusting the number.

Example A: llama-3.1-8b, tp2, 8 users, CPU attention, kill switch vs kernel

Prompt 1024. Context at mid-run 1152 tokens = 18 pages per user, 17 of them full. Visits = 8 users x 32 layers x 8 KV heads x 17 full pages = 34,816 per forward. The run used 23 to 24 attention workers [Table 1 source], so about 1,450 visits per worker. At this context the pages are between the cache and the DRAM regime, so the unit saving is 0.50 to 0.66 us: 0.73 to 0.96 ms per worker per forward (est.). Measured: busy per job fell from 103 to 91 us over 64 jobs per worker per forward = 0.77 ms. The two minibatches overlap most of it with the cards' work for the other minibatch: the pass is about one third, so T1 drops 0.24 to 0.32 ms of 8.92 ms = +2.8 to +3.7 % (est.). Measured: T1 8.92 -> 8.66 ms, TPS 110.7 -> 113.9 per user = +2.9 %.

Prompt 8192. Context 8320 tokens = 130 pages, 129 full. Visits = 8 x 32 x 8 x 129 = 264,192 per forward, 26 workers, 10,161 per worker. Saving = 10,161 x 0.75 us = 7.6 ms per worker per forward (est.). Measured drop of T2 over the 64 jobs: (679 - 574) us x 64 = 6.7 ms. Attention is 93 % of the forward, so the pass is 1:1: T1 46.05 -> 38.4 to 39.3 ms = +17 to +20 % (est.). Measured: 39.64 ms, TPS 21.4 -> 24.8 = +16.0 %.

The same model in the CI harness at 8 users per engine and prompt 1024 gains +10.8 % (nightly package vs canonical package, 3 passes) and +12.9 % (same binary, kill switch, rinzler) [CI-test/status/llama-3.1-8b.html, and VNNIed-K-in-place/status/llama8b-AMX-gain-vs-load.html]. The map's decode-only arithmetic gives +3 % for that cell. The gap is the first edge of the map (section 9).

Example B: qwen3-4b, tp2, 8 users, AoF (the deployed mode)

Step 2 ends the estimate. The card scores every whole GOF of every user from position 127 on. The CPU keeps (p mod 4) + 1 keys per (user, KV head, layer) per step, 1 to 4 keys, mean 2.49. No page is ever full on the CPU, so the kernel-eligible visits are 0 and the predicted gain is 0. Measured: TPS -0.9 % at prompt 1024 and -0.5 % at prompt 8192 with the kernel on, busy per job equal within 1 %, 0 AMX visits in both cells (Table 1, and attn-stats-compare.md section 2.1).

The useful question for qwen3-4b is therefore AoF vs CPU attention, not AMX vs AVX: at prompt 1024 and 8 users AoF gives 126.6 TPS per user against 79.5 with CPU attention and the kernel (1.6x). At prompt 8192 the ratio is 3.6x (61.5 vs 17.1 TPS, runtron 8 users, 2026-09-22) [CI-test/status/qwen3-4b-prefill-amx-vs-fpga.html section 7]. The kernel matters for this model only where the card is absent, full (HBM exhaustion), or bypassed (prefix-cache branches, prompts under 128 tokens) [counter.html section 2.3].

Example C: gpt-oss-120b, tp4, 8 users, AoF, prompt 1024 (the Scratch page question)

The question on the Scratch page was whether the 10 % of decode keys that gpt-oss scores on the CPU means a kernel for its shape would pay. The map answers in four lines.

  1. What is on the CPU. The 18 card layers keep a 1-to-4-key tail (40,960 AVX keys per layer per run, no full page). The 18 sliding-window layers score 128 keys per query on the CPU: 1 full page plus 2 partial pages in 252 of the 256 steps. That is 2,097,152 AVX keys per layer per run (8 users x 8 KV heads x 128 keys x 256 steps) [attn-stats-compare.md section 6, and the exit report's per-layer line].
  2. Kernel-eligible visits. One full page per (user, KV head, sliding layer) per step: 8 x 8 x 18 = 1,152 per forward, holding half of those layers' keys. Today the shape gate (64 wide, kv_mul 8) sends them to the AVX loop.
  3. Time. Busy per job in a sliding-window layer is 36.0 us (29.4 us scoring plus 6.6 us join wait), 18 jobs per worker per forward = 0.65 ms = 6.3 % of the 10.26 ms forward (Figure 2d). The join wait does not change with a kernel, so the ceiling for any kernel is the 0.53 ms of scoring = 5.2 % of T1.
  4. Price. On the fitting models the kernel cut decode busy per job by 12 to 16 % while taking 96 to 99 % of the keys (Table 1: llama 103 -> 91 us, qwen 229 -> 193 us). Half the keys at that rate is 6 to 8 % of 0.65 ms = 0.04 to 0.05 ms per forward = 0.4 to 0.5 % of T1 (est.). Pass 1:1 (one minibatch). So the answer is: under 1 % of decode TPS, with 5.2 % as the ceiling.

Two cautions that the map makes visible. The 128-key window of one KV head is 32 KiB and stays in cache across steps. So the per-key cost there is the cache-regime one, not the 3.6 us DRAM unit (Insufficient data for the exact value: only a built kernel measures it). Prefill has more room than decode. The sliding layers' attention busy is 8.7 % of a 335 ms prompt forward, and the kernel's prefill cut on the fitting models is 1.7x to 2.5x per job. So 3 to 4 % of TTFT is reachable (est.) [Notion Scratch page 2026-10-07, and the leaves prompt_or_mixed_layer_*].

Example D: qwen-2.5-32b, tp2, nightly (2 users per engine), CPU attention

qwen-2.5-32b is a hand-written plugin configuration (model_type::llama), so it defaults to CPU attention like llama [llama.hpp:1594, and hw_attn_config.hpp:12-15]. Its attention has 40 query heads over 8 KV heads: kv_mul 5 with head size 128. The gate fails, the AMX branch is not compiled for it, and every page visit runs on the AVX loop [tron-amx-distilled.html 4.1.1]. Predicted AMX gain today: 0. The nightly row moved +1.2 to +1.6 % between the pre and post windows, the same small step as nine other rows without the kernel, which arrived six nights after the AMX package [Was-AMX-boosting-all-models.html sections 1 and 2].

If a kv_mul-5 kernel existed, the map gives the shape of the gain but not its size. Visits per forward at 2 users per engine and prompt 1024 = 2 x 64 layers x 8 KV heads x 17 full pages = 17,408, about 645 per worker over 27 workers. At 0.5 to 0.66 us saved per visit that is 0.3 to 0.4 ms per forward (est.). The forward time of that row is at most 28 ms (1 / 35.3 TPS per user) [nightly table], so the gain at that cell is at least +1 % and probably a few percent (est.). The missing input is the attention share of this model's forward, which also decides the 8-users-per-engine case. Insufficient data: one TRON_ATTN_STATS=1 runtron cell of qwen-2.5-32b-it-fast tp2 at 2 and 8 users, prompt 1024 and 8192, gives T2 x 64 jobs / T1 directly, with no kernel needed.

Card 2: machine and engine numbers (delphi-3bda)

  • Engine cores: tp2 = 28 application cores (main thread + 27 workers), tp4 = 56 (main + 55). The card drivers use separate dev cores. Our half of the machine = socket 1 with cards 90/93/b9/bc [exec/results/attnstats-20261002/rt-results.txt placement lines].
  • Attention workers the split heuristic actually used at 8 users: qwen3-4b 20 of 27, llama-3.1-8b 23-24 (prompt 1024) and 26 (prompt 8192), gpt-oss-120b 40 of 55 at tp4 [exit report model lines, active_workers, and attn-stats-compare.md section 7].
  • Per-core streaming rate from DRAM: 19.8 GB/s for one core alone, 13.1 GB/s per core with 27 cores reading. Memory time of one 32 KiB unit: 2.49 us. DRAM latency 127 to 147 ns [perf-model/index.html sections 5 and 10].
  • Caches: L2 2 MiB per core, L3 432 MiB per socket. One qwen3-4b user at prompt 8192 reads 36 layers x 8 KV heads x 130 pages x 32 KiB = 1,170 MiB per decode step, 2.7x the L3, so the pages come from DRAM [perf-model/index.html, Words used here].
  • Clocks while busy: 3.74 GHz on the AVX path, 3.60 GHz with AMX tiles in use on 27 cores (the AMX license clock) [perf-model/index.html section 5]. The stats count TSC cycles at 2.70 GHz: divide by tsc_hz from the exit report's model line.
  • Fixed costs per attention operation: joins plus barrier 9 to 13 us per layer at 1 user (320 to 480 us per token), join wait T5 3 to 6 us per job at 8 users under CPU attention [make-sense-amx-vs-avx.html 7.2.1, and the Table 1 source].

Card 3: unit costs and visit counts

  • Unit (one visit, 32 KiB), AVX / canonical AMX / mirror AMX: 3.64 / 2.89 / 2.66 us at prompt 8192. 2.80 / 2.14 / 2.07 us at prompt 2048. 2.88 / 2.38 / 1.36 us at prompt 256. Hot in L2: 1.68 us (AVX) and 0.62 us (AMX) [Figure 4 sources].
  • Visits per decode step on the CPU: U x L(CPU) x KV heads x ceil(context / 64). Kernel-eligible = the full pages: floor(context / 64) per (user, KV head, layer), plus the pending page in 1 of 64 steps.
  • AoF steady state: 0 kernel visits, one AVX visit of (p mod 4) + 1 keys per (user, KV head, layer) per step, and the card scores 4 x floor(p / 4) keys per query. Exceptions that put pages on the CPU: a prompt under 128 tokens, a whole-page copy lag, a prefix-cache branch inside a shard, a full card store [counter.html 2.3, and attn-stats-compare-QA.html 1.3].
  • Prefill: 128-token chunks per user per forward. The chunk's own pages are always AVX (one range per token), and earlier chunks' full pages are kernel-eligible. One 8-user prompt-1024 run has 7,168 ready kernel visits per (user, KV head, layer) [attention-stats-claude.html].
  • Kill-switch identity: the same visits with the same key counts, every former AMX visit becomes one avx_full_page visit of 64 keys. Use it to check a counter reading before trusting a timing.

9. Edges of the map: what it does not predict

  1. The CI harness at 8 users per engine, prompt 1024. The map gives +3 % for llama-3.1-8b (lockstep decode, measured +2.9 %) while the CI harness measures +10.8 to +12.9 % in that cell. Hypothesis: in continuous batching a user's decode steps share forwards with other users' prefill chunks, and the kernel speeds those jobs 1.7x to 2.5x, so the per-user token interval drops more than the pure decode step. Measurement that decides it: the TRON_ATTN_STATS exit report of one rinzler engine under the CI harness, both arms, reading the T1 sums of the decode_like and prompt_or_mixed classes.
  2. The card's own time under AoF. The counters see it only as waits and join wait on the CPU side (Figure 2c). A card-side timer or a trace would split the matmuls from the attention passes.
  3. qwen-2.5-32b's attention share. No stats cell exists. One runtron cell with TRON_ATTN_STATS=1 (no kernel needed) closes it (example D).
  4. The llama pass fraction at short prompts. The one-third pass comes from one cell (8 users, prompt 1024). Cells at 2 and 4 users per engine, and at prompt 2048 and 4096, would show the shape of the rule.
  5. Per-unit costs for shapes without a kernel. kv_mul 5 (qwen-2.5-32b), kv_mul 8 (llama-70b) and 64x8 (gpt-oss) have no measured unit. The memory time (2.49 us per 32 KiB, or 1.25 us per 16 KiB page of a 64-wide head) is the only number the map can give.
  6. The AMX clock license in serving. Busy clocks fall from 3.74 to 3.60 GHz when the tiles are in use. The effect on the other work of the same cores is not separated in any run.
