Tron timing by hand

Short version

Learn the order of the work and the conditions that choose its execution path. Keep model dimensions and measured operation costs beside your drawing. In the GPT-OSS run from your image, the CPU handled 10.19% of scored keys, but a speedup estimate also needs their cost and their position in the execution schedule. [R1]

Rebuilt 7 October 2026 · implementation checked at Tron dd0f942c7525 · measurements from 2 October 2026 · accelerator-backed execution

Tron, CPU, and FPGA
Tron is the inference program under test. The CPU is the host processor. The FPGA is the programmable accelerator card.
AoF, AMX, and AVX
AoF means attention on FPGA. AMX and AVX are CPU instruction sets. Here they select how CPU attention runs.
Token, forward, prefill, and decode
A token is a piece of text. A forward is one model invocation. Prefill processes prompt tokens. Decode produces subsequent tokens.
Attention, heads, and KV
Attention scores stored keys against a query and combines their values. Heads are separate groups of these vectors. KV means cached keys and values.
KV page, GQA, and bf16
A software KV page is a 64-token block. GQA is grouped-query attention: several query heads share one KV head. bf16 is a 2-byte number format.
Elapsed time and critical path
Elapsed time is time on the clock. The critical path is the chain of dependencies that determines when the result can finish.
01 · Learn the relationships

What should you internalize?

Learn these until you can draw them

  • A token passes through every layer. The next layer needs the previous layer’s result.
  • Inside a layer, some CPU work can overlap device work. The last required result controls the next step.
  • Full attention grows with visible history. A sliding window caps the history used by that layer.
  • AoF chooses device attention where it is eligible. AMX chooses an implementation for eligible CPU pages.
  • A count becomes a time only after you apply a matching measured cost.
  • Faster work shortens elapsed time only where it advances a required result.

Keep these in a reference card

  • Exact model dimensions, attention windows, and active experts.
  • The build, hardware, worker count, and actual path counters.
  • Measured costs for complete pages, partial pages, joins, transfers, and device operations.
  • The boundaries and units of every timer you use.
  • A matching baseline for prompt processing and for decode.

Memorizing a particular microsecond value is less useful than recording the conditions under which it was measured.

1 · ShapeWhich vectors and layers?Read the model card.

02 · Draw one layer first

Where does the time go?

For Llama and Qwen, draw the dense layer below. “Dense” means each token uses the same feed-forward matrices. GPT-OSS replaces that feed-forward block with selected experts, which are separate learned feed-forward networks.

  • Q, K, and V are the query, key, and value vectors. Their projections are matrix multiplications that create those vectors.
  • Normalization rescales the input vector. Position transforms add token-position information. The activation and gate transform and combine the feed-forward vectors.
  • The CPU can score already cached KV after Q becomes ready. It handles pending KV after their producer finishes. [C3]
  • A join combines partial attention results. Some join time is useful merge work. Some is waiting for a device or another worker. [C1]
  • Weights are loaded into the accelerator’s memory for execution. Per-token host transfers carry intermediate vectors and relevant KV data. Estimate transfers from actual buffers and placement. [C5]

The dense layer is the part to memorize. For GPT-OSS, add expert selection, the selected expert matrices, and their weighted combination. GPT-OSS 120B’s total parameter count includes all experts. Each token selects 4 of 128 experts per layer. [M7]

03 · Separate the two decisions

AoF and AMX can be enabled together

AoF controls eligible attention ranges on the accelerator. The remaining CPU attention chooses AMX or AVX page by page. Switching AoF off leaves the other accelerator matrix operations in place. [C2] [C4] [C5]

ConfigurationEligible full-attention rangesCPU remainder and window layers
AoF off · AMX offCPU AVXCPU AVX
AoF off · AMX onCPU AMX on eligible pages; AVX elsewhereSame per-page test
AoF on · AMX offFPGA where the hardware plan assigns workCPU AVX
AoF on · AMX onFPGA where the hardware plan assigns workCPU AMX on eligible pages; AVX elsewhere

AMX needs every condition

  • The build includes TRON_AMX_DISPATCH.
  • The CPU and operating system allow AMX.
  • TRON_AMX_DISABLE is not exactly 1.
  • Queries use bf16, with a head width of 128 elements and 4 query heads per KV head.
  • The full 64-token page is visible and inside the query’s window.

These are the rules in the measured build. A later kernel can change them. [C2]

AoF needs an eligible operation

  • Model geometry, the device, and runtime policy must allow it.
  • The layer must have a hardware candidate operation and a supported attention scale.
  • Windowed attention remains on the CPU in this build.
  • The hardware plan can leave partial or newly written ranges on the CPU.

USE_HW_ATTN=0 disables AoF. A positive value enables policy and sets a rounded engagement threshold. It does not bypass the model checks. [C4]

Use the path counters to confirm execution. An “AMX on” run can record zero AMX keys. That is exactly what happened for GPT-OSS in this example. [R1]

05 · Count before assigning time

Three calculations cover most of the work

Attention work in a decode forward

Let B be query tokens in this forward, and S be visible keys per query, including the current token. Ordinary decode usually has one query per active user. Let Lfull and Lwindow count the two layer types.

R = Lfull × S + Lwindow × min(S, 128)key/head pairs = B × Hkv × RQK + PV arithmetic ≈ 4 × B × Hq × h × R operationslogical KV scan = 2 × B × Hkv × h × R × 2 bytes

QK is query–key scoring. PV multiplies attention weights by values. The arithmetic counts multiplication and addition separately. It omits normalization of the scores, position transforms, and merge work. The KV scan assumes bf16 and one read of K and V per query and KV head. Cache reuse, layout padding, and actual memory traffic need their own measurements.

Change the model or sequence length

—key/head pairs across all layers
—billion QK + PV operations, approx.
—MiB logical KV scan; 1 MiB = 2²⁰ bytes

All values here are calculated work amounts. They are not timing measurements. Default S = 1,152 tokens is a round example near the measured run’s average history. The exact run includes a different S at each step.

Prefill counts every query’s history

For a fresh causal prompt of P tokens, full attention has P(P + 1) / 2 query–key pairs per head and layer. For a window of W tokens, use Σ min(i, W) for i = 1…P. For P > W, this is W(W + 1)/2 + (P − W)W pairs.

Prompt chunks with cached history use each new query’s actual visible keys. Prefix reuse can remove work. Reuse also changes memory traffic. Keep prefill and decode cost measurements separate.

Matrix arithmetic, memory traffic, and the limit of peak-rate estimates

One matrix with a × b weights applied to B vectors costs approximately 2Bab arithmetic operations. For the layer’s attention projections, sum Q, K, V, and the output projection:

projection weights = 2 × d × h × (Hq + Hkv)dense feed-forward weights = 3 × d × mselected expert weights per token = 3 × k × d × mfinal vocabulary projection weights = d × V

k is selected experts per token. These formulas count matrix elements used, excluding biases and the expert router. Multiply by 2 operations per multiply-add and the appropriate token count. The vocabulary projection runs for tokens requiring output scores. Across a batch, selected experts can differ, so distinct expert weights read are the union of those selections.

For one stage with overlapping compute and memory access, a first lower estimate is:

stage time est. ≳ max(operations / measured operation rate, bytes moved / measured bandwidth) + exposed fixed overhead

Use rates for the same matrix shape, batch, data format, and hardware placement. If compute and transfer happen in sequence, add their times. Peak specifications do not supply the missing utilization, queueing, or synchronization cost. Insufficient data for an absolute latency prediction here: matching device-operation and transfer measurements are needed.

Full pages inside a sliding window

A 128-token window can overlap three 64-token pages. The two end pages are partial unless the window starts at a page boundary. Only complete visible pages qualify for this AMX implementation’s dense-page rule. [C2]

Full-page candidateVisible part of a partial pageOutside the window

One contiguous window with no prefix split is shown. Averaged equally over all 64 start offsets: (128 + 63 × 64) / 64 = 65 candidate keys per query. That is 65 / 128 = 50.78125% of window keys. This matches the completed run’s candidate count. GPT-OSS still fails the current AMX shape check.

06 · Put work on the clock

Time the dependency that finishes last

Use a common start time for all branches. For the simplified attention schedule below, all durations and arrival times are in microseconds:

CPU done = max(Q ready + ready-page work, KV ready) + pending-page workattention done = max(CPU done, FPGA done, other workers done) + merge work

“Ready” pages already hold their KV. “Pending” pages are updated in this forward. The formula follows Tron’s ready pass, KV wait, pending pass, and join. Streamed joins can merge earlier partials before the final result arrives. Use a trace for their exact overlap. [C3]

Wall-clock lanes: why less CPU work may save no time

This is an assumed schedule for teaching the dependency rule. It is not a reconstruction of the GPT-OSS trace. Both producers start at 0 µs. “Merge” means useful merge work after both results arrive.

Durations are to scale on one shared axis. Dashed rectangles include spin-wait if a real worker polls during that interval. The simple merge shown here waits for both complete results.

Build the full forward from these dependencies, then add the final vocabulary projection and token-delivery work. Add sequential stages. Use the latest finish time for concurrent prerequisites. Count each interval once.

Keep throughput and user latency separate

  • For ordinary steady decode with B users, aggregate throughput is approximately B / Tforward tokens per second. Per-user output spacing is approximately Tforward.
  • TTFT means time to first token. It includes the prompt forwards on the request’s path and any request-level overhead.
  • Mixed batches and speculative decoding change tokens produced per forward. Read the output count before converting a forward time to tokens per second.

08 · Make the assumptions explicit

Convert saved work into a timing estimate

Start with a measured service budget for the code being replaced. Let c be the fraction of that time eligible for replacement. Let r be the fractional reduction of that eligible time. Let e be the fraction of saved service time that advances the forward’s completion. Let H be added exposed overhead.

forward time saved est. = C × c × r × e − Htime reduction est. = saved / original timethroughput increase est. = original time / (original time − saved) − 1

A kernel speedup of s gives r = 1 − 1/s. A 2× kernel gives a 50% service-time reduction. For a schedule with several dependencies, calculate the before-and-after finish times directly when possible.

A conditional estimate for the GPT-OSS window layers

The 0.530459 ms budget is a snapshot-derived proxy. Using it assumes that the average worker represents the worker controlling completion. The starting 50.78125% coverage assumes that key share equals service-time share. Kernel gain and exposed share are deliberately blank until supplied. All outputs are estimates.

The calculator instead starts with the measured proxy after removing join waiting. It still includes merge work. A useful next measurement isolates the actual eligible kernel service time. This avoids assigning a kernel’s speedup to time spent elsewhere.

TSC is the time-stamp counter. tsc_hz is its ticks per second. It is not the CPU’s changing core clock. For aggregate worker counters, divide by the matching job count before treating the result as an average. Never add the workers’ times to obtain elapsed time. [C1]

A manual estimate on one sheet

  1. Write the target: TTFT, forward time, or output-token spacing.
  2. Write the model shape, query count, and visible history.
  3. Mark CPU and FPGA work for each layer type.
  4. Multiply work counts by matching service costs.
  5. Draw ready times and take the latest required finish.
  6. Sum sequential layers and final output work. Compare with T1.

How to build intuition from existing runs

  • First predict which counters can change when one option changes. Check that prediction against the recorded path counts.
  • Keep paired AoF-on/off measurements at the same model shape. Keep paired AMX-on/off measurements only where AMX actually executes.
  • Compare different sequence lengths at the same batch. Full-layer attention work should grow with visible history. Window-layer work stops growing after its window fills.
  • Compare small and large batches separately. More queries can change reuse, worker balance, and hardware launch timing.
  • Use repeated runs to judge a small predicted gain. The example used one repetition per configuration.

The checked build chooses early hardware launch at 4 or more query jobs by default. Smaller batches launch after current KV saves. This is a scheduling threshold, separate from AoF eligibility. [C3]
