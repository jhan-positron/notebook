3. W1: T5 misses the software join poll

Wade, on h/tron/models/self_attention.hpp:1131

T5 is only timed here, inside stream_hw_joins (the HW join). In SW-only layers the join waits for peer partials in the poll at run_joins: if (!join_hw && plan_state.sections_left[kv_head]) continue; // poll. That spin is never timed. So on a CPU-attention run join_wait_cycles reads 0 even when workers are spinning on load imbalance; the "join_wait_cycles":0 in the PR description's sample comes from exactly that config. The Note and README say T5 ends when "an FPGA pass or the other workers' software partials become ready", which suggests SW waits are included.

Either time the SW poll too (start the clock on the first continue for a kv head, stop when it proceeds), or narrow the docs to "HW join wait only".

What the code does

Each attention job ends with run_joins, one call per worker per job [self_attention.hpp:842-843]. run_joins first computes join_hw: true only when the model uses FPGA attention and this minibatch has FPGA passes [self_attention.hpp:1251]. It then loops over the KV heads assigned to this worker. For each head it polls: if join_hw is false and some peer is still computing that head, it moves on to the next head [self_attention.hpp:1256-1258]. 4. W2: two writers of the per-forward record

Wade, on h/tron/scheduler/full.hpp:2093

Two layers write <class>_forwards: forwards, wall_cycles and wall_max_cycles come from here in full_scheduler, while token_jobs, fpga_queries and token_jobs_by_path_set come from model::run_forward (begin_forward/end_forward). Any other caller of state.forward(...) In plain words

The record. For every forward the PR adds to one small block of six counters, the per-forward record (the C++ struct forward_counters). There is one record per forward class. Each record is published as the FUSE leaf <class>_forwards.

The writers. A writer is a code site that adds to the record. Today there are three writers, in two files. Writer A is in the scheduler. It adds the forward count and T1, the wall time. Writer B is in the model. It stores the class, then adds the token-job count and the path-set histogram. A path set is the set of attention paths (AVX, AMX, FPGA) that served one token job anywhere in the forward, over all layers, KV heads and pages. There are 8 possible sets: none, avx, amx, avx+amx, fpga, fpga+avx, fpga+amx, fpga+avx+amx. The histogram (the array token_jobs_by_path_set[8]) counts the token jobs of the forward per path set [attn_stats.hpp:122-130]. Writer C is deeper in the model. It adds the FPGA query count.

The risk Wade sees. Writer A picks the record by the class that writer B stored. Nothing checks that order. Only the fact that writer A wraps the call into the model keeps the record consistent. A second caller of the model's forward() that skips the scheduler would get a record with token jobs but no forwards.

The answer. Agree, and take Wade's second suggestion: one owner. The owner is a small RAII object (constructor acquires, destructor releases) declared at the top of the model's forward(). It stores the class and takes the start stamp (one rdtsc reading) when it is constructed. It takes the stop stamp and writes the record when it is destroyed, at the end of forward(). Every caller of forward() then gets a complete record. The PR no longer changes the scheduler file (full.hpp).

In plain words

The class. Every forward gets one label, its forward class: decode_like when every token job of the forward has a listener, prompt_or_mixed otherwise. All counters of the forward are filed under that label. A listener is the scheduler entry that receives the logits (per-word scores) of one token job. A generated token always has one. A prompt chunk (one slice of a prompt, 128 tokens by default, the unit in which a prompt enters a forward) has one, on its last token only.

The problem Wade sees. In serving, rinzler runs continuous batching: a new request joins the running batch at the next forward. So one forward can hold a prompt chunk of one user next to the generated tokens of seven other users. That forward has jobs without a listener. Its class is prompt_or_mixed. The seven users' decode work (decode = one new generated token per user per forward, after the user's prompt is already in the KV cache) is then counted as prompt-or-mixed work. runtron (our test tool) starts all users together. So it never produces such a forward, and a runtron run could not show this problem.

What the code does

The class is one decision per forward on the main thread, before the attention workers start [model.hpp:1745-1748]. Every hook files its value under current_class_ix() (the accessor that returns the class index of the current forward): visits, K tokens (the stored key tokens one visit scores, counted once per kv head), path sets (per token job, the set of paths that served it in one forward), FPGA counts, T1 to T5 [attn_stats.hpp:384-477; path sets in end_forward :452-469, FPGA query counts in note_fpga_query :473-477]. The workers never see a job's own state.

In serving (rinzler, with continuous batching), one scheduler serves every request of a model [src/rinzler.cpp:2130, :3236]. Each forward walks the whole token tree (every live request's tokens, shared prefixes merged) [full.hpp:1968 onward]. An edge is a run of tokens between two branch points of that tree. A KV entry is the stored key and value of one token in the attention cache. On every edge of a request still in the tree, the walk turns the tokens that have no KV entry yet into token jobs, up to a per-forward token limit (a soft limit live_token_limit and a hard limit capacity_limit [full.hpp:1896-1897, :2111-2129, :2472]). Tokens beyond the limit wait for the next forward [full.hpp:2488]. A prompt enters in chunks of 128 tokens by default (the environment variable TRON_PER_USER_PROMPT_CHUNK_LIMIT changes the chunk size) [src/tron/generation/context.cpp:40-42, h/libtron.hpp:196-204]. Every chunk registers a listener on its node [src/tron/scheduler/full.cpp:191-193]. The walk gives that listener to the chunk's last token [full.hpp:2465-2478]. Nothing keeps a prompt chunk in a forward of its own. So a forward with one user in prefill (prefill = feeding the user's prompt tokens into the KV cache, 128 per chunk by default) and seven in decode holds 128 prompt jobs (one with a listener) plus 7 decode jobs (each with a listener). Its class is prompt_or_mixed, and the 7 decode jobs' visits land there.

What the two counters look like, with an example

Option E adds two keys to the <class>_forwards leaf (the per-class file under /model/<id>/attention/, one JSON object). Both count token jobs, summed over the forwards of the class:

  • listener_jobs: token jobs that had a listener. Every generated token is one. The last token of a prompt chunk is one. So this is "decode tokens plus chunk ends".
  • kv_only_jobs: token jobs without a listener. Those are prompt tokens that only stored their K and V. So this is "prefill work".

The two add up to token_jobs. A reader compares them with forwards. Take the serving example of Figures 5 to 7: user A sends a 1,024-token prompt (8 chunks of 128) while users B to H decode. The 8 forwards that carry A's chunks are prompt_or_mixed. Each holds 128 prompt jobs of A (127 without a listener, 1 chunk end with one) and 7 decode jobs of B to H (each with a listener). After those 8 forwards the leaf reads, keys abbreviated:

How to read the prompt_or_mixed line:

  • listener_jobs 64 over 8 forwards = 8 listener jobs per forward. One of them is A's chunk end. The other 7 are generated tokens of B to H. So 7 of the 135 token jobs per forward were decode work, and 56 of the 1,080 token jobs of the class were.
  • Today's leaf has token_jobs 1,080 and nothing else. The reader cannot tell 1,080 prompt jobs from 1,016 prompt jobs plus 64 with a listener. The visit counters of the class (visits and K tokens per path) mix both, and the class name says only "some job had no listener".
  • The same leaf on the runtron run of prompt 1024 reads forwards 8, token_jobs 8,192, listener_jobs 64, kv_only_jobs 8,128. There the 64 are all chunk ends (8 users x 8 forwards), and 64 / 8 = 8 per forward = the number of users. No decode token is hidden. So the rule is: listener jobs per forward, minus the number of users in prefill during those forwards, is the number of generated tokens the class hides per forward.
  • The leaf does not carry the users-in-prefill count. A reader takes it from the run shape (users per engine, prompt length), or reads it off the decode_like line, whose listener jobs per forward is the number of users decoding at once (2,400 / 300 = 8 above).

Two cases need care when reading the rule. A prompt chunk that the per-forward token limit cuts registers its listener in the forward that finishes it, not in the one that started it [full.hpp:2452-2455]. In plain words

A guard. Each hook takes one to three indices: the worker, the layer, the token job. A range guard is an if-statement at the top of the hook: when an index is beyond its bound, return and count nothing. Nothing is logged. The header (h/tron/models/attn_stats.hpp, the file Wade's comment is on) has nine of them.

Why they exist. Not for production. In production every index is in range. Each index comes from a producer that is bounded by the same quantity that sizes the counters (Figure 11). They exist for the unit tests:

  • Four test fixtures (test setups) drive the hooks without the begin_forward call. That call sizes the per-token vectors.
  • One fixture grows the worker vector after the rows were sized, and then calls the hooks with a worker index and a layer index past the sized rows [t/t_attn_stats.cpp:264-275].

What Wade asks. Replace the guards by asserts (a TRON_ASSERT, active in every build, aborts the process with a message), and make the tests set up their state the way production does. A guard hides a future indexing bug as a wrong total. An assert turns it into a crash in CI.
