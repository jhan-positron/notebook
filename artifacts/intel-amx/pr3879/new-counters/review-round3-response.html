Is there a global prefill or decode state?

Short answer. No. The prompt length and the phase exist per request only above the scheduler, and nothing that reaches the model forward says whether a token came from the client or from sampling. Your rule "position greater than the prompt length means decode" cannot be evaluated at forward time, and even with the prompt length in hand it would label the phase, not the attention work shape.

What exists, and where

  • Generation layer, per request: the prompt vector, prompt_processed, prompt_tokens_processed, num_tokens_seen [h/tron/generation/context.hpp:74-78]. rinzler keeps prompt_tokens per HTTP request [h/rinzler/rinzler.hpp:601], and the token stream monitor records the prompt token count per session handle [src/tron/generation/token_stream_monitor.cpp:912-919]. That is where TTFT (time to first token) and the prompt-versus-output token rates come from.
  • The boundary: prompt chunks and generated tokens enter the scheduler through the same call, sequence_prompt(loc, tokens, n, num_ephemeral, logits, cb, tokens_reused_out), and the same extend_request [h/libtron.hpp:422-428; src/tron/scheduler/full.cpp:48-55]. The only differences at that level: a non-final prompt chunk carries an empty logits buffer [src/tron/generation/context.cpp:48-50], and prompt chunks pass a non-null tokens_reused_out [context.cpp:70-72 versus 230-231]. Neither is stored per token. num_ephemeral marks speculative tokens, not the phase.
  • Token tree: a token entry holds {token, kv_ready, eagle_ready, kv_replay_pending} [h/tron/scheduler/token_tree.hpp:47-52]. Edges, nodes and the per-request tip hold no prompt length and no origin flag [token_tree.hpp:67-81, 368-383; full.hpp:275-340].
  • Model forward: 13 inputs: tokens, positions, pages, groups, two EAGLE buffers, token jobs, the do_kv byte, listener index, buffers and notifications, the query mask [h/tron/models/model.hpp:1639-1653]. No prompt length, no per-token request id. The model has one active_handle_id per forward [src/tron/scheduler/full.cpp:211], so a multi-user forward cannot map its tokens to their sessions.

Answers to the questions

"empty" means neither AVX nor AMX? How about AoF?

Yes. An empty visit reached apply_page_tok and its loop found no K token for the software to score. There is exactly one return of path::empty, guarded by relevant_k_tokens == 0 [self_attention.hpp:1915-1918 at 04dab92a77]. A K token is not scored when one of these holds:

  • the range that holds it belongs to the FPGA in a hardware layer (the query sees it only through the hardware mask),
  • the query does not see the range at all,
  • the sliding window excludes it,
  • the EAGLE first-token exception skips K token 0,
  • the entry lies past page.count().

Attention on the FPGA is not a visit path by design. The FPGA share is counted per hardware pass (note_fpga_pass: K tokens and queries per class and layer) and per token job (note_fpga_query sets the FPGA bit from hw_plan.by_job). Under FPGA attention the card-owned pages are dismissed by the page-level gates before apply_page_tok. So the measured steady state has ready_empty_visits = 0 [exec/results/attnstats-20260925-fpga/exit-reports.txt].

Is it really running 2 passes?

Yes, per attention job. run_attention_job calls run_sections twice without any condition between the calls [self_attention.hpp:823-843 at 04dab92a77]. An empty pending plan runs zero sections but the call still happens.

one attention job (one worker, one layer, one minibatch)

run_sections(pending=false)  -> wait upstream K/V -> run_sections(pending=true) -> run_joins
      ready pages                                        pending pages             fold + finish
      index 0                                            index 1

So the names stay, and the comment now says what the two passes are. One fact you may want anyway: the header uses "pass" for two things. The software pass above, and the FPGA hardware pass (query_passes, note_fpga_pass, fpga_query_passes). tron's own word for the software split is "phase" ("Ready and Pending phases", model.hpp:2814). The naming section has the candidates.

"decode_like" is chosen because we cannot know it is decode, and the reason is the first token generated during prefill?

Half right. The classifier is literal: a forward is decode_like when every token job has a listener, that is n_listeners == token_jobs.size() [model.hpp:1746]. A listener is one scheduler entry per request edge, attached to the edge's last token [full.hpp:2141-2148]. Every prompt chunk gets one, not only the final chunk. A non-final chunk's listener has an empty logits buffer, and it still counts. So a 128-token chunk is 128 token jobs with 1 listener, which is prompt_or_mixed.

The forwards that land in decode_like without being a decode step:

  • a one-token prompt chunk (prompt length mod 128 == 1 gives a final chunk of one token). This is the case you had in mind,
  • a cached-prompt re-query: a prefix-cache hit produces one token job per chunk with do_kv = 0,
  • a speculative verify step: one token job per draft node, each with a listener,
  • a scheduler edge split that leaves exactly one token for the completing forward.

prompt_or_mixed holds every forward with at least one job without a listener: multi-token chunks, a partial edge cut by the live token limit (which can have zero listeners), a decode step that carries constraint fast-forward tokens (more than one token per user), and any mix of decode users with a chunk. The "_like" hedges for the four cases above. The naming section has exact names.

Verified by the fact-check workflow (claim C4 corrected, 2 refuters found no counter-example) [full.hpp:2141-2148, 2462-2478; src/tron/scheduler/full.cpp:190-193; src/tron/generation/context.cpp:38-78, 136-181; speculate.cpp:692-710].

Is it really possible there is a "none" path set?

Not in a correct run. "none" is counted for a token job with no non-empty software visit on any worker and no FPGA pass. Every query attends at least to its own K: the range builder puts the query's own token into the software mask or the hardware mask [src/tron/models/ranged_mask.cpp:29-90]. tron treats the remaining case as a bug: the comment at model.hpp:746-747 calls tokens "computed by neither path" silently wrong output, and model.hpp:2511-2520 asserts against it.

Measured: "none" is 0 in all 52 forwards lines of the four result directories (attnstats-20260924, -20260924b, -20260925-fpga, -20260925-warm). The only nonzero "none" is the synthetic unit test.

Recommendation: keep the bucket. It is index 0 of the 8-entry histogram, and a nonzero value is an invariant check that costs nothing. If the name should say so, "unserved" is the candidate.

path_bit: the AoF path is not needed to consider?

Correct. path_bit maps the path of one visit (avx, amx, or empty) to a bit. The FPGA bit is set on the main thread from the hardware plan, because the FPGA's work is not a visit. end_forward folds both:

token job j:   fpga_bits[j] (0 or PATH_BIT_FPGA_4, main thread)
             | path_bits[worker 0][j] | path_bits[worker 1][j] | ...   (each 0..3)
             = set in 0..7  ->  token_jobs_by_path_set[set]++

[attn_stats.hpp end_forward and note_fpga_query; model.hpp:2730-2737 at 04dab92a77]

T3 "wall": the source is the processor's counter, that is not wall clock, right?

Right about the source, and "wall" still means what it says. Every timer T1 to T5 is a difference of two rdtsc() reads, so the unit is TSC ticks, never a real-time clock value. tsc_hz in the summary leaf is get_cpu_freq(), which despite its name is the TSC tick rate measured against CLOCK_MONOTONIC every 50 ms (2.70 GHz on delphi-3bda), not the core clock (turbo up to 4.4 GHz). Dividing by that rate gives elapsed real time.

"Wall" here means elapsed real time including waits, as opposed to "busy" (T2, which excludes the upstream K/V wait). The comment now reads "entry-to-return cycles ... the job's wall time, in TSC cycles". I did not rename the field: "elapsed" is the word the code uses for T2 (attn_elapsed), so it would mislead the other way.

[h/system/system.hpp:315-319; src/system/system.cpp:1773-1788, 1965-1967, 2011-2019]

model_stats::on: can it be not enabled? What does it mean that a model is enabled?

The object exists for every model state, always [self_attention.hpp:477-500]. The flag says whether this state collects statistics. Production passes env_enabled(), so it is false whenever TRON_ATTN_STATS is not exactly "1". Two unit tests replace the member with an always-on object. The comment above the field now says this, and what still exists when false: the summary, totals and forwards leaves exist, no counter row is allocated.

Is visit_tally const& tally the same as const visit_tally& tally?

Yes, the same type. tron's models directory writes the const after the type in 274 of 419 such declarations (65 %), and self_attention.hpp in 24 of 38. clang-format leaves both forms (QualifierAlignment: Leave). Kept as is.

hw_wait_cycles: the wait can end on software partials, is there a better name?

Your reading is right. The timed loop exits when a hardware pass becomes ready or when the peer workers' software partials are done (sections_left == 0) [self_attention.hpp:1134-1147]. The row field, the JSON key and README.stats.md already call this quantity join_wait_cycles. Only the local, the parameter and the hook still say "hw". Recommendation: join_wait_cycles and note_join_wait. Not applied, waiting for your pick.
