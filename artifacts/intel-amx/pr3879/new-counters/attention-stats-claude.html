Attention path stats of PR 4596: what is counted, and why

Short version. PR 4596 adds counters that say where tron's attention work ran (the AVX loop, the AMX kernel or the FPGA card) and timers that say how long attention took. This page states the question each counter answers, then derives the numbers of four samples (A, B, the two runs of C, and the live snapshot D) from the run shape by closed-form arithmetic (72 checks, 0 failed). It does not describe the implementation.

1. What the counters cover, from coarse to fine

The PR answers one question about one model run. It splits all attention work three ways: the AVX loop, the AMX kernel, and the FPGA card. It also records how long attention took. 2. Why these counters: the questions they answer

This section states, for each group of counters, the question it was built to answer, why it has the unit and the dimensions it has, and what it cannot tell. Each claim carries its source in brackets. "counter.html section N" is the design page, "review round 4, comment Wn" is the reviewer comment answered on respond-Wade-comments.html, and "the Note" is Note [Attention path stats] at the top of attn_stats.hpp.

2.1 The path counters, per visit and per pass

Why per visit. The question the PR was built for is how much of the CPU attention work the AMX kernel served, and whether that count reads 0 under the kill switch [counter.html section 5.1, row amx_visits]. A visit is the only place where the path is known without ambiguity. The AMX return of the page call follows the dense-page kernel. The AVX return follows the loop [counter.html section 5, figure 3 caption]. The FPGA is deliberately not a visit path. Its share is counted per hardware pass and per token job [attn_stats.hpp comment on visit_path]. A card-owned range that reaches the page call is an empty visit, and a card-owned page dismissed before the call is no visit at all [the Note, paragraph Unit of the path counters]. In sample B no card-owned page reached a visit (section 5).

Why visits and K tokens both. The AMX kernel serves a whole dense page. Its K tokens are therefore always 64 per visit [the Note, paragraph Unit of the path counters]. The AVX loop serves the relevant K tokens of a page, from 1 to 64. Its visit count alone therefore does not say how much work it did. K tokens are counted once per KV head. Dot products are therefore K tokens × kv_mul [the Note, same paragraph].

Why the ready and pending split. The split is one dimension of the same count and needs no extra hook (counting statement in the attention code) [counter.html section 7, row pending versus ready split]. It separates the pages written in earlier forwards from the page written in this forward. That separation confirms two claims the design page had left open: a full pending decode page takes AMX in the same forward (sample A: pending_amx_visits 6912 = 3 steps × 2304), and a prefill chunk's own pages take AVX (sample A prompt class: pending_amx_visits 0) [counter.html section 2.2 and section 10, Prefill claim].

Why avx_full_page_visits.

  • What it counts: AMX-eligible volume that did not take AMX, an AVX visit that scored all 64 tokens of a page [counter.html section 5.1, row avx_full_page_visits].
  • Why it lives in the same build as the AMX visit count: the kill-switch check can then compare one binary with itself [counter.html section 9, row avx_full_page_visits].
  • The check: avx_full_page_visits under the kill switch = amx_visits + avx_full_page_visits with AMX on.
  • The correction: the original form had no second term. With AMX on, some full pages still take AVX [counter.html section 9, first paragraph, and section 13, Review rounds].
  • Observed in prefill: the chunk's own two pages take AVX for every query of the chunk (sample A prompt class: pending_avx_full_page_visits 1216512, pending_amx_visits 0).
  • Observed in decode: the full pending page takes AMX (pending_amx_visits 6912).
  • Why the prefill pages take AVX: the dense-page rule has no "written in this forward" clause. The clause that fails is the one-visible-range clause. A prefill chunk writes its pending pages in this forward, and each of its 128 query tokens has its own visibility range. The causal mask (the rule that a query token sees only the tokens at or before its own position) gives each token of a chunk a different range end. The page's last token is therefore never inside the first query token's range [self_attention.hpp, comment on the page-level visibility gate]. That is why a full pending page of a prefill chunk takes AVX.
  • Section 6 runs the check on sample C.

Why empty visits. An empty visit reached the page call and did no work. Either the range belongs to the FPGA, or every token of the page lies outside the query's window. It is a pure overhead count [counter.html section 5.1, row empty_visits]. It does not count the pairs dismissed before the call (workless ranges, invisible pages, whole-page window skips) [the Note, paragraph Unit of the path counters]. Sample B, under FPGA attention, reads ready_empty_visits 0. In that run every card-owned page was dismissed before a visit.

What the path counters do not tell:

  • No time per visit. The per-phase timers stayed a build-time option for lab use, not built in this PR [counter.html section 9, row phase timers, and section 13, Not built].
  • No user or query token per visit. The row has no token-job dimension [review round 4, comment W3].
  • No reason why a page took the AVX loop (tail page, range boundary, window edge, page written this forward). That classification was listed and not built [counter.html section 7, first row, and section 13, Not built].

2.2 The forward class

The rule. A forward is decode_like when every token job of the forward has a listener, and prompt_or_mixed otherwise [the Note, paragraph Forward class]. The labels carry the rule. A reader of the report therefore sees what the class means without the header [review-round3-response.html, Class labels: name plus rule].

Why one class per forward, and only two.

  • Set once per forward on the main thread.
  • Filed with the per-forward hooks by the design's hook-frequency rule (each counter is filed with the hook that runs least often, per forward, per job or per visit) [counter.html section 9].
  • Named after the listener count, the one fact the forward has. Nothing that reaches the model forward says whether a token came from the client or from sampling [review-round3-response.html, Is there a global prefill or decode state].
  • A three-way origin bit (all prompt, all generated, mixed) would be a scheduler change across the public API (application programming interface, the functions that other code calls). It was kept out of PR 4596 [review-round3-response.html, The smallest exact change].
  • Under continuous batching in rinzler (new requests join the batch while other users are still generating), a forward with one prompt chunk next to other users' generated tokens is prompt_or_mixed. decode_like counts pure-decode forwards only [review round 4, comment W3].

Why listener_jobs and kv_only_jobs. runtron starts all users together. Its forwards are therefore never mixed. The two counts let a reader of a rinzler run see how mixed the forwards were: how many token jobs had a listener (every generated token, and the last token of each prompt chunk), and how many only stored K and V [attn_stats.hpp comment on forward_counters]. A per-token-job split of the visit counters was offered as a follow-up PR [review round 4, comment W3].

Why the three job counts move together. At head bff317e0d3 the listener count was added at the start of the forward and token_jobs at its end. A live read of the forwards leaf then showed listener_jobs 1144 next to token_jobs 1136 after 142 decode forwards of 8 jobs, one forward ahead (section 7). Commit 04da001cb5 adds all three counts at the end of the forward. listener_jobs + kv_only_jobs = token_jobs therefore holds at every read except inside the few instructions of the three adds [commit 04da001cb5, README.stats.md].

What the class does not tell. The record does not carry the number of users in prefill. The generated tokens per forward are therefore not read directly. A reader takes the users from the run shape and subtracts them from the listener jobs [attn_stats.hpp comment on listener_jobs]. One case inflates the count. A speculative verify step (a forward that checks several draft tokens proposed by a small model) carries one listener per draft token. listener_jobs then over-counts decode tokens [attn_stats.hpp comment on listener_jobs].

2.3 Per worker and per layer

Why rows are keyed by pool worker. The rows were first indexed by attention worker. The split changes inside one run. A single-user run has 7 main helpers in the first prompt forward and 1 in its one-token decode forwards. A row indexed by attention worker could then mix two threads and two cores [review round 4, comment W5]. Keying by pool worker has four effects [review round 4, comment W5, option B, commit bff317e0d3]:

  • One row stays on one thread and one core across forwards.
  • The row index matches the thread ids of the speedometer (tron's per-thread load display) and of the perfetto trace (the timeline trace tool).
  • Each row keeps one writer (the single-writer property).
  • The change costs nothing in the off state.

Attention worker i of a forward with n attention workers writes pool row n_workers - n + i. The first rows belong to the main helpers and read zero.

Why the split range is recorded. The plugin (the model-specific forward code that tron loads per model) picks the split per forward. A reader therefore needs n_attn_workers_min and n_attn_workers_max to know which pool rows were attention rows [attn_stats.hpp comment on n_attn_workers_min]. active_workers in the summary counts the pool workers with at least one attention job in either class [attn_stats.hpp comment on active_workers]. When the split does not change it equals n_attn_workers_max (sample A: 20 and 20). The range does not give the split of each forward [review round 4, comment W5, option D].

Why per worker. Each row is written by its owning worker only. The per-worker view was asked for to see imbalance across attention workers, and max over mean across workers bounds the attention wall together with the serial join fold [counter.html section 5.2, last paragraph, and section 7, row per-worker imbalance].

Why per layer. Only models whose layers differ (sliding-window layers, FPGA layers, EAGLE drafts) make the per-layer line carry information. For qwen-3-4b every layer prints the same value, and section 4.4 shows that [counter.html section 3 and section 13.1].

2.4 The FPGA counters and their scale

Why they exist. fpga_k_tokens gives the third share next to AMX and AVX: how much of each query's context the card scored in this layer [counter.html section 5.1, row fpga_k_tokens]. Per (pass, query) it adds the inclusive index of the last K token the card scores, plus 1, and sums over the pass's queries [attn_stats.hpp comment on layer_fpga_counters]. It is counted once per hardware pass, not per visit. The CPU-versus-FPGA share therefore costs no per-visit code [counter.html section 9, row fpga_k_tokens]. fpga_query_passes counts (pass, query) pairs, the denominator for K tokens per pass. fpga_queries in the forwards leaf counts token jobs with at least one card pass [counter.html section 5.1, rows fpga_query_passes and fpga_queries].

Why a different scale. One hardware pass serves all KV heads of a query at once, while the software K tokens count one KV head per visit. So the raw fpga_k_tokens compares with the software values only after multiplying by n_kv_heads. The leaves carry that product as fpga_k_tokens_x_kv_heads. The per-layer stderr line prints the raw value, not the product [attn_stats.hpp comment on layer_fpga_counters, counter.html section 13.1, One way to misread the line]. Section 5 shows the two scales on sample B.

What they do not tell. The value may be off by one per query. The card's last-token index may name the last token scored (inclusive) or the number of tokens scored (a count). Which one holds is not yet confirmed from the device [counter.html section 11, third bullet]. They give the mean CPU tail per query, not a histogram of the DMA lag (the delay before the card's copy of the newest K/V tokens is complete) [counter.html section 11, second bullet].

Three subtractions a reader can make, each with its meaning:

  • T1 minus the sum of the T4 periods of a forward = two parts of the forward. The first part is before the first attention job of layer 0. The second part is after the first attention job of the last layer: the last layer's attention and feed-forward block, the logits, and the delivery. Only 35 of 36 layers have a period.   • T2 minus T5 = compute plus join fold of an attention job [the Note, paragraph Timers].
  • T3 minus T2 on attention worker 0 = the waits that T2 excludes: the wait for the queries at job entry and the upstream K/V wait. The counters do not say which of the two is larger. Across the totals the subtraction also contains the imbalance between worker 0 and the mean worker. busy_cycles is summed over all workers. T3 is worker 0's alone.

What the timers do not tell [the Note, paragraph Timers, and counter.html section 9]:

  • T2 does not separate compute from waiting on its own.
  • T3 is one worker's view.
  • T4 does not cover the last layer's feed-forward block and the logits.
  • None of them gives a per-step distribution. The max is the only shape information.

Timers never subtract a worker stamp from a main-thread stamp. Cross-core skew of the TSC (a small constant offset between the counters of two cores) therefore does not enter [counter.html section 5.2, last paragraph].

2.6 The switch, the leaves and the stderr report

Why an environment variable and no build option. The rule had two parts. Prefer the environment variable. It is easier to turn on. Fall back to a build option only if the always-compiled hooks show an obvious cost with the variable unset [counter.html section 13, Decision]. The approving reviewers of the counters PR #4267 had asked for exactly a run-time switch with FUSE leaves (issue #4303) [counter.html section 13]. The same deb (Debian package of tron) then serves every arm (one binary or setting under comparison) on the CI machine under platformd (the service manager that starts rinzler on the CI machine) [counter.html section 8, row D2]. The switch is on only when TRON_ATTN_STATS is exactly 1. An unset variable leaves it off silently. Any other set value leaves it off and writes one warning to the log. The value is read once per process. It therefore cannot change during a run [the Note, paragraph Switch].

Why the per-visit hook was allowed behind the same variable.

  • Cost with the switch on: a visit costs 2.1 to 2.4 us (microseconds) on the AMX path and 2.8 to 2.9 us on the AVX path, measured on 2026-09-01. That is est. 5700 to 11300 cycles at core clocks of 2.7 to 3.9 GHz, recomputed from the microsecond range. counter.html section 13 prints 5800 to 11200 cycles for the same range.
  • Cost with the switch off: one test of a bool per visit (est. 1 to 2 cycles).
  • Ratio to a 1 % change: the off cost is 60 to 400 times smaller than the per-visit cost that would change tokens per second by 1 % (est., counter.html section 13, Why the environment variable can carry the per-visit hooks).
  • The A/A rule (A/A = two runs of the same binary, compared to measure the run-to-run spread) was fixed before the runs finished, in exec/attnstats-20260924/decide.py.
  • The band per cell (the change in tokens per second that counts as no change) is the largest of: the base-to-base difference, twice the largest per-arm standard deviation, and 0.5 % of base.
  • Measured: the head with the variable unset was inside the band at prompt 1024 (-0.17 %) and faster at prompt 8192 (+0.77 %, outside the band on the fast side).
  • Attribution: the design page attributes the +0.77 % to code placement (the position of the compiled code in memory, seen before on this host) and not to the hooks. The variable therefore stays [counter.html section 13, Measurement record and Verdict].

The off-state contract. With the switch off [the Note, paragraph Switch]:

  • No row, FPGA counter, timer or per-token path record is allocated. The stats object itself, with its two per-class forward records (a few hundred bytes), exists in every model state and stays at zero.
  • The leaves summary (with "on":false), <class>_totals and <class>_forwards still exist, and the last two read {}. The layer and worker leaves do not exist.
  • The cost per visit, per job and per forward is one test of a bool.

Why the counters never reset. Every value counts from the construction of the model state, and an interval is the difference of two reads [the Note, paragraph Output, and README.stats.md]. A further reason is not stated in the sources.

Memory when on. The rows take 2 classes × pool workers × layers × 192 bytes. For sample A that is 2 × 27 × 36 × 192 bytes = 373 KB (KB = 1000 bytes). The timers add 2 × 36 layers × 64 bytes = 4.6 KB [the Note, last paragraph].

Why a stderr report in addition to the leaves. A batch runtron run destroys the model state before the FUSE leaves can be read. The exit report is therefore the end-of-run record [pr-body.md]. rinzler under platformd never reaches a normal exit. An exit report alone would therefore not serve production. That is the reason the leaves exist [counter.html section 8, options D1 and D2].

Why the summary carries the model facts.

  • Without amx_compiled and amx_available a zero AMX count is misread: the nightly deb had no AMX code at all until PR #4505 landed [counter.html section 5.2, Report header].
  • n_kv_heads, kv_mul and page_size give the counts their meaning (the FPGA scale factor, the dot products per K token, the K tokens per AMX visit).
  • n_workers depends on the CPU list that platformd passes to tron and is not in the repository. The process must therefore print it [counter.html section 10, last bullet].
  • The summary shows the kill switch indirectly: amx_available reads false when TRON_AMX_DISABLE=1 was set. The availability probe reads that variable (sample C: false in the kill-switch run, true in the AMX-on run). The summary has no key that names the variable. Two further signs are AMX visits 0 with avx_full_page_visits nonzero, and the hardware counter EXE.AMX_BUSY (a CPU performance counter of the cycles in which the AMX unit was busy) reading 0 [pr-body.md, Cross-checks, and counter.html section 10, Kill-switch cross-check].

Hypothesis: prefill jobs are larger and less even across workers. A worker then waits longer in the join. The per-worker leaves of a prefill-only snapshot would confirm or reject it.

  • The meaning of T2 against T1 when a forward has several minibatches per layer: every sample here has one minibatch. attn_jobs = forwards × layers × workers therefore holds exactly. With several minibatches a worker runs several jobs per layer. The per-forward busy time is still the sum. The per-job means change meaning. T4 counts one period per attention operation. A second minibatch of the same layer does not start a new period, and period_count_w0 stays at 35 per forward. attn_jobs and T3 count every job [the Note, T4 state comment].
  • The exact tokens the card scores per pass. The (p mod 4) + 1 tail is a fitted hypothesis (section 5), and whether the card's last-token index is inclusive or a count is open [counter.html section 11].
