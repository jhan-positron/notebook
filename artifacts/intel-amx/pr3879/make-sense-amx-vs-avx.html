  • Short contexts: the boost is within a couple of spreads of zero - +0.6% at 256 (at the noise floor), ~2% at 512-1024. The mirror's costs (scatter write-through, per-token overheads) are fully paid back even here, just barely.

  • +26.0% at 16K, +27.6% at 32K: the curve is flattening - the gain grows 1.6 points over the last doubling after growing 8.0 points over the one before, so the asymptote sits near +28-30% for this model on this host. 3 · Q1: why is the boost bigger at larger contexts?

The premise "the AMX boost is constant per token" assumes attention time per token is constant. It is not - that is the whole first-order answer.

Model. Tavx(prompt) = R + aavx·prompt and Tamx(prompt) = R + aamx·prompt + ctok (ctok = per-token AMX overhead: Q pack, tile-config region, the one new token's mirror scatter ~20 µs est.). Two distinct bounds Sol: at a FIXED context, the attention share caps the gain (14/30/64% at 256/2K/8K); as prompt grows the boost approaches the asymptote 1 − aamx/aavx. The measured +4.5% → +19.6% (1u, 2K→8K, mirror) is this curve in flight. R is only approximately constant - at 8u it inflates with contention, so fit 1u and 8u separately, and fit against actually-visited pages/bytes rather than the nominal prompt length Sol.

Secondary mechanisms, same direction, measured:

  • Dense-page coverage rises: 64.4% → 92.2% → 97.8% of pages take AMX at prompt 32 / 2K / 8K (cells: one off-grid 1-user run, not in the reviewed grid / the 1-user grid cell / the 8-user grid cell; coverage is a dispatch-gate property, so the user count does not change it); and calls that pay the region + Q-pack cost for zero AMX pages fall 36.7% → 24.0% (prompt-32 1-user cell → prompt-8192 8-user cell). Section 7.7 is the more accurate coverage record: reviewed-grid prompts 256 / 2048 / 8192, two agreeing runs per prompt, every fallback visit attributed by cause.
  • Per-token fixed costs amortize: Q pack once per (token, kv_head), reused across all pages (mirror-build pack = one 1 KB memcpy; 6.3 ns/op); ldtilecfg 182-216 cycles once per page-range (amx-overhead-20260821.txt).
  • Working-set regime shifts in AMX's favor: cache-resident single page the dotter WINS at Nq=1 (422 vs 588 ns/page); at pages=16384 (RAM-resident) AMX wins even at Nq=1 (1633 vs 1970 ns) and 2.45× at Nq=8; the dotter's useful GFLOPS collapse 77.6→16.6 cache→RAM (fused-sweep-v2.txt). Sol this shows a working-set/latency/MLP + per-byte-instruction-overhead effect, NOT proven bandwidth saturation: both arms stream the same K/V bytes, so a truly saturated DRAM bus would make their rates CONVERGE. The AVX-arm perf-stat (IPC 0.38-0.52, LLC-miss 51-85% at 1u/8K, p2-perf-decode.txt) says memory-limited, not which limit.

Counterweight: at high occupancy the boost stops growing - 8u/8K is 14.5 → 18.6 tok/s, both arms far below 8× their 1u rates. Candidate causes Sol: DRAM bandwidth, remote-NUMA/SNC imbalance, mesh/LLC contention, power limits, synchronization - IMC/UPI counters would separate them; none are measured yet ("consistent with a memory wall" is a hypothesis, not a finding).

4 · Q2: what else, besides 8× MAC throughput, helps or hurts?

First: the 8× headline never applies at decode width. A decode GQA group is 4 query heads; tron configures 16-row tiles (one ldtilecfg per page-range, amx_attn.cpp:84-96) and zero-pads Q rows 4-15, so each tile multiply does useful work on 4/16 of its output (Note [Tile stores write 16 rows]; confirmed in source - Sol asked for this check). Measured kernel-grid: M=4 1141 ns vs dotter 1748 ns = 1.53×; 8×-class gains appear only at M≥8 (298 ns) / M=16 (276 ns, 1900 GFLOPS) - microbench-quiet.txt. Decode sharing is ~absent (avg visit width 1.022 tokens, private 8u, p1-sharing.txt), so decode cannot ride the M≥8 curve; prefill can (width 110.9). Follow-up idea: a 4-row C-tile configuration could cut TDP work per page - costs a reconfig per region switch and a kernel redesign; unmeasured.

6 · Decisions from the discussion (2026-08-31)

Words used here: F1 and F3 are the two per-token sync points on the scheduler thread (F1 = all workers joined after the forward pass; F3 = the produced token consumed by all listeners); "the listener" is the per-request code that receives each finished token and submits the request for the next one; "arm" is one side of a comparison (AMX on vs AMX off).

  • What F3→F3 does and does not measure. The time between two consecutive F3 events is how often tokens complete - the right denominator for a boost percentage. It is not how long one token takes from start to finish, because the listener submits the next token's request BEFORE its F3 tick, so two tokens' work can overlap even with a single user. Consequence: the split of a token into [F3→F1] (forward pass) and [F1→F3] (logits + listeners) describes scheduler phases, not exclusive ownership of the wall time.
  • Instead of assuming the overlap away, measure it. The campaign adds five timestamps per token, each a numbered "stamp" in a crash-proof record file: 7600 = F3, 7601 = F1, 7602 = the instant the next request is submitted (its payload carries the count of tokens generated so far, which anchors token identity), 7603 = the instant the 69 attention workers are released into layer 0, 7604 = the instant the last layer's attention join completes. 7604−7603 is the attention span; 7602 relative to F3 is the overlap lead, measured directly.
  • Decision (jhan): hold 8u; make sense of 1u first. Reasoning: every added user brings cross-request interleaving that the performance model would have to explain before it explains AMX, and even 1u contains the overlap above. Agreed - the fence campaign is 1u only. The existing 8u serving numbers (section 2) remain valid as deployment data; new 8u cells wait until the 1u model holds. One consequence stays on record: the 1u model will not predict 8u (measured +4.5% at 1u vs +22.8% at 8u, same context), so one 8u check comes later.
  • Decision (jhan): run the detailed measurement. Executed as campaign item 3 below, running now.

7.2.1 · Single attention: AVX→AMX boost per unit, estimated then measured (phase probe, 2026-09-01 21:01-21:20 UTC)

Words used here: a single attention is the smallest unit of attention work in tron: one query token's group of 4 query heads scored against ONE KV page (64 stored tokens) of ONE KV head, then folded into that token's running softmax state. It is one call of apply_page_tok (self_attention.hpp). Its cost does not depend on the number of users or on the context length; what those change is how many units a token needs: users × 36 layers × 8 KV heads × (KV length ÷ 64) pages. "Common work" is the part of a unit that both arms execute with the same code (the softmax pieces: scale, max, exp, sum, correction; the running-state update v*, s*, m*; the Q pack and bookkeeping); "arm-specific work" is the QK score block and the PV product, which are the only parts AMX replaces.

Why the table above is not a single-attention measurement. Stamp 7605 is the wall time of attention worker 0 across the 36 operations; each operation scores the new token against the WHOLE stored KV of its layer (8 KV heads × KV length ÷ 64 pages), with the units spread over the 27 attention workers of this run (28 app cores, one main worker; the run log lists 27 worker speeds). So "per pass" = 36 operations over all KV, "average per layer" = one operation over all KV, and neither is a single attention. Also, wall time on one worker with a closing barrier per operation is not CPU time: the 27 workers together spend about 27× that wall time.

Estimate method (est., to be replaced by the measurement below). Adding one token to the KV adds 1/64 of a page to each of 8 KV heads in each of 36 layers, i.e. 4.5 units per pass. The slope removes the per-operation fixed costs (joins, barriers, Q pack, releases), which the all-inclusive average keeps. The ratio AVX ÷ AMX does not depend on the worker count or on the load-balance assumption, as long as both arms balance alike. 8 · Glossary

decode vs prefill
Decode = one new token per step, re-reading all stored KV; prefill = the prompt's tokens processed in bulk (wide, AMX-friendly).
prompt 256 / 2048 / 8192 ...
The prompt length in tokens, passed to runtron as --prompt-length. It is not the total context. Every run in this page then generates 256 tokens (-l 256; the perf-stat rounds use 2600 so the counters can be read at decode token 400), so the total context grows from prompt+1 at the first decode pass to prompt+256 at the last. "prompt 8192" therefore means an 8192-token prompt plus up to 256 generated tokens. Earlier versions of this page and the campaign scripts labelled the same value "prompt"; raw result files still carry that label.
page
64 tokens of KV storage. Decode attention visits one page per 64 tokens of total context (prompt plus tokens generated so far), per layer per KV head, per pass.
dotter
The AVX-512 software-attention inner loop (dotter.hpp): per-token dot products, K converted bf16→fp32 on the fly.
dense page
A fully visible, full 64-token page inside the window - the only case the AMX fast path handles; everything else falls back to the dotter.
Fence 1 / Fence 3
Scheduler-thread sync points: F1 after all 70 workers join (forward pass done, before wcls); F3 after logits are consumed by all listeners. From the tron-perf-fluctuation project.
wcls
The output-vocabulary matmul producing logits, offloaded to the FPGA; runs in [F1→F3].
kill switch
TRON_AMX_DISABLE=1: same binary, AMX off at start-up (no arena, no scatter, dotter everywhere).
M / Nq (microbenches)
Query rows per tile operand - decode's GQA group gives 4; gains scale strongly with it because tiles are 16 rows.
IMC / UPI / SNC
