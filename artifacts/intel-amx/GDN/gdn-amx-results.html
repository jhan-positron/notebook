GDN and AMX on Qwen3.5 4B: what was built and what it gave

2026-11-21 (PST). Measured on our half of delphi-3b35, the test server. The code is tron, the inference program under test, on the branch jhan-gdn-amx.

This page follows the design page gdn-amx-design.html. It compares the measurement with the prediction of that page.

Short version

  • Three changes that speed up the model Qwen3.5 4B are built in tron and measured on delphi-3b35.
  • With all three changes the time to first token fell by 25 to 39 %, against working predictions of 30 to 41 % (est.).
  • With 8 users and prompts of 4,096 tokens or more, token generation after the prompt got 18 to 23 % faster.

The three changes, and one addition:

  • Part 0 is a faster loop for the GatedDeltaNet (GDN) layers of the model Qwen3.5 4B. It uses no AMX.
  • Part A is a kernel for the same layers that uses AMX, a set of Intel matrix instructions.
  • Part B is an AMX kernel for the attention layers of the model.
  • Part A is built on Part 0, and a build with Part A always has Part 0. So the run named Parts A and B has all three changes.
  • tron also got counters for its GDN layers. Section 8 describes them.

Words used here
  • tron, runtron: tron is the inference program under test. runtron is its command-line tool.
  • Qwen3.5 4B: the model under study. Its tron name is ingested-qwen-3.5-4b.
  • GDN (GatedDeltaNet): a recurrent layer type. 24 of the 32 layers of Qwen3.5 4B are GDN layers. The other 8 are attention layers.
  • state: the memory of a GDN layer. It is one matrix of 128 key rows by 128 value columns per value head, in FP32.
  • decay: a factor between 0 and 1 that multiplies the state of a value head for each token.
  • key head, value head: a GDN layer has 16 key heads and 32 value heads. Each key head serves 2 value heads.
  • recurrence: the arithmetic that reads and rewrites the state for one token.
  • GDN step: the work of one token for one key head. Its parts are the convolution, the normalization, the recurrence on 2 value heads, the norm and the output gate.
  • GDN operation, work item: tron runs one GDN operation per GDN layer and pass. A work item is one chain of one key head inside it.
  • GDN threads, median thread: 16 CPU threads run the GDN work. 2 of them run on faster CPUs (4.00 GHz, from the design page). The median thread is a thread at 2.70 GHz.
  • chain: the consecutive tokens of one sequence in one pass. A GDN layer must take them in order.
  • token kernel, chain kernel, block kernel: three routines for the recurrence.
    • The token kernel is the code of the base build. It takes one token per call.
    • The chain kernel is Part 0. It gives the same bits with another loop order.
    • The block kernel is Part A. It takes 32 tokens at once with AMX.
  • step(), advance(): two entries of tron's GDN code. step() takes one token. advance() is new and takes a run of tokens.
  • window, block: advance() cuts a chain into windows of at most 32 tokens. A full window of 32 tokens is a block.
  • working copy: a copy of the state that tron makes for a chain of 2 or more tokens. The stored state stays as it was until the chain ends.
  • AMX: Intel Advanced Matrix Extensions: tile registers, and instructions that multiply two tiles.
  • tile, tile product: a tile is an AMX register of 16 rows by 64 bytes. A tile product is one TDPBF16PS instruction, which multiplies two tiles of bf16 values.
  • AVX-512: 512-bit vector instructions. The code without AMX uses them.
  • bf16, FP32, float64: number formats with 8, 24 and 53 significant bits.
  • bf16 step: the distance between two neighbouring bf16 values. It is 0.125 for values from 16 to 32. Earlier pages call it one notch.
  • scores: the values that the model gives to every token id for the next token. The sampler of these runs takes the token id with the best score.
  • correction: the value that the recurrence adds to the state for one token.
  • error band: a stated limit on how far a result may differ from a reference result. tron's AMX tests check such limits.
  • numerics contract: a written rule about results. It says which results must be equal bit for bit and how far the others may differ.
  • subnormal value: a nonzero value below the smallest normal value of its format (2^-126 for FP32). A CPU computes with such values slowly.
  • FTZ, DAZ: two control bits of the CPU. With FTZ a result that would be subnormal becomes zero. With DAZ a subnormal operand is read as zero.
  • core clock: the frequency at which a CPU core runs. The CPU lowers it under AVX-512 or AMX work.
  • prefill, pass: prefill is the processing of the prompt. A pass is one forward computation through all 32 layers. A prefill pass has 128 prompt tokens per user.
  • decode step: a pass with one token per user.
  • listener: a token has a listener when its scores are read. Every generated token has one.
  • trace: a recording of timed events that runtron can write. It slows the run.
  • thread split: how tron divides its CPU threads between the kinds of work. A runtron option keeps it fixed.
  • registry entry: the record of a model in tron's list of models.
  • TTFT: time to first token: from the request to the first generated token.
  • decode, tok/s: decode is the generation of tokens after the prompt. Its speed is given in tokens per second per user.
  • wall: wall-clock time: the elapsed time of a piece of work, waits included.
  • GDN wall: per GDN layer and pass: the time from the first thread's start to the last thread's end. The tables give the sum over the 24 GDN layers of a pass.
  • busy time: the time a thread spends inside its GDN or attention work, without the waits before it. The attention busy time of a pass is the mean over the 40 attention threads, summed over the 8 attention layers.
  • join wait: the time an attention thread waits, inside its work, for the other threads or for data. It is part of the attention busy time.
  • attention job: the attention work of one layer in one pass on one thread. The counters keep its wall time for one thread only, attention thread 0.
  • attention wall: the wall time of the attention job on attention thread 0, with every wait inside the job. Section 5 gives the sum over the 8 attention layers.
  • other work: the wall of a decode step minus its GDN wall and its attention wall. It holds the matrix multiplies on the FPGA cards, the data transfers and the remaining CPU work.
  • start of a chain: the work that prepares the state of one key head before a chain. The counters time it.
  • NaN: not a number: a float value that marks an invalid result.
  • query head, KV head: an attention layer of this model has 16 query heads and 4 KV heads. Each KV head stores the keys and values for 4 query heads.
  • K token, page unit: a K token is one stored key row that a query is scored against. A page unit is the attention work of one query token on one 64-token page of one KV head.
  • counters: the new GDN statistics of tron. The environment variable TRON_GDN_STATS=1 turns them on.
  • head token: the unit of the counters: one token of one key head of one GDN layer.
  • kill switch: the environment variable TRON_AMX_DISABLE=1. It turns every AMX kernel off.
  • GDN switch: the new environment variable TRON_AMX_GDN_DISABLE=1. It turns only the AMX block kernel of GDN off.
  • arm: one build with one set of switches. The campaign has 6 arms. Section 2 lists them.
  • kill-switch pair, GDN-switch pair: two pairs of runs that differ in one switch only.
    • The kill-switch pair is the build with all changes, with the kill switch set and with the GDN switch set. Its two runs differ in Part B.
    • The GDN-switch pair is the build without Part B, with the GDN switch set and with no switch. Its two runs differ in Part A.
  • cell: one combination of user count and prompt length.
  • base build, base run: the base build is tron with the new counters and with none of the three changes. A base run is a run of the base build in the same session.
  • Part 0, Part A, Part B: the three changes of the design.
    • Part 0 is the GDN chain kernel, without AMX.
    • Part A is the AMX block kernel for GDN. It is built on Part 0, so a run with Part A also has Part 0.
    • Part B is the AMX attention kernel for 256-wide heads. It does not depend on the other two.
  • working value, range: the design gave each prediction a low, a working and a high value. The range runs from the low to the high value.
  • delphi-3b35, our half: the test server. We use its second CPU socket and 4 of its 8 FPGA cards. Other users have the first socket and the other cards.
  • FPGA cards, engine, tp4: tron runs its large matrix multiplies on FPGA cards. An engine is one copy of the model on a group of cards. tp4 is an engine on 4 cards.
  • us: the microsecond, one millionth of a second.
  • est.: an estimate. Every number without it is measured.
  • Insufficient data: a value that we could not measure. The text names the measurement that would give it.

1. What was built

  • The work is 3 commits on the branch jhan-gdn-amx, on top of commit 72e1191804 of the open pull request that adds the model [Ref1].
  • Commit 0d69ef3ce8 adds the GDN counters. It changes no kernel.
  • Commit 775bba7661 adds Part 0 and Part A. They are the chain kernel, the executor entry advance() and the AMX block kernel.
  • Commit 882e5322f1 adds Part B: the AMX attention kernels for heads of 256 values.
  • The branch is pushed. It is the draft PR #5572 of the tron repository, on top of PR #3696 [Ref1].

Differences from the design

  • The chain kernel has another loop than the design describes.
    • In a stand-alone test the loop order of the design was 1.45 to 1.47 times faster than the loop of the base build [Ref4].
    • Another loop joins the write pass of a token with the read pass of the next token. It was 2.00 to 2.02 times faster, with equal bits [Ref5].
  • The halves of the state are stored row by row. The layout of the design gave 2,105 ns per value head and token in one run and 1,524 ns in the next run [Ref5].
  • The chain kernel also works in windows of at most 32 tokens. The design ran each half of the state over the whole chain.
  • The windows follow the token position in the sequence, as the design asked for the blocks. So the same tokens fall into the same blocks, except where a cut of the scheduler divides a window.
  • The block kernel has a second refusal rule: a correction of 2^100 or larger. The design refused only results that are not finite.
  • The block kernel sets the CPU bits FTZ and DAZ for its own work. Section 7 gives the measurement behind this.
  • The design asked to clear the 512-bit registers before tile work. Per value head and token the block kernel took 590 to 601 ns with the clearing and 590 to 592 ns without it. So the kernel does not clear the registers [Ref7].
  • Part 0 and Part A are one commit. The design listed them as two tasks.
  • The counters are kept per GDN operation, not per model layer. tron's GDN code does not know the layer number.

2. How it was measured

  • Every run uses runtron on our half of delphi-3b35, with one engine on four FPGA cards (tp4) [Ref2].
  • A cell is 1 or 8 users with a prompt of 1,024, 4,096 or 8,192 tokens. Every run then generates 256 tokens per user.
  • The campaign ran 108 runs: 6 cells, 6 arms and 3 repetitions. The arm order changes with each repetition.
  • These runs are session 2. They ran on 2026-11-22 from 00:13 to 01:17 UTC (2026-11-21, 16:13 to 17:17 PST), on the commits after the code review [Ref13].
  • Session 1 ran earlier, on the commits before the code review. It was stopped after 43 runs, and session 2 took its place.
  • Every value on this page comes from session 2, unless the text names session 1.
  • After session 2, only comments, tests, commit messages and two README files changed [Ref16]. The 3 commits of the branch include these changes. The code that runs is the same.
  • Every value is the median of the repetitions of one cell and arm.
  • The 3 repetitions of one cell and arm differ by up to 1.4 % in the time to first token. In decode speed they differ by up to 1.6 %.
  • With 8 users, the time to first token of a run is that of the slowest user. The decode speed of a run is the mean of the 8 users.
  • The base run is part of the same session. The values of 2026-11-20 are not used as a denominator.
  • A load snapshot was taken before every run. A run does not start when our CPUs are more than 5 % busy.
  • The 6 arms of the campaign have both sets of counters on (TRON_ATTN_STATS=1 and TRON_GDN_STATS=1).
  • The two control arms have the attention counters only. One runs with TRON_GDN_STATS not set. The other is the build of 2026-11-20, which has no GDN counters.

Which kernel takes a token

  • A token of a GDN layer takes exactly one of the three recurrence kernels. So one token gets the gain of Part 0 or the gain of Part A, never both.
  • A chain of 1 token takes the token kernel. Every decode token is such a chain.
  • With Part A on, a full window of 32 prompt tokens takes the block kernel.
  • A shorter window takes the chain kernel of Part 0. A block that the block kernel refuses takes it too.
  • So a run with Part A always includes Part 0. The arm named Parts A and B is the run with all three changes.
  • In the 6 cells every chain of a prefill pass is a whole number of blocks. The block kernel refused 0 blocks there (section 9). So with Part A on, 100 % of the prompt tokens took the block kernel.

3. Time to first token

  • With Part 0 alone the time to first token fell by 9.0 to 14.1 %. The working values were 14 to 23 % (est.), and the range was 8 to 26 % (est.). The result is below the working value in 6 of 6 cells and inside the predicted range in all 6 cells.
  • With Part A the time to first token fell by 15.3 to 24.8 %. The working values were 18 to 29 % (est.), and the range was 11 to 32 % (est.). The result is below the working value in 6 of 6 cells and inside the predicted range in all 6 cells.
  • With Parts 0 and B the time to first token fell by 14.9 to 32.3 %. The working values were 24 to 37 % (est.), and the range was 13 to 42 % (est.). The result is below the working value in 6 of 6 cells and inside the predicted range in all 6 cells.
    • With 8 users, prompt 1,024 the fall is 14.9 %, and the low end of the range is 14.4 % (est.).
    • 1 of the 18 single repetitions of this arm is outside its range.
  • With Parts A and B the time to first token fell by 25.2 to 39.0 %. The working values were 30 to 41 % (est.), and the range was 18 to 47 % (est.). The result is below the working value in 6 of 6 cells and inside the predicted range in all 6 cells.
  • Part B alone is the fall from the Part 0 run to the run with Parts 0 and B. It is 0.8 to 23.0 % of the base run. The working values were 2 to 22 % (est.).
    • With 8 users, prompt 1,024 it is below the range: 0.8 % against 1.8 to 4.2 % (est.).
    • This is the only comparison of a time to first token that is not inside its range.
  • The prediction for Parts 0 and B is not printed on the design page. It comes from the same prediction file [Ref3].
  • The GDN changes help most at short prompts, and the attention change helps most at long prompts. The prediction said the same.

8 users against 1 user at prompt 1,024

  • At prompt 1,024 the two GDN changes give a little more with 8 users than with 1 user.
    • Part 0: 14.1 against 13.8 %
    • Part A: 24.8 against 23.8 %
  • With 8 users the GDN wall is 44 % of the prefill pass of the base run. With 1 user it is 42 %.
  • With Part B the order is the opposite. Parts A and B give 25.2 % with 8 users and 26.0 % with 1 user.
  • The cause is Part B alone. It gives 0.8 % of the base run with 8 users and 2.5 % with 1 user.
  • The kill-switch pair shows where the difference comes from. Its two runs differ in Part B only.
  • With 8 users the attention busy time without the join wait got 1.52 times shorter. That saves 10.6 ms per prefill pass.
  • In the same runs the join wait rose from 3.3 to 10.9 ms. So the pass got only 2.9 ms shorter, of 310 ms.
  • With 1 user that busy time got 1.32 times shorter, and the join wait did not rise. The pass got 1.25 ms shorter, of 41.4 ms.
  • Insufficient data for why the join wait rose with 8 users. In the join a thread waits until the other threads have finished their scoring. A time stamp per thread at the end of its scoring would show which threads end late.
  • The design page reports the same rise on delphi-3bda, another server, with the 128-wide kernel. There the join wait rose from 4.1 to 12.0 ms with 8 users, prompt 1,024.
  • The design page lists another wait as an open point. It is the wait for the K and V data of the pass. tron counts that wait outside the busy time and outside the join wait.
  • The attention wall minus the mean busy time holds that wait. With 8 users it changed from 19.2 to 19.8 ms.

4. Decode speed

  • Part 0 and Part A do not touch decode. Their decode speed is within 0.7 % of the base run.
  • With Part B, decode changed by -1.0 to +22.2 % against the same build with the kill switch set.
  • The prediction for Part B was no change at the working value. Its range grows with the users and the prompt. The widest range is -5.3 to +7.8 % (est.).

Where the decode gain comes from

  • The prediction assumed that the attention busy time of a decode step gets 0.9 to 1.17 times shorter (est.).
  • The design took 1.18 and 1.22 times from measurements of the 128-wide kernels on delphi-3bda, another server. It multiplied them by an assumed clock ratio of 0.76 to 0.96 (est.).
  • The kill-switch pair gives the measured value. With 8 users the busy time got 1.31 to 1.55 times shorter.
  • With 1 user the change depends on the prompt.
    • prompt 1,024: 12 % longer, from 0.181 to 0.202 ms
    • prompt 4,096: 1.10 times shorter
    • prompt 8,192: 1.19 times shorter
  • Take 8 users and prompt 8,192. There the attention busy time of a decode step fell from 8.88 to 6.01 ms. The decode step fell from 16.89 to 13.71 ms.
  • The busy time includes the join wait. In that cell the join wait fell from 1.40 to 0.11 ms. That is 45 % of the fall of the busy time.
  • Without the join wait the busy time got 1.27 to 1.34 times shorter with 8 users. The stand-alone test gave 1.33 times for decode with pages from main memory [Ref9].
  • So with 8 users the kernel work got shorter in all 3 cells. The join wait of a decode step got shorter only at the two longer prompts.
    • prompt 1,024: from 0.06 to 0.06 ms
    • prompt 4,096: from 0.89 to 0.08 ms
    • prompt 8,192: from 1.40 to 0.11 ms
  • The design divided the kernel work and the join wait by one factor.
  • Insufficient data for why the join wait fell. A timer inside the join of a decode step would show what the threads wait for.
  • The decode step is the wall of one forward pass. The time between two passes is not part of it.

5. Why decode gains little

  • Section 4 gives the measured decode speed. This section gives the reasons for it.
  • A decode step gives every GDN layer one token per user. tron gives a chain of 1 token to step(), which runs the token kernel on the stored state.
  • So Part 0 and Part A do not run in decode. The chain kernel works on a copy of the state in another layout. For 1 token that would add two copies of 128 KiB.
  • Part B runs in decode. It changes the attention kernel only.
  • With 1 user, 67 to 76 % of a decode step is neither GDN work nor attention work. None of the three changes touches that part.
  • So the decode gain is large only where attention is a large part of the step. That is with 8 users and prompts of 4,096 tokens or more: 18 to 23 %. In the other 4 cells decode changed by -0.8 to +3.3 %.

One token at a time

  • A prefill pass holds 128 prompt tokens per user. tron knows all of them when the pass starts.
  • A GDN layer takes them as one chain. So a kernel can work on many tokens of the chain in one call.
  • The chain kernel computes the read of the next token while it writes the current token. The block kernel takes 32 tokens per call.
  • A decode step is different. The model must run all 32 layers for one token before the sampler can pick the next token.
  • So in a decode step a GDN layer holds one token per user. tron then runs step(), with the token kernel of the base build.
  • With 8 users a decode step has 8 tokens. They belong to 8 sequences with 8 states, so they are 8 chains of 1 token.
  • The counters show the same. In all 6 arms and all 6 cells, 100 % of the decode head tokens took the token path. That path is step() with the token kernel.
  • With 1 user, prompt 1,024 the GDN wall of a decode step is 0.383 to 0.384 ms in all 6 arms.
  • In that cell a prefill pass spends 6.55 us of GDN wall per layer and token in the base run. With all three changes it spends 2.91 us.
  • A decode step spends 15.96 us per layer and token in the base run and 15.99 us with all three changes.

Where the time of a decode step goes

  • The figure and the table split the wall of a decode step into three parts.
    • the GDN wall of the 24 GDN layers
    • the attention wall of the 8 attention layers
    • the other work: matrix multiplies on the FPGA cards, data transfers and the remaining CPU work
  • The attention wall is the time of an attention job on attention thread 0, from its entry to its return. It includes every wait inside the job. The values sum it over the 8 attention layers.
  • After the job, thread 0 waits until the other attention threads have finished. That wait is not in the attention wall, so it counts as other work.
  • The other work is the decode step minus the two walls. The counters do not split it.
  • With 1 user the other work is 67 to 76 % of the step. The GDN wall is 9 to 11 %, and the attention wall is 13 to 23 %.
  • With 8 users the other work is 27 to 49 % of the step. The GDN wall is 18 to 33 %, and the attention wall is 18 to 55 %.
  • Take 8 users, prompt 8,192. With all three changes the attention wall fell from 9.30 to 6.38 ms. The decode step fell from 16.94 to 13.71 ms.
  • In that cell the other work fell by 0.27 ms, to 4.26 ms. The GDN wall changed by -0.04 ms.
  • Insufficient data for why the other work fell. Hypothesis: thread 0 waits less for the other attention threads after its job. A timer around that wait would test it.
  • With 1 user, prompt 1,024 the attention wall is 0.47 ms in both runs. The decode step is 3.62 ms in both.

Inside the GDN work of a decode step

  • In a decode step with 1 user, prompt 1,024, a GDN step takes 14.4 us. In a prefill pass of the base run it takes 6.08 us.
  • The counters split the decode value into three parts.
    • the start of the chain: 7.47 us
    • the token step: 6.72 us
    • the bookkeeping and the time stamps: 0.17 us
  • The token step is the convolution, the normalization, the recurrence, the norm and the output gate of one token.
  • A chain of 1 token changes the state in place. So no write of the state follows the token step.
  • The start prepares the state of one key head for the chain [Ref21]. It copies the state when the chain writes to another buffer. It also checks every state value for NaN, a marker of an invalid result.
  • The state of one key head is 128 KiB, or 131,072 bytes. The counters do not split the start further.
  • A chain runs the start once. A prefill chain has one start per 128 tokens: 0.08 us per token in the base run.
  • In decode every token is its own chain, so every token has a whole start.
  • In the 6 cells the start is 52 to 59 % of the GDN step in decode (base run). A faster recurrence does not shorten it.
  • Suppose the token step took no time. With 1 user, prompt 1,024 the decode step would be about 5 % shorter (est.). With 8 users, prompt 1,024 it would be about 15 % shorter (est.).
  • This estimate assumes that the GDN wall falls in proportion to the GDN step.
  • Hypothesis: in decode the start reads the state from main memory, not from the cache. A timer around the NaN check alone would test it.
  • Insufficient data for the chain kernel on chains of 1 token. A stand-alone timing with windows of 1 token would give it.

What Part B gives in decode

  • Part B is the only change that runs in decode. Section 4 gives its effect in every cell.
  • With 1 user the attention wall is 13 to 23 % of the step. So a faster attention kernel can shorten the step by at most 13 to 23 % there.
  • The attention wall itself got 1.00 to 1.08 times shorter with 1 user. With 8 users it got 1.21 to 1.50 times shorter.
  • With 1 user the mean busy time of the attention threads is 40 to 73 % of that wall. The rest of the wall holds the waits.
  • In decode the kernel gains less when the pages come from main memory. In the stand-alone test it was 1.33 times faster there [Ref9]. Loading the page takes most of the time there.
  • For prefill with pages from main memory it was 2.33 to 2.63 times faster. With the pages in cache it was 2.48 to 2.70 times faster for decode too.
  • With 8 users and prompts of 4,096 tokens or more, the attention wall is 41 to 55 % of the step. There the decode step got 15.5 to 19.1 % shorter, and the decode speed rose by 18 to 23 % (section 4).

7. A problem found during the work

  • The first runs of Part A in tron were slower than expected.
  • Before the fix the time to first token with Part A was 0.318 to 0.320 s [Ref18]. This is from 2 runs with 1 user and prompt 1,024.
  • 8 of the 24 GDN layers had a GDN wall above 1.5 times the median layer. The largest was 2.9 to 3.0 times.
  • The cause was subnormal numbers. A value head that forgets fast has small decay values. The block kernel multiplies the decays of up to 32 tokens.
  • That product then drops below the smallest normal FP32 value. The CPU computes with such values through a slow path.
  • In a stand-alone test with decays from 0.01 to 0.1 the block kernel took 3,239 ns per value head and token. With the bits FTZ and DAZ set it took 598 ns [Ref8].
  • The kernel now sets both bits for its own work and restores the caller's setting on return. A unit test checks the restore.
  • After the fix the time to first token was 0.292 to 0.295 s. The largest GDN wall of a layer was 1.10 to 1.11 times the median layer.
  • A unit test covers decays whose products underflow. The kernel with the two bits stays inside its error band there.
  • In the stand-alone test the times of the token kernel and of the chain kernel change by less than 0.5 % over the decay ranges.

8. The new GDN counters

  • Until now only a trace could time GDN. The new counters time it in every run, with no trace.
  • They follow the attention statistics of tron.
    • One environment variable turns them on.
    • Each worker thread has its own counters.
    • tron prints a report at exit.
    • Files show the values while the program runs.
  • Per GDN operation and thread they count the work items and the head tokens on each of the three paths.
  • The paths are the token path (step()), the chain path (the chain kernel) and the AMX block path.
  • They also count the blocks that the AMX kernel finished and the blocks that it refused.
  • They time the parts of the work.
    • the start of a chain
    • the work before the recurrence
    • the recurrence, per path
    • the work after the recurrence
    • the write of the state
  • Per operation they give the sum, the largest value and the count of the GDN walls.
  • Two classes of pass are kept apart.
    • passes in which every token has a listener: these are decode steps
    • all other passes: prefill passes and mixed passes
  • With the switch off, a GDN call tests one flag and reads no clock.
  • The files are under /model/<model_id>/gdn/ of tron's statistics folder [Ref12].

9. Numerics and tests

  • Part 0 changes no bit. New unit tests compare advance() with step() byte by byte, for outputs and for the stored state.
  • They cover these cases.
    • at 128 value columns: chains of 1, 2, 3, 31, 32, 33, 127 and 128 tokens from 4 start positions
    • at 16 and 80 value columns: chains of 2, 33 and 70 tokens from 2 start positions
  • The existing tests of the prefill path now run the chain kernel too. They still require equal bytes.
  • Part A changes few bits, as the design said. New tests bound the difference against the chain kernel and against a float64 computation.
  • In the stand-alone check 0.006 to 0.034 % of the bf16 output words differ [Ref6]. An output above 1 % of the typical size differs by at most 1 bf16 step. A smaller output differs by up to 16 steps.
  • Against float64 the output error of the block kernel is 0.37 to 0.61 times the error of the token kernel.
  • The state error of the block kernel is 0.48 to 1.30 times that of the token kernel. It is larger in 2 of 8 input families.
  • A block is refused when a correction or an output is not finite. It is also refused when a correction is 2^100 or larger. Its state stays untouched.
  • Tests cover these cases.
    • an infinity and a NaN in the start state
    • a value of 3e38
    • a value of 2^99, which the kernel must take
    • an output that overflows
  • advance() then gives the refused value head to the chain kernel. A test checks that the state of this head gets the bytes of step().
  • In the campaign the block kernel refused 0 blocks.
  • Part B has the error band of the existing 128-wide kernels. The existing band tests now run for both shapes.
  • Part B changes many low bits. In the self-check of the stand-alone test, 676 of 1,024 bf16 words of the attention sums differ [Ref9]. The largest difference is 0.0625 at a largest value of 12.2.

What the scores show

  • A dump keeps the 320 best scores of every generated step [Ref17]. Two runs of the base arm give equal scores at 4 of 4 compared steps.
  • At generated token 0 the kept scores of the runs with an AMX kernel are close to the base run.
    • With Parts 0 and B, 316 of the 320 token ids are in both lists. 56 of these scores differ, by at most 1 bf16 step.
    • With Part A, 319 token ids are in both lists. 73 of these scores differ, by at most 1 bf16 step.
  • The run with Parts 0 and B first differs at generated token 1. There the two best scores of the base run are equal.
    • The base run scores 16.375 for token id 40 and 16.375 for token id 3850. The sampler takes the first one.
    • The run with Parts 0 and B scores 16.375 for token id 3850 and 16.25 for token id 40.
    • So one score moved by 1 bf16 step, and the other token id wins.
  • An earlier campaign on another model found the same kind of tie [Ref15].
  • The run with Part A has the same tie at generated token 1. It scores 16.375 for token id 40 and 16.375 for token id 3850, and it takes token id 40.
  • The run with Parts A and B scores 16.375 for token id 40 and 16.375 for token id 3850 there. So with both AMX kernels the same score does not move, and the token of the base run stays.
  • The run with Part A gives the tokens of the base run for 185 steps. Its scores move away from the base run during these steps.
    • In steps 0 to 79 its best score differs from the base run by at most 1 bf16 step.
    • In the later steps it differs by up to 10 bf16 steps.
    • At generated token 185 the base run scores 17.875 for token id 6351 and 16.875 for token id 198. They are 8 bf16 steps apart.
    • The run with Part A scores 16.5 and 16.625 for them. So the other token id wins.
  • The block kernel runs in prefill only. The counters show all GDN tokens of decode on the token path, in every arm.
  • So after the prefill the base run and the run with Part A take the same kernels. They are the token kernel for GDN and the AVX-512 path for attention.
  • The score difference becomes larger while both runs take these kernels.
  • This is not a tie. At generated token 185 the score of token id 6351 is 11 bf16 steps lower in the run with Part A. So token id 198 wins.
  • The dump has scores only. It does not show how much the GDN states and the stored keys and values differ after the prefill.
  • Insufficient data for how such differences grow with other prompts. The output of this prompt repeats: the base run has 28 different tokens in 256. The same dump for more prompts would show it.

11. Limits and open points

  • The measurement covers one server, one model and the prompt texts built into runtron. Other prompts give other decay values and other attention patterns.
  • The other socket of the server was 42 % busy with other users' jobs in every run. Its effect on our runs is not measured.
  • Two verdicts lie closer to their limit than the spread of the repetitions.
    • The first is the range of Parts 0 and B with 8 users and prompt 1,024. 1 of 3 repetitions is below its low end.
    • The second is the decode rule with 1 user and prompt 1,024. Its margin is 0.1 percentage points.
  • The miss of the Part B rule with 8 users and prompt 1,024 is not such a case. All 9 pairs of repetitions give 0.0 to 0.9 %, below the low end of 1.8 % (est.).
  • The core clock inside tron was not read. The clock readings on this page come from stand-alone loops.
  • The numeric checks used synthetic inputs. A capture of the GDN inputs of one real prompt would give the size of the differences on real data.
  • The owners of the GDN code have not accepted the numerics contract of Part A. The design named this as a condition. The score comparison of section 9 is data for that decision.
  • No person has reviewed the code yet. The reviews named on this page were made by AI agents.
  • The model's registry entry says that its tokens are not yet valid. The token comparison on this page is a check of equal tokens, not of quality.
  • Part B serves every model with 256-wide heads and 4 query heads per KV head. Only Qwen3.5 4B was run.
  • Part B also changes two lines of the dispatch code that the 128-wide models run. Their unit tests passed. No 128-wide model was run in tron on this branch.
  • With Part A the work before and after the recurrence is the largest part of the GDN step: 54 %. The convolution alone was 0.50 us per step in a stand-alone test of 2026-11-20.
  • 16 of 56 threads run GDN, as before. Spreading the work over more threads is a scheduling change outside this design.
  • With 1 user decode changed by -0.8 to +2.9 %. Section 5 gives the reasons for the small gain.
  • In decode the start of a chain is 52 to 59 % of the GDN step. None of the three changes shortens it there, and the counters do not split it.
