GDN and AMX: design for Qwen3.5 4B

2026-11-20. Measured on delphi-3b35 (our test server), on our half of it. The code is tron (the inference program under test) at commit 72e1191804 (open pull request #3696).
Status: baseline, prediction and design. Nothing is built yet.

Short version

  • In Qwen3.5 4B, 24 of the 32 layers are GDN layers (layers with a fixed-size memory matrix).
  • Today tron runs no AMX code (Intel's matrix instructions) for this model, we propose three changes, and none is built.
  • The table below gives each change's estimated effect (est.) on the time to first token, from the baseline measured on delphi-3b35.

Words used here
  • tron, runtron: tron is the inference program under test. runtron is its command-line tool.
  • Qwen3.5 4B: the model under study. Its tron name is ingested-qwen-3.5-4b.
  • llama-3.1-8b, qwen-3-4b: two models that tron already runs. Every layer of both is an attention layer. Our earlier AMX numbers come from qwen-3-4b.
  • GDN (GatedDeltaNet): a recurrent layer type. It does the job of attention with a matrix of fixed size, the state.
  • state S: the memory of a GDN layer. One matrix of 128 key rows by 128 value columns per value head, in FP32.
  • key head, value head: a GDN layer has 16 key heads and 32 value heads. Each key head serves 2 value heads.
  • decay, beta: two numbers that the model computes per token and value head. Decay shrinks the old state. Beta scales the correction.
  • convolution, norm, output gate: the small operations around the recurrence of a GDN layer. The convolution is a filter over the last 4 tokens. The norm is a normalization, and the output gate is a multiplication by a gate value.
  • recurrence: the four lines that read and rewrite the state for one token (figure 2).
  • SiLU, RMS norm: SiLU is the function x / (1 + exp(-x)). The RMS norm divides the values by their root mean square.
  • full attention: ordinary attention: the new token is scored against every earlier token.
  • software attention: full attention computed on the host CPU, not on the FPGA cards.
  • head, query head, KV head: attention splits a token's vector into heads. Qwen3.5 4B has 16 query heads and 4 KV heads per attention layer. A KV head holds the stored K and V rows that 4 query heads share.
  • 128-wide, 256-wide, 256 x 4: the number of values per head. 256 x 4 means heads of 256 values with 4 query heads per KV head.
  • KV cache, KV page: the stored K and V rows of earlier tokens. tron keeps them in pages of 64 tokens.
  • K token: one stored K row that a query is scored against. The attention statistics count K tokens per kernel.
  • page unit: the attention work of one query token on one KV page of one KV head.
  • QK, PV: the two products of the attention kernel. QK is queries times stored keys, and it gives the scores. PV is softmax weights times stored values.
  • AMX: Intel Advanced Matrix Extensions: tile registers, and instructions that multiply two tiles.
  • tile, tile row: an AMX register of 16 rows by 64 bytes. A tile product is efficient only when most of the 16 rows carry data.
  • tile product (TDPBF16PS): one AMX instruction. It computes 8,192 bf16 multiply-adds and adds them into a 16 by 16 FP32 tile.
  • AVX-512, FMA: 512-bit vector instructions. FMA is the fused multiply-add on 16 FP32 values at once.
  • bf16, fp16, FP32, float64: number formats.
    • bf16 has 16 bits and 8 significant bits.
    • fp16 has 16 bits and 11 significant bits.
    • FP32 has 32 bits and 24 significant bits.
    • float64 has 64 bits. The checks use it as the exact reference.
  • piece, plane: Part A splits one FP32 value into 3 bf16 values, the pieces.
    • The sum of the pieces is the FP32 value when its size is 2^-103 (about 9.9e-32) or larger. Section 5.4 gives the rule.
    • A plane is the matrix of one piece of every state value.
  • subnormal value: a nonzero value that is smaller than the smallest normal value of its number format. For bf16 and for FP32 the smallest normal value is 2^-126, about 1.2e-38.
  • L1, L2 cache, cache line: the two private caches of a CPU core. They hold 48 KiB and 2 MiB on this CPU, and data in L1 is the fastest to reach. A cache line is 64 bytes.
  • core clock: the frequency at which a CPU core runs. The CPU lowers it while AVX-512 or AMX instructions run.
  • clock probe: our small test program. It runs one instruction mix on one CPU and reads the core clock.
  • tile run, AVX-512 run, turn: a tile run is a stretch of tile instructions with no AVX-512 work between them. An AVX-512 run is a stretch of AVX-512 work with no tile instruction. A turn is one tile run plus the AVX-512 run next to it.
  • FPGA cards: the accelerator cards that do tron's large matrix multiplies (projections, feed-forward layers).
  • host: the server's own CPUs, as opposed to the FPGA cards.
  • engine, tp4: an engine is one running copy of the model. tp4 is the executor that spreads one engine over four FPGA cards.
  • plugin: the C++ code that tron generates for one model.
  • kernel: a small, performance-critical routine, for example the GDN recurrence or the attention dot products.
  • dispatch: the code that picks a kernel at run time.
  • prefill, TTFT: prefill is the processing of the prompt. TTFT is the time to first token: from the request to the first generated token.
  • decode, tok/s: decode is the generation of tokens after the prompt. Its speed is given in tokens per second per user.
  • pass, decode step: a pass is one forward computation through all 32 layers. A prefill pass holds 128 prompt tokens per user. A decode step is a pass with one token per user.
  • wall: wall-clock time: the elapsed time from the start of a piece of work to its end, waits included.
  • us: the microsecond, one millionth of a second.
  • percentage point: the unit of a difference between two percentages.
  • chain: the consecutive tokens of one sequence in one pass. A GDN layer must take them in order.
  • GDN step: the work of one token for one key head. It contains the convolution, the recurrence on 2 value heads, the norm and the output gate.
  • work item: one chain of one key head. The GDN threads divide the work items among themselves.
  • working copy: in prefill each GDN thread copies the state of one key head (128 KiB) to a private buffer. The thread works on this copy and then copies it back.
  • token form, block form: two ways to compute the same recurrence. The token form updates the state token by token, as tron does today. The block form takes a block of tokens at once with matrix products.
  • block, block kernel: a block is 32 consecutive tokens of a chain. The block kernel is the AMX routine of Part A for one block.
  • column-half order, slice: the loop order of Part 0. A slice is a group of value columns of the state, here one half (64 columns).
  • main thread, main helpers, attention workers: tron's CPU threads. The main thread and 15 main helpers run GDN. The 40 attention workers run software attention only.
  • application CPUs: the CPUs that tron's threads may use: 56 per engine in this setup.
  • attention statistics: counters and timers that tron reports when the environment variable TRON_ATTN_STATS=1 is set.
  • attention busy time: the time of the attention jobs on one attention worker. It leaves out the worker's waits for the queries (Q) and for K and V. The page gives the mean over the 40 workers.
    • The busy time has four parts. The first is the scoring of the full pages of earlier passes.
    • The second is the scoring of the pages that the pass in progress writes.
    • The third is the join.
    • The fourth is the join wait.
  • join, join wait: the join is the last step of an attention job.
    • The join adds the partial results of the workers into one result per token.
    • The join wait is a worker's waiting time in the join. It ends when the other workers have finished their scoring. It is part of the busy time.
  • other attention work: the attention busy time of a prefill pass without the full-page time and without the join wait. It is the AVX-512 scoring of the pages that the pass writes, and the join (est.).
  • full-page time: one part of the attention busy time of a prefill pass. It is the time spent on the full pages of earlier passes (est.). In a prefill pass Part B makes only this part faster.
  • attention wait: the wall time of the attention jobs on attention worker 0, minus the mean busy time.
    • It contains the worker's wait for Q at the start of a job.
    • It also contains the worker's wait for K and V in the middle of a job.
    • tron has no timer for either wait alone.
  • memory stall: the time a core waits while data is loaded from main memory. It is part of the busy time.
  • trace, trace event: a trace is a recording of timed events made by runtron, in the Perfetto format. Its trace event named GatedDeltaNet is tron's only timer for GDN.
  • kill switch: the environment variable TRON_AMX_DISABLE=1. It turns the AMX kernels off at run time.
  • arm: one of the two settings of a comparison. Here: AMX allowed, or the kill switch set.
  • A/B run: two runs that differ in one switch only.
  • base build, base run: the base build is tron without Parts 0, A and B. A base run is a run of the base build. It is made in the same session as the runs that are compared with it.
  • GDN switch: a new run-time switch of this design. It turns the GDN block path of Part A off alone.
  • token path, column-half path, block path: the three code paths of the GDN recurrence.
    • The token path runs step() per token. It is today's code.
    • The column-half path runs advance() with the loop order of Part 0.
    • The block path runs advance() with the block kernel of Part A.
  • chain path: advance(), the new code path for chains of 2 or more tokens. The column-half path and the block path both run advance().
  • session: one series of runs on delphi-3b35 with no reboot between them. The server's own settings (CPU settings, SYSTEM_CONFIG) also stay unchanged between them.
  • cell: one combination of user count and prompt length.
  • prompt N: a prompt of N tokens. Every baseline run then generates 256 tokens per user. A traced run generates 32 tokens per user.
  • Part 0, Part A, Part B: the three proposed changes.
    • Part 0 is a new loop order for GDN prompt processing, without AMX.
    • Part A is the AMX block kernel for GDN.
    • Part B is the AMX attention kernel for 256-wide heads.
  • factor, working value: a factor is old time divided by new time. Each factor has a low value, a working value and a high value. The working value is the one we expect.
  • error band: a stated limit on how far a result may differ from the reference result.
  • increment: the step between two neighboring values of a number format, here bf16 or FP32.
  • logits: per-word scores. The model gives one score to every word of its vocabulary for the next token.
  • numerics contract: a written rule. It says which results must be equal bit for bit and which may differ inside an error band.
  • pull request: a proposed code change on GitHub that is not merged yet.
  • delphi-3b35, our half: the test server. We use its second CPU socket and FPGA cards 4 to 7.
  • delphi-3bda: a second server with the same CPU model. Our earlier AMX numbers were measured there.
  • TSX, flat-frequency service, deep idle states: three CPU settings that differ between the two servers. The flat-frequency service holds the core clock at a fixed value.
  • Hugging Face Transformers, vLLM, SGLang, llama.cpp: open-source programs that also run this model.
  • est.: an estimate. Every number without it is measured or read from the code.
  • Insufficient data: a value that we could not measure. The text names the measurement that would give it.

1. What GDN is, compared with llama-3.1-8b

  • llama-3.1-8b has 32 layers. Every layer is a full-attention layer [Ref20].
  • Qwen3.5 4B has 32 layers too. 24 are GDN layers and 8 are full-attention layers [Ref1, Ref2].
  • A GDN layer does the job of attention. It brings information from earlier tokens into the current token. It uses a different mechanism.

3. Attention metrics: where the time goes

  • The attention statistics were turned on in every run, with TRON_ATTN_STATS=1 [Ref8].
  • The statistics give the wall time of every pass. The page calls it the pass wall. For a decode step the page calls it the step wall.

Attention busy time

  • The statistics give the attention busy time per worker. It is the time of the attention jobs without the worker's waits for Q and for K and V [Ref8]. The page divides the sum over all workers by the 40 workers.
  • The busy time is not kernel time only. It contains four parts:
    • the scoring of the full pages of earlier passes
    • the scoring of the pages that the pass in progress writes
    • the join
    • the join wait

Join wait

  • A worker finishes its scoring. Then it waits in the join until the other workers have finished theirs. This wait is the join wait.
  • The statistics time the join wait. It is inside the busy time [Ref8].
  • Per prefill pass the join wait is 1.4 to 2.3 ms with 1 user and 3.2 to 3.9 ms with 8 users. With 1 user at prompt 1,024, that is 24 % of the busy time. With 8 users at prompt 8,192 it is 1.6 %.
  • Per decode step the join wait is 0.02 to 1.39 ms, or 6 to 19 % of the busy time.

Attention wait

  • The statistics also give the wall time of the attention jobs on attention worker 0, waits included. This wall time is longer than the mean busy time:
    • by 2.3 to 2.6 ms per prefill pass with 1 user
    • by 19 ms per prefill pass with 8 users
    • by 0.3 to 0.4 ms per decode step
  • The page calls this difference the attention wait. It contains two waits of worker 0:
    • The first is the wait for Q at the start of each job.
    • The second is the wait for K and V. It comes before the scoring of the pages that the pass writes [Ref8].
  • The attention wait also contains the difference between the busy time of worker 0 and the mean. So it does not give the wait for K and V alone. tron has no timer for that wait.
  • The attention wait stays in the rest.

GDN wall and the rest

  • The statistics do not cover GDN. The GDN code does not call the statistics code [Ref8].
  • GDN was timed with tron's trace, in one traced run per cell. A traced run generates 32 tokens per user.
  • The trace event named GatedDeltaNet covers the GDN host work of one layer on one thread [Ref10]. The GDN wall of a layer runs from the first thread's start to the last thread's end.
  • The rest is the pass wall minus the GDN wall minus the attention busy time. It is FPGA matrix multiplies, small host kernels and the attention wait.

Limit of the decode numbers

  • The decode table divides the GDN wall of a traced run by the step wall of the untraced runs. So its GDN shares are estimates (est.).
  • The rest of a decode step is computed with the same GDN wall. It is an estimate too. The last column gives the GDN share inside the traced run.
  • The two kinds of run differ in three ways:
    • The trace is on. A traced decode step is 3 to 28 % longer than an untraced one. A traced prefill pass is 0.2 to 3.1 % longer.
    • A traced run generates 32 tokens per user, and an untraced run generates 256.
    • The traced mean leaves out the first pass of each kind, and the untraced mean covers every pass.
  • The untraced runs have no timer for GDN. So we do not know whether the GDN shares are too high or too low, or by how much. Insufficient data.
  • The GDN wall counter proposed in section 5.6 (row Counters) runs without the trace. It would give the direction and the size of the error.
  • A decode step of the traced run is 0.5 to 1.0 ms longer than a step of the untraced runs.
    • 0.1 to 0.3 ms of that is attention busy time.
    • No timer locates the other 0.3 to 0.7 ms. With 1 user that is 73 to 134 % of the traced GDN wall. With 8 users it is 11 to 22 % [Ref18].
  • The prefill table is built the same way. There the time that no timer locates is at most 4 % of the GDN wall [Ref18].

What the numbers say

  • The GDN time of a prefill pass does not depend on the prompt length. It is 20.2 to 20.3 ms with 1 user and 160 ms with 8 users.
  • One GDN step takes 6.3 to 6.5 us on 14 of the 16 GDN threads in prefill.
    • The 2 threads on CPUs 108 and 109 take 3.8 to 4.0 us. Their cores run at 4.00 GHz [Ref11].
    • The mean over the 16 threads is 6.1 us.
  • The slowest thread sets the GDN wall of a layer. One GDN layer takes 0.85 ms for 128 tokens with 1 user. That is 6.6 us per token.
  • A stand-alone benchmark of the recurrence alone takes 3.06 us per value head (1 thread, 2 MiB state) [Ref11]. The convolution takes 0.50 us per key head.
    • The benchmark is not the same quantity as the traced GDN step.
    • In tron the recurrence takes about 2.8 us per value head (est.). This estimate is 6.4 us minus 0.8 us of other work, for 2 value heads.
  • Our hypothesis is that the GDN step is limited by moving the state, not by arithmetic.
    • A value head's matrix is 64 KiB. The L1 cache is 48 KiB. Each token passes over the matrix twice.
    • The arithmetic alone needs 0.95 to 1.16 us per value head (est.), against about 2.8 us (est.) in tron.
    • Task 1 of the plan confirms or rejects this hypothesis. A timing on another CPU gives the moving of the state a smaller share (section 4, low case of Part 0).
  • The same GDN step takes 13 to 16 us in decode (mean over the threads, traced runs).
    • Our hypothesis has two parts. In decode the state comes from outside the core's own caches for every token. The check for invalid values reads the state once more [Ref4].
    • The open points name the measurement that confirms or rejects this hypothesis.
  • Only 16 of the 56 threads run GDN. With 8 users each of the 16 threads has 8 chains to run, one after another. Compared with the wall with 1 user, the GDN wall with 8 users is:
    • 7.9 times as long in prefill
    • 5.2 to 6.8 times as long in decode

4. Prediction, made before any test of the solution on delphi-3b35

Method

  • The layers of a pass run one after another.
  • In a GDN layer the FPGA projections, the host work and the next projection run one after another. So a time saved in GDN shortens the pass by the same amount.
  • In an attention layer the scoring of the full pages starts when Q is ready. It can run while the FPGA cards produce K and V of the pass [Ref8]. Assumption of the model: with Part B on, this scoring still ends after K and V are ready.
    • Under this assumption a time saved in attention shortens the pass by the same amount.
    • The open point on the wait for K and V names the measurement that tests it.
pass_new = pass - GDN_wall x (1 - 1/s_gdn)
                - attention_scaled x (1 - 1/s_attn)
                + rest x clock_cost
                + attention_other x clock_cost_attention
attention_scaled = full-page time        (prefill pass)
attention_scaled = attention busy time   (decode step)
attention_other  = attention busy time - full-page time - join wait
                   (prefill pass, Part B only)
TTFT_new = TTFT - passes x (pass - pass_new)
ms_per_token_new = ms_per_token - (step - step_new)

Symbols of the formulas

  • s_gdn and s_attn are the factors of the table below for the GDN step and for the attention.
  • attention_scaled is the part of the attention busy time that s_attn divides.
  • clock_cost and clock_cost_attention are the last two rows of the table below.
  • attention_other is the other attention work: the AVX-512 scoring of the pages that the pass writes, and the join.
  • step is the wall of one decode step. step_new is computed like pass_new.

Prefill: what the factor divides

  • In a prefill pass the factor divides the full-page time only. The AMX kernel replaces the scoring of the full pages of earlier passes.
  • The pages that the pass in progress writes stay on the AVX-512 path [Ref8]. They contain these shares of the scored K tokens of a pass [Ref9]:
    • 12.6 % at prompt 1,024
    • 3.1 % at prompt 4,096
    • 1.6 % at prompt 8,192
  • The join and the join wait are not kernel work.

Size of the full-page time

  • The busy time without the join wait fits a straight line. The line is a fixed part per pass, plus 67 ns of CPU time per K token in full pages. The error of the line is below 0.1 ms at each of the three prompt lengths [Ref18].
  • The full-page time is the part that grows with the K tokens (est.). It is this share of the busy time (est.):
    • 51 % with 1 user at prompt 1,024
    • 72 % with 8 users at prompt 1,024
    • 88 to 96 % at prompt 8,192
  • The part that s_attn does not divide holds the join wait and the other attention work. Its size per pass is (est.):
    • 3.0 to 3.8 ms with 1 user
    • 9.6 to 10.4 ms with 8 users
  • The model holds the join wait fixed. The other attention work gets slower under Part B (last row of the factor table).

Join wait of a prefill pass

  • The join wait of a prefill pass grows far less than the kernel work.
  • From prompt 1,024 to prompt 8,192 the K tokens in full pages become 9 times as many. The join wait gets 1.1 to 1.6 times longer.
  • The model holds it fixed.

Check against a measurement

  • On delphi-3bda the same statistics were recorded for qwen-3-4b with the 128-wide kernel on and off [Ref23]. Each arm was one run with 8 users and prompt 1,024.
  • The kernel scored every K token of the full pages. It scored no K token of the pages that the pass wrote.
  • The busy time per pass got 1.88 times shorter. The join wait rose from 4.1 to 12.0 ms. This rise is already inside the measured ratio of 1.88 times.
  • The pass wall fell by 99.7 ms, and the busy time fell by 106.5 ms. So 94 % of the fall of the busy time appeared in the pass wall.
  • The kernel factor of that server is 2.95 to 3.05 (est.). With that factor, this model gives 1.90 to 1.93 times for our cell with 8 users and prompt 1,024 (est.). A factor on the whole busy time gives 2.95 to 3.05 times [Ref18].

How to read the prediction

  • With Part 0 alone, TTFT falls by 14 to 23 % (est.). The range is 8 to 26 %.
  • With Part A, TTFT falls by 18 to 29 % (est.). The range is 11 to 32 %.
  • At the working values Part A gives 4 to 6 percentage points more than Part 0 (est.). This difference is what AMX itself adds for GDN.
    • Part 0 then gives about 79 % of the fall that Part A gives (est.).
    • These values depend on the assumed clock of 2.40 GHz for the block kernel (clock note above).
    • In its low case Part A gives 3 to 5 percentage points less than Part 0 at its working value (est.). In that case the block kernel is no faster than the loop of Part 0. The lower core clock then also slows the rest of the pass.
  • With Part B, TTFT falls by 2 to 22 % (est.). The range is 1 to 26 %. The gain grows with the prompt length.
  • With Parts A and B together, TTFT falls by 30 to 41 % (est.). The range is 18 to 47 %.
  • The decode speed does not change at the working values (est.). The range is -5.3 % to +7.8 %. All of it comes from Part B.
  • The decode values are the weakest part of the prediction. They are based on measurements from delphi-3bda and on a clock ratio.

What would prove the prediction wrong

Part 0

  • The prediction is wrong if the measured GDN step on a 2.70 GHz thread is above 4.6 us, the low case. The estimate from the counts is 2.7 to 3.5 us.
  • A step between 3.5 and 4.6 us has three possible causes.
    • Hypothesis 1 is that the recurrence with the state in L1 takes more than 1.16 us per value head, the high end of the estimate. Then moving the state costs less today than the estimate assumes. Test: task 1 times the recurrence on one 32 KiB slice that stays in L1.
    • Hypothesis 2 is that the slice does not stay in L1. Test: task 1 also times the column-half order on the 128 KiB working copy. The difference between the two timings tests this hypothesis.
    • Hypothesis 3 is that the other work of the step takes more than 1.0 us, the high end of the estimate. This work is the convolution, the normalization, the rounding to bf16, the copies, the norm and the output gate. Test: task 2 separately times the copy into the contiguous buffer and back, the normalization and the other per-token work.

Part A

  • The prediction is wrong if the measured GDN step of the block kernel is not below the measured GDN step of Part 0. Then Part A adds nothing. The estimate is 1.7 to 2.5 us against 2.7 to 3.5 us.

The method

  • The test of the method is Part 0 against the base build. Part 0 uses no AMX. So no core clock changes.
  • On one serial path the pass wall then falls by the same time as the GDN wall, within the spread of repeated runs. If the pass wall falls by less, the layers do not form one serial path.
  • The spread is the largest minus the smallest pass wall of a cell. The 6 runs of section 2 give 0.2 to 0.5 ms with 1 user and 0.3 to 1.7 ms with 8 users [Ref18].
  • Both walls must come from the same kind of run. Either both come from counters of untraced runs, or both come from traced runs.
  • Part A alone cannot show whether the layers form one serial path. Its lower core clock also slows the rest of the pass (factor table, clock cost row of Part A). That clock cost must be subtracted from the fall of the GDN wall first.

Part B

  • The test is the A/B run of task 5. It gives the fall of the pass wall and the fall of the attention busy time. The prediction is wrong if the first fall is smaller than the second by more than the spread of repeated runs.
  • The hypothesis for this case is that the workers wait for K and V after the faster scoring. A longer join wait gives the same pattern. The timer of the open point on the wait for K and V separates the two.
The same data also show a finding that is not an AMX matter.
  • With 8 users the 16 GDN threads each run 8 chains, one after another, while 40 attention workers wait.
  • Spreading the 128 work items over all 56 threads would cut the GDN wall to about 3/8 of today's value (est.). This estimate comes from the work-item count.
  • In prefill with 8 users at prompt 1,024, the saving is about 100 ms of the 362 ms pass (est.).
  • In decode for the same cell, the saving is about 1.8 ms of the 8.1 ms step (est.). The GDN wall behind this value comes from a traced run. So the value can be too high or too low (section 3, limit of the decode numbers).
  • Spreading the work items needs a scheduling change, not a new kernel. It does not help 1 user.

5.2 Part 0: a chain path that keeps the state in L1 (no AMX, same bits)

  • Today the kernel passes over a 64 KiB matrix twice for each token [Ref3]. The matrix does not fit the 48 KiB L1 cache. So each of the two passes moves it between L2 and L1.
  • The new loop order uses one fact: each value column of S is its own recurrence. Column c depends only on the keys, the decay, the beta and column c of the values.
  • The new order splits each value head into two halves of 64 columns (32 KiB). It runs all tokens of the chain on one half, then on the other half. The half stays in L1 for the whole chain.
  • Each chain runs in three phases.
    • Phase 1 runs per token: convolution, normalization, decay and beta. It saves the results in a small buffer.
    • Phase 2 runs the recurrence over the chain, half by half.
    • Phase 3 runs per token: norm and output gate.
  • Each half is stored as one contiguous block of 32 KiB in a buffer of its own. In the layout of today's working copy, too many rows of a half need the same L1 positions (cache sets). The half would then not stay in L1 [Ref18].
  • The bits are unchanged. Every column sees the same operations in the same order.
  • No timing of this order on delphi-3b35 exists so far.
  • On another CPU (AMD Zen 5) a stand-alone copy of this order gave equal bits. It ran 1.46 to 1.74 times faster than today's order [Ref18]. The low case of Part 0 in section 4 uses this ratio.
  • Part 0 is in an AMX design for two reasons.
    • At the working values it gives about 79 % of the fall that Part A is predicted to give (est.). In its low case it gives about 43 % (est.).
    • It also builds the chain entry point and the per-token buffers that Part A needs.

5.3 Part A: the AMX block kernel

The block form and why AMX fits it

  • The idea is to process a block of 32 tokens at once. The state is then read twice and written once per block. Today it is read twice and written once per token.
  • AMX fits the block form. The three large products become matrix times matrix. A tile product then uses all 16 rows.
  • The block kernel needs 18.5 tile products and about 680 AVX-512 operations per value head per token (est. count). Today's kernel needs about 5,120 AVX-512 operations (est. count).
  • Three other programs that run this model use the same algebra.
    • Hugging Face Transformers uses this block form (block size 64) for every call with several tokens.
    • vLLM and SGLang include a CPU kernel that is built on the block form. Its matrix products call a library routine. A comment in that kernel says that the routine uses AMX bf16 products [Ref14].
  • The block size is 32 tokens. In the L1 cache model, the tile loads find 87 % of their cache lines in L1 with blocks of 32 tokens (est.). With blocks of 64 tokens the value is 40 % (est.) [Ref18].

The FP32 state

  • AMX has no tile product for FP32 inputs. Its floating-point tile products take 16-bit inputs: bf16, and fp16 on this CPU.
  • Each FP32 value is split into 3 bf16 pieces. The product is computed once per piece, and the 3 results are added [Ref18].
  • The sum of the pieces is exactly the FP32 value when its size is 2^-103 (about 9.9e-32) or larger. Section 5.4 gives the split rule and what is lost for smaller values.

Two stages in detail

  • Stage 1 takes 16 value columns of S0 (the state at the start of the block) at a time. AVX-512 code splits them into 3 pieces in a 12 KiB buffer that stays in L1. Then 48 tile products run on that buffer.
  • Stage 4 starts with AVX-512 code. It scales Delta (the 32 correction rows of the block) and splits it into 3 pieces.
  • Tile product 3 then builds the update in 16 parts. One part has 12 tile products and covers 64 key rows by 16 value columns. After each part, AVX-512 code writes the decayed start state plus the update for these values (64 FMAs).

  • The lengths leave out the cache lines from L2 of the table above. Those add 22 to 54 % to the cycles of a block (est.).
  • The final write of stage 4 has 64 FMAs per run. The short turn of the clock probe has the same count.
  • The clock of the AVX-512 runs is not measured either. The table uses the two clocks that the probe read under tile work.

5.4 Numerics: what changes and what the contract should say

  • Part 0 changes no bit of the result.
    • Each value column of S is its own recurrence. Part 0 runs the columns in two halves, with all tokens of the chain per half. Each column still sees the same operations in the same order.
    • Two independent scripts confirm equal bits for outputs and state. A stand-alone copy in AVX-512 code on another CPU confirms it too [Ref18].
  • Part A changes the order of the FP32 sums. It also applies the scale of the read step (figure 2, line 4) in FP32 after the tile products.
    • Part A applies the scale to the coefficients of the read sum. The token kernel applies it to q before the sum. The tile product needs q as a bf16 value, and scale x q is not a bf16 value.
    • The result is close to today's result, and it is not equal. Three numeric checks on synthetic inputs compared the block form with today's kernel. 0.005 to 0.10 % of the bf16 output words differ [Ref18].
  • The differences in the output words are small. An output above 1 % of the typical output size differs by one bf16 increment. Outputs nearer to zero differ by up to 67 increments [Ref18].
  • The error is of the same size as today's. The checks compare both kernels with a float64 computation.
    • The block form's output error is 0.3 to 1.1 times the error of today's kernel.
    • The block form's state error is 0.3 to 3.2 times today's [Ref18].
  • Long chains with a decay near 1 were checked too. After 1,024 tokens the two kernels differ by up to 33 FP32 increments in the state. Today's kernel is then 27 increments away from float64, and the block form 9 [Ref18].
  • The split rule makes the three pieces in four steps.
    1. The first piece is the FP32 value with the low 16 bits of its bit pattern cleared. This is truncation, which rounds toward zero.
    2. The remainder is the value minus the first piece.
    3. The second piece is the remainder with its low 16 bits cleared.
    4. The third piece is the remainder minus the second piece.
    Both subtractions are FP32 subtractions. tron's bf16 conversion rounds to nearest, and the split does not use it [Ref18].
  • The split is exact from 2^-103 upward.
    • Take an FP32 value of size 2^-103 (about 9.9e-32) or larger. Its three pieces are bf16 values, and their sum is the value. None of the three is a subnormal value.
    • This holds up to the largest FP32 value, 3.4028235e38. A script checked every finite FP32 bit pattern of both signs [Ref18].
  • Below 2^-103 the tile product reads some pieces as zero.
    • The second or the third piece can then be a subnormal value.
    • TDPBF16PS reads a subnormal input as zero. It also replaces a subnormal result by zero. So a piece can exist as a number and still be absent from the product.
    • A subnormal FP32 value is absent as a whole.
    • In every case the unread part of one value is below 2^-126 (about 1.2e-38) [Ref18].
  • Below 2^-110 an exact split does not always exist.
    • Every finite bf16 value is a multiple of 2^-133 (about 9.2e-41). An FP32 value below 2^-110 (about 7.7e-34) can have bits below 2^-133. No sum of bf16 values holds such bits.
    • The smallest positive FP32 value, 2^-149, is an example. The third piece then keeps its upper 16 bits, and the part dropped is below 2^-133.
    • From 2^-110 to 2^-103 the three pieces still add up to the value [Ref18].
  • Under the truncation rule every finite FP32 value gives three finite pieces. At the top of the range, round to nearest does not.
    • The largest finite bf16 value is 3.3895314e38. Round to nearest turns every value of size 3.3961775e38 (2^128 - 2^119) or larger into an infinite first piece. These are the 32,768 largest FP32 values of each sign.
    • The checks covered both rules up to the largest FP32 value [Ref18].
  • One of the three numeric checks above uses the truncation rule. The other two round every piece to nearest.
    • The first one also ran the round-to-nearest rule on the same inputs in 3 of its test cases.
    • Between the two rules, 0 to 56 of 131,072 bf16 output words differ.
    • The error against float64 with round to nearest is 0.99 to 1.13 times the error with truncation [Ref18].
  • Two pieces are not enough for the split. In the three checks their state error against float64 is 7.5e-8 to 1.6e-5. That is 5 to 227 times the error of today's kernel [Ref18].
  • Decay factors are built by multiplication only. Dividing two running products gives wrong results when the product becomes very small inside a block [Ref18].
  • The fallback of the block path is the column-half path of Part 0. A block takes it when its start state or an intermediate result is not finite. The state is still untouched at that point.
    • The column-half path has the bits of the token path.
    • One check found a case where the block form overflows and today's kernel does not [Ref18].
    • The split adds no fallback case. Under the truncation rule every finite value gives three finite pieces [Ref18].
    • Values below 2^-103 take no fallback. Their loss is part of the error band of the contract.
  • The existing tests require three things today.
    • The recurrence is checked with an absolute tolerance of 1e-7.
    • Other tests require equal bytes between the prefill path and the decode path.
    • One test fixes 320 output words to values from PyTorch (a machine-learning library) [Ref16].
  • No existing test runs the block path.
    • The equal-bytes tests and the test with 320 fixed output words use a small head. It has 16 key rows and 80 value columns.
    • The tolerance tests call the token kernel directly, one of them at 128 by 128 for 2 tokens.
    • So these tests never run a block path that is limited to chains on a 128 by 128 head. They stay unchanged.
    • The equal-bytes tests run chains of 2 or more tokens on the small head. So they will run the chain path of Part 0 at 16 by 80.
    • New tests of both paths at 128 by 128 are needed.
  • We propose this contract for Part A.
    • The block path stays within a stated error band of the token path.
    • The block path runs only for the 128 by 128 shape.
    • The block path runs only for full blocks of 32 tokens on a fixed grid of token positions.
    • The block path runs only when AMX is on.
    • The token path stays the reference.
  • The contract has two consequences to accept.
    • With Part A, prefill and decode of the same text can differ in rare output bits. Hugging Face Transformers has the same property. It uses the block form for prompts and the token form for single tokens [Ref14].
    • tron can resume a prompt from a stored state at any token position. If such a position cuts a block, the block runs on the column-half path of Part 0. So the GDN output of a resumed run and of a run from the start can differ in rare bits.
      • Today all GDN paths give equal bytes for equal inputs [Ref16].
      • The logits of a resumed request can already differ today. Its passes hold other numbers of tokens than the passes of a request from the start [Ref22].

5.5 Part B: attention kernels for 256-wide heads

  • Part B uses the same method as the existing kernels. K and V are bf16 already. No split is needed.
  • QK has 8 groups of 32 dimensions instead of 4, and they go into the same 4 result tiles. That is 32 tile products per query token, page and KV head. Today's 128-wide kernel has 16 [Ref6].
  • PV has 4 groups of output dimensions instead of 2. That is 32 tile products per query token, page and KV head. Today's kernel has 16.
  • The buffer of the packed queries of one token grows from 4 KiB to 8 KiB. The buffer of the PV output grows from 8 KiB to 16 KiB.
  • The eligibility check shape_ok accepts head width 256 with 4 query heads per KV head. The dispatch, the kill switch and the attention statistics work as today.
  • The numerics have the same two known differences from AVX-512 as today's kernel. The weights are rounded to nearest, and the sums are added in another order. The existing error-band tests extend to the new shape.
  • Each kernel call serves one query token. So 4 of 16 tile rows carry data, in prefill and in decode. Today's kernel has the same property.
  • The clock of this kernel is a hypothesis.
    • Section 4 assumes 1.90 GHz at the working value and 2.40 GHz in the high case. No probed turn has the mix of this kernel. Task 4 measures the clock.
    • The probe read 1.90 GHz for turns of 4 tile products and 64 FMAs. It read 2.40 GHz for turns of 4,096 tile products and 16,384 FMAs [Ref11].
    • One page unit has two tile runs. Their lengths are estimates from counts, with every load from L1.
      • The QK run has 32 tile products, 40 tile loads and 4 tile stores. That is 917 cycles: 0.38 us at 2.40 GHz or 0.48 us at 1.90 GHz (est.).
      • The PV run has 32 tile products, 40 tile loads and 16 tile stores. That is 1,110 cycles: 0.46 us at 2.40 GHz or 0.58 us at 1.90 GHz (est.).
    • When the 512 cache lines of K or of V come from L2, a run is 0.4 to 0.6 us longer at 2.40 GHz (est.).
    • AVX-512 work follows each tile run. After QK it turns the scores into softmax weights. After PV it adds the result to the running sums of the token.
    • No count of this AVX-512 work exists for the 256-wide kernel. With the 128-wide kernel on delphi-3bda, the softmax step took 0.08 to 0.11 us per page unit in decode (measured). There the update after PV took 0.07 to 0.17 us per page unit in decode (measured) [Ref19].
  • One risk is that the page does not fit L1. One page of a 256-wide head holds 64 KiB of K and V.
    • At 128-wide a page holds 32 KiB. That fits the 48 KiB L1 cache. So the page stays in L1 while the tokens of one prefill pass visit it.
    • The low case of section 4 covers this risk.
  • An optional later step for prefill is to serve 4 query tokens per kernel call.
    • Then all 16 tile rows carry data, and a page is loaded once per 4 tokens.
    • The bits equal those of the single-token AMX kernel.
    • This step is not part of the prediction.

5.7 What stays outside this design

  • AMX is not used for GDN decode. One token fills 1 or 2 of the 16 tile rows. Users cannot share a tile, because each sequence has its own state.
  • Decode has options that do not need AMX.
    • The check for invalid values reads the state before every token. The state part of this check could be done inside the first loop of the recurrence. This keeps the bits.
    • The gain is 1.1 to 1.2 times on the decode recurrence (est.). This gain holds for a cost of 1.8 to 2.96 cycles per cache line from L2 [Ref18].
  • A state stored in column halves could help decode more.
    • Together with the merged check, the gain is 1.2 to 1.55 times on the decode recurrence (est.). This gain holds for the same range of line costs [Ref18].
    • This option needs a new layout of the stored state. It is not part of this design.
  • 16 of 56 threads run GDN while 40 attention workers wait. Using all threads would cut the GDN wall of a prefill pass with 8 users to about 3/8 (est.). It changes the scheduler and the code generator, not a kernel.
  • A state stored in 16 bits is rejected.
    • A state in fp16 or in bf16 could be loaded into tiles without a split.
    • In a numeric check with synthetic inputs, 7 to 36 % of the bf16 output words change with an fp16 state. With a bf16 state, 32 to 81 % change [Ref18].

Open points

  • No timing of the column-half order exists for delphi-3b35.
    • On another CPU (AMD Zen 5) it was 1.46 to 1.74 times faster than today's order [Ref18]. That is below the 2 times that the counts predict.
    • Insufficient data for the size of the Part 0 gain on this CPU. Task 1 measures it.
  • The probe measured the core clock under AMX in stand-alone loops only, not in tron.
    • The probe covered two turns. The first has 4 tile products with 64 FMAs (35 ns per turn, 1.90 GHz). The second has 4,096 tile products followed by 16,384 FMAs (33 us per turn, 2.40 GHz).
    • Neither kernel has one turn length. The runs of the block kernel are in the second table of section 5.3. The tile runs of the attention kernel are in section 5.5.
    • The AVX-512 work of the attention kernel is not counted.
    • Insufficient data for the clock of either kernel. Tasks 3 and 4 measure it.
    • The clock of the other attention work under Part B is not measured either. A reading of the core clock of one attention worker during a prefill pass of task 5 would give it.
  • Insufficient data for the wait for K and V under Part B. tron has no timer for this wait alone.
    • A worker scores the full pages while K and V of the pass are produced. The AMX kernel of Part B may end this scoring before K and V are ready. Then the worker waits for them, and that part of the saving is lost.
    • The tron function run_attention_job runs one attention job on one worker. A timer around the wait for K and V in this function would give the missing value [Ref8].
    • The risk is largest at prompt 1,024, where the full-page time is 0.38 ms per layer with 1 user (est.).
  • The block kernel's cost model does not count two costs. Task 3 measures both. The low case of section 4 includes a margin for them.
    • A tile load right after an AVX-512 store of the same data waits until the data is written to memory [Ref21].
    • Small decay values put subnormal values into the AVX-512 parts. The CPU handles such values much more slowly.
  • On this server 3 of the 29 probed CPUs run at 4.00 GHz and 26 run at 2.70 GHz [Ref11]. All factors in section 4 are for 2.70 GHz threads. A server with another clock setup needs its own baseline.
  • Insufficient data for the CPU share of the rest of a prefill pass on the 16 GDN threads. This share decides how much a lower clock costs outside the kernel. A trace of the main thread with the matrix-multiply events turned on would give it.
  • The numeric checks used synthetic inputs, not the real value ranges of state, decay and beta in this model. A capture of the GDN inputs of one real prompt would give the size of the error band.
  • After a resume from a stored state, a chain does not always start on a block boundary. In that case a chain of 128 tokens holds only 3 full blocks.
    • Then 96 of its 128 tokens run in the block kernel. The other 32 run on the column-half path of Part 0.
    • The 6 cells of this page do not show this case.
  • The hypothesis in section 3 on the cause of the slow decode step is not confirmed. Either of two measurements would confirm or reject it:
    • a stand-alone benchmark of one decode step on a 128 KiB state that is outside the caches of the core
    • cache-miss counters on one GDN thread
  • The owners of the GDN code must decide two things for the numerics contract. Part 0 does not need these decisions. Part A does.
    • May prefill differ from decode in rare output bits?
    • May the GDN output of a resumed run differ from that of a run from the start? The logits of such runs can already differ today [Ref22].
  • The model's registry entry says that its tokens are not yet valid. The design should be checked again after the merge of the pull requests that add the model.
  • We did not read the design document of that series of pull requests. We could not open it.
