TL;DR

  • AMX is a per-physical-core matrix-multiply-accumulation unit. One instruction computes C[16×16] += A[16×32] × B[32×16] on bf16 data (fp32 accumulation) held in eight 1 KB tile registers.
  • Peak: 512 MAC/cycle/core - 8x AVX-512 BF16
  • The B operand must be stored in a pair-interleaved ("VNNI") layout
  • The OS must grant permission per process (arch_prctl). delphi-3bda has everything needed: AMX-TILE/BF16/INT8 and AMX-FP16, kernel 6.8

What AMX is

Introduction

Transplanted from 01-amx-rampup.html §1 + §1.1 (generator: exec/gen_distilled.py).

Advanced Matrix Extensions (AMX) is an x86 ISA extension (first shipped in Sapphire Rapids, inherited and extended by Granite Rapids) that adds two things to every P-core isa-extensions-progref:956-968:

  • A tile register file: 8 registers TMM0..TMM7, each up to 16 rows × 64 bytes (1 KB per tile, 8 KB total), described by a "palette" configuration sdm-vol-1:20752-20755. On the 6962P: 8 tiles × 1024 B, 16 rows × 64 B/row, TMUL max K=16, max N=64 B measured (CPUID leaves 1DH/1EH).
  • TMUL, a multiply-add grid (a dedicated array of fused multiply-add circuits, distinct from the AVX-512 vector FMA units) that executes tile-times-tile matrix multiply-accumulate instructions: C[M][N] += A[M][K] × B[K][N], operating only on tile registers (no memory operands) isa-extensions-progref:7089-7091, 7065-7066.

Configuration lifecycle

  • LDTILECFG [mem64] — loads a 64-byte configuration (per-tile rows/colbytes). Zeroes all tile data. Expensive: 204-cycle latency — issue once per kernel, not per loop iteration isa-extensions-progref:7067-7074; opt-manual:31310-31329.
  • TDP* — the multiply-accumulates (§2). Illegal (#UD) unless tiles are configured.
  • TILERELEASE — returns tiles to the INIT state. Strongly recommended when leaving an AMX region, and required by this plan's lifecycle policy: non-initialized tile state blocks deep core sleep states and carries power cost opt-manual:33771-33772; sdm-vol-1:20966-20971.

1.1 AMX and AVX-512 on the same core: what is shared, what is exclusive, how they collide

Yes — one physical core executes both at the same time. The out-of-order core keeps dispatching AVX-512 (and scalar) work while the multi-cycle TDP* instructions grind in the TMUL unit; Intel's own optimization guidance is to software-pipeline AVX-512 code between AMX tile operations, precisely because TDP* "utilize resources very lightly (1/2 of the available ALU ports, 1/TILE_M of the time)" opt-manual:32369-32381. The direct execution-unit cost runs one way: while the port-5 FMA is closed during TDP* execution, AVX-512 loses one of its two FMA ports, and the AMX frequency license lowers the whole core's clock. The local Intel references document no corresponding dedicated mechanism in the other direction; AVX-512's expected costs to AMX run through the shared front end, load/store ports, caches and power budget, and are workload-dependent rather than negligible. For tron this interaction is not hypothetical — the attention kernels interleave AVX-512 packing and epilogue code between TDP* operations, so every measured system gain in doc 02 and the status report already includes these costs.

Numeric behavior (matters for correctness tests)

  • All AMX float instructions: round-to-nearest-even, FP exceptions masked, MXCSR ignored isa-extensions-progref:7240-7252.
  • bf16 input denormals are treated as zero; fp32 outputs are flushed to zero; fp16 input denormals are honored (unlike bf16) isa-extensions-progref:7240-7252.
  • This matches AVX-512 vdpbf16ps semantics element-wise — but an AMX port of an existing vdpbf16ps kernel still changes the accumulation order (different reduction tree), so results are close but not bit-identical: plan for tolerance-based tests, not bit-equality.

The instruction sequence in practice (tron's kernels)

New for this document (jhan's question, 2026-08-31); code-verified in the PR worktree: src/tron/kernels/amx_attn.cpp (the only translation unit with tile intrinsics), self_attention.hpp:1380–1680; branch jhan-amx-p0 @ 60d66d9c04.

The table above lists the instructions one by one; this subsection shows the order in which a real kernel issues them. Typical AMX usage — and tron's attention kernels specifically — nests the instructions at four frequencies: an OS grant once per process, one configuration instruction per region, a zero → load → multiply → store cycle per matmul, and a release when the region ends. A region is the span between LDTILECFG and TILERELEASE; in tron it is one worker thread's whole loop over KV pages (a KV page is a 64-token block of the key/value cache). tron runs two matmuls per page: QK (the score matmul, S = Q·Kᵀ) and PV (the output matmul, O = P·V, where P holds the exponentiated scores). AMX has no elementwise instructions — the table above is complete: configure, load, store, zero, multiply-accumulate — so the arithmetic between the two matmuls (scaling, softmax) must leave the tile registers, run on AVX-512 (the CPU's ordinary 512-bit vector instructions), and re-enter through a fresh tile load.

  1. Once per process — the OS grant. Before any tile instruction, detect_and_request() (amx_attn.cpp:54–68) checks the TRON_AMX_DISABLE kill switch, CPUID leaf 7.0 (AMX-BF16 + AMX-TILE), and XCR0 bits 17:18 (the OS tile-state enable), then calls arch_prctl(ARCH_REQ_XCOMP_PERM, XFEATURE_XTILEDATA). The result is computed once and cached for the process lifetime (available(), :72–82). Measured cost: about 0.9 µs for the system call, plus a one-time 4–9 µs trap on each thread's first TILEDATA-touching instruction — a tile load, store, zero, or multiply; LDTILECFG alone does not trap (§6.4).
  2. Once per region — configure. begin_region() (amx_attn.cpp:84–92) fills a 64-byte tile_config struct (palette 1 — the only tile layout the ISA currently defines — with all 8 tiles set to 16 rows × 64 B) and issues LDTILECFG. tron calls it once before a worker's page loop (self_attention.hpp:1380), so the roughly 200-cycle cost (measured 182–216, §6.4) is amortized over every page the worker visits.
  3. Per matmul, first — clear the accumulators. TILEZERO clears the four fp32 accumulator tiles tmm0–tmm3 (e.g. amx_attn.cpp:243–246); no memory traffic. Four accumulators give the multiplier four independent dependency chains. Intel's timing table (the Throughput section below) recommends ≥3–4 such chains to cover the 52-cycle latency of TDPBF16PS (written TDP below); the §6.4 microbenchmark measured no added stall even on one dependent chain, so on the 6962P this is Intel guidance, not a measured requirement.
  4. Per 32-dim reduction step — load operands. TILELOADD fills the operand tiles: one load of the operand all four TDPs in the step share (the packed Q group in QK, the bf16 P rows in PV; tmm4 in the figure), then four loads of the per-block KV operand, one per accumulator — in QK the K-mirror panels (a panel = one 16-token × 32-dim block of the page's pair-interleaved K copy; the mirror flavor is defined in the note after this list), in PV the V pair-rows. Each load moves up to 1 KB as 16 row reads of 64 B through the ordinary cache hierarchy (8.4 cycles/load measured L1-hot, §6.4). The KV loads alternate between two tiles (tmm5/tmm6 in the figure) so a load never overwrites the tile a still-in-flight TDP is reading.
  5. Per step, interleaved with the loads — multiply. TDPBF16PS accumulates C += A · B into each accumulator tile in turn (16×16×32 = 8192 multiply-accumulate operations (MACs) per instruction; 16.2–16.4 cycles/op measured back-to-back). In QK each accumulator holds one 16-token block of the 64-token page; the step loop is amx_attn.cpp:249–263.
  6. Per matmul, last — store the result. TILESTORED writes each accumulator tile to an ordinary fp32 buffer: the 16×64 score block s after QK (amx_attn.cpp:264–267), the 16×128 output o after PV (:225–228). A tile store is the only way results leave the tile file.
  7. Between the two matmuls — AVX-512, inside the region. The softmax arithmetic (scale, running max, exp — the streaming-softmax update of the per-worker (m*, s*, v*) scratchpad described in the Decode architecture section) runs on AVX-512 against the stored s rows (self_attention.hpp:1642–1657), and the PV kernel packs the resulting exp rows to bf16 pairs (P, amx_attn.cpp:190–199) before they re-enter as the next A tile. The tile configuration stays loaded throughout — mixing vector and tile instructions needs no fence or reconfiguration (§6.4).
  8. Region exit — release. end_region() issues TILERELEASE (self_attention.hpp:1480), returning the tile file to its INIT state so context switches can skip saving the 8 KB TILEDATA (§6.2); about 15 cycles measured.

Instruction counts, counted from the kernel loops. One QK call (one 64-token page × one GQA group — the query heads that share one KV head, four of them in the geometry these kernels serve, per the kv_mul = 4 gate of the Supported geometry section) issues 44 tile instructions: 4 TILEZERO + 20 TILELOADD + 16 TDPBF16PS + 4 TILESTORED (amx_attn.cpp:241–268). One PV call issues 52: 8 + 20 + 16 + 8, because the 128-dim output is produced in two 64-dim halves (:201–229). With the loads overlapped, the 16 TDPs bound each call at roughly 16 × 16.2 ≈ 260 core cycles (est., from the §6.4 back-to-back measurements).

Operand roles per build flavor: the mirror QK kernel (qk_mirror_128x4) uses zero-padded Q rows as A and the page's VNNI (pair-interleaved) K-mirror panels as B, so C is S = Q·Kᵀ directly — the tile assignment the figure shows. The canonical QK kernel (qk_canonical_128x4) swaps the roles — the K page as stored is A (alternating through tmm4/tmm5), the VNNI-packed Q group is B (tmm6) — producing Sᵀ, which an AVX-512 transpose then flips (amx_attn.cpp:151–180); its tile-instruction sequence and counts are identical. PV uses the figure's assignment in both flavors. Q is packed once per (token, KV head) and reused across all pages of the region (self_attention.hpp:1426–1447).

VNNI B-operand layout

Transplanted from 02-tron-decode-amx-plan.html §2b (generator: exec/gen_distilled.py).

The bf16 dot-product instructions (AVX-512's VDPBF16PS and AMX's TDPBF16PS) never multiply single numbers — the smallest unit they consume is a pair of adjacent bf16 values: each fp32 accumulator lane takes two matching reduction-axis values from each operand and adds both products at once. For a matrix used as the B operand, those two values must appear side by side in the pair-interleaved ("VNNI") layout; the A operand needs only ordinary row-major adjacency along its reduction dimension. Doc 01 covers the instruction-set view; this section shows what it means for tron's data, with example numbers.

Reading panel 2 (two common stumbles): First, the P values are attention weights — the softmax outputs of the QK step ("this new token attends 50% to t0, 25% to t1") — not model parameters; no model parameter appears anywhere in this kernel. Second, the pair (0, 10) in the C[d0] line is dim d0 of two different tokens, and adding them into one accumulator is not a mix-up: the PV output at each dim is defined as a sum over tokens, O[d0] = P[t0]·V[t0][d0] + P[t1]·V[t1][d0] + …, so the instruction step is adding two consecutive terms of that sum (0.50×0 + 0.25×10), and the next step adds the (t2, t3) terms. Blending tokens per dim is exactly what attention's weighted sum does.

What plain row-major V would compute (why the interleave is mandatory): the bf16 units reuse the fp32 datapath, so the hardware never addresses a lone 16-bit value — it reads 32-bit lanes, and its per-lane contract is fixed: C[lane] += A.lo×B.lo + A.hi×B.hi, with both halves of a B lane feeding the same accumulator and no stride or gather mode to change that. Store V plainly (one row per token) and t0's first lane holds (V[t0][d0], V[t0][d1]) = (0, 1); the instruction would blindly compute C[lane0] += 0.50×0 + 0.25×1 = 0.25 instead of 2.50 — token t1's weight applied to token t0's d1 value, and a d1 value accumulated into d0's output — silently wrong in every lane, no fault raised. The layout is the only way to tell the instruction what the reduction pairs are. Geometry says which operand needs the fix: the bf16 reduction is 32 deep but a tile has 16 rows; A's reduction axis runs along its row, so consecutive pairs are already adjacent in memory, while B's reduction axis runs down the rows, so a consecutive pair straddles two logical rows — software must fold rows 2k and 2k+1 into one physical row beforehand, and that fold is the pair-interleave.

The rule that makes sense of it: in these dot-product layouts, each pair is two adjacent elements of the reduction axis. In the B operand's pair-interleaved layout, PV (which sums over tokens) therefore pairs adjacent tokens, while QK (which sums over dims) pairs adjacent dims when K is the B operand. tron's V is already stored token-paired (it was designed for VDPBF16PS), which is why the AMX PV kernel consumes it with zero repacking. K is stored plain, so the canonical kernel sidesteps the requirement by making K the A operand — at the price of the transposed output (§4b) — while the mirror formulation pays with the pre-paired K copy instead.

A common misreading, spelled out: "K became the A operand, so does Q get token-paired?" No — token pairs never appear in QK at all. Tokens and queries are the output axes of QK; only dims are summed away, so every pair in QK is a dim pair. K's dim pairs come free (a stored K row is 128 contiguous dims — enough for an A operand); Q's must be built, because the B layout wants each query's two dim values side by side per dim pair. Example with Q[query][dim] = 100·query + dim: the packed B row for dim pair (d0, d1) reads (0,1) (100,101) (200,201) (300,301) — one bracket per query — and one instruction step computes S[t5][q] += K[t5][d0]·Q[q][d0] + K[t5][d1]·Q[q][d1] for all four queries at once (with the K row (50, 51, …): q0 gets 50×0 + 51×1 = 51). The pack is cheap because Q is tiny (4×128 per GQA group) and packed once per (token, kv-head), reused across every page; K is the big per-page operand — which is exactly why the canonical design rearranges Q and not K.

What the hardware consumes. As the panel above says, the smallest unit TDPBF16PS eats is a PAIR of adjacent bf16 values: per step, each fp32 accumulator lane takes one 32-bit element (= two adjacent bf16) from A and one 32-bit element (= two adjacent bf16) from B, and adds both products at once. A's pairs come free — its reduction axis runs along the row, so (1, 2) and (3, 4) are already adjacent in memory. B's reduction axis runs down a COLUMN: the value that must pair with the 1 in column 0 is the 2 one row below — four elements away in row-major storage. So B is stored with conceptual rows 2k and 2k+1 zipped together: stored row k holds, for every output column n, the pair (B[2k][n], B[2k+1][n]) side by side:

The instruction's walk for C[0,0] (all four output columns run simultaneously, each lane using its own pair from the SAME stored row):

  • step k=0: A pair (1, 2) × stored-row-0 pair (1, 2) → 1·1 + 2·2 = 5
  • step k=1: A pair (3, 4) × stored-row-1 pair (3, 4) → 3·3 + 4·4 = 25
  • sum: 30 — the conceptual dot product, completed in two pair steps.
The trap the Scratch page hit. Its stored bytes were RIGHT — read linearly, a correctly interleaved stream is exactly the stored rows above. The wrong number comes from then multiplying that stored block as if it were an ordinary matrix: reshape the eight pairs into a 4×4 scalar matrix ([1,2,8,16] / [64,128,512,1024] / [3,4,24,32] / [192,256,1536,2048]) and dot A's row against its first column, and you get 1·1 + 2·64 + 3·3 + 4·192 = 906 ≠ 30. The stored tile is not the original logical 4×4 scalar matrix: physically it has two rows of four 32-bit pair lanes, so reshaping its eight bf16 pairs into an ordinary 4×4 scalar matrix and dotting a stored scalar column applies the wrong interpretation. Its logical meaning is defined by TDP's pair consumption along the reduction axis. The interleave exists precisely so that the ONE stored row the instruction reads per step carries, for all output columns at once, the two B values that multiply A's next two elements.

Scale note: the toy has K=4, so 2 stored rows of 4 pairs; a real tile step is K=32 (16 stored rows of 64 bytes, 16 pairs each), and a 128-dim reduction chains 4 such steps. In tron's data this pairing is over the reduction axis of each GEMM: V pairs adjacent TOKENS (the PV reduction), and the K mirror pairs adjacent HEAD DIMS (the mirror-QK reduction) — the two panels above.

4b. The transpose in practice (addendum 2026-08-19): optimizations, measured cost, and the alternative that removes it

Section 4 is the consensus-v2 design, frozen as reviewed. This addendum consolidates what P0–P2 then learned about the transposing store, which was previously scattered across the results pages and status entries.

  • Why a transpose exists at all: with the canonical orientation (D1, Sᵀ = K·Qᵀ), the C tiles hold scores as 64 token rows × Nq query columns, but the epilogue (max/exp over the 64-token axis) needs them as Nq rows × 64 columns. The mirror orientation avoids this by consuming a pre-interleaved K copy instead (see the last bullet).
  • Optimization 1 — width-specialized transposing store (shipped in increment 1): a full 16×16 fp32 lane transpose takes two stages (stage 1: unpacklo/unpackhi at 32-bit then 64-bit granularity per 4-row group; stage 2: shuffle_f32x4 combinations). At the guaranteed decode width 4, only output rows 0–3 are needed, so only their output-specific stage-2 paths are emitted — a quarter of the full transpose's stage-2 paths, while the shared stage-1 work remains (qk_canonical_128x4, src/tron/kernels/amx_attn.cpp). The first transpose implementation had a wrong permutation; the harness's runtime self-check against a scalar reference caught it, which is why the harness runs that self-check for every kernel variant.
  • Optimization 2 — merged transpose + scale (harness only): the P0 harness merged the softmax scale into the transposing store (one combined pass). The in-tree increment 1 deliberately kept the store UNSCALED with the existing epilogue untouched, trading a little speed for a byte-identical scoring epilogue.
  • Optimization 3 — pipelined double-buffering (measured, rejected): hypothesis was that the tile-store → vector-load round-trip stalls the transpose; alternating score buffers across an 8-page ring improved throughput by only ≈2% (982 vs 1006 ns/page at width 4; an unsaved run, recorded only in exec/QUEUE.md), showing the store→load round trip was not the dominant bottleneck under these measured conditions; the variant was not adopted.
  • The measured floor: the best experimental canonical result in the grid remained ≈560 ns/page slower than the mirror kernel at width 4 in the saved grid v2 (1250 vs 686 ns, fused-sweep.html); the pipelined variant's unsaved 8-page-ring run narrowed that to ≈300 ns (982 vs 686; an earlier note said ≈200 ns — arithmetic corrected 2026-08-19; provenance corrected 2026-08-25). The canonical path's transpose and score-memory round-trip are expected to account for much of this gap, but the end-to-end kernel comparison does not isolate their exact contribution. The layout mismatch is inherent to this orientation under the current epilogue contract, although its implementation cost may still be reducible; eliminating the reorientation requires changing the formulation or the downstream contract.
  • The remover — the mirror formulation (increment 2): S = Q·Kᵀ read from a VNNI-interleaved K copy needs no transposing store at all (the formulation originates from Bill's PR #2934; the implementation and numbers are ours). Precision

Transplanted from 02-tron-decode-amx-plan.html §6b (generator: exec/gen_distilled.py).

This section answers a review question from Jeremy: do AVX and AMX use different floating-point formats, and if so what does the AMX plan do about it? Short answer: both attention dot-product implementations use bf16 operands with fp32 accumulation, so no datatype conversion is needed to move QK/PV from AVX-512 BF16 to AMX-BF16 — there is no format mismatch to bridge. For ordinary finite values, the expected numeric differences between the two arms are one rounding-mode choice and the fp32 reduction order (details and caveats below). This section also corrects an earlier claim of ours (in the increment-1b notes) that the AVX PV path multiplied with fp32 weights — it does not; it rounds them to bf16 too.

What tron's two attention paths actually compute

  • AVX QK: the dotter multiplies bf16 Q against bf16 K with VDPBF16PS (_mm512_dpbf16_ps, dotter.hpp:167, 218), accumulating fp32.
  • AVX PV: scaled_v_expr converts the fp32 softmax weights to bf16 by truncation — a 16-bit right shift that simply drops the low mantissa bits (kv_cache.hpp:1795–1800) — interleaves them into pairs, and multiplies against the bf16 V with VDPBF16PS (kv_cache.hpp:1678, 1682), accumulating fp32.
  • AMX QK/PV (increments 1 and 1b): TDPBF16PS on the same bf16 K/V data; the PV weights are converted fp32→bf16 with VCVTNE2PS2BF16, which rounds to nearest even (RNE) instead of truncating; all accumulation fp32 in the tile registers.
  • Everything around the multiplies (scale, softcap, max, exp, the deferred-softmax v*/s*/m* updates) is the identical fp32 code in both paths.

Plain words: bf16 has 8 bits of significand precision (7 stored fraction bits plus the implicit leading bit). Within one power-of-two range, adjacent representable values are spaced about 0.78% of that range's base apart ("1 ULP"). Chopping the low 16 fp32 bits rounds toward zero — for these nonnegative weights that means downward — with error below 1 ULP. Round to nearest even picks the nearest representable value, with error at most 0.5 ULP for ordinary finite values, and avoids truncation's systematic downward tendency. (The AVX conversion, _mm512_srli_epi32(..., 16), is a bit-level chop, not an IEEE conversion instruction.)

The resulting A/B differences and the decision

  • Numeric deltas between the AVX and AMX arms — for finite, non-subnormal inputs and identical softmax update sequencing and padding: (1) the PV-weight conversion (chop vs RNE); (2) fp32 accumulation/reduction order (non-associative; this heading also covers VDPBF16PS's two-product grouping vs the tile FMA topology). Exceptional and subnormal behavior (DAZ/FTZ, NaN/infinity) is outside this comparison and should be ruled out or tested separately in T1.
  • Measured effect (t1-quick, 2026-08-18, greedy + seeded + --pay-for-determinism; control: two AVX runs byte-identical): AMX output byte-identical at prompt 8192; one argmax flip about 20 tokens in at prompt 2048, after which the continuations diverge by construction. One prompt per context — a sample, not a verdict. The P0 harness observed a worst-case relative error of 8×10-5 on the normalized outputs (denominator floored at 10-3) against its scalar reference on the tested cases — an observation, not a proven bound. Note the reference itself rounds the softmax weights to bf16 (amx_fused_bench.cpp:439, matching all fast paths), so that figure measures the score-path and reduction-order effects, not the weight quantization.
  • Decision (2026-08-19, approved by jhan): keep RNE — the locally more accurate conversion for ordinary finite values — and let the formal T1 logit-tolerance test judge both arms against an fp32 reference (T1 should compare pre-sampling logits with a predeclared absolute-plus-relative criterion; byte-identical generated text is a nondeterminism check, not an accuracy test). If T1's owners prefer minimum divergence from the shipped AVX behavior instead, switching the AMX conversion to the same chop is a one-line change in weights_times_v_128x4, making the PV weight operands bit-identical between the arms; for the tested finite, non-subnormal domain the remaining expected numerical delta would be the reduction order.

Reading "latency / throughput": the two columns count different things. In Intel's table, latency is the number of cycles from an instruction's start (its operands ready) until its result can be used by a dependent instruction — the result-to-consumer delay. Throughput is reciprocal throughput: the minimum number of cycles between starting two independent instructions of the same kind — the sustained repeat interval. The two differ because the unit is pipelined: one TDPBF16PS takes 52 cycles to produce its C tile, but a new TDPBF16PS may start every 16 cycles as long as it writes a different C tile. 52 ÷ 16 ≈ 3.25, so by Intel's numbers ≥4 independent accumulator tiles are needed to keep the multiplier busy; the kernels in this PR cycle four (tmm0–tmm3, §"The instruction sequence in practice"). On the 6962P even one dependent chain measured no stall (the TDPBF16PS bullet below), so the four accumulators are Intel's guidance plus headroom, not a measured requirement here.

What the measured column is. The benchmark (exec/bench_amx_overhead.cpp) runs one instruction in a tight loop and divides total cycles by iterations, with a null-loop baseline subtracted. That is a repeat-interval measurement — a throughput-style number, because the loop lets consecutive instructions overlap — and where Intel publishes a throughput it matches: TILELOADD 8.4 vs 8, TDPBF16PS 16.2–16.4 vs 16, TILESTORED 16.1 vs 16 (TILEZERO is discussed in the closing paragraph). It is not a latency measurement. Two rows still say something about latency:

  • TDPBF16PS: the tdp_lat mode chains every TDP through the same C tile — a deliberate dependency chain, the standard latency probe — yet it also measured 16.2–16.4 cycles/op. So the effective C→C dependency completes in ≤16 cycles, consistent with internal forwarding of the accumulator. On this reading, Intel's 52 cycles would be the delay to other consumers of the result (for example TILESTORED reading C); this suite did not measure that path, so 52 remains the published number, not a confirmed one.
  • LDTILECFG: its back-to-back repeat interval measured 182–216 cycles (4 of 5 reps at ~182) — the same magnitude as Intel's published 204-cycle latency, and about 11% below it (the published table is Sapphire-Rapids-era, so the 6962P's own latency may be nearer 182). An interval this close to the latency means consecutive LDTILECFGs gain little or nothing from pipelining — each applies the configuration, which also zeroes all tile data isa-extensions-progref:7127 — so for this non-pipelined instruction the repeat interval and the latency roughly coincide.

Latency and the memory hierarchy; the "—" cells. For the memory-touching instructions, a fixed published latency must assume a fixed cache level; Intel does not state which, and the usual convention is a first-level hit — our own TILELOADD measurement was taken L1-hot. A miss adds the ordinary L2/L3/DRAM latency on top, which the table does not model. TILESTORED writes into the DCU (the Data Cache Unit — the first-level cache) opt-manual:31300-31310. Intel marks the remaining cells "Not Relevant" without giving reasons; our reading: TILESTORED has no latency entry since no register-side instruction consumes a store's result, and the three configuration instructions (LDTILECFG, STTILECFG, TILERELEASE) have no throughput entry since a real kernel issues them once per region rather than in a stream. TILEZERO's published throughput of 0 is conventionally read as the zeroing being handled before the execution units; we measured 0.50 cycles/op — two per cycle — consistent with that reading rather than a literal 0.

Crossing between AMX and non-AMX instructions. Three separate seams, with different verdicts on this machine:

  • Data seam, tile store → vector load.   • Issue seam, port-5 closure. A common worry: "AMX is power-hungry, and running it lowers other cores' frequencies." What Intel actually documents is more specific, in three parts.

(1) The frequency license is per-core, and its class ladder puts AMX at the bottom. Each core independently runs at a max frequency set by the "license" class of the instructions it is executing opt-manual:3868-3870 (Figure 2-7):

Within a class, the ceiling depends on how many cores are in that class: "The more cores belonging to a category at any given time, the lower the maximum frequency" opt-manual:3865-3867. And Intel states the cross-class scope explicitly: when cores enter a license level, the PCU "adjusts their frequency as necessary, potentially lowering the frequency. Cores that execute at other license levels are not affected" opt-manual:3917-3920. So via the license mechanism, AMX on the attention workers does not throttle scalar/AVX cores — but every additional AMX-active core can pull down the ceiling of the other AMX-active cores.

What we measured on delphi-3bda measured: in the P0 frequency/power capture, one core running either of the two AMX benchmark variants recorded there (amx44, amxqk) held 3.59 GHz vs 3.89 GHz for the AVX-512 variant (≈8% license clock cost), with package power flat across all three (223.8–226.3 W, ~13 s sustained per variant) (exec/results/slot1/p0c-freq-power.txt, 2026-08-18). At service scale — 8 users / 8K context, two-socket system total — the busy-clock cost was ~4% and package power moved +0.3% (arena-mirror) to +1.6% (canonical) against the AMX-off binary (exec/results/t4/t4-power.txt). The per-core split this section's takeaway asks for — APERF/MPERF on non-AMX cores while attention workers run AMX — remains unmeasured.

(2) The documented cross-core path is the shared package power budget. The manual notes that some workloads are power-limited and never reach their license's max frequency at all (its example: LINPACK "is power limited and does not reach the processor's maximum frequency" opt-manual:3931-3934). Package power (PL1/PL2) is shared by all cores, so a power-hungry AMX workload on many cores can, through that budget, reduce frequency for everything on the socket — including the FPGA-serving threads on the same socket. The manual documents the phenomenon, not an AMX-specific cross-core magnitude: on our platform this is a labeled hypothesis to measure, not a known number.

(3) The transition dynamics and the mitigating factors. License grants take up to 500 µs (the core runs at reduced capability meanwhile) and a ~2 ms timer holds the lower frequency before recovery opt-manual:3917-3922 — an argument for dedicating cores to AMX rather than sprinkling short AMX bursts across many cores. Below 15% AMX-unit utilization the core may exceed the nominal AMX-license ceiling opt-manual:31289-31291 — likely our regime, since decode attention issues TDPs sparsely between loads and softmax work. And lower frequency does not mean lower performance: Intel's own example shows AVX-512-heavy DL workloads gaining 1.3–1.5× over AVX2 versions despite the frequency drop opt-manual:3936-3939.

How to measure it on delphi-3bda (folded into doc 02's P0/T4): per-core license residency via CORE_POWER.LVL0/1/2_TURBO_LICENSE PMU events opt-manual:3873-3877; per-core effective clock via APERF/MPERF on non-AMX cores (main helpers, FPGA driver threads) while attention workers run AMX; package power via RAPL. Caveats: this section's mechanism is documented on Skylake Server and the AMX chapter defers to it (§20.2.1 → §2.6.3); Granite Rapids license-bin magnitudes are absent from the local refs, and SDM Vol 4's Xeon 6 P-core MSR table lists no AMX power/frequency MSR — so GNR numbers must be measured, not looked up.

What the PR actually changes

The one design fork you need to know: the QK multiply can read K two ways. Canonical-K (the default) reads K exactly as stored today — free, but the scores come out sideways and need a small transpose. The mirror (opt-in, TRON_AMX_K_MIRROR) keeps a second, pre-rearranged copy of K in a separate memory arena so no transpose is needed — faster at long context, at the cost of extra ordinary RAM (≈50% of the KV cache's size, allocated at cache setup only when mirror support is built AND the runtime AMX check passes) and more moving parts. Generating the mirror is cheap and measured: 70 ns per token-row on this machine (≈20 µs per prefill token across 36 layers × 8 heads, spread over the driver workers — and the system-level A/B shows prefill still nets +1–2% ahead of a build with no mirror writes at all; on decode it is ≈0.3–0.4% of a step). Both are in this PR; deep details with figures: doc 02 §2b (the data layouts) and §4b (the transpose).

Canonical vs mirror: one page iteration in each QK formulation

New for this document (jhan's request, 2026-09-01); code-verified in the PR worktree ~/workspace/tron-amx @ 60d66d9c04: src/tron/kernels/amx_attn.cpp, self_attention.hpp:1568–1683, the notes [Mirror orientation] and [K mirror parallel arena]; not a transplant (generator: exec/gen_distilled.py).

The PR ships two kernels for the score matmul (QK) and one kernel for the output matmul (PV). Both QK kernels compute the same 64 × 4 scores for one page and one GQA group; they differ in which matrix is the tile multiply's left operand (A, plain row-major) and which is the right operand (B, which must be in the VNNI pair-interleaved layout). That choice decides whether the result comes out sideways.

  • Canonical-K (default). A = the K page exactly as stored (64 token rows × 128 dims, loaded as 4 row blocks of 16 tokens), B = the query group packed into VNNI pairs (a 4 KB buffer, packed once per query per pass and reused for every page). The 4 result tiles hold Sᵀ = K · Qᵀ, 64 token rows by 16 columns of which 4 are real query heads. The kernel stores them to a stack buffer and an AVX-512 shuffle network transposes them into the 4 score rows the softmax code expects amx_attn.cpp:115–176. That transpose is the "transpose 64×4" box of the earlier figure.
  • Mirror (build option TRON_AMX_K_MIRROR). The 4 result tiles hold S = Q · Kᵀ (rows = query heads, columns = tokens) and are stored straight into row-major score rows; the 4 real rows are then copied contiguously into s_pages (1 KB), no transpose amx_attn.cpp:236–268; self_attention.hpp:1575–1589. If the arena is absent (allocation failed, AMX unavailable, kill switch), the page falls through to the AVX-512 dotter, not to canonical-K.
  • P·V, identical in both. The design figure's "6+2" was the Intel-manual blocking (6 result tiles + 1 A + 1 B, then 2); the shipped 4+4 keeps 7 registers live and double-buffers the V tile (decision D4, amx-design.md). The TDP count is the same either way.

Deep-dive: the mirror layout

Transplanted from 2026-08-19-amx-status.html §4 + pr-rampup.html §4.3 (generator: exec/gen_distilled.py).

4.1 Why the mirror layout exists (design motivation)

The canonical AMX kernel computes scores sideways and must transpose them back — a structural cost of roughly 300 ns per page that cannot be removed within that orientation (doc 02 §4b has the full story with figures). The mirror formulation removes the transpose entirely by keeping a second copy of K, pre-arranged the way the AMX tiles want to read it; measured at equal layout, the mirror kernel decodes ≈14% faster than the canonical kernel. The first implementation put that copy inside each KV block — the simplest correct design: one allocation, one offset table, and the single single page-move code path keeps it coherent through defragmentation. The price of that simplicity is the layout below. (Bill's PR #2934 places its mirror the same way, inside each KV block — verified in its source — so this penalty class is expected to apply to it as well, though that was never measured on his models. The separate-arena fix in §4.3 is new to both implementations.)

4.2 The experiment: proving the layout alone is the penalty

The suspicious observation: the mirror build ran slower even with AMX switched off and zero mirror writes happening. Zero writes rules out write bandwidth — but not the cause. So a control build was made: the 3-plane layout with none of the mirror code (no writes, canonical kernels). If the control reproduces the slowdown, the layout alone carries it.

4.3 The plan to remove the penalty

  • MEASURED the same day (increment 3 built and A/B'd; A7 tests pass on the new design): prediction (a) CONFIRMED — the fallback penalty is gone (kill-switch arm within ±1.3% of the clean binary on three workloads, +3.3% on the fourth) and the kill switch is a true rollback again; mirror memory is now allocated only when AMX actually runs. Prediction (b) REFUTED — the AMX arm is unchanged (within ±1.1% of the in-block mirror): the ≈9% "layout tax on the AMX path" belonged to the canonical kernel reading through fat blocks, and the mirror kernel's own access pattern never paid it. Increment 3's value is safety and capacity economics, not extra speed. And the capacity economics turned out better than first framed: the arena allocates from ordinary RAM (32 GB here, on a 1.58 TB machine), not from the hugepage budget that sets the KV page count — so the arena build's page capacity EQUALS canonical's. Verified at the edge: both binaries admit 48 users at prompt 8192 (≈58 of the 64 GB page budget) with zero failures, where the old in-block design would have stopped near 36; the arena-mirror is +6% aggregate even there.
  • What stays the same: save_k writes through to the mirror at the same single site; page moves rebuild it at the same single code path (copy_storage_slot); the byte-equivalence tests carry over.
  • What it costs: a second allocation and offset table, and the mirror arena must grow/shrink with the book — the added complexity the first design avoided. That trade is now justified by measurement.

4.3 Why keep two copies of K instead of just storing K transposed? (Bill's question)

The mirror stores a second, rearranged copy of K next to the original. A fair question: why not store K in the rearranged form once and drop the original? tron already does exactly that for V — V is stored in the tile-friendly interleaved form natively, every consumer reads it that way, and V needs no mirror. The difference is that V has one layout every reader wants, while the original K layout is a shared interface with three consumers that need the row form:

What replacing would actually save, honestly: (a) the arena's memory — about half the KV cache's size in ordinary RAM (≤32 GB on this machine's 64 GB KV configuration, out of 1.58 TB installed — small next to both budgets, though its traffic and placement are still real; the scarce DMA page budget is untouched: in the measured capacity probe, both builds admitted 32 and 48 users at prompt 8192 with no failures); (b) the mirror's moving parts — the allocation/lifetime plumbing and null-check fallbacks, the defrag rebuild, the two-copy consistency invariant across writes and page moves, and the byte-equivalence tests that guard it all; (c) almost nothing on the write side — the 70 ns/token-row scatter would remain as the primary K store, replacing only a cheap contiguous row write.

So the two copies are not an accident: the original K plane is the interface the FPGA and every narrow/partial CPU case consume, and the transposed plane is a private view for one kernel. Replacing rather than mirroring is a cross-stack layout migration (FPGA contract, new narrow-width CPU kernels, loss of the rollback) purchased with savings the arena design already made small relative to the machine's memory and page budgets. The V cache shows when replacement is right: when every consumer wants the rearranged form. If a future card consumed transposed K natively — or an FPGA-free build existed — this question should be reopened.

4.4 Why no K transpose was needed before AMX (jhan's question)

New for this document (jhan's question, 2026-08-24); code-verified in the PR worktree: self_attention.hpp:1568–1589, dotter.hpp:176, model.hpp:2784.

§4.3 raises a follow-up: software attention computes S = Q·KT and existed long before AMX — so where was the K transpose then? Was it done on the FPGA when the FPGA did the matmul, sparing the CPU? No, on both counts: the pre-AMX CPU path never materialized a transposed K, and the FPGA is not the reason. The transpose in Q·KT exists only on paper — a dot-product kernel absorbs it in its loop order:

In code: the fallback loop (self_attention.hpp:1568) visits stored tokens in storage order; each iteration reads ONE K row — token i's key, 128 contiguous bf16, exactly as the save path wrote it (model.hpp:2784) — and computes one dot product against q (:1586 reads the row, :1588 writes the score). dotter<bf16,128> keeps q in four 512-bit registers for the whole page and issues four contiguous 64-byte loads plus _mm512_dpbf16_ps per row. Row i of K is column i of KT; writing the result into s[i] is the entire transpose, performed by the loop index at zero data movement.

Why the FPGA cannot be the explanation:

  • Disjoint work. With hardware attention on, the CPU computes scores only for the queries the query mask marks software-required (§4.2, next section) — and it computes those scores entirely by itself, from the K pages in the KV cache. No intermediate result flows from the card back into the CPU's QK arithmetic.
  • One-way, byte-for-byte traffic. The card receives the row-form K pages verbatim over DMA (§4.3: the layout is a hardware contract; gof.hpp:33, full.hpp:2382). Whatever rearrangement the card's internal matmul dataflow uses happens inside the card, is not observable from the host, and changes nothing for the CPU path.

So the correct history: before AMX, no consumer ever paid for a K transpose — the FPGA reads K rows as a byte contract, and every CPU kernel folds the transpose into its loop index for free. TDPBF16PS is the first consumer in the stack that needs the transpose to exist as bytes in memory, because a tile instruction loads whole tiles from consecutive addresses and has no loop order to hide the transpose in. That is the entire reason the mirror (§4.3) exists — and why nothing like it was needed before.

The cost of maintaining the mirror

New section (2026-08-24), answering a review question; not a transplant (generator: exec/gen_distilled.py).

The mirror adds two things: one arena allocation at book construction, and one additional destination-row write for every stored K row. The end-to-end suite shows no observed net slowdown. The accounting has three parts, and only one of them recurs:

  • Allocation: once, at startup. When AMX is available, the mirror arena is allocated once as ordinary RAM (kv_bytes/2) at KV-book construction, before any request is served (kv_cache.hpp, maybe_allocate_mirror_arena; on non-AMX hosts and under the kill switch nothing is allocated). No allocation, resize, or free occurs on the serving path, so there is no steady-state allocator work at all.
  • Reads: nothing else changed. This is the parallel arena's whole point (§“Deep-dive” above): kv_block keeps its dense 2-plane K+V layout, so every pre-existing consumer — the AVX fallback, the FPGA's DMA reads, the kill-switch path — touches exactly the bytes it always did. Measured: the kill-switch arm of the mirror binary runs at clean-binary speed (−1.3..+3.3%) exec/results/t4/p2-inc3-arena.txt.
  • The write: the only recurring cost. Every stored K row is scattered once into the mirror. The rest of this section prices that write.

Where the write runs, and what it costs. The write-through sits on the per-card driver RX workers — the threads that run DMA-completion callbacks (rope_k, save_k, save_v) when the card finishes a group of K/V rows. The scatter runs inside save_k, immediately after the canonical K store, while the source row is still L1-hot — avoiding an expected lower-cache or DRAM refetch. The recurring work writes one scattered 256-byte destination row per (layer, KV head, token); the isolated benchmark includes that scatter's source loads and destination stores. Measured in isolation: 70.9 ns per row (five retained repetitions across two otherwise idle cores, range 70.8–71.0 ns; one 107.7 ns interference result recorded separately while serving remained active) exec/results/bench-scatter-20260824.txt. Per token that is 36 layers × 8 KV heads × 70.9 ns ≈ 20.4 us serial-equivalent: about 2.2% of the derived 942.6 us prefill wall per token. Applied mechanically to the measured single-user decode-step durations, the same 20.4 us serial-equivalent work is approximately 0.2–0.4% of a decode step (estimate, not measured added latency).

Q (jhan): is the write hidden by pipelining or concurrency?
Some of it may overlap, but this experiment does not quantify how much. RX callbacks execute on workers distinct from the FPGA and the CPU compute workers, so their work can run concurrently with other activity, and the writes are spread across the per-card RX workers. The scatter itself is not deferred: it is a plain synchronous store inside save_k, placed there deliberately because that is the moment the K row is L1-hot (see Note [K mirror coherence] in kv_cache.hpp), and the RX callback remains on the per-layer critical chain — so the write is not hidden by construction. The robust explanation is its small measured size (a 0.567 us tick in a 26.2 us slot), potentially aided by ordinary pipeline concurrency; the 20.4 us per-token figure is aggregate serial-equivalent work, not a prediction of 20.4 us added wall time, and the system A/B below determines the net effect.

The system A/B is the ground truth for net serving performance in this suite — not for the write's standalone contribution. Because the mirror build also changes the QK kernel, the A/B cannot separately measure how much mirror-write latency reaches wall clock; what it establishes is the net result. Among the tested modes, prefill has the highest K-row write rate (prompt tokens are processed much faster, so the write is a larger fraction of elapsed time), and even there the integrated mirror build shows no observed net regression: it parses prompts faster than the write-free canonical build in every tested cell — +46.7% vs +44.9%, +105.2% vs +102.7%, +43.6% vs +41.3%, +100.0% vs +90.4% over clean at 1u/2K, 1u/8K, 8u/2K, 8u/8K (3 reps/cell, no prefill confidence intervals captured) exec/results/t4/t4-suite.txt. Decode shows the same net picture (+19.7% vs +15.3% at 1u/8K, 95% CIs excluding zero exec/results/t4/t4-reps.txt).

Why the arena never grows

New section (2026-08-24), answering a review question; not a transplant (generator: exec/gen_distilled.py).

A natural reading of "the KV cache grows as tokens arrive" suggests the mirror must grow with it - and raises the question of whether scatter_k_mirror allocates memory for each new row. Neither happens, because growth works differently than the premise assumes: each KV-cache book is a fixed-capacity allocation, and the mirror arena is sized to that same fixed capacity when the book is built.

  • Each book is a fixed pool, allocated at its construction. The book constructor allocates DMA memory for its full page capacity in one call; n_pages is fixed for the book's lifetime (kv_cache.hpp: "The capacity of this book in pages. Does not change during the lifetime of the book"). As tokens are added, the book's occupancy grows within storage allocated at construction; the K/V arena never resizes. Cache-level growth, when needed, happens by creating additional fixed-capacity books (try_create, the "cache growth" factory in kv_cache.hpp), and allocation failure there is handled by the higher-level KV-OOM path (the t/t_kv_oom_* tests).
  • The mirror arena gets one capacity-sized allocation attempt per book. During each book's construction, after the fixed-size K/V arena has been allocated, the constructor calls maybe_allocate_mirror_arena once: if amx_attn::available(), it attempts a single non-throwing allocation of kv_bytes / 2 - one mirror plane for EVERY (storage slot, KV head, page) the book could ever hold, occupied or not. If that allocation fails, the arena stays null and consumers fall back. A kv_block is two equal-sized planes (K + V) and its mirror is one plane - hence exactly half of kv_bytes.
  • Where a new row lands is pure address arithmetic. The k_mirror_data accessor delegates to book::mirror_at_storage (kv_cache.hpp), which computes a pointer into the existing mirror arena: mirror_arena_.get() + byte_base + (kv_head * n_pages + pg) * plane_bytes - the same fixed slot/head/page addressing the canonical planes use inside arena_data.
  • scatter_k_mirror is stores only. Its whole body computes destination offsets inside the supplied plane and writes one row: head_size / 2 bf16 pairs = 2 * head_size bytes (for a 128-dim head: 64 pairs, 128 bf16 values, 256 bytes). It is noexcept, performs no allocation or other fallible resource operation, and - given the valid plane and row pointers its callers null-check before invoking it - only computes offsets and stores; that is what makes it suitable for the RX worker's DMA-completion callback (write site 1 of Note [K mirror coherence]). The mirror arena's entire heap lifecycle is one aligned allocation attempt per book construction and one matching aligned delete at destruction - the pairing t/t_amx_arena_leak.cpp pins.

token ranges the FPGA serves they never reach the CPU; there is nothing to accelerate

Practical size: for qwen-class models (no window layers), the CPU's share in FPGA-attention mode is just those early-position queries, so the AMX contribution there is small. The measured +15–28% decode gains are for the all-software operating mode (USE_HW_ATTN=0), where every page is CPU work. No extra code is needed for the mixed mode — it composes as-is, and the kill switch behaves identically in both.

Testing trap (we hit it during T1): the page rule above applies to any test, in any mode. A run whose total length — prompt plus generated tokens — stays under 64 never completes a page, so AMX never engages: both arms run the identical AVX code, an A/B shows nothing, and a numerics comparison "passes" without ever testing the AMX path. The repo's canned 21-token prompts do exactly this. Any meaningful test must push the total sequence past 64 tokens (the measured campaigns use prompt 2048 and 8192).

Q (jhan): does this mean the AMX solution needs no change when hw_attention is enabled?
Yes — no code change is needed. The AMX dispatch sits inside the software page loop, and that loop runs in BOTH modes: hardware mode still routes part of the work to it (positions below 127, sliding-window and software-only layers, hw-ineligible configurations), and every full, fully-visible page inside that subset takes the AMX path exactly as in all-software mode (self_attention.hpp: run_visible_in_software, the dispatch has no uses_hw check). What DOES change is the payoff, not the code: all measured end-to-end gains (+15–28% decode) are from all-software mode; in hardware mode the CPU's share of attention is smaller, so the end-to-end effect of AMX is proportionally smaller and has not been measured separately.

4.1 The attention geometry we support — exactly, and which models have it

The fast path engages only when the model's attention has one exact shape. The whole gate is one line of compile-time arithmetic plus the runtime CPU check (h/tron/models/self_attention.hpp):

constexpr bool amx_shape_ok = geometry.kv.head_size == 128 && geometry.kv_mul() == 4;
const bool amx_on = amx_shape_ok && amx_attn::available();

In plain words: each attention head must be 128 numbers wide, and exactly 4 query heads must share each stored K/V head (kv_mul() is that sharing ratio; modern models store fewer K/V heads than query heads to shrink the KV cache). Why this exact shape: one query group of 4 heads × 128 numbers = 512 bf16 values = 1,024 bytes; the kernel packs those as 16 rows × 32 values — exactly one full AMX tile (16 rows × 64 bytes), no padding waste. The kernel names carry the shape: qk_canonical_128x4, weights_times_v_128x4, qk_mirror_128x4.

Is tensor-parallel (tp1/tp2/tp4) part of the geometry? No. The gate reads two compile-time model constants (head width, sharing ratio). The tp mode is a separate build parameter that decides how work is split across FPGA devices; it changes neither constant (and it divides query and K/V head counts by the same factor, so the ratio could not change anyway). A model passes or fails this gate identically at tp1, tp2, and tp4.

4.1.1 Why the kv_mul 3 / 5 / 8 models are not served — and what would break if the gate were simply forced open

From the nightly-CI list, llama-3.2-3b (3 query heads per K/V head), qwen-2.5-32b (5) and llama-3.3-70b (8) all have 128-wide heads but fail the kv_mul() == 4 half of the gate. As shipped, nothing fails on them: the gate is compile-time (if constexpr), so for these models the AMX branch is not even compiled into their plugin instantiation — they run the unchanged AVX path (that is the measured "ineligible shape" class: gpt-oss showed −0.3..−1.6%, run-to-run noise).

The interesting question is what the gate is protecting against. The *_128x4 kernels hard-code the number 4 in three load-bearing places: the Q pack reads exactly 4 consecutive query heads starting at kv_head × kv_mul × 128; the tile kernels compute exactly those 4 rows; and the epilogue writes exactly scratchpad entries sp[kv_head × 4 + offset], then returns early so the AVX loop never revisits the page. Run that machinery on a group that is not 4 heads wide and, per geometry:

  • kv_mul 3 (llama-3.2-3b): the 4-head window reads one head PAST the group — the next K/V head's first query is scored against the wrong K/V data (silently wrong attention), and for the last K/V head the pack reads past the end of the query tensor while the ×4 epilogue stride writes scratchpad slots 28–31 of a 24-entry array: out-of-bounds read AND write, i.e. memory corruption, not just wrong numbers.
  • kv_mul 5 (qwen-2.5-32b): the window covers 4 of the 5 heads; the 5th head is never computed — and because the AMX branch returns early, the AVX loop never fills it either, so 1 in 5 heads remains uncomputed and its scratchpad entry is not updated. From the second group on, the ×4 stride (correct would be ×5) lands every update on the WRONG head's scratchpad entry: in-bounds, silent, wrong.
  • kv_mul 8 (llama-3.3-70b): half of every group is skipped, and the ×4-vs-×8 stride mis-addresses every group after the first. (This shape could use TWO full query tiles rather than one, but it requires a width-8 kernel variant and a generalized stride — it cannot be enabled by loosening the shape check.)

That is the design point: the gate makes the unsupported case impossible by construction rather than checked at runtime, and the failure modes above are why widening support means new per-width kernels plus a kv_mul-derived stride (the planned actual-width bucketing), never just deleting the check.

Q (jhan): we found the two gpt-oss models can work with AMX after some changes. From a pure KV-head-width point of view, is that a similar solution to llama-68m and llama-3.2-1b, which have the same head width (64)?
Partially. The shared part: all three have 64-wide heads, so they would share the head-64 kernel family (qk/pv_64xN: a K row is 128 B, a 64-token K page is 8 KB, and the reduction runs over 64 dims instead of 128). The part that is NOT shared is the guaranteed decode width, which is the query-heads-per-KV-head ratio (kv_mul) — it decides how many of the 16 tile rows carry real work in private decode:
  • gpt-oss-20b/120b: 64Q/8KV, head 64 → kv_mul 8; one GQA group = 8 × 64 = 512 bf16 = a FULL tile operand — the same "tile identity" as today's 4 × 128 shape, full utilization. This is why the gpt-oss port is worth doing (new kernels + 2 gate sites; sinks and sliding windows already need zero AMX changes — code-verified in gptoss-estimate.html).
  • llama-3.2-1b: 32Q/8KV, head 64 → kv_mul 4; a group fills only 4 × 64 = 256 bf16 = HALF a tile operand — the same kernels would run with half the rows as padding, so at best half the AMX utilization of the gpt-oss case (h/tron/plugins/llama.hpp:1539).
  • llama-68m: 12Q/12KV, head 64 → kv_mul 1 (no grouping at all); guaranteed decode width 1 sits BELOW the measured AVX crossover (Nq=2), so the dispatcher would correctly leave private decode on AVX — not a candidate (h/tron/plugins/llama.hpp:1531).
So: one shared head-64 kernel family, three different payoffs — full-tile for gpt-oss, half-tile for llama-3.2-1b, none for llama-68m private decode (prefill and shared-prefix batching, where width comes from token count rather than kv_mul, could still engage for the small llamas).

Terminology for the numbers

Transplanted from 01-amx-rampup.html §0 (generator: exec/gen_distilled.py).

The performance claims in this document (and in docs 02–03) are stated in a small set of units. Definitions, in the order you will meet them:

TermMeaning
MAC (multiply-accumulate)One operation of the form c = c + a × b — a multiply and an add, fused. It is the basic work unit of matrix math: a matrix multiply C[M×N] += A[M×K] · B[K×N] performs exactly M·N·K MACs — each of the M×N output elements is a sum of K products (M, N, K are defined two rows down). One MAC counts as 2 floating-point operations (flops).
MAC/cycle/coreHow many MACs one CPU core completes per clock cycle at peak. Reading the TL;DR line with this: one max-shape TDPBF16PS instruction performs 16×16×32 = 8192 MACs — that is M=16 output rows × N=16 output columns × K=32 bf16 values summed per output element (a tile row is 64 bytes = 32 bf16) — and a new one can retire every 16 cycles, so 8192 / 16 = 512 MAC/cycle/core. Multiply by the clock to get a rate: at the ~1.89 GHz AMX clock measured in the PoC microbenchmark, 512 × 1.89·10⁹ ≈ 968 GMAC/s ≈ 1936 GFLOPS for one core.
FMA (fused multiply-add)The hardware circuit — and instruction family — that executes one MAC as a single operation d = a × b + c with one rounding step (the "fused" part). MAC is the operation you count; FMA is the unit that runs it, one MAC per lane per cycle. A P-core has two kinds of FMA hardware: (1) two 512-bit vector FMA units — in Intel's documented port model behind issue ports 0 and 5, the second one present "on some parts", with no 6962P-specific port map in the local refs (§1.1) — which run AVX-512 instructions like vfmadd* and vdpbf16ps; (2) the TMUL, which Intel defines as "conceptually a grid of fused multiply-add units able to read and write tiles" isa-extensions-progref:7086-7088 — a separate, dedicated array, not the vector units reused. Same technology, different silicon. To keep the two kinds of hardware apart, this document reserves plain FMA for the AVX-512 vector units and calls TMUL's internal array the multiply-add grid. What they do share: the port-5 issue slot (in that documented model), the load ports, and the core's power/frequency budget — while TDP* instructions execute, the CPU usually closes port 5's vector FMA "to conserve power" opt-manual:32519-32523, so concurrent AVX-512 FMA throughput halves (port 0 only). There is one TMUL per physical core, shared by both hyper-threads; each hyper-thread has only its own private tile-register state.
fused / kernel fusionRunning several pipeline steps as one combined pass, so intermediate results stay in registers or cache instead of being written to memory and read back between steps. A "fused-page benchmark" times all per-page steps together (pack, matrix multiply, transpose, softmax, multiply-by-V, accumulate) rather than the matrix multiply alone — which matters because the surrounding steps are often where the time goes. "Fuse the transpose into the softmax" = do the transpose as part of the softmax step instead of as its own pass. Note this is a different "fused" than the one in FMA above (there it means multiply+add with a single rounding).
cycleOne tick of the core clock. A 2 GHz core has 2·10⁹ cycles per second. Costs of individual instructions are quoted in cycles because the clock frequency varies (see "frequency license", §7.2).
flop / GFLOPSOne floating-point operation / 10⁹ of them per second. 1 MAC = 2 flops (the multiply and the add).
throughput vs latency (of an instruction)Throughput here means reciprocal throughput: the number of cycles between starting consecutive independent instructions of that kind — "TDP* throughput 16" means a new tile multiply can begin every 16 cycles. Latency is how long until one instruction's own result is ready (52 cycles for TDP*) — the gap between the two is why a kernel keeps several independent accumulator tiles in flight.
M, N, KThe three dimensions of a matrix multiply C[M×N] += A[M×K] · B[K×N]: M = rows of A = rows of the output C; N = columns of B = columns of the output C; K = the shared inner dimension (columns of A = rows of B) — the contraction (reduction) dimension that gets summed away. Each output element C[i][j] = Σk A[i][k]·B[k][j] costs K MACs, and there are M×N output elements — hence M·N·K MACs total. In the attention kernels of doc 02, the "query width" lands on N for the Q·K score computation (transposed formulation) and on M for the P·V computation.
GEMM / GEMVGeneral matrix–matrix multiply / matrix–vector multiply. GEMV is the M=1 degenerate case — the shape where AMX wastes most of its grid (§7.1).
arithmetic intensityFlops performed per byte of memory traffic. Low intensity means the kernel is limited by memory bandwidth no matter how fast the math units are; high intensity means the math units are the limit. Decode attention is ~4 flops/byte — low.
tok/s, TPS, TTFTTokens per second (the end-to-end serving metric; "prompt/parse" = prefill phase, "generation" = decode phase); TTFT = time to first token.

Canonical-K / mirror-K
Our own shorthand, not a standard term. Canonical-K = K stored the way tron stores it today: one copy, original layout, byte-for-byte unchanged; the canonical kernel reads those existing bytes directly (and therefore needs the transposing store, §4b). KV block layout / layout penalty
"Layout" = how one kv_block (the storage unit for one layer-slot × kv-head × 64-token page) arranges its data planes in memory. Default: two planes, K then V (32 KB at head 128), blocks packed back-to-back. The mirror build adds a third plane (the rearranged K copy) inside each block (48 KB). The "layout penalty" is the slowdown from that fatter arrangement by itself: pages sit 1.5× farther apart and a 16 KB plane the AVX path never reads sits between every K and V, breaking hardware prefetch streams. Proven by a layout-only control build (3-plane blocks, zero mirror code) that reproduced the mirror build's fallback penalty exactly, with decode-phase counters showing LLC-load misses 50.8%→84.6% and TLB misses ≈0 in both arms (rampup/p2-inc2.html, "The costs").
