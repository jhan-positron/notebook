Response to R1-47 — Claude for jhan, 2026-08-25 (not part of the review): agree in part

What the comment points at. cpuid_bit(leaf, reg, bit) (h/system/mwaitx.hpp:22) runs CPUID for one leaf (sub-leaf 0) and tests one bit of one register. is_rtm_supported (src/system/mwaitx.cpp:36–55) is a lazy<bool> = “CPU reports the feature (cpuid_bit(7, ebx, 11)) and the env kill switch is not set (TRON_NO_RTM, exact match strcmp(v, "1") == 0)”, evaluated once. detect_and_request() here does four things: the env switch (TRON_AMX_DISABLE, first-character test — R1-48), CPUID 7.0 EDX bits 22/24 through its own inline asm, XGETBV to read XCR0 bits 17–18 (the OS has enabled tile state), and arch_prctl(ARCH_REQ_XCOMP_PERM, XTILEDATA) — a per-process permission request with a side effect; available() caches the result in a function-local static (:71–80).

Where he is right. Steps 1 and 2 are exactly the RTM shape: the CPUID test is cpuid_bit(7, cpuid_register_edx, 22) && cpuid_bit(7, cpuid_register_edx, 24) — one existing helper instead of a second hand-written cpuid asm — and the env parse should be the house rule strcmp(v, "1") == 0 (which also settles R1-48). Including system/mwaitx.hpp from amx_attn.cpp has precedent (h/tron/threading.hpp, h/tron/tensor/tensor.hpp) and pulls in only <atomic>, <cstdint>, <vector> and common/assert.hpp, common/attributes.hpp, common/util.hpp; the interface header stays intrinsics-free because the include goes in the .cpp. Two CPUID executions instead of one is nothing — it runs once per process. The once-only caching can be the same lazy<bool> or the function-local static already there; they are equivalent.

Where the whole-function replacement stops. Steps 3 and 4 have no counterpart in mwaitx: RTM needs no OS-enabled register state and no per-process permission, AMX needs both (and arch_prctl must be issued before the first tile instruction). So the probe can reuse cpuid_bit but cannot be a lazy<bool> over cpuid alone — which is the “or say why the AMX probe can't” half of his ask: one comment line saying exactly that. A bonus the RTM code shows: log_capabilities() (mwaitx.cpp:59) announces the probe result at INIT, loudly when the kill switch is on; the same one line for AMX (“enabled / disabled by TRON_AMX_DISABLE / unsupported”) would answer the silent parts of R1-48 and R1-21.

// src/tron/kernels/amx_attn.cpp - sketch, not applied
#include "system/mwaitx.hpp"  // cpuid_bit, the same probe helper is_rtm_supported uses

static bool amx_disabled_by_env() {  // same rule as TRON_NO_RTM: exactly "1"
  const char* v = std::getenv("TRON_AMX_DISABLE");
  return v != nullptr && std::strcmp(v, "1") == 0;
}

bool detect_and_request() noexcept {
  using namespace tron::hardware::mwaitx;
  if (amx_disabled_by_env()) return false;
  // CPUID 7.0 EDX: bit 22 AMX-BF16, bit 24 AMX-TILE.
  if (!cpuid_bit(7, cpuid_register_edx, 22) || !cpuid_bit(7, cpuid_register_edx, 24))
    return false;
  // The next two have no helper: unlike RTM, AMX needs the OS to have enabled
  // the tile state (XCR0 bits 17:18) and a per-process permission request.
  unsigned xlo, xhi;
  __asm__ volatile("xgetbv" : "=a"(xlo), "=d"(xhi) : "c"(0));
  if ((xlo & (3u << 17)) != (3u << 17)) return false;
  return syscall(SYS_arch_prctl, ARCH_REQ_XCOMP_PERM, XFEATURE_XTILEDATA) == 0;
}

Verdict. Agree on reusing cpuid_bit and the env-parse convention; disagree that the function is “the same shape” end to end — the two OS/process steps are the reason it cannot be, and the fix is to reuse the two parts that match and say so in one line. Small, mechanical; I can apply it.

Decision (jhan, 2026-08-25): ignore. Refactor, not a bug fix; the probe stays hand-written. Recorded in PR3879/triage.json as R1-47: ignore; the next round will show this item under “declined by the author” with his predicted reply rather than re-raise it.

What R1-48 means — explanation for jhan, Claude, 2026-08-25 (not part of the review)

The line. if (off && off[0] == '1') return false; (amx_attn.cpp, inside detect_and_request()) reads TRON_AMX_DISABLE and looks only at its first character. What he asks. Not a new parser — only that this switch follow one of the two conventions the tree already has, so an operator learns one rule for every TRON_* switch: exact-match "1" (src/system/mwaitx.cpp:36–39 for TRON_NO_RTM; src/system/memory.cpp:38–39 documents the same rule for TRON_USE_ARENA_ALLOCATOR: “Env "0" (or any non-"1" value) forces legacy”) or numeric atoi as for USE_HW_ATTN. The nearest sibling is TRON_NO_RTM — also a benchmark/emergency kill switch on a CPU-feature probe — so exact-match "1" is the natural pick, and it is what the R1-47 sketch above uses.

What it does not fix, and the cheap way to close it. As the table shows, none of the three rules turns =true into “off”; the convention buys consistency, not protection from a typo. The RTM precedent handles that at INIT: log_capabilities() prints whether the feature is enabled, and prints a loud block when the kill switch is active. One log line for AMX (“AMX attention: enabled / disabled by TRON_AMX_DISABLE=1 / unsupported on this host”) makes any mistaken value visible in the first lines of every run. Related: R1-16 asks the Note to say the switch is “not 1” rather than “not set”, and the t_amx_logit_ab recipe already uses =1 / =0, which every rule above treats the same way.
