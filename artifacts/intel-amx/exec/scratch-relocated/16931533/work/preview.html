Was AMX boosting all models? What the nightly CI measured, 2026-09-15 to 2026-10-04

delphi-3bda (Intel) and andoria-b1a3 (AMD) nightly System CI perf rows, 20 nightly runs per machine (19 AMD runs with data), read from the GitHub Actions run logs. Written 2026-10-05 (UTC). Generator and data: exec/ci-poll-20261004/.

Short version

No. Since 09-23 the Intel machine is faster on every row, every gain is a step that has held every night since, and the data show three separate causes.

AMX explains one gain, the llama-3.1-8b 32-user row (+15 % decode, the same as our own on/off test), and the AMD machine on the same packages gained nothing on that row. The other large gains (qwen-3-4b tp4 +18 %, gpt-oss-120b +13 %, llama-3.3-70b tp4 +4 %, median change) arrived in the same first AMX package, two of them on FPGA-attention rows that the AMX kernels do not serve, with the wait-counter removal (#4534) and Bill's FPGA-join change (#4258) as the candidates. The broad +1 to +2.5 % step of 09-29 on the other nine rows matches no tron merge, and its most likely cause is a new FPGA bitfile activated on the machine that night (not yet confirmed, section 6.3).

Words used here

tron, rinzler, engine
tron is the inference program under test. rinzler is its production server binary. An engine is one rinzler server process that owns a set of accelerator cards. The nightly installs rinzler from a Debian package (.deb) built from tron's main branch.
nightly, System CI
the automated test run of the positron-ai/systems_test repository. It starts at about 03:30 UTC every night, installs the newest tron package and runs a fixed list of performance rows on each test machine.
delphi-3bda, andoria-b1a3
the two test machines. delphi-3bda has two Intel Xeon 6 6962P processors (Granite Rapids), which have AMX. andoria-b1a3 has AMD Genoa processors, which have no AMX. Both machines carry the same accelerator cards and run the same package every night.
AMX, AMX kernels
AMX = Intel Advanced Matrix Extensions, the matrix unit in Xeon 6 processors. The AMX kernels are tron's attention code that uses that unit. The .deb build option TRON_AMX_DISPATCH compiles them in. They serve only models with head size 128 and 4 query heads per KV head, and only when attention runs on the CPU. TRON_AMX_DISABLE=1 is the environment variable that turns them off at run time.
FPGA, FPGA card, bitfile, platformd
FPGA = field-programmable gate array, the chip on each accelerator card. "FPGA card" and "accelerator card" mean the same thing here. A bitfile is the firmware image loaded into the FPGA. It ships in the Debian package archer-ia860m. platformd is the daemon that manages the cards. It writes a new bitfile into the cards only at the next card bring-up (a platformd restart), not when the package is installed.
FPGA attention, CPU attention
FPGA attention = attention computed on the accelerator cards. PR titles call it "HW attention". In the nightly, qwen-3-4b, gpt-oss-120b, gemma-4-31b and Muse-Glimmer-30B run FPGA attention. The AMX kernels do not run for them. CPU attention = attention computed on the CPU. PR titles call it "software attention". The llama, mixtral, qwen-2.5 and gemma-2 rows run CPU attention.
package
one tron .deb, named by build date and the first 8 characters of the source commit, for example 2026.09.23-5cf65b92. That one is the first package with the AMX kernels. It was installed on the night of 09-23 (UTC).
merge, #NNNN
one pull request merged into tron main, named by its number. Merge times on this page are GitHub's merge timestamps, in UTC.
row
one performance measurement of the nightly: a model, a tensor-parallel split and a user count, for example "qwen-3-4b tp4, 8 users". tp2 / tp4 = the model is split over 2 or 4 cards. A tp2 row runs 4 engines of 2 cards, a tp4 row runs 2 engines of 4 cards. The users are spread over the engines.
decode TPS
decode speed, generated tokens per second for one user. The harness averages the per-request samples of the row (320 samples for a 32-user row, 80 for an 8-user row, 40 for a 4-user row).
TTFT, prefill rate
TTFT = time to first token, in milliseconds. Prefill rate = prompt length divided by the mean TTFT, in tokens per second (tok/s). It is the harness's own number. With several users per engine it includes the wait behind other users' prompts.
pre window, post window
pre = the nightlies from 09-15 to 09-22 UTC (8 on Intel, 7 on AMD), all on packages without AMX kernels. post = the 12 nightlies from 09-23 to 10-04 UTC, all on packages with AMX kernels. All dates are the UTC date on which the perf rows ran. In Pacific time the run belongs to the previous evening.
median change, night step
two kinds of percent change appear on this page. Median change = the post-window median vs the pre-window median (Figures 1, 3, 4, Table 1, section 1). Night step = one night vs the night before it (Table 2, section 2, section 4, section 6). The two differ when a row stepped twice.
median, CV
median = the middle value of the nights in a window. CV = coefficient of variation = standard deviation divided by the mean, in percent. A low CV means the nights agree with each other.
step, rise, fluctuation
a step is a change that appears on one night and stays on the following nights. A rise is a change that later reverts. A fluctuation comes and goes from night to night.
A/B test
a paired run of the same build with one setting changed, for example the AMX kernels on and off, so that the difference measures that one setting.
thresholds
the minimum decode TPS a row must reach, or the nightly reports a failure. They are stored in systems_test and raised by hand when a row is faster for a while.

1. Did several models get faster on the Intel machine after 09-22? Yes, in two groups

Figure 1 compares the median decode speed of the 12 post nights with the median of the pre nights, for every row and both machines (median change).

The Intel rows fall into two groups.

  • Group A, large gains on four rows. qwen-3-4b tp4 +18.3 % (147.45 to 174.40 TPS), llama-3.1-8b 32 users +15.4 % (28.25 to 32.61 TPS), gpt-oss-120b tp4 +12.8 % (107.54 to 121.33 TPS), llama-3.3-70b tp4 +4.2 % (30.24 to 31.52 TPS). Three of the four are tp4 rows. Only one of the four, llama-3.1-8b 32 users, is known to run the AMX kernels. That row was added to the nightly as the AMX benchmark. Our own same-code A/B test of 2026-09-20 measured +14.0 % on it [CI-test/status/CI-merges-20260923.html, Figure 1]. qwen-3-4b and gpt-oss-120b run FPGA attention in the nightly. The AMX kernels are therefore not on their main path. llama-3.3-70b has the head shape the AMX kernels serve, so AMX is not excluded for its tp4 row. Its tp2 rows, same model and same CPU attention, moved by +0.1 % and -0.1 % on the 09-23 night while tp4 moved +3.2 %. That argues against an AMX effect on the tp4 row, but it is not proof.
  • Group B, small gains on the other nine rows. +1.2 % to +1.6 % on seven rows (llama-3.1-8b 8 users, llama-3.3-70b tp2 at 4 and 8 users, mixtral, qwen-2.5-32b, gemma-2-9b, qwen-3-4b tp2) and under +0.7 % on llama-3.2-3b and gemma-4-31b. None of these runs the AMX kernels. Two of them, qwen-3-4b tp2 and gemma-4-31b, run FPGA attention. Section 2 shows that this group did not move on the AMX night at all. It moved six nights later.

So the answer to "did AMX boost most models" is no. One row has a measured AMX gain. Two rows have large gains that AMX cannot explain. One row has a gain that AMX is unlikely to explain. Nine rows have small gains that arrived on a different night from the AMX package.

2. Consistent or fluctuating? Step changes, then flat

Figure 2 shows every night. Each line is indexed to its own machine's pre-window median, so both machines share one axis and the percent change can be read directly.

The gains are consistent, not fluctuating. The numbers:

  • Group A stepped once, on 09-23. qwen-3-4b tp4 went 148.67 to 172.12 TPS between the 09-22 and 09-23 nights and stayed between 172.12 and 176.72 for all 12 post nights. gpt-oss-120b tp4 went 109.70 to 118.91 and stayed between 118.91 and 123.60. llama-3.3-70b tp4 went 30.37 to 31.33 and stayed between 31.20 and 31.85. The AMX row went 28.25 to 32.49 and stayed between 32.43 and 32.78.
  • Group B stepped once, on 09-29. The medians of the first post week (09-23 to 09-28) are within 0.8 % of the pre medians for all nine rows. The medians of the second post week (09-29 to 10-04) are 1.1 % to 2.4 % above the first week on eight of the nine rows: llama-3.3-70b tp2 8 users 16.61 to 17.02 TPS, mixtral 79.34 to 80.84, qwen-2.5-32b 35.34 to 36.02, gemma-2-9b 102.65 to 104.06, llama-3.1-8b 8 users 141.35 to 143.83. Group A rows also gained 1.3 % to 2.1 % on 09-29 on top of their 09-23 step. The only Intel rows that did not move on 09-29 are llama-3.2-3b (+0.3 %) and the AMX row (+0.4 %).
  • Night-to-night spread is small. After 09-23 the CV of every Intel row is at most 1.3 % (Table 1). Before 09-23 the two FPGA-attention tp4 rows were the noisy ones: qwen-3-4b tp4 ranged 140.89 to 153.14 TPS (CV 2.5 %) and gpt-oss-120b 101.16 to 109.70 (CV 2.6 %). Every post value of these two rows is above every pre value. The step is therefore larger than the night-to-night spread.

Section 6 ties the two steps to two different events. The 09-23 step is the first package with the AMX kernels, which also carried 31 other merges. The 09-29 step has no tron merge behind it. It coincides with a platformd restart on delphi-3bda, which most likely activated a new FPGA bitfile (hypothesis, section 6.3).

Rhys raised the thresholds on the Intel machine for qwen-3-4b tp4 (137.59 to 165.23 TPS) and gpt-oss-120b (99.60 to 114.15 TPS) on 2026-09-30 and 10-01 [systems_test commits 1724cb8, df046d5, 6c2e2f8 "Raise nightly TPS floors after sustained Granite gains"]. Those commits record the belief this page examines: that the gains are real and permanent. The gains are real and have persisted. The question is what caused them.

3. Prefill (time to first token)

Figure 3 repeats Figure 1 for the prefill rate. Prefill rate is derived from TTFT, so a higher rate means a shorter wait for the first token.

  • Intel: AMX row +61.1 % (219.7 to 353.9 tok/s, TTFT 18.6 s to 11.6 s), qwen-3-4b tp4 +12.9 % (1610 to 1817 tok/s), gpt-oss-120b +8.8 % (941 to 1024 tok/s), qwen-3-4b tp2 +8.2 % (1986 to 2149 tok/s), llama-3.1-8b 8 users +2.4 %. llama-3.3-70b tp2 4 users shows +8.2 % by median, inside its night-to-night spread (Figure 3 caption). All other rows within 1 %.
  • AMD: qwen-3-4b tp4 +9.5 % (1478 to 1618 tok/s), qwen-3-4b tp2 +7.5 % (1992 to 2142 tok/s), gpt-oss-120b +6.7 % (966 to 1030 tok/s). AMX row -0.1 %. llama-3.3-70b tp2 4 users -7.2 % (the same noisy row). All other rows within 2.3 %.
  • Timing (night steps): on Intel the gpt-oss-120b prefill gain came in two steps, +3.0 % on 09-24 (955 to 984 tok/s) and +7.6 % on 09-29 (988 to 1062 tok/s). On AMD the gpt-oss prefill rose on 09-23 (960 to 999 tok/s) and again on 09-26 (999 to 1124 tok/s). It stayed at 1124 to 1142 tok/s on the normal nights when the cards ran the new bitfile (09-26, 09-27, 09-28, 09-30; see section 4 for the bitfile history). It stayed at 1018 to 1050 tok/s on the nights the old bitfile was restored (10-01, 10-03, 10-04). The qwen rows rose on 09-23 on both machines.

The prefill picture separates the causes more clearly than decode does. The FPGA-attention models got faster prefill on both machines, with the Intel and AMD steps on nearby nights. AMX cannot run on the AMD machine. A shared cause in the package is therefore the only reading that fits those three rows.

4. The AMD machine over the same nights

The AMD machine ran the same packages on the same nights. Its data answers the control question.

  • No AMX-like gain anywhere. The AMX row stayed at 28.55 to 28.91 TPS (-0.9 % vs its 09-22 value of 29.00). llama-3.3-70b tp4 stayed at 34.0 TPS on its normal nights. The eight group-B rows that do not run FPGA attention are within -0.0 % to +1.3 % of their pre medians (median change). The ninth, qwen-3-4b tp2, is covered next.
  • The FPGA-attention rows did gain, less than on Intel. Median change: qwen-3-4b tp4 +5.4 % (185.88 to 195.99 TPS), qwen-3-4b tp2 +3.7 % (207.04 to 214.75 TPS), gpt-oss-120b +1.3 % (123.16 to 124.80 TPS). The first qwen step came on 09-23 with the first AMX package: qwen tp4 187.9 to 191.2 TPS (+1.8 %, about one ninth of the Intel step of +15.8 % that night), qwen tp2 207.4 to 211.1 TPS (+1.8 %, while Intel qwen tp2 decode did not move that night, -0.1 %). gpt-oss decode moved to 128.8 TPS on 09-30 and stayed at 127.7 to 128.8 TPS on 10-01, 10-03 and 10-04. That is +3 % vs the 09-29 night and +3.7 % to +4.6 % vs the pre median. Rhys measured +3.5 % to +3.8 % in two extra trials on 10-01 [Slack #ci-cd-notifications, Rhys, 2026-10-01 09:29 PDT].
  • A rise tied to the bitfile that switched on and off. Most AMD rows rose 1.5 % to 3.0 % on the 09-26 night (night step: mixtral 77.79 to 78.92, llama-3.3-70b tp2 8 users 17.59 to 18.12, llama-3.1-8b 8 users 151.0 to 154.8, qwen-3-4b tp4 190.6 to 196.3). They stayed high through 09-30, fell back on 10-01, rose again on 10-02 and fell back on 10-03 and 10-04. The FPGA bitfile history of that machine matches those nights:
    • 09-25: the nightly's own package update step (apt-get upgrade) installed archer-ia860m 1.5.9.0, the package that carries the new bitfile [amd run 36089207076 log].
    • 09-26: a reset service that Rhys had added restarted platformd before the nightly. That bring-up wrote 1.5.9.0 into the cards [Slack #ci-cd-notifications, Rhys, 2026-10-02 09:33 PDT].
    • 09-30, after the nightly: Rhys rolled the cards back to 1.5.8.0 [Slack #ci-cd-notifications, Rhys, 2026-09-30 10:49 PDT].
    • 10-01: the nightly re-installed 1.5.9.0 [amd run 36809584625 log], and the reset service applied it again on 10-02.
    • 10-02: Rhys pinned the package (apt-mark hold). The 10-03 and 10-04 logs show it "kept back" [amd runs 37092804519, 37176065812].
    High nights = new bitfile, low nights = old bitfile, on all 12 post nights for mixtral, llama-3.1-8b 8 users, qwen-2.5-32b, llama-3.3-70b tp2 and gemma-4-31b. A tron change cannot switch on and off like that while the package moves forward every night.
  • Anomalous AMD nights. llama-3.3-70b tp4 on 09-26, 09-27, 09-28 and 10-02 (21.9 to 28.3 TPS instead of 34.0), gpt-oss-120b on 09-29 and 10-02 (73.7 and 81.4 TPS instead of 124 to 129), and most rows on 09-18. The 09-26 to 10-02 drops are the "one card runs at 10 % of normal" defect of bitfile 1.5.9.0 reported by the FPGA team. They occur only on new-bitfile nights [Slack #fpga, Mike Cherba, 2026-09-29 17:25 PDT; Rhys's reconstructed reports of 09-28]. The medians are nearly unaffected by them (at most 0.3 % shift). The CV and min..max columns of Table 1 include them. The 09-18 drop predates this window's question and is not examined.

Reading: the Intel-only part of the change is group A minus what AMD also gained on the same package night (night steps of 09-23). For qwen-3-4b tp4 that is about +16 % minus +2 %. For gpt-oss-120b it is about +8 % minus +1.5 %. For llama-3.3-70b tp4 it is all of +3 %. For the AMX row it is all of +15 %. Group B's +1 to +2.5 % on 09-29 has no AMD counterpart on that night. AMD showed a rise of the same size three nights earlier, on the night its cards were programmed with the new bitfile.

6.1 How the 155 merges were screened

Every merge was classified by reading its diff and body. The question was: does the changed code run inside rinzler while it serves the nightly rows, or change what the .deb compiles? 41 merges passed that first screen (one of them is #4756, which never ran in a nightly). Each of those was then checked by two independent reviews, model-run reads of the diff recorded in exec/ci-poll-20261004/audit.json. One review asked "is this path reached in the nightly at all". The other asked "could it move decode or prefill of any row by 1 %". 24 merges were rejected by both reviews. Examples: #4726, a cleanup of the AVX-512 (Intel vector instruction set) compiler flags whose compiled output matches main; #4685, expert placement without a load profile, which gpt-oss-120b does not use because it ships a measured profile; #4596, attention statistics that stay off unless TRON_ATTN_STATS=1; #4205, a build-layout change. 17 merges were kept by at least one review. Of those, only four were judged able to move a row by 1 % or more: #4505, #4534, #4258 and #4713, plus #4353 for prefill only.

  • platformd was started by hand at 23:54:37 UTC.
  • All eight FPGA cards were re-enumerated (rediscovered by the operating system, which happens after a card reset) at 00:03:50 UTC on 09-29. Bring-up finished at 00:03:59 UTC.

The bitfile package archer-ia860m 1.5.9.0 had been installed by the nightly's package update step on 09-25 [intel run 36091251382 log; /var/log/dpkg.log 2026-09-25 03:42:55]. Cards keep their image until the next platformd bring-up. 09-29 is therefore the first Intel nightly that can have run on 1.5.9.0. The step shape fits that reading:

  • The rows whose decode time is dominated by the cards (weight streaming from card memory) moved by a similar 1 to 2.5 %.
  • The two 32-user rows, whose decode time is dominated by CPU attention, did not move (llama-3.2-3b +0.3 %, AMX row +0.4 %).

This is a strong hypothesis, not a confirmed cause. The platformd journal for 23:54 to 00:04 UTC on delphi-3bda would show whether an image was activated and which version. It is readable only by members of the Linux group adm (the machine's administrator group). Rhys can confirm in one sentence.

Three paired measurements, in order of value. Each needs the machine under the CI lease rules (the booking procedure in notebook handoffs/check-CI.md), 3 or more interleaved pairs, the nightly harness rows and the nightly prompt set.

  1. Wait counters vs AMX on the 09-23 package (Intel). Build source 5cf65b92 twice, once with -DTRON_MWAIT_STATS=ON (the behaviour before #4534) and once OFF. Run qwen-3-4b tp4, gpt-oss-120b tp4, llama-3.3-70b tp4 and mixtral on both builds. The ON-minus-OFF gap is the share of the gain that #4534 explains. 8. Data and method

  • Source. The GitHub Actions run log of each nightly, fetched with gh (the GitHub command-line tool): gh run view RUN_ID -R positron-ai/systems_test --log. 20 Intel runs (workflow system_ci_granite_rapids_72_rinzler_OCI.yaml) and 20 AMD runs (system_ci_genoa96_rinzler.yaml), 2026-09-15 to 2026-10-04 UTC. The 10 logs of 09-16 to 09-23 were reused from exec/ci-amx-row-20260923/. The AMD run of 09-17 was cancelled before any perf row ran. AMD therefore has 19 nights with data.
  • Extraction. exec/ci-poll-20261004/extract.py reads every row's Config(...) block, the per-request Done (TTFT=..., x / y TPS) lines and the Perf test for ... completed line. A row is used only if it completed with the expected sample count (users x rounds). All 502 rows in the 39 runs with data met that condition. The row mean recomputed from the samples matches the harness's own final running average within 0.011 TPS and 1.1 ms (same check as the 09-28 analysis).
  • Prefill. prompt length / round(mean TTFT in ms), the harness formula [systems_test scripts/perf.py].
  • Windows and statistics. pre = 09-15 to 09-22, post = 09-23 to 10-04, medians per window over all nights, anomalies included. CV over the nights of a window. A step = the median of the next three nights lies outside the range of the previous three nights by at least 1 % (steps.py).
  • Packages and merges. The installed package is read from the log line Setting up tron (...). Merges per package = git log --first-parent (which lists only the merges into main, not the commits inside each PR) between consecutive package commits in a read-only tron checkout fetched 2026-10-04. Merge metadata from gh pr view (prs.json). The merge audit is in audit.json.
  • Harness changes in the window. systems_test moved from 0ab579bf (09-15) to b1ccc0b8 (10-02 onward). The row definitions in scripts/perf.py changed twice: the 32-user llama-3.1-8b row was added on 09-21 (PR #221) and the Muse-Glimmer-30B row on 09-30. The measurement code (capture window, TTFT, prefill formula, users, rounds, prompt lengths, stagger, prompt data set, speculation flag) did not change for existing rows. The prompt-selection rewrite of 09-21 was re-run against the data set and picks the same conversation for every seed of every existing row. This paragraph is the only audit of the harness; section 6 audits the tron merges.
  • Chart colours. blue and orange are the first two colours of our chart palette. They stay distinguishable under colour-vision deficiency (simulated colour distance 9.1 units, above our 8-unit target). Light theme only.
