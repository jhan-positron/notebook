
Was AMX boosting all models?
Was AMX boosting all models? What the nightly CI measured, 2026-09-15 to 2026-10-04
delphi-3bda (Intel) and andoria-b1a3 (AMD) nightly System CI perf rows, 20 nights per machine, read from the GitHub Actions run logs. Written 2026-10-05 (UTC). Generator and data: exec/ci-poll-20261004/.
Short version
No. The nightly data show three separate changes, and AMX explains only one of them.
Since 9/22 the Intel machine gained decode speed on 4 rows by 4 % to 18 % and on 9 more rows by 1 % to 2 %, and every gain is a step that has held for every night since. The AMD machine, which ran the same tron packages, gained nothing on the AMX benchmark row, 1 % to 5 % on the FPGA-attention rows, and nothing on the rest. The one measured AMX effect is the llama-3.1-8b 32-user row (+15 %); the three other large gains arrived in the same first AMX package but on FPGA-attention rows that AMX does not serve, where the wait-counter removal (#4534) and Bill's earlier FPGA-join change (#4258) are the candidates; the broad +1 to 2 % step on 9/29 coincides with an FPGA bitfile update on the machine, not with any tron merge.
Words used here
tron, rinzlertron is the inference program under test. rinzler is its production server binary. The nightly installs rinzler from a Debian package (.deb) built from tron's main branch.
nightly, System CIthe automated test run of the positron-ai/systems_test repository that starts at about 03:30 UTC every night, installs the newest tron package and runs a fixed list of performance rows on each test machine.
delphi-3bda, andoria-b1a3the two test machines. delphi-3bda has two Intel Xeon 6 6962P processors (Granite Rapids), which have AMX. andoria-b1a3 has AMD Genoa processors, which have no AMX. Both machines carry the same accelerator cards and run the same package every night.
AMX, AMX kernelsAMX = Intel Advanced Matrix Extensions, the matrix unit in Xeon 6 processors. The AMX kernels are tron's attention code that uses that unit. The .deb build option TRON_AMX_DISPATCH compiles them in. They serve only models with head size 128 and 4 query heads per KV head, and only when attention runs on the CPU.
FPGA attentionattention computed on the accelerator cards instead of the CPU. In the nightly, qwen-3-4b and gpt-oss-120b run with FPGA attention. The AMX kernels do not run for them.
packageone tron .deb, named by build date and the first 8 characters of the source commit, for example 2026.09.23-5cf65b92. The first package with the AMX kernels is that one. It was installed on the night of 2026-09-23 (UTC).
merge, #NNNNone pull request merged into tron main, named by its number.
rowone performance measurement of the nightly: a model, a tensor-parallel split and a user count, for example "qwen-3-4b tp4, 8 users". tp2 / tp4 = the model is split over 2 or 4 accelerator cards. A tp2 row runs 4 rinzler engines, a tp4 row runs 2 engines, and the users are spread over the engines.
decode TPSdecode speed, generated tokens per second for one user. The harness averages the per-request samples of the row (320 samples for a 32-user row, 80 for an 8-user row, 40 for a 4-user row).
TTFT, prefill rateTTFT = time to first token in milliseconds. Prefill rate = prompt length divided by the mean TTFT, in tokens per second (tok/s). It is the harness's own number. With several users per engine it includes the wait behind other users' prompts.
pre window, post windowpre = the 8 nightlies from 09-15 to 09-22 UTC (packages without AMX kernels). post = the 12 nightlies from 09-23 to 10-04 UTC (packages with AMX kernels). All dates are the UTC date on which the perf rows ran. In Pacific time the run belongs to the previous evening.
median, CVmedian = the middle value of the nights in a window. CV = coefficient of variation = standard deviation divided by the mean, in percent. A low CV means the nights agree with each other.
stepa change that appears on one night and stays on the following nights. The opposite is a fluctuation, which comes and goes.
1. Did several models get faster on the Intel machine after 9/22? Yes, but in two groups
Figure 1 compares the median decode speed of the 12 post nights with the median of the 8 pre nights, for every row and both machines.
[SVG]
Figure 1. On the Intel machine (blue) four rows moved by 4 % or more and nine rows moved by less than 2 %. On the AMD machine (orange) only the two qwen-3-4b rows moved by more than 2 %. The AMD whiskers that run off the left edge come from single anomalous nights (see section 4). The llama-3.1-8b 32-user row has one pre night only (09-22), because the row was added to the nightly on 09-21.
The Intel rows fall into two groups.
Group A, large gains on four rows. qwen-3-4b tp4 +18.3 % (147.45 to 174.40 TPS), llama-3.1-8b 32 users +15.4 % (28.25 to 32.61 TPS), gpt-oss-120b tp4 +12.8 % (107.54 to 121.33 TPS), llama-3.3-70b tp4 +4.2 % (30.24 to 31.52 TPS). Three of the four are tp4 rows. Only one of the four, the llama-3.1-8b 32-user row, runs the AMX kernels: it is the row that was added as the AMX benchmark, and our own same-code AMX on/off test of 2026-09-20 measured +14.0 % on it [CI-test/status/CI-merges-20260923.html, Figure 1]. qwen-3-4b and gpt-oss-120b run FPGA attention in the nightly, so the AMX kernels are not on their path. llama-3.3-70b has the AMX head shape, but its tp2 rows (same model, same CPU attention) moved by only +1.2 % and +1.4 %, so the +4.2 % of the tp4 row is not an AMX-shape effect either.
Group B, small gains on the other nine rows. +1.2 % to +1.6 % on seven rows (llama-3.1-8b 8 users, llama-3.3-70b tp2 at 4 and 8 users, mixtral, qwen-2.5-32b, gemma-2-9b, qwen-3-4b tp2) and under +0.7 % on llama-3.2-3b and gemma-4-31b. None of these runs the AMX kernels. Section 2 shows that this group did not move on the AMX night at all. It moved six nights later.
So the answer to "did AMX boost most models" is no. One row has a measured AMX gain. Three rows have large gains that AMX cannot explain. Nine rows have small gains that arrived on a different night from the AMX package.
2. Consistent or fluctuating? Step changes, then flat
Figure 2 shows every night. Each line is indexed to its own machine's pre-window median, so both machines share one axis and the percent change can be read directly.
[SVG]
Figure 2. Every Intel gain is a step, not a drift. Group A (top row of panels) jumps on the 09-23 night, the first night with the AMX package, and then stays flat. Group B (the other panels) does nothing on 09-23 and rises by 1 to 2.5 points on the 09-29 night, then stays flat. The AMD lines (orange) show the 09-23 step only on the qwen rows and a smaller gpt-oss step, plus a bump on 09-26 to 09-29 on several rows that reverts afterwards. Hollow triangles mark nights that fall outside the panel range (AMD anomalies, see section 4).
The gains are consistent, not fluctuating. The numbers:
Group A stepped once, on 09-23. qwen-3-4b tp4 went 148.67 to 172.12 TPS between the 09-22 and 09-23 nights and stayed between 172.12 and 176.72 for all 12 post nights. gpt-oss-120b tp4 went 109.70 to 118.91 and stayed between 118.91 and 123.60. llama-3.3-70b tp4 went 30.37 to 31.33 and stayed between 31.20 and 31.85. The AMX row went 28.25 to 32.49 and stayed between 32.43 and 32.78.
Group B stepped once, on 09-29. The medians of the first post week (09-23 to 09-28) are within 0.8 % of the pre medians for all nine rows. The medians of the second post week (09-29 to 10-04) are 1.1 % to 2.4 % above the first week: llama-3.3-70b tp2 8 users 16.61 to 17.02 TPS, mixtral 79.34 to 80.84, qwen-2.5-32b 35.34 to 36.02, gemma-2-9b 102.65 to 104.06, llama-3.1-8b 8 users 141.35 to 143.83. Group A rows also gained 1.3 % to 2.1 % on 09-29 on top of their 09-23 step. The only Intel rows that did not move on 09-29 are llama-3.2-3b (+0.3 %) and the AMX row (+0.4 %).
Night-to-night spread is small. After 09-23 the CV of every Intel row is at most 1.3 % (Table 1). Before 09-23 the two FPGA-attention tp4 rows were the noisy ones: qwen-3-4b tp4 ranged 140.89 to 153.14 TPS (CV 2.5 %) and gpt-oss-120b 101.16 to 109.70 (CV 2.6 %). The post-9/22 values of these two rows are above every pre night, so the step is not a lucky sample.
Section 6 ties the two steps to two different events. The 09-23 step is the first package with the AMX kernels, which also carried 31 other merges. The 09-29 step has no tron merge behind it; it coincides with the activation of a new FPGA bitfile on delphi-3bda.
Rhys raised the Granite Rapids thresholds for qwen-3-4b tp4 (137.59 to 165.23 TPS) and gpt-oss-120b (99.60 to 114.15 TPS) on 2026-09-30 and 10-01 [systems_test commits 1724cb8, df046d5, 6c2e2f8 "Raise nightly TPS floors after sustained Granite gains"]. That commit series is the written form of the impression this page examines. The gains it reacted to are real and persistent. The question is what caused them.

[SVG]
Figure 3. The AMX row's prefill rate rose 61 % on Intel and did not move on AMD, as expected for the one row that runs the AMX kernels. The three other large prefill gains (qwen-3-4b tp4, gpt-oss-120b, qwen-3-4b tp2) appear on BOTH machines at a similar size, so they are not AMX effects. The llama-3.3-70b tp2 4-user whiskers are wide on both machines because that row's TTFT varies from night to night (Intel 207 to 338 tok/s across all 20 nights); its +8.2 % median change is inside that spread and is not treated as a step.

AMD: qwen-3-4b tp4 +9.5 % (1478 to 1618 tok/s), qwen-3-4b tp2 +7.5 % (1992 to 2142 tok/s), gpt-oss-120b +6.7 % (966 to 1030 tok/s). AMX row -0.1 %. All other rows within 2.3 %.
Timing: on Intel the gpt-oss-120b prefill gain came in two steps, +3.7 % on 09-24 (955 to 984 tok/s) and +8.5 % on 09-29 (982 to 1066 tok/s). On AMD the gpt-oss prefill rose on 09-23 (960 to 999 tok/s) and again on 09-26 (999 to 1136 tok/s); it stayed near 1140 tok/s while the new bitfile was active (09-26 to 09-30 and 10-02) and sat at 1018 to 1050 tok/s on the nights the old bitfile was restored (10-01, 10-03, 10-04). The qwen rows rose on 09-23 on both machines.
The prefill picture separates the causes more clearly than decode does. The FPGA-attention models got faster prefill on both machines, with the Intel and AMD steps on nearby nights. AMX cannot run on the AMD machine, so a shared cause in the package is the only reading that fits those three rows.
4. The AMD machine over the same nights
The AMD machine ran the same packages on the same nights. Its data answers the control question.
No AMX-like gain anywhere. The AMX row stayed at 28.55 to 28.91 TPS (-0.9 % vs its 09-22 value of 29.00). llama-3.3-70b tp4 stayed at 34.0 TPS on its normal nights. The seven group-B rows are within -0.0 % to +1.3 % of their pre medians.
The FPGA-attention rows did gain, less than on Intel. qwen-3-4b tp4 +5.4 % (185.88 to 195.99 TPS), qwen-3-4b tp2 +3.7 % (207.04 to 214.75 TPS), gpt-oss-120b +1.3 % by median (123.16 to 124.80 TPS). The first qwen step came on 09-23 with the first AMX package (qwen tp4 187.9 to 191.2, qwen tp2 207.4 to 211.1), the same night as the Intel step and about one fifth of its size. gpt-oss decode moved to 128.6 to 128.8 TPS on 09-30 and stayed there on 10-01, 10-03 and 10-04 (+4.6 % vs the pre median); Rhys measured the same +3.5 % to +3.8 % in two extra trials on 10-01 [Slack #ci-cd-notifications, Rhys, 2026-10-01 09:29 PDT].
A bitfile-driven bump that switched on and off. Most AMD rows rose 1.6 % to 3.8 % on 09-26 (mixtral 77.79 to 78.92, llama-3.3-70b tp2 8 users 17.59 to 18.12, llama-3.1-8b 8 users 151.0 to 154.8, qwen-3-4b tp4 190.6 to 196.3) and stayed high through 09-30, fell back on 10-01, rose on 10-02 and fell back on 10-03 and 10-04. The same nights carry the FPGA bitfile history of that machine: the nightly's own apt-get upgrade installed archer-ia860m 1.5.9.0 on 09-25 [amd run 36089207076 log], a reset service that restarts platformd before the nightly programmed it into the cards on 09-26, Rhys rolled back to 1.5.8.0 on 09-30 after the nightly, the 10-01 nightly re-installed 1.5.9.0 and the reset applied it on 10-02, and apt-mark hold kept 1.5.8.0 from 10-03 [amd run logs 36809584625, 37092804519, 37176065812; Slack #ci-cd-notifications, Rhys, 2026-10-02 09:33 PDT]. High nights = new bitfile, low nights = old bitfile, on all 13 nights. A software change cannot switch on and off like that while the tron package moves forward every night.
Anomalous AMD nights. llama-3.3-70b tp4 on 09-26, 09-27, 09-28 and 10-02 (21.9 to 28.3 TPS instead of 34.0), gpt-oss-120b on 09-29 and 10-02 (73.7 and 81.4 TPS instead of 124 to 129), and most rows on 09-18. The 09-26 to 10-02 drops are the "one card runs at 10 % of normal" defect of bitfile 1.5.9.0 reported by the FPGA team, seen only on the new-bitfile nights [Slack #fpga, Mike Cherba, 2026-09-29 17:25 PDT; Rhys's reconstructed reports 09-28]. Medians exclude them. The 09-18 drop predates this window's question and is not examined.
Reading: the Intel-only part of the change is group A minus what AMD also gained on the same package night. For qwen-3-4b tp4 that is about +16 % minus +2 % on 09-23, for gpt-oss-120b +8 % minus +1.5 %, for llama-3.3-70b tp4 all of +3 %, and for the AMX row all of +15 %. Group B's +1 to +2.5 % on 09-29 has no AMD counterpart on that night, but AMD showed the same size of bump three nights earlier when its cards took the new bitfile.

6.1 How the 155 merges were screened
Every merge was classified by reading its diff and body: does the changed code run inside rinzler while it serves the nightly rows, or change what the .deb compiles? 41 merges passed that first screen. Each of those was then challenged by two independent reviewers, one asking "is this path reached in the nightly at all" and one asking "could it move decode or prefill of any row by 1 %". 24 were refuted by both (examples: #4726 AVX-512 flag cleanup, no machine-code change; #4685 expert planning without a load profile, gpt-oss ships a profile; #4596 attention stats, off unless TRON_ATTN_STATS=1; #4205 per-architecture model specializations, build layout only). 17 survived at least one reviewer, and of those only four were judged able to move a row by 1 % or more: #4505, #4534, #4258 and #4713, plus #4353 for prefill only. The full classification is in exec/ci-poll-20261004/audit.json.

The 09-29 package added 13 merges (#4011, #4679, #4495, #4597, #4173, #4683, #4673, #4591, #4172, #4023, #4675, #4051, #3390). Each was read. None has a code path that runs for the hand-written dense models that moved (llama-3.3-70b, qwen-2.5-32b, gemma-2-9b, mixtral) and also differs between the two machines: #4495 and #4673 touch MoE routing only, #3390 compiles to a multiply by 1.0, #4591 and #4597 remove dead casts and compile-time branches, the rest are ingest tooling, tests, Perfetto configuration or a Ninja pin. The same .deb left every AMD row flat on 09-29.
What did change on delphi-3bda between the 09-28 nightly (ended 05:28 UTC) and the 09-29 nightly (began 04:05 UTC): platformd, the daemon that programs the FPGA cards, was started by hand at 2026-09-28 23:54:37 UTC and all eight FPGA PCI devices were re-enumerated at 2026-09-29 00:03:50 UTC, with user rhys logged in from 23:11 UTC [systemctl show platformd; stat of /sys/bus/pci/devices; last -F, read on delphi-3bda 2026-10-05 00:35 UTC]. Rhys had asked for the machine that evening ("any chance I can steal delphi-3bda for some testing later today or tonight before the nightly run?" [Slack DM, 2026-09-28 15:42 PDT]). The FPGA bitfile package archer-ia860m 1.5.9.0 had been installed by the nightly's apt step on 09-25 [intel run 36091251382 log; /var/log/dpkg.log 2026-09-25 03:42:55] but cards keep their image until the next platformd bringup, so 09-29 is the first Intel nightly that can have run on 1.5.9.0. The step shape fits that: the rows dominated by FPGA weight streaming moved by a similar 1 to 2.5 %, the two 32-user CPU-attention-bound rows did not move (llama-3.2-3b +0.3 %, AMX row +0.4 %), and the largest move is gpt-oss prefill (+8.5 %), which runs attention and expert matmuls on the FPGA. The AMD machine shows the same bump of the same size on the same rows on the nights its cards ran 1.5.9.0 (section 4). Intel never rolled back, so its bump stayed.
This is a strong hypothesis, not a confirmed cause. The platformd journal for 23:54 to 00:04 UTC on delphi-3bda would show whether an image was activated and which version; it is readable only by group adm. Rhys can confirm in one sentence.

The only place that lists all four group-A rows under one AMX heading is Rhys's table in the 09-23 report thread ("AMX Performance gains: Llama 8B TP2 @32u +15.0 %, Qwen 3 4B TP4 +15.8 %, GPT-OSS 120B TP4 +8.4 %, Qwen 3 4B TP2 -0.1 %") [Slack #ci-cd-notifications, 2026-09-23 09:22 PDT]. It is a one-night delta that spans the whole 09-18 to 09-23 package change. Our own messages that day attributed only the llama-8b row to AMX [Slack DMs, 2026-09-23]. The Slack numbers were cross-checked against the run logs: 130 of 130 rows match within 0.05 TPS.

8. Data and method
Source. The GitHub Actions run log of each nightly, fetched with gh run view RUN_ID -R positron-ai/systems_test --log: 20 Intel runs (workflow system_ci_granite_rapids_72_rinzler_OCI.yaml) and 20 AMD runs (system_ci_genoa96_rinzler.yaml), 2026-09-15 to 2026-10-04 UTC. The 10 logs of 09-16 to 09-23 were reused from exec/ci-amx-row-20260923/. The AMD run of 09-17 was cancelled before any perf row ran, so AMD has 19 nights with data.
Extraction. exec/ci-poll-20261004/extract.py reads every row's Config(...) block, the per-request Done (TTFT=..., x / y TPS) lines and the Perf test for ... completed line. A row is used only if it completed with the expected sample count (users x rounds). All 502 rows in the 39 runs with data met that condition. The row mean recomputed from the samples matches the harness's own final running average within 0.011 TPS and 1.1 ms (same check as the 09-28 analysis).
Prefill. prompt length / round(mean TTFT in ms), the harness formula [systems_test scripts/perf.py].
Windows and statistics. pre = 09-15 to 09-22, post = 09-23 to 10-04, medians per window; CV over the nights of a window; a step = the median of the next three nights lies outside the range of the previous three nights by at least 1 % (steps.py).
Packages and merges. The installed package is read from the log line Setting up tron (...). Merges per package = git log --first-parent between consecutive package commits in a read-only tron checkout fetched 2026-10-04. Merge metadata from gh pr view (prs.json).
Harness changes in the window. systems_test moved from 0ab579bf (09-15) to b1ccc0b8 (10-02 onward). The row definitions in scripts/perf.py changed twice: the 32-user llama-3.1-8b row was added on 09-21 (PR #221) and the Muse-Glimmer-30B row on 09-30. The measurement code for existing rows did not change; see section 6 for the audit.
Chart colours. blue and orange are slots 1 and 2 of the validated dataviz palette (adjacent colour-vision-deficiency distance 9.1, above the 8 target). Light theme only.
