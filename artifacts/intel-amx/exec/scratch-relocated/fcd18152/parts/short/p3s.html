1. The mock pass used in every figure

  • Request B is decoding (one new token per pass): shared prompt s0..s8 (cached), b0, b1 (cached), b2 (new). B wants logits at b2.
  • Request A is prefilling (new prompt tokens need K and V): a0..a4 after the same prompt. A wants logits at a4.
  • The tree has root edge S (an edge is a run of consecutive tokens between two nodes) and child edges B (inserted first, continues S's book X) and A (new book Y). At most one child shares its parent's book [h/tron/scheduler/token_tree.hpp:426].
  • The model has 2 layers: layer 0 full causal (window INT_MAX), layer 1 sliding window W = 6 positions. One KV head, no FPGA.

A live token is one in this pass's context. All 17 are live. The 6 tokens whose kv_ready flag is false (no K/V job scheduled yet) become the queries [h/tron/scheduler/full.hpp:2127-2135]. The traversal (compute_forward_args, a depth-first walk) numbers tokens on its descent and builds the mask on its ascent. It gives every live token a token_id (traversal order), records its position (depth in its sequence) and page, gives each query a token_job_id, and pushes each page onto kv_pages[] [h/tron/scheduler/full.hpp:2117]. Four numberings: position (persistent), token_id (per pass), token_job_id (the mask bit), batch_job_ix (slot inside a minibatch).

3. KV cache page: persistent storage, two per-pass numbers

A page holds 64 entries in code [h/tron/models/kv_cache.hpp:1164], 4 in the mock. lo is the token_id of entry 0, so entry i has token_id lo + i [h/tron/models/kv_cache.hpp:1227]. The kernel (the CPU routine that computes attention for one minibatch) reads entries [0, count()) only [h/tron/models/self_attention.hpp:1403]. A page is pending when a query writes K and V into it this pass, otherwise ready [h/tron/models/model.hpp:1897]. Attention over a pending page waits for the layer's K and V writes through a countdown latch (a counter that releases the work when the writes are done) [h/tron/models/model.hpp:1979]. Pages are freed only by token-cache eviction, never by the end of a pass.

Takeaway: the bytes persist. lo and count are rewritten every traversal and stale between passes.

Common confusion

A page is a per-pass object.

Correct picture

The page and its bytes persist. Only lo and offset_bound (behind count()) are rewritten by every traversal [h/tron/models/kv_cache.hpp:1475]. FPGA pages (128 tokens) and shards (1024 tokens) are separate copies.

4. Visible range of K/V: one ranged mask per pass

The brief's phrase does not occur in the source. This page reads it as the ranged mask. The mask is the only mechanism that decides which entries a query may read [h/tron/models/kv_cache.hpp:96]. It is a sorted, gap-free list of token_range spans over token_ids [h/tron/models/ranged_mask.hpp:98-99]. Each span carries two disjoint bitmasks indexed by token_job_id, with room for 4096 queries [h/tron/models/ranged_mask.hpp:20]. visible(job) is true when the bit is in either mask [h/tron/models/ranged_mask.hpp:159].

The mask is built while the traversal climbs back up the tree (the ascent), one edge at a time. When the ascent leaves a query, it sets that query's bit for itself and for every earlier token of the same edge [src/tron/models/ranged_mask.cpp:42-65]. A parent then ORs (combines) its children's masks into its own [h/tron/scheduler/full.hpp:2809]. A query therefore sees exactly its ancestors and itself, never a sibling branch. The kernel's page gate (the whole-page visibility test, section 6) always uses visible(). Inside a page it uses sw_required() only on full layers that use the FPGA, otherwise visible() [h/tron/models/self_attention.hpp:1284-1285; :1406]. In the mock both agree.

Common confusion

Visibility lives on each page, or per minibatch, or includes the window.

Correct picture

One mask per pass, built before any minibatch exists, reached through token_id = lo + offset. The window is a separate second test.

5. Minibatch: a cut of this pass's queries

A minibatch (q_batch) is a subset of this pass's queries [h/tron/models/common.hpp:880], made so that CPU attention of one minibatch overlaps FPGA matrix multiplications of another [h/tron/models/model.hpp:223]. The FPGA-less mock still gets 2: chunk_evenly never checks for hardware [h/tron/models/model.hpp:185-261]. It works in five steps:

  1. Group queries by a tree-affinity label (B and A get gB and gA).
  2. Cut each group into grains (runs of queries packed as one unit) of at most 8 queries, 2 in the mock.
  3. Keep the even and odd offsets of one page in the same grain, because they are written together.
  4. Merge grains greedily toward ceil(n / cap) chunks, where n is the query count and cap is max_minibatch_size.
  5. Halve a lone chunk.

A query keeps its token_job_id in any minibatch. Its batch_job_ix (position in items[]) selects its scratchpad slot (a worker's per-query row for partial results).

orange border = label gBaqua border = label gA

Takeaway: with mock constants MB0 = (b2, a0, a1) mixes two requests. With the real llama constants the same queries give MB0 = (b2), MB1 = (a0..a4). The mask bits never change.

select_relevant_pages builds one page list per minibatch and per layer profile (layers with the same head geometry, window value and hardware use share one profile). A page stays when some query of the minibatch is visible in the range of the page's first entry. On a windowed layer that query must also be within W of the page's first position + count [h/tron/models/model.hpp:2415-2427]. kv_pages[] itself is never trimmed.

Durations are schematic.

Common confusion

A minibatch is a request, a set of requests, or the context tokens.

Correct picture

A subset of this pass's queries, cut from token_jobs[] after the mask is final, with its own page lists, work plans, Q/O buffers and latches for one pass [h/tron/models/model.hpp:1881; :1826].

6. Attention: the kernel where the four meet

Attention runs once per (operation, minibatch). Worker threads receive page ids in kv_sections (one KV head plus a list of pages) [h/tron/models/common.hpp:735]. Per page and query, in order:

  1. Page gate: skip the page unless the query is visible in the range of the page's first entry [h/tron/models/self_attention.hpp:1303].
  2. Whole-page window test: skip when q_position − (first position + count) ≥ W [h/tron/models/self_attention.hpp:1306].
  3. Entry loop over [0, count()): advance the range at its end, jump over invisible ranges, and drop entries with q_position − k_position ≥ W [h/tron/models/self_attention.hpp:1419-1422]. Otherwise compute the dot product into a per-page score row. After the loop, one deferred-softmax update folds the page into the accumulator (running max m*, running sum s*, running weighted V sum v*) in scratchpad slot batch_job_ix.

Workers then merge partials into the output rows [h/tron/models/self_attention.hpp:1121].

Takeaway: mask first, window second. Only entries that pass both enter the dot product. The minibatch decides which queries share the run and which slot each gets.

7. Sliding window: a second filter, measured in positions

The window is one optional integer on an attention operation's config [h/tron/models/kv_cache.hpp:197-198], copied into attention_runtime_configs; a missing value becomes INT_MAX [h/tron/models/model.hpp:660]. Its parent is the attention operation, not the model, page, or mask. GPT-OSS, for example, alternates windowed and full layers [src/tron/gof.cpp:96]. It is applied after the mask at three points: per-minibatch page selection [h/tron/models/model.hpp:2415], the whole-page skip [h/tron/models/self_attention.hpp:1306], and the per-entry skip [:1422]. Distance is in positions. A windowed operation never runs on the FPGA [h/tron/models/self_attention.hpp:482-490]. The traversal, kv_pages[], and host KV memory do not change. The window saves dot products, and FPGA memory only because windowed layers never copy their K/V to the hardware.

Common confusion

A window frees pages, is encoded in the mask, or is measured in token_ids.

Correct picture

One integer per operation, tested by position after the mask. b2 (token_id 11) and a0 (token_id 12) are 2 positions apart, so the same W reaches different tokens.
