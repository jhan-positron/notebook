# platformd integration brief: Intel AMX and Intel Speed Select (meeting with John Mark, 2026-10-05)

Paths in brackets are relative to `~/workspace` unless they start with `~/.claude`.

## Words used here

- **platformd**: Positron's host daemon (HTTP API on port 8080). At each provisioning it writes `/etc/rinzler/instance-N.env`. That file holds CPUAFFINITY (the core list rinzler is pinned to) and RZ_CLI_ARGS (rinzler's command-line arguments). platformd then starts the `rinzler@N` units. Version 0.10.7 reads resource-map.yaml once at start. 0.11 was not checked [notebook/handoffs/claude_20260722_resource-map-change.md:25,49-57].
- **rinzler**: the production inference server binary, one systemd unit `rinzler@N` per engine. It runs as user `positron`, without root [tron/packaging/systemd/rinzler@.service:40-62].
- **tron**: Positron's inference engine library and repository. rinzler is built from it. **runtron** is tron's command-line benchmark tool (no rinzler, no HTTP).
- **engine**: one running rinzler with its FPGA cards. **tp2 / tp4**: the model split over 2 or 4 cards. **users per engine**: the number of concurrent users one engine serves.
- **resource-map.yaml**: tron's data file, installed at `/opt/positron/config/resource-map.yaml`, that assigns cores to roles per machine type. Roles: `platform_cores`, `rinzler_cores` (front end), `dev_cores` (FPGA driver), `tron_cores` (model workers), `peer_cores` (cores whose HT sibling is also free for work) [tron/config/resource-map.yaml:16-21].
- **6962P / 6960P**: the two Intel machine types in the map, `granite_rapids_6962p` and `granite_rapids_6960p`. The map carries no hostnames. Hosts seen in the notes: 6962P = delphi-3bda, 3af6, 3c51 (3bd6 assumed, SKU not recorded); 6960P = delphi-17cf [tron/config/resource-map.yaml:155-176; notebook/handoffs/claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1049]. **SKU**: one product variant of a CPU.
- **AMX**: Intel Advanced Matrix Extensions, the tile matrix unit on Granite Rapids Xeon 6 CPUs. tron uses it in the CPU attention kernel. **AVX-512 / AVX**: Intel's 512-bit vector instruction set, the attention path tron used before AMX and the path every engine runs when AMX is absent or disabled.
- **TRON_AMX_DISPATCH**: CMake build option that compiles the AMX kernels into the binary. **TRON_AMX_DISABLE**: environment variable; exactly the string "1" turns AMX off for that process (the kill switch).
- **USE_HW_ATTN**: environment variable that selects FPGA attention or CPU attention for one engine. Unset = FPGA attention for **ingested models** (models whose tron build ships FPGA attention, for example qwen-3-4b and gpt-oss-120b), CPU attention for the rest. 0 = CPU attention for all [tron/h/tron/models/hw_attn_config.hpp:12-14].
- **128x4 shape**: head size 128 with 4 query heads per KV head, the only attention geometry the AMX kernel serves.
- **TRON_ATTN_STATS**: environment variable (tron PR #4596, on main). Exactly "1" turns on AMX/AVX/FPGA attention counters. **tronstats**: tron's statistics tree, served as files through **FUSE** (a filesystem implemented by a user-space program) by a thread inside rinzler. platformd scrapes only the leaves mirrored under `/exported/` into Prometheus [notebook/handoffs/claude_20260909_tron-pr-4267-review-comment.md:18].
- **EXE.AMX_BUSY**: a CPU hardware counter (raw event 0xb7, umask 0x02) that counts cycles the AMX unit is busy. Read with `perf stat` as root. A non-zero count proves AMX ran in that process [notebook/handoffs/claude_20260917-20260920_nightly-ci-mimic-with-amx-and-vnni-k.md:30].
- **turbo license**: the per-core frequency ceiling level the CPU picks from the instruction mix. Scalar code gets the highest ceiling, AVX-512 a lower one, AMX the lowest [notebook/handoffs/claude_20260623_intel-xeon-6-core-frequency-configuration.md:43].
- **SST / intel-speed-select**: Intel Speed Select, the core-frequency control feature set and its command-line tool. **MSR**: model-specific register, a per-CPU control register.
- **CLOS**: class of service. A table of four classes, each with a min/max frequency window, plus an association of every logical CPU to one class. Shipped policy: **CLOS0** = fast, 2700 MHz to 4400 MHz; **CLOS3** = capped, 800 MHz to 2700 MHz.
- **SST-TF / turbo-freq**: Speed Select Turbo Frequency, Intel's name for Priority Core Turbo. With it enabled, high-priority cores may reach the 4400 MHz bucket. With more than 8 high-priority physical cores per socket the ceiling is 3900 MHz. The shipped policy keeps it enabled [notebook/handoffs/claude_20260623_intel-xeon-6-core-frequency-configuration.md:43,63].
- **PCT / boot default**: the BIOS Priority Core Turbo partition, re-programmed at every boot: 32 logical CPUs fast, the other 256 capped at 2700 MHz.
- **intel-speed-select-state**: the boot service (systemd oneshot) and script that apply the policy today. Config at `/etc/default/intel-speed-select-state`, with the core list `FAST_CORE_RANGES`. Rendered by Hannah's **Ansible role** (a configuration-management script) [notebook/artifacts/intel-speed-select/reminder.md:56-77].
- **FE un-clamp**: FE = front end, the rinzler process. The pending change that moves `rinzler_cores` (1, 2, 73, 74 and siblings 145, 146, 217, 218) from CLOS3 to CLOS0 [tron/config/resource-map.yaml:183].
- **HT sibling**: the second hardware thread of a physical core. On the 6962P, CPU N pairs with CPU N+144. Both threads share one clock.
- **anchor CPUs**: CPUs 0, 24, 48, 72, 96, 120, one per compute die (the `ANCHOR_CPUS` value in the boot-service config). Per-die commands are issued once on each anchor. "Die A" below is the die anchored at CPU 0 [notebook/artifacts/intel-speed-select/reminder.md:67-82].
- **uncore**: the CPU package parts outside the cores (memory controller, mesh, last-level cache), clocked separately.
- **TPS / TTFT**: decode tokens per second per user; time to first token. **CV**: coefficient of variation, standard deviation divided by mean, in percent.
- **Bzy_MHz**: turbostat's average clock of a CPU while it is not idle.
- **the nightly**: the GitHub Actions workflow `system_ci_granite_rapids_72_rinzler_OCI.yaml` in repo positron-ai/systems_test. Every night it reinstalls tron and provisions through platformd on delphi-3bda. A second workflow runs the same rows on andoria-b1a3 (AMD, no AMX) as a control [notebook/handoffs/claude_20260923_amx-benchmark-tps-regression-between-ci-runs.md:21].
- **CI lease**: the file `/run/lock/systems-test-ci.lease` that the nightly writes while it holds delphi-3bda. **ci-runner**: the systemd service and timer on delphi-3bda that run the day/night handoff [notebook/handoffs/check-CI.md:27-29,52].
- **reconciliation**: platformd's stop-and-start of engines after a config PATCH.
- **Gate C**: the planned reboot A/B test of the frequency policy, opened 2026-07-31, run 2026-08-01, stopped before completion. **ab56**: the 2026-07-29 turbo-freq on/off A/B kit. Its register readbacks changed in 60 of 60 checks, but frequency and TPS did not move (the "placebo" run) [notebook/handoffs/claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:2003].
- **posadm**: the Positron admin command-line tool that changes engine settings through platformd.

## Short version

For AMX, platformd needs to restart engines after a tron package install and to offer a per-engine kill switch, because the kernels ship in the tron apt package (since 2026-09-23) and enable themselves. For Speed Select, platformd needs to derive the core-frequency policy from the resource-map core roles it already reads, in place of a boot service and an Ansible role that use a hand-copied core list. For both, platformd must verify the physical state after provisioning (binary contents, CLOS associations, frequency under load), not a service status.

## A. AMX: what platformd must do

**What breaks if platformd gets it wrong.** Nothing crashes. Every failed gate (host without AMX, ineligible model, kill switch) runs the unchanged AVX-512 path [tron/h/tron/kernels/amx_attn_iface.hpp:33-53]. The only failure mode is a silently missed gain. On CPU-attention models that gain is up to 15 % TPS (section D).

**Inputs platformd must know**

- Package version. The first apt package with AMX code is tron 2026.09.23-5cf65b92. Packages up to 2026.09.18-3faba6d0 contain no AMX kernels: 0 `TRON_AMX_DISABLE` strings in the installed rinzler, and 0 AMX tile instructions under objdump on the 09-17 package [notebook/handoffs/claude_20260923_amx-benchmark-tps-regression-between-ci-runs.md:22,72; notebook/handoffs/claude_20260917_amx-in-nightly-ci-on-delphi-3bda.md:82-90]. No package was published 09-19 to 09-22 [notebook/artifacts/intel-amx/memory/first-ci-amx-row-20260922.md:24-26].
- Host eligibility. platformd needs no host gate. tron probes the CPU and kernel itself at the first attention call [tron/src/tron/kernels/amx_attn.cpp:58-72]. The host kernel must be 5.16 or newer [tron/src/tron/kernels/amx_attn.cpp:16]. delphi-3bda runs 6.8. The same package runs on AMD hosts with no regression: +0.4 % to +1.1 % TPS over five configs by hand, and -0.9 % to +2.5 % over the eleven AMD nightly rows (AMX row -0.3 %) [notebook/handoffs/claude_20260920_cmakepresets-json-amx-ci-pr.md:57-67; notebook/handoffs/claude_20260923_amx-benchmark-tps-regression-between-ci-runs.md:71,99-110].
- Model eligibility. Only the 128x4 shape reaches the kernel, fixed per model variant at compile time [tron/h/tron/kernels/amx_attn_iface.hpp:19-23,145-165]. In the nightly set: llama-3.1-8b, mixtral-8x7b, qwen-3-4b. Not eligible: llama-3.2-3b, llama-3.3-70b, qwen-2.5-32b, gemma-2-9b, gpt-oss-120b, gemma-4-31b [notebook/handoffs/claude_20260918_amx-compatible-128x4-models-in-nightly-ci.md:74-86]. The full registry audit (2026-08-19) found 8 of 30 model families eligible: qwen-3-4b-2507, llama-3-8b, llama-3.1-8b, mistral-7b, ministral-8b, mixtral-8x7b, phi-4, granite-3.3-8b. Only qwen-3-4b, llama-3.1-8b and mixtral have measurements [~/.claude/projects/-home-jhan-workspace-intel-AMX/memory/amx-tron-softattn-project.md:341-350].
- Attention placement. llama-3.1-8b and mixtral run CPU attention (their plugins do not force FPGA attention) [notebook/artifacts/intel-amx/memory/ci-mimic-20260918-campaign.md:173]. On llama-3.1-8b AMX scored 96.5 % (prompt 1024) and 98.9 % (prompt 8192) of decode attention keys [notebook/handoffs/claude_20261001-20261002_amx-attention-stats-comparison-at-3bda.md:92-93]. Mixtral's share was not measured. Its nightly row moved -0.2 % between the no-AMX and AMX packages [notebook/handoffs/claude_20260923_amx-benchmark-tps-regression-between-ci-runs.md:89]. qwen-3-4b runs FPGA attention, so AMX scores 0 decode keys and at most 0.6 % of prefill keys. gpt-oss-120b runs FPGA attention and has an ineligible shape (head size 64), so its CPU-scored 10.2 % goes to AVX [same handoff:95-100].
- CPU attention does appear on FPGA-attention engines in two measured cases. (1) FPGA K/V space exhaustion: about 800 "lose HW attention" warnings per night on qwen tp4 in the nightly MMLU phase, counted by `sw_fallback_total` [notebook/handoffs/claude_20260921-20260922_amx-vs-attention-on-fpga-prefill-on-qwen3-4b.md:139-150]. (2) 501 M EXE.AMX_BUSY cycles on a warm prefix cache with FPGA attention on 2026-09-17, cause still open [notebook/artifacts/intel-amx/memory/aof-amx-question-20260925.md:32-34]. Core sizing for FPGA-attention engines should keep headroom for this path.
- Memory. AMX adds no persistent copy of K or V [notebook/artifacts/intel-amx/amx_software_attention.md:25-28]. The kill switch needs no change to `--nr_hugepages` (128 x 1 GiB per tp2 engine) [notebook/artifacts/intel-amx/memory/l8bload-20260918-campaign.md:19-21]. This stops being true if the unmerged TRON_K_VNNI variant (tron PR #4424) ever ships (see rollback below).

**Responsibilities**

- Restart engines after a tron package install. apt never restarts engines. Engines keep running the deleted old binary until something re-execs them [notebook/handoffs/claude_20260917-20260920_nightly-ci-mimic-with-amx-and-vnni-k.md:96,270]. An explicit PATCH to `/api/config` restarted all units, and `POST /api/inference/down` then `/up` restarts them (observed on platformd 0.10.7) [notebook/artifacts/intel-amx/memory/ci-mimic-20260918-campaign.md:50-52,80-81]. The legacy posadm same-model provisioning on 0.10.7 did not restart [notebook/artifacts/intel-amx/memory/l8b-levers-20260919-campaign.md:22-24]. On 0.11 (on 3bda since 2026-09-21) the first nightly AMX row ran on "already provisioned" engines without a restart [notebook/artifacts/intel-amx/memory/first-ci-amx-row-20260922.md:18-20]. The gap is a restart when the package changes but the model does not.
- Own the kill-switch channel. TRON_AMX_DISABLE is read once at the first attention dispatch [tron/src/tron/kernels/amx_attn.cpp:58-86]. A disable therefore needs an engine restart with the variable in the engine environment. The only sanctioned places are `instance-N.env` (platformd-owned, per engine) and `/opt/positron/user/config.env` (host-global, loaded last, wins) [tron/packaging/systemd/rinzler@.service:7-26,43]. Today the instance env holds CPUAFFINITY, RZ_CLI_ARGS, RZ_FUSE_MOUNT_PATH and TRON_USE_SPECULATION, no free-form variable [notebook/artifacts/intel-amx/memory/ci-mimic-20260918-campaign.md:170]. Without a per-engine knob, the only rollback is config.env, which switches every engine on the host. The campaigns treat a non-empty config.env as a fault [same file:78-79]. Precedent: `inference.engines.<n>.use_speculation` (platformd 0.4.0, PR 65) becomes TRON_USE_SPECULATION in the instance env [notebook/handoffs/claude_20260825_aiperf-comparison-config-column.md:59-63]. Records say posadm `config.set` is a PUT to the settings API whose value lands in `instance-N.env`, never exercised for TRON_AMX_DISABLE [notebook/artifacts/intel-amx/memory/ci-amx-test-shapes-recommendation.md:49].
- Contract rules for any env channel: never set RZ_FUSE_MOUNT_PRESCOPED (double-nests the FUSE path) [tron/README.stats.md:19,41-47]; never carry SYSTEM_CONFIG (applied after argv, replaces `--devices` and `--app-cores`) [~/.claude/projects/-home-jhan-workspace-intel-AMX/memory/3bda-shared-with-bill.md:77-82]; a stale value in config.env overrides any per-engine value, so platformd must own or audit config.env [tron/packaging/systemd/rinzler@.service:26,43].
- Decide nothing about placement to get AMX. Enabling AMX does not change attention placement [notebook/artifacts/intel-amx/memory/amx-options-notion-page.md:27-38]. Switching qwen-3-4b to CPU attention to use AMX costs 20 % decode at 2 users per engine and 37 % at 8 users per engine (prompt 1024; section D). Keep USE_HW_ATTN unset.
- Know the rollback cost and its limits. The kill switch is not bit-exact (AMX and AVX differ in rounding order) [notebook/artifacts/intel-amx/amx_software_attention.md:57-61]. On llama-3.1-8b at 8 users, prompt 8192, rollback costs -13.8 % TPS and +128 % TTFT (34.6 s to 78.8 s), one repetition per arm [notebook/handoffs/claude_20261001-20261002_amx-attention-stats-comparison-at-3bda.md:77,86-88]. If TRON_K_VNNI (tron PR #4424, unmerged) ever enters the deb, TRON_AMX_DISABLE=1 no longer restores today's numerics (tron issue #4444), and FPGA-attention models regress (-5.0 % tp2, -11.0 % tp4, issue #4500) [notebook/artifacts/intel-amx/amx_software_attention.md:111-115; notebook/artifacts/intel-amx/memory/i4500b-policy-campaign.md:69-77]. The meaning of a platformd "disable AMX" control is therefore tied to the package version.
- The deployed llama-3.1-8b-instruct-good weights carry a tokenizer truncation at 4096 tokens. Prompts above 4096 are cut on that deployment, so the prompt-8192 figures do not occur on production llama-8b. The reachable gain tops out at the 4096 cell (+14.0 % at 8 users) [notebook/artifacts/intel-amx/memory/l8b-levers-20260919-campaign.md:39-62].

**Checks platformd should perform or expose**

- Installed binary has the kernels: the stripped rinzler contains exactly one `TRON_AMX_DISABLE` string when AMX is compiled in, zero otherwise [notebook/handoffs/claude_20260917_amx-in-nightly-ci-on-delphi-3bda.md:82-90].
- Running engine executes the on-disk binary (`/proc/<pid>/exe` not marked deleted) [notebook/artifacts/intel-amx/memory/ci-mimic-20260918-campaign.md:51-52,151-152].
- AMX actually ran. The AMX probe runs at the first software-attention dispatch of an eligible model, not at process start [tron/src/tron/kernels/amx_attn.cpp:76-86]. A readiness check therefore cannot see AMX. Only a post-traffic counter can. Two proofs exist. One is EXE.AMX_BUSY (needs root) [notebook/artifacts/intel-amx/memory/amx-busy-perf-counter.md:11-35]. The other is the TRON_ATTN_STATS FUSE leaves under `/model/<id>/attention/`, which exist only when the engine environment has TRON_ATTN_STATS=1 [notebook/artifacts/intel-amx/memory/attn-stats-pr-implementation.md:20,34]. That is a second per-engine variable platformd would have to write. Its cost is inside noise (-0.17 % at prompt 1024, +0.77 % at prompt 8192) [same file:65-67]. Without TRON_ATTN_STATS, tron prints no log line for AMX [notebook/artifacts/intel-amx/memory/amx-busy-perf-counter.md:31]. With it, one `[attn-stats]` summary goes to stderr at model destruction, which rinzler under platformd never reaches [notebook/artifacts/intel-amx/attention-stats-claude.html:413,423].
- Reference for the nightly owner, not a platformd check: the AMX row reads about 32.2 TPS to 32.5 TPS with AMX; 28.3 TPS means kernels missing or disabled [notebook/artifacts/intel-amx/memory/ci-amx-row-20260923.md:50]. The threshold lives in systems_test, and the row has no threshold as of 2026-09-21 [notebook/handoffs/claude_20260921_systems-test-pr-221-amx-ci-test.md:13,63].

**Placement decision that sets the gain.** The AMX gain grows with users per engine and prompt length. On llama-3.1-8b at prompt 1024: +0.2 % at 2 users per engine (not resolved), +3.9 % at 4, +12.9 % at 8 [notebook/artifacts/intel-amx/memory/l8bload-20260918-campaign.md:29-34]. At 2 users per engine and prompt 4096: +8.2 % [notebook/handoffs/claude_20260917-20260920_nightly-ci-mimic-with-amx-and-vnni-k.md:226]. At 8 users per engine and prompt 4096: +15 % (section D). platformd's users-per-engine choice therefore decides how much AMX is worth. Open placement question: Intel guidance is one AMX thread per physical core. tron pins one worker per logical CPU from `--app-cores` and does not check siblings. The 6962P `tron_cores` list mixes physical and sibling ids [notebook/artifacts/intel-amx/intel-amx.md:92-95; tron/config/resource-map.yaml:172-209]. Insufficient data: a paired run with and without sibling pairs in `--app-cores` would resolve it.

## B. Speed Select: what platformd must do

**What breaks if platformd gets it wrong**

- The policy is missing. On the boot default, 72 of the 80 busy worker threads per socket run at 2700 MHz [notebook/handoffs/claude_20260702-20260706_debug-flat-freq-on-ci-machine.md:12]. Measured cost against the shipped policy: decode per user -12.93 % (llama-3.1-8b tp2), -4.03 % (qwen-3-4b), -1.75 % (mixtral-8x7b), -2.57 % (qwen-2.5-32b) [notebook/artifacts/intel-speed-select/results/sst-ab-20260917/summary.md:24,27,30,33].
- Two writers of one CLOS table. The `intel-speed-select-state` oneshot re-applies its list at every boot and at every restart of the unit [notebook/artifacts/intel-speed-select/reminder.md:59-61,144]. The Ansible role rewrites that unit's config file on every run [same file:150-153]. A platformd-written state is replaced at the next boot or unit restart, unless one owner is chosen.
- Three commands change the policy without saying so. `core-power enable` resets the CLOS2 and CLOS3 windows. `turbo-freq enable --auto` rewrites the whole partition and clears all four windows [notebook/artifacts/delphi-flat-freq/docs/ALLCORE_CEILING_HETERO_CLAUDE_20260702.md:249-258]. `turbo-freq disable` keeps the table but lowers the grant from 4100 MHz to 3900 MHz on the 80-CPU CI shape. Under all-core load the 500 W package limit decides instead (3241 MHz to 3295 MHz) [same file:16-21,33-35].
- Enable-bit readback is misleading. Disabling turbo-freq or core-power never clears CLOS windows or associations, and the 2700 MHz cap stays enforced [notebook/handoffs/claude_20260702-20260706_debug-flat-freq-on-ci-machine.md:24,48,63]. A health check must read the class table and the per-CPU associations.
- A core list copied between machine types caps worker cores on the other type. On 2026-07-21 delphi-17cf (6960P) had the unit enabled with the same `FAST_CORE_RANGES` and MODEL_PATTERNS=6960P [notebook/handoffs/claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1043-1055]. The current 6960P map (changed 2026-07-24) puts tron cores at 75-84 and 85-94, of which 75-78 and 87-94 fall outside that list [tron/config/resource-map.yaml:168]. Inferred, not measured: 12 of the 80 6960P tron cores sit in CLOS3 there. A `get-assoc` read on delphi-17cf would confirm it.
- Idle reads do not show the class. An idle CPU reads the 800 MHz floor in either class. A frequency check must sample a loaded CPU or it reports a false clamp [notebook/handoffs/claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1076-1079].
- Nothing re-asserts the policy during uptime. The BIOS resets the table at every boot and the boot unit re-applies the list once [notebook/artifacts/delphi-flat-freq/docs/flat_freq_tests-README.md:40-42; notebook/artifacts/intel-speed-select/reminder.md:134]. Zero CLOS writes followed over the observed window [flat_freq_tests-README.md:417-419]. Any later association write by any tool stays until the next boot or unit restart. Experiment kits with hard-coded restore lists would silently undo the FE un-clamp [same file:2621-2625].

**Inputs platformd must know, per machine type**

- Vendor and model pattern. Only Intel map entries are candidates. The policy must be a no-op on AMD types [tron/config/resource-map.yaml:4-153].
- Expected logical CPU count (288 on the 6962P), one anchor CPU per 24-core power domain (0, 24, 48, 72, 96, 120 on the 6962P; no other type measured), and the HT sibling of every CPU from the kernel's topology, not assumed as N+144 [notebook/artifacts/intel-speed-select/reminder.md:71-73,80-81; notebook/artifacts/delphi-flat-freq/docs/ALLCORE_CEILING_HETERO_CLAUDE_20260702.md:5].
- The derivation rule. `tron_cores` plus `peer_cores` plus siblings into CLOS0, everything else into CLOS3, gives the same 112 physical cores as the deployed `FAST_CORE_RANGES` (224 fast CPUs, 64 capped) by computation [tron/config/resource-map.yaml:190-208; notebook/artifacts/intel-speed-select/reminder.md:34,74]. `peer_cores` is a subset of `tron_cores` on both Intel entries. A live read on 2026-09-17 confirmed the counts and 17 sampled cores [notebook/artifacts/intel-speed-select/results/sst-ab-20260917/part1-config-coverage.md:17,19]. The map lists some die-A cores by sibling id (151-158, 223-230) on purpose, so that each engine's lowest core sits on die B [tron/config/resource-map.yaml:185-189]. platformd must map each id to its physical core first. Unlisted cores (15-23, 87-95 on the 6962P) go in the capped class [notebook/artifacts/intel-speed-select/reminder.md:93-101]. Reason: with every CPU in CLOS0, decode was 0.9 % to 1.8 % lower [notebook/artifacts/delphi-flat-freq/docs/flat_freq_tests-README.md:213]. Note: platformd today emits only devices, tron_cores, dev_cores, numa_nodes and rinzler_cores. `peer_cores` would be a new map field for it to read [notebook/artifacts/intel-amx/exec/results/p0perf-20260913/platformd-instance-1.env.txt:12-15].
- Existing reference code: `gen_tron_flatfreq.py` reads a map section and emits the command sequence, supports `--also-boost dev,rinzler,platform` and `--revert`. Its output matched the boot service except one extra `core-power disable` per anchor [notebook/artifacts/delphi-flat-freq/gen_tron_flatfreq.py:1-24,34-40; notebook/handoffs/claude_20260917_speed-select-recollect-paths-after-move.md:74-81,100].
- Which roles go fast, by evidence: `tron_cores` (shipped), plus `rinzler_cores` (the FE un-clamp: +1.12 % +/- 0.21 decode at 8 users, +2.44 % +/- 1.05 at 24 users, gpt-oss-120b tp4 in the serving path, 5 of 5 draws positive, +6 W to 8 W package power, 2026-07-23) [notebook/handoffs/claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1709-1713,1777]. `dev_cores` and `platform_cores` stay capped on runtron evidence only: making cores 72-78 fast changed runtron decode by +0.15 +/- 1.01 % (llama-3.1-8b), -0.53 +/- 0.41 % (qwen-3-4b), +0.03 +/- 0.31 % (mixtral), +0.13 +/- 0.11 % (qwen-2.5-32b) [notebook/artifacts/intel-speed-select/results/sst-ab-20260917/summary.md:26-35]. runtron places no thread on cores 72-74. No serving-path measurement of dev or platform cores exists.
- The window definitions. CLOS0 2700 MHz to 4400 MHz, CLOS3 800 MHz to 2700 MHz, both weight 0 [notebook/artifacts/intel-speed-select/reminder.md:91-92,117-118]. Two classes are sufficient. A three-tier layout was identical within noise [flat_freq_tests-README.md:216-228]. Rule for any future floor: `--min 800 --max 2000` did not hold cores at 2 GHz under contention (they fell to about 800 MHz); `--min 2000 --max 2000` held all 48 control CPUs at exactly 2000 MHz [ALLCORE_CEILING_HETERO_CLAUDE_20260702.md:278-284].
- Prerequisites platformd checks but does not own: `/dev/isst_interface` from three kernel modules, and an executable tool at a known path. The tool at `/opt/intel-speed-select/intel-speed-select` is the same size as a locally patched build with the root-only guard removed, not a distro package (byte identity not checked) [notebook/artifacts/intel-speed-select/reminder.md:39-45,56-58]. Privilege is root or a sudoers entry for that exact path [notebook/handoffs/claude_20260702-20260706_debug-flat-freq-on-ci-machine.md:52,56]. rinzler runs without root, so no engine-side component can write CLOS state. platformd or a helper it owns is the only candidate writer. One host (delphi-3af6) came up without the drivers after a reboot [notebook/handoffs/codex_2026-06-30-2026-07-02_root-cause-flat-freq-not-working.md:52].
- Per-host expected frequency differs. The 6960P tops out at 3.9 GHz against 4.4 GHz on the 6962P [notebook/handoffs/claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1049-1050]. Same-SKU hosts differ in BIOS (92011500 on 3bda, 92011600 on 3c51) [notebook/handoffs/claude_20260810_compare-bill-delphi-3c51-with-delphi-3bda.md]. The under-load expectation is per machine type and per host BIOS, set from one loaded read per host after install.

**Decisions platformd must make**

- Ownership: replace the boot service and the Ansible role, or verify only and leave the writer where it is. One owner, one re-apply entry point for experimenters and CI.
- Scope on a shared host. The class windows are set per 24-core power domain and shared by every process on that die [ALLCORE_CEILING_HETERO_CLAUDE_20260702.md:5; notebook/handoffs/claude_20260623_intel-xeon-6-core-frequency-configuration.md:62]. Associations are per CPU. Per-engine windows are not possible. Per-engine class membership is. On delphi-3bda Bill owns socket 0 and jhan socket 1. The September campaign changed only socket-1 associations and wrote nothing to socket 0 [notebook/handoffs/claude_20260916-20260917_speed-select-retune-delphi-3bda.md:15; notebook/artifacts/intel-speed-select/reminder.md:193-202]. A whole-machine apply from platformd would rewrite the other owner's associations at every provisioning. Decision needed: whole-host policy with one owner, or associations scoped to the slices platformd provisions.
- Failure policy when prerequisites are missing (no device, no tool, no sudoers entry): block provisioning, warn and continue, or mark the host degraded. delphi-3af6 already is in this state (see E). A silent skip reproduces today's drift. A block takes a host down over a 13 % decode item.
- Timing: at boot before the first provisioning, or at each provisioning. One apply takes 2 s [notebook/artifacts/intel-speed-select/reminder.md:120-126]. A CLOS change took effect on a running rinzler during the July A/B blocks (2700 MHz to about 4000 MHz between 5-minute blocks, no restart) [flat_freq_tests-README.md:780-800]. Ordering against rinzler start is therefore a performance question, not a correctness one (inferred from that design).
- The first policy change platformd would apply: the FE un-clamp, not deployed as of 2026-09-17 [notebook/handoffs/claude_20260916-20260917_speed-select-retune-delphi-3bda.md:5,153,158].

**State platformd must own:** the desired class table and per-CPU association derived from the map, the boot-default ranges as the rollback target (32 fast CPUs) [notebook/artifacts/intel-speed-select/reminder.md:137-140], and a readback snapshot before every change [notebook/artifacts/delphi-flat-freq/docs/core_power_help_source_distill.md:78-93]. A ready field list exists: `sysconfig_snapshot.sh` captures BIOS, microcode, all 288 CLOS associations, uncore range, governor, RAPL limits, hugepage state, boot-service config, tron and platformd versions plus map md5, and instance envs [flat_freq_tests-README.md:1691-1713].

**Checks platformd must perform**

- Before apply: tool executable, device present, CPU count and machine type match [notebook/artifacts/intel-speed-select/reminder.md:79-80].
- During apply: the tool can fail on part of a CPU list and still exit 0. The result must be checked per CPU (288 `assoc:success` lines for a full association) and the output must contain neither "fail" nor "error" [notebook/handoffs/claude_20260702-20260706_debug-flat-freq-on-ci-machine.md:67]. Some commands print benign MSR warning text while still applying [intel-vs-amd/speed-select/distilled_knowledge.md:14].
- After apply: turbo-freq enabled on every anchor, both windows exact, and the per-CPU association table equal to the desired table derived from the map (today 224 fast and 64 capped on the 6962P; 232 and 56 after the FE un-clamp) [notebook/artifacts/intel-speed-select/reminder.md:115-118; notebook/handoffs/claude_20260916-20260917_speed-select-retune-delphi-3bda.md:153].
- Host knobs outside the CLOS table: intel_pstate active, governor performance, turbo on, and uncore range 0.8 GHz to 2.5 GHz. All of these read correct on the June 2026 host while the clamp was active [notebook/handoffs/codex_2026-06-30_check-speed-select-config.md:35-54]. A BIOS uncore cap costs 6 % to 7 % decode with no CLOS signature [flat_freq_tests-README.md:1789-1799].
- Under load: the maximum Bzy_MHz across the fast set should read about 3.9 GHz to 4.1 GHz. An exact 2700 MHz with zero variance is the class-window cap. A plateau that moves by tens of MHz (3241 MHz to 3260 MHz) is the package power limit [notebook/artifacts/delphi-flat-freq/docs/speed_select_intuition.html:198-202]. 4400 MHz is the top of the allowed window, not a frequency the policy delivers. The measured grant with 80 loaded cores is 4100 MHz [same file:326-341].
- After a rollback or reboot: read the class table and associations, not the unit status. In Gate C the two-class layout was still present after a boot with the unit masked [notebook/handoffs/claude_20260730-20260802_tron-moe-randomness-investigation.md:148-156].

**Outputs to expose:** applied/verified status, per-class CPU counts, the derived fast set, the frequency observable under load, and package power. Under the shipped policy socket 1 drew 48 W to 60 W more than on the boot default, whole-run means, depending on the model [notebook/artifacts/intel-speed-select/results/sst-ab-20260917/summary.md:3,24,27,30,33].

## C. Shared and cross-cutting requirements

- **Machine-type detection.** tron enables AMX from CPU feature bits, not from the map [tron/h/tron/kernels/amx_attn_iface.hpp:42-47]. The frequency policy today uses a hand-copied list. If platformd derives the fast set from the map, it must use the same server-type match tron uses: vendor, physical cores, NUMA node count (NUMA node = one memory domain, here one socket), model pattern [tron/src/system/system.cpp:1221-1248]. Only the two Intel entries carry a policy. Of the Intel hosts, only 3bda and 3bd6 are recorded running it.
- **Stale map cache.** platformd 0.10.7 reads the map once at startup with no watcher [notebook/handoffs/claude_20260722_resource-map-change.md:25,49-54]. The nightly removes and reinstalls the tron deb [notebook/artifacts/intel-amx/memory/rinzler-unit-expert-replicas-750.md:36-40]. The deb replaces the map and its postinst only daemon-reloads, so platformd keeps its cached copy [claude_20260722_resource-map-change.md:91-97]. This caused provisioning from a stale map twice in July (ab40) [claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1635-1638]. delphi-3bda ran platformd 0.11.0 on 2026-09-23 [claude_20260923_amx-benchmark-tps-regression-between-ci-runs.md:77]. Whether 0.11.0 still caches is not recorded (Insufficient data: a read of the 0.11 source would resolve it).
- **Numbering.** platformd can change which `rinzler@N` unit serves which `--instance` slot at every provisioning [flat_freq_tests-README.md:1893-1895]. In ab34 the mapping was identical across 6 draws, so it can change, not does change [same file:2370-2371]. The `--instance` slot fixes the cards and cores (for example `--instance 2,4` = cards 90/93, cores 73,217) [notebook/artifacts/intel-amx/memory/p0perf-20260913-campaign.md:22-23]. 0.11 adds named engines default-K [notebook/handoffs/claude_20260921-20260922_amx-vs-attention-on-fpga-prefill-on-qwen3-4b.md:22]. A per-engine policy must be stated per `--instance` slot.
- **Per-engine channel.** `instance-N.env` is rewritten by platformd at every provisioning. It is the only per-engine setting platformd owns [rinzler-unit-expert-replicas-750.md:159-161]. Two `rinzler@.service` files exist: platformd ships one under `/usr/lib/systemd/system/`, and the tron deb ships `/etc/systemd/system/rinzler@.service`, which wins [~/.claude/projects/-home-jhan-workspace-intel-AMX/memory/rinzler-unit-expert-replicas-750.md:57-58]. Hand edits to tron's unit are deleted by the nightly's apt remove and install [notebook/artifacts/intel-amx/memory/rinzler-unit-expert-replicas-750.md:36-43]. Only a drop-in under `rinzler@.service.d/` survives [same file:151-163]. `/etc/default/intel-speed-select-state` is overwritten by the next Ansible run [notebook/artifacts/intel-speed-select/reminder.md:150-152].
- **Verification must be physical, not status.** For AMX: the `TRON_AMX_DISABLE` string count in the installed rinzler plus a rising AMX counter under load. For SST: association readback of every CPU plus Bzy_MHz of CLOS0 cores above 2700 MHz under load. In ab56 the register changed on all 60 read-backs while every busy core stayed at 3900 MHz [claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:2003,2158-2160].
- **Acceptance tests need more than one night.** Decode TPS on gpt-oss-120b varies between provisionings with a CV of 2.4 % in serving tests [flat_freq_tests-README.md:2351-2352] and 3.6 % to 4.7 % across 77 draws [claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:2034-2035]. Over 13 nightlies, TPS CV was at most 0.73 % for 10 of 12 configs; gpt-oss tp4 and qwen-3-4b tp4 were the noisy ones [ci-mimic-20260918-campaign.md:47-49]. For those two, effects below about 5 % need a toggle within one running instance or several provisionings averaged.
- **Open risk on boot-time apply.** Within-night dispersion on 3bda stepped from 1.54 % to 4.67 % on 2026-07-09, and on 3bd6 on 07-12/13, each coinciding with that host's double reboot plus policy install. Live CLOS and TF toggles were excluded as the cause. The boot-time apply remains a suspect. 3af6 (no policy) also disperses, so the policy is not required for the effect [claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:2020-2027,2056-2062]. The discriminating test (Gate C) was never run.
- **AMX and frequency interact.** AMX puts a core into a lower turbo license. Single-core: 3.59 GHz under AMX against 3.89 GHz under AVX, package power flat [notebook/artifacts/intel-amx/memory/amx-vs-avx-sense.md:23; notebook/artifacts/intel-amx/pr3879/make-sense-amx-vs-avx/draft.md:88]. Under a 1-user, 8K-to-16K prompt serving load, AMX-busy cores ran 3.52 GHz to 3.55 GHz against 3.75 GHz for AVX [amx-vs-avx-sense.md:52-54]. The SST turbo table on 3bda sets the 54-core high-priority group to 4100 MHz at level 0 and 3900, 3600, 3200, 3000 MHz at levels 1 to 4 [notebook/artifacts/delphi-flat-freq/sysconfig-snapshots/delphi-3bda_20260720_045931.txt:52-60]. Which level AMX lands in is not measured; Granite Rapids exposes no CORE_POWER.LVL* events [amx-vs-avx-sense.md:55-56]. No run has measured Bzy_MHz with the CLOS policy active and AMX on at the same time (Insufficient data: a turbostat read during an AMX serving run). A CLOS0 pass threshold must come from a measurement under AMX load, not from the table.
- **CI schedule on delphi-3bda.** The ci-runner stop timer POSTs `/api/inference/up` at 02:45 UTC [ci-mimic-20260918-campaign.md:81]. The nightly reinstalls tron at about 03:39 UTC and keeps the machine until about 13:18 UTC [same file:44-46]. The nightly also runs `apt-get upgrade`, which restarts platformd only when a new platformd package exists [ai-runs/systems_test/scripts/cfgdut.py:136-157]. Restarting platformd during reconciliation aborts it, and with auto_start=false it does not resume [claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1233-1236]. A policy apply step that restarts platformd, or runs from an outside unit during the nightly's provisioning, breaks the nightly.
- **platformd's own cores.** platformd 0.10.7 runs with affinity 0-287 (all 288 logical CPUs) [notebook/artifacts/intel-amx/memory/l8bload-20260918-campaign.md:47]. While its engines are down and health checks fail it uses about 34 % to 38 % of one CPU [same line; notebook/handoffs/claude_20260715-20260716_ef720667-regression-investigation.md:53-54]. Those cycles can land on `tron_cores`. Pinning to `platform_cores` (0 and 72 plus siblings) removes that jitter source.
- **Machines of the same type run different policies.** On 2026-07-10 3bda ran the tron80 list from positron-infrastructure PR #165. On 2026-07-12 3bd6 ran the tron112 list [flat_freq_tests-README.md:363-366,692-699]. Only a read of each host catches this today. A benchmark on one 6962P does not predict another.

## F. Open questions for John

1. Does platformd want to own the Speed Select policy (replace the boot service and the Ansible role), or only verify it at provisioning? The hazard is two writers of the same CLOS table: the Ansible role re-renders the config on every run, and the boot service re-applies it at every boot, so a platformd-written policy is overwritten at the next boot or Ansible run.
2. If platformd derives the fast set from the map, which roles belong in it? `tron_cores` (shipped; `peer_cores` is a subset). `rinzler_cores`: +1.12 % decode at 8 users in the serving path (gpt-oss-120b tp4, July 2026). `dev_cores` and `platform_cores`: no measurable change in runtron (within 0.6 %, four models, 2026-09-17); no serving-path measurement exists.
3. Will platformd offer a per-engine environment knob (for TRON_AMX_DISABLE, TRON_ATTN_STATS, and possibly USE_HW_ATTN and TRON_HWATTN_EARLY_LAUNCH_MIN_B, the tron variable for the batch size below which FPGA attention launches early, +7.7 % TPS at 2 users per engine [notebook/handoffs/claude_20260918-20260919_tron-4500-fpga-attention-decode-tps-loss.md:28-29,276])? Records say posadm `config.set` lands in `instance-N.env` after a restart, never exercised for these variables. posadm 0.12.1 `config set` cannot carry typed lists [claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1236-1238]. One engine restart with the variable set plus a 20 s AMX-busy probe would settle it.
4. Does platformd 0.11 still read resource-map.yaml only at startup? That behaviour was observed at 0.10.7 in July 2026. The nightly's apt remove and install re-installs the map, and tron's postinst only daemon-reloads [tron/packaging/postinst:42].
5. Does a same-model provision (identical config) trigger a restart at 0.11? At 0.10.7 the July record calls an identical re-PATCH untested [claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1677-1680], a 2026-09-18 note says every PATCH restarted all units [ci-mimic-20260918-campaign.md:80], and a 2026-09-19 note says a same-model provision through legacy posadm did not restart [l8b-levers-20260919-campaign.md:22]. If 0.11 behaves the same, platformd must restart engines itself after a package change, or the new AMX binary never runs.
6. What should a health check report when the frequency under load disagrees with the policy readback? In June 2026 the enable bits read "disabled" while the CLOS associations still held the boot partition and the cores ran capped [notebook/handoffs/codex_2026-06-30-2026-07-02_root-cause-flat-freq-not-working.md:38]. The recorded method is two layers: `get-assoc` readback plus turbostat under load [claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:1273]. The reporting rule when the layers disagree is not recorded.
7. If platformd applies the policy at provisioning, when does it run relative to (a) the `ci-runner-stop` timer at 02:45 UTC, which POSTs inference/up, and (b) the nightly's apt reinstall under the CI lease? The boot-service-versus-ci-runner ordering was flagged on 2026-07-07 and never closed [claude_20260702-20260729_debug-3bda-flat-freq-run-ci-tests.md:384-385]. The lease file came later (2026-09-14).
