GDN AMX Design
GDN and AMX: design for Qwen3.5 4B
2026-11-20. Measured on delphi-3b35 (our test server), on our half of it. tron commit 72e1191804 (open pull request #3696). Status: baseline, prediction and design. Nothing is built yet.
Short version
In Qwen3.5 4B, 24 of the 32 layers are GDN layers (GatedDeltaNet: a layer that keeps a memory matrix of fixed size), and tron (our inference program) runs no AMX code (Intel's matrix instructions) for this model today.
We propose three changes, and the table below gives what each one is predicted to do to the time to first token.
Nothing is built yet, so every gain is an estimate (est.) from the baseline that we measured on delphi-3b35.

1. What GDN is, seen from llama-3.1-8b
llama-3.1-8b has 32 layers. Every layer is a full-attention layer [Ref20].
Qwen3.5 4B has 32 layers too. 24 are GDN layers and 8 are full-attention layers [Ref1, Ref2].
A GDN layer does the job of attention. It mixes what earlier tokens said into the current token. It uses a different mechanism.

[SVG]Figure 2. What one new token does in one layer. Gray boxes run on the FPGA cards. Colored boxes run on the host CPU. Attention looks at a list that grows. GDN rewrites a matrix of fixed size.

The 8 full-attention layers of Qwen3.5 4B differ from llama's too. They have 16 query heads of 256 values and 4 KV heads [Ref17]. llama-3.1-8b has 32 heads of 128 values and 8 KV heads [Ref20].
tron's AMX attention kernels accept only 128-wide heads [Ref6].
tron's FPGA attention accepts only 64-wide and 128-wide heads [Ref7].
So every attention layer of this model runs the AVX-512 path, at every prompt length.
The attention statistics confirm it. AMX scored 0 K tokens in all 36 runs [Ref9].
[SVG]Figure 3. CPU arithmetic per generated token, computed from the model shape. It is a count, not a timing. Attention costs 262,144 multiply-adds per context token in llama-3.1-8b and 65,536 in Qwen3.5 4B. GDN costs 37.7 million multiply-adds per token at every context length. By this count GDN looks small at long context. Section 3 shows that its time is not small.

3. Attention metrics: where the time goes
What was turned on. TRON_ATTN_STATS=1 in every run [Ref8].
Pass wall. The statistics give the wall time of every pass.
Attention busy time. The statistics give the time that the attention workers spend on attention jobs, without their waits for input. The page divides the sum over all workers by the 40 workers.
Attention wait. The statistics also give the wall time of the attention jobs on one worker, waits included. It is 2.3 to 2.6 ms longer than the busy time per prefill pass with 1 user, 19 ms with 8 users, and 0.3 to 0.4 ms per decode step. The worker waits for K and V from the FPGA cards. This wait stays in the rest.
What the statistics do not see. GDN. They have no hook in the GDN code [Ref8].
How GDN was timed. With tron's trace, one traced run per cell. The slice named GatedDeltaNet covers the GDN host work of one layer on one thread [Ref10]. The GDN wall of a layer runs from the first thread's start to the last thread's end.
The rest. Pass wall minus GDN wall minus attention busy time. It is FPGA matrix multiplies, small host kernels and the attention wait.
Limit of the decode numbers. A traced decode step is 3 to 28 % longer than an untraced one. A traced prefill pass is 0.2 to 3.1 % longer. The decode table divides the traced GDN wall by the untraced step. So its GDN shares are upper values. The last column gives the share inside the traced run.

What the numbers say
The GDN time of a prefill pass does not depend on the prompt length. It is 20.2 to 20.3 ms with 1 user and 160 ms with 8 users.
One GDN step takes 6.3 to 6.5 us on 14 of the 16 GDN threads in prefill. The 2 threads on CPUs 108 and 109 take 3.8 to 4.0 us. Their cores run at 4.00 GHz [Ref11]. The mean over the 16 threads is 6.1 us.
The slowest thread sets the wall. One GDN layer takes 0.85 ms for 128 tokens with 1 user. That is 6.6 us per token.
A stand-alone benchmark of the recurrence alone takes 3.06 us per value head (1 thread, 2 MiB state) [Ref11]. The convolution takes 0.50 us per key head. The benchmark is not the same quantity as the traced GDN step. In tron the recurrence takes about 2.8 us per value head (est.: 6.4 us minus 0.8 us of other work, for 2 value heads).
Hypothesis: the GDN step is limited by moving the state, not by arithmetic. A value head's matrix is 64 KiB. The L1 cache is 48 KiB. Each token passes over the matrix twice. The arithmetic alone needs 0.95 to 1.16 us per value head (est.), against about 2.8 us (est.) in tron. Task 1 of the plan confirms or rejects this.
The same GDN step takes 13 to 16 us in decode (mean over the threads, traced runs). Hypothesis: in decode the state comes from outside the core's own caches for every token, and the check for invalid values reads it once more [Ref4]. The open points name the measurement that confirms or rejects this.
Only 16 of the 56 threads run GDN. With 8 users each of the 16 threads has 8 chains to run, one after another. The GDN wall with 8 users is 7.9 times the wall with 1 user in prefill, and 5.2 to 6.8 times in decode.

4. Prediction, made before any test of the solution
Method
The layers of a pass run one after another. Inside a layer the FPGA projections, the host work and the next projection run one after another.
So a time saved in GDN or in attention shortens the pass by the same amount.
pass_new = pass - GDN_wall x (1 - 1/s_gdn) - attention_busy x (1 - 1/s_attn) + rest x clock_cost
TTFT_new = TTFT - passes x (pass - pass_new)
ms_per_token_new = ms_per_token - (step - step_new)
Measured inputs: pass wall, attention busy time, number of passes, TTFT and decode speed (attention statistics and runtron, section 2), and the GDN wall (trace, section 3).
Measured today for this prediction: the core clock under AMX on delphi-3b35, and the cost of the tile and FMA instructions [Ref11].
Estimated inputs: the factors in the table below. Each one comes from operation counts, measured instruction costs, or an earlier measurement on delphi-3bda.

How to read the prediction
Part 0 alone (new loop order, no AMX, same bits): TTFT falls by 15 to 24 % (est.). Range: 12 to 26 %.
Part A (AMX block kernel for GDN): TTFT falls by 18 to 29 % (est.). Range: 11 to 32 %.
What AMX itself adds for GDN. At the working values Part A gives 3 to 5 points more than Part 0. At the low values Part A is 1.0 to 1.6 points worse than Part 0, because the lower core clock costs more than the kernel gains. Part 0 gives about 83 to 83 % of the fall that Part A gives.
Part B (AMX attention kernel for 256-wide heads): TTFT falls by 5 to 25 % (est.). Range: 4 to 29 %. The gain grows with the prompt length.
Parts A and B together: TTFT falls by 35 to 43 % (est.). Range: 22 to 49 %.
Decode: no change at the working values (est.). Range: -5.3 % to +7.8 %. All of it comes from Part B. This is the weakest part of the prediction. It rests on measurements from delphi-3bda and on a clock ratio.
What would prove the prediction wrong
Part 0: the measured GDN step on a 2.70 GHz thread is above 3.6 us. The estimate is 2.6 to 3.5 us.
Part A: the measured GDN step of the block kernel is not below the measured GDN step of Part 0. Then Part A adds nothing. The estimate is 1.7 to 2.5 us against 2.6 to 3.5 us.
The method: the GDN wall of a pass gets shorter by some milliseconds, and the pass wall gets shorter by less. Then the layers do not form one serial path.
Seen in the same data. It is not an AMX matter.With 8 users the 16 GDN threads each run 8 chains in a row while 40 attention workers wait.
Spreading the 128 work items over all 56 threads would cut the GDN wall to about 3/8 of today's value (est., from the work-item count).
Prefill, 8 users, prompt 1,024: that is about 100 ms of the 362 ms pass (est.).
Decode, same cell: at most 1.8 ms of the 8.1 ms step (est., an upper value because the GDN wall comes from a traced run).
It needs a scheduling change, not a new kernel. It does not help 1 user.

5.2 Part 0: a chain path that keeps the state in L1 (no AMX, same bits)
Today. For each token the kernel passes over a 64 KiB matrix twice [Ref3]. The matrix does not fit the 48 KiB L1 cache. So every pass moves it between L2 and L1.
Fact used. Each value column of S is its own recurrence. Column c depends only on the keys, the decay, the beta and column c of the values.
New order. Split each value head into two halves of 64 columns (32 KiB). Run all tokens of the chain on one half. Then run them on the other half. The half stays in L1 for the whole chain.
Three phases per chain. Phase 1, per token: convolution, normalization, decay and beta, saved in a small buffer. Phase 2: the recurrence over the chain, half by half. Phase 3, per token: norm and output gate.
Layout. Each half is stored as one contiguous block of 32 KiB in a buffer of its own. In the layout of today's working copy the rows of a half would compete for the same places in L1 [Ref18].
Bits. Unchanged. Every column sees the same operations in the same order.
Why it is in an AMX design. It gives about 83 to 83 % of the fall that Part A is predicted to give (est.). It also builds the chain entry point and the per-token buffers that Part A needs.
5.3 Part A: the AMX block kernel
Idea. Process a block of 32 tokens at once. The state is read twice and written once per block. Today it is read twice and written once per token.
Why AMX fits. The three large products become matrix times matrix. A tile product then uses all 16 rows. The kernel needs 18.5 tile products and 272 FMAs per value head per token. Today's kernel needs about 5,120 vector operations (est. count).
The FP32 state. AMX multiplies bf16 by bf16 only. Each FP32 value is split into 3 bf16 pieces whose sum is exactly the FP32 value. The product is computed once per piece, and the 3 results are added [Ref18].
Same algebra as the reference. Hugging Face Transformers uses this block form (block size 64) for every call with several tokens. vLLM and SGLang ship an AMX kernel that is built on it [Ref14].
Block size 32. One block of K, Q and their products fits the L1 cache. The cost model has its lowest value near 32 [Ref18].
Stage 1 in detail. The kernel takes 16 value columns of S0 at a time. AVX-512 code splits them into 3 pieces in a 12 KiB buffer that stays in L1. Then 48 tile products run on that buffer.
Stage 4 in detail. AVX-512 code scales Delta and splits it into 3 pieces. Tile product 3 builds the update. AVX-512 code then writes the decayed start state plus the update.
Clock. So tile work and AVX-512 work take turns about every 0.2 to 0.4 us (est.). The clock probe covered turns of 34 ns (1.90 GHz) and of 25 us (2.40 GHz) [Ref11]. Insufficient data for the length between. Task 3 of the plan measures it.
If the clock is 1.90 GHz at this turn length. The alternative is to split the whole state first and to run all tile products in one long run. The pieces of one value head are then 96 KiB, which do not fit L1.

5.4 Numerics: what changes and what the contract should say
Part 0 changes no bit. Each value column of S is its own recurrence. Part 0 runs the columns in two halves, with all tokens of the chain per half. Each column still sees the same operations in the same order. Two independent scripts confirm equal bits for outputs and state [Ref18].
Part A changes the order of the FP32 sums. The result is close to today's result, and it is not equal. Three numeric checks on synthetic inputs compared the block form with today's kernel. 0.005 to 0.10 % of the bf16 output words differ [Ref18].
The differences are small. An output above 1 % of the typical output size differs by one bf16 increment. Outputs nearer to zero differ by up to 46 increments [Ref18].
The error is of the same size as today's. The checks compare both kernels with a float64 computation. The block form's output error is 0.3 to 1.1 times the error of today's kernel. Its state error is 0.3 to 3.2 times today's [Ref18].
Long chains with a decay near 1. After 1,024 tokens the two kernels differ by up to 33 FP32 increments in the state. Today's kernel is then 27 increments away from float64, and the block form 9 [Ref18].
The 3-piece split is exact. For every FP32 value of size 9.9e-32 or larger the three bf16 pieces add up to the value. A script checked every finite FP32 bit pattern [Ref18].
Below 9.9e-32. A piece can be a subnormal number. TDPBF16PS treats subnormal inputs and subnormal results as zero. The part lost is below 1.2e-38 [Ref18].
Two pieces are not enough. In the checks their state error against float64 is 7.5e-8 to 1.7e-6, which is 18 to 61 times the error of today's kernel [Ref18].
Decay factors are built by multiplication only. Dividing two running products gives wrong results when the product becomes very small inside a block [Ref18].
Fallback. If the start state or an intermediate result of a block is not finite, the block runs on the token path. The state is still untouched at that point. One check found a case where the block form overflows and today's kernel does not [Ref18].
What the tests require today. The recurrence is checked with an absolute tolerance of 1e-7. Other tests require equal bytes between the prefill path and the decode path. One test fixes 320 output words to PyTorch values [Ref16].
These tests use a small head. Their state has 16 key rows and 80 value columns. A block path that is limited to 128 by 128 never runs in them. So they stay unchanged, and they do not cover the new paths. New tests at 128 by 128 are needed.
Contract proposed for Part A. The block path stays within a stated error band of the token path. It runs only for the 128 by 128 shape, only for full blocks of 32 tokens on a fixed grid of token positions, and only when AMX is on. The token path stays the reference.
Consequence to accept: prefill and decode. With Part A, prefill and decode of the same text can differ in rare output bits. Hugging Face Transformers has the same property. It uses the block form for prompts and the token form for single tokens [Ref14].
Consequence to accept: resumed prompts. tron can resume a prompt from a stored state at any token position. A block that is cut by such a position runs on the token path. So a resumed run and a run from the start can differ in rare output bits. Today all paths give equal bytes [Ref16].
5.5 Part B: attention kernels for 256-wide heads
Same method as the existing kernels. K and V are bf16 already. No split is needed.
QK (queries times stored keys, which gives the scores). 8 groups of 32 dimensions instead of 4, into the same 4 result tiles. That is 32 tile products per query token, page and KV head. Today's 128-wide kernel has 16 [Ref6].
PV (softmax weights times stored values). 4 groups of output dimensions instead of 2. That is 32 tile products per query token, page and KV head. Today's kernel has 16.
Buffers grow. The packed queries of one token grow from 4 KiB to 8 KiB. The PV output grows from 8 KiB to 16 KiB.
Eligibility check. shape_ok accepts head width 256 with 4 query heads per KV head. The dispatch, the kill switch and the attention statistics work as today.
Numerics. The same two known differences from AVX-512 as today's kernel: the weights are rounded to nearest, and the sums are added in another order. The existing error-band tests extend to the new shape.
Tile rows. Each kernel call serves one query token. So 4 of 16 tile rows carry data, in prefill and in decode. Today's kernel has the same property.
Clock (hypothesis). The probe read 1.90 GHz when 4 tile products alternate with 64 FMAs, and 2.40 GHz for runs of 4,096 tile products [Ref11]. One visit of a page has 64 tile products between pieces of AVX-512 work. This case was not probed. Task 4 measures it.
Risk: the page does not fit L1. One page of a 256-wide head holds 64 KiB of K and V. At 128-wide it holds 32 KiB, which fits the 48 KiB L1 cache while the tokens of a prompt chunk visit the page. The low case of section 4 covers this.
Optional later step for prefill. Serve 4 query tokens per kernel call. Then all 16 tile rows carry data, and a page is loaded once per 4 tokens. The bits equal those of the single-token AMX kernel. It is not part of the prediction.

5.7 What stays outside this design
AMX is not used for GDN decode. One token fills 1 or 2 of the 16 tile rows. Users cannot share a tile, because each sequence has its own state.
Decode has options without AMX. The check for invalid values reads the state before every token. The state part of this check could be folded into the first loop of the recurrence. This keeps the bits. Est. gain: 1.1 to 1.2 times on the decode recurrence [Ref18].
A state stored in column halves could help decode more. Together with the folded check: est. 1.2 to 1.55 times on the decode recurrence [Ref18]. It needs a new layout of the stored state. It is not part of this design.
Threads. 16 of 56 threads run GDN while 40 attention workers wait. Using all threads would cut the GDN wall of a prefill pass with 8 users to about 3/8 (est.). It changes the scheduler and the code generator, not a kernel.
A state stored in 16 bits is rejected. A state in fp16 or in bf16 could be loaded into tiles without a split. In a numeric check with synthetic inputs, 7 to 36 % of the bf16 output words change with an fp16 state, and 32 to 81 % with a bf16 state [Ref18].

Open points
Core clock under AMX in tron. The probe measured stand-alone loops only. In the block kernel, tile work and AVX-512 work take turns every 0.2 to 0.4 us (est.). In the attention kernel they take turns about every 1 us (est.). The probe covered turns of about 34 ns and of about 25 us. Insufficient data for the lengths between. Tasks 3 and 4 measure them.
Costs that the block kernel's cost model does not count. A tile load right after an AVX-512 store of the same data waits until the data is in the cache (Intel optimization manual, section 20.15). Small decay values put subnormal numbers into the AVX-512 parts, which the CPU handles on a slow path. Task 3 measures both. The low case of section 4 leaves room for them.
Mixed core clocks on this server. 3 of the 29 probed CPUs run at 4.00 GHz and 26 run at 2.70 GHz [Ref11]. All factors in section 4 are for 2.70 GHz threads. A server with another clock setup needs its own baseline.
CPU share of the rest of a prefill pass on the 16 GDN threads. It decides how much a lower clock costs outside the kernel. Insufficient data. A trace of the main thread with the matrix-multiply events turned on would give it.
Real value ranges of state, decay and beta in this model. The numeric checks used synthetic inputs. A capture of the GDN inputs of one real prompt would give the size of the error band.
Chains that do not start on a block boundary. After a resume from a stored state, a chain of 128 tokens holds only 3 full blocks. Then 96 of its 128 tokens run in the block kernel, and the other 32 run on Part 0. The 6 cells of this page do not show this case.
Cause of the slow decode step. The hypothesis in section 3 is not confirmed. A stand-alone benchmark of one decode step on a cold 128 KiB state would confirm or reject it. Cache-miss counters on one GDN thread would do the same.
The numerics contract. The owners of the GDN code must decide whether prefill may differ from decode in rare output bits. Part 0 does not need this decision. Part A does.
Model status. The model's registry entry says that its tokens are not yet valid. The design should be checked again when the pull requests that add the model are merged.
