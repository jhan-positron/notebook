Typed cache tensors for packed V and native K

Issue #4525 · Assigned to jhan-positron · Repository: positron-ai/tron

Short version

Give packed V its own storage type and use layout-specific cache arguments at the kernel boundary. Native K keeps its existing storage and view. Add this interface on main first, then adapt PR #4424 to use a separate packed-K owner.

This revision incorporates the round-3 review and its verifier corrections. It specifies packed-storage access, fixture construction, template constraints, and the remaining verification steps. The decision record separates proposed choices from reviewer agreement. Section 9 records the changes and remaining implementation or approval work.

2. The reviewer's comments and proposed decisions

The problem is that a bare bf16* pointer does not identify the cache layout. The same pointer type can describe native K, packed V, or the child's blocked packed K. The proposed types make those kernel arguments distinct. [Saved GitHub comments and issue]

The issue author's reading was that the address formula belongs in the view rather than in a separate layout type. That addresses the reviewer's reservation about a separate layout type. In the sketch, the layout is a template argument of both the owner and the view. It is not an ownership stage between them. The reviewer expressed doubt about that separation, rather than a final decision. [Saved GitHub comments and issue]

Retain: private packed storage, restricted construction of views, mutable-to-read-only conversion, typed kernel arguments, and optimized bulk operations.

Choose: one concrete view per layout. This repeats a small amount of view plumbing when the child adds packed K. It avoids a public layout-policy template.

Limit the parent: expression reads and existing row operations. Defer slices, iteration, generic expression assignment, and expression constructors until a caller needs them.

Native K: reuse its current storage and view types. The issue author requested native-K typing in issue #4525. The parent changes the K parameter of qk_rowmajor_128x4 from a pointer to the existing read-only matrix view. This is an issue-author scope decision beyond the sketch's packed types.

Representation | Position from the start of the plane, in bf16 elements | Where selected | 

Native K and AVX2 V | token * D + dimension | First pull request. Keep the existing row-major path. | 

Packed V | (token / 2) * (2 * D) + 2 * dimension + token % 2 | First pull request, for V in the build with 16 fp32 values per vector instruction. | 

Blocked packed K | ((((dimension / 32) * (R / 16) + token / 16) * 16 + (dimension % 32) / 2) * 16 + token % 16) * 2 + dimension % 2 | PR #4424 only. Keep the existing layout-selection condition. Keep the kernel restricted to 64 tokens × 128 dimensions. | 

R is the stored token count. D is the stored dimension count. The packed-K formula uses groups of 32 dimensions and groups of 16 tokens. Each 16-token by 32-dimension panel is one AMX B tile. Let s = dimension / 32 and c = token / 16. Its base is (s * (R / 16) + c) * 512 bf16 elements. Inside it, use the packed-V formula on a 32-row by 16-column plane with row dimension % 32 and column token % 16. The in-panel offset is ((dimension % 32) / 2) * 32 + 2 * (token % 16) + dimension % 2 bf16 elements. Across the plane, dimension groups are outermost and token blocks are next. Swapping the two plane coordinates alone does not produce this order. [S1] [S10]

The new V storage type requires a positive even number of rows. Its column count must be positive and divisible by chunk_size, the selected SIMD width. This satisfies the sketch’s positive-dimension rule. The 16-lane packed page::set_v, the page method that writes one V row, still requires widths divisible by 32 dimensions. The packed scaled_v_expr supports 64, 128, 256, or 512 dimensions. The unchanged 8-lane path requires head_size / chunk_size % 8 == 0. There is no new 8-lane V-save wrapper. Type constraints do not expand kernel support.

5. Interface design

These declarations specify the proposal. They have not been compiled. Keep the types in namespace tron and follow the repository's attributes and formatting.

// h/tron/tensor/kv_cache_fwd.hpp: declarations only, no intrinsics.
struct bf16;
template <typename T, bool aligned, bool dma,
          typename Dim, typename Stride> struct view;
template <typename T, bool aligned, bool dma,
          typename Dim, typename Stride> struct const_view;

template <size_t Rows, size_t Cols> class v_vnni_tensor;
template <typename T, size_t Rows, size_t Cols> class v_vnni_view;
template <typename T, size_t Cols> class v_vnni_row;

template <size_t Rows, size_t Cols>
using native_k_view = view<bf16, true, false,
    std::integer_sequence<size_t, Rows, Cols>,
    std::integer_sequence<ptrdiff_t, Cols, 1>>;
template <size_t Rows, size_t Cols>
using const_native_k_view = const_view<bf16, true, false,
    std::integer_sequence<size_t, Rows, Cols>,
    std::integer_sequence<ptrdiff_t, Cols, 1>>;

These declarations are in namespace tron. Use the struct key for the existing bf16, view, and const_view definitions. The new writable native_k_view alias is declared for symmetry. No parent caller requires it. Declare all five view parameters without defaults. Include only the standard headers needed for sizes and integer sequences. The explicit strides avoid depending on a default declared in an intrinsics-bearing header. [S15]

Owner and expression reads

v_vnni_tensor contains exactly one 64-byte-aligned bf16 array. It allocates no separate memory. Default construction leaves values uninitialized. Keep construction, copying, and destruction trivial. The owner does not inherit expr.

Provide as_view() & and as_view() const &. Delete both rvalue forms, including const &&. Keep same-type copy and move operations defaulted. Store no pointer to the owner's own array.

v_vnni_view<T,R,D> inherits expr<view_type,R,D>. v_vnni_row<T,D> inherits expr<row_type,D>. Restrict T to bf16 or const bf16. A row stores its pair address and parity by value. It outlives a temporary matrix view while the owner remains alive.

The packed types have no DMA template parameter or static DMA flag. No proposed consumer requires one. An arbitrary logical row is not a contiguous DMA input. The backing arena can still be DMA-safe memory. Do not inherit views<>, whose leaf rows must be contiguous.

The matrix supplies operator[] returning its row expression. The named host-tensor constructor reads row chunk() values. Add no dim, element, const_element, shape0(), or valid() member without a caller. No null-view state or default view constructor is proposed. Leave the rank-1 expression concept unchanged. The named V expression consumer is the ordinary host-tensor construction check in section 8. Production V paths continue to use bulk operations. Native K remains compatible with dotter, the existing query/key dot-product helper. [S2] [S3] [S4]

One cache row-write rule

append_v_row is this design's name for the sketch's V store_row. The name records partner zeroing. The child's K store_row does not zero a partner.

// Parameter families, not new wrapper types.
append_v_row(v_vnni_view<bf16, R, D> dst, size_t token,
             const_view<Source, true, Dma, seq<D>, sseq<1>> src);
load_row(v_vnni_view<const bf16, R, D> src, size_t token,
         view<Destination, true, Dma, seq<D>, sseq<1>> dst);
copy_token(v_vnni_view<bf16, R, D> dst, size_t dst_token,
           v_vnni_view<const bf16, R, D> src, size_t src_token);

Source is bf16, fp16, or float. Destination is bf16 or float. Dma is deduced from the ordinary contiguous row view: the source of append_v_row or the destination of load_row. The model source already has a view with dma = false. Use dma = false when wrapping GOF scratch or raw-array test fixtures. Explicitly construct read-only source views where template deduction would otherwise see writable views. The shown alignment flag is true: preserve the existing aligned load/store contract and use 64-byte-aligned rows at every migrated call site. The flag describes a precondition; wrapping a pointer does not establish alignment. Add alignas(64) to the V fixture in t/heterogeneous_scheduler_compile.cpp. [S16]

append_v_row moves today's packed set_v bodies into h/tron/tensor/v_vnni.hpp. An even destination writes its row and zeros its odd partner in one pass, without reading the destination. An odd destination merges into the initialized pair and preserves its even partner.

load_row moves today's get_v loops. Wrap existing caller-owned scratch in the ordinary contiguous destination view.

copy_token moves the four source/destination parity branches of append_v. Preserve overlap restrictions and fresh destination ranges. Even destinations zero their partner. Odd destinations preserve it.

Do not add copy_plane for V. The existing append path copies token rows, including when a requested range spans a whole page. Range splitting and completion copying remain in cache code. Defaulted same-type owner copying is sufficient if an ordinary owner copy is needed.

Preserve book::fill_random and its fill_storage_slot helper. This existing test-support operation fills an entire K/V block without interpreting coordinates. It is an explicit exception to the raw-access rule and must not establish readiness. Retain its comment about bypassing partner zeroing. The parent adds no new claim about the existing whole-block cast's C++ aliasing behavior. [S16]

V padding and write ordering

A packed-V weighted sum rounds an odd live-token count up to a complete pair. The unused odd row must be zero: a NaN multiplied by a zero weight still contaminates the sum. The row-major path reads exactly the live-token count. [S5]

→

Append even tokenNew even valuesOdd row: all zero

→

Append odd tokenEven values preservedNew odd values

The even append must clear the partner every time the pair is reused. This is an operation sequence, not a timing diagram.

Write | Destination read? | Partner result | 
Even cache append | No | Odd row becomes zero | 
Odd cache append | Yes, pair must be initialized | Even row is preserved | 
Direct element update | No read of other elements required | Other elements unchanged; this does not establish cache readiness |
