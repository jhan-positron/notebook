from claude - Short version: the reviewer's comment is anchored on the Haskell hunk that PR #4424 itself added (the helper-side `save_k_helper` emission in `runHelperStatement`), so his suggestion changes what that hunk emits. If the helpers are to call `save_k`, a generator change is unavoidable, and this PR's generator change is the smallest one: one callee string and one literal. A version with no generator change would have to give up the sharing, or move the helpers' participation into the wait primitives, where it does not work as a simple hook.

**Where the comment sits.** The comment (https://github.com/positron-ai/tron/pull/4424#discussion_r4065141577) is attached to `ingest/src/TronCpp.hs`, inside PR #4424's hunk that replaced `AttentionStmt _ -> []` by the case that emits `save_k_helper<geometry, op>(q_batch->outer_batch, k, worker_ix, n_workers)` on the helper side. The "new function" in "Why do we need to introduce a new function for this?" is `save_k_helper`, the name that hunk emits. "Extend `save_k` itself with a `worker_ix` argument and call it consistently from both the main thread and the helpers" means: the helper side emits `save_k(..., worker_ix, n_workers)` and the main side `save_k(..., 0, n_workers)`, the way the generated kernel calls already pass `worker_ix` on the helpers and `0` on the main thread (`kernelCall`). That is what this PR does.

**How much Haskell this PR changes.** Against the branch head, the code lines in `TronCpp.hs` are two: the callee string `"save_k_helper"` becomes `"save_k"`, and the main-side argument list gains the literal `0`. The rest is comments and the expected call texts in `LoopyTronSpec.hs`. Against main, which is what the PR #4424 reviewer reads, `ingest/` is 49 lines added and 5 removed at the branch head, and 48 added and 5 removed with this PR. So this PR adds no Haskell. It renames.

**What reverting the Haskell changes gives.** With `ingest/` back at the branch head 6b939d25d2, the generated helpers call `save_k_helper(k, worker_ix, n_workers)` and the main thread calls `save_k(k, n_workers)`. The C++ then has to keep a function named `save_k_helper`, which is the entry point the reviewer asked about. Any C++ shape (a forwarding wrapper, a macro) keeps that second name in every generated plugin. I have not reverted on the branch, because that state does not build without `save_k_helper`.

**A design with no generator change at all (relative to main, where the helpers emit nothing at the attention statement).** Three ways, none of which keeps the measured gain cleanly:

| way | what changes | why it falls short |
|---|---|---|
| no sharing: the main thread stores every row with the block save | C++ only: drop the window protocol | Save K per prefill layer 346 us (tp2) / 353 us (tp4) instead of 80 / 60 us with sharing; the row-major base is 274 / 281 us, so the VNNI store would cost more than the store it replaces. Measured TTFT at prompt 1024 (qwen-3-4b, 8 users): block save alone 3.135 s (tp2) / 2.208 s (tp4), with sharing 3.098 s / 2.108 s, row-major base 3.143 s / 2.197 s. Dropping the sharing gives back 37 ms (tp2) and 100 ms (tp4), and leaves the branch's TTFT equal to the base at tp2 and 11 ms worse at tp4. |
| the helpers help from inside the wait they enter right after the statement (`channel::start_reading` and the per-item latch wait in `common.hpp`) | C++ only, in primitives every channel read uses | a helper in that wait is asleep in a monitored wait (`indefinitely()` in `src/system/mwaitx.cpp`) that wakes only when its own latch word changes, so it never sees a window the main thread opens later. Keeping the gain would need polling in the shared wait primitives, a type-erased store call in the window, and an "all units stored" wait on the main thread. The second entry point then moves from the plugin API into `channel` and the latch code. |
| other threads store K (attention workers, the thread pool) | C++ only | every pool worker is either a main helper or an attention worker (`n_attn_workers = tp.num_workers() - n_main_helpers`), so there is no idle pool thread. The attention workers are idle during Save K only in the first pass of a prompt; from the second pass on they run the Ready sections (attention over the pages of earlier passes), so the gain is not kept. A thread also has no way to learn its worker index without the generated argument. |

(Per-layer numbers: the 2026-09-15 traces in `status/store-remedies-report.html`, section 3, qwen-3-4b, 8 users x 128 tokens per pass. TTFT numbers: the same report, section 4, arms a / ab / base, n = 3 at tp2 and n = 2 at tp4.)

**My reading.** The suggestion asks for one entry point called from both sides, not for an unchanged generator. The current change is the smallest generator change that gives that, and it follows the generator's own convention for calls both sides make.
