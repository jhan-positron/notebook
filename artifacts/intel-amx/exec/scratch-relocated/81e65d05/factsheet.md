# Fact sheet: AMX involvement in attention, campaign of 2026-10-02 on delphi-3bda

## Short version

The AMX attention kernel serves exactly one shape: head size 128 and 4 query heads per KV head on a bf16 executor. llama-3.1-8b and qwen3-4b have that shape, gpt-oss-120b (head size 64, 8 query heads per KV head) does not, so gpt-oss can never record an AMX visit in either arm. With USE_HW_ATTN unset, llama runs CPU software attention and the two ingested models run FPGA attention with a software remainder, and the stats report prints 7 lines per model state with the class labels of origin/main, not the 5 lines of the September samples.

## Words used here

- tron: the inference program under test. runtron: its command-line tool. rinzler: the production server.
- AMX, AVX: two CPU instruction sets. AMX-on arm: TRON_AMX_DISABLE unset. AMX-off arm, also "kill switch": TRON_AMX_DISABLE=1.
- AoF: attention on the FPGA, called "HW attention" in tron logs. Software attention: attention computed on the CPU by AVX or AMX.
- bf16: 16-bit floating point format of the activations.
- kv_mul: query heads per KV head. GQA: grouped query attention, the same ratio.
- KV page: a 64-token block of the KV cache.
- Visit: one call of apply_page_tok for one (query token, KV page, KV head) triple. Visit paths: amx, avx, empty.
- Ready pass / pending pass: the first software pass over pages whose K/V were already present, and the second pass after the K/V wait. These are not FPGA passes.
- Ingested model: a model whose C++ plugin is generated by tron's ingest tool, served under a slug starting with "ingested-".
- FUSE leaves: the files under the stats mount where tron publishes counters.
- The nightly: the systems_test workflow system_ci_granite_rapids_72_rinzler_OCI that runs against delphi-3bda. The lease: the file /run/lock/systems-test-ci.lease that the nightly holds.
- platformd: the service manager on 3bda that starts and restarts rinzler engines.
- Our half: socket 1 of 3bda with FPGA cards 90/93/b9/bc.
- origin/main: tron commit 9c88327931. Every file:line below is at that commit unless a different path is given.

## 1. AMX shape rule and per-model verdict

### The gates, in order

- Gate 1 (compile time, shape). shape_ok(head_size, kv_mul) is true only for head size 128 and kv_mul 4 [h/tron/kernels/amx_attn_iface.hpp:136-138, 148-150]. Decisive line: `return model_head_size == HEAD_SIZE_128 && model_kv_mul == GROUP_HEADS_4;` [amx_attn_iface.hpp:149]. The predicate checks nothing else (not n_kv_heads, not n_layers).
- Gate 2 (compile time, scalar). eligible<scalar> = shape_ok && query_scalar_ok, and query_scalar_ok means the activation scalar is bf16 [amx_attn_iface.hpp:158-165]. Executors tp1/tp2/tp4 and perm_tp1/2/4 use bf16 activations [h/tron/models/common.hpp:77-79, 94-102; h/tron/hardware/btensor.hpp:21]. The host executor uses float and host_fp16 uses fp16, so those two compile no AMX path.
- Gate 3 (process start). available() needs CPUID AMX-BF16 and AMX-TILE bits, XCR0 bits 17 and 18, a successful arch_prctl, and TRON_AMX_DISABLE not exactly "1" [src/tron/kernels/amx_attn.cpp:58-72]. The result is cached once per process [amx_attn.cpp:76-86]. So TRON_AMX_DISABLE selects a whole run.
- Gate 4 (per model, in the dispatch). `constexpr bool amx_eligible = eligible<activation_scalar>(geometry.kv.head_size, geometry.kv_mul()); const bool amx_on = amx_eligible && available();` [h/tron/models/self_attention.hpp:1535-1538]. When amx_on is false, no Q is packed and no tile region opens [self_attention.hpp:1549-1556, 1628-1635]. The AMX branch sits inside `if constexpr (amx_eligible)`, so an ineligible shape compiles no AMX code at all [self_attention.hpp:1630, 1879-1880].
- Gate 5 (per (query, page) pair). The verified wording is in Refuted R1. In short: a packed Q must exist and is_dense_amx_page must hold [self_attention.hpp:1710-1721, 1881-1883].

### Why exactly 4 and exactly 128

One GQA group of 4 query heads x 128 dims is packed as 4 live columns plus 12 zero columns of a 16-column tile panel [amx_attn_iface.hpp:23-27]. The 16 tile rows are filled by K tokens (64 tokens = 4 tiles of 16 rows), not by query heads [amx_attn_iface.hpp:199-210]. Head size must be 128 because one K tile row covers four 32-dim steps [amx_attn_iface.hpp:199-210]. shape_ok compares with == on both values, so kv_mul 8 or kv_mul 2 does not fit [amx_attn_iface.hpp:148-150].

### Head size matters twice

- The AMX gate requires 128 (above).
- The FPGA gate accepts 64 or 128: `(head_size == 128 || head_size == 64) && n_kv_heads <= HW_MAX_KV_HEADS && (n_heads / n_kv_heads) <= HW_MAX_GQA` [h/tron/models/model.hpp:726-736]. HW_MAX_KV_HEADS is 8 and HW_MAX_GQA is 31 [h/libpos.hpp:57, 62]. Head size 64 is zero padded to the bitfile's 128 cells [h/libpos.hpp:72, 82-84].
- So gpt-oss is FPGA-eligible but never AMX-eligible. llama and qwen3 are eligible for both.
- The EMEM gate (on-card memory for one shard) passes for 64 heads by arithmetic: max_shards_for_emem(64, 64, 1024) = min((1024/64) x 128 / 1024, 4096/1024) = 2 shards [h/libpos.hpp:147-153; constants at :77, 79, 81; shard_tokens 1024 at h/tron/gof.hpp:36]. The header's own comment says "64 heads -> 2 shards" [h/libpos.hpp:142-143].

### Sliding windows and sinks do not bypass the AMX gate or the stats

- Sliding-window layers never go to the FPGA. The ingest marks them software_only, and the checker rejects a sliding-window operation marked hardware-capable [ingest/src/TronCheck.hs:1118-1120; ingest/src/LoopyTron.hs:1141-1148]. The runtime refuses them twice more [h/tron/models/kv_cache.hpp:402-405; self_attention.hpp:506-514; model.hpp:1554-1556]. So the 18 even layers of gpt-oss run entirely on the CPU, with the AVX dotter, in both arms.
- The window is folded into the same loops as everything else. A page wholly outside the window is skipped before any visit and is not counted [self_attention.hpp:1612-1614]. Individual tokens outside the window are skipped inside the dotter loop [self_attention.hpp:1927-1930]. A visit that finds no token returns empty [self_attention.hpp:1939-1942]. is_dense_amx_page requires the page's first token inside the window [self_attention.hpp:1720].
- Sinks are applied once per (token, KV head) in finish_job after all pages are folded, as a running-softmax update with a zero V vector [self_attention.hpp:1282-1308, 2047-2059, 2081-2096]. The AMX kernel writes the same v*/s*/m* state that the sink update reads [self_attention.hpp:1792-1808]. Sinks add no visits and no counters.

### What the stats header and counters say about shape

- The header carries amx_compiled, amx_available, n_kv_heads, kv_mul, head_size, n_layers, page_size [self_attention.hpp:476-485; h/tron/models/attn_stats.hpp:726-733]. amx_compiled is true in every TRON_AMX_DISPATCH=ON build for every model. amx_available is available() of the process, so it reads true on the AMX-on arm and false on the kill-switch arm, also for gpt-oss. No header field says "shape eligible". The reader derives it from head_size == 128 and kv_mul == 4.
- avx_full_page_visits counts every AVX visit whose relevant_k_tokens equals 64, with no shape input [attn_stats.hpp:200-216]. For gpt-oss this counter is nonzero in both arms even though no AMX kernel could serve those pages. The comment's reading "AMX-eligible volume that did not take the AMX path" holds only for a shape-eligible model (see Refuted R15).
- A dense page must also be "ready": a full page written in the current forward fails is_dense_amx_page [attn_stats.hpp:200-203; self_attention.hpp:1719, 1586-1589]. So prefill-heavy forwards show avx_full_page_visits even with AMX on. The prompt/decode mix changes the AMX share independently of the shape gate.
- Per-token path sets: each token job gets a bit set over {avx=1, amx=2, fpga=4}, folded into 8 names: none, avx, amx, avx+amx, fpga, fpga+avx, fpga+amx, fpga+avx+amx [attn_stats.hpp:140-152, 553-576, 589-594]. Derived expectation (not a measurement): gpt-oss shows avx and fpga+avx only; llama shows avx, amx, avx+amx; qwen3 under FPGA attention can show fpga+avx, fpga+amx, fpga+avx+amx.
- The dispatch test confirms the gate on CPU fakes: a full 64-token page runs pack, QK and PV once; a 63-token page packs but runs no kernel; float and fp16 executors never call an AMX entry point [t/t_amx_dispatch_dtype.cpp:9-19, 68-72].

## 2. gpt-oss attention path and stats coverage

### Where the plugin comes from

- ingested-gpt-oss-120b is a generated plugin. The repo holds only the registry entry and a Python export helper: `- name: ingested_gpt_oss_120b / hf_id: openai/gpt-oss-120b / source: generated / moe_router: cpu / slug: ingested-gpt-oss-120b / executors: [host, tp1, tp2, tp4]` [config/models.yaml:645-657]. `git ls-tree -r origin/main | grep -i gpt.oss` lists only ingest/export/gpt_oss_export.py and t/t_generate_ingest_1_gpt_oss_20b.cpp.
- The build generates the plugin at build time with -DBUILD_INGEST_MODELS=ON [nix/model-plugins.nix:27-31; bin/ci/model-plugins/generate.py:57-72]. The geometry is read from the HF config.json at ingest time [ingest/src/Loopy.hs:621-624].

### The generated plugin uses the shared attention code

- The generated state holds `tron::model<plugin>::state& outer_state` [ingest/src/TronCpp.hs:1067]. Every attention operation becomes one `outer_state.run_attention_job<...>(...)` call in run_attention_worker [TronCpp.hs:1605-1635, 1428-1441, 30-31].
- The model.hpp wrapper passes the cached per-operation hardware decision into self_attention::state::run_attention_job and then calls finish_attention_job [model.hpp:2205-2219, 2189-2192]. The generated plugin cannot bypass the hooks inside run_attention_job.
- forward() owns the attn_stats::forward_scope (forward wall time T1 and the decode_like / prompt_or_mixed class) [model.hpp:1735-1739, 1764, 1826]. The generated run() enqueues run_attention_worker per attention worker [TronCpp.hs:1322-1327].
- Hook sites all live in self_attention.hpp and model.hpp; neither ingest/ nor llama.hpp calls a hook. The complete verified site list is in Refuted R5.

### Per-visit decision for gpt-oss

- apply_page_tok decides per (query token, KV page, KV head): amx when a packed Q exists and the page is dense, else avx when at least one K token is relevant, else empty [self_attention.hpp:1879-1890, 1939-1942, 1974]. For gpt-oss the amx branch is compiled out, so only avx and empty occur.
- The window size is a per-operation runtime value; full-causal operations carry illegal_sliding_window = INT_MAX [TronCpp.hs:463-464; model.hpp:614-615; self_attention.hpp:192, 1501-1503].
- Sinks run in finish_job in both the software join and the hardware join [self_attention.hpp:1301-1307, 1320-1324, 1309-1314, 2085-2102]. Sink spans come from the generated plugin [TronCpp.hs:553-557, 578-583; model.hpp:616-622].

### FPGA candidacy of gpt-oss layers

- Per operation: the ingest marks an operation kv_slot_candidate only when it writes K/V and is FullCausal with the standard geometry [ingest/src/AttentionHardware.hs:14-18; LoopyTron.hs:1146-1148]. So only the 18 full-attention (odd) layers can be FPGA layers. The 18 sliding-window (even) layers always run in software.
- Per model: gpt-oss passes the static shape gate (head 64 accepted, 8 KV heads = HW_MAX_KV_HEADS, GQA 8 <= 31) [model.hpp:731-735; h/libpos.hpp:57, 62, 76-77, 82-84]. Generated plugins set `force_hw_attn = true` [TronCpp.hs:243]. With USE_HW_ATTN unset and FPGA devices present, the full-attention layers run on the FPGA [model.hpp:742-744, 762; src/tron/models/hw_attn_config.cpp:37-40].
- Live confirmation on 3bda (2026-10-01 19:55 UTC journal, read with sudo by a refuter): `HW attention enabled for model ingested-gpt-oss-120b-tp4: max_layers=36 engagement=127 kv_slot_extent=36` with hw_attn_params 64/8/64, gqa 8. The 2026-09-16 runtron log shows the same line with `hw_slots: 18` [exec/results/wedperf-20260916/rt/gptoss-tp4-8u__fpga__base__rep1.log:149]. 18 slots = the 18 full-attention layers.
- On those FPGA layers the CPU still computes attention for query positions below the engagement point (127) and for the per-query causal tail ranges [h/libpos.hpp:91; model.hpp:2662, 2669; self_attention.hpp:1504-1517]. See Refuted R6 and R11 for the verified wording.

### MoE routing is outside the attention stats

- The attention hooks sit only in self_attention.hpp and model.hpp. `git grep -n -i 'amx\|attn_stats\|note_' origin/main -- h/tron/models/mixture_of_experts.hpp` returns nothing. AMX in this tree is used only by the attention kernel (files: amx_attn_iface.hpp, attn_stats.hpp, kv_cache.hpp, self_attention.hpp, src/tron/CMakeLists.txt, amx_attn.cpp). MoE has its own counter group [model.hpp:1756-1762]. The gpt-oss router runs on the CPU [config/models.yaml:652]. The PR 4596 body says MoE stats are not covered.

### Stats object lifetime

- The stats object is created per model state in the self_attention state constructor, keyed by cfg.id [self_attention.hpp:488-491]. FUSE leaves live under /model/<model_id>/attention/. One [attn-stats] summary goes to stderr when the state is destroyed [README.stats.md:234-246]. runtron builds one state per prompt batch. Collection needs TRON_ATTN_STATS exactly "1" [attn_stats.hpp:8-12, 161-172].

## 3. Nightly attention mode per model, and the nightly shapes

### The switch

- The per-model default is plugin_t::force_hw_attn. Only generated plugins define it, and they define it true [model.hpp:742-748, 750-763; TronCpp.hs:243]. llama.hpp does not define it, so llama defaults to off. `git grep -n force_hw_attn origin/main` finds only model.hpp:743-744, TronCpp.hs:243 and a test plugin.
- USE_HW_ATTN is an override, not the only gate. Unset: plugin default. 0 or unparsable: off for all models. N > 0: on for all eligible models, and N is also the engagement point rounded up to a page boundary [h/tron/models/hw_attn_config.hpp:12-21; src/tron/models/hw_attn_config.cpp:22-30, 37-40]. The verified full chain of gates is in Refuted R9 and R10.
- runtron uses the same switch as rinzler [h/runtron/stream_generate.hpp:41, 803-811; model.hpp:1542-1546]. So the campaign with USE_HW_ATTN unset reproduces the nightly's modes. The AMX arms change only the software kernel, not the FPGA/CPU split [self_attention.hpp:1535-1538].

### Per model

- llama-3.1-8b-instruct-good-tp2: CPU software attention. It is a hand-written llama.hpp model [config/models.yaml:284-287]. The log line is `HW attention disabled for model '...': default off for this model` [model.hpp:1613-1633]. The 3bda journal of 2026-10-01 19:55 UTC shows that line for llama-3.1-8b-instruct-good-tp4 (128/8/32, 32 layers). No USE_HW_ATTN appears anywhere in systems_test (local e4727d5 and upstream b1ccc0b). The "-good" suffix is a quantization tag that tron strips, not an attention flag [llama.hpp:476-480]. Its shape passes every FPGA gate, so USE_HW_ATTN=1 would turn FPGA attention on for it [llama.hpp:204-205; kv_cache.hpp:450-451; model.hpp:726-736]. No such run exists on record.
- ingested-qwen-3-4b-instruct-2507-tp2: FPGA attention on all 36 layers, with the software exceptions below [config/models.yaml:743-756; model.hpp:1542-1546, 1587-1594]. The enabled line reads `kv_head_size: 128 n_kv_heads: 8 n_heads: 32 gqa: 4 pre_attn_scalar: 0.088388346 hw_slots: 36` [exec/results/wedperf-20260916/rt-results.txt:2169].
- ingested-gpt-oss-120b-tp4: FPGA attention on the 18 odd layers (above the engagement point), CPU software attention on the 18 even sliding-window layers and on the software remainder of the odd layers. Live line confirmed on 3bda 2026-10-01 (section 2).
- Software exceptions under FPGA attention: every sequence position below 127 is computed in software [h/libpos.hpp:83-90; hw_attn_config.hpp:18-22]. When the driver's HBM bypass space is exhausted, the caller degrades that work to software attention [src/pos/driver.cpp:890]. The 2026-09-22 qwen3-4b campaign saw 2804 such warnings at prompts 4096-8192 and none at 1024 [memory q4b-fpga-20260921-campaign].
- The AMX kernel is a fast path inside software attention only [amx_attn_iface.hpp:19-23]. Under FPGA attention, AMX can only touch the software remainder, and only for the fitting shapes.

## 4. Exit-report format at origin/main

### When and how many lines

- print_report runs from the model_stats destructor only when the switch is on; a state with zero forwards and zero visits prints nothing [attn_stats.hpp:388-390, 815-828].
- One report is exactly 7 stderr lines per model state, preceded by an empty line: 1 header line, then for each class (decode_like first, prompt_or_mixed second) a totals line, a forwards line and a k_tokens-per-layer line [attn_stats.hpp:829-847]. No per-worker or per-layer JSON goes to stderr; those exist only as FUSE leaves [attn_stats.hpp:789-811, 941-948].
- Several reports per log are possible: runtron builds one state per prompt batch, and each prints when destroyed [attn_stats.hpp:71-74; README.stats.md:270-272]. The 09-29 CPU sample has one report per log (7 lines, grep -c = 7 in q3-4b-tp2-8u-p1024__cpu__headon4__rep1.log).
- An EAGLE draft state shares the target's model_id; its only discriminator is `"eagle":true` and its leaves live under attention_eagle/ [attn_stats.hpp:326, 727-731, 918-919]. Key reports on (model_id, eagle).

### Line kinds

1. `[attn-stats] model <model_id>: {JSON}` with 14 keys in this order [attn_stats.hpp:726-733; facts filled at self_attention.hpp:476-490]:
   - on: the switch was on for this state.
   - model_id: runtron model name (cfg.id).
   - eagle: EAGLE draft state.
   - amx_compiled: built with TRON_AMX_DISPATCH (true for every model in this build).
   - amx_available: available() of the process (true on the AMX-on arm, false on the kill-switch arm, for every model including gpt-oss).
   - n_kv_heads, kv_mul (query heads per KV head), head_size, n_layers, page_size (64).
   - n_workers: app-pool workers = rows per class per layer.
   - active_workers: pool workers that ran at least one attention job [attn_stats.hpp:708-720].
   - tsc_hz: TSC frequency in Hz to convert every *_cycles key to seconds; 0 until calibration is published.
   - switch: the constant string "TRON_ATTN_STATS=1".
   - Sample: `{"on":true,"model_id":"ingested-qwen-3-4b-instruct-2507-tp2","eagle":false,"amx_compiled":true,"amx_available":true,"n_kv_heads":8,"kv_mul":4,"head_size":128,"n_layers":36,"page_size":64,"n_workers":27,"active_workers":20,"tsc_hz":2699988471,"switch":"TRON_ATTN_STATS=1"}` [09-29 CPU log line 144].

### FUSE leaves and mount location
