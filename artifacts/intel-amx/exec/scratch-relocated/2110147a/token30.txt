The question this page answers (added 2026-08-30, after review)
jhan asked: "Is my understanding right - there is no proof AMX introduced regression - or would you rather say, it is proved that AMX did not introduce regression? And, the exact root causes are not identified even though some suspicions are strong, e.g. the token was picked from a tie at AMX-off config, so change could cause change."
Answer. The first wording is the correct one, and one part of the second can be said more strongly.
"Proved that AMX did not introduce a regression" - no. Testing cannot prove the absence of a defect; it can only fail to find one. Every test that could catch the defect classes we listed came back clean, and the caveats say what such tests cannot see: a small fault that changes every block in the same way, inputs we did not test, one prompt and one model, and the fact that the AMX-on run was not repeated with the same binary.
"No proof AMX introduced a regression" - yes, and more. For the word change we analysed (step 22 with today's build), the cause is not an open suspicion; it is demonstrated. The AMX-off run rates its top two words exactly equally (the gap is 0.0000). Tron picks the lower-numbered word on an exact tie. Turning AMX on moves that pair by one notch, so the other word wins. A change with nothing to do with AMX (the same program, AMX off, two fewer CPU cores) flips the same tie to the same word. A changed word at an exact tie is also not a quality loss: the model rated both words equally.
What is genuinely not identified: (a) the original 2026-08-18 step-30 event - the binary is gone, and even the AMX-off output has changed since that day, so its cause is unresolved; (b) how AMX's two known difference sources share the effect is now measured at the source (see the rounding-vs-addition-order section below): at the first place AMX acts, the weight rounding is the dominant term (about 30 times the addition-order term) and its size equals an accepted non-AMX perturbation's; downstream both terms are amplified to the same size, which is why removing rounding changed little end to end; (c) the strong-sense "no defect" claim - the one test that would come closest (replaying the exact inputs of the step-22 attention call through the old code, the AMX code, and a high-precision reference) was not run.
One sentence: no regression was demonstrated, no defect was found by any test that was run, and the analysed word change is fully explained by a tie; "proved no regression" would claim more than testing can deliver. The follow-up work is listed in definitive-decode/HANDOFF.md.
Conclusions in plain English
Short version. No AMX defect was found by any of the tests we ran. The word change that started this work is fully explained: at the step where the AMX-off and AMX-on runs first chose different words (step 22 with today's build), the AMX-off run had an exact tie between its top two candidate words. Two different small changes to the arithmetic each broke that tie: turning AMX on, and running the old code with a different number of CPU cores.
Words used below
  tron: the program under test. It runs the language model on this machine.
  AMX, AVX: two sets of CPU instructions for doing arithmetic on many numbers at once. AVX is the older set that the existing code uses. AMX is the newer set that the new code uses for the attention matrix products. "AMX-on" runs the new code; "AMX-off" runs the same program with the new code switched off, so the old AVX code runs instead.
  Token, step: a token is one piece of text, roughly one word. The model reads the prompt as a numbered list of tokens (token 0, 1, 2, ... 2047 here) and then produces one new token per step. "Step 22" means the 22nd token the model produced after the prompt (it sits at position 2069 in the numbered list). "Token 128 in layer 0" means the 128th token of the prompt.
  Score (logit): the number the model gives each candidate word at each step. The highest score wins. Each candidate word has a fixed number called its id.
  Layer: the model computes its answer in 36 stages, one after another; each stage is a layer. Each layer has an attention stage; its result is then multiplied by a fixed matrix called WO.
  Record, label: during a run we save values to disk, one record per (label, layer, token). The label says what the value is: for example WO (the result of the WO multiplication), WK roped, WV (values the attention stage stores for later tokens), Logits (the scores). Attn out is a label we added for this study; see the caveats.
  bf16: the 16-bit number format tron uses for these scores and for the values inside each layer. It keeps only about 2-3 significant decimal digits, so many candidates get exactly the same score.
  One notch (1 ulp): the smallest distance between two bf16 numbers of a given size. Around a score of 10 it is 0.0625; around 20 it is 0.125.
  Free-running run: the normal mode: the program chooses each word itself and uses its own choice as the input for the next step.
  Forced run: we feed the AMX-on run the exact words the AMX-off run had produced, one by one. Both runs then answer the same question at every step, so their scores can be compared step by step even after a word would have changed.
  Control run: AMX-off, but with two fewer CPU cores. Tron splits the attention work across cores, so the core count changes the order in which partial sums are added; it changes nothing else (tron's own design note names the core count as an input to that split). Both core counts are normal ways to run the program, so any difference between them is, by definition, an accepted one.
  Canonical, mirror, truncation build: three builds of the same source. Canonical is the normal AMX build. Mirror keeps an extra copy of the K data (one of the sets of numbers each layer stores for every token so later tokens can look back at it) arranged differently in memory. Truncation converts the attention weights to bf16 by cutting off digits, the way the old AVX code does, instead of rounding to nearest; everything else is unchanged.
  Kernel tests: small programs that run each AMX routine on made-up inputs and compare its output with a plain, slow version of the same math written without AMX. A check passes when the two agree within 0.01 % of the sum of the absolute products being added (plus a tiny constant).

Where the AMX difference comes from: rounding vs addition order (added 2026-08-30, after review)
AMX-on and AMX-off can differ for exactly two accepted reasons: the attention weights are rounded to bf16 differently (AMX rounds to nearest, the old code cuts off digits), and the additions happen in a different order. The truncation build lets us separate them. The clean place to measure is WO at layer 0: layer-0 attention reads values made from the raw input embeddings, which are identical in every arm, so a difference there is the local effect of a single attention computation, with no accumulation from earlier layers or tokens. Over the 1,920 prompt records (tokens 128-2047):
 |  | Comparison (what differs) | Values that differ | Median relative change | 95th percentile
 | Rounding only (truncation-AMX vs normal-AMX: same additions, different rounding) | 100 % | 0.00222 | 0.00392
 | Addition order only (truncation-AMX vs AMX-off: same rounding, different engine) | 32 % | 0.00007 | 0.00025
 | Both = production AMX vs AMX-off | 100 % | 0.00222 | 0.00392
 | Control (no AMX at all; different core count) | 100 % | 0.00202 | 0.00327
Reading. At the source, the rounding of the attention weights is the dominant term - about 30 times the addition-order term - and the total AMX-vs-AMX-off difference equals the rounding term alone. The control row is the context: a change with no AMX in it produces local differences of the same size as the rounding term, so AMX's local effect sits inside the range of already-accepted perturbations. End to end both terms saturate: 36 layers amplify even the tiny addition-order term into the same class of score differences, which is why the truncation build still flipped steps 22 and 37 and only reduced the score movement to 0.89 of normal. As a product change, making AMX truncate would buy nothing: the outputs still would not match (the addition-order term remains and any one-notch difference cascades), and truncation is the worse rounding (one-sided error; rounding to nearest is unbiased) - the 2026-08-19 decision to keep round-to-nearest stands.
What we did not prove, and other caveats
  The original event (2026-08-18) is not reproduced. That report found the first different word at step 30. The binary that produced it no longer exists (its recorded checksum matches no file on the machine). Today's build with AMX off already produces different words from that day's AMX-off run starting at step 4. The nearest preserved binary (runtron.inc1b, built the next morning) produces exactly today's words with AMX off (256 of 256) and the same step-22 change with AMX on, yet it also differs from the archived run from step 4. So the archived sequence is not explained by any code that changed since that preserved binary; the model weights, tokenizer files or machine state of that day remain as suspects, and the step-30 event stays unresolved. A code change made while adding AMX support before that binary could also be the cause; we did not check. The step-22 event we analysed is stable across the two builds we have.
  AMX-on was not repeated with the same binary. The mirror and canonical builds, both AMX-on, agree byte for byte, and the forced and free-running AMX-on runs make the same choice at step 22; that is indirect evidence of repeatability, not a repeat.
  A comparison against an independent implementation of the same model (the HuggingFace software, which does not use tron's code) was not run. A step that prepares the prompt for it failed on a formatting problem (fixable). It also could not have decided a tie: in an earlier measurement (2026-08-19, three prompts, 956 steps) tron's scores differed from that implementation by far more than one notch per word, and it agreed with tron's word choice in only 126 of 148 steps, for AMX-off and AMX-on alike.
  One of our own debug measurements was wrong. The new Attn out record (the attention result before the WO multiplication) differs between two identical AMX-off runs, while the WO record computed from that same result is identical. WO could not be identical if its input truly differed, so the recorder is not capturing the value actually used (most likely it copies the memory before or after the value is valid). It was excluded from every check; the conclusions use WO and the other stable records.
  "Harmless" was measured on this model and prompt. One prompt, 256 generated words, one control run. The pattern (differences appear exactly where the design says and match a non-AMX control) is what we would expect in general, but that is an expectation, not a measurement.
  Small, uniform faults are not excluded. Rows 5-7 would catch a fault whose effect is larger than the control run's differences or that disagrees with the reference on the tested inputs. A fault that changed every AMX block by less than that, in the same way, would pass these tests. Replaying the exact inputs of the attention call at step 22 through AVX, AMX and a high-precision reference would close this gap; it was not done.
Verdict (written 2026-08-30 after reading the numbers below)
The flip is a quantization-level exact tie resolved differently by admissible numerics. No AMX bug. Hypothesis H1; the rounding-mode vs add-order split comes out "not rounding-mode dominated" (H3-leaning), with the qualification that the delta size is saturated by bf16 amplification, so any admissible perturbation produces the same class of difference.
Target moved (H6). The archived binary no longer exists; today's canonical OFF arm already differs from the 2026-08-18 OFF arm at generated token 4 (different builds, same AVX path family), and today's free-running OFF-vs-ON flip is at token 22 (231 of 256 differ afterwards). The method was applied to that flip.
Gates all held. A/A: two OFF runs give identical tokens and byte-identical values for every deterministic label (WQ roped, WK roped, WV, WO, Logits, Top-k: 0 of the 304,176 records outside the excluded Attn out label differ; the 75,996 Attn out records are the instrumentation fault described below); the forced replay reproduces the ids exactly; the forced ON arm's own choice at step 22 (13) equals the free-running ON token; AMX engaged in every ON run (9.4 M kernel invocations in R4; 0 in every OFF run; arena_absent=0); mirror ON == canonical ON in every deterministic label; kernel envelope tests passed with 6158 / 6414 / 6157 assertions (canonical / mirror / truncation), no skips.
The flip step is an exact tie. In the OFF arm at step 22 the top two candidates (ids 11 and 13) have equal bf16 logits: margin 0.0000 = 0 ulps, resolved to the lower id. The ON arm has 13 above 11 by one ulp (0.125 at that magnitude). The second flip in 64 steps (step 37) is also a 0-ulp tie. Over 256 forced steps there are 3 flips: 22 and 37 at 0 ulps (exact ties), and 145 at a 3-ulp margin, where AMX moved that pair by 6 ulps; over those 256 steps the pair movement was typically 1 ulp (median) and 4 ulps at the 95th percentile, computed in each step's own ulp size (0.75 in absolute units). Non-flip steps: median |delta pair| 0, p95 0.125 (1 ulp); max TVD 0.036 in 64 steps.
Localization shows the expected dispatch pattern, not a bug pattern. The first per-layer difference ON vs OFF is WO layer 0 of token 128: the first token of the second prefill chunk, i.e. the first query for which complete, ready 64-token pages exist (pages filled in the same pass are not dense-dispatched). Nothing differs before token 128; from there every one of the 36 layers differs. No delta at T < 63, no page-edge pattern, no missing layers.
The add-order control reproduces the whole picture without AMX. R3c (AMX off, two fewer app cores, hence a different attention plan) differs from R3a at the same first key (WO layer 0 of token 128), with the same "every layer, nearly every element at the bf16 level" cascade, and flips the same tie at step 22 the same way (13 instead of 11). What AMX does to the numbers is indistinguishable in kind and scale from what a core-count change does.
Rounding mode does not reduce the end-to-end difference; at the source it is the dominant term. The truncation build (AMX rounds PV weights like AVX) still differs from AVX with the same graded size (median mean |delta| 0.027 vs 0.031, ratio 0.89) and still flips steps 22 and 37; canonical vs truncation (rounding-only change, same add order) differs in 279,795 keys, add-order-only in 274,258. Any single-ulp perturbation anywhere is amplified through 36 layers into the same class of logit deltas.
Not done. The HF arbiter (R8) was not run: the tokenizer step took the nix shell banner as JSON (fixable), and by the predeclared rule it cannot decide a 0-ulp tie anyway (the tron-vs-HF gap is median TVD ~0.11). The debug label Attn out (patch P2) is unreliable as placed: it differs between two identical OFF runs while WO, computed from that same output, is identical, so it was excluded from every gate; fixing its placement is a follow-up on the debug branch only.
What this says about the method. The run-twice idea works only as the A/A control; the working instrument is the teacher-forced A/B with graded statistics, an engagement counter, and a non-AMX perturbation control to calibrate "admissible". Token identity between arms is not a correctness signal: with bf16 logits, exact top-1 ties occur (2 in 64 steps here), and any admissible change flips them.
