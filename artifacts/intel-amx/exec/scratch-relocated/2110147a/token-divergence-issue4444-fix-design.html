Issue #4444: design for the fix

Companion to token-divergence-issue4444-report.html (the measurement). Written 2026-10-16 by Claude Code for jhan, revised after a technical review the same night. Numbers cite the report's records: the kernel test (exec/td-20261016/ktest/results.txt, lines named T...), the replay (exec/td-20261016/replay/results.md, sections M...) and the record comparisons (exec/results/td-20261016/). Code lines refer to the PR 4959 head 6b081187e1.

Short version

Two changes are worth making. The AVX-512 PV path should round the softmax weights to nearest instead of truncating them: a small change in one function, and it removes a -0.08 % bias and 20 to 45 % of the error. The kill switch should run AVX-512 kernels written in the AMX add order on dense pages, so that TRON_AMX_DISABLE=1 reproduces the AMX binary's numbers bit for bit (proved at kernel level, +18 % cost per dense page while the switch is on).

1. What the measurement settled

  • The VNNI layout changes no number. With the kill switch, a stack binary whose reader is replaced by unpack + dotter equals main bit for bit over all 416,443 records of a 1,280-token run [report, section 3].
  • The three add orders (dotter, reader, AMX) move a score by one fp32 ulp and an output element at a minority of tokens. The weight rounding (AVX truncation against AMX round-to-nearest) moves a third of the attention output elements by a bf16 notch at every dense page. It is biased: -0.08 % of the output on real data, and its RMS error is 1.25 times (real data) to 1.8 times (random pages) that of rounding to nearest [report, section 4].
  • At the PR 4959 head only, the page-completing decode step scores one page in the software loop where main uses AMX [report, section 5].
  • Every difference shrinks to ulp-level differences on about 80 % of the logits within one forward pass. A greedy flip needs a near tie: the margins at the three observed flips were 0 to 2 ulps [report, section 6].
  • An AVX-512 reader and an AVX-512 PV loop written in the AMX order reproduce the AMX kernels bit for bit (512,000 of 512,000 scores; 1,024,000 of 1,024,000 outputs). They cost 1.30x and 1.06x the current AVX versions on one core with the data in cache. The ratios come from a loaded machine and repeated within 2 % over two runs [ktest T9a, T9b, T9c].

2. The decisions

Two smaller items follow from the measurement. The page-completing decode step of PR 4959 should convert its block before attention, so the stack chooses the same path as main at every step. A model-level bound test (issue item 3) then checks the whole contract with two forced runs.

3. D1: the kill-switch contract

Today the switch on a VNNI-K binary gives "AMX off, same binary", not "the clean binary's numbers". The reader's add order stays, so newoff differs from baseoff from prompt token 1 on. The pair flips a token at step 20 of 256 [report, section 2]. The issue lists two options. The measurement adds a third.

Recommendation. Option C, keyed on the environment variable only, with option A's sentence in the Note until C is merged. Rationale: the two kill-switch arms that exist today (reader order, dotter order) flip tokens against each other just as the AMX arm does. So "AMX off" without a numerics promise does not help correctness work. Option C makes the switch the one tool that separates "the hardware did something different" from "the numbers were summed in another order". The cost applies only when the variable is set. A host without AMX runs the unchanged AVX path unless the variable is set there too.

Implementation sketch for C

  • Kernels (from the kernel test program exec/td-20261016/ktest/ktest.cpp, sections T9a and T9b). QK, one token per lane over the VNNI plane panels: per 32-dimension step keep two fp32 accumulators per head, E and O, both starting at zero. For each of the 16 pairs, E = fma(q_even, k_even, E) and O = fma(q_odd, k_odd, O), with the pair's two bf16 values widened to fp32 as the float-query path already does (shift for the even half, mask for the odd half). Then acc = acc + (E + O). Four steps per 128 dimensions. PV over the V pair rows: P rounded to nearest bf16 and widened. Per instruction of 16 token pairs, E = chain over the even tokens' products, O = chain over the odd tokens', acc = acc + (E + O). Two instructions per 64-token page. Scope: VNNI-K builds. A row-major build with AMX (main's configuration) scores dense pages with qk_rowmajor_128x4, which equals qk_vnni_128x4 bit for bit [ktest T1b], so option C there would need a third kernel, an AMX-order reader over 64 row-major rows. That kernel is not proposed here.
  • Dispatch. Today the dense-page branch needs a packed Q (amx_q_packed != nullptr, self_attention.hpp:1923). The packed Q is null whenever amx_on is false (line 1540), so the branch is never entered under the switch. Add a second flag amx_order_on = amx_eligible && !available() && the variable is set, read through a new accessor beside available(), since available() folds the variable into the cached hardware probe. The gate becomes (amx_q_packed != nullptr || amx_order_on) && is_dense_amx_page(...) && k_layout_dense(). apply_dense_amx_page takes the kernel pair as a template parameter. The AVX-order QK reads the raw bf16 Q group pointer that the reader takes today (line 2039), so no packed Q and no tile region are needed. It is called with all 64 live bits, so it writes every lane of s_pages[head][token], the array both paths share. The hint is returned unchanged, as the AMX branch does (lines 1929-1933).
  • Stats label. page_tok_result.served has three values (empty, avx, amx; attn_stats.hpp:116-118). A dense page scored by the AVX-order kernels gets a fourth value, amx_order, so the counters tell the arms apart.
  • Tests. An identity case in t_amx_numerics: the AMX kernel against the AVX-order kernel, bit for bit, like the existing VNNI-against-row-major identity case (it needs AMX hardware). A mutation check with an order the measurement showed to differ: one sequential chain over the 32 products of an instruction (the reader's order, where 49.5 % of scores differ [ktest T1]) or fl(fl(acc + E) + O) (25.3 % differ [ktest T5m]). The identity case must fail on either. The case "available() false: no pack, no kernel call" in t/t_amx_dispatch_dtype.cpp (line 321) encodes today's behavior and changes. At model level, bound 1 of D4.

4. D2: round the softmax weights to nearest in the AVX-512 PV path

The AVX loop (scaled_v_expr, kv_cache.hpp:2936-2990) takes the weights two tokens at a time. interleave_bf16_ps(scales[i], scales[i + 1]) (defined at kv_cache.hpp:2996, called in the constructor branches 2941-2990) receives the two fp32 weights as broadcast vectors and returns a vector whose every 32-bit lane holds (weight of token 2p in the low half, weight of token 2p+1 in the high half), the layout of the V pair rows (v_vnni.hpp:41). It builds that lane by a shift and a mask, which truncates both weights.

The change: round the weights once per page and broadcast. Convert the page's fp32 weights to bf16 with _mm512_cvtneps_pbh (16 weights per instruction, round to nearest even) into a small aligned scratch of 64 bf16, then for token pair p broadcast the 32-bit word that holds weights 2p and 2p+1 (_mm512_set1_epi32 of that word). The lane layout is the one the loop expects. Instruction count per pair: one broadcast, against two broadcasts, one shift and one ternary-logic operation today, plus four conversions per page. The nightly perf job is the check.

Subnormal weights: tron's vector exp returns 0 below -88.376 (fp32.hpp:831, 925-937), so a weight can fall in the fp32 subnormal range. The conversion and the multiply instructions treat subnormal inputs as zero in both the old and the new code, so no number changes there. The divisor s* uses the unrounded fp32 weights in both cases.

Scope: scaled_v_expr serves head sizes 64, 128, 256 and 512. The change applies to every model with CPU attention, including models that never use AMX (for example gpt-oss-120b with 64-dimension heads), to the sliding-window layers under FPGA attention, and to every partial page of the AMX arms.

What must be measured before merging:

  • A forced-run comparison, clean before against clean after, on the campaign's cell. Expected: a rounding-type first record at the first page, flips only at near ties.
  • The nightly perf numbers. Expected: no change.
  • An accuracy benchmark on both binaries (the nightly MMLU-Pro job is the existing instrument). The expected difference is within its noise, so this is a guard, not a proof.
  • Whether the FPGA attention path rounds its weights to nearest or truncates. Not measured here. If it truncates, the FPGA-against-CPU difference grows by the bias the AVX path loses.
  • A unit case: scaled_v_expr against a scalar reference with weights rounded to nearest, bit for bit (the PV case of t_amx_numerics at line 279 already has the rounding helper).

Why this is worth doing although the bias is small. The truncation costs accuracy with no benefit. The rounding instruction is as cheap. It is the single largest contributor to the CPU-path differences: ten to twenty times the add order (median layer-0 WO change 2.17e-3 against 1.06e-4 [report, section 4]). Every CPU host without AMX runs it on every page. It is not urgent: a 0.08 % bias on one layer's attention branch is far below the bf16 noise of the residual stream, and no quality regression has been attributed to it.

5. D3: convert the page-completing block before attention

At the PR 4959 head, a decode step that saves the 16th row of a block queues the block (model.hpp:3425-3427) and converts it at the forward end (model.hpp:1834-1842, 3170-3177), after attention. On the page-end step this leaves the page non-dense for one step, and the page goes through the software loop where main uses AMX [report, section 5].

Proposal: convert the block in save_k_impl, on main, in the loop that sets the saved-row bits after the shared-save join (model.hpp:3414-3428), where the block is queued today, and before mark_k_complete and the latch count-down (model.hpp:3448-3449). The conversion can only run after the row bits are set, because k_block_to_vnni_at checks them (kv_cache.hpp:2261-2268). Cost: k_block_to_vnni_at converts every KV head of the slot (kv_cache.hpp:2272-2280), so n_kv_heads in-place 4 KiB transposes per completed block (qwen3-4b: 8 KV heads, 32 KiB, 16 KiB per tp2 rank), on main, before the attention of that layer starts, once per 16 decode steps per layer per user.

Safety argument, to be completed in the PR. Note [K VNNI storage] gives the reason the conversion is not in save_k today (kv_cache.hpp:726-737): a block can be split across two minibatches of one pass (grains of 8 tokens, model.hpp:199-232), and the cooperative GOF staging gather of the earlier minibatch reads the block's rows row-major while the later minibatch saves its last rows (model.hpp:3152-3160). Two facts must be established in the PR, with citations:

  • The GOF staging is credited only for operations with a hardware slot (credit_gof_save under has_hardware_slot, model.hpp:3434-3437), and rows are recorded for conversion only when the operation does not use hardware attention (model.hpp:3419). If those two predicates are complements, the staging never reads a block that converts. The Note's reason is then obsolete. The PR rewrites that paragraph of the Note.
  • The split-block case: the pending attention of minibatch A must not read the block before minibatch B's latch. The Note says a pending page is read only after every minibatch that writes it counted its latch down. The PR cites that rule.

After the change the forward-end queue is empty in every case: under hardware attention no block is queued at all (model.hpp:3419, Note [Row-major blocks under hardware attention]). The PR removes pending_k_blocks_ and convert_pending_k_blocks, or keeps them for the split-block case if the second fact above does not hold. A test case in the runtime scheduler test t/t_scheduler.cpp (case name to be confirmed) exercises the page-end step and checks that the page is dense in the completing step.

Alternative: leave the behavior and document it in Note [K VNNI storage], which already says "the page is dense from the next pass on". The cost of leaving it: the stack can never be bit-identical to main with AMX on, even once the reader's order is settled, and a per-step comparison between the two shows a difference at every 64th decode step that has nothing to do with the kernels.

6. D4: a model-level bound test

Issue item 3 asks for a bound at model level instead of the per-kernel envelope. The campaign's tooling gives one directly: forced runs with --intermediates-file filtered to the logits lines, compared by dd_logits_step.py. Proposed test, on a fixed prompt (the cell of this campaign: qwen3-4b tp2, prompt 1024, 256 generated tokens, greedy, --pay-for-determinism):

  1. Run the binary with AMX on, free-running, and record its tokens. Run the binary with the kill switch and, when available, the row-major build, force-fed those tokens, and record the logits of every step.
  2. Bound 1 (identity, after option C): AMX on against the kill switch, all 256 logit vectors identical. Until option C is merged, bounds 2 and 3 apply to that pair.
  3. Bound 2 (distribution): per step, the TVD between the two arms at most twice the measured baseline of the cell (tonight: maximum 0.057 over all pairs, so 0.11; the 2026-08-30 run reached 0.36 at prompt 2048, so the baseline is per cell).
  4. Bound 3 (flips only at near ties): every step whose top token differs must have a margin in the reference arm at most the measured 99th percentile of the pair movement of that cell (tonight: the movements at the three flips were 1 to 2 ulps; the 95th percentile of all movements is 2.1 ulps for base vs new and up to 10 ulps for the other pairs). The number of flips per 256 steps at most 6 (the flip model expects 0.8 to 2.1 per pair; at the upper rate a cap of 4 would fail about one run in 15 by that model, a cap of 6 about one in 150).

What the test needs in CI: the comparison script and the forced-token file ported into the tron repository; a runner with the FPGA cards and AMX (the cell runs tp2 on two cards; label [self-hosted, fpga, test, intel, avx512]; no AMX-labelled job exists yet); the row-major comparator as a third build; 2 to 3 runs of 5.3 minutes plus the comparison. The test fails on a wrong index, a dropped token or a precision loss. Any of those breaks bound 2 at the first affected step by far more than the cap. It passes across the admissible numerics differences measured here.

7. D5: the numerics contract text

Note [AMX attention dispatch] states that the AVX and AMX outputs differ "for exactly two reasons": the bf16 rounding of the PV weights and the fp32 add order. That stays true. The measurement adds detail inside the second reason, worth writing down with the numbers:

  • The QK add orders differ three ways. Dotter: two lane-split chains and a halving tree. Reader: one sequential chain. AMX tile: per instruction two 16-product chains joined once. No AVX order equals both others.
  • The PV add orders differ the same way: the AMX PV kernel and the AVX loop disagree on 73 % of outputs even for identical bf16 weights [ktest T6a].
  • The rounding of the weights (truncation against nearest) is the largest of the three at the first differing record and carries a bias [report, section 4].

The same contract sentence lives in two other places: h/tron/kernels/k_vnni.hpp lines 33-35 ("Only the order of the fp32 adds differs") and the last paragraph of Note [K VNNI storage] (kv_cache.hpp:852-856). Both get the same update. Item 4's contract sentence gets the condition of option A until option C is merged. Then it reads: "with the switch on, the dense-page kernels run in the AMX order and the run equals the AMX run bit for bit".
