## loop
SUMMARY: On the kill-switch path (TRON_AMX_DISABLE=1, the AMX kernels off inside the same binary) every (query, page) visit of apply_page_tok runs the software loop, and PR #4901's loop adds two kinds of work that PR #4898's loop did not have: per visit, it builds 4 dotters (dotter<bf16,128>, the per-token dot product over one row-major K row) with 16 aligned 512-bit loads of the same 1024 bytes of q that the AVX-512 reader k_vnni::qk_group reads anyway, and per relevant token it tests a std::optional and a block bit before setting the live bit. The dotters are built even when no token of the page is row-major, which is the case for every page but the newest one of a user. The tail rows are scored by the dotter with a different fp32 add order than qk_group (two accumulators over 32-dimension chunks, a lane-wise add, then a 16-lane horizontal reduction), so a token's score changes add order when its block converts; the epilogue after the loop does not care which path wrote a score. Prefill and decode go through the same per-(query, page) call with no batched software path, so an 8192-token software prefill pays the per-visit cost on the order of 10^8 times (est.). The probe ca6456b7dc defers the dotter build to the first row-major token, and its comment is wrong: dotter<bf16,128> copies q as bf16 and converts nothing at construction.

Q: (3) How is apply_page_tok called; do prefill queries go through the same per-(query, page) call or a batched path?
A: The same per-(query, page) call. apply_page_range loops over the section's pages (line 1566) and inside each page over the batch's queries q_begin..q_end (line 1597), calling apply_page_tok once per (query, page) at line 1640. The AMX packer (lines 1529-1564 setup, 1631-1638 per query, 1684-1715 packed_amx_query) packs one token's Q group once per call at its first page and reuses it for later pages; with the kill switch, amx_on is false (line 1540 and available()), so amx_qp stays nullptr and every pair runs the software loop. The `items` list is the batch's token jobs whether they are prompt tokens or decode tokens (run_sections, lines 1170-1172), so a prefill query visits each of its visible pages one at a time; there is no batched software QK over several queries. The hardware (FPGA) attention path is a separate function set (prepare_uniform_hw_attention, lines 555-621) and is selected by uses_hw / run_visible_in_software (lines 1506-1507). The only call site of apply_page_tok is line 1640.

Q: (4) Does the dense AMX gate return before the dotters are built with AMX on?
A: Yes. The gate `amx_q_packed != nullptr && is_dense_amx_page(...) && k_layout_dense()` at lines 1932-1935 and its `return` at line 1942 come before `s_pages` (line 1946) and the dotter array (lines 1969-1974). So with AMX on, a dense page whose 4 blocks are VNNI never builds dotters; the dotter cost is paid only by software-visited pages: partial pages, pages with a row-major block (the newest page of a user in decode, until its block converts at the forward end), and pages outside the gate. The k_layout_dense lambda is evaluated only when the first two gates hold (short-circuit &&); on the AMX-on path it adds one k_state_ix and one 1-byte acquire load per dense visit, which PR #4898 did not have.

Q: (5) What does the probe ca6456b7dc change exactly, and is its comment wrong?
A: It changes self_attention.hpp only. It moves the dotter construction into a lambda make_dot_q; on a VNNI slot dot_q becomes an empty std::optional<std::array<dotter,4>> at visit start (on a row-major slot it stays the plain array); at the first row-major token inside the loop it does `if (!dot_q) dot_q.emplace(make_dot_q());` and scores with `(*dot_q)[offset](k)`. Its comment ("a dotter converts its query row to fp32 at construction") is wrong for this path: dotter<bf16, 128> loads 4 x 64 bytes of bf16 and keeps them as bf16 (dotter.hpp:196-200, members at :223); the fp32 conversion at construction exists only in dotter<float, 128> built from a bf16 view (dotter.hpp:94-102) and in the generic fallback (dotter.hpp:38), neither instantiated when scalar_t is bf16. Q: (6) The numerics of the row-major dotter<bf16,128>::dot, precisely, for a bit-identical replacement.
A: Construction: x01, x23, x45, x67 = the four aligned 512-bit loads of the query head row (bf16 dims 0-31, 32-63, 64-95, 96-127), kept as bf16. dot(K row): y01..y67 = the four aligned 512-bit loads of the K row (same dimension chunks). sum1 = VDPBF16PS(zero, x01, y01): 16 fp32 lanes, lane j = q[2j]*k[2j] + q[2j+1]*k[2j+1] for dims 0-31. sum2 = VDPBF16PS(zero, x23, y23) for dims 32-63 (lane j covers dims 32+2j, 32+2j+1). sum1 = VDPBF16PS(sum1, x45, y45) for dims 64-95. sum2 = VDPBF16PS(sum2, x67, y67) for dims 96-127. Then `sum1 + sum2` = one lane-wise VADDPS on __m512 (fp32x16 converts through operator __m512), then reduce_sum(fp32x16) = _mm512_reduce_add_ps, whose lane order is the compiler's (clang-19 in the presets; its header is not installed on this machine, so the exact tree is Insufficient data here). A bit-identical replacement must: start each accumulator from zero, assign chunks 0 and 2 to accumulator 1 and chunks 1 and 3 to accumulator 2 in that order, use VDPBF16PS (the same instruction, with its own bf16 x bf16 product and fp32 add semantics), do the single lane-wise add sum1 + sum2, and call the same reduce_sum helper on that lane vector. The 4 heads are independent dot calls; their order does not matter. The per-token result is stored as one float into s_pages[head][i]. The reader qk_group uses a different order (one accumulator per head, 64 chained VDPBF16PS per token lane in dimension-pair order, no horizontal reduction), and the repository documents that the two orders can differ by rounding and change a generated token.

## savek
SUMMARY: qwen3-4b is an ingested (generated) plugin, so each forward pass runs one minibatch of at most 1024 tokens and save_k is shared with the main helpers only when the minibatch holds more than 16 tokens; a decode step of 8 users is stored by the main thread alone. At ea94e95a4e a decode token costs 4 whole 64-byte lines per KV head (memcpy into the row-major tail block) instead of 64 partial-line scatter writes at dfafd13dce, but PR #4901 adds a serial main-thread loop after the join that runs once per (token, layer) in every pass (1024 iterations per layer, 36,864 per forward pass, 2,359,296 per 8-user 8192-token prefill) and a serial forward-end conversion of every block a step completes (288 queue entries = 2304 block_to_vnni calls = 18 MiB of plane traffic in one step every 16 steps for 8 users at prompt 1024). The block queue is per forward pass, filled across all layers, drained after wait_for_coop_gof on the main thread. cached_operation_uses_hw is a per-operation table filled once in the state constructor; under hardware-scored operations nothing is queued or converted. For the single-minibatch generated plugin I found no reader of a queued block that can be in flight at the join inside save_k: pending-page attention sections wait on a latch that save_k counts down only after the note loop, GOF credits of this pass's tokens happen after the join, and the earlier-minibatch staging hazard the Note names needs several minibatches per pass.

Q: (1) Which thread runs each piece?
A: save_k / save_k_impl worker 0 = the main thread (generated run() passes 0 and n_workers). Helpers = the main helpers: app-pool workers 0..n_main_helpers-1 running run_main_help, which calls save_k with worker_ix 1+i at the same statement position; they wait for their window, claim units, run store_k_block on them, increment `finished` and return. store_k_block runs on whichever thread claimed the unit (main alone when the store is not shared, which is every decode step of 8 users). note_k_block_saved runs on the thread that stored the whole block. The join (main spins on `finished == n_helpers`), the note_k_row_saved loop, pending_k_blocks_.push_back, the mark loop, credit_gof_save and the latch count_down are main-thread only, after the join. Attention workers (the last n_attn_workers pool workers) never call save_k; they run help_drain_gof(4) at each attention operation begin. wait_for_coop_gof and convert_pending_k_blocks run on the main thread after plugin run() returned (run() waits for all helpers and attention workers first).

Q: (2) Decode with 8 users: what does store_k_block do per token per KV head at ea94e95a4e vs dfafd13dce?
A: Both revisions: 8 items form one minibatch (generated plugin, --max-minibatches 1), k_store_shared is false (8 <= 16), so main stores alone, runs of n = 1. ea94e95a4e: set_k_row -> one acquire load of the block bit -> store_row_major = memcpy of 256 bytes = 4 whole 64-byte lines per (token, KV head); 32 whole lines (2 KiB) and 8 atomic loads per token. A row re-saved into an already converted block takes store_row (scatter). dfafd13dce: set_k_row -> store_row = 4 scatters of 16 dwords = 64 writes of 4 bytes into 64 distinct lines per (token, KV head); 512 partial-line writes per token. After the stores, ea94e95a4e adds per token on main: relaxed load + fetch_or (acq_rel, the bit is clear in decode) + acquire load, and every 16th step one vector push_back; the pre-existing mark loop (page_of, offset_in_page, mark_k_complete fetch_add, GOF credit) is unchanged.

Q: (3) The note_k_row_saved loop in an 8-user x 8192-token prefill: iterations per layer and per forward pass, chunking, cost per iteration, note_k_block_saved per block, per-prefill count.
A: Chunking: there is no TRON_CHUNK_SIZE; the pass size is the scheduler's live-token limit = max_minibatches x max_minibatch_size = 1 x 1024 for an ingested plugin (TRON_LIVE_TOKEN_LIMIT and the 4096 hard cap are larger), so a pass holds one minibatch of 1024 tokens (documented as 128 per user). Note loop: 1024 iterations per layer per pass, 36 x 1024 = 36,864 per forward pass, 64 passes, 2,359,296 for the prefill. Each iteration: token_jobs_do_kv read, token_jobs read, page_of (pointer table lookup), offset_in_page (integer subtraction), note_k_row_saved = k_state_ix (eagle check) + relaxed load of the row bits + fetch_or only when the bit is clear (never in a whole-block prefill, since note_k_block_saved already set the 16 bits) + acquire load of the block bits; returns false for a block-saved row, so no push_back. note_k_block_saved: once per whole block on the storing thread, two fetch_or; 4096 blocks per layer, 147,456 per prefill, spread over main and helpers. The mark loop runs the same 2,359,296 iterations at both revisions. Per-iteration time in ns: Insufficient data (needs a TSC or perf measurement of the loop).

Q: (4) When does save_k run relative to this layer's attention readers; could a block be converted right after the join inside save_k; which readers of K rows could be in flight?
A: Order in the generated pass: launch_early_hw_attention, save_k, save_v, prepare_late_hw_attention, launch_late_hw_attention. The layer's attention workers may already be running READY sections (pages not written this pass) during save_k; PENDING sections (pages written this pass, where every queued block lives) wait on upstream_kvs_ready[slot], which save_k counts down only at its very end (after the note loop and the mark loop) and save_v counts down after its stores; the single minibatch is its own producer (page-wide token_ix_needed). Readers that can be in flight at the join: attention workers on ready pages (no queued block there); attention workers inside help_drain_gof doing GOF staging (reads rows in place through k_row_if_row_major), but a GOF of this pass's tokens is credited only after the join (mark loop of save_k, then save_v), and earlier passes' GOFs were drained by wait_for_coop_gof at the previous forward end; main helpers (writers only, returned); other layers' workers (other kv_slots); page copies / clear_kv_complete_at (between passes, tree lock). So for the single-minibatch generated plugin I found no reader that a conversion right after the join (before count_down) could corrupt. The Note's reason for deferring (an earlier minibatch's GOF staging reading a block whose last rows a later minibatch saves) needs several minibatches per pass, i.e. the handwritten llama.hpp plugin. Q: (1) The exact per-(page, storage slot) layout state: which bits exist, their types, whether shared across KV heads, plain or atomic
A: Two masks per (page, storage-slot entry), both std::atomic, both shared by all KV heads of the slot: k_rows_saved_ (std::atomic<uint64_t>, bit o = the K row at page offset o is saved) and k_vnni_blocks_ (std::atomic<uint8_t>, bit c = 16-token block c (offsets 16c..16c+15) holds the VNNI layout; bits 0-3 used). Each array has n_slots + 1 entries: entries 0..n_slots-1 are the logical slots, entry n_slots is the EAGLE storage (used for slot 0 while the EAGLE view is active). A set block bit implies the block's 16 row bits. Row-major slots keep the arrays but never set bits. There is no per-KV-head bit, so one conversion covers all 8 KV heads of qwen-3-4b and a reader must not see the block bit before every head holds the layout.

Q: (2) The exact rule of note_k_row_saved and of k_block_to_vnni_at (every KV head; bytes moved)
A: note_k_row_saved(slot, offset): row-major slot -> false. VNNI slot: relaxed-load the row mask; if the row's bit is clear, fetch_or it (acq_rel); return true iff (mask after | bit) has all 16 bits of the row's block AND the block's converted bit (acquire load) is clear. So it returns true for the row that completes the block, and again for any later re-save of a row of that block while the block waits for its conversion; false once the block is converted. k_block_to_vnni_at(storage, c): returns false unless the 16 row bits of block c are set and the block bit is clear (both acquire loads); otherwise, for every KV head of the storage slot's geometry (8 for qwen-3-4b) it runs block_to_vnni on that head's K plane, then sets the block bit with fetch_or(release) and returns true. block_to_vnni per KV head: 16 memcpy of 256 B from the block to a 4 KiB stack array, then store_block transposes 4 x 16 registers and writes 64 lines of 64 B = 4 KiB back; so 8 KiB of plane traffic (4 KiB read, 4 KiB write) plus 8 KiB of stack traffic per KV head per block, 64 KiB plane traffic per block per slot for 8 KV heads, 2.25 MiB plane traffic per completed block across 36 slots (computed, not measured). The conversion is a serial main-thread loop.

Q: (3) set_k_row: how it decides row-major vs VNNI column; what a re-save into a converted block does
A: set_k_row reads the block's converted bit at call time (k_block_is_vnni, one acquire load) for each (token, KV head) call: bit set -> store_row (4 AVX-512 scatters of 16 dwords into the token's VNNI column); bit clear -> store_row_major (one 256-byte memcpy, 4 whole lines). It never touches the row bits. A re-save into a converted block therefore scatters into the VNNI column, and the following note_k_row_saved returns false (block bit set), so nothing is queued. ## hwpath
SUMMARY: The hardware/software split is fixed once per model state at construction (cached_operation_uses_hw reads an array filled right after configure_hw_attention), so a lost shard (HBM exhausted), a prompt below the 127-token engagement point, or an empty per-batch hardware plan never flips an operation back to "software-scored": its blocks stay row-major forever and the software loop scores them with the row-major dotter. The FPGA staging gather (gof::populate via page_info::k_head_fn) runs only for KV slots in the hardware slot mask, which under hardware eligibility is exactly the set of hardware-scored operations, so for a software-scored operation no staging gather can ever read its pages and the "convert after wait_for_coop_gof" ordering is defensive, not required. Under the measured cells (TRON_AMX_DISABLE=1 with USE_HW_ATTN=0) no hardware path is active at all: no shards, no GALs/GOFs, empty gof_jobs_span, null gof_rodeo_fn, wait_for_coop_gof returns at once, and every short-run block is recorded and converted on the main thread at the forward end. Under the FPGA path with every operation hardware-scored (qwen-3-4b has no sliding window), pending_k_blocks_ stays empty and convert_pending_k_blocks returns on its first line. A fix must keep: the 4-line row-major store for short runs, the in-place row return in k_head_fn, no conversion of hardware-scored operations' blocks, and a software loop that still handles row-major blocks scattered anywhere in the history (the page already carries a 4-bit per-page block mask, so no new mask is needed).

Q: (1) When does cached_operation_uses_hw(op) hold; once per operation or per minibatch/pass; what happens on 'lose HW attention'?
A: It holds iff the model state was built with hw_attn_eligible true (devices present, USE_HW_ATTN not 0 or model default on, shape eligible, EMEM fits a shard) and the operation is a hardware candidate with no sliding window (scale uniformity is guaranteed by eligibility). It is decided exactly once, in the model-state constructor (configure_hw_attention, then cache_attention_operation_hardware_eligibility fills attention_operation_uses_hw); nothing rewrites the array, so it never flips per minibatch or per pass. Losing HW attention (HBM exhausted: a 1024-token shard with sw_fallback, scored on the CPU), a prompt below the 127-token engagement point, or an empty per-batch hardware plan do not change it: the operation still counts as hardware-scored, save_k records no row bits for it, its decode-completed blocks stay row-major, and the software loop (driven by the sw_required mask for that range) scores those tokens with the row-major dotter (4 lines per token) while whole-block prefill blocks are read by k_vnni::qk_group. The shard note states this split is deliberately static: 'decided once per attention operation for a whole batch, while residency is per shard'.

Q: (2) Which thread gathers K rows for the GOF staging, for which operations, can an earlier minibatch's gather still read pages of a software-scored operation, and is the forward-end ordering needed for software-scored ope
A: Gather chain: credit_gof_save (main thread, in save_k/save_v after the stores) enqueues a completed GOF; fire_gof_rodeo -> gof_rodeo_impl -> gof::prepare_for_dma -> gof::populate calls page_info::k_head_fn for 4 tokens x n_kv_heads. Drainers: attention workers via help_drain_gof(budget 4) in begin_attention_job (only the handwritten llama plugin at llama.hpp:754 and tests call it; generated plugins use run_attention_job which has no drain call), and the main thread in wait_for_coop_gof at the forward end; backfill_shard also populates, on the scheduler thread outside the forward. Operations: gof_rodeo_impl returns unless slot_uses_hw(slot), and GOFs exist only for slots in the hardware mask; that mask is set for exactly the candidate-and-no-sliding-window operations, the same predicate that makes cached_operation_uses_hw true once hw_attn_eligible holds. So a software-scored operation's KV slot is never staged (unless two operations share one slot, which was not verified), and no gather of an earlier minibatch can read rows that this pass records: rows are recorded only for software-scored operations (3425) and gathered only for hardware-scored ones. The forward-end ordering 'convert after wait_for_coop_gof' is therefore not required by any staging reader; it is defensive. What the forward-end placement still provides is 'after run() joined its workers'; the Note claims attention workers are not a reader of a block during its completing save because pending pages are read only after every writing minibatch counted its latch down (upstream_kvs_ready.wait at self_attention.hpp:821-823; save_k counts down at its end, model.hpp:3455-3457). Whether a page written in this pass can appear in a 'ready' section was not verified here.

Q: (3) Under the kill switch with USE_HW_ATTN=0 (the measured cells), is any hardware path active (gof, staging)?
A: No. USE_HW_ATTN=0 makes fwd_hw_attn_enabled return false, configure_hw_attention takes its disabled branch (hw_attn_eligible stays false, hw_kv_slots stays the empty default), so the scheduler creates no shards, no GALs/GOFs, passes empty hw_plan_entries, an empty gof_jobs_span and a null gof_rodeo_fn. In the model, cached_operation_uses_hw is false for every operation, so every short-run block is recorded (one atomic per token per layer per pass) and converted on the main thread at the forward end (for qwen-3-4b: 36 blocks x 8 KV heads = 288 block_to_vnni calls per user per 16 decode steps, computed from the Note's per-block figures). The only hardware remnants on the path are credit_gof_save's empty-span early return per (token, layer) in save_k and save_v, and wait_for_coop_gof finding an empty queue. The attention loop runs with uses_hw=false, i.e. run_visible_in_software, visiting every visible token.

Q: (4) In a mixed deployment (FPGA attention on), how often does the software loop score row-major blocks with the dotter per 1024-token shard, and does a fix that removes the per-token layout test need a mask of row-major 
A: A software-scored range under a hardware operation (a degraded shard's 1024 tokens, positions below the engagement point, the causal tail above the DMA'd prefix) is visited every decode step by every query whose sw mask covers it, for every layer and KV head: 16 page visits per (query, layer, KV head) per shard, each walking up to 64 tokens, i.e. up to 1024 x 36 x 8 = 294,912 per-token bit tests per query per step for one fully-relevant degraded shard on qwen-3-4b (arithmetic from constants, not measured). Which of those tokens are row-major: every token saved by a run shorter than 16 (every decode token and a prompt's last partial block), permanently, because hardware-scored operations never queue a conversion; whole-block prefill tokens are VNNI and go through qk_group. The page already keeps the needed mask: page::k_vnni_blocks is one uint8_t per slot with one bit per 16-token block, fetched once per page visit (self_attention.hpp:2020-2022); the per-token test is a bit test on that register value. A fix can iterate per block from that 4-bit mask, so no new per-page mask is needed. What a fix must not assume is that row-major blocks sit only in the newest page's tail block: under hardware attention they are scattered through the whole decode history, so the row-major dotter path (or an equivalent row-major reader) must remain for any block whose bit is clear.

Q: (5) Under the FPGA path, does anything in the forward end (convert_pending_k_blocks) run at all (queue empty)? What must a fix keep unchanged to preserve PR #4901's FPGA gains (issue #4500)?
A: For a model whose operations are all hardware-scored (qwen-3-4b: no sliding window; candidate status per layer is declared by the plugin and was not read here), pending_k_blocks_ is never pushed (gate at model.hpp:3425) and convert_pending_k_blocks returns on its first line (3177); wait_for_coop_gof still runs and drains the tail of the GOF queue on main. Models with software-scored operations (sliding-window layers) still queue and convert those blocks. To keep the issue-#4500 gains a fix must keep: (a) short-run K rows stored row-major as 4 whole 64-byte lines (store_row_major via set_k_row), not the 64-line scatter of PR #4898; (b) page_info::k_head_fn returning the row-major row in place (zero copy) and gathering 64 lines only for converted blocks; (c) no conversion of hardware-scored operations' blocks (so the staging never pays the 64-line gather for decode tokens and the main thread does no serial forward-end conversion under FPGA); (d) every reader taking the layout from the block bit, since row-major blocks are permanent and scattered under hardware attention (software loop, staging, copy_from, clear_kv_complete_at); (e) the GOF credit after the stores and wait_for_coop_gof before the scheduler rebuilds gof_jobs; (f) whole-block prefill saves writing VNNI at once, which is the only way a page is dense for the AMX kernel before the engagement point or when DMA lags.

## harness
SUMMARY: The harness is three layers: build2.sh builds one runtron binary into a /var/tmp/jhan worktree on our half of delphi-3bda, campaign-probe.sh runs the runtron cells (arms mapped by name to RT_BASE/RT_HEAD/RT_NEW/RT_LAZY) and summarize.py reads WEDPERF_ARMS/WEDPERF_PAIRS from the environment, and a detached driver (probe-off.sh, a fork of probe-lazy.sh) takes Bill's marker, takes serving down through platformd, runs the cells and restores serving in its exit handler. Measured costs from the 2026-10-14 pr4off-E-cpu record: takeover 33 s, serving-up 127 s, one run 45 s (tp2 prompt 1024), 103 s AMX-on or 173 s AMX-off (tp2 prompt 8192), 56 to 70 s (tp4 prompt 1024); a 54-run CPU campaign with three AMX-on and three AMX-off arms took 75.2 min on 2026-10-13, an 18-run FPGA campaign 16.6 min, and a fresh runtron-only build 785 s. All four binaries exist on 3bda with sha256 equal to the record header, the shared repo sees 175b1837b9, and /var/tmp has 899 GB free. A fifth binary needs edits at campaign-probe.sh lines 33, 34, 35, 70, 72, 222, 223 and 226 (plus the header), and both campaign-probe.sh and the driver must be forked to new file names because a running script must never be edited over NFS. Only two steps need jhan's order per the script headers: bill-share.sh take and the platformd serving-down; builds and fake-device unit tests run on our half without an order, but the runtron cells cannot run while a rinzler@N unit is active, so they are a whole-machine step.

## prefill
SUMMARY: Prefill under the kill switch (TRON_AMX_DISABLE=1, attn = cpu in every recorded cell) scores every visible (query, page) pair one at a time through apply_page_tok inside apply_page_range's page loop and per-query loop, so an 8192-token prompt makes 528,384 visits per user per layer per KV head (about 1.22e9 visits for 8 users x 36 layers x 8 KV heads). At 8192 tokens every K block is saved whole (runs of 16 in store_k_block), so no row-major tail block, no set_k_row, no pending conversion and no dotter use exists on the prefill path; the diff's prefill-time changes are (i) per visit in the software loop: 4 dotters built, a plane optional plus a block-bit test per relevant token, one k_vnni_blocks load at the first token, and (ii) per save_k on main: a note_k_row_saved call per item (no atomic RMW, the bits are already set by note_k_block_saved) plus one note_k_block_saved and one assert per block. The measured TTFT loss grows 52-113x from prompt 1024 to 8192 while the visit count grows 61x and the token count 8x, so the per-visit loop changes are the leading TTFT suspect (est. 22-43 ns per visit = 27-52 s of worker time per 8-user prefill, 0.45-1.3 s wall for 40-60 workers) and the per-item save_k loop is second (est. 19-35 ms serial). The lazy-dotter probe builds no dotter for any prefill visit at 8192 (no row-major token exists) and did not change TTFT (+21 ms / +100 ms, inside noise), which removes dotter construction as the TTFT cause and leaves the per-token tests and the save_k per-item loop.

Q: (1) Is prefill attention computed per query token through apply_page_tok (one (query, page) visit per call), about 8192 x 64.5 page visits per user per layer per KV head? Is there a batched prefill path?
A: Yes. apply_page_range iterates the pages of its range (self_attention.hpp:1566) and, inside, every query of the minibatch (1597); each query that sees the page calls apply_page_tok once (1640), which scores that one (query, page) pair: the loop over the page's tokens at 2001-2033 builds the live mask, then qk_group scores up to 64 tokens x 4 heads (2045-2048) and the softmax/PV epilogue follows (2054-2080). Queries that do not see the page are skipped at 1612 before the call. There is no batched (multi-query) prefill kernel on the CPU path with AMX off; the AMX dense path (apply_dense_amx_page) is also one (query group, page) per call. Count per user per layer per KV head for 8192 tokens: sum over the 128 pages of (8192 - 64 p) = 528,384 = 8192 x 64.5 visits, 63.5 relevant tokens per visit on average; x 8 KV heads x 36 layers x 8 users = about 1.22e9 visits per 8-user prefill.

Q: (2) How many save_k calls and how many items per call does an 8192-token prompt x 8 users produce per layer (chunk size)?
A: One save_k per minibatch per layer. A forward holds at most 4096 KV token jobs (capacity_limit = ranged_mask_capacity 4096; rinzler default max_minibatches = -1), so each user's prompt is 2 forwards of 4096 tokens and the 8 users take 16 prefill forwards. chunk_evenly cuts 4096 token jobs into ceil(4096 / max_minibatch_size) chunks: with the ingested plugin's max_minibatch_size of 1024 (stated in the comment at self_attention.hpp:1548-1549; the plugin source is outside this repo) that is 4 minibatches of 1024 tokens (64 whole 16-token blocks, 16 pages) per forward, i.e. 4 save_k calls x 1024 items per layer per forward, 64 calls x 1024 items per layer for the whole 8-user prefill (if the plugin used 128, it would be 32 calls x 128 items per forward; the item and block totals do not change). Per layer over the whole prefill: 65,536 items, 4096 whole blocks, 32,768 set_k_block calls (8 KV heads per block), 4096 note_k_block_saved calls, 65,536 note_k_row_saved calls, 65,536 mark_k_complete calls. The store is shared with the main helpers (items > 16), in units of one block.

Q: (5) Is there anything in the prefill path where the row-major tail block matters at 8192 tokens? Confirm from store_k_block's run grouping.
A: No, when every block is whole. store_k_block groups a run as consecutive items with KV work in the same page and the same 16-token block, stopping at 16 items, a page change, a block change or a repeated offset (model.hpp:3284-3301). Prompt tokens have consecutive positions, each forward holds 4096 tokens (64 pages) from page offset 0 of the user's book, and minibatch boundaries fall at multiples of 1024 (chunk_evenly with grains of 8 and 4 chunks of 1024), so every run has n == 16 and takes the whole-block branch (3303 false -> 3324-3339): set_k_block writes the VNNI layout directly and note_k_block_saved sets the 16 row bits and the block bit. No set_k_row, no row-major block, no pending_k_blocks_ entry, no forward-end conversion, and in the loop every block-bit test at 2024 is true so the dotters are never used. The shared store's unit cut (3207-3230) also cuts at block boundaries, so a helper's unit is one whole block. Caveat: if the harness prompt is not a multiple of 16 tokens (template tokens), the last run of each prompt is partial and that one block per user is stored row-major (store_row_major, 4 whole lines per row) and converted at the end of the forward that saves its 16th row (a decode step); one block per user is negligible for TTFT.

Q: (6) Does the lazy-dotter probe remove the dotter construction for prefill page visits too? What does its failure to recover the TTFT eliminate?
A: Yes. In the probe, dot_q is a std::optional for VNNI slots and is built by 'if (!dot_q) dot_q.emplace(make_dot_q());' inside the row-major else branch (probe self_attention.hpp:1979-1985, 2041). At 8192 prefill there is no row-major token (every block is whole, fact (5)), so no prefill visit builds a dotter under the probe. Measured lazyoff vs newoff TTFT at 8192: +21 ms (sd 119, t +0.3) and +100 ms (sd 81, t +2.1), at 1024: +0/+4 ms, i.e. no recovery of the +453..587 ms. This eliminates the per-visit dotter construction (16 zmm loads) and the 16 zmm registers held across the loop (the optional lives in memory in the probe) as the TTFT cause. It does not touch, and therefore leaves as the remaining candidates: the per-relevant-token block-bit test and the plane-optional test in the loop (2020-2025), the first-token k_vnni_blocks acquire load, the larger loop body (the else branch's code is still inside the loop), and the save_k-side per-item note_k_row_saved loop (model.hpp:3426-3436) plus the per-block bookkeeping. The probe did recover +1.6 to +2.3 % of decode TPS at tp2, so dotter construction matters for decode visits but not for TTFT.

## tracing
SUMMARY: Perfetto tracing is enabled through runtron's --trace / --trace-gen / --trace-passes flags or the perfetto/tronperf launcher (which runs runtron with --trace traced). The tree has a main-thread span "convert_k_blocks" (new in PR 4901, carries the block count) and a per-layer "Save K" span, but nothing wraps the note_k_row_saved loop or a page visit; the finest attention span is one per apply_page_range call. TRON_ATTN_STATS (attn_stats.hpp) is present: it counts visits and K tokens per path (empty/avx/amx) and keeps per-job busy cycles, but it has no per-path cycle counter and one "avx" visit covers both the qk_group reader and the row-major dotter tail, so it cannot split those two. The cheapest probe is rdtsc() pairs from h/system/system.hpp at three sites (convert loop, note loop, software loop) with accumulators printed at exit in the page_share exit_reporter pattern or added to attn_stats rows. perf exists on delphi-3bda per the memory note (perf 6.8.12, sudo -n needed, not re-verified here); the build keeps frame pointers and DWARF-4 line info, so perf record -g gives call chains and per-source-line attribution inside the always_inline apply_page_tok, but only on a build-tree binary (the .deb is stripped).

Q: (1) How to enable a Perfetto trace of a runtron run (flag/env, output file, cost)?
A: Two routes. Route A, the launcher: run 'nix run .#tronperf -- --output-file /path/run.trace --gen --trace-passes 300-340 -m qwen-3-4b ... -l 256' inside the checkout. tronperf starts traced and traced_probes, passes '--trace-gen traced' to gen/runtron, and the daemon writes --output-file. '--trace-passes' needs --trace-gen and gates application events to the chosen forward passes (0 = startup, so prefill can be isolated with '1' for the prompt pass, and decode steady state with a late range). TRON_TRACE_FROM_TOKEN=N is the older way to skip the first tokens. Route B, in-process: 'gen/runtron --trace-gen /path/run.trace --trace-passes 300-340 ...' writes the file itself; categories then come from TRON_TRACE_CATEGORIES (for example '-*,+model'). Without --trace-passes an in-process capture stops after 5 s (perfetto_duration_ms). Cost: the memory category measured within 0.2 % of untraced; the memory note from the router work measured a full trace at about 19 % lower TPS and channel waits inflated about 2.5x. So a trace gives structure (which spans, how many, in which thread) and relative sizes, and every magnitude used in a verdict must be re-measured untraced. For the H3 question the trace is cheap in events: 'convert_k_blocks' is one span per forward and 'Save K' is one per layer per thread.

Q: (2) Which existing spans attribute H3 (convert_k_blocks) and save_k time per layer; is there a span around the attention worker loop or per page visit?
A: H3: TRACE_EVENT("model", "convert_k_blocks", "blocks", N) [model.hpp:3178], main thread, once per forward, after wait_for_coop_gof and before logit delivery [model.hpp:1840-1847]; the 'blocks' argument is the queue length, so the trace gives both ns per step and blocks per step directly. Save K: TRACE_EVENT("model", "Save K") [model.hpp:3367] covers the whole save_k_impl of one layer on the main thread (and one span per helper when the store is shared). It includes the note_k_row_saved loop [model.hpp:3425-3437] but does not isolate it; a nested span would be needed for that. Attention: the finest span is per apply_page_range call ('Attention Ready' / 'Attention Pending', with layer, kv head, thread, q range) [self_attention.hpp:1487-1497]; there is no span around run_attention_job (only rdtsc timers at :813-845) and none per page visit. A per-visit span would be too fine: about 36,864 visits per user per decode step at prompt 8192 (36 layers x 8 KV heads x 128 pages).

Q: (3) Is TRON_ATTN_STATS available in this tree, does it count visits per path and cycles, and can it split qk_group from the dotter tail?
A: Yes, it is in the tree (h/tron/models/attn_stats.hpp, included by self_attention.hpp:28, state at :465-493). Switch: environment variable TRON_ATTN_STATS exactly '1'. It counts visits and K tokens per path (empty, avx, amx) per (class, pool worker, layer, ready/pending pass), plus avx_full_page_visits, and it keeps cycle timers T1-T5 (forward wall, per-job busy, job wall on worker 0, layer period, join wait). There is no cycle counter per path, and one avx visit covers both k_vnni::qk_group on the VNNI blocks and the row-major dotter tail of the same page (attn_stats.hpp:112-118; self_attention.hpp:2027-2050 then one return at :2087). So it cannot split the software loop between qk_group and the dotter tail. What it can give for Issue 4934: a kill-switch vs AMX-on comparison of busy_cycles (T2) per layer and of avx_full_page_visits, and a PR 4898 vs PR 4901 comparison of T2 per layer under the kill switch (same visit counts, different time). For batch runtron the stderr '[attn-stats]' report at state destruction is the output; the FUSE leaves need fuse::stats initialized.
