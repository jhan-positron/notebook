• llama-3.1-8b (CPU attention, AMX kernel eligible). canon vs base +1.2 % (paired t +2.8), the only resolved canon effect. The kernel ran: 30.2 billion AMX-busy cycles in the 20 s probe, 0 on base. The target arm had shown +0.8 % on the same config. Both are small. The nightly layout puts 2 users on each engine, and each engine has 28 application cores (the --app-cores list in its unit). A campaign on 2026-09-18 measured the same kernel at +0.2 %, +3.9 % and +12.9 % with 2, 4 and 8 users per engine (VNNIed-K-in-place/status/llama8b-AMX-gain-vs-load.html). The 2-user layout is therefore the likely reason (hypothesis). The CI number cannot show the kernel's larger gains.
  • qwen-3-4b tp2 and tp4 (FPGA attention, AMX only in the CPU share). canon vs base: tp2 +0.1 % (t +0.1), tp4 -2.6 % (t -3.7). The tp4 change is inside that config's 13-night band of 7.0 % (sd 5.09 TPS). It is therefore not resolved. target vs canon: tp2 -5.1 % (t -7.4) and tp4 -8.6 % (t -7.3), both resolved. The kernel did run in canon on tp2 (10.5 billion AMX-busy cycles, target 13.7 billion). Effect B isolates PR #4424 as a package, not one part of it. The loss tracked in issue #4500 appears in target vs canon (tp2 -5.1 %, tp4 -8.6 %, both resolved) and not in canon vs base (tp2 +0.1 %, tp4 -2.6 %, unresolved). So the canonical AMX kernel is not the main cause. The kernel's own share on tp4 is bounded by the unresolved -2.6 % (paired t -3.7, 95 % interval +/-1.6 %, band 7.0 %) and needs a repeat run to be set to zero. Which part of PR #4424 causes the loss (the VNNI-K layout in the K cache, the gof::populate copy of K to the FPGA, or the dispatch changes) is a hypothesis this run cannot separate. The issue #4500 root-cause campaign measures that. Client conditions: the target arm provisioned qwen-3-4b tp2 at 45 % and tp4 at 27 % client CPU pressure, canon at 5 % and 0 %. The stall indicator shows no effect: 2 and 0 anomalous samples in target, 1 and 0 in canon (section 1). The two qwen rows therefore compare like client conditions. Threshold: canon passes the qwen-3-4b tp4 goal of 135 TPS (146.05). The target arm failed it (133.44).
  • mixtral-8x7b (CPU attention, AMX kernel eligible). canon vs base -0.6 % (t -2.2), below the 1 % floor. It is therefore not resolved. No AMX probe ran on mixtral in any arm. Whether the kernel engaged there is therefore not measured in this run. A probe on the mixtral benchmark would resolve it.
  • Controls (no AMX kernel for their shapes). gpt-oss-120b tp4: canon vs base -3.9 % (t -2.6), inside its 13-night band of 5.7 % (sd 3.01 TPS). It is therefore not resolved. The same-day nightly gave 101.16 TPS, closer to canon (102.33) than to base (106.51). llama-3.3-70b tp4 @4u: +1.8 % (t +1.8), t below 2.26, not resolved. Five of the six other controls are within 0.3 % of base. The sixth, llama-3.2-3b, is +1.5 % (95 % interval +/-3.7 %, not resolved). Its base value was lowered by the client stall (hypothesis, see the llama-3.2-3b bullet).
  • llama-3.3-70b tp2 @4u. canon equals base (-0.0 %). target is +1.1 % against base and +1.2 % against canon (t +18.3 against canon). The change belongs to the target arm. Two candidate causes remain: the VNNI-K layout (kv_mul 8, no kernel) or the mix of this config's two TTFT groups (0.3 s and 5 s per request), which differs between runs: mean TTFT 4567 ms base, 3302 ms canon, 3794 ms target. Neither cause is isolated by this data.
  • llama-3.2-3b (client-affected in the earlier arms). canon 197.36 TPS against the same-day nightly's 197.66 (-0.2 %). This is consistent with the base value of 194.54 having been lowered by the client stall on 2026-09-18 (hypothesis). canon vs base is +1.5 % with a 95 % interval of +/-3.7 %. The run therefore does not resolve it. A base repeat on an idle client would. target vs canon -5.1 % (t -19.4) is marked resolved by the rule. The target arm ran this config at 99 % client CPU pressure at provisioning, but its stall indicator shows 3 anomalous samples, the same as canon and the nightly (section 1). So the client-load explanation is not supported by the harness's own indicator. The -5.1 % may be a real PR #4424 effect on a CPU-attention model with kv_mul 3 (the VNNI-K layout applies, the AMX kernel does not). One 10-minute re-run of the target package on llama-3b on an idle client decides it. Until then this page reports it as an open candidate regression of PR #4424, not as noise.
