GDN and AMX: design for Qwen3.5 4B

2026-11-20. Measured on delphi-3b35, our half. tron commit 72e1191804 (open PR #3696). Status: baseline, prediction and design. No solution code is written yet.

Short version

  • Qwen3.5 4B replaces 24 of its 32 attention layers with GDN layers, which keep a matrix of fixed size per sequence, and today no AMX code runs for this model.
  • AMX can speed up GDN in prompt processing (a new block kernel) and the 8 attention layers (a kernel for 256-wide heads), and it cannot speed up GDN in decode.
  • Predicted on delphi-3b35 (est.): time to first token falls by 37 to 45 % and decode speed rises by 1.7 to 7.3 %, and a new loop order without AMX already gives a fall of 14 to 23 %.
Words used here
  • tron, runtron: tron is the inference program under test. runtron is its command-line tool.
  • Qwen3.5 4B: the model under study. Its tron name is ingested-qwen-3.5-4b.
  • GDN (GatedDeltaNet): a recurrent layer type. It does the job of attention with a matrix of fixed size, the state.
  • state S: the memory of a GDN layer. One matrix of 128 key rows by 128 value columns per value head, in FP32.
  • key head, value head: a GDN layer has 16 key heads and 32 value heads. Each key head serves 2 value heads.
  • full attention: ordinary attention: the new token is scored against every earlier token.
  • KV cache, KV page: the stored K and V rows of earlier tokens. tron keeps them in pages of 64 tokens.
  • AMX: Intel Advanced Matrix Extensions. Tile registers of 16 rows by 64 bytes, and instructions that multiply two tiles.
  • tile product (TDPBF16PS): one AMX instruction. It computes 8,192 bf16 multiply-adds and adds them into a 16 by 16 FP32 tile.
  • AVX-512, FMA: 512-bit vector instructions. FMA is the fused multiply-add on 16 FP32 values at once.
  • bf16, FP32: bf16 is a 16-bit float with 8 significant bits. FP32 is the 32-bit float with 24 significant bits.
  • L1, L2 cache: the two private caches of a CPU core: 48 KiB and 2 MiB on this CPU. Data in L1 is the fastest to reach.
  • FPGA cards: the accelerator cards that do tron's large matrix multiplies (projections, feed-forward layers).
  • tp4: the executor that spreads one engine over four FPGA cards.
  • prefill, TTFT: prefill is the processing of the prompt. TTFT is the time to first token: from the request to the first generated token.
  • decode, tok/s: decode is the generation of tokens after the prompt. Its speed is given in tokens per second per user.
  • pass, decode step: a pass is one forward computation through all 32 layers. A prefill pass holds 128 prompt tokens per user. A decode step is a pass with one token per user.
  • chain: the consecutive tokens of one sequence in one pass. A GDN layer must take them in order.
  • step (GDN step): the work of one token for one key head: convolution, recurrence on 2 value heads, norm and gate.
  • main thread, main helpers, attention workers: tron's CPU threads. The main thread and 15 main helpers run GDN. The 40 attention workers run software attention only.
  • attention statistics: counters and timers that tron reports when the environment variable TRON_ATTN_STATS=1 is set.
  • trace: a Perfetto recording made by runtron. Its slice named GatedDeltaNet is tron's only timer for GDN.
  • kill switch: the environment variable TRON_AMX_DISABLE=1. It turns the AMX kernels off at run time.
  • cell: one combination of user count and prompt length.
  • prompt N: a prompt of N tokens. Every run then generates 256 tokens per user.
  • Part 0, Part A, Part B: the three proposed changes. Part 0: a new loop order for GDN prompt processing, no AMX. Part A: the AMX block kernel for GDN. Part B: the AMX attention kernel for 256-wide heads.
  • delphi-3b35, our half: the test server. We use its second socket and FPGA cards 4 to 7. delphi-3bda is its sister machine, where our earlier AMX numbers were measured.
  • est.: an estimate. Every number without it is measured or read from the code.

1. What GDN is, seen from llama-3.1-8b

  • llama-3.1-8b has 32 layers. Every layer is a full-attention layer.
  • Qwen3.5 4B has 32 layers too. 24 are GDN layers and 8 are full-attention layers [Ref1, Ref2].
  • A GDN layer does the job of attention. It mixes what earlier tokens said into the current token. It uses a different mechanism.

  • The 8 full-attention layers of Qwen3.5 4B differ from llama's too. They have 16 query heads of 256 values and 4 KV heads. llama-3.1-8b has 32 heads of 128 values and 8 KV heads.
  • tron's AMX attention kernels accept only 128-wide heads [Ref6]. tron's FPGA attention accepts only 64-wide and 128-wide heads [Ref7].
  • So every attention layer of this model runs the AVX-512 path, at every prompt length. The attention statistics confirm it: 0 K tokens were scored by AMX in all 36 runs [Ref9].

What the numbers say

  • GDN time per pass is constant. It is 20.3 ms per prefill pass with 1 user and 160 ms with 8 users, at every prompt length.
  • One GDN step costs 6.1 us in prefill. The stand-alone benchmark of the kernel agrees: 97.9 us per token per layer on one thread, which is 6.1 us per key head [Ref11].
  • The step is bound by moving the state, not by arithmetic. A value head's matrix is 64 KiB. The L1 cache is 48 KiB. Each token passes over the matrix twice. The measured 3.06 us per value head is about 3 times the time its arithmetic needs (est. 0.95 to 1.16 us).
  • The same step costs 13 to 16 us in decode. In decode the state is fetched from outside the core's own caches for every token, and a check for invalid values reads it once more [Ref4].
  • Only 16 of the 56 CPUs run GDN. With 8 users each of the 16 threads has 8 chains to run, one after another. So the GDN wall with 8 users is 8 times the wall with 1 user.

4. Prediction, made before any test of the solution

Method

  • The layers of a pass run one after another. Inside a layer the FPGA projections, the host work and the next projection run one after another.
  • So a time saved in GDN or in attention shortens the pass by the same amount.
pass_new = pass - GDN_wall x (1 - 1/s_gdn) - attention_wall x (1 - 1/s_attn) + rest x clock_cost
TTFT_new = TTFT - passes x (pass - pass_new)
ms_per_token_new = ms_per_token - (step - step_new)
  • Measured inputs: pass wall, attention wall, number of passes, TTFT and decode speed (attention statistics and runtron, section 2), and the GDN wall (trace, section 3).
  • Measured today for this prediction: the core clock under AMX on delphi-3b35, and the cost of the tile and FMA instructions [Ref11].
  • Estimated inputs: the speedup factors s below. Each is a kernel-level estimate from operation counts and measured instruction costs.

How to read the prediction

  • Part 0 alone (new loop order, no AMX, same bits): TTFT falls by 14 to 23 % (est.).
  • Part A (AMX block kernel for GDN, instead of Part 0's loop): TTFT falls by 18 to 28 % (est.). That is 3 to 5 points more than Part 0. This small step is what AMX itself adds for GDN on this machine.
  • Part B (AMX attention kernel for 256-wide heads): TTFT falls by 9 to 28 % (est.). The gain grows with the prompt length.
  • Parts A and B together: TTFT falls by 37 to 45 % (est.). With the low and the high factors the fall is 22 to 51 %.
  • Decode: speed rises by 1.7 to 7.3 % (est.), all from Part B. With the low and the high factors the change is +0.0 % to +12.1 %. This is the weakest part of the prediction. In decode a tile uses 4 of its 16 rows, and the clock drop takes most of the kernel's gain on this machine.
  • What would prove the prediction wrong: a measured block kernel step slower than 3.0 us, or a pass that does not get shorter when the GDN wall does.
Seen in the same data, and not an AMX matter. With 8 users the 16 GDN threads each run 8 chains in a row while 40 attention workers wait. Spreading the 128 work items over all 56 threads would cut the GDN wall to about 3/8 of today's value (est., from the work-item count). That is 100 ms of the 362 ms prefill pass and 1.8 ms of the 8.1 ms decode step at 8 users and prompt 1,024. It needs a scheduling change, not a new kernel, and it does not help 1 user.

5.2 Part 0: a chain path that keeps the state in L1 (no AMX, same bits)

  • Today. For each token the kernel passes over a 64 KiB matrix twice [Ref3]. The matrix does not fit the 48 KiB L1 cache. So every pass moves it between L2 and L1.
  • Fact used. Each value column of S is its own recurrence. Column c depends only on the keys, the gates and column c of the values.
  • New order. Split each value head into two halves of 64 columns (32 KiB). Run all tokens of the chain on one half. Then run them on the other half. The half stays in L1 for the whole chain.
  • Three phases per chain. Phase 1, per token: convolution, normalization, decay and beta, saved in a small buffer. Phase 2: the recurrence over the chain, half by half. Phase 3, per token: norm and gate.
  • Layout. The per-thread working copy stores each half as one contiguous block. Without that, the half's rows collide in the cache [Ref18].
  • Bits. Unchanged. Every column sees the same operations in the same order.
  • Why it is in an AMX design. It gives about half of the GDN gain. It also builds the chain entry point and the per-token buffers that Part A needs.

5.3 Part A: the AMX block kernel

  • Idea. Process a block of 32 tokens at once. The state is read once and written once per block.
  • Why AMX fits. The three large products become matrix times matrix. A tile product then uses all 16 rows: 19 tile products per value head per token replace 3,072 FMAs.
  • The FP32 state. AMX multiplies bf16 by bf16 only. Each FP32 value is split into 3 bf16 values whose sum is exactly the FP32 value. The product is computed 3 times and added up [Ref18].
  • Same algebra as the reference. Hugging Face Transformers uses this block form (block size 64) for every multi-token call. vLLM and SGLang ship an AMX kernel built on it [Ref14].
  • Phases. The kernel does all tile work of a block first and the AVX-512 work after it, never mixed. Today's clock probe shows why: 2.40 GHz in phases, 1.90 GHz when mixed [Ref11].

5.4 Numerics: what changes and what the contract should say

  • Part 0 changes no bit. Each value column of S is its own recurrence. Running the columns in two halves, with all tokens of the chain per half, executes the same operations in the same order per column. A script confirms equal bits for outputs and state [Ref18].
  • Part A changes the order of the FP32 sums. The result is close to today's, not equal. In the prototype 0.005 to 0.03 % of the bf16 output words differ from today's kernel, each by one bf16 step for all but near-zero outputs [Ref18].
  • It is as accurate as today's kernel. Against a float64 computation the block kernel's output error is 0.3 to 0.65 times the error of today's kernel [Ref18].
  • The 3-piece split is exact. For every FP32 value from 9.9e-32 to 1.7e38 the three bf16 pieces add up to the value (433 million values checked, 0 failures). Two pieces are not enough: they break the 1e-7 test tolerance [Ref18].
  • Decay factors are built by multiplication only. Dividing two running products fails when the product underflows inside a block [Ref18].
  • What the tests say today. The recurrence is checked with an absolute tolerance of 1e-7. But several tests require equal bits between the prefill path and the decode path, and one test pins 320 output words to PyTorch [Ref16].
  • Contract proposed for Part A. The block path stays within a stated error band of the token path. It is used only for the 128 by 128 geometry and only when AMX is on. The token path stays the reference and stays bit-pinned. The bit-equality tests run with the block path off.
  • Consequence to accept. With Part A the state after a prompt depends on where the blocks were cut, at the level of the last FP32 bits. Prefill and decode of the same text then differ in rare output bits. Hugging Face Transformers has the same property: it uses the block form for prompts and the token form for single tokens [Ref14].

5.5 Part B: attention kernels for 256-wide heads

  • Same method as the existing kernels. K and V are bf16 already. No split is needed.
  • QK: 8 steps of 32 dims instead of 4, into the same 4 result tiles. 32 tile products per page and KV head (today's 128-wide kernel: 16) [Ref6].
  • PV: 4 groups of output dims instead of 2. 32 tile products per page and KV head (today: 16).
  • Buffers grow: the packed query group from 4 KiB to 8 KiB, the PV output from 8 KiB to 16 KiB.
  • Gate: shape_ok accepts head width 256 with 4 query heads per KV head. The dispatch, the kill switch and the attention statistics work as today.
  • Numerics: the same two known differences from AVX as today's kernel (weights rounded to nearest, order of the sums). The existing error-band tests extend to the new shape.
  • Clock rule from today's probe: tile products that alternate with 512-bit work page by page run at 1.90 GHz on this machine. The kernel should group tile work into phases if the measurement in step 4 confirms the loss.

5.7 What stays outside this design

  • GDN decode gets no AMX. One token fills 1 or 2 of 16 tile rows. Users cannot share a tile, because each sequence has its own state. The step is bound by moving the state, not by arithmetic.
  • Decode has non-AMX options. The check for invalid values reads the whole state before every token. It could be folded into the first loop. The column-half layout also helps decode. Both keep the bits.
  • Threads. 16 of 56 CPUs run GDN while 40 attention workers wait. Using all threads would cut the GDN wall with 8 users to about 3/8 (est.). It changes the scheduler and the code generator, not a kernel.
  • A state stored in bf16 or fp16 would feed tiles without a split. It is rejected: 7 to 81 % of the output words change in the prototype [Ref18].

Open points

  • Core clock under AMX on delphi-3b35. Measured for stand-alone loops only. Insufficient data for tron's own mix of work. Step 3 and step 4 measure it.
  • Share of the rest of a pass that is CPU work on the 16 GDN threads. It decides how much a lower clock costs outside the kernel. Insufficient data. A trace of the main thread with the matmul category on would give it.
  • Real value ranges of state, decay and beta in this model. The prototype used synthetic inputs. A capture of the GDN inputs of one real prompt would settle the error band.
  • The numerics contract. The owners of the GDN code must decide whether prefill may differ from decode in rare output bits. Part 0 does not need this decision. Part A does.
  • Model status. The model is registered with unvalidated tokens. The design should be re-checked against the stack when it merges.
