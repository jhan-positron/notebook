## traps
- bench_gdn.c was never run on delphi-3b35. Its banner (line 557) and header comments say 'KVM guest on AMD Ryzen 9 9950X' unconditionally. A run on the Xeon prints the wrong host unless that text is changed.
- Rows (1) and (2) of bench_gdn.c exclude normalization, decay, beta and the convolution. They are 'recurrence only'. tron's GDN step (6.4 us) is convolution + prelude + 2 value-head recurrences + norm and gate. Do not compare a bench row with the traced step directly.
- The clock rule of bench_gdn.c (highest calib_tick reading of the run, lowest time of interleaved rounds) fits a noisy guest. On delphi-3b35 the clock depends on the instruction mix (2.70, 2.40 or 1.90 GHz). Interleaving AMX cases and AVX-512 cases in one process makes both the sysfs reading and the calibration ambiguous. Run each case alone for 4 s or more, as clock_probe does with --only.
- The clock probe reads the clock from the shell, with one sample per 0.25 s and the first 1 s dropped. A kernel run shorter than a few seconds gives no usable median. The run() helper also keeps only the last output line (tail -1).
- _mm256_zeroupper() before tile work changes the clock: tile products alone read 2.40 GHz with it and 1.90 GHz without it (clock-probe2.txt tdpz against tdp). Short turns of 4 tile products and 64 FMAs read 1.90 GHz even with it.
- CPUs 108 and 109 (two of the 16 GDN threads, CPUs 96 to 111) and CPU 126 run at 4.00 GHz. A 16-thread benchmark on CPUs 96 to 111 mixes two clocks. Report per thread and select the 2.70 GHz threads by CPU number.
- gen_design.py:108-113 separates fast and slow threads with the threshold 'v < 5.0' us. After Part 0 every thread is below 5 us (prediction 2.7 to 4.6 us), so this threshold then puts all threads in the fast group.
- clock-probe3 probed only 29 of our 56 CPUs. CPUs 98, 99, 103 to 106 and 112 were not probed (the traces show the threads on 98, 99, 103 to 106 at about 6.4 us, like the 2.70 GHz threads). The 4.00 GHz set may change after a reboot; it was read once.
- The clock-probe scripts take no load snapshot. The user's machine rule requires a load snapshot before every performance test and the load in every report. New benchmark scripts must call exec/3b35-inspect-20261112/load-snapshot.sh themselves.
- A one-CPU benchmark keeps our app cores at about 1.8 % busy (1 of 56), below the 5 % refusal limit of run-one.sh. So a campaign can start while a benchmark runs, and the clock-probe scripts refuse only when a runtron already runs. A 16-thread benchmark (about 29 %) makes run-one.sh refuse with exit 3, and 3 consecutive failed runs end the campaign.
- collect.py recognizes only arms named 'on' and 'off' (regex at line 117). A run named with another arm gets arm None and is left out of the per-cell aggregate. Its results folder is hard-coded (line 21).
- The run name does not contain the build tag, and run-one.sh:43 skips a run whose log already holds 'average tok/s'. Two builds in the same NAME folder with the same cell, arm and repetition collide: the second run is silently skipped as 'already done'.
- campaign.sh takes one TAG for the whole invocation. Base and Part 0 are different builds, so one invocation cannot alternate them within a repetition.
- predict.py pools the runs of both arms as baseline samples (cell_median, med). That was valid only because both arms ran the same code on this model. Re-running predict.py on a campaign whose arms differ gives wrong inputs. predict.py also overwrites predictions.json.
- The pass-rule ranges are percent of the BASE run. An A/B run alone gives a percent of its run 1, which already runs Part 0, and is not comparable with a range (design.txt:956-962). Part B and Part A are compared through their fall in seconds divided by the base TTFT.
- 'Part B on today's GDN' (scenario amx_attn) and, in a build that holds Part B, 'Part A with AVX-512 attention' (scenario amx_gdn) are not runnable: no switch selects today's token loop in a build with Part 0, and no switch turns Part B off alone (design.txt:858-861).
- The 2026-11-20 base values are not the denominator of the new comparison. Every session needs its own base run (design.txt:952). The base build of the plan also holds the new counters, which the 2026-11-20 build did not.
- The GDN wall in predictions.json comes from traced runs with 32 generated tokens, with the first pass of each kind left out. The plan wants pass wall and GDN wall from counters in untraced runs, and both walls from the same kind of run (design.txt:552, 915).
- trace.sh has only 4 default cells. The p4096 traces of the baseline were run with a CELLS_ALL override that is saved in no file ('t-1u-p4096|1|4096|32|1-72' and 't-8u-p4096|8|4096|32|1-72' reproduce what rt-results.txt shows).
- analyze_trace.py hard-codes 16 key-head groups (lines 152, 157) and assumes an equal split of work items over the threads. It needs the perfetto Python module, which is on the agent server (python 3.10 user site), so it reads the trace over NFS.
- run-one.sh:28 uses ${ARMENV-...} without a colon. An empty ARMENV stays empty and the attention statistics are then off. It also unsets only TRON_AMX_DISABLE and USE_HW_ATTN, so a new GDN switch variable set in the shell would leak into every run.
- Per-layer and per-worker statistics exist only in the FUSE leaves; the exit report holds totals. poll-leaves2.sh must run next to the campaign, it looks only for a directory named 'attention', and it keeps a snapshot only after the first decode forward.
- bench_gdn.c slice_step does 4 loads, then 4 stores in loop 2; tron's kernel stores chunk c and then loads chunk c+1. In the blocked layout the 4 chunks of a key row are 8,192 B apart (same low 12 address bits). alias_test.c found no cost on the AMD host only; an Intel core may behave differently.
- bench_gdn.c uses _mm512_cvtneps_pbh (AVX512_BF16) and a new AMX kernel needs -mamx-tile -mamx-bf16. The flag set known to work on delphi-3b35 is '-march=x86-64-v4 -mavx512bf16 -mamx-tile -mamx-bf16' with g++; '-march=native' was used only on the AMD host.
- The stand-alone bench is built with gcc -O3, the tron kernel with clang-19 RelWithDebInfo (--preset native). Check the gcc build of today's order against the tron benchmark (3.06 us per value head at 2 MiB state on cpu 140) before trusting a ratio.
- build-3b35.sh fails when the worktree /var/tmp/jhan/b35-gdn-$TAG exists at another commit, and the SHA must be visible in /home/jhan/workspace/tron. Use a new lowercase alphanumeric TAG per build. Never run 'git worktree prune' on that repository, and never edit a script while a copy of it runs (NFS).
- The decode prediction uses ms_per_token = 1000 / tps, not the step wall T1 (predict.py:206, 219). The two differ by the time between decode steps.
- The threshold 1.1 % of the task-5 decode rule is the rounded value of +1.09 % (same_code_spread.out). The threshold 4.6 us is the rounded value of 6.4 / 1.4 = 4.571 us. The pass rules with ranges use unrounded bounds, these two do not.
