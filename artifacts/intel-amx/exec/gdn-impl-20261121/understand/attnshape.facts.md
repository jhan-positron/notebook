## traps
- Packing 8 panels into the existing 4096-byte amx_qpack_slot overruns into the next token's slot (and past the vector for the last token) with no error. The slot size is a state-level constant (self_attention.hpp:259-261), not derived from the geometry, so it does not grow by itself. Add a static_assert in packed_amx_query.
- Do not size the slot from model::head_size. A model can register several kernel geometries; size from the maximum over plugin::attention_kernels of the eligible shapes.
- The PV output buffer must hold 16 rows, not 4: TILESTORED writes all 16 rows at the row stride. For 256 that is 16 * 256 fp32 = 16384 bytes with a row stride of 1024 bytes. The call site (self_attention.hpp:1786) is already right; a test or fake that allocates 4 rows or 16 * 128 floats is overrun.
- The PV kernel hardcodes more than HEAD_SIZE_128: `for (int half = 0; half < 2; half++)`, the store offsets `half * 64 + {0,16,32,48}` and PV_TILES_PER_HALF_4 (amx_attn.cpp:243, 271-274). Replacing only HEAD_SIZE_128 yields the first 128 output dims and leaves dims 128..255 unwritten.
- Each PV tile product covers 16 output dims (32 bf16 of a pair row = 16 dims x 2 tokens), not 32. DIM_STEP_32 in the V offset counts bf16 elements. The V load offset for 256 is `s*16*256*2 + (group*4 + i)*32` elements with stride 1024 bytes.
- t_amx_dispatch_dtype links only while its own file defines every AMX symbol the binary references. If the 256 dispatch is instantiated there (or available/begin_region/end_region are moved to another namespace) without matching fakes, the linker extracts the real amx_attn.cpp object and its definitions collide with the fakes (duplicate-definition link error).
- Part A interaction: if code that runs for every model (for example GDN stats header facts in the model state constructor) calls a symbol defined only in the new amx_gdn.cpp, t_amx_dispatch_dtype extracts that object too. Keep amx_gdn symbols in their own namespace and let the probe call amx_attn_h128g4::available() (which the test fakes), or the claim in the test header that no AMX code is linked no longer holds.
- The exported kernels cannot be header templates: only amx_attn.cpp is compiled with -mamx-tile/-mamx-bf16 and the interface header must stay free of intrinsics. A new source file needs its own set_source_files_properties entry.
- The unnamed namespace with the tile register constants is nested inside tron::amx_attn_h128g4 (amx_attn.cpp:31-101). Code in a second namespace needs a using-directive or a restructured file to reach them; BF16_ROW_BYTES, V_PAIR_ROW_BYTES and O_ROW_BYTES there are the 128 values and must not be reused.
- Refactoring the three 128 kernels into shared templates risks changing the instruction order of a path whose numerics and speed were measured in earlier campaigns. The band tests accept any summation order, so they would not detect a reordering. Leave the 128 bodies unchanged or prove bit equality.
- amx_qpack.resize(items.size()) value-initializes every slot it adds, also when it regrows inside the existing capacity. With 8192-byte slots and 1024-token forwards a regrow zero-fills up to 8 MiB per worker per apply_page_range call. This happens whenever a small batch is followed by a large one (continuous batching).
- The packed query of one token is 8192 bytes, of which 6144 bytes are zero padding (12 of 16 columns). The loop order is page outer, token inner (self_attention.hpp:1561, 1592), so a 1024-token prefill forward streams 8 MiB of packed queries per page and KV head through a 2 MiB L2 cache. The design's cycle counts assume every load from L1 and do not count this stream.
- Each apply_page_range call (one KV head, one page section) repacks every token once: the `amx_packed` bitset is local to the call (1546). Pack cost doubles to 1024 scalar bf16 copies per token and call.
- Widening the gate makes every model with a 256x4 kernel on a bf16 executor take the AMX path in builds with TRON_AMX_DISPATCH=ON, which includes the deb preset (CMakePresets.json:68). That changes their attention numerics within the documented band, not only Qwen3.5 4B.
- avx_full_page_visits is documented as AMX-eligible volume that did not take the AMX path. For a model whose shape is not eligible (this model today) the counter still counts, so its baseline value is the volume Part B is expected to move, not a sign of a failing predicate.
- The band tests execute AMX only when available() is true; on a host without AMX they pass by skipping with a WARN. A green CI run does not prove the 256 kernels ran. Run t_amx_numerics on delphi-3b35 and check that no skip warning is printed.
- The fakes in t_amx_dispatch_dtype.cpp are compiled in every build (they are outside #ifdef TRON_AMX_DISPATCH), so new fakes need the new declarations to exist in the interface header without the build option, as the existing ones do.
- amx_attn_h128g4::eligible must keep returning false for (256, 4): t_amx_numerics.cpp:109-113 and the namespace name depend on it. Put the 256 gate in the new namespace and OR the two at the call sites instead of widening the existing shape_ok.

## open questions
- Which other models in config/models.yaml declare an attention kernel with head 256 and 4 query heads per KV head (the gemma-4 entries and other ingested models were not checkable: no build tree and no generated plugin headers exist in the worktree)? Measurement that resolves it: grep the generated plugin headers of a full build for `attention_geometry{N, tron::kv_geometry{N/4, 256}}`.
- Slot sizing: per-model constant from plugin::attention_kernels (128-only models keep 4096-byte slots) or 8192 bytes for every model? The first keeps existing models unchanged; the second is one line. Not decided by the code.
- Does the 8 MiB per-worker packed-query stream in 1024-token prefill forwards lower the Part B gain below the design's working value? Insufficient data: the design's counts assume L1 loads. Task 4 (stand-alone kernel timing) with 1024 packed queries per page, or busy_cycles per ready_amx visit from the A/B run, would resolve it.
- Does `model<llm<config, host_bf16>>` instantiate with head_size 256, n_heads 4, n_kv_heads 1 for a 256 arm of t_amx_dispatch_dtype? llama.hpp builds head 256 for gemma_2_2b (8 heads, 4 KV heads), but this exact config was not compiled here.
- Should a 256 arm be added to t_amx_dispatch_dtype in this change, or only the kernel band tests? The design text (5.6) lists the dispatch test file under Part B tests but does not state the cases.
- Is there a CI runner with AMX for the new band cases? README.ci.md:592-594 says the kernel cases execute only when the job lands on a Granite Rapids runner; issue 3997 (src/tron/CMakeLists.txt:216-217) is still a TODO.
- Should the shape-independent entry points (available, begin_region, end_region) keep the qualified name amx_attn_h128g4:: at the 256 call sites, or get using-declarations in amx_attn_h256g4? Both resolve to the same symbols; the first has the smaller diff.
- Is the design's optional step (4 query tokens per kernel call, so all 16 tile rows carry data and the padding of the packed query disappears) wanted if the packed-query stream turns out to cost time? It is outside the prediction and would change the packer layout and the call site loop.
