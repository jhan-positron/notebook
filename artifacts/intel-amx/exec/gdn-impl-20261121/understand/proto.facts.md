## traps
- Applying the scale in the wrong place. Specified: CQ = (w*H)*scale (two multiplies in this order) and sg = g*scale, inside the FP32 coefficients. 03_amx_emulation.py multiplies the finished sum by scale, and integration/gdn_block_math.py scales the tile result; both give other bits.
- Using tron's round_to<bf16> for the split. The rule is truncation (clear the low 16 bits). Round to nearest gives infinite pieces for abs(x) >= 2^128 - 2^119 and is the rule of gdn_block_proto.py, not of the design.
- Packing the third piece without a mask. bench_gdn.c:195-196 does or(srli(even,16), odd). For abs(x) < 2^-110 the third piece has low bits set, so the OR corrupts the even word. Store only the top 16 bits (for example a 16-bit word blend with mask 0xAAAAAAAA).
- Summing tile product 1 in another order. The verified order per accumulator element is key block 0..3 outer and pieces lo, mid, hi inner. Pieces outer (the prototype's tdp_mm) changes 3,571 of 16,384 FP32 outputs.
- Building decay products by dividing two running products, or by a prefix product and ratios. Each w_tu must be w_(t-1,u) * d_t with one rounded multiply; the diagonal is exactly 1.
- Index slips that the mutation test caught: o_t must include the u = t term with the delta_t just computed; r_t uses g_t, not g_(t-1); W uses row B of w (w_Bu), and W[B] = delta_B.
- Writing delta as an fma or fnmadd. It is (v - r) * beta: subtract, round, multiply, round. Likewise r and o start with a plain multiply (g_t * R0, sg_t * U0), not an fma onto zero.
- Loading the accumulator tiles of tile product 3 from the decayed state (the form that 07_tile_layout_check.py verified). The design form starts from zero, stores 4 tiles to a 4 KiB scratch and then does S = fma(g_B, S0, T). Bits and load counts differ (112 against 176 loads).
- Guarding only S0 and W. Case F3 gives 128 non-finite outputs with both finite, because Q S0 overflows before the decay is applied. The outputs (or Q S0) need a guard too, and all guards must be decided before the first state write.
- Assuming an infinite start state cannot occur. The executor rejects NaN only. An infinity splits into inf, NaN, NaN, so the block must fall back to keep the token path's IEEE result.
- Treating decay or beta as per key head. Both are per value head, so g, w, CK, CQ, sg are per value head. Only the bf16 packs of K and Q and the Gram results G, H are shared by the 2 value heads.
- Swapping the operand roles. A is row-major (row = output row, 32 bf16 = inner index). B is pair-interleaved: B[k][2n+e] = M[inner 2k+e][output column n]. Call order is _tile_dpbf16ps(accumulator, A, B).
- Writing a scalar reference without DAZ/FTZ or with a multiply followed by an add. The instruction ignores MXCSR, reads inputs below 2^-126 as zero, flushes results below 2^-126, and uses fma steps in two chains (even, odd) of 16.
- Using gdn_common.fma32 (kernel/03) as a bit reference. It rounds twice through float64. The exact emulations are in gdn_block_proto.py:62-83 and vm_engine.py:69-79.
- Expecting some outputs to be bit-equal to the token path. Even the first token of a block differs in FP32 bits. Tests must use a band, and an absolute 1e-7 band is too tight at state size 0.5 (the token loop itself reaches 1.05e-7).
- Putting a bf16 step limit on all outputs. Outputs near zero differ by up to 67 steps at C = 32. Only outputs at or above 1 % of the rms are within 1 step.
- Reading the scripts' variable G as the design's G. In vm_engine, the prototype and lead_numerics, G is the decay-product matrix (design w and g). The design's G and H are KK and QK there, and A and B in kernel/01 and kernel/03.
- Setting FTZ or DAZ in MXCSR for the AVX-512 parts, or assuming it is set. tron leaves it off. The split's remainders rely on plain FP32 subtraction, and small decays put subnormal values into the coefficient code (slow path of the CPU).
- Forgetting the third bf16 layout of K. The kernel needs KQ_a (rows), KT_a (transposed rows, A operand of product 3) and KT_b (pair-interleaved transpose, B operand of product 2). The last pack is missing from the old specification's operation list.
- Running the block form on a partial block or off the 32-token grid. The scripts only checked full blocks (block_spec asserts T % C == 0 and C % 32 == 0); the design sends other tokens to the column-half path.

## open questions
- Which intermediates trigger the fallback, exactly? The scripts model guards on S0 and W only, and no script implements a fallback. The design says 'start state or an intermediate result'. My inference (not checked by a script): guards on S0, the 32 output rows and W cover stages 1 to 3.
- Tile product 3 and the final fma can overflow with finite S0 and W (32 terms of size abs(k) <= about 1.005 times abs(W)). In the design form the state is written part by part, so such an overflow is seen after earlier parts are written. Options: a magnitude guard on W and S0 before stage 4b, or store all 64 result tiles first (64 KiB). No script covers this.
