## traps
- Reading the forward class from self_attn_state.stats->current_class_ix() is wrong when TRON_ATTN_STATS is unset: the store happens only when the attention stats are enabled, so every forward would read class 0 (decode_like). GDN stats need their own class store, fed with the same expression at model.hpp:2112-2114.
- Worker 0 of run_gdn_operation is the scheduler thread, not a pool worker. The attention rows (sized app_pool().num_workers(), keyed by pool worker) have no slot for it. GDN rows need 1 + app_pool().num_workers() entries, indexed by worker_ix directly. Do not reuse attn_stats::model_stats::pool_worker().
- inc_relaxed is load + add + store and is correct only with one writer per row. A GDN row [class][worker_ix][op] has one writer because one worker_ix runs on one thread in a forward. Any shared per-op counter (for example the wall fold) must be written by the main thread only, or use fetch_add.
- Do not put timers or counters inside gdn_rolling_executor::step() or gdn_recurrence. gated_delta_net.hpp:113-116 records that an inlining change in this loop made replay slower. Time around the token loop in run_gdn_operation. Otherwise the base-build timing changes and the Part 0 comparison is spoiled.
- Take the entry stamp after `if (worker_ix >= work_item_count) return;` and next to the TRACE_EVENT. A stamp at function entry would count empty shards as jobs and would not match the traced GDN wall used in the design.
- The row key must be the GDN operation id. The C++ descriptor has no model layer, and gdn_op_id 3 is model layer 4 for this model. Labelling the leaves `layer_<L>` would mislead; use `op_<I>` and document the mapping (layer = op + op/3 for Qwen3.5 4B).
- Gate the object on `!gdn_operations.empty()`, not on `recurrent_execution`. The test plugin recurrent_mock has recurrent_execution = true and no GDN operation.
- A new run_gdn_operation parameter needs the generator change in TronCpp.hs gdnExecutionCall. The file exec/results/gdn-20261120/plugin/qwen_3p5_4b.hpp is only a copy of one generated output and is not compiled. Make the parameter a defaulted trailing pointer so the two calls in t_gated_delta_net.cpp and a header rendered by a prebuilt generator (TRON_GENERATED_GDN_SCHEDULER_EXECUTABLE) still compile.
- model::state builds plugin_state before self_attn_state, and min/max_main_helpers are declared after both. A GDN stats member built in the init list must not read max_main_helpers. Size the rows from app_pool().num_workers(), and build the object in the constructor body or after cfg in the init list.
- Do not pass exported=true to make_file for the new leaves. Exported leaves need a manifest descriptor, markers and an allowed dimension name, and t_tronstats_convention plus the live /exported/ merge gate would then apply.
- Keep every leaf one JSON object below 2048 characters and split by op and by worker, as the attention leaves do. The test at t_attn_stats.cpp:483-558 sets this convention, although a read callback may serve longer strings.
- Off-state leaves must match the README contract of the attention group: summary exists and says "on":false, <class>_totals and <class>_forwards exist and read {}, per-op and per-worker leaves are not registered.
- cycles_to_ns, tsc_in_ns and get_corrected_ns assert on TSC calibration. Using them in the hooks would abort unit tests that never start the calibration thread. Use raw rdtsc and publish tsc_hz from get_cpu_freq() in the summary.
- The GDN wall (first start to last end) needs timestamps from different threads. Raw TSC is safe for that on 3b35 (offsets within 46 cycles), but system.cpp:2178-2182 warns of per-core offsets in general. Also keep the same-thread busy_cycles per row, and document the wall as a raw-TSC span.
- The per-forward scratch (entry and exit stamps per worker and op) must be zeroed by the main thread in begin_forward and read only in end_forward. That is safe only because the plugin's run waits for all workers before it returns (model.hpp:2232-2240) and the scope object lives in forward().
- The counters must land as their own commit before Part 0. The design's base build has no Part 0 but must print the GDN wall and the pass wall. In that build every chain, also a prefill chain of 128 tokens, runs the step() loop and must be counted under the token path.
- A data member named `gdn_stats` next to the namespace `tron::gdn_stats` compiles (qualified lookup before `::` ignores data members) but reads badly. The attention code avoids it: the member is `stats`. Use another member name, for example `gdn_path_stats`.
- Test sources must use made-up model ids. A real model slug in a test file trips the CMake model-requirement audit (t_attn_stats.cpp:628-629).
- A new test target needs a row in config/test-benchmarks.json (t/AGENTS.md:23-26). Adding t_gdn_stats.cpp as a second FILES entry of t_gated_delta_net avoids that, the way t_attn_stats.cpp rides on t_llama_unit.
- The summary fact amx_available comes from amx_attn_h128g4::available() today. For Part B (256 x 4) and for the GDN summary, take the fact from the probe that applies to the shape, and add a separate fact for the GDN switch, so an A/B run can be verified from the exit report.
- The exit report is printed from the destructor of the shared object. A FUSE read callback holds a temporary strong reference (weak.lock()), so the last release, and the print, can happen on the FUSE thread. Keep print_report free of state that only the model thread may touch.
- exec/gdn-20261120/run-one.sh, collect.py and build-3b35.sh know only TRON_ATTN_STATS and [attn-stats]. Without TRON_GDN_STATS=1 in ARMENV and a [gdn-stats] parser, a campaign run would produce no GDN numbers and no error.

## open questions
- Names are not fixed by the design text: the stats switch (proposed TRON_GDN_STATS), the GDN switch that turns the AMX block path off (the design only calls it "the GDN switch"), and the leaf directory (proposed /model/<id>/gdn).
- Should rows be keyed by GDN operation id (proposed, no descriptor change) or by model layer? Keying by layer needs a model_layer field in gdn_operation_descriptor, a generator change in gdnOperationDescriptorExpr, and edits of every brace-initialized descriptor in t_gated_delta_net.cpp and t_llama_unit.cpp.
- Is a new defaulted parameter on run_gdn_operation plus a one-line generator change acceptable to the owners of the GDN stack (open PR #3696)? No alternative without a signature change was found: none of the current arguments can carry a stats object.
- Time cost of the hooks when on is not measured. Insufficient data: an A/B run of the base build with TRON_GDN_STATS unset and set, in the 6 cells, would give it. The proposal takes about 4 to 6 rdtsc per (chain, key head) work item.
- Is the raw-TSC span (max exit minus min entry across threads) acceptable as the GDN wall on machines other than 3b35? Only 3b35 offsets were read (at most 46 cycles apart). A check would compare the counter wall with the traced GDN wall of one traced run.
- Does any GDN model run as an EAGLE draft state? The attention code publishes a draft under attention_eagle because the draft shares the target's model id. qwen_3p5_4b has is_eagle = false. The proposal keeps the suffix rule for parity; it can be dropped if no GDN draft exists.
- Should the GDN forward record repeat the pass wall (forwards, wall_cycles), or should a campaign read it from the attention forwards leaf with both switches set? The proposal repeats it so that TRON_GDN_STATS alone gives GDN share of the pass.
- Where should the tally type live so that gdn_rolling_executor.hpp (Part 0's advance) does not pull the FUSE headers through gdn_stats.hpp into kernel-level translation units? Not decided; attn_stats.hpp includes system/fuse_stats.hpp and system/fuse_sysfs.hpp unconditionally.
