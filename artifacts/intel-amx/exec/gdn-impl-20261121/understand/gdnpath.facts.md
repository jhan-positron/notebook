## traps
- A chain is not limited to 128 tokens. The scheduler bound is max_minibatch_size = 1024 (full.hpp:2619-2620, plugin line 58). 128 is only the default prompt chunk of the generation layer (libtron.hpp:194-206). A per-token buffer of about 2 KiB sized for 128 tokens overflows; at 1,024 tokens it needs about 2.1 MiB per work item, which no longer fits the 2 MiB L2 cache. Size it from chain.order.size() or run the three phases per sub-chain.
- Chain lengths are arbitrary (1 to 1,024): pass-capacity cuts, keep points and resume points end chains anywhere. 32-token blocks must be counted from the chain start, and the last block can be short.
- There is no contiguous [token][channel] buffer. Each token row is its own DMA allocation, and the job ids of one chain need not be consecutive (jobs of different chains may interleave). Read rows only through buffer[job] for job in chain.order.
- The decay and update rows are 32 values wide but each occupies 8,192 bytes of its own. Reading them for many tokens touches one separate cache line per token per row.
- Rows can be bf16 (dmatensor) or float (tensor, used by the unit tests and by the generated test plugin on a host executor), and const views also satisfy the read concept. advance() must compile and give equal bytes for all of them; raw() on dmatensor is non-const and tensor has no data.get().
- mixed_qkv, output_gate, decay and update arrive as `auto const&` buffers and output as `auto&`. The executor header does not include tron/models/common.hpp, so token_job_id is unknown there. Either pass rows per token from run_gdn_operation or add the include and a buffer-level concept.
- run_gdn_operation has no handle to the model state. Counters (gdn_stats) and the GDN switch cannot be reached from its 11 arguments. Changing the signature means editing TronCpp.hs:3121-3145, regenerating every ingested plugin, the generated test plugin (ingest/test/generated-gdn-scheduler) and the direct calls in t_gated_delta_net.cpp:2014 and 2285.
- gdn_operation_descriptor has no layer id. Operation i is layer i + i/3 only for this model. A counter keyed 'per layer' needs a mapping or must key by gdn_op_id.
- GDN worker 0 is the forward thread, not a pool worker. attn_stats keys rows by pool worker; that indexing does not cover the forward thread. GDN rows need 1 + n_main_helpers entries, and n_main_helpers can reach max_main_helpers (27 here) with the environment variables.
- A forward can mix 1-token chains (decode of one user) with long chains (prompt chunk of another user). Path counters must be counted per work item or per chain, not per forward class.
- gdn_recurrence normalizes q and k and computes decay and beta inside the call. A chain path that hoists them must use the same expressions, including the scalar libm calls (std::exp, std::log1p) and `normalized_query[k] * query_scale` as a scalar product before the broadcast, or the bits change.
- Keep explicit fma() calls and separate statements. A new expression of the form a*b + c in scalar or vector code can be contracted by clang into one fused operation and change bits.
- The convolution shifts its history on every call (gdn_conv1d_silu). Phase 1 must run the tokens in chain order, exactly once each, and source_chunks must name each chunk at most once.
- postprocess() rounds its `values` argument in place and writes only the group's 16 output chunks. Phase 3 needs each token's unrounded FP32 recurrence output, so phase 2 must keep 256 floats per token per group.
- The working copy keeps the history at payload offsets in a buffer of the whole operation's history (98,304 bytes), and write_checkpoint copies from working_->recurrent_state and working_->convolution_history. If advance() keeps the state in separate column-half buffers, it must write them back before write_checkpoint runs.
- Source and destination can be the same bytes for a chain of 2+ tokens (a prompt chunk that continues in place). Other holders can read a distinct source at the same time; never write it.
- The NaN scan runs on the working copy inside start_from_checkpoint and reads all 131,072 state bytes of the group before the first token. It also pulls the state into the cache. Moving or merging it changes the cost picture of the first token; it must still cover state and history.
- tests call step() on multi-token chains after a start with in_place access. If advance() supports only working_copy, it must assert that, and step() must stay correct for every access mode.
- The header gdn_execution.hpp is compiled in the plugin translation unit without AMX flags. The tile bracket and the kernel must be out-of-line functions in the AMX translation unit, and every call site must sit inside #ifdef TRON_AMX_DISPATCH with a run-time check.
- A bracket around the whole worker loop would enclose memcpy and the AVX-512 NaN scan of every work item. The design asks for one bracket per work item around the chain replay only (the place of gdn_execution.hpp:141-143).
- With 16 workers, worker w always runs head group w, and CPUs 108 and 109 run the step in 3.8 to 4.0 us against 6.4 to 6.5 us on the other 14 threads. Per-thread timings compare unlike CPUs, and the slowest thread sets the layer's wall time.
- gdn_conv1d_silu is noinline because its inlining once stopped clang from inlining step into the replay loop. A new branch in that loop can change the inlining of the 1-token path. Check decode speed against the base build.
- The trace analysis (analyze_trace.py) selects slices named GatedDeltaNet with the argument operation. Renaming the slice or adding inner slices of the same name breaks the existing numbers.
- The output rows feed an FPGA matmul and finish_writing follows the call. All output rows of the worker's groups must be written before run_gdn_operation returns.
- t_amx_dispatch_dtype.cpp defines a CPU fake for every amx_attn_h128g4 entry point so that the linker does not pull amx_attn.cpp. New entry points referenced from headers that this test instantiates need fakes there too.
- With a block kernel the state bits depend on where the scheduler cuts a chain, because the FP32 sum order depends on the block partition. Today the GDN bits do not depend on the cuts. Runs with other user counts, chunk limits or snapshots then give other bits.

## open questions
- Is the forward thread (the work_queue jthread) pinned to exactly one CPU? Its code calls no pin function (work_queue.hpp:433-451); it inherits the mask of the thread that called request_worker(). Traces name it 96/?-work_queue. Reading Cpus_allowed_list of that thread during a run would settle it.
- What does the NaN scan cost per decode step in time? Only the byte count is known (50.25 MiB per user per step). A TSC timer around validate_checkpoint_values, or a build without it, would give the time.
- How should gdn_stats reach run_gdn_operation: a new argument through the generator (TronCpp.hs and regenerated plugins), counters stored in the per-worker executors, or a process-wide object? The current signature offers no handle.
- Should advance() also serve chains started with in_place access, or only working_copy? run_gdn_operation uses working_copy for every chain of 2+ tokens, but the tests start multi-token chains in place.
- Which tests compare logits of a GDN model against recorded values (pay_for_determinism goldens)? They were not searched. Part A changes bits and makes them depend on chain cuts.
- Does the new branch in the replay loop change the inlining of step() for 1-token chains and so the decode speed? Not measurable without a build; an A/B decode run against the base build answers it.
- Not found: any existing GDN counter or timer (only the one TRACE_EVENT), any multi-token or contiguous activation view, any begin_region call on the forward thread or the main helpers, any generator golden text that contains run_gdn_operation.
