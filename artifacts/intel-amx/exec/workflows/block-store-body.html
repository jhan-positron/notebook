Tron · Pull request 4424 · An interactive explanation

Block store: turn token rows
into complete cache lines.

Short version

Block store collects keys from up to 16 tokens and rearranges them in vector registers. A full block then writes 64 complete cache lines, instead of writing a small piece of each line for every token. The saved values and the total payload stay the same. [1]

Source: PR #4424, commit 30c4ac82cb, checked 21 September 2026. Companion: how shared save works. Illustrative data and Measured results are labeled separately. No new hardware benchmark was run for this page.

Words used here

Tron, token, pass
Tron is the inference program under test. A token is a piece of text. A pass processes a batch of tokens through the model.
K, V, head, attention
K and V are key and value vectors. A head is one group of these vectors. Attention uses keys to score how much each saved value contributes.
Dimension, bf16, pair
A dimension is one value in a vector. bf16 is a 2-byte floating-point format. A dimension pair is two adjacent values: 4 bytes.
Page, plane, block, panel
A page holds 64 tokens. A K plane holds one head’s keys for that page. A block covers 16 token positions. A panel holds 32 dimensions of a block.
AVX-512, register, lane
AVX-512 is an instruction set for the CPU (host processor). Its vector register holds 64 bytes. Here each register has 16 lanes of 4 bytes each.
AMX, VNNI layout
AMX is a CPU instruction set for matrix multiplication. VNNI layout puts one dimension pair from 16 tokens in a 64-byte row for its right-hand input.
Cache line, scatter, mask
A cache line is a 64-byte memory unit here. A scatter writes lanes to separate addresses. A mask selects which lanes a store may write.
Layer, prefill, decode
A layer is a repeated model stage. Prefill processes prompt tokens. Decode generates subsequent tokens.
Block store, shared save
Save K copies keys into their saved pages. Block store changes how one worker writes them. Shared save divides the work among the main thread and its existing helper threads.
01

The destination wants a pair from every token

The incoming keys are rows: 128 bf16 values per token, per head. PR4424 stores those keys in VNNI layout so AMX can read them directly as its right-hand matrix. One destination line holds the same dimension pair from 16 tokens. [1]

Per-token scatter

One token touches 64 lines

A token supplies 64 dimension pairs. Each pair writes 4 bytes in a different line. The next token writes the neighboring 4 bytes in those same lines.

t0t1t2t3t4t5t6t7t8t9t10t11t12t13t14t15

One line receives 16 separate 4-byte writes.

Each token issues 4 scatter instructions. Each instruction sends 16 pairs to 16 different lines. [1]

Full block store

Combine the tokens before writing

Load 16 token slices. Transpose the pairs in registers. Each output register now holds one complete destination line.

t0t1t2t3t4t5t6t7t8t9t10t11t12t13t14t15

One line receives one 64-byte store.

Repeat for 64 dimension pairs. The transpose moves bits without changing their values. The writer uses AVX-512 instructions. [1]

What happens inside the transpose?

For one dimension step, the input register indexed by token lane contains 16 dimension pairs. The output register indexed by pair contains that pair from all 16 token lanes. The source implements this exchange in four stages: interleave 32-bit lanes, interleave 64-bit groups, then two stages that rearrange 128-bit groups. Each stage uses 16 shuffle operations. This is 64 operations per panel and 256 operations across the four panels of a full block. [1]

The two bf16 values of a pair stay together in their 32-bit lane. Absent token registers are filled with zero without loading a source row. The final lane mask prevents those zeros from overwriting other tokens in memory.

03

A block occupies four separated panels

One K plane contains 64 tokens × 128 dimensions × 2 bytes = 16 KiB (16,384 bytes). It holds 16 panels of 1 KiB each. The panels are ordered by dimension step first, then token block. [1]

One head’s K plane · offsets from its start

Every panel is 16 pair rows × 16 tokens × 4 bytes = 1024 bytes. Each pair row is 64 bytes. Changing the block or dimension step above updates the highlighted panels.

All indices start at zero. s is the dimension step; c is the token block. pair is the pair within that step. lane is the token’s position in its block. j selects the first or second value of the pair.

This is the source’s index() element map multiplied by 2 bytes per bf16 value. [1]

A panel is the size and layout of one AMX input tile. In the PR’s eligible attention path over full pages, attention computes S = Q × Kᵀ directly. Here Q means query vectors, S means attention scores, and Kᵀ means keys arranged by dimension across tokens. [5]

04

The number of tokens selects the write pattern

The build must enable TRON_K_VNNI, the option for this K layout. The K head must have 128 dimensions. Other head sizes retain their original per-token row storage. [1]

A run is about destination positions

  • It cannot cross a page or a 16-token block.
  • It stops before a duplicate destination position.
  • Positions can be sparse or arrive out of order. The writer puts each row pointer at its destination lane.
  • For example, page offsets 21, 25 and 18 can use one masked block store. Offsets 31 and 32 belong to different blocks. [2]
Shared work units impose additional boundaries

The shared-save partitioner cuts the item list when the page, block or “needs K/V work” flag changes. Each worker scans only its assigned item range. Within a range, the block writer skips items without K/V work. The partitioner can therefore split a run that a single unshared scan could combine. [2]

Block store and shared save are separate

Block store can run on one thread. It can also apply to a pass with at most 16 items.

Shared save adds helper threads when the eligible pass has more than 16 items and 2–128 workers, including main. The same block writer runs inside each claimed work unit. [2]

In the measured 8-user decode workload, each user contributes one token to its own page. Those items form single-token runs. They use scatter stores. [4]

Sources and verification

The low-level block-store test compares the complete destination plane against per-token scatter. It includes 38 masks at each of 4 block positions: 152 comparisons. Unwritten positions begin with a marker value, so an unintended overwrite changes the comparison. These are source-level test assertions; the test suite was not rerun for this page. [3]
