First nightly with the AMX kernels: is 32.5 TPS what we expected?

Short version

Yes: last night’s 32.5 TPS is the value we expected once the AMX kernels reached the nightly package.

It is +15.0 % above the night before (28.25 TPS), and our own campaign measured +14.0 % for the same test.

The 09-22 prefill rate, which Slack did not print, was 220 tok/s (TTFT 18.6 s).

Words used here

TPS
Decode speed: generated tokens per second for one user. The CI harness measures it between generated tokens 896 and 1024 of each request and reports the mean over all samples.
TTFT
Time to first token: the time from sending a request to receiving its first generated token, in milliseconds. With 8 users per engine it includes the wait behind other users’ prompts.
prefill rate (prefill≈)
Prompt length divided by mean TTFT, in tokens per second (tok/s). The CI computes it on the client. It is not a server-side prefill timing.
AMX
Advanced Matrix Extensions: the matrix unit in Intel Xeon CPUs, such as the Xeon 6962P in delphi-3bda.
AMX kernels
tron’s attention code that uses AMX. It is compiled in only when the build option TRON_AMX_DISPATCH is ON. PR #4505 turned it on for the nightly .deb package.
no-kernel / kernels-in package
A tron package built without / with the AMX kernels.
kill switch
The environment variable TRON_AMX_DISABLE. It turns the AMX kernels off at run time in a kernels-in build.
canon
Our 09-20 kernels-in build: tron main 3faba6d0 plus the AMX build option, with the canonical (default) AMX kernels.
tron, rinzler
tron is the inference program under test. rinzler is the server binary inside the tron package.
delphi-3bda, andoria-b1a3
The two CI machines: Intel Xeon 6962P (has AMX) and AMD Genoa (no AMX unit).
tp2, tp4
The model is split over 2 or 4 accelerator cards (tensor parallel).
@32u per machine
32 users in total, spread over 4 engines: 8 users per engine.
p05, sd
p05 is the 5th percentile of the per-user TPS samples (95 % of samples are faster). sd is the population standard deviation of those samples.
systems_test, talos, publish-deb
systems_test is the repository with the CI harness. talos is the bot that posts the nightly report to Slack. publish-deb is the tron workflow that builds the nightly package at 01:35 UTC.

1. Is 32.5 TPS what we expected?

Chart 1 places the two nights of the CI row next to our 09-20 campaign of the same test (32 users, prompt 4096 tokens, 1536 generated tokens). The shaded band is the range we wrote down before our campaign: +11 to +21 % over the no-kernel value [CI-test/status/llama-3.1-8b-8u-4k-plan.md, section 7].

  • The CI value is 32.494 TPS, the mean of 320 samples. Slack rounds it to 32.5.
  • The CI gain is +15.0 %. Our campaign measured +14.0 % (paired t 338 over 3 pass pairs).
  • The CI value is +0.29 TPS (+0.9 %) above our canon mean of 32.206 TPS. Our three canon passes spanned 32.18 to 32.24 TPS, so the CI value is above all three. On 09-22 the no-kernel values agreed to +0.02 %. Section 5 lists what could cause the 0.9 % gap.
  • TTFT is 11,569 ms, +0.8 % slower than our canon (11,481 ms). My estimate on 09-22 was 11.2 to 11.5 s, so the CI value is 0.07 s above its upper edge.
  • The row still has no threshold. “(placeholder threshold)” is only a display label. With the thresholds we proposed (mean 30.6, p05 30.3, slowest 30.0 TPS; CI-test/status/llama-3.1-8b.html section 9.4), this night passes by 1.89, 1.93 and 2.08 TPS.

2. The prefill rate of the 09-22 row

The 09-22 row was measured like every other row. Only its Slack line was shorter. These are the two lines as posted:

09-22: llama-3.1-8b-instruct-good-tp2 @32u per machine (AMX benchmark): 28.3 TPS 09-23: llama-3.1-8b-instruct-good-tp2 @32u per machine (AMX benchmark): 32.5 TPS (placeholder threshold), prefill~354 tok/s, TTFT 11569ms (@4.1k prompt)

The value

  • Mean TTFT over the 320 samples was 18,646.29 ms. The harness rounds it to 18,646 ms.
  • Prefill = 4096 tokens / 18.646 s = 219.7 tok/s. The Slack line would have read “prefill≈220 tok/s, TTFT 18646ms (@4.1k prompt)”.
  • The AMD row of 09-22 also lacked it: 308.8 tok/s (TTFT 13,266 ms).

Why Slack did not print it

  • The 09-22 nightly ran systems_test commit 7327184. In that version, a row with no threshold at all got a short line with the TPS value only [testlib/results.py, branch if not has_threshold].
  • The gemma-4 row printed timing that same night. It has a placeholder goal of 1.00 TPS in scripts/system_ci.py, so it took the placeholder branch, which already added timing. The AMX row had no goal entry.
  • PR #227, “Include prefill and TTFT in uncalibrated benchmark Slack reports”, changed the short line to the placeholder format with timing. It merged at 2026-09-22 17:48:38 UTC, after the 09-22 run. The 09-23 run used commit 5b2250b9, which includes it.
  • The harness computed the value on 09-22 as well. The formula at scripts/perf.py:396-397 is the same in both commits, and it stores prefill with each result. Only the Slack line left it out.

Check of the method

The same computation over the 09-23 log gives TTFT 11,569 ms and 354 tok/s. Those are the numbers Slack printed. For the AMD row it gives 13,324 ms and 307 tok/s, also as printed. The per-sample TTFT means match the Slack TTFT of all 13 rows on both machines for 09-23.

5. What is not explained yet

Open item A

The CI kernels-in value is +0.9 % above ours. On 09-22 the no-kernel values agreed to +0.02 % with the same binary. So the harness setup, the prompt set and platformd 0.11 did not change the no-kernel value.

The two kernels-in builds differ in their tron code. CI ran main 5cf65b9241, which is 32 merges (102 commits) after our canon base 3faba6d0.

Hypothesis: one of those merges speeds up this row on Intel with AMX. Candidates by title: #4455 and #4456 (sliding KV storage and reclamation), #4516 (slice cost data for the Xeon 6962P), #4258 (FPGA attention streaming join), and the placement changes. Measurement that decides it: interleaved passes of the nightly package 2026.09.23-5cf65b92 and our canon package on delphi-3bda with our harness.

Open item B

CI TTFT is +0.8 % above ours, while CI TPS is +0.9 % above ours. On 09-22, CI TTFT was −2.0 % relative to our no-kernel value. The cause is unknown. The measurement in item A also reports TTFT and would show whether the newer code shifts time from prefill to decode.

Open item C

Three tp4 rows rose on delphi-3bda only. The cause is not determined.

Hypotheses: (1) the AMX kernels also help these engines; (2) #4516 changed placement cost data for this CPU model only; (3) another merge in the same range. Measurement that decides (1): rerun the three rows on the 09-23 package with and without the kill switch and read EXE.AMX_BUSY per engine. The kill switch arm ran a few points slower than a no-kernel build in our 08-31 test [memory amx-vs-avx-sense]. A clean split therefore also needs a no-kernel build of 5cf65b92.
