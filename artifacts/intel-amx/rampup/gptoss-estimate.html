Adding gpt-oss to the AMX fast path: what it takes, what it buys

2026-08-19 · estimate on top of draft PR #3879 · repo facts verified against branch jhan-amx-p0 (file:line citations inline) · companion docs: PR ramp-up, geometry audit §4.1

Verdict in three sentences. Feasible and clean: gpt-oss's attention shape (8 query heads sharing each 64-wide K/V head) fills an AMX tile exactly as well as today's supported shape, and the two hard-looking features — attention sinks and sliding windows — already live outside the code the AMX path replaces, so they need zero changes (verified in code, §4). The work is one new kernel family plus a two-shape gate: est. about one engineering week plus one or two measurement nights. The payoff is modest: est. +4 to +7% decode at 1 user / ctx 8192 in the all-software mode (vs +19.7% measured on qwen), because gpt-oss reads 5.9× fewer KV bytes per token, leaving attention an est. 20% slice of its decode step (vs the measured 64% on qwen); in production FPGA-attention mode the gain is est. ≈0. Measure before committing: a one-slot decode profile pins the real attention share (§6).

1. What gpt-oss looks like inside tron today

Both gpt-oss models run in tron now (registry level "working", tagged production+test) and both have the same attention geometry: 64 query heads, 8 K/V heads, heads 64 numbers wide — so 8 query heads share each K/V head (ratio 8), where the current fast path requires 4 sharing a 128-wide head. The 20b has 24 layers (12 window + 12 full), the 120b has 36 (18 + 18, verified in its plugin). The kernel and gate work below applies to both models unchanged; the traffic and payoff numbers are computed for the 20b — the 120b would need its own payoff arithmetic on its own baseline.

Today, with the current PR in the tree, gpt-oss simply never enters the fast path — the shape gate routes every page to the unchanged AVX code. That is the measured −0.3% to −1.6% (within noise) in the PR ramp-up §5.1.

if constexpr (operation_kv_mul == 4 && operation_head_size == 128) // :1534, the page-loop twin

Those two sites are the only places that hard-code the shape. Everything else in the dispatch — the build flag, the CPUID/OS check, the kill switch, the full-page check, the visibility check, and (already!) the sliding-window check — is shape-independent.

3. Why the gpt-oss shape fits AMX just as well

The arithmetic carries through the whole kernel recipe: the reduction over the 64 head numbers is 2 chunks of 32 instead of 4, so each (K/V head, page) costs 8 tile multiplies instead of 16 — exactly matching the halved bytes. The score tile even gets wider use (8 query columns instead of 4). New kernels qk_st_64x8 and pv_64x8 follow the same recipe as the existing qk_st_128x4 / pv_128x4 (transposing store and all); the V storage is consumed as-is because its token-pair interleave does not depend on head width.

6. What it buys (est.) — and the measurement that would firm this up

Chain of reasoning, each step labeled:

  • On qwen at 1u/8K, attention is 64% of the decode step (measured) and AMX cut attention time by 26% (derived from the measured step times 9.46 → 7.91 ms and the measured 64% share, assuming the non-attention remainder is unchanged).
  • gpt-oss reads 5.9× fewer KV bytes per token (computed from geometry, bars above). Scaling qwen's measured attention time by that byte ratio puts gpt-oss attention at ≈1.0 ms of its 5.02 ms step — a 20% share (est.). This rests on TWO assumptions: equal effective memory bandwidth, and that attention stays bandwidth-bound the way qwen's decode-phase counters showed (LLC-miss-dominated). The multiply arithmetic shrinks only ≈3×, not 5.9× (12 vs 36 full layers; per-layer multiply work per attended token is equal: 32 heads × 128 = 64 heads × 64 = 4,096 query numbers) — so in the compute-bound worst case the share would be nearer 40% and the estimate nearer +12%.
  • Applying the same 26% attention cut to that slice (assumes the 64x8 kernels achieve the same relative cut): decode +5.5% (est.) at 1u/8K; if the true share is ±30% off, the range is +3.8% to +7.3%. At short contexts the share shrinks further — expect low single digits or nothing.
  • Production FPGA-attention mode: est. ≈0. There the CPU only runs the 12 window layers (they are software_only) plus queries at positions below 127, and the window work is the 3 MB orange sliver in the chart — those full in-window pages WOULD take the fast path, but scaled through the same model that is under 0.1% of a step. The practical case for gpt-oss support is the all-software operating mode.
  • Prefill: Insufficient data — the full-attention layers should benefit the way qwen prefill did (+29% to +105% measured there), but we have no gpt-oss attention-share profile for prefill; the same one-slot measurement below resolves it.
Before committing the week: spend one machine slot first. A decode-phase perf attach on a gpt-oss run with USE_HW_ATTN=0 (same method as the layout deep-dive in the status report §4) pins the real attention share. If it comes back ≈20% as estimated, the estimate stands at the +3.8%–7.3% above and the priority call is a product question; if it comes back near the compute-bound case (≈40%), the estimate rises to ≈+12%.

7. Where the same generalization leads (one paragraph, no commitment)

The tile identity "head width × sharing ratio = 512" has a third member in the registry: 256-wide heads with ratio 2 — gemma-2-2b/9b, gemma-3-4b, gemma-4-12b. The same kernel recipe (2 heads × 8 chunk-rows) would serve them; gemma's score softcap, like the sinks, lives in the untouched epilogue. And qwen-3-32b / qwen-3-30b-a3b / the 70b llamas (128-wide, ratio 8) need two tiles per query group — doable but a different, heavier recipe. Worth a separate estimate only if one of those models becomes a priority.

8. Glossary (plain words)

Attention sink
A learned per-head score that always participates in the softmax, as if there were one extra token every query can attend to. Keeps the distribution stable when a window hides old tokens.
Sliding window
The layer only looks at the most recent N tokens (N=128 here) instead of the whole history.
software_only
The plugin marks these layers as always computed on the CPU, even when FPGA attention is enabled.
Query group
The query heads that share one stored K/V head and are therefore multiplied against the same page together: 4 heads today, 8 for gpt-oss.
Chunk
32 numbers — the slice of a head that fits one 64-byte tile row as bf16.
Mirror
The opt-in pre-rearranged second copy of K (formulation from Bill's PR #2934; implementation and numbers ours). Not proposed for gpt-oss v1.

Estimate method: geometry bytes computed by script; qwen anchors are measured (replicated, 95% CIs in the status report); every derived number is labeled est. or derived and traced to its assumption. Code citations refer to branch jhan-amx-p0.
