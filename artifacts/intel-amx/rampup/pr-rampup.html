Ramp-up for reviewing PR #3879: AMX software attention

You are new to this project. This page gives you everything needed to review the draft PR; its companion, pr-walkthrough.html, then maps every changed file to the ideas here.

1. The problem being solved

tron serves language models by splitting each generated token's work between an FPGA (the big weight multiplies) and the CPU (attention: for every new token, compare its query against every stored token's key, then blend the stored values by those comparison weights). The CPU part reads the whole conversation history every step, so its share of the time grows with conversation length — at 8K context it IS most of the step.

2. Intel AMX

Advanced Matrix Extensions (AMX) is an x86 ISA extension (first shipped in Sapphire Rapids, inherited and extended by Granite Rapids) that adds two things to every P-core isa-extensions-progref:956-968:

  • A tile register file: 8 registers TMM0..TMM7, each up to 16 rows × 64 bytes (1 KB per tile, 8 KB total), described by a "palette" configuration sdm-vol-1:20752-20755. On the 6962P: 8 tiles × 1024 B, 16 rows × 64 B/row, TMUL max K=16, max N=64 B measured (CPUID leaves 1DH/1EH).
  • TMUL, a grid of FMA units that executes tile-times-tile matrix multiply-accumulate instructions: C[M][N] += A[M][K] × B[K][N], operating only on tile registers (no memory operands) isa-extensions-progref:7089-7091, 7065-7066.

Two facts from the above matter most for this PR: AMX reads bf16 (the format tron's K/V cache already uses) and accumulates in fp32 (the precision the existing code already uses), so the stored K/V cache needs no conversion or format change. Small temporary rearrangements do happen inside the fast path: the 4 query rows are packed once per token, and the softmax weights are rounded to bf16 for the PV multiply, exactly as today's AVX-512 code already rounds them. Full primer: doc 01.

3. What the PR actually changes

The one design fork you need to know: the QK multiply can read K two ways. Canonical-K (the default) reads K exactly as stored today — free, but the scores come out sideways and need a small transpose. The mirror (opt-in, TRON_AMX_K_MIRROR) keeps a second, pre-rearranged copy of K in a separate memory arena so no transpose is needed — faster at long context, at the cost of extra ordinary RAM (≈50% of the KV cache's size, allocated at cache setup only when mirror support is built AND the runtime AMX check passes) and more moving parts. Generating the mirror is cheap and measured: 70 ns per token-row on this machine (≈20 µs per prefill token across 36 layers × 8 heads, spread over the driver workers — and the system-level A/B shows prefill still nets +1–2% ahead of a build with no mirror writes at all; on decode it is ≈0.3–0.4% of a step). Both are in this PR; deep details with figures: doc 02 §2b (the data layouts) and §4b (the transpose).

4. The safety model — why this is low-risk to merge

4.1 The attention geometry we support — exactly, and which models have it

The fast path engages only when the model's attention has one exact shape. The whole gate is one line of compile-time arithmetic plus the runtime CPU check (h/tron/models/self_attention.hpp):

constexpr bool amx_shape_ok = geometry.kv.head_size == 128 && geometry.kv_mul() == 4;
const bool amx_on = amx_shape_ok && amx_attn::available();

In plain words: each attention head must be 128 numbers wide, and exactly 4 query heads must share each stored K/V head (kv_mul() is that sharing ratio; modern models store fewer K/V heads than query heads to shrink the KV cache). Why this exact shape: one query group of 4 heads × 128 numbers = 512 bf16 values = 1,024 bytes; the kernel packs those as 16 rows × 32 values — exactly one full AMX tile (16 rows × 64 bytes), no padding waste. The kernel names carry the shape: qk_st_128x4, pv_128x4, qk_mirror_128x4.

Is tensor-parallel (tp1/tp2/tp4) part of the geometry? No. The gate reads two compile-time model constants (head width, sharing ratio). The tp mode is a separate build parameter that decides how work is split across FPGA devices; it changes neither constant (and it divides query and K/V head counts by the same factor, so the ratio could not change anyway). A model passes or fails this gate identically at tp1, tp2, and tp4.

4.2 Does FPGA attention bypass AMX? No — the two compose

The AMX dispatch never looks at whether FPGA attention is on. It sits inside the software-attention page loop, and that loop runs in both modes: with FPGA attention on, it processes exactly the queries the query mask marks "software required" (self_attention.hpp:1344 selects the mode, :1526 picks sw_required vs visible per query). Whatever attention lands on the CPU flows through the same gates as §4: a full, fully visible 64-token page takes the AMX kernels; anything partial takes the unchanged AVX loop.

CPU attention work while FPGA attention is ondoes AMX fire on it?
queries early in the sequence — any query at position below 127 always runs in software (an FPGA constraint) partly — not every such query, and never all of its work. The query reads every stored token from position 0 up to itself, but AMX only takes complete 64-token pages. A query in roughly the first 64 positions has no complete page yet, so all of its work runs the AVX loop. A query at position ≈64–126 has exactly one complete page (tokens 0–63): AMX computes that page, and the leftover tokens after 63 sit in a partly filled page and go through the AVX loop.
layers the FPGA cannot serve: sliding-window layers always run in software (:1343), as do layers the plugin marks software_only (gpt-oss's window layers) yes, on pages fully inside the window; window-boundary pages fall to AVX
models/configs where hardware attention is ineligible at all (no hardware plan is built) every page becomes CPU work; whether AMX fires is then decided by the §4 gates alone — a matching-shape model behaves exactly as under USE_HW_ATTN=0, a non-matching one stays on AVX
token ranges the FPGA serves they never reach the CPU; there is nothing to accelerate

Practical size: for qwen-class models (no window layers), the CPU's share in FPGA-attention mode is just those early-position queries, so the AMX contribution there is small. The measured +15–28% decode gains are for the all-software operating mode (USE_HW_ATTN=0), where every page is CPU work. No extra code is needed for the mixed mode — it composes as-is, and the kill switch behaves identically in both.

Testing trap (we hit it during T1): the page rule above applies to any test, in any mode. A run whose total length — prompt plus generated tokens — stays under 64 never completes a page, so AMX never engages: both arms run the identical AVX code, an A/B shows nothing, and a numerics comparison "passes" without ever testing the AMX path. The repo's canned 21-token prompts do exactly this. Any meaningful test must push the total sequence past 64 tokens (the measured campaigns use ctx 2048 and 8192).

Also measured: prefill (prompt reading) up to +105% (mirror, 1 user / ctx 8192).

  • Power: package power is flat at 8 users / ctx 8192, yet energy per token drops by 14.5% (canonical) / 21.6% (mirror) — no contradiction: energy = power × time. The machine draws the same watts either way, but the AMX arms finish the same tokens in less time (+18–28% tokens per second), so each token costs fewer joules: joules per token = watts ÷ tokens per second.
  • Numerics: two separate comparisons over the same 956 steps. (a) AMX-vs-AVX — worst per-step TVD 0.054 (same TVD definition and per-step comparison the repo's golden tests use, whose outlier cap is 0.30). (b) Each arm vs HF fp32 references — AMX sits at the SAME distance as AVX — by this metric it adds no measurable error on top of the engine's pre-existing gap. And when both arms pick tokens greedily (always take the single highest-scoring token), they chose the SAME token at every compared step except two — and at both exceptions the model's top two candidates were nearly tied (score gaps of 0.031 and exactly 0.000, against a typical gap of 0.27). In plain words: across these 956 steps the rounding differences only ever tipped choices the model was near-indifferent about; no confident choice was overturned.

6. Glossary (plain words)

Page
64 consecutive stored tokens of one attention head's K and V — the unit of attention work.
KV cache
The stored keys and values of every token seen so far; bf16; lives in host DRAM.
dotter / scaled_v
Today's AVX-512 code for the QK and PV multiplies — what AMX replaces when eligible.
Canonical-K
Our name for "K stored the one standard way it is today", read as-is.
Mirror
A second copy of K, pre-rearranged for the tile instructions. The idea comes from Bill's PR #2934; the implementation and all numbers here are ours.
Arena
The separate ordinary-RAM allocation holding all mirror copies — exists only when AMX is available at runtime.
Kill switch
TRON_AMX_DISABLE=1: same binary, AMX off, measured at clean-binary speed.
TVD
Total variation distance: how different two probability distributions are, 0 = identical, 1 = disjoint. The repo's existing accuracy tests use it.
