Ramp-up for reviewing PR #3879: AMX software attention

You are new to this project. This page gives you everything needed to review the draft PR; its companion, pr-walkthrough.html, then maps every changed file to the ideas here.

1. The problem being solved

tron serves language models by splitting each generated token's work between an FPGA (the big weight multiplies) and the CPU (attention: for every new token, compare its query against every stored token's key, then blend the stored values by those comparison weights). The CPU part reads the whole conversation history every step, so its share of the time grows with conversation length — at 8K context it IS most of the step.

2. Intel AMX

Advanced Matrix Extensions (AMX) is an x86 ISA extension (first shipped in Sapphire Rapids, inherited and extended by Granite Rapids) that adds two things to every P-core isa-extensions-progref:956-968:

  • A tile register file: 8 registers TMM0..TMM7, each up to 16 rows × 64 bytes (1 KB per tile, 8 KB total), described by a "palette" configuration sdm-vol-1:20752-20755. On the 6962P: 8 tiles × 1024 B, 16 rows × 64 B/row, TMUL max K=16, max N=64 B measured (CPUID leaves 1DH/1EH).
  • TMUL, a multiply-add grid (a dedicated array of fused multiply-add circuits, distinct from the AVX-512 vector FMA units) that executes tile-times-tile matrix multiply-accumulate instructions: C[M][N] += A[M][K] × B[K][N], operating only on tile registers (no memory operands) isa-extensions-progref:7089-7091, 7065-7066.

Two facts from the above matter most for this PR: AMX reads bf16 (the format tron's K/V cache already uses) and accumulates in fp32 (the precision the existing code already uses), so the stored K/V cache needs no conversion or format change. Small temporary rearrangements do happen inside the fast path: the 4 query rows are packed once per token, and the softmax weights are rounded to bf16 for the PV multiply, exactly as today's AVX-512 code already rounds them. Full primer: doc 01.

3. What the PR actually changes

The one design fork you need to know: the QK multiply can read K two ways. Canonical-K (the default) reads K exactly as stored today — free, but the scores come out sideways and need a small transpose. The mirror (opt-in, TRON_AMX_K_MIRROR) keeps a second, pre-rearranged copy of K in a separate memory arena so no transpose is needed — faster at long context, at the cost of extra ordinary RAM (≈50% of the KV cache's size, allocated at cache setup only when mirror support is built AND the runtime AMX check passes) and more moving parts. Generating the mirror is cheap and measured: 70 ns per token-row on this machine (≈20 µs per prefill token across 36 layers × 8 heads, spread over the driver workers — and the system-level A/B shows prefill still nets +1–2% ahead of a build with no mirror writes at all; on decode it is ≈0.3–0.4% of a step). Both are in this PR; deep details with figures: doc 02 §2b (the data layouts) and §4b (the transpose).

4. The safety model — why this is low-risk to merge

4.1 The attention geometry we support — exactly, and which models have it

The fast path engages only when the model's attention has one exact shape. The whole gate is one line of compile-time arithmetic plus the runtime CPU check (h/tron/models/self_attention.hpp):

constexpr bool amx_shape_ok = geometry.kv.head_size == 128 && geometry.kv_mul() == 4;
const bool amx_on = amx_shape_ok && amx_attn::available();

In plain words: each attention head must be 128 numbers wide, and exactly 4 query heads must share each stored K/V head (kv_mul() is that sharing ratio; modern models store fewer K/V heads than query heads to shrink the KV cache). Why this exact shape: one query group of 4 heads × 128 numbers = 512 bf16 values = 1,024 bytes; the kernel packs those as 16 rows × 32 values — exactly one full AMX tile (16 rows × 64 bytes), no padding waste. The kernel names carry the shape: qk_canonical_128x4, weights_times_v_128x4, qk_mirror_128x4.

Is tensor-parallel (tp1/tp2/tp4) part of the geometry? No. The gate reads two compile-time model constants (head width, sharing ratio). The tp mode is a separate build parameter that decides how work is split across FPGA devices; it changes neither constant (and it divides query and K/V head counts by the same factor, so the ratio could not change anyway). A model passes or fails this gate identically at tp1, tp2, and tp4.

4.1.1 Why the kv_mul 3 / 5 / 8 models are not served — and what would break if the gate were simply forced open

From the nightly-CI list, llama-3.2-3b (3 query heads per K/V head), qwen-2.5-32b (5) and llama-3.3-70b (8) all have 128-wide heads but fail the kv_mul() == 4 half of the gate. As shipped, nothing fails on them: the gate is compile-time (if constexpr), so for these models the AMX branch is not even compiled into their plugin instantiation — they run the unchanged AVX path (that is the measured "ineligible shape" class: gpt-oss showed −0.3..−1.6%, run-to-run noise).

The interesting question is what the gate is protecting against. The *_128x4 kernels hard-code the number 4 in three load-bearing places: the Q pack reads exactly 4 consecutive query heads starting at kv_head × kv_mul × 128; the tile kernels compute exactly those 4 rows; and the epilogue writes exactly scratchpad entries sp[kv_head × 4 + offset], then returns early so the AVX loop never revisits the page. Run that machinery on a group that is not 4 heads wide and, per geometry:

  • kv_mul 3 (llama-3.2-3b): the 4-head window reads one head PAST the group — the next K/V head's first query is scored against the wrong K/V data (silently wrong attention), and for the last K/V head the pack reads past the end of the query tensor while the ×4 epilogue stride writes scratchpad slots 28–31 of a 24-entry array: out-of-bounds read AND write, i.e. memory corruption, not just wrong numbers.
  • kv_mul 5 (qwen-2.5-32b): the window covers 4 of the 5 heads; the 5th head is never computed — and because the AMX branch returns early, the AVX loop never fills it either, so 1 in 5 heads remains uncomputed and its scratchpad entry is not updated. From the second group on, the ×4 stride (correct would be ×5) lands every update on the WRONG head's scratchpad entry: in-bounds, silent, wrong.
  • kv_mul 8 (llama-3.3-70b): half of every group is skipped, and the ×4-vs-×8 stride mis-addresses every group after the first. (This shape could use TWO full query tiles rather than one, but it requires a width-8 kernel variant and a generalized stride — it cannot be enabled by loosening the shape check.)

That is the design point: the gate makes the unsupported case impossible by construction rather than checked at runtime, and the failure modes above are why widening support means new per-width kernels plus a kv_mul-derived stride (the planned actual-width bucketing), never just deleting the check.

4.2 Does FPGA attention bypass AMX? No — the two compose

The AMX dispatch never looks at whether FPGA attention is on. It sits inside the software-attention page loop, and that loop runs in both modes: with FPGA attention on, it processes exactly the queries the query mask marks "software required" (self_attention.hpp:1344 selects the mode, :1526 picks sw_required vs visible per query). Whatever attention lands on the CPU flows through the same gates as §4: a full, fully visible 64-token page takes the AMX kernels; anything partial takes the unchanged AVX loop.

CPU attention work while FPGA attention is ondoes AMX fire on it?
queries early in the sequence — any query at position below 127 always runs in software (an FPGA constraint) partly — not every such query, and never all of its work. The query reads every stored token from position 0 up to itself, but AMX only takes complete 64-token pages. A query in roughly the first 64 positions has no complete page yet, so all of its work runs the AVX loop. A query at position ≈64–126 has exactly one complete page (tokens 0–63): AMX computes that page, and the leftover tokens after 63 sit in a partly filled page and go through the AVX loop.
layers the FPGA cannot serve: sliding-window layers always run in software (:1343), as do layers the plugin marks software_only (gpt-oss's window layers) yes, on pages fully inside the window; window-boundary pages fall to AVX
models/configs where hardware attention is ineligible at all (no hardware plan is built) every page becomes CPU work; whether AMX fires is then decided by the §4 gates alone — a matching-shape model behaves exactly as under USE_HW_ATTN=0, a non-matching one stays on AVX
token ranges the FPGA serves they never reach the CPU; there is nothing to accelerate

Practical size: for qwen-class models (no window layers), the CPU's share in FPGA-attention mode is just those early-position queries, so the AMX contribution there is small. The measured +15–28% decode gains are for the all-software operating mode (USE_HW_ATTN=0), where every page is CPU work. No extra code is needed for the mixed mode — it composes as-is, and the kill switch behaves identically in both.

Testing trap (we hit it during T1): the page rule above applies to any test, in any mode. A run whose total length — prompt plus generated tokens — stays under 64 never completes a page, so AMX never engages: both arms run the identical AVX code, an A/B shows nothing, and a numerics comparison "passes" without ever testing the AMX path. The repo's canned 21-token prompts do exactly this. Any meaningful test must push the total sequence past 64 tokens (the measured campaigns use ctx 2048 and 8192).

4.3 Why keep two copies of K instead of just storing K transposed? (Bill's question)

The mirror stores a second, rearranged copy of K next to the original. A fair question: why not store K in the rearranged form once and drop the original? tron already does exactly that for V — V is stored in the tile-friendly interleaved form natively, every consumer reads it that way, and V needs no mirror. The difference is that V has one layout every reader wants, while the original K layout is a shared interface with three consumers that need the row form:

who reads original Kwhy it needs rowsif K were stored transposed
FPGA attention. The save path stores each roped K row into the page "so HW sees the latest K values" (comment at the store, model.hpp:2779); hardware offload then ships completed 4-token groups of those page bytes to the card as they fill (gof.hpp:33, full.hpp:2382). The KV pages live in DMA-visible hugepage memory; the mirror arena is deliberately ordinary RAM the card never sees. the card's layout is a hardware contract; the pages are shipped byte-for-byte with no conversion step anywhere the FPGA reads a layout it does not understand. The fix is either an FPGA-side change or a convert-and-stage copy at the DMA boundary — the transpose work does not disappear, it moves to the transfer path and brings a staging buffer with it
The AVX-512 fallback. dotter<bf16,128> (dotter.hpp:176) consumes one K row as one contiguous 128-value vector — the QK reduction runs along the head dimension, which is contiguous within a row. this path is not legacy; it serves everything AMX declines: group widths below the crossover, partial and young pages (every page until its 64 tokens complete, including the partial tails of early-position software queries in FPGA mode — §4.2), non-matching geometries, hosts without AMX, and the kill switch one token's 128 values are scattered across the transposed panels 32 bytes apart (the layout formula: kv_cache.hpp, mirror scatter comment), so the single-token dot product loses its contiguous-row loads and needs strided or gather-style loads plus rearrangement instead, unless a new family of narrow kernels is written for the transposed form
The rollback story. TRON_AMX_DISABLE currently returns to the unchanged code path at clean-binary speed (measured −1.3% to +3.3% of a build with no AMX code at all). a reviewer can reason: flag off = old engine there is no unchanged path left to return to — disabling AMX would strand the AVX code on a layout it was never written for

What replacing would actually save, honestly: (a) the arena's memory — about half the KV cache's size in ordinary RAM (≤32 GB on this machine's 64 GB KV configuration, out of 1.58 TB installed — small next to both budgets, though its traffic and placement are still real; the scarce DMA page budget is untouched: in the measured capacity probe, both builds admitted 32 and 48 users at ctx 8192 with no failures); (b) the mirror's moving parts — the allocation/lifetime plumbing and null-check fallbacks, the defrag rebuild, the two-copy consistency invariant across writes and page moves, and the byte-equivalence tests that guard it all; (c) almost nothing on the write side — the 70 ns/token-row scatter would remain as the primary K store, replacing only a cheap contiguous row write.

So the two copies are not an accident: the original K plane is the interface the FPGA and every narrow/partial CPU case consume, and the transposed plane is a private view for one kernel. Replacing rather than mirroring is a cross-stack layout migration (FPGA contract, new narrow-width CPU kernels, loss of the rollback) purchased with savings the arena design already made small relative to the machine's memory and page budgets. The V cache shows when replacement is right: when every consumer wants the rearranged form. If a future card consumed transposed K natively — or an FPGA-free build existed — this question should be reopened.

And when both arms pick tokens greedily (always take the single highest-scoring token), they chose the SAME token at every compared step except two — and at both exceptions the model's top two candidates were nearly tied (score gaps of 0.031 and exactly 0.000, against a typical gap of 0.27). In plain words: across these 956 steps the rounding differences only ever tipped choices the model was near-indifferent about; no confident choice was overturned.

6. Glossary (plain words)

Page
64 consecutive stored tokens of one attention head's K and V — the unit of attention work.
KV cache
The stored keys and values of every token seen so far; bf16; lives in host DRAM.
dotter / scaled_v
Today's AVX-512 code for the QK and PV multiplies — what AMX replaces when eligible.
Canonical-K
Our name for "K stored the one standard way it is today", read as-is.
Mirror
A second copy of K, pre-rearranged for the tile instructions. The idea comes from Bill's PR #2934; the implementation and all numbers here are ours.
Arena
The separate ordinary-RAM allocation holding all mirror copies — exists only when AMX is available at runtime.
Kill switch
TRON_AMX_DISABLE=1: same binary, AMX off, measured at clean-binary speed.
TVD
Total variation distance: how different two probability distributions are, 0 = identical, 1 = disjoint. The repo's existing accuracy tests use it.
