Intel AMX Ramp-Up

What AMX is, how it is leveraged, what it requires from the system, and its trade-offs — for the tron software-attention project on Intel Xeon 6 6962P (Granite Rapids). Every claim carries a citation to the local Intel reference cache (/scratch/jhan/Intel_vs_AMD/refs, format doc:line) or is a measurement taken on delphi-3bda (marked measured): the 2026-08-16 probe set unless a later-dated result file is cited in place.

TL;DR
  • AMX is a per-core matrix-multiply unit. One instruction computes C[16×16] += A[16×32] × B[32×16] on bf16 data (fp32 accumulation) held in eight 1 KB tile registers.
  • Peak: 512 bf16 MAC/cycle/core — 8× AVX-512 BF16 (1024 MAC/cycle for int8). Derived from tile shapes and instruction throughput, see §3.
  • It pays off only when enough output rows and columns are useful. Matrix–vector work with M=1 wastes most row capacity; tron's transposed QK formulation fills M but can still underfill the output-column dimension at Nq=4.
  • The B operand must be stored in a pair-interleaved ("VNNI") layout — layout is the main integration cost.
  • The OS must grant permission per process (arch_prctl); each thread that touches tiles grows its context-switch state by 8 KB.
  • delphi-3bda has everything needed: AMX-TILE/BF16/INT8 and AMX-FP16, kernel 6.8. measured

0. Terminology for the numbers

The performance claims in this document (and in docs 02–03) are stated in a small set of units. Definitions, in the order you will meet them:

TermMeaning
MAC (multiply-accumulate)One operation of the form c = c + a × b — a multiply and an add, fused. It is the basic work unit of matrix math: a matrix multiply C[M×N] += A[M×K] · B[K×N] performs exactly M·N·K MACs — each of the M×N output elements is a sum of K products (M, N, K are defined two rows down). One MAC counts as 2 floating-point operations (flops).
MAC/cycle/coreHow many MACs one CPU core completes per clock cycle at peak. Reading the TL;DR line with this: one max-shape TDPBF16PS instruction performs 16×16×32 = 8192 MACs — that is M=16 output rows × N=16 output columns × K=32 bf16 values summed per output element (a tile row is 64 bytes = 32 bf16) — and a new one can retire every 16 cycles, so 8192 / 16 = 512 MAC/cycle/core. Multiply by the clock to get a rate: at the ~1.89 GHz AMX clock measured in the PoC microbenchmark, 512 × 1.89·10⁹ ≈ 968 GMAC/s ≈ 1936 GFLOPS for one core.
FMA (fused multiply-add)The hardware circuit — and instruction family — that executes one MAC as a single operation d = a × b + c with one rounding step (the "fused" part). MAC is the operation you count; FMA is the unit that runs it, one MAC per lane per cycle. A P-core has two kinds of FMA hardware: (1) two 512-bit vector FMA units — in Intel's documented port model behind issue ports 0 and 5, the second one present "on some parts", with no 6962P-specific port map in the local refs (§1.1) — which run AVX-512 instructions like vfmadd* and vdpbf16ps; (2) the TMUL, which Intel defines as "conceptually a grid of fused multiply-add units able to read and write tiles" isa-extensions-progref:7086-7088 — a separate, dedicated array, not the vector units reused. Same technology, different silicon. To keep the two kinds of hardware apart, this document reserves plain FMA for the AVX-512 vector units and calls TMUL's internal array the multiply-add grid. What they do share: the port-5 issue slot (in that documented model), the load ports, and the core's power/frequency budget — while TDP* instructions execute, the CPU usually closes port 5's vector FMA "to conserve power" opt-manual:32519-32523, so concurrent AVX-512 FMA throughput halves (port 0 only). There is one TMUL per physical core, shared by both hyper-threads; each hyper-thread has only its own private tile-register state.
fused / kernel fusionRunning several pipeline steps as one combined pass, so intermediate results stay in registers or cache instead of being written to memory and read back between steps. A "fused-page benchmark" times all per-page steps together (pack, matrix multiply, transpose, softmax, multiply-by-V, accumulate) rather than the matrix multiply alone — which matters because the surrounding steps are often where the time goes. "Fuse the transpose into the softmax" = do the transpose as part of the softmax step instead of as its own pass. Note this is a different "fused" than the one in FMA above (there it means multiply+add with a single rounding).
cycleOne tick of the core clock. A 2 GHz core has 2·10⁹ cycles per second. Costs of individual instructions are quoted in cycles because the clock frequency varies (see "frequency license", §7.2).
flop / GFLOPSOne floating-point operation / 10⁹ of them per second. 1 MAC = 2 flops (the multiply and the add).
throughput vs latency (of an instruction)Throughput here means reciprocal throughput: the number of cycles between starting consecutive independent instructions of that kind — "TDP* throughput 16" means a new tile multiply can begin every 16 cycles. Latency is how long until one instruction's own result is ready (52 cycles for TDP*) — the gap between the two is why a kernel keeps several independent accumulator tiles in flight.
M, N, KThe three dimensions of a matrix multiply C[M×N] += A[M×K] · B[K×N]: M = rows of A = rows of the output C; N = columns of B = columns of the output C; K = the shared inner dimension (columns of A = rows of B) — the contraction (reduction) dimension that gets summed away. Each output element C[i][j] = Σk A[i][k]·B[k][j] costs K MACs, and there are M×N output elements — hence M·N·K MACs total. In the attention kernels of doc 02, the "query width" lands on N for the Q·K score computation (transposed formulation) and on M for the P·V computation.
GEMM / GEMVGeneral matrix–matrix multiply / matrix–vector multiply. GEMV is the M=1 degenerate case — the shape where AMX wastes most of its grid (§7.1).
arithmetic intensityFlops performed per byte of memory traffic. Low intensity means the kernel is limited by memory bandwidth no matter how fast the math units are; high intensity means the math units are the limit. Decode attention is ~4 flops/byte — low.
tok/s, TPS, TTFTTokens per second (the end-to-end serving metric; "prompt/parse" = prefill phase, "generation" = decode phase); TTFT = time to first token.

Hardware-specific terms (tile, TMUL, palette, VNNI layout, XFD…) are defined where they first appear and collected in the glossary (§9).

1. What AMX is

Advanced Matrix Extensions (AMX) is an x86 ISA extension (first shipped in Sapphire Rapids, inherited and extended by Granite Rapids) that adds two things to every P-core isa-extensions-progref:956-968:

  • A tile register file: 8 registers TMM0..TMM7, each up to 16 rows × 64 bytes (1 KB per tile, 8 KB total), described by a "palette" configuration sdm-vol-1:20752-20755. On the 6962P: 8 tiles × 1024 B, 16 rows × 64 B/row, TMUL max K=16, max N=64 B measured (CPUID leaves 1DH/1EH).
  • TMUL, a multiply-add grid (a dedicated array of fused multiply-add circuits, distinct from the AVX-512 vector FMA units) that executes tile-times-tile matrix multiply-accumulate instructions: C[M][N] += A[M][K] × B[K][N], operating only on tile registers (no memory operands) isa-extensions-progref:7089-7091, 7065-7066.

Configuration lifecycle

  • LDTILECFG [mem64] — loads a 64-byte configuration (per-tile rows/colbytes). Zeroes all tile data. Expensive: 204-cycle latency — issue once per kernel, not per loop iteration isa-extensions-progref:7067-7074; opt-manual:31310-31329.
  • TDP* — the multiply-accumulates (§2). Illegal (#UD) unless tiles are configured.
  • TILERELEASE — returns tiles to the INIT state. Strongly recommended when leaving an AMX region, and required by this plan's lifecycle policy: non-initialized tile state blocks deep core sleep states and carries power cost opt-manual:33771-33772; sdm-vol-1:20966-20971.

1.1 AMX and AVX-512 on the same core: what is shared, what is exclusive, how they collide

Yes — one physical core executes both at the same time. The out-of-order core keeps dispatching AVX-512 (and scalar) work while the multi-cycle TDP* instructions grind in the TMUL unit; Intel's own optimization guidance is to software-pipeline AVX-512 code between AMX tile operations, precisely because TDP* "utilize resources very lightly (1/2 of the available ALU ports, 1/TILE_M of the time)" opt-manual:32369-32381. The figure's one-core view above focuses on AMX; this one puts both stacks side by side:

port 5shared: AVX-512 FMA #2 and the TMUL feed (documented model)while TDP* execute the port-5 FMA is usually closed; while closed, AVX-512 FMA peak drops 2/cycle → 1/cycle opt-manual:32519-32523; the reopen costs a few stall cycles and never happens inside AVX blocks under 100 instructions; 100–300-instruction blocks lose up to 20% to the churn (TILEZERO keeps the port closed); longer blocks run faster reopened opt-manual:32516-32531

The direct execution-unit cost runs one way: while the port-5 FMA is closed during TDP* execution, AVX-512 loses one of its two FMA ports, and the AMX frequency license lowers the whole core's clock. The local Intel references document no corresponding dedicated mechanism in the other direction; AVX-512's expected costs to AMX run through the shared front end, load/store ports, caches and power budget, and are workload-dependent rather than negligible. For tron this interaction is not hypothetical — the attention kernels interleave AVX-512 packing and epilogue code between TDP* operations, so every measured system gain in doc 02 and the status report already includes these costs.

Numeric behavior (matters for correctness tests)

  • All AMX float instructions: round-to-nearest-even, FP exceptions masked, MXCSR ignored isa-extensions-progref:7240-7252.

3. Throughput: why it is fast

One max-shape TDPBF16PS performs 16×16×32 (M×N×K, §0) = 8 192 MACs and retires at a throughput of one per 16 cycles → 512 bf16 MAC/cycle/core. Int8 doubles K → 1 024 MAC/cycle. AVX-512 BF16 peaks at 2 × vdpbf16ps/cycle × 32 MACs = 64 MAC/cycle. (Derived from tile shapes opt-manual:31339-31343 and instruction timing opt-manual:31320-31329; the timing table is Sapphire-Rapids-era — Granite Rapids values are unpublished in our refs and should be confirmed by microbenchmark. est.)

4. How a matrix multiply maps onto tiles

The operand roles: A (M×K) stays in its natural row-major layout; B (K×N) must be pair-interleaved (§5); C (M×N) accumulates in fp32/int32. Max logical shapes per tile: A = 16 rows × 32 bf16, B = 32 rows × 16 bf16 (stored as 16 rows × 64 B), C = 16×16 fp32 opt-manual:31338-31351.

Minimal intrinsics skeleton

One naming note before the code: Intel's field for a tile's row width is colsb = "columns in bytes" (also called "tile column bytes"). The struct below is our own declaration of the 64-byte LDTILECFG memory operand, so the field is spelled out as column_bytes. The config counts bytes, not elements — the tile file is type-agnostic raw storage, and the element type is decided by the instruction that reads the tile (TDPBF16PS treats A/B rows as bf16 and C rows as fp32). That is why the same 64-byte row width means 16 fp32 for C (64 B ÷ 4 B) but 32 bf16 for A and B (64 B ÷ 2 B).

// compile with: -mamx-tile -mamx-bf16   (<immintrin.h>)

// The 64-byte memory operand of LDTILECFG (our own struct declaration;
// Intel's name for column_bytes is "colsb" = columns in bytes).
struct tile_config {
  uint8_t  palette, start_row;
  uint8_t  reserved[14];
  uint16_t column_bytes[16];   // bytes per row. The FORMAT reserves 16 slots,
                               //   but palette 1 implements only 8 tiles
                               //   (tmm0..tmm7); slots 8..15 must stay zero,
                               //   or LDTILECFG raises #GP
  uint8_t  rows[16];           // rows per tile (same 16-slot format rule)
};                             // total: exactly 64 bytes

tile_config cfg = {};
cfg.palette = 1;
// Widths are in BYTES; the element type comes from the consuming instruction:
cfg.rows[0] = 16; cfg.column_bytes[0] = 64;  // tmm0: C accumulator
                                             //   64 B / 4 B per fp32 = 16 fp32 per row
cfg.rows[1] = 16; cfg.column_bytes[1] = 64;  // tmm1: A operand
                                             //   64 B / 2 B per bf16 = 32 bf16 per row
cfg.rows[2] = 16; cfg.column_bytes[2] = 64;  // tmm2: B operand, logically 32x16 bf16,
                                             //   stored pair-packed as 16 rows x 64 B
_tile_loadconfig(&cfg);                      // 204 cycles - once per kernel

_tile_zero(0);
for (int k = 0; k < K; k += 32) {
  _tile_loadd(1, A + k, lda_bytes);          // A: flat, strided
  _tile_loadd(2, B_packed + k*8, ldb_bytes); // B: pre-packed
  _tile_dpbf16ps(0, 1, 2);                   // C += A x B
}
_tile_stored(0, C, ldc_bytes);               // fp32 out
_tile_release();                             // on leaving AMX code

5. The VNNI B-operand layout

TMUL consumes the B operand dword-by-dword: each 4-byte element of a B-tile row holds a pair of consecutive-K values (2 × bf16, or 4 × int8). A flat K×N matrix must be re-laid out as B_mem[K/2][N][2] (bf16) before tiles can load it opt-manual:31403-31408; isa-extensions-progref:7539-7545.

5.1 Who does the rearranging? You do, in memory — nothing in AMX will do it for you

A common question (added 2026-08-20): do we pre-create the rearranged copy ourselves, does an AMX load instruction rearrange during the load, or does the multiply rearrange automatically? The answer is the first one, and only the first one:

  • There is no rearranging load. The AMX instruction set is small, and for the base set in the ISA-reference revision cited here (-052) plus the extensions the 6962P advertises, this list is complete: TILELOADD/TILELOADDT1, TILESTORED, TILEZERO, TILERELEASE, the config pair, and the TDP* multiplies isa-extensions-progref:421, 7022. The loads copy memory into the tile byte-for-byte, one row per stride step — a strided memcpy, no shuffle, no transpose isa-extensions-progref:7197-7201.
  • The multiply does not rearrange either. TDPBF16PS reads the B tile's byte pairs positionally, exactly as loaded isa-extensions-progref:7539-7545. Feed it a flat (non-interleaved) B and nothing faults — it just computes the wrong product silently.
  • So the bytes must already sit in memory in the §5 layout. There are three ways to get there, and tron's attention design uses all three:
    strategycost profilewhere tron uses it
    store the data pre-interleaved from the startfree at multiply time the V cache — already written token-pair-interleaved (§5 figure)
    maintain a pre-rearranged second copyextra RAM + a write-through at save time (measured 70 ns per token-row)the opt-in K mirror (doc 02 §4b)
    re-formulate the math so the flat matrix becomes the A operand (consumed as stored)the small result comes out sideways; fixed by a transposing store of the tiny C outputcanonical-K: Sᵀ = K·Qᵀ; only the small Q gets packed, on the fly (doc 02 §4)
    The general fallback — repack with AVX-512 shuffles right before each multiply (Intel ships vpermt2w kernels for this opt-manual:33150-33153) — costs time proportional to the data you feed, which is why tron applies it only to the tiny per-token Q and never to the big K/V pages.

Terminology note: people casually say "the B operand is transposed". Strictly it is not a plain transpose — it is pair-interleaving along the reduction dimension (two rows zipped element-wise into one, §5 figure; quadruples for int8). Newer revisions of the ISA reference than the -052 used here define an AMX-TRANSPOSE extension for rearranging tile data on future CPUs; the 6962P does not advertise it — our CPUID probe found amx-tile/bf16/int8/fp16 only (§6.1) — so on this machine, memory-side layout is the only option.

6.2 Per-thread state cost

  • AMX state = XSAVE components 17 (TILECFG, 64 B) + 18 (TILEDATA, 8192 B) sdm-vol-1:15871-15873. When non-INIT tile data must be saved or restored, the XTILEDATA component occupies the full 8 KB — configured tile sizes do not shrink it sdm-vol-1:16672-16675. TILERELEASE permits the XSAVE init-state optimization; exact save/restore work remains OS and context-switch dependent.
  • The init-state optimization (XSAVEC/XSAVES) skips the 8 KB only when tiles are in the INIT state — one more reason to TILERELEASE when leaving the kernel sdm-vol-1:16934-16961, 16752.
  • Signal stacks: the user-visible XSAVE frame grows past 8 KB; audit any sigaltstack against the kernel-provided AT_MINSIGSTKSZ (topic absent from Intel refs; Linux-side requirement).
  • Confine AMX to the pinned worker threads that need it — only they pay the 8 KB switch cost.

6.3 Scheduling and BIOS

  • One AMX thread per physical core. Intel: running two AMX threads on HT siblings of one core loses performance; leave the sibling idle or parked in a TPAUSE C0.2 wait opt-manual:33199-33213. tron already pins one worker per CPU from an explicit CPU list (app_set_cpu_list, peer_of() HT helpers exist in h/system/system.hpp:90-131), so this is an operational configuration choice, not new code.
  • No BIOS switch is needed for AMX itself (flags visible on delphi-3bda today). One BIOS-adjacent check: the L2 adaptive-prefetcher auto-tuning ("AMP") introduced with Emerald Rapids cost up to ~7% on AMX DL workloads and Intel recommends disabling it for DL opt-manual:32739-32750. Verify the GNR BIOS default on delphi before/after measurement.
  • NUMA: 2 sockets, SNC currently off (1 NUMA node/socket) measured. Keep AMX worker threads and the data they stream (KV cache in 1 GB hugepages) on the same socket; SNC3 is a later experiment bios-numa-sql-guide:123-148.

Teardown. TILERELEASE itself is 13 cycles (spec) / ~15 (measured). The reasons to pay it are state-management, not speed: it puts tiles in INIT so XSAVEC/XSAVES skip the 8 KB component on context switch (§6.2), and on Sapphire Rapids a still-valid tile state at MWAIT blocks core C6 (the core is demoted to C1; the idle process is unaffected because its tile state is INIT) opt-manual:33427-33440 — SPR-specific statement; the local references do not document the GNR equivalent.

Crossing between AMX and non-AMX instructions. Three separate seams, with different verdicts on this machine:

  • Data seam, tile store → vector load. The manual: TILESTORED can forward to non-TileLoad loads only at exactly cache-line (64 B) size, forwarding "is generally not advised because this mechanism has outliers", and the safe pattern keeps "enough distance ... in the order of 10s of cycles" opt-manual:32781-32784. (The hard restriction is the opposite direction: TileLoad cannot read store buffers at all and must wait for the store to reach the cache — "a significant slowdown" opt-manual:32752-32758.) Measured here: a dependent 64 B vector load of the just-tile-stored line cost no extra cycles vs loading an unrelated hot line (16.0–16.2 both) measured. In the measured width-4 L2 case, our canonical kernel's whole path (score tile stores, then vector loads for the transpose) was 1250 ns/page vs 686 ns/page for the mirror kernel that avoids it, a ~560 ns gap (exec/results/slot1/fused-sweep-v2.txt, amx44 vs amxqk, one L2-resident page); a pipelined-epilogue variant narrowed it to 982 ns in an unsaved 8-page-ring run (exec/QUEUE.md only). That gap combines transpose work and score traffic; its components were not isolated, and the direct 64-byte probe above found no raw store-forwarding penalty.
  • Issue seam, port-5 closure. Section 1.1 describes Intel's documented model (20.11.3): while TDP* execute, the port-5 FMA is closed, and an AVX-512 block under 100 instructions runs before it reopens. Measured probe here: an 80-FMA register-chain block (10 independent chains) right after one TDP cost +0.9±0.1 cycles vs the same block with no AMX in flight (32.3 → 33.1–33.3 cycles) measured — the closure penalty the SPR-era model predicts did not reproduce on the 6962P in this one experiment (one block size; not a general disproof). The nominal 80-FMA instruction count divided by measured cycles gives 2.48 FMA/cycle, above the documented two-port model; treat that as an anomalous probe result, not evidence of a particular 6962P port map — no such map exists in the local references (§1.1).
  • Frequency seam (the one that is real here). Same probe, wall-clock: cycles rose only 0.9±0.1 per iteration (32.24–32.31 → 33.11–33.26), while wall time rose 11.96–11.98 → 17.16–17.17 ns as the observed core clock fell from ~2.70 to ~1.93 GHz — the wall-time increase was dominated by frequency, in the serving-active environment of this run measured. This is the AMX frequency license: "Intel AMX adds yet another license level whose max frequency is usually lower than that of the Intel AVX-512 license", with an exemption when TMUL utilization stays under 15% opt-manual:31286-31293. Quiet-slot numbers for our actual kernels are in §7.3: 3.59 vs 3.89 GHz on the busy core (~8%), busy clock −4% at 8-user service scale with package power flat.
Take-away for the overhead question: entering AMX costs ~0.9 µs once per process, ~4–9 µs once per thread, and ~229 cycles per work region. Leaving costs ~15 measured cycles; until TILERELEASE, live tile state may require the 8 KB XSAVE component on a context switch. Between AMX instructions there is no waiting beyond pipelined latencies (measured 16.2–16.4 cycles/op TDP back-to-back). In the two tested seams — one dependent 64-byte store→vector load and one 80-FMA block after a TDP — the probes found no material extra instruction stall; these limited tests do not disprove Intel's forwarding-outlier or port-closure guidance. For the actual project kernels the measured license-clock cost was ~8% in the quiet-slot run (exec/results/slot1/p0c-freq-power.txt) and ~4% at 8-user service scale (exec/results/t4/t4-power.txt); the serving-active seam probe observed ~2.70→1.93 GHz. The system-level A/B nets +15–28% decode (exec/results/t4/t4-reps.txt) and 15–22% less energy per token (exec/results/t4/t4-power.txt) with these costs included.

7. Trade-offs and pitfalls

7.1 The M-utilization problem (the most important trade-off)

The planning model assumes a TDP instruction has the same reciprocal-throughput slot when only part of its configured output shape is useful. Matrix–vector work fills one output row, and narrow transposed-QK work can similarly underfill output columns. Granite Rapids occupancy-dependent timing is unverified and is measured in P0.

7.3 Power draw and cross-core frequency effects

A common worry: "AMX is power-hungry, and running it lowers other cores' frequencies." What Intel actually documents is more specific, in three parts.

(1) The frequency license is per-core, and its class ladder puts AMX at the bottom. Each core independently runs at a max frequency set by the "license" class of the instructions it is executing opt-manual:3868-3870 (Figure 2-7):

License classTriggered byMax frequency
Level 0scalar, SSE, light AVX2 (no FP/INT MUL/FMA)highest (P0n)
Level 1heavy AVX2, light AVX-512medium (P0n-AVX2)
Level 2heavy AVX-512 (FP/INT MUL/FMA)lower (P0n-AVX-512)
AMXTDP* tile compute"usually lower than that of the Intel AVX-512 license" opt-manual:31288-31291

Within a class, the ceiling depends on how many cores are in that class: "The more cores belonging to a category at any given time, the lower the maximum frequency" opt-manual:3865-3867. And Intel states the cross-class scope explicitly: when cores enter a license level, the PCU "adjusts their frequency as necessary, potentially lowering the frequency. Cores that execute at other license levels are not affected" opt-manual:3917-3920. So via the license mechanism, AMX on the attention workers does not throttle scalar/AVX cores — but every additional AMX-active core can pull down the ceiling of the other AMX-active cores.

What we measured on delphi-3bda measured: in the P0 frequency/power capture, one core running either of the two AMX benchmark variants recorded there (amx44, amxqk) held 3.59 GHz vs 3.89 GHz for the AVX-512 variant (≈8% license clock cost), with package power flat across all three (223.8–226.3 W, ~13 s sustained per variant) (exec/results/slot1/p0c-freq-power.txt, 2026-08-18). At service scale — 8 users / 8K context, two-socket system total — the busy-clock cost was ~4% and package power moved +0.3% (arena-mirror) to +1.6% (canonical) against the AMX-off binary (exec/results/t4/t4-power.txt). The per-core split this section's takeaway asks for — APERF/MPERF on non-AMX cores while attention workers run AMX — remains unmeasured.

(2) The documented cross-core path is the shared package power budget. The manual notes that some workloads are power-limited and never reach their license's max frequency at all (its example: LINPACK "is power limited and does not reach the processor's maximum frequency" opt-manual:3931-3934). Package power (PL1/PL2) is shared by all cores, so a power-hungry AMX workload on many cores can, through that budget, reduce frequency for everything on the socket — including the FPGA-serving threads on the same socket. The manual documents the phenomenon, not an AMX-specific cross-core magnitude: on our platform this is a labeled hypothesis to measure, not a known number.

(3) The transition dynamics and the mitigating factors. License grants take up to 500 µs (the core runs at reduced capability meanwhile) and a ~2 ms timer holds the lower frequency before recovery opt-manual:3917-3922 — an argument for dedicating cores to AMX rather than sprinkling short AMX bursts across many cores. Below 15% AMX-unit utilization the core may exceed the nominal AMX-license ceiling opt-manual:31289-31291 — likely our regime, since decode attention issues TDPs sparsely between loads and softmax work. And lower frequency does not mean lower performance: Intel's own example shows AVX-512-heavy DL workloads gaining 1.3–1.5× over AVX2 versions despite the frequency drop opt-manual:3936-3939.

How to measure it on delphi-3bda (folded into doc 02's P0/T4): per-core license residency via CORE_POWER.LVL0/1/2_TURBO_LICENSE PMU events opt-manual:3873-3877; per-core effective clock via APERF/MPERF on non-AMX cores (main helpers, FPGA driver threads) while attention workers run AMX; package power via RAPL. Caveats: this section's mechanism is documented on Skylake Server and the AMX chapter defers to it (§20.2.1 → §2.6.3); Granite Rapids license-bin magnitudes are absent from the local refs, and SDM Vol 4's Xeon 6 P-core MSR table lists no AMX power/frequency MSR — so GNR numbers must be measured, not looked up.

8. How AMX is leveraged for LLM inference

General pattern (what oneDNN/PyTorch do on Xeon): weights or cache data are stored bf16/int8 pre-packed; GEMMs run on TMUL with fp32 accumulators; everything element-wise (activations, normalization, softmax) stays on AVX-512; kernels block for the 2 MB per-core L2 and prefetch 100–500 TDP-ops ahead opt-manual:32587-32693.

For attention at decode time specifically, the GEMMs available are, per KV page (64 tokens) and KV head:

  • Q·Kᵀ — scores: contraction over head_dim (128). M = grouped query rows, N = page tokens (64), K = 128.
  • P·V — weighted sum: contraction over page tokens. M = grouped query rows, K = 64, N = head_dim (128).

Both are bf16-in/fp32-out — exactly the TDPBF16PS contract. The guaranteed query-row group is the GQA head group (4 for qwen3-4b); it widens only when several queries legally multiply the same physical KV page (shared system prompts, speculative/token-tree decode) — a batching rule that doc 02 §design covers in detail. Softmax between the two GEMMs stays on AVX-512. The tron-specific design, replacement points, wall-clock timing, and the implementation/test plan are in doc 02 — tron decode AMX plan.

9. Glossary

AMX / TMUL / tile
Advanced Matrix Extensions; the per-core matrix engine; a 2-D register (≤16 rows × 64 B) it operates on.
Palette
A named tile-file configuration. Palette 1 = the standard 8-tile layout; palette 0 = released/INIT state.
TDP*
The tile dot-product instruction family (TDPBF16PS = bf16, TDPBSSD = int8, TDPFP16PS = fp16).
VNNI layout / K-pairing / KPACK
The B-operand storage order: consecutive elements along the contraction (K) dimension are interleaved into each 4-byte lane (2 bf16 or 4 int8 per dword).
GEMM / GEMV
General matrix–matrix multiply / matrix–vector multiply. GEMV is the M=1 degenerate case where AMX is weak.
bf16
bfloat16: a 16-bit floating-point format with fp32's 8-bit exponent and a 7-bit explicit fraction. Same exponent range as fp32; normal fp32→bf16 conversion rounds the discarded fraction bits, typically round-to-nearest-even.
fp32 accumulation
Products are summed in 32-bit float regardless of 16-bit inputs, bounding error growth.
XSAVE / XFD / arch_prctl
The x86 mechanism for saving extended register state on context switch; the per-thread fault switch the OS arms so first AMX use traps; the Linux syscall a process calls to be granted AMX state.
DAZ / FTZ / RNE
Denormals-are-zero, flush-to-zero, round-to-nearest-even — the fixed float behavior of AMX (and of AVX-512 bf16 dot products).
GQA / kv_mul
Grouped-query attention: several query heads share one KV head. qwen3-4b: 32 Q heads / 8 KV heads → group of 4 (tron calls it kv_mul).
KV cache / page
Per-layer, per-head store of past tokens' K and V vectors, read every decode step. tron stores it in 64-token pages in host DRAM.
Frequency license
The CPU's mechanism of capping clock speed based on which vector/matrix units are active; AMX adds the lowest-clock license class.
SNC / sub-NUMA clustering
BIOS mode splitting one socket into 2–3 NUMA domains for locality; delphi-3bda currently runs SNC off.
HT / SMT sibling
The second hardware thread sharing one physical core.
SPR / EMR / GNR
Sapphire Rapids (4th-gen Xeon Scalable), Emerald Rapids (5th), Granite Rapids (6th — the Xeon 6 P-core, our target).
