Tron Decode AMX Plan

Where Intel AMX can replace code in tron's software attention to speed up decode of ingested-qwen-3-4b-instruct-2507-tp2 on Xeon 6 6962P — architecture walkthrough, replacement points, kernel design, implementation & test plan, and system configuration. Companion primer: doc 01 — Intel AMX ramp-up. Citations: tron file:line at commit 1407f48dd (main), Intel refs as in doc 01.

Sol's round-1 review rejected two of Claude's original design points — cross-user tile batching and tile-resident cross-page accumulation — and both were withdrawn/corrected; the resolution log is in §10. Everything below is the agreed v2 design.

Gate note: this document is preserved unmodified as the pre-PoC independent plan. Post-gate amendments informed by Bill's PoC (notably: prefill-first framing, the measured FPGA-pipeline decode ceiling, a blocked-AVX-512 middle tier, independent QK/PV thresholds, and 4+4-vs-6+2 PV blocking as an A/B) are in doc 03 §6 and supersede this document where they conflict.
TL;DR
  • tron decode: FPGAs do all weight matmuls; the CPU does RoPE, norms, SiLU — and, in software-attention mode, the whole attention over the KV cache. The pending portion of that CPU attention sits between the FPGA's WV and WO matmuls on the per-layer critical path, and the attention path is assigned roughly half the worker pool; its measured CPU-time share is still a P0 item. (P0 = phase 0 of this plan's implementation phases P0–P5, §7: the measure-first microbenchmark/profiling step that runs before any code changes.)
  • Two inner loops are written as one-dot-product-at-a-time vector code, but the math they compute is a small matrix multiply — which is what makes them the AMX replacement points: Q·Kᵀ scores (dotter, one dot per K token today) and P·V weighted sum (scaled_v_expr).
  • The KV layouts are already AMX-native: K pages load as A tiles unchanged; V pages are byte-identical to the AMX B-operand format. No stored-layout change is needed or wanted (the FPGA DMA path shares these pages).
  • The honest catch: guaranteed tile width at decode is only 4 (the GQA head group). Wider batching is legal only for queries sharing the same physical KV page (shared prefixes, token-tree/speculative decode). The first milestone is a fused-page microbenchmark at width 4 — no speedup is claimed before that measurement.
  • System side: no BIOS/kernel changes needed; the code must request AMX per process (arch_prctl), manage tile state around waits, and keep one AMX worker per physical core.

1. Decode architecture: who does what

One decode step = one forward pass over 36 layers for a minibatch of tokens (typically 8 users → two minibatches of 4; the lone-chunk split exists to let FPGA and CPU work overlap model.hpp:199-249). Per layer, the plugin schedule is wq → rope_q → attention → wo → w1,w3 → SiLU·gate → w2 → rmsnorm with placement FPGA / CPU / CPU / FPGA / FPGA / CPU / FPGA / CPU llama.hpp:1332-1338. K and V come back from the FPGA; the per-card driver RX workers run K's normalization + RoPE and save K plus unchanged V into host-DRAM KV pages, as the Wk/Wv DMA-completion callbacks (llama.hpp launch_kv_jobs; pos/worker.cpp:605-616; model.hpp:2752-2862) — attention then reads those pages on the CPU. RoPE on Q runs on the attention workers themselves. tp2 means each weight matmul is split across 2 FPGA cards (common.hpp:91; ptensor.hpp:610-611); CPU attention is not sharded — it sees all 8 KV heads.

When is attention on the CPU at all?

  • Forced software: USE_HW_ATTN=0, or the model/op is ineligible (sliding window, non-standard geometry, EAGLE draft) hw_attn_config.cpp:10-31; self_attention.hpp:519-527.
  • Even with FPGA attention on (the default for ingested qwen-3-4b: force_hw_attn=true ingest/src/TronCpp.hs:233): every query below position 127 and the causal tail past the last complete 1024-token HBM shard still run in software and join with the FPGA partials on the CPU model.hpp:2529-2547; libpos.hpp:79.

Consensus caveat (Sol): benchmark runs must set USE_HW_ATTN=0 explicitly for the primary software-kernel result — the deployed default for this model would otherwise measure mostly FPGA attention plus a software tail.

2. Inside software attention

The kernel is a paged, streaming-softmax ("Rabe–Staats monoid") attention self_attention.hpp:125-193. KV lives in host DRAM as 64-token pages per (layer, kv_head) kv_cache.hpp:1145, 1843. Work is split across dedicated attention workers by kv_section = (kv_head, page range) model.hpp:2296-2360; each worker keeps a private (m*, s*, v*) scratchpad, merged afterwards by a parallel join self_attention.hpp:1039-1113, 1520-1563.

Why the layouts make this cheap

  • K page = ready-made A operand. kv_block.k is a contiguous 64×128 bf16 row-major block, 64-B aligned, row stride 256 B kv_cache.hpp:1843-1846 — loadable as a 4×4 grid of AMX tiles with plain TILELOADD, unchanged.
  • V page = ready-made B operand. V is stored token-pair-interleaved [p/2][dim][p%2] kv_cache.hpp:1848-1850 — byte-identical to the AMX/VNNI B layout (doc 01 §5). Zero repacking. (Consensus note: one research report suggested V might need de-interleaving; that was reviewed and rejected — the stored layout matches the tile operand exactly.)
  • Everything is bf16-in / fp32-accumulate already — the exact TDPBF16PS contract, so the port changes accumulation order only (tolerance tests, not bit-equality).
  • Layouts must not change: the same pages are DMA'd to FPGA HBM when hardware attention is active model.hpp:2752-2862 — a shared contract, and the reason the design keeps K on the A side instead of repacking it (§4, D1).

2b. The interleaved pair, concretely (addendum 2026-08-19)

The bf16 dot-product instructions (AVX-512's VDPBF16PS and AMX's TDPBF16PS) never multiply single numbers — the smallest unit they consume is a pair of adjacent bf16 values: each fp32 accumulator lane takes two matching reduction-axis values from each operand and adds both products at once. For a matrix used as the B operand, those two values must appear side by side in the pair-interleaved ("VNNI") layout; the A operand needs only ordinary row-major adjacency along its reduction dimension. Doc 01 covers the instruction-set view; this section shows what it means for tron's data, with example numbers.

Reading panel 2 (two common stumbles): First, the P values are attention weights — the softmax outputs of the QK step ("this new token attends 50% to t0, 25% to t1") — not model parameters; no model parameter appears anywhere in this kernel. Second, the pair (0, 10) in the C[d0] line is dim d0 of two different tokens, and adding them into one accumulator is not a mix-up: the PV output at each dim is defined as a sum over tokens, O[d0] = P[t0]·V[t0][d0] + P[t1]·V[t1][d0] + …, so the instruction step is adding two consecutive terms of that sum (0.50×0 + 0.25×10), and the next step adds the (t2, t3) terms. Blending tokens per dim is exactly what attention's weighted sum does.

What plain row-major V would compute (why the interleave is mandatory): the bf16 units reuse the fp32 datapath, so the hardware never addresses a lone 16-bit value — it reads 32-bit lanes, and its per-lane contract is fixed: C[lane] += A.lo×B.lo + A.hi×B.hi, with both halves of a B lane feeding the same accumulator and no stride or gather mode to change that. Store V plainly (one row per token) and t0's first lane holds (V[t0][d0], V[t0][d1]) = (0, 1); the instruction would blindly compute C[lane0] += 0.50×0 + 0.25×1 = 0.25 instead of 2.50 — token t1's weight applied to token t0's d1 value, and a d1 value accumulated into d0's output — silently wrong in every lane, no fault raised. The layout is the only way to tell the instruction what the reduction pairs are. Geometry says which operand needs the fix: the bf16 reduction is 32 deep but a tile has 16 rows; A's reduction axis runs along its row, so consecutive pairs are already adjacent in memory, while B's reduction axis runs down the rows, so a consecutive pair straddles two logical rows — software must fold rows 2k and 2k+1 into one physical row beforehand, and that fold is the pair-interleave.

The rule that makes sense of it: in these dot-product layouts, each pair is two adjacent elements of the reduction axis. In the B operand's pair-interleaved layout, PV (which sums over tokens) therefore pairs adjacent tokens, while QK (which sums over dims) pairs adjacent dims when K is the B operand. tron's V is already stored token-paired (it was designed for VDPBF16PS), which is why the AMX PV kernel consumes it with zero repacking. K is stored plain, so the canonical kernel sidesteps the requirement by making K the A operand — at the price of the transposed output (§4b) — while the mirror formulation pays with the pre-paired K copy instead.

A common misreading, spelled out: "K became the A operand, so does Q get token-paired?" No — token pairs never appear in QK at all. Tokens and queries are the output axes of QK; only dims are summed away, so every pair in QK is a dim pair. K's dim pairs come free (a stored K row is 128 contiguous dims — enough for an A operand); Q's must be built, because the B layout wants each query's two dim values side by side per dim pair. Example with Q[query][dim] = 100·query + dim: the packed B row for dim pair (d0, d1) reads (0,1) (100,101) (200,201) (300,301) — one bracket per query — and one instruction step computes S[t5][q] += K[t5][d0]·Q[q][d0] + K[t5][d1]·Q[q][d1] for all four queries at once (with the K row (50, 51, …): q0 gets 50×0 + 51×1 = 51). The pack is cheap because Q is tiny (4×128 per GQA group) and packed once per (token, kv-head), reused across every page; K is the big per-page operand — which is exactly why the canonical design rearranges Q and not K.

4b. The transpose in practice (addendum 2026-08-19): optimizations, measured cost, and the alternative that removes it

Section 4 is the consensus-v2 design, frozen as reviewed. This addendum consolidates what P0–P2 then learned about the transposing store, which was previously scattered across the results pages and status entries.

  • Why a transpose exists at all: with the canonical orientation (D1, Sᵀ = K·Qᵀ), the C tiles hold scores as 64 token rows × Nq query columns, but the epilogue (max/exp over the 64-token axis) needs them as Nq rows × 64 columns. The mirror orientation avoids this by consuming a pre-interleaved K copy instead (see the last bullet).
  • Optimization 1 — width-specialized transposing store (shipped in increment 1): a full 16×16 fp32 lane transpose takes two stages (stage 1: unpacklo/unpackhi at 32-bit then 64-bit granularity per 4-row group; stage 2: shuffle_f32x4 combinations). At the guaranteed decode width 4, only output rows 0–3 are needed, so only their output-specific stage-2 paths are emitted — a quarter of the full transpose's stage-2 paths, while the shared stage-1 work remains (qk_st_128x4, src/tron/kernels/amx_attn.cpp). The first transpose implementation had a wrong permutation; the harness's runtime self-check against a scalar reference caught it, which is why the harness runs that self-check for every kernel variant.
  • Optimization 2 — merged transpose + scale (harness only): the P0 harness merged the softmax scale into the transposing store (one combined pass). The in-tree increment 1 deliberately kept the store UNSCALED with the existing epilogue untouched, trading a little speed for a byte-identical scoring epilogue.
  • Optimization 3 — pipelined double-buffering (measured, rejected): hypothesis was that the tile-store → vector-load round-trip stalls the transpose; alternating score buffers across an 8-page ring improved throughput by only ≈2% (982 vs 1006 ns/page at width 4), showing the store→load round trip was not the dominant bottleneck under these measured conditions; the variant was not adopted.
  • The measured floor: the best experimental canonical result in the grid remained ≈300 ns/page slower than the mirror kernel at width 4 (982 vs 686 ns, fused-sweep.html grid v2; an earlier note said ≈200 ns — arithmetic corrected 2026-08-19). The canonical path's transpose and score-memory round-trip are expected to account for much of this gap, but the end-to-end kernel comparison does not isolate their exact contribution. The layout mismatch is inherent to this orientation under the current epilogue contract, although its implementation cost may still be reducible; eliminating the reorientation requires changing the formulation or the downstream contract.
  • The remover — the mirror formulation (increment 2): S = Q·Kᵀ read from a VNNI-interleaved K copy needs no transposing store at all (the formulation originates from Bill's PR #2934; the implementation and numbers are ours). In-tree verdict (p2-inc2.html): the mirror kernel gains ≈14% decode at equal layout, netting +3.7/+5.2% after the 3-plane layout tax; canonical-K remains the default and the mirror is a gated opt-in (formulation decision, doc 04).

Reading order for the full transpose story: this section → fused-sweep.html (the measured grid and variants) → p2-inc2.html (the in-tree mirror verdict and layout costs) → doc 04 P0/P2 status entries (dated record).

5. Tile utilization & the batching rule

The width-4 problem: at decode, one query token engages 4 query heads per KV head (GQA 32/8). In R1 those 4 queries fill only 4 of 16 output columns; in R2, 4 of 16 A rows. A TDP costs its full slot regardless (doc 01 §7.1). The consensus rule for widening:

Queries may share one GEMM only if they multiply the same physical KV page. Independent decode users own disjoint pages — batching them multiplies memory traffic, not arithmetic intensity, and is not a valid utilization strategy (this was the original plan's central error; withdrawn in round 1, see §10). The consensus grouping condition: same immutable physical K/V page and KV head, compatible attention math/configuration, and independently representable per-query visibility masks — queries sharing a page may keep distinct visibility (dense QK + per-query masking handles it); pointer identity must hold for the duration of the kernel invocation; logical page numbers, common ancestry, or equal contents are insufficient. Legal width sources, in order of reliability:
  1. The 4-head GQA group (always, width 4). "Private decode pages guarantee only QK N=4 and PV M=4 for qwen3-4b GQA."
  2. Multiple in-flight tokens of the same sequence (speculative / token-tree decode) attending shared pages.
  3. Different users over physically shared prefix pages — tron dedups shared prefixes via the token tree (full.hpp:1600-1724; --shared-system-prompt-length in tronperf), and the per-query visibility machinery (ranged_mask.hpp:97-182) exists precisely because several query jobs can legally attend one page. Real but workload-dependent coverage; the incidence is unmeasured — P1 instruments it as weighted work coverage (a few hot shared-prefix pages can carry a large share of QK/PV work), and any batching restructure (P4) is gated on that measurement.

6b. Precision: what each engine computes (addendum 2026-08-19)

This section answers a review question from Jeremy: do AVX and AMX use different floating-point formats, and if so what does the AMX plan do about it? Short answer: both attention dot-product implementations use bf16 operands with fp32 accumulation, so no datatype conversion is needed to move QK/PV from AVX-512 BF16 to AMX-BF16 — there is no format mismatch to bridge. For ordinary finite values, the expected numeric differences between the two arms are one rounding-mode choice and the fp32 reduction order (details and caveats below). This section also corrects an earlier claim of ours (in the increment-1b notes) that the AVX PV path multiplied with fp32 weights — it does not; it rounds them to bf16 too.

So the common statement "AMX is bf16/int8 only" describes Sapphire/Emerald Rapids; Granite Rapids adds AMX-FP16. Neither fp16 unit matters here: tron's KV cache stores K and V as bf16, and no fp16 appears anywhere in software attention.

What tron's two attention paths actually compute

  • AVX QK: the dotter multiplies bf16 Q against bf16 K with VDPBF16PS (_mm512_dpbf16_ps, dotter.hpp:167, 218), accumulating fp32.
  • AVX PV: scaled_v_expr converts the fp32 softmax weights to bf16 by truncation — a 16-bit right shift that simply drops the low mantissa bits (kv_cache.hpp:1795–1800) — interleaves them into pairs, and multiplies against the bf16 V with VDPBF16PS (kv_cache.hpp:1678, 1682), accumulating fp32.
  • AMX QK/PV (increments 1 and 1b): TDPBF16PS on the same bf16 K/V data; the PV weights are converted fp32→bf16 with VCVTNE2PS2BF16, which rounds to nearest even (RNE) instead of truncating; all accumulation fp32 in the tile registers.
  • Everything around the multiplies (scale, softcap, max, exp, the deferred-softmax v*/s*/m* updates) is the identical fp32 code in both paths.

Plain words: bf16 has 8 bits of significand precision (7 stored fraction bits plus the implicit leading bit). Within one power-of-two range, adjacent representable values are spaced about 0.78% of that range's base apart ("1 ULP"). Chopping the low 16 fp32 bits rounds toward zero — for these nonnegative weights that means downward — with error below 1 ULP. Round to nearest even picks the nearest representable value, with error at most 0.5 ULP for ordinary finite values, and avoids truncation's systematic downward tendency. (The AVX conversion, _mm512_srli_epi32(..., 16), is a bit-level chop, not an IEEE conversion instruction.)

The resulting A/B differences and the decision

  • Numeric deltas between the AVX and AMX arms — for finite, non-subnormal inputs and identical softmax update sequencing and padding: (1) the PV-weight conversion (chop vs RNE); (2) fp32 accumulation/reduction order (non-associative; this heading also covers VDPBF16PS's two-product grouping vs the tile FMA topology). Exceptional and subnormal behavior (DAZ/FTZ, NaN/infinity) is outside this comparison and should be ruled out or tested separately in T1.
  • Measured effect (t1-quick, 2026-08-18, greedy + seeded + --pay-for-determinism; control: two AVX runs byte-identical): AMX output byte-identical at ctx 8192; one argmax flip about 20 tokens in at ctx 2048, after which the continuations diverge by construction. One prompt per context — a sample, not a verdict. The P0 harness observed a worst-case relative error of 8×10-5 on the normalized outputs (denominator floored at 10-3) against its scalar reference on the tested cases — an observation, not a proven bound. Note the reference itself rounds the softmax weights to bf16 (amx_fused_bench.cpp:439, matching all fast paths), so that figure measures the score-path and reduction-order effects, not the weight quantization.
  • Decision (2026-08-19, approved by jhan): keep RNE — the locally more accurate conversion for ordinary finite values — and let the formal T1 logit-tolerance test judge both arms against an fp32 reference (T1 should compare pre-sampling logits with a predeclared absolute-plus-relative criterion; byte-identical generated text is a nondeterminism check, not an accuracy test). If T1's owners prefer minimum divergence from the shipped AVX behavior instead, switching the AMX conversion to the same chop is a one-line change in pv_128x4, making the PV weight operands bit-identical between the arms; for the tested finite, non-subnormal domain the remaining expected numerical delta would be the reduction order.

11. Glossary

Canonical-K / mirror-K
Our own shorthand, not a standard term. Canonical-K = K stored the way tron stores it today: one copy, original layout, byte-for-byte unchanged; the canonical kernel reads those existing bytes directly (and therefore needs the transposing store, §4b). Mirror-K = a second, rearranged copy of K kept next to the original so the kernel can skip the transpose (the formulation from Bill's PR #2934; costs measured in rampup/p2-inc2.html). "Canonical" is the software word for "the standard/official version".
KV block layout / layout penalty
"Layout" = how one kv_block (the storage unit for one layer-slot × kv-head × 64-token page) arranges its data planes in memory. Default: two planes, K then V (32 KB at head 128), blocks packed back-to-back. The mirror build adds a third plane (the rearranged K copy) inside each block (48 KB). The "layout penalty" is the slowdown from that fatter arrangement by itself: pages sit 1.5× farther apart and a 16 KB plane the AVX path never reads sits between every K and V, breaking hardware prefetch streams. Proven by a layout-only control build (3-plane blocks, zero mirror code) that reproduced the mirror build's fallback penalty exactly, with decode-phase counters showing LLC-load misses 50.8%→84.6% and TLB misses ≈0 in both arms (rampup/p2-inc2.html, "The costs").
Software attention / hw attention
Attention computed on the host CPU over DRAM KV pages vs. on the FPGA over HBM-resident KV shards. This project targets the CPU path only.
Page
64 contiguous tokens of one (layer, kv_head)'s K and V, stored as one contiguous block in host DRAM. The unit of attention work and of parallel reduction.
kv_section
A (kv_head, page-range) chunk of work assigned to one attention worker for one attention operation.
Minibatch
The tokens of one forward pass are split into 1–2 chunks (≤128 tokens) so FPGA and CPU stages of different chunks overlap.
Ready / pending pages
Pages already filled before this pass (attendable immediately) vs. pages receiving this pass's K/V (attendable only after save_k/save_v).
Rabe–Staats monoid / (m*, s*, v*)
The streaming-softmax bookkeeping: running max, running exp-sum, running weighted V sum — lets pages be processed in any order/parallel and merged ("join").
Join / "pink work"
The parallel merge of per-worker (m*, s*, v*) partials into the final attention output (nicknamed for its Perfetto color).
dotter / scaled_v
Today's AVX-512 kernels: the Q·K dot product object and the P·V accumulation expression.
GQA group / kv_mul
The 4 query heads sharing one KV head in qwen3-4b (32 Q / 8 KV heads).
tp2
The executor variant that splits each FPGA weight matmul across 2 cards. CPU attention is unaffected by tp-degree.
Ingested model
A model whose C++ plugin was generated by the ingest pipeline (torch.export trace → generated header) rather than handwritten. qwen-3-4b runs as ingested-qwen-3-4b-instruct-2507-tp2.
GOF
The host→FPGA DMA machinery that ships KV pages to HBM for hardware attention — the reason stored KV layouts are a shared contract.
ranged_mask / visibility
Per-query-job bitmask machinery deciding which KV tokens a query may attend (causality, trees, windows).
USE_HW_ATTN / force_hw_attn
Env override (0 = force software) / the per-plugin default (true for all ingested plugins).
P0–P5 / T1–T5 / D1–D8 / R1–R4 / G, A
This plan's label families: P = implementation phases (§7; P0 is the measure-first microbenchmark step), T = test layers (§8), D = design decisions (§4), R = replacement points (§3), G/A = gaps and amendments from the PoC comparison (doc 03 §6).
AMX terms
Tile, TMUL, TDPBF16PS, palette, VNNI pairing, XFD, frequency license — see doc 01 glossary. Performance units (MAC, MAC/cycle/core, flop, throughput vs latency, M/N/K, arithmetic intensity) — see doc 01 §0 terminology.
