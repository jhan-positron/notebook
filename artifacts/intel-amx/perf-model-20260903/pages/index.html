Perf model · report · 2026-09-03

The AMX decode boost from a model with data waits

Machine: delphi-3bda (the test server, Intel Xeon 6962P)Workload: qwen-3-4b-tp2, one user, prompt 8192, 256 generated tokensPlan: action-plan.html

Short version. AMX (Intel's CPU instructions that multiply small matrices of 16-bit numbers in one step) made Tron (Positron's inference program) generate tokens 17.3% faster at prompt 8192 (a prompt of 8192 tokens) than the same program with AMX switched off, measured on the test machine delphi-3bda. The model of this report estimates +14.4% for that gain, 2.9 points below the measurement, from Tron's AVX-only run plus small test programs on the same machine; the earlier estimate from the same starting point was +33%. The term the earlier estimate missed is the data wait: under decode load each of the 27 attention cores streams 13 GB/s from memory, so at prompt 8192, where the 1170 MiB of keys and values live in DRAM, the 32 KiB of one attention unit take about 2.5 µs to arrive however fast the arithmetic runs, and the AMX unit measures 2.73 µs.

Every other term (unit, page, worker, book, and so on) is defined in "Words used here" below.

Words used here

Tron, runtron
Positron's inference program and its command-line tool. Here Tron runs the weight matrix multiplies on FPGA cards (field-programmable gate arrays, the reconfigurable chips on Positron's accelerator cards) and the attention on CPU cores.
AMX, AVX, dotter
Two CPU instruction sets. AVX-512 is the ordinary 512-bit vector set; Tron's AVX attention loop is called the dotter. AMX (Advanced Matrix Extensions) multiplies 16-row tiles of bf16 numbers (bfloat16, a 16-bit floating-point format) in one instruction, TDPBF16PS. VDPBF16PS is the AVX-512 instruction the dotter uses (32 multiply-adds at once); TILELOADD loads one tile; LDTILECFG sets up the tile registers.
Arena-mirror
The AMX build of Tron that keeps a second copy of the keys in the tile-friendly layout (the K mirror, on ordinary 4 KiB pages); the build whose measured boost (+17.3%) this report estimates.
Kill switch, AVX form
TRON_AMX_DISABLE=1: the AMX binary with AMX switched off, so it runs the dotter everywhere. The baseline of this report is that run (M7), the same binary and flags as the 2026-09-01 measurement.
Pre-AMX input
An input that would exist before AMX was added to Tron: Tron's own AVX-path timers, page geometry, Intel documents and non-Tron processor measurements. The "pre-AMX bracket" rows of section 8 use only such inputs. The AMX unit itself is measured with a copy of Tron's AMX kernel run outside Tron (section 2).
Pre-registered
Fixed in the plan (action-plan.html) before any measurement was taken: the rules, the search order and the acceptance thresholds.
Decode, token
The phase where the model produces one token per step; every step re-reads all stored keys and values. Times are per generated token.
Page, KV head, unit
A page is 64 tokens of stored keys (16 KiB) and values (16 KiB) for one layer and one KV head (a key/value head; each serves 4 query heads). A unit is one query token's 4 query heads against one page, including the softmax pieces and the running-state update.
QK, PV, common work
The two matrix multiplies of a unit (queries against keys; probabilities against values) and the rest (scaling, running maximum, exponentials and sum, state update).
Page work, joins, barrier, untimed rest
The three timed phases of one attention operation on one worker: its loop over units; merging results across workers; waiting for the slowest worker. The untimed rest is attention time minus the three phases: handshakes and bookkeeping no phase timer covers; it is held unchanged in the estimate.
Worker, worker 0
One of the 27 CPU threads that run attention units at the same time, each on its own core of socket 0 (CPUs 24 to 35, 48 to 59, 151 to 154; one of the 28 hosts the main thread). Worker 0 is the one whose timers Tron exports; all per-token numbers are its medians. Tron's planner splits pages by measured worker speed, so worker 0's share differs from run to run.
Range, per-range overhead, AMX per-token extras
A range is one run of consecutive pages a worker handles in one attention operation; worker 0 has 36 per token, one per layer. The per-range overhead is page work minus units × unit cost: the page loop and the probe's own reads. The AMX per-token extras are the AMX-only costs paid once per range (tile configuration, the 1 KiB query copy, the tile release), measured by the benchmark's range timer.
Book, arena
Tron's KV allocator places a sequence's pages adjacent in books of 24 pages (a book holds 1600 tokens by default; 24 pages are used with 128-token prompt chunks); each book is its own arena, one contiguous block of memory. Found in the KV cache and scheduler source; reproduced by the benchmark's --book-pages 24 option.
Probe, stamps
The timing code compiled into the Tron binary used here (git branch jhan-amx-fence, commit 8fd1e7798d), switched on with TRON_ATTN_PHASE=1; it records the per-token and per-phase counters (numbered "stamps") this report reads.
Coverage
The share of units that can use AMX: only full 64-token pages qualify (99.24% at prompt 8192, 97.14% at 2048, 84.78% at 256; from the fallback counters of 2026-09-01).
Data wait, compute, eta, memory time
Compute: the unit's time with all bytes already in the core's L2 cache. Memory time: 32 KiB divided by the per-core streaming rate under load. Data wait: the unit's time minus its compute. eta: the share of the shorter of compute and memory time that is hidden behind the longer one (1 = perfect overlap, the roofline case; 0 = the two add, the serial case).
Memory lower bound
The memory time: a unit cannot finish before its 32 KiB has arrived, however fast its instructions run.
Rcore(N)
The bytes per second one core streams from DRAM (main memory) when N cores on the socket read at once.
L1, L2, L3, DRAM, hot
The core's caches and main memory. L1 (48 KiB) and L2 (2 MiB) are private to each core; L3 (432 MB) is shared by the socket. A "hot" unit reads a page that is already in the core's L2.
Cache line, demand miss, hardware prefetch
A cache line is 64 bytes (32 KiB = 512 lines). A demand miss is a load the program itself issued whose line was not in the cache. Hardware prefetch is the core fetching lines ahead of the program on its own guess; prefetched lines do not count as demand misses.
1 GiB pages, THP, hugetlb, TLB, dTLB walk
Memory page sizes and their cost. 1 GiB pages: the pool of huge pages Tron's KV arena uses (hugetlb). THP: transparent huge pages, 2 MiB pages the kernel assigns on request. The TLB caches address translations; a dTLB walk is the slow page-table lookup after a data-side TLB miss (one per 4 KiB page touched, when pages are small).
rdtsc, turbostat, perf stat
rdtsc: the CPU's cycle-counter instruction, used as the clock by Tron's probe and by the benchmark. turbostat: the Linux tool that reports each core's clock; its Bzy_MHz column is the clock while the core is busy (M4). perf stat: the Linux tool that reads the CPU's hardware counters (M6).
Residual, calibration gate
The residual is Tron's AVX unit minus the benchmark's AVX unit under the same load and layout (as a share of Tron's). The gate is the plan's limit on it: within 5% at prompt 8192 with QK and PV each within 10%; within 10% at prompts 2048 and 256. When it fails, the verdict is "calibration failed", the AMX numbers are provisional, and the search of section 4 runs.
s, transfer rule
s = Tron's AVX unit ÷ the benchmark's AVX unit; the pre-registered rule of the plan (section 7) decides how the residual is carried to the AMX unit: none, multiplicative (× s) or additive (+ residual).
Band, points
The pre-registered band is the range of the estimate over the alternative rules of plan section 8, rule 6 (the three transfer variants, the AMX clock ±5%, the two barrier rules). Points are percentage points: +20% minus +17% is 3 points.
Verdict: on par, close
The plan's acceptance rule (section 1). On par: the primary estimate within 3 points of the measured +17.3% and the whole pre-registered band within 3 points. Close: the primary within 6 points. A failed calibration gate gives "calibration failed" instead.
Record labels
Tron's names for the weight multiplies: WQ, WK, WV (query, key, value), WO (attention output projection), WFF1, WFF3, WFF2 (the three feed-forward multiplies). Norms are the normalization layers; rope is the rotary position embedding; logits are the per-word scores produced once per token.
M0 to M8
The measurement steps of the plan, in the order the campaign ran them: M0 hardware check, M7 Tron in AVX form, M1 memory streaming rate, M2 memory latency, M5 instruction costs, M3 the unit benchmark, M4 clocks, M6 hardware counters, M8 a traced Tron run. Section 10 names the file of each step.
est., Insufficient data
est.: an estimated number, not a measured one. Insufficient data: a quantity the campaign could not measure, with the measurement that would settle it named.

1. Result

Estimate at prompt 8192: +14.4%. Measured: +17.3%. Pre-registered band: +7.9% to +15.9%.

Verdict under the plan's rules: calibration failed (plan section 7: benchmark unit 9.5% short of Tron's, limit 5%; QK 13.4% short of Tron's, limit 10%). The gate compares the benchmark's AVX unit with Tron's under the same load and layout; round 2 changed the transfer rule, not that comparison, so the gate is still failed and the +14.4% estimate is provisional. If the gate is waived, the acceptance rule of plan section 1 gives "close", not "on par": the primary value is -2.9 points from the measurement (within 3), but the pre-registered band's low edge, +7.9%, is 9.4 points away (outside 3). Over the alternatives the search does not rule out (barrier rules, AMX clock ±5%) the band is +13.7% to +15.9%; that band is post hoc and not part of the acceptance rule.

The model's first pass, run exactly as pre-registered in the plan, gave +8.8%. Its calibration rule carried the whole difference between the benchmark's AVX unit and Tron's AVX unit onto the AMX unit, and its own calibration gate failed, so the plan's search ran (section 4). The search explained part of that difference and established two facts about the AMX unit. First, the memory-layout settings that move the AVX unit move the AMX unit little: pages placed at random add 27% to the AVX unit and 1% to the AMX unit; 2 MiB pages add 2.6% and 1.3%. Second, Tron's book layout, which the search identified in Tron's allocator, moves both units (AVX +1.9%, AMX +2.9%), so it was applied to both by taking the book-layout runs as the primary configuration. The second pass carries none of the remaining, unexplained difference to the AMX unit and estimates +14.4%. That choice departs from the pre-registered transfer rule and was made after the round-1 result was seen; the estimate under the opposite reading, in which the unexplained difference carries in full to the AMX unit, is +9.1%, and the pre-registered rule as written gives +8.8%. The validation rows use the single-arena runs: +6.4% against a measured +6.1% at prompt 2048, and +1.9% against +0.5% at prompt 256, where the measured gain is smaller than the 0.8% run-to-run variation of the two AVX runs.

2. The model

The model is the plan's section 3: the earlier "model in one picture" with a data-wait term at the unit level. Only the covered units change between the AVX and the AMX build; everything else in a token keeps its measured time.

token time   = other work                                           unchanged
             + attention
attention    = page work + joins + barrier + untimed rest           joins, barrier, rest unchanged
page work    = per-range overhead + AMX per-token extras
             + sum over units of  covered unit -> AMX unit (99.24%)  /  uncovered unit -> AVX unit (0.76%)
unit         = compute (whole unit hot in L2, per code path) + data wait
             = max(compute, memory) + (1 - eta) * min(compute, memory),   memory = 32 KiB / R_core(27)

The AMX unit is measured by a copy of Tron's AMX kernel run outside Tron on 27 cores over Tron's page layout (the unit benchmark, M3). The plan required the same benchmark to first reproduce Tron's own AVX unit within 5% under the same conditions. It came within 9.5% (3.19 µs against Tron's 3.53 µs at prompt 8192), 4.5 points outside that gate, so under the plan's rule the AMX reading is provisional. Section 4 reports the search for the cause and what it established about the AMX unit; section 9 the round that uses the AMX reading as measured. The compute, memory and wait terms decompose that measurement (section 5).

4. Calibration: the benchmark against Tron's AVX unit

Before any AMX number is read, the benchmark must reproduce Tron's own AVX unit under the same load and the same page layout. With Tron's book layout it comes within 9.5% (3.19 µs against Tron's 3.53 µs at prompt 8192), outside the 5% gate the plan set; by phase, the benchmark is short of Tron by 13.4% in QK, 23.6% in the common work and 3.9% in PV. With a single arena it came within 12.5% (3.09 µs). The pre-registered search for the cause has four steps. Step 1, a run with the timing probe switched off, was not made; in its place stands an argument: Tron's AVX path and the benchmark read the rdtsc timer at the same points of each unit, so the probe's cost is the same on both sides and cannot explain a difference between them. Steps 2 to 4 ran in the plan's order. Page order: with the 130 pages of each head placed at random instead of adjacent, the AVX unit rises from 3.09 to 3.91 µs (+27%) while the AMX unit moves from 2.64 to 2.66 µs (+0.9%). Page size: 2 MiB pages instead of 1 GiB pages add 2.6% (AVX) and 1.3% (AMX). Counters: the AVX benchmark takes about 130 demand L2 misses per unit for its 512 lines (m6-perf.txt, fill-only control subtracted, 2020 passes), so most lines arrive by hardware prefetch, which is why page adjacency matters so much to it. A further test, not one of the plan's four steps, was added after reading Tron's allocator: Tron keeps a sequence's pages adjacent within books of 24 pages, each book its own arena, so the benchmark was given the same layout; against a same-session control it adds 1.9% (AVX) and 2.9% (AMX), and it is now the primary layout for both paths. Of the remaining 0.33 µs difference, one part is known: Tron's AVX workers ran at 3.74 GHz (turbostat during Tron's AVX arm, perf-stat round 3 of 2026-09-01; not re-sampled in this campaign) against the benchmark's 3.89 GHz (M4), which is worth 0.07 µs on the compute part of the unit. The other 0.27 µs (7.6% of Tron's unit) is unexplained. Two labeled hypotheses: per-page bookkeeping in Tron's page loop that sits inside the QK timer (range lookups, validity marks), and memory traffic from Tron's other threads. Neither the layout tests nor the counters say whether that part carries to the AMX unit.

5. The unit, decomposed into compute and data wait

Hot in the L2 cache, one AVX unit takes 1.68 µs and one AMX unit 0.62 µs (both scaled to their serving clocks), so AMX removes about 1.06 µs of compute per unit. Under decode load, with 27 cores streaming, one core gets 13.1 GB/s, so the 32 KiB of a unit need 2.49 µs to arrive. With Tron's book layout the AVX unit measures 3.19 µs under that load, 1.51 µs of it data wait (47% of the unit); the AMX unit measures 2.73 µs, 2.11 µs of it data wait (77%). The AMX unit is 9% above the memory lower bound: removing 1.06 µs of arithmetic shortens the unit by only 0.47 µs, because most of the removed arithmetic had been overlapping with the wait. This is the mechanism the earlier estimate missed.

Inside "other work": the traced run (M8, labeled traced)

One kill-switch run at prompt 8192 was traced (M8; span medians in m8-spans.json, computed with the perfetto trace processor over 253 decode tokens). Its median forward time was 9.85 ms per token against the untraced 9.28 ms of M7, so tracing added about 6%. The traced spans per token are: waiting for FPGA results 4.06 ms (the span 'waiting for mbox', 1486 waits per token, about 41 per layer); preparing and launching the weight multiplies 1.34 ms ('Prepare hardware matmul job' 1.05 ms plus 'Launch hardware matmul job' 0.30 ms, which do not nest); and the logits stage 1.03 ms ('fill_logits_buffer' 0.35 ms, 'notify_listener' 0.36 ms, 'waiting_for_logits' 0.33 ms). These spans run on different threads, overlap in part with the attention phases, and carry tracing overhead, so only their proportions are carried into the picture of the non-attention work: about 63% waiting on the FPGA, 21% launch bookkeeping, 16% logits (est., traced). 9. Refinement rounds

Round 1 applied the plan's rules without change and reached +8.8%, outside the 6-point band; its calibration gate had already failed. The pre-registered search (section 4) explained part of the AVX residual and showed which parts move the AMX unit. Round 2 therefore uses Tron's book layout for both paths and the transfer variant "none": the AMX unit is the benchmark's 27-thread reading as measured, 2.73 µs. The estimate becomes +14.4%, 2.9 points below the measurement. The plan's round list has four further items; none changed the estimate. Joins and barrier as imbalance: the least-squares line through the three M7 prompts is joins plus barrier = 383 + 0.019 × page work (µs per token), with residuals of −12% at prompt 2048 and +14% at prompt 256 against a 10% limit, so the line is rejected and rule 1 (joins and barrier unchanged) stands. Page order and page size: those runs were made in the search of section 4 and are the basis of round 2. L3 residency: this round has two triggers. The first, eta above 1, does not fire at prompt 8192 (AVX 0.58, AMX 0.62); it does fire at prompts 2048 and 256, where the working sets fit in L3, and there it changes only the decomposition, not the estimate (section 8). The second, a demand L3-miss count more than 10% below 512 lines per unit, fires as written (74 misses per unit on the AVX path, 31 on the AMX path, section 10), but that counter excludes prefetched lines, so it does not measure the bytes read; a counter that includes prefetches (an all-fills or offcore-response count) would settle it (Insufficient data), and the round was not applied because the benchmark streams 1755 MiB per pass, four times the L3, and the AMX unit stays above the DRAM memory time. Worker-0 share: page work and barrier move in the same direction, so the restatement is not triggered. The plan's verdict stays "calibration failed": the gate of plan section 7 tests the benchmark's AVX unit against Tron's, and round 2 did not change that comparison. If the gate is waived, the acceptance rule of plan section 1 gives "close", not "on par": the primary value is within 3 points, but the pre-registered band still contains the two transfer variants the search argues against, and its low edge (+7.9%) is 9.4 points from the measurement. Over the alternatives the search does not rule out, the band is +13.7% to +15.9%; that band is post hoc and not part of the acceptance rule.

Joins-and-barrier fit (plan section 9): Joins plus barrier = 383 + 0.0191 × page work (µs per token), fitted by least squares to the three M7 prompts; residuals +13.9% at prompt 256, -12.3% at prompt 2048, +1.9% at prompt 8192; accepted: no (the plan requires every residual within 10%).
