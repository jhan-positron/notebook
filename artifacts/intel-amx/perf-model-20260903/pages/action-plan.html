Perf model · action plan · revision 2, written before any run on the machine

Estimating the AMX decode boost with a model that includes data waits

Date: 2026-09-03 Machine: delphi-3bda (Intel Xeon 6962P) Workload: qwen-3-4b-tp2, one user, prompt 8192 tokens, 256 generated tokens Author: Claude, for jhan

Short version. AMX (Intel's CPU instructions that multiply small matrices of 16-bit numbers in one step) made Tron (Positron's inference program) generate tokens 17.3% faster at prompt 8192 than the same program with AMX switched off, measured on delphi-3bda on 2026-09-01. An earlier estimate, built only from data that existed before AMX was added to Tron, said +33%, because it priced the arithmetic of the attention work and not the time each CPU core waits for its keys and values to arrive from memory. This plan rebuilds the estimate with that waiting time as an explicit term, filled in from Tron's own AVX-only run and from test programs on delphi-3bda; one of those programs is a copy of Tron's AMX attention kernel run outside Tron, which the brief allows as non-Tron software. The plan passes if the estimate is within 3 percentage points of +17.3%.

Every other term (unit, page, worker, and so on) is defined in "Words used here" below. This page is the plan. The final report is perf-model/index.html in the same folder.

Outcome (2026-09-03, after the campaign). The campaign ran between 14:02 and 14:27 UTC, plus one added test at 14:25. The model estimates +14.4% at prompt 8192 against the measured +17.3% (2.9 points low), +6.4% against +6.1% at prompt 2048 and +1.9% against +0.5% at prompt 256. Round 1, with the rules exactly as written here, gave +8.8% and failed its own calibration gate (the benchmark's AVX unit 9.5% short of Tron's with Tron's book layout, 12.5% with a single arena). The search of section 7 explained part of that residual (the AVX clock, the book layout) and showed that the layout settings move the AMX unit little; round 2 took Tron's book layout as the primary configuration for both paths and carried none of the unexplained rest to the AMX unit, a departure from the pre-registered transfer rule decided after round 1. Under the rule of section 7 the verdict is "calibration failed" and the estimate is provisional; if that gate is waived, the acceptance rule of section 1 gives "close", because the pre-registered band (+7.9% to +15.9%) still spans the ruled-out transfer variants. Details, arithmetic and the measurement record are in the report.

What changed in this revision

  • Tron may run in its AVX form (jhan, 2026-09-03): the kill-switch binary or a pre-AMX binary. Revision 1 treated the machine as a host without FPGA cards. This revision re-takes the AVX baseline fresh (step M7) instead of reusing the 2026-09-01 numbers, and adds one traced AVX run (M8) for the per-layer split of the non-attention work. The AMX path of Tron is still never run.
  • Refine until the exit test is met (jhan, 2026-09-03): data waits are the first refinement, not the last. Section 9 pre-registers the order of further refinements and the rule that each must rest on a measurement, never on tuning toward the target.
  • Adversarial review applied (section 14): 61 review agents checked the plan and the benchmark sources against the production code and the data. Twelve findings were confirmed and are fixed here; the largest are the resolution of the exit test (section 1), how the calibration residual is carried to the AMX side (section 7), the benchmark's exp constants and check gates, and the instruction loops.

Words used here

Tron, runtron
Positron's inference program and its command-line tool. In this setting Tron runs the weight matrix multiplies on FPGA cards and the attention on CPU cores.
FPGA, tp2
FPGA: field-programmable gate array, the reconfigurable chip on Positron's accelerator card that runs the weight multiplies. tp2: the model's weights are split across two cards.
Decode
The phase after the prompt has been read, where the model produces one token per step. Every step re-reads all stored keys and values.
AMX, AVX, dotter
Two CPU instruction sets. AVX-512 is the ordinary 512-bit vector set; Tron's AVX attention loop is called the dotter. AMX (Advanced Matrix Extensions) multiplies 16-row tiles of bf16 numbers in one instruction, TDPBF16PS. VDPBF16PS is the AVX-512 instruction the dotter uses (32 bf16 multiply-adds at once).
Arena-mirror, canonical
The two AMX builds of Tron. Arena-mirror keeps a second copy of the keys in the tile-friendly layout (the K mirror arena, ordinary memory on 4 KiB pages); canonical reads keys as stored and transposes the scores. This plan estimates the arena-mirror build, the one measured at +17.3%.
Kill switch
TRON_AMX_DISABLE=1: the AMX binary run with AMX switched off, so it executes the dotter everywhere. The +17.3% uses it as the baseline; a separately compiled AVX-only binary gave +18.0% in the pinned pair of 2026-09-01.
Pre-AMX input
An input that would exist before AMX was added to Tron: Tron's own AVX-path timers, page geometry, Intel documents, and non-Tron processor measurements. The Tron timer values on this page come from the kill-switch binary, whose timers also exist in pre-AMX builds. One input falls outside this definition: the AMX unit is measured with a copy of Tron's AMX kernel run outside Tron (section 7). That copy is non-Tron software, but the kernel code did not exist before AMX was added to Tron.
IPC, tok/s, TLB, top-down
IPC: instructions completed per clock cycle. tok/s: generated tokens per second. TLB: the cache of address translations; a "walk" is the slow page-table lookup after a TLB miss (dTLB: the data-side TLB). Top-down: Intel's method that assigns each cycle slot to one of four causes; its memory-bound share is the fraction stalled on data.
ARK, sub-channel, FMA, scalef
ARK: Intel's product specification site. Sub-channel: a DDR5 memory channel has two; the kernel's counter on this host counts one, so counts are doubled. FMA: fused multiply-add, one instruction that multiplies and adds. scalef: the instruction that multiplies by a power of two (the last step of the exp).
SIGINT, perfetto, smoke run, journal
SIGINT: the interrupt signal that tells a program to stop cleanly. perfetto: the trace format Tron writes with --trace-gen. Smoke run: a short run whose only purpose is to show that the setup works. Journal: the system log (systemd), read here to see whether the serving processes had traffic.
Register barrier, spin barrier
Register barrier: an empty instruction that marks a register as used, so the compiler cannot delete the load that filled it. Spin barrier: a synchronization point where threads wait by polling a counter, as Tron's attention workers do.
bf16
bfloat16, a 16-bit floating-point format; keys, values and queries are stored in it.
Page, KV head, GQA
A page is 64 tokens of stored keys (16 KiB) and values (16 KiB) for one layer and one KV head (a key/value head). In qwen-3-4b each KV head serves 4 query heads; this ratio is called kv_mul or GQA (grouped-query attention).
Unit
The smallest piece of attention work: one query token's 4 query heads against one page of one KV head, including the softmax pieces and the running-state update. One call of the function apply_page_tok.
QK, PV, common work
QK and PV are the two matrix multiplies inside a unit (queries against keys; probabilities against values). The common work is the rest: scaling, running maximum, exponentials and their sum (the softmax pieces) and the update of the running state v*, s*, m*.
Page work, joins, barrier
The three timed phases of one attention operation on one worker: the loop over its units; merging partial results across workers; waiting for the slowest worker.
Worker, worker 0, app cores
One of the 27 CPU threads that run attention units at the same time, each on its own core of socket 0 (the app cores, CPUs 24 to 35, 48 to 59, 151 to 154; the 28th hosts the main thread). Worker 0 is the one whose timers Tron exports, and every per-token number here is worker 0's median.
Stamps, probe, fence branch
Numbered timing points compiled into the binary (stamp 7605 = attention time per token; 7617 to 7627 = per-unit and per-phase counters). The probe is the code that records them; it lives on the fence branch of Tron (git branch jhan-amx-fence, commit 8fd1e7798d) and is switched on with TRON_ATTN_PHASE=1.
Coverage
The share of units that can use AMX. Only full 64-token pages qualify; the newest, partial page of each KV head falls back to the dotter.
Data wait
The time a core spends stalled because the bytes it needs have not arrived from the cache or DRAM (main memory). No instruction rate can shorten it.
L1, L2, L3, DRAM, residency
The core's caches (L1 48 KiB and L2 2 MiB private to each core; L3 432 MB shared by the socket) and main memory. Residency is where a page lives when it is read; a "hot" unit reads a page that is already in the core's L2.
Per-core streaming rate
How many bytes per second one core pulls from DRAM when it reads sequentially with all its outstanding-miss slots in use. Written Rcore(N) for N cores reading at once on one socket.
Loaded latency
The time one memory read takes while other cores are also reading. Little's law relates it to the rate: rate = outstanding misses × 64 bytes ÷ latency.
Roofline
The rule that a piece of work takes the larger of its compute time and its data-movement time, valid when the two overlap perfectly.
THP, 1 GiB pages, NUMA node
THP: transparent huge pages, 2 MiB memory pages the kernel assigns on request. 1 GiB pages: the pool of 512 huge pages Tron's KV arena uses. NUMA node: the memory attached to one socket; node 0 is socket 0's.
turbostat, perf stat, rdtsc
turbostat: a Linux tool that reports each core's clock (its Bzy_MHz column is the clock while busy). perf stat: the Linux tool that reads the CPU's hardware counters. rdtsc: the CPU's cycle-counter instruction, used as a clock by the probe and the benchmark.
LDTILECFG
The instruction that sets up the AMX tile registers; Tron issues it once per run of pages (Intel's manual prices it at 204 cycles).
Intel manual
The Intel 64 and IA-32 Architectures Optimization Reference Manual, document 248966, revision 050. Table 20-2 gives the AMX instruction rates.
Record labels
Tron's names for the weight multiplies: WQ, WK, WV (query, key, value), WO (attention output projection), WFF1, WFF3, WFF2 (the three feed-forward multiplies). Norms are the normalization layers; rope is the rotary position embedding applied to Q and K.
CI lease
The file /run/lock/systems-test-ci.lease on delphi-3bda. When it says busy and has not expired, the nightly CI owns the machine and we run nothing there.
Median, est., percentage point
Median: the middle value of a set; used for all per-token and per-unit times. est.: a number that is estimated, not measured. Percentage point (pp): the difference between two percentages, for example +20% minus +17% is 3 points.
sha256
A fingerprint of a file's contents; the results header records it for every binary so a run can be tied to its exact code.

1. Goal and exit test

Goal: a performance model of one decode token that includes data waits, and an estimate of the AMX decode boost at prompt 8192 built from that model. The inputs are pre-AMX inputs (see Words) with one exception. The pre-AMX inputs are Tron's AVX-path timers, page geometry, Intel documents, and non-Tron measurements of the processor. The exception is the AMX unit: it is measured with a copy of Tron's AMX kernel (the two tile functions and the AMX branch of the per-unit code, transcribed into unit_bench.cpp) run outside Tron with 27 threads over Tron's page layout (section 7). The brief allows AMX metrics from non-Tron software; this plan reads a transcribed kernel as such software, and jhan can overrule that reading. Tron itself runs on the machine only in its AVX form; the AMX path of Tron is never executed for this project.

Exit test: the estimate is on par with the measured boost. The reference is the same-binary result of 2026-09-01: token time 9260 µs with the kill switch against 7897 µs with arena-mirror AMX, a gain of +17.3% in tokens per second. The other rounds of 2026-09-01 gave +16.2% (same binary, fence round 3) and +18.0% (clean AVX binary against arena-mirror, pinned pair). Older rounds gave +15.0% to +16.1% (fence rounds of 2026-08-31 and 2026-09-01 on an earlier branch state) and +19.6% (2026-08-21 builds). The rounds on the fence branch span 3.0 points (+15.0% to +18.0%); adding the 2026-08-21 builds widens the span to 4.6 points. The 3-point acceptance band below is the span of the fence-branch rounds.

Acceptance rule, fixed now. The estimate is on par if its primary value lies within 3 points of +17.3% and its whole band (section 8, rule 6) also lies within 3 points. It is close if the primary value lies within 6 points. Beyond 6 points the model has a defect the report must name. The band includes two alternative barrier rules that sit above the primary by construction (about 1 and 2 points at the measured unit ratio), so the whole-band clause in effect requires the primary to land between about +14.3% and +18.3%.

Resolution of the test. Through the chain of section 3.2, 0.1 µs on the AMX unit moves the boost by about 2.1 points, so the 3-point band is ±0.14 µs (±5.3%) on a 2.66 µs unit. A calibration residual at the 5% gate of section 7 is worth 0 points if it is not transferred (variant a), 2.8 to 2.9 points if transferred multiplicatively (variant b), and 3.6 to 4.3 points if transferred additively (variant c: 5% of the 3.64 µs AVX unit is 6.5 to 7.2% of the 2.66 µs AMX unit). The two values in each pair are the two signs of the residual. That is why section 7 pre-registers the transfer rule and section 8 reports the estimate with a band.

2. Starting point: the model in one picture, and what it lacks

The Notion page "Estimate: the AMX decode boost from pre-AMX data" states the earlier model as follows. Only the line marked "faster" changes between the AVX and AMX builds.

token time   = other work (FPGA matmuls, norms, logits)   unchanged
             + attention

attention    = merge results + wait for slowest worker    unchanged
               (the "joins" and the "barrier")
             + page work

page work    = sum over units of
                 covered unit   (full 64-token page)  -> AMX cost
                 uncovered unit (partial tail page)   -> AVX cost

covered unit = QK matmul + PV matmul                      faster
             + softmax + running-state update             unchanged
               (the "common work")

What it lacks, in three points. Each was established on the Notion page from measurements.

  • No data-wait term. The AVX unit spends 3.48 µs in its two matmuls at prompt 8192. Only 0.55 to 1.64 µs of that is arithmetic (est., from instruction counts). The rest is the core waiting for 32 KiB of keys and values from DRAM. AMX replaces the arithmetic and leaves the wait in place.
  • No load dependence. The AMX unit was priced from a one-core benchmark of the whole page (1.80 µs). In serving, 27 cores stream at once and each gets less memory throughput than alone: the AMX matmuls alone took 2.35 µs.
  • Common work assumed equal. On the AMX path the common work doubled, from 0.16 to 0.31 µs per unit, because that code copies tile results out of scratch buffers before the state update. The earlier model kept 0.16.

3. The new model

The top three levels are kept. The unit level is rebuilt around a data-wait term. The common work is priced per code path. The small AMX-only per-token costs are made explicit.

token time   = other work                                           unchanged
             + attention

attention    = page work + joins + barrier + untimed scaffolding    joins, barrier, scaffolding unchanged (primary rule)

page work    = per-range overhead                                   the AVX residual below (unchanged)
             + AMX per-token extras (tile config, Q pack)           priced from Intel data (est.)
             + sum over units of
                 covered unit   (full page, 99.24%)  -> AMX unit
                 uncovered unit (partial page, 0.76%) -> AVX unit (3.64 µs, kill-switch run)

unit         = compute time  +  data wait                           THE NEW PART
               compute time  = the whole unit (QK + PV + the common work of that code path)
                               with all bytes already in L2, measured hot, scaled to the serving clock
               memory time   = bytes per unit / R_core(27)
                               (32 KiB / per-core streaming rate with 27 cores reading)
               data wait     = the part of memory time not hidden behind compute:
                               unit = max(compute, memory) + (1 - eta) * min(compute, memory)
                               eta  = overlap efficiency, 0 (serial) to 1 (perfect overlap)

3.1 Why this form

A core that streams a page issues loads ahead of the instructions that use them, so compute and memory transfer overlap partly. Two limits bracket the truth. With perfect overlap the unit takes the larger of the two times (the roofline rule). With no overlap it takes their sum. One number, eta, places the unit between the limits. It is measured: run the unit code hot in L2 (compute only), run it over a DRAM-resident working set with 27 cores (compute plus wait), and the difference against the memory time gives eta. The report uses eta to say what share of a unit is waiting; the primary estimate itself is described in section 8, rule 5.

The memory time is set by the per-core streaming rate under load, not by the socket's peak bandwidth. On this workload the memory controller counted about 101 GiB/s of DRAM reads on the kill-switch arm and 116 GiB/s on the arena-mirror arm, averaged over the token (perf-stat round 3 of 2026-09-01, sub-channel-0 counts corrected by 2.01; PR3879/make-sense-amx-vs-avx.html section 7.4). That is 18 to 20% of the socket's 614 GB/s pin peak. During page work the demand is higher: 27 workers × 32 KiB per 3.48 µs is 254 GB/s (est.), 41% of the pin peak, if every key and value byte comes from DRAM once per token. The limit is how many misses one core can keep outstanding and how long each takes while 26 other cores read; both move with load, so Rcore is measured as a curve over the number of readers (M1).

Estimate (AMX path):
  AMX unit        = compute_AMX (hot, including common_AMX) composed with the memory time   <- section 8, rule 5
  AVX unit        = 3.640                          <- kill-switch measurement (line above), for the 0.76% uncovered units
  page work_AMX   = 1440 x (0.9924 x AMX unit + 0.0076 x 3.640) + 70.8 + AMX per-token extras
  attention_AMX   = page work_AMX + 231.7 + 250.3 + 58.3
  token_AMX       = 3407.7 + attention_AMX
  boost           = 9260.0 / token_AMX - 1
  resolution      : d(token)/d(AMX unit) = 1440 x 0.9924 = 1429 µs per µs; 0.1 µs on the unit = about 2.1 points of boost

The same chain is run at prompts 2048 and 256 with their own baseline rows (attention share 32.1% and 16.0%, coverage 97.1% and 84.8%, AVX unit 2.80 and 2.88 µs). Those two are validation only; the exit test is the prompt-8192 number.

Why worker 0's count is used: Tron's planner cuts the page list by each worker's measured speed, so worker 0 does 1440 units while the average worker does 1386.7. Worker 0's page work plus its barrier wait equals the slowest worker's page work plus the fixed synchronization cost, which is what the attention time depends on. Keeping worker 0's units and worker 0's barrier together is therefore self-consistent; the report compares page work against joins plus barrier component by component so a cancellation between the two cannot pass unnoticed.

6. Measurements on delphi-3bda, after CI releases the machine

Tron runs only in its AVX form (M7, M8). Everything else is non-Tron software built on the machine from sources under exec/perf-model-20260903/src/. Results go to exec/results/perf-model-20260903/ with a header naming the date, the binaries' sha256, the CPU list, the lease state, the free 1 GiB pages and the page sizes actually obtained. Memory layout and access order

  • Canonical arena: blocks of 32 KiB (K plane 16 KiB then V plane 16 KiB), indexed block[(layer × 8 + head) × n_pages + page] as in kv_block(), so consecutive pages of one KV head are consecutive blocks. Backed by 1 GiB huge pages when the pool is free after CI, else by 2 MiB pages with the region aligned to 2 MiB. The size actually obtained is read back from the kernel and recorded.
  • K mirror arena: planes of 16 KiB, same index (mirror_at_storage), on 4 KiB pages, as in production.
  • Working set: prompt 8192 at the median decode pass has 130 pages per (layer, head): 36 × 8 × 130 × 32 KiB = 1170 MiB canonical plus 585 MiB mirror. Prompt 2048: 34 pages, 306 MiB. Prompt 256: 6 pages, 54 MiB. Hot mode: one page, which with the thread's buffers (about 37 KiB) sits in L2.
  • Assumption: one request's pages carry consecutive page numbers, so its pages of one head are adjacent in memory. The shuffled-order run of M3 measures what changes if they are not.
  • Assignment to threads: Tron's planner walks KV heads in order and pages in order and hands each worker a consecutive run whose work matches its share (finish_sw_plan), by measured worker speed. The benchmark uses equal speeds: each of 27 threads gets about 38.5 consecutive pages per layer, sometimes split across two heads. Because the shares differ from Tron's, only per-unit medians are compared with Tron; the benchmark's units per pass, pass time and barrier time are not.
  • Sequence: each thread runs its 36 layers in order with a spin barrier between layers (Tron has one attention operation per layer) for enough passes to time the median; per-unit times are recorded with rdtsc as the probe does. The state of every head is reset at each layer, as Tron resets it per operation.
  • Pinning: 27 threads on CPUs 24 to 35, 48 to 59 and 151 to 153; memory on NUMA node 0.
  • Correctness gates: before timing, each path is checked against a scalar reference that models the same bf16 rounding of the probabilities: running maximum and softmax sum within 1e-4 relative, normalized output within 1e-3 (a correct transcription measures about 1e-7).

Calibration before prediction. The AVX rows of M3 (27 threads, prompt-8192 working set) must reproduce Tron's AVX unit from M7 within 5% in either direction, with QK and PV each within 10%. The prompt-2048 and prompt-256 rows must reproduce their Tron values within 10%. If they do not, the model script marks the verdict "calibration failed" and the AMX numbers provisional, and the benchmark is fixed before any AMX number is read. The pre-registered order of that search is: a probe-off run (timer overhead), the shuffled page order, 2 MiB against 1 GiB pages, then the counters of M6.

How the residual is carried to the AMX side, fixed now. Let s = Tron AVX unit ÷ benchmark AVX unit. Three AMX units are computed and reported side by side. (a) No transfer: the benchmark's AMX unit as measured. (b) Multiplicative: the AMX unit × s, which assumes the residual scales with unit time. (c) Additive: the AMX unit plus the residual in microseconds, which assumes the residual is a per-unit cost common to both paths (both read the same 32 KiB). The primary uses (a) when |s − 1| ≤ 2%. Otherwise it uses (c) when more than 80% of the residual sits in QK plus PV and the common-work residual is within 10% of Tron's common work; in every other case, including a missing per-phase split, it uses (b). The model script records which rule fired and why. The band of section 8, rule 6 always spans all three.

8. Pre-registered modeling rules

  1. Joins, barrier and untimed scaffolding are unchanged (482 + 58 µs per token at prompt 8192). Sensitivity reported: if the barrier's imbalance part scales with the unit cost, the barrier drops in proportion to the AMX-to-AVX unit ratio; a second variant scales the joins too. The primary estimate uses "unchanged".
  2. Other work is unchanged (3407.7 µs). It runs on the FPGA cards and the main thread, which execute no AMX.
  3. The uncovered 0.76% of units cost the AVX unit (3.64 µs from M7). The per-range overhead (70.8 µs) is unchanged. The AMX per-token extras are added as worker 0's runs of pages per token (36, from the range counter) times the benchmark's measured cost per run; about 4 µs (est.).
  4. Compute time is scaled by clock: Tcomp(serving) = Tcomp(hot benchmark) × fhot ÷ fserving. fhot is the clock sampled on the hot run of the same configuration (27 threads). fserving is 3.74 GHz for the AVX path (measured on Tron) and fAMX from M4 for the AMX path. The memory time is not scaled by the core clock. A missing clock sample is reported as missing and the affected term labeled est.
  5. The primary AMX unit is the 27-thread DRAM-mode benchmark unit of the transcribed kernel, adjusted by the section 7 rule; compute, memory time and data wait are its decomposition. Compute means the whole hot unit including the common work; the roofline edge (eta = 1) is max(compute, memory), the serial edge (eta = 0) is their sum. Since the composed terms add up to the 27-thread reading by construction, the model's contribution is the decomposition, and the prediction rests on running the production kernel code outside Tron under decode-like load. If the 27-thread unit is shorter than max(compute, memory), the 64-byte-load rate is not the binding rate: the report prints eta as "above 1, memory rate not binding" and treats it as the trigger of refinement round 3 (section 9). A strict pre-AMX bracket is reported beside the primary: eta = 1 and eta = 0 with the hot AMX compute and the measured memory time, and the value the AVX-side eta would give. If the 27-thread AMX run could not be made, that bracket is the fallback and the report labels the result "bracketed, not measured under load".
  6. The estimate is a primary value with a band. The band is the union of: the three transfer variants of the calibration residual (section 7); the clock ±5% on the AMX compute part; the barrier sensitivities of rule 1. Every band edge is labeled with its source.
  7. Prompt 2048 and prompt 256 are validation rows, not part of the exit test; the report shows them with the measured gains (+6.1% and +0.5%).
  8. Every estimated number is labeled "est." with units; every measured number names its file.

9. Refinement rounds

Round 1 is the model of section 3 with rules 1 to 8. Two items that an earlier draft listed as rounds are already inside round 1 and are only reported: the common work of each path (the benchmark's AMX softmax and state timers are part of the primary unit) and the AMX clock (it enters the primary only through the per-token extras and sets the compute/wait split, the ±5% band edge and the fallback bracket). If round 1's primary value misses the 3-point band, the work continues in rounds. Each round adds one mechanism, in the order below, and must rest on a measurement from section 6 or on Tron's AVX-path data; no input is tuned toward +17.3%. Every round is kept whether it moves the estimate toward or away from the measurement. Rounds stop when the exit test is met or when the list is exhausted; the report then names the unexplained term and its size. The report records every round with the term it changed and the estimate before and after.

  1. Joins and barrier as imbalance. Fit J+B = a + b × page work (per token) by least squares to the three M7 prompts. The rule is accepted only if b ≥ 0 and every residual is within 10% of that prompt's J+B; it is then applied as J+BAMX = a + b × page workAMX. If rejected, rule 1 stands and the report shows the fit and its residuals. On the 2026-09-01 data the fit is 371.9 + 0.0227 × page work with residuals +17.0%, −14.2% and +2.2%, so it would be rejected at 10%; the fresh M7 data decide.
  2. Page order and page size. The shuffled-order and 2 MiB-page runs of M3, if the calibration residual points at memory placement (either run differs from its reference by more than 3%).
  3. L3 residency of recently written pages. Triggered by eta above 1 (rule 5) or by M6's L3-miss count per unit below 512 lines by more than 10%: a share of the 32 KiB is served from L3, and the memory time shrinks by that share.
  4. Worker-0 share. If the component comparison shows the page work and the barrier moving in opposite directions by more than 30 µs each, restate the chain on the slowest worker (page work + barrier together) and report both forms.

12. Risks and how each is handled

  • The AVX calibration fails (benchmark more than 5% from Tron's unit). Then the benchmark does not reproduce serving conditions and every AMX number from it is suspect. Action: the pre-registered search of section 7, then rerun. The report states the residual either way.
  • Serving comes up after CI and occupies the app cores. Action: the traffic check and stop of section 6, step 2; if traffic is present, wait.
  • Huge-page pool not free. Action: 2 MiB pages for the canonical arena; the 1 GiB-against-2 MiB run of M3 measures the difference directly instead of assuming it.
  • The memory-side numbers differ from the 2026 records (hardware change). Then M7's fresh baseline carries the change and the 2026-09-01 rows are reported as history.
  • The estimate misses by more than 3 points. Section 9 applies, round by round, until the exit test is met or a round finds no further mechanism supported by a measurement; in the second case the report names the unexplained term and its size.

14. Review record

Before any machine time, revision 1 of this plan and the benchmark sources went through an adversarial review: five reviewers with different lenses (fidelity to the production code, measurement method, model arithmetic, compliance with the brief and the writing rules, code defects), and two independent refuters per medium or high finding. Of 64 findings, 12 were confirmed, 8 were contested and 8 refuted; 36 were low. The confirmed and contested ones changed this revision as follows.

  • Exit test: the resolution statement and the band (section 1, section 8 rule 6).
  • Calibration residual: the three transfer variants and the selection rule (section 7).
  • Benchmark: Tron's exact exp constants; the running-max and sum gates in the correctness check; token ids by arithmetic instead of an array; the query loads kept alive on the AMX path; the separate sum pass; AVX timers grouped as Tron's common counter; 2 MiB-aligned regions and the obtained page size recorded; a fill-only control; RUN-START/RUN-END markers; the planner's one-step-per-page rule.
  • Instruction loops: distinct accumulator start values and 4/8/16 chains; reduction throughput and latency separated; the dotter's own per-token sequence added; one loop per run with its own clock sample.
  • Measurement method: instrumented runs lengthened to about 10 s; latency probe on 8 GiB with 1 GiB pages; the tile-load pattern described as the code has it (64 B stride, K-mirror panels).
  • Text: the DRAM-share figures replaced by this workload's own counts; "measured pre-AMX" replaced by the exact provenance; the 1440-unit explanation corrected (speed-weighted planner); about thirty terms added to Words; the Short version rewritten.
  • Refuted and left as they were: barrier "unchanged" as the primary rule (the AVX data alone do not support a proportional rule); the reference band; the clock sample (kept, with the deviation from the brief stated in section 4).

A second round (three lenses, one refuter per finding) reviewed this revision and the code together. Its 17 confirmed findings were applied before the campaign: the turbostat captures got iteration caps and a stop signal aimed at the right process; the clock-sampled hot runs were lengthened to at least 12 s and a missing clock sample is now reported, never replaced silently; the 1 GiB page pool is checked and stale huge-page files are removed before Tron starts; the sources are verified against a hash list before building; the correctness gate tests exit codes; the campaign can resume by stage; the instruction loops keep their accumulators in registers; the model script applies the calibration gate, records which transfer rule fired and flags eta outside 0 to 1; the plan text was aligned with the code on the unit formula, the selection rule, the resolution numbers, the compute-time definition, the per-token extras, the refinement rounds and the boundary of "pre-AMX" inputs.
