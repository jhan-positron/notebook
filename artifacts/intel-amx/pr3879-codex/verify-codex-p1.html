Finding self_attention.hpp:1358-1360 gates AMX on geometry only Codex confidence 0.99 Our verdict confirmed Method code trace · standalone harness · in-tree test at HEAD · 10-agent adversarial workflow (3 claims × 2 refuters, 0 refuted)
Bug confirmed

With TRON_AMX_DISPATCH, the host (fp32 Q) and host_fp16 executors of any 128-dim / GQA-4 model reach the AMX pack, which reads their Q bytes as bf16. Every dense 64-token page then gets wrong attention scores. Nothing crashes.

Codex's test demonstrates, does not pin

It compiles and fails on HEAD (0 == 16256, 15360 == 16256). But it calls the pack with the same reinterpret_cast as the buggy caller, so it keeps failing after either realistic fix. It must be replaced, not kept.

Fix gate, do not convert

Add "the executor's Q element is bf16" to the eligibility predicate and apply it at all three AMX gates (dispatch, mirror write-through, arena allocation). Converting fp32 Q to bf16 would change the host reference path's numerics.

landed 02208bebcf (gate) + 62bc343923 (tests) on jhan-amx-p0, 2026-08-28; AMX-host run queued on delphi-3bda (exec/p3-q-scalar-gate.sh). Work log: PR3879-codex/claude-report.md.

1 · What codex found

The gate checks shape and CPU, not what type Q is stored in

Codex's comment, verbatim: "When TRON_AMX_DISPATCH runs an eligible host/host_fp16 model … this geometry-only gate is true even though those executors store Q as float/fp16 (h/tron/models/common.hpp:96-98). The pack at lines 1424-1432 then reinterprets those bytes as bf16, corrupting every dense 64-token page (the float case also consumes only half of Q); gate on the query scalar or convert it to bf16 before packing."

Every line reference in the comment matches HEAD 609dabba: the gate is at 1358 and 1360, the two pack calls at 1424-1425 and 1429-1430, the executor aliases at common.hpp:96-98, and the llama_3_8b block starts at models.yaml:208. No earlier review round (alexey-review-1 … 6) raised this; the closest was a suggestion to type the kernel API as const bf16*, which would not have caught a reinterpret_cast.

Precision notes on the comment, none of which changes the verdict:

  • llama-3-8b-host is a runtime id, not a yaml slug: models.yaml:212-213 registers slug: llama-3-8b with executors: [host, tp1, tp2, tp4]; config/model_definitions.py:45-46 appends -host, and the build registers it at gen/…/model-definitions.i:360. The 32/8/128 geometry is in h/tron/plugins/llama.hpp:1535, not in the yaml.
  • "consumes only half of Q" is understated: the per-KV-head offset is halved too, so KV head k packs float heads 2k-2k+1 instead of 4k-4k+3 (section 2).
  • host_fp16 exists only in the experimental llama-3-8b-host-precision variant and is absent from a default --tags test build; the host half is in the default build.
  • The exposure is opt-in: TRON_AMX_DISPATCH defaults OFF, no CI or packaging configuration enables it, and the path runs only where amx_attn::available() is true.
  • The comment names one gate; the same geometry-only test is duplicated at self_attention.hpp:1499, model.hpp:2769-2771 (mirror write-through) and kv_cache.hpp:181-190 via full.hpp:1457 (arena allocation). The last two are cost-only for host models, but the fix must reach them (section 7).
  • The comment offers "gate or convert"; the test it ships encodes only "convert" and, as written, passes under neither (section 6).
2 · Mechanism

What the pack sees for the same value 1.0 in each executor

Attention then multiplies K rows against this misread Q group. For the fp32 case the group is [low16(q₀), trunc_bf16(q₀), low16(q₁), trunc_bf16(q₁), …] over 256 floats, so every dimension is misaligned and two of the four heads never contribute. The per-KV-head start offset kv_head * kv_mul * head_size (self_attention.hpp:1426, 1431) is added to a uint16_t*, so for KV head k the pack begins at float index 256·k instead of 512·k: only KV head 0 even reads its own heads. The result is wrong logits with no error, from the first fully populated 64-token page onward (partial pages still take the AVX loop).

6 · The regression test codex added

It proves the bug exists; it cannot prove the bug is fixed

The test (t/t_amx_numerics.cpp, uncommitted) fills a scalar_t q[512] with 1.0, calls pack_q_*_128x4(reinterpret_cast<const uint16_t*>(q), q_packed), and requires q_packed[0] == bf16(1.0), once for tron::host::btensor_t<512>::element (float) and once for tron::host_fp16::btensor_t<512>::element (fp16).

The assertion asks a const uint16_t* function to recover the value of a float it was never told about. No change to the dispatch code can make that true, because the test performs the reinterpret itself, one layer below the bug:

Smaller defects: the value 1.0 is exactly representable in bf16, so the check cannot tell round-to-nearest from truncation (a value such as 1.005859375f = 0x3f80c000 would: RNE 0x3f81, truncation 0x3f80); only q_packed[0] is inspected, so the "half of Q consumed" half of the finding is not pinned (column q_packed[2h] for h = 0..3 would show heads 2-3 holding heads 0-1's upper halves); REQUIRE(shape_ok(HD, NQ)) compares the header's constants with themselves; the title claims a contract ("preserves non-bf16 host queries") the pack never had. In CI the file compiles to its SUCCEED stub (no lane defines TRON_AMX_DISPATCH), so CI is untouched; in every AMX build the fake-labelled t_amx_numerics is red on HEAD and stays red after the fix.

What is good about it: the element types come from the executor aliases, so it tracks common.hpp rather than restating it; it needs no AMX hardware; it covers both pack variants under #ifdef TRON_AMX_K_MIRROR. Keep it as a negative control while working on the fix, then replace it with tests that encode the fixed behaviour:

7 · Recommended fix

Gate on the executor's Q element, at every place that decides AMX eligibility

Why gate rather than convert. Note [AMX attention dispatch] promises that both engines multiply bf16 inputs and differ only by fp32 add order and the PV rounding mode. For host the AVX QK is fp32 Q × bf16 K (dotter<float,128>, dotter.hpp:44-133): rounding Q to bf16 for AMX would add a third, undocumented difference on the executor that exists to be the fp32 reference (t_trace_passes_host, t_scheduler use llama-3-8b-host as ground truth). Excluding it costs nothing: the AMX work targets the bf16 production executors, which are unaffected. Two more reasons against converting: the refuter's harness measured one fp32 Q·K dot product change from 128.125 to 128.000 when Q is rounded to bf16 first (scratchpad/wf/refuter-c2/); and partial pages would still take the fp32 AVX loop, so one query's scores would mix two Q precisions across its pages.

Three gates share shape_ok today and must share the new condition too, or a host model would keep paying for a mirror it never reads: the K-mirror arena is kv_bytes/2 of RAM (maybe_allocate_mirror_arena, kv_cache.hpp:1050-1053) and the write-through runs on every save_k (model.hpp:2769-2771, 2789-2796).

11 · Glossary

Terms used above

executor
The tensor-type bundle a model is compiled with (common.hpp:93-98). tp1/tp2/tp4 = FPGA DMA tensors (bf16); host = plain CPU tensors (float); host_bf16 / host_fp16 = CPU with bf16 / fp16 activations. Runtime ids (config/model_definitions.py:41-52): llama-3-8b is tp1, llama-3-8b-host, llama-3-8b-host-fp16, llama-3-8b-tp2.
btensor_t
The executor's activation tensor template; its ::element is the scalar type of Q, K and V as produced by the layer.
Q group / GQA-4
The 4 query heads that share one KV head; 4 × 128 bf16 = 1024 bytes = one AMX tile operand.
pack
pack_q_rows_128x4 (mirror layout) or pack_q_group_128x4 (VNNI layout): copies the 512 bf16 lanes of a Q group into the 4 KB tile buffer.
shape_ok
head_size == 128 && kv_mul == 4, the one geometry the kernels serve.
dense page
A 64-token KV page that is full, fully visible to the query and inside the sliding window; only such pages take the AMX path.
K mirror / arena
A second, VNNI-interleaved copy of K in ordinary RAM (kv_bytes/2), written on every save_k, read only by the mirror-orientation AMX kernel.
