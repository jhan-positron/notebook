Tron KV Cache: Book, Page, Token, K, V

How Tron (Positron's inference engine) stores the key and value vectors of past tokens, and how the five words relate. Worked example: Qwen3-4B-Instruct-2507.

Short version
Tron keeps every past token's K and V vectors in a cache made of books, where a book is one contiguous block of memory divided into pages of 64 token slots. Each slot holds that token's K and V vectors for every layer and every KV head. For Qwen3-4B that is 144 KiB per token, 9 MiB per page, and 225 MiB for the default first book of 25 pages (all computed from the code's size formulas, not measured).

Glossary (plain words)

Tron
Positron's inference engine. The scheduler part that manages conversations and the KV cache is called alderaan in the code.
Token
One unit of text as the model sees it: an integer id from the tokenizer's vocabulary (Qwen3 has 151,936 ids). In Tron the id itself is stored in a token tree; what the KV cache stores for the token is its K and V vectors.
Layer
One of the repeated transformer blocks. Qwen3-4B has 36. Each layer has its own attention step and therefore its own K and V storage. Tron calls a layer's K/V storage index a layer slot (kv_slot_id in the code). A layer slot is not a token slot (one of the 64 positions in a page). For Qwen3-4B the layer slot number equals the layer number.
K and V (key and value)
Two vectors computed from each token at each layer. Later tokens compare their query against K to decide how much attention to pay, then read V. K and V are stored so they are never recomputed; that stored set is the KV cache. The third vector, Q (query), is used once and not stored.
KV head
One of the groups a layer's K and V are split into. For one token at one layer, a KV head holds one K vector and one V vector. Qwen3-4B has 8 KV heads and 32 query heads, so 4 query heads share each KV head (grouped-query attention). Background: Query Heads vs KV Heads.
head_dim (head_size in Tron)
The length of one K or V vector: 128 numbers for Qwen3-4B.
bf16
bfloat16, a 16-bit floating-point format. Every stored K or V number takes 2 bytes.
KV entry
Everything the cache holds for one token: its K and V vectors for all layers and all KV heads.
Token slot, offset, book entry number
A token slot is one of the 64 positions in a page. Its offset is its index inside the page, 0 to 63. The book entry number is the same slot counted across the whole book: entry number = page number × 64 + offset. The KV entry is the data stored in the slot.
RoPE (rotary position embedding)
The way Qwen3 encodes a token's position: pairs of numbers in q and k are rotated by an angle that depends on the position. It is applied to q and k, not to v.
Page
A fixed unit of 64 token slots. In Tron a page is a small bookkeeping object (which book it is in, where its tokens sit in the current batch, how many are in use); the K/V bytes themselves are in the book.
Book
The memory owner. A book allocates one contiguous block of DMA memory (DMA: direct memory access; memory that the FPGA, the programmable chip in Positron's hardware, can read without the CPU copying it) and a fixed number of pages. Every run of tokens in the token tree points at exactly one book; several runs can share a book.
Arena
The code's word (arena_data) for a book's single contiguous memory allocation. Every kv_block of the book is a piece of the arena.
kv_block
The smallest storage unit inside a book's memory: the K and V vectors of the 64 tokens of one page, for one KV head in one layer. 32 KiB for Qwen3-4B.
Attention worker
The thread that computes attention for one KV head over a range of pages (section 6).
Prompt chunk
The piece of a prompt that the scheduler admits in one step. Long prompts are split into chunks.
Token tree, edge, node
Tron stores all active conversations as one prefix tree of tokens. An edge is a run of consecutive tokens; a node is a point where conversations branch. Each edge carries a pointer to the book that stores its tokens' K/V and the entry number where they start.
Allocated, valid, live
Three states of a KV slot (from the code's Note [KV Token Lifetimes]). Allocated: a book exists that could hold it. Valid: a token in the tree occupies it. Live: the current forward pass reads or writes it. Live implies valid; valid implies allocated.
Forward pass
One run of the model over a batch of tokens: compute K and V for new tokens, run attention against the cache, produce logits.
KiB, MiB, GiB
Powers of 1024 bytes. Tron's log lines print "GB" but compute GiB (230 bytes); this page uses the binary units throughout.

1 · The five things in one picture

Read the figure top to bottom. A book contains pages. A page contains 64 token slots. A token slot holds one KV entry. A KV entry is a grid of K and V vectors, one pair per (layer, KV head).

Containment view for Qwen3-4B. Blue = structure (book, page, slot); orange = K vectors; teal = V vectors. The page row is drawn inside the book to show ownership; in memory, a page's 288 blocks are spread across the book's arena (section 5), not packed together.

One sentence each
  • Token: an integer id; the cache stores things about it, not the id.
  • K, V: two 128-number vectors per (layer, KV head) computed from the token; 288 pairs for Qwen3-4B.
  • Page: 64 consecutive token slots; the unit attention loops over.
  • Book: the object that owns the memory for a fixed set of pages. Every edge points at exactly one book; several edges can share a book.

2 · Token: one word piece, five integers

In Tron the word "token" names the vocabulary id. The id lives in the token tree, in a per-edge list (token_info.token). During a forward pass the scheduler copies the ids of all context tokens into a flat array tokens[]. The cache never stores the id; it stores the token's K and V.

To find where a token's K and V are, Tron uses the book entry number. Every edge records which book it uses (kv_book) and the entry number of its first token (kv_first_entry_nr). Token i of the edge is at entry kv_first_entry_nr + i, and the entry number decides the page and the slot:

page   = kv_book->page_of(entry)      // = pages[entry / 64]
offset = entry % 64                     // slot inside that page

Addressing example (numbers constructed for arithmetic clarity). Gray = the parent edge's tokens, blue = this edge's tokens. Edge boundaries and page boundaries are independent: one page may hold tokens of several edges, and one edge may span several pages.

So one token carries several different integers. Keeping them apart avoids most confusion when reading the code:

3 · K and V: what is stored for one token

At each layer, the model turns the token's hidden state (a vector of 2,560 numbers for Qwen3-4B) into three kinds of vectors by matrix multiplication. Q (query) is used immediately and discarded. K (key) and V (value) are written into the token's slot so that every later token can attend to this one without recomputing them.

What one token contributes to the cache at one layer. Dashed blue = computed and dropped (Q); solid orange and teal = written into the token's page slot (K and V). The same happens in each of the 36 layers: layer ℓ writes into the block for (layer slot ℓ, head, page), row o, so one token slot holds 36 layer slots' worth of K and V.

Two facts about this storage matter for everything below:

  • K and V are per KV head, not per query head. Qwen3-4B has 32 query heads but stores only 8 K and 8 V vectors per layer. During attention the 4 query heads of a group all read the same K and V (grouped-query attention; kv_mul = 32 / 8 = 4 in the code).
  • Each layer has its own K and V. The 36 layers write into 36 separate layer slots. So one token's KV entry is 36 × 8 = 288 K/V pairs.

Grouped-query attention in Qwen3-4B, one layer. Query heads 4c..4c+3 share KV head c. The cache holds only the bottom row.

4 · Page: 64 slots and a live count

A page is Tron's fixed unit of 64 consecutive token slots (page_size = 64). Attention kernels loop over pages, and inside a page over slots. The page struct itself holds no K or V bytes. Its data members are:

MemberWhat it is
bookReference to the one book that owns this page. A page never changes book.
loThe pass-local index (token_id) of slot 0 in the current forward pass. Set by the tree walk each pass; slot o has token_id = lo + o.
offset_bound, read as count()How many slots, counting from 0, are live in this pass. The attention loop visits slots [0, count()) only.
kv_saves_One small counter per (slot, layer): 0, 1, or 2 = how many of {K, V} have been written this pass. Used to tell when a token's K/V for a layer are both complete.

A page finds its own number by pointer arithmetic against the book's page array (pageno()), and reaches its K/V bytes by asking the book: book.kv_block(layer_slot, kv_head, pageno()). So "the page's K for token o" is really "the book's block for (layer, head, page), row o".

Capacity vs valid vs live, in one page
A page always has 64 slots (capacity). The book's counter tok_ct says how many entries of the whole book are valid (occupied by tokens in the tree). The valid entries are always entries 0 to tok_ct − 1: new tokens take the next entry number, and removed tokens give back entries from the end (last in, first out). count() says how many of the page's slots are live in this particular pass. Pages before the last page of a conversation are usually fully live (count = 64). The last page is partly filled. A page whose later slots belong to a branch that is not being computed this pass is also partly live.

4b · Inside a kv_block: K rows and V pairs

The kv_block is the 32 KiB unit that a page's accessors point into: K and V for the 64 tokens of one page, for one KV head in one layer slot. K and V are laid out differently inside it.

  • K: one row per token. Row p holds token p's 128 bf16 values in order, 256 B, as 8 chunks of 16 values (32 B each). The Q·K step reads one row as four 64 B loads.
  • V: one row per token pair. Under AVX-512 (Intel's 512-bit vector instructions, the normal build) row j holds tokens 2j and 2j+1 together, 512 B, as 8 tiles of 64 B. Inside a tile, each 32-bit lane holds one dimension of both tokens: the even token in the low 16 bits, the odd token in the high 16 bits.

One kv_block for Qwen3-4B, drawn to structure (not to byte scale). Orange = K, one row per token. Teal = V, one row per token pair; the dark teal tile is expanded into its 16 lanes. Sizes come from the code's static assert: 2 × 64 × 128 × 2 B = 32,768 B.

The reason for the V layout is the P·V step of attention, which multiplies every cached V row by a softmax weight and sums them. With two tokens in each 32-bit lane, one _mm512_dpbf16_ps instruction multiplies both tokens of a pair by their two weights and adds them, for 16 dimensions at once. The K layout stays one row per token because the Q·K step needs one dot product per token.

Four rules follow from the pair layout:

  • A page's even and odd offsets are written by the same thread. The scheduler adjusts minibatch boundaries so a pair is never split between threads.
  • Every write of an even token zeroes its odd partner's half. When a page has an odd live count, the read rounds up to the pair and touches one padding slot; the zero keeps NaN out, because NaN × 0 = NaN in IEEE 754.
  • The page size must be a multiple of the vector chunk size, 16 bf16 values under AVX-512. 64 is.
  • Copying tokens between pages copies K with one memcpy per head but must copy V one token at a time, to keep the pairs right.

The AVX2 build (chunk size 8, used only when AVX-512 is unavailable) stores V exactly like K, one row per token. Byte sizes are the same in both builds.

5 · Book: the memory owner

A book is the object that owns KV memory. When a book is created it allocates one contiguous DMA arena (memory the FPGA can read directly) sized for a fixed number of pages, plus a vector of that many page objects. Nothing about its size changes afterwards; when the cache needs more room, the scheduler creates another book.

5a · How the arena is laid out

The arena is an array of kv_blocks. One block holds K and V for the 64 tokens of one page, for one KV head in one layer: 64 × 128 × 2 B = 16 KiB of K followed by 16 KiB of V, 32 KiB in total. The block for (layer slot s, KV head h, page p) is at index:

(s × n_kv_heads + h) × n_pages + p        // layer outermost, page innermost

Page is the fastest-varying index. That has a consequence worth stating plainly: the 9 MiB that belong to one page are not one contiguous region. They are 288 separate 32 KiB blocks spread through the arena. What is contiguous is one (layer, head) across all pages of the book, which is the order the attention worker (the thread that computes attention for one KV head; section 6) reads them in.

Memory order inside one book. The arena is one allocation; the picture is drawn to structure, not to byte scale.

5b · How big a book is, and how many there are

  • Sizing is the scheduler's decision, not the book's. A request for N tokens needs ⌈N / 64⌉ pages. The first book of a conversation is sized by policy to TRON_BOOK_INITIAL_TOKENS (default 1,600 tokens = 25 pages), clamped to TRON_BOOK_MAX_TOKENS, or more if the prompt chunk (the piece of a prompt the scheduler admits in one step) needs more pages. A book that continues a sequence that ran out of room is sized to the previous book's capacity times TRON_BOOK_GROWTH_FACTOR (default 2.0), capped by TRON_BOOK_MAX_TOKENS (default 1,600). A book that starts a new branch gets 1 page, except when the branch point is the node directly below the root (the end of the first edge, typically just the first token once prompts diverge there); that book gets the initial size again because the code assumes a large user prompt follows.
  • Hard cap: one book must fit one DMA allocation, which is 1 GiB. For Qwen3-4B that is ⌊230 / 9,437,184⌋ = 113 pages = 7,232 tokens. A longer prompt chunk is split across several books, linked as a chain of edges.
  • Every edge points at one book, but one book can serve several edges. When a conversation is split at a shared prefix (a second user sends the same prompt), both halves keep the original book, the second half simply starting at a later entry number. When more tokens are added to a leaf, they stay in the same book only if the whole chunk fits in the book's remaining capacity; the scheduler then appends them to the leaf's own edge or, if a listener (a request waiting for that leaf's next logits) is pending, creates a child edge that starts at the next entry number. If the chunk does not fit, a new book is allocated for the entire chunk and the old book's remaining slots stay unused.
  • Lifetime. Every edge holds a shared pointer to its book; the book and its arena are freed when the last such edge is destroyed by cache eviction. Because the book is the only copy of those K/V values, freeing it means the prefix must be recomputed if it is needed again. Copies of K and V that the FPGA reads for hardware attention, GOF blocks (GOF: group of four, a 4-token unit of K and V for one layer in the FPGA's layout) and 1,024-token shards, can be rebuilt from the book.

6 · How they connect at run time

One forward pass ties the five together in three steps.

Where each concept appears: the walk produces tokens and pages; the model writes K and V into page slots inside books; the attention loop reads K and V page by page. Step 3 can start on "ready" pages before step 2 finishes the "pending" ones.

Inputs from the model's config.json: 36 layers, 32 query heads, 8 KV heads, head_dim 128. K and V are stored as bf16 (2 B per number) because Tron's kv_block element type is bf16, independent of the weight format (the default served weights for this model are GPTQ-quantized). Reading the numbers
  • 144 KiB per token equals the per-token formula in doc/memory_pressure_governor.md, 4 × n_layers × n_kv_heads × head_size bytes: the factor 4 is "K and V" (2) times "bytes per bf16" (2).
  • Growth by policy stops at 25 pages (the 1,600-token cap), so books larger than 225 MiB appear only when one prompt chunk itself needs more pages, up to the 113-page DMA limit.
  • The allocator rounds each book up to a power-of-two size class: a 25-page book (225 MiB) occupies one 256 MiB size-class slot (the allocator's word; not a token slot or a layer slot). Four such slots fit in one 1 GiB hugepage (an operating-system memory page of 1 GiB, unrelated to Tron's 64-token page). This is allocator accounting, not book content.

8 · Things that are easy to get wrong

  • A page's bytes are not contiguous. The page object is a view; its 288 blocks are strided through the arena by page index (section 5). One (layer, head) across pages is contiguous.
  • The token id is not in the cache. Books store K and V only. Ids live in the token tree and are copied into tokens[] each pass.
  • Q is never stored. Only K and V are saved; Q lives in a per-pass buffer.
  • Two different "pages". The software page described here is 64 tokens. The hardware attention path uses its own units: a hardware page of 128 tokens, a 4-token GOF (group of four) block, and a 1,024-token shard. Those are copies built from the book, not the book. A hugepage is a third thing: an operating-system memory page of 1 GiB from which Tron's allocator carves books.
  • Two different "slots". A token slot is one of the 64 positions in a page. A layer slot (kv_slot_id) is a layer's K/V storage index inside the book; for Qwen3-4B it equals the layer number. A size-class slot is the memory allocator's word for the fixed-size region a book occupies (section 7).
  • kv_ready is set early. The walk marks a token's kv_ready true when it schedules the KV job, not when the K and V bytes have been written. Actual completion per layer is tracked by the page's kv_saves_ counters.
  • Valid is not live. A book's tok_ct counts valid entries (occupied by tree tokens). A page's count() counts entries live in this pass. Valid entries may still hold garbage if their K/V have not been computed yet.
  • "GB" in Tron logs is GiB. The KV footprint log divides bytes by 230 and prints "GB"; the cache size target multiplies the configured "GB" count by 230. Both treat GB as GiB.
  • EAGLE storage is separate. Generated plugins (the per-model C++ code that Tron's ingestion step emits) declare 5,120 B per token of embedding storage (x_bytes) for EAGLE, a speculative-decoding method in which a small draft model proposes several tokens that the main model checks in one pass. That buffer is allocated only when such a draft model is attached. With an EAGLE draft attached the book also carries one extra KV layer slot per page (256 KiB for Qwen3-4B, so 9.25 MiB per page) and the 1 GiB cap drops to 110 pages. Neither is counted in the numbers above.
  • An older design note is stale. doc/attention-scheduling.md section 2.2 describes a per-page hi[] array; the page struct has no such member. Which context tokens each query may attend to is decided by the ranged mask (Tron's attention-mask structure, which stores the allowed token indices as ranges).
