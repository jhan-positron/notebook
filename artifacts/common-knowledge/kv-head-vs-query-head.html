Query Heads vs KV Heads

Why modern LLMs have more query heads than key/value heads, and why the KV-head count is the number that decides inference memory cost.

Glossary (plain words)

Attention head
One independent "looker". Each head compares the current token against all previous tokens and pulls in information from the ones it scores highly. A layer runs many heads in parallel, each looking for different patterns.
Q, K, V (query, key, value)
Three vectors made from each token. Query: "what am I looking for?" Key: "what do I contain?" (used for matching). Value: the actual information handed over when a match scores highly.
Query head
One question the current token asks about the earlier context. A model with 32 query heads asks 32 different questions at once for every token — for example, one head may in effect ask "which earlier noun does this word refer to?", another "what was the most recent number?". Each question produces its own answer (that head's output in the diagram below). Count in config files: num_attention_heads.
KV head
A stored K-and-V pair set. Several query heads can share one KV head. Count in config files: num_key_value_heads.
KV cache
During generation, the K and V vectors of every past token are kept in GPU memory so they are not recomputed. Its size grows with context length and is proportional to the KV-head count, not the query-head count.
MHA / GQA / MQA
Multi-Head Attention (1 KV head per query head), Grouped-Query Attention (one KV head per group of query heads), Multi-Query Attention (one KV head shared by all query heads). Naming note: the "multi" in MHA contrasts with the original single-head attention (one attention computation over the whole hidden vector), not with MQA — "multi-head" meant many heads, each with its own Q, K, and V (Vaswani et al. 2017, before separate query-head/KV-head counts existed). MQA (Shazeer 2019) then picked "multi-query" to say only the queries stay per-head. Read the trio as: everything per-head / queries per-head + KV per-group / queries per-head + one shared KV.

1 · The token axis: one head reading a 3-token cache (worked example)

One query head, one new token, three cached tokens — everything in this section uses a SINGLE KV head; we walk along the token axis. In matrix form the whole read is two small products. The keys of the 3 past tokens stack as the rows of K (3×128); the values stack as the rows of V (3×128). The new token's query q (1×128) is scored against every row of K at once, and the softmaxed scores mix the rows of V:

Matrix view: one query head reading a 3-token cache. Blue = query side (computed this step, then discarded), orange = cached K/V (stored rows, one per past token). Real models also divide the scores by √head_dim = √128 before the softmax; the example numbers assume that division has already been applied.

Where the “3” comes from — and why it is not in config.json
3 is the number of past tokens stored in the KV cache at this decode step — the sequence length so far, not counting the new token. It grows by one with every generated token, so it is runtime state, not an architecture parameter: no weight matrix has a dimension of size 3, and config.json has no entry for it. The config stores only the fixed sizes — max_position_embeddings (8192 for Llama-3-8B, the upper limit the cache can grow to), num_attention_heads, num_key_value_heads, hidden_size. head_dim = 128 is not a stored key either; it is derived as hidden_size / num_attention_heads = 4096 / 32. One simplification in the diagram: in a real decode step the new token's own K and V are appended to the cache first and its query also scores against itself, so the score row would be 1×4; the example keeps only the 3 past tokens.

The same computation unrolled token by token — each q·kᵢ arrow below is one 1×1 cell of the score row above, and the weighted sum on the right is the w·V product:

One query head attending over a 3-token KV cache. softmax([2.0, 0.5, 1.0]) ≈ [0.63, 0.14, 0.23]. Blue = query side, orange = cached K/V. Numbers constructed for arithmetic clarity. This is the dashed slice of the cache grid drawn at the start of section 2: one KV head (one row), three tokens.

The orange boxes (K and V of every past token) are what the KV cache stores. The two head counts can differ because Q and K/V play different roles and have different lifetimes:

  • The math does not require a private K/V per query head. A query head's output is distinct because its query vector is distinct: two query heads can score against the same keys and still attend to different tokens, since different q vectors give different scores, different softmax weights, and therefore different weighted sums of the same values. So several query heads can share one KV head without collapsing into one head.
  • Only K and V are stored; Q is transient. The query vector is used once, at the step its token is generated, then discarded. K and V stay in GPU memory for every later token of the sequence. The query-head count therefore costs only compute at that one step, while the KV-head count is paid in memory again for every cached token.

Sharing K/V across query heads (next section) exploits both facts: keep many query heads because they are cheap and carry quality, cut KV heads because they are what the cache is made of.

2 · The head axis: mapping query heads → KV heads

Sections 1 and 2 draw two different axes of the same object. Per layer, the KV cache is a grid: one ROW per KV head, one COLUMN per token. Section 1 showed one row across three columns. This section counts rows, and asks how query heads map onto them.

The section-1 diagrams walk along one row (token axis); the mapping diagram below counts rows (head axis) with the token axis hidden inside each orange box.

Common question: within one column (one token), are the 8 (K,V) pairs identical copies?
No. Each KV head has its own learned projection — its own 128-column slice of WK and WV (section 5's table: 4096 × (8×128); the 8 slices are 8 different learned matrices). The same token vector is multiplied by 8 different matrices, giving 8 different K vectors and 8 different V vectors: 8 distinct learned descriptions of one token, not 8 copies. Tiny example (2 dims, 2 KV heads): token vector x = [1, 2]; head 0's W_K = [[1,0],[0,1]] → key [1, 2]; head 1's W_K = [[0,1],[1,0]] → key [2, 1]. Same token, different keys. In effect each KV head stores a different aspect of the token — one head's key may act like "this word's grammar role", another's like "this word's topic" — so the query heads grouped on that KV head can match on the aspect they need (real heads are learned and only sometimes this interpretable). This is also the honest reading of GQA's memory saving: it cuts the number of distinct per-token descriptions from 32 to 8; it does not remove duplicates, because there never were any.

In MHA every query head has its own K and V. GQA lets a group of query heads share one K/V pair; MQA is the extreme where all query heads share one. The query heads stay fully independent — each still computes its own scores and its own weighted sum — they just read the same cached K/V.

Schematic: 8 query heads shown per panel for readability. The GQA ratio drawn (4 query heads per KV head) is the same ratio Llama-3-8B ships (32 query heads : 8 KV heads). Each orange box is one ROW of the cache grid above (all tokens); "1 : 1" means each query head reads one row, never one token. Every query head reads exactly ONE row in all three schemes — what varies is how many query heads share a row.

3 · Where q, k, v come from: the projection matrices (toy example)

Inside a layer, each token is one long hidden vector x — in Llama-3-8B, 4096 numbers holding everything the model currently represents about that token. A projection matrix is a learned extractor: each of its output dimensions is one weighted sum over x — in effect one learned question about the token — so multiplying x by the matrix answers all of a head's questions at once and yields a short vector (128 numbers per head). The three matrices extract three different things:

  • WQ (one slice per query head): "what is this token looking for?" → q
  • WK (one slice per KV head): "what does this token advertise about itself?" → k, stored in the cache
  • WV (one slice per KV head): "what does this token hand over when a query matches it?" → v, stored in the cache

Toy setup: pretend the hidden vector has only 4 dims with human-readable meanings [noun-ness, verb-ness, food-ness, place-ness], and two KV heads whose extractors keep different pairs of dims — a "grammar" head and a "topic" head. Two cached tokens: apple = [0.9, 0.0, 0.8, 0.1] and bake = [0.1, 0.9, 0.7, 0.0].

One token's hidden vector pushed through two KV heads' WK extractors. Applying the same two extractors to "apple" gives keys [0.9, 0.0] (grammar) and [0.8, 0.1] (topic).

Now the query side, drawn the same way. A new token "flour" arrives with hidden vector [noun 1.0, verb 0.0, food 1.0, place 0.0]. Say query head 2 belongs to group 0 (which reads the "grammar" KV head) and query head 5 to group 1 (which reads the "topic" KV head). Each extracts its own question from the SAME flour vector via its own WQ slice. One difference from the KV side is worth noticing: the toy WK only kept dims, but WQ can rewire — "I am a noun" becomes "I am seeking a verb":

Same sentence, two heads, two different matches — because WQ decided what each head asks and WK decided what each cached token advertises. WV is the third extractor: once the grammar head matches "bake", it does not receive bake's whole 4096-dim vector — it receives v = Wₛ·x, the slice the V extractor selected as the useful payload (for a grammar head, in effect things like "this is an action, it takes an object").

Zooming out from the toy to the real matrices: a "head" IS a slice of a weight matrix. Each query head owns one 128-column slice of WQ; each KV head owns one 128-column slice of WK and one of WV. The whole matrices are these slices laid side by side:

Weight-space view: a head IS one 128-column slice of a projection matrix. GQA in weight space = 4 WQ slices per one WK/WV slice. The toy diagrams above each showed a single slice, shrunk to 4 dims in and 2 out.

3b · The three matrices with every slice named (teaching props)

The figure above showed the slices as unlabeled blocks. Below, the same three matrices are drawn with a made-up specialty written on every slice, in the spirit of the toy — pretend the model learned one slice per topic. Two axes to keep straight:

  • Rows of WQ, WK, WV are the 4096 dims of the incoming hidden vector x (the toy's noun-ness, verb-ness, food-ness, place-ness, …). They are not tokens; every token goes through the same rows. Tokens are the rows of the activation matrix X — see the last strip in this subsection.
  • Columns come in slices of 128. WQ has 32 slices (one per query head); WK and WV have 8 each (one per KV head). Query heads 4g…4g+3 read KV head g, so a WQ group of four slices sits over one WK/WV slice.

Honesty caveat
The named dims, the 0/1 extractors, and the head labels are teaching props. Real hidden dims are unlabeled; WQ/WK/WV are dense matrices learned by training; head specialties emerge on their own and are only sometimes this interpretable. The slice structure in the last figure is exactly true, and section 5's table is those shapes in table form.

4 · Grouped-query attention: inside one group

"Grouped-query" means the query heads are split into equal groups and each group is assigned one KV head. In Llama-3-8B: 32 query heads → 8 groups of 4, and group g uses KV head g. Inside a group, every query head runs the full section-1 computation against the same cached K and V — only the query vector differs from head to head.

Worked example: the same 3-token cache as section 1, two query heads from the same group. They see identical keys and values, but ask different questions:

scores q·k₁, q·k₂, q·k₃ softmax weightshead output
query head A2.0, 0.5, 1.0 0.63, 0.14, 0.23 0.63v₁ + 0.14v₂ + 0.23v₃
query head B0.0, 2.0, 1.0 0.09, 0.67, 0.24 0.09v₁ + 0.67v₂ + 0.24v₃

Head A's output is mostly v₁; head B's is mostly v₂. Same keys, same values, different query → different weights → different output. This is why sharing K/V does not collapse a group into one head: a head's identity lives in its query vector, and each head in the group keeps its own.

The group is also where the decode-time hardware win comes from: the group's one KV cache page is read from GPU memory once and reused by all 4 query heads, so GQA performs 4× more attention arithmetic per byte of KV cache read than MHA with the same query-head count.

5 · Real config numbers (Llama-3-8B)

From the published config.json of Meta-Llama-3-8B: num_attention_heads = 32, num_key_value_heads = 8, hidden_size = 4096, head_dim = 128 (derived: hidden_size / num_attention_heads; not a stored key), num_hidden_layers = 32. Group size = 32 / 8 = 4 query heads per KV head; query head h uses KV head floor(h / 4) (heads 0–3 → KV 0, heads 4–7 → KV 1, …, heads 28–31 → KV 7).

7 · Why KV heads decide inference memory

KV cache size per token = 2 (K and V) × layers × kv_heads × head_dim × bytes. For Llama-3-8B in bf16 (2 bytes): 2 × 32 × 8 × 128 × 2 B = 128 KiB per token. The same model with MHA (32 KV heads) would need 512 KiB per token. Over an 8192-token sequence:

Only the KV-head count changes between bars; query heads (32), layers (32), and head_dim (128) are held fixed. MHA and MQA rows are hypothetical variants of the same geometry; GQA is the shipped config.

This matters most during decode: to generate each new token, the GPU reads the entire KV cache from memory, and decode throughput is usually bound by that memory traffic rather than by arithmetic. Cutting KV heads 32 → 8 cuts both the cache footprint and the bytes read per generated token by 4×, and lets 4× more sequences fit in the same GPU memory for batching.

8 · The trade-off

  • Query heads carry the diversity. Each query head still asks its own question and produces its own output; sharing K/V only forces heads in a group to match against the same stored descriptions.
  • Quality evidence: the GQA paper (Ainslie et al., EMNLP 2023, arXiv:2305.13245) reports GQA with 8 KV heads reaching quality close to full MHA on T5 summarization/QA benchmarks, while MQA (1 KV head) loses measurably more. That result is why 8 KV heads became the common choice (Llama 3, Mistral).
  • MQA origin: Shazeer 2019, "Fast Transformer Decoding: One Write-Head is All You Need" (arXiv:1911.02150) — the first statement that decode is memory-bound on K/V and that one shared KV head fixes it.
  • Parameter side effect: WK/WV shrink with the KV-head count (table in section 5), but this is minor next to the KV-cache and bandwidth savings, which scale with context length.
One-line summary
Query heads = how many different questions each token asks (compute-side, fixed per token). KV heads = how many K/V pairs per token are stored in the cache (memory-side, paid again for every token of context). GQA keeps many query heads for quality and few KV heads for memory: Llama-3-8B uses 32 : 8, making its KV cache 4× smaller than MHA at no architecture cost elsewhere.
