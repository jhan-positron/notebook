Architecture investigation · PR #3879

One K layout for AMX and AVX

Yes, a single persistent CPU K in the mirror’s swizzled format is technically viable. It needs a storage-interface migration and a native AVX reader; its performance still needs production validation.

Recommendation

Bill is right about the instruction-level issue. The swizzled K layout naturally supports vector lanes that each represent a token. A 64-byte K load supplies two dimensions for 16 tokens; broadcasting the corresponding query pair lets AVX-512 BF16 accumulate 16 scores directly. The existing per-token dotter cannot use that layout unchanged, but a pagewise AVX kernel can.

The current FPGA path also permits this change: it already converts CPU cache data into separate GOF staging before DMA. Adapt that conversion and retain the device’s existing K format. There is no demonstrated requirement for a persistent canonical CPU K copy in either consumer. dotter.hpp:213; gof.cpp:135.

FeasibleOne durable CPU K serves AMX, AVX, and the input to FPGA staging.
−⅓ KV payloadThree allocated planes become two for mirrored slots. The existing hugepage capacity stays the same.
UnmeasuredProduction latency after the full migration, especially tails, stores, copies and FPGA staging.

Recommended direction: build a separately selectable single-K implementation for head-128 slots, with direct packing into existing GOF staging and an early measured GOF-cost gate, retaining canonical storage as a process-start rollback during validation. Keep the current AMX kernel and V layout. The mirror remains a defensible way to limit the scope of PR #3879, but its justification should be migration cost and measured risk, rather than an assertion that AVX or the FPGA requires canonical CPU K.

The two VNNI encodings have different panel orders

Both put a dimension pair from each token into one 32-bit lane, but their page-wide ordering differs. For head-128, Bill’s older format is [token block][dimension block][pair][token][2]; PR3879’s mirror is [dimension block][token block][pair][token][2]. The two outer axes are exchanged. PR2934 amx_kv_layout.hpp:48; kv_cache.hpp:640.

// BF16 element offsets, p = token, d = dimension, P=64 and D=128.
Bill:   (p/16)*128*16 + (d/2)*32 + (p%16)*2 + d%2
PR3879: ((((d/32*4 + p/16)*16 + (d%32)/2)*16 + p%16)*2 + d%2)

Example K[0][32]: Bill offset = 512; PR3879 offset = 2048.

Therefore the PDF’s simple pair-stride source expression must not be pasted into a PR3879 shuffle with one token-tile base. Pass the page base, token offset, geometry and encoding—or a typed equivalent—and apply the complete current offset function. Retaining PR3879’s format also retains its existing AMX panel offsets. Choosing Bill’s outer order instead would require updating the AMX reader too. PDF p. 8; amx_attn.cpp:249.

A new scalar address check confirmed that both formulas are bijections over 8,192 values, but 6,144 logical values have different physical offsets. Composing either correct decoder with the existing H=128 HBM permutation gave identical logical staging rows for all 64 tokens. This checks address algebra only; it does not execute the production shuffle or measure GOF latency. Check source; result.

Direct GOF packing is the right target; negligible cost is unproven

I adopt Bill’s preferred production design: change the source reads of the existing shuffle and write directly into the current GOF staging destination. There is no need for an additional contiguous K staging buffer. An unpack-then-old-shuffle path is useful as a test oracle or reference fallback, rather than the production target. Bill’s own step 3 makes a measured gof_populate comparison an early gate. PDF pp. 8–10.

The operation count alone does not make the conversion free. A head-128 token spans four canonical cache lines, versus 64 swizzled lines. Four GOF tokens share those 64 lines only when their physical source placement permits it; cross-book or different token-block sources may touch more. A just-written row may be hot, but later backfill, staging reconstruction after eviction, and execution on another worker do not inherit that assumption. Even L1 hits leave load-uop and vectorization costs to measure. The report therefore retains an explicit first-fill, cold-rebuild and cross-book GOF performance gate. PDF p. 10; gof.cpp:140; gof.cpp:193.

The exact layout and why AVX fits

Let K[p][d] be the BF16 key at token p and dimension d. A page has 64 tokens and the current fast path has 128 dimensions. The mirror is a permutation of the same 8,192 BF16 values, occupying 16 KiB. Its shape is [4 dimension blocks][4 token blocks][16 dimension pairs][16 tokens][2]. kv_cache.hpp:640.

s = d / 32;  c = p / 16;  dp = (d % 32) / 2;
t = p % 16;  j = d % 2;                 // integer division

offset(p, d) = ((((s * 4 + c) * 16 + dp) * 16 + t) * 2 + j)
swizzled[offset(p, d)] = K[p][d]         // offset in BF16 elements

// Fixed s, c, dp: exactly one 64-byte vector row
[K[16c+0][2r], K[16c+0][2r+1], ...,
 K[16c+15][2r], K[16c+15][2r+1]]         // r = 16s + dp
p=17, d=34 → BF16 offset 2594; byte offset 5188. SIMD lane 1 of token block 1.

Each box is a 32-bit pair from one token. AVX accumulates along dimensions while the lanes stay on tokens.

Native AVX-512 BF16 QK

For each 16-token block, keep one score vector per query head. Load one pair row, reuse it across the query heads, and broadcast each head’s two query values as one 32-bit word. After the 64 dimension pairs, each vector contains 16 final dot products. The following is explanatory pseudocode for one query head; the retained prototype implements the checks and masks.

for (int c = 0; c < 4; ++c) {
  mask16 active = visibility_mask[c];
  if (!active) continue;
  vec16f acc = zero();
  for (int s = 0; s < 4; ++s) {
    for (int dp = 0; dp < 16; ++dp) {
      auto* row = K + ((s * 4 + c) * 16 + dp) * 32;
      vec32bf16 k_pair = masked_load_16_dwords(row, active);
      uint32_t q_pair = load_pair_bits(Q + s * 32 + 2 * dp);
      acc = dpbf16(acc, broadcast_dword(q_pair), k_pair);
    }
  }
  masked_store(S + 16 * c, active, acc); // all other S slots stay -infinity
}

VDPBF16PS adds an adjacent BF16 pair product into each FP32 lane. This is AVX-512 BF16, a specific CPU feature; generic AVX support alone does not provide it. The current Tron BF16 dotter already uses this instruction. Intel SDM, VDPBF16PS; dotter.hpp:218.

AVX2/FMA and non-BF16 queries

The layout does not require a BF16 dot instruction. Load eight packed pairs with AVX2, or sixteen with AVX-512, and split each dword into exact FP32 encodings:

K_even_fp32 = bitcast_float(pair_bits << 16);
K_odd_fp32  = bitcast_float(pair_bits & 0xffff0000);
acc = fma(K_even_fp32, broadcast(Q_even_fp32), acc);
acc = fma(K_odd_fp32,  broadcast(Q_odd_fp32),  acc);

This performs no rounding when widening stored BF16 K. FP32 queries can remain FP32; FP16 queries can be widened to FP32. Do not reinterpret either as BF16 or downcast Q simply to enter the BF16 kernel. The K cache is BF16 even when the executor’s query type differs; AMX’s BF16-query gate is a separate restriction. AVX2 and FMA are independent feature requirements. Clang AVX2 intrinsics; Clang FMA intrinsics; kv_cache.hpp:2227; amx_attn_iface.hpp:140.

Compatibility does not guarantee speed or bitwise equality

For 64 tokens × 128 dimensions × four queries, both the current BF16 dotter and this straightforward AVX kernel execute 1,024 BF16 dot instructions. Token-lane SIMD removes horizontal reductions and allows K-load reuse, but introduces query broadcasts and long accumulation chains. Use independent accumulators or partial sums to hide latency, and inspect register spills. Sparse and very short pages may favor a scalar or small temporary-row reader over a full vector block.

The layout itself preserves every K bit. FP32 results can differ because the old dotter horizontally reduces partial sums, the new AVX kernel accumulates along dimensions, and AMX has its own reduction ordering. BF16 dot instructions also define subnormal and rounding behavior separately from ordinary FMA. Preserve the existing AVX-versus-AMX PV weight-rounding choices during this migration; changing K storage does not remove that difference. Intel VDPBF16PS; Intel TDPBF16PS; amx_attn_iface.hpp:58.

Detailed implementation design

1. Make K encoding an explicit storage property

Introduce an internal encoding such as row_major_bf16 or vnni_16t_32d_bf16 on each physical KV slot. Select it before the first write and keep it immutable for the book’s lifetime. Initially enable swizzling for supported head-128 slots; retain existing encoding for other geometries. Enable swizzling only after every reader and writer of the physical slot supports it. All books in a sequence should share the policy. A runtime AMX availability check must never determine how already-populated K is interpreted.

Attach encoding to storage, not to a query operation. In this PR, a writer with one query/KV ratio can feed a read-only consumer with another. The mirror writer deliberately ignores the writer’s query ratio. EAGLE’s logical slot zero maps to a different physical slot; its encoding must follow that same remap. Mixed-geometry books require per-slot treatment. model.hpp:2763; kv_cache.hpp:616; kv_cache.hpp:883.

Reuse the current 16-KiB K plane inside the two-plane KV block. Keep byte sizes, 64-byte alignment, page offsets, V storage, and allocator accounting. Move the indexing helper out of the mirror-only compilation guard. There is no need for a third plane, an in-place conversion of live books, or an allocator migration.

2. Replace the contiguous-row contract honestly

A swizzled token cannot expose a contiguous page.k(...).data. Retain that API only for row-major storage, with an encoding check, and migrate production uses to explicit operations:

store_k(slot, head, token, logical_values);       // preserves existing BF16 conversion
read_k_into(slot, head, token, destination);      // bounded reference/test adapter
k_plane_view(slot, head);                        // base, encoding, geometry
copy_k_tokens(dst, src, src_begin, dst_begin, n); // physical slot-aware
fill_hw_k(..., destination);                     // direct layout-aware GOF shuffle

These are proposed internal interfaces, not new public APIs. Production migration sites are save_k_impl, apply_page_tok, the scheduler’s page_info factory, and copy_storage_slot. Test fixtures that directly write K pointers must migrate too. Make accidental canonical interpretation fail clearly. kv_cache.hpp:1570; kv_cache.hpp:2243.

3. Store K once and preserve publication ordering

Take the projection/RoPE result, apply the same BF16 conversion as the current .set(kout), and store its pairs directly into the selected K plane. For already-BF16 results, copy the bits. For other input types, use a bounded local conversion buffer or equivalent conversion in the store loop. Publish mark_k_complete and GOF save credit only after every pair has been written. Preserve the downstream-minibatch dependency notifications. model.hpp:2789; model.hpp:2806.

Each token owns a separate 32-bit pair in every vector row. Use stores that touch only that token’s bytes; do not read-modify-write whole neighboring vectors. Different token writers can share cache lines, so false sharing remains a performance question. Removing the canonical copy saves its contiguous store and the mirror’s source reread; it does not eliminate the scatter.

5. Extract visibility without weakening its semantics

Walk the same token ranges as today to build a 64-bit visibility mask and return the same updated range_hint. Include page.count(), branch/causal visibility, visible versus sw_required, sliding-window positions, and EAGLE’s first-token exception. Then use four 16-bit masks for AVX-512, or eight 8-bit masks for AVX2. Count the active tokens and retain the zero-visible early return. Dense AMX keeps the existing all-64-valid gate. self_attention.hpp:1543; self_attention.hpp:1600.

Mask memory loads as well as scores. Inactive columns may be uninitialized or being written. A full vector load followed by an output mask is insufficient. Use pair-sized masked loads, skip empty blocks, and leave invalid scores at negative infinity. A zero key produces a valid zero score and is not a softmax mask. No reader may infer readiness just from being inside an allocated page.

Reapply the score mask after scale/softcap and before max/exp. In particular, tanh(-infinity) is finite: the current fallback’s use of a sentinel before softcapping cannot by itself establish masked softmax behavior. Include an explicit softcap-mask regression test; handle any existing masking defect as a separately identified correctness change. Preserve the existing AVX PV truncation and AMX PV rounding during the storage migration. self_attention.hpp:1688; kv_cache.hpp:2091.

6. Make token copying layout-aware

The current copy helper assumes a contiguous K token range. That assumption becomes invalid. For a whole same-format page, copying the 16-KiB K plane remains valid. For arbitrary append/defrag ranges, split the move at both source and destination 16-token boundaries, then copy each dimension-pair row’s contiguous run of token pairs.

// Non-overlapping case. Handle overlapping moves separately.
while (remaining) {
  run = min(remaining, 16 - src_token % 16, 16 - dst_token % 16);
  for (s = 0; s < 4; ++s)
    for (dp = 0; dp < 16; ++dp)
      copy_bytes(dst_pair_row(s, dst_token, dp),
                 src_pair_row(s, src_token, dp), run * 4);
  src_token += run; dst_token += run; remaining -= run;
}

Define overlap handling across the entire move, not only within an individual row copy: use a suitable traversal direction or bounded scratch when ranges overlap. Preserve untouched token columns, V’s current pair-copy logic, completion counters, and the extra EAGLE slot. Reject cross-encoding copies by invariant, or use an explicit conversion adapter during rollout. kv_cache.hpp:1951; kv_cache.hpp:1997.

7. Adapt hardware staging and its reconstruction paths

Replace the contiguous-row callback with a typed source descriptor carrying base, token offset, encoding and geometry, or a callback that directly fills the current GOF destination. Preserve the existing hardware destination indexing and change only how logical source elements are read. Use PR3879’s full offset formula, not the older branch’s token-tile stride. Keep an unpack-and-existing-shuffle version as a test oracle or bounded reference fallback. Avoid adding a persistent K scratch allocation to every page_info; that would reintroduce redundant cache storage under a different owner.

The same adapter must serve first populate, staging eviction/reacquisition, and backfill to later shards. Defrag already rebuilds the captured page_info callbacks; rebuild the encoding and token-offset information there too. Preserve staging locks and in-flight credits. The H=128 fused shuffle shown above must pass byte-for-byte comparison against the existing hardware packer. Measure first populate, cold reconstruction and GOFs spanning different source books before deleting the mirror; a recent save does not guarantee locality for those later paths. gof.hpp:206; gof.cpp:190; full.hpp:1200.

8. Define both kernel disable and full rollback

Under a single-K configuration, TRON_AMX_DISABLE=1 can disable AMX while AVX continues to read the same swizzled K. That validates the new fallback but does not restore the old dotter’s timing or reduction tree. Provide a separate process-start layout override that allocates row-major K and uses the old reader for a full rollback. Select it before any cache allocation. Do not change the encoding of populated books when a kernel check fails.

If retaining the current environment variable’s entire old-behavior rollback contract is mandatory, let it select row-major storage at process start and provide a distinct way to force AVX on swizzled storage for testing. Choose and document one contract. Neither contract needs two persistent copies. The current availability result is cached, so it is not a live layout-conversion mechanism. amx_attn.cpp:72.

Determinism is a separate contract. Preserve the current fixed worker-planning behavior. If a reference-output mode must reproduce the old dotter’s reduction order, route it through canonical storage selected at construction or a bounded unpack/reference reader. Add repeated-run and golden-output checks; a native AVX kernel can be repeatable while producing different bits from the old dotter. Bill’s explicit scalar-dispatch gate is a requirement of his branch, not an existing check established for PR3879.

9. Remove the mirror’s allocation and accounting

When the single-K path is complete, remove the extra arena, write-through coherence updates, mirror view offset, null-arena reader cases, and arena byte counters for that path. Keep the existing two-plane hugepage accounting, EAGLE embedding allocation and GOF staging accounting. Replace mirror-coherence tests with primary-encoding tests; do not merely delete their coverage. A temporary explicit mirror mode can remain as an A/B reference during development, without being part of the final single-K storage.

Implementation sequence

  1. Introduce layout-aware accessors with canonical behavior. Migrate production consumers and fixtures; validate unchanged canonical runs.
  2. Add native AVX readers and exact store/copy transforms. Exercise all masks and query types supported by the proposed policy.
  3. Add the direct GOF adapter and slot policy. Prove hardware staging bytes and reconstruction paths, then pass the measured GOF-cost gate before removing the extra copy. Enable the primary swizzled plane behind a process-start option.
  4. Compare single-K with both existing modes. Run model/numerical and workload measurements, then remove the mirror machinery from the selected production path.

Memory is a clear win; runtime needs a complete comparison

For each 64-token/head-128 slot/head, K and V are 16 KiB each. Mirroring adds another 16 KiB. A primary swizzled K restores the two-plane total. Across an entirely mirrored KV allocation of B bytes for K+V, the saving is B/2 bytes of ordinary RAM, or one third of the current 1.5B three-plane payload. Metadata, EAGLE embeddings, GOF staging and HBM are excluded from this calculation. kv_cache.hpp:562; kv_cache.hpp:2227.

At a fixed hugepage budget, page capacity stays unchanged: both designs already allocate two planes in that budget. The saving is the external mirror arena. Holding the total RAM budget fixed may allow later pool resizing, but a 50% increase in page capacity is not an automatic effect of this patch. Moving CPU K out of the hugepage allocator is a separate change.

The 64-cache-line store footprint is 4 KiB of addressed lines for a 256-byte token. It is not a claim of 4 KiB of DRAM traffic on every write: adjacent tokens reuse those lines. A complete page still holds only 16 KiB of K. Small reads and writes are where the transpose’s locality tradeoff needs scrutiny.
